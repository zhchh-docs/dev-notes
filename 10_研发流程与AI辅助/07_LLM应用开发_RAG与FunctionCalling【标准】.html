LLM 应用开发：RAG 与 Function Calling

标准 定位：RAG 与 Function Calling——把大模型接入业务的两条工程路径

大模型本身只有预训练知识，要在业务里用起来靠两条路径：RAG 把私有知识检索出来喂给模型（解决"不知道"），Function Calling 让模型输出结构化意图、由你的后端校验并执行（解决"不能动"）。本篇按"核心模型 → 分场景代码 → 链路图 → 30 分钟可跑通 Demo → 分阶段坑与面试详答"展开，并诚实标注 Demo 与生产之间的差距。

1简介与阅读指引

1.1 定位

本篇讲的是把"会说话的大模型"变成"能查私有资料、能调业务接口"的应用的两条工程路径：RAG（检索增强生成）解决"模型不知道私有知识"，Function Calling（函数调用）解决"模型不能动真实系统"。两条路径构成当前 LLM 应用开发的 80% 地图。

1.2 痛点

  • 模型训练有截止时间，企业内部文档、最新数据它一无所知——直接问就是幻觉；
  • 模型只能吐文字，不能查库、下单、调接口——"会聊天的 demo"落不了地；
  • 大多数教程停在"调一次 API"，不讲多轮状态管理、检索调参、工具执行权这些真正决定能不能上生产的工程问题。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
想把大模型接入业务系统（知识库问答、智能工单、助手类功能）想训练/微调模型 → 属算法方向，本篇不涉及
面试要讲清 RAG / Function Calling 的链路与边界只想在聊天框里用好模型 → 《大模型应用》
评审团队里"AI 功能"的技术方案AI 辅助写代码的工作流 → 《AI 辅助开发》

2核心模型

本章按依赖顺序讲五个核心模型：先会"调一次 API"（2.1），再理解它的两个硬约束——Token 与窗口（2.2）、无状态（2.1 内）；然后是让输出可控的提示词工程（2.3）；最后是两条增强路径 RAG（2.4）与 Function Calling（2.5）。2.4 和 2.5 是本篇的主菜。

2.1 Chat Completions 与 messages 结构

一次对话就是一组带角色的 messages 数组，模型根据上下文补全下一条。角色四种：system（定人设/约束）、user（用户）、assistant（模型历史回复）、tool（工具返回，见 2.5）。

关键约束——API 是无状态的：服务端不记你的聊天，多轮对话要自己把历史 messages 全量带上。"第二轮失忆"的 bug 全部源于忽略这一点。

协议差异要注意：OpenAI 原生是 POST /v1/chat/completions（DeepSeek 等兼容此格式）；Anthropic Claude 原生是 POST /v1/messages，且 system 是顶层参数而非 messages 里的角色——两者不互通，要统一调用需经 OpenAI 兼容网关（接口字段以最新官方文档为准）。工程含义：选型时先确认"走兼容网关还是分头适配"。

2.2 Token 与上下文窗口

输入和输出都按 token 计费、都消耗上下文窗口。窗口决定一次能塞多少内容，由此推出两个工程约束：①RAG 召回的片段不能贪多——top-k 太大既撑爆窗口又推高成本还稀释注意力；②超长文档分析要么选长上下文模型，要么靠 RAG 只送相关片段。成本意识从第一行代码就要有：messages 是全量重发，多轮长对话的成本是平方级增长的。

2.3 提示词工程：让输出稳定可解析

用结构化、可复用的指令模板稳定模型输出。五要素：角色、任务、约束、输入数据、输出格式——要 JSON 就明确给 schema 或示例。三个高频技巧：few-shot（给一两个输入输出示例，格式遵从性立竿见影）、先想后答（要求模型先列分析再给结论，复杂问题准确率提升）、限定范围（"只依据以下资料回答，没有就说不知道"——RAG 场景的标配约束）。工程化要点：提示词当代码管理——版本化、可测试，改一版跑一轮测试集，不要在聊天框里凭感觉改。

2.4 RAG 检索链路：把"记忆"问题变成"检索"问题

RAG 分离线与在线两段：

  • 离线：文档 → 切块（chunk，粒度是召回质量的第一变量）→ Embedding 向量化 → 存入向量库（PG 向量扩展 / FAISS 等）；
  • 在线：用户问题用同一个 Embedding 模型向量化（保证同空间可比）→ 向量库按相似度召回 top-k 片段 → 作为"参考资料"拼进 messages（system 里加"只依据资料回答"）→ 模型据资料生成。

为什么 RAG 能抑制幻觉：模型从"凭参数记忆编"变成"照着给定资料答"，且答案可溯源到具体文档。为什么不需要重训模型就能更新知识——换文档、重新入库即可，这是 RAG 相比微调的最大工程优势（对比详见 8.2）。完整链路图见第 5 章。

2.5 Function Calling：模型点菜，后端炒菜

模型不真的执行任何代码——它只输出"要调哪个函数、参数是什么"的结构化 JSON，真正的执行在你的应用里。闭环四步：

  1. 声明：请求里带 tools，每个工具给 name、描述、参数 JSON Schema（描述写得好坏直接决定模型会不会正确用它）；
  2. 决策：模型判断该不该调工具，返回 tool_calls（不是最终回答）；tool_choice 参数可控制行为：auto（模型自定）/ required（必须调）/ 指定某工具 / none（禁用）；
  3. 执行：你的代码校验参数后执行真实查询；把结果作为 role:'tool' 消息再发一次；
  4. 收口：模型基于工具结果生成面向用户的自然语言回答。

协议差异：Claude 原生不用 tool_calls/role:tool，而是 assistant 消息里的 tool_use 内容块、user 消息里的 tool_result 内容块来回灌（以最新官方文档为准）。安全铁律：tool_calls 里的参数必须经 schema 校验后才能执行——模型会编造参数值，直接信任等于把 SQL 注入的门重新打开。

2.6 两条路径怎么选：不是二选一

真实应用往往同时用两条：智能工单助手 = RAG（检索历史工单与内部文档）+ Function Calling（查订单状态、创建工单）。判断口诀：问题是"知识性的"→ RAG；问题是"操作性的"→ Function Calling；混合问题 → 先检索再调工具再生成。两条路径的位置关系见第 5 章图 1。

3核心 API 与代码（按场景）

四个场景从最小调用到完整闭环，代码全部可跑（配 Node 18+ 与任一 OpenAI 兼容 API Key）。

3.1 场景一：最小对话请求

const res = await fetch('https://api.openai.com/v1/chat/completions', {
  method: 'POST',
  headers: { 'Authorization': `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
  body: JSON.stringify({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '你是需求管理助手，只依据提供的资料回答。' },
      { role: 'user', content: '本期 Sprint 包含哪些需求？' }
    ],
    temperature: 0.2 // 低温度：要稳定、少发挥
  })
})
// ❌ 注意：API_KEY 只能存在于后端。出现在前端 = 任何人打开 DevTools 就能盗刷你的账户

temperature 怎么调：知识问答/结构化输出用低值（0~0.3，求稳定）；创意生成用高值（0.7+）。生产环境给模型调用加超时与重试（网络失败是常态）。

3.4 场景四：Function Calling 闭环

// 1) 声明工具：查需求列表
tools = [{ type: 'function', function: {
  name: 'list_requirements',
  description: '按状态查询本期需求列表',        // 描述写给模型看：它据此决定何时调用
  parameters: { type: 'object', properties: { status: { type: 'string' } } }
}}]
// 2) 模型返回 tool_calls（不是最终回答），应用执行真正的查询
// 3) 把执行结果作为 role:'tool' 再发一次，模型据此生成自然语言回答
messages.push({ role: 'assistant', tool_calls: res.tool_calls })
messages.push({ role: 'tool', tool_call_id, content: JSON.stringify(realData) })
// 再次请求 → 得到最终面向用户的回答

// 4) 执行前必须校验参数——模型会编造参数值
const args = JSON.parse(tool_call.function.arguments);
if (!ALLOWED_STATUS.includes(args.status)) throw new Error('非法参数');  // schema/白名单校验

职责分界：模型负责"决定调什么、传什么"（自然语言 → 结构化意图），你的后端负责"校验并执行"（真实系统操作）。执行权永远在后端——这句话是 Function Calling 安全设计的全部。

4进阶知识点【进阶】

首次学习可整章跳过。本章讲检索质量优化、协议适配与成本工程。前置：已跑通第 6 章 Demo。

4.1 Rerank：召回之后的二次精排

向量检索（双塔/近似检索）快但粗——它比的是"整体语义相似"，经常召回"话题相关但答非所问"的片段。Rerank 用 cross-encoder 类模型（如 bge-reranker、Cohere Rerank，选型以最新官方文档为准）把"问题+片段"成对精算相关性，对召回的 top-20 重排出 top-3 再拼 prompt。取舍：Rerank 显著提升相关性，但增加一次模型调用延迟——只对"召回候选"做，不对全库做。

4.2 多协议适配：兼容网关 vs 分头适配

2.1 说过 OpenAI 与 Claude 格式不互通。两种工程方案：兼容网关（自建或用网关层把 Claude 转成 OpenAI 格式，业务代码只写一种）——省心但多一跳、丢特性；分头适配——为每家写 adapter（统一内部的 messages 表示，出口各自转换）——灵活但维护面大。选型依据：只用一家 → 直连；多模型路由/切换 → 网关或 adapter 层。无论哪种，把"协议适配"收敛在一个模块里，不要散在业务代码里。

4.3 tool_choice 与工具调用的可控性

tool_choice 四档（auto / required / 指定工具 / none）对应不同产品形态：聊天助手用 auto（模型自己判断）；结构化抽取用 required（强制走工具，输出格式天然稳定）；流程固定的场景直接指定工具（把模型当"参数填充器"用，确定性最高）；纯闲聊入口用 none 省成本。从 auto 收紧到指定，确定性递增、灵活性递减——按业务对"答错"的容忍度选。

4.4 成本工程：token 预算的三个阀门

①输入阀门：top-k 截断、历史压缩（摘要代替全量）、片段去重；②模型阀门：简单请求路由小模型（意图分类/改写），复杂推理才上大模型；③输出阀门：max_tokens 限长 + 提示词里限定输出结构。监控口径：每次调用记录 prompt/completion token 数，按功能聚合——没有这个，月底账单会教你做人。

5架构与流程图

5.1 两条增强路径的位置关系

图 1 RAG 与 Function Calling 两条增强路径（示意）

读图要点：RAG 喂给模型的是信息（改变"它知道什么"），Function Calling 从模型拿走的是意图（改变"它能做什么"）。两者方向相反、可组合：混合型问题走"检索 → 调工具 → 生成"三段式。

5.2 RAG 在线问答链路（含异常分支）

图 2 RAG 一次问答的完整链路（含空召回分支）

  • 1 问题向量化：用与文档同一个 Embedding 模型转向量，保证同空间可比；
  • 2 相似度召回：取 top-k 最相关片段——这是"私有知识"的来源，也是质量瓶颈所在；
  • 3 拼上下文：片段 + 问题组装 messages，system 要求"只依据资料回答"；
  • 4 生成：模型基于片段作答而非凭参数记忆，幻觉显著减少且可溯源。

要点：RAG 把"记忆"问题变成"检索"问题——不必重训模型即可更新知识，答案可溯源到具体文档。异常分支：召回相似度低于阈值时，正确行为是直答"资料里没有"，而不是让模型自由发挥——空召回分支的设计质量，决定用户信不信任你的 AI 功能。

5.3 Function Calling 闭环时序（文字版）

  1. 应用 → 模型：messages + tools 声明；
  2. 模型 → 应用：tool_calls（工具名 + 参数 JSON）——此时没有任何事发生；
  3. 应用内部：schema/白名单校验参数 → 执行真实操作（查库/调接口）→ 拿到结果；
  4. 应用 → 模型：追加 assistant(tool_calls) + tool(结果) 消息，再次请求；
  5. 模型 → 用户：基于真实数据的自然语言回答。

异常分支：参数校验失败 → 不调工具，把校验错误作为 tool 消息回灌，让模型修正参数重试一次；重试仍失败 → 降级为人工处理提示。模型不会真的连数据库——它只是"填单员"。

6最小可运行 Demo

性质声明：这是自学 + 自建 demo，非生产环境项目——目标是 30 分钟跑通"检索 + 生成 + 工具调用"完整链路。生产化差距见 6.5。

保存为 llm-demo.mjs（Node 18+，npm i openai，设置环境变量 OPENAI_API_KEY）：本地知识库（3 条需求文档）+ RAG 问答 + 一个"查需求详情"工具。

6.1 完整代码

import OpenAI from 'openai';
const client = new OpenAI();                       // 读 OPENAI_API_KEY 环境变量

// ===== 离线：知识库切块 + 伪向量检索（Demo 用关键词匹配代替真实向量库）=====
const docs = [
  { id: 'REQ-101', text: '需求101：登录页支持手机号+验证码登录，验证码60秒有效期。' },
  { id: 'REQ-102', text: '需求102：订单列表支持按状态筛选，默认展示待支付订单。' },
  { id: 'REQ-103', text: '需求103：个人中心展示近30天的积分变动明细。' },
];
function search(question, topK = 2) {              // 生产环境换真向量库（见 6.5）
  return docs
    .map(d => ({ ...d, score: matchScore(question, d.text) }))
    .sort((a, b) => b.score - a.score).slice(0, topK)
    .filter(d => d.score > 0);
}
function matchScore(q, text) {                     // 极简相关性：关键词重合数
  return q.split('').filter((_, i) => text.includes(q.slice(i, i + 2))).length;
}

// ===== 工具声明：查需求详情 =====
const tools = [{
  type: 'function',
  function: {
    name: 'get_requirement',
    description: '按需求编号查询需求的详细内容',
    parameters: { type: 'object', properties: { req_id: { type: 'string' } }, required: ['req_id'] },
  },
}];
function execTool(args) {                          // 执行权在后端 + 参数白名单校验
  if (!/^REQ-\d{3}$/.test(args.req_id)) throw new Error('非法需求编号');
  return docs.find(d => d.id === args.req_id)?.text ?? '未找到该需求';
}

// ===== 主流程：RAG 拼装 → 调用（含工具闭环） =====
async function ask(question) {
  const hits = search(question);
  const context = hits.map(h => `[${h.id}] ${h.text}`).join('\n') || '（资料库中无相关内容）';
  const messages = [
    { role: 'system', content: `你是需求管理助手。只依据以下资料回答，资料没有就说不知道：\n${context}` },
    { role: 'user', content: question },
  ];
  let res = await client.chat.completions.create({ model: 'gpt-4o-mini', messages, tools });

  // Function Calling 闭环：模型可能要求调工具
  while (res.choices[0].finish_reason === 'tool_calls') {
    for (const call of res.choices[0].message.tool_calls) {
      const args = JSON.parse(call.function.arguments);
      let result;
      try { result = execTool(args); } catch (e) { result = `参数校验失败：${e.message}`; }
      messages.push(res.choices[0].message);                       // assistant(tool_calls)
      messages.push({ role: 'tool', tool_call_id: call.id, content: result });  // 回灌结果
    }
    res = await client.chat.completions.create({ model: 'gpt-4o-mini', messages, tools });
  }
  return res.choices[0].message.content;
}

console.log(await ask('验证码登录的有效期是多久？'));   // 走 RAG：命中 REQ-101
console.log(await ask('查一下 REQ-103 的详情'));        // 走 Function Calling
console.log(await ask('公司年假有几天？'));             // 空召回：应回答"资料里没有"

6.2 逐段解析

  • search()：Demo 用关键词重合度模拟向量检索——链路与真实 RAG 完全一致（检索 → 拼 prompt），只是相似度算法换了；生产换 FAISS/PG 向量即可，其余代码不动；
  • system 里的"没有就说不知道"：空召回分支（第三个问题）的守护约束——运行结果里它会如实回答不知道，而不是编一个年假天数；
  • while (finish_reason === 'tool_calls')：闭环循环——模型可能连续要求调多个工具，直到给出最终回答；
  • execTool 的正则白名单：模型如果编造 REQ-99999 或传注入字符串，在执行前就被拦下——2.5 的"执行权在后端"落到代码上就是这一行。

6.3 运行结果说明

验证码有效期为 60 秒。（来源：REQ-101）          ← RAG：答案来自检索片段，非模型记忆
REQ-103：个人中心展示近 30 天的积分变动明细。      ← Function Calling：工具返回真实数据
抱歉，资料库中没有关于年假的信息。                ← 空召回分支：诚实承认，未幻觉

6.4 与真实生产的差距（诚实清单）

  • 检索：关键词匹配 → 真实 Embedding 向量库 + 相似度阈值 + Rerank；
  • 规模：3 条文档 → 企业级文档量需要分块策略、增量入库、权限过滤（谁能检索哪些文档）；
  • 工程：无评测集（回答质量怎么回归测试）、无监控（token 消耗/延迟/失败率）、无流式输出体验；
  • 安全：单机 Key 明文 → 密钥收敛后端代理 + 调用审计。

6.5 生产改造扩展方向

  1. 把伪检索换成真实 Embedding + 向量库，观察召回质量差异，练习调 chunk 大小与 top-k；
  2. 加流式输出（stream: true），体验打字机效果的实现方式；
  3. 给 Demo 加一层"后端代理"：前端只调你自己的 /api/ask，Key 永不出后端——这是上生产的第一个硬要求。

7常见坑 & Debug

按"接入 → 开发 → 上线"三阶段分组，五要素格式。

7.1 接入阶段

坑 1：API Key 放前端

  • 现象：功能能用，几天后账户余额被刷光；
  • 根因：浏览器里的一切（源码、网络请求）对用户可见，Key 写在前端等于公开；
  • 复现：打开自己页面的 DevTools → Network，看请求头；
  • 修复：Key 只存后端环境变量，前端调你自己的 /api/ask 代理接口；已泄漏的 Key 立即作废；
  • 规避：code review 硬规则——前端目录出现 sk- 开头的字符串直接打回。

7.2 开发阶段

坑 2：第二轮提问模型"失忆"

  • 现象：第一轮说的内容第二轮它不知道了；
  • 根因：Chat Completions 无状态，每次请求只看当次传入的 messages；
  • 复现：两次独立调用，第二次不带上文；
  • 修复：服务端维护会话历史，每次全量带上（3.2 代码）；超长会话做截断/摘要；
  • 规避：把"管理 messages 历史"当作和"管理数据库连接"同级别的工程任务。

坑 3：RAG 召回不相关，答非所问

  • 现象：明明库里有答案，模型却答错或答得含糊；
  • 根因：召回环节没把对的片段送进上下文——切块太大（一个 chunk 塞了多个主题，相似度被稀释）或太小（语义不完整）、top-k 太小漏掉、太大淹没、Embedding 模型与文档语言/领域不匹配；
  • 复现：打印每次召回的片段人工检查——RAG 调试的第一原则：先看检索到了什么，再怪模型；
  • 修复：调 chunk 大小（经验起点 300~500 字 + 重叠）、加相似度阈值、top-k 控制在 3~5 段、必要时上 Rerank；
  • 规避：建立一个小评测集（20 个问题+期望命中的文档），检索改动后跑一遍防回归。

坑 4：直接信任模型输出的参数/代码

  • 现象：tool_calls 里的参数没校验直接执行，模型编造的 ID/数值引发业务异常甚至注入；
  • 根因：把"模型输出结构化 JSON"误解为"输出可信"——结构化≠正确；
  • 复现：让模型传一个不存在的需求编号；
  • 修复：所有工具执行前过 schema/白名单校验（6.1 的 execTool），失败回灌让模型重试；
  • 规避：模型产出与用户输入同级对待——都是不可信输入。

7.3 上线阶段

坑 5：把模型结论当权威

  • 现象：模型说的版本号/API/行为与实际不符，照抄出事故；
  • 根因：训练截止时间 + 幻觉概率；
  • 修复/规避：版本、参数、行为以官方文档与本地实测为准；面向用户的 AI 功能必须加"来源标注 + 人工复核路径"，不要让 AI 答案成为唯一决策依据。

坑 6：没做成本与超时控制

  • 现象：月底账单爆炸；或模型偶发响应 30 秒拖死整个接口；
  • 根因：多轮全量重发 + 无 max_tokens + 无超时重试（4.4 的三个阀门一个都没装）；
  • 修复：加 max_tokens、请求超时与有限重试、按功能的 token 监控；
  • 规避：LLM 调用当外部依赖对待——超时、降级、熔断一个都不能少（对应 09 模块的思路）。

8重点讲解

Q1：RAG 和微调（Fine-tuning）怎么选？

参考答案：先看知识变化的频率与溯源要求。RAG 解决"知识更新与私有化"：文档随时增删、答案可溯源到具体段落、无需训练成本——知识库问答、文档助手的首选；微调解决"行为与风格"：让模型学会特定的输出格式、领域话术、任务模式——但它不适合灌知识（训练贵、更新慢、易过拟合且无法溯源）。

口诀：知识问题用 RAG，行为问题用微调，两个都要就 RAG + 轻度微调组合。追问：为什么微调不适合灌知识？——知识存在参数里无法定位更新，新增一条文档要重训；而 RAG 里知识在外置库中，增删改查即生效。

Q2：Function Calling 里，为什么工具的执行权必须在应用侧？

参考答案：三层原因。①能力：模型只能生成文本，没有运行时，"执行"物理上就只能由应用完成；②安全：模型会编造参数（幻觉），执行前必须 schema/白名单校验——执行权在应用侧才有校验的落点，直接信任等于把用户输入注入的老问题在 LLM 层重演；③审计：真实系统操作需要鉴权、限流、日志，这些都长在应用侧。

口诀：模型是"填单员"——决定调什么工具、填什么参数；应用是"柜员"——验单、执行、反馈。单可以由 AI 填，章必须人来盖。

Q3：为什么 RAG 能抑制幻觉？它消灭幻觉了吗？

参考答案：抑制的机制：RAG 把生成约束从"凭参数记忆自由发挥"改为"依据给定资料作答"，system 里再叠加"资料没有就说不知道"——模型的输出空间被收窄到"资料内容 + 忠实转述"，编造概率显著下降；同时答案可溯源（引用了哪个片段），错了能定位。

但没有消灭：模型仍可能"资料里有 A，它答成 A 的变体"（忠实性偏差）、或资料互相矛盾时选错。所以工程上还要：答案附引用来源、低相似度走"直答没有"分支、关键场景保留人工复核。幻觉管理是概率压低 + 后果兜底，不是消灭。

Q4：RAG 召回质量差，你的调参顺序是什么？

参考答案：先定位再调参——打印召回片段人工检查，区分"没检索到"还是"检索到了但模型没用好"。

检索侧（最常见），按顺序调：①chunk 大小与重叠（300~500 字起步，一块一个主题）；②top-k 与相似度阈值（k=3~5，阈值过滤垃圾召回）；③Embedding 模型与领域/语言匹配度；④上 Rerank 精排。生成侧：system 是否强约束"只依据资料"、片段是否带来源标注、资料冲突时给模型裁决规则。兜底：空召回直答"没有"。

追问：怎么证明你的调参有效？——建评测集（问题 + 期望命中片段/期望答案），每次改动跑回归。没有评测集的 RAG 调参 = 凭感觉。

Q5：自测 5 问

  1. messages 的四种角色各干什么？API 无状态意味着什么工程责任？
  2. RAG 离线与在线各做哪几步？为什么问题向量化要用"同一个 Embedding 模型"？
  3. Function Calling 闭环四步？"执行权在后端"对应哪行代码？
  4. tool_choice 四档分别适用什么产品形态？
  5. RAG 抑制幻觉的机制是什么？为什么说"抑制"而不是"消灭"？
