代码评审与协作流程

标准 定位：分支策略 / PR 门禁 / 人机分工 / AI 辅助评审

代码评审（Code Review）是团队保证质量、共享知识的核心环节。它不只是"挑错"，而是通过分支与 PR/MR、明确检查清单、聚焦关键问题，让变更可控可追溯。本页讲分支策略、PR AI AI 辅助评审的落地。

1简介与阅读指引

1.1 定位

代码评审（Code Review）是"任何改动合入主干前，由同伴审查"的协作机制——完整链路：分支隔离改动 → 提 PR/MR → 自动检查 + 人工评审 → 合并。它解决三件事：质量（每个变更都被看过）、追溯（被记录、可回滚）、知识共享（没有人的代码只有他自己懂）。本篇按"分支策略 → PR 流程 → 评审怎么做"展开，最后给出一套可直接落地的团队评审规范。

1.2 痛点

  • 直接往主干提交：未审过的改动进主干，出问题难定位、难回滚；
  • 评审走形式："LGTM" 一扫而过——门禁存在但没起作用；
  • 评审变成挑错会/口水战：作者与评审者对立，讨论离题万里；
  • 大 PR 扔过来："有时间帮我看下"——3000 行的 diff，谁看谁头大，最后没人认真看。

1.3 适用 / 不适用场景

1.4 学习目标：读完本篇你能

  1. 为团队选择合适的分支模型（GitHub Flow / Trunk-Based / Git Flow），说清合并策略的取舍；
  2. 写出合格 PR：改动说明、需求关联、自查清单——让评审者 10 分钟内可评审；
  3. 执行"机器管风格、人管逻辑"的分工，用好评审检查清单与意见分级；
  4. 把 AI 辅助评审放在正确位置：第二双眼睛，不是第一双。

2核心模型

评审机制的三个核心模型：分支策略决定改动怎么隔离与合入，人机分工决定评审精力放哪，反馈写法决定评审是协作还是对抗。三者顺序：先有分支策略（2.1），PR 是策略的载体（2.2），然后才是评审怎么做（2.3~2.5）。

2.1 分支策略：主干保护，短分支小步提交

图 2 三种分支模型对比（示意）

共同底线是主干保护：任何改动经 PR 进主干，避免长生命周期的大分支（分支活得越久，合并冲突与"最后一周大爆炸"越猛）。合并策略三选一：merge 保留完整分支历史；squash 把多条提交压成一条、主干历史干净（小团队最常用）；rebase 得到线性历史。配套受保护分支做硬门禁："必需 reviewer + CI 必过"由平台强制，不靠自觉。

2.2 PR / MR：评审的载体

PR（GitHub）/ MR（GitLab）不只是"请求合并"，它是评审现场：改动 diff、改动说明（为什么改）、需求关联（对应哪张任务单）、CI 状态、评审记录——全部沉淀在一个链接里。合格的 PR 自带上下文：评审者不需要找人来问"这个改动是干嘛的"（描述模板见 6.2）。

2.3 评审的人机分工：机器管风格，人管逻辑

图 3 评审中的人机分工（示意）

分工原则：机器管机械项——lint、格式、类型、单测、构建、安全扫描（速度快、不疲劳、100% 覆盖）；CI 绿了才进人工评审。人只聚焦机器判断不了的：设计是否合理、边界与异常、可读性、有没有埋坑。评审者别在空格和引号上消耗精力——那些事 lint 比你快也比你有耐心。

2.4 AI 辅助评审：第二双眼睛，不是第一双

AI（Cursor/ChatGPT 等）的评审定位：先扫 diff 找潜在问题，人工复核后采纳。它擅长明显问题——未处理的边界、命名不规范、可疑的空值路径；它不可靠的地方——业务上下文（不知道哪个改动碰了雷区）、误报与漏报并存。AI 提的问题必须人工确认后才成为正式评审意见；AI 漏的人照样看。流程见第 5 章图 4。

2.5 评审反馈的写法：对事不对人的机制化

  • 具体可执行：指出"这里边界情况会怎样"，而不是"你写错了"；给方向而不是给成品的重写代码——大段代笔会让评审变成替代劳动，作者也学不到东西；
  • 分级：【必须改】阻塞合并；【建议】可后续优化；【提问】只是想理解。作者可以优先只处理必须改，讨论不被淹没；
  • 对事不对人：评论代码不评论人——"这段没处理空值"而不是"你怎么又忘了判空"。机制化做法见 4.4。

3核心流程（一次 PR 的生命周期）

图 1 一次 PR 的流转（示意）

3.1 开分支：一个分支一件事

从最新主干切出 feature 分支，命名带任务号（feature/ORD-142-export）。一个分支只做一个需求——夹带改动的 PR 是评审质量崩坏的第一步。

3.2 提 PR：自带上下文

## 做了什么
订单列表新增服务端分页导出（对应任务单 ORD-142）
## 为什么这样做
数据量 10 万行级，前端导出会内存溢出，改为后端流式写盘
## 自查清单
- [x] 单测覆盖空结果/超大数据量分支
- [x] 导出字段已过脱敏规则
- [x] 未改动订单查询主流程（只新增了导出查询）
## 评审提示
重点看 stream 写盘的错误处理分支

"评审提示"栏是效率神器：作者主动指出"哪里最值得看"，评审者把有限的注意力花在刀刃上。

3.3 CI 门禁 → 人工评审

  1. PR 触发 CI：lint + 类型检查 + 构建 + 测试（+ 安全扫描）；红了先修，评审者不看红 PR；
  2. （可选）AI 初筛：按检查清单扫 diff，输出问题清单；
  3. 人工评审：对照检查清单（6.1）逐项过，意见按【必须改/建议/提问】分级；
  4. 作者回应每条意见（采纳/解释为什么不行），改完 re-request；
  5. 评审通过 → 合并（按团队选定的合并策略）→ 主干始终是"被审过、CI 绿"的状态。
流程灵魂：合并进主干的东西默认可信（可发布、可回滚）——这就是门禁存在的意义。门禁越松，主干越像赌场。

4进阶知识点【进阶】

首次学习可整章跳过。前置：完整提过并评审过若干 PR。

4.1 小 PR 原则：评审质量与 diff 大小强相关

研究与实践共识：超过 400 行的 diff，问题发现率骤降——评审者只剩耐心看前 200 行。工程对策：需求拆小提交；同一需求的大改动分步提（先基础层后应用层）；重构与功能改动分开成 PR，绝不含糊。作者自查："这个 PR 我自己愿意认真看完吗？"不愿意，就拆。

4.2 评审时限（Review SLA）

评审积压是协作流程最常见的隐形杀手——作者等评审的時間比写码还长。给评审定 SLA 并写进规范：常规 PR 24 小时内首次响应（哪怕只是"排上了，明早看"）；紧急 hotfix 走绿色通道（+电话提醒）。SLA 的前提是 PR 尺寸可控（4.1）——没人能对 3000 行 PR 做 24 小时响应。

4.3 受保护分支与 CODEOWNERS：让门禁自动找对人

  • 受保护分支：平台配置"禁止直推、必需 N 个 approve、CI 必过"——把"共识"变成"机制"；
  • CODEOWNERS：按目录声明Owner（如 src/api/ @backend-team），PR 自动请求对应 Owner 评审——改动自动找到最懂的人，新人不用问"该找谁审"。

4.4 评审心理：把"对事不对人"机制化

靠提醒没用，靠机制有用：①评论以问题或建议句式开头（"这里如果 X 会怎样？""考虑过 Y 吗？"）而非判断句；②作者对每条意见必须公开回应（哪怕"不改，因为——"），避免意见被无声吞掉；③分歧升级为拉群讨论或过规范文档，不在 PR 评论里打口水战；④评审者养成"先找一处值得肯定的点"的习惯——评审的目的是让代码更好，不是让作者难受。

6最小可交付产物

团队评审规范一页纸，四份模板照抄即用：

6.1 评审检查清单（评审者视角）

□ 是否只做本需求的改动（无夹带）
□ 边界/空值/异常分支是否处理
□ 命名与可读性是否达标
□ 是否有测试、是否跑过
□ 安全与权限是否被破坏（导出/接口暴露/密钥）
□ 破坏性变更有没有周知（接口/配置/依赖升级）

6.2 PR 描述模板（作者视角）

见 3.2 的五段结构：做了什么 / 为什么 / 自查清单 / 评审提示 / 关联任务号。放进团队的 PR 模板配置（GitHub 的 .github/pull_request_template.md），新建 PR 自动带出。

6.3 意见分级标签

【必须改】阻塞合并：正确性/安全/规范的硬伤
【建议】   不阻塞：更优写法，作者自行决定
【提问】   不阻塞：评审者想理解设计意图
回应规则：作者对每条意见公开回应（采纳或说明理由）

6.4 时限与保护配置

  • 评审 SLA：常规 PR 24 小时内首次响应；紧急 hotfix 电话提醒走绿色通道；
  • 受保护分支：禁止直推 + 至少 1 个 approve + CI 全绿；
  • CODEOWNERS：按目录绑定 Owner，PR 自动找对人。

6.5 落地对照

规范上线一个月后的典型变化：平均 PR 尺寸下降（作者知道大 PR 拖 SLA）、CI 红的 PR 不再流向评审者、【必须改/建议】分级让合并判断从"吵"变成"看标签"。规范的检验标准只有一个：新人进来第一周就能按规范完成一次合格的评审。

6.6 扩展方向

  1. 接入 AI 辅助评审（图 4 流程）：先在一个低风险目录试点，统计 AI 意见的采纳率再决定推广范围；
  2. 把评审数据（PR 尺寸、评审时长、返工轮次）按月回顾一次，找流程瓶颈；
  3. 对照 Conventional Commits 规范统一提交信息，让 squash 后的主干历史可读可查。

7常见坑 & Debug

按"作者侧 → 评审者侧 → 机制侧"分组，每条五要素。

7.1 作者侧

坑 1：大 PR 难评审

  • 现象：3000 行 PR 挂三天没人动，认真看了的也只评了前 200 行；
  • 根因：评审质量与 diff 大小强负相关（4.1）——大 PR 必然被草草看过；
  • 修复：拆小、分步提；已存在的大 PR 至少补"评审提示"标注重点；
  • 规避：自查"我自己愿意认真看完吗"；重构与功能分开提。

坑 2：夹带改动

  • 现象：导出功能的 PR 里混进了格式化全文件、顺手升级依赖；
  • 根因："顺手改了"没成本——成本转嫁给了评审者和回滚者；
  • 复现：diff 里出现与任务无关的文件；
  • 修复：夹带部分撤出，单独提 PR；
  • 规避：检查清单第一项就是"是否只做本需求的改动"（6.1）。

7.2 评审者侧

坑 3：评审只看风格

  • 现象：意见全是"这里该用双引号"，真正越权的导出字段没人发现；
  • 根因：风格问题最容易看见——但那是 lint 的工作；
  • 修复：按 2.3 分工执行——风格意见直接贴 lint 规则链接，人只看清单上的逻辑项；
  • 规避：把"机器管风格、人管逻辑"写进团队规范一页纸。

坑 4：评审变成挑错会 / 口水战

  • 现象：评论区 60 楼还没吵完命名，作者与评审者已进入对抗状态；
  • 根因：没有意见分级与分歧出口，讨论无限滚动；
  • 修复：用 6.3 的分级标签收敛；分歧过大拉群当面聊或对照规范文档裁决；
  • 规避：4.4 的机制化——建议句式、公开回应、升级路径。

7.3 机制侧

坑 5：AI 评审结论照单全收

  • 现象：AI 说"没问题"就直接合并；或 AI 的每条意见都原样贴给作者；
  • 根因：把 AI 当第一双眼睛——它没有业务上下文，误报漏报并存；
  • 修复：AI 输出仅作为评审参考（图 4），人工确认后才成为正式意见；
  • 规避：定位写死在规范里："AI 是第二双眼睛，不是第一双"；持续统计采纳率校准它的分工边界。

坑 6：门禁形同虚设

  • 现象："特批直推"常态化，主干再次变成没人知道能不能发布的状态；
  • 根因：保护分支没配置，或紧急流程缺绿色通道——逼大家走野路子；
  • 修复：平台配置受保护分支 + 明确 hotfix 绿色通道（4.3/6.4）；
  • 规避：直推行为在回顾会公开盘点——门禁的敌人不是恶意，是"就这一次"。

8重点讲解

Q1：代码评审的目的是什么？

参考答案：三个层次，很多人只知道第一个——①质量：合并前拦截缺陷（但研究表明它单独拦截的缺陷其实有限）；②可追溯：每个变更有记录、可回滚，主干默认可信；③知识共享：让"为什么这么写"沉淀在 PR 里，消除"只有作者懂"的巴士系数——这往往是最有长期价值的。

追问：既然拦截缺陷有限，为什么还要做？——因为它的价值是组合的：质量门禁 + 组织记忆 + 团队标准传播。只按"抓 bug"考核评审，就会把评审做成流水账。

Q2：评审中人和机器（和 AI）怎么分工？

参考答案：机器（CI）管机械项：lint/格式/类型/单测/构建/安全扫描——快、不疲劳、全覆盖；人管判断项：设计合理性、边界与异常、可读性、业务风险；AI 在 CI 与人之间：按清单初筛 diff 找显性问题（未处理边界、可疑空值），输出供人复核采纳。顺序是 CI 绿了才进人工（别让评审者看编译不过的代码），AI 是第二双眼睛不是第一双。

一句话：把评审者的注意力当成最贵的资源，机械工作全部前置消化。

Q3：大 PR 怎么治理？

参考答案：先讲原理——评审质量随 diff 尺寸骤降（400 行是常见经验线），所以治理核心是让大 PR 产生不了：①需求拆小提交；②重构与功能分离；③基础层/应用层分步提。存量的大 PR：补"评审提示"标重点、约定分批评审段落。配套机制：评审 SLA 让小 PR 得到快速响应（正向激励拆小），PR 模板让描述成本降低。

Q4：怎么让"对事不对人"真正落地？

参考答案：机制而非口号——①句式约束：意见以问题/建议开头（"这里如果并发会怎样？"），不用判断句评价人；②分级标签：【必须改/建议/提问】把情绪从"挑错"转为"协作"；③公开回应：作者对每条意见回应，分歧有升级出口（拉群/查规范）而不是评论区打持久战；④评审记录存档：好的评审对话本身就是团队知识库的一部分（衔接 04 篇文档建设）。
