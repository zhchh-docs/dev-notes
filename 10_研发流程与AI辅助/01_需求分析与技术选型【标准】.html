1简介与阅读指引

1.1 定位

本篇讲的是"动手写第一行代码之前"的两类决策：①需求分析——把"老板/客户想要个导出功能"这类模糊诉求，变成可验收的需求清单；②技术选型——把"用什么技术做"变成可辩护的决策（有依据、有记录、可复盘）。这两件事的质量决定了后面所有工时是花在"做对的事"还是"返工"上。

1.2 痛点

  • 拿到需求直接开写，做完才发现理解的和要的不是一回事——最大的浪费是做错东西；
  • 选型全凭"听说很火"或"我熟悉这个"，三个月后才发现生态撑不住、团队接不住、迁移像扒皮；
  • 决策没有记录：半年后"当时为什么选 X？"——没人记得，新方案来了又吵一遍。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要独立负责一个模块/小项目的需求澄清与技术方案已经定型的大团队研发流程 → 《Scrum 敏捷开发》
面试被问"你怎么做需求分析/技术选型"具体技术栈的深度原理 → 对应技术模块各篇
想给团队建立 ADR / 评审等决策机制纯项目管理工具用法 → 官方文档

1.4 学习目标：读完本篇你能

  1. 用需求四层次拆解一条模糊诉求，产出带验收标准的需求清单；
  2. 用五维度 + 加权评分矩阵完成一次选型，并写出一页能存档的 ADR；
  3. 对非功能需求（性能/安全/可用性）给出可量化的指标而不是"要快、要安全"；
  4. 识别需求与选型两个阶段的六类典型坑，并说出对应的规避动作。

1.5 本篇阅读指引

前置知识：无硬性技术前置；但建议有 1~2 个真实项目的经历（参与过需求评审或踩过选型的坑），例子才能对上号。

难度等级：★★☆☆☆（方法论本身不难，难在每次都坚持执行）。

读者建议路线
即将接需求按顺序读第 2、3 章 → 照第 6 章模板产出文档
要定技术方案第 2.3~2.5 节 → 第 5 章流程图 → 第 6 章选型表与 ADR
面试准备第 2、7 章 → 第 8 章重点讲解

第一遍可跳过：第 4 章进阶知识点（非功能需求量化、跨团队谈判、退出成本）。务必动手：第 6 章的产物模板——本篇的价值不在"读过"，而在你下次接需求时真的照着产出三份文档。

本篇不涉及：需求管理工具的用法（Jira/禅道以官方文档为准）；详细的项目排期技术（属 02 Scrum 篇）。

2核心模型

本章按认知顺序讲五个核心模型。2.1~2.2 是需求分析，2.3~2.4 是技术选型，2.5、2.6 是两个进阶视角。贯穿全篇的示例是一条真实感十足的需求："给订单系统加个导出功能"。

2.1 需求的四个层次：先分清你在处理哪一层

层次回答的问题"导出功能"示例
业务需求为什么做？达成什么业务目标？财务月结要人工核对订单，导出能把对账时间从 2 天缩到 2 小时
用户需求谁在什么场景下用它解决什么问题？财务每月 1 号导出上月全部订单明细，用 Excel 透视核对
功能需求系统要做什么？支持按时间范围+状态筛选导出，生成 xlsx，保留筛选条件
非功能需求做得要有多好？10 万行导出 ≤ 30 秒；失败可重试；数据字段脱敏合规

为什么要分层：沟通里的绝大多数扯皮，是因为两个人在不同层次对话——需求方说业务目标（"月底对账太累了"），你听到了功能（"加个导出按钮"），中间的用户场景没人确认。四层拆解就是强制把对话拉到同一层。

2.2 需求三问：验收标准是分水岭

任何一条需求过三问：①为什么做（对应哪个业务目标/痛点，做不成会怎样）；②为谁做（具体用户与场景，出现频率）；③做成什么样算完成（验收标准）。

验收标准是需求的分水岭：写得出"什么样算完成"的才是需求，写不出的只是愿望。示例：❌"导出要快" → ✅"10 万行订单导出耗时 ≤ 30 秒（P95），超时有进度提示"。验收标准同时是开发的自测清单和测试用例的来源——它写不出来，后面所有人都只能猜。

2.3 选型五维度：评估一个候选技术到底看什么

维度关键问题常见误判
技术适配解决我们这个问题合适吗？（不是"它强不强"）拿锤子找钉子：因为想用某技术而找场景
团队能力团队现在/半年内能接住吗？招人容易吗？高估学习能力：demo 会跑 ≠ 生产能维护
生态成熟度文档、社区、周边、长期维护方靠谱吗？只看 GitHub star，不看 issue 响应与发版节奏
总成本学习 + 开发 + 运行 + 迁移 + 商业授权只算开发工时，漏了运维与 license 成本
退出成本一年后要换掉它，代价多大？默认"不会换的"——恰恰最需要评估这条

选型建议：新项目优先成熟方案，不为"轻量/新潮"牺牲可维护性；老项目改造先算迁移成本与团队熟悉度。没有银弹——每个方案都有适用场景和代价，选型是把取舍讲清楚，而不是找到完美答案。

2.4 决策的两个工具：评分矩阵与 ADR

加权评分矩阵：给五个维度按项目情况分配权重（如团队适配 30%、生态 25%……），候选方案逐项打分（1~5），加权求和。它的价值不在分数本身，而在打分过程逼你把模糊感觉拆成具体依据，也把讨论从"我喜欢 A"变成" A 在退出成本上为什么得 2 分"。

ADR（Architecture Decision Record，架构决策记录）：一页纸存档一个决策——背景（为什么现在要决策）/ 候选方案 / 决策结果 / 理由与取舍 / 后果（接受什么代价）。它解决的是"半年后没人记得为什么"，同时让后来者明白当时的约束（约束变了，决策可以重开——ADR 不是判决书，是会议纪要）。

2.5 Spike：用最小实验代替争论【进阶】

两个候选吵不出结果时，别开会了——各花半天到两天做一个 Spike（探针实验）：用候选方案实现最关键的那 10%（通常是性能瓶颈或集成难点），拿数据说话。Spike 代码是一次性实验品，写的时候就要接受扔掉；产出物是结论和数据，不是代码。

2.6 需求变更与技术债【进阶】

需求一定会变——把"拒绝变更"当目标注定失败。工程做法是给变更定价：任何变更先回答"改哪里、影响多少工时、牺牲什么"（范围/时间/资源三角），再由需求方决策。选型同理：评估时就要记录"这个选择欠了什么债"（如选了某轻量框架，将来并发上来要重写网关），债可以欠，但要记账。

3实操流程（三阶段）

从接到模糊诉求到开工写码，完整走三阶段。每阶段有明确产物，产物是流程的锚——没有产物的流程会议都是闲聊。

3.1 阶段一：需求澄清（产物：需求清单表）

  1. 收集：拿到原始诉求，别急着评判，先记录；
  2. 澄清：带着问题清单找需求方——8 个高频问题：
    • 这个功能给谁用？多久用一次？（判断投入级别）
    • 现在没有它时大家怎么做的？（现状即底线方案）
    • 什么场景下会用到它的哪些字段/能力？（拉细节）
    • 做到什么程度算完成？（逼验收标准）
    • 不做的后果是什么？（验证优先级）
    • 有没有截止时间/合规硬约束？
    • 数据量级多大？（非功能需求的输入）
    • 这事儿谁说了算？（确认验收人）
  3. 拆解：按 2.1 四层次整理成需求清单表（编号/层次/描述/优先级/验收标准/验收人）；
  4. 确认：清单发需求方书面确认——书面确认是需求阶段的唯一防线，口头共识约等于没有共识。

3.2 阶段二：方案与选型（产物：对比表 + ADR）

  1. 列候选：2~4 个候选（通常含"自己造"与"用现成"两个端点）；
  2. 定权重：按 2.3 五维度，结合项目实际分权重（内部工具重团队能力，对外产品重生态与成本）；
  3. 打分：逐项给依据打分，有分歧的项做 Spike（2.5）；
  4. 写 ADR：按 2.4 模板落一页纸，团队评审；
  5. 评审：拉上会受影响的人（后端被前端选型影响？叫上）——评审的意义是买共识，不只是挑错。

3.3 阶段三：落地对齐（产物：任务拆解）

  1. 拆任务：需求清单 → 工作项，每个工作项挂对应验收标准（颗粒度：1~3 天可完成可验收）；
  2. 排里程碑：先做风险最大的部分（技术不确定性早暴露），不要把 Spike 类风险留到末期；
  3. 定变更流程：约定"新增/修改需求走清单变更 + 重新估时"，堵住"顺手加个小功能"；
  4. 过程同步：固定节奏向需求方同步进展与风险（哪怕只是周报），坏消息要早说。
三阶段的取舍：小需求（半天能做完）三阶段合并成一次对话 + 一条带验收标准的任务；中大需求严格执行。流程的尺度跟着返工代价走——返工越贵，前期越要慢。

4进阶知识点【进阶】

首次学习可整章跳过。前置：完整走过一次第 3 章流程。

4.1 非功能需求的量化

非功能需求是"做得有多好"，模糊表述毫无约束力，必须量化。常用指标参考：

类别模糊说法量化表述示例
性能"要快"列表页 P95 ≤ 500ms；导出 10 万行 ≤ 30s
容量"能扛住并发"峰值 500 QPS 下错误率 < 0.1%
可用性"要稳定"月度可用性 99.9%（月停机 ≤ 43 分钟）
安全"要安全"导出数据过脱敏规则；操作留审计日志
兼容"支持主流浏览器"Chrome/Edge 最近两个大版本 + 移动端核心流程可用

量化数字从哪来：现状测量 + 需求方业务目标 + 行业常识三者取交集，写进需求清单时就标注依据。测不出依据的指标，宁可不写——假指标比没指标更糟（团队会真的为它优化）。

4.2 跨团队需求谈判：范围/时间/资源三角

需求方要加范围时，用三角形谈判：加范围必须至少动三角之一——延期、加人、或砍掉别的范围。"都要"的结果是全部做一半。谈判姿态：带着数据（影响面评估）而不是情绪；给出选项（"可以加，A 方案延期一周，B 方案下迭代"）而不是硬顶。

4.3 选型的退出成本

评估候选时多问一句："如果一年后要换掉它，要付什么代价？"——数据能导出吗（格式锁定）、代码深度耦合吗（接口隔离了吗）、团队能维护旧系统到迁移完成吗。工程上的通用保险：用适配层隔离核心依赖（业务代码只依赖自己的接口，不直接依赖三方 SDK 的类型与调用方式），退出成本立刻从"重写"降为"换实现"。

6最小可交付产物

决策型工作流的"Demo"是三份文档。以真实任务"给订单系统加 Excel 导出"为例，30~60 分钟产出：

6.1 产物一：需求澄清记录（节选）

Q: 这个功能给谁用？多久用一次？
A: 财务 2 人，每月 1 号月结时用一次（低频、数据量大）。
Q: 现在没有它怎么做的？
A: 运维跑 SQL 导 CSV，财务用 Excel 再加工（现状即底线方案）。
Q: 做到什么程度算完成？
A: 按月份+订单状态筛选导出 xlsx；10 万行 ≤ 30 秒；金额字段脱敏规则生效。
Q: 这事儿谁说了算？
A: 财务主管张经理（验收人）。

6.2 产物二：需求清单表（节选）

#层次描述验收标准优先级
1功能按月份+状态筛选导出 xlsx筛选结果与页面列表一致P0
2非功能导出性能10 万行 ≤ 30s（P95），超时有进度提示P0
3非功能数据安全客户手机号/银行卡按脱敏规则输出，操作留审计日志P0
4用户失败可重试导出失败保留任务记录，可一键重试P1

6.3 产物三：选型对比表 + ADR

候选优势劣势退出成本评分（权重后）
前端导出（SheetJS）零后端改动，快10 万行内存爆，数据全量下发有安全面低2.8
后端流式导出（现有 Java 服务 + EasyExcel）分页流式写、可控脱敏、复用现有权限后端开发 3 天低（标准 xlsx）4.4
独立导出服务 + 消息队列可扩展到任意大数据量新增运维面，当前量级过度设计中3.1
# ADR-014：订单导出采用后端流式生成
日期：2026-10-15　状态：已采纳
## 背景
财务月结需要导出订单明细（月度峰值约 10 万行），现状靠运维手工导 SQL，
耗时且无脱敏审计。
## 候选
前端 SheetJS 导出 / 后端流式导出 / 独立导出服务
## 决策
后端流式导出（EasyExcel，分页游标写盘）。
## 理由
10 万行量级排除前端方案；独立服务对当前频次（每月一次）过度设计。
## 后果（接受的代价）
- 数据量增长到百万级时需引入异步导出+对象存储（记为技术债 ADR-014-DEBT）
- 后端投入约 3 人日，本期不做前端实时导出体验
## 复审条件
月导出量级超过 50 万行，或导出频次从月级变为日级时重开本决策。

6.4 产物价值与对照

三份产物合计一小时，换来的是：开发自测有清单（验收标准列）、测试有用例来源、半年后有人问起为什么没上独立导出服务时有处可查。对照经验：没有这三份产物的同规模需求，平均返工 1~2 轮——文档不是负担，是把返工提前消化掉。

6.5 扩展方向

  1. 把 ADR 模板放进团队仓库 docs/adr/ 目录，编号递增，评审会直接对着 ADR 开；
  2. 给需求清单表加"验收人确认"列并要求签名（邮件回复确认也算）；
  3. 下一个真实需求完整走一遍三阶段，事后复盘产物哪一栏没起到作用、砍掉或改进它。

7常见坑 & Debug

按"需求阶段 → 选型阶段 → 落地阶段"分组，每条五要素。

7.1 需求阶段

坑 1：把方案当需求

  • 现象：需求方直接说"给我加个按钮，点了发邮件"——方案已被指定；
  • 根因：需求方用自己的专业直觉代你做了方案设计；
  • 复现：照做后发现真实诉求是"异常时能及时知道"，轮询看板比邮件更合适；
  • 修复：退回 2.1 四层次追问业务目标与用户场景，把"方案"翻译回"问题"再重新求解；
  • 规避：评审时每个功能项都标注对应的业务目标，对不上目标的功能就是可疑项。

坑 2：没有验收标准就开工

  • 现象：做完了，需求方说"不是这个意思"，来回返工；
  • 根因：2.2 的分水岭没跨过去——愿望进了排期；
  • 修复：补齐验收标准并请需求方书面确认后才继续投入；
  • 规避：任务单没有验收标准字段不允许进入"进行中"。

坑 3：非功能需求缺席

  • 现象：功能全对，上线第一天 10 万行导出把服务打挂；
  • 根因：清单里只有功能需求，数据量级从没人问过（澄清 8 问里的第 7 问被跳过）；
  • 修复：按 4.1 量化补齐性能/安全/容量指标，按 2.5 做 Spike 验证；
  • 规避：需求清单表固定包含"非功能"分区，哪怕填"无特殊要求"也要显式写。

7.2 选型阶段

坑 4：追新——用未成熟技术赌生产

  • 现象：选了发布半年的新框架，半年后核心插件停止维护，被迫迁移；
  • 根因：把"技术适配"维度和"尝鲜欲望"混为一谈，生态成熟度打分虚高；
  • 修复：按 2.3 重打分（重点核 issue 响应速度、发版节奏、背后维护方）；
  • 规避：生产项目给"新技术"设准入门槛（如发版 > 1 年、有生产案例），想试先用 Spike 或个人项目试。

坑 5：只看 Demo 就拍板

  • 现象：官方 demo 华丽，接入后发现在我们的数据量级/网络环境下表现完全不同；
  • 根因：demo 是理想环境的最优展示，你的约束（数据、网络、合规）它一个都没体现；
  • 修复：用 2.5 Spike 在自己的约束下重测关键路径；
  • 规避：评分表里"技术适配"一栏必须引用自测数据，不许填"官方宣称"。

坑 6：忽略退出成本

  • 现象：深度绑定了某云厂商特有服务，一年后成本或合规原因必须迁出，评估下来等于重写；
  • 根因：五维度里"退出成本"默认没打分（2.3 表中最常被漏的一列）；
  • 修复：补评估并用 4.3 的适配层隔离核心依赖；
  • 规避：ADR 模板里"后果"栏强制回答"换掉它的代价是什么"。

7.3 落地阶段

坑 7：变更无流程，"顺手加个需求"

  • 现象：开发中途"就加个小功能"，三次之后排期全乱、质量失控；
  • 根因：没有变更定价机制，"小"的成本从未被摆上桌面；
  • 修复：按 2.6 给变更定价（影响面/工时/三角取舍），需求方决策后再动；
  • 规避：固定话术——"可以，我先评估影响面，今天下班前给你三个选项"。

坑 8：决策无记录

  • 现象："当时为什么选 A？"——全员失忆，新一轮争论从头再来；
  • 根因：决策只发生在会议里，没有落纸；
  • 修复/规避：ADR 机制（2.4）——决策从"记忆"变成"文档"，争议从"吵架"变成"复审条件是否触发"。

7.4 通用排查思路

  • 扯皮 → 先查层次：双方是不是在四层次的不同层说话（2.1）；
  • 返工 → 先查验收标准：写了吗？需求方确认了吗？；
  • 选型翻车 → 先查评分依据：有没有 Spike 数据，退出成本打分了吗。

8重点讲解

Q1：拿到一个模糊需求，你的完整分析过程是什么？

参考答案：四层次拆解 + 三问过滤 + 产物确认。①分层：把诉求拆成业务/用户/功能/非功能四层，找出缺哪层；②三问：为什么做（对齐业务目标）、为谁做（场景与频率，定投入级别）、做成什么样算完成（逼出验收标准）；③产物：整理成需求清单表（含优先级与验收人），请需求方书面确认。

举例："加个导出功能" → 追问后可能是"财务月结对账耗时 2 天，要缩到 2 小时"——答案可能根本不是导出，而是对账报表。面试官想听到的关键词：分层、验收标准、书面确认。

Q2：技术选型你会怎么评估？说一个你做过的选型。

参考答案：框架是五维度加权评分 + Spike + ADR：技术适配（解决我们的问题吗）、团队能力（接得住吗）、生态成熟度（文档/社区/维护方）、总成本（学习+开发+运行+迁移）、退出成本（一年后换掉它代价多大）。分歧大的维度用最小实验（Spike）拿数据，结论落 ADR 存档（背景/候选/决策/理由/后果/复审条件）。

讲案例的加分结构：当时的约束 → 候选与取舍 → 选了什么、放弃了什么代价 → 后来复审条件是否被触发。能说出"放弃了什么"和"接受什么后果"的候选人极少——这正是成熟决策与拍脑袋的分界。

Q3：需求频繁变更怎么办？

参考答案：先摆态度——变更不是敌人，失控的变更才是。机制三件套：①定价：每个变更评估影响面与工时，用范围/时间/资源三角让需求方做取舍；②流程：变更进需求清单、重新确认验收标准，不走口头；③缓冲：排期时预留 15~20% 缓冲吸收小变更，大变更走迭代规划。另外要区分两类变更：需求真变了（值得做）vs 前期没分析清楚（该复盘的是分析质量，不是抱怨变更）。

Q4：非功能需求怎么处理？给个例子。

参考答案：核心是量化。"要快"没有约束力，"P95 ≤ 500ms"才有。做法：从现状测量、业务目标、行业常识三个来源取数，标注依据写进清单；性能类指标在开发早期用 Spike 或压测验证，不要留到上线。例子：导出功能"10 万行 ≤ 30s（P95）"——它直接影响了选型（排除前端方案）和实现方式（流式写盘），这就是非功能需求驱动技术决策。

Q5：自测 5 问

  1. 需求四层次是什么？"导出功能"的各层表述分别长什么样？
  2. 验收标准为什么是需求的分水岭？谁负责确认它？
  3. 选型五维度中哪两个最常被漏掉？各用一句话解释。
  4. ADR 的六个栏目是什么？"后果"栏为什么必须写？
  5. Spike 的产出物是什么？为什么说它的代码是"一次性实验品"？
