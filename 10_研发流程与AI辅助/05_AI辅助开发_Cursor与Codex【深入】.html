1简介与阅读指引

1.1 定位

本篇讲的是"AI 编码工作流"——不是工具测评，而是把补全、Agent、上下文工程、验收规范串成一套可复用的日常工作方法。AI 辅助编码分两层：补全层预测你下一段代码；Agent 层（Cursor Agent、Codex、Claude Code）给定目标后自己读文件、改代码、跑测试、根据报错迭代。

1.2 痛点

  • 很多人"装了 AI 插件"，但还是一行行手写——不会委派，Agent 的价值用不出来；
  • 随手把大任务丢给 Agent，收获一堆连带改动和幻觉 API，清理比手写还慢；
  • 团队没有验收规范，AI 代码直接进主干，线上出事说不清责任。

根源都是同一个：把 AI 当"自动写代码机"，而不是"需要明确任务书与验收流程的初级同事"。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
想把 AI 编码从"偶尔用用"升级为稳定工作流想了解大模型原理与 API → 《大模型应用》/《LLM 应用开发》
团队要建立 AI 代码的验收规范纯工具安装教程 → 各工具官方文档
面试要讲"你如何用 AI 提效"提示词的通用写作课 → 第 4 章只讲编码场景

1.4 学习目标：读完本篇你能

  1. 按场景正确路由：什么时候用补全、什么时候委派 Agent，并给出判断依据；
  2. 写出"目标 + 约束 + 上下文 + 验收标准"四要素的合格任务描述，配好团队规则文件；
  3. 建立"AI 产出必须本地验证 + 逐 diff 人工审"的落地规范，说出三类典型坑的防法；
  4. 用工程语言（上下文窗口、Agent 循环、工具调用、MCP）讲清这些工具的工作原理。

2核心模型

本章按认知顺序讲清这些工具的五个核心模型。每一节都依赖前一节：先分清两层工具（2.1），再理解它们共同的约束——上下文窗口（2.2），然后是 Agent 层的运行方式（2.3~2.5），最后是模型选择的依据（2.6）。

2.1 补全层 vs Agent 层：先分清你在用哪一层

图 1 补全层与 Agent 层（示意）

两层的本质区别是谁掌握控制流：补全层里人写代码、AI 猜下文，控制流在人手里；Agent 层里你只给目标，控制流交给 Agent——它自己决定读哪个文件、改哪里、跑什么命令验证。控制流交出去换来的效率，要靠 2.2 的上下文管理和 2.8 的验收规范赎回来。

工具形态对比：Cursor vs GitHub Copilot vs Codex / Claude Code

维度CursorGitHub CopilotCodex / Claude Code
形态AI 原生 IDEIDE 插件命令行编码 Agent
能力补全+Chat+Agent 模式补全+Chat/Edits+Agent 模式（以最新官方文档为准）读仓库/跑测试/自动改
取舍日常主力 IDE插件内问答/跨文件改后台跑整任务

选型结论（以当前版本为准）：主力 IDE 选 Cursor（三层能力一体）；已被 VSCode 工作流绑住选 Copilot；整任务后台托管（CI 跑任务、批量重构）选 Codex / Claude Code。

2.2 上下文窗口：模型一次能"看到"什么

上下文窗口（Context Window）是模型单次推理能容纳的 token 上限，它决定了 Agent "看得见"什么。关键推论：上下文质量决定输出质量——给错文件，再强的模型也改错地方。Agent 的很多"聪明"或"愚蠢"，本质都是它上下文里装了什么：装了正确的相关文件片段，它就是专家；装了无关文件，它就是瞎猜。所以第 3 章的工作流里，"框定上下文"是人的核心职责之一。

2.3 Agent 循环：目标驱动的自动迭代

补全层没有"过程"，Agent 层有：接收目标 → 调工具 → 观察结果 → 判断是否完成，未完成回到调工具——这就是 Agent 循环（Agent Loop），也是 2.5 工具调用存在的意义（详细图见第 5 章）。理解循环的意义在于知道在哪介入：循环可能跑偏（改错方向、越改越乱），人要在关键节点审阅 diff、决定是否继续——人是验收者与方向把控者，不是旁观者。

2.4 工具调用与 MCP：Agent 的手和脚

Agent 不只是生成文本，它通过工具调用（Tool Use）与环境交互：编辑文件、运行 shell、查搜索、跑测试。每个工具是一个"声明了入参和用途的函数"，模型输出"调哪个工具+参数"，宿主执行后把结果回填给模型——这就是循环里"调工具→观察结果"的实现。

MCP（Model Context Protocol）则是把"接入工具"这件事标准化的协议：数据库、浏览器、issue 系统……都能以统一方式接入编码 Agent，是当下 Agent 生态的事实标准（以最新官方文档为准）。理解 MCP 的意义：团队内部的系统（内部 API 文档、工单系统）也能变成 Agent 的工具——这是下一阶段定制化的入口。

2.5 仓库索引 / RAG：装不下整个仓库怎么办

大仓库远超上下文窗口。解法是检索增强：对全仓库建索引（符号索引/向量索引），你的问题进来先检索出相关代码片段，只把片段注入上下文。这也是为什么 Agent 偶尔"找不到"你说的那个文件——检索没命中。工程含义：给任务时主动点名相关文件路径，比指望检索万无一失靠谱得多。

2.6 补全模型 vs 推理模型【进阶】

工具背后通常路由两类模型：补全模型小而快（毫秒级出下一段，行内预测）；推理模型大而慢（先"想"再答，适合规划跨文件改动、分析复杂报错）。你不需要记型号，只需要记住路由原则：高频低延迟的场景用补全模型，低频高难度的场景用推理模型——工具已经帮你路由好了，但理解这件事能解释为什么 Chat 里"思考模式"更慢也更准。

2.7 上下文隔离：跨任务不串味

会话是有记忆的——上个任务的假设、失败的尝试、错误的结论都会留在上下文里。新任务开干净会话，不带旧假设；这是最容易被忽视却最影响输出质量的习惯。"这个 bug 修了三版都不对"很多时候是会话里已经堆满了错误前提，开个新会话重述问题反而一次过。

2.8 落地规范（Guardrails）：AI 提效不等于免审

必须四件套：①本地验证可运行（build/test 通过）；②过 lint 与既有测试；③人审 diff（逐条看，不接受"看起来没问题"）；④敏感/核心逻辑人工把关（权限、支付、加密）。这套规范是 2.3"人是验收者"的工程化落地，第 3 章工作流和第 6 章 Demo 都建立在它之上。

3工作流（按场景渐进）

本章按四个日常场景给出渐进式工作流。每个场景都遵循同一框架：框定上下文 → 给任务书 → 验收，差别只在介入深度。

3.1 场景一：小改动、熟悉代码 → 用补全

手写到哪补到哪。适用：样板代码（表单、类型定义、重复结构的第三个实例）、你非常熟悉的语言与模块。判断依据：改动范围在你脑子里已经清晰、不需要 AI 理解项目其他部分——这时补全最快，开 Agent 反而慢。

3.2 场景二：跨文件任务 → 委派 Agent

适用：跨文件重构、不熟悉模块的新功能。关键是任务书。四要素模板：

目标：给某个列表加虚拟滚动。
约束：不改现有 API；保留 Vue3 + TS；行数 1000+ 也要流畅。
上下文：相关文件 X.ts/Y.vue，现有实现见 Z。
验收：本地 npm run build 通过，滚动不卡顿。

正反例对比：

❌ "帮我优化一下这个列表"            —— 目标模糊、无约束、无验收 → 得到泛泛的"建议"
✅ 上面的四要素模板                   —— Agent 能直接开工，且你能机械地验收

再补一个习惯：让模型先说方案再动手。先问"你打算怎么改，涉及哪些文件"，方案对了再放行执行——方案审查的成本远低于回滚错误改动。

3.3 场景三：调试定位 → 喂报错栈，不喂猜测

把完整报错栈 + 相关代码 + 复现步骤贴给模型，让它给"最可能的原因排序"。两个要点：①贴原始报错，不要自己转述（转述丢信息）；②让它给可验证的假设（"如果是 X，改 Y 应该会 Z"），你本地验证——不要让它直接"改好"，调试的价值在于你理解了根因。

3.4 场景四：评审 diff → 模型初筛，人终审

AI 产出的 diff（或同事的 PR）先让模型扫一遍："找出潜在 bug、遗漏的边界、与项目规范的冲突"，输出问题清单；你再带着清单人工过一遍。模型初筛解决"看不细"，人终审解决"看不偏"——模型不知道业务上下文里哪些改动静电危险（比如动了支付回调），你知道。

全篇的取舍总结：小而熟用补全；大而跨文件委派 Agent（先审方案）；调试喂原始报错要假设不要魔法；评审模型初筛人终审。所有场景的兜底都是 2.8 的四件套。

4进阶知识点进阶

首次学习可整章跳过。本章讲配置层与生态层，用于把个人习惯升级为团队规范。前置：已实践第 3 章。

4.1 规则文件：把"每次都要交代的话"沉淀下来

团队约束、代码规范、常用命令不该每次重复打——各工具支持常驻上下文的规则文件，自动加载：.cursorrules（Cursor）、AGENTS.md（Codex 等通用）、CLAUDE.md（Claude Code）。内容写三类：技术栈与版本约束、目录结构与命名规范、验证命令（"改完必须跑 npm run lint && npm run test"）。这是把个人技巧变成团队资产的最低成本方式——规则文件随仓库提交，新人 clone 下来 AI 就"懂规矩"。

4.2 MCP 深入：把内部系统接进 Agent

2.4 讲了 MCP 是什么，这里讲怎么用：三个典型接入——①数据库只读工具（Agent 能直接查 schema 写迁移代码）；②内部文档检索（Agent 回答"我们项目的登录流程"时有据可依）；③工单系统（"按 issue #142 的描述修"自动读单）。接入后配套收紧权限：内部工具只给只读或白名单操作，Agent 能调用的面 = 攻击面。

4.3 上下文工程：比提示词工程更进一步

提示词工程关注"怎么说"，上下文工程关注"让模型看到什么"——在 Agent 时代后者权重更大。三个手段：①主动框定（点名相关文件，别指望检索）；②清理干扰（关掉无关 tab、别把日志噪音贴进会话）；③规则文件常驻（2.6 的 4.1 节），把稳定约束从每次对话挪到常驻层。

4.4 模型路由与成本意识【进阶】

团队落地后的现实问题：token 就是钱。实践原则：高频操作（补全、小问答）走小模型，大任务（跨文件重构、架构分析）才上推理模型；长会话定期开新会话——上下文越长越贵也越慢，且质量先升后降。给团队算账：一次跨文件重构省下的 2 小时 vs Agent 消耗的 token 费，通常差两个数量级，该用就用。

6最小可运行 Demo

10 分钟给一个真实项目配好"AI 工作流最小套件"：一个规则文件 + 一个四要素任务 + 一套验收动作。全程在 Cursor（或任一支持规则文件的工具）里完成。

6.1 第一步：配置规则文件

项目根目录新建 .cursorrules（或 AGENTS.md）：

# 项目约束
- 技术栈：Vue3 + TypeScript + Vite，禁止引入新框架
- 状态管理用 Pinia，样式用 Tailwind，不要写原生 CSS 文件
- 所有异步用 async/await，禁止 .then 链
- 提交前必须通过：npm run lint && npm run build

# 代码风格
- 组件用 <script setup lang="ts">
- API 层统一放 src/api/，返回类型必须显式声明

# 禁止
- 不要修改 src/core/ 目录（核心逻辑，人工维护）
- 不要升级任何依赖版本

6.2 第二步：用四要素模板委派一个真实任务

在 Agent 对话中输入（替换成你项目的真实文件）：

目标：给 src/views/OrderList.vue 的订单表格加服务端分页。
约束：不改 src/api/order.ts 的现有函数签名；保留现有筛选逻辑；
     分页状态放 Pinia，不放进组件。
上下文：表格组件在 src/components/KTable.vue，分页参数规范见
     src/api/types.ts 里的 PageResult。
验收：npm run build 通过；翻页时 network 面板只发一次请求；
     筛选条件变化时分页重置到第 1 页。
先给出你的改动方案和涉及文件清单，我确认后再动手。

6.3 第三步：验收（机械可执行）

  1. Agent 先输出方案与文件清单——检查：有没有它不该碰的文件（对照规则文件的"禁止"节）；
  2. 放行后逐个文件看 diff——重点看：有没有顺带改了无关代码（连带改动）；
  3. 本地跑 npm run lint && npm run build——不过就打回；
  4. 按"验收"三条手动验证——翻页请求数、筛选重置行为；
  5. 全部通过才 commit，commit message 写"AI 协助：订单列表服务端分页"。

6.4 运行结果说明与对照

做完这 10 分钟你会得到两组对照体验：没有规则文件时，Agent 可能给你引入新库、改掉 API 签名、写 .then 链——每条都要人肉纠正；有规则文件后，这些约束自动生效，驳回率显著下降。四要素任务书让 Agent 的产出从"碰运气"变成"可验收"。

6.5 生产改造扩展方向

  1. 把 6.1 的规则文件提交进仓库并写进团队 README——新人与 AI 共用同一份规范；
  2. 团队约定 commit 前缀区分"AI 协助/人工"，评审时对 AI 协助的 diff 加严一级；
  3. 接入 MCP：把内部接口文档、数据库 schema（只读）接给 Agent，减少"上下文靠手贴"。

7常见坑 & Debug

按"配置 → 编码 → 验收"三个阶段分组，每条五要素：现象 → 根因 → 复现 → 修复 → 规避。

7.1 配置阶段

坑 1：没有规则文件，每个任务都要重复交代规范

  • 现象：每次对话都要说"用 TS""别改这个文件"，漏说就翻车；
  • 根因：稳定约束放在了会话层，而会话是易失的；
  • 复现：新会话问同一个项目问题，答案风格与上次完全不同；
  • 修复：按 6.1 配置规则文件；
  • 规避：规则文件进版本库，团队共用。

7.2 编码阶段

坑 2：上下文给错/给少，改错地方

  • 现象：Agent 改了"同名但不是你要的"函数，或自作主张新建了一套平行实现；
  • 根因：模型只能看见上下文里的东西——检索没命中 + 你没点名文件；
  • 复现：只说"优化列表性能"，不给文件路径；
  • 修复：任务书里点名相关文件（四要素的"上下文"栏），必要时贴关键代码；
  • 规避：宁可多给上下文；发现 Agent 理解偏差立刻纠正而不是将错就错。

坑 3：幻觉——编造不存在的 API

  • 现象：代码引用了一个看起来很合理的函数/参数，实际不存在或版本不符；
  • 根因：语言模型按概率生成，"合理的 API"不等于"存在的 API"，训练数据 cutoff 之后的版本变化尤其常见；
  • 复现：问一个很新的库的用法，与官方文档对照；
  • 修复：一律以官方文档与本地实测为准；IDE 里安装对应类型包，幻觉 API 会直接标红；
  • 规避：验收四件套的"本地验证可运行"就是幻觉过滤器——编译都过不了的代码不存在"看起来对"。

坑 4：跨任务不隔离上下文

  • 现象：修一个新 bug，Agent 的方案总带着上个任务的残留假设，越聊越歪；
  • 根因：会话上下文里堆满了上一个任务的错误尝试与结论；
  • 复现：同一个会话连问三个不相关问题；
  • 修复：新任务开干净会话，重新给最小上下文；
  • 规避：任务切换 = 会话切换，把"上下文隔离"变成肌肉记忆。

7.3 验收阶段

坑 5：一个大任务丢给 Agent 不管

  • 现象："把这个项目重构一下"，回来收获 40 个文件的大 diff，还引入了连带 bug；
  • 根因：任务粒度超出单次循环的可靠范围，且中途无人纠偏；
  • 修复：拆小任务（一个可验收的子任务一次委派），关键节点审阅；
  • 规避：委派粒度 = "你能在一个 diff 里看完并判断对错"的粒度。

坑 6：不验证就提交 AI 代码

  • 现象：代码"看起来对"，合并后线上挂——最常见的是没跑过的分支逻辑和幻觉依赖；
  • 根因："AI 写的"带来的虚假信任感；
  • 修复：严格执行验收四件套（build/test/lint/人审）；
  • 规避：团队规范写死："AI 协助的代码与人工代码执行完全相同的评审标准"，没有例外。

7.4 通用排查思路

  • 产出不对 → 先查上下文：它看到了哪些文件？规则文件加载了吗？（绝大多数"AI 太笨"是上下文问题）
  • 反复修不好 → 换干净会话重述，而不是在同一会话里继续叠补丁；
  • 怀疑幻觉 → 查文档 + 本地实测，永远不让"模型说的"直接进主干。

8重点讲解

按 概念题 → 原理追问 → 场景设计题 递进，每题附详细答案。

Q1：补全和 Agent 分别适合什么场景？怎么判断？

参考答案：判断维度是控制流和上下文范围。改动范围小、逻辑已在脑中、不需要理解项目其他部分 → 补全（人保持控制流，毫秒级反馈）；改动跨文件、需要理解仓库结构、任务可描述为"目标+验收"→ Agent（控制流交给它，人审 diff 收回控制权）。

追问：为什么不大任务全用 Agent？——三个原因：①粒度失控（产出大 diff 难审，连带改动多）；②成本（推理模型 + 长上下文贵且慢）；③风险（控制流完全交出，人失去对代码库的"手感"）。工作流的本质是按任务特征分配控制流。

Q2：什么是上下文工程？它和提示词工程的关系？

参考答案：提示词工程关注指令的表达（怎么说清楚）；上下文工程关注信息的选择与组织（让模型在推理那一刻看到什么）。在补全/问答时代提示词权重更大；在 Agent 时代，上下文工程权重反超——因为 Agent 的行为由它"看到"的文件、检索结果、规则文件共同决定，指令只占其中一小部分。

实践三手段：主动框定相关文件（别指望检索）、清理无关干扰、用规则文件把稳定约束常驻化。一句话：与其琢磨怎么措辞，不如琢磨"它到底看见了什么"。

Q3：AI 生成的代码，你们的验收流程是什么？为什么这么设计？

参考答案：四件套——本地验证可运行（build/test 通过）→ 过 lint 与既有测试 → 人逐 diff 审 → 敏感/核心逻辑人工把关。

为什么这样设计：每一层拦一类问题——build/test 拦幻觉 API 与语法错误（机器可判）；lint/测试拦风格偏移与回归（既有测试是安全网）；人审拦连带改动与业务语义错误（只有人知道哪段是雷区）；核心逻辑人工把关是责任与合规要求（支付/权限代码不接受黑箱产出）。

追问：会不会太重、抵消了提效？——不会：四件套中前三步是自动化的秒级操作，真正花时间的人审只对"AI 产出"加严，而这份加严远小于清理一次幻觉事故的成本。

Q4：MCP 是什么？它解决了什么问题？

参考答案：MCP（Model Context Protocol）是把外部工具与数据源接入 AI 应用标准化的协议。解决的问题：此前每个工具要为每个 Agent 单独写适配，MCP 之后工具方实现一次协议，任何支持 MCP 的 Agent 都能接入——类似 USB-C 之于外设。

工程意义：团队可以把内部系统（数据库 schema 只读、接口文档、工单）封装成 MCP 工具，让编码 Agent 直接"看到"组织内的真实信息，而不是靠人肉粘贴上下文。

追问：接入内部系统有什么风险？——Agent 的可调用面 = 攻击面：只读权限、白名单操作、敏感数据脱敏，三件事要在接入前定好。

Q5：自测 5 问

  1. 任务书四要素是哪四个？缺"验收标准"会发生什么？
  2. Agent 循环的四个环节？"完成？"的判断为什么不可信？
  3. 规则文件解决什么问题？写哪三类内容？
  4. 幻觉的根因是什么？两道过滤网是什么？
