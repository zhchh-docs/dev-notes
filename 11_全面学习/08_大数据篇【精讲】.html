1.1 大数据生态概览

大数据 = 海量数据的采集、存储、计算与服务。生态以 Hadoop 为核心，批处理与流处理两条技术主线并行发展。

  • 4V 特征：Volume（数据量大）、Velocity（增长快）、Variety（类型多样）、Veracity（质量与可信度）
  • Hadoop 三剑客：HDFS（存储）、MapReduce（批计算）、YARN（资源调度）；生态周边 Hive / HBase / ZooKeeper / Flume / Sqoop
  • 批 vs 流：批处理（MapReduce / Spark 批）适合离线统计；流处理（Kafka + Flink / Spark Streaming）适合实时场景
  • 选型口诀：数据落盘分析用批、实时告警/风控用流、检索用 ES、明细查询用 OLAP
# 大数据链路速览（一条命令串起各环节）

# 存储：HDFS 分布式文件系统（默认 3 副本）
# 计算：MapReduce 批处理 → Hive 写 SQL 替代手写 MR
# 实时：Kafka 消息总线 + Flink 流处理
# 服务：Hive / SparkSQL 出报表，ClickHouse / Doris 服务高并发查询

1.2 HDFS 分布式文件系统

把海量文件分散存储在多台机器上，对外仍是"一个文件系统"。NameNode 管元数据、DataNode 存数据块，默认 3 副本保证容错。

  • 架构：NameNode（元数据：文件名→块→位置）、DataNode（实际存块）；Secondary NameNode 辅助合并镜像
  • 数据块：默认 128MB/块（旧版 64MB）；大块减少寻址开销，适合大文件顺序读
  • 副本策略：默认 3 副本；机架感知（同机架 2 副本 + 跨机架 1 副本），容忍机器与机架故障
  • 写流程：客户端 → NameNode 分配块 → 写 DataNode 管道（pipeline）逐副本落盘 → 全部确认后提交
  • 特点：适合一次写多次读、大文件、批处理；不适合低延迟随机读与频繁小文件
# HDFS 常用命令（hdfs dfs 或 hadoop fs）
hdfs dfs -mkdir -p /warehouse/logs          # 建目录
hdfs dfs -put app.log /warehouse/logs/      # 上传文件（自动分块、复制）
hdfs dfs -ls -R /warehouse/logs             # 递归列出
hdfs dfs -cat /warehouse/logs/app.log | head  # 读取内容
hdfs dfs -get /warehouse/logs/app.log ./    # 下载
hdfs dfsadmin -report                        # 查看块/副本/节点状态
hdfs fsck /warehouse/logs/app.log -files -blocks -locations  # 查看块的物理位置

1.3 数据仓库概念与维度建模

数据仓库面向分析：把业务数据按"维度 + 事实"组织成星型/雪花模型，让报表与洞察又好写又快查。区别于 OLTP 的在线事务库。

  • OLTP vs OLAP：OLTP 面向事务（增删改、行存、高并发）；OLAP 面向分析（聚合、列存、大数据量扫描）
  • 星型模型：中间一张事实表（度量 + 外键）+ 周围维度表（商品/时间/门店）；查询连接少、最快
  • 雪花模型：维度表继续规范化拆层，节省存储但查询连接变多
  • 数仓分层：ODS（原始）→ DWD（明细清洗）→ DWS（汇总）→ ADS（应用），层层加工
-- 星型模型：订单事实表 + 维度表
CREATE TABLE dim_date (          -- 时间维度
  date_key DATE PRIMARY KEY, year INT, month INT, day INT, quarter INT);

CREATE TABLE dim_shop (          -- 门店维度
  shop_id INT PRIMARY KEY, shop_name VARCHAR(50), city VARCHAR(20));

CREATE TABLE fact_order (        -- 事实表：度量 + 外键
  order_id BIGINT PRIMARY KEY,
  date_key DATE REFERENCES dim_date(date_key),
  shop_id INT REFERENCES dim_shop(shop_id),
  amount DECIMAL(12,2),          -- 度量：金额
  cnt INT);                      -- 度量：件数

-- 分析：按季度 × 城市 汇总销售额（星型一次 join 即可）
SELECT d.quarter, s.city, SUM(o.amount) AS revenue
FROM fact_order o
JOIN dim_date d ON o.date_key = d.date_key
JOIN dim_shop  s ON o.shop_id   = s.shop_id
GROUP BY d.quarter, s.city;

2.1 MapReduce 计算原理

把大任务拆成可并行的小任务：Map 阶段就地处理、Shuffle 阶段按 Key 分组、Reduce 阶段聚合。经典"分而治之"批计算模型。

  • 三个阶段：Map（输入分片 → 产出 (K,V) 对）→ Shuffle（按 K 排序、分区、合并，把相同 K 发给同一 Reduce）→ Reduce（对每个 K 聚合）
  • 容错：任务失败自动重跑；推测执行（慢任务另起一个副本）
  • 局限：中间结果落盘（磁盘 IO 重）、延迟高；所以 Spark 用内存 + DAG 取代它
// WordCount 的 Mapper：一行 → 多个 (单词, 1)
public class WcMapper extends Mapper {
  protected void map(LongWritable key, Text value, Context ctx)
      throws IOException, InterruptedException {
    for (String w : value.toString().split("\\s+")) {
      ctx.write(new Text(w), new IntWritable(1));   // 输出 (word, 1)
    }
  }
}
// Reducer：把同一单词的所有 1 加起来
public class WcReducer extends Reducer {
  protected void reduce(Text key, Iterable vals, Context ctx)
      throws IOException, InterruptedException {
    int sum = 0;
    for (IntWritable v : vals) sum += v.get();
    ctx.write(key, new IntWritable(sum));           // 输出 (word, 总数)
  }
}
// 驱动：job.setMapperClass / setReducerClass / setOutputKeyValueClass

2.2 Hive 与 SQL-on-Hadoop

Hive 把 SQL 翻译成 MapReduce/Spark 任务执行，让大数据分析从"写 Java"变成"写 SQL"。

  • 架构：客户端（CLI/JDBC）→ HiveServer → 解析 SQL → 生成执行计划 → 提交到 MapReduce/Spark
  • Metastore：元数据（表/分区/字段）存到关系库（Derby/MySQL），与 HDFS 数据解耦
  • 内部表 vs 外部表：DROP 时内部表连数据一起删；外部表只删元数据（保护原始文件）
  • 分区与分桶：分区=目录（WHERE 裁剪加速）；分桶=文件（抽样与 join 优化）
-- 建外部表：数据在 HDFS，删除表不影响原始文件
CREATE EXTERNAL TABLE IF NOT EXISTS ods_order (
  order_id   BIGINT,
  shop_id    INT,
  amount     DECIMAL(12,2),
  create_ts  TIMESTAMP
)
PARTITIONED BY (dt STRING)              -- 按日期分区 → 目录 /ods/order/dt=2026-10-10
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
STORED AS ORC;                           -- 列存格式，压缩 + 列裁剪

-- 加载分区数据（指向 HDFS 路径）
ALTER TABLE ods_order ADD PARTITION (dt='2026-10-10')
  LOCATION '/data/ods/order/2026-10-10';

-- 分析：Spark on Hive 引擎自动并行执行
SELECT shop_id, SUM(amount) AS revenue
FROM ods_order
WHERE dt = '2026-10-10'
GROUP BY shop_id
ORDER BY revenue DESC
LIMIT 10;

2.3 Spark Core（RDD / DataFrame）

Spark 用内存计算 + DAG 调度取代 MapReduce 的磁盘往返：RDD 是不可变分布式数据集，算子构建血缘、行动算子触发真正计算。

  • RDD 特性：分区（parallel）、不可变、可缓存（persist/cache）、血缘（lineage）可重建
  • 转换 vs 行动：map/filter/flatMap/reduceByKey 是惰性转换（构建 DAG）；count/collect/saveAsTextFile 是行动（触发 Job）
  • 宽窄依赖：窄依赖（map，同分区直传，可管道化）；宽依赖（reduceByKey，需 Shuffle，产生 Stage 边界）
  • DataFrame/Dataset：结构化 API，Catalyst 优化器做谓词下推、列裁剪，比 RDD 更快更简洁
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("demo").getOrCreate()

# RDD 方式：WordCount
rdd = spark.sparkContext.textFile("hdfs:///data/app.log")
wc = (rdd.flatMap(lambda line: line.split())
        .map(lambda w: (w, 1))
        .reduceByKey(lambda a, b: a + b))     # 转换：惰性，只建 DAG
print(wc.count())                             # 行动：此刻才真正执行
wc.saveAsTextFile("hdfs:///out/wc")           # 又一个行动（重跑 DAG）

# DataFrame 方式：SQL 风格，Catalyst 自动优化
df = spark.read.parquet("hdfs:///warehouse/ods/order")
df.filter("dt = '2026-10-10'") \
  .groupBy("shop_id").agg({"amount": "sum"}) \
  .orderBy("sum(amount)", ascending=False) \
  .show(10)

# 缓存：被反复使用的中间结果
wc.cache()                                    # 建议缓存到内存（StorageLevel.MEMORY_AND_DISK）

2.4 Kafka 生产消费与分区机制

Kafka 是分布式消息总线：Topic 分 Partition 并行存储，Producer 按 key 路由，Consumer Group 内分摊分区、组间各自独立消费。

  • 核心概念：Broker（服务节点）、Topic（逻辑主题）、Partition（物理分片，有序追加）、Offset（分区内消息序号）
  • 可靠性：副本（默认 1/3）+ ISR 同步副本集合；acks=all 保证不丢
  • 消费模型：组内分区分配（一个分区同一时刻只被组内一个消费者消费）；组间广播（不同组都能读到全量）
  • 顺序保证：只在分区内有序；全局顺序需单分区（牺牲吞吐）
# 命令行快速验证
kafka-topics.sh --create --topic orders --partitions 3 --replication-factor 3 \
  --bootstrap-server node1:9092
kafka-console-producer.sh --topic orders --bootstrap-server node1:9092
# > 1001,apple,2
# > 1002,banana,5
kafka-console-consumer.sh --topic orders --from-beginning \
  --bootstrap-server node1:9092 --group g1
# Python 生产者/消费者（kafka-python）
from kafka import KafkaProducer, KafkaConsumer
import json

producer = KafkaProducer(bootstrap_servers="node1:9092",
                         value_serializer=lambda v: json.dumps(v).encode())
# key 相同 → 进入同一分区 → 该 key 的消息有序
producer.send("orders", key=b"user_42", value={"uid": 42, "sku": "a", "cnt": 2})

consumer = KafkaConsumer("orders", bootstrap_servers="node1:9092",
                         group_id="g1", auto_offset_reset="earliest")
for msg in consumer:                 # 组内均衡分摊各分区
    print(msg.partition, msg.offset, msg.value)

2.5 数据采集（Flume / 同步工具）

数据进湖之前先采集：Flume 拉日志进 HDFS/Kafka，Sqoop 把关系库全量/增量同步到 HDFS，CDC 监听 binlog 做实时同步。

  • Flume：Source（读源）→ Channel（缓冲）→ Sink（写出）；agent 串联可多级
  • Sqoop：JDBC 导入导出；增量用 last-value / 时间戳；底层还是 MapReduce
  • 实时同步：Canal/Debezium 监听 MySQL binlog → Kafka → 下游（数据一致性毫秒级）
  • 选型：日志采集用 Flume/Filebeat；库表同步用 Sqoop（离线）/Canal（实时）；文件与 Kafka 对接用 Connect
# Flume 单 agent 配置：tail 日志 → HDFS
a1.sources  = r1
a1.channels = c1
a1.sinks    = k1

a1.sources.r1.type = exec                          # Source：执行命令读日志
a1.sources.r1.command = tail -F /var/log/app.log
a1.sources.r1.channel = c1

a1.channels.c1.type = memory                       # Channel：内存缓冲
a1.channels.c1.capacity = 10000

a1.sinks.k1.type = hdfs                            # Sink：写 HDFS，按天分目录
a1.sinks.k1.hdfs.path = /data/logs/%Y%m%d
a1.sinks.k1.hdfs.fileType = DataStream
a1.sinks.k1.channel = c1

3.1 Spark 调优（内存 / Shuffle / 数据倾斜）

Spark 性能瓶颈集中在三处：Executor 内存不够、Shuffle 过大、数据倾斜拖慢整体。调优先定位，再对症下药。

  • 内存模型：Executor 内存分 storage（缓存）/ execution（计算）/ other；调 spark.memory.fraction 与 spark.memory.storageFraction 平衡
  • Shuffle 优化：spark.sql.shuffle.partitions（默认 200）按数据量调；开 Kryo 序列化 + 压缩（spark.serializer / spark.io.compression）
  • 数据倾斜：热点 key 导致个别任务慢；修法——加盐 + 两阶段聚合、广播小表、调整分区数
  • 通用：优先用 DataFrame（Catalyst 优化）、广播变量（broadcast join 小表）、缓存复用中间结果
# spark-submit 调优参数示例
spark-submit \
  --master yarn --deploy-mode cluster \
  --executor-memory 8G --num-executors 20 --executor-cores 4 \
  --conf spark.memory.fraction=0.75 \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  --conf spark.sql.shuffle.partitions=400 \
  --conf spark.sql.autoBroadcastJoinThreshold=10485760 \
  --conf spark.driver.memory=4G \
  app.py
# 数据倾斜修复：加盐 + 两阶段聚合
from pyspark.sql import functions as F

# 1) 对倾斜 key 加随机前缀：user_42 -> user_42_0..7
df2 = df.withColumn("salted",
    F.when(F.col("uid") == "user_42",
           F.concat(F.col("uid"), F.lit("_"), (F.rand() * 8).cast("int")))
     .otherwise(F.col("uid")))

# 2) 阶段一：按加盐 key 预聚合（把热点打散到 8 个任务）
s1 = df2.groupBy("salted").agg(F.sum("amount").alias("a"))
# 3) 阶段二：去掉盐再聚合
s2 = (s1.withColumn("uid", F.regexp_replace("salted", "_\\d+$", ""))
        .groupBy("uid").agg(F.sum("a").alias("total")))

3.2 Flink 流处理（窗口 / 状态 / 精确一次）

Flink 是真正的流式计算引擎：事件时间 + 水位线对齐乱序数据，状态后端做增量计算，Checkpoint + 两阶段提交保证精确一次语义。

  • 窗口：滚动（Tumbling，无重叠）/ 滑动（Sliding，有重叠）/ 会话（Session，空闲断开）；按事件时间（event time）更准
  • 水位线：Watermark 表示"此时间之前的数据已到齐"，迟到数据进侧输出流
  • 状态：Keyed State（每个 key 的状态）；Checkpoint 定期快照（Barrier 对齐），故障从最近一次恢复
  • 精确一次：source 可重放（Kafka offset 提交） + 状态 Checkpoint + sink 两阶段提交（如 Kafka 事务）
from pyflink.datastream import StreamExecutionEnvironment, TimeCharacteristic
from pyflink.datastream.window import TumblingProcessingTimeWindows, Time

env = StreamExecutionEnvironment.get_execution_environment()
env.set_stream_time_characteristic(TimeCharacteristic.EventTime)

# 每 60 秒滚动窗口聚合一次订单金额
stream = env.add_source(kafka_source) \
    .key_by(lambda o: o["shop_id"]) \
    .window(TumblingProcessingTimeWindows.of(Time.seconds(60))) \
    .aggregate(lambda a, b: a + b["amount"])

stream.print()
env.execute("order-window")
-- Flink SQL 等价写法：滚动窗口 + 结果写 Kafka（精确一次）
CREATE TABLE orders (
  shop_id INT, amount DECIMAL(12,2), ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND        -- 容忍 5s 乱序
) WITH ('connector' = 'kafka', 'topic' = 'orders', ...);

CREATE TABLE agg_sink (...)
WITH ('connector' = 'kafka', 'topic' = 'shop_agg',
      'sink.semantic' = 'exactly-once', ...);          -- 两阶段提交

INSERT INTO agg_sink
SELECT shop_id, SUM(amount), TUMBLE_END(ts, INTERVAL '60' SECOND)
FROM orders GROUP BY shop_id, TUMBLE(ts, INTERVAL '60' SECOND);

3.3 实时数仓架构（Lambda / Kappa）

数仓要"又快又准"：Lambda 用批 + 流双路径分别保证准确与实时；Kappa 只用流，简化架构但依赖强流处理能力。

  • Lambda：批路径（Spark/Hive 全量重算，准） + 流路径（Flink 增量，快）；服务层合并；维护两套代码
  • Kappa：只有流（Kafka 保留全量事件，Flink 随时重放重算）；代码一套，重放成本可控
  • 实时分层：ODS（Kafka 原始）→ DWD（清洗/明细）→ DWS（汇总指标）→ 结果写 OLAP（Doris/ClickHouse）
  • 选型：批流一体引擎（Flink 批模式 / Spark 流模式）正在模糊边界；多数团队 Kappa + 定期离线核对
# Lambda 架构（双路径合并）
实时路径：MySQL binlog → Canal → Kafka(ODS) → Flink(DWD/DWS) → Doris（秒级）
离线路径：Sqoop → HDFS(ODS) → Spark/Hive(DWD/DWS) → 结果表（天级，全量校准）
服务层：查询优先走 Doris 实时结果，定时用离线结果对账修正

# Kappa 架构（单一流路径）
binlog → Kafka（保留 7 天全量）→ Flink 重放/增量 → Doris
# 修正 bug 或口径调整：从 Kafka 某 offset 重放任务即可，无需批路径

3.4 数据湖与湖仓一体

数据湖把"原始数据"以开放格式全量留存（schema-on-read），数仓强调"治理后数据"（schema-on-write）；湖仓一体用表格式统一两者。

  • 数据湖：存储任意格式原始数据（结构化/半/非结构化），低成本、可回溯；问题：无 schema 约束、易变数据沼泽
  • 表格式：Delta Lake / Apache Iceberg / Hudi——给湖上文件加事务、索引、时间旅行（time travel）、ACID
  • 湖仓一体：同一份数据既能"湖"存原样，又能"仓"查询分析；元数据统一、避免双份拷贝
  • 对比：数仓=加工后可靠、贵；湖=原始全量、灵活；一体=兼顾
-- Apache Iceberg 表：湖上的"数仓表"（Spark SQL 示例）
CREATE TABLE iceberg_db.orders (
  order_id BIGINT, shop_id INT, amount DECIMAL(12,2), ts TIMESTAMP
) USING iceberg
PARTITIONED BY (days(ts));                       -- 隐藏分区：按天

-- 时间旅行：查历史版本（回看某时刻全量）
SELECT * FROM iceberg_db.orders
  VERSION AS OF 582988352348686238;              -- snapshot id

-- 增量读取（CDC 消费湖表变化）
SELECT * FROM iceberg_db.orders.changes
WHERE ts > '2026-10-10 00:00:00';

3.5 OLAP 引擎（ClickHouse / Doris）

OLAP 引擎服务"高并发、多维度、秒级聚合"的查询：列式存储 + 向量化执行 + 预聚合，与 OLTP 的行存库是两套设计。

  • 列式存储：只读所需列（列裁剪）+ 高压缩比（同列类型一致）；对比行存"读整行"
  • ClickHouse：MergeTree 家族表引擎；向量化执行 + SIMD，单表聚合极快；join 能力弱
  • Apache Doris：MPP 架构，支持标准 SQL + join + 实时导入（Unique 模型做 upsert）；适合报表与即席查询
  • 选型：单表大聚合 / 明细查询 → ClickHouse；多表 join + 实时更新报表 → Doris；检索带评分 → ES
-- ClickHouse：MergeTree 建表 + 物化视图预聚合
CREATE TABLE shop_orders (
  shop_id UInt32, amount Float64, ts DateTime
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (shop_id, ts);                        -- 排序键 = 查询裁剪键

-- 秒级大聚合（10 亿行内毫秒级返回）
SELECT shop_id, sum(amount), count()
FROM shop_orders
WHERE ts >= '2026-10-01' AND ts < '2026-11-01'
GROUP BY shop_id
ORDER BY sum(amount) DESC LIMIT 100;
-- Doris：Unique 模型支持实时 upsert（binlog → 实时导入）
CREATE TABLE dws_shop_daily (
  shop_id INT, dt DATE, revenue DECIMAL(18,2),
  UNIQUE KEY(shop_id, dt)
) DISTRIBUTED BY HASH(shop_id) BUCKETS 16
PROPERTIES ("replication_num" = "2");

-- 即席多表 join 报表
SELECT s.city, SUM(d.revenue)
FROM dws_shop_daily d JOIN dim_shop s ON d.shop_id = s.shop_id
WHERE d.dt = '2026-10-10' GROUP BY s.city;

3.6 数据治理与数据质量

数据治理是"让数据可信、可用、可管"的工程：元数据与血缘回答"数据从哪来"，质量校验保证"数据对不对"，安全分级控制"谁能看"。

  • 元数据管理：表/字段/负责人/口径统一登记（如 DataHub、Atlas）；数据血缘记录加工链路，问题可追溯
  • 数据质量四性：完整性（无缺失）、准确性（值正确）、一致性（跨系统口径一致）、及时性（按时到达）
  • 质量手段：任务内校验（空值/唯一/范围）+ 任务后对账（行数/金额比对）+ 告警与订正
  • 安全分级：敏感字段（手机号/身份证）加密、脱敏、权限隔离；分级审批
-- 数据质量校验：任务跑完自动检查（示例）
-- 1) 完整性：关键字段空值率
SELECT COUNT(*) AS total,
       SUM(CASE WHEN order_id IS NULL OR order_id = '' THEN 1 ELSE 0 END) AS bad
FROM ods_order WHERE dt = '2026-10-10';

-- 2) 唯一性：主键重复检测
SELECT order_id, COUNT(*) c FROM ods_order
WHERE dt = '2026-10-10'
GROUP BY order_id HAVING c > 1;

-- 3) 一致性：金额不允许为负 / 超上限
SELECT COUNT(*) FROM ods_order
WHERE dt = '2026-10-10' AND (amount < 0 OR amount > 1000000);

-- 4) 及时性：分区数据应在约定时间前就绪（调度系统校验）
-- 任一检查失败 → 阻塞下游 + 告警

6常见误区与实战要点

  • "大数据 = Hadoop"：Hadoop 是批时代产物；现代体系是 Hadoop + Spark + Flink + 云上对象存储的组合，按场景选型
  • HDFS 适合所有存储：小文件（< 128MB）在 HDFS 是灾难（元数据膨胀）；小文件先合并（SequenceFile / 分区合并）
  • Kafka 全局有序：Kafka 只保证分区内有序；全局有序 = 单分区 = 放弃并行
  • 窗口用处理时间就行：乱序/延迟场景必须用事件时间 + 水位线，否则统计口径漂移
  • 数仓 = 大数据集群：数仓首先是模型设计（维度建模），工具只是实现；没有模型的集群只是"数据沼泽"
  • 精确一次 = 不重不漏万事大吉：精确一次保证"恰好一次处理"，但业务侧幂等（重复写入不翻倍）仍要自己做
  • 数据质量是事后检查：质量要在采集/加工每一环做约束（非空、枚举、阈值），最后一道校验只是兜底
