1.1 关系模型与 SQL 基础（DDL / DML / DQL）

关系型数据库用"表"组织数据。SQL 是唯一通用语言，分 DDL（结构）、DML（数据）、DQL（查询）。

  • 关系模型：表 = 关系，行 = 元组，列 = 属性；主键唯一标识一行，外键表达关联
  • 范式：1NF（列不可再分）、2NF（非主属性完全依赖主键）、3NF（消除传递依赖）；实际工程常适度反范式换性能
  • DDL：CREATE / ALTER / DROP TABLE；DML：INSERT / UPDATE / DELETE；DQL：SELECT
  • 连接 JOIN：INNER（交集）、LEFT（左全 + 右匹配）、RIGHT；聚合 GROUP BY + HAVING（对分组后过滤）
  • 备份恢复基本方法：mysqldump 逻辑备份（-u -p --single-transaction）、物理备份（Xtrabackup）、binlog 增量恢复
-- DDL：建表
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  status TINYINT DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- DML + DQL：两表连接聚合
SELECT u.name, COUNT(o.id) AS cnt, SUM(o.amount) AS total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.created_at >= '2026-01-01'
GROUP BY u.id, u.name
HAVING cnt > 0
ORDER BY total DESC
LIMIT 10;

1.2 MySQL 存储引擎与表设计

InnoDB 是 MySQL 5.5+ 的默认引擎。表设计决定系统的性能上限。

  • InnoDB vs MyISAM：InnoDB 支持事务、行级锁、外键、崩溃恢复（redo log）；MyISAM 只有表锁、无事务，已淘汰
  • 字段类型：整数 TINYINT ~ BIGINT 按需选；金额用 DECIMAL 不用 FLOAT（精度）；长文本用 TEXT；可变长度 VARCHAR vs 定长 CHAR
  • 主键设计：优先自增或雪花 ID（有序）；InnoDB 聚簇索引按主键组织数据，主键应短且稳定
  • 字符集统一 utf8mb4（支持 emoji）；引擎级别与建表规范
CREATE TABLE product (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  sku VARCHAR(64) NOT NULL COMMENT 'SKU',
  price DECIMAL(10,2) NOT NULL DEFAULT 0 COMMENT '价格',
  stock INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1 COMMENT '1上架 0下架',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_sku (sku),
  KEY idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品表';

1.3 事务 ACID 与隔离级别

事务把多条操作绑定为"要么全成功、要么全失败"。隔离级别决定并发读写的可见性。

  • ACID：原子性（undo log）、一致性（约束）、隔离性（锁/MVCC）、持久性（redo log）
  • 隔离级别（由低到高）：READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ（MySQL 默认）、SERIALIZABLE
  • 对应问题：脏读（读到未提交）、不可重复读（同查两次结果不同）、幻读（范围内行数变化）
  • MVCC：快照读（普通 SELECT）不阻塞；当前读（SELECT ... FOR UPDATE）走最新版本加锁
-- 开启事务并演示
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 或 ROLLBACK;

-- 查看/设置隔离级别
SELECT @@transaction_isolation;              -- REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

1.4 索引的基本概念

索引是数据库的"目录"。MySQL 默认用 B+ 树组织索引，平衡读性能与写代价。

  • 聚簇索引：InnoDB 表按主键组织的 B+ 树，叶子节点存整行数据；二级索引叶子存主键值，需回表
  • B+ 树特点：多叉矮树、叶子有序链表，适合范围查询；节点按页（16KB）加载
  • 建索引场景：WHERE 等值/范围、ORDER BY、JOIN 列、唯一约束
  • 不建索引场景：低区分度列（性别）、频繁写的小表、大文本
-- 建索引（推荐用 ALTER，不阻塞写入）
ALTER TABLE user ADD INDEX idx_age_name (age, name);
-- 唯一索引
ALTER TABLE user ADD UNIQUE KEY uk_email (email);
-- 查看索引
SHOW INDEX FROM user;

B+ 树索引结构：矮树 + 叶子有序链表，3~4 层可支撑千万级数据

1.5 Linux 常用命令与文件权限

后端服务最终跑在 Linux 上。文件、进程、网络、服务管理是日常高频操作。

  • 目录结构：/etc 配置、/var 日志与数据、/home 用户、/opt 软件、/tmp 临时

1.6 Shell 脚本基础

Shell 脚本把运维操作固化成可复用工具：备份、部署、巡检都能自动化。

  • shebang：#!/bin/bash；变量 $VAR / ${VAR}；位置参数 $1 $2、$# 个数、$? 上一条命令退出码
  • 条件：if [ 条件 ]; then ... fi；test 与 [[ ]]；数字 -eq/-gt，字符串 = / !=
  • 循环：for i in ...; do done；while read line; done < file
  • 函数 function_name() { ... }；管道 | 与重定向 > / 2>&1
#!/bin/bash
# 简易数据库备份脚本
set -e
BACKUP_DIR=/backup/mysql
DATE=$(date +%Y%m%d_%H%M%S)
DB_USER=root
DB_PASS='******'

mkdir -p "$BACKUP_DIR"
mysqldump -u"$DB_USER" -p"$DB_PASS" --single-transaction   --routines --triggers myapp > "$BACKUP_DIR/myapp_$DATE.sql"

# 保留最近 7 天
find "$BACKUP_DIR" -name "myapp_*.sql" -mtime +7 -delete
echo "备份完成: $DATE"

1.7 Nginx 基础配置

Nginx 是高性能 Web 服务器 / 反向代理。静态资源、网关入口、负载均衡都由它承担。

  • 核心指令块：http → server（虚拟主机）→ location（路径规则）；listen / server_name / root
  • 反向代理：location /api/ { proxy_pass http://backend; }；透传头 proxy_set_header
  • 负载均衡：upstream 定义后端组，策略轮询 / weight 加权 / ip_hash 会话保持
  • 静态缓存与 gzip 压缩；HTTPS 证书配置（listen 443 ssl）
http {
  upstream backend {
    server 10.0.0.11:8080 weight=3;
    server 10.0.0.12:8080 weight=1;
  }

  server {
    listen 80;
    server_name api.example.com;

    location /static/ {
      root /data/www;               # 静态资源
      expires 7d;
    }
    location /api/ {
      proxy_pass http://backend;     # 反向代理
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
    }
  }
}

2.1 MySQL 索引原理进阶（覆盖索引 / 最左前缀）

索引原理决定 SQL 快慢。联合索引的顺序、覆盖索引的写法是优化核心。

  • 覆盖索引：索引包含查询所需全部字段（Extra 显示 Using index），无需回表，快
  • 最左前缀：联合索引 (a, b, c) 按 a、a+b、a+b+c 生效；跳过 a 直接用 b 失效
  • 索引失效场景：对列做函数/运算、隐式类型转换（varchar 列传数字）、LIKE '%xx'、OR 连接非索引列
  • 索引下推（ICP）：联合索引条件下推到存储引擎过滤，减少回表
-- 联合索引 (age, name)
ALTER TABLE user ADD INDEX idx_age_name (age, name);

-- 生效：age 等值 + name 前缀
SELECT id FROM user WHERE age = 30 AND name LIKE '张%';
-- 失效：跳过了 age，只用 name 无法走 idx_age_name
SELECT id FROM user WHERE name = '张三';
-- 覆盖索引：只查 (id, age, name)，Extra = Using index
EXPLAIN SELECT id, age, name FROM user WHERE age = 30;

2.2 SQL 优化与执行计划（EXPLAIN）

EXPLAIN 是 SQL 优化的唯一入口：先看 type，再看 key 与 rows，最后看 Extra。

  • type 从好到坏：const / eq_ref / ref / range / index / ALL（全表扫描）
  • key：实际用到的索引；rows：预估扫描行数；Extra：Using index（覆盖）、Using filesort（排序未用索引）、Using temporary（临时表）
  • 慢查询治理：开启 slow_query_log + long_query_time=1，用 mysqldumpslow / pt-query-digest 汇总
  • 深分页优化：LIMIT 100000,20 扫描大量行 → 延迟关联（先取主键）或游标分页（WHERE id > last_id）
EXPLAIN SELECT u.name, o.amount
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 1 AND o.created_at > '2026-01-01'
ORDER BY o.id
LIMIT 20;
-- 关注列：type(ALL→优化为 range/ref)、key、rows、Extra

-- 深分页优化：延迟关联
SELECT u.name, o.amount FROM orders o
JOIN users u ON u.id = o.user_id
JOIN (SELECT id FROM orders WHERE status=1
      ORDER BY id LIMIT 100000, 20) t ON t.id = o.id;

2.3 事务隔离级别与锁机制

InnoDB 用锁 + MVCC 实现隔离。行锁粒度细，间隙锁防幻读，死锁靠检测与回滚。

  • 锁类型：共享锁 S（读不互斥）、排他锁 X（写互斥）；Record Lock 行锁、Gap Lock 间隙锁、Next-Key Lock（行 + 间隙，InnoDB 在 REPEATABLE READ 防幻读）
  • 快照读（普通 SELECT 走 MVCC，不加锁）vs 当前读（SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE 加锁）
  • 死锁：两个事务互相持有对方需要的锁；MySQL 自动检测并回滚代价较小的事务；innodb_lock_wait_timeout 控制等待
  • 减少锁冲突：短事务、精确条件走索引、批量操作分批、避免大范围锁
-- 当前读：扣库存必须加锁防止超卖
START TRANSACTION;
SELECT stock FROM product WHERE id = 1 FOR UPDATE;
-- 校验 stock > 0 后 UPDATE
UPDATE product SET stock = stock - 1 WHERE id = 1;
COMMIT;

-- 查看锁等待与死锁
SHOW ENGINE INNODB STATUS;
SELECT * FROM information_schema.INNODB_TRX;

2.4 Redis 数据结构与缓存模式

Redis 是内存键值数据库，单线程事件模型。五种基础结构覆盖绝大多数场景。

  • 五种结构：String（计数/缓存）、Hash（对象字段）、List（队列）、Set（去重/交集）、ZSet（排行榜，score 排序）
  • 扩展结构：Bitmap（签到）、HyperLogLog（UV 统计）、Geo（地理位置）、Stream（消息队列）
  • 缓存读写模式：Cache Aside——先查缓存，未命中查库并回写；更新时先更库再删缓存
  • 三大问题：穿透（查不存在数据，用空值缓存/布隆过滤）、击穿（热点 key 过期，互斥重建）、雪崩（大量 key 同时过期，过期时间加随机数）
# 基础命令
SET user:1:name "张三" EX 3600        # 带过期
GET user:1:name
HSET user:1 field name "张三" age 28   # Hash
LPUSH task:queue "job-1"               # List 队列
SADD tag:hot "java" "redis"            # Set
ZADD rank 100 "user1" 95 "user2"       # ZSet 排行榜
ZREVRANGE rank 0 9 WITHSCORES

# 缓存穿透防御：空值缓存
SET empty:key:xxx "" EX 60

2.5 主从复制与读写分离

主从复制把写库的 binlog 同步到从库重放，读写分离让查询打到从库、减轻主库压力。

  • 复制原理：主库 binlog → 从库 IO 线程拉取写 relay log → SQL 线程顺序重放
  • 复制模式：异步（默认，可能丢）、半同步（至少一个从库确认）、GTID（全局事务 ID，易管理）
  • 读写分离：应用层双数据源 / 中间件（ProxySQL、MyCat）；写走主、读走从
  • 主从延迟：查询刚写入即读从库会读到旧数据；缓解——关键读走主库、延迟监控（seconds_behind_master）

2.6 Docker 镜像与容器

Docker 把应用与依赖打包成镜像，容器即开即用，彻底解决环境不一致。

  • 镜像分层：只读层叠加（Union FS），层可复用；容器 = 镜像 + 可写层
  • Dockerfile 指令：FROM 基础镜像、RUN 构建命令、COPY 拷贝、CMD / ENTRYPOINT 启动命令、EXPOSE 端口、WORKDIR
  • 常用命令：build / run -d -p / exec -it / logs / ps / images / rmi
  • 网络：默认 bridge；-p 端口映射；--network host；容器间用自定义 network + 服务名通信
  • 数据持久化：volume（docker volume）/ bind mount（-v 目录映射）；容器删除数据不丢
# Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production      # 精简依赖
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

# 构建与运行
docker build -t my-app:v1 .
docker run -d --name app -p 3000:3000   -v /data/logs:/app/logs my-app:v1
docker exec -it app sh
docker logs -f app
docker ps -a

2.7 Docker Compose 多容器编排

Compose 用一份 YAML 描述多个服务（应用 + 数据库 + 缓存），一条命令拉起整个环境。

  • docker-compose.yml 顶层：services（服务定义）/ networks / volumes
  • 服务字段：image / build / ports / environment / volumes / depends_on（启动顺序）/ restart（失败重启策略）
  • healthcheck：健康检查，配合 depends_on condition: service_healthy 等待就绪
  • 常用命令：up -d / down / logs -f / ps / exec 服务名 命令
# docker-compose.yml
version: "3.8"
services:
  app:
    build: .
    ports: ["3000:3000"]
    environment:
      DB_HOST: mysql
      REDIS_HOST: redis
    depends_on:
      mysql:
        condition: service_healthy
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: "******"
      MYSQL_DATABASE: myapp
    volumes: ["dbdata:/var/lib/mysql"]
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 5
  redis:
    image: redis:7-alpine
volumes:
  dbdata:

2.8 CI/CD 流水线

CI/CD 让提交即构建、测试、部署。流水线把重复劳动自动化，发布从"提心吊胆"变"可回滚"。

  • 概念：CI 持续集成（提交后自动构建测试）、CD 持续交付/部署（通过后自动发到环境）
  • 流水线阶段：checkout → install → build → test → package（镜像）→ deploy → 通知
  • 工具：Jenkins（Pipeline 脚本）、GitLab CI（.gitlab-ci.yml）、GitHub Actions（workflow）
  • 发布策略：蓝绿（两套环境切换）、金丝雀（灰度放量）、滚动（分批替换）；失败自动回滚
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 18 }
      - run: npm ci
      - run: npm run test
      - run: npm run build
      - name: Build & push image
        run: |
          docker build -t registry/app:${{ github.sha }} .
          docker push registry/app:${{ github.sha }}
      - name: Deploy
        run: ssh deploy@host "docker compose up -d app"

2.9 Kubernetes 核心概念

K8s 是容器编排的事实标准：声明期望状态，集群自动达成并自愈。

  • 架构：Master 组件（API Server / etcd / Scheduler / Controller Manager）+ Node 组件（kubelet / kube-proxy / 容器运行时）
  • 核心对象：Pod（最小调度单元）、Deployment（管理副本 + 滚动更新，内含 ReplicaSet）、Service（稳定访问入口：ClusterIP / NodePort / LoadBalancer）、ConfigMap / Secret（配置）、Namespace（隔离）
  • 自愈：Pod 挂了 ReplicaSet 自动重建；探针 liveness（存活）/ readiness（就绪）
  • kubectl：apply / get / describe / logs / exec / scale / rollout
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: web, namespace: prod }
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: registry/app:v1
          ports: [{ containerPort: 3000 }]
          livenessProbe:
            httpGet: { path: /healthz, port: 3000 }

# Service 暴露
apiVersion: v1
kind: Service
metadata: { name: web-svc }
spec:
  selector: { app: web }

3.1 分库分表与分布式 ID

单库单表到瓶颈后：先垂直拆分（按业务/字段），再水平拆分（按分片键）。分片键决定查询效率。

  • 垂直拆分：按业务拆库（订单库/用户库）、按列拆表（大字段拆出）；解决单库连接数
  • 水平拆分：按分片键取模 / 范围 / 一致性哈希；分片键必须覆盖核心查询（如 user_id 或 order_id）
  • 分布式 ID 要求：全局唯一、趋势递增、高可用；雪花算法（时间戳 41bit + 机器 10bit + 序列 12bit）；号段模式（Leaf 一次取一段）；UUID 无序且长，不推荐作主键
  • 中间件：ShardingSphere-JDBC（客户端分片）/ ShardingSphere-Proxy（代理）；跨分片查询、分布式事务是代价
// 雪花算法核心思路（简化）
long id = (timestamp - EPOCH) << 22      // 41 位时间戳
        | (workerId << 12)               // 10 位机器
        | sequence;                      // 12 位序列

// ShardingSphere 分片规则（YAML 片段）
rules:
  - !SHARDING
    tables:
      order:
        actualDataNodes: ds.order_${0..15}
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: hash_mod
    shardingAlgorithms:
      hash_mod:
        type: HASH_MOD
        props: { sharding-count: 16 }

3.2 缓存一致性（Cache Aside / 延迟双删）

缓存与数据库双写必然存在一致窗口。目标不是零延迟一致，而是尽快收敛到最终一致。

  • 标准姿势 Cache Aside：读——先缓存后库；写——先更库、再删缓存（不是更新缓存，避免并发写旧值）
  • 延迟双删：更库 → 删缓存 → 延迟 100~500ms 再删一次，兜住"删缓存后恰好有读回写"的竞态
  • 最终一致增强：订阅 binlog（Canal）异步刷新缓存，与业务代码解耦
  • 极端一致场景（强一致）宁可不加缓存或走"缓存旁路直读库"

3.3 Redis 持久化、哨兵与分布式锁

Redis 是内存库，持久化决定重启不丢数据；哨兵保证可用性；分布式锁是分布式互斥的基石。

  • 持久化：RDB（定期快照，fork 子进程，恢复快但可能丢最后一次快照后数据）；AOF（追加写命令，fsync 策略 everysec，最多丢 1 秒）；可混用
  • 高可用：哨兵 Sentinel 监控主节点，主挂后自动选举从库提升；集群 Cluster 用 16384 个槽位分片，支持多主多从
  • 分布式锁：SET key value NX EX 秒级原子加锁；value 存唯一标识，释放时 Lua 脚本校验后 DEL 防误删；Redisson 看门狗自动续期
  • 锁的边界：进程内锁只在本机有效；跨实例互斥必须 Redis/ZooKeeper；锁要有过期时间防死锁
# 加锁：原子 SET NX EX（Redis 6+ 推荐 SET key val NX EX seconds）
SET lock:order:1001 "token-abc" NX EX 10

# 释放：Lua 脚本保证"校验是自己"与"删除"原子
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end

# RDB + AOF 配置
save 900 1 300 10 60 10000        # RDB 触发条件
appendonly yes
appendfsync everysec

3.4 Elasticsearch 倒排索引与查询 DSL

ES 是分布式全文搜索引擎：倒排索引让"关键词搜文档"从全表扫描变成词项查找。

  • 倒排索引：文档分词后建立 词项 → 文档ID 的映射；查询时按词查文档，再打分排序
  • 核心概念：索引（库）、文档（行）、分片 + 副本；7.x 移除多类型
  • 查询 DSL：match（分词匹配）、term（精确值）、range（范围）、bool（must / should / must_not 组合）、aggs（聚合统计）
  • 分词：标准 / IK 中文分词；keyword 字段不分词用于精确过滤
  • 适用：全文检索、日志分析（配合 Filebeat/Kibana）、商品搜索；事务与强一致场景仍用 MySQL
# 检索标题含"手机"且价格 1000~5000 的商品
GET /product/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "手机" } }
      ],
      "filter": [
        { "range": { "price": { "gte": 1000, "lte": 5000 } } },
        { "term": { "status": 1 } }
      ]
    }
  },
  "aggs": {
    "brand_count": { "terms": { "field": "brand.keyword" } }
  },
  "from": 0, "size": 20
}

3.5 数据库高可用与容灾备份

高可用 = 主节点故障后快速切换不丢服务；容灾 = 数据可恢复到故障前一刻。

  • 高可用架构：主从 + 自动故障转移（MHA / Orchestrator / 云 RDS 自动切换）；半同步复制减少丢数据窗口
  • 读写分离 + 多从库：读能力水平扩展；从库可跨机房（异地灾备）
  • 备份体系：全量（mysqldump 逻辑 / Xtrabackup 物理热备）+ 增量（binlog）；定期恢复演练验证备份可用
  • 容灾：同城双活（机房间 RPO≈0）、异地多活（单元化）；RTO（恢复时间）/ RPO（丢失量）是核心指标
  • 云 RDS：自动备份、多可用区、只读实例、一键主备切换，降低运维门槛

3.6 监控与可观测性（Prometheus / ELK / 链路追踪）

可观测性三支柱：指标（Metrics）、日志（Logs）、链路（Traces）。先有观测，才能谈稳定。

  • 指标：Prometheus 拉取 + 规则告警 + Grafana 面板；exporter（node_exporter 机器、mysqld_exporter、redis_exporter）
  • 日志：ELK 栈（Filebeat → Logstash → Elasticsearch → Kibana）；轻量替代 Loki + Grafana；日志分级与采样
  • 链路追踪：SkyWalking / Zipkin，Trace + Span 还原一次请求经过的所有服务耗时，定位慢节点
  • 告警：Alertmanager 规则（CPU > 90% 5 分钟、错误率、延迟 P99）；分级与值班 on-call；告警要可行动、去重

6常见误区与实战要点

常见误区：
  • 索引失效不自知：对索引列做函数 / 隐式类型转换 / LIKE '%xx'，EXPLAIN 后 type=ALL 才发现
  • Redis 当主存储：只配内存不配持久化，重启丢全部数据；热点数据才进缓存，落库必须保底
  • 缓存三大问题裸奔：穿透 / 击穿 / 雪崩不处理，流量洪峰直接打到数据库
  • 分库分表过早：单表几百万就拆，跨分片查询与分布式事务复杂度陡增；先做索引与归档
  • 主从延迟不自知：写完立刻读从库读到旧数据，关键读必须走主库
  • mysqldump 高峰期裸跑：无锁备份会锁表影响线上，用 --single-transaction 或物理热备
  • Docker 镜像不精简：每层都大、不清理，镜像几百 MB，拉取部署都慢；多阶段构建 + .dockerignore
  • K8s 服务直接暴露 Pod IP：Pod 会重建 IP 会变，必须通过 Service 访问
  • 监控只看大盘不看告警：指标存了没人告警等于没监控，规则要可行动、可去重
