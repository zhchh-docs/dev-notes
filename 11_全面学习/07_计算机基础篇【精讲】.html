2基础层 · 入门必备

1.1 二进制与位运算

计算机的一切都是 0 和 1。理解原码/反码/补码与位运算，是读源码、做性能优化（位掩码、状态压缩）的底层语言。

  • 进制基础：二进制 → 十进制 / 十六进制互转；1 byte = 8 bit，n 位无符号数范围 0~(2^n − 1)
  • 原码 / 反码 / 补码：负数用补码表示（取反加一）；补码让加减法统一为加法，0 只有一种表示
  • 六种位运算：&（与，掩码）、|（或，置位）、^（异或，翻转 / 无临时变量交换）、~（取反）、<< / >>（移位，乘除 2^n）
  • 经典用途：奇偶判断用 n&1
  • 取最低位 1 用 n&-n；权限用位掩码；状态用位压缩
# 补码：-5 在 8 位下的表示
#   5     = 0000 0101
#   取反   = 1111 1010
#   +1    = 1111 1011  ← -5 的补码
# 验证：-5 + 5 = 1111 1011 + 0000 0101 = 1 0000 0000（进位丢弃）= 0 ✓

# 位运算实战（Python）
n = 0b101010
print(n & 1)        # 0 → 偶数（奇偶判断）
print(4 & 0b111100) # 掩码：只保留高 4 位 → 0b0100 = 4
print(1 << 4)       # 16（乘 2^4）
print(16 >> 2)      # 4（除 2^2）
# 权限位掩码
READ, WRITE, EXEC = 0b100, 0b010, 0b001
perm = READ | WRITE            # 0b110
print(bool(perm & EXEC))       # False → 无执行权限
print(bool(perm & WRITE))      # True → 有写权限

补码的数轴：负数从高位往下表示，减法变加法

1.2 数据单位与字符编码

"中文乱码"是每个开发者都踩过的坑。搞清 bit / Byte 与 ASCII / Unicode / UTF-8 的层次，乱码一眼看穿。

  • 数据单位：bit（位）→ Byte（字节，8 位）→ KB / MB / GB / TB；存储厂商按 1000，系统按 1024（注意差异）
  • ASCII：7 位 128 个字符（含控制符），一个字节存一个 ASCII 字符
  • Unicode：为每个字符分配唯一码点（U+XXXX），如"中"= U+4E2D；Unicode 只是字符集，不管存储
  • UTF-8：Unicode 的可变长存储编码，1~4 字节；ASCII 兼容（1 字节），中文 3 字节，emoji 4 字节；还有 UTF-16（2~4 字节）、GBK（中文 2 字节）
  • 乱码本质：字节流用一种编码解读另一种编码的产物（如 UTF-8 字节按 GBK 解）；修复 = 找对编码重新解码
# Python 编码解码示例
text = "中"
print(hex(ord(text)))            # 0x4e2d → Unicode 码点 U+4E2D
b = text.encode('utf-8')         # b'\xe4\xb8\xad'（3 字节）
print(len(b))                    # 3 → UTF-8 中文占 3 字节
print(b.decode('utf-8'))         # 中 ✓

# 乱码演示：UTF-8 字节按 GBK 解码
wrong = b.decode('gbk')          # '涓' → 乱码
# 修复：重新按 UTF-8 解码
print(wrong.encode('gbk').decode('utf-8'))  # 中 ✓

# UTF-8 编码规则（首个字节高位数 = 总字节数）
# 0xxxxxxx            → 1 字节（ASCII）
# 110xxxxx 10xxxxxx   → 2 字节
# 1110xxxx 10xxxxxx 10xxxxxx → 3 字节（中文）
# 11110xxx ...        → 4 字节（emoji / 生僻字）

字符 → 码点 → 字节流的转换链

1.3 CPU 与内存的基本模型

程序性能瓶颈 90% 在"数据离 CPU 有多远"。存储层级是理解缓存、Redis、数据库缓冲池的统一模型。

  • 存储金字塔：寄存器（~0.3ns）→ L1/L2/L3 缓存（~1-40ns）→ 主存（~100ns）→ 磁盘/SSD（~0.1-10ms）；越往上越快、越贵、越小
  • 寄存器：CPU 内部，存指令、地址、临时数据；32 位 CPU 的寄存器 32 位宽，可寻址 4GB（2^32）
  • 缓存：解决 CPU 与主存速度差；以缓存行（通常 64 字节）为单位加载；局部性原理是缓存命中的前提
  • 主存与总线：内存通过总线与 CPU 交换；一次访存 = 寄存器操作时间的 ~100 倍，所以"能不进内存就不进"
# 直观理解速度差（数量级，来自经典数字表）
# 寄存器          ~0.3 ns     （CPU 一拍）
# L1 缓存         ~1 ns
# L2 缓存         ~5 ns
# L3 缓存         ~15-40 ns
# 主存            ~100 ns     （一次内存访问 ≈ 300 个寄存器周期）
# SSD             ~0.1 ms     （≈ 30 万 ns）
# 机械磁盘        ~10 ms      （≈ 3000 万 ns）

# 性能启示（写代码时的经验法则）
# 1. 循环里避免随机内存访问 → 顺序读利用缓存预取
# 2. 热数据放缓存（Redis），冷数据落库 —— 就是把访问从 100ns 提升到 1ns 的问题
# 3. 数据结构要"缓存友好"：紧凑数组 > 指针链表（后者每次访问都在跳内存）

存储金字塔：性能优化 = 让数据尽量待在金字塔上层

1.4 冯·诺依曼结构与指令执行

现代计算机几乎都是冯·诺依曼架构：程序和数据同存、按地址访问、顺序执行。理解指令周期，才能理解"程序是怎么跑起来的"。

  • 五大部件：运算器（ALU 做计算）、控制器（取指令、指挥）、存储器（存指令和数据）、输入设备、输出设备
  • 存储程序思想：指令和数据都存内存、都以二进制表示——这是冯·诺依曼与"插线式"计算机的根本区别
  • 指令周期五步：取指（IF）→ 译码（ID）→ 执行（EX）→ 访存（MEM）→ 写回（WB），周而复始（CPU 主频 = 每秒多少个周期）
  • 变体：哈佛结构（指令与数据分开存储，如嵌入式 / DSP），性能更好但结构更复杂；现代 CPU 内部多用哈佛 + 外部冯·诺依曼
# 一条指令的生命周期（以 add a, b 为例）
# 1. IF  取指：从 PC（程序计数器）指向的地址读出指令
# 2. ID  译码：控制器解析"add"和操作数地址
# 3. EX  执行：ALU 完成 a + b
# 4. MEM 访存：如需读内存中的值则发生（本指令无）
# 5. WB  写回：结果写回寄存器/内存
# 6. PC  +4：程序计数器指向下一条指令（顺序执行的基础）

# 分支与循环的本质
# - if / for / while 只是改变 PC 的跳转指令
# - 跳转预测失败是现代 CPU 性能损失的重要来源（分支预测）
# 可运行验证（Python 反汇编看到指令序列）
import dis
def add(a, b):
    return a + b
dis.dis(add)
# 输出中的 LOAD_FAST / BINARY_OP / RETURN_VALUE 即"取指-执行"的软件层体现

冯·诺依曼结构：五大部件 + 存储程序

1.5 操作系统基本概念

操作系统是"资源管家"：管理 CPU、内存、文件、设备，并把裸机包装成安全的编程接口。用户态 / 内核态是理解系统调用的钥匙。

  • OS 四大管理：进程管理（调度）、内存管理（虚拟内存）、文件管理（VFS）、设备管理（驱动）
  • 内核态 vs 用户态：内核态可执行特权指令（访问硬件、改内存映射），用户态受限；切换成本高（约 100ns~1µs），所以"减少系统调用"是性能优化的常见手段
  • 系统调用：用户态程序请求内核服务的唯一通道，如 read / write / fork / mmap；文件描述符（fd）是内核给进程的"文件句柄"
  • 进程 / 线程 / 文件：进程是资源分配单位，线程是调度单位，文件是数据抽象（"一切皆文件"）
# 用户态 → 内核态：系统调用的发生点
import os
fd = os.open("/tmp/a.txt", os.O_CREAT | os.O_WRONLY)  # open 系统调用
os.write(fd, b"hello")                                 # write 系统调用
os.close(fd)                                           # close 系统调用

# Linux 查看进程与系统调用
# ps -ef                → 查看进程（PID / PPID / 状态）
# strace -c ls          → 统计 ls 用了多少系统调用
# ltrace ls             → 跟踪库函数调用
# /proc/PID/status      → 进程详细信息（内存、线程数）

# 一个进程的"虚拟内存视图"（cat /proc/PID/maps 可看）
# 高地址：栈（向下增长）
#         ↓
#         ↑
# 低地址：文本段(代码) → 数据段(全局变量) → 堆(向上增长)
# 中间空洞由 mmap 映射（动态库、共享内存）

用户态 / 内核态 / 硬件三层，系统调用是唯一的桥

3标准层 · 日常开发

2.1 进程与线程模型

进程是资源容器，线程是执行流。理解 PCB、上下文切换和地址空间布局，是理解线程池、协程、容器的基础。

  • 进程：拥有独立的地址空间（代码 / 数据 / 堆 / 栈）、文件表、信号处理；进程间默认隔离，通信靠 IPC
  • PCB（进程控制块）：内核记录进程状态 / 寄存器现场 / 内存映射 / 打开文件；上下文切换 = 保存 A 的 PCB、恢复 B 的 PCB
  • 进程三态：就绪（Ready）→ 运行（Running）→ 阻塞（Blocked，等 IO / 锁）；IO 密集型进程多数时间在 Blocked
  • 线程：同一进程内共享地址空间与文件，独有栈 + 寄存器（线程局部状态）；创建 / 切换成本远低于进程（不换地址空间）
  • 多线程模型：1:1（Java 线程 = 内核线程）、N:1（协程 / 绿色线程）、N:M（混合）
# Java 中进程 / 线程的直观对应
# - 一个 JVM = 一个操作系统进程
# - 每次 new Thread() = 一个内核线程（1:1 模型）
# - 线程池 = 复用线程，避免频繁创建销毁
ExecutorService pool = Executors.newFixedThreadPool(8); // 8 个常驻线程
pool.submit(() -> System.out.println(Thread.currentThread().getName()));

# 进程状态变化（ps 里的 S 列）
# R 运行/就绪   S 可中断睡眠(等IO/锁)   D 不可中断睡眠   Z 僵尸
# ps -eo pid,stat,comm | grep java
# 发现大量 D 状态 → 磁盘 IO 卡住；大量 R → CPU 或锁竞争

# 线程独有 vs 共享（速记）
# 独有：程序计数器、栈、寄存器、线程局部变量(ThreadLocal)
# 共享：堆、方法区、文件描述符、信号

进程 = 隔离的容器；线程 = 容器内的执行流

2.2 进程间通信（IPC）

多进程协作绕不开 IPC。从最快的共享内存到跨主机的 Socket，每种方式都有适用场景。

  • 管道 pipe：单向字节流，常用于 shell 管道 |；只适合有亲缘关系的进程；命名管道 FIFO 可跨无关进程
  • 消息队列：内核维护的消息链表，按类型收发（如 SysV msg），解耦但复制开销大
  • 共享内存：多进程映射同一物理内存，最快（无复制）；必须配信号量同步，否则有竞态
  • 信号量 semaphore：计数器，P（申请）/ V（释放）操作，用于互斥与同步；信号 signal 是异步通知（如 SIGKILL）
  • Socket：唯一能跨主机的 IPC（TCP / UDP / Unix domain socket）；对比：本地优先 Unix socket，跨机用 TCP
# Python 多进程通信示例
from multiprocessing import Process, Queue, Value

def worker(q, counter):
    q.put("hello from worker")        # 消息队列式通信
    with counter.get_lock():          # 信号量/锁保护共享变量
        counter.value += 1

if __name__ == "__main__":
    q = Queue()
    counter = Value('i', 0)           # 共享内存 + 锁
    p = Process(target=worker, args=(q, counter))
    p.start(); p.join()
    print(q.get())                    # hello from worker
    print(counter.value)              # 1

# shell 管道：cat file | grep err | wc -l
# 三个进程通过管道串联，数据从左流到右（pipe 半双工）
# 共享内存 vs 管道（速记）
# 共享内存：快（无复制），需信号量同步，进程须在同一台机器
# 管道：慢（内核拷贝两趟），简单安全，只能字节流
# Socket：能跨机器，序列化开销大，是分布式系统的通信底座

IPC 谱系：管道 → 消息队列 → 共享内存 → Socket

2.3 虚拟内存与分页

"我的程序怎么用了 2GB 内存，实际物理内存才 1GB？"——虚拟内存让每个进程拥有完整独立的地址空间，物理内存按页按需映射。

  • 虚拟地址空间：每个进程看到从 0 到 2^n−1 的连续地址（32 位 4GB / 64 位巨大）；进程间地址隔离，天然安全
  • 分页：内存以页（通常 4KB）为单位；页表记录 虚拟页 → 物理页 的映射；TLB 是页表的高速缓存
  • 缺页（page fault）：访问未映射页 → 内核从磁盘/文件载入 → 慢（ms 级）；程序首次访问、mmap 文件都触发
  • 换页策略：内存不够时按策略淘汰（LRU 近似 / Clock）；局部性原理（时间局部性 + 空间局部性）保证命中率
  • mmap：文件映射进地址空间，读写文件像读写内存；零拷贝技术的基础之一
# Linux 下查看内存映射与缺页
# pmap -x PID        → 进程虚拟内存分布（每段映射到哪）
# cat /proc/PID/statm → 虚拟/驻留内存页数
# vmstat 1           → si/so 列：swap in/out，>0 说明内存吃紧

# 虚拟内存的意义（三句话）
# 1. 隔离：进程 A 的 0x1000 和进程 B 的 0x1000 是不同物理页
# 2. 惰性：只把用到的页映射进物理内存（省内存）
# 3. 统一：磁盘文件、共享库、匿名内存都统一成"页映射"

# 用 Python 观察缺页（首次访问触发）
import mmap, time
with open("big.bin", "r+b") as f:
    mm = mmap.mmap(f.fileno(), 0)      # mmap 映射，此时未读入
    t0 = time.time(); _ = mm[0]         # 首次访问 → 缺页，读盘
    print(f"首次访问 {time.time()-t0:.3f}s")  # 明显慢
    t0 = time.time(); _ = mm[4096]      # 之后访问走内存映射，快
    print(f"再次访问 {time.time()-t0:.6f}s")

虚拟内存：虚拟页 → 页表 → 物理页帧

2.4 死锁：四个必要条件与预防

两个线程互相等对方持有的锁，程序永远卡住——死锁。判断死锁只需对照四个必要条件，预防只需破坏其中一个。

  • 四个必要条件（缺一不可）：① 互斥（资源一次只能一个进程用）② 持有并等待（拿着 A 锁还等 B 锁）③ 不可剥夺（锁不能强抢）④ 循环等待（A 等 B，B 等 A）
  • 预防：破坏②一次性申请全部资源；破坏③可剥夺（如超时放弃重试）；破坏④锁排序（全局约定加锁顺序）
  • 避免：银行家算法——分配前判断是否仍存在安全序列（理论价值高，工程少用）
  • 检测与恢复：锁等待超时 / 死锁检测（如 MySQL InnoDB 自动检测回滚）；jstack / pstack 找循环等待链
# 经典死锁代码（Java：两线程交叉持锁）
class DeadlockDemo {
    static final Object LOCK_A = new Object();
    static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(10);                       // 故意制造交叉
                synchronized (LOCK_B) {          // 等 B 锁…
                    System.out.println("T1 done");
                }
            }
        }).start();
        new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(10);
                synchronized (LOCK_A) {          // 等 A 锁…互相等 → 死锁
                    System.out.println("T2 done");
                }
            }
        }).start();
    }
}
# 定位：jstack PID  → 找 "Found one Java-level deadlock"
#       或查看两个线程都卡在 BLOCKED 且互相持有对方想要的锁

# 预防方案（选一即可）：
# 1. 全局锁顺序：约定"永远先 A 后 B"，T2 也先拿 A → 打破循环等待
# 2. tryLock 超时：拿不到就释放已有锁重试 → 打破持有并等待
# 3. 尽量少用多个锁：合并或换无锁结构（原子变量 / CAS）

死锁四条件之一"循环等待"的环状结构

2.5 网络分层：OSI 七层与 TCP/IP 四层

网络协议数以百计，分层让每一层只操心自己的事。面试高频：OSI 七层 → TCP/IP 四层的对应关系，以及数据封装/解封装过程。

  • OSI 七层：物理 → 数据链路 → 网络 → 传输 → 会话 → 表示 → 应用
  • TCP/IP 四层（事实标准）：链路层（以太网）→ 网络层（IP）→ 传输层（TCP/UDP）→ 应用层（HTTP/DNS）；OSI 上三层合并为应用层
  • 每层关键协议：链路：以太网 / ARP；网络：IP / ICMP；传输：TCP（可靠）/ UDP（快）；应用：HTTP / DNS / SSH
  • PDU 名称：链路层叫"帧"，网络层叫"数据报"，传输层叫"报文段"，应用层叫"报文"
  • 封装 / 解封装：发送逐层加头（H1→H2→H3），接收逐层剥头；抓包看到的正是封装后的字节

2.7 HTTP 请求模型

Web 开发天天打交道的就是 HTTP。报文结构、方法语义、状态码、缓存——每一项都是面试与排查的考点。

3.1 线程同步：互斥锁 / 自旋锁 / 信号量 / 条件变量

多线程共享数据必然产生竞态。同步原语解决两件事：互斥（同一时刻只有一个人改）和等待/通知（条件满足再继续）。

  • 临界区与竞态：多个线程同时读写共享变量 → 结果不确定（如 i++ 非原子：读-改-写三步可能交错）
  • 互斥锁 mutex：拿不到就睡眠（让出 CPU），适合持锁时间长的场景；由内核调度，有上下文切换成本
  • 自旋锁 spinlock：拿不到就忙等（死循环），适合持锁极短（几纳秒）的场景；单核/多核都要注意
  • 读写锁：读读并发、写写互斥；适合读多写少（如缓存、配置）
  • 信号量：计数器（>1 允许多个）；条件变量：配合互斥锁实现"等条件"（wait 释放锁并睡眠，signal 唤醒）
  • 原子操作 / CAS：Compare-And-Swap 无锁更新（乐观），ABA 问题需版本号；适合简单计数场景

3.2 并发模型对比：多线程 / 协程 / 异步

"高并发"不等于"多线程"。IO 密集用协程/异步，CPU 密集用多线程；选错模型，机器加再多也白搭。

  • 多线程：每个任务一个（或池化）内核线程；简单直观，但线程多时调度开销大（8G 内存默认只够几千线程）
  • 协程（用户态线程）：一个线程内多个协程，切换由程序控制（无内核介入）；goroutine / Python asyncio / Kotlin coroutine；百万级并发可行
  • 异步事件驱动：单线程 + 事件循环（epoll 等）；回调/状态机表达流程，适合 IO 密集（Nginx、Redis、Node.js）
  • 关键区分：IO 密集（等网络/磁盘，让出 CPU）→ 协程/异步；CPU 密集（算满核）→ 线程数 ≈ 核数
# Python 协程示例（asyncio，单线程并发 IO）
import asyncio

async def fetch(url):
    # await 处让出控制权，IO 完成回来继续
    print(f"start {url}")
    await asyncio.sleep(0.1)   # 模拟 IO
    return url

async def main():
    tasks = [fetch(f"http://api/{i}") for i in range(100)]
    print(await asyncio.gather(*tasks))  # 100 个并发完成

asyncio.run(main())

# 选型口诀：IO 密集 → 协程/异步（省内存省切换）

3.3 TCP 三次握手与四次挥手

面试必考、排障必用。三次握手建立连接、四次挥手断开连接，配合状态机（ESTABLISHED / TIME_WAIT 等）理解网络行为。

  • 三次握手：① 客户端发 SYN（seq=x）→ ② 服务端回 SYN+ACK（seq=y, ack=x+1）→ ③ 客户端发 ACK（ack=y+1）；此后双方都知道"我能发你也能收"
  • 为什么三次而非两次：防止"失效的旧连接请求"突然到达服务端造成资源浪费——第三次 ACK 让服务端确认客户端确实活着（两次的话服务端会为幽灵 SYN 建立半连接）
  • 四次挥手：① 主动方 FIN → ② 被动方 ACK（半关闭，被动方还能发）→ ③ 被动方 FIN → ④ 主动方 ACK；TCP 全双工，两方向独立关闭
  • TIME_WAIT（2MSL）：主动关闭方等 2 个最大报文寿命再释放端口，确保最后一个 ACK 能重传、旧报文不会串到新连接
  • 常见状态排查：大量 SYN_RECV → SYN Flood 或服务端 backlog 满；大量 CLOSE_WAIT → 应用没调 close（连接泄漏）；大量 TIME_WAIT → 短连接频繁

# 1.2.3.4.54321 > 5.6.7.8.80: Flags [.], ack 2001          ← ACK

3.4 TCP 可靠传输与拥塞控制

TCP 承诺"不丢、不乱、不重"，靠的是确认、重传、序号与窗口；而拥塞控制决定网络"公平且不过载"。

  • 可靠传输四件套：序号（乱序重排）、确认 ACK（累计确认）、重传（超时 RTO 重传 / 快速重传：连续收到 3 个重复 ACK 立即重传）、滑动窗口（批量确认、流量控制）
  • 流量控制：接收方通告窗口（rwnd）限制发送速率，防止发送方打爆接收方缓存——端到端
  • 拥塞控制：发送方维护拥塞窗口（cwnd），探测网络容量：慢启动（cwnd 指数翻倍，1→2→4…）→ 拥塞避免（线性 +1）→ 超时则回到慢启动（乘法减小）
  • 快重传与快恢复：3 个重复 ACK 视为"轻度丢包"，快重传 + 减半 cwnd（快恢复），不必回到慢启动
  • 为什么重要：不加拥塞控制，所有 TCP 流一起重试会击垮网络（拥塞崩溃）
# 拥塞窗口演化（示意，cwnd 单位：报文段）

# 拥塞避免阶段（线性）：17 → 18 → 19 → …（每次 RTT +1）

3.5 TLS/HTTPS 握手过程

HTTPS = HTTP + TLS。握手要回答：怎么证明"对方是真的"（证书），怎么安全地交换密钥（非对称），之后怎么高效加密（对称）。

  • 两个加密体系分工：非对称（RSA / ECDSA）用于身份认证与密钥交换，慢；对称（AES）用于数据加密，快；TLS 用非对称"协商"出一个对称密钥，再用它加密正文
  • 证书链：站点证书 ← 中间 CA ← 根 CA；浏览器内置根证书，逐级验证签名 → 建立信任
  • TLS 1.2 握手：ClientHello（支持的算法）→ ServerHello（选定算法 + 证书 + 密钥交换参数）→ 客户端验证证书 + 计算预主密钥 → 双方派生会话密钥 → Finished（加密握手完成）
  • 密钥交换：经典 RSA（客户端加密预主密钥给服务端）；现代 ECDHE（双方各自算临时密钥对，Diffie-Hellman 交换，前向安全：泄露长期私钥不泄露历史流量）
  • TLS 1.3：握手从 2-RTT 降到 1-RTT，0-RTT 恢复会话；删除不安全算法（RSA 密钥交换、SHA-1）

# New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384   ← TLS1.3 + AES-GCM
# Server public key is 2048 bit                     ← 服务端证书公钥
# Verify return code: 0 (ok)                        ← 证书链验证通过
# ---

# TLS 1.2 握手简化时序
# 客户端                                    服务端
#   |-------- ClientHello（算法列表）--------->|
#   |<------- ServerHello + 证书 + 密钥交换参数--|
#   | 验证证书链 → 计算预主密钥                  |
#   |-------- 密钥交换（加密预主密钥/ECDHE）--->|
#   |-------- Finished（加密） --------------->|
#   |<-------- Finished（加密） ---------------|
#   |=========== 对称密钥加密数据 =============|

# 常见问题
# - 证书过期/域名不匹配 → Verify return code 非 0
# - 双向 TLS（mTLS）：服务端也要求客户端证书（微服务内部）

3.6 缓存一致性：MESI 协议与伪共享

多核 CPU 各自有缓存，同一变量被两个核改了怎么办？MESI 协议用"总线嗅探 + 状态机"保证一致性——这也是并发编程里 volatile 的硬件基础。

  • 缓存层级：每个核独有 L1/L2，多核共享 L3；缓存行通常 64 字节（读写的原子单位）
  • MESI 四状态：Modified（我改过，独占最新）· Exclusive（只有我有，干净）· Shared（多核有副本，干净）· Invalid（失效，要读得重取）
  • 一致性流程：写前发"失效"广播（总线嗅探），其他核把自己的副本置 Invalid；读失效行 → 从最新来源取（可能触发写回）
  • 伪共享（False Sharing）：两个无关变量落在同一缓存行，A 核写它 → 广播失效 → B 核被迫重取 → 性能莫名下降；解决：缓存行填充（padding）或按行对齐
  • 与编程的关联：volatile = 每次读写都走主存一致性协议（禁止缓存优化重排）；锁的实现依赖缓存一致性 + 内存屏障
# 伪共享示例（Java，@Contended 可禁）
# 反直觉：两个互不相关的计数器，多线程分别自增，
# 若落在同一缓存行 → 互相使对方缓存失效 → 比预期慢几倍
class FalseSharing {
    static final int THREADS = 4;
    // 方案1（坏）：紧密相邻
    static volatile long[] counters1 = new long[THREADS];
    // 方案2（好）：每个计数器占满一个缓存行（填充 7 个 long = 56B + 8B = 64B）
    static class Padded {
        volatile long value;
        long p1,p2,p3,p4,p5,p6,p7;   // 填充到 64 字节
    }

    // 验证思路：两版各自 4 线程 * 1 亿次自增，测耗时差
    // 坏版可能慢 2-4 倍 → 就是伪共享在作祟
}

# MESI 状态转换速记
# 读缺失：I → S（其他核也有）或 E（只有我）
# 写命中：S/E → M（并广播失效）；M → M（写回）
# 写缺失：I → M（读后改，或直接写分配）
# 任何核写 E/M → 广播失效，其他核 S→I

伪共享：无关变量同住一行导致的性能陷阱

3.7 CPU 调度算法与性能分析

CPU 是稀缺资源，调度算法决定"谁先用、用多久"。而系统性能分析（CPU/内存/IO 三件套）是排障的看家本领。

  • 调度目标：吞吐量（单位时间完成任务数）、周转时间（任务从到达到完成）、响应时间（交互系统首响应）；没有免费的午餐，按场景取舍
  • 经典算法：FCFS（先来先服务，长任务饿死短任务）· SJF（短作业优先，最优周转但需预知）· 时间片轮转（公平，片长 1-10ms）· 优先级（低优先级饿死 → 老化机制）· 多级反馈队列（Linux CFS：按动态优先级分队列，兼顾响应与吞吐）
  • 上下文切换成本：保存/恢复寄存器 + TLB 失效 + 缓存降温；切换越频繁，有效计算越少
  • 性能分析三板斧：CPU（top 的 %cpu / load average）· 内存（free / vmstat si so）· IO（iostat / dstat）；先看资源哪一项打满，再定位到进程、线程、调用栈
# 性能分析第一屏：top
# top -H -p PID
# %CPU  → 每核利用率（如 400% = 用了 4 个核）
# load average 1.50 1.20 1.10  → 1/5/15 分钟平均运行队列长度
#   判断：load ≈ 核数 = 刚好；load 明显大于核数 = CPU 排队

# 三板斧命令
# vmstat 1
#   r 列：运行队列（>核数 → CPU 不够）
#   b 列：阻塞进程（多在等 IO）
#   si/so：swap 进出（>0 → 内存不足，性能悬崖）
# iostat -x 1
#   %util ≈ 100 → 磁盘打满；await 大 → IO 排队
# free -h → 内存；df -h → 磁盘容量
# sar -u 1   → 历史采样看 CPU 趋势（排查"什么时候开始高"）

# 定位"谁在吃 CPU"
# top -H -p PID            → 找到线程 ID（TID）
# printf '%x\n' TID        → 转十六进制（jstack 需要）
# jstack PID | grep nid=   → 找到该线程的栈（Java 场景）

多级反馈队列：时间片递增、优先级递减

6常见误区与实战要点

常见误区：
  • 以为"线程越多并发越高" —— 线程有栈内存 + 调度开销；IO 密集靠协程/异步，CPU 密集线程数≈核数
  • 用 cat /proc/meminfo 或 free 的内存值吓自己 —— Linux 的"可用内存"要看 available，不是 free（缓存会回收）
  • 抓包只看 TCP 层，忘了四层模型 —— 排查 HTTP 问题先确认是应用层（curl）还是传输/网络层（ping/ss）
  • 把"乱码"当玄学 —— 本质是字节流 × 解码器不匹配；确定源头编码（UTF-8/GBK）就能解
  • 死锁了只重启 —— 死锁必有循环等待链，jstack/pstack 定位后从"锁排序/超时"根治
  • 认为 HTTPS 装了证书就安全 —— 证书过期/私钥泄露/弱算法同样危险；TLS 1.2 以下尽快升级
  • 高并发就上消息队列 —— 先问瓶颈在 CPU 还是 IO；不加度量的"优化"都是猜
实战要点：线上问题按"四层定位"走——资源层（top/free/iostat）→ 系统层（ss/jstack）→ 应用层（日志/指标）→ 网络层（ping/curl/tcpdump）；每一层都有一两个命令能一锤定音。
