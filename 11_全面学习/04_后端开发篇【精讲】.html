1.1 Java 语法与面向对象

Java 是服务端最主流的语言。核心：8 种基本类型、引用类型、面向对象三大特性、接口与抽象类、equals/hashCode 契约。

  • 基本类型：byte / short / int / long / float / double / char / boolean；其余都是引用类型（存对象地址）
  • 三大特性：封装（private + 访问方法）、继承（extends 单继承）、多态（父类引用指向子类对象，运行时动态绑定）
  • 接口 vs 抽象类：接口可多实现、JDK8 起可有 default/static 方法；抽象类单继承、可含字段与构造器
  • equals 与 hashCode 契约：equals 相等则 hashCode 必相等；重写 equals 必须重写 hashCode，否则 HashMap 等容器失效
// 接口：定义能力（可多实现）
public interface Payable {
  void pay(BigDecimal amount);
}

// 抽象类：沉淀公共状态与模板逻辑（单继承）
public abstract class BaseAccount {
  protected String accountNo;
  public abstract BigDecimal balance();
}

// 多态：父类引用指向子类对象，调用时动态绑定
Payable p = new WechatPay();
p.pay(new BigDecimal("99.00"));

1.2 集合框架（List / Map / Set）

Java 集合两大体系：Collection（List / Set）与 Map。理解底层数据结构，才能选对容器、估对复杂度。

  • ArrayList：动态数组，默认容量 10，扩容 1.5 倍；随机访问 O(1)，中间插入 O(n)
  • LinkedList：双向链表；头尾增删 O(1)，随机访问 O(n)，内存开销大
  • HashMap：数组 + 链表 + 红黑树；默认容量 16、加载因子 0.75；链表长度 ≥ 8 且数组 ≥ 64 时转红黑树；JDK8 尾插避免死链
  • HashSet 底层是 HashMap；TreeSet / TreeMap 用红黑树保持有序
  • fail-fast：遍历中结构性修改会抛 ConcurrentModificationException（modCount 校验）
Map map = new HashMap<>(16);
map.put("u1", new User("张三", 28));
map.put("u2", new User("李四", 30));

// 遍历（推荐 entrySet）
for (Map.Entry e : map.entrySet()) {
  System.out.println(e.getKey() + " -> " + e.getValue().getName());
}

// 并发场景必须用 ConcurrentHashMap，HashMap 在扩容时会丢数据
Map safe = new ConcurrentHashMap<>(16);

1.3 异常处理与日志体系

异常处理决定代码健壮性；日志是线上排障的"黑匣子"。两者都是后端基本功。

  • 异常体系：Throwable → Error（JVM 级错误，如 OOM / StackOverflow，不捕获）与 Exception；受检异常（编译期强制处理）vs 运行时异常 RuntimeException（可冒泡）
  • try-catch-finally：finally 保证释放资源；JDK7 起 try-with-resources 自动关闭 AutoCloseable
  • 日志规范：SLF4J 门面 + Logback 实现；级别 TRACE < DEBUG < INFO < WARN < ERROR；占位符 {} 延迟拼接
  • 反模式：e.printStackTrace()（打到 stdout 易丢）、catch 后吞异常、把业务异常当错误日志打
// try-with-resources：自动 close
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
  ps.setString(1, id);
  ResultSet rs = ps.executeQuery();
} catch (SQLException e) {
  log.error("查询用户失败, id={}", id, e);  // 占位符 + 堆栈
}

// 业务异常 vs 系统异常
if (user == null) {
  throw new BusinessException("用户不存在");   // 业务异常，全局处理器转 4xx
}
log.info("用户登录成功, userId={}", user.getId());

1.4 构建工具 Maven / Gradle

构建工具统一依赖管理与构建流程。Maven 是 Java 生态主流，Gradle 是 Android 与新项目首选。

  • 坐标：groupId:artifactId:version 唯一定位一个依赖
  • 生命周期（Maven）：validate → compile → test → package → install → deploy；阶段按序执行
  • 依赖 scope：compile（默认，打包进产物）/ test（仅测试）/ provided（编译需要但运行期由容器提供，如 servlet-api）/ runtime

  • Gradle：Groovy / Kotlin DSL，基于 task 的增量构建，构建更快；settings.gradle + build.gradle

1.5 泛型、反射与注解

泛型让代码类型安全；反射与注解是 Spring 等框架"魔法"的底层基础。

  • 泛型：类型参数 <T> 编译期检查；运行时泛型擦除（无边界擦除为 Object，有边界擦除到上界）
  • 通配符：? extends T 上界（只读）、? super T 下界（只写），即 PECS：生产者用 extends，消费者用 super
  • 反射：Class.forName / getDeclaredMethod / setAccessible(true) / invoke；动态代理 JDK Proxy（面向接口）与 CGLIB（面向类）
  • 注解：@Retention（SOURCE / CLASS / RUNTIME）、@Target 限定使用位置；RUNTIME 注解靠反射读取生效
// 自定义运行时注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface NeedLogin {}

// 反射读取注解并执行
public void handle(Object obj) throws Exception {
  for (Method m : obj.getClass().getDeclaredMethods()) {
    if (m.isAnnotationPresent(NeedLogin.class)) {
      System.out.println("方法需要登录: " + m.getName());
    }
  }
}

// 泛型方法：T 编译期检查，擦除后是 Object
public static <T> T requireNonNull(T value) {
  if (value == null) throw new NullPointerException();
  return value;
}

1.6 Java 8+ 新特性（Lambda / Stream）

Lambda 与 Stream 把"怎么算"抽象成"算什么"，代码更简洁、更易并行。

  • 函数式接口：Supplier / Consumer / Function / Predicate；@FunctionalInterface 标注，可 Lambda 实例化
  • Stream：中间操作（map / filter / sorted / distinct）惰性，终端操作（collect / reduce / forEach / count）才触发执行
  • Collectors：toList / toMap / groupingBy / joining
  • Optional：ofNullable / orElse / orElseThrow 显式处理空值，避免深层判空
  • 时间 API：LocalDate / LocalDateTime / Instant 线程安全，替代 SimpleDateFormat
List<User> users = Arrays.asList(
    new User("张三", 28, 8000), new User("李四", 35, 12000),
    new User("王五", 22, 6000));

// 过滤 + 排序 + 提取 + 汇总
double avg = users.stream()
    .filter(u -> u.getAge() >= 25)
    .sorted(Comparator.comparing(User::getSalary).reversed())
    .mapToDouble(User::getSalary)
    .average().orElse(0);
System.out.println("25 岁以上平均薪资: " + avg);

// 分组统计
Map<Integer, Long> byAge = users.stream()
    .collect(Collectors.groupingBy(User::getAge, Collectors.counting()));

// Optional 兜底
User u = Optional.ofNullable(users)
    .filter(list -> !list.isEmpty())
    .map(list -> list.get(0))
    .orElseThrow(() -> new BusinessException("用户列表为空"));

1.7 设计模式与 SOLID 原则

设计模式是解决特定问题的成熟方案；SOLID 是面向对象设计的五个基本原则。

  • SOLID：单一职责、开闭（对扩展开放、对修改关闭）、里氏替换、接口隔离、依赖倒置
  • 创建型：单例（双重检查锁）、工厂方法、抽象工厂、建造者 Builder
  • 结构型：代理（Spring AOP）、装饰器（IO 流）、适配器、外观
  • 行为型：策略（支付渠道）、模板方法（流程骨架）、观察者（事件监听）、责任链（拦截器）
// 双重检查锁单例（懒加载 + 线程安全）
public class ConfigHolder {
  private static volatile ConfigHolder instance;
  private ConfigHolder() {}
  public static ConfigHolder getInstance() {
    if (instance == null) {
      synchronized (ConfigHolder.class) {
        if (instance == null) instance = new ConfigHolder();
      }
    }
    return instance;
  }
}

}

3标准层 · 日常开发（8）

2.1 JVM 内存模型与类加载机制

JVM 把字节码变成可执行代码。内存分区决定对象放哪、异常怎么抛。

  • 运行时数据区：程序计数器（当前指令地址）、虚拟机栈（栈帧：局部变量表 / 操作数栈）、本地方法栈、堆（对象实例，GC 主战场）、方法区（JDK8 起为元空间 Metaspace，存类元信息）
  • 栈溢出：递归过深抛 StackOverflowError；堆溢出：对象太多抛 OutOfMemoryError: Java heap space
  • 类加载五步：加载 → 验证 → 准备 → 解析 → 初始化
  • 双亲委派：类加载请求先交给父加载器，父加载不了才自己加载；防止核心类被篡改（自己写 java.lang.String 不生效）
// 查看 JVM 内存与参数（生产排查常用）
java -Xms512m -Xmx1024m -XX:+PrintGCDetails -jar app.jar

// 运行时获取堆大小
long heap = Runtime.getRuntime().maxMemory();   // 最大堆
long used = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();

2.2 垃圾回收 GC 与分代

GC 自动回收堆上无引用对象。理解分代与收集器，才能做 JVM 调优。

  • 对象判定：可达性分析，从 GC Roots（栈引用 / 静态变量 / 常量 / JNI 引用）出发，不可达即回收
  • 分代：新生代 Eden + S0 + S1（复制算法，Minor GC 频繁且快）；老年代（标记-整理，Major / Full GC）；元空间（类卸载）
  • 收集器：Serial（单线程）、Parallel（JDK8 默认）、CMS（并发标记清除，JDK9 标记废弃）、G1（Region 分区，可预测停顿，JDK9+ 默认）、ZGC（超低停顿，大堆）
  • 调优目标：减少 Full GC 频率与停顿时间；用 jstat -gcutil 观察各代使用率

分代回收：新生代对象熬过多次 Minor GC 晋升老年代

2.3 多线程与 JUC 并发编程

并发是后端高吞吐的基石：线程池管理线程，锁与 CAS 保证线程安全。

  • ThreadPoolExecutor 七参：corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler（拒绝策略 Abort / CallerRuns / DiscardOldest / Discard）
  • 任务提交顺序：核心线程 → 工作队列 → 最大线程 → 拒绝策略
  • synchronized（隐式锁，可重入）vs ReentrantLock（可中断、可超时、公平锁）
  • volatile 保证可见性、不保证原子性；CAS 乐观锁（AtomicInteger）解决 ABA 需版本号
  • ConcurrentHashMap：JDK8 以 synchronized + CAS 锁桶头，并发度更高；禁止用 HashMap 做全局缓存
  • JUC 工具：CountDownLatch（等 N 件事）、CyclicBarrier（屏障）、Semaphore（信号量限流）、CompletableFuture（异步编排）
// 手动创建线程池（避免 Executors 无界队列 OOM）
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),          // 有界队列
    Thread::new,
    new ThreadPoolExecutor.CallerRunsPolicy()); // 满时由调用线程执行

// 异步编排：并行查两个数据源再合并
CompletableFuture<User> f1 = CompletableFuture.supplyAsync(() -> userDao.get(id), pool);
CompletableFuture<List<Order>> f2 = CompletableFuture.supplyAsync(() -> orderDao.list(id), pool);
User user = f1.thenCombine(f2, (u, orders) -> { u.setOrders(orders); return u; })
             .get(3, TimeUnit.SECONDS);

2.4 Spring 核心：IOC 与 AOP

IOC 把对象创建与装配从代码抽走交给容器；AOP 把日志、事务、权限等横切逻辑收敛成切面。

  • IOC 容器：ApplicationContext 管理 Bean；Bean 生命周期：实例化 → 属性填充 → Aware 回调 → BeanPostProcessor → 初始化（@PostConstruct）→ 使用 → 销毁
  • 作用域：singleton（默认单例）/ prototype（每次新对象）/ request / session
  • 循环依赖：三级缓存（singletonObjects / earlySingletonObjects / singletonFactories）解决 setter 注入；构造器循环依赖无法解决
  • AOP：JDK 动态代理（目标实现接口）与 CGLIB（无接口时）；切点 execution() 表达式、通知 @Before / @After / @Around / @AfterReturning / @AfterThrowing
// 构造器注入（比字段注入更利于测试）
@Service
public class UserService {
  private final UserMapper userMapper;
  public UserService(UserMapper userMapper) { this.userMapper = userMapper; }
  public User getUser(Long id) { return userMapper.selectById(id); }
}

// 环绕通知：统一记录耗时
@Aspect
@Component
public class LogAspect {
  @Around("execution(* com.example.service.*.*(..))")
  public Object log(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.currentTimeMillis();
    Object result = pjp.proceed();
    log.info("{} 耗时 {}ms", pjp.getSignature().getName(),
             System.currentTimeMillis() - start);
    return result;
  }
}

2.5 Spring Boot 自动配置与快速开发

约定大于配置：一个 main 方法启动，Tomcat 内嵌，依赖即配置。

2.6 MyBatis 持久层与 SQL 映射

半自动 ORM：SQL 自己写、映射自己控。复杂 SQL 与性能优化空间大，团队掌控力强。

  • 架构：SqlSessionFactory → SqlSession → Mapper 动态代理；Configuration 持有 MappedStatement
  • 动态 SQL：if / where / set / choose / foreach；#{} 预编译占位（PreparedStatement，天然防注入），${} 字符串拼接（仅表名、排序字段等，必须白名单校验）
  • 缓存：一级缓存默认开启（SqlSession 级）；二级缓存按 namespace 配置（多会话共享，注意脏读）
  • MyBatis-Plus：BaseMapper / IService 内置 CRUD、LambdaQueryWrapper 类型安全查询、分页插件 PaginationInnerInterceptor

2.7 RESTful API 设计与接口文档

REST 用资源 + HTTP 方法表达一切操作；OpenAPI 让前后端契约可机器校验、可自动生成文档。

  • 资源命名：名词复数 /users、/users/{id}；子资源 /users/{id}/orders
  • 方法语义：GET 查询（幂等、安全）、POST 新建、PUT 全量替换（幂等）、PATCH 部分更新、DELETE 删除（幂等）
  • 状态码：200 成功、201 创建、204 无内容、400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突、429 限流、500 服务器错误
  • 规范：统一响应体（code/message/data）、分页参数 page / pageSize、版本前缀 /v1/
  • 接口文档：OpenAPI 3.0（@Operation / @Parameter / @ApiResponse）+ springdoc / Knife4j 生成 Swagger UI，可在线调试
@RestController
@RequestMapping("/v1/users")
@Tag(name = "用户管理")
public class UserController {

  @GetMapping("/{id}")
  @Operation(summary = "查询用户")
  @ApiResponse(responseCode = "200", description = "成功")
  public Result<User> get(@PathVariable Long id) {
    return Result.ok(userService.getUser(id));
  }

  @PostMapping
  @Operation(summary = "创建用户")
  public Result<Long> create(@Valid @RequestBody UserDTO dto) {
    return Result.ok(userService.create(dto));
  }
}

2.8 JWT 鉴权与 Spring Security

无状态鉴权：服务端签发、客户端携带、签名验证，不依赖 session，天然支持水平扩展。

  • JWT 三段：Header（算法与类型）、Payload（claims：sub / exp / iat / 自定义）、Signature（HS256 对称密钥或 RS256 私钥签名）
  • 流程：登录校验 → 签发 access token → 客户端请求头 Authorization: Bearer <token> → 过滤器验签 → 放行
  • 与 session 对比：无状态、可扩展，但无法主动注销、泄密不可控；用短时 access + refresh token 缓解
  • Spring Security 过滤器链：SecurityFilterChain 配置 permitAll / authenticated；自定义 JwtAuthenticationFilter 解析 token 后塞入 SecurityContext
  • OAuth2 授权模式：授权码 / 客户端凭证 / 密码 / 刷新令牌；JWT 常作为 access token 载体格式
// 签发与校验（简化）
public class JwtUtil {
  private static final SecretKey KEY = Keys.hmacShaKeyFor(secret.getBytes());

  public static String create(Long userId, String name) {
    return Jwts.builder()
        .setSubject(String.valueOf(userId))
        .claim("name", name)
        .setIssuedAt(new Date())
        .setExpiration(new Date(System.currentTimeMillis() + 30 * 60 * 1000L)) // 30 分钟
        .signWith(KEY, SignatureAlgorithm.HS256)
        .compact();
  }

  public static Claims verify(String token) {
    return Jwts.parserBuilder().setSigningKey(KEY).build()
        .parseClaimsJws(token).getBody();
  }
}

    .anyRequest().authenticated())

3.1 Spring 事务传播行为与失效场景

@Transactional 基于 AOP 代理实现。传播行为决定多个事务方法嵌套时的边界；代理失效是线上最常见的坑。

  • 传播行为 7 种：REQUIRED（默认，有事务则加入）、REQUIRES_NEW（挂起外层、新开事务）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER、NESTED（Savepoint 嵌套回滚）
  • 隔离级别：DEFAULT / READ_UNCOMMITTED / READ_COMMITTED / REPEATABLE_READ / SERIALIZABLE，最终由数据库实现
  • 失效场景：同类方法自调用（绕过代理）、private 方法、异常被 catch 吞掉、抛出受检异常未配 rollbackFor、类未被 Spring 管理、数据库引擎不支持事务（如 MyISAM）
  • 兜底方案：编程式事务 TransactionTemplate 精确控制提交 / 回滚边界
// 新开事务：外层失败不影响内层（如积分累计）
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void addPoints(Long userId, int points) { ... }

// 自调用失效示例：this 调用不经过代理，事务不生效！
public void outer() {
  this.inner();            // ❌ 走 this，@Transactional 失效
  innerService.inner();    // ✅ 注入代理对象调用才生效
}
@Transactional
public void inner() { ... }

// 正确写法：指定回滚类型
@Transactional(rollbackFor = Exception.class)
public void createOrder(OrderDTO dto) { ... }

3.2 JVM 调优与线上排查

线上问题 80% 是 CPU / 内存 / 线程问题。工具链：jps → jstack → jmap → jstat → Arthas。

  • CPU 高：top 定位进程 → top -Hp 定位线程 → jstack 导出栈，找 RUNNABLE 热点代码；也可用 Arthas thread -n 3
  • 内存高：jmap -dump:format=b,file=heap.hprof 生成快照 → MAT / Eclipse 分析大对象与泄漏链；jstat -gcutil 观察 GC 频率
  • OOM 分类：Java heap space（堆满）、GC overhead limit exceeded（GC 空转）、unable to create native thread（线程数超限）、Metaspace（类太多）、Direct buffer memory（直接内存）
  • 调优参数：-Xms / -Xmx 设相等避免动态扩容、-Xmn 新生代大小、-XX:MetaspaceSize、-XX:+HeapDumpOnOutOfMemoryError 自动留证
  • Arthas 在线诊断：dashboard / watch / trace / redefine，不停机排查
# 排查命令速查
jps -l                          # 列出 Java 进程
top -Hp <pid>                   # 查看进程内线程 CPU（十六进制 nid）
jstack <pid> > thread.txt       # 导出线程栈
jstat -gcutil <pid> 1000        # 每秒看 GC 使用率
jmap -dump:format=b,file=h.hprof <pid>   # 堆快照
# 启动参数留证
java -Xms512m -Xmx512m -XX:+HeapDumpOnOutOfMemoryError -jar app.jar

3.3 分布式事务（2PC / TCC / Seata）

跨库、跨服务的一致性问题。强一致用 2PC / TCC，高可用场景用可靠消息 + 最终一致。

  • 2PC 两阶段提交：准备阶段（协调者询问、各参与者锁资源）→ 提交阶段；协调者单点故障会阻塞，参与者宕机无法回滚
  • TCC：Try（冻结资源）→ Confirm（提交）→ Cancel（回滚）；业务侵入大但灵活，适合强一致
  • 可靠消息最终一致：本地消息表（业务与消息同库事务）+ MQ 重投递 + 对账兜底
  • Seata AT 模式：全局事务 + 分支事务 + undo_log 自动回滚；@GlobalTransactional 注解使用
  • 选型：强一致场景（账务）用 TCC；高可用场景（订单通知）用最终一致；能不分就不分（单体事务最可靠）
// Seata AT 模式：一个注解管全局事务
@GlobalTransactional(name = "create-order-tx")
public void createOrder(OrderDTO dto) {
  orderMapper.insert(dto);          // 分支1：订单库
  accountMapper.deduct(dto.getAmount()); // 分支2：账户库（各自本地事务 + undo_log）
}

// 本地消息表：业务与消息同库，先写消息再异步投递
@Transactional
public void createOrderTx(OrderDTO dto) {
  orderMapper.insert(dto);
  msgMapper.insert(new Msg("order.created", orderId)); // 同库同事务
}
// 定时任务：扫描未投递消息 → 发送 MQ → 标记已投递；消费端幂等

3.4 微服务拆分与治理

微服务把单体按业务能力拆分为独立服务；注册、发现、网关、熔断构成治理底座。

  • 拆分原则：按业务能力 / 领域边界（DDD Bounded Context）；高内聚低耦合；数据独立、接口契约化；避免过度拆分
  • 注册中心：Nacos / Eureka（服务注册、心跳续约、健康检查、客户端本地缓存服务列表）
  • 网关：Spring Cloud Gateway（路由断言、过滤器链、统一鉴权 / 限流 / 灰度）
  • 熔断降级：Sentinel / Hystrix；状态机 CLOSED → OPEN（熔断）→ HALF_OPEN（半开探测）；降级返回兜底结果
  • 配套：配置中心 Nacos Config（动态刷新）、链路追踪 SkyWalking / Zipkin、统一日志与监控

3.5 消息队列集成（RabbitMQ / Kafka）

MQ 解决异步解耦与削峰填谷。RabbitMQ 路由灵活，Kafka 高吞吐、适合日志与流处理。

  • 核心模型：Producer → Broker → Consumer；RabbitMQ 用 Exchange 路由到 Queue；Kafka 用 Topic 分 Partition
  • RabbitMQ：Exchange 类型 direct（精确路由）/ topic（通配匹配）/ fanout（广播）/ headers；confirm 确认 + 手动 ACK；死信队列（消息过期 / 被拒 / 超限）
  • Kafka：分区内有序、offset 消费位点、消费者组负载均衡、副本 ISR 机制、acks=all 保证不丢
  • 投递语义：至少一次（默认，可能重复）、最多一次（可能丢）、恰好一次（幂等 + 事务）；消费侧必须幂等
  • 场景：订单异步通知、秒杀削峰、日志采集、事件驱动架构
// Spring Kafka：生产与消费
@Service
public class OrderProducer {
  @Autowired private KafkaTemplate<String, String> kafka;
  public void sendCreated(Long orderId) {
    kafka.send("order-events", String.valueOf(orderId));
  }
}

@KafkaListener(topics = "order-events", groupId = "order-consumer")
public void onEvent(String orderId) {
  // 消费必须幂等：按 orderId 判重（唯一键 / 状态机）
  if (orderService.isProcessed(orderId)) return;
  orderService.notifyUser(orderId);
}

3.6 高并发设计（限流 / 幂等 / 异步化）

高并发三板斧：缓存、异步、限流。再加幂等与隔离，系统才扛得住流量洪峰。

  • 缓存：Cache Aside 读写；防穿透（空值缓存 / 布隆过滤器）、防击穿（热点互斥重建 / 逻辑过期）、防雪崩（过期时间加随机数）
  • 限流：令牌桶 / 漏桶算法；Guava RateLimiter、Sentinel 规则、Nginx limit_req
  • 幂等：唯一业务键（订单号）+ 状态机流转 + 分布式锁（Redis SETNX + 过期时间 + 校验 value 防误删）
  • 异步化：MQ 削峰（秒杀请求先进队列）、写库后异步刷新缓存、串行依赖改并行
  • 性能测试：JMeter 压测；指标 QPS / TPS / RT 均值与 P99；先定位瓶颈（慢 SQL → 索引 / 缓存）再优化
// Redis 分布式锁（防重复提交 / 防超卖）
public boolean tryLock(String key, String value, long expireMs) {
  // SETNX + 过期时间原子执行；value 存唯一标识（订单号）
  return redis.opsForValue()
      .setIfAbsent(key, value, Duration.ofMillis(expireMs));
}

public void releaseLock(String key, String value) {
  // 校验 value 是自己才删，防止误删他人锁（Lua 脚本保证原子）
  String lua = "if redis.call('get',KEYS[1])==ARGV[1] then " +
               "return redis.call('del',KEYS[1]) else return 0 end";
  redis.execute(new DefaultRedisScript<>(lua, Long.class),
                Collections.singletonList(key), value);
}

// 幂等校验：先查状态机，已处理直接返回
if (!orderService.canPay(orderId)) return Result.fail("重复请求");

6常见误区与实战要点

常见误区：
  • 事务自调用失效：同类内 this 调用 @Transactional 方法，代理不生效，事务形同虚设
  • 用 ${} 拼接 SQL：MyBatis 中 ${} 直接拼字符串，用户输入可注入 SQL，必须用 #{} 预编译
  • Executors.newFixedThreadPool：无界队列，任务积压会 OOM，应手动 new ThreadPoolExecutor
  • JWT 存 localStorage：XSS 可窃取 token，应放 HttpOnly Cookie 或内存；access token 设短有效期
  • 日志打 e.printStackTrace()：输出到 stdout 易丢失，应 log.error("上下文", e) 记录完整堆栈
  • catch (Exception e) { } 吞异常：线上故障无从排查，至少记录日志或抛出业务异常
  • HashMap 当全局缓存：高并发扩容会丢数据，必须用 ConcurrentHashMap
  • 过度拆分微服务：单体即可的规模强拆，徒增分布式事务与运维成本
