2基础层 · 入门必备

2.1 npm / yarn / pnpm 常用命令

包管理器负责安装、更新、移除依赖并运行脚本：npm 内置，yarn 更快，pnpm 用硬链接省磁盘、防幽灵依赖。

  • install：安装依赖并写入 package.json；-D（--save-dev）写入 devDependencies
  • remove / uninstall：移除依赖；update：按范围升级
  • run：执行 package.json 里的 scripts（npm run dev 等）
  • npx：直接执行一次性工具命令（npx vite --version），无需全局安装
  • config：npm config set registry 配置镜像源
# 安装依赖
npm install vue              # 运行时依赖 → dependencies
npm install -D vitest        # 开发依赖 → devDependencies
npm uninstall vue            # 移除

# 执行脚本
npm run dev                  # 等价于运行 scripts.dev
npm run build -- --mode prod # 向脚本传参（-- 后传给命令）

# npx 临时执行
npx eslint src/              # 用项目本地 eslint，不全局装
深入阅读 → npm与包管理篇

2.2 package.json 字段

package.json 是项目的"身份证 + 使用说明"：记录元信息、依赖关系与脚本入口，包管理器与工具都读它。

  • name / version：包的唯一标识与版本号（遵循语义化版本）
  • scripts：命令入口，统一团队操作
  • dependencies：运行时依赖；devDependencies：仅开发/构建需要
  • peerDependencies：对等依赖（插件声明宿主，如组件库要求 vue 版本）
  • main / module / exports：包入口文件（Node / ESM 不同入口）
  • engines：声明兼容的 Node 版本
{
  "name": "my-app",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  },
  "dependencies": { "vue": "^3.4.0" },
  "devDependencies": { "vite": "^5.0.0", "vitest": "^1.0.0" },
  "peerDependencies": { "vue": "^3.0.0" },
  "engines": { "node": ">=18" }
}

2.3 依赖与 lockfile

lockfile（package-lock.json / pnpm-lock.yaml）锁定依赖的精确版本与依赖树，保证团队与生产环境依赖完全一致。

  • 语义化版本（semver）：主版本.次版本.补丁；^1.2.3 允许次版本更新，~1.2.3 只允许补丁
  • lockfile 记录解析后的精确版本与完整依赖树，必须提交进仓库
  • node_modules 是安装结果目录，由 lockfile 还原，不提交
  • 生产安装用 --omit=dev，只装运行时依赖，减小体积
  • 依赖提升与幽灵依赖：pnpm 用符号链接严格隔离，避免误用未声明的包
// package.json 中的范围写法
"dependencies": {
  "vue": "^3.4.21",   // ^：允许 3.x 内次版本更新（不含 4.0）
  "dayjs": "~1.11.0", // ~：只允许补丁更新（1.11.x）
  "lodash": "4.17.21" // 精确锁定
}

// pnpm-lock.yaml 里是解析后的精确版本
// vue: 3.4.21 及它的每个依赖都被锁定

2.4 脚本 script 命令

scripts 把长命令包成短命令、统一团队操作入口，还支持生命周期钩子自动串联。

  • npm run <name> 执行任意 script；npm 会自动设置 PATH，node_modules/.bin 下的命令可直接调用
  • pre/post 钩子：npm run build 会先自动执行 prebuild，再执行 build，最后 postbuild
  • 传参用 -- 分隔：npm run test -- --coverage
  • 跨平台环境变量用 cross-env，避免 Windows / Linux 语法差异
{
  "scripts": {
    "prebuild": "npm run lint",          // build 前自动执行
    "build": "vite build",
    "postbuild": "node scripts/notify.js",
    "lint": "eslint src",
    "test:ci": "vitest run --coverage",
    "dev:win": "cross-env NODE_ENV=development vite"
  }
}

3标准层 · 日常开发

3.1 Vite 配置与构建

Vite 基于原生 ESM 的开发服务器：依赖预打包（esbuild）+ 按需加载，启动快、热更新快；生产构建用 Rollup。

  • 开发模式：浏览器直接请求 ESM 模块，源码零打包按需编译
  • plugins：插件体系（@vitejs/plugin-vue / react）扩展转译能力
  • resolve.alias：路径别名（@ → /src）；server.proxy：开发代理
  • build：产物配置（outDir、rollupOptions、chunk 分割）
  • 环境变量：import.meta.env.VITE_XXX（仅 VITE_ 前缀暴露）
// vite.config.js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: { alias: { '@': '/src' } },
  server: {
    port: 3000,
    proxy: { '/api': 'http://localhost:8080' }
  },
  build: {
    outDir: 'dist',
    rollupOptions: {
      output: { manualChunks: { vendor: ['vue'] } }
    }
  }
})

3.2 Webpack 核心概念

Webpack 把所有资源当模块：loader 负责转译（把 .vue/.ts/.css 变成 JS），plugin 做 loader 做不了的全局操作，最终打包成静态资源。

  • entry / output：入口与出口；mode：development / production
  • loader：babel-loader（转译 JS/TS）、vue-loader、css-loader + style-loader
  • plugin：HtmlWebpackPlugin（生成 HTML）、MiniCssExtractPlugin（抽离 CSS）
  • resolve：模块解析（extensions、alias）；devServer：开发服务器 + HMR
  • 关键认知：loader 是"文件的转换器"，plugin 是"构建流程的钩子"
// webpack.config.js（简写）
module.exports = {
  entry: './src/main.js',
  output: { path: 'dist', filename: '[name].[contenthash].js' },
  mode: 'production',
  module: {
    rules: [
      { test: /\.vue$/, loader: 'vue-loader' },
      { test: /\.ts$/, loader: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] }
    ]
  },
  plugins: [new HtmlWebpackPlugin({ template: 'index.html' })]
}

3.3 Git 分支模型与协作流程

Git 分支是轻量指针，团队用分支模型组织并行开发、评审与发布，避免互相踩踏。

  • Git Flow：main（稳定发布）+ develop（日常集成）+ feature / release / hotfix 分支
  • GitHub Flow：main + feature 分支 + PR，适合持续发布
  • Trunk-Based：直接往主干提交短命分支，配合特性开关，适合高节奏团队
  • PR 评审：代码评审 + CI 检查通过后才合并；merge 保留历史，rebase 得到线性历史
  • 冲突解决：git status 定位冲突文件，手动合并后提交
# 常见流程
git switch -c feature/login      # 新建并切换分支
git add . && git commit -m "feat: 登录"   # 提交
git push -u origin feature/login # 推送 → 提 PR → 评审合并

# 同步主干（rebase 变基保持线性）
git switch main && git pull
git switch feature/login
git rebase main
git push --force-with-lease      # 变基后推送（带保护）

3.4 ESLint / Prettier 代码规范

ESLint 管代码质量（找 bug 和坏味道），Prettier 管代码格式（统一风格），配合 git hook 在提交前自动把关。

  • ESLint：rules + extends（eslint:recommended、plugin:vue/vue3-recommended）
  • Prettier：统一引号、分号、缩进、换行；与 ESLint 冲突时用 eslint-config-prettier 关闭格式类规则
  • husky + lint-staged：提交前只检查暂存区文件，快且不打扰
  • commitlint：约束提交信息格式（conventional commits）
// .eslintrc.cjs
module.exports = {
  extends: [
    'eslint:recommended',
    'plugin:vue/vue3-recommended',
    'prettier' // 关闭与 Prettier 冲突的格式规则
  ],
  rules: { 'vue/multi-word-component-names': 'off' }
}

// .prettierrc
{ "semi": false, "singleQuote": true, "printWidth": 100 }

3.5 单元测试（Jest / Vitest）

单元测试验证"最小逻辑单元"的行为，是重构与回归的安全网；Vitest 与 Vite 无缝集成，速度更快。

  • 结构：describe（分组）/ it 或 test（用例）/ expect（断言）
  • 常用断言：toBe / toEqual / toHaveBeenCalled / toBeTruthy
  • mock：vi.mock / vi.fn() 模拟依赖，隔离外部副作用
  • 覆盖率：vitest --coverage 看分支/语句覆盖，重点盯关键逻辑
  • Vue 组件测试：@vue/test-utils 的 mount / shallowMount
// utils.spec.js
import { describe, it, expect, vi } from 'vitest'
import { calcTotal } from './cart'

describe('calcTotal', () => {
  it('空购物车总价为 0', () => {
    expect(calcTotal([])).toBe(0)
  })

  it('计算多件商品并叠加优惠', () => {
    const items = [{ price: 100, count: 2 }, { price: 50, count: 1 }]
    expect(calcTotal(items, 10)).toBe(140) // 250 - 折扣
  })
})

3.6 E2E 测试（Playwright / Cypress）

端到端测试在真实浏览器里模拟用户操作，验证"登录 → 下单 → 支付"这类完整业务流程。

  • 真实浏览器自动化：Chromium / Firefox / WebKit 多内核覆盖
  • 核心 API：page.goto() 导航、page.click() 点击、expect(locator).toBeVisible() 断言
  • 自动等待：Playwright 内置等待机制，避免手工 sleep 的脆弱
  • trace 与录屏：失败时定位问题；CI 集成（GitHub Actions / Jenkins）
  • 适用边界：覆盖关键路径（happy path），细节逻辑交给单元测试
// login.spec.js（Playwright）
import { test, expect } from '@playwright/test'

test('用户能登录成功', async ({ page }) => {
  await page.goto('http://localhost:3000/login')
  await page.getByLabel('用户名').fill('admin')
  await page.getByLabel('密码').fill('123456')
  await page.getByRole('button', { name: '登录' }).click()

  await expect(page.getByText('欢迎回来')).toBeVisible()
})

3.7 TypeScript 工程配置

TS 给 JS 加类型系统；工程配置（tsconfig）决定类型检查的严格度与编译输出，是项目类型安全的开关。

  • strict：开启后默认严格空值检查，是类型安全的关键开关
  • target / module：编译目标与模块系统（ES2020 / ESNext）
  • paths：路径别名映射；include / exclude：检查范围
  • 类型检查：tsc --noEmit（纯检查不输出）；Vue 项目用 vue-tsc
  • 构建配合：Vite 用 esbuild 剥离类型（不做检查），检查单独跑 vue-tsc
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "paths": { "@/*": ["./src/*"] },
    "types": ["vite/client"]
  },
  "include": ["src/**/*.ts", "src/**/*.vue"]
}

// 检查命令（Vue 项目）
// npx vue-tsc --noEmit

4深入层 · 原理进阶

4.1 构建原理（依赖图 / 代码分割 / 懒加载）

构建器从入口出发遍历 import 语句形成依赖图，再把依赖图按需拆成 chunk，运行时按需加载——这是"打包"的本质。

  • 依赖图：解析每个模块的 import/require，处理循环依赖，形成有向图
  • 代码分割：多入口、动态 import、splitChunks 把代码拆成多个 chunk
  • 懒加载：动态 import 的 chunk 在运行时才请求，减小首屏体积
  • Tree Shaking：基于 ESM 静态分析，删除未使用的导出（摇树）
  • 产物优化：压缩（terser）、合并小文件、hash 文件名做缓存
// 动态 import：构建时自动拆成独立 chunk
// 点击"打开报表"时才下载对应代码
const openReport = async () => {
  const { ReportPanel } = await import('./ReportPanel.vue')
  // 挂载组件...
}

// Tree Shaking 前提：只用 ESM 的具名导出
// import { debounce } from 'lodash-es'  // 只打包 debounce

4.2 热更新 HMR 原理

HMR（Hot Module Replacement）在不刷新页面的前提下替换修改过的模块，保住组件状态——开发体验的核心。

  • dev server 与浏览器建立 WebSocket 长连接
  • 文件变化 → 服务端只重新编译该模块 → 推送更新消息 → 客户端替换
  • module.hot.accept()：声明模块接受热替换；不接受的边界触发整页刷新
  • Vite 基于 ESM：更新边界更小、替换更快；Webpack 走完整模块图
  • 样式热更新：CSS 修改只替换样式标签，不动 JS 状态
// 模块级热替换声明（Webpack 时代写法）
if (import.meta.hot) {
  import.meta.hot.accept('./store.js', (newModule) => {
    // 替换后重新执行逻辑，保留组件状态
    setupStore(newModule.store)
  })
}

4.3 Babel 转译与 Polyfill

Babel 把新语法转成目标环境能跑的语法，Polyfill（core-js）补齐目标环境缺失的 API——兼容性的两大手段。

  • 语法转译 vs API polyfill：let/const/箭头函数是语法；Promise/Array.includes 是 API
  • preset-env：按 browserslist 目标自动决定转译与 polyfill 内容
  • core-js：按需注入 API 补丁（useBuiltIns: 'usage' 只加用到的）
  • @babel/preset-typescript 处理 TS；插件与预设执行顺序有讲究
  • 现代替代：esbuild / swc 转译更快，常用于 Vite 等工具内部
// babel.config.json
{
  "presets": [
    ["@babel/preset-env", {
      "targets": { "chrome": "60", "ie": "11" },
      "useBuiltIns": "usage",   // 按需引入 core-js polyfill
      "corejs": 3
    }]
  ]
}

// browserslist（.browserslistrc）
// > 0.5%, last 2 versions, not dead

4.4 Monorepo（pnpm workspace / Turborepo）

Monorepo 把多个包放进一个仓库统一管理：pnpm workspace 共享依赖，Turborepo 缓存任务、按变更增量构建。

  • workspace 协议：包内用 workspace:* 引用内部兄弟包，发布时替换成真实版本
  • pnpm 优势：内容寻址存储 + 硬链接，多包共享依赖、节省磁盘、防幽灵依赖
  • Turborepo：任务管道（build 依赖 lint）+ 远程/本地缓存，跳过未变更部分
  • 按变更范围（affected）增量构建：只构建改动的包及其依赖
  • 利弊权衡：统一规范、原子提交 vs 工具链复杂、权限控制难
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'

# 某包 package.json
{ "name": "@app/ui", "dependencies": { "@app/utils": "workspace:*" } }

# turbo.json（任务缓存）
{ "tasks": { "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] } } }

4.5 前端性能优化

性能优化围绕"加载快、渲染顺、可感知"，用核心指标量化，先测量再动手。

  • 核心指标 Web Vitals：LCP（最大内容绘制）、INP（交互延迟）、CLS（布局偏移）
  • 首屏优化：SSR / 预渲染 / 骨架屏 / 关键 CSS 内联
  • 资源缓存：文件名加 hash + Cache-Control 长缓存，HTML 不缓存
  • 虚拟列表：只渲染可视区域，处理万级长列表
  • 图片优化：懒加载（loading=lazy）、WebP/AVIF、响应式尺寸
  • 性能预算：在 CI 里限制体积与指标回归

<img src="photo.webp" loading="lazy" width="800" height="600" alt="照片">

<!-- 虚拟列表（Vue）：只渲染可视窗口内的项 -->

4.6 版本管理与发布策略

语义化版本 + 规范的发布门禁，决定依赖生态的兼容性与回滚能力。

  • 语义化版本：主版本（不兼容变更）/ 次版本（新增功能）/ 补丁（bug 修复）
  • 发布流程：feature → release 分支 → 打 tag → 生成 changelog → publish
  • 门禁：lint + 单测 + 构建全绿才允许发布（CI 自动化）
  • npm version patch：自动升版本号并打 tag；npm publish 发布
  • 回滚策略：revert 提交 / 重新发布旧版本；私有包配 access 权限
# 语义化版本流程
npm version patch   # 1.2.3 → 1.2.4（bug 修复）
npm version minor   # 1.2.4 → 1.3.0（新功能）
npm version major   # 1.3.0 → 2.0.0（不兼容变更）

npm publish --dry-run   # 发布前预览
# 配合 conventional-changelog 自动生成 CHANGELOG.md

4.7 前端监控与错误上报

上线后需要"眼睛"：错误监控、性能监控、用户行为分析，用线上数据驱动稳定与优化。

  • 错误捕获：window.onerror / unhandledrejection / Vue errorHandler
  • sourcemap 还原：压缩代码的报错堆栈映射回源码位置（仅上传到平台）
  • Sentry 等平台：错误聚合、告警、版本关联
  • 性能上报：Performance API 采集 LCP/INP/CLS，上报到监控
  • 上报策略：采样、去重、脱敏（不传用户敏感信息）

6常见误区与实战要点

常见误区：
  • lockfile 不提交 / 被删，导致团队与生产环境依赖版本漂移，"本地好的线上炸"
  • 把依赖一股脑装进 dependencies，运行时体积虚胖，该用 devDependencies 的没分清
  • 所有人都直接往 main 提交，没有分支与 PR 评审，冲突与事故频发
  • ESLint 规则堆到"严格到没法写"，开发体验差，最后全员 --disable 形同虚设
  • 只写"能跑"的测试不写断言，或全测组件 UI 不测业务逻辑，覆盖率虚高无意义
  • E2E 测试覆盖一切细节，跑一次十几分钟，CI 变成摆设——关键路径才用 E2E
  • 性能优化不先量化（不看 Lighthouse / Profiler）就盲目加缓存和 memo，复杂度上去了指标没变
  • sourcemap 直接发布到生产公网，源码泄露——只上传监控平台，不下发到 CDN
✅ 实战建议：先配好"包管理 + Git 分支 + ESLint/Prettier + 单测"这套底线工程；性能与监控按指标驱动，先测量再优化；E2E 只覆盖关键路径；lockfile 永远提交、永远用 CI 门禁。
