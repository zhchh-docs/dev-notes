AntV G6 图可视化

深入 定位：图（Graph）可视化引擎——节点/边的关系网络与流程编排

G6 是蚂蚁集团 AntV 团队开源的图可视化引擎（本页示例基于 v4 API；v5 已重构、API 不兼容），专治"节点 + 连线"这类图数据：流程图、组织架构、依赖网络、关系图谱。它把图数据模型（nodes/edges/combo）、布局算法、交互行为、插件收敛进一个 Graph 实例。本套技术栈用它做后端设计平台的拖拽编排与低代码开发平台的可视化流程编辑器，本页讲透数据模型、布局、交互模式与大图性能，并诚实说明它与 JsPlumb、GoJS 的分工取舍。

1技术点概览

是什么

一句话定位：G6 是关系型数据可视化引擎——输入 nodes/edges，它负责摆位、绘制与交互。

  • 输入是一张图：一组节点 nodes、一组边 edges，可选分组 combos。
  • 引擎负责四件事：布局算坐标、节点边画成图形、提供交互行为（拖拽/缩放/框选/连线）、用插件补小地图/网格/工具栏。
  • 与 ECharts 的区别：ECharts 是"图表"（数据值→坐标图形），G6 是"图"（实体与关系→拓扑布局）。

解决什么问题

一句话定位：把"图编辑基础设施"内置，业务只描述节点长相与连线规则。

  • 手撸深坑：节点命中、贝塞尔连线、拖拽坐标转换、画布缩放平移、框选多选、序列化导出，每一项都是工程坑。
  • 内置能力：G6 把这些图编辑基建封装好。
  • 项目落地：后端设计编排、流程编辑器都建立在它之上。

  • 选 G6：需要独立画布 + 布局 + 完整图编辑能力（开源、与 AntV 生态一致）。
  • 叠加 JsPlumb：在已有 Vue/ElementUI 表单节点之间只需补连线交互时。
  • GoJS：因商业授权与成本在选型阶段被否，仅做评估对比（见 GoJS 专篇）。

2核心概念

2.1 图数据模型（Graph Data Model：nodes / edges / combos）

一句话定位：边引用节点 id 而非坐标，所以布局移动节点时连线自动跟随。

  • 节点 nodes：id 唯一标识，带 data（业务字段）与 style。
  • 边 edges：用 source/target 引用节点 id，带 label 与 data。
  • 分组 combos：节点的逻辑容器，支持折叠展开。

心智模型边引用 id 不引用位置——这是图能序列化存库、再还原的基础。

2.2 布局算法（Layout）

一句话定位：布局是"算坐标"的纯函数，按图的形态选算法。

  • grid：网格；force：力导向，关系自动散开、强连接聚拢。
  • dagre：层次/有向无环图，适合流程图 DAG，按上下游自动分层。
  • radial：辐射；circular：环形。
  • 选型：流程编辑器选 dagre；关系探索选 force。

2.3 节点与边的样式及状态（Node/Edge & State）

一句话定位：样式不写死在数据里，而由状态映射管理。

  • 形状：节点 circle/rect/diamond/modelRect；边 line/polyline/cubic/quadratic。
  • 状态：默认态、选中态 selected、hover 态 active、自定义 invalid。
  • 切换：graph.setItemState(id, 'selected', true)，样式按状态自动变。

要点"规则校验失败高亮"这类需求只需切状态，不必手动改样式。

2.4 交互行为与模式（Behaviors / Modes）

一句话定位：交互以行为为单位注册，模式是行为集合，用于编辑态/只读态切换。

  • 常用行为：drag-canvas、drag-node、zoom-canvas、click-select、brush-select、create-edge。
  • 模式切换：default 可拖可缩；进入"连线模式"只允许 create-edge。
  • 用途：流程编辑器"编辑态/只读态"切换的核心机制。

2.5 事件系统（Events）

一句话定位：按"图形:事件"粒度监听，回调带节点 id。

  • 常用事件：node:click/node:drag/edge:click/canvas:click/afterlayout。
  • 用途：点节点弹配置面板、拖完触发校验、建边时校验规则。
  • 坐标换算：v4 区分画布坐标与数据坐标，graph.getPointByClient() 换算。

2.6 插件（Plugins：Minimap / Grid / Toolbar）

一句话定位：插件挂在 Graph 上补周边 UI，与主图数据联动。

  • Minimap：小地图大图导航；Grid：对齐网格；Toolbar：缩放/适应；History：撤销重做。
  • 典型组合：流程编辑器 = G6 内核 + Minimap + Grid + History。

2.7 渲染层与引擎（Render & Engine）

一句话定位：SVG/Canvas/WebGL 后端按规模选型，内核分层可插拔。

  • 取舍：节点少需 CSS/可访问性用 SVG；节点上千频繁重绘用 Canvas/WebGL。
  • 分层架构：图模型、布局、渲染、交互拆成内核层可插拔模块，可替换布局算法或自定义节点渲染器。
  • 关键版本对齐：v5（2024 起）为命名导入 new Graph()、节点/边用 node/edge 映射、交互用 behaviors、数据先 setData() 再 render()，与 v4 的 new G6.Graph({defaultNode,modes}) 不兼容——本页代码按 v4 写法，升级 v5 需对照迁移指南改写法。

2.8 数据驱动更新与序列化（Update & Serialization）

一句话定位：改 data 后 render 全量重绘，单节点用 updateItem，save/restore 存取。

  • 全量：改 graph.data() 再 render()。
  • 增量：单节点 updateItem(id, cfg)；增删 addItem/removeItem。
  • 存取：graph.save() 导出图数据 JSON，存库后 restore。

3工作原理与流程

3.1 渲染管线：从图数据到可交互画布

图 2 G6 从图数据到可交互画布的管线（示意）

  1. 喂数据：graph.data({nodes, edges}) 建立数据层，此时不绘制。
  2. 布局：render() 触发布局算法给每个节点算坐标，边按 source/target 自动连。
  3. 实例化与绘制：每个节点/边变成图形对象，按渲染层画到画布。
  4. 交互绑定：modes 里的行为挂上画布，事件系统开始分发。

3.2 大图性能：为什么千节点会卡，怎么救

图 3 大图渲染的瓶颈与优化策略（示意）

  1. 选对布局：力导向适合几百节点的探索图；上千节点用 dagre/grid 一次性布局，避免 O(n²) 迭代。
  2. 换渲染层：节点过千即从 SVG 切 canvas，消除 DOM 膨胀。
  3. 增量更新：平时交互只 updateItem，避免每次 render() 全重建。
  4. 视口裁剪与折叠：只画视口内的节点边，combo 默认折叠，展开时再加载子图。

4核心语法与 API 要点

4.1 最小可运行图

import G6 from '@antv/g6';
const graph = new G6.Graph({
  container: 'container',
  width: 800, height: 500,
  layout: { type: 'dagre', rankdir: 'LR' },     // 从左到右分层
  defaultNode: { type: 'rect', size: [140, 40] },
  defaultEdge: { type: 'polyline', style: { stroke: '#9cae90' } },
  modes: {
    default: ['drag-canvas', 'zoom-canvas', 'drag-node', 'click-select']
  },
  plugins: [ new G6.Minimap({ size: [120, 80] }), new G6.Grid() ]
});
graph.data({
  nodes: [
    { id: 'start', data: { label: '开始' } },
    { id: 'task',  data: { label: '执行任务' } },
    { id: 'end',   data: { label: '结束' } }
  ],
  edges: [
    { source: 'start', target: 'task' },
    { source: 'task',  target: 'end' }
  ]
});
graph.render();

4.2 写法对比：全量 render() vs 增量 updateItem

// 写法 A：数据整体替换 → 全量 render（结构大变/初次加载时用）
graph.setData(newGraphData);
graph.render();                 // 重跑布局 + 重建所有图形

// 写法 B：只改一个节点 → 增量更新（高频交互时用，便宜）
graph.updateItem('task', {
  style: { fill: '#fef3c7' },   // 只改这个节点
  data: { label: '已修改' }
});
// 加/删单项
graph.addItem('node', { id: 'n4', data: { label: '新节点' } });
graph.removeItem('node', 'task');
取舍：render() 是"把整图推倒重摆"，只在首次加载或结构大改时用；日常的节点拖动、状态切换、单节点改样式都走 updateItem/updateEdge，避免重跑布局与重建 DOM。这是流程编辑器拖拽时不卡的关键。

4.3 状态切换与规则校验高亮

graph.on('edge:mouseup', (e) => {
  const edgeModel = e.item.getModel();
  const ok = validateConnection(edgeModel.source, edgeModel.target);
  if (!ok) {
    // 校验失败：把边切到自定义 invalid 态，样式在注册时映射成红色虚线
    graph.setItemState(e.item, 'invalid', true);
  }
});
// 注册状态样式映射
graph.on('afterrender', () => {
  // 或在初始化 nodeStateStyles/edgeStateStyles 配置
});

4.4 模式切换：编辑态 vs 只读态

// 进入连线模式：只允许 create-edge，禁止拖节点/画布
graph.setMode('addEdge');
// modes 初始化时声明

4.5 序列化保存与还原

const data = graph.save();          // 导出 {nodes, edges} 含坐标与样式

5实战项目经验（实战落地）

5.1 项目背景（业务量级/场景）

一句话定位：两个平台都要可视化编排——数据编排平台画后端数据流，低代码平台画审批流程。

  • 数据编排平台：后端设计平台（Vue2+ElementUI+Vuex），拖出数据源/处理/输出节点并连线表达数据流向，节点是带配置表单的 Vue 组件。
  • 低代码平台：流程编辑器（Vue3+Vuex+G6），节点上千，需拖拽编排、动态规则校验、历史回溯与版本对比。

5.2 我的角色与职责

一句话定位：画布层前端，负责图模型、交互、规则校验与性能。

  • 分工：负责 G6 画布、自定义 Vue 节点、连线与规则校验引擎；后端负责图数据 JSON 存读。
  • 协作：与产品确认连线规则（输出不能接输出、审批节点必须有处理人）。

5.3 技术栈

  • 数据编排平台：Vue2 + ElementUI + Vuex + G6 + JsPlumb + vxe-table + Monaco。
  • 低代码平台：Vue3 + Vuex + G6，沉淀流程校验/历史回溯/版本对比组件库。

5.4 落地设计（关键选型理由）

一句话定位：G6 管整体图模型与布局，JsPlumb 补 DOM 端口连线，canvas 渲染层扛千节点。

  • 分工：G6 管画布缩放/小地图/整体布局；端口级锚点吸附交给 JsPlumb（为 DOM 连线设计）。
  • 布局：选 dagre 一次性分层，不用力导向（千节点每次交互重算会卡）。
  • 渲染：低代码平台切 canvas 渲染层 + Minimap/Grid/History 插件。

5.5 关键实现要点

const graph = new G6.Graph({
  container: 'editor', width: '100%', height: '100%',
  renderer: 'canvas',                 // 千节点：canvas 渲染层
  layout: { type: 'dagre', rankdir: 'LR' },
  modes: { default: ['drag-canvas', 'zoom-canvas', 'drag-node', 'click-select'] },
  plugins: [ new G6.Minimap(), new G6.Grid(), new G6.History() ]
});
graph.on('afteredgeadd', (e) => {
  const m = e.edge.getModel();
  if (!validFlow(m.source, m.target)) {
    graph.setItemState(e.edge, 'invalid', true);   // 红色虚线告警
    toast.error('非法连接：输出不能接输出');
  }
});
graph.on('node:dragend', () => validateFlow(graph));   // 拖完触发规则校验

5.6 真实问题与解法

  • 坑两层坐标系错位：全用 G6 做端口连线，Vue 节点内部端口 DOM 与 G6 画布坐标换算错位——端口连线交给 JsPlumb，G6 只管整体。
  • 坑连线建了两条：create-edge 与 JsPlumb 拖拽重复触发——统一建边入口。
  • 坑表单输入丢失：自定义 Vue 节点 render() 全量重建把编辑中节点销毁——改增量 updateItem。
  • 坑力导向卡/SVG 掉帧：千节点用力导向每次交互重算、SVG 模式 DOM 上千掉帧——换 dagre + canvas 渲染层。
  • 要点校验全量遍历：每次拖动全量遍历千节点是长任务——改只校验受影响节点及邻居的增量校验，配合 rAF。

5.7 量化成果

  • 规模：低代码平台支持上千节点流程流畅拖拽（估算），违规连线实时拦截。
  • 复用：沉淀流程校验/历史回溯/版本对比组件库，复用于后续流程类需求。

5.8 协作与排期过程

  • 契约先行：与后端约定图数据 JSON 格式（graph.save() 存、read() 还原坐标）。
  • 规则协商：与产品逐条确认连线合法性规则，落成校验引擎配置。

5.9 复盘与可复用经验

  • 要点按职责分工：G6 管图模型/布局，DOM 端口连线交给 JsPlumb，别让一个库硬撑。
  • 要点大图画布选 dagre+canvas：力导向与 SVG 在千节点量级都会卡。
  • 要点校验增量化：规则校验只跑受影响子图，别整图遍历。

5.10 面试讲法

实战要点「上千节点的流程编排，实践中常采用 G6 canvas 渲染层+dagre 一次性布局扛住拖拽，端口连线拆给 JsPlumb 解决坐标系错位，规则校验改增量只跑受影响子图。」

6易错点与面试重点

6.1 边引用坐标还是 id

  • 误区：把边写成"从坐标 A 到坐标 B"。

坑正解：边引用节点 id（source/target），坐标由布局或拖拽决定——节点移动时连线自动跟随，也才能序列化存库。

6.2 每次交互都 render() 全量重建

  • 现象：拖一下节点整图闪一下、节点内表单状态丢失。
  • 原因：render() 重跑布局并重建所有图形对象。

坑正解：交互期用 updateItem/addItem/removeItem 增量更新；只有首次加载或整体数据替换才 render()。

6.3 力导向布局扛大图

  • 现象：几百上千节点时布局计算卡顿、节点抖动不停。
  • 原因：力导向是 O(n²) 迭代，节点多了每帧重算所有节点的引力斥力。

坑正解：流程/DAG 选 dagre，规整图选 grid；力导向只留给几百节点的探索图。

6.4 SVG 渲染层画大图

  • 现象：节点过千后画布拖动掉帧、内存上涨。
  • 原因：SVG 每个节点一个 DOM 元素，上千节点让 DOM 树与样式计算暴涨。

坑正解：节点量级上去后切 renderer:'canvas'（或 WebGL 渲染层）；SVG 只留给小图或需可访问性场景。

6.5 保存后重开坐标丢失

  • 现象：graph.save() 存库后再加载，节点全挤在一起或错位。
  • 原因：还原时又跑了一遍自动布局，覆盖了用户拖拽的坐标。

坑正解：还原用 graph.read()（保留数据里已有坐标、不重排），而不是 graph.data()+render()（会重新布局）。

6.6 G6 与 JsPlumb 坐标系混用错位

  • 现象：G6 画布节点与 JsPlumb 连线对不齐。
  • 原因：两者画布/视口变换（缩放平移）各自维护，混用同一 DOM 时坐标换算不一致。

坑正解：明确分工——G6 管整体画布与节点布局，JsPlumb 只在同一坐标系的 DOM 节点间补端口连线；连线入口统一，避免两套引擎同时建边。
