1简介与阅读指引

1.1 定位：本质矛盾与主流解法

大屏（数据可视化监控屏）的适配与普通 Web 响应式目标不同：普通页面"内容随宽度重排"，大屏要"一张设计稿在任意屏幕上保持布局比例不变"。三大方案：①scale 等比缩放（主流）——按 1920×1080 设计稿开发，运行时对 #app 整体 transform: scale()；②rem/vw 动态根字号——尺寸全用 rem，按屏宽换算根字号；③纯响应式——Grid/flex + 媒体查询重排（成本最高，大屏布局复杂时不现实）。

1.2 横向对比：三方案取舍

方案还原度改造成本主要问题适用
scale 等比缩放100% 还原设计稿极低（一处 transform）缩放模糊、事件坐标偏移、iframe 内层级大屏首选
rem/vw高（等比）中（尺寸全换算）非等比屏幕仍要留白策略；canvas 内不自动跟混合方案/移动端
纯响应式按断点重排高布局复杂时工作量爆炸后台系统/官网

1.3 学习目标与阅读指引（实战锚点）

  1. 掌握 scale 方案的完整实现（等比/全铺满/留白三策略 + 事件坐标修正）；
  2. 理解 缩放后 ECharts resize 的必要性——不做就是"图表错位"事故；
  3. 会用 ResizeObserver 监听容器（微前端子应用尤其）；
  4. 知道三方案的取舍与混合用法。

实战锚点：本套技术栈的电力大屏（01 模块 01 篇 rem 缩放 Demo、02 篇 ResizeObserver）正是本篇方案的真实落地——两处实战互相引用。难度：★★☆☆☆。

2核心模型

四个核心模型：scale 三策略→ 事件坐标换算→ rem/vw 换算→ resize 信号链。

2.1 scale 三策略：等比/全铺满/留白

  • 等比留白：scale = min(sw/1920, sh/1080)，居中——比例保持、两侧留黑边（大屏默认）；
  • 等比铺满：scale = max(...)——无留白但内容可能超出被裁剪；
  • X/Y 独立缩放：scale(sw/1920, sh/1080)——铺满但比例被拉伸变形（字变形，慎用）。

核心：三策略是"完整性 vs 满屏观感"的取舍——电力大屏选等比留白（数字不能变形）。

2.2 事件坐标换算：scale 的隐形税

transform: scale(0.8) 后，鼠标 clientX 是缩放后的屏幕坐标，而元素内逻辑坐标是设计稿坐标——两者差 scale 倍。依赖 e.offsetX/e.clientY 手算的交互（自定义 tooltip、画框选）必须除以 scale 修正；用库内事件（ECharts getZr().on）时它已按容器尺寸处理，但要确保容器尺寸取的是缩放前逻辑值。

2.3 rem/vw：尺寸单位的等比换算

rem 方案：设计稿 1920 宽分 24 份，1rem=80px，JS 按屏宽设 html.style.fontSize，CSS 里 px→rem（PostCSS 插件自动换算）；vw 方案：直接 1vw=屏宽 1%，100vw=1920 时 1px = 0.052vw，无需 JS。局限：canvas 类图表不随 rem 缩放（要靠 chart.resize），所以大屏常 rem 管布局 + scale 管整体。

2.4 resize 信号链：谁变了谁 resize

触发源三层：window.resize（窗口变）、scale 变化（我们的缩放函数里主动调）、容器变化（ResizeObserver——微前端子应用/抽屉开合时窗口没变但容器变了）。坑：ECharts init 时按容器尺寸定布局，之后不自动跟踪——每个变化源都要汇聚到 chart.resize()。

3核心用法（按场景）

3.1 场景一：scale 等比缩放完整实现（主力方案）

const DESIGN_W = 1920, DESIGN_H = 1080;
function fitScreen() {
  const sw = window.innerWidth, sh = window.innerHeight;
  const scale = Math.min(sw / DESIGN_W, sh / DESIGN_H);   // 等比留白策略
  const el = document.querySelector('#screen');
  el.style.transform = `scale(${scale})`;
  el.style.transformOrigin = 'left top';
  el.style.left = (sw - DESIGN_W * scale) / 2 + 'px';     // 居中
  el.style.top  = (sh - DESIGN_H * scale) / 2 + 'px';
  chart && chart.resize();                                 // 缩放后必触发
}
window.addEventListener('resize', fitScreen);
fitScreen();

CSS 侧：#screen { width:1920px; height:1080px; position:absolute; }——按设计稿固定尺寸开发。

3.2 场景二：ResizeObserver 监听容器（微前端必加）

const ro = new ResizeObserver(() => chart.resize());
ro.observe(document.getElementById('panel'));
// 卸载时 ro.disconnect()，成对清理（02 篇 ECharts dispose 同款纪律）

3.3 场景三：rem 动态根字号

function setRem() {
  const w = document.documentElement.clientWidth;
  document.documentElement.style.fontSize = (w / 24) + 'px';  // 1920 分 24 份，1rem=80px
}
window.addEventListener('resize', setRem);
setRem();
// CSS 配合 PostCSS px2rem：设计稿 160px → 2rem，任意屏等比

3.4 场景四：事件坐标修正

// scale 后自定义交互：屏幕坐标 → 设计稿逻辑坐标
function toLogic(e) {
  const scale = currentScale;                  // 缓存当前 scale 值
  const rect = screenEl.getBoundingClientRect();
  return {
    x: (e.clientX - rect.left) / scale,
    y: (e.clientY - rect.top) / scale
  };
}

4进阶知识点【进阶】

首次学习可整章跳过。前置：scale 方案已会实现。

4.1 缩放模糊与 text-rendering

transform: scale 是先渲染后变换——非整数倍缩放时文字/线条亚像素插值发虚。缓解：①关键数值大字号（放大 1.2 倍反而更清晰）；②阴影/边框用 0.5px 以内的设计避免锯齿放大；③对清晰度极敏感的数字牌用独立层不缩放（按屏宽 rem 定字号）。

4.2 超宽屏与拼接屏

现场常见 3840×1080（两屏拼接）或 7680×2160：等比留白会留出巨大黑边——工程做法是设计稿升级为对应比例（如 3840×1080 版式重排）或分区域独立 scale；拆分渲染：每个拼接单元独立浏览器实例拉取自己的分区（与 09 篇大数据量拆分同思想）。

4.3 iframe/微前端内的适配层级

Qiankun 子应用挂进主应用容器：主应用做 scale，子应用内部不要再 scale（双重缩放）；子应用只负责 ResizeObserver 监听容器变化 → chart.resize（02 篇 ECharts 实战同款）。坑：主应用 scale 后 getBoundingClientRect 返回的是缩放后值——跨边界坐标传递要统一换算。

4.4 视频与 WebGL 层的适配

video/canvas 画面在 scale 下与 DOM 同步缩放，但性能敏感层建议反向操作：外层不缩放、内部 canvas 按实际分辨率 setSize（GPU 像素对齐更清晰）——Three.js 大屏（06 篇）用 renderer.setSize(realW, realH) 而非吃 scale。

4.5 分辨率与 DPR

4K 屏上 1080p 设计稿放大 2 倍：DOM 矢量无损，但位图图片糊——素材按 @2x 出图；ECharts 的 renderer 分辨率随容器 devicePixelRatio 自动处理（v5 默认），大字号下无需干预。

7常见坑 & Debug

五条高频坑。

7.1 缩放后 ECharts 不 resize，图表错位

原因：init 时按容器定布局，不自动跟踪。正解：三个触发源（window.resize/scale 变化/ResizeObserver）全部汇聚到 chart.resize（图 2）。

7.2 X/Y 独立缩放拉变形

现象：文字压扁、圆形变椭圆。正解：数字大屏禁用 skew/独立缩放，等比 min 策略留白。

7.3 事件坐标未除 scale

现象：自定义框选/tooltip 位置偏移。正解：屏幕坐标 → 逻辑坐标统一换算（3.4 toLogic），坐标换算收口一个函数。

7.4 微前端双重缩放

现象：子应用内容缩了两倍。正解：缩放权在主应用；子应用只监听容器变化做 chart.resize。

7.5 100vh/百分比高度链断裂

现象：容器高度塌陷、地图/图表不显示。正解：显式高度或 100% 链路打通（01 模块同款坑），大屏根节点用固定设计稿尺寸绕开 vh 问题。

8重点讲解

Q1：大屏适配为什么主流用 scale 等比缩放而不是响应式？

参考答案：目标不同——普通页面"内容随宽度重排"，大屏要"设计稿在任意屏幕保持布局比例"（大屏布局是精心排布的整体，重排=设计作废）。scale 方案：按 1920×1080 开发，运行时对根节点 transform:scale(min(sw/1920,sh/1080))——一处代码 100% 还原。代价与对策：非整数倍缩放文字发虚（关键数值大字号）、事件坐标差 scale 倍（统一 toLogic 换算）、缩放后 ECharts 必须手动 resize。rem/vw 作为补充管字号细节。三策略取舍：等比留白（数字不变形，默认）/等比铺满（接受裁剪）/独立缩放（变形，监控大屏禁用）。

Q2："缩放后图表错位"的完整因果与修复？

参考答案：因果链——ECharts 在 init 时按容器尺寸计算布局，之后容器任何变化都不自动跟踪；scale 改变了视觉尺寸但没通知图表。修复是建立resize 信号链：window.resize、fitScreen 内 scale 变化、ResizeObserver 容器变化，三个触发源全部汇聚到 chart.resize()。实战坑：微前端子应用"窗口没变但容器变了"（抽屉开合/主应用布局调整），必须 ResizeObserver——02 篇 ECharts 实战（旧内核退回 resize 防抖）与本篇是同一信号链。纪律：卸载时 observer.disconnect()，成对清理。

Q3：拼接屏/超宽屏怎么适配？

参考答案：3840×1080 等超宽比例下，1920 设计稿等比留白会黑边过半——缩放方案解决不了"版式比例不匹配"。工程做法：①设计稿升级为对应比例（3840×1080 版式重排，内容重新分区）；②拼接屏拆分渲染：每个拼接单元独立浏览器实例拉取自己的分区数据（与大数据量拆分同思想），各自 1080p 等比适配；③混合：核心区独立 scale、装饰带响应式拉伸。本质：适配方案的选择前提是"版式比例先对齐"。
