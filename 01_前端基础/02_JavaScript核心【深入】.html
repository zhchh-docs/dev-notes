JavaScript 核心

深入 定位：前端编程语言本体——类型、作用域、闭包、this、原型链的心智模型

JavaScript 的"难"不在语法，而在一套与多数后端语言不同的执行模型：动态类型、词法作用域、函数即对象、原型继承、闭包捕获词法环境。本页从执行上下文与调用栈讲起，落到闭包、this、原型链三块硬骨头，再以 智能监控大屏 智能监控与数据可视化大屏项目的真实代码（光跟踪算法、分布式数据聚合、自研 Grid/Tree/Dialog 插件）展示这套语言如何支撑一个 10 年的前端栈。异步与事件循环单独成页，本页聚焦"语言本体"。

1技术点概览

是什么

一句话定位：日常说的 JS 是三层叠加——语言标准 + DOM + BOM，由 V8 实现语言、浏览器宿主再挂接口。

  • ECMAScript（ES）：语言标准本身（语法、类型、原型、闭包），由 ECMA-262 定义、TC39 按年滚动发布（ES2015/ES2020…）。
  • DOM API：浏览器提供的"操作网页"接口（Document Object Model）。
  • BOM：与浏览器外壳打交道的接口（window/navigator/location 等）。

"JS 难"常难在：同一门语言在浏览器里既有函数式一面（一等函数、闭包），又有命令式操作 DOM 一面，还有动态类型带来的运行期意外。

解决什么问题

一句话定位：JS 把网页从静态文档变成应用；功底分水岭是"能否预测代码在运行期做了什么"。

  • 它是浏览器里唯一能动态执行逻辑的语言：表单校验、交互、数据请求、Canvas、实时大屏都靠它。
  • 分水岭：不在"会不会写 for"，而在能否预测运行期——this 指向谁、闭包捕获哪个变量、原型链在哪步命中、GC 会不会漏掉大对象。

这些恰是 jQuery 时代插件、大屏实时聚合这类"无框架兜底"代码里最容易埋雷的地方。

  • 原生 ES vs TypeScript：TS 不改变运行时，它在编译期把类型擦除成普通 JS。原生 JS 的动态性是"灵活但把错误推迟到运行期"，TS 把这部分风险前移到编译期。本套技术栈早期（智能监控大屏、大屏）全是原生 JS + jQuery，后期 业务系统 全面切到 TS——迁移的收益正是"大型公共包与 API 客户端不再靠人肉契约"（见 TypeScript 页）。
  • 命令式操作 DOM vs 框架声明式渲染：jQuery/原生时代，状态与 DOM 的同步全靠手写（改 .text()、.html()），一旦状态分支多就极易漏改。Vue/React 用"数据驱动视图"接管了这层映射，代价是要接受框架的响应式模型。理解原生 JS 仍然必要：框架编译产物、虚拟 DOM diff、插件底层最终都是原生 JS。
  • CommonJS vs ESM 模块：早期大屏 Webpack 项目用 CommonJS（require，运行时动态加载、值拷贝），现代 Vite/Node 用 ESM（import/export，编译期静态分析、活绑定、可 tree-shaking）。工程选型上，新代码一律 ESM，老代码靠工具兼容。

2核心概念

2.1 动态类型与隐式转换（Dynamic Typing & Coercion）

一句话定位：变量无类型、值才有类型，错误全部推迟到运行期——工程上用显式转换与 === 把不确定性压死。

  • 动态类型：变量不绑定类型，今天存数字、明天存字符串都合法；类型检查发生在运行期，而非编译期。
  • 按值 vs 按引用：六种原始类型（number/string/boolean/null/undefined/symbol，ES2020 加 bigint）赋值拷贝值；object（含数组、函数）赋值只拷贝引用。
  • 隐式转换：运算符两侧类型不一致时引擎自动转换——+ 遇字符串会拼接，== 按抽象相等规则辗转比较，是大量"看起来对其实错"的根因。

铁律比较一律用 ===（不转换、值与类型都比）；需要转换时显式写 Number(x) / String(x)，不依赖引擎的隐式行为。

2.2 执行上下文与作用域链（Execution Context & Scope Chain）

一句话定位：变量从哪来由"源码写在哪"决定，引擎靠沿作用域链向上查找来解析名字。

  • 执行上下文：每进入一段可执行代码，引擎就建一个上下文——全局一个、每次函数调用一个；里面存当前作用域的变量声明与对外层词法环境的引用。
  • 作用域链：沿父词法环境引用一路向上直到全局对象，形成一条链；查变量时从当前作用域开始沿链找，命中即停。
  • 词法作用域（静态作用域）：变量可见性由函数在源码中的书写位置决定，与"谁调用它"无关——这是闭包成立的前提。

2.3 闭包（Closure）

一句话定位：函数把"出生时所在的词法环境"绑在自己身上，即使外层函数已返回，仍能访问那些变量。

  • 本质：内部函数在创建时把外层词法环境捕获到自身；外部函数返回后，这个环境因仍被函数引用而不被垃圾回收。
  • 典型用途：数据私有化（模块模式）、回调保持状态、函数柯里化、防抖节流——都靠闭包留住"上次的状态"。

坑被闭包长期引用的对象不会被回收；在大屏长驻页面里用闭包持有大数组，会造成"切屏后内存只涨不降"。

2.4 this 的绑定规则（this Binding）

一句话定位：this 不看函数定义在哪，而看它"怎么被调用"——四条规则按优先级裁决。

  • new 调用（最高优先级）：new Foo()，this 是新创建的实例对象。
  • 显式绑定：foo.call/apply/bind(ctx)，this 是手动传入的 ctx。
  • 隐式绑定：obj.foo()，this 是调用点前面的对象 obj。
  • 默认绑定（兜底）：直接 foo()，严格模式下是 undefined，非严格模式是全局对象。
  • 箭头函数：不绑定自己的 this，捕获定义处的 this——回调里"this 丢了"的标准解法。

坑把对象方法当回调传出去（setTimeout(obj.foo)）后，this 退化为全局/undefined；要么用箭头函数包一层，要么 .bind(obj)。

2.5 原型与原型链（Prototype & Prototype Chain）

一句话定位：JS 没有经典继承，对象靠"内部指针委托"把属性查找沿原型链向上传递。

  • 委托而非复制：每个对象内部有隐藏指针 [[Prototype]]（经 __proto__ 访问）指向另一个对象；自身没有的属性沿链向上找，直到 null。
  • prototype vs __proto__：prototype 是函数的属性，指向"实例的原型对象"；__proto__ 是实例指向其原型对象的链接。两者方向相反，是最易混的点。
  • new 接线：new 出来的实例，其 __proto__ 指向构造函数的 prototype。

要点改了原型对象上的方法，所有"继承自它"的对象都会看到——这正是 class 只是语法糖、以及"为什么改数组原型全局生效"的底层原因。

2.6 class 与继承（ES6 Class）

一句话定位：ES6 class 不是新的继承模型，而是原型继承的语法糖。

  • 三个关键件：constructor 对应原构造函数；extends 经 Object.setPrototypeOf 接好父子原型链；super() 调用父类构造函数。
  • 细节：类方法默认不可枚举，static 成员挂在构造函数本身上；#privateField 是运行期真正的私有字段。

工程上 class 比手写 Child.prototype = new Parent() 清晰得多；自研 Grid/Tree 插件的内部状态就用私有字段藏住。

2.7 模块化：ESM 与 CommonJS（Modules）

一句话定位：模块解决全局污染与代码组织；ESM 静态、CommonJS 运行时，二者语义不同。

  • ESM（import/export）：编译期静态确定导入导出，支持 tree-shaking；绑定是活的（导出值变，导入方跟着变）；模块只执行一次、形成单例。
  • CommonJS（require/module.exports）：运行时动态加载；对原始类型导出的是值拷贝（首次 require 时快照，导出方重新赋值不影响导入方），对对象/数组仍是共享引用（导入方修改其属性会同步回导出方）。

坑老 CommonJS 构建里"改了导出对象的字段页面没更新"，往往就是值拷贝/活绑定的差异所致；大屏老项目走 CJS，业务系统 走 ESM。

2.8 垃圾回收与内存管理（Garbage Collection）

一句话定位：V8 靠"可达性"决定回收，前端内存泄漏几乎都是"本该不可达却仍被引用"。

  • 可达性判定：从根（全局对象、当前调用栈变量）出发能到达的对象保留，不可达的回收。
  • 回收算法：早期引用计数因循环引用被淘汰；现代引擎以标记-清除为主，辅以分代回收（新生代 Scavenge、老生代 Mark-Compact）。
  • 防泄漏工具：WeakMap/WeakSet 的 key 是弱引用，不阻止 GC 回收——用它给 DOM/对象挂附加数据（weakMap.set(el, meta)），元素被销毁后条目自动消失，是避免"全局表长期持有大对象"的标准做法。

坑三类典型泄漏：未解绑的事件监听、忘记清理的定时器、被闭包或全局数组长期持有的大对象——大屏"切屏后内存只涨不降"基本都能归到这三类。

3工作原理与流程

3.1 调用栈与执行上下文生命周期

JS 是单线程执行：同一时刻只跑一段代码，靠调用栈（call stack）记录"现在执行到哪个函数、该返回哪里"。每进入一个函数就压入一个执行上下文，函数返回就弹出。栈有上限（V8 约一万余帧），递归过深就是栈溢出。下图是一次函数调用的入栈过程：

图 2 调用栈与执行上下文生命周期（示意）

  1. 全局上下文入栈：页面脚本启动，先创建全局上下文并压栈。
  2. 函数调用压栈：每调用一个函数，创建其执行上下文（含变量环境、this、外层作用域链引用）压到栈顶。
  3. 栈顶即当前：JS 永远只执行栈顶上下文的代码；变量查找沿作用域链、this 按当前调用规则确定。
  4. 返回出栈：函数返回，上下文弹出。若其内部函数已被外部引用（闭包），词法环境不被回收——这就是闭包的内存本质。

为什么这样设计：JS 用"对象关联对象"而非"类拷贝实例"，节省内存——所有实例共享同一份方法（方法挂在 prototype 上，而不是每个实例复制一份）。代价是理解成本：for...in 会把原型上可枚举的属性也遍历出来，必须用 hasOwnProperty 过滤；随意给原型塞方法会造成原型污染（pollution），被第三方库或恶意输入利用。

4核心语法与 API 要点

4.1 现代变量声明：let/const 与暂时性死区

const MAX = 100;          // 基本类型：不可重新赋值，优先用 const
let count = 0;            // 需要重新赋值才用 let
// var count = 0;         // 函数作用域 + 提升 + 挂全局，新项目不再用

console.log(a);           // let/const 在声明前访问 = ReferenceError（暂时性死区 TDZ）
let a = 1;

对比：var 是函数作用域，存在提升（声明被提到作用域顶部、值为 undefined），且在循环里用 var 会导致所有迭代共享同一个变量（经典闭包陷阱）。let/const 是块级作用域，彻底解决这两个问题。

4.2 this 绑定：四种写法对比

const grid = {
  name: '告警表',
  render() { console.log(this.name); }
};
grid.render();                 // 隐式绑定：this = grid，输出"告警表"

const fn = grid.render;
fn();                          // 丢失绑定：this = undefined（严格模式），报错！

const bound = grid.render.bind(grid);   // 显式 bind：永久锁定 this = grid
setTimeout(bound, 100);

// 箭头函数：不绑定自己的 this，捕获定义处的 this
const obj = {
  name: 'x',
  tick() { setTimeout(() => console.log(this.name), 100); }  // this 仍是 obj
};

4.3 手写 call / apply / bind

Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx || globalThis;
  const key = Symbol();
  ctx[key] = this;              // 把当前函数临时挂到 ctx 上
  const res = ctx[key](...args); // 以 ctx 为 this 调用
  delete ctx[key];
  return res;
};
// apply 与 call 只差在参数：apply 收数组，call 收展开参数
// bind：返回一个永久绑定 this 的新函数（上方 bound 的底层逻辑）

4.4 闭包实战：私有状态与模块化

// 闭包实现模块私有变量：外部无法直接触碰 _counter
function createCounter(init = 0) {
  let _counter = init;                 // 被返回函数闭包引用，不随函数返回销毁
  return {
    inc() { return ++_counter; },
    get() { return _counter; }
  };
}
const c = createCounter(10);
c.inc(); c.inc();
console.log(c.get());    // 12；外部访问不到 _counter

4.5 原型与 class 两种继承写法对比

// 老式原型继承（易写错：Child.prototype = new Parent() 会执行父构造）
function Parent(name) { this.name = name; }
Parent.prototype.say = function () { return this.name; };

// 新式 class（等价、清晰，工程统一用这个）
class Parent2 {
  constructor(name) { this.name = name; }
  say() { return this.name; }
}
class Child extends Parent2 {
  constructor(name, age) { super(name); this.age = age; }  // super 必调
}
const ch = new Child('row', 3);
console.log(ch.say());   // 'row'，沿原型链命中 Parent2.prototype.say

4.6 数组与常用高阶 API

const rows = [{ level: 1 }, { level: 2 }, { level: 1 }];
// map / filter / reduce / find：纯函数风格，避免手写 for
const alarms = rows.filter(r => r.level === 1).map(r => ({ ...r, status: 'alarm' }));
const total = rows.reduce((sum, r) => sum + r.level, 0);
// 注意：filter/map 返回新数组，不污染原数据；改原数据用 forEach 或直接索引

5实战项目经验（实战落地）

5.1 项目背景

一句话定位：智能监控大屏——把多个变电站的摄像头画面、光跟踪算法框选结果、设备状态聚到一屏展示。

  • 业务场景：调度中心一屏看多站，算法侧通过 WebSocket/轮询推送归一化目标坐标，前端要做数据清洗、聚合、叠加层绘制。
  • 量级：单屏并发约 9 路视频叠加（估算），多个采集节点分布式上报。
  • 年代：约 2016-2018，Vue2 尚新、jQuery 仍是主力，靠原生 JS 功底无框架兜底。

5.2 我的角色与职责

  • 角色：前端开发，负责监控叠加层的数据处理与 Grid/Tree/Dialog 通用插件。
  • 团队与分工：前端 2-3 人、算法与后端若干（估算）；我负责前端数据聚合、去重与插件这一块，并与算法侧对坐标协议。

5.3 技术栈

  • 前端：Vue2 + jQuery 混合 + 原生 JS（闭包、原型、事件委托）。
  • 通信：后端 Java，WebSocket + 轮询双通道推送。
  • 组件：现场老机器跑不动 ElementUI，团队自研基于 jQuery 的 Grid/Tree/Dialog 插件。

5.4 落地设计

  • 闭包跟踪注册表：每路视频维护私有 tracks，外部只能经 update/clear 操作，防多轮推送互相污染。
  • 分布式去重：按 deviceId 归一，时间戳旧的丢弃。
  • 坐标换算：算法输出 0~1 归一化坐标，叠加层用百分比等比定位对齐画面。
  • 聚合与插件：用 reduce 把告警按站点分桶；Grid 方法挂在原型上共享给所有实例。

5.5 关键实现要点

// 跟踪注册表：闭包封装私有 tracks，防止外部直接篡改
function createTrackStore() {
  const tracks = {};                 // 私有：{ [deviceId]: { box, ts } }
  return {
    update(deviceId, box, ts) {
      const old = tracks[deviceId];
      if (old && old.ts > ts) return;   // 分布式乱序：旧数据丢弃
      tracks[deviceId] = { box, ts };
      renderOverlay(deviceId, box);
    },
    clear(deviceId) { delete tracks[deviceId]; hideOverlay(deviceId); },
    snapshot() { return Object.keys(tracks).map(id => ({ id, ...tracks[id] })); }
  };
}
// 告警聚合：扁平数组 → 按站点分桶（reduce 纯函数）
function groupBySite(alarms) {
  return alarms.reduce((acc, a) => {
    (acc[a.site] = acc[a.site] || []).push(a);
    return acc;
  }, {});
}
// Grid 插件原型：方法共享给所有实例
function Grid(el, options) { this.$el = el; this.rows = options.rows || []; }
Grid.prototype.render = function () { /* 渲染 rows */ };
Grid.prototype.sortBy = function (key) {
  this.rows = [...this.rows].sort((a, b) => a[key] - b[key]);  // 不改原数组
  this.render();
};

5.6 真实问题与解法

  • var 循环闭包事故：for 循环用 var 绑定每路回调，所有闭包共享同一循环变量——9 路跟踪框全画到最后一路；改 IIFE 立即传参后逐路正确（修复前 9 框错位 → 修复后逐路跟随）。
  • 推送乱序：分布式上报乱序，必须按 ts 丢弃旧帧，否则跟踪框会"回跳"。
  • 闭包持有大对象：切走监控页后 tracks 未 clear，长运行内存缓慢上涨；路由离开统一 clearAll 释放。
  • sort 默认字典序：数字列必须传 (a,b)=>a-b，否则 10 排在 2 前面。
  • e.target 是子元素：事件委托后动态新行无需重绑，但 e.target 可能是行内图标，用 closest('tr') 找到真正行。
  • 原型共享引用：原型上的数组配置写成引用会多实例互染——默认值必须在构造函数里深拷贝。

5.7 量化成果

  • 9 路画面跟踪框稳定跟随、坐标偏差视觉可接受（估算）。
  • Grid/Tree/Dialog 三插件复用到多个大屏页面，新页面接入不再重写表格逻辑。

5.8 协作与排期过程

  • 契约先行：与算法侧先定坐标协议（归一化 0~1、原点定义），与后端定 deviceId/ts 字段后再开发，避免边写边对。
  • 联调协商：分布式上报乱序问题与后端协商出"前端按 ts 去重"的责任边界，双方不重复清洗。
  • 排期：叠加层与插件分两期——先跑通单路叠加，再扩多路并抽离通用插件。

5.9 复盘与可复用经验

  • 闭包管私有状态：注册表模式天然防外部篡改，比挂全局对象安全。
  • 时间戳去重是分布式前端必备：多源上报必乱序，前端要有兜底。
  • 离开即清理：闭包、定时器、监听器在路由卸载时统一释放。

5.10 面试讲法

实战要点在 jQuery 时代用闭包注册表 + 时间戳去重，扛住了约 9 路分布式视频目标的前端聚合，并用原型共享把表格插件做成可复用资产。

6易错点与面试重点

6.1 回调里 this 丢失

一句话定位：方法被单独传出去后脱离了调用前缀，this 退化为默认绑定。

  • 现象：把 obj.method 单独传给 setTimeout 或事件监听，运行时 this 变成 undefined/全局。
  • 原因：方法传出去后脱离了 obj. 调用前缀，触发"默认绑定"而非隐式绑定。
  • 正解：bind(obj)、箭头函数，或调用时保持 obj.method() 形式。

坑这是面试高频追问，也是 Vue2 里"methods 当回调传"的原型坑。

6.2 == 隐式转换的雷区

一句话定位：抽象相等规则绕，业务里别用 ==。

  • 现象：[] == ![] 为 true、null == undefined 为 true、'0' == 0 为 true。
  • 原因：抽象相等会先转数字/布尔再比较，规则绕。
  • 正解：业务代码一律 ===；唯一例外 x == null 同时判 null/undefined（ESLint 常放行）。

6.3 循环 + 闭包（var 时代经典 bug）

一句话定位：var 无块级作用域，循环里的回调共享同一个 i。

  • 现象：for(var i=0;i<3;i++){ setTimeout(()=>console.log(i),0); } 打印 3 个 3。
  • 原因：var 没有块级作用域，三个回调共享同一个 i，循环结束后 i=3。
  • 正解：改 let i（每次迭代新建绑定），或老环境用 IIFE 传参。

6.4 原型上的引用被共享

一句话定位：可变数组/对象写在原型或共享默认值上，多实例互相污染。

  • 现象：给一个实例改了 grid.rows，所有表格实例的 rows 都变了。
  • 原因：把可变数组/对象写在了原型上（或构造函数默认值共享引用）。
  • 正解：实例状态在构造函数里独立创建，如 this.rows = options.rows ? [...options.rows] : []。

6.5 类型判断：typeof null 与数组

一句话定位：typeof 分不清 null 与数组，用专用 API 判。

  • 现象：typeof null === 'object'（历史 bug，修不了）、typeof [] === 'object' 分不清数组。
  • 正解：判空用 x === null；判数组用 Array.isArray(x)；判普通对象用 Object.prototype.toString.call(x)。

6.6 浮点精度 0.1 + 0.2

一句话定位：IEEE 754 无法精确表示十进制小数，比较要用容差。

  • 现象：0.1 + 0.2 === 0.3 为 false，结果是 0.30000000000000004。
  • 原因：IEEE 754 双精度无法精确表示十进制小数。
  • 正解：比较用 Math.abs(a-b) < Number.EPSILON，或定点整数（分）算后再格式化；显示时 toFixed(2)。
