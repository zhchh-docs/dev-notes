1简介与阅读指引

1.1 定位

本篇讲 JS 的"运行模型"——类型、作用域、闭包、this、原型链、模块、垃圾回收。它是前端转全栈后学习 Node.js、读懂框架源码、排查内存问题的地基。

日常说的 "JS" 其实是三层叠加，先把它说清楚，后面所有概念才不会混：

  • ECMAScript（ES）：语言标准本身（语法、类型、原型、闭包），由 ECMA-262 定义、TC39 按年滚动发布（ES2015/ES2020…）。
  • DOM API：浏览器提供的"操作网页"接口（Document Object Model），如 document.querySelector。
  • BOM：与浏览器外壳打交道的接口（window/navigator/location 等）。

图 1 JavaScript 的三层组成（示意）

为什么要分清三层：Promise、Map、闭包是 ES 的，换到 Node 里照样能用；document、window 是宿主环境给的，Node 里没有。报错时先分清是语言问题还是宿主问题，找资料的方向完全不同。

1.2 痛点：为什么"JS 难"不在语法

多数后端语言是"静态类型 + 类继承 + 块级作用域"，而 JS 是"动态类型 + 原型委托 + 函数作用域历史包袱"。这门语言的"难"难在四套与后端直觉不同的执行模型：

  • 动态类型：错误推迟到运行期才暴露；
  • 词法作用域 + 闭包：函数能"记住"出生地；
  • this 动态绑定：同一个函数，this 指向随调用方式变化；
  • 原型委托：没有类继承，对象靠内部指针关联。

分水岭功底不在于"会不会写 for 循环"，而在于能否预测代码在运行期做了什么：this 指向谁、闭包捕获了哪个变量、原型链在哪一步命中、GC 会不会漏掉大对象。这些恰是"无框架兜底"代码里最容易埋雷的地方。

2核心概念

本章按认知顺序排列：先搞清"变量怎么存"（2.1~2.2），再理解"函数执行时的环境"（2.3~2.4），然后是这门语言最独特的三件事——闭包（2.5）、this（2.6）、原型链（2.7~2.8），最后是工程化的两块：模块（2.9）与垃圾回收（2.10）。每一节都依赖前一节，跳读前请确认前置小节已理解。

2.1 动态类型与隐式转换

变量无类型、值才有类型，错误全部推迟到运行期——工程上用显式转换与 === 把不确定性压死。

  • 动态类型：变量不绑定类型，今天存数字、明天存字符串都合法；类型检查发生在运行期，而非编译期。
  • 按值 vs 按引用：七种原始类型（number/string/boolean/null/undefined/symbol，ES2020 加 bigint）赋值拷贝值；object（含数组、函数）赋值只拷贝引用——两个变量指向同一个对象，一处修改处处可见。
  • 隐式转换：运算符两侧类型不一致时引擎自动转换——+ 遇字符串会拼接，== 按抽象相等规则辗转比较，是大量"看起来对其实错"的根因。

铁律比较一律用 ===（不转换、值与类型都比）；需要转换时显式写 Number(x) / String(x)，不依赖引擎的隐式行为。唯一惯例例外：x == null 同时判 null 和 undefined（ESLint 通常放行）。

理解了"错误推迟到运行期"，下一个问题自然是：运行期代码到底是怎么执行的？这就要引入执行上下文。

2.2 执行上下文与调用栈

每进入一段可执行代码，引擎就建一个"运行环境"；JS 单线程，靠栈决定此刻执行谁。

  • 执行上下文（Execution Context）：全局代码一个、每次函数调用各一个；里面存当前作用域的变量声明、this 绑定，以及对外层词法环境的引用。
  • 调用栈（Call Stack）：JS 单线程执行，同一时刻只跑一段代码。函数被调用时上下文压栈，返回时弹出；栈顶上下文决定当前执行的代码。栈有上限（V8 约 1 万余帧），递归没有出口就是 Stack Overflow。

一次函数调用的完整生命周期：全局上下文入栈 → 调用函数、新上下文压到栈顶 → 执行栈顶代码 → 函数 return、上下文出栈。记住"上下文出栈 ≠ 环境被回收"——这个伏笔在 2.5 闭包处揭晓。

2.3 作用域链与词法作用域

变量从哪来由"源码写在哪"决定，引擎靠沿作用域链向上查找来解析名字。

  • 作用域链（Scope Chain）：查变量时从当前作用域开始，沿上下文里保存的"外层词法环境引用"一路向上直到全局对象，命中即停；到全局还没命中就是 undefined（直接读取则 ReferenceError，见 5.3）。
  • 词法作用域（静态作用域）：变量可见性由函数在源码中的书写位置决定，与"谁调用它"无关。

为什么强调"书写位置决定"：它是下一节闭包成立的前提——正因为外层引用在定义时就固定了，函数被传到任何地方执行时，依然能访问定义处的变量。

2.4 闭包（Closure）【进阶】

函数把"出生时所在的词法环境"绑在自己身上，即使外层函数已返回，仍能访问那些变量。

  • 本质：内部函数在创建时把外层词法环境捕获到自身；外部函数返回后，上下文虽然出栈了，但这个环境因仍被函数引用而不被垃圾回收——2.2 节的伏笔在这里揭晓。
  • 典型用途：数据私有化（模块模式，见 3.6）、回调保持状态、函数柯里化、防抖节流——本质都是靠闭包留住"上次的状态"。
  • 代价：被闭包长期引用的大对象不会被回收；长驻页面里用闭包持有大数组，会造成"切屏后内存只涨不降"（排查见 7.3）。

2.5 this 的绑定规则【进阶】

this 与作用域相反——作用域看"定义在哪"，this 看"怎么被调用"。四条规则按优先级裁决。

优先级规则调用形式this 指向
1new 绑定new Foo()新创建的实例对象
2显式绑定foo.call/apply/bind(ctx)手动传入的 ctx
3隐式绑定obj.foo()调用点前面的对象 obj
4默认绑定（兜底）直接 foo()严格模式 undefined；非严格模式全局对象
  • 特例——箭头函数：不绑定自己的 this，捕获定义处的 this——回调里"this 丢了"的标准解法；但也意味着箭头函数不能当对象方法（拿不到调用者）。
  • 为什么设计成动态绑定：为了让同一个函数能被多个对象复用（方法共享），代价是"方法被单独传出去就丢 this"——JS 最高频的 bug 来源（见 7.2）。

坑把对象方法当回调传出去（setTimeout(obj.foo)）后，this 退化为全局/undefined；要么用箭头函数包一层，要么 .bind(obj)。

解决了"函数执行时 this 是谁"，还剩一个更大的问题：对象上的属性和方法从哪来？这就进入 JS 与多数后端语言差异最大的部分——原型。

2.6 原型与原型链（Prototype Chain）【进阶】

JS 没有经典继承，对象靠"内部指针委托"把属性查找沿原型链向上传递。

  • 委托而非复制：每个对象内部有隐藏指针 [[Prototype]]（经 __proto__ 访问）指向另一个对象；自身没有的属性沿链向上找，直到 null。
  • prototype vs __proto__（最易混）：prototype 是函数的属性，指向"实例的原型对象"；__proto__ 是实例指向其原型对象的链接。两者方向相反。
  • new 接线：new Foo() 出来的实例，其 __proto__ 指向构造函数的 prototype。

要点改了原型对象上的方法，所有"继承自它"的对象都会看到——这正是 class 只是语法糖、以及"为什么改数组原型全局生效"的底层原因。

2.7 class 与继承（ES6 Class）【进阶】

ES6 class 不是新的继承模型，而是原型继承的语法糖。

  • 三个关键件：constructor 对应原构造函数；extends 经 Object.setPrototypeOf 接好父子原型链；super() 调用父类构造函数（必须在 this 使用前调用）。
  • 细节：类方法默认不可枚举，static 成员挂在构造函数本身上；#privateField 是运行期真正的私有字段（比闭包私有的约束更硬）。

工程上 class 比手写 Child.prototype = new Parent()（会执行一遍父构造函数、还会共享引用）清晰安全得多；团队统一用 class。理解了"实例与方法的关系"，接着看代码怎么组织——模块。

2.8 模块化：ESM 与 CommonJS

模块解决全局污染与代码组织；ESM 静态、CommonJS 运行时，二者语义不同。

ESM（import/export）CommonJS（require/module.exports）
依赖分析编译期静态确定，支持 tree-shaking运行时动态加载
导出绑定活绑定：导出值变，导入方跟着变原始类型是值拷贝（首次 require 快照）；对象/数组仍是共享引用
执行次数模块只执行一次，单例缓存后同样单例

坑老 CommonJS 构建里"改了导出对象的字段页面没更新"，往往就是值拷贝/活绑定的差异所致；工程选型：新代码一律 ESM，老代码靠工具兼容（边界案例见 4.4）。

2.9 垃圾回收与内存管理【进阶】

V8 靠"可达性"决定回收，前端内存泄漏几乎都是"本该不可达却仍被引用"。

  • 可达性判定：从根（全局对象、当前调用栈变量）出发能到达的对象保留，不可达的回收——只看"能否到达"，不看你有没有"打算用"。
  • 回收算法：早期引用计数因循环引用被淘汰；现代引擎以标记-清除为主，辅以分代回收（新生代 Scavenge、老生代 Mark-Compact，取舍见 4.2）。
  • 防泄漏工具：WeakMap/WeakSet 的 key 是弱引用，不阻止 GC 回收——用它给 DOM/对象挂附加数据（weakMap.set(el, meta)），元素被销毁后条目自动消失，是避免"全局表长期持有大对象"的标准做法。

坑三类典型泄漏：未解绑的事件监听、忘记清理的定时器、被闭包或全局数组长期持有的大对象——"切屏后内存只涨不降"基本都能归到这三类（排查步骤见 7.3 与 8.5）。

3核心语法与 API（按使用场景分组）

本章不是 API 字典，按"你要做什么事"分六个场景。每组给推荐 / 不推荐写法对比，并解释推荐写法背后的原因。

3.1 场景一：声明变量（作用域控制）

const MAX = 100;          // 推荐：默认用 const——不可重新赋值，意图清晰
let count = 0;            // 需要重新赋值才用 let
// var count = 0;         // 函数作用域 + 提升 + 挂全局，新项目不再用

console.log(a);           // let/const 在声明前访问 = ReferenceError（暂时性死区 TDZ）
let a = 1;

为什么不推荐 var：var 是函数作用域，存在提升（声明被提到作用域顶部、值为 undefined），且循环里用 var 会让所有迭代共享同一个变量（经典闭包陷阱，见 7.2 坑 3）。let/const 是块级作用域，同时消灭这两个问题。TDZ 的意义：让"先使用后声明"直接报错，而不是悄悄变成 undefined 让 bug 晚点爆。

3.2 场景二：修正 this（回调传函数前必查）

const grid = {
  name: '告警表',
  render() { console.log(this.name); }
};
grid.render();                 // ✅ 隐式绑定：this = grid，输出"告警表"

const fn = grid.render;
fn();                          // ❌ this 丢失：严格模式下 undefined，报错！

const bound = grid.render.bind(grid);   // ✅ 显式 bind：永久锁定 this = grid
setTimeout(bound, 100);

const obj = {
  name: 'x',
  tick() { setTimeout(() => console.log(this.name), 100); }  // ✅ 箭头函数：捕获定义处 this
};

选择顺序：箭头函数（回调场景）> bind（需要独立函数引用时）> 保持 obj.method() 调用形式。原理对应 2.5 的四条规则。

3.3 场景三：类型判断（typeof 的三个盲区）

// ❌ 不推荐
typeof null            // 'object'（历史 bug，改不了）
typeof []              // 'object'（分不清数组和普通对象）

// ✅ 推荐
x === null                                     // 判空：严格相等
Array.isArray(x)                               // 判数组
Object.prototype.toString.call(x)              // 判任意精确类型，'[object Date]' 等
typeof x === 'function'                        // 判函数（typeof 唯一可靠的场景）

记忆点：typeof 只对函数可靠，其余场景用专用 API——因为 null 和数组都会被误判为 'object'。

3.4 场景四：数据转换与浮点比较

// ❌ 依赖隐式转换
if (str == 5) {}                    // 抽象相等规则绕，结果难预测
'10' + 1                            // '101'（拼接），'10' - 1 却是 9（转数字）

// ✅ 显式转换 + 严格相等
if (Number(str) === 5) {}

// ✅ 浮点比较用容差（IEEE 754 无法精确表示十进制小数）
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON
Math.round(price * 100) / 100       // 金额用定点整数（分）计算后再格式化

0.1 + 0.2 === 0.3 为 false（结果是 0.30000000000000004），这是 IEEE 754 双精度的语言级限制，永远修不了，只能规范绕开。

3.5 场景五：集合操作（高阶 API）

const rows = [{ level: 1 }, { level: 2 }, { level: 1 }];
// map / filter / reduce / find：纯函数风格，避免手写 for
const alarms = rows.filter(r => r.level === 1).map(r => ({ ...r, status: 'alarm' }));
const total = rows.reduce((sum, r) => sum + r.level, 0);

// ⚠️ sort 两个坑：默认字典序 + 改原数组
rows.sort()                                  // ❌ 默认字典序：10 排在 2 前面
rows.sort((a, b) => a.level - b.level)       // ✅ 数字必须传比较函数
const sorted = [...rows].sort((a, b) => a.level - b.level);  // ✅ 不改原数据

原则：filter/map 返回新数组不污染原数据；需要改原数组时用 forEach 或直接索引，并让"改了谁"在代码里一眼可见。

3.6 场景六：私有状态与原型操作

// ✅ 闭包实现模块私有变量：外部无法直接触碰 _counter
function createCounter(init = 0) {
  let _counter = init;                 // 被返回函数闭包引用，不随函数返回销毁
  return {
    inc() { return ++_counter; },
    get() { return _counter; }
  };
}

c.inc(); c.inc();
console.log(c.get());    // 12；外部访问不到 _counter
// 原型继承：老式 vs class（工程统一用 class）
function Parent(name) { this.name = name; }
Parent.prototype.say = function () { return this.name; };   // 方法挂原型，实例共享

class Parent2 {

4进阶知识点进阶

首次学习可整章跳过。本章讲引擎底层与设计取舍，用于面试深水区和疑难排查。前置：已理解第 2 章。

4.1 手写 call / apply / bind（原理：借用调用形式改 this）

Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx || globalThis;
  const key = Symbol();
  ctx[key] = this;              // 把当前函数临时挂到 ctx 上
  const res = ctx[key](...args); // 以 ctx 为 this 调用——调用形式变成 ctx.fn()，触发隐式绑定
  delete ctx[key];
  return res;
};
// apply 与 call 只差在参数：apply 收数组，call 收展开参数
// bind：返回一个永久绑定 this 的新函数（内部闭包保存 ctx，即 3.2 的 bound 的底层逻辑）

设计取舍：this 的动态绑定看似是缺陷，实际是"方法复用"的机制——手写 call 的过程会让你彻底理解：所谓绑定 this，本质是控制"函数调用时的形式"。

4.2 分代回收的取舍逻辑

新生代（存活时间短的对象多）用 Scavenge：空间换时间，复制存活对象到另一半空间，快但费内存；老生代用 Mark-Compact：三色标记 + 清除 + 整理碎片，慢但省内存。取舍依据是"弱分代假说"——大多数对象朝生夕死。理解这个，才能理解为什么"长驻的大数组"特别伤：它熬过晋升进了老生代，回收成本高且触发 Full GC 卡顿。

4.3 原型污染与防御

Object.prototype 是几乎所有对象的链尾，往它上面塞属性会全局可见。攻击面：JSON 解析含 "__proto__": {...} 的输入可篡改原型。防御三招：解析后 delete obj.__proto__；用 Object.create(null) 建无原型字典；深度合并时过滤 __proto__ / constructor / prototype 三个键名。

4.4 CommonJS 值拷贝的边界场景

// counter.js
let count = 0;
setTimeout(() => { count = 42; }, 100);
module.exports = { count };        // 导出的是快照：{ count: 0 }

// main.js
const { count } = require('./counter.js');
setTimeout(() => console.log(count), 200);   // 0！不是 42

如果导出 getter，或导出对象再改属性（exports.obj.count = 42），导入方才能看到变化。ESM 的活绑定没有这个问题——这是"新代码一律 ESM"的技术理由之一（呼应 2.8）。

5架构与流程图

三张图对应三条"查找链"：作用域链（找变量）、原型链（找属性）、GC 可达性（找活对象）。每张图都标注了 miss 时的行为——三条链的 miss 行为各不相同，这是面试辨析的高频点。

5.1 调用栈与执行上下文生命周期

图 3 调用栈与执行上下文生命周期（示意）

  1. 全局上下文入栈：页面脚本启动，先创建全局上下文并压栈。
  2. 函数调用压栈：每调用一个函数，创建其执行上下文（含变量环境、this、外层作用域链引用）压到栈顶。
  3. 栈顶即当前：JS 永远只执行栈顶上下文的代码；变量查找沿作用域链、this 按当前调用规则确定。
  4. 返回出栈：函数返回，上下文弹出。若其内部函数已被外部引用（闭包），词法环境不被回收——这就是闭包的内存本质。

5.2 作用域链查找：miss 时会发生什么

沿 2.3 的链查找变量，两种结局：

  • 命中：返回值，查找停止；
  • 到全局仍未命中：分两种行为——typeof x 安全地得到 'undefined'；直接读取 x 抛 ReferenceError。

这就是"用 typeof x !== 'undefined' 探测全局变量"写法的由来。注意查找沿静态作用域链进行，与调用方无关。

5.3 原型链查找：委托与陷阱

图 4 原型链委托查找（示意）

与作用域链不同，原型链 miss 不报错、安静地返回 undefined——这也是很多"以为有值其实是 undefined"bug 的来源。为什么这样设计：JS 用"对象关联对象"而非"类拷贝实例"，所有实例共享同一份方法（方法挂在 prototype 上），省内存。代价是理解成本：for...in 会把原型上可枚举的属性也遍历出来，必须用 hasOwnProperty 过滤；随意给原型塞方法会造成原型污染（防御见 4.3）。

5.4 GC 可达性：三条链之外的第四条判定

  • 判定规则：从根（全局对象、当前调用栈变量）出发沿引用图遍历，能到达的保留，不可达的回收；循环引用不影响回收（引用计数法才会死在这，这也是它被淘汰的原因）。
  • 与前三条链的关系：作用域链/原型链决定"能不能找到值"，可达性决定"值还活着吗"。闭包之所以让变量活着，正是因为函数对象维持了一条从根可达的引用链。

7常见坑 & Debug

每条坑统一五要素：现象 → 根因 → 复现 → 修复 → 规避，按开发阶段分组。规避方案尽量给可直接抄走的代码示范，而不是一句口号。最后附通用排查思路（7.5）。

7.1 初始化阶段

坑 1：脚本位置错误导致 DOM 取不到

  • 现象：document.querySelector('#app') 返回 null，接着读写它的属性报 Cannot read properties of null。报错点不在取元素那行，而在下一行使用它时——报错位置有迷惑性。
  • 根因：HTML 按顺序解析，<script> 同步执行；脚本在 <head> 里时，<body> 还没解析，DOM 树为空。
  • 修复：加 defer（延迟到解析完且按顺序执行）或把脚本放到 </body> 前。
  • 规避：初始化逻辑统一包进 DOMContentLoaded 回调，从根源上与脚本位置解耦。

复现（错误写法）与修复：

<!-- ❌ 复现：head 里同步执行，#app 还不存在 -->
<head>
  <script>
    const app = document.querySelector('#app');   // null
    app.textContent = 'hi';                       // TypeError!
  </script>
</head>

<!-- ✅ 修复一：defer，解析完再按顺序执行 -->
<script defer src="./init.js"></script>

<!-- ✅ 修复二：显式等待 -->
<script>
  document.addEventListener('DOMContentLoaded', () => {
    document.querySelector('#app').textContent = 'hi';
  });
</script>

两个修复的差异要能说清：defer 解决"加载与执行的时机"，多个 defer 脚本保持顺序，适合入口脚本；DOMContentLoaded 解决"逻辑与时机解耦"，脚本放哪里都不会坏。注意 async 不保证顺序，入口脚本别用。

7.2 编码阶段

坑 2：方法当回调传出去，this 丢失（最高频）

  • 现象：setTimeout(obj.method, 100) 运行时 this 变 undefined/全局，读 this.name 报错或读到脏数据。
  • 根因：方法脱离 obj. 调用前缀，从隐式绑定降级为默认绑定（2.5 规则 4）。this 由调用形式决定，与定义位置无关。
  • 修复：三种写法，按场景选。
  • 规避：评审约定——函数引用作为回调传递前，先问一句 this 从哪来。
const grid = {
  name: '告警表',
  render() { console.log(this.name); }
};

// ❌ 复现：方法脱离调用前缀
const fn = grid.render;
fn();                                  // this = undefined（严格模式），报错
setTimeout(grid.render, 100);          // 同样丢失

// ✅ 修复一：bind 永久绑定（生成新函数，原方法不受影响）
const bound = grid.render.bind(grid);
setTimeout(bound, 100);

// ✅ 修复二：箭头函数包一层（保留调用点写法）
setTimeout(() => grid.render(), 100);

规避示范——用类字段箭头函数从定义处焊死 this，实例方法怎么传都不丢：

class Grid {
  name = '告警表';
  // 类字段箭头函数：this 在定义时绑定实例，传出去也不丢
  render = () => { console.log(this.name); };
}
const g = new Grid();
setTimeout(g.render, 100);           // ✅ 稳定输出"告警表"

坑 3：var 循环闭包，所有回调共享同一个变量

  • 现象：for(var i=0;i<3;i++){ setTimeout(()=>console.log(i),0); } 打印 3 个 3，期望 0 1 2。
  • 根因：var 无块级作用域，整个循环只有一个 i；三个回调闭包引用同一个变量，同步循环跑完 i=3，异步回调才执行。
  • 修复：改 let i（每次迭代新建绑定）；老环境用 IIFE 传参。
  • 规避：ESLint no-var 规则从源头禁掉。
// ❌ 复现：三个闭包共享同一个 i
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 3 3 3
}

// ✅ 修复一：let——每次迭代新建绑定
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 0 1 2
}

// ✅ 修复二：IIFE 传参（老环境兜底）——用函数参数复制值
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j)); // 0 1 2
  })(i);
}
// 规避：.eslintrc 从源头禁 var
{ "rules": { "no-var": "error", "prefer-const": "error" } }

坑 4：== 隐式转换的雷区

  • 现象：[] == ![] 为 true、null == undefined 为 true、'0' == 0 为 true——反直觉三连。
  • 根因：抽象相等先做类型转换（对象转原始值、布尔转数字）再比较，规则链长难记。完整推演见 8.1 Q2。
  • 复现：控制台直接输即可。
  • 修复：业务代码一律 ===；唯一惯例例外 x == null 同时判 null/undefined。
  • 规避：ESLint eqeqeq，把"用没用对"变成 CI 问题而不是线上 bug。
// 复现三连（都能在控制台直接验证）
[] == ![]          // true ：![] 先得 false→0；[] 转原始值 ''→0
null == undefined  // true ：规范特例，两者互等
'0' == 0           // true ：字符串转数字

// ✅ 规避：唯一推荐保留 == 的场景——同时判两种空值
if (value == null) { }        // 等价于 value === null || value === undefined

坑 5：sort 默认字典序 + 原地修改

  • 现象：[10, 2, 1].sort() 得 [1, 10, 2]；且排序后原数组被改了，依赖原顺序的逻辑跟着错。
  • 根因：sort 无参时把元素转字符串按字典序比较；同时 sort 是原地算法。
  • 修复：数字必须传比较函数 (a,b) => a-b。
  • 规避：团队封装统一的"不可变排序"工具，从工具层禁掉裸 sort。
// ❌ 复现
[10, 2, 1].sort();                       // [1, 10, 2]——字符串序

// ✅ 修复：比较函数
[10, 2, 1].sort((a, b) => a - b);        // [1, 2, 10]

// ✅ 规避示范：封装不可变排序工具，所有业务代码只用这个
function sortBy(arr, keyFn, desc = false) {
  return [...arr].sort((a, b) => {
    const ka = keyFn(a), kb = keyFn(b);
    const cmp = ka < kb ? -1 : ka > kb ? 1 : 0;   // 数字/字符串通吃
    return desc ? -cmp : cmp;
  });
}
const sorted = sortBy(rows, r => r.level);      // 原数组 rows 保持不动

坑 6：原型/共享引用互染

  • 现象：给一个实例改了 grid.rows，所有表格实例的 rows 都变了——"一个表格操作，全页表格出错"。
  • 根因：可变数组/对象写在原型上（或构造函数默认值传引用）——原型属性被所有实例共享，这是原型机制的正常行为（2.6），错在用法。
  • 修复：实例可变状态在构造函数里独立创建并拷贝。
  • 规避：规范——原型上只放方法与常量；默认配置对象用 Object.freeze 冻结防误改。
// ❌ 复现：原型上的数组被所有实例共享
function Grid() {}
Grid.prototype.rows = [];
const a = new Grid(), b = new Grid();
a.rows.push(1);
console.log(b.rows.length);              // 1！b 也"多了一行"

// ✅ 修复：实例状态在构造函数里独立创建
function Grid2(rows = []) { this.rows = [...rows]; }   // 拷贝入参
Grid2.prototype.render = function () {};                // 原型只放方法

// ✅ 规避示范：默认配置冻结 + 构造函数合并
const DEFAULTS = Object.freeze({ pageSize: 20, sortable: true });
function Table(options = {}) {
  this.options = { ...DEFAULTS, ...options };   // 每个实例一份独立配置
}

坑 7：闭包/监听器/定时器泄漏——切屏后内存只涨不降

  • 现象：SPA 切走页面后内存不回落；长时间运行越来越卡、GC 停顿越来越明显。
  • 根因：本该不可达的对象仍被引用。三类典型：未解绑的事件监听（回调闭包持有 DOM）、未清理的定时器、闭包/全局数组持有大对象（2.9 可达性）。
  • 修复：卸载钩子里统一清理；成对出现（setup/teardown）。
  • 规避：用 AbortController 统一注销监听——一次 abort 解绑全部；附加数据用 WeakMap。
// ❌ 复现：注册了三次，永远不注销
window.addEventListener('resize', onResize);
window.addEventListener('resize', onResize2);
window.addEventListener('resize', onResize3);
// 页面销毁后，三个回调 + 各自闭包持有的大对象全部滞留

// ✅ 修复：成对注册/注销（手动管理）
const onResize = () => { /* ... */ };
window.addEventListener('resize', onResize);
window.removeEventListener('resize', onResize);   // 卸载时

// ✅ 规避示范：AbortController——一个信号解绑全部监听
const controller = new AbortController();
window.addEventListener('resize', onResize,   { signal: controller.signal });
window.addEventListener('scroll',  onScroll,  { signal: controller.signal });
document.addEventListener('click', onClick,   { signal: controller.signal });
// 路由/组件卸载时一行解绑全部：
controller.abort();

// ✅ 规避示范：WeakMap 挂附加数据，元素销毁条目自动消失（2.9）
const meta = new WeakMap();
meta.set(domNode, { bigBuffer });
// domNode 从文档移除且无其他引用后，meta 里的条目可被 GC，无需手动 delete

坑 8：分布式推送乱序，状态"回跳"

  • 现象：多来源上报同一条状态，后到的反而是旧的，界面来回跳；日志里 ts 乱序清晰可见。
  • 根因：网络路径不同，到达顺序 ≠ 发生顺序——多源写入同一状态时必须有兜底。
  • 修复：消息带时间戳/版本号，旧帧直接丢弃（幂等）。
  • 规避：封装"只接受最新"的写入器，任何多源写状态的地方复用。
// ❌ 复现：无脑覆盖，旧数据把新状态顶掉
function onPush(msg) { state[msg.id] = msg; }

// ✅ 修复：时间戳判定，旧帧丢弃
function onPush(msg) {
  const old = state[msg.id];
  if (old && old.ts > msg.ts) return;    // 乱序旧帧，直接丢
  state[msg.id] = msg;
}

// ✅ 规避示范：封装"latest-wins"写入器（可复用，工程案例见 8.4）
function createLatestStore(apply) {
  const store = {};
  return {
    push(id, payload, ts) {
      const old = store[id];
      if (old && old.ts >= ts) return false;   // 旧帧幂等丢弃
      store[id] = { payload, ts };
      apply(id, payload);
      return true;
    }
  };
}

8.1 基础概念题（附详细解读）

Q1：var / let / const 三者区别？

参考答案：从三个维度展开。

① 作用域：var 是函数作用域——在函数内任何位置声明，整个函数都可见；let/const 是块级作用域——只在 {} 内可见。最典型的差异在循环里：for(var i...) 的 i 在循环外也能访问，for(let i...) 的 i 每次迭代都是一个新的绑定。

② 提升（Hoisting）的行为差异：引擎处理声明的完整过程是"创建 → 初始化 → 赋值"三步。var 的声明在进入函数时就创建并初始化为 undefined，所以声明前访问得到 undefined（不报错但埋雷）；let/const 同样会提前"创建"绑定，但不初始化——从作用域开始到声明语句之间的区域就是暂时性死区（TDZ），访问直接抛 ReferenceError。TDZ 不是缺陷而是设计：让"先用后声明"尽早暴露。

③ 重新赋值与全局挂载：const 声明后不可重新绑定（注意：const obj = {} 之后 obj.x = 1 合法——const 锁的是绑定不是内容）；var 会把变量挂到全局对象 window 上，let/const 不会；var 还允许重复声明（后者覆盖前者），let/const 重复声明直接报错。

加分点：主动说出"循环 + setTimeout"的经典场景——var 版打印 3 3 3（见 7.2 坑 3），let 版打印 0 1 2，并解释原因在"每次迭代新建绑定"。

Q2：== 与 === 区别？举一个 == 的坑并完整推演。

参考答案：=== 严格相等——类型不同直接返回 false，不做任何转换；== 抽象相等——类型不同时按规范先做转换再比较，规则复杂难记。

完整推演 [] == ![] 为什么是 true（面试加分题）： ① 右边 ![] 优先求值：数组是 truthy，取反得 false； ② 比较式变成 [] == false，布尔值参与比较先转数字：false → 0； ③ 左边空数组转原始值：String([]) → ''，再转数字 Number('') → 0； ④ 于是 0 == 0，结果 true。

类似的：null == undefined 为 true（规范特例：两者相等且都与自身相等，但不与其他任何值相等）；'0' == 0 为 true（字符串转数字）。

工程结论：业务代码一律 ===，唯一惯例例外 x == null 同时判两种空值；用 ESLint eqeqeq 规则强约束。

Q3：typeof 能判断哪些类型？盲区是什么？为什么有盲区？

参考答案：typeof 的结果由值的底层类型标签决定，不是 JS 层面的类型系统。可靠区分：string / number / boolean / undefined / symbol / bigint / function（函数有内部槽位 [[Call]]，typeof 唯一能认出 function 的场景）。

盲区一：typeof null === 'object'——第一版实现里值的类型标签用低位比特表示，对象标签是 000，而 null 是全零指针，实现时顺手返回了 'object'。这个 bug 已被 TC39 讨论过但为了兼容性永远不修。
盲区二：typeof [] === 'object'——typeof 分不清对象的具体分类。

补救方案及原理：判空用 x === null；判数组用 Array.isArray（跨 iframe 也可靠）；精确类型用 Object.prototype.toString.call(x)——它读取对象内部的 [[Class]]/slot 标记，返回 '[object Date]' 这类字符串，比 typeof 精确一个层级。

Q4：ES6 class 是什么？和手写原型继承有什么差异？

参考答案：class 是原型继承的语法糖，不是新的继承模型——运行时依然走 [[Prototype]] 委托（2.6）。对应关系：constructor 就是原来的构造函数体；extends 内部调 Object.setPrototypeOf 接好两条链（子类实例 → 子类.prototype → 父类.prototype，以及子类构造函数 → 父类构造函数——后者保证静态方法也能继承）；super() 调父类构造函数，且必须先于 this 使用。

与手写原型的五个差异（答出来就是加分项）： ① 类方法默认不可枚举（手挂 prototype 的方法是可枚举的，for...in 行为不同）； ② 类体默认严格模式； ③ class 必须用 new 调用，直接调用报 TypeError（内部标记 [[IsClassConstructor]]）； ④ class 声明有 TDZ，声明前访问报错； ⑤ #privateField 是运行期真正的私有——比闭包私有更硬，实例外部完全无法访问。

工程结论：手写 Child.prototype = new Parent() 有两个坑（执行一遍父构造、引用共享，见 7.3 坑 6），团队统一用 class。

Q5：ESM 与 CommonJS 的核心差异？为什么说"静态"是关键？

参考答案：

① 依赖分析时机：ESM 的 import/export 必须写在顶层、不能包在条件语句里，所以打包器在编译期就能画出完整依赖图——没被引用的导出可以在打包时删除（tree-shaking）；CommonJS 的 require 可以写在 if 里、路径可以是变量，只能在运行时逐个解析，无法静态优化。

② 导出绑定：ESM 导出的是绑定（名字到内存位置的引用）而不是值的快照——导出方修改后导入方读到的跟着变（活绑定），这是为什么 ESM 可以实现"配置中心热更新"式模块；CommonJS 导出原始类型是值拷贝（首次 require 时的快照，边界案例见 4.4），只有对象是共享引用。

③ 单例与循环引用：两者模块都只执行一次。但循环引用时 ESM 靠"活绑定 + 提升的函数声明"能正常工作；CommonJS 拿到的是"执行到一半的 exports"（半成品对象），容易踩 undefined。

工程结论：新代码一律 ESM；这也是 Vite/现代打包器能做按需加载和摇树优化的前提。

8.2 原理连环追问（每一步都可能被追问，答案都往原理层答）

追问链 1：闭包 → 内存 → 排查

  • 问：什么是闭包？ 答：函数与它创建时所处词法环境的引用的组合。最小例子：function outer(){ let x = 1; return () => x; }——返回的函数捕获了 x 所在的环境，调用它仍能读到 1。
  • 问：闭包的变量存在哪？ 答：存在被捕获的词法环境对象里。JS 引擎把环境对象分配在堆上——所以外层函数的栈帧弹出后，环境依然存在（这也是"出栈 ≠ 回收"的原因，2.2 的伏笔）。
  • 问：外层函数返回后为什么没被回收？ 答：GC 按可达性判定：内部函数仍被外部引用 → 函数对象可达 → 它引用的词法环境可达 → 整条链从根出发都可达，标记-清除不会回收。循环引用也不影响（引用计数法才会死在这）。
  • 问：闭包会导致内存泄漏吗？ 答：闭包本身不泄漏，长期持有不再需要的大对象才泄漏。三类典型：未解绑的事件监听（回调闭包持有 DOM）、未清理的定时器、闭包/全局数组持有大对象。修复模式："谁注册谁注销" + WeakMap 挂附加数据。
  • 问：线上怎么排查？ 答：Performance Monitor 先看 JS Heap Size 曲线是否阶梯式上涨确认泄漏 → Memory 面板操作前后各拍一次堆快照 → Summary 视图按 Retained Size 排序找增长对象 → 展开 Retainers 链找到"谁攥着它"（通常是某个未解绑的 listener 或全局集合）→ 修复后复拍验证。详细步骤见 8.5。

追问链 2：this → 箭头函数 → 设计动机

  • 问：this 怎么确定？ 答：看调用形式，四条规则按优先级裁决（2.5 表格）：new > 显式 > 隐式 > 默认。举例：grid.render() 隐式绑定 this=grid；把方法赋值给变量再调用，前缀丢失走默认绑定。
  • 问：箭头函数的 this？ 答：箭头函数没有自己的 this 绑定，它的 this 是沿词法作用域向外找到的——即定义处的 this。因此 call/apply/bind 传什么都没用，第一个参数被忽略。
  • 问：为什么箭头函数不能做对象方法？ 答：const obj = { say: () => console.log(this.name) }——箭头函数定义在对象字面量里，而对象字面量不创建作用域，所以它捕获的是外层（全局/模块）的 this，obj.say() 永远拿不到 obj。要拿调用者必须用普通方法（隐式绑定）。
  • 问：为什么 JS 把 this 设计成动态的？这不是坑吗？ 答：动态绑定让一个函数可以被多个对象复用——方法挂在 prototype 上，谁调用 this 就指向谁，这是"共享方法省内存"设计的配套机制。代价是"方法脱离对象传递就丢 this"，于是才有了 bind/箭头函数这些补丁。答出"这是共享机制的代价与补丁"，比背规则高一档。

追问链 3：new 的过程

  • 问：new Foo() 做了什么？ 答：四步——①创建空对象；②接原型：obj.__proto__ = Foo.prototype（这一步让 instanceof 与方法共享成立）；③以 this 执行构造函数（给实例挂字段）；④决定返回值：构造函数若显式 return 一个对象，则用它（this 被丢弃），否则返回新实例。
  • 追问：为什么 class 不能不写 new 就调用？ 答：类构造函数带内部标记 [[IsClassConstructor]]，引擎直接抛 TypeError——防止把初始化逻辑当普通函数误用，而普通构造函数非严格模式下会静默挂到全局（更隐蔽的 bug）。
  • 追问：用代码表达 new 的四步？ 答：function myNew(F, ...args){ const o = Object.create(F.prototype); const r = F.apply(o, args); return (r !== null && typeof r === 'object') ? r : o; }——一行 Object.create 同时完成建对象和接原型。

8.3 手写代码题（附参考实现与解题要点）

题 1：手写 call / apply / bind——核心思路一句话：把函数临时挂到目标对象上再调用，让"调用形式"触发隐式绑定。参考实现见 4.1。bind 的两个加分细节：①返回的函数若被 new 调用，this 应指向新实例（内部用 this instanceof F 分流）；②支持参数预置（偏函数）。

题 2：手写防抖 debounce（高频，必须默写）

function debounce(fn, wait) {
  let timer = null;                       // 闭包保存定时器 id——闭包让"上次的状态"活着
  return function (...args) {
    clearTimeout(timer);                  // 每次触发先取消上一次
    timer = setTimeout(() => fn.apply(this, args), wait);
    // 箭头函数捕获返回函数的 this——保证事件回调里 this 不丢
  };
}

解题要点：①用闭包保存 timer（对应 3.6 私有状态）；②用箭头函数保 this（对应 2.5）；③常见追问：节流 throttle 怎么写（时间戳版 + 定时器版）、immediate 首次立即执行怎么加。

题 3：手写 instanceof

function myInstanceof(obj, Ctor) {
  if (typeof Ctor !== 'function') return false;   // 右侧必须是构造函数
  let p = Object.getPrototypeOf(obj);             // 等价于 obj.__proto__
  while (p) {
    if (p === Ctor.prototype) return true;        // 原型链上找到即命中
    p = Object.getPrototypeOf(p);                 // 沿链上移，直到 null
  }
  return false;
}

解题要点：instanceof 的语义就是"构造函数的 prototype 是否出现在对象的原型链上"——这句话本身就是标准答案的前半句。

题 4：手写深拷贝（处理循环引用）

function deepClone(obj, map = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj;  // 原始值直接返回
  if (map.has(obj)) return map.get(obj);   // 循环引用：命中缓存直接返回，避免无限递归
  const out = Array.isArray(obj) ? [] : {};
  map.set(obj, out);                       // WeakMap 缓存已拷贝对象（弱引用不阻 GC，2.9）
  for (const k of Reflect.ownKeys(obj)) out[k] = deepClone(obj[k], map);
  return out;
}

解题要点：①递归终止条件（原始值）；②map.has 一行是本题的灵魂——没有它，obj.self = obj 直接栈溢出；③常见追问：Date/RegExp 怎么处理（按类型分支或用结构化克隆 structuredClone）、为什么用 WeakMap 不用 Map。

8.4 工程场景设计题（附答题骨架与参考实现）

题目：多路视频监控大屏，约 9 路摄像头目标框由分布式算法节点推送（WebSocket + 轮询双通道），前端如何聚合渲染？

答题骨架（每一点都能对应本篇的一个概念，这是本题的"重心"）：

  1. 私有状态：每路一个闭包注册表 createTrackStore()，外部只能经 update/clear 操作，防多轮推送互相污染（2.4）；
  2. 乱序兜底：消息带 ts，旧帧丢弃（7.3 坑 8）；
  3. 坐标协议：与算法侧约定归一化 0~1 坐标、原点定义，叠加层百分比定位——契约先行，避免边写边对；
  4. 可复用性：表格插件方法挂 prototype 共享给所有实例，但可变状态在构造函数独立创建（7.3 坑 6）；
  5. 生命周期：路由离开统一 clearAll，闭包/定时器/监听器不跨页存活（7.3 坑 7）；
  6. 协作边界：分布式乱序与后端协商"前端按 ts 去重"的责任边界，双方不重复清洗。
// 跟踪注册表：闭包封装私有 tracks，防止外部直接篡改
function createTrackStore() {
  const tracks = {};                 // 私有：{ [deviceId]: { box, ts } }
  return {
    update(deviceId, box, ts) {
      const old = tracks[deviceId];
      if (old && old.ts > ts) return;   // 分布式乱序：旧数据丢弃
      tracks[deviceId] = { box, ts };
      renderOverlay(deviceId, box);
    },
    clear(deviceId) { delete tracks[deviceId]; hideOverlay(deviceId); },
    snapshot() { return Object.keys(tracks).map(id => ({ id, ...tracks[id] })); }
  };
}

8.5 故障排查题（附完整排查步骤）

题目：SPA 长时间运行越来越卡，怀疑内存泄漏，怎么查？

参考答案（六步法，每步说明"做什么、看什么"）：

第 1 步 确认泄漏存在：DevTools → Performance 面板（或 Performance Monitor）录制 30 秒操作，观察 JS Heap Size 曲线——正常是锯齿状（上升后 GC 回落），泄漏是阶梯式上升不回落。同时看 DOM Node Count 是否只增不减（另一种泄漏）。

第 2 步 建立假设：按三类来源定位嫌疑——未解绑的事件监听、未清理的定时器、被闭包/全局集合持有的大对象（7.3 坑 7）。回顾代码里所有 addEventListener / setInterval / 全局缓存。

第 3 步 堆快照 diff：Memory 面板 → 操作前拍 Snapshot A → 执行一遍可疑操作（如进出页面 3 次）→ 拍 Snapshot B → 选 Comparison 视图对比，按 "#Delta" 或 Retained Size 排序，找增量最大的对象。

第 4 步 找到引用者：选中可疑对象，展开 Retainers 链从下往上看——谁攥着它？常见链路：listener → closure → 大数组，或 window → 全局 Map → DOM 元素。

第 5 步 修复：卸载钩子里统一清理（removeEventListener / clearInterval / 置 null）；附加数据改用 WeakMap（元素销毁条目自动消失）。

第 6 步 验证与制度化：复拍快照确认回收；把"谁注册谁注销"写进评审清单。

加分点：快照看不出时可改用 Allocation instrumentation on timeline（按分配点定位泄漏源）；长连接场景记得排查 WebSocket 回调闭包。

8.6 自测 5 问（先自测，再展开答案）

  1. 函数出栈后，闭包变量为什么还活着？存在哪？
    参考答案存在被捕获的词法环境对象中——JS 引擎把环境对象分配在堆上而不是栈帧里。函数返回后上下文出栈，但该环境仍被内部函数引用，从 GC 根出发可达，标记-清除不会回收它。这也解释了"出栈 ≠ 回收"：栈管执行位置，堆管数据存活（2.2、2.4、2.9 三节联动）。
  2. for(var i) 与 for(let i) 里的 setTimeout 分别打印什么？为什么？
    参考答案var 打印 3 3 3——var 没有块级作用域，整个循环只有一个 i，三个回调闭包引用的是同一个变量，同步循环跑完后 i=3，异步回调才执行，读到 3。let 打印 0 1 2——let 在每次迭代创建一个新的绑定，每个回调捕获的是各自那次迭代的 i。老环境修复用 IIFE 传参 (function(i){...})(i)——用函数参数复制一份值（7.2 坑 3）。
  3. obj.method 赋值给变量再调用，this 是什么？三种修法？
    参考答案this 是 undefined（严格模式）或全局对象——方法脱离了 obj. 调用前缀，从隐式绑定降级为默认绑定（2.5 规则 4）。三种修法：①obj.method.bind(obj)——显式绑定，生成永久锁定的新函数；②箭头函数包一层 () => obj.method()——捕获定义处 this；③保持调用形式，如 setTimeout(() => obj.method(), 100)（7.2 坑 2）。
  4. prototype 和 __proto__ 的区别？new 做了哪四步？
    参考答案prototype 是函数才有的属性，指向"用这个函数 new 出来的实例的原型对象"，是构造者视角；__proto__ 是每个对象都有的内部链接（[[Prototype]] 的 getter/setter），指向自己的原型，是实例视角——两者方向相反。new 四步：①建空对象；②接原型 obj.__proto__ = Foo.prototype；③以 this 执行构造函数；④构造函数返回对象则用之，否则返回新实例（8.2 追问链 3，含手写 myNew）。
  5. ESM 导出的数字被导出方修改后，导入方能读到新值吗？CommonJS 呢？
    参考答案ESM 能——导出的是绑定（名字到内存位置的引用）而非值快照，导入方每次读取都走当前值（活绑定）。CommonJS 不能——原始类型在首次 require 时按值拷贝进 exports，之后导出方修改与导入方无关；只有导出对象时才能通过修改属性同步（4.4 有完整边界案例）。这也是"新代码一律 ESM"的技术理由。
