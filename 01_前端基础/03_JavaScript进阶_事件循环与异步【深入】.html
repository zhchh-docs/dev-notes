JavaScript 进阶：事件循环与异步

深入 定位：单线程语言如何不被阻塞——事件循环、宏微任务、Promise/async-await 的执行时序

浏览器 JS 是单线程的，却能同时处理网络请求、定时器、UI 事件、音视频回调而不卡死页面，靠的就是事件循环（Event Loop）这套调度模型。本页讲透宏任务/微任务的优先级、Promise 状态机、async/await 的底层时序，再落到大屏高频刷新节流、数据编排平台 API 并发、WebRTC 信令与媒体回调三类真实异步时序问题。输出顺序题与"为什么 setTimeout(fn,0) 不立即执行"是本页面试主线。

1技术点概览

是什么

事件循环（Event Loop）是浏览器协调"单线程 JS 执行"与"海量异步事件"的调度机制：JS 主线程从上到下跑完同步代码，遇到异步操作（定时器、网络请求、事件回调）就把它交给浏览器的对应模块（定时器线程、网络线程）去跑，自己继续往下；等异步结果就绪，浏览器把对应的回调函数推进任务队列，主线程把当前栈清空后，再依次从队列取出回调执行。这套"栈空了再取任务"的循环就是 Event Loop。ES 规范（HTML 标准里定义浏览器版 Event Loop）规定了它的精确步骤，核心是宏任务（macrotask）与微任务（microtask）两类队列的优先级。

解决什么问题

没有这套机制，JS 只能同步阻塞：发个 HTTP 请求页面就冻住直到响应回来。事件循环让"等待 IO 的时间"被用来干别的，页面保持响应。对工程而言，理解它的价值是预测执行顺序：为什么改了数据视图没立刻更新、为什么 await 之后代码像"暂停"了、为什么 Promise.then 总比 setTimeout 先跑——这些都不是玄学，而是队列优先级。

横向对比：异步方案的三代演进

  • 回调函数（Callback）vs Promise：回调能跑，但嵌套三层就是"回调地狱"（callback hell），错误处理要逐层传参、无法 return 也无法 catch。Promise 把异步包成状态对象，支持链式 .then 与统一 .catch。
  • Promise 链 vs async/await：await 是"让异步代码读起来像同步"的语法糖，它本质仍然是 Promise——await x() 等价于 x().then(...)。两者完全可互相转换，await 只是消除了 .then 嵌套。
  • 宏任务 vs 微任务：微任务（Promise）每轮循环清空，优先级极高；宏任务（setTimeout）要等下一轮。WebRTC 的媒体回调、setTimeout 的时序差异，本质就是这条优先级线。

2核心概念

2.1 单线程与事件循环（Single-threaded Event Loop）

一句话定位：JS 同一时刻只跑一段代码，Event Loop 是让它"边等异步边不空等"的调度机制。

  • 单线程的理由：避免多线程同时操作 DOM 的竞态；代价是"不能阻塞"——一段同步代码跑太久（>50ms 长任务），后续渲染与事件回调全得排队，页面就卡。
  • Event Loop 的补救：把耗时的异步操作交给浏览器其他线程（网络、定时器、GPU），主线程只负责调度回调。

要点主线程是唯一执行者，其他线程只是"把回调推回队列"——这是理解一切前端性能问题的前提。

2.2 宏任务（Macrotask / Task）

一句话定位：Event Loop 每轮只取一个宏任务执行，是异步任务的"大块"。

  • 常见来源：setTimeout/setInterval 回调、I/O、UI 事件（点击、滚动）、<script> 整体、MessageChannel/MessagePort 消息。注：MessageChannel 消息与 window.postMessage 同为 task，早年被用作"近乎 0ms 的宏任务调度"，优势是不受 setTimeout 嵌套 5 层后 clamp 到 4ms 的限制。
  • 取法：每轮循环只从宏任务队列取一个任务，然后去清空微任务、再渲染。

坑setTimeout(fn,0) 也要排队等"当前同步代码 + 已有微任务"全部跑完，并非立即执行。

2.3 微任务（Microtask）

一句话定位：当前宏任务结束后立即整批执行，优先级高于下一个宏任务。

  • 来源：Promise.prototype.then/catch/finally 回调、queueMicrotask()、MutationObserver、Node 的 process.nextTick。
  • 整批清空：微任务执行期间新入队的微任务也在本轮一起跑完，直到队列清空才进入渲染。

结论这就是为什么 Promise.resolve().then(f) 总排在 setTimeout(f,0) 之前。

2.4 一轮 Event Loop 的精确步骤

一句话定位：所有异步时序题，答案都藏在"一个宏任务 → 清空微任务 → 渲染"这个循环里。

  1. 从宏任务队列取一个任务执行。
  2. 栈清空后，把整个微任务队列清空（期间新产生的微任务也加入本轮）。
  3. 尝试渲染（更新视图、处理 resize/scroll、rAF 回调）。
  4. 页面无交互需要时，进入空闲回调（requestIdleCallback）。

2.5 Promise 状态机（Promise State Machine）

一句话定位：Promise 是三态对象，状态落定即不可逆，then 回调进微任务队列。

  • 三态：pending（进行中）→ fulfilled（成功，不可变）或 rejected（失败，不可变），一旦落定不可逆。
  • 链式：.then 注册的回调在状态落定后被推入微任务队列；.then 又返回新 Promise，可链式串联。

坑Promise 一旦创建就立即执行构造函数里的同步代码，只是 .then 回调延迟到微任务阶段——这是"为什么 new Promise 里的 log 先打印"。

2.6 async / await（语法糖）

一句话定位：用同步的书写顺序表达异步逻辑，本质是把后续代码注册成微任务。

  • 行为：async function 总是返回 Promise；函数内遇 await，把其后代码当 .then 回调挂起，让出主线程，等 Promise 落定再从暂停处继续。
  • 不是阻塞：await 不阻塞线程，而是"把后续代码注册成微任务"。

要点错误用 try/catch 捕获——相比回调嵌套，这是错误处理范式的根本改善。

2.7 并发原语（Promise Combinators）

一句话定位：多个异步任务并发时，用四个组合器决定"等谁、怎么算成功"。

  • Promise.all：全成功才成功，一个失败整体 reject（快速失败）。
  • Promise.allSettled：等全部落定不管成败，适合批量上报、不希望一个失败拖垮全部。
  • Promise.race：取最先落定的（常用于超时竞速）。
  • Promise.any：取最先成功的（一个成功即成功）。

大屏批量拉设备状态、数据编排平台批量查节点元数据，就是这些组合器的典型场景。取消请求则用 AbortController：把 signal 传给 fetch(url,{signal})，再配合 Promise.race 与定时器做"超时即 abort"，避免过期响应污染状态。

2.8 定时器为何不准（Timer Throttling）

一句话定位：setTimeout 不是精确计时，浏览器为省电会主动拉长后台页的回调间隔。

  • 最小延迟：setTimeout(fn,0) 不是 0ms——嵌套 5 层后规范 clamp 到 4ms，且必须等当前宏任务与微任务清空。
  • 后台节流：后台标签页里定时器被节流到 1 秒一次；嵌套 iframe、未激活页面进一步拉长延迟。

坑用 setTimeout 做动画帧是错的——动画必须用 requestAnimationFrame，它与浏览器渲染节奏对齐。

3工作原理与流程

3.1 一轮 Event Loop 的完整时序

图 2 一轮 Event Loop 的完整步骤（示意）

  1. 取一个宏任务：整段 <script> 就是第一个宏任务。它把所有同步代码跑完。
  2. 同步期间的 Promise：new Promise(fn) 的 fn 同步执行，但 .then 的回调只被登记，等栈空后进微任务队列。
  3. 清空微任务：栈一空，引擎优先把微任务队列跑完，包括这期间新塞进队列的微任务。
  4. 渲染：微任务清空后才有渲染机会，然后循环回顶部取下一个宏任务（比如那个 setTimeout 回调）。

4核心语法与 API 要点

4.1 输出顺序题：先在脑子里跑一遍 Event Loop

console.log('1');
setTimeout(() => console.log('2'), 0);        // 宏任务
Promise.resolve().then(() => console.log('3')); // 微任务
console.log('4');
// 输出顺序：1 4 3 2
// 同步先跑 1、4 → 栈空清空微任务 3 → 下一轮宏任务跑 2

4.2 async/await 与 Promise 链对照

// 写法一：Promise 链
function load() {
  return fetch('/api/a').then(r => r.json())
    .then(a => fetch('/api/b?id=' + a.id))
    .then(r => r.json());
}
// 写法二：async/await（等价，读起来像同步）
async function load() {
  const a = await (await fetch('/api/a')).json();
  const b = await (await fetch('/api/b?id=' + a.id)).json();  // 有依赖，必须串行
  return b;
}
// 无依赖的并发：先一起 await 发起，再等结果
async function loadAll() {
  const p1 = fetch('/api/a');   // 立刻发起请求
  const p2 = fetch('/api/b');
  const [a, b] = await Promise.all([p1, p2].map(p => p.then(r => r.json())));
}

4.3 手写 Promise 最简版

function MyPromise(executor) {
  let state = 'pending', value = null;
  const onFns = [], onRns = [];
  const resolve = (v) => {
    if (state !== 'pending') return;
    state = 'fulfilled'; value = v;
    queueMicrotask(() => onFns.forEach(f => f(v)));   // 回调走微任务
  };
  const reject = (e) => { state = 'rejected'; value = e;
    queueMicrotask(() => onRns.forEach(f => f(e))); };
  executor(resolve, reject);
  return {
    then(onF, onR) {
      if (state === 'fulfilled') onF(value);
      else if (state === 'rejected') onR(value);
      else { onFns.push(onF); onRns.push(onR); }
      return this;   // 最简版链式，省略穿透与返回值处理
    }
  };
}

4.4 并发池：限制同时在跑的请求数

// 数据编排平台要批量查 50 个节点元数据，但并发太高会压垮后端
async function poolLimit(urls, limit, fn) {
  const results = [];
  const executing = new Set();
  for (const url of urls) {
    const p = Promise.resolve().then(() => fn(url));
    results.push(p); executing.add(p);
    const done = p.then(() => executing.delete(p));
    if (executing.size >= limit) await Promise.race(executing);  // 一个完成才补下一个
    await done;
  }
  return Promise.all(results);
}

4.5 防抖与节流

// 防抖 debounce：连续触发只在停下后执行一次（搜索输入）
function debounce(fn, wait) {
  let t; return function (...args) {
    clearTimeout(t); t = setTimeout(() => fn.apply(this, args), wait);
  };
}
// 节流 throttle：固定频率执行，中间丢弃触发（滚动、高频数据刷新）
function throttle(fn, interval) {
  let last = 0; return function (...args) {
    const now = Date.now();
    if (now - last >= interval) { last = now; fn.apply(this, args); }
  };
}

5实战项目经验（实战落地）

5.1 项目背景

一句话定位：两个真实场景正面撞上事件循环——大屏高频遥测刷新，和 WebRTC 播放器的信令/媒体异步时序。

  • 场景一：电力大屏负荷/告警面板经 WebSocket 或 2s 轮询持续收遥测，初版"每来一条就重绘"导致掉帧。
  • 场景二：WebRTC 无插件播放器（Vue2+Janus）启动是一段严格异步时序，顺序错就黑屏。

5.2 我的角色与职责

  • 角色：前端开发，负责大屏实时渲染节流与播放器启动时序。
  • 团队与分工：前端若干（估算），实践中通常做渲染调度与信令时序，后端/媒体服务同学对 Janus 信令接口。

5.3 技术栈

  • 大屏：Vue2 + ECharts + WebSocket/轮询。
  • 播放器：Vue2 + Janus + WebRTC（信令 HTTP、媒体 UDP）。

5.4 落地设计

  • 脏标记 + rAF：数据到达只存最新值打 dirty，渲染循环每帧与刷新率对齐重绘一次。
  • 读写分离：clientWidth 等布局读集中在帧开头，setOption 写在后，避免强制同步布局。
  • 事件 Promise 化：ontrack 用 {once:true} 包装成可 await 的 Promise，并入信令流程。

5.6 真实问题与解法

  • 渲染频率失控：初版每条数据重绘一次，峰值长任务 120ms+；改脏标记+rAF 后降到每帧一次、16ms 内（估算）。
  • rAF 不是解药：只加 rAF 没去掉"每帧读 clientWidth"仍卡——rAF 是节奏对齐，必须配读写分离。
  • 动画插值叠加：ECharts 默认开系列动画，高频 setOption 每帧都在插值，必须 animation:false。
  • 超时与媒体竞速：用 Promise.race 做"媒体到达或超时二选一"，不假定信令必成功。
  • play() 需用户手势：无手势时 video.play() 被拦截抛 rejection，必须 catch 并引导用户点播放。
  • ICE 边到边加：曾错误 await"收齐"candidate 致建连超时，正确做法是边到边 addIceCandidate。

5.7 量化成果

  • 大屏面板渲染从"每数据一次"降到"每帧一次"，峰值长任务 120ms+ → 16ms 内（估算），切屏不再卡。
  • 播放器信令/媒体时序理顺后黑屏率明显下降（估算）。

5.8 协作与排期过程

  • 契约先行：与媒体服务同学定 Janus attach/offer 信令字段与 candidate 推送方式。
  • 联调协商：黑屏问题和后端一起复现，定位到"等 ICE 收齐"的前端假设错误。
  • 排期：先修大屏掉帧（高频刷新），再做播放器启动时序治理。

5.9 复盘与可复用经验

  • 高频更新统一走 rAF + 脏标记：数据快、渲染慢时，中间必须有"只留最新"的闸门。
  • 异步时序用 async/await 线性化：把事件回调 Promise 化，复杂时序才不写成回调地狱。
  • 竞速问题用 Promise.race：超时与成功路径要显式二选一。

5.10 面试讲法

实战要点用 rAF + 脏标记把大屏高频渲染压到每帧一次，并用 async/await + Promise.race 理顺了 WebRTC 信令与媒体的异步竞速。

6易错点与面试重点

6.1 setTimeout(fn, 0) 不是立即执行

一句话定位：它是宏任务，必须等当前同步代码 + 微任务队列清空才轮到。

  • 现象：以为设 0ms 就马上跑。
  • 原因：规范还有 4ms 最小嵌套延迟，后台页更会被节流到 1s。
  • 正解：想"当前代码后尽快执行"用 queueMicrotask 或 Promise.then；想与渲染帧对齐用 rAF。

6.2 Promise.then 插队到 setTimeout 前

一句话定位：微任务在每轮宏任务后整批清空，优先级高于下一个宏任务。

  • 考点：输出顺序题。
  • 正解：记住"同步 → 微任务清空 → 下一个宏任务"三段式。

6.3 forEach 里 await 不等待

一句话定位：forEach 不 await 回调返回的 Promise，所以"以为串行实际并发"。

  • 现象：arr.forEach(async x => await fn(x)) 以为串行，实际并发跑完。
  • 正解：串行用 for...of + await；并发用 Promise.all(arr.map(fn))。

真坑这是数据编排平台批量查节点时踩过的。

6.4 Promise.all 一个失败全挂

一句话定位：批量上报一条失败就整体 reject，成功结果也拿不到——该用 allSettled。

  • 现象：批量上报里一条请求失败，Promise.all 整体 reject，其余成功的结果也拿不到。
  • 正解：这种"一条失败不影响其他"的场景用 Promise.allSettled，再自行过滤成功/失败。

6.5 async 函数里漏 await

一句话定位：漏 await 时函数立即 resolve，内部异步仍在跑，调用方等了个寂寞。

  • 现象：async function f(){ fetch('/a'); } 忘了 await，调用方等它返回时请求可能还没发出。
  • 原因：不 await 时函数立即 resolve，内部异步仍在跑。
  • 正解：ESLint no-floating-promises 兜底，需要等结果就必须 await。

6.6 unhandledrejection：没人 catch 的 Promise

一句话定位：rejected 的 Promise 没人 catch，错误被吞、页面静默。

  • 现象：接口失败却没有任何报错提示，页面静默无响应。
  • 原因：rejected 的 Promise 全程没有 .catch 或 try/catch，错误被吞。
  • 正解：全局挂 window.onunhandledrejection 统一上报，每个 async 都要有错误处理路径。
