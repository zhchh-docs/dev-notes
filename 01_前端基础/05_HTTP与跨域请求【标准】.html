HTTP 与跨域请求

标准 定位：前后端数据通道——HTTP 协议报文、同源策略、CORS 与代理方案

前端几乎所有数据都走 HTTP。本页讲清请求/响应报文结构、状态码、浏览器同源策略、CORS 预检机制，以及工程上最常用的跨域解法（开发态 Vite proxy、生产态网关）。案例取自 业务系统 的前后端联调与 Token 鉴权，以及 WebRTC 项目"信令走 HTTP、媒体走 UDP"的分层设计。

1简介与阅读指引

1.1 定位

HTTP 是客户端与服务端之间的"请求-响应"协议：浏览器发方法+路径+头+体，服务端回状态码+头+体。跨域是同源策略（Same-Origin Policy）带来的限制：页面源（协议+域名+端口）与接口源不一致时，浏览器默认禁止 JS 读取响应；CORS 是官方放行机制。前后端分离后（前端 :5173、后端 :8080）天生不同源，必须靠 CORS 或代理——理解这套机制，就知道"为什么 Postman 能调通、浏览器却报跨域"。

1.2 痛点

  • "OPTIONS 404/405"看不懂——预检失败被当成接口错误；
  • 带 Cookie 跨域怎么配都不生效——三件套缺一；
  • 跨域报错笼统看不到真实响应——不知道先绕开浏览器验证后端。

1.3 学习目标与阅读指引

  1. 讲清同源策略的本质：拦截点在读不在发——"发得出去、读不回来"；
  2. 分清简单请求与非简单请求，会排查 OPTIONS 预检失败；
  3. 掌握三种跨域方案选型（CORS 头 / Vite proxy / Nginx 反代）；
  4. 落地 axios 拦截器统一鉴权（Bearer Token + 401 跳登录）；
  5. 避开五条高频坑。

前置知识：04 篇导航时序（DNS/TCP/TLS 在哪发生）。难度：★★★☆☆。务必动手：第 6 章 Demo——本地跑通一次带预检的跨域请求。本篇不涉及：HTTP/2·3 特性细节、WebSocket（04 模块）。

2核心模型

四个核心模型：报文结构（Header 是元信息通道）→ 状态码五类（拦截器的分支依据）→ 同源策略（跨域的本质）→ CORS 与预检（放行机制）。

2.1 报文结构：起始行 + 头 + 空行 + 体

请求四块：请求行（方法+路径+版本）、请求头（Host/Content-Type/Authorization/Cookie）、空行、请求体（POST/PUT 数据，GET 一般没有）；响应同理。要点：鉴权令牌放 Authorization，跨域放行也靠响应头——Header 是这两件事的关键通道。

2.2 状态码：按首位分五类

  • 2xx 成功：200 OK、201 Created、204 无返回体；
  • 3xx 重定向：301 永久、302 临时、304 走缓存；
  • 4xx 客户端错：400 参数错、401 未认证、403 无权限、404 不存在；
  • 5xx 服务端错：500 内部错、502/504 网关/超时。

工程落点：axios 拦截器按 401 跳登录、5xx 提示服务异常——状态码分类是前端错误处理骨架。

2.3 同源策略：拦截点在读不在发

同源要求协议+域名+端口三者一致。跨域时请求真到了后端，但浏览器拦截 JS 读响应——目的是防恶意站偷读已登录站点的数据。例外：img/script/link 标签天然跨域加载资源（JSONP 的原理）。本质：跨域错误 = 你发得出去、读不回来。这也解释了"Postman 能调通、浏览器报跨域"——Postman 没有浏览器这道拦截。

2.4 CORS 与预检：简单 vs 非简单请求

  • 放行头：Access-Control-Allow-Origin 指明允许哪个源；
  • 简单请求：GET/POST 且只用安全头、Content-Type 仅 text/plain 等——直接发，浏览器看响应头放行；
  • 非简单请求：PUT/DELETE、自定义头（Authorization）、JSON body——先发 OPTIONS 预检，同意后才发真正请求；
  • 坑：带 Authorization 或 application/json 的接口几乎都是非简单请求——本地联调报跨域，先看 OPTIONS 预检有没有放行。

2.5 凭证与自定义响应头

Cookie 跨域：默认不带；要带需三件套——前端 credentials:'include'、后端 Access-Control-Allow-Credentials:true、Allow-Origin 必须具体源不能写 *。读自定义响应头：跨域时 JS 默认只能读少数简单响应头，要读 X-Total-Count 这类自定义头，后端必须回 Access-Control-Expose-Headers——否则 resp.headers.get() 拿到 null。实践：业务系统用 Bearer Token 放 Authorization 头，不依赖 Cookie，绕开这层。

3核心用法（按场景）

3.1 场景一：fetch 带鉴权头

const res = await fetch('/api/requirements', {
  headers: {
    'Authorization': 'Bearer ' + getToken(),   // Token 放自定义头
    'Content-Type': 'application/json'          // 这个头会触发预检
  }
});
if (!res.ok) throw new Error('HTTP ' + res.status);
const data = await res.json();

3.2 场景二：Vite 开发代理（开发态最常用）

// vite.config.ts：/api 开头的请求转发到后端，浏览器看到的是同源
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,          // 改 Host 头为目标地址
      }
    }
  }
};

3.3 场景三：axios 拦截器统一鉴权

// 请求拦截器：统一注入 Token
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = 'Bearer ' + token;
  return config;
});
// 响应拦截器：401 统一跳登录
api.interceptors.response.use(
  (res) => res.data,
  (err) => {
    if (err.response?.status === 401) location.href = '/login';
    return Promise.reject(err);
  }
);

3.4 场景四：三种跨域方案选型

方案原理适用场景
CORS 头后端回放行头，浏览器允许跨源读取前后端分离、后端可控
Vite/Webpack proxy开发服务器中转，浏览器看是同源本地开发
Nginx/网关反代生产环境同域反代到后端线上部署，最干净

选型判断：代理优于开 CORS——同源从源头消灭跨域，省掉一堆 CORS 调试；生产同域反代（衔接 09 模块 Nginx 篇）是最终形态。

4进阶知识点【进阶】

首次学习可整章跳过。前置：CORS 三种方案已跑通。

4.1 HTTP 缓存：强缓存与协商缓存

强缓存：Cache-Control: max-age=3600——期内直接用本地副本不发请求；协商缓存：ETag/If-None-Match 或 Last-Modified/If-Modified-Since——发请求问服务器变没变，没变回 304 用本地。策略与静态资源 hash 长缓存一脉相承（衔接 09 模块 Nginx 篇缓存分层）。

4.2 HTTP/1.1 队头阻塞与 HTTP/2

HTTP/1.1 同一 TCP 连接上请求串行（队头阻塞），浏览器用多个并发连接绕（同域 6 个）；HTTP/2 二进制分帧+多路复用——一条连接并行多请求，消除 HTTP 层队头阻塞（TCP 层仍在）。前端动作：升级 HTTPS 后开 h2，合并雪碧图等"减少请求数"优化在 h2 下不再必要。

4.3 OPTIONS 预检缓存

预检有开销（多一个往返），后端可回 Access-Control-Max-Age: 86400——预检结果缓存一天，期间同请求不再预检。联调时改了 CORS 配置却"不生效"，先清这个缓存（浏览器强刷或等过期）。

4.4 Token 放哪：Authorization vs Cookie

两派取舍：Authorization 头 + Bearer Token——不依赖 Cookie（绕开 credentials 三件套）、天然适配跨域与 App；代价是 Token 存储要防 XSS（localStorage 可被脚本读）。Cookie + HttpOnly——脚本读不到（防 XSS 偷）、CSRF 要另防（SameSite/CSRF Token）。业务系统选了 Bearer Token 是"跨域友好优先"。

4.5 控制面/数据面分离

WebRTC 播放器的协议分层：信令（SDP/ICE 协商）走 HTTP/WS——低频、可靠、JSON 友好；媒体流走 SRTP/UDP——高频、大带宽、容忍丢包。控制面与数据面选型不同是常态，混为一谈延迟和带宽都不对。

6最小可运行 Demo

性质：业务系统前后端分离联调实战——跨域 + Token 鉴权完整链路。

6.1 完整请求层（axios 封装）

import axios from 'axios';

const api = axios.create({ baseURL: '/api', timeout: 10000 });

api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = 'Bearer ' + token;
  return config;
});
api.interceptors.response.use(
  (res) => res.data,
  (err) => {
    if (err.response?.status === 401) location.href = '/login';
    return Promise.reject(err);
  }
);
export default api;

6.2 环境配置

// 开发态：vite.config.ts 代理（3.2）；生产态：Nginx 同域反代
// 后端 CORS（如直连）：
// Access-Control-Allow-Origin: http://localhost:5173
// Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
// Access-Control-Allow-Headers: Content-Type,Authorization

6.3 逐段解析与踩坑记录

  • baseURL '/api'：请求走同源路径，代理/反代转发——前端代码零跨域感知；
  • 预检没放行：后端起初没配 CORS，OPTIONS 预检 404——请求根本没到业务接口；补 CORS 后正常；
  • credentials 与 * 冲突：曾用 credentials:include 配 Cookie，后端 Allow-Origin 写 * 被浏览器拒；改用 Bearer Token 头绕开；
  • 契约先行：与后端约定 Token 放 Authorization 头、401 即跳登录——拦截器是这份契约的执行者。

6.4 验证清单

  1. 本地联调无跨域报错（Network 里预检 204、正式请求 200）；
  2. Token 过期后任意请求触发 401 → 自动跳登录；
  3. 自定义分页头（X-Total-Count）能读到（后端已配 Expose-Headers）。

7常见坑 & Debug

五条高频坑。

7.1 OPTIONS 预检失败被当成接口错误

现象：控制台跨域报错，但后端日志没看到请求。根因：非简单请求的预检被拒，真正请求根本没发出。正解：看 Network 里 OPTIONS 的响应，配好后端 CORS 头（含 Max-Age 缓存排查，4.3）。

7.2 带 Cookie 跨域不生效

现象：设了 withCredentials，Cookie 还是没带上。根因：前端 withCredentials、后端 Allow-Credentials:true、Allow-Origin 具体源（不能 *）——三件套缺一不可。正解：逐项核对；或干脆用 Bearer Token。

7.3 跨域错误被浏览器"吞掉"

现象：报错信息笼统，看不到真实响应。根因：跨域响应被拦截，JS 拿不到真实内容。正解：用 Postman/curl 直接打后端确认接口本身正常，再排查 CORS——先绕开浏览器定位问题归属。

7.4 GET 误带 body、Content-Type 错

现象：GET 带 JSON body，或 POST JSON 忘设 Content-Type。正解：GET 用 query；POST JSON 必须设 Content-Type: application/json（否则后端收不到）。

7.5 304 与缓存误判

现象：改了接口前端拿到旧数据。根因：GET 响应被浏览器/中间层缓存。正解：合理设置 Cache-Control，或查询参数加时间戳。

8重点讲解

Q1：什么是同源策略？为什么"Postman 能调通、浏览器报跨域"？

参考答案：同源策略要求协议+域名+端口三者一致才允许 JS 读取响应，目的是防恶意站偷读用户已登录站点的数据。关键：拦截点在读不在发——跨域请求其实到达了后端并执行，只是浏览器不让 JS 读响应（控制台看到的报错是读取被拒）。Postman/curl 没有浏览器这道安全模型，所以能调通——这也正是排查跨域问题"先绕开浏览器验证后端"的依据。

加分点：img/script/link 标签天然跨域（JSONP 原理）；CORS 是服务端用响应头主动放行。

Q2：简单请求与非简单请求的区别？OPTIONS 预检失败怎么排查？

参考答案：简单请求——GET/POST 且只用安全头、Content-Type 限于 text/plain 等少数几种，直接发、看响应头放行；非简单请求——PUT/DELETE、自定义头（Authorization）、application/json 等，浏览器先发 OPTIONS 预检问"允许这个源用这些方法这些头吗"，通过才发真正请求。排查：控制台跨域报错先看 Network 里 OPTIONS 的响应——404/405 说明后端没处理预检，204 但缺 Allow-Origin/Headers 说明配置不全；改配置后注意 Max-Age 预检缓存。

经验：带鉴权头或 JSON 的接口几乎都是非简单请求。

Q3：跨域的三种解法怎么选？带 Cookie 的跨域要注意什么？

参考答案：CORS 头（后端放行，前后端分离且后端可控）、开发代理（Vite proxy，开发态同源）、Nginx 反代（生产同域，最干净）。选型原则：代理优于开 CORS——同源从源头消灭跨域问题。带 Cookie 跨域三件套缺一不可：前端 credentials:'include'、后端 Allow-Credentials:true、Allow-Origin 必须是具体源（* 与 credentials 冲突会被浏览器拒绝）。实践上更推荐 Bearer Token 放 Authorization 头，绕开整层。
