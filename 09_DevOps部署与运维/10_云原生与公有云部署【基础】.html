云原生与公有云部署

基础 定位：云主机 / 容器服务 / Serverless、对象存储与 CDN——与自建部署的对比与取舍

把应用部署到自己买的物理服务器上，叫自建；把服务器/运行环境租给云厂商，就是公有云。云原生则更进一步——应用天生按容器、弹性、可观测来设计。本页入门讲清楚云主机、容器服务、Serverless、对象存储与 CDN 分别是什么，并和项目组项目里实际用的 Nginx/Docker 自建部署做对比——这块以了解与评估为主。

1简介与阅读指引

1.1 定位

云原生/公有云部署是把运行环境租给云厂商的一整套方式，核心三类：云主机（IaaS）租一台虚拟服务器自己装环境、容器服务（PaaS）云厂商托管 K8s 你只丢镜像、Serverless（FaaS）只上传函数按调用量计费。它把自建服务器的"买机器、托管、修硬件、等采购扩容"变成"点几下开通、按用量付费、随用随扩"。配套的对象存储（OSS/S3）+ CDN 是前端静态产物上云的标准路径。

1.2 痛点

  • 自建扩容要采购、慢——流量来了扛不住；
  • 不知道该选哪层服务——盲目追 Serverless 被冷启动坑；
  • 上了 OSS+CDN 忘刷缓存——发版了用户看旧版。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要做"自建 vs 上云"的选型判断容器与 K8s 本身 → 本模块 05/07 篇
前端静态产物上云（OSS+CDN）路径Nginx 自建细节 → 本模块 04 篇
面试（IaaS/PaaS/FaaS 边界、缓存刷新是高频）云厂商记账与合规细节 → 按需查官方文档

诚实声明：项目组真实部署是内网自建（Nginx+Docker，数据不出域），云原生是我评估与概念验证过的方向，不编造上云履历。

1.4 学习目标与阅读指引

  1. 讲清 IaaS / PaaS / FaaS 三层边界（抽象层级越高、你管的越少）；
  2. 掌握 OSS+CDN 上云发布链路与缓存策略（和 Nginx 缓存分层同理）；
  3. 判断 Serverless 的适用边界（波动型/事件驱动，非常驻低延迟）；
  4. 避开三条高频坑（忘刷 CDN、index.html 被缓存、误用 FaaS）。

前置知识：Nginx 缓存策略（本模块 04 篇——本篇多处对照）；容器概念（05 篇）。难度：★☆☆☆☆（概念为主，重在取舍判断）。务必动手：第 6 章 Demo——用本地 Nginx 验证同一套缓存策略。

2核心模型

四个核心模型：三层云服务（责任边界）→ 对象存储 + CDN（前端最相关）→ 按量付费与弹性（经济模型）→ 冷启动（Serverless 的代价）。

2.1 三层云服务：抽象层级越高、你管的越少

  • IaaS（云主机 ECS/EC2）：租一台带公网 IP 的虚拟机，OS/运行时/应用全自己装——"把机房搬进云里"，省硬件采购但系统层归你管，管的最多、灵活性最高；
  • PaaS（容器服务/托管 K8s）：控制面与节点运维由云托管，你只打成镜像、写 Deployment/Service 清单——云管底层、你管应用（衔接 07 篇，只是"自己搭 K8s"换成"用云托管的"）；
  • FaaS（Serverless）：上传函数、按调用量计费、闲时不花钱——你管的最少。

一条记忆线：IaaS 给你虚拟机 → PaaS 给你运行时 → FaaS 给你函数。每一层上升，都是"运维责任换抽象效率"的交易。

2.2 对象存储 + CDN：前端静态产物的上云路径

对象存储（OSS/S3/COS）：海量文件（图片/附件/dist）的高可靠存储，自带 HTTP 访问。CDN：把 OSS 里的资源缓存到离用户最近的边缘节点，全国访问都快，还挡掉回源流量。前端意义：build 出的带 hash 静态资源丢 OSS+CDN，比自建 Nginx 更快更省带宽——缓存策略与 Nginx 完全同理：hash 资源长缓存、index.html no-cache。

2.3 按量付费与弹性：云的经济模型

自建 = 固定成本（机器/托管），云 = 可变成本（按用量）。流量波动大的公网业务弹性扩缩价值最大；内网、数据不出域、负载稳定的系统，自建可控且便宜——这就是项目组（电力内网、现场网络隔离）选择自建的根因（图 1，第 5 章）。选型的第一问不是"云好不好"，是"我的负载和数据约束是什么"。

2.4 冷启动：Serverless 的隐藏代价

FaaS 请求来了才拉起容器执行、执行完释放——长时间没请求后第一次调用要重新拉起，秒级延迟。所以：波动型/事件驱动（图片处理、webhook、定时报表）适合 FaaS；常驻低延迟 API 不适合——不能为了"没人访问不花钱"把延迟敏感服务搬上去（坑 7.3）。

3核心用法（按场景）

3.1 场景一：自建 vs 云原生选型（判断先于动手）

维度自建（Nginx/Docker）公有云/云原生
初始成本买机器/托管，前期投入大按量付费，起步成本低
运维责任操作系统、故障、扩容全自己管云托管底层，你只管应用
弹性扩容要采购、慢分钟级扩缩
适用内网/数据不出域/长期稳定公网业务、流量波动大

3.2 场景二：静态产物上传 OSS（概念命令）

# 以阿里云 ossutil 为例（概念示意，实际用各家官方 CLI）
ossutil cp -r ./dist/ oss://my-bucket/www/ --update
# 上传后在 CDN 控制台刷新对应缓存，新发布才会对用户生效

要点：带内容 hash 的资源可设长缓存，index.html 必须设不缓存——否则发版后用户拿到旧入口（与 Nginx 篇缓存分层完全同理）。

3.3 场景三：Serverless 选型判断清单

  1. 触发方式：事件驱动/HTTP 且频次波动大？→ 适合；
  2. 延迟要求：常驻低延迟 API？→ 不适合（冷启动）；
  3. 状态依赖：需要长连接/本地状态？→ 不适合（无状态短生命周期）；
  4. 成本曲线：低频调用为主？→ 省钱明显；高 QPS 常驻？→ 不一定比包年便宜。

4进阶知识点【进阶】

首次学习可整章跳过。前置：三层概念与 OSS+CDN 链路已清楚。

4.1 CDN 回源与刷新机制

边缘节点首次未命中才回 OSS 拉取并缓存——所以发版必须主动刷新 CDN 缓存（URL 刷新或目录刷新），否则旧文件在边缘缓存到期前一直被命中。配合 hash 资源策略：hash 资源文件名天然不同无需刷新，真正要刷的只有 index.html。

4.2 云原生 12 要素（12-Factor）

云原生应用设计的经典方法论，前端最相关的几条：配置与代码分离（环境变量注入，不把环境写死进构建产物）、无状态进程（状态外置到存储）、可弃性（进程可随时销毁重建）。对照 K8s 篇的 ConfigMap——同一思想在不同层的表达。

4.3 蓝绿/灰度在云上的形态

云的弹性让发布策略更从容：蓝绿——两套环境切流量，秒级回滚；灰度/金丝雀——按比例放流量（CDN/网关层按 header 或权重分发）。自建也能做但成本高，云上通常托管服务自带（如容器服务滚动更新+健康检查，衔接 07 篇）。

4.4 静态托管平台谱系

Vercel/Netlify（前端一站式：构建+托管+CDN）、OSS/S3 静态网站（自管缓存策略）、自建 Nginx（完全可控）——三档对应"省事程度 vs 可控程度"的递增。内网/合规项目没得选（自建），公网个人/小项目首选托管平台。

6最小可运行 Demo

性质：自学 + 概念验证（不真买云资源），重点是缓存与刷新策略的本地复现。

6.1 完整配置（Nginx 复现 CDN 缓存策略）

# 带 hash 的静态资源长缓存；index.html 不缓存（上云与自建通用）
location /assets/ {
  expires 1y;
}
location = /index.html {
  add_header Cache-Control "no-cache";
}

6.2 跑通与验证

npm run build && cp -r dist/* /usr/share/nginx/html/ && nginx -s reload
curl -I localhost/assets/app.abc123.js    # 预期：max-age=31536000
curl -I localhost/index.html              # 预期：no-cache
# 改代码重新 build 后不 reload：index.html 即时更新、旧 hash 资源命中长缓存
# ——这正是"OSS+CDN + 只刷 index.html"策略的行为模型

6.3 逐段解析

  • expires 1y + no-cache 两行：上云缓存策略的全部核心，本地可完全复现；
  • 验证方法：改内容重新 build——hash 变的资源自然加载新版、index.html 即时更新；
  • 与 CDN 的映射：OSS=本地磁盘源站，CDN=浏览器/代理缓存，刷新 CDN=重载入口。

6.4 生产改造扩展方向

  1. 真开一个对象存储桶跑一遍 ossutil 上传 + 控制台刷新；
  2. 把上传+刷新接入 CI/CD 流水线（衔接本模块 08 篇 deploy stage）；
  3. 给一个低频事件（如图片压缩）写 FaaS 函数，实测冷启动延迟。

7常见坑 & Debug

三条高频坑，每条五要素。

7.1 坑 1：上云后忘刷 CDN 缓存

  • 现象：新 dist 传上去了，用户打开还是旧版；
  • 根因：CDN 边缘节点命中旧缓存，源站已新但边缘未过期；
  • 复现：本地 Nginx 模拟——改内容后强命中缓存路径观察；
  • 修复：发版流程加"刷新 CDN 缓存"一步（URL/目录刷新）；
  • 规避：CI/CD 的 deploy stage 固定"上传 OSS → 刷 CDN"两连（4.1）。

7.2 坑 2：index.html 被 CDN 长缓存

  • 现象：刷新了 CDN 也偶发旧版（不同节点/不同用户不一致）；
  • 根因：入口文件带缓存时间——任何节点缓存的 index.html 都是新版的敌人；
  • 修复：index.html 设 no-cache，带 hash 资源才长缓存；
  • 规避：与 Nginx 篇同一条铁律——入口保鲜、资源提速。

7.3 坑 3：误把常驻低延迟服务搬上 Serverless

  • 现象：API 上 FaaS 后，每次"第一发"请求秒级延迟；
  • 根因：冷启动——长时间无请求后要重新拉起容器；
  • 修复：常驻低延迟服务用容器/云主机；FaaS 留给波动型/事件驱动任务；
  • 规避：选型清单三连问——触发方式/延迟要求/状态依赖（3.3）。

8重点讲解

Q1：IaaS / PaaS / FaaS 怎么区分？

参考答案：按责任边界分——IaaS（ECS/EC2）给你虚拟机，操作系统、运行时、应用全自己装；PaaS（托管容器服务）给你运行时环境，你只管镜像与副本声明；FaaS（Serverless）只给你函数，按调用计费、闲时为零。记忆线：抽象层级越高、你管的越少、云厂商替你做的越多——但灵活性也逐层下降，选层是"管控需求"与"运维成本"的权衡。

Q2：前端静态资源上 OSS+CDN，缓存策略怎么配？和自建 Nginx 有什么异同？

参考答案：策略完全同理——带 hash 的资源长缓存（1 年）、index.html 设 no-cache；差异在多了一层 CDN 边缘缓存，所以发版要加"刷新 CDN"一步。原理：hash 让内容版本编码进文件名，天然绕过缓存失效问题；index.html 文件名固定、每次发版都变，必须保持"每次都问服务器/源站"。异同一句话：同一套分层原则，CDN 多了"边缘节点回源"与"主动刷新"两个环节。

Q3：什么业务适合 Serverless？什么不适合？

参考答案：适合——波动型/事件驱动负载（图片处理、webhook 回调、定时报表）：没人访问不花钱，突发流量自动伸缩。不适合——常驻低延迟服务（冷启动秒级延迟）、有状态/长连接应用（无状态短生命周期）、高 QPS 常驻（按量计费可能反而贵）。判断框架：触发方式是否事件驱动、延迟是否敏感、是否依赖常驻状态（3.3 清单）。

加分点：给出真实约束案例——内网/数据不出域项目（如电力系统）连公有云都进不去，自建是唯一解，选型先看约束再看收益。
