Shell 脚本

基础 定位：把重复运维动作写成脚本——部署/清理日志/定时任务

部署、清理日志这些重复动作，手写一遍要敲好几条命令、还容易漏步。Shell 脚本把它们固化成一个可重复执行的 .sh 文件，配合 crontab 定时跑。本页入门讲清脚本的基本结构、变量与判断，并给两段能直接跑的脚本：部署脚本与日志清理。

1技术点概览

是什么：Shell 脚本就是把一连串 Linux 命令写进一个 .sh 文件、一次执行：

  • 定位：Linux 自动化运维的基础工具。
  • 收益：重复的手工动作（部署、备份、清日志）写成脚本，既快又不会漏步。

解决什么问题："每次部署都要手动传文件、进目录、重启服务"——这种重复又易错的操作，写成脚本一条命令完成；再配 crontab 定时跑（如每天凌晨清日志），就完全自动了。

2核心概念

2.1 shebang（#!/bin/bash）

一句话定位：脚本第一行声明用哪个解释器跑这个脚本。

  • 作用：坑./deploy.sh 能直接跑的前提是先 chmod +x deploy.sh 加执行权限；shebang 本身并不赋予可执行性，它只是指定用哪个解释器（#!/bin/bash 用 bash、#!/bin/sh 用 POSIX sh）。
  • 否则：没执行权限会 Permission denied；不加 shebang 时在 bash 下 ./deploy.sh 仍会由当前 shell 兜底执行，只是 bash 专有语法在 sh 里会报错。

2.2 变量与参数

一句话定位：等号两边不能有空格，用 $VAR 取值、$1/$2 取位置参数。

  • 坑语法：VAR=value 定义（等号两边不能有空格），$VAR 取值。
  • 位置参数：$1 $2 是传入的第几个参数，脚本化时常把环境名/版本号传进去。

2.3 crontab（定时任务）

一句话定位：crontab 让脚本定时无人值守运行，格式是"分 时 日 月 周 命令"。

  • 编辑：crontab -e。
  • 举例：0 3 * * * /opt/clean.sh = 每天凌晨 3 点跑清理脚本。

3工作原理与流程

脚本本质是"命令的批处理"：从上到下依次执行每条命令。配合 && 让前一条失败就中断（build && deploy——build 失败就不部署），配合 set -e 让脚本遇错即停。部署脚本的典型流程：备份旧版本 → 解压新版本 → 重启服务 → 校验。把这套固化，每次执行结果一致。

set -e 是好习惯：让脚本里任何一条命令失败就立即退出，避免"前面失败了还继续往下跑、把服务搞成半成品"。

4核心语法要点

#!/bin/bash
set -e                      # 出错即停
APP_NAME="myapp"            # 定义变量
echo "开始部署 $APP_NAME"   # 输出
# 判断参数
if [ -z "$1" ]; then
  echo "用法: $0 <环境名>"; exit 1
fi
ENV=$1

crontab 写法

# crontab -e 编辑：分 时 日 月 周 命令
0 3 * * * /opt/scripts/clean_logs.sh    # 每天 3:00 清日志

5实战项目经验（实战落地）

5.1 项目背景：把重复运维动作脚本化

一句话定位：每次部署都手动备份→解压→重载，日志手动清，容易出错也慢，写成脚本一次到位。

  • 场景：大屏/平台项目反复部署，日志日积月累占磁盘。

5.2 我的角色与职责

  • 分工：我自己写部署与日志清理脚本并挂 crontab，供自己与团队复用。

5.3 技术栈

  • Bash + tar/find + crontab。

5.4 落地设计：部署脚本 + 定时清理

  • 关键部署脚本：先备份旧版再解压新版，失败即停（set -e）。
  • 日志清理：find 删 7 天前日志，挂 crontab 每日跑。

5.5 关键实现要点

#!/bin/bash
set -e
# 备份旧版本 → 解压新版本 → 重载 Nginx
DEPLOY_DIR=/usr/share/nginx/html
BACKUP_DIR=/data/backup

echo "== 备份旧版本 =="
tar -zcf $BACKUP_DIR/dist-$(date +%Y%m%d%H%M).tar.gz $DEPLOY_DIR

echo "== 解压新版本 =="
tar -zxf /tmp/dist.tar.gz -C $DEPLOY_DIR

echo "== 校验并重载 Nginx =="
nginx -t
nginx -s reload
echo "== 部署完成 =="
#!/bin/bash
set -e
# 删除 7 天前的日志文件（挂 crontab）
LOG_DIR=/var/log/myapp
find $LOG_DIR -name "*.log" -mtime +7 -delete
echo "已清理 7 天前日志：$(date)"

5.6 真实问题与解法

  • 坑脚本没加执行权限：Permission denied——chmod +x。
  • 坑没加 set -e：中间命令失败还继续跑。
  • 坑crontab 环境变量不同：定时任务环境干净，脚本里要用绝对路径。

5.7 量化成果

  • 部署从手动多步变成跑一个脚本；旧版有备份可回滚；日志由 crontab 自动清理，不再人工盯磁盘。

5.8 协作与排期过程

  • 流程：脚本经小步验证后挂 crontab；部署脚本纳入发布流程。

5.9 复盘与可复用经验

  • 要点set -e + 绝对路径：脚本健壮的两个底线。
  • 要点先备份再覆盖：部署脚本可回滚。

5.10 面试讲法（一句话抓手）

一句话抓手："我写过部署脚本（备份→解压→nginx -t&&reload）和挂 crontab 的 7 天日志清理脚本，踩过脚本没加执行权限、crontab 里找不到命令这两个最常见的坑。"

6易错点与面试重点

6.1 没加执行权限

一句话定位：脚本没执行权限，运行报 Permission denied。

正解：chmod +x xx.sh。

6.2 变量等号两边有空格

一句话定位：VAR = value（带空格）会被当成命令。

正解：VAR=value，紧贴等号。

6.3 crontab 里用相对路径/缺环境变量

一句话定位：定时任务环境很"干净"，找不到你手动时的命令与路径。

正解：脚本里用绝对路径。

6.4 脚本遇错继续跑

一句话定位：没 set -e，前面失败后面还执行，搞出半成品。

正解：开头加 set -e。
