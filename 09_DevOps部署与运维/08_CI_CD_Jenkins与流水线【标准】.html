CI/CD：Jenkins 与流水线

标准 定位：三档位 / 制品化 / 门禁与通知

CI/CD 把"拉代码→构建→测试→打包→部署"固化成失败即停的自动化链。本篇讲透三个核心模型：CI/持续交付/持续部署三档位（前端通常停在持续交付）、流水线即代码（Jenkinsfile 进版本管理）、制品化铁律"构建一次、到处部署"；配本地 Jenkins 五阶段 Demo 与五条高频坑（lockfile/每环境重构建/无通知等）。（说明：Jenkins 在我项目里以配合使用为主，如实说明深度。）

1简介与阅读指引

1.1 定位

CI/CD 是把"拉代码→安装→构建→测试→打包→部署"固化成一条自动化链：CI（持续集成）每次合入自动构建+测试，尽早暴露"改 A 坏 B"；CD（持续部署/交付）验证过的产物自动部署到环境。Jenkins 是最经典的引擎（同类 GitLab CI、GitHub Actions，理念一致）。它终结的是手工部署时代："本地打包、手动传服务器、人肉跑测试——上次手动发的，谁知道发了啥"。

1.2 痛点

  • 手工部署慢且易错、不可审计（"发的什么版本？"没人说得清）；
  • CI 装出和本地不同的依赖——"我本地能过 CI 挂"；
  • 流水线红灯挂半天没人发现——失败没通知。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要为前端项目搭/参与维护 CI 流水线部署目标环境本身 → 04 Nginx / 05 Docker
面试（构建一次到处部署/lockfile/门禁是高频）Jenkins 服务器运维 → 运维方向
排查"CI 与本地不一致/产物不一致"lint/测试本身 → 06 工程化模块

诚实声明：真实项目里 Jenkins 由后端/运维主导，我以前端视角配合（提供 build/test 命令与产物路径）；本篇含自建流水线 demo，如实呈现深度。

1.4 学习目标与阅读指引

  1. 区分 CI / 持续交付 / 持续部署三档位，知道前端项目通常停在哪；
  2. 写出分阶段、带门禁与失败通知的 Jenkinsfile；
  3. 理解并落地铁律"构建一次、到处部署"（制品化）；
  4. 避开五条高频坑（lockfile、每环境重构建、无通知、无门禁、钩子过重）。

前置知识：Git 分支与合并（衔接 10 模块 03 篇评审流程——CI 是评审的门禁引擎）；npm scripts。难度：★★☆☆☆。务必动手：第 6 章 Demo——本地 Jenkins 跑通一条完整流水线。

2核心模型

四个核心模型：CI 与 CD 的档位（自动化到哪一步）→ 流水线即代码（工程形态）→ Stage 与门禁（执行结构）→ 制品化（本篇最重要的纪律）。

2.1 CI → 持续交付 → 持续部署：自动化到哪一步

三个档位（图 2 见第 5 章）：CI 持续集成——每次提交自动构建+跑测试；持续交付——自动到测试/预发，上生产人工点一下；持续部署——全自动上生产，要求测试覆盖极高。前端项目通常停在持续交付：测试环境自动上、生产走人工审批——平衡速度与风险。

2.2 流水线即代码（Pipeline as Code）

流水线写成文件（Jenkinsfile / .gitlab-ci.yml）跟代码一起进版本管理——不是在 Jenkins 界面上点点点配。收益：流水线改动也能 code review、可追溯（谁改的为什么改）、可复制（新项目拷模板）。这是现代 CI/CD 的标准形态。

2.3 Stage 与门禁：失败即停

流水线分 stage（拉代码/构建/测试/部署），stage 间串行（构建不过不测试——下游永远不碰不合格产物），stage 内可并行（多平台测试同时跑）。CI 门禁是质量杠杆的引擎：lint+单测作为独立 stage，红了即停、通知责任人——不污染下游环境（衔接 10 模块 03 篇质量杠杆全景）。

2.4 制品化：构建一次、到处部署

构建一次产物，测试/预发/生产都用同一个制品——如果每个环境重新 build，测试过的和生产上的就不是同一份代码，"环境一致性"从根上就不成立。制品要有归宿：archiveArtifacts 归档或推制品仓库（Nexus/Harbor），后续环境拉同一个包部署（图 3 见第 5 章）。

3核心用法（按场景）

3.1 场景一：最小 Jenkinsfile（前端流水线）

pipeline {
  agent any
  stages {
    stage('install') { steps { sh 'pnpm install --frozen-lockfile' } }
    stage('build')   { steps { sh 'pnpm build' } }
    stage('test')    { steps { sh 'pnpm lint && pnpm test' } }  // CI 门禁
    stage('deploy-test') { steps { sh 'deploy.sh dist' } }
  }
  post { failure { echo '发通知给开发' } }
}

3.2 场景二：关键声明式块

environment {
  NODE_ENV = 'production'
  DEPLOY_KEY = credentials('deploy-key')      // 凭据引用，不写明文进库
}
stage('deploy') {
  when { branch 'main' }                      // 只 main 分支才部署
  steps { sh 'deploy.sh dist' }
}
options { buildDiscarder(logRotator(numToKeepStr: '10')) }  // 只留最近 10 次构建

三件套：environment + credentials() 管密钥（账号/密钥永不写明文进库）；when 控制分支条件；buildDiscarder 管构建历史膨胀。

3.3 场景三：制品落地

stage('package') {
  steps {
    archiveArtifacts 'dist/**'        // 归档产物（简单版）
    // 或 stash/unstash 在 stage 间传递；规范版推 Nexus/Harbor
  }
}

对照：GitLab CI / GitHub Actions 用 YAML 写同样的 stage 逻辑，理念一致——"提交触发 → 分阶段跑 → 失败告警"。会一种，另外两种半天上手。

4进阶知识点【进阶】

首次学习可整章跳过。前置：流水线已跑通。

4.1 依赖安装的确定性：--frozen-lockfile

CI 必须严格按 lockfile 安装（pnpm install --frozen-lockfile / npm ci）——裸 install 会按 semver 拉新版本，CI 装出和本地不同的依赖树，"我本地能过 CI 挂"的经典来源。lockfile 冲突时在本地解决后提交，绝不让 CI "自由发挥"。

4.2 缓存与提速

CI 构建慢的主因是每次全量装依赖：用 CI 的缓存机制（Jenkins workspace 保留 / GitLab CI cache / actions/cache）缓存 pnpm store / node_modules——依赖未变时秒装。配合分层思想（衔接 05 篇镜像分层）：依赖层稳定才值得缓存。

4.3 触发机制：webhook 与定时

主流触发是 webhook：Git 服务器在 push/merge 时回调 Jenkins（或平台内置触发）；另有 cron 定时（夜间全量回归）。触发范围要收敛：不是所有分支都触发全量流水线——feature 分支跑轻量（lint+相关测试），main 跑全量+部署。

4.4 环境分级与晋级

标准三级：dev（自动）→ test/staging（自动）→ prod（审批门禁）。晋级的是同一个制品（2.4），环境差异只体现在配置（环境变量/ConfigMap，衔接 07 篇）。前端多项目可加矩阵并行（多浏览器/多 Node 版本同时测）。

6最小可运行 Demo

性质：自学自建 demo（本地 Jenkins），非生产；诚实呈现深度。

6.1 完整 Jenkinsfile

pipeline {
  agent any
  options { buildDiscarder(logRotator(numToKeepStr: '10')) }
  stages {
    stage('install') { steps { sh 'pnpm install --frozen-lockfile' } }
    stage('build')   { steps { sh 'pnpm build' } }
    stage('test')    { steps { sh 'pnpm lint && pnpm test' } }   // CI 门禁
    stage('package') { steps { archiveArtifacts 'dist/**' } }    // 制品归档
    stage('deploy-test') {
      when { branch 'main' }
      steps { sh './deploy.sh dist' }                            // 测试环境自动上
    }
  }
  post {
    failure { echo '流水线失败，通知开发（邮件/IM 机器人）' }
    success { echo '部署完成，通知测试验收' }
  }
}

6.2 跑通步骤

# 本地起 Jenkins（Docker 单机）
docker run -d -p 8080:8080 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts
# Jenkinsfile 提交到仓库根目录 → Jenkins 建流水线任务指向仓库 → push 触发
# 观察：install → build → test → package → deploy-test 五阶段依次亮绿

6.3 逐段解析

  • --frozen-lockfile：CI 依赖确定性的第一道闸（坑 2）；
  • test 在 build 后：lint+单测做门禁，红了即停不进部署；
  • archiveArtifacts：制品归档——为"构建一次到处部署"铺路；
  • when branch main：部署只发生在 main——feature 分支只验证不上环境。

6.4 与真实项目的差异（诚实说明）

真实项目流水线由后端/运维主导，我提供前端命令与产物路径；本 demo 单机、无多环境审批流、无制品仓库、无并行矩阵——面试如实定位："独立写过流水线，生产多环境编排是配合视角。"

6.5 生产改造扩展方向

  1. 制品推 Nexus/Harbor，生产 stage 拉同一制品（兑现图 3）；
  2. 加依赖缓存（4.2）与矩阵并行测试；
  3. 部署后自动探活（curl /health），失败自动回滚到上一制品。

7常见坑 & Debug

五条高频坑，每条五要素。

7.1 坑 1：每环境重新构建

  • 现象：测试环境验证过，上生产就出问题；
  • 根因：每个环境重新 build——产物不一致，违背"构建一次到处部署"；
  • 修复：构建一次存制品，各环境拉同一个包部署（图 3）；
  • 规避：流水线评审必问"生产上的是不是测试过的那个制品"。

7.2 坑 2：CI 不按 lockfile 安装

  • 现象：本地能过 CI 挂，报的错跟依赖版本有关；
  • 根因：裸 install 按 semver 拉新版本，CI 与本地依赖树不同；
  • 修复：pnpm install --frozen-lockfile / npm ci（4.1）；
  • 规避：前端项目流水线模板写死确定性安装。

7.3 坑 3：失败无通知

  • 现象：流水线红了半天没人发现，测试环境一直旧版；
  • 根因：没配 post.failure 通知；
  • 修复：failure 通知（邮件/IM 机器人）；
  • 规避：通知与门禁同为一期流水线的标配。

7.4 坑 4：环境不分级，直接上生产

  • 现象：一改代码直接上生产，出事没有缓冲；
  • 根因：没有环境分级与门禁；
  • 修复：测试自动、生产审批（持续交付档位，图 2）；
  • 规避：生产部署永远是"按钮"而不是"自动"（除非测试覆盖极高）。

7.5 坑 5：重构建塞进 git hook

  • 现象：本地提交巨慢，每次 commit 卡几十秒；
  • 根因：把完整构建/全量测试塞进提交钩子；
  • 修复：钩子只做轻量检查（lint-staged），重活交给 CI；
  • 规避：分工口诀——钩子管秒级反馈，CI 管分钟级门禁。

8重点讲解

Q1：CI 和 CD 的区别？前端项目应该做到哪个档位？

参考答案：CI——每次提交自动构建+测试，尽早暴露集成问题；CD 分两档——持续交付（自动到测试/预发，生产人工审批）与持续部署（全自动上生产）。前端通常停在持续交付：前端发版风险高（直接面对用户）、自动化验证手段相对弱（UI 测试覆盖有限），生产留人工门禁平衡速度与风险；测试覆盖极高、发布节奏极快的团队才进持续部署。

考察点：知道档位是风险决策，不是越自动越好。

Q2：什么是"构建一次、到处部署"？为什么重要？

参考答案：构建一次产物（制品），测试/预发/生产拉同一个包部署——环境差异只体现在配置。重要性：如果每环境重新 build，测试验证的和生产上线的不是同一份代码（依赖解析时点、构建参数都可能不同），"测试通过"就失去了对生产的担保力——环境一致性是 CI/CD 的初衷本身。

落地：archiveArtifacts/制品仓库存档 + 环境晋级机制；与 K8s 的镜像 tag 不可变（05 篇）同理同源。

Q3：为什么 CI 要用 --frozen-lockfile？

参考答案：CI 的使命是确定性——同一份代码必须装出同一棵依赖树。裸 install 按 semver 拉新版本（依赖作者发了新版就变），CI 与本地、上一次与这一次的构建环境都在漂移，构建结果不可复现。--frozen-lockfile/npm ci 严格按 lockfile 装，lockfile 冲突回本地解决后提交。一句话：lockfile 是依赖的"契约"，CI 是契约的执法者。
