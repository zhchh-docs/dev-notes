9.1简介与阅读指引

定位

前 8 个阶段学的是"零件"，这一阶段教你"组装"：用三个难度递进的项目（TODO → 博客 → 商城）把全部知识串成完整产品。项目实战不是可选项——没有做过完整项目的简历，面试官一眼就能看出来。

痛点

初学者做项目的两大死法：①上来就做太难的——想直接做商城，结果卡在环境配置一周后放弃；②做完不复盘——项目跑通了，但被问"你为什么这么设计"时答不上来，等于没做。本篇用"最小闭环 → 加用户体系 → 加架构挑战"的递进法避开这两个坑。

前置知识

  • 阶段 1~6 全部过完（至少扫过）；每章都标注了项目用到它的哪个部分；
  • 工具就绪：Node.js 安装、Git 基本操作（06 模块 2）、一个趁手的编辑器。

阅读指引

  • 边读边做：本篇的正确打开方式是"左手这篇、右手编辑器"，每个项目按 9.3~9.5 的步骤走完；
  • 第一遍可跳过：9.5 商城里秒杀/MQ 等进阶内容、9.8 的面试题；
  • 别跳过：9.2 的方法论——它比三个项目本身更保值。

学习目标：读完本阶段你能

  1. 独立完成一个前后端 + 数据库的最小闭环项目并跑通联调；
  2. 给项目加上用户体系（注册/登录/JWT）并部署到公网；
  3. 在项目中实际使用缓存、事务、消息队列，并说出"为什么这里要用"；
  4. 用 STAR 法则把自己的项目讲成一段有说服力的面试经验。

9.2实战方法论

三个项目为什么这样设计

难度递进，每个项目只引入一层新复杂度：

对应关系：TODO 练阶段 3+4 的最小组合；博客把阶段 7 的安全与阶段 5 的部署接进来；商城把阶段 4 的 Redis 与阶段 6 的系统设计真正用上。每个项目结束时，你都应该能回答"这一层复杂度解决了什么问题"。

四条节奏原则

  1. 先跑起来：不要一开始死磕原理，先写个能跑的东西——能跑的最小版本比设计完美的空想有价值一百倍；
  2. 遇到问题再回头补：比如跨域报错了，再去看阶段 2 的跨域章节——带着问题学的知识留存率最高；
  3. 每周复盘：把本周踩的坑写进自己的笔记库（这个知识库就是范本）；
  4. 不要追求全学完：9 个阶段全部精学要一两年，先抓住主线（前端三件套 → Node → 数据库 → 一个上线项目）。

每个项目的统一节奏（重要，照做）：

  1. 花 30 分钟写下"功能清单 + 数据库表设计"，不写代码；
  2. 先做竖切：一个功能从前端到数据库完整打通（哪怕界面很丑）；
  3. 再横向铺开其他功能；
  4. 每完成一个功能就 git commit，写清"完成了什么"；
  5. 项目结束写一篇复盘：三个最难的坑 + 是怎么定位的。

9.3项目一：TODO 应用（1~2 周）

目标：跑通全栈最小闭环——前端能发请求、后端能收请求、数据库能存数据。别加花里胡哨的东西，把一个 TODO 的增删改查做完整就够了。

层技术练什么
前端HTML/CSS/原生 JS 或 React表单、列表渲染、fetch 请求
后端Node.js + Express写 CRUD 接口、路由、中间件
数据库SQLite 或 MySQL建表、增删改查 SQL
部署本地跑通即可前后端联调、跨域处理

第一步：接口先行（30 分钟）

写代码前先把接口定下来——这就是"契约先行"的最小实践：

方法路径作用请求体返回
GET/api/todos列表-[{id,title,done}]
POST/api/todos新建{title}新建的 todo
PUT/api/todos/:id改状态/改名{title?,done?}更新后的 todo
DELETE/api/todos/:id删除-{ok:true}

第二步：后端 30 行跑通

// server.js —— npm i express cors better-sqlite3
const express = require('express');
const cors = require('cors');
const Database = require('better-sqlite3');
const db = new Database('todo.db');
db.exec('CREATE TABLE IF NOT EXISTS todos (id INTEGER PRIMARY KEY, title TEXT, done INTEGER DEFAULT 0)');

const app = express();
app.use(cors());                       // 跨域：本地前后端端口不同（联调第一个坑，见 9.7）
app.use(express.json());

app.get('/api/todos', (req, res) => {
  res.json(db.prepare('SELECT * FROM todos ORDER BY id DESC').all());
});

app.post('/api/todos', (req, res) => {
  const { title } = req.body;
  if (!title || !title.trim()) return res.status(400).json({ error: 'title 必填' });  // 参数校验别省
  const info = db.prepare('INSERT INTO todos (title) VALUES (?)').run(title.trim());
  res.status(201).json({ id: info.lastInsertRowid, title, done: 0 });
});

app.put('/api/todos/:id', (req, res) => {
  const t = db.prepare('SELECT * FROM todos WHERE id = ?').get(req.params.id);
  if (!t) return res.status(404).json({ error: 'not found' });
  const done = req.body.done ?? t.done;
  db.prepare('UPDATE todos SET done = ? WHERE id = ?').run(done ? 1 : 0, t.id);
  res.json({ ...t, done });
});

app.delete('/api/todos/:id', (req, res) => {
  db.prepare('DELETE FROM todos WHERE id = ?').run(req.params.id);
  res.json({ ok: true });
});

app.listen(3000, () => console.log('API on http://localhost:3000'));

第三步：前端联调

async function loadTodos() {
  const res = await fetch('http://localhost:3000/api/todos');
  if (!res.ok) throw new Error('HTTP ' + res.status);   // fetch 对 4xx/5xx 不抛错，要自己判断！
  return res.json();
}
async function addTodo(title) {
  const res = await fetch('http://localhost:3000/api/todos', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },    // 不写这行，后端 req.body 是 undefined
    body: JSON.stringify({ title }),
  });
  return res.json();
}

验收清单（全部打勾才算完成）：增删改查四个接口都能从前端触发；刷新页面数据不丢（落库了）；后端控制台能看到请求日志；git log 里有清晰的提交记录。

9.4项目二：博客系统（3~4 周）

目标：引入用户体系、权限、登录、部署——从一个"本地玩具"变成一个"像模像样、别人能访问的网站"。

模块技术点对应前面哪个阶段
用户注册登录JWT、密码 bcrypt 哈希阶段3 后端 + 阶段7 安全
文章 CRUD数据库索引、分页阶段4 数据库
评论关联表查询阶段4
页面渲染服务端渲染或前端路由阶段2 前端
部署上线Nginx + 云服务器 + HTTPS阶段5+6 DevOps

第一步：数据库设计（三张表起步）

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  username TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL              -- 永远不存明文密码！
);
CREATE TABLE posts (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_posts_user ON posts(user_id);       -- 按作者查文章要用（08 阶段的索引知识）
CREATE TABLE comments (
  id INTEGER PRIMARY KEY,
  post_id INTEGER NOT NULL REFERENCES posts(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  content TEXT NOT NULL
);

设计思考：为什么密码要 bcrypt 而不是 MD5？（MD5 太快可被彩虹表撞库，bcrypt 故意慢且带盐）为什么评论单独建表而不是存在文章里？（一对多关系，独立表才能按人查、分页）——每张表都要能回答"为什么这么设计"。

第二步：注册登录与 JWT

// 注册：bcrypt 哈希后入库
const bcrypt = require('bcrypt');
app.post('/api/register', async (req, res) => {
  const hash = await bcrypt.hash(req.body.password, 10);   // 10 = salt rounds
  // INSERT INTO users ... 捕获唯一键冲突返回"用户名已存在"
});

// 登录：校验密码后签发 JWT
const jwt = require('jsonwebtoken');
app.post('/api/login', async (req, res) => {
  const user = /* 按用户名查 */;
  const ok = await bcrypt.compare(req.body.password, user.password_hash);
  if (!ok) return res.status(401).json({ error: '用户名或密码错误' });  // 别说"密码错误"，防用户名探测
  const token = jwt.sign({ uid: user.id }, process.env.JWT_SECRET, { expiresIn: '7d' });
  res.json({ token });
});

// 鉴权中间件：保护"写"接口
function auth(req, res, next) {
  const token = (req.headers.authorization || '').replace('Bearer ', '');
  try { req.uid = jwt.verify(token, process.env.JWT_SECRET).uid; next(); }
  catch { res.status(401).json({ error: '未登录或登录过期' }); }
}
app.post('/api/posts', auth, (req, res) => { /* req.uid 就是作者 */ });

第三步：部署上线（阶段 5/6 落地）

  1. 买一台最低配云服务器，按 09 模块装好 Node 与 Nginx；
  2. 代码上服务器（git pull），pm2 start server.js 守护进程；
  3. Nginx 80 端口反代 3000：前端静态文件直出、/api 转发后端（同域后跨域问题自动消失）；
  4. 用 Let's Encrypt 上 HTTPS；
  5. 配好防火墙只开 80/443/22。

验收清单：手机流量（不连家里 WiFi）能打开网站；注册→登录→发文→评论全流程可走；重启服务器后服务自动拉起（pm2）；密码库里查是哈希不是明文。

9.5项目三：商城简化版（4~6 周）

目标：把系统设计阶段学的东西用上——缓存、事务、消息队列、Docker。这次的重点不是"更多功能"，而是"同一功能在压力下怎么设计"。

功能用到的进阶技术设计要点
商品列表Redis 缓存热点商品、分页Cache Aside：先更库再删缓存（阶段 4 的一致性方案）
下单数据库事务、库存扣减UPDATE stock SET n=n-1 WHERE id=? AND n>0——用条件更新防超卖，而不是先查再改
下单后通知消息队列异步发短信接口只写"待发送"，MQ 消费者慢慢发——响应时间从 2s 降到 50ms
秒杀场景Redis 预扣库存、限流库存预热进 Redis，DECR 扣到负数直接拒绝，DB 只接收成功单
整体部署Docker Compose 一键起全套web/api/db/redis 四个服务一个 yaml

防超卖：三行 SQL 的进化史（面试金句素材）

-- ❌ 版本一：先查再改——并发下两个请求都读到 stock=1，都下单成功，超卖！
const s = db.prepare('SELECT stock FROM goods WHERE id=?').get(id);
if (s.stock > 0) db.prepare('UPDATE goods SET stock=stock-1 WHERE id=?').run(id);

-- ✅ 版本二：条件更新，靠数据库行锁保证原子
UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0;
-- 影响行数为 0 = 库存不足，下单失败

-- ✅ 版本三：高并发加 Redis 预扣，DB 只接成功单
const left = await redis.decr('stock:' + id);
if (left < 0) { await redis.incr('stock:' + id); return '已售罄'; }  // 回补误扣
await createOrder(...);   // 只有 Redis 扣成功的才写 DB
⚠️ 这一阶段不追求完美，重点是把"书本上的概念"亲手敲一遍、踩一遍坑——比如你会真实体验到"Redis 扣成功了但写 DB 失败"的一致性问题，这正是阶段 4 讲的内容变成你自己的过程。

9.6学习节奏与复盘

节奏曲线不是直线上升：做项目 → 卡住 → 补底层 → 继续，是常态。卡住不代表方法错了，卡住就是学习正在发生。

每周复盘模板（直接抄）

  1. 本周完成了什么：可演示的功能（不是"看了什么"）；
  2. 三个最难的坑：现象、怎么定位的、根因、修复——写成小短文；
  3. 下周计划：具体到"完成 XX 接口"而不是"继续开发"；
  4. 一个问题：本周最想搞懂但没搞懂的一个点，列为下周第一优先级。

9.7常见坑 & Debug

三个项目里新手必踩的坑，统一"现象 → 根因 → 修复 → 规避"。

坑 1：前端请求后端报 CORS 跨域错误

  • 现象：控制台 CORS policy: No 'Access-Control-Allow-Origin' header，请求根本没到业务逻辑；
  • 根因：浏览器同源策略——前端 5173、后端 3000 端口不同即不同源；
  • 修复：开发期后端 app.use(cors()) 或 Vite 配 proxy；上线后用 Nginx 同域反代，跨域自动消失；
  • 规避：开发期就配 proxy，别等部署才处理。

坑 2：POST 请求后端 req.body 是 undefined

  • 现象：前端明明发了 JSON，后端读 body 全是 undefined；
  • 根因：Express 不自带 body 解析——前端没设 Content-Type: application/json，或后端没挂 express.json()，两处缺一不可；
  • 修复：两侧都补上（见 9.3 代码注释）；
  • 规避：请求发不进去时，先在后端第一行打印 req.headers 看类型。

坑 3：密码明文入库

  • 现象：能登录，但数据库泄露时所有用户密码直接暴露；
  • 根因：注册时直接存了 req.body.password；
  • 修复：bcrypt 哈希（9.4 代码）；登录用 bcrypt.compare；
  • 规避：任何"凭据"入库前必过哈希，MD5 也不行（可撞库）。

坑 4：SQL 注入

  • 现象：登录框输入 ' OR '1'='1 竟然能登录；
  • 根因：SQL 字符串拼接 "SELECT * FROM users WHERE name='" + name + "'"；
  • 修复：全部用参数化查询（占位符 ?，见 9.3 代码）——值永远不参与 SQL 解析；
  • 规避：code review 看到 SQL 拼接直接打回。

坑 5：fetch 对 404/500 不报错

  • 现象：接口明明返回 500，前端却走进了成功分支，拿到一堆难懂的 HTML；
  • 根因：fetch 只在网络层失败时 reject，HTTP 错误状态码要自己判断；
  • 修复：封装统一请求函数，if (!res.ok) throw（见 9.3 代码）；
  • 规避：全项目只允许通过封装的请求函数发请求。

坑 6：上完线才发现没配环境变量

  • 现象：本地好好的，上线 JWT 校验全部失败；
  • 根因：process.env.JWT_SECRET 在服务器上没配置，sign 与 verify 用的 secret 不一致；
  • 修复：服务器配 .env（不入库！加进 .gitignore），启动时注入；
  • 规避：所有环境相关配置（密钥/连接串）一律走环境变量，代码里不许出现明文。

9.8重点讲解

Q1：面试让你"讲一个你做过的项目"，怎么讲？

参考答案（STAR 骨架，以博客系统为例）：

S 情境：为了把全栈知识串成完整产品，独立开发并上线了一个多用户博客系统，覆盖注册登录、发文、评论与部署。
T 任务：重点解决三件事——用户密码与鉴权安全、文章列表的分页性能、从零到公网可访问的完整部署。
A 行动：密码用 bcrypt 加盐哈希；鉴权用 JWT + 中间件统一拦截写接口；文章列表对 author_id 建索引并做分页；部署用 pm2 守护 + Nginx 反代 + HTTPS。
R 结果：网站公网稳定运行；最大的收获是踩了跨域、body 解析、环境变量三个坑并沉淀了排查方法（对应 9.7）。

要领：面试官追问的一定是 A 里的技术细节——每个技术点都要能往下讲两层"为什么"。

Q2：三个项目做下来，你觉得"最难的部分"是什么？怎么回答？

参考答案：不要说"都不难"（不真诚）也不要说某个报错（格局小）。推荐结构："把各阶段知识在真实约束下组合起来最难——比如防超卖，单独看是一条 SQL，但放进秒杀场景就要同时考虑 Redis 预扣、DB 事务、消息补偿三层的失败组合。我的解法是先保证单点正确（条件更新），再逐层往上叠加（Redis 预扣），并明确每一层的失败补偿策略。"——展示的是组合与权衡能力。

Q3：项目里你只用 Node，为什么面试常被问 Java/Spring？

参考答案：诚实回答 + 展示迁移能力："我主力用 Node，但后端的核心问题——鉴权、事务、缓存、部署——是语言无关的，我在 Node 里都实际处理过。Spring 的 IoC/AOP 我也系统学过（07 模块），比如依赖注入解决的问题是共通的，只是实现机制不同（运行时反射 vs JS 的闭包与模块）。"然后把话题引回你熟悉的场景设计。

Q4：自测 5 问

  1. TODO 项目的四个接口，方法与路径分别是什么？为什么列表用 GET、新建返回 201？
  2. bcrypt 相比 MD5 好在哪？"加盐"解决什么问题？
  3. JWT 由哪三段组成？放在哪里面传输？过期了怎么处理？
  4. 防超卖为什么"先查再改"不行？条件更新与 Redis 预扣各自适用什么量级？
  5. 下单接口为什么要用消息队列发通知？不用会怎样？
