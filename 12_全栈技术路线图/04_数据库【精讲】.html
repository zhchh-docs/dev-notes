4.1简介与阅读指引

定位

数据库阶段的重点是两件事：把 SQL 写得又对又快（MySQL 的索引与事务），以及用缓存扛住流量（Redis 的结构与策略）。这一阶段的知识直接决定你的系统"能跑"还是"能扛"，也是后端面试的最高频考区。

痛点

多数初学者的数据库认知停在"会写 CRUD"：不知道为什么加了索引还是慢、不知道并发下两个事务会互相干扰、不知道缓存能挡住什么也挡不住什么。结果就是——数据量一上来页面超时，一上并发数据就错。

  • 08 模块《MySQL》与《Redis缓存》是本篇的展开版，路线图篇讲主干、专篇讲全量。

4.2事务与并发控制

事务 ACID：不只是四个名词

事务把一组操作绑成一个原子执行单元，要么全成功，要么全回滚。四个特性各自有明确的实现机制——答出机制才算懂：

特性含义靠什么实现反面例子
A 原子性事务里的操作要么全做，要么全不做undo log（回滚日志）：每步修改前先记旧值，回滚时逆序恢复扣款成功、加款失败——没有原子性时钱会凭空消失
C 一致性事务前后数据库约束不被破坏AID 三者共同保证 + 业务约束（唯一键、外键、触发器）转账后双方总额变了——一致性被破坏
I 隔离性并发事务互相看不见对方中间状态锁 + MVCC（见下）读到别人改了一半的数据
D 持久性提交后数据永久保存，宕机不丢redo log（重做日志）：先写日志再刷盘，WAL 机制提交成功后断电，数据丢了
💡 经典例子：转账 A 扣 100、B 加 100。如果 A 扣完数据库崩了，事务回滚（undo log），A 没扣成功，B 也没加——钱不会凭空消失。为什么崩了也不丢已提交的数据？因为提交时 redo log 已经落盘（WAL：先写日志再刷数据页）。

隔离级别：并发正确性与性能的交换

隔离级别越高，并发越安全，但并发性能越低。MySQL 默认是 RR（可重复读）。三种并发异常先看懂现象：

隔离级别脏读不可重复读幻读
读未提交 RU会会会
读已提交 RC不会会会
可重复读 RR（默认）不会不会MySQL 基本解决
串行化不会不会不会
  • 脏读：读到别的事务还没提交的数据，它回滚了你就读了个假数据——比如看到"余额 50"据此下单，结果对方回滚了。
  • 不可重复读：同一事务内，两次读同一行结果不一样（被别人改了并提交）——影响"读-计算-写回"类逻辑。
  • 幻读：同一事务内，两次按条件范围查，行数变了（被别人插入/删除）——影响"统计后批量操作"类逻辑。
为什么 RR 能基本解决幻读：快照读靠 MVCC（读启动时的快照，别人插入的你根本"看不见"）；当前读（select ... for update）靠间隙锁锁住范围。两种读混用时仍可能出现幻读现象——这是面试的深水区，见 4.8。

MVCC：读写不互相阻塞的秘密

MVCC（多版本并发控制）让读操作读快照、写操作才加锁，读写互不阻塞。靠三个东西实现：

💡 为什么能可重复读：事务启动时生成一个 Read View，整个事务期间都用这同一个视角看数据，所以同一事务内两次读结果一样——就算别的事务提交了，你看到的还是启动时的快照。RC 与 RR 的唯一区别：RC 每条查询都生成新 Read View，RR 整个事务共用一个。

4.3索引原理与 SQL 优化

聚簇索引 vs 二级索引：回表是怎么发生的

阶段1 画过 B+ 树结构，这里讲两种索引的区别和"回表"——这是 SQL 优化的第一原理：

聚簇索引（主键）二级索引（普通索引）
叶子节点存什么整行数据主键值
查一行要几步1 次树查找先查二级索引拿主键，再回主键索引查整行 = 回表
数量每表一个（数据本身按它组织）可以多个

联合索引与最左前缀

建了联合索引 (a, b, c)，B+ 树先按 a 排序，a 相同再按 b，b 相同再按 c——本质是"字典先按首字母、再按第二字母排序"。查询必须从最左列开始才能用上索引：

查询条件能否用上 (a,b,c)原因
where a=1能，用 a满足最左前缀
where a=1 and b=2能，用 a,b连续命中
where a=1 and b=2 and c=3能，全用完整匹配
where b=2❌ 索引失效跳过 a，B+ 树无法定位
where a=1 and c=3只能用 ab 断了，c 无法连续使用

设计启示：把等值查询最频繁的列放最左；范围查询列放最后（范围之后的列都用不上）；(name, age) 顺序的索引对 where age=? 无效。

EXPLAIN 实操：用执行计划代替猜测

优化 SQL 的第一步永远是看执行计划，不是凭感觉：

EXPLAIN SELECT * FROM orders WHERE user_id = 1 AND status = 'PAID';

-- 重点看四列：
-- type: 访问类型。system > const > eq_ref > ref > range > index > ALL
--        ALL = 全表扫描，出现就要警惕
-- key:  实际用到的索引（NULL = 没用上）
-- rows: 预估扫描行数（越小越好，配合表数据量判断）
-- Extra: Using index（覆盖索引，最理想）
--        Using filesort（额外排序，考虑索引覆盖 ORDER BY）
--        Using temporary（临时表，GROUP BY 常见，需优化）

索引失效的六大场景（每条都能在 EXPLAIN 里看到）

  1. 对索引列用函数或运算：WHERE DATE(create_time)='2026-01-01'——改写成范围查询 >= '2026-01-01' AND < '2026-01-02'；
  2. 隐式类型转换：字段是 varchar，查询传数字 WHERE phone = 13800000000——加引号；
  3. 违反最左前缀（见上表）；
  4. like 前导通配：LIKE '%Tom'——业务允许就改成后缀匹配 'Tom%'，或用倒排索引（ES）；
  5. or 连接了非索引列——拆成两条 union 或给 or 的列都建索引；
  6. 优化器判断全表更快——数据量小、区分度低（如性别列）时这是正确行为，别强建索引。
💡 覆盖索引：如果查询的字段正好都在索引里，就不用回表。比如联合索引 (name, age)，查 SELECT name, age FROM user WHERE name='Tom' 直接从索引返回——EXPLAIN 的 Extra 显示 Using index。这就是"select 别随手写 *"的原理依据。

4.4Redis 数据结构与缓存模式

五种数据结构：每种都有它的"专属场景"

用对结构比背命令重要——多数 Redis 性能问题源于"所有东西都存 String"：

结构常见用途底层典型场景举例
String缓存对象、计数器、分布式锁SDS 动态字符串INCR article:1:views 文章计数
Hash存对象（用户信息）压缩列表 / hashtableHSET user:1 name Tom age 25 单字段更新不整存整取
List消息队列、最新列表quicklistLPUSH + LTRIM 保留最新 N 条动态
Set去重、共同好友哈希表 / 整数集合SINTER 求共同关注
ZSet 有序集合排行榜、延迟队列跳表 + 哈希表ZINCRBY + ZREVRANGE 实时排行榜
💡 Redis 是内存数据库，读写纳秒级，适合做缓存、计数器、排行榜、分布式锁。不适合：大 value（超过 10KB 考虑拆分）、需要复杂查询的数据（那是关系库的活）。

缓存与数据库一致性：先更库还是先删缓存

方案流程问题适用
先更库再删缓存（Cache Aside）update DB → del cache删除失败或并发读写瞬间不一致绝大多数业务（默认选它）
延迟双删del cache → update DB → 睡 500ms → 再 del降低不一致窗口，但延迟值难定读多写多、容忍秒级不一致
订阅 binlog（Canal）DB 变更异步同步删缓存引入组件与延迟一致性要求高、写后立刻被读
💡 为什么是"删缓存"而不是"更新缓存"：并发写时更新缓存可能把旧值后写覆盖新值；删除则让下次读自然回源，简单且不会覆盖错。绝大多数业务，「先更库再删缓存」+ 合理过期时间就够了，不要追求强一致，成本太高。

4.6最小可运行实验

两个动手实验：一个是"亲眼看见"隔离级别的差异，一个是"亲眼看见"索引把扫描行数从全表降到 1。

实验一：复现"不可重复读"（MySQL）

-- 终端 A 和终端 B 各开一个 mysql 客户端，都执行：
SET autocommit = 0;

-- A：第一次读
SELECT balance FROM account WHERE id = 1;        -- 1000

-- B：改钱并提交
UPDATE account SET balance = 500 WHERE id = 1;
COMMIT;

-- A：第二次读
SELECT balance FROM account WHERE id = 1;
-- RR（默认）：仍是 1000 —— 可重复读，Read View 没变
-- 切到 RC（SET SESSION transaction_isolation = 'READ-COMMITTED'）再试：读到 500
--   —— 这就是"不可重复读"

-- A：确认与提交
COMMIT;

观察点：把隔离级别在 RR 与 RC 之间切换，同样的操作序列结果不同——隔离级别不是背出来的，是跑出来的。

实验二：EXPLAIN 前后对比（MySQL）

-- 准备 10 万行测试数据后：
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- 无索引：type=ALL，rows≈100000（全表扫描）

ALTER TABLE orders ADD INDEX idx_user (user_id);

EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type=ref，rows≈几十 —— 索引生效

-- 再验证覆盖索引：
EXPLAIN SELECT user_id, status FROM orders WHERE user_id = 42;
-- 建联合索引 idx_user_status (user_id, status) 后：
-- Extra 出现 "Using index" —— 不回表

实验三：缓存穿透模拟（Redis）

// 恶意请求 id = -1（库里永远不存在）
for (let i = 0; i < 10000; i++) {
  const v = await redis.get('user:-1');   // 永远 null
  if (!v) await db.query('SELECT * FROM user WHERE id = -1');  // 10000 次全打 DB！
}

// ✅ 修复：缓存空值 + 短过期
const v = await redis.get('user:-1');
if (v === 'NULL_PLACEHOLDER') return null;          // 空值标记，挡住后续请求
if (v) return JSON.parse(v);
const row = await db.query('...');
if (!row) {
  await redis.set('user:-1', 'NULL_PLACEHOLDER', 'EX', 60);  // 只挡 60s，防长期占用
  return null;
}
await redis.set('user:-1', JSON.stringify(row), 'EX', 3600);

4.7常见坑 & Debug

按"现象 → 根因 → 修复 → 规避"整理本阶段五大坑，前三条就是缓存三大问题的落地形态。

坑 1：缓存穿透——恶意 id 打穿 DB

  • 现象：DB 的 CPU/连接数异常飙升，日志里全是查同一个不存在的 id；
  • 根因：不存在的 key 永远不会进缓存，每次都回源；
  • 修复：缓存空值（短过期）+ 布隆过滤器拦截（代码见 4.6 实验三）；
  • 规避：入参校验（id <= 0 直接拒绝）+ 对异常流量限流。

坑 2：缓存击穿——热点 key 过期的瞬间

  • 现象：某接口平时 QPS 平稳，每隔 N 秒（=过期时间）出现一次延迟毛刺与 DB 查询尖峰；
  • 根因：热点 key 过期瞬间，所有并发请求同时回源（缓存没挡住任何请求）；
  • 修复：互斥锁重建——抢到锁的一个请求回源，其他请求短暂等待后读新缓存：
const val = await redis.get(key);
if (val) return JSON.parse(val);
// 抢互斥锁：只有一个人去重建缓存
const ok = await redis.set('lock:' + key, '1', 'NX', 'EX', 5);
if (ok) {
  try {
    const row = await db.query('...');
    await redis.set(key, JSON.stringify(row), 'EX', 3600);
    return row;
  } finally { await redis.del('lock:' + key); }
} else {
  await sleep(50); return getWithCache(key);   // 别人重建好了，重读
}
  • 规避：极热点 key 设"逻辑过期"（value 里带过期时间，过期后异步刷新，业务永远读得到）。

坑 3：缓存雪崩——同一批 key 同时过期

  • 现象：整点刚过 DB 压力陡增——很多缓存是同一个批量任务写入、过期时间相同；
  • 根因：批量写入时统一 EX 3600，一小时后集体过期；
  • 修复/规避：过期时间加随机抖动 EX 3600 + random(0, 600)；核心数据多级缓存（本地 + Redis）+ DB 侧限流兜底。

坑 4：分布式锁误删——A 把 B 的锁删了

  • 现象：偶发性出现两个实例同时执行"应该互斥"的任务；
  • 根因：A 的业务执行超过锁过期时间，锁自动释放后被 B 抢到；A 执行完后直接 DEL，删掉的是 B 的锁；
  • 修复：value 存唯一随机值，删锁用 Lua 保证"判断是自己的 + 删除"原子执行：
// 加锁：value 用随机值（标识"是我的锁"）
SET lock:order:123 8f3a... NX EX 10

// 解锁：必须原子——先比对 value 再删（Lua 脚本）
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
  • 规避：业务执行时间不可预估时用 Redisson 看门狗（默认 30s，每 10s 自动续期），不自己猜过期时间。

坑 5：改了数据库缓存没更新——读到旧值

  • 现象：后台改了数据，前台页面半天不更新；重启 Redis 才好。
  • 根因：写路径只更了 DB，没动缓存（或先删缓存后更库，删除后到更新前的读请求把旧值又填回缓存）。
  • 修复：统一走"先更库、再删缓存"（Cache Aside），删除失败要重试或进消息队列补偿。
  • 规避：读写路径收敛到统一的缓存访问层，禁止业务代码直接操作缓存；过期时间作为最后兜底。

4.8重点讲解【进阶】

五道高频题，答案按"结论 → 原理 → 延伸"展开。

Q1：为什么 MySQL 用 B+ 树而不用 B 树 / 哈希表？

参考答案：

vs 哈希表：哈希只能等值查询，不支持范围查询与排序（WHERE age > 18、ORDER BY 全靠遍历）——而范围查询是业务最常见的需求。B+ 树叶子节点天然有序且用链表串联，范围查询就是顺着链表扫。

vs B 树：B 树的数据存在所有节点上，单节点容纳的键少、树更高，一次查找要更多磁盘 IO。B+ 树非叶子节点只存键不存数据，同样 16KB 的页能放更多键，3~4 层就能撑千万级数据——即一次查询最多 3~4 次磁盘 IO。另外叶子链表也天然支持范围扫描。

延伸：这也是为什么主键要自增——自增主键的插入总在树的最右侧，顺序写不分裂页；用随机 UUID 做主键会导致频繁页分裂与碎片。

Q2：RR 隔离级别下到底有没有幻读？

参考答案：分两种读，答案不同。

快照读（普通 SELECT）：靠 MVCC，读的是事务启动时的 Read View，别的事务插入的行对你不可见——没有幻读。

当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）：读的是最新已提交数据，靠间隙锁 + 行锁（Next-Key Lock）锁住范围，阻止别人在范围内插入——也没有幻读。

会出现幻读现象的场景：同一事务先快照读、再当前读——两次读到的行数不同。例如先 SELECT（快照，3 行）再 SELECT ... FOR UPDATE（当前读，4 行，别人插入并提交的那行出现了）。严格说这属于"快照读与当前读切换导致的不一致"，InnoDB 已经在各自范围内防住了幻读。

延伸：这也是为什么"一个事务里混用普通读和锁定读"要格外小心——要么全程当前读，要么先 FOR UPDATE 再读。

Q3：缓存与数据库的一致性，为什么是"删缓存"而不是"更新缓存"？为什么先更库？

参考答案：

为什么不更新缓存：并发写时序问题——线程 1 更新缓存为 100，线程 2 更新缓存为 200，但 DB 里的顺序可能是反的（线程 2 先写库、线程 1 后写库），最终缓存 100 与 DB 200 不一致且永远不自愈。删除缓存则没有覆盖问题：下次读自然回源写回正确值。

为什么先更库再删缓存：反过来"先删缓存再更库"的窗口更大——删除后、更新前，读请求把旧值读回缓存，而更新 DB 之后没人再删它，旧值会一直呆到过期。

先更库再删缓存仍有的小概率不一致：读请求在旧值时代回源（缓存未命中），读到旧值；此时写请求更库+删缓存完成；读请求才把旧值写入缓存。概率低（要求"读比写慢"），加过期时间兜底即可；要求更高就上延迟双删或 binlog 订阅（4.4 表格）。

延伸：追求强一致的正确姿势是分布式锁串行化读写——但那会杀死缓存的意义。工程上永远先问："这个场景能容忍多久的不一致？"

Q4：Redis 为什么快？单线程为什么还这么快？

参考答案：四个原因。①纯内存操作——没有磁盘 IO，读写纳秒级；②高效数据结构——SDS、跳表、压缩列表都是为内存与访问模式定制（对比 MySQL 的 B+ 树是为磁盘页设计）；③单线程无锁竞争——命令执行没有上下文切换与死锁问题（6.0 后 IO 多线程只用于网络读写，命令执行仍单线程）；④IO 多路复用——epoll 让单线程同时监听大量连接。

延伸：单线程也意味着慢命令会阻塞一切——KEYS *、大 key 删除、一次操作百万级成员的 ZSet 都会卡住整个实例，生产环境用 SCAN 代替 KEYS、用 UNLINK 代替 DEL。

Q5：RDB 和 AOF 怎么选？

参考答案：先理解两者机制，再按"丢多少能接受"选。

RDB 快照AOF 日志
原理定时把内存数据 dump 成二进制文件每条写命令追加到日志
恢复速度快（直接加载二进制）慢（重放命令）
数据安全可能丢最后一次快照后的数据丢更少（everysec 最多丢 1 秒）
文件体积小大（需重写压缩）

选择逻辑：纯缓存（丢了回源重建）→ RDB 甚至不开持久化；数据重要 → AOF everysec；两者都要 → 混合持久化（4.0+）：AOF 重写时把当前数据存成 RDB 格式、增量继续写 AOF——恢复快且丢得少，生产环境的一般选择。

延伸：RDB 的 fork 在大内存实例上可能造成毫秒级卡顿；AOF 重写同样 fork——大实例要挑低峰期。
