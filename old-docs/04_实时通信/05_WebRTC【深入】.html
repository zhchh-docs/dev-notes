WebRTC 实时通信

深入 定位：浏览器原生 P2P 实时音视频——用一套 JS API 取代插件与流媒体服务器转发

WebRTC（Web Real-Time Communication）是 W3C/IETF 标准化的浏览器原生实时音视频框架，提供 getUserMedia 采集、RTCPeerConnection 建连、DTLS/SRTP 加密传输与 JitterBuffer 抖动缓冲，端到端延迟可压到亚秒级。本页从 PeerConnection/SDP 协商/ICE 候选讲到接收渲染与 getStats 质量统计，并以 2020-2022 年主导的 WebRTC 无插件播放器（Vue2+Janus+Canvas，把变电站监控从 ActiveX 插件迁移到浏览器原生低延迟直播）这条真实链路收尾。

1简介与阅读指引

1.1 定位：浏览器原生的实时音视频标准

WebRTC 是让浏览器直接做实时音视频与数据传输的开源标准（API 侧 W3C webrtc-pc、协议侧 IETF）。三大家族 API：getUserMedia()（采集）、RTCPeerConnection（建连与媒体传输）、RTCDataChannel（P2P 数据通道）。关键心智模型：WebRTC 本身不含信令服务器——浏览器怎么"认识彼此"要自己搭（WebSocket 都行），WebRTC 只管之后的媒体面。它消灭了 ActiveX 插件（绑定 IE/安全告警）与 HLS 的 3-30s 延迟：浏览器直接拿 SRTP 加密包，端到端 200-500ms。代价：把 NAT 打通/编解码协商/质量保障的复杂度暴露成前端要懂的协议细节。

1.2 横向对比与架构取舍

  • vs 插件方案：零安装跨浏览器 vs 每机重装插件过审计——去插件化是本项目改造的核心动机；
  • vs HLS/HTTP-FLV：延迟硬指标决定取舍——看回放用 HLS（CDN 生态），实时看现场用 WebRTC（强依赖 UDP，企业网封 UDP 要靠 TURN 中继）；
  • 关键P2P vs SFU：浏览器对浏览器是真 P2P；但监控是"多路源 × N 观看者"，P2P 会让源端带宽爆炸——正确做法是中间架 SFU（只转发不混流），各端只和 SFU 建一条连接——本项目选 Janus 的原因（06 篇）。

1.3 学习目标与阅读指引

  1. 吃透 RTCPeerConnection 状态机与 offer/answer 协商；
  2. 理解 ICE/STUN/TURN 找路与兜底；DTLS-SRTP 加密链；
  3. 掌握接收端 recvonly 标准写法（本篇中心代码）；
  4. 用 getStats 做质量可观测与自愈；
  5. 避开六条高频坑。

前置知识：01 篇协议栈、02 篇 WebSocket（信令）。难度：★★★★☆。本篇不涉及：Janus 服务端细节（06 篇）。

2核心模型

八个核心模型：RTCPeerConnection（总纲）→ MediaStream/Track→ SDP→ ICE→ STUN/TURN→ DTLS-SRTP→ 信令→ getStats。

2.1 RTCPeerConnection：严格状态机

WebRTC 核心对象，抽象"一条到对端的实时连接"，内部聚合四件事：本地/远端 SDP、ICE 代理（找路）、DTLS 握手（密钥协商）、SRTP 传输栈+JitterBuffer。不碰 DOM——产出 MediaStreamTrack 要挂 video 或喂 Canvas。坑它是状态机（new→have-local-offer→stable…），状态乱跳就是"协商失败"的根源。

2.2 MediaStream 与 Track

MediaStream 是"一组轨"容器，每根 Track 一路视频/音频（kind/id/enabled）；接收侧 pc.ontrack 拿远端轨，video.srcObject = event.streams[0] 即播。本项目做法：不用 video 黑盒，把视频轨绘到 Canvas——叠加监控 OSD（时间戳/通道名/状态字）并统一多路绘制节奏。

2.3 SDP：一段文本描述，交换即协商

描述编解码（m=video 行 payload type、a=rtpmap/fmtp 的 H.264 profile）、媒体端口、加密 fingerprint、ICE 凭据；offer 列自己会的、answer 从交集选最终参数。要点：offer/answer 必须一次完整往返才进 stable，中途改要走重协商。

2.4 ICE：NAT 后找一条能通的路

收集候选：host（本机网卡）/srflx（STUN 反推公网映射）/relay（TURN 中继）；候选经信令互发，对每个候选对做 STUN 连通性检查，按优先级选第一个打通的；对称型 NAT 打洞失败回落 TURN 中继。

2.5 STUN 与 TURN

STUN：轻量反问"我公网地址是啥"（RFC 5389）；TURN：打不通时中继转发（RFC 5766，生产用 coturn），代价是带宽与延迟。判断走没走中继：getStats 看 selected pair 的 candidateType——host/srflx 直连、relay 中继。

2.6 DTLS-SRTP：强制加密

SDP 附证书指纹 → DTLS 1.2 握手协商会话密钥 → 用它把 RTP 加密成 SRTP（AES+认证）。坑时钟漂移/证书过期/NAT 会话超时导致 DTLS 断——是"看几分钟黑一下"的高频根因，需 ICE 重启恢复。

2.7 信令：规范故意不规定

交换 SDP/ICE 候选要应用自己搭——工程惯例几乎都用 WebSocket。一条完整信令链：创建会话句柄 → attach streaming 插件 → getoffer → setRemoteDescription → createAnswer → 回传 answer → 逐个互传 trickle ICE candidate。

2.8 getStats：唯一的定量质量接口

inbound-rtp（framesReceived/freezeCount/jitter/packetsLost）、candidate-pair（当前链路与 RTT）、track（framesDecoded/Dropped）——用它做质量看板与自动降级，不靠用户主观反馈。

3核心用法（按场景）

3.1 场景一：接收型 PeerConnection（中心代码）

// 接收场景：本端不发，只收 Janus 的流。方向用 direction 控制，不是靠 addTrack。
var pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' }
  ]
});

// 关键：声明"我这端只收不发"；若走默认 sendrecv，本端被要求发流（往往要先 getUserMedia
// 采集摄像头，无设备的值班机就报错/弹权限框）
pc.addTransceiver('video', { direction: 'recvonly' });
pc.addTransceiver('audio', { direction: 'recvonly' });

// 远端轨到达：挂到 video 或喂 Canvas
pc.addEventListener('track', function (ev) {
  var stream = ev.streams[0] || new MediaStream([ev.track]);
  videoEl.srcObject = stream;          // 或：drawToCanvas(ev.track, canvas)
});

// trickle ICE：候选一来就发给 Janus
pc.addEventListener('icecandidate', function (ev) {
  if (ev.candidate) wsSend({ janus: 'trickle', candidate: ev.candidate });
});

addTrack vs addTransceiver：addTrack 需要传入本端 track（通常来自 getUserMedia）并协商成 sendrecv——纯接收端没有本地流；正确做法是 addTransceiver 显式 recvonly，这是"只看不发"播放器的标准写法。

3.2 场景二：answer 端完整协商循环

async function handleRemoteOffer(offerSdp) {
  await pc.setRemoteDescription(new RTCSessionDescription({
    type: 'offer', sdp: offerSdp
  }));
  var answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);   // setLocal 后才开始收集 ICE 候选
  wsSend({ janus: 'answer', sdp: pc.localDescription.sdp });
}
// 收到对端 candidate：
async function addRemoteCandidate(cand) {
  try { await pc.addIceCandidate(new RTCIceCandidate(cand)); }
  catch (e) { /* 候选到达过早/过晚，忽略，不影响整体 */ }
}

3.3 场景三：Canvas 绘制视频轨（OSD 叠加）

var ctx = canvas.getContext('2d');
function drawLoop() {
  // video 元素只是"解码后的帧容器"，可见性隐藏；这里把它的当前帧贴到 Canvas
  ctx.drawImage(videoEl, 0, 0, canvas.width, canvas.height);
  // 叠加 OSD：通道名 + 时间戳，随画面缩放自动对齐
  ctx.fillStyle = 'rgba(0,0,0,.45)';
  ctx.fillRect(0, 0, canvas.width, 22);
  ctx.fillStyle = '#7CFC00';
  ctx.font = '13px monospace';
  ctx.fillText('CH-01 ' + new Date().toLocaleTimeString(), 8, 16);
  requestAnimationFrame(drawLoop);
}
videoEl.addEventListener('loadedmetadata', drawLoop);

3.4 场景四：getStats 质量量化与中继判断

setInterval(function () {
  pc.getStats().then(function (report) {
    report.forEach(function (r) {
      if (r.type === 'inbound-rtp' && r.kind === 'video') {
        // framesDecoded 持续增长但 freezeCount 涨 → 卡；packetsLost 高 → 网络差
        console.log('解码帧:', r.framesDecoded, '冻帧:', r.freezeCount,
                    '丢包率:', r.packetsLost / (r.packetsReceived || 1));
      }
      if (r.type === 'candidate-pair' && r.selected) {
        // localCandidateType: host/srflx=直连, relay=TURN 中继
        console.log('当前链路:', r.localCandidateType, '→', r.currentRoundTripTime, 's');
      }
    });
  });
}, 2000);

4进阶知识点【进阶】

首次学习可整章跳过。前置：协商循环与 getStats 已会用。

4.1 多路同屏的 CPU 优化：池化 + 降帧

多路同屏的 CPU 压力主要来自解码与 Canvas 上屏，而不是网络。手段：①池化渲染——每路一个 pc，但渲染共用池化的 video+Canvas，不每路新建 DOM（GPU 上下文有限）；②降帧——不需要满帧率的小窗降到 15fps（requestAnimationFrame 节流绘制）；③复用同一个 Canvas 上下文，多路绘制收敛到一个 rAF 循环。

4.2 质量自愈状态机

getStats 采样（2s）→ 规则判断 → 自愈动作：freezeCount 涨+丢包>5% 连续 3 次 → 发 PLI 请求关键帧；RTT>0.6s 或链路 relay → restartIce()。把"偶发花屏"从人肉反馈变成自动恢复——这是监控 7×24 场景的刚需。

4.3 renegotiation 与动态切流

中途换源/加轨触发 onnegotiationneeded 增量重协商（仍是一轮 offer/answer，状态机不变）；切通道的正确姿势：复用 pc 走重协商 vs 销毁重建 pc——频繁切换用重协商，长期换源重建更干净。

4.4 DataChannel 的非媒体用途

RTCDataChannel 走 SCTP（可靠/不可靠可配，maxRetransmits/ordered），P2P 低延迟传任意数据——协作白板、游戏状态同步、大文件 P2P 分片；与 WebSocket 对比：不经服务器中转（P2P 打通时），延迟更低但穿越失败率更高。

4.5 WHEP 与标准化拉流

传统接入要自定义信令协议（Janus JSON）；WHEP（WebRTC-HTTP Egress Protocol）用标准 HTTP POST 交换 SDP 拉流——"一个 URL 就能播"，正在成为播放器接入的标准化方向；推流对应 WHIP。新选型可优先支持 WHEP 的媒体服务器。

6最小可运行 Demo

性质：真实实战——变电站监控去插件化改造（2020-2022）：ActiveX→浏览器原生 WebRTC；7×24 常驻值班多路同屏；后被 Qiankun 整合为子应用。

6.1 落地设计：SFU + recvonly + Canvas 三选

  • 弃 P2P 选 SFU：多路源 × 多观看者，P2P 打爆源端带宽——流进 Janus streaming 插件，浏览器 answer 端拉流；
  • recvonly：只收不发，避免无摄像头值班机建连失败与权限弹框；
  • Canvas 渲染：解码帧 drawImage + OSD 叠加，多路绘制收敛一个 rAF 循环。

6.2 多路同屏与质量自愈（关键实现）

// 多路同屏：每一路一个 pc，但渲染共用池化的 video + Canvas，避免每路新建 DOM
function createPlayer(channelId, canvas) {
  var pc = new RTCPeerConnection({ iceServers: STUN_TURN });
  pc.addTransceiver('video', { direction: 'recvonly' });   // 只收不发，别用默认 sendrecv
  var hiddenVideo = document.createElement('video');
  hiddenVideo.muted = true; hiddenVideo.playsInline = true;
  pc.addEventListener('track', function (e) {
    hiddenVideo.srcObject = e.streams[0];
    hiddenVideo.play().catch(function () {/* 自动播放被拦：需用户手势解锁 */});
    bindDrawLoop(hiddenVideo, canvas, channelId);   // 进入统一 rAF 绘制池
  });
  return pc;
}
var lastFreeze = 0, badStreak = 0;
setInterval(async function () {
  var s = await collectStats(pc);
  if (s.freezeCount - lastFreeze > 0 && s.lossRate > 0.05) {
    badStreak++;
    if (badStreak >= 3) { requestKeyframe(); badStreak = 0; }   // 丢参考帧→请求关键帧
  } else { badStreak = 0; }
  lastFreeze = s.freezeCount;
  if (s.rtt > 0.6 || s.linkType === 'relay') pc.restartIce();   // 链路劣化，ICE 重启
}, 2000);

6.3 踩坑记录（含量化对比）

  • 坑自动播放策略：带声音媒体需用户手势，muted 后仍偶发 play() reject——catch 后用户点击页面补一次 play；
  • 坑忘了 recvonly：第一版默认 sendrecv，打开页面弹摄像头权限、无摄像头值班机建连失败——改 recvonly 消失；
  • 坑企业网封 UDP：部分现场只能走 TURN relay——用 getStats 的 candidateType 监控中继路数，从无监控做到可见，超阈值扩容 TURN；
  • 坑GPU 上下文爆炸：多路每路新建 video+Canvas——改池化+降帧后稳住；
  • 坑PLI 不是浏览器直接发：要经信令告诉 Janus；restartIce() 必须配合新 offer/answer 才算完整重启。

6.4 成果与复盘

  1. 量化：彻底下线 ActiveX（零安装、审计取消插件项）；延迟从插件方案数秒压到约 300-500ms（估算）；4 路同屏普通办公机 CPU 可控；Qiankun 子应用独立部署；
  2. 协作：契约先行（信令消息表 create/attach/offer/answer/candidate/PLI）；按"单路打通→多路同屏→质量自愈→子应用封装"分迭代现场真机验证；
  3. 可复用经验：媒体面与信令面分离；接收端默认 recvonly；质量要可观测（getStats+规则自愈）。

7常见坑 & Debug

六条高频坑。

7.1 signalingState 状态机乱跳

现象：偶发 InvalidStateError（setLocalDescription）。原因：stable 之外再 createOffer/answer 未先 setRemote。正解：一次协商一轮完整往返；动态改走 onnegotiationneeded。

7.2 recvonly 漏设，纯接收页弹摄像头权限

原因：默认 sendrecv。正解：纯拉流端一律 addTransceiver(direction:'recvonly')，确认 offer/answer 方向一致。

7.3 trickle ICE 候选乱序到达

正解：addIceCandidate 包 try/catch 容忍过早到达；或先缓存候选等 setRemoteDescription 完成后批量补加。

7.4 HTTPS/localhost 限制

现象：http 页面 getUserMedia/RTCPeerConnection undefined。正解：生产必须 HTTPS（信令 wss）；本地调试 localhost。

7.5 UDP 被企业防火墙封死

现象：家里通、现场超时，getStats 一直没有 selected candidate-pair。正解：部署 coturn 配 relay 候选回落 TCP/TLS 中继；监控 relay 比例平衡成本与体验。

7.6 花屏 = 丢关键帧，而非网络"卡"

原因：H.264 帧间依赖，丢参考帧后到下个 IDR 才恢复。正解：getStats 丢包率自动触发 PLI/FIR（经 SFU）。

8重点讲解

Q1：WebRTC 建连的完整流程？信令为什么不在标准里？

参考答案：信令面（自研，通常 WebSocket）：交换 SDP offer/answer 与 trickle ICE 候选——标准故意不规定信令，因为应用场景千差万别（呼叫模式/房间模式/拉流模式各不同），只约定媒体协商与传输本身。媒体面建立：①setRemoteDescription(offer)→createAnswer→setLocalDescription（状态机一轮往返进 stable）；②trickle ICE：候选逐个互发，ICE 代理对候选对做 STUN 连通性检查选中最优链路（host/srflx 直连，失败回落 TURN relay）；③DTLS 握手用 SDP 指纹协商 SRTP 密钥；④对端开始发 SRTP 包，ontrack 触发渲染。心智模型：WebRTC 只管媒体面，信令面与"怎么认识彼此"全是应用的事。

Q2：ICE/STUN/TURN 三者的关系？怎么知道流量走了中继？

参考答案：ICE 是框架——收集三类候选（host 本机网卡/srflx 经 STUN 反推的公网映射/relay TURN 中继地址），候选对互做连通性检查按优先级选路；STUN 是工具——发包给 STUN 服务器看回包源地址，得知自己的 NAT 映射（打洞的前提）；TURN 是兜底——对称型 NAT 或防火墙封 UDP 时打洞必败，媒体回落 TURN 中继转发（生产用 coturn），代价是带宽与延迟。判别方法：getStats 里 selected candidate-pair 的 localCandidateType——host/srflx=直连、relay=中继；实战用它监控"多少路在 relay"，超阈值扩容 TURN。

Q3：为什么监控场景选 SFU 而不是 P2P？多路同屏怎么控 CPU？

参考答案：P2P 的带宽爆炸——N 路源 × M 个观看者，P2P 要求每路源与每个观看者各建一条连接，上行带宽 O(N×M)；SFU（只转发不混流）让源和每个观看者各只对 SFU 建一条连接，转发开销在服务端水平扩展——这是 Janus/mediasoup 一类网关的存在意义。多路同屏控 CPU：CPU 压力主要来自解码与 Canvas 上屏而非网络——①渲染池化（共用 video+Canvas，不每路新建 DOM，防 GPU 上下文爆炸）；②小窗降帧 15fps；③多路绘制收敛一个 rAF 循环。实战：4 路同屏普通办公机 CPU 可控。

  • MDN WebRTC API：developer.mozilla.org/zh-CN/docs/Web/API/WebRTC_API
  • W3C webrtc-pc 与 getStats 规范（w3c.github.io/webrtc-pc、webrtc-stats）；web.dev WebRTC 基础。

权威资料

  • WebRTC For The Curious（ICE/DTLS/SRTP 全链路正典）：webrtcforthecurious.com
  • RFC 8829 / 5389（STUN）/ 5766（TURN）；coturn：github.com/coturn/coturn；Janus 文档（06 篇配套）。

练习（按顺序做）

  1. 本机回环：两个 RTCPeerConnection 互连（getUserMedia 摄像头），跑通 offer/answer/trickle；
  2. chrome://webrtc-internals 观察 signalingState、候选对与 getStats 指标；
  3. 把回环改成 recvonly + 远端 canvas 绘制 + 2s getStats 采样打印。
