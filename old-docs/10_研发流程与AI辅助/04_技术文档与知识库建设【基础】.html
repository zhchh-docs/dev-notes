1简介与阅读指引

1.1 定位

本篇讲的是团队的知识基础设施：哪些东西必须写成文档、写成什么样、放在哪、怎么保证它不过期。目标是把"知识在个人脑子里"变成"知识在团队系统里"——让新人三天上手、让三个月前的决策可查、让同一个坑不踩两次。

1.2 痛点

  • 知识在人不在库：核心系统只有老王懂，老王休假=事故处理降级；老王离职=知识清零；
  • 重复踩坑：三个月前排查过的问题、写过的方案，没人记得在哪，再踩一遍再查一遍；
  • 文档过期成噪音：写过的文档没人维护，半年后"文档不可信"，于是更没人写——恶性循环；
  • 新人上手全靠口传：同一套环境配置、同一套规范，每个新人问一遍、每个导师讲一遍。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
团队 3 人以上、有交接/协作，想建文档规范API 文档自动生成工具链 → 09 模块 DevOps
文档没人看/没人写的困境要破局Markdown 语法 → 任何速查表
面试被问"如何做知识沉淀"个人笔记方法（本篇聚焦团队文档，个人笔记自行适配）

1.4 学习目标：读完本篇你能

  1. 用四象限法判断哪些东西值得写、哪些不值得写；
  2. 为每类文档选对类型与模板（README / 决策记录 / Runbook / 故障复盘），按"读者视角"组织内容；
  3. 建立文档的生命周期管理：入库、更新触发点、过期判定——让文档可信；
  4. 为团队搭建最小知识库结构（本篇第 6 章可直接套用）。

1.5 本篇阅读指引

前置知识：经历过至少一次"找不到信息/信息过期"的协作场景；01 篇的 ADR 概念（本篇会用到）。

难度等级：★☆☆☆☆（方法朴素，难在长期执行）。

读者建议路线
从零建知识库按顺序读第 2、3 章 → 第 6 章照抄结构
已有文档但没人看第 4 章进阶（可信度管理）→ 第 7 章坑清单自查
面试准备第 2 章 → 第 8 章重点讲解

第一遍可跳过：第 4 章进阶知识点（文档可信度量化、文档即代码）。务必动手：第 6 章的仓库文档结构——知识库是"搭出来"的，不是"想出来"的。

本篇不涉及：具体文档平台选型对比（Wiki/Notion/语雀以团队现状为准，原则通吃）。

2核心模型

三个核心模型：四象限解决"写什么"，文档类型学解决"写成什么样"，生命周期解决"怎么不过期"。顺序很重要——多数团队的文档失败，是因为跳过第一问直接开始堆文档。

2.1 四象限法：先回答"值得写吗"

多人需要只有自己用
重复用到①必写：规范、Runbook、环境配置——这是知识库的主体③写 cheatsheet 即可：个人速查，不入库
用一次②写"结论 + 出处"：临时决策记录一段话，别铺开成大文档④不写：写了也只会变成过期噪音

判断口诀：②③象限轻写或不写，团队精力只投给①象限。大多数"文档没用"的团队，是把力气花在了②④象限——写了一堆没人看也没人再用的东西，反而淹没了真正重要的①。

2.2 文档类型学：不同问题用不同文档

类型回答的问题典型文档生命特点
入门（Onboarding）"新环境怎么跑起来？"README、环境配置指南相对稳定，随环境变更更新
决策（ADR）"当时为什么这么做？"ADR（见 01 篇）永久存档，只追加不修改
操作（Runbook）"这事怎么执行/出事怎么办？"发布手册、故障应急步骤强时效，必须随系统变更同步
复盘（Postmortem）"那次事故学到什么？"故障复盘报告存档 + 沉淀进规范
规范（Guideline）"团队约定是什么？"评审规范、命名约定随共识演进，版本化

最大的类型错误：把"决策"写成"现状文档"。现状会变，决策理由不会——过期文档的过期能力正来自"它描述的是易变的现状"。解决方案：现状类文档尽量自动生成（API 文档），人写的文档聚焦"理由、过程、经验"这些不易变的东西。

2.3 文档生命周期：让文档可信的循环

文档不是"写完即终点"，它有生命周期：创建 → 入库（放对位置、有 Owner）→ 更新（有触发点）→ 归档/删除（有判定）。没有后三步的文档库，半年后必然变成"不可信信息堆"——而不可信比没有更糟：读者按过期文档操作出了事，从此再没人信文档。生命周期管理详见 4.2。

3实操流程（写一份好文档）

写任何一篇文档走五步，每步都有一条质量标准：

3.1 第一步：定义读者与场景

动笔前回答两问：谁在什么时候读它？他读的时候手里有什么、缺什么？——环境配置指南的读者是"第二天要跑通项目的新人"（他缺依赖清单和启动命令）；Runbook 的读者是"凌晨三点处理故障的值班者"（他缺操作步骤，不需要原理科普）。读者不同，同一主题的写法完全不同。

3.2 第二步：选类型与模板

对照 2.2 的类型表选类型，用团队的对应模板（第 6 章）。不要发明新格式——一致性本身就是可读性。

3.3 第三步：按"读者的下一步"组织结构

  1. 开门见山：第一段就说清"这篇讲什么、读完你能做什么"（本库每篇的"简介与阅读指引"就是这个作用）；
  2. 结论先行：先给结论/命令，再给解释——读者是来"办成事"的，不是来上课的；
  3. 命令可复制：所有操作给完整命令块，不给"执行相应操作"这种废话；
  4. 预期结果：关键步骤写明"你会看到什么"——读者能自查是走对了还是偏了。

3.4 第四步：验收——找目标读者试读

写完别直接入库：找一个真实目标读者读一遍（新人指南就找新人）。他卡住的地方就是你以为显而易见、实则不是的地方。这一步的投入产出比高于任何写作技巧。

3.5 第五步：入库并声明 Owner 与复审条件

入库三要素：放对位置（按 6.1 的目录结构）、标 Owner（谁负责它不过期）、写复审条件（"发布流程变更时更新本篇"）。没有 Owner 的文档，等于宣告它从今天开始过期。

五步的取舍：小文档（一段 Runbook）五步 10 分钟走完；大文档（新服务 README）可能要半天。比例不变的是：验收试读与入库声明这两步最常被跳过，也最不该被跳过。

4进阶知识点【进阶】

首次学习可整章跳过。前置：团队已有初步文档库。

4.1 文档即代码（Docs as Code）

把文档放进代码仓库、走与代码相同的流程：Markdown 存储、Git 版本化、PR 评审、CI 校验（链接有效性、格式 lint）。好处：文档变更与代码变更在同一 PR——"改了接口但忘了改文档"在流程上就过不了门禁；文档历史天然可追溯（谁、何时、为什么改）。代价：非技术角色协作门槛略高。这是技术团队文档的默认推荐形态。

4.2 可信度管理：文档库的核心资产是"可信"

读者信一次过期文档，就再也不信整个库。三个机制：

  • 更新触发点：文档头部声明"何时必须更新我"（变更发布流程时、新增服务时），并挂进对应的流程检查单（如发布 checklist 含"更新 Runbook？"）；
  • 定期巡检：每季度轮值抽检核心文档，头部标注"最后验证：2026-10"——验证日期比更新日期更可信（更新过≠验证过）；
  • 过期判定：连续两个巡检周期无人认领/验证的文档，移入 archive 目录——宁可少而可信。

4.3 搜索优先的结构设计

知识库的真实使用模式是搜索，不是浏览。结构设计为搜索服务：①文档标题含可搜索的关键词（"订单导出超时排查" 而非 "问题记录（三）"）；②每篇文档有固定元数据头（Owner/最后验证/标签）；③命名约定统一（6.1）。目录层级宁浅勿深——三层以上的目录，大家靠搜索而不是逐层点。

4.4 复盘文化的文档化闭环

故障复盘的价值不在报告本身，在闭环：复盘报告 → 改进项进任务单 → 结论沉淀进规范/Runbook。检验标准：同类事故复发时，值班者按 Runbook 就能处理——如果复盘知识只存在于报告里而没进 Runbook，下次事故还要靠回忆。

6最小可交付产物

30 分钟为团队搭起最小知识库骨架（以代码仓库 docs/ 目录为例）：

6.1 产物一：仓库文档目录结构

docs/
├── onboarding/          # 新人上手（①象限·入门类）
│   └── dev-setup.md     #   环境配置：依赖/启动/常见报错
├── adr/                 # 决策记录（永久存档，只追加）
│   └── ADR-014-订单导出方案.md

6.3 产物三：README 导航首页

我是谁在读：新人 → onboarding/ ；值班 → runbook/incident.md
我要找决策背景 → adr/ （文件名含编号与主题关键词）

规则：验证日期超过 2 个季度且无人认领的文档会被移入 archive/

6.4 产物价值与对照

三份产物共 30 分钟，换来的对照：新人问环境问题 → 甩 dev-setup.md 链接（导师每周省 1 小时）；凌晨故障 → 值班者按 incident.md 走（不靠回忆和翻聊天记录）；"当初为什么这么做" → adr/ 目录可查（不重吵一遍）。知识库的 ROI 不体现在"文档数量"，体现在这三类高频场景的响应速度。

6.5 扩展方向

  1. 开启"文档即代码"：docs/ 走 PR 评审，接口文档与代码同 PR 变更（4.1）；
  2. 把 Runbook 更新挂进发布 checklist：每次发布勾选"Runbook 是否需要更新"；
  3. 季度巡检排班表上墙（4.2），验证日期写入元数据头。

7常见坑 & Debug

按"写什么 → 怎么写 → 怎么活"分组，每条五要素。

7.1 写什么

坑 1：什么都写，重要被淹没

  • 现象：知识库里几百篇文档，新人不知道看哪篇，搜出来一半是过期的会议纪要；
  • 根因：没有四象限判定，②④象限的文档大量入库；
  • 修复：按 2.1 清库——archive 掉只有自己用的、写过的临时文档；
  • 规避：入库前过四象限；README 导航只指向①象限核心文档。

坑 2：把"决策"写成"现状"

  • 现象：精心维护的架构文档半年后与系统完全不符，成了误导源；
  • 根因：现状文档天然会过期——它描述的是易变的东西；
  • 修复：现状类信息尽量自动生成（API 文档从代码生成、架构图用 IaC 生成）；人写的聚焦决策与理由（ADR）；
  • 规避：每篇现状文档声明更新触发点，没触发点的不许入库。

7.2 怎么写

坑 3：自嗨式写作——读者视角缺席

  • 现象：文档按作者的记忆顺序写，新人第一屏就看不懂在讲什么；
  • 根因：知识的诅咒——作者无法想象"不知道这件事"的状态；
  • 复现：找一个目标读者试读，数他卡住的次数；
  • 修复：按 3.3 重排——结论先行、命令可复制、写明预期结果；
  • 规避：试读验收（3.4）作为入库前的固定动作。

坑 4：文档没有 Owner

  • 现象：文档出错没人修、过时没人删，"谁发现谁尴尬"；
  • 根因：集体负责 = 无人负责；
  • 修复：补 Owner 字段，元数据头模板强制；
  • 规避：入库三要素（位置/Owner/复审条件）作为硬门槛。

7.3 怎么活

坑 5：文档过期成噪音，信任崩塌

  • 现象："文档不可信"成为团队共识 → 没人写 → 库彻底死亡；
  • 根因：只有创建没有生命周期管理（2.3）；
  • 修复：按 4.2 三机制——更新触发点、季度巡检（验证日期）、过期入档；
  • 规避：把"文档是否过期"列入回顾会议题，巡检轮值排班。

坑 6：知识与流程脱节

  • 现象：复盘报告写得很深刻，下次同类事故照样手忙脚乱；
  • 根因：复盘结论停留在 postmortem/ 目录，没有沉淀进 Runbook 与规范；
  • 修复：复盘闭环（4.4）——改进项进任务单、结论进 Runbook；
  • 规避：复盘模板最后一栏固定写"本结论更新了哪篇 Runbook/规范"。

8重点讲解

Q1：哪些东西值得写成文档？怎么判断？

参考答案：用四象限——按"是否多人需要"与"是否重复使用"划分。多人 × 重复（规范、环境配置、Runbook）必写，是知识库主体；单人 × 重复写个人 cheatsheet；多人 × 单次写"结论+出处"短记录；单人 × 单次不写。核心观点：团队的文档带宽有限，全部投入给"多人重复"象限——多数团队的失败不是写得不够多，而是写了太多没人需要的东西，淹没了真正重要的。

Q2：怎么让文档不过期？

参考答案：先承认"现状类文档必然过期"，然后三招管理可信度——①触发点：每篇文档声明"何时必须更新我"并挂进流程 checklist（发布时勾选"Runbook 更新了吗"）；②验证日期：定期巡检并在文档头标注"最后验证时间"——验证过比更新过更可信；③过期入档：无人认领的文档移入 archive，宁可少而可信。

追问：为什么说"不可信比没有更糟"？——读者按过期文档操作出事故后，会永久放弃整个文档库；而一个可信的小库会持续被使用、被补充。可信度是知识库唯一的复利资产。

Q3：新人上手文档应该怎么写？

参考答案：读者是"第二天要跑通项目的新人"，结构按他的时间线：①前置依赖（账号/权限清单）；②环境配置（可复制命令 + 每步预期输出）；③跑通第一个功能（端到端的最小验证）；④常见报错（实测遇到的坑及解法）；⑤去哪问（Owner 与求助渠道）。写完必须找真实新人试读验收——知识的诅咒靠自检破不了。

Q4：你们团队怎么做知识沉淀？

参考答案：用"流转闭环"回答而非罗列文档类型：知识产生于事件（决策/事故/踩坑）→ 四象限判定是否入库 → 按类型用模板写（ADR/Runbook/复盘）→ 入库三要素（位置/Owner/复审条件）→ 季度巡检保可信 → 被检索使用。举一个具体例子最加分：如"一次导出超时事故 → 复盘报告 → 结论沉淀进 Runbook 的超时排查分支 → 下次值班直接按 Runbook 处理"。

面试官想验证的：你是否理解知识库的生死线是"可信度管理"而不是"写作热情"。
