1简介与阅读指引

1.1 定位

本篇讲的是"把大模型当随身专家"的对话式用法——在 ChatGPT / Claude / DeepSeek 这类对话产品里完成三类工程任务：生成（按需求写初稿）、解释（讲清陌生代码与概念）、评审（挑 diff 的毛病）。它区别于《AI 辅助开发》（讲 IDE 内的补全与 Agent 编码）和《LLM 应用开发》（讲 API 与 RAG）：本篇聚焦人直接与模型对话这个最高频的日常场景。

1.2 痛点

  • 把模型当搜索引擎，一句"帮我写个表格"换来一份完全没法用的大杂烩——不是模型不行，是提问没有信息量；
  • 一个会话里混着三个任务，模型带着前文的假设越答越歪；
  • 模型说啥信啥，幻觉 API 直接抄进项目——出问题的从来不是"用了 AI"，而是"没验证就用"。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
想让对话式 AI 真正提效（解释/初稿/评审）IDE 内补全与 Agent 编码 → 《AI 辅助开发》
面试要讲"你怎么用大模型工作"API 调用、RAG、Function Calling → 《LLM 应用开发》
想系统掌握提示词四要素与验证纪律模型原理/训练 → 超出本库范围

1.4 学习目标：读完本篇你能

  1. 用四要素模板（角色/上下文/约束/输出格式）写出一次到位的提问；
  2. 按三类场景（解释/生成/评审）选择正确的对话策略与验证方式；
  3. 理解系统提示、长上下文、上下文隔离三个机制并用于日常；
  4. 守住验证纪律：模型结论以文档与本地实测为准，不直接采信。

1.5 本篇阅读指引

前置知识：任意一款对话式 AI 产品的使用经验（哪怕只聊天过几次）；被陌生代码折磨过的经历。

难度等级：★★☆☆☆（上手零门槛，进阶在纪律与习惯）。

读者建议路线

本篇不涉及：模型 API 调用与集成（见《LLM 应用开发》）；编码 Agent 的工作流（见《AI 辅助开发》）。

2核心模型

对话式用法的四个核心模型：三类用途定义"让它干什么"，提示词四要素解决"怎么问"，上下文机制（系统提示/长上下文/隔离）解决"它看到什么"，幻觉与验证解决"怎么敢信"。按此顺序读。

2.1 三类工程用途：先分清你要它干什么

图 1 大模型的三类工程用途（示意）

三类用途对应三种不同的对话策略（第 3 章展开）。共同的价值定位：给快速的第二意见与初稿，缩短"想法到可运行初稿"的距离；共同的边界：它不替你拍板——生成的是初稿要你改，解释的要你对照源码，评审的要你复核。

2.2 提示词四要素：好结果来自好提问

图 2 好提示词的四个组成部分（示意）

四要素缺一的效果：缺角色——回答深度随机；缺上下文——模型只能泛泛而谈或编造；缺约束——给你引入新框架的"最优解"，与你的项目格格不入；缺输出格式——要代码给一堆文字，要结论给一堆代码。记忆口诀："你是谁、看到什么、不能做什么、交什么作业"。

2.3 上下文机制：它只"看见"你给的

  • 贴上下文：模型基于你贴入的代码/报错/文档作答——上下文质量决定输出质量，贴原始报错而非转述（与《AI 辅助开发》3.3 同源）；
  • 系统提示（system prompt）：对话开头的一条贯穿全程设定——规定人设、边界与输出格式（如"只输出 Python 代码、不要解释"），优先级高于普通消息；产品里的"自定义指令/项目说明"本质相同；
  • 上下文隔离：会话有记忆，上个任务的假设会污染下个任务——新任务开新对话。这是成本最低、效果最猛的习惯；
  • 长上下文：把整段长代码/长文档喂进去做解释与评审——Claude 的长文分析口碑好（对比见 4.2）。

2.4 幻觉：它不会说"我不知道"

模型会一本正经地编造 API、参数、库名——因为它按概率生成"看起来合理"的内容，且不主动承认不知道。两个推论：①关键前提自己显式交代（语言版本、框架、约束——它猜错前提时不会提醒你）；②结论以官方文档与本地实测为准。验证纪律是本篇的底线，第 7 章坑 1 展开反例。

2.5 产品形态对照：对话产品 vs 编码 Agent

对话产品（ChatGPT/Claude 网页版）负责"聊清楚"：解释、方案对比、初稿；Agent 产品（Claude Code、Codex）把模型包成能读仓库、跑命令、动手改的工具（见《AI 辅助开发》）。分工口诀：想明白用对话，干起来用 Agent；对话里聊透的方案，正是 Agent 任务书的素材——两类产品不是竞争关系，是工作流的前后两段。

2.6 多轮对话与澄清

大模型擅长"边问边澄清"：一次没讲清就追问补约束，多轮把模糊需求收敛成可执行任务。不要指望一句话问出完美答案——把它当一位会追问、需要交代背景的同事，而不是许愿机。多轮收敛的节奏：先要方案骨架 → 确认方向 → 再要细节实现；一轮就要成品，得到的多半是要大改的半成品。

3核心用法（三类场景）

三类场景各自的对话策略与验证方式。共同框架不变：给上下文 → 拿结果 → 本地验证。

3.1 场景一：解释——让陌生代码变得可读

策略：贴完整函数/模块 + 说明运行环境，要求"先讲数据流，再讲关键设计，最后指出可疑之处"。模板：

你是资深后端。下面是订单服务的一段代码（见下），运行环境 Java 17 + Spring Boot。
请按顺序回答：
1) 这段代码的数据流：输入从哪来、状态存在哪、输出到哪去
2) 关键设计意图（为什么这样写）
3) 你看到的三处可疑点（并发/边界/资源释放）

验证方式：解释类输出的验证是对照源码与打断点跑一遍——理解错误比代码错误更隐蔽，"听懂了"不等于"它说对了"。

3.2 场景二：生成——初稿机器，成品人工

策略：四要素齐全 + 需求拆细（复杂任务拆成两三轮：先骨架后细节）；约束写全（技术栈版本、不许引入的东西、必须复用的现有工具函数）。验证方式：生成的代码先读后跑——理解每一行再合入；跑通但看不懂的代码不要合（等于引入没人维护的黑盒）。

3.3 场景三：评审——第二双眼睛

策略：贴 diff + 改动意图 + 关注点，让它按清单找问题：

下面是一段 diff（见下），改动意图：给列表加服务端分页。
请按优先级列出问题：正确性 > 边界与异常 > 性能 > 可读性。
每条给：问题描述 + 为什么是问题 + 建议方向（不要给完整重写）。

验证方式：AI 评审意见逐条人工复核后才成为正式意见（与《代码评审》2.4/图 4 同一纪律——AI 是第二双眼睛）。它的价值在"广撒网"，你的价值在"业务判断"。

三场景的共同取舍：解释省的是"读懂时间"，生成省的是"打字时间"，评审省的是"扫描时间"——三者的共同前提都是人不退出验收位。

4进阶知识点【进阶】

首次学习可整章跳过。前置：已在日常使用三类场景。

4.1 系统提示工程：把重复交代变成常驻设定

每次对话都要重复"我是做什么的、代码规范是什么、输出要什么格式"——把这些沉淀进系统提示/自定义指令：角色（资深前端，输出带注释 TS 代码）、边界（不引入新依赖、不用 any）、格式（先结论后代码）。与《AI 辅助开发》的规则文件（.cursorrules）同构：一个作用于对话产品，一个作用于 IDE Agent，思想相同——稳定约束常驻化，会话消息只装易变信息。

4.2 多模型路由：不同任务用不同的刀

ChatGPT / Claude / DeepSeek 各有所长（以当前版本与最新官方信息为准）：

维度ChatGPTClaude
长文本较强长上下文、长文分析口碑好
代码综合强、工具生态广代码与长推理、文档跟随强
取舍通用首选长文档/长篇推理/代码评审

实践原则：通用问答用顺手的；长文档分析/长代码评审优先长上下文模型；成本敏感的批量小任务用高性价比模型（如 DeepSeek）。路由不需要精确，只需要有意识——"什么都用同一个"和"什么都用最贵的"都是浪费。

4.3 多轮收敛的对话设计

复杂任务的正确节奏：①先要方案（"你打算怎么实现，涉及哪些部分"）→ ②人审方案 → ③再要实现 → ④跑不通贴报错让它修（而不是换个问法重来——会话里已有有效上下文）。对比反面：一句话要成品，不满意就整个重问——每轮都在烧 token 重建上下文。多轮的价值在于每一轮只收敛一件事。

4.4 数据安全边界

对话式产品里贴什么要过脑子：公司代码、客户数据、密钥凭证——先确认组织的 AI 使用规范与产品隐私条款（数据是否用于训练、是否有企业版隔离）。通用底线：密钥与凭证永不入对话；核心敏感代码脱敏或用企业协议产品。这不是技术问题，是职业责任问题。

6.4 对照实验：同一问题，两种问法

差提问："帮我写个订单导出"
典型输出：通用代码，可能用原生 fetch、无进度态、文件名随意、
        引入你项目没有的库 —— 几乎每行都要改

模板二输出：贴合约束（Element Plus、现有 api 函数、时间戳文件名），

结论：模板四要素把"猜"变成了"按规格交付"，返工量从"重写"降到"微调"。

6.5 把模板变成团队资产

  1. 三个模板按团队技术栈改造成固定版本，放进团队知识库（衔接《技术文档》篇）；
  2. 沉淀个人的"高频提问库"：每次手写超过三行的提问，问自己要不要存成模板；
  3. 结合 4.1 的系统提示，把"你是谁 + 代码规范"挪进自定义指令，模板只需带上下文与任务。

7常见坑 & Debug

按"提问 → 会话 → 信任"三阶段分组，每条五要素。

7.1 提问阶段

坑 1：提问太笼统

  • 现象："帮我写个表格/优化一下这段代码"——输出泛泛、要大改，然后抱怨"AI 不行"；
  • 根因：模型没有你的项目上下文，笼统提问 = 让它猜规格；
  • 复现：把同一问题用四要素模板重问，对比输出；
  • 修复：按 2.2 四要素补齐——角色、上下文、约束、输出格式；
  • 规避：6.5 的模板库，高频场景不手写提问。

7.2 会话阶段

坑 2：跨任务不重置上下文

  • 现象：一个会话从"改按钮样式"聊到"排查线上 bug"，模型方案总带着前面的残留假设，越聊越歪；
  • 根因：会话记忆把旧任务的结论与错误尝试都带进了新任务；
  • 复现：同会话连问三个不相关问题；
  • 修复：新任务开新对话，重新给最小上下文；
  • 规避：任务切换 = 会话切换（与《AI 辅助开发》坑 4 同源同解）。

坑 3：一轮就要成品，不满意整个重问

  • 现象：复杂任务一句话要完整实现，不满意就换措辞从头再来，反复循环；
  • 根因：没有多轮收敛设计——每轮都烧 token 重建上下文；
  • 修复：按 4.3 节奏——先方案后人审再实现，报错在原会话续修；
  • 规避：复杂任务默认拆两轮起。

7.3 信任阶段

坑 4：不验证模型给的代码

  • 现象：生成的代码"看起来对"直接合入——幻觉 API、没考虑的分支在生产暴露；
  • 根因："AI 写的"自带虚假信任感；
  • 修复：生成类先读后跑（看懂每一行）、解释类对照源码、评审类逐条复核；
  • 规避：验证是闭环里唯一不可省的人工步骤（第 5 章红色节点）。

坑 5：把模型结论当权威

  • 现象：模型说的版本号/参数/行为与文档不符，照抄出事故；
  • 根因：模型不主动说"我不知道"（2.4），幻觉与训练截止并存；
  • 修复/规避：版本、参数、行为以官方文档与本地实测为准；关键前提（版本/约束）主动显式交代，不给它猜的机会。

8重点讲解

Q1：你日常怎么用大模型？边界在哪？

参考答案：三类用法——解释（贴陌生模块讲数据流与可疑点）、生成（四要素模板拿初稿再人工改造）、评审（贴 diff 按优先级找问题）；长文档分析走长上下文模型。边界三条：①它出初稿与第二意见，拍板的是我——核心逻辑、安全相关代码不外包；②一切结论回文档与源码验证，幻觉是概率行为的必然产物；③数据安全——密钥永不入对话，敏感代码按公司规范脱敏。

加分点：能说出"对话产品聊清楚、Agent 干起来"的分工，以及两类工具在个人工作流里的衔接。

Q2：什么是好的提示词？为什么？

参考答案：四要素——角色（定调回答的专业度与风格）、上下文（贴代码/报错/文档，模型只"看见"你给的）、约束（技术栈版本、不能做什么，防止跑偏）、输出格式（代码还是说明、什么结构）。原理：语言模型按上下文概率生成，四要素把"猜你的意图"变成"按你的规格执行"——提问的信息量直接决定输出的可用度。

举例："帮我写个表格"（猜，返工重写）vs"Vue3+TS、虚拟滚动、列后端配置、输出可运行代码"（按规格交付，微调即用）。

Q3：模型幻觉是什么？工程上怎么应对？

参考答案：幻觉 = 模型以高置信度输出不真实内容（编造 API、参数、引用）。根因是概率生成机制——"看起来合理"不等于"真实存在"，且模型缺乏"我不知道"的自我认知。工程对策三层：①提问时显式交代关键前提（版本/约束），减少猜错；②验证纪律——结论回官方文档、代码本地实测，幻觉在编译/运行时大量暴露；③流程兜底——AI 产出与人工代码过同样的评审门禁（衔接《代码评审》篇）。

追问：能消灭幻觉吗？——不能，只能压低概率 + 兜住后果；RAG 等技术是在"供给真实上下文"层面抑制（见《LLM 应用开发》），验证纪律是在"采纳"层面兜底。

Q4：ChatGPT 和 Claude 怎么选？

参考答案：按任务路由而非站队——通用问答用顺手的即可（差异在日常任务上不显著）；长文档分析、长代码评审优先长上下文见长的 Claude；工具生态/插件场景 ChatGPT 生态更广；成本敏感的批量小任务用高性价比模型（如 DeepSeek）。两个前提：模型迭代快，结论有时效性（以最新版本实测为准）；团队里"统一一款 + 按需加一款"比人人各自为战好协作。

这题真正考的：你是否把 AI 当工具箱做有意识的路由，而不是品牌信仰。
