1简介与阅读指引

1.1 定位：Python 测试的事实标准

pytest = 极简的测试函数写法 + 强大的 fixture 依赖注入 + 插件生态。它不要求类继承、不要求特定命名方法，测试就是"以 test_ 开头的函数 + 原生 assert"，失败时还能看到表达式中间值。其 unittest 兼容层让老测试可以无痛迁移。

1.2 横向对比

框架写法强项适合 / 代价
pytest函数 + 原生 assertfixture、参数化、插件、失败信息友好Python 首选；需额外装依赖
unittest继承 TestCase + assertXxx标准库自带、JUnit 风格样板代码多；可被 pytest 直接跑
Jest(Vitest)describe/it + expect前端同语言、快照测试对照理解：pytest 的 fixture ≈ beforeEach 的可复用版
JUnit注解 + 断言库Java 生态标准概念可对照：fixture ≈ @BeforeEach
心智对照：pytest 的 fixture ≈ 可复用的 setup/teardown + 依赖注入，比 beforeEach 更强的是"按名字声明、按作用域缓存、可相互依赖"。

1.3 测试分层（写多少、写在哪）

  • 单元测试（多、快）：纯函数与类，不碰 IO，毫秒级；
  • 集成测试（中）：接数据库/HTTP（TestClient），验证接线正确；
  • 端到端测试（少、慢）：跑完整服务，验证关键业务链路。

经验比例金字塔：单测 70% / 集成 20% / E2E 10%。不要为了覆盖率给 getter/setter 写测试——覆盖"有逻辑的代码"才有价值。

1.4 学习目标

  1. 掌握测试发现规则与断言重写带来的失败信息；
  2. 会用 fixture（含作用域与 conftest.py）与 parametrize 参数化；
  3. 会 mock 外部依赖（monkeypatch）与写 FastAPI 集成测试；
  4. 会用覆盖率、标记与 pytest.ini 配置，并接入 CI。

难度：★★☆☆☆。前置：函数、装饰器、包与模块导入。版本：pytest 7+/8+。

2核心模型

五个核心模型：发现规则→ 断言重写→ fixture→ 参数化→ 插件生态。

2.1 发现规则：约定优于配置

pytest 递归扫描目录，收集 test_*.py 或 *_test.py 里的 test_* 函数（以及 Test* 类里的 test_* 方法）。注意类名 Test* 且不能有 __init__——pytest 无法实例化它。

2.2 断言重写：为什么 assert 就够了

pytest 会在导入测试模块时重写 assert 语句，记录表达式的中间值。所以失败时你看到的不是"AssertionError"，而是每个子表达式的实际值——这是它胜过 unittest.assertXxx 的关键。

def test_sum():
    items = [1, 2, 3]
    assert sum(items) == 7        # 失败时打印：sum(items) == 6，items == [1,2,3]

2.3 fixture：可声明的依赖注入

用 @pytest.fixture 装饰的函数，测试按参数名声明使用；pytest 负责创建、按作用域缓存、并在结束后执行 yield 之后的清理代码。对照setup/teardown 的升级版：可复用、可组合、可按需请求。

2.4 参数化：一份逻辑跑多组数据

@pytest.mark.parametrize 把多组输入输出展开成多个独立用例——每组数据独立报告、一个失败不影响其他，比在测试里写 for 循环好得多。

2.5 插件生态

pytest-cov（覆盖率）、pytest-mock（mock 封装）、pytest-asyncio（异步测试）、pytest-xdist（并行）、pytest-timeout（超时）——生态是 pytest 的核心竞争力。

3核心用法（按场景）

3.1 场景一：安装与第一个测试

pip install pytest pytest-cov
pytest                        # 自动发现并运行
pytest -q                     # 简洁输出
pytest tests/test_user.py::test_create -v   # 指定单个用例
pytest -k "user and not slow"               # 按关键字过滤

def add(a, b):
    return a + b

def test_add():
    assert add(1, 2) == 3

def test_add_negative():
    assert add(-1, -1) == -2

3.2 场景二：异常与近似值断言

import pytest

def test_div_zero():
    with pytest.raises(ZeroDivisionError):
        1 / 0

def test_raises_message():
    with pytest.raises(ValueError, match="must be positive"):
        parse(-1)                    # 同时断言异常消息（正则匹配）

def test_float():
    assert 0.1 + 0.2 == pytest.approx(0.3)      # 浮点必须用 approx

3.3 场景三：fixture 与临时资源

import pytest

@pytest.fixture
def user():                          # 默认 function 作用域：每个用例一份
    return {"id": 1, "name": "张三"}

@pytest.fixture
def db():                            # 带清理：yield 之后必执行
    conn = create_conn()
    yield conn
    conn.close()

def test_user_name(user, db):        # 按名字声明即可注入
    assert user["name"] == "张三"

内置 fixture：tmp_path（临时目录，自动清理）、monkeypatch（安全的运行时替换）、capsys（捕获 stdout）、caplog（捕获日志）。

3.4 场景四：参数化与边界覆盖

@pytest.mark.parametrize("age,expect", [
    (0, False), (17, False), (18, True), (120, True), (121, False),
])
def test_is_adult(age, expect):
    assert is_adult(age) is expect

@pytest.mark.parametrize("a", [1, 2])
@pytest.mark.parametrize("b", [10, 20])      # 笛卡尔积：4 个用例
def test_mul(a, b):
    assert mul(a, b) == a * b
价值：边界值（0/空/负数/极大值/null）写成一行数据，比复制 N 个测试函数清晰，且失败时能精确定位到具体参数组合。

3.5 场景五：conftest.py 共享 fixture

# tests/conftest.py —— 该目录及子目录自动可用，无需 import
import pytest

@pytest.fixture(scope="session")          # 整个测试会话只建一次
def app_config():
    return load_config("test")

@pytest.fixture(autouse=True)             # 该目录下所有用例自动生效
def reset_state():
    clear_cache()
    yield
    clear_cache()

4进阶知识点【进阶】

4.1 Mock：monkeypatch 与 unittest.mock

def test_fetch_user(monkeypatch):
    # 替换掉真实网络调用，测试只关注自身逻辑
    monkeypatch.setattr("myapp.client.http_get", lambda url: {"id": 1})
    assert fetch_user(1)["id"] == 1

def test_env(monkeypatch):
    monkeypatch.setenv("MODE", "test")        # 自动还原，不污染其他用例
    monkeypatch.delenv("SECRET", raising=False)
from unittest.mock import Mock, patch

def test_send(monkeypatch):
    mailer = Mock()
    monkeypatch.setattr("myapp.notify.mailer", mailer)
    notify("a@b.com")
    mailer.send.assert_called_once_with("a@b.com")   # 断言调用方式

with patch("myapp.time.sleep") as m:                 # 上下文式 patch
    run_retry()
    assert m.call_count == 3
Mock 的第一法则：mock 你拥有的边界（对外 HTTP、时间、随机、文件系统），不要 mock 被测函数内部的私有方法——那只会把实现细节钉死，重构时测试全红。

4.2 FastAPI 集成测试（TestClient）

# 需要 pip install httpx（Starlette TestClient 基于 httpx）
from fastapi.testclient import TestClient
from myapp.main import app
from myapp.deps import get_db

client = TestClient(app)

def test_create_task(monkeypatch):
    monkeypatch.setitem(app.dependency_overrides, get_db, lambda: FakeDB())
    resp = client.post("/tasks", json={"title": "写测试", "priority": 2})
    assert resp.status_code == 201
    assert resp.json()["title"] == "写测试"

def test_validation_error():
    r = client.post("/tasks", json={"title": ""})     # 非法入参
    assert r.status_code == 422
    assert r.json()["detail"][0]["loc"] == ["body", "title"]

技巧用 app.dependency_overrides 替换数据库/鉴权依赖，是 FastAPI 集成测试最省力的写法（见 05 篇 2.3）。

4.3 覆盖率怎么看、怎么设

pytest --cov=myapp --cov-report=term-missing     # 终端显示缺失行
pytest --cov=myapp --cov-report=html             # 生成 htmlcov/index.html
pytest --cov=myapp --cov-fail-under=80           # 低于 80% 直接失败（CI 门禁）

正确用法：覆盖率用于发现"完全没被测到的模块"，而不是追求 100%。给配置类、DTO、简单 getter 刷覆盖率毫无意义。

4.5 并行与提速

pytest -n auto                 # pytest-xdist：按 CPU 核数并行
pytest --lf                    # 只跑上次失败的用例
pytest -x                      # 首次失败即停止（调试用）
pytest --durations=10          # 列出最慢的 10 个用例
并行的前提：用例之间无共享状态、无顺序依赖。若测试共用同一个数据库/文件，并行会随机失败——先保证每个用例自带 fixture 隔离。

6最小可运行 Demo

性质（诚实声明）：本篇为可运行的教学测试套件（订单计价逻辑 + FastAPI 接口），非生产履历。

6.1 Demo 设计：给订单计价模块写测试

  • 目标：覆盖正常/边界/异常/参数化/mock 外部汇率，并跑覆盖率；
  • 验证：pytest --cov=. --cov-report=term-missing，观察哪几行没被覆盖。
# pricing.py（被测代码）
DISCOUNT_RULES = [(1000, 0.9), (500, 0.95)]      # 满 1000 九折，满 500 九五折

def calc_total(items: list[dict], rate: float = 1.0) -> float:
    """按数量小计 → 阶梯折扣 → 汇率换算"""
    if not items:
        raise ValueError("items must not be empty")
    subtotal = sum(i["price"] * i["qty"] for i in items)
    for threshold, factor in DISCOUNT_RULES:
        if subtotal >= threshold:
            subtotal *= factor
            break
    return round(subtotal * rate, 2)
# test_pricing.py
import pytest
from pricing import calc_total

@pytest.fixture
def items():
    return [{"price": 100.0, "qty": 3}, {"price": 25.5, "qty": 2}]   # 351.0

def test_no_discount(items):
    assert calc_total(items) == 351.0

@pytest.mark.parametrize("price,qty,expect", [
    (200, 3, 570.0),      # 600 → 九五折
    (400, 3, 1080.0),     # 1200 → 九折
    (0, 5, 0.0),          # 边界：零金额
])
def test_discount_levels(price, qty, expect):
    assert calc_total([{"price": price, "qty": qty}]) == expect

def test_rate_conversion(items):
    assert calc_total(items, rate=0.5) == 175.5

def test_empty_raises():
    with pytest.raises(ValueError, match="must not be empty"):
        calc_total([])

def test_rate_from_api(monkeypatch):
    monkeypatch.setattr("pricing.fetch_rate", lambda: 7.2)     # mock 外部汇率
    assert calc_total([{"price": 10, "qty": 1}], rate=7.2) == 72.0
pytest --cov=. --cov-report=term-missing -q
# ---------- coverage ----------
# pricing.py    10      0   100%
# 5 passed in 0.12s

6.2 踩坑记录

  • 坑测试之间共享了一个全局购物车对象，导致单独跑能过、一起跑就红——状态必须放进 fixture，每个用例重建；
  • 坑用 assert total == 0.3 断言浮点结果偶发失败——改用 pytest.approx；
  • 坑mock 时 patch 的路径写成了定义处而非使用处（myapp.pricing.fetch_rate 而非 utils.fetch_rate），mock 不生效。

6.3 成果与复盘

  1. 能力：单测、参数化边界、异常断言、mock、集成测试、覆盖率门禁一套流程跑通；
  2. 一句话抓手："用 pytest 给计价模块写了测试套件：fixture 做隔离、parametrize 覆盖边界、monkeypatch mock 外部汇率，FastAPI 用 TestClient + dependency_overrides 做集成测试，CI 里配了 --cov-fail-under 门禁。"

7常见坑 & Debug

7.1 fixture 名被覆盖 / 找不到

现象：fixture 'db' not found 或注入了错误的对象。Debug：pytest --fixtures 列出可用 fixture 及其定义位置；正解：确认 conftest.py 在同级或上级目录，且测试函数参数名与 fixture 名一致。

7.2 用例之间有顺序依赖

现象：单独跑通过、整体跑失败，或 -n auto 并行后随机失败。正解：每个用例自带数据准备（fixture 重建状态），禁止依赖"上一个测试留下的数据"。

7.3 mock 打了错误的路径

现象：mock 没生效、真实函数仍被调用。规则：patch 使用处，不是定义处——patch("myapp.pricing.fetch_rate")（该模块 from utils import fetch_rate 后形成的名字），而不是 patch("utils.fetch_rate")。

7.4 断言浮点相等

现象：0.1+0.2 == 0.3 失败。正解：pytest.approx(expected) 或 abs(a-b) < 1e-6；金额场景优先用 Decimal。

7.5 conftest 放错目录 / 导入报错

现象：测试收集阶段 ModuleNotFoundError。正解：把项目根目录加进 sys.path（pytest.ini 配 pythonpath = .），或用 pip install -e . 可编辑安装。

7.6 覆盖率虚高

现象：覆盖率 90% 但线上照样出 bug。正解：看 term-missing 的缺失行，重点补"分支与异常路径"；覆盖率只用来找完全没测的模块。

8重点讲解

Q1：pytest 相比 unittest 好在哪？核心机制是什么？

参考答案：写法极简——普通函数 + 原生 assert 即可，不需要继承 TestCase、不需要 self.assertEqual。断言重写（assertion rewriting）是它的核心机制：pytest 在导入测试模块时重写 AST，记录 assert 语句中每个子表达式的值，失败时逐项回显（如 sum(items) == 6、items == [1,2,3]），调试成本远低于 unittest 的一句 AssertionError。fixture 机制让"准备与清理"变成可声明、可组合、按作用域缓存的依赖（替代 setUp/tearDown 的样板代码）；parametrize 让同一逻辑跑多组数据且每组独立报告。此外它能直接运行 unittest 风格的测试，迁移无痛，并拥有 pytest-cov/-mock/-asyncio/-xdist 等成熟插件生态。

Q2：fixture 的作用域怎么选？写出正确清理代码的关键是什么？

参考答案：作用域从细到粗为 function（默认）< class < module < session：越细隔离性越好、越粗执行越快。原则：默认 function；只有创建昂贵且只读的资源才上提（模块级建表结构、session 级启动容器/加载模型）。清理必须用 yield 而不是 return——yield 之前是准备、之后是 teardown，pytest 保证它在用例结束后执行即使用例失败（关闭连接、删临时目录、还原 monkeypatch）。常见坑：把可变状态（购物车、缓存）放到 session 级 fixture 会造成用例互相污染，表现为"单独跑绿、一起跑红"。

Q3：单元测试里怎么 Mock 才不至于把实现钉死？

参考答案：只 mock 边界——外部 HTTP、数据库、时间、随机数、文件系统、环境变量；不要 mock 被测对象的私有方法或内部函数，否则测试变成"验证实现细节"，一重构就全红。工具选择：monkeypatch 是 pytest 内置、用例结束自动还原（首选，安全不泄漏）；unittest.mock.patch 功能更全（断言 assert_called_once_with、Mock 对象），但要注意退出上下文/装饰器后还原。patch 路径规则：patch 使用处而非定义处——模块 A from utils import fetch 后，名字存在于 A.fetch，必须 patch "A.fetch" 才生效。分层建议：单元测试 mock 掉所有 IO；集成测试用 FastAPI 的 dependency_overrides 或测试数据库容器，验证真实接线。
