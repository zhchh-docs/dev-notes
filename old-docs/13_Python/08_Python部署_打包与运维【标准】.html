1简介与阅读指引

1.1 定位：让 Python 程序"跑得久、改得动、查得到"

部署不是"把代码拷到服务器"，而是把不确定性全部固定下来：依赖版本固定、运行环境固定、启动方式固定、日志出口固定、健康检查固定。剩下的才是业务代码。

1.2 上线前必须回答的五个问题

  1. 依赖怎么锁——换台机器 pip install 后行为一致吗？
  2. 进程怎么起——用 WSGI 还是 ASGI？几个 worker？崩了会不会自动拉起？
  3. 日志去哪——stdout 还是文件？有没有 request_id 可串联？
  4. 健康怎么判——探活接口能反映数据库是否可用吗？
  5. 发布怎么回滚——镜像有 tag 吗？数据库迁移能向下兼容吗？

1.3 三种运行形态对照

形态典型做法适合关键点
脚本 / CLIvenv + cron + 日志数据处理、定时同步锁依赖、写日志、幂等
Web 服务Docker + uvicorn/gunicorn + nginxAPI、Web 应用进程模型、优雅重启、探活
桌面/分发工具PyInstaller / Nuitka 打包给非技术同事用体积、反病毒误报、平台构建
主线推荐：服务端一律容器化 + 进程管理器；只有"必须双击运行"的场景才用 PyInstaller。

1.4 学习目标

  1. 用 venv + 锁定文件做到依赖可复现；
  2. 写一份多阶段、体积小的 Dockerfile；
  3. 理解 WSGI/ASGI 与 worker 数量选择，配好 uvicorn/gunicorn；
  4. 配通 systemd/nginx 反代、日志、健康检查与定时任务。

难度：★★★☆☆。前置：Linux 基础命令、HTTP、pip 使用；建议先读 05 篇（FastAPI）。

2核心模型

五个核心模型：依赖隔离与锁定→ WSGI / ASGI→ 进程模型（worker）→ 反向代理→ 配置外置。

2.1 依赖隔离：venv 是底线

python -m venv .venv 创建独立环境，source .venv/bin/activate（Windows：.venv\Scripts\activate）后安装的所有包都只影响当前项目。禁止直接往系统 Python 里 pip install——不同项目版本冲突会让你在半夜排查。

2.2 依赖锁定：requirements vs lock

方式内容适用
requirements.txt手写顶层依赖，可带版本区间小项目、库
pip freeze导出全部精确版本（含间接依赖）快速固定，但会混入无关包
pip-tools / uv / Poetry从 requirements.in 编译出带哈希的完整锁文件生产推荐，可复现且可审计
 
# pip-tools 流程（推荐）
pip install pip-tools
echo "fastapi" > requirements.in
echo "uvicorn[standard]" >> requirements.in
pip-compile --generate-hashes requirements.in      # 生成 requirements.txt（全量锁定）
pip-sync                                            # 让环境与锁文件完全一致

2.3 WSGI vs ASGI：同步与异步的接口标准

WSGI（同步，如 Flask/Django 传统部署）：一个请求占一个 worker（进程/线程）直到返回；ASGI（异步，如 FastAPI/Starlette）：单进程内事件循环处理大量并发连接，长连接/WebSocket 天然支持。对照WSGI ≈ Java Servlet 的同步模型；ASGI ≈ Node 的事件循环。

2.4 进程模型：worker 不是越多越好

  • 进程 worker：吃满多核、隔离性好，但内存 ×N；
  • 线程 worker：省内存，受 GIL 限制，适合 IO 密集；
  • 异步 worker（uvicorn.workers.UvicornWorker）：高并发长连接首选。
经验公式：进程 worker 数 ≈ CPU 核数（同步应用 2×核数+1）；异步应用 1 进程即可扛大量连接，多核用 --workers N 或 gunicorn 管理。

2.5 配置外置：十二要素应用

配置（数据库地址、密钥、开关）从环境变量注入，不写死在代码里；本地用 .env（python-dotenv），生产由编排平台注入。禁止镜像里塞生产密钥、仓库里提交 .env。

import os
from pydantic import BaseModel

class Settings(BaseModel):                  # 集中管理 + 类型校验
    db_url: str = os.getenv("DB_URL", "sqlite:///./app.db")
    debug: bool = os.getenv("DEBUG", "false").lower() == "true"
    workers: int = int(os.getenv("WORKERS", "4"))

settings = Settings()

3核心用法（按场景）

3.1 场景一：本地环境与依赖落地

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip freeze > frozen.txt            # 仅用于排查，生产请用 pip-compile
python -m pytest                   # 部署前跑一遍测试（见 07 篇）

3.2 场景二：Dockerfile（多阶段 + 瘦身）

# ---------- 阶段 1：构建依赖 ----------
FROM python:3.12-slim AS builder
WORKDIR /app
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
COPY requirements.txt .
RUN python -m venv /opt/venv \
 && /opt/venv/bin/pip install --upgrade pip \
 && /opt/venv/bin/pip install -r requirements.txt

# ---------- 阶段 2：运行 ----------
FROM python:3.12-slim
WORKDIR /app
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    TZ=Asia/Shanghai
RUN groupadd -r app && useradd -r -g app app        # 非 root 运行
COPY --from=builder /opt/venv /opt/venv
COPY --chown=app:app . .
USER app
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/health')"
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
# .dockerignore —— 别把垃圾打进镜像
.venv
__pycache__/
*.pyc
.git
tests/
.env
*.log
瘦身要点：①用 -slim 基础镜像；②多阶段只拷 venv；③PIP_NO_CACHE_DIR=1 不留 pip 缓存；④--chown 避免 root 权限；⑤.dockerignore 排除测试与本地环境。

3.3 场景三：启动命令与进程模型

# 开发：热重载
uvicorn main:app --reload --port 8000

# 生产（纯 ASGI，多进程）
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4

# 生产（gunicorn 管进程 + uvicorn 管异步，推荐：自带平滑重启与探活）
gunicorn main:app \
  -k uvicorn.workers.UvicornWorker \
  -w 4 -b 0.0.0.0:8000 \
  --timeout 60 --graceful-timeout 30 --access-logfile -

gunicorn 的价值：worker 崩溃自动拉起、支持 SIGTERM 优雅退出（先停止接收新请求、处理完在途请求再退出）、--max-requests 定期重启防内存泄漏。

3.4 场景四：systemd 守护（不用容器时）

# /etc/systemd/system/myapp.service
[Unit]
Description=My FastAPI App
After=network.target

[Service]
User=app
WorkingDirectory=/srv/myapp
Environment="PATH=/srv/myapp/.venv/bin"
Environment="DB_URL=postgresql://user:pwd@127.0.0.1:5432/db"
ExecStart=/srv/myapp/.venv/bin/gunicorn main:app \
          -k uvicorn.workers.UvicornWorker -w 4 -b 127.0.0.1:8000
Restart=always
RestartSec=3
KillSignal=SIGTERM           # 配合 graceful-timeout 优雅退出

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
journalctl -u myapp -f --since "10 min ago"      # 看日志

3.5 场景五：nginx 反向代理

upstream myapp { server 127.0.0.1:8000; }

server {
    listen 80;
    server_name api.example.com;
    client_max_body_size 20m;               # 上传大小限制

    location / {
        proxy_pass http://myapp;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    location /static/ { alias /srv/myapp/static/; expires 7d; }
}

要点反代负责 TLS 终止、静态资源、限流与缓冲；应用只监听 127.0.0.1。必须转发 X-Forwarded-*，否则应用拿不到真实客户端协议与 IP（FastAPI 还需 --proxy-headers --forwarded-allow-ips='*'）。

3.6 场景六：健康检查接口

@app.get("/health")
def health():
    # 轻量：只证明进程活着
    return {"status": "ok"}

@app.get("/ready")
def ready(db=Depends(get_db)):
    db.execute(text("select 1"))          # 关键依赖探活：数据库可用才算就绪
    return {"status": "ready"}

区分：/health（liveness，进程活着）与 /ready（readiness，能接流量）——K8s 与负载均衡器分别使用，避免数据库抖动时把实例摘掉又重启的死循环。

4进阶知识点【进阶】

4.1 日志：从 print 到结构化

import logging, sys, json

logging.basicConfig(
    level=logging.INFO,
    stream=sys.stdout,                       # 容器里必须打到 stdout
    format='{"ts":"%(asctime)s","lvl":"%(levelname)s","msg":"%(message)s","mod":"%(name)s"}',
)
log = logging.getLogger("myapp")
log.info("order created", extra={"order_id": 1001})   # 关键业务留痕
  • 容器原则：日志只写 stdout/stderr，由 Docker/K8s 收集，不要在容器里写日志文件（会随容器消失、占满可写层）；
  • 必开 PYTHONUNBUFFERED=1，否则 print/log 被缓冲，容器日志会延迟甚至丢失；
  • 加 request_id：中间件生成并写入日志上下文，才能把一次请求的多条日志串起来。

4.2 优雅退出与零停机发布

流程：负载均衡摘流量 → 发 SIGTERM → 应用停止接收新连接、处理完在途请求 → 退出。要点：①容器里用 exec 形式启动（PID 1 才能收到信号）；②设置 graceful-timeout 大于最长请求耗时；③K8s 配 preStop 睡眠几秒等待端点摘除。

4.3 定时任务

# cron：最简单可靠（注意用绝对路径的 venv python）
0 2 * * * /srv/myapp/.venv/bin/python /srv/myapp/jobs/sync.py >> /var/log/sync.log 2>&1
# APScheduler：应用内的轻量定时（多 worker 时会重复执行！）
from apscheduler.schedulers.background import BackgroundScheduler
sched = BackgroundScheduler(timezone="Asia/Shanghai")
sched.add_job(sync_data, "cron", hour=2, minute=0, id="sync")
sched.start()          # 必须在 lifespan 里启动与关闭，且只在一个进程里跑
多实例陷阱：应用内定时器在每个 worker/每个副本都会跑一遍。要么用 --workers 1 的独立 job 进程，要么用分布式锁（Redis/数据库锁），要么交给 cron/K8s CronJob。

4.4 PyInstaller：给非技术用户分发

pip install pyinstaller
pyinstaller -F -n mytool main.py                 # 单文件（启动慢、体积大）
pyinstaller -D -n mytool main.py                 # 单目录（推荐：启动快、易排查）
pyinstaller -F -w main.py                        # -w：无控制台窗口（GUI 程序）
  • 平台绑定：Windows 上打包出的是 Windows 程序，macOS 需 macOS 构建——用 CI 矩阵分别打包；
  • 数据文件：模板/配置文件要用 --add-data 显式打包，或用 sys._MEIPASS 取运行时路径；
  • 注意单文件模式会被部分杀毒软件误报；体积通常 30MB 起。

4.5 发布与回滚

  1. 镜像打不可变 tag（commit sha 或版本号），禁止用 latest 发布；
  2. 数据库迁移与代码分离：先发布向下兼容的迁移（加列不加约束），再发代码，最后清理旧列；
  3. 回滚：镜像回滚 = 改 tag；迁移回滚 = 提前写好 downgrade（见 06 篇 Alembic）。

6最小可运行 Demo

性质（诚实声明）：本篇为可复制的部署模板（FastAPI + Docker + systemd），非生产履历；生产还需补监控告警与密钥管理。

6.1 Demo 设计：把 FastAPI 服务容器化并守护

  • 目标：一份 Dockerfile + compose + systemd 单元，覆盖构建、启动、探活、日志；
  • 验证：docker compose up --build 后访问 /health，docker stats 看镜像体积与内存。
# docker-compose.yml
services:
  api:
    build: .
    image: myapi:1.0.0                 # 不可变 tag，禁止 latest
    environment:
      - DB_URL=postgresql://app:secret@db:5432/app
      - WORKERS=4
      - TZ=Asia/Shanghai
    ports: ["8000:8000"]
    depends_on: [db]
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/health')"]
      interval: 30s
      retries: 3
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=secret
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:
# 构建与发布
docker build -t myapi:1.0.0 .
docker compose up -d
curl http://127.0.0.1:8000/health          # {"status":"ok"}
docker compose logs -f api                 # stdout 日志
docker compose exec api alembic upgrade head   # 迁移独立于代码发布

6.2 踩坑记录

  • 坑没设 PYTHONUNBUFFERED=1，日志迟迟不出现、容器被 kill 时最后一段日志丢失；
  • 坑CMD uvicorn ... 写成 shell 形式，信号收不到 → 无法优雅退出，发布时请求被硬中断；改用 JSON 数组形式；
  • 坑4 个 worker × 连接池 20 = 80 个连接，与数据库 max_connections=100 几乎打满，压测时出现排队。

6.3 成果与复盘

  1. 能力：能从零把服务做成"可复现构建 + 可守护运行 + 可观测日志 + 可回滚发布"；
  2. 一句话抓手："部署上用多阶段 Dockerfile 把镜像瘦身到百 MB 内，非 root 运行、stdout 日志、health/readiness 双探活；进程模型是 gunicorn 管 uvicorn worker，连接池按 worker 数核算上限，镜像用不可变 tag 发布，迁移与代码分离。"

7常见坑 & Debug

7.1 依赖不锁导致"本地能跑线上炸"

现象：某库自动升了大版本，API 变化导致线上报错。正解：生产用 pip-compile 锁全量版本（含 hash），部署用 pip-sync；CI 里跑一次"干净环境安装 + 测试"。

7.2 镜像体积大、构建慢

现象：镜像 1GB+，构建每次都重装依赖。正解：多阶段构建、-slim 基础镜像、PIP_NO_CACHE_DIR、.dockerignore、先 COPY 依赖文件再 COPY 代码（利用层缓存）。

7.3 日志丢失 / 延迟

现象：容器里看不到 print 输出。正解：PYTHONUNBUFFERED=1（或 python -u），日志输出到 stdout 而非文件，用 logging 而非 print。

7.4 时区和编码不一致

现象：容器里时间差 8 小时、写文件乱码。正解：镜像设 TZ=Asia/Shanghai，读写文件显式 encoding="utf-8"，数据库存 UTC、展示层转本地时区。

7.5 单 worker 被阻塞拖垮

现象：一个慢请求让整个服务无响应。正解：异步应用开多 worker；同步应用配足 worker 与 timeout；慢任务丢队列异步执行。

7.6 debug 模式上生产

现象：--reload 或 DEBUG=true 留在生产，性能差且泄露堆栈。正解：生产启动命令与开发分开维护，用环境变量校验启动时断言 debug is False。

7.7 定时任务重复执行

现象：4 个 worker 各跑一遍定时同步，数据重复。正解：独立 job 进程（--workers 1）、cron/K8s CronJob，或加分布式锁；任务本身保证幂等。

8重点讲解

Q1：WSGI 和 ASGI 有什么区别？worker 数量怎么定？

参考答案：WSGI 是同步接口标准（Flask/Django 传统部署）：一个请求从进入到返回独占一个 worker（进程或线程），期间不能做别的；并发能力 ≈ worker 数，长连接/WebSocket 难以支持。ASGI 是异步接口标准（FastAPI/Starlette）：单进程内事件循环可同时推进大量请求，IO 等待不占线程，天然支持 WebSocket 与长轮询。worker 数量：同步应用常见 2×CPU核数+1（兼顾 IO 等待），异步应用按核数配 --workers N（每个 worker 一个事件循环，吃一核）。不要盲目加：进程 worker 会 N 倍内存 与 N 倍数据库连接（总连接 = 单进程池上限 × worker 数），超限会导致数据库排队。生产常用 gunicorn + UvicornWorker：gunicorn 负责进程管理与优雅重启，uvicorn worker 负责异步并发。

Q2：Dockerfile 怎么写才算合格？有哪些必做项？

参考答案：①多阶段构建——builder 阶段装依赖到 /opt/venv，运行阶段只拷 venv，不残留编译工具；②小基础镜像——python:3.12-slim（ alpine 需谨慎，部分轮子无 musl 预编译包，会现场编译）；③层缓存——先 COPY requirements.txt 安装依赖，再 COPY 代码，改代码不重装依赖；④不留垃圾——PIP_NO_CACHE_DIR=1、.dockerignore 排除 .venv/__pycache__/.git/tests；⑤安全——创建非 root 用户并 USER app，不把密钥打进镜像；⑥可观测——PYTHONUNBUFFERED=1 让日志实时到 stdout，HEALTHCHECK 或 K8s 探活；⑦信号——CMD 用 JSON 数组形式（exec 形式）让应用成为 PID 1，才能收到 SIGTERM 优雅退出；⑧时区——设 TZ。发布时用不可变 tag，禁止 latest。

Q3：线上日志和健康检查应该怎么设计？

参考答案：日志：容器环境下只写 stdout/stderr（由 Docker/K8s 驱动收集），不写容器内文件（随容器消失、撑大可写层）；开 PYTHONUNBUFFERED=1 关闭缓冲，否则日志延迟甚至丢失；用 logging 而非 print，输出结构化（JSON）便于检索；中间件生成 request_id 并贯穿所有日志与响应头，才能把一次请求的多条日志串起来；记录关键业务事件（下单、支付回调）与所有异常堆栈，但不要记敏感信息（密码、token、身份证）。健康检查：拆成两个——/health（liveness：进程活着，不查依赖，失败才重启）与 /ready（readiness：查数据库/缓存，失败就从负载均衡摘流量）。这样区分可避免"数据库抖动 → 所有实例被判定不健康 → 全部重启"的雪崩。
