1简介与阅读指引

1.1 定位：性能与并发主战场

Python 慢吗？分场景：业务编排/胶水层慢一点无所谓；CPU 密集靠多进程与 C 扩展；IO 密集靠 asyncio。本篇回答三个工程问题：什么时候并发、选哪种并发、慢了怎么查。

1.2 横向对照：Python 并发 vs JS/Java

模型PythonJavaScriptJava
单线程事件循环asyncio（async/await）原生（JS 之根）Netty/NIO
多线程有但受 GIL 限制（IO 密集可用）Worker Threads 少用主力（JVM 无全局锁）

并发成本协程最轻 > 线程 > 进程协程最轻虚拟线程（21+）趋轻

2核心模型

五个核心模型：GIL→ 并发三选型→ 生成器协议→ 装饰器本质→ 内存管理。

2.1 GIL：全局解释器锁

GIL（Global Interpreter Lock）：CPython 中同一时刻只允许一个线程执行 Python 字节码。为什么存在：CPython 内存管理（引用计数）非线程安全，用一把大锁换实现简单。限制什么：CPU 密集多线程无法并行（8 核跑出 1 核）；不限制什么：IO 等待时 GIL 会释放——多线程对网络/磁盘并发仍然有效。

2.2 并发三选型：任务类型决定工具

IO 密集 + 中小并发 → 多线程（threading/线程池，等待时释放 GIL）；CPU 密集 → 多进程（multiprocessing，每进程独立解释器与 GIL，代价是启动重+序列化开销）；IO 密集 + 高并发（千级连接） → asyncio 协程（单线程事件循环，切换成本最低）。混合负载：协程 + 进程池（事件循环调度 CPU 活丢给进程）。

2.3 生成器与迭代器协议：惰性求值

含 yield 的函数是生成器——调用不执行，每次 next 推进到下一个 yield 并暂停（局部状态留在栈上）；实现 __iter__/__next__ 即迭代器。价值：流式处理不把全量数据装内存（读 10GB 日志逐行处理、无限序列）；对照 Java Stream 惰性与 JS generator（同源思想）。

2.4 装饰器：高阶函数 + 语法糖

@cache 等价 f = cache(f)——装饰器是接收函数返回函数的高阶函数；闭包保存状态（调用计数/缓存/注册路由）。FastAPI 的 @app.post、pytest 的 fixture 都基于它——装饰器是 Python 框架魔法的通用载体（对照 Java 注解：注解靠反射扫，装饰器本身就是运行时包装）。

2.5 内存管理：引用计数 + 分代 GC

主力是引用计数（归零即回收，实时性好），辅以分代 GC 处理循环引用；gc 模块可观测，weakref 弱引用做缓存不阻止回收。大对象被全局 list 顺手一存就是泄漏——排查思路：tracemalloc 快照对比（呼应 02 Java 篇的内存区域心智）。

3核心用法（按场景）

3.1 场景一：线程池与进程池（统一接口）

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

urls = [f"https://api.example.com/i/{i}" for i in range(200)]

# IO 密集：线程池（等待时释放 GIL，并发有效）
with ThreadPoolExecutor(max_workers=32) as ex:
    pages = list(ex.map(fetch, urls))

# CPU 密集：进程池（每进程独立 GIL，真并行）
with ProcessPoolExecutor(max_workers=8) as ex:
    results = list(ex.map(crunch, chunks))
经验：两个池 API 完全一致——先按任务类型选池，再调参；进程池的函数与参数必须可序列化（pickle）。

3.2 场景二：asyncio 高并发 IO

import asyncio, httpx

async def fetch_one(client, url):
    r = await client.get(url)          # await 让出控制权（对照 JS await）
    return r.status_code

async def main():
    async with httpx.AsyncClient() as client:
        return await asyncio.gather(   # 并发跑全部（对照 Promise.all）
            *(fetch_one(client, u) for u in urls))

asyncio.run(main())

3.3 场景三：生成器管道

def read_lines(path):                  # 惰性：不整读 10GB 文件
    with open(path, encoding="utf-8") as f:
        yield from f

def parse(lines):

4进阶知识点【进阶】

首次学习可整章跳过。前置：GIL 与三种并发已会。

4.1 事件循环的调度细节

事件循环维护就绪任务队列与 IO 完成回调——await 挂起时把控制权交回循环，循环去跑其他就绪任务；同步段不 slice：一个不 await 的死循环能卡死整个循环的所有任务（对照 JS：长任务阻塞渲染，机制同源）。

4.2 协程 + 进程池混合架构

高并发服务里的 CPU 活（压缩/图像/ML 推理）：loop.run_in_executor(ProcessPoolExecutor(), fn, arg)——事件循环调度、进程池干重活，两全；uvicorn 多 worker 进程是部署层先手（每核一进程）。

4.3 性能常量与 C 边界

numpy/pandas 慢在"把循环下沉到 C"：向量化一次算一批，比 Python for 快百倍——优化优先级：算法 → 数据结构（set/dict 查找）→ 内置函数与推导式 → C 扩展（numpy）→ 并发并行；lru_cache 缓存纯函数、__slots__ 省对象头。

4.4 GIL 的现在与未来

PEP 703 free-threaded 构建（3.13 实验性，可关闭 GIL）与 subinterpreters 推进中——工程决策仍按"GIL 存在"来做：CPU 并行交给进程池/C 扩展，等生态成熟再迁移；多核部署用"多进程 worker + 负载均衡"兜底（呼应 09 DevOps 部署）。

6最小可运行 Demo

性质（诚实声明）：本篇为本地并发对比实验（mock 延迟的下载任务 ×100），数字为实验环境相对值，非生产基准。

6.1 Demo 设计：三种并发下载对比

  • 任务：100 个模拟网络请求（每请求 50ms 延迟），串行 vs 线程池 vs asyncio 三版计时；
  • 验证点：串行 ≈ 5s；线程池/协程 ≈ 数百 ms——IO 密集下两种并发都有效。
import time, asyncio
from concurrent.futures import ThreadPoolExecutor

def fetch(i):
    time.sleep(0.05)                 # 模拟 IO 等待（会释放 GIL）
    return i

t0 = time.perf_counter()
[fetch(i) for i in range(100)]       # 串行
print("serial:", round(time.perf_counter() - t0, 2))

t0 = time.perf_counter()
with ThreadPoolExecutor(32) as ex:
    list(ex.map(fetch, range(100)))  # 线程池
print("threads:", round(time.perf_counter() - t0, 2))

6.2 踩坑记录

  • 坑把 fetch 换成纯计算：线程池耗时回升到接近串行——GIL 下 CPU 密集多线程无效，换 ProcessPoolExecutor 才并行；
  • 坑asyncio 版误用 time.sleep：整个循环卡住，耗时反超串行——换 await asyncio.sleep()。

6.3 成果与复盘

  1. 能力：亲手验证 GIL 行为边界与"阻塞卡死循环"，选型决策有了实验依据；
  2. 一句话抓手："做过串行/线程池/asyncio 下载对比实验，讲得清 GIL 限制什么不限制什么、什么场景换多进程、asyncio 里为什么不能写阻塞调用。"

7常见坑 & Debug

五条并发/性能高频坑。

7.1 事件循环里跑阻塞调用

现象：async def 里用 time.sleep/requests/重 CPU，所有任务一起卡。正解：换异步库（httpx/aiomysql）或 asyncio.to_thread() 丢线程池。

7.2 创建协程不 await

现象：fetch(1) 只得到协程对象，函数从未执行（无报错！）。Debug：RuntimeWarning "coroutine was never awaited" 是线索；并发 gather、单个 await。

7.3 进程池传不可序列化对象

现象：PicklingError——lambda/闭包/连接对象过不了 pickle。正解：模块顶层函数 + 纯数据参数；结果也按可序列化设计。

7.4 线程共享可变状态没加锁

现象：counter += 1 多线程下丢更新（读-改-写非原子）。正解：threading.Lock，或改用 queue.Queue 生产者消费者、每线程独立数据。

7.5 没测就优化

现象：凭感觉改，越改越慢。正解：cProfile/py-spy 定位 Top 热点 → 改一处 → timeit 验证——先测量后优化，瓶颈通常不在猜想处。

8重点讲解

Q1：GIL 是什么？限制什么？工程上怎么绕？

参考答案：GIL 是 CPython 的全局解释器锁——同一时刻一个进程内只有一个线程能执行 Python 字节码，根源是引用计数内存管理的线程安全简化。限制：CPU 密集多线程无法利用多核（8 核当 1 核）；不限制：IO 等待（网络/磁盘/锁等待）期间释放 GIL，多线程 IO 并发仍有效。绕法三路：①多进程（multiprocessing/进程池，独立解释器独立 GIL，代价是启动与 pickle 开销）；②asyncio（单线程事件循环，IO 密集高并发最优，不解决 CPU）；③C 扩展（numpy 等把热点下沉到无 GIL 的 C 代码）。部署层兜底：多进程 worker + 负载均衡。补充前沿：PEP 703 free-threaded 实验构建可关 GIL，但生态未熟，工程决策暂按 GIL 存在处理。

Q2：asyncio 与 JS 事件循环的异同？为什么 async 里不能写阻塞调用？

参考答案：同：都是单线程事件循环 + 协程/回调，await 让出控制权，适合 IO 密集高并发（切换成本远低于线程）。异：JS 的运行时天生事件循环（浏览器/Node 只此一条路），生态库全部异步化；Python 是双世界——同步库海量存在，async 里误用同步库（requests/time.sleep）就阻塞整个循环且无报错。因此铁律：循环内只允许非阻塞等待——要么用 async 生态库，要么 to_thread/run_in_executor 把阻塞活丢线程池。这点与 Node 事件循环"长任务阻塞一切"同病同解，也呼应 JVM 虚拟线程的"阻塞即让出"设计。

Q3：生成器/迭代器协议是什么？yield 解决什么问题？

参考答案：迭代器协议 = 实现 __iter__/__next__ 即可被 for 消费；生成器是协议的语法糖——含 yield 的函数，调用返回生成器对象，每次 next 推进到 yield 暂停，局部状态与执行位置都保留。解决：惰性求值与流式处理——10GB 日志逐行读逐行过滤，内存 O(1)；无限序列可行；管道组合（yield from 串联多级）。对照：Java Stream 的惰性中间操作、JS generator function 同构。工程点：大数据处理默认生成器管道，只在确需随机访问/多次遍历时才物化成 list。
