1简介与阅读指引

1.1 定位：为 IO 密集而生的单线程并发

asyncio 用一条线程 + 一个事件循环，把大量"等网络/等磁盘"的等待时间重叠掉。它不是多线程的替代品，而是另一套并发范式：线程由操作系统调度（抢占式），协程由程序自己调度（协作式，遇到 await 主动让出）。

对全栈工程师的价值：写高并发爬虫/网关聚合层、批量调 LLM API、WebSocket 长连接服务、FastAPI 的异步路由——这些场景下 asyncio 是主战场。

1.2 四种并发方案怎么选

方案核心机制适合场景代价 / 边界
同步（无并发）一条道走到黑CLI 脚本、一次性批处理IO 等待时 CPU 空转占用
多线程 threadingOS 抢占式切换IO 密集 + 无法改造的阻塞库线程开销、共享状态要加锁
多进程 multiprocessing多核并行CPU 密集（计算、图像处理）内存开销大、IPC 复杂
异步 asyncio单线程事件循环 + 协作式让出高并发 IO（万级连接、批量请求）一个阻塞调用拖垮整个循环
口诀：CPU 密集用进程，IO 密集用协程，改不动的阻塞库丢线程池——三者常混合使用。

1.3 与已有语言的对照

  • JS 开发者最轻松：async/await 语义几乎一致（Promise ↔ 可等待对象；Promise.all ↔ asyncio.gather）。差别是 JS 的事件循环由浏览器/Node 内置且永远在跑，Python 的循环要你显式创建并驱动（asyncio.run）。
  • Java 开发者：可对照虚拟线程（Project Loom）——Loom 让"阻塞"变廉价，asyncio 让"等待"变显式；CompletableFuture ≈ Task/Future。
  • 心智差Python 异步里没有"异步传染"的强制标注，但一旦某个函数是 async def，调用它的人也必须是 async——初学者最容易写出"协程对象没被 await"的静默 bug。

1.4 学习目标

  1. 建立事件循环 + await 让出点的心智模型（不是魔法，是"单线程多任务排队"）；
  2. 掌握 create_task / gather / TaskGroup 的并发编排与 wait_for 超时取消；
  3. 会用 Semaphore 限流、async with/async for 写异步资源与流式数据；
  4. 知道什么时候不该用 asyncio，以及阻塞代码怎么安全混入（to_thread）。

难度：★★★★☆。前置：函数、装饰器、生成器、上下文管理器；Python 3.10+（TaskGroup 需 3.11+）。

2核心模型

五个核心模型：协程对象→ 事件循环→ await = 让出点→ Task→ Future。

2.1 协程函数 vs 协程对象

async def 定义的是协程函数；调用它不会执行函数体，只返回一个协程对象（像生成器函数返回生成器）。关键函数体只在被 await、被包成 Task、或被 asyncio.run 驱动时才真正运行。

import asyncio

async def greet():                 # 协程函数
    print("hello")                 # 只有被驱动时才执行
    return 42

coro = greet()                     # 只是创建对象，没有输出
print(type(coro))                  # <class 'coroutine'>
asyncio.run(greet())               # 真正执行
忘记 await 的代价：greet() 写了却不 await，代码静默不执行，还会收到 RuntimeWarning: coroutine ... was never awaited——这是新手第一坑。

2.2 事件循环（Event Loop）

事件循环是一个单线程调度器：维护一个"就绪队列"和一堆"等待 IO 的回调"。它循环做三件事：取就绪任务执行 → 遇到 await 让出 → 检查 IO 完成并唤醒对应任务。asyncio.run() = 创建循环 + 驱动主协程 + 收尾关闭，是程序唯一的异步入口。

2.3 await 是"让出点"，不是"等死"

await some() 的语义是：如果 some() 还没好，就挂起当前协程、把控制权还给事件循环，让循环去跑别的任务；好了再回来。所以异步提速的本质是"等待时间被别人拿去干活了"，而不是 CPU 变快了。

2.4 Task：被循环托管的协程

asyncio.create_task(coro) 把协程注册进循环并立即排队——从此它会在后台推进，你拿着返回的 Task 对象在需要结果的地方 await task。对照直接 await coro() 是顺序执行（一个完了才下一个）；create_task 才能并发。

2.5 Future：结果的占位符

Future 是"将来会有的结果"的容器，Task 是 Future 的子类（协程版实现）。业务代码一般只用 Task 就够了；Future 主要出现在底层库和 loop.run_in_executor 等桥接场景。await future 就是等结果并拿到值或异常。

3核心用法（按场景）

3.1 场景一：顺序 await vs 并发 gather

import asyncio, time

async def job(t):                  # 模拟一次 1 秒的网络/IO 等待
    await asyncio.sleep(t)
    return t

async def main():
    t0 = time.perf_counter()
    r1 = await job(1)              # 顺序：1s
    r2 = await job(1)              # 再 1s
    print("串行", time.perf_counter() - t0)          # ≈ 2.00s

    t0 = time.perf_counter()
    out = await asyncio.gather(job(1), job(1))        # 并发
    print("并发", time.perf_counter() - t0, out)      # ≈ 1.00s [1, 1]

asyncio.run(main())

要点：asyncio.sleep() 是异步睡眠（让出控制权），而 time.sleep() 会阻塞整条线程——异步代码里必须用前者。

3.2 场景二：create_task 手动编排

async def main():
    t1 = asyncio.create_task(job(1))     # 立刻排入循环，后台推进
    t2 = asyncio.create_task(job(2))
    print("任务已发起，可以先干别的")
    a = await t1                          # 需要结果时再等
    b = await t2                          # 总耗时 ≈ max(1, 2) = 2s
    return a, b
选型：任务数量固定、要统一收集结果 → gather；要"边发边干别的"、或任务动态产生 → create_task 后自己 await。

3.3 场景三：超时与取消

async def fetch_with_timeout(coro, timeout=3):
    try:
        return await asyncio.wait_for(coro, timeout)
    except asyncio.TimeoutError:
        print("超时，走降级/兜底逻辑")
        return None

task = asyncio.create_task(slow_job())
task.cancel()                       # 主动取消
try:
    await task
except asyncio.CancelledError:      # 取消也是异常，必须能被向外传播
    print("已被取消")
取消的本质：cancel() 会在目标协程下一个 await 点抛出 CancelledError。所以协程里如果长时间没有任何 await（比如写了个同步大循环），就取消不掉。

3.4 场景四：Semaphore 限流（保护下游）

async def fetch_all(urls, limit=10):
    sem = asyncio.Semaphore(limit)          # 同时最多 10 个在飞

    async def one(url):
        async with sem:                     # 拿到许可才继续
            return await fetch(url)         # 假设是 aiohttp 请求
    return await asyncio.gather(*(one(u) for u in urls))

实战批量调第三方 API（含 LLM）必须限流，否则要么被限频 429、要么把对方打挂。

3.5 场景五：异步上下文管理器与异步迭代器

async with aiohttp.ClientSession() as session:      # 异步资源自动关闭
    async with session.get(url) as resp:
        data = await resp.json()

async for line in tail_file(path):                  # 异步迭代：一行来了就处理
    print(line)

协议：对象实现 __aenter__/__aexit__ 就能 async with；实现 __aiter__/__anext__ 就能 async for。对照同步的 with / for，只是每个钩子都换成 await 版。

3.6 场景六：gather 的错误处理

results = await asyncio.gather(*coros, return_exceptions=True)
for r in results:
    if isinstance(r, Exception):        # 逐个判断，不因一个失败丢掉全部结果
        log(r)
    else:
        handle(r)

坑gather 默认 return_exceptions=False：一个任务抛异常，gather 立刻抛出，其余任务仍在后台跑但结果被丢弃。批量任务务必加 return_exceptions=True。

4进阶知识点【深入】

4.1 TaskGroup（Python 3.11+，推荐的结构化并发）

async def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(job(1))
        t2 = tg.create_task(job(2))
    # 退出 async with 时，所有子任务必已完成（或被取消）
    print(t1.result(), t2.result())        # 结果在这里才可用

结构化并发：with 块结束时保证所有子任务收尾——不会出现"主协程结束了，后台 task 还在跑"的孤儿任务。其中一个任务异常，其余会被自动取消并抛出 ExceptionGroup。

4.2 asyncio.timeout：更现代的超时写法

async def main():
    try:
        async with asyncio.timeout(5):       # 3.11+，作用于整个代码块
            await job(1)
            await job(10)                    # 整体 5 秒预算，不是每个 5 秒
    except TimeoutError:
        print("整块超时")

对照wait_for 作用于单个 await；asyncio.timeout 作用于一段代码的总预算，且天然支持嵌套。

4.3 阻塞代码混入：to_thread / run_in_executor

async def main():
    # 把同步阻塞函数丢到线程池，避免堵死事件循环
    data = await asyncio.to_thread(blocking_parse, big_file)   # 3.9+
    # 等价旧写法：
    # data = await asyncio.get_running_loop().run_in_executor(None, blocking_parse, big_file)
CPU 密集的边界：to_thread 受 GIL 限制，纯计算仍无法多核并行；真要吃多核，用 ProcessPoolExecutor：loop.run_in_executor(ProcessPoolExecutor(), cpu_fn, args)。

4.4 同步原语与队列

异步版原语：asyncio.Queue（生产者-消费者，背靠背限流）、asyncio.Event（信号通知）、asyncio.Lock（临界区）。注意这些是协程级原语，不能保护线程间共享数据——跨线程仍用 threading.Lock。

q = asyncio.Queue(maxsize=100)     # 背压：满了生产者 await 等待
await q.put(item)
item = await q.get()
q.task_done()

4.5 调试：asyncio 的慢回调告警

PYTHONASYNCIODEBUG=1 python app.py          # 开启调试模式：报告慢回调、未 await 协程
loop.set_debug(True)
loop.slow_callback_duration = 0.1           # 超过 100ms 的回调打日志

性能排查第一招：开 debug 看"哪个回调占住了循环"——99% 的异步性能问题是某处混入了阻塞调用。

读图要点：①三个 Task 在同一线程内交替推进；②决定快慢的是"等待是否重叠"，不是 CPU 核数；③红框是 asyncio 唯一的死穴——任何阻塞调用都会让整条循环停摆。

5.2 一句话原理：asyncio 的三个"不是"

  • 不是多线程：默认单线程，没有锁竞争，但也吃不到多核；
  • 不是自动并发：只有被 create_task/gather 显式编排才并发，顺序 await 仍是串行；
  • 不是万能加速：只加速"等待"，不加速"计算"。

6最小可运行 Demo

性质（诚实声明）：本篇为可运行的教学 demo（并发 HTTP 请求方向），需 pip install aiohttp，非生产履历。

6.1 Demo 设计：并发抓取并统计耗时

  • 目标：并发请求 N 个 URL，带并发上限与单请求超时，统计成功/失败与总耗时；
  • 验证：把 limit 改成 1 观察退化成串行，体会"限流 = 并发度预算"。
import asyncio, time, aiohttp

URLS = ["https://example.com"] * 20

async def fetch(session, sem, url):
    async with sem:                                   # 限流：同时最多 5 个
        try:
            async with asyncio.timeout(5):            # 单请求 5s 预算（3.11+）
                async with session.get(url) as resp:
                    return resp.status
        except TimeoutError:
            return "timeout"
        except aiohttp.ClientError as e:
            return f"error:{type(e).__name__}"

async def main():
    sem = asyncio.Semaphore(5)
    t0 = time.perf_counter()
    async with aiohttp.ClientSession() as session:    # 连接池复用
        results = await asyncio.gather(
            *(fetch(session, sem, u) for u in URLS),
            return_exceptions=True,
        )
    print(f"{len(URLS)} 个请求耗时 {time.perf_counter()-t0:.2f}s")
    ok = sum(1 for r in results if r == 200)
    print(f"成功 {ok} / 失败 {len(URLS)-ok}")

if __name__ == "__main__":
    asyncio.run(main())

6.2 踩坑记录

  • 坑用 requests.get 替换 aiohttp 后耗时回到串行量级——requests 是同步阻塞库，异步里必须用 aiohttp/httpx；
  • 坑每个请求都新建 ClientSession 导致连接无法复用、握手开销巨大——整个应用共享一个 session；
  • 坑没加 Semaphore 时 20 个变 2000 个会直接被对端限频或本机端口耗尽。

6.3 成果与复盘

  1. 能力：事件循环、Task 编排、限流、超时取消一条龙写通；能判断某段代码该不该异步化；
  2. 一句话抓手："用 asyncio + aiohttp 写过并发抓取，Semaphore 限流、timeout 超时取消、gather 收集结果；理解它只省等待时间，CPU 密集要上进程池。"

7常见坑 & Debug

7.1 协程对象没被 await

现象：代码没执行、只出现 RuntimeWarning: coroutine 'x' was never awaited。正解：await x() 或 asyncio.create_task(x())；开 PYTHONASYNCIODEBUG=1 让告警变醒目。

7.2 在 async 函数里调用阻塞库

现象：并发毫无加速，甚至比同步慢（还多了调度开销）。排查：开 loop.set_debug(True) 看慢回调；正解：换异步库（aiohttp/httpx/asyncpg/aiomysql），或用 asyncio.to_thread() 包一层。

7.3 顺序 await 伪装成并发

现象：await f1(); await f2() 写成了串行还以为在并发。正解：要并发必须 gather / TaskGroup / create_task；用 time.perf_counter() 实测总耗时验证是否等于 max 而非 sum。

7.4 孤儿任务被垃圾回收

现象：asyncio.create_task(...) 后不保存返回值，任务可能在完成前被 GC 掉，日志出现 "Task was destroyed but it is pending"。正解：始终持有 task 引用；或用 TaskGroup 让生命周期由 with 块托管。

7.5 吞掉 CancelledError

现象：except Exception: 把 CancelledError 一起吞了，导致取消失效、程序退出时卡住。正解：Python 3.8+ 的 CancelledError 继承自 BaseException，不要用裸 except Exception 包裹 await；确需捕获时要重新抛出。

7.6 事件循环不可重入

现象：RuntimeError: asyncio.run() cannot be called from a running event loop（常见于 Jupyter/已有异步框架内）。正解：一个线程一个循环；在已运行的循环里用 await 而不是再 run；Jupyter 可直接 await 顶层协程。

8重点讲解

Q1：asyncio 到底是怎么"并发"的？和多线程有什么本质区别？

参考答案：asyncio 是单线程内的协作式多任务。协程在 await 处主动让出控制权，事件循环（基于 selector/epoll）负责在 IO 就绪时把它放回就绪队列继续执行；整个过程中只有一条 OS 线程，切换由用户代码控制（协作式），没有线程切换与锁竞争。多线程是抢占式：OS 随时可能打断线程，共享数据必须加锁。因此：asyncio 在高并发 IO（成千连接）下开销极低、吞吐高；但只要混入一个阻塞调用，整条循环就停摆。多线程能容纳阻塞代码，代价是内存与上下文切换、以及共享状态的并发安全问题。落地选择：IO 密集 → asyncio；CPU 密集 → 进程池；改不动的阻塞库 → 线程池 to_thread。

Q2：asyncio.gather 与 create_task + await 怎么选？异常怎么处理？

参考答案：gather 适合任务集合已知、要统一收集结果的场景，返回按传入顺序排列的结果列表；create_task 更灵活——任务可以动态产生、可以先发起后处理（发起后做别的再 await）。异常：gather 默认第一个异常就会抛出（其余结果丢失、任务仍在后台跑），批量任务必须加 return_exceptions=True 后逐个 isinstance(r, Exception) 判断。Python 3.11+ 推荐 asyncio.TaskGroup：async with 退出时保证子任务全部收尾（结构化并发，无孤儿任务），异常以 ExceptionGroup 抛出，可用 except* 分别处理。

Q3：为什么异步代码里不能用 time.sleep/requests？怎么救？

参考答案：这些是同步阻塞调用，会把整条线程（连同事件循环）卡住，期间所有其他协程都得不到执行——并发彻底退化为串行，且没有任何报错提示。三种解法：①换异步库（最优）：asyncio.sleep、aiohttp/httpx.AsyncClient、asyncpg、aiomysql、aiofiles；②丢线程池：await asyncio.to_thread(blocking_fn, *args)，适合没有异步替代品的库；③CPU 密集则丢进程池：loop.run_in_executor(ProcessPoolExecutor(), fn, args)。排查手段：PYTHONASYNCIODEBUG=1 或 loop.set_debug(True) + slow_callback_duration，慢回调日志会直接指出是哪一行堵住了循环。
