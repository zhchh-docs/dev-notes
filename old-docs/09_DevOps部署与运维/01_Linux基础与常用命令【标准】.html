1简介与阅读指引

1.1 定位

Linux 是绝大多数服务器的操作系统——前端产物、后端服务、数据库都跑在它上面。本篇的立场：前端不需要成为运维，但必须能在 SSH 上完成基本运维动作——部署文件、看日志、查进程、查端口、改权限。本篇不堆命令，按"排障流程 + 用途分类速查"组织，并用一次真实的部署排障收尾。

1.2 痛点

  • 线上"页面打不开"只能干猜——不知道还能上服务器自己看；
  • 命令会敲但不成体系：不知道"先查什么后查什么"，一次排障半小时；
  • 权限/端口/防火墙三类根因反复踩，每次都像第一次。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要把前端产物部署到 Linux 服务器并负责一线排障Shell 脚本编程 → 本模块 02 篇

面试（chmod 755、查端口、排障顺序是高频题）Linux 系统管理深耕 → 运维方向

2核心模型

三个核心模型：一切皆文件（世界观）→ 权限模型（部署第一坑）→ 进程与日志（排障主场）。

2.1 一切皆文件

Linux 里设备、进程信息、配置大多抽象成文件——日志是读文件、端口是查文件句柄、配置是改文件。抓住这一点就理解了线上排障为什么都是"读文件、查句柄、改文件"：没有神秘的黑盒，只有你还没找到的文件。

2.2 权限模型：rwx 与数字表示

每个文件有属主/属组/其他人三组身份，各持 r/w/x 三种权限（读=4、写=2、执行=1，数字相加表示）。chmod 改权限、chown 改属主。权限不对是部署高频根因——上传文件属主是 root，Nginx 读不到 → 403。

图 2 rwx 权限数字拆解（示意）

2.3 进程与服务：systemd 时代

现代 Linux 用 systemd 管理服务：查服务状态优先 systemctl status nginx（还能看到最近日志片段），而不是 ps 里瞎猜。ps -ef 查进程、top/htop 看资源占用。区分"服务"与"进程"：systemctl 管的是注册过的服务（有开机自启、日志聚合），裸起的进程只有 ps 能看到——这也是"为什么我起的进程重启后没了"的原因（没注册成服务）。

3命令分类速查

按用途背场景，不按字母背命令。每条命令都对应一个排障动作。

3.1 文件与目录

命令作用
ls -lh列目录，人性化大小
cd / pwd进目录 / 看当前路径
cp / mv / rm拷贝 / 移动 / 删除（rm -rf 高危）
tar -zxvf解压 tar.gz
tail -f app.log实时跟踪日志
grep -rn "err" .递归搜关键词

3.2 进程与端口

命令作用
systemctl status nginx查服务状态
systemctl restart nginx重启服务
ss -ltnp列监听端口及对应进程
ps -ef | grep java找 java 进程
kill -9 PID强杀进程（慎用，最后手段）

3.3 权限与部署

命令作用
chmod 755 deploy.sh给脚本加执行权限
chown nginx:nginx dist改文件属主，让 Nginx 能读（运行用户随发行版：CentOS/RHEL 是 nginx，Debian/Ubuntu 是 www-data，先 ps -ef | grep nginx 确认实际 worker 用户再 chown，别写死）
scp file user@ip:/path本地上传文件到服务器
df -h / free -h看磁盘 / 内存占用

4进阶知识点【进阶】

首次学习可整章跳过。前置：第 3 章命令已顺手。

4.1 journalctl：systemd 服务的统一日志入口

systemd 服务的日志不都在 /var/log 下——journalctl -u nginx -f 跟踪指定服务的日志、--since "10 min ago" 按时间过滤。service 类问题先 journalctl 再翻文件，能省一半时间。

4.2 文本三剑客：grep / sed / awk 的分工

日志处理进阶三件：grep 找行、sed 改文本（批量替换/按行删除）、awk 取列（awk '{print $1}' 按空格切列）。前端够用的组合：grep 找到错误行 → awk 取出其中的耗时/URL 字段 → sort/uniq -c 统计频次——一条管道完成简易日志分析。

4.3 nohup 与后台运行

SSH 断开进程就死？nohup node app.js & 让进程脱离会话存活，输出进 nohup.log。更正规的做法：注册成 systemd 服务（Restart=always 自动拉起）——裸 nohup 只是临时方案，进程挂了没人管。

4.4 crontab 定时任务

crontab -e 编辑，五行表达式（分 时 日 月 周）+ 命令——日志切割、定时备份的标配。坑：cron 的环境变量与登录 shell 不同，路径写绝对路径、输出重定向到日志文件以便排查。

5排障流程图

图 1 线上排障的标准定位路径（示意）

四步排查链的展开：①systemctl status nginx 看服务起没起；②ss -ltnp 看 80 端口听没听、被谁占；③tail -f 看 Nginx/应用日志报什么错；④对症修复（重启服务/改配置/改权限/放端口）。前端部署场景三类最高频根因：权限不对（Nginx 读不到 dist）、端口被旧进程占、防火墙没放行。顺序的意义：从外到内排除——服务没起就不用查权限，端口没听就不用看日志，每一步都在缩小范围。

6最小可运行 Demo

15 分钟部署排障演练：把前端 dist 部署到服务器并修好"页面打不开"。全程用第 3 章命令 + 第 5 章排查链。

6.1 完整流程

# ① 上传产物（本地执行）
scp dist.zip user@10.0.0.5:/tmp/

# ② 登录后：解压到 Nginx 站点目录
cd /usr/share/nginx/html
tar -zxvf /tmp/dist.zip -C .

# ③ 访问失败！开始排查链——
# 3.1 服务起没起？
systemctl status nginx          # → active (running)，服务没问题
# 3.2 端口听没听？
ss -ltnp | grep :80             # → LISTEN 0.0.0.0:80 nginx，端口没问题
# 3.3 日志报什么？
tail -f /var/log/nginx/error.log
# → "open() /usr/share/nginx/html/index.html failed (13: Permission denied)"
#    ↑ 权限问题实锤！
# 3.4 修权限：先看 Nginx worker 的实际用户
ps -ef | grep nginx             # → worker 用户是 nginx
chown -R nginx:nginx /usr/share/nginx/html
# ④ 页面恢复 ✓

6.2 逐段解析

  • 排查链的顺序价值：前两步各花 10 秒就排除了服务/端口，日志直接给出 Permission denied——比全服务器翻一遍快 10 倍；
  • 先确认 worker 用户再 chown：CentOS 是 nginx、Ubuntu 是 www-data——写死属主在另一个发行版上就是新的坑；
  • error.log 是权限问题的实锤来源：403 的浏览器侧信息量为零，服务器日志才有一切。

6.3 生产改造扩展方向

  1. 把这套排查链写成 deploy.sh 一键部署脚本（衔接 02 Shell 篇）；
  2. 加上防火墙检查（firewall-cmd --list-ports）作为排查链第 0 步；
  3. 部署后自动 curl 探活，失败输出排查链提示。

7常见坑 & Debug

六条高频坑，每条五要素。

7.1 坑 1：rm -rf 路径写错

  • 现象：删错目录，轻则丢部署产物，重则丢系统文件；
  • 根因：带变量/通配符的路径没展开验证，手滑；
  • 复现：rm -rf $DIR/* 而 DIR 为空时等于 rm -rf /*；
  • 修复：删除前先 pwd + ls 确认目标真实存在；
  • 规避：脚本里 rm -rf "$DIR/"* 加引号并判空；高危命令纪律写进团队规范。

7.2 坑 2：权限不对读不到（403）

  • 现象：部署完 403 或空白页；
  • 根因：上传文件属主是 root（或权限 600），Nginx worker 用户读不到；
  • 复现：error.log 见 Permission denied；
  • 修复：chown 给 Nginx 实际运行用户 + 目录保证 x 可进入；
  • 规避：部署脚本里固定 chown 步骤。

7.3 坑 3：端口被旧进程占

  • 现象：新服务起不来，报 Address already in use；
  • 根因：旧进程还活着占着端口；
  • 修复：ss -ltnp 找到占用进程 → 优先正常停（systemctl stop），kill -9 只作最后手段；
  • 规避：启动脚本里先检查端口再启动。

7.4 坑 4：改配置不校验就 reload

  • 现象：Nginx 改完 reload，服务挂了整站 502；
  • 根因：配置语法错误，reload 失败且旧配置未保住；
  • 修复：永远先 nginx -t 校验再 reload；
  • 规避：把 nginx -t 写进部署脚本，校验不过直接退出。

7.5 坑 5：kill -9 滥用

  • 现象：强杀后数据文件损坏、临时文件残留；
  • 根因：kill -9 不给进程清理机会（SIGKILL 不可捕获）；
  • 修复：优先 systemctl stop 或 kill（SIGTERM，允许优雅退出）；
  • 规避：kill -9 只在进程完全僵死后作为最后手段。

7.6 坑 6：SSH 断开进程就死

  • 现象：SSH 里起的进程，断开连接后就没了；
  • 根因：进程随会话收到 SIGHUP；
  • 修复：临时用 nohup cmd &，正规做法注册 systemd 服务（4.3）；
  • 规避：任何要长期存活的服务不裸起。

8重点讲解

Q1：755 是什么意思？644 呢？什么时候用哪个？

参考答案：三位数字分别对应属主/属组/其他人，每位是 r(4)+w(2)+x(1) 的和。755 = 属主 rwx、属组与其他人 r-x——目录和需要执行的东西（脚本、可执行文件）用它；644 = 属主 rw、其他人 r——普通文本文件（配置、日志）用它，不需要执行位。

追问：部署后 403 一般是什么原因？——Nginx worker 用户读不到文件：属主不对（chown 修）或目录没有 x 权限（不可进入）。先 ps 确认 worker 实际用户（发行版差异）再修。

Q2：线上页面打不开，你的排查步骤？

参考答案：四步排查链，从外到内——①systemctl status nginx 服务状态；②ss -ltnp | grep :80 端口监听；③tail -f error.log 看报错（403 权限/502 后端挂/404 路径错各有特征）；④对症修复。

面试官想听的：顺序感（每步缩小范围）与高频根因库（权限/端口占用/防火墙）——而不是罗列命令。能补一句"防火墙没放行"作为第 0 步（外部可达性）更加分。

Q3：怎么找到占用 80 端口的进程？kill -9 有什么问题？

参考答案：ss -ltnp | grep :80（或 lsof -i:80）直接显示监听进程与 PID。kill -9 的问题：SIGKILL 不可捕获，进程没有机会清理——数据文件损坏、子进程残留、锁未释放。正确姿势：优先 systemctl stop（服务）或 kill（SIGTERM，允许优雅退出），kill -9 只对完全僵死的进程作最后手段。
