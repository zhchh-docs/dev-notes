Docker Compose 多容器编排

标准 定位：服务名即 DNS / 数据卷分离 / 健康等待

Docker Compose 用一个 YAML 描述一组容器、一条命令整组起停——本地与测试环境的多容器标配。本篇讲透三个核心模型：服务声明（部署说明书）、容器网络（服务名即 DNS，localhost 是头号坑）、数据卷分离（数据库用命名卷、配置用绑定挂载），并给 healthcheck + depends_on.condition 解决"顺序≠就绪"。配四容器（Nginx+API+MySQL+Redis）一键起 Demo 与五条高频坑。

1简介与阅读指引

1.1 定位

Docker Compose 是"用一个 YAML 文件描述一组容器，一条命令整组起停"的编排工具——单机多容器的标配。前端的典型场景：本地/测试环境要同时跑前端 Nginx + 后端 API + MySQL + Redis，四条 docker run 参数各一大串——Compose 把它们收敛成一个文件，docker compose up -d 一键全起。

1.2 痛点

  • 多条 docker run 手敲：参数长、顺序敏感、换台机器就配错；
  • 容器间怎么互访（localhost 不通！）不知道——网络是新手第一堵墙；
  • MySQL 数据没挂卷，容器一删数据全没。

1.3 适用 / 不适用场景

适合用 Compose不适合（看别的）
本地开发环境、单机测试环境、演示环境多机集群/自动扩缩容 → 07 Kubernetes
单容器应用想省参数 → 也值得写 compose镜像构建细节 → 05 Docker 篇
面试（容器互访/数据卷/depends_on 是高频）CI/CD 流水线 → 08 篇

1.4 学习目标：读完本篇你能

  1. 写出四容器（Nginx/API/MySQL/Redis）的 compose.yml：构建、端口、数据卷、环境变量、依赖关系；
  2. 理解容器网络：compose 自动建网，服务名就是 DNS——容器互访用服务名不用 localhost；
  3. 用 healthcheck + depends_on.condition 解决"后端起在 MySQL 前面"的经典问题；
  4. 掌握五条高频坑（localhost 误区、数据卷丢失、启动顺序等）。

2核心模型

三个核心模型：服务声明（compose.yml 怎么读）→ 容器网络（服务名即 DNS，全篇最重要）→ 数据卷（状态持久化）。

2.1 服务声明：一个 service = 一组容器

compose.yml 的顶层三段：services（每个服务 = 镜像/构建/端口/卷/环境变量/依赖）、networks（默认自动建，一般不用手写）、volumes（命名卷声明）。docker compose up -d 按 yml 创建整组容器与网络；down 整组删除（-v 连卷一起删——小心数据）。心智模型：compose.yml 就是"这台机器的部署说明书"，可提交进仓库、可复现。

2.2 容器网络：服务名就是 DNS（全篇最重要）

Compose 自动创建一个网络，把所有服务加进去，且每个服务可以用"服务名"当域名互相访问——后端容器连数据库写 mysql:3306，不是 localhost:3306！localhost 在容器里指容器自己。这一条是 Compose 新手的第一个大坑（坑 1），也是理解容器网络的钥匙：每个容器有独立网络栈，"跨容器访问"本质是 DNS 解析到对方容器 IP。

2.3 数据卷：状态与容器分离

容器是可抛奔的，数据必须在卷里：命名卷（mysql_data:，由 Docker 管理，适合数据库文件）与绑定挂载（./nginx.conf:/etc/nginx/nginx.conf，宿主机路径直接映射，适合配置文件与前端 dist）。原则：数据库用命名卷，配置用绑定挂载；down -v 会删命名卷——生产操作禁用或三思。

3核心用法（按场景）

3.1 场景一：常用命令四件套

docker compose up -d        # 按 yml 启动整组（后台）
docker compose ps           # 看组内容器状态
docker compose logs -f api  # 跟踪某服务日志
docker compose down         # 停止并删除整组（保留卷）
docker compose up -d --build api   # 只重建并重启 api 服务

3.2 场景二：改配置只重启单个服务

改了 yml 里某个服务的配置或代码：docker compose up -d --build <服务名>——只重建该服务，其他容器不动。改了配置文件（绑定挂载）甚至只需 restart——这是绑定挂载开发体验好的原因。

3.3 场景三：查看与调试网络

docker compose exec api ping mysql    # 验证服务名解析
docker network ls                     # 看自动创建的网络
docker compose exec mysql mysql -uroot -p   # 进容器内调试

4进阶知识点【进阶】

首次学习可整章跳过。前置：第 6 章 Demo 已跑通。

4.1 healthcheck + depends_on.condition：真正的"等待就绪"

depends_on 默认只保证启动顺序（MySQL 容器先起），不保证服务就绪（MySQL 进程能接连接要再等几秒）——后端起来就连库失败。解法：MySQL 加 healthcheck（探测 mysqladmin ping），后端 depends_on 用 condition: service_healthy——等健康才启动。这是 6.4 生产改造的核心一步。

4.2 .env 变量化：一份 yml 多环境用

yml 里写 MYSQL_PASSWORD: ${MYSQL_PASSWORD}，同目录 .env 提供值——密码/端口等环境差异不进仓库。compose 自动读同目录 .env；不同环境给不同 .env，yml 不改一行。

4.3 profiles：按需启动部分服务

profiles: ["dev"] 标记可选服务——docker compose --profile dev up 才启动。用途：默认只起核心服务，调试工具（phpMyAdmin/mailhog）按需开。

4.4 override 文件：基础与差异分层

docker compose -f compose.yml -f compose.prod.yml up——后者覆盖前者。实践：compose.yml 放公共定义，compose.prod.yml 只放生产差异（资源限制、镜像 tag）。比维护两份完整 yml 干净得多。

6最小可运行 Demo

四容器本地开发环境：Nginx（前端）+ API（后端）+ MySQL + Redis，10 分钟一键起。

6.1 compose.yml 完整文件

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"                                   # 唯一对外出口
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf   # 配置：绑定挂载
      - ./dist:/usr/share/nginx/html                  # 前端产物：绑定挂载
    depends_on:
      - api

  api:
    build: ./backend                               # 用 Dockerfile 构建
    environment:
      - DB_HOST=mysql                              # ⭐ 服务名，不是 localhost！
      - DB_PASSWORD=${MYSQL_PASSWORD}              # 从 .env 读
      - REDIS_HOST=redis
    depends_on:
      mysql:
        condition: service_healthy                 # 等 MySQL 健康
      redis:
        condition: service_started

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_PASSWORD}
      MYSQL_DATABASE: app
    volumes:
      - mysql_data:/var/lib/mysql                  # ⭐ 数据：命名卷
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  mysql_data:
  redis_data:

6.2 配套 nginx.conf（关键一行）

location /api/ {
    proxy_pass http://api:8080;    # ⭐ 容器网络里用服务名，不是 localhost
}

6.3 启动与验证

echo "MYSQL_PASSWORD=secret123" > .env    # 环境变量不进仓库
docker compose up -d
docker compose ps                          # 四个容器都 Up（api 要等 mysql healthy）
curl http://localhost/                     # 前端页面 ✓
curl http://localhost/api/health           # 后端探活 ✓（nginx → api 服务名转发）

6.4 逐段解析

  • 端口只映射 nginx：80 对外，其余容器纯内网——攻击面最小；
  • 两类挂载分工：nginx 配置与 dist 用绑定挂载（改了即生效/重启生效），数据库用命名卷（Docker 管理生命周期）；
  • healthcheck + condition：api 等到 MySQL 真正能接连接才启动——消灭"起太快连库失败"；
  • .env 变量化：yml 可提交仓库，密码留本地。

6.5 生产改造扩展方向

  1. 加 override 文件区分 dev/prod（4.4）：prod 用镜像 tag 而非本地构建；
  2. 全服务加 healthcheck；
  3. 数据备份：cron 定时 docker compose exec mysql mysqldump 到宿主机（衔接 01 篇 crontab）。

7常见坑 & Debug

五条高频坑，每条五要素。

7.1 坑 1：容器互访写 localhost

  • 现象：后端连数据库报 Connection refused，宿主机 telnet 却通；
  • 根因：容器里的 localhost 是容器自己——跨容器必须走 compose 网络；
  • 复现：docker compose exec api ping mysql（通）vs 容器内 curl localhost:3306（不通）；
  • 修复：连接串全部改服务名（mysql/redis）；
  • 规避：所有容器内配置文件禁出现 localhost 指向别的服务。

7.2 坑 2：数据没挂卷，down 后丢失

  • 现象：down 再 up，数据库表全没了；
  • 根因：数据写在容器可写层，容器删除即销毁；
  • 修复：数据库目录挂命名卷（6.1）；
  • 规避：有状态服务（DB/队列/上传目录）评审时必查卷；down -v 会删卷，生产禁用。

7.3 坑 3：depends_on 只管顺序不管就绪

  • 现象：加了 depends_on: mysql，api 起来还是连库失败；
  • 根因：depends_on 默认只等容器启动，MySQL 进程初始化（初始化库表）要数秒；
  • 修复：MySQL 加 healthcheck + condition: service_healthy（4.1）；或 api 侧重试连接；
  • 规避："依赖数据库的服务"默认带健康等待。

7.4 坑 4：改了文件不生效

  • 现象：改了后端代码/yml，容器行为没变；
  • 根因：镜像构建的服务不会自动吸收新代码——需要 rebuild；yml 改动需要 up 重建对应容器；
  • 修复：docker compose up -d --build api 只重建该服务；
  • 规避：开发期后端代码走绑定挂载 + 热重载，避免频繁 rebuild。

7.5 坑 5：yml 缩进/枚举名错误

  • 现象：up 报 yaml 解析错误或 services.xxx 不存在；
  • 根因：YAML 对缩进敏感；旧教程用 version 字段/第一版命令 docker-compose（新版已并入 docker compose 子命令）；
  • 修复：检查缩进（统一 2 空格）；新版 Compose 无需 version 字段，命令用 docker compose（空格）；
  • 规避：编辑器装 YAML 校验插件；以官方最新文档为准。

8重点讲解

Q1：Compose 里容器之间怎么互访？为什么不能用 localhost？

参考答案：Compose 自动创建网络并把所有服务接入，每个服务名注册为该网络的 DNS——容器互访直接用服务名（mysql:3306、http://api:8080）。不能用 localhost：每个容器有独立网络栈，容器里的 localhost 指容器自身回环，不是宿主机也不是其他容器。

追问：容器访问宿主机服务呢？——用 host.docker.internal（Docker Desktop/新版引擎支持）或宿主机内网 IP。

Q2：depends_on 解决了什么？没解决什么？怎么补？

参考答案：depends_on 解决启动顺序（被依赖的容器先创建启动）；不解决就绪——MySQL 容器"启动"到"能接连接"之间有初始化窗口。补法：healthcheck 定义健康探测 + depends_on 的 condition: service_healthy，依赖方等到健康才启动；应用侧再加连接重试兜底。

这题考的分寸感：知道 depends_on 的边界比会写 yml 更重要——"顺序 ≠ 就绪"是分布式系统的一般规律在单机的缩影。

Q3：命名卷和绑定挂载怎么选？down 会删数据吗？

参考答案：命名卷（volumes 顶层声明）由 Docker 管理路径与生命周期——适合数据库文件等纯数据；绑定挂载（宿主机路径:容器路径）直接映射——适合配置文件、前端产物等"人要编辑"的东西。down 默认保留卷；down -v 连命名卷一起删——生产环境禁用或三思。数据备份永远不依赖"卷还在"——定期 mysqldump 导出。

Q4：自测 5 问

  1. compose.yml 顶层三段是什么？为什么说它是"部署说明书"？
  2. 容器互访用什么地址？localhost 在容器里指什么？
  3. 绑定挂载 vs 命名卷的分工？down 与 down -v 的区别？
  4. healthcheck + condition: service_healthy 解决什么问题？
  5. 改了后端代码为什么不生效？正确的重建命令？
