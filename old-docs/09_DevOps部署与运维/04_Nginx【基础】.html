Nginx

基础 定位：try_files 回退 / 反代跨域 / 缓存分层

Nginx 一台机器干三件事：托管静态资源、反向代理 /api（同源自然不跨域）、gzip 与缓存分层。本篇讲透 SPA 部署三件套——try_files 回退（刷新 404 的原理与救法）、反代跨域的因果本质、hash 资源长缓存 + index.html 不缓存的分层策略，并给 nginx -t 先行等四条高频坑的工程对策。配 10 分钟本地部署 Demo 与四项验证清单。

1简介与阅读指引

1.1 定位

Nginx 是高性能的 Web 服务器 / 反向代理——前端部署绕不开的一层：构建出的 HTML/JS/CSS 没法"直接放网上"，要靠 Nginx 托管静态资源；前端调后端有跨域，要靠 Nginx 反向代理 /api；加载慢，靠它 gzip 压缩与缓存分层。一台 Nginx 同时干这三件事，是前端部署的最小完整架构。

1.2 痛点

  • SPA 刷新二级路由就 404——前端路由不是服务器文件，Nginx 找不到对应文件；
  • 发版后用户还是旧版——缓存策略配反了（index.html 被长缓存）；
  • 写了 gzip on; 却没效果——Nginx 默认只压 HTML。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要把 Vue/React SPA 部署到服务器（托管+反代+缓存）容器化部署 → 本模块 05/06 篇
排查"刷新 404/发版不更新/跨域"三类问题负载均衡架构深耕 → 运维方向
面试（try_files/反向代理跨域/缓存分层是高频题）Windows 服务器 → 本篇不涉及

1.4 学习目标：读完本篇你能

  1. 写出一份最小可用的 SPA 部署配置（托管 + try_files 回退 + 反代 + gzip）；
  2. 讲清 try_files 回退原理（为什么刷新会 404、回退怎么救）；
  3. 落地缓存分层策略（index.html 不缓存、hash 资源长缓存）；
  4. 掌握四条高频坑（404、gzip_types、缓存反置、改配置不校验）。

2核心模型

三个核心模型：反向代理（跨域的解）→ SPA 回退（404 的解）→ 缓存分层（加载慢与发版不及时的共同解）。

2.1 反向代理：浏览器只认 Nginx 一个地址

浏览器只跟 Nginx 一个地址对话，Nginx 把 /api/xxx 悄悄转发给内网后端、再把结果带回浏览器。"反向"的含义：对外只暴露 Nginx，后端藏在后面——后端可换可扩容，前端无感知。

它为什么"顺便"解决了跨域：页面从 Nginx 来，/api 也在 Nginx 上——同源了自然不跨域，后端连 CORS 都不用配。这是"反向代理解决跨域"的原理本质：不是 Nginx 会绕过同源策略，而是请求根本没跨源。

2.2 静态托管与 SPA 回退：try_files 是 SPA 的命根

root 指定静态目录，访问 / 返回 index.html。坑在 SPA：前端路由（/login）只存在于 JS 里，服务器上根本没有这个文件——用户刷新 /login，Nginx 找文件找不到就 404。解法：try_files $uri $uri/ /index.html;——找不到文件就回退 index.html，让前端路由接管（原理见图 2，第 5 章）。

2.3 缓存分层：快与新的两全

gzip：把 JS/CSS 压缩后再发，体积小加载快——坑Nginx 默认只压 text/html，必须显式声明 gzip_types text/css application/javascript application/json; 才压 JS/CSS。缓存：给带 hash 的资源（app.abc123.js）设长缓存——文件名随内容变，可放心缓存一年；index.html 设 no-cache（每次问服务器）——发版即更新。两层搭配：入口保鲜、资源提速（原理见图 3，第 5 章）。

3核心用法（按场景）

3.1 场景一：一份最小可用的 SPA 部署配置

server {
  listen 80;
  root /usr/share/nginx/html;        # 前端 dist 拷贝到这里

  location / {
    try_files $uri $uri/ /index.html;   # SPA 回退到 index.html
  }

  location /api/ {
    proxy_pass http://127.0.0.1:8080/;  # 接口转发给后端
  }

  gzip on;                            # ⚠️ 见 3.3：还要配 gzip_types
}
上面 gzip on; 默认只压 text/html；要压 JS/CSS/JSON，必须再加 gzip_types text/css application/javascript application/json;，否则拿不到 JS/CSS 的压缩收益。

3.2 场景二：加缓存分层（完整生产形态）

# 带 hash 的静态资源：长缓存（文件名随内容变，可放心缓存）
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
# 入口与数据类请求：不缓存
location = /index.html {
  add_header Cache-Control "no-cache";
}
# 压缩（放 http/server 级）
gzip on;
gzip_types text/css application/javascript application/json;
gzip_min_length 1k;

3.3 场景三：常用命令（三步纪律）

nginx -t                # 检查配置语法（改完先测，必做）
nginx -s reload         # 平滑重载配置（不断现有连接）
systemctl restart nginx # 重启（配置大改/起不来时）

纪律：改配置永远先 nginx -t 再 reload——语法错误直接 reload 可能让服务挂掉（衔接 01 篇坑 4）。

4进阶知识点【进阶】

首次学习可整章跳过。前置：SPA 部署三件套已跑通。

4.1 proxy 转发头：让后端知道真实来访者

反代后默认后端看到的所有请求都来自 Nginx——要补两个头：proxy_set_header X-Real-IP $remote_addr;（真实客户端 IP，日志与限流依赖它）、proxy_set_header Host $host;（原始域名，后端多域名路由依赖它）。忘了配，后端日志里全是 Nginx 的 IP——排查用户问题时两眼一抹黑。

4.2 upstream：为扩容预留负载均衡

upstream backend {
  server 127.0.0.1:8080;
  server 127.0.0.1:8081;    # 加一个实例就是负载均衡
}
location /api/ { proxy_pass http://backend/; }

单实例时 proxy_pass 直写地址；后端扩到多实例时改成 upstream 块——Nginx 自动轮询分发。前端视角的价值：知道"后端加机器不用改我任何东西"。

4.3 多站点与 server_name

一台 Nginx 托管多个前端项目：不同域名不同 server 块（server_name a.com / b.com）；同域名下多项目用 location /app2/ 前缀区分（注意前端构建的 base/publicPath 要对齐前缀）。SPA 部署在子路径时：try_files 的回退目标与 base 配置必须一致，否则子路径刷新又 404。

4.4 history 路由 vs hash 路由：部署视角的选择

history 模式hash 模式（/#/login）
URL 观感干净（/login）带 # 号
服务器要求必须配 try_files 回退无要求（# 后不发给服务器）
取舍正式产品首选静态托管受限（OSS 直挂等）时的兜底

部署视角结论：能控制服务器就 history + try_files；部署在纯静态托管（改不了服务器配置）才退而求其次用 hash。

6最小可运行 Demo

10 分钟本地完成一次完整 SPA 部署（本机 Nginx 或 Docker 里的 nginx 均可）：

6.1 完整配置（nginx.conf 站点段）

server {
  listen 8080;
  root /usr/share/nginx/html;

  location / {
    try_files $uri $uri/ /index.html;              # SPA 回退
  }
  location /api/ {
    proxy_pass http://127.0.0.1:3000/;             # 本地 mock 后端
    proxy_set_header X-Real-IP $remote_addr;       # 真实 IP（4.1）
    proxy_set_header Host $host;
  }
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
  location = /index.html {
    add_header Cache-Control "no-cache";
  }
  gzip on;
  gzip_types text/css application/javascript application/json;
  gzip_min_length 1k;
}

6.2 部署与验证

npm run build                       # 本地产出 dist
cp -r dist/* /usr/share/nginx/html/
nginx -t && nginx -s reload         # ⭐ 先校验再重载

# 验证清单（四项全过才算部署完成）
curl -I localhost:8080              # ① index.html 200，无 Cache-Control 长缓存
curl -I localhost:8080/login        # ② 刷新路由也 200（try_files 生效）
curl -I localhost:8080/assets/*.js  # ③ 带 hash 资源有 max-age=31536000
curl -I -H "Accept-Encoding: gzip" localhost:8080/assets/*.js
                                    # ④ 响应头出现 Content-Encoding: gzip

6.3 逐段解析

  • 四项验证对应四个坑：入口/回退/缓存/压缩——每项都是一类线上事故的"体检项"；
  • proxy_set_header：反代补真实 IP 头，本地可省、生产必配（4.1）；
  • nginx -t 在 reload 前：语法错误拦在加载前——这条纪律能救整站。

6.4 生产改造扩展方向

  1. 多站点：再加一个 server 块托管第二个项目（4.3）；
  2. 后端多实例：proxy_pass 改 upstream 块（4.2）；
  3. 整段配置容器化：塞进 nginx:alpine 镜像，衔接 05 篇前端容器化。

7常见坑 & Debug

四条高频坑，每条五要素。

7.1 坑 1：SPA 刷新二级路由 404

  • 现象：首页正常，刷新 /login 就 404；
  • 根因：前端路由不是服务器文件，没配回退；
  • 复现：删掉 try_files 对照；
  • 修复：try_files $uri $uri/ /index.html;（子路径部署注意回退目标与 base 一致，4.3）；
  • 规避：SPA 部署配置模板里 try_files 是默认项；或退而用 hash 路由（4.4）。

7.2 坑 2：gzip on 了但 JS/CSS 没压缩

  • 现象：配置写了 gzip on，Network 面板里 JS 还是几百 KB 原样；
  • 根因：Nginx 默认只压 text/html——gzip_types 没配；
  • 复现：curl -H "Accept-Encoding: gzip" -I 看响应头有无 Content-Encoding；
  • 修复：gzip_types text/css application/javascript application/json;；
  • 规避：部署验证清单固定"压缩检查"一项（6.2 第④项）。

7.3 坑 3：缓存策略配反，发版不更新

  • 现象：发版后用户还是旧版，强刷才更新；
  • 根因：index.html 被长缓存（入口旧→引用旧 hash→永远旧版）；
  • 修复：index.html 设 no-cache，带 hash 的资源才设长缓存；
  • 规避：记住分层钥匙——hash 资源缓存一年、入口不缓存（图 3）。

7.4 坑 4：改配置不校验就 reload

  • 现象：reload 后 Nginx 挂了，整站不可用；
  • 根因：配置语法错误未拦截；
  • 修复：先 nginx -t 校验再 reload；
  • 规避：部署脚本固定 "nginx -t && nginx -s reload"——校验不过不执行（衔接 01 篇坑 4）。

8重点讲解

Q1：Nginx 反向代理为什么能解决跨域？

参考答案：跨域是浏览器的同源策略行为——页面源与请求源不同就拦。Nginx 反代把 /api 挂在与页面同一域名端口下，浏览器看到的请求同源，根本不触发跨域；Nginx 在服务端把请求转给真实后端（服务器之间没有同源策略）。后端因此连 CORS 都不用配。注意因果：不是"绕过"同源策略，而是"不跨源"。

加分点：补充"反向"的含义——对外只暴露 Nginx，后端可换可扩容前端无感知；顺带 proxy_set_header 传真实 IP（4.1）。

Q2：SPA 部署为什么刷新会 404？怎么解决？

参考答案：history 模式下 /login 只是前端 JS 路由，服务器上没有这个文件——刷新时浏览器直接向 Nginx 要 /login 这个"文件"，找不到就 404。解法 try_files $uri $uri/ /index.html;：先找真实文件（$uri），找不到回退 index.html，让 JS 加载后由前端路由接管。

延伸：hash 模式（/#/login）把路由放 # 后——# 后不发给服务器，所以无此问题；代价是 URL 带井号。能控制服务器就 history+try_files，静态托管受限才用 hash（4.4）。

Q3：前端静态资源的缓存策略怎么设计？

参考答案：分层两极——①带 hash 的资源（构建产物 JS/CSS/图片）：文件名含内容 hash，内容变则名变，设 max-age=31536000, immutable 一年长缓存；②index.html 入口：文件名固定、每次发版内容变，设 no-cache（协商缓存，每次问服务器有没有新版）。

原理一句话：hash 让"内容版本"编码进"文件名"，缓存失效由文件名变化天然完成——入口保鲜、资源提速两全。反例后果：index.html 长缓存 = 发版用户看不到新版。
