1简介与阅读指引

1.1 定位

本篇讲的是文件上传与图片处理的完整前端工程链路：从用户选文件（校验类型大小）→ 预览 → 压缩 → 上传（进度/并发控制）→ 大文件分片/断点续传。这条链路几乎每个业务系统都要做一遍，但坑密度极高——本篇把"能用的上传"到"可靠的上传"之间的差距讲透。

1.2 痛点

  • 用户传 50MB 文件卡死页面、超时失败后只能从头再传；
  • 上传没有进度反馈，用户狂点按钮触发 N 个重复请求；
  • 手机拍的 8MB 原图直接上传，流量与存储双浪费——其实 200KB 的压缩图就够展示用；
  • 校验只信前端（改后缀就能绕过），后端裸奔。

1.3 适用 / 不适用场景

适合读本篇不适合（看别的）
要做头像/附件/大文件上传功能WebSocket 文件传输 → 04 实时通信
排查"上传卡顿/无进度/重复上传"类问题对象存储服务端配置 → 09 模块 DevOps
面试（分片续传原理/压缩实现是高频题）Canvas 绘图教学 → 03 模块可视化

1.4 学习目标：读完本篇你能

  1. 实现带类型/大小校验、预览、进度、并发控制的可靠上传；
  2. 用 Canvas 压缩把图片压到目标体积，理解质量与尺寸两个变量；
  3. 实现大文件分片上传与断点续传，说出 hash 计算的三档方案取舍；
  4. 守住安全边界：前端校验是体验优化，真正的校验必须后端做。

2核心模型

上传链路的四个核心模型：文件对象模型（2.1）、校验分层（2.2）、压缩两变量（2.3）、上传策略分级（2.4）。

2.1 文件对象模型：File / Blob / FormData / URL.createObjectURL

  • File：用户选中的文件（继承自 Blob），有 name/size/type——校验的依据；
  • Blob：二进制数据的通用容器，file.slice() 切片是分片上传的基础；
  • FormData：multipart/form-data 的载体——文件上传的标准编码（后端按 multipart 解析）；
  • URL.createObjectURL(file)：给本地文件生成临时 URL 用于预览（用完 revokeObjectURL 释放）；或用 FileReader 读成 dataURL（base64，体积 +33%，适合小图缩略）。

2.2 校验分层：前端是体验，后端是底线

层校验什么性质
前端（选文件后立刻）类型（type/后缀）、大小上限、数量体验优化——免得用户传完才被告知失败
前端（上传前）图片解码校验（能否真的画进 canvas）拦截改后缀的伪装文件
后端（必须）类型（魔数/MIME）、大小、数量、权限、病毒扫描安全底线——前端一切校验都可绕过

前端校验的价值是快速反馈（秒拒不合格文件），不是安全——改个后缀就能绕过 MIME 检查。安全底线永远在后端：按文件头魔数（如 JPEG 的 FF D8）判断真实类型，而非信任扩展名。

2.3 压缩的两个变量：尺寸与质量

Canvas 压缩两条路，通常组合使用：①降尺寸——把图片 draw 到限宽的 canvas 再导出（长边 ≤ 1920 之类）；②降质量——canvas.toBlob(cb, 'image/jpeg', 0.7) 的质量参数。实践算法：先降尺寸到目标长边，再从 0.9 质量起步逐次降 0.1 直到体积达标或下限。PNG 转 JPEG 通常体积骤降（代价是失去透明通道——透明图保留 PNG）。

2.4 上传策略分级：按文件大小选方案

文件规模策略要点
小文件（< 5MB）整体单请求进度条 + 防重复点击即可
中文件（5~50MB）压缩后单请求 / 直传对象存储预签名 URL 直传，绕开业务服务器带宽
大文件（> 50MB）分片 + 并发 + 断点续传hash 标识文件、切片并行传、失败只补传

3核心用法（按场景）

3.1 场景一：基础上传（校验 + 预览 + 进度 + 防重复）

const input = document.querySelector<HTMLInputElement>('#file')!
input.onchange = async () => {
  const file = input.files![0]
  // ① 校验：类型 + 大小（前端体验层）
  const okType = ['image/jpeg', 'image/png', 'image/webp'].includes(file.type)
  if (!okType || file.size > 5 * 1024 * 1024) return alert('仅支持 5MB 内图片')

  // ② 预览：createObjectURL（记得 revoke）
  const url = URL.createObjectURL(file)
  previewImg.src = url

  // ③ 上传：FormData + 进度
  const fd = new FormData()
  fd.append('file', file)
  uploading.value = true                              // 防重复点击
  try {
    await http.post('/upload', fd, {
      headers: { 'Content-Type': 'multipart/form-data' },
      onUploadProgress: e => {
        progress.value = Math.round((e.loaded / e.total!) * 100)
      },
    })
  } finally {
    uploading.value = false
    URL.revokeObjectURL(url)                          // 释放内存
  }
}

3.2 场景二：图片压缩（Canvas 两步法）

async function compressImage(file: File, maxLen = 1920, targetKB = 300): Promise<Blob> {
  // 1) 解码成 Image
  const img = await createImageBitmap(file)
  // 2) 降尺寸：长边不超 maxLen
  const scale = Math.min(1, maxLen / Math.max(img.width, img.height))
  const canvas = document.createElement('canvas')
  canvas.width = img.width * scale
  canvas.height = img.height * scale
  canvas.getContext('2d')!.drawImage(img, 0, 0, canvas.width, canvas.height)
  // 3) 降质量：从 0.9 逐档降到达标
  for (let q = 0.9; q >= 0.5; q -= 0.1) {
    const blob: Blob = await new Promise(r =>
      canvas.toBlob(b => r(b!), 'image/jpeg', q))
    if (blob.size <= targetKB * 1024 || q === 0.5) return blob
  }
  throw new Error('unreachable')
}

注意：createImageBitmap 同时是"真图校验"——伪装成 .jpg 的文本文件在这里解码失败，直接拒绝。

3.3 场景三：并发控制（多文件上传）

// 最多同时 3 个上传，完成一个补一个（衔接 Axios 篇的取消能力）
async function uploadAll(files: File[], limit = 3) {
  const queue = [...files]
  const workers = Array.from({ length: limit }, async () => {
    while (queue.length) {
      const f = queue.shift()!
      await uploadOne(f)          // 单文件上传 + 状态更新
    }
  })
  await Promise.all(workers)      // 全部跑完才整体结束
}

为什么限制并发：浏览器对同域名 HTTP/1.1 有 6 个连接限制，占满了会阻塞页面其他请求；且带宽被打满时每个请求都变慢——3 并发通常比 10 并发总耗时更短。

4进阶知识点【进阶】：大文件分片与断点续传

首次学习可整章跳过。前置：基础上传已跑通。

4.1 分片上传流程

  1. 计算文件 hash（作为文件唯一标识，用于秒传与续传）；
  2. 请求 /upload/verify：服务端查该 hash——已存在 → 秒传（直接返回 URL）；部分存在 → 返回已传分片索引；都不存在 → 全新上传；
  3. file.slice(start, end) 切成 5MB 分片，并发 3~6 个上传（每片带 hash + index）；
  4. 全部分片完成 → 请求 /upload/merge，服务端按序合并。

4.2 hash 计算的三档方案

方案优点缺点适用
全量 MD5（spark-md5）准确大文件计算慢（秒级~十秒级）后台/低频
抽样 hash快（只算首/尾/中间若干块）极小概率碰撞前端常规选择
Web Worker 计算不阻塞主线程实现稍复杂配合前两者使用

hash 的三个用途：秒传判断、断点续传的文件标识、服务端去重。抽样 hash 的碰撞由"大小+修改时间"辅助字段兜底。

4.3 断点续传：状态在服务端，不再从头来

续传的关键是已传分片记录存服务端（localStorage 不可靠：多设备/清缓存）。刷新页面后重新 verify，服务端返回已传分片列表，前端只补传缺失分片。配合 Axios 的 AbortController：用户点暂停 → abort 所有在途分片请求 → 已完成的分片不丢，恢复时从 verify 接着传。

4.4 直传对象存储：让文件绕开业务服务器

生产架构的标配：前端向后端要预签名 URL（Presigned URL）→ 用 PUT 直传 OSS/S3 → 回传文件 key 给后端入库。收益：文件流量不经过业务服务器（带宽/内存友好）、天然支持分片与续传（存储服务原生能力）。前端改动很小：把 axios 的 baseURL 换成签名 URL，方法从 POST 换 PUT。

6最小可运行 Demo

一个完整的头像上传组件：校验 → 压缩 → 带进度上传 → 失败重试，30 行核心逻辑（Vue3）。

6.1 组件代码

<script setup lang="ts">
import { ref } from 'vue'
import http from '@/utils/request'          // 衔接 Axios 篇的请求模块

const progress = ref(0)
const uploading = ref(false)
const preview = ref('')
const input = ref<HTMLInputElement>()

async function onPick(e: Event) {
  const file = (e.target as HTMLInputElement).files![0]
  // ① 校验：类型 + 大小 + 真图（三关）
  const ok = ['image/jpeg', 'image/png', 'image/webp'].includes(file.type)
  if (!ok || file.size > 10 * 1024 * 1024) return alert('仅支持 10MB 内图片')

  // ② 压缩：长边 1080，目标 300KB（复用 3.2 的 compressImage）
  const blob = await compressImage(file, 1080, 300)
  preview.value = URL.createObjectURL(blob)

  // ③ 上传：FormData + 进度 + 防重复
  const fd = new FormData()
  fd.append('file', blob, `avatar_${Date.now()}.jpg`)
  uploading.value = true
  try {
    const { url } = await http.post('/upload/avatar', fd, {
      onUploadProgress: e => (progress.value = Math.round(e.loaded / e.total! * 100)),
    })
    console.log('上传成功:', url)
  } finally {
    uploading.value = false
    URL.revokeObjectURL(preview.value)
  }
}
</script>

<template>
  <input ref="input" type="file" accept="image/*" :disabled="uploading" @change="onPick">
  <img v-if="preview" :src="preview" style="max-width:200px">
  <progress v-if="uploading" :value="progress" max="100"></progress>
</template>

6.2 逐段解析

  • accept + JS 双重类型校验：accept 只过滤文件选择器，JS 校验拦截拖拽进来的；
  • 压缩在前、上传在后：8MB 原图 → 300KB JPEG，上传时间从秒级降到亚秒级（用户无感）；
  • progress 由 onUploadProgress 驱动：Axios 原生支持，无需轮询；
  • finally 兜底：uploading 复位与 revoke 无论成败都执行——防重复点击的锁不会死锁。

6.3 生产改造扩展方向

  1. 大附件场景升级为分片 + 断点续传（第 4 章），配 Web Worker 算 hash；
  2. 接入预签名 URL 直传对象存储（4.4），业务服务器只发签名与入库；
  3. 多文件场景加 3 并发队列（3.3）与全局失败清单（哪几个失败了一键重传）。

7常见坑 & Debug

按"校验 → 上传 → 大文件"分组，每条五要素。

7.1 校验阶段

坑 1：只信 MIME/后缀，伪装文件入库

  • 现象：用户把 .exe 改名 .jpg 传上去，前端全绿通过；
  • 根因：file.type 取自文件名推断，可任意伪造；
  • 复现：任意文件改后缀再选入；
  • 修复：前端加"真图解码"（createImageBitmap 失败即拒）；后端按魔数判真实类型（FF D8=JPEG、89 50=PNG）；
  • 规避：把"前端校验只是体验层"写进团队共识，后端校验是安全底线。

7.2 上传阶段

坑 2：上传无防重复，狂点多请求

  • 现象：慢网络下用户连点上传按钮，同一文件传了 5 份；
  • 根因：按钮未禁用/无进行中标志；
  • 修复：uploading 标志 + 按钮禁用 + finally 兜底复位（6.1）；
  • 规避：上传类按钮统一走封装的上传 hook，内建防重。

坑 3：createObjectURL 不 revoke，内存缓慢上涨

  • 现象：长时间使用的页面越用越卡；
  • 根因：每个 objectURL 都持有文件引用，不手动释放不回收；
  • 修复：预览结束（或替换预览）时 URL.revokeObjectURL(oldUrl)；
  • 规避：封装 createPreview 工具函数，创建与释放配对。

坑 4：压缩把透明 PNG 压成黑底

  • 现象：带透明通道的 logo 压缩后透明区域变黑色；
  • 根因：toBlob 导出 'image/jpeg' 无透明通道，canvas 默认透明底被填黑；
  • 修复：透明图保留 PNG（或先垫白底再转 JPEG）；按 file.type 分支处理；
  • 规避：压缩函数入参带"允许的目标格式"，透明图跳过 JPEG 分支。

7.3 大文件阶段

坑 5：分片全量并发，页面请求被占满

  • 现象：100 个分片同时发，浏览器连接池被占满，页面其他请求全卡；
  • 根因：无并发限制（HTTP/1.1 同域 6 连接限制）；
  • 修复：并发池限 3~6 个，完成一个补一个（3.3）；
  • 规避：所有批量请求场景默认走并发池。

坑 6：续传状态存 localStorage

  • 现象：换设备/清缓存后"续传"又从头传；
  • 根因：已传分片记录放本地——状态应该以服务端为准；
  • 修复：verify 接口以文件 hash 查询服务端已存分片，前端只补缺（4.3）；
  • 规避：断点续传的状态权威永远是服务端。

8重点讲解

Q1：大文件为什么要分片？讲一下完整流程。

参考答案：不分片的三个死穴——超时（单请求传 1GB 必超时）、不可恢复（失败从头再来）、无法秒传/去重。分片方案四步：①hash 计算文件唯一标识（抽样 hash + Worker）；②verify——服务端查 hash：已存在秒传、部分存在返回已传分片；③分片并发上传（slice 切 5MB，并发池 3~6）；④merge——服务端按序合并。

追问：断点续传怎么实现？——已传分片记录在服务端，重传前先 verify 拿缺失列表只补缺；暂停用 AbortController abort 在途请求，恢复从 verify 接续。

Q2：前端图片压缩怎么实现？

参考答案：Canvas 两步法——①降尺寸：createImageBitmap 解码后按目标长边缩放画到 canvas；②降质量：toBlob('image/jpeg', q) 从 0.9 逐档降到达标体积。注意：透明图保留 PNG（JPEG 无透明通道会黑底）；createImageBitmap 顺带完成"真图校验"（伪装文件解码失败）。

追问：为什么不直接压完就传？——要区分场景：头像/展示图压缩（有损可接受）；凭证/原始证据文件必须传原图，压缩会破坏法律效力。压缩策略是业务决策，不是技术默认。

Q3：上传的安全校验应该怎么做？

参考答案：分层观点——前端校验（类型/大小/真图解码）是体验优化：秒拒不合格文件省用户流量等待；安全底线在后端：按文件头魔数判断真实类型（不信扩展名与 MIME）、限制大小与数量、鉴权与隔离存储路径、必要时病毒扫描。前端一切校验都可绕过（改后缀/直接 curl 接口），所以后端校验不是"双保险"而是"唯一保险"。
