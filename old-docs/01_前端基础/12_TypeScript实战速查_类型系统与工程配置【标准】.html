2核心模型

五个速查组：基础标注→ interface vs type→ 联合与字面量→ 类型收窄→ unknown 与 any。

2.1 基础标注纪律

能推断就不写（const n = 1 自动字面量类型）；边界必写：函数参数/返回值、公共 API、组件 props——类型写在"人机接口"上，内部让推断跑。

2.2 interface vs type：定死选型

对象形状用 interface（可声明合并、extends 清晰）；联合/映射/工具组合用 type——type Status = "draft" | "review" 这种联合只能 type。团队统一一条线，别混着玩。

2.3 联合类型与字面量类型

type Status = "draft" | "review" | "done";     // 字面量联合替代 enum
type Shape = Circle | Rect;                      // 判别联合（tag）
interface Circle { kind: "circle"; r: number }
interface Rect   { kind: "rect"; w: number; h: number }

2.4 类型收窄：TS 安全性的核心体验

if/typeof/in/instanceof/判别字段都能收窄——判别联合靠 shape.kind 分支，每个分支里拿到精确类型。收窄优于断言：让编译器算，别替它拍板。

2.5 unknown 取代 any

any = 关掉检查（传染全链）；unknown = 未知但安全——用前必须收窄。纪律：JSON.parse/第三方回调/动态数据一律 unknown，收窄后再用；真正需要 any 的场景一个项目屈指可数。

3核心用法（按场景）

3.1 场景一：函数与组件 props

function fmt(amount: number, currency = "CNY"): string {
  return new Intl.NumberFormat("zh-CN", { style: "currency", currency }).format(amount);
}

interface TodoProps { todo: Todo; onRemove?: (id: number) => void }
// 返回值类型自动推断；导出函数显式写返回类型更稳

3.2 场景二：工具类型 Top6

type PartialTodo  = Partial<Todo>;                 // 全可选（表单草稿）
type TodoBrief    = Pick<Todo, "id" | "title">;     // 挑字段
type TodoNoMeta   = Omit<Todo, "createdAt">;        // 去字段
type GroupBy      = Record<Status, Todo[]>;         // 键→值映射
type FnRet        = ReturnType<typeof fetchList>;   // 取返回值
type Data         = Awaited<ReturnType<typeof fetchList>>;  // 解 Promise
使用频率真相：Partial/Pick/Omit 覆盖日常 80%；Record 管映射表；ReturnType/Awaited 接后端函数类型——从函数类型派生数据类型避免双份维护。

3.3 场景三：接口响应建模

interface ApiResponse<T> { code: number; msg: string; data: T }
interface PageQuery { page: number; size: number; kw?: string }
type UserListData = { list: User[]; total: number };

function fetchList(q: PageQuery): Promise<ApiResponse<UserListData>> {
  return http.get("/users", { params: q });
}

3.4 场景四：泛型初用（够用即止）

function firstOrNull<T>(arr: T[]): T | undefined { return arr[0]; }
function pickField<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
// 约束 extends：K 必须是 T 的键——泛型只在"类型间有关系"时才上

4进阶知识点【进阶】

首次学习可整章跳过。

4.1 类型守卫与自定义 is

function isUser(x: unknown): x is User {
  return typeof x === "object" && x !== null && "id" in x;
}
if (isUser(raw)) { raw.id; }   // 收窄成 User

x is User 让运行时判断产生类型收窄——比 as 断言安全（真检查 vs 假声明）。

4.2 枚举 vs 联合字面量

优先字面量联合（零运行时、tree-shaking 友好、序列化简单）；enum 有反向映射/运行时对象两套坑（数字枚举反向索引意外存在）；const enum 与隔离模块编译还有兼容问题——新项目基本可以只用字面量联合 + 对象常量。

4.3 tsconfig 五个关键项

  • strict: true（内含 noImplicitAny/strictNullChecks——nullable 是最大 bug 源）；
  • noUncheckedIndexedAccess：数组/记录索引访问自动加 undefined；
  • moduleResolution: "bundler" / module: "ESNext"：现代工程；
  • paths：@/ 别名（与打包器同步配，别只配一边）；
  • skipLibCheck: true：跳过第三方 d.ts 检查，提速编译。

4.4 声明文件与类型导入

无类型第三方库写 declare module "lib" 最小补丁或装 @types；import type 明确纯类型导入（编译期擦除，防运行时引包）。

6最小可运行 Demo

性质：工程速查演示——把"接口层类型建模"完整走一遍，可直接放进项目。

// 1) 领域类型
interface User { id: number; name: string; role: "admin" | "member" }

// 2) 通用响应 + 分页
interface Page<T> { list: T[]; total: number }
interface ApiResponse<T> { code: number; msg: string; data: T }

// 3) 从函数派生类型（单一事实源）
declare function fetchUsers(kw: string): Promise<ApiResponse<Page<User>>>;
type UsersData = Awaited<ReturnType<typeof fetchUsers>>["data"];

// 4) 收窄处理
function firstAdmin(data: UsersData): User | undefined {
  return data.list.find((u): u is User & { role: "admin" } => u.role === "admin");
}
  • 覆盖点：泛型响应、字面量联合、Awaited/ReturnType 派生、is 守卫；
  • 复盘：后端改返回结构时只改 User/ApiResponse 两处，全链类型报错自动跟上——这就是类型的价值。

7常见坑 & Debug

五条工程高频坑。

7.1 any 泛滥

根源：图省事 any 一把梭，检查全空转。正解：unknown+收窄；第三方没类型写 declare 补丁；lint 禁 any（no-explicit-any）。

7.2 as 断言滥用

后果：as 是"我说是就是"，编译让步运行时炸。正解：能用收窄/守卫就不用 as；仅存于"确实知道编译器不知道"的边界（且留注释）。

7.3 enum 反向映射与 Tree-shaking

坑：数字 enum 生成运行时对象且反向索引存在；const enum 与 babel 隔离编译不兼容。正解：字面量联合 + as const 对象常量。

7.4 只配 tsconfig 没同步打包器

现象：@/ 别名 IDE 能跳转、构建报错（或反之）。正解：tsconfig paths 与 vite/webpack alias 双侧同步。

7.5 @ts-ignore 一把梭

后果：错误被埋，后来人背锅。正解：@ts-expect-error（若无错反而报错，天然防陈旧）+ 注明原因。

8重点讲解

Q1：interface 和 type 到底怎么选？

参考答案：功能重叠但侧重不同——interface 擅长"对象形状"：extends 继承语义清晰、支持声明合并（同名接口自动合并，给 window/第三方扩展类型的正道）、报错信息更友好；type 擅长"组合"：联合、交叉、映射、条件类型、工具类型只能 type。工程纪律：对象/组件 props 用 interface，一切联合与类型运算用 type，团队一条线。差异点补充：type 不能被 extends 的类实现（implements interface 可以）、重名 type 直接冲突而 interface 合并——后者既是特性也是事故源，业务代码避免依赖合并。

Q2：unknown 和 any 的区别？什么场景还允许 any？

参考答案：any 关闭检查——任何读写合法且双向传染（赋给谁都不报错），错误延迟到运行时；unknown 保持检查——编译器拒绝直接使用，必须先收窄（typeof/instanceof/in、自定义 is 守卫、schema 校验如 zod）。它是"运行时动态、编译期安全"的正解，JSON.parse 结果、第三方回调参数、动态数据边界一律 unknown。仍允许 any 的场景：确实无法描述的互操作（老 JS 库、动态生成的代码），且范围收到最小+注释。as 也不该成为 any 的替代品——as 是拍板，unknown+守卫是验证。

Q3：泛型什么时候该上？工具类型怎么组合出常用类型？

参考答案：泛型只在"类型间存在关系"时上——入参类型决定返回类型（firstOrNull）、键与值有约束（pickField 的 K extends keyof T）；没有关系的泛型是装饰。工具类型组合是日常主力：接口响应 ApiResponse<T> 泛型套壳；表单草稿 Partial<T>；列表页 Omit<T, "id"|"createdAt"> 出入参；映射表 Record<Status, Color>；从函数派生 ReturnType + Awaited 拿后端数据类型避免双份维护。原则：先写具体类型，重复出现了再抽泛型，和抽象函数同纪律。
