Git 进阶 · 分支模型与冲突恢复

深入 定位：《02_Git【标准】》讲日常命令，本篇讲分支本质、历史改写与"后悔药"

标准篇解决了"每天怎么提交"，本篇解决三类进阶问题：分支和 HEAD 到底是什么（rebase/merge 的选择依据）、历史怎么安全改写（interactive rebase/amend）、出事后怎么救（reflog/reset/bisect）。核心心智：Git 的提交是快照链、分支只是指针——想透了，大部分"玄学"都变成确定性操作。案例为冲突演习，已如实标注。

1简介与阅读指引

1.1 定位：从"会打命令"到"懂对象模型"

Git 的一切进阶都建立在三个事实上：提交是不可变快照、分支/HEAD 是可移动指针、reflog 记录 HEAD 的每一步。理解这三点，rebase/reset/恢复就全是确定性操作。

1.2 学习目标与阅读指引

  1. 讲清四区数据流与分支/HEAD/提交的关系；
  2. 会选 merge vs rebase（公共分支 vs 个人分支）；
  3. 掌握历史改写三件（amend/interactive rebase/cherry-pick）与安全边界；
  4. 会用后悔药三件（reflog/reset/stash）与 bisect 定位坏提交。

难度：★★★☆☆。性质：本地演习验证（见 6）；协作规范呼应 10 模块代码评审篇。

2核心模型

四个核心模型：四区与数据流→ 提交与指针→ merge vs rebase→ reflog 后悔药。

2.1 四区：工作区/暂存区/本地库/远程库

改动流向：工作区 --add→ 暂存 --commit→ 本地 --push→ 远程；回流：pull = fetch + merge/rebase。暂存区的价值：把"一次逻辑变更"从散乱改动里挑出来组一个提交（add -p 逐块挑）。

2.2 提交、分支与 HEAD

每个提交 = 树快照 + 父指针 + 元信息，内容寻址（SHA）；分支只是指向某提交的 40 字节指针——切分支便宜、分支不是"副本"；HEAD 指向"当前所在"（分支或裸提交）。detached HEAD：HEAD 直接指提交——历史查看用，别在上面开发后弄丢。

2.3 merge vs rebase：两种历史观

merge：合并提交保留分叉史——"真实发生过"；rebase：把提交摘下来重放到目标顶端——线性史、评审干净，但改写了提交身份（新 SHA）。纪律：个人 feature 分支内 rebase 随意；已推送的公共分支禁止 rebase（等于换了历史，强推砸别人）。

2.4 reflog：本地后悔药

reflog 记录 HEAD 的每次移动（commit/reset/checkout）——哪怕 reset --hard、误删分支，只要提交对象还在（90 天 GC 窗口）就能 git reset --hard HEAD@{n} 找回。恐慌时的第一命令：git reflog。

3核心用法（按场景）

3.1 场景一：提交前整理（amend 与软重置）

git commit --amend --no-edit        # 补文件/改信息（仅限未推送）
git reset --soft HEAD~1             # 撤提交留改动在暂存，重新组织
git reset HEAD~1                    # 撤提交+撤暂存，改动保留在工作区

3.2 场景二：交互式 rebase 清理历史

git rebase -i main~5     # 或 origin/main
# pick/pick → 改成：
#   pick   a1b2c3 feat: 列表页
#   squash d4e5f6 fix: 补样式          ← 并入上一条
#   reword g7h8i9 wip: xx              ← 改提交信息
git push --force-with-lease              # 安全强推（他人有新提交会拒绝）
force-with-lease > force：带租约检查，远程比预期新就拒绝——防覆盖队友提交。

3.3 场景三：cherry-pick 摘提交

把别的分支上"某一个修复"摘过来：git cherry-pick <sha>；批量/连续区间用 -n（不自动提交）再统一整理——热修复跨版本搬运的标准做法。

3.4 场景四：bisect 二分定位坏提交

git bisect start
git bisect bad v2.3.0          # 当前版本坏
git bisect good v2.2.0         # 这个版本好
# Git 自动切到中间提交 → 测试 → git bisect good/bad
# log(n) 次定位到引入点 → git bisect reset

4进阶知识点【进阶】

首次学习可整章跳过。

4.1 团队分支模型：为主干服务

中小团队主流：main + 短命 feature 分支（合并即删）+ PR 评审；发版打 tag 或 release 分支。git flow 全套对 Web 持续部署过重——分支活得越久冲突越贵；"小步快跑 + trunk-based"渐成主流（呼应 10 模块流程篇）。

4.2 merge 冲突的标准处理

冲突标记 <<</===/>>> 三段：ours/theirs——处理顺序：先跑测试再标记解决（git add）；大冲突借助 git checkout --ours/--theirs <file> 整文件取舍；解决到一半想弃：git merge --abort。

4.3 stash 与部分提交

git stash -u（含未跟踪文件）临时收起改动切分支救火；git stash pop/apply stash@{n} 恢复；add -p 把混在一起的改动拆成多个提交——评审可读性的关键。

4.4 仓库级问题：大文件与钩子

大文件进了历史：checkout 都慢——预防用 .gitignore + LFS（大模型/设计稿）；已污染历史要 filter-repo 清洗（团队协同重代价，先约定）。钩子：pre-commit 跑 lint/format（06 模块呼应），客户端可绕过——CI 再兜一道。

6最小可运行 Demo

性质（诚实声明）：本地演习仓库（制造冲突/误删/坏提交并自救），非生产事故记录；目的是把"后悔药"练成肌肉记忆。

6.1 冲突演习

  1. 建空仓库，main 提交 A（同一文件同一行）；
  2. 开 feat 改该行提交 C；回 main 改同一行提交 B；
  3. git merge feat → 观察冲突标记 → 手工合并 → add → commit；
  4. 再来一次但用 git merge --abort 中途放弃。

6.2 自救演习

git reset --hard HEAD~2        # "误删"两个提交
git reflog                      # 找到丢失前 HEAD 位置
git reset --hard HEAD@{1}       # 全部找回
git branch -D feat-x            # 误删分支
git reflog | grep feat-x        # 找到该分支顶端提交
git branch feat-x <sha>         # 重建分支

6.3 成果与复盘

  1. 能力：冲突解决/放弃、reflog 救回提交与分支、bisect 定位坏提交；
  2. 一句话抓手："演习过冲突合并与 reflog 自救，理解分支是指针、rebase 会换 SHA，能判断什么时候可以强推、必须用什么姿势推。"

7常见坑 & Debug

五条高频坑。

7.1 rebase 已推送的公共分支

后果：历史被换，队友 pull 出鬼影提交/冲突风暴。纪律：公共分支只 merge；个人分支 rebase 后用 force-with-lease。

7.2 reset --hard 丢工作

恐慌：改动没了。自救：未提交改动被清才真丢（stash 过可找）；已提交的必在 reflog——先 reflog 再哭。

7.3 裸 force push

风险：覆盖他人新提交。正解：一律 --force-with-lease；共享分支保护（GitHub 禁 force push）。

7.4 大文件进历史

后果：clone 越来越慢，删文件也没用（历史还在）。正解：LFS/对象存储；已污染用 git filter-repo 清洗（提前广播全团队重克隆）。

7.5 带着冲突标记提交

现象：`<<<<` 直接上线。预防：pre-commit grep 冲突标记；解决后必跑构建/测试再 commit。

8重点讲解

Q1：Git 分支的本质？为什么切分支比 SVN 快？

参考答案：Git 提交是内容寻址的不可变快照（带父指针的有向无环图），分支只是指向某提交的 41 字节指针文件，HEAD 再指向分支。切分支=移动两个指针+更新工作区——O(1) 便宜操作；SVN 分支是目录复制。推论：①分支随便开（feature 即开即弃）；②"删分支"只删指针不删提交（reflog/SHA 仍可达）；③rebase 重放生成的 C' 是新对象——SHA 变了就是新身份，这是公共分支禁 rebase 的根本原因。

Q2：merge 与 rebase 怎么选？冲突处理有什么讲究？

参考答案：rebase 换线性史、评审干净，适合个人/未共享分支更新基线；merge 保留分叉史实、SHA 不变，适合公共分支合入。冲突处理纪律：①逐文件看三段标记（ours=当前分支/theirs= Incoming），从语义合并而非逐行机械选边；②解决完先跑测试再 git add 标记解决；③合不下去 merge --abort / rebase --abort 随时撤；④复杂冲突可用 checkout --ours/--theirs 整文件定夺。团队约定大于技巧：比如"feature 更新用 rebase、合入 main 用 merge（Squash PR）"。

Q3：误操作了怎么救？reflog 为什么几乎万能？

参考答案：reflog 记录 HEAD 的每一步本地移动（提交/重置/切分支），保存期默认 90 天——所以 reset --hard 丢的提交、误删分支的顶端、rebase 前的原始链都能找回：git reflog 定位 → git reset --hard HEAD@{n} 或 git branch feat <sha>。配合：①stash drop 也能从 reflog 找（dangling commit）；②reset 三档区别：--soft 退提交留暂存、mixed 留工作区、--hard 全退（危险）；③提交到远程后的误操作：revert 生成反向提交（公共安全），绝不 reset+force。真正的丢失场景只有一种：从未提交且未 stash 的工作区改动被 clean/hard 清掉——所以"高频小提交"是最便宜的保险。
