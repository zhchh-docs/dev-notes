7.1 useState 的基本形态

import { useState } from 'react';

function Stepper() {
  const [count, setCount] = useState(0);              // 解构：[值, 设置函数]
  const [user, setUser] = useState({ name: '张三', age: 18 });

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(0)}>重置</button>
    </div>
  );
}

关键点：

  • 初始值只在首次渲染生效。之后每次重渲染都会忽略参数（哪怕是昂贵的计算，见下方惰性初始化）。
  • 必须调用 setter 更新。直接给变量赋值（count = 1）既不触发更新也无意义——count 是 const 声明的普通变量。
  • setter 是稳定引用：它在组件的整个生命周期中不变，因此可以安全地放进依赖数组。
  • 多个 state 用多次 useState；相关的数据也可以合并成一个对象（但更新时必须整体替换）。
// 惰性初始化：传函数，只在首次渲染执行一次（适合昂贵计算 / 读本地存储）
const [todos, setTodos] = useState(() => {
  const raw = localStorage.getItem('todos');
  return raw ? JSON.parse(raw) : [];
});

// ✗ 这样写每次渲染都会跑一遍 JSON.parse（浪费）
const [todosWrong, setTodosWrong] = useState(JSON.parse(localStorage.getItem('todos') || '[]'));

7.2 为什么读到的是旧值：快照模型

function Demo() {
  const [n, setN] = useState(0);

  const handle = () => {
    setN(n + 1);
    setN(n + 1);
    setN(n + 1);
    console.log(n);     // 打印 0 —— 不是 3，甚至不是 1
  };

  return <button onClick={handle}>点我</button>;
}

点击后界面上 n 变成 1（不是 3），控制台打印 0。这不是 bug，是 React 的核心模型：

快照（snapshot）模型：每一次渲染都有自己的 props 与 state 常量。事件处理函数里的 n，是那次渲染捕获的常量值，不会因为 setTimeout 里修改了同名的 setN 而改变。

换句话说：setN(n + 1) 调用三次，等价于"请下一次渲染时用值 n+1"重复三遍，结果自然是 1。想要累加，必须让 React 基于"最新值"计算：

const handle = () => {
  setN(prev => prev + 1);
  setN(prev => prev + 1);
  setN(prev => prev + 1);
  // 界面变成 3 ✓
};

一句话：值与更新都是"排入队列"的语义。传值 → 直接替换；传函数 → React 依次调用，以上一次的结果为参数。

为什么 console 打的是旧值：setN 只是通知 React"待会儿重渲染"，此刻变量不会变。想看新值，请在下一次渲染的函数体里打印（console.log(n) 放在组件顶层）。

7.3 函数式更新

// 形式：setState(prev => nextValue)
setCount(c => c + 1);
setUser(u => ({ ...u, age: u.age + 1 }));
setList(l => [...l, newItem]);
setList(l => l.filter(x => x.id !== id));
setObj(o => o.active ? o : { ...o, active: true });   // 也可 return 原值跳过更新
场景传值 setX(v)传函数 setX(p => v)
依赖旧值累加❌ 会丢失更新✅ 推荐
同一 tick 内多次更新❌ 覆盖✅ 依次执行
异步回调里更新⚠ 容易读到过期值✅ 安全
纯替换（如重置）✅ 简洁✅ 等价

一个异步场景的对比：

// ✗ 慢接口连点两次会丢一次：第二次 setCount 基于的还是旧 count
async function loadMore() {
  const more = await fetchMore();
  setCount(count + more.length);
}

// ✓ 基于最新值计算，永不丢失
async function loadMore() {
  const more = await fetchMore();
  setCount(c => c + more.length);
}

7.4 自动批处理

多次 setState 会让组件重渲染几次？答案是 1 次——React 会把同一个事件里的多次更新合并处理，这就是批处理（batching）。

const handle = () => {
  setA(1);
  setB(2);
  setC(3);
  // React 18：只重渲染 1 次（三次 setState 被合并）
};
版本批处理范围说明
React 17仅 React 事件回调内setTimeout、原生监听、Promise 里不批处理
React 18全部场景（自动批处理）定时器、原生事件、异步回调一律合并
 
// React 18 下这三处都只渲染一次
setTimeout(() => { setA(1); setB(2); }, 1000);
el.addEventListener('click', () => { setA(1); setB(2); });
promise.then(() => { setA(1); setB(2); });

// 极少数场景真的需要同步读取更新后的 DOM：
import { flushSync } from 'react-dom';
flushSync(() => setA(1));     // 强制立即同步刷新（会伤性能，慎用）
console.log(document.querySelector('#a').textContent);
坑升级到 18 后，某些依赖"setTimeout 里多次 setState 会多次渲染"的老代码行为会变化。绝大多数情况是变快了；若确实需要"每次更新后立即拿到 DOM"，用 flushSync 并把这段逻辑推到第 12 章讲的 useLayoutEffect。

7.5 不可变更新：对象与数组

React 判断"状态变没变"用的是 Object.is（近似 ===）浅比较。因此：必须替换引用，而不是在原地修改。

// ✗ 原地修改：引用没变，React 认为没变化，界面不更新
function badUpdate() {
  user.age = 19;            setUser(user);        // ❌ 同一个对象引用
  list.push(item);          setList(list);        // ❌
  list[0].done = true;      setList(list);        // ❌ 嵌套也不行
}

// ✓ 创建新引用
setUser(u => ({ ...u, age: 19 }));                       // 对象：展开 + 覆盖
setList(l => [...l, item]);                              // 追加
setList(l => l.map(x => x.id === id ? { ...x, done: !x.done } : x));  // 修改某项
setList(l => l.filter(x => x.id !== id));                // 删除
setList(l => l.slice(0, -1));                            // 删尾

深层嵌套怎么办

// state = { user: { profile: { city: '北京' } }, list: [] }

// 手写层层展开（能用但啰嗦）
setState(s => ({
  ...s,
  user: { ...s.user, profile: { ...s.user.profile, city: '上海' } },
}));

// 推荐：Immer（写起来像原地修改，内部产出新引用）
import { produce } from 'immer';
setState(produce(s => { s.user.profile.city = '上海'; }));
原则记住一句就够了：谁被改，就把谁所在的整条路径上的对象都换成新副本。这也是第 44 章"不可变为什么必须"的原理基础。

别为了"性能"到处深拷贝：JSON.parse(JSON.stringify(x)) 会让所有子树失去引用相等性，反而让 memo 全面失效；精确到被改的那一层才是正确做法。

7.6 什么该放进 state，什么不该

数据该放 state 吗放哪
用户输入、开关、列表数据✅useState / 状态库
可由 props 或 state 算出（全名、总价、过滤结果）❌ 派生值渲染时直接算；成本高则 useMemo（第 49 章）
DOM 度量值（宽高、滚动位置）❌useRef 读取，必要时再同步进 state
定时器 id、请求取消标记、上一次的值❌ 与渲染无关useRef（第 13 章）
服务端返回结果❌ 服务端状态TanStack Query（第 25 章）
 
// ✗ 冗余 state：看起来"更清楚"，实际是 bug 温床
const [list, setList] = useState([]);
const [doneCount, setDoneCount] = useState(0);   // 需要在三处手动同步
const toggle = id => { setList(...); setDoneCount(c => c + 1); };

// ✓ 派生即可：永远自动一致
const doneCount = list.filter(x => x.done).length;

什么时候该把 state 提到父组件（状态提升）

  • 两个及以上兄弟组件都需要这份数据时，把 state 放到最近的公共父组件，通过 props 下发；
  • 提升过头会让顶层组件臃肿且引发大范围重渲染，此时就该进入第三篇的状态分层设计了。

✓ 本章小结

要点一句话
快照模型每次渲染有自己的常量 state；set 后下次渲染才变
函数式更新p => next 保证基于最新值，多次调用依次生效
自动批处理React 18 全场景合并更新，只渲染一次
不可变更新必须换引用；对象展开、map/filter 返回新数组
深嵌套逐层展开或引入 Immer
初始化昂贵计算用惰性初始化 useState(() => ...)
不该进 state派生值、DOM 度量、timer id、服务端数据
