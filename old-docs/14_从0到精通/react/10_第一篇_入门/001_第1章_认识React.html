1.1 React 是什么

一句话定义：React 是一个用于构建用户界面的 JavaScript 库——它只负责一件事：根据数据（状态）高效地渲染出界面，并在数据变化时更新界面。

注意两个关键词的分量：

  • 库不是框架 React 自称 library 而非 framework。路由、请求、状态管理都不在它体内，由生态（React Router、TanStack Query 等）补齐——这也是本书第三、四篇存在的原因。
  • 它管的是 UI React 不关心你的业务逻辑怎么写，它只负责"状态 → 界面"这最后一公里。

一段 13 年的短历史

2013 年，Facebook 在 JSConf US 上开源了 React。驱动它诞生的真实痛点是：Facebook 广告系统的界面太复杂，jQuery 时代的 DOM 手工操作让代码互相踩踏、没人敢改。React 的解法很激进——既然手动同步"数据"和"界面"容易出错，那就让开发者只声明"界面长什么样"，同步这件事交给框架自动完成。2019 年引入 Hooks（16.8），让函数组件成为主角；2022 年发布 React 18，带来并发渲染（Concurrent Rendering）与自动批处理。今天（React 18/19 时代），它依然是全球使用量最大的前端 UI 方案。

React 的本质承诺：把"数据变了界面跟着变"这件容易出错的事，变成一件不需要你操心的事。

1.2 从命令式到声明式

理解 React 最好的方式，是先看它"反对什么"。先写一个最常见的 jQuery 风格需求：点一下按钮，计数加一。

命令式写法（原生 DOM）

// 命令式：一步一步"指挥"浏览器怎么改
const btn = document.querySelector('#btn');
const span = document.querySelector('#count');
let count = 0;

btn.addEventListener('click', () => {
  count += 1;
  span.textContent = String(count);   // 手动把数据"刷"到界面
});

代码不长，但注意隐患：数据和界面是两份东西。哪天你又在别的分支里改了 span.textContent（比如重置按钮逻辑忘了同步 count），界面和 count 变量就"对不上账"了。真实项目里，这种"手动同步"分散在几十个事件回调里，正是"没人敢动祖传代码"的根源。

声明式写法（React）

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      点了 {count} 次
    </button>
  );
}

区别不在行数，在心智模型：

维度命令式（DOM 直操）声明式（React）
关注点"怎么改"：先取节点，再改属性"是什么"：界面在当前状态下长什么样
数据与视图两份，需要人工保持同步一份，视图由状态推导出来
出 bug 的方式忘了同步、同步了两次、顺序错了状态设计错了（同步 bug 整类消失）
可读性要脑补出"界面各时刻的样子"看 return 语句就知道界面长什么样
声明式 = 你只负责"描述结果"，"达成结果的过程"由 React 完成。这是 React 一切 API 设计的出发点。

1.3 UI = f(state)：React 的核心思想

把上一节的思想压缩成公式：

UI = f(state) —— 界面（UI）是状态（state）的函数（f）。相同的 state 永远渲染出相同的界面；state 变了，React 自动重新执行 f，算出新的界面。

图 1-1 UI = f(state)：数据单向流动，界面永远是状态的投影

这个公式带来三条铁律，后面每一章都会反复回来对照：

  1. state 是唯一的"事实源"（single source of truth）。界面显示什么，永远由 state 推导，绝不另存一份"界面上的值"。
  2. 改界面 = 改 state。想更新界面，不要去摸 DOM，而是调用 setState 之类的函数改数据。
  3. 组件函数应当是"纯"的。同样的 props 和 state 进来，就该渲染出同样的 JSX——第 19、41 章会解释这条纪律为什么是 React 性能与正确性的基石。
常见误区"React 会监听我的变量变化，一变就刷新页面"——错。React 不监听任何东西，只有你主动调用 setState 触发更新。直接改 count = 5 不调用 setState，界面纹丝不动（第 7 章详解）。

1.4 第一个 React 组件

下面是一个完整可运行的 React 组件（先看代码建立直觉，下一章我们把它跑起来）：

import { useState } from 'react';

// 1. 组件就是一个"首字母大写"的普通函数
function GreetingCard({ name }) {
  // 2. Hooks：给函数组件接入状态能力
  const [liked, setLiked] = useState(false);

  // 3. return 的 JSX 就是"这个状态下界面长什么样"的声明
  return (
    <div className="card">
      <h3>你好，{name}！</h3>
      <p>{liked ? '❤️ 已收藏' : '🤍 未收藏'}</p>
      <button onClick={() => setLiked(!liked)}>
        {liked ? '取消收藏' : '收藏'}
      </button>
    </div>
  );
}

export default GreetingCard;

逐行拆解三个关键点：

  • 函数名必须大写开头（GreetingCard 而不是 greetingCard）。JSX 里 <GreetingCard /> 大写表示"这是一个组件"，小写（<div>）表示"这是 HTML 标签"——大小写就是 React 区分二者的唯一依据。
  • props 是只读入参（{ name } 解构自 props 对象），相当于函数参数；state 是组件私有记忆（liked），相当于函数内部的可变数据。数据下行用 props，组件内部变化用 state——第 4、7 章分别展开。
  • JSX 不是字符串也不是 HTML，它是 JavaScript 的语法扩展，编译后是普通的函数调用（第 3 章看编译产物）。所以文件后缀是 .jsx，标签里能写任何 JS 表达式（{liked ? '❤️' : '🤍'}）。

组件 = 输入（props + state）→ 输出（JSX 描述的界面）。整个 React 应用，就是把几百个这样的小函数像积木一样组合起来。
