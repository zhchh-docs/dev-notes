4.1 为什么要拆组件

React 没有告诉你"文件怎么分"，但拆错了会从第一天开始持续付利息。拆组件的收益只有三条，每条都对应一个具体痛点：

收益解决的问题判断信号
复用同一段 UI 在多处重复发现自己在复制粘贴 JSX
单一职责一个函数管太多事，改一处牵一片组件超过 150 行、混合多种关注点
渲染边界一处小改动导致整页重渲染性能优化时需要把"动的部分"隔离出来

看一个典型"拆之前 vs 拆之后"：一个订单卡片里混合了商品列表、金额汇总和操作按钮。

// ✗ 拆之前：一个组件里塞了三件事
function OrderPanel({ order }) {
  return (
    <div className="panel">
      <h3>订单 {order.no}</h3>
      {order.items.map(it => (
        <div key={it.id}>
          <span>{it.name}</span><span>x{it.qty}</span><span>￥{it.price}</span>
        </div>
      ))}
      <div>合计：￥{order.items.reduce((s, i) => s + i.price * i.qty, 0)}</div>
      <button>付款</button><button>取消</button>
    </div>
  );
}

// ✓ 拆之后：每个组件一件事，金额计算也有了"家"
function OrderItem({ item }) {
  return (
    <div className="order-item">
      <span>{item.name}</span>
      <span>x{item.qty}</span>
      <span>￥{item.price}</span>
    </div>
  );
}

function OrderSummary({ items }) {
  const total = items.reduce((s, i) => s + i.price * i.qty, 0);
  return <div className="summary">合计：￥{total}</div>;
}

function OrderPanel({ order, onPay, onCancel }) {
  return (
    <div className="panel">
      <h3>订单 {order.no}</h3>
      {order.items.map(it => <OrderItem key={it.id} item={it} />)}
      <OrderSummary items={order.items} />
      <button onClick={onPay}>付款</button>
      <button onClick={onCancel}>取消</button>
    </div>
  );
}
拆分口诀：凡是"能被起一个业务名字的 UI 片段"，就值得抽成一个组件；凡是"会被复制第二次的 JSX"，必须抽。
文件粒度：本书约定一个组件一个文件，同目录组件 ≤ 12 个、单层目录 ≤ 6 个子目录；组件 script（模板）超过 150 行就该考虑继续拆。

4.2 props：只读的一份入参

props 就是组件函数的第一个参数，用法：

// 写法一：props 对象整体接收
function Avatar(props) {
  return <img src={props.url} alt={props.name} width={props.size} />;
}

// 写法二：解构（推荐，一眼看全 API）
function Avatar({ url, name, size = 48 }) {
  return <img src={url} alt={name} width={size} />;
}

// 使用：  —— 属性名随意，顺序无关

三条铁律

  1. props 只读。组件内部绝不修改 props.xxx。这不是建议，是 React 的强制约定——第 44 章会解释：修改对象型 props（如 props.items.push(x)）会让父组件"看起来没变"从而跳过更新，制造极难排查的 bug。
  2. 单向数据流：数据只能从父组件流向子组件（父持有 state → 通过 props 下发）。子组件想改数据，只能调用父组件传下来的回调函数，由父组件去 setState。
  3. props 变化引发重渲染：父重渲染时，子组件默认跟着重渲染（不论 props 是否真的变了）——这是第六篇性能优化要解决的核心现象。
// 子组件上传孔子组件的状态变更：回调上行
function TodoItem({ todo, onToggle, onRemove }) {
  return (
    <li>
      <input
        type="checkbox"
        checked={todo.done}
        onChange={() => onToggle(todo.id)}   {/* 只管通知，数据由父组件改 */}
      />
      <span>{todo.title}</span>
      <button onClick={() => onRemove(todo.id)}>删除</button>
    </li>
  );
}

function TodoList({ todos, setTodos }) {
  const toggle = (id) => setTodos(prev => prev.map(
    t => t.id === id ? { ...t, done: !t.done } : t
  ));
  const remove = (id) => setTodos(prev => prev.filter(t => t.id !== id));

  return (
    <ul>
      {todos.map(t => (
        <TodoItem key={t.id} todo={t} onToggle={toggle} onRemove={remove} />
      ))}
    </ul>
  );
}
常见坑props.xxx = 1 在开发环境直接抛 Cannot assign to read only property；但 props.list.push(1) 不报错——它污染了父组件的数据却不触发更新，属于"静默事故"，务必避免。

4.3 默认值与类型约束

默认值

// 推荐：解构时给默认值（ES6 语法，直观且与 TS 兼容）
function Button({ type = 'primary', size = 'middle', disabled = false, onClick }) {
  /* ... */
}

// 老写法（类组件时代的 defaultProps）—— 函数组件中已不推荐
Button.defaultProps = { type: 'primary' };

类型检查：TypeScript（推荐）

type User = { id: number; name: string; avatar?: string };

type Props = {
  user: User;                       // 必传
  size?: 'small' | 'middle' | 'large';  // 可选 + 字面量联合
  onSelect?: (id: number) => void;  // 函数签名
  children?: React.ReactNode;       // 任意可渲染内容
};

function UserCard({ user, size = 'middle', onSelect, children }: Props) {
  return <div onClick={() => onSelect?.(user.id)}>{children}</div>;
}

类型检查：propTypes（JS 项目轻量方案）

import PropTypes from 'prop-types';

UserCard.propTypes = {
  user: PropTypes.shape({
    id: PropTypes.number.isRequired,
    name: PropTypes.string.isRequired,
  }).isRequired,
  size: PropTypes.oneOf(['small', 'middle', 'large']),
  onSelect: PropTypes.func,
};

// 不匹配时控制台会给出清晰警告（仅开发模式生效）

类型不是枷锁：它替你拦住"少传一个参数""传错字段名"这两类最高频的低级 bug，是团队规模变大后的必需品。

4.4 children 与插槽模式

children 是 props 里最特殊的一个：它表示开标签与闭标签之间的内容。有了它，组件就能像 HTML 一样"包裹内容"，这就是"插槽"。

function Card({ title, children }) {
  return (
    <div className="card">
      <div className="card-head">{title}</div>
      <div className="card-body">{children}</div>
    </div>
  );
}

<Card title="用户信息">
  <p>姓名：张三</p>
  <Avatar url="/a.png" />
</Card>

多插槽：用"具名 props 传 JSX"

// 把 JSX 当作普通值塞进任意 prop —— React 没有真正的"具名插槽"
<Layout
  header={<SiteHeader />}
  sidebar={<Nav />}
  footer={<Copyright />}
>
  <Article />
</Layout>

function Layout({ header, sidebar, footer, children }) {
  return (
    <div className="layout">
      <header>{header}</header>
      <aside>{sidebar}</aside>
      <main>{children}</main>
      <footer>{footer}</footer>
    </div>
  );
}

函数式插槽（render props 雏形）

// 子组件把内部数据"吐"出来给调用方决定怎么渲染
<DataProvider url="/api/user">
  {({ data, loading }) => loading ? <Spinner /> : <UserCard user={data} />}
</DataProvider>

function DataProvider({ url, children }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  useEffect(() => {
    fetch(url).then(r => r.json()).then(d => { setData(d); setLoading(false); });
  }, [url]);
  return children({ data, loading });   // children 是函数，调用它
}

这个模式在 Hooks 出现前是逻辑复用的主力；今天多数场景被自定义 Hook（第 16 章）取代，但 Ant Design、React Router 等库中仍大量存在，必须认识。

4.5 组合优于继承

React 官方文档的态度非常明确：你没有继承组件的必要。类继承带来的层级耦合在 UI 这种"结构多变"的领域弊大于利，React 提供的组合能力已经覆盖全部场景。

需求继承思路（不推荐）组合思路（推荐）
复用外框所有页面继承 BasePage<Layout><Page /></Layout>
注入通用能力多层 Mixin / 抽象基类自定义 Hook（第 16 章）
局部差异常子类覆写 render 碎片props 开关 + children 插槽
 
// 一个"具备边框和标题的通用容器"，通过 children 容纳任意内容
function Panel({ title, extra, children }) {
  return (
    <section className="panel">
      <header>
        <h3>{title}</h3>
        <div className="extra">{extra}</div>
      </header>
      {children}
    </section>
  );
}

<Panel title="待办" extra={<Button>新建</Button>}>
  <TodoList todos={todos} />
</Panel>
判断标准：如果你打算"继承一个组件只为改它的一部分 UI"，那就应该把它拆成"容器 + children"，而不是开继承链。

4.6 props 设计六准则与常见坑

  1. 命名对齐：数据用名词，事件用 on 前缀：value / items / user 表示数据，onChange / onSubmit / onSelect 表示回调，前者不加前缀，后者必须 on 开头。
  2. 受控 vs 非受控要统一：一个组件要么全受控（value + onChange），要么全非受控（defaultValue），不要两套并存——第 8 章详述。
  3. 扁平优先：<Avatar user={user} /> 比 <Avatar user={user} size={size} theme={theme} className={c} /> 更好维护吗？不一定——props 超过 7 个就该考虑是否要拆组件；而"整对象传入"会带来无谓重渲染，需权衡。
  4. 谨慎使用 spread 透传：<input {...inputProps} /> 很方便，但会把未知属性一起送进 DOM，React 会给出 Unknown prop 警告；可用 ESLint 规则 react/jsx-props-no-spreading 约束。
  5. 加 key 而不是 index：列表渲染的 props 里必须有稳定 key（第 6 章）。
  6. className / style 要可覆盖：组件内部接收外部传入的 className 并合并，否则调用方永远改不了样式。
// 准则 1 + 6 的示范
function Tag({ text, color = 'green', className = '', style, onClick }) {
  const cls = ['tag', 'tag-' + color, className].filter(Boolean).join(' ');
  return <span className={cls} style={style} onClick={onClick}>{text}</span>;
}
坑清单
  • props 名字拼错不报错，只是得到 undefined——用 TS 或 propTypes 兜住；
  • 回调写成 onClick={remove(id)}（立即执行）而不是 onClick={() => remove(id)}（传引用），导致渲染时就删除；
  • 把对象/数组直接写在 JSX 里作为 props（style={{...}}、<C items={[...]}>），每次渲染都是新引用，会让下游 memo 失效——第 48、49 章解释。

✓ 本章小结

要点一句话
拆分标准可复用、单一职责、隔离渲染；JSX 被复制第二次就抽
props 本质组件函数的第一个参数，只读
单向数据流state 在父组件，props 下行，事件回调上行
默认值/类型解构默认值；TS 优先，propTypes 为 JS 备选
children内容分发（插槽），多插槽用 props 传 JSX
render propschildren 为函数，把内部数据交还调用方
组合优于继承容器 + children + 自定义 Hook 覆盖全部复用需求
