第 36 章 校验：zod 与类型安全

教科书 第 36 章 / 共 64 章 · 预计 45 分钟 · 单一数据源的运行时校验

TypeScript 类型只在编译期存在，运行时拿到的表单值仍是不可信的输入。本章用 zod 把「类型、规则、错误信息」收敛为一份 schema，通过 z.infer 反推 TS 类型，用 zodResolver 接入 react-hook-form，并把同一 schema 复用到服务端边界校验。

◆本章目标

  • 理解 TypeScript 类型在编译期被擦除，运行时输入必须独立校验；
  • 能用 zod 编写对象、字符串、数字、枚举、数组、可选字段等基础 schema；
  • 会用 refine 与 superRefine 实现单字段与跨字段自定义校验；
  • 掌握 z.infer 从 schema 反推类型，并用 zodResolver 接入 react-hook-form；
  • 区分 parse 与 safeParse 的错误处理方式，理解前后端复用同一份 schema 的价值。

36.1 手写校验的问题

没有 schema 工具时，类型定义、校验规则、错误提示分散在三个地方：先写一份 TypeScript interface，再在提交回调里手写 if 判断，错误文案散落各处。规则一改，三处同步；接口返回结构变化时，类型与真实数据经常脱节。

// 类型定义
interface ProfileInput {
  name: string
  email: string
  age: number
}

// 校验规则散落在提交回调中
function validate(data: ProfileInput) {
  if (!data.name || data.name.length < 2) return '姓名至少 2 个字符'
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(data.email)) return '邮箱格式不正确'
  if (!Number.isInteger(data.age) || data.age < 18) return '年龄必须是 18 岁以上整数'
  return null
}
问题说明
规则与类型两份真相interface 描述结构，if 描述规则，修改时容易漏改其中一处
运行时无类型保护编译期类型在打包后被擦除，接口返回的字符串数字、缺失字段不会被 TS 拦截
错误信息重复每个表单重复书写正则、长度判断与提示文案，风格不统一
跨层复用困难浏览器一套规则，服务端接口再写一套，前后端口径可能不一致
嵌套结构校验繁琐对象嵌套、数组元素、联合类型需要逐层手写判断，错误路径难以定位
zod 的思路是声明一份 schema：运行时校验由 schema 执行，TypeScript 类型由 schema 反推。schema 成为唯一数据源——这与 Java 后端 Bean Validation（@NotBlank、@Email 标注在字段上）同属「规则附着于结构」的思路，区别是 zod 在前端运行时同样生效。
TypeScript 类型在打包后被擦除，编译期类型不能替代运行时校验：接口返回、URL 参数、本地存储、表单输入都是不可信外部数据，进入应用结构之前必须由 schema 独立校验。

36.2 zod schema 基础

先安装 zod 与 react-hook-form 的 zod 解析器：

npm install zod @hookform/resolvers

从 zod 导入 z，用 z.object 描述表单结构，字段上链式挂载规则与错误信息：

import { z } from 'zod'

const profileSchema = z.object({
  name: z
    .string({ required_error: '姓名必填' })
    .min(2, '姓名至少 2 个字符')
    .max(20, '姓名最多 20 个字符'),
  email: z
    .string({ required_error: '邮箱必填' })
    .email('邮箱格式不正确'),
  age: z.coerce
    .number({ required_error: '年龄必填' })
    .int('年龄必须是整数')
    .min(18, '必须年满 18 岁'),
  role: z.enum(['admin', 'editor', 'viewer'], {
    required_error: '请选择角色',
  }),
  subscribe: z.boolean().optional(),
  tags: z.array(z.string()).default([]),
})
zod 写法对应 TypeScript 类型说明
z.string()string字符串，可接 min / max / email / url / regex 等规则
z.number() / z.coerce.number()number数值；coerce 先把输入转为数字再校验，适合表单字符串输入
z.enum(['a', 'b'])'a' | 'b'字面量联合，取值限定在枚举内
z.boolean().optional()boolean | undefined可选布尔值；z.optional(...) 等价包裹
z.array(z.string())string[]数组，元素类型由内部 schema 决定
z.object({ ... })对象字面量类型嵌套对象可继续 z.object 内嵌
z.string().default('匿名')string（缺省值自动填充）输入为 undefined 时写入默认值
z.coerce.number() 与 z.number() 的区别：前者先做类型转换再校验，表单数字输入框拿到的是字符串，使用 coerce 可避免「'25' 不是数字」一类误报。

36.3 联合、数组与跨字段校验

基础规则覆盖单字段；字段之间的约束（两次密码一致、金额区间、至少勾选一项）需要 refine 与 superRefine。联合类型用 z.union 或 z.discriminatedUnion 描述「结构取决于某个字段」的场景。

import { z } from 'zod'

const passwordSchema = z
  .object({
    password: z.string().min(8, '密码至少 8 位'),
    confirm: z.string().min(1, '请再次输入密码'),
  })
  .refine((data) => data.password === data.confirm, {
    message: '两次密码不一致',
    path: ['confirm'],   // 错误挂到 confirm 字段上展示
  })

const contactSchema = z.union([
  z.object({ type: z.literal('email'), email: z.string().email() }),
  z.object({ type: z.literal('phone'), phone: z.string().regex(/^1\d{10}$/) }),
])

const interestsSchema = z
  .array(z.string())
  .min(1, '至少选择一项兴趣')
  .max(5, '最多选择 5 项')
  • .refine(fn, { message, path })：同步自定义判断，返回布尔值，可指定错误归属字段，适合单字段附加规则与两字段一致性检查；
  • .superRefine((val, ctx) => ...)：通过 ctx.addIssue 追加多条错误，路径可自由指定，适合一个校验点产生多条错误、复杂嵌套规则的场景；
  • z.union([...])：按顺序尝试各分支，全部失败才报错，用于结构不确定的联合输入；
  • z.discriminatedUnion('type', [...])：按判别字段直接定位分支，错误信息更清晰，用于表单选项决定后续字段结构的场景；
  • .transform(fn)：校验通过后转换输出值，用于去空格、拼接全名、单位换算等归一化处理。
跨字段 refine 挂在对象 schema 上，path 指向需要展示错误的字段；若把一致性校验写进 password 字段内部，就无法读取 confirm 的值，这是新手最常见的放错位置问题。

36.4 z.infer 类型推导与 zodResolver 接入

用 z.infer<typeof schema> 从 schema 反推 TypeScript 类型，表单 useForm 泛型直接使用这份推导类型；zodResolver(schema) 作为 resolver 传入，react-hook-form 提交时自动执行 schema 校验，错误信息映射到 formState.errors。

import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'

const profileSchema = z.object({
  name: z.string().min(2, '姓名至少 2 个字符'),
  email: z.string().email('邮箱格式不正确'),
  age: z.coerce.number().int().min(18, '必须年满 18 岁'),
})

// 从 schema 反推类型：不再手写 interface
type ProfileInput = z.infer<typeof profileSchema>

export default function ProfileForm() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<ProfileInput>({
    resolver: zodResolver(profileSchema),
    defaultValues: { name: '', email: '', age: 18 },
  })

  function onValid(data: ProfileInput) {
    // data 类型即 ProfileInput，已通过 zod 校验
    api.save(data)
  }

  return (
    <form onSubmit={handleSubmit(onValid)}>
      <input {...register('name')} placeholder="姓名" />
      {errors.name && <p className="field-error">{errors.name.message}</p>}

      <input {...register('email')} placeholder="邮箱" />
      {errors.email && <p className="field-error">{errors.email.message}</p>}

      <input type="number" {...register('age')} />
      {errors.age && <p className="field-error">{errors.age.message}</p>}

      <button type="submit">保存</button>
    </form>
  )
}
维度手写 interface + 内置规则schema + z.infer
类型来源独立手写 interfacez.infer 从 schema 反推，结构与规则同源
规则修改改类型、改校验、改提示三处同步只改 schema，类型自动跟随
错误展示组件内判断并拼接文案resolver 自动映射到 errors.field.message
编辑器提示字段名靠人工记忆推导类型驱动 register('field') 的补全与检查

图 36-1 schema 单一数据源闭环：类型推导、表单校验与边界复核共用同一份规则定义

类型与规则同源后，改 schema 即同时改类型、校验规则与错误文案；z.infer 推导的类型还会反向约束 register('字段名')，字段名拼错在编译期就能被发现。
resolver 只执行同步校验；验证码、用户名是否占用等需要网络往返的异步规则，应放在 action / loader 或提交回调中调用接口后回传错误，不要期待 zod resolver 内自行发请求。

36.5 parse / safeParse 与服务端边界

schema 不仅服务于表单。接口响应、URL 参数、本地存储读取等「外部输入」进入应用前，都应过一遍 schema。两种执行方式对应两种错误处理策略：parse 失败直接抛 ZodError，safeParse 返回结构化结果供分支处理。

import { z } from 'zod'

const userSchema = z.object({ id: z.string(), name: z.string() })

// 方式一：parse，失败抛出 ZodError，配合 try/catch 使用
function loadUser(raw: unknown) {
  try {
    return userSchema.parse(raw)
  } catch (err) {
    if (err instanceof z.ZodError) {
      console.warn('数据结构不合法', err.issues[0]?.message)
    }
    return null
  }
}

// 方式二：safeParse，不抛异常，按 success 分支处理
async function fetchUser() {
  const res = await fetch('/api/me')
  const raw = await res.json()
  const result = userSchema.safeParse(raw)
  if (!result.success) {
    // result.error.issues 包含每条错误的 path 与 message
    console.warn(result.error.issues)
    return null
  }
  return result.data
}
方式返回 / 行为适用
schema.parse(data)成功返回类型化数据；失败抛出 ZodError确信输入应合法、失败即异常流程的代码路径
schema.safeParse(data)返回 { success: true, data } 或 { success: false, error }需要展示错误、分支兜底、不希望异常打断流程的场景
error.issues错误数组，含 path、message、code定位出错字段、聚合提示、上报日志
选择标准看错误是否属于异常流程：确信输入应合法、失败即中断的代码路径用 parse 配合 try/catch；需要展示错误、分支兜底、不希望异常打断流程的场景用 safeParse。表单 resolver 内部走的是结构化错误分支，不向外抛异常。
前后端复用：TypeScript 工程可把 schema 抽到共享模块，浏览器用它做表单校验，服务端接口入口用 safeParse 复核请求体；即便前后端不共仓，字段规则也应在文档层面对齐。服务端校验始终不可省略，前端校验只改善体验（呼应第 32 章守卫边界）。
safeParse 失败时 result.data 不存在，不要先读 result.data 再判 success；分支顺序必须是先 if (!result.success) 处理错误，再在成功分支内使用 result.data，否则类型收窄失败且运行时可能读到 undefined。

36.6 常见坑清单

现象原因解法
类型被推成 any 或 unknownschema 标注缺失、混用 z.any()，或 z.infer 引用顺序错误逐字段使用具体类型；避免 z.any()，未知结构用 z.unknown() 再细化
错误只显示通用英文提示规则未传中文 message，或 required 场景漏配 required_error每个规则补充错误信息；必填字段配置 required_error
异步规则在 resolver 中不生效zod 规则同步执行，resolver 内无法等待网络请求用户名占用、验证码等异步校验放接口提交后回传错误
嵌套字段错误路径错乱refine 的 path 指错层级，嵌套对象错误未逐层声明按 ['parent', 'child'] 路径指定；嵌套结构用子级 z.object 分开校验
数字字段被存成字符串使用 z.number() 直接校验表单字符串输入表单数字字段用 z.coerce.number()，或在 transform 中转换
schema 版本与 resolver 版本不匹配报错zod 与 @hookform/resolvers 大版本组合不在兼容范围按 resolver 文档对齐 zod 版本，升级时二者一起更新
不要把 zod schema 当成数据转换器代替组件层归一化：transform 只在校验通过后改写输出，若输入非法，原始值不会被转换后再校验；需要先转换再校验的字段，使用 z.coerce 或显式在 schema 外层处理。

✎ 本章习题

A 基础为登录表单编写 zod schema：用户名 3–20 位、邮箱格式正确、密码至少 8 位；用 z.infer 推导出类型，通过 zodResolver 接入 react-hook-form，错误信息展示在对应输入框下方。
