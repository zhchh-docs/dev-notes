28.1 可测试状态设计原则

可测试性不是写完代码再补测试就能获得的——它由状态设计决定。更新逻辑越集中在纯函数、越不依赖组件渲染与全局网络，测试就越容易写、跑得越快、失败定位越准。
原则正确做法难以测试的反例
更新逻辑纯函数化状态变更集中在 reducer / store action / selector 中，给定输入产出确定输出把计算与更新逻辑写进组件事件回调，测试必须先渲染组件
store 与组件解耦组件只负责读取与派发，不藏业务规则；store 可脱离组件单独实例化与重置组件内部闭包保存关键状态，store 里看不到完整业务流程
外部依赖可注入取数函数、API 客户端通过参数或参数化 hook 传入，测试时替换为 mock组件内直接调用全局 fetch，测试无法拦截网络层
状态边界清晰本地状态、共享状态、服务端状态各归其层（第 20 章），测试对象明确服务端数据镜像进全局 store，两份真相难以判定正确结果
判断标准：不渲染任何组件、不发一个真实网络请求，能否把核心状态逻辑测完？能，说明状态设计具备单元测试条件；不能，先回头调整分层与归属。

28.2 纯逻辑单元测试：actions、reducer、selector

状态库里最容易测的部分恰恰是核心规则：actions、reducer、selector 都是给定输入产出输出的纯函数，不需要渲染组件、不需要网络环境，单元测试可以跑得很快、很确定。

状态库的核心逻辑都是纯函数，测试时直接调用 store 方法或 reducer，断言状态前后变化，不需要挂载组件。以下示例使用 vitest 风格断言，测试框架语法不影响设计原则。

28.2.1 Zustand store actions 测试

// counterStore.test.js
import { describe, it, expect, beforeEach } from 'vitest';
import { useCounterStore } from './counterStore';

describe('counter store', () => {
  beforeEach(() => {
    // 每个用例前重置状态，避免用例间互相污染
    useCounterStore.setState({ count: 0 });
  });

  it('increment 让计数加 1', () => {
    useCounterStore.getState().increment();
    expect(useCounterStore.getState().count).toBe(1);
  });

  it('incrementByAmount 按传入数值累加', () => {
    useCounterStore.getState().incrementByAmount(5);
    expect(useCounterStore.getState().count).toBe(5);
  });

  it('reset 回到初始值', () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().reset();
    expect(useCounterStore.getState().count).toBe(0);
  });
});

28.2.2 Redux Toolkit reducer 测试

// counterSlice.test.js
import { describe, it, expect } from 'vitest';
import counterReducer, { increment, decrement, incrementByAmount } from './counterSlice';

describe('counter reducer', () => {
  const initial = { value: 0 };

  it('处理 increment', () => {
    const next = counterReducer(initial, increment());
    expect(next.value).toBe(1);
  });

  it('处理 incrementByAmount', () => {
    const next = counterReducer(initial, incrementByAmount(5));
    expect(next.value).toBe(5);
  });

  it('未知 action 保持原状态', () => {
    const next = counterReducer(initial, { type: 'unknown' });
    expect(next).toEqual(initial);
  });
});

28.2.3 selector 测试

selector 是接收状态对象、返回派生值的纯函数，直接传入构造好的状态对象断言结果即可，不需要真实 store。

// selectTotal.test.js
import { describe, it, expect } from 'vitest';
import { selectTotal } from './cartSelectors';

describe('selectTotal', () => {
  it('按单价与数量求和', () => {
    const state = {
      cart: {
        items: [
          { price: 10, qty: 2 },
          { price: 3, qty: 1 },
        ],
      },
    };
    expect(selectTotal(state)).toBe(23);
  });
});
测试对象构造方式断言重点
Zustand actions调用 getState().action()，用 setState 重置状态字段变化正确、不可变更新未破坏其他字段
RTK reducer调用 reducer(prevState, action)返回新状态、未知 action 原样返回、不可变性成立
selector传入手工构造的状态对象派生值正确、不修改传入状态对象

28.3 组件与 store 集成测试

纯逻辑测完后，再验证「组件读取 store、派发动作、界面随之更新」这条链路。使用 React Testing Library 渲染组件并包裹 store Provider，通过可访问性角色查询元素，触发事件后断言界面变化。组件测试的完整手法在第 62 章展开，本章只覆盖状态相关部分。

// Counter.test.jsx
import { render, screen, fireEvent } from '@testing-library/react';
import { Provider } from 'react-redux';
import { store } from './app/store';
import Counter from './Counter';

describe('Counter 组件', () => {
  it('点击 +1 后计数变为 1', () => {
    render(
      <Provider store={store}>
        <Counter />
      </Provider>
    );

    fireEvent.click(screen.getByRole('button', { name: '+1' }));

    expect(screen.getByText('1')).toBeInTheDocument();
  });
});
集成测试之间需要重置 store 状态：RTK store 在每个用例前重新创建或派发重置 action；Zustand store 在 beforeEach 中 setState 回到初始值。用例共享同一个脏 store 会导致断言互相污染、结果随机失败。
集成测试断言应针对用户可见的界面结果（文案、计数、提示），不要反复断言内部 store 状态字段；纯规则正确与否已由单元测试覆盖，集成测试重复断言只会让组件重构时测试批量失败。

28.4 服务端状态测试与网络隔离

涉及 useQuery / useMutation 的组件测试要解决两个问题：每个用例使用独立的 QueryClient，避免缓存残留；网络请求被拦截为受控响应，不访问真实后端。

// PostList.test.jsx
import { render, screen, waitFor } from '@testing-library/react';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import PostList from './PostList';

function renderWithClient(ui) {
  // 每个测试用例新建 QueryClient，缓存互不影响
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });
  return render(
    <QueryClientProvider client={queryClient}>{ui}</QueryClientProvider>
  );
}

describe('PostList', () => {
  it('渲染接口返回的文章标题', async () => {
    // 拦截 fetch，返回受控响应（真实项目可用 MSW 等服务端 mock 方案统一拦截）
    global.fetch = vi.fn().mockResolvedValue({
      ok: true,
      json: async () => [{ id: 1, title: '测试文章' }],
    });

    renderWithClient(<PostList />);

    await waitFor(() => {
      expect(screen.getByText('测试文章')).toBeInTheDocument();
    });
  });
});
关注点处理方式
缓存残留每个用例新建 QueryClient，挂载独立 Provider 包裹
网络请求拦截 fetch 返回固定响应；多接口项目可用 MSW 在服务端层统一 mock
三态渲染分别 mock pending、成功、错误响应，验证加载态、列表态、错误态分支
mutation 链路触发动作后断言成功提示出现，且对应查询缓存被失效重取
MSW（Mock Service Worker）在浏览器与测试环境拦截真实网络层、按接口返回受控数据，适合团队级测试基建；本章示例以最小化 fetch mock 演示思路，具体 API 以所选版本官方文档为准。
服务端状态测试不要复用全局共享的 QueryClient：上一个用例残留的缓存会让当前用例读到旧数据，表现为偶发的测试失败；每个用例新建实例、独立 Provider 包裹是必须的隔离动作。

28.5 状态可测试性反模式清单

反模式后果修正方向
业务规则写进组件事件回调必须渲染组件才能测试规则，用例慢且脆规则上移到 action / reducer / 独立纯函数模块
组件闭包隐藏关键状态store 中读不到完整流程，失败时无法定位关键状态归入 store，组件只做展示与派发
全局单例 store 不重置测试用例间状态泄漏，结果随机失败beforeEach 重置；组件测试重建 store 与 QueryClient
reducer / action 内直接发请求纯函数被网络依赖污染，无法单元测试请求放入 thunk / mutationFn，reducer 只处理状态分支
服务端数据镜像进全局 store两份真相，测试无法判断谁正确服务端状态留在查询缓存，全局 store 只放客户端共享状态
选择器内部请求外部全局变量同样输入不同输出，断言不稳定selector 只接收状态参数，依赖显式传入
不要把测试价值寄托在「点遍页面」的 E2E 用例上：状态规则一旦变更，慢而脆的端到端测试会首先变红，团队倾向于跳过维护；规则应下沉到快速单元测试，E2E 只保留关键路径。

28.6 测试金字塔与覆盖率建议

状态相关测试应按金字塔分层：大量快速的单元测试覆盖 actions、reducer、selector；适量集成测试覆盖组件与 store、查询缓存的配合；少量端到端测试覆盖关键业务路径。越往上测试越慢、越不稳定，占比应越小。

图 28-1 状态测试金字塔：单元测试覆盖纯逻辑，集成测试覆盖组件与 store 链路，端到端只保留关键路径

层级覆盖对象比例建议
单元测试store actions、reducer、selector、派生工具函数主体部分，优先追求覆盖核心分支与边界输入
组件集成测试组件读取 store、派发动作、三态渲染、缓存配合关键交互组件，验证链路而非重复纯逻辑断言
端到端测试登录、下单、支付等跨页面关键路径少量保留，避免把状态规则下沉到 E2E 用例重复验证
覆盖率不是越高越好：高价值在分支覆盖而非行数覆盖——空状态、错误态、边界输入与并发操作路径都应有测试，纯展示 JSX 不必追求逐行覆盖。

✓ 本章小结

要点一句话
设计原则纯函数化、store 与组件解耦、依赖可注入、状态边界清晰
单元测试对象Zustand actions、RTK reducer、selector 均可脱离组件直接断言

✎ 本章习题

A 基础为一个 Zustand 待办 store 编写单元测试：包含 addTodo(text)、toggleTodo(id)、clearCompleted() 三个 action；每个用例前重置状态，分别断言新增条目、切换完成态、清除已完成条目后的结果。
B 进阶为 RTK 购物车切片编写 reducer 测试：加购同 id 商品累加 qty、不同 id 追加新条目、输入未知 action 保持原状态；再补一个 selectTotal selector 的单元测试，覆盖空数组与混合单价数量两种输入。
