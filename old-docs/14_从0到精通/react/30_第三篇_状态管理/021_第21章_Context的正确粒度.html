第 21 章 Context 的正确粒度

教科书 第 21 章 / 共 64 章 · 预计 48 分钟 · 广播不是订阅，粒度决定性能

Context 本身是依赖注入工具，整值广播、没有 selector，粒度越粗重渲染代价越大。本章拆解粗粒度 Provider 的真实代价，讲清多 Context 拆分、value 引用稳定、memo 组合拳三道防线，并划清 Context 与 Zustand、Redux Toolkit 的职责边界。

21.1 Context 的本质：注入与广播

Context 解决的问题是props 钻取：让深层组件直接读取祖先提供的值，而不必逐层透传。它的机制是「沿组件树向下广播」，而不是「按需订阅切片」——这两个性质决定了它的能力边界。

第 14 章已经介绍过 createContext、Provider 与 useContext 的基本用法，这里先回顾最小闭环，再聚焦本章的粒度问题。

const ThemeContext = createContext('light');

function App() {
  return (
    <ThemeContext.Provider value="light">
      <Page />
    </ThemeContext.Provider>
  );
}

function Page() {
  const theme = useContext(ThemeContext);
  return <p>当前主题：{theme}</p>;
}
关键事实：useContext 订阅的是整个 Context 值。只要 Provider 提供的 value 引用发生变化，所有读取该 Context 的组件都会重渲染，哪怕组件只用了其中一个字段。

这与 Zustand、Redux 的 selector 机制形成鲜明对比：后两者允许组件只订阅 store 中的一个切片，其他切片变化时组件不重渲染。Context 原生没有 selector，这是它在高频场景下吃力的根本原因。

21.2 粗粒度 Provider 的重渲染问题

Context 的订阅粒度是「整值」：Provider 一广播，所有消费者一起重渲染。组件越多、value 字段越杂，一次无关变更波及的范围就越大，这一节先看清代价，再学拆分手段。
实战中最常见的错误：把主题、用户、购物车数量、语言全部塞进一个 AppContext，Provider 包在根组件上。任何一个字段变化，整棵树里所有 useContext(AppContext) 的组件全部重渲染。
// ✗ 一个 Context 装下所有共享值，订阅粒度等于整棵树
const AppContext = createContext(null);

function App() {
  const [theme, setTheme] = useState('light');
  const [user, setUser] = useState(null);
  const [cartCount, setCartCount] = useState(0);

  return (
    <AppContext.Provider value={{ theme, user, cartCount, setTheme }}>
      <Dashboard />
    </AppContext.Provider>
  );
}

function Header() {
  const ctx = useContext(AppContext);
  // 只需要 theme，却跟着 cartCount 一起重渲染
  return <header>{ctx.theme}</header>;
}

图 21-1 粗粒度 Provider 的整值广播：一个字段变更触发全部分支重渲染

第二个隐蔽坑：Provider 的 value 直接写成对象字面量时，每次父组件渲染都会生成新引用。即使字段值一个都没变，引用变了，消费组件照样重渲染。
// ✗ 对象字面量：每次 App 渲染都是新引用，消费组件无条件重渲染
<ThemeContext.Provider value={{ theme, setTheme }}>
  <Page />
</ThemeContext.Provider>

21.3 细粒度拆分：多 Context 分层嵌套

第一道防线是按职责拆 Context：主题、用户、语言各自独立，Provider 分层嵌套。主题变化只波及订阅 ThemeContext 的组件，与 UserContext 的消费方互不干扰。

const ThemeContext = createContext('light');
const UserContext = createContext(null);
const LocaleContext = createContext('zh-CN');

function App() {
  const theme = useTheme();
  const user = useCurrentUser();
  const locale = useLocale();

  return (
    <ThemeContext.Provider value={theme}>
      <UserContext.Provider value={user}>
        <LocaleContext.Provider value={locale}>
          <Dashboard />
        </LocaleContext.Provider>
      </UserContext.Provider>
    </ThemeContext.Provider>
  );
}

拆分粒度再细一层：只被某棵子树使用的值，Provider 就挂在该子树根上，而不是根组件。例如「当前编辑表单的草稿状态」只挂在表单路由对应的子树，离开该子树即随 Provider 卸载而消失。

拆分策略做法解决的问题
按职责拆 Context主题 / 用户 / 语言 / 购物车各自独立 Context一类值变化不再波及其他类别的消费方
按子树挂 Provider只在相关子树根提供值，而非根组件缩小广播范围，卸载时自动释放
消费端就近读取把 useContext 放到真正使用值的叶子组件避免中间组件因订阅而被牵连重渲染

实践中 Provider 层级还可以按路由分组：只在需要主题与用户的布局外层挂载，纯工具页面（如登录页）不接收业务 Provider，避免无关订阅；子树卸载时，仅属于该子树的 Provider 一并释放，缓存的上下文值随之消失。

21.4 稳定 value 与 memo 组合拳

第二道防线是保证引用稳定：value 对象用 useMemo 包裹，对象内的回调函数用 useCallback 固定引用；消费组件在必要时用 React.memo 包裹，避免父组件自身渲染把它带累。

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');

  const toggle = useCallback(() => {
    setTheme((t) => (t === 'light' ? 'dark' : 'light'));
  }, []);

  // value 引用只在 theme / toggle 变化时才更新
  const value = useMemo(() => ({ theme, toggle }), [theme, toggle]);

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
}
// 消费组件：只在 user 变化时重渲染；父组件其他 state 变化不波及
const Avatar = memo(function Avatar() {
  const user = useContext(UserContext);
  return <span>{user.name}</span>;
});
memo 只比较 props 引用：父组件传给被 memo 组件的对象、回调若仍是新字面量，memo 不会命中；useMemo、useCallback 必须配套使用，单独包 memo 收益有限。
手段解决什么局限
useMemo 包裹 value避免对象字面量每次渲染产生新引用value 内部字段真变了仍会广播，这是设计行为
useCallback 固定回调保证 Provider 与子树内回调引用稳定依赖数组写错反而引入陈旧闭包（第 11 章）
memo 包裹消费组件阻断父组件渲染向本组件的传导props 引用不稳定时 memo 失效，需配合 useMemo
Context 原生没有 selector：组件读到的永远是整个 value。想要「只订阅 store 的一个切片、其余字段变化不触发渲染」，需要 Zustand 或 Redux 的 selector 机制，分别见第 22 章与第 23 章。

21.5 Context 的能力边界

Context 擅长承载低频、跨树、形态简单的值；高频更新、结构化数据、服务端数据都不是它的职责范围。下表给出可直接对照的判断清单。

场景是否适合 Context原因 / 替代方案
主题色、界面语言、登录用户适合更新低频、形态简单、跨树共享，正是 Context 的主场
购物车数量、侧边栏折叠谨慎可拆成独立 Context 承载；条目明细这种高频结构化数据应进 Zustand / RTK
商品列表、订单详情等服务端数据不适合需要缓存、去重、失效、刷新，交给 TanStack Query / RTK Query（第 24–27 章）
表单字段与校验状态不适合交给 react-hook-form，按字段粒度管理订阅（第 35 章）
需要中间件、Action 日志、时间旅行调试的业务状态不适合Context 不提供这些工程能力，应选 Redux Toolkit
不要用 Context 硬模拟 Redux：自己写一个 reducer + Context 包裹全树后，依然缺少 action 序列化日志、DevTools、中间件、选择器缓存与可预测的状态变更流程。需要这些工程能力时，直接使用第 23 章的 Redux Toolkit。

综合判断：主题、语言、用户这类低频跨树值用 Context 承载是合理的工程选择；一旦发现某个 Context 内字段更新频繁、消费组件多且字段杂，就是时候引入第 22 章的 Zustand 或第 23 章的 Redux Toolkit，把切片订阅能力交给外部 store。

21.6 Context / Zustand / Redux Toolkit 对照

下表把三者放在同一组维度下比较，作为第 22、23 章的预热；细节 API 在对应章节展开。

维度ContextZustandRedux Toolkit
订阅粒度整值广播，无 selectorselector 订阅单个切片selector 订阅单个切片
样板代码很少极少中等，createSlice 已大幅简化
DevTools / 中间件无内置内置 DevTools，生态中间件丰富官方完善的中间件与 DevTools 体系
状态位置React 组件树内组件树外的外部 store组件树外的单一 store
典型适用规模低频共享配置值中小到中大型应用大型团队、强规范与协作场景

三个库在同一项目里并不冲突：低频配置值用 Context，业务共享状态用 Zustand 或 RTK，服务端状态交给查询库；选型问题本质是状态分层问题，回到第 20 章的决策树即可定位当前状态属于哪一层。

一句话边界：Context 解决 props 钻取，不解决全局状态工程化；高频、结构化、需要切片订阅的共享状态，交给 Zustand 或 Redux Toolkit。
