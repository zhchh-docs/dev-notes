24.1 服务端状态与手写请求的缺陷

第 20 章把服务端状态单独分了一层：它的权威来源是后端，前端需要缓存、去重、失效、刷新与错误重试。手写 useEffect + useState 只能拿到「发请求、存结果」的最小闭环，工程能力全部要自己补。
能力手写 useEffect + useState查询库（RTK Query / TanStack Query）
多组件同参数请求去重各自发请求，无法共享缓存按 queryKey / endpoint 自动去重共享
组件卸载后过期响应处理需手写 ignore 标记与竞态防护框架内置竞态丢弃
缓存复用与过期判断刷新即丢失，无 stale / gc 概念内置 staleTime、keepUnusedDataFor 生命周期
变更后刷新相关列表手动重新调用查询函数，易漏改标签 / 失效键自动触发重取
重试、轮询、窗口聚焦刷新逐处手写逻辑配置项声明式开启
加载 / 错误 / 成功三态每个组件维护三个布尔值hook 返回标准化状态字段
第 10 章用 useEffect 处理请求是为了理解同步心智；生产项目里，列表、详情、表单提交等服务端交互应交给查询库，不要把缓存逻辑重复写进每个组件。

24.2 RTK Query 的定位与集成方式

RTK Query 是 Redux Toolkit 官方内置的服务端状态方案，随 @reduxjs/toolkit 一起发布，不需要单独安装。它在 RTK store 内部维护一个 api 切片：请求缓存、标签、变更结果都存进 Redux 状态树，组件通过自动生成的 hooks 读取。

适用前提：项目已经使用 Redux Toolkit 管理客户端共享状态。此时引入 RTK Query 可以让客户端状态与服务端状态共享同一个 store、同一套 DevTools；项目若没有 Redux 基础，单独为查询能力引入 RTK Query 并不划算。

24.3 createApi：endpoints、query 与 mutation

createApi 是 RTK Query 的契约中心：一次调用声明后端基地址、标签枚举与全部 endpoints；query 管读、mutation 管写，hook 由框架按命名规则自动生成，不需要手写请求样板。

createApi 定义后端接口契约：baseQuery 指定基础请求器与基地址，endpoints 用 builder.query 声明读操作、用 builder.mutation 声明写操作。定义完成后，RTK Query 按命名规则自动生成对应的 React hooks。

// app/apiSlice.js
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export const apiSlice = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Post'],
  endpoints: (builder) => ({
    // 读：获取文章列表
    getPosts: builder.query({
      query: () => '/posts',
      providesTags: ['Post'],
    }),
    // 读：获取单篇文章
    getPost: builder.query({
      query: (id) => `/posts/${id}`,
      providesTags: (result, error, id) => [{ type: 'Post', id }],
    }),
    // 写：新增文章
    addPost: builder.mutation({
      query: (body) => ({ url: '/posts', method: 'POST', body }),
      invalidatesTags: ['Post'],
    }),
  }),
});

// 自动生成 hooks：useGetPostsQuery / useGetPostQuery / useAddPostMutation
export const { useGetPostsQuery, useGetPostQuery, useAddPostMutation } = apiSlice;

把 api 切片注册进 store：reducer 挂载到 apiSlice.reducerPath，中间件追加 apiSlice.middleware，负责缓存生命周期、去重与标签失效。

// app/store.js
import { configureStore } from '@reduxjs/toolkit';
import { apiSlice } from './apiSlice';

export const store = configureStore({
  reducer: {
    [apiSlice.reducerPath]: apiSlice.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(apiSlice.middleware),
});
概念query（读）mutation（写）
语义获取服务端数据，结果进入缓存创建 / 更新 / 删除服务端资源
hook 形态useGetPostsQuery()，挂载即自动请求useAddPostMutation() 返回 [触发函数, 状态]
返回值data、isLoading、isFetching、error、refetch触发函数、isLoading、error、reset
标签角色providesTags：声明本缓存属于哪些标签invalidatesTags：声明完成后使哪些缓存失效
 
import { useGetPostsQuery, useAddPostMutation } from './app/apiSlice';

function PostList() {
  const { data: posts, isLoading, error } = useGetPostsQuery();
  const [addPost, { isLoading: isAdding }] = useAddPostMutation();

  if (isLoading) return <p>加载中…</p>;
  if (error) return <p>加载失败，请稍后重试</p>;

  return (
    <div>
      <button disabled={isAdding} onClick={() => addPost({ title: '新文章' })}>
        新增文章
      </button>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>{post.title}</li>
        ))}
      </ul>
    </div>
  );
}

24.4 缓存标签体系

标签（tags）是 RTK Query 组织缓存失效的方式：先在 tagTypes 声明可用标签名，query 用 providesTags 把缓存挂上标签，mutation 用 invalidatesTags 在成功后让对应标签的缓存过期，相关组件下一次挂载或重新订阅时自动重取。

配置项规则与用途
tagTypes在 createApi 顶层声明标签枚举，如 ['Post', 'User']，后续 endpoints 只能引用已声明的标签
providesTags（query）把当前缓存归入标签；支持 { type: 'Post', id } 形式的带实体标签，实现单条记录级失效
invalidatesTags（mutation）变更成功后使对应标签缓存过期；标签全量失效或按 id 精准失效均可
失效结果被失效缓存在下次挂载 / 窗口聚焦等时机重取；当前已挂载组件可配置自动刷新
 
endpoints: (builder) => ({
  getPost: builder.query({
    query: (id) => `/posts/${id}`,
    // 带 id 的实体标签：只失效这一篇，不影响其他详情缓存
    providesTags: (result, error, id) => [{ type: 'Post', id }],
  }),
  updatePost: builder.mutation({
    query: ({ id, body }) => ({
      url: `/posts/${id}`,
      method: 'PUT',
      body,
    }),
    // 精准失效该 id，同时让列表标签 Post 过期
    invalidatesTags: (result, error, { id }) => [
      { type: 'Post', id },
      'Post',
    ],
  }),
})
标签粒度要与业务一致：新增文章只需要让「文章列表」标签失效；编辑单篇文章应精准失效对应 id，避免整类缓存全部重取造成多余请求。第 26 章会把这套思路与 TanStack Query 的失效键体系对照讲解。

24.5 缓存生命周期与刷新配置概览

RTK Query 为每个 query 缓存维护生命周期参数；本章先建立概念，具体时间阈值与策略选择在第 26 章统一展开。

配置项含义
keepUnusedDataFor缓存脱离所有订阅后保留的时长（秒），到期从 store 移除
refetchOnMountOrArgChange组件重新挂载或参数变化时是否重新请求；可设为 true 或秒数阈值
refetchOnFocus / refetchOnReconnect窗口重新聚焦、网络恢复时是否自动重取（需配置监听）
pollingInterval轮询间隔（毫秒），适合实时性要求高的看板类页面
上述参数在 endpoint 级别或 createApi 全局级别配置；默认值与 TanStack Query 的 staleTime、gcTime 概念对应，第 25、26 章会给出并列对照表。
缓存参数不要在每个 endpoint 上复制粘贴：全局默认值集中在 createApi 配置，单个 endpoint 只覆盖特殊项；否则后续调整阈值要逐处修改，容易遗漏。

参数覆盖顺序与其他查询库一致：全局默认低于 endpoint 默认，endpoint 默认低于单查询配置；排查「为什么没按预期刷新」时，按这一顺序核对当前生效值，先确认是哪一层配置在起作用。

24.6 取舍：RTK Query 还是 TanStack Query

两者解决同一类问题（服务端状态缓存、去重、失效、三态），生态归属不同：RTK Query 长在 Redux 技术栈内，TanStack Query 框架无关、React 侧为 @tanstack/react-query（第 25 章）。

维度RTK QueryTanStack Query v5
技术栈前提项目已使用 Redux Toolkit无状态管理库依赖，可单独接入
状态存放位置RTK store 的 api 切片，可在 DevTools 时间旅行独立 QueryCache，不进入 Redux 状态树
接口定义方式createApi 集中声明 endpoints 与标签每个 hook 内 queryKey + queryFn，就近定义
失效机制标签体系（tagTypes / provides / invalidates）查询键前缀匹配 invalidateQueries（第 26 章）
异步变更体验mutation hook 直接返回触发函数与状态mutation 配套乐观更新与回滚 API 更完整（第 27 章）
生态与社区Redux 官方体系，与 thunk / slice 协同紧密独立团队维护，Vue / Svelte 等框架均有对应版本
决策口径：已经是 RTK 项目 → RTK Query 保持技术栈统一；使用 Zustand、Context 或没有全局状态库 → 直接选 TanStack Query。不要在同一项目里并行两套查询库。
不要因为「以后可能换技术栈」就同时引入两套查询库：缓存、失效与三态状态会在两套体系间重复维护，排错时还要先判断问题属于哪一套；选型一旦确定，全项目统一。

要点一句话
服务端状态权威来源在后端，前端需要缓存、去重、失效、重试与三态管理
