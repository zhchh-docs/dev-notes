20.1 状态的六种出身

选型错误的根源往往不是工具不会用，而是动手前没有先问一句：这份状态属于谁？ 是组件自己的、跨组件共享的、后端来的，还是地址栏里的？归属不同，工具完全不同。

一个 React 应用里看似都叫 state，其实来源、生命周期、更新频率、归属范围完全不同。下表把它们分成六类，后续每一章都对应其中一层。

类别典型例子归属范围生命周期
本地组件状态输入框聚焦态、弹窗开关、当前展开的 Tab、暂存的草稿单个组件（或组件与其直接子级）随组件卸载消失
跨组件共享状态登录用户、主题色、侧边栏折叠、购物车数量、全局语言整棵子树或全局跨路由、跨组件长期存在
服务端状态商品列表、用户资料、订单详情、搜索结果后端数据源受缓存、过期与刷新策略管理
表单状态字段值、校验错误、是否脏数据、提交中标记表单组件内部提交成功后清空或归档
路由 / URL 状态当前路径、查询参数、选中的筛选条件、分页页码浏览器地址栏随 URL 变化，可刷新可分享
派生状态总价、过滤后的列表、格式化后的时间计算时存在不需要单独存储
派生状态根本不该进入 state：它由其他状态计算得出，存储一份等于维护两份真相，必然产生不同步。
常见惯性做法是先把数据存进 state、再用 effect 同步到另一份显示值；读到「先存后算」的代码时，优先问一句：这个值能不能直接由已有状态算出来？
// ✗ 多余：把派生值再存进 state，等于让 effect 去同步另一份数据
const [total, setTotal] = useState(0);
useEffect(() => setTotal(price * count), [price, count]);

// ✓ 渲染期间直接计算，零额外状态
const total = price * count;

这与第 10 章「你不需要 Effect」的结论一脉相承：只要一个值能由已有的 props 或 state 算出来，就不要新建 state，也不要用 effect 去同步它。

20.2 状态分层模型

把六类状态投影到一张分层图上：自下而上依次是服务端状态层、全局共享层、组件本地层，而 URL 状态横跨整棵应用；派生状态不落地，只在渲染时计算。越靠近底层的状态越「权威」，越靠近组件层的状态越「临时」。

图 20-1 React 应用状态分层：服务端状态为权威来源，本地状态最临时，URL 状态独立成层

分层原则：能放低层就不放高层，状态尽量靠近使用它的组件。上提一层就要承担一层的订阅、重渲染与测试成本。

为什么要强调「靠近使用方」？因为状态每上提一层，受影响的组件范围、重渲染概率、调试难度都随之上升。一个只被弹窗内部使用的开关，放进全局 store 后，所有订阅者都要为它的一次开关付出订阅成本。

状态层首选工具备选工具不该用什么

20.4 两种典型误配

实战中 80% 的状态混乱都来自两个方向：要么把本地状态全局化，要么把全局状态本地化（prop 钻取）。它们方向相反，症状相似：代码能跑，但越写越慢、越测越重。

20.4.1 误配一：把本地状态全局化

一个只被单个组件使用的开关、草稿、选中项，被放进全局 store 或 Context，理由是「以后别的组件可能要用」。这是典型的提前抽象。
// ✗ 弹窗开关放进全局 store，只为这一个组件服务
import { create } from 'zustand';

const useUiStore = create((set) => ({
  panelOpen: false,
  togglePanel: () => set((s) => ({ panelOpen: !s.panelOpen })),
}));

function HelpPanel() {
  const { panelOpen, togglePanel } = useUiStore();
  // …
}

// ✓ 留在组件内部，卸载即清空，订阅者只有自己
function HelpPanel() {
  const [panelOpen, setPanelOpen] = useState(false);
  const togglePanel = () => setPanelOpen((v) => !v);
  // …
}

20.4.2 误配二：把共享状态本地化（prop 钻取）

当 props 穿过三层以上组件、中间组件根本不关心这个值时，说明状态被压在了错误的层。继续往下传会让每一层都多出无关签名，修改时一路连锁改动。
// ✗ user 一路钻取：Layout、MenuBar 只是透传，并不使用
function App() {
  const user = useUser();
  return <Layout user={user} />;
}

function Layout({ user }) {
  return <MenuBar user={user} />;
}

function MenuBar({ user }) {
  return <Avatar user={user} />;
}

// ✓ 上提到共享层（Context / Zustand / Redux），Avatar 直接读取
function Avatar() {
  const user = useCurrentUser();
  // …
}
症状诊断处理方向
全局 store 里某个 state 只有一个组件读写本地状态被全局化退回 useState，等真有第二个使用方再上提
props 钻取超过 3 层、中间组件不关心共享状态被本地化上提到 Context / Zustand / Redux Toolkit（第 21–23 章）
列表数据在组件卸载后丢失、切回页面重复请求服务端状态被当成本地状态交给查询库管理缓存（第 25 章）
刷新页面后主题、登录态丢失共享状态缺少持久化store 内同步 localStorage，或由后端会话提供
返回上一页，表单草稿还在旧组件里残留本地状态生命周期边界不清用 key 重置，或明确归到表单状态层

20.5 选型决策流程

每新增一份状态，按顺序回答四个问题：来自后端吗？被多个不相邻组件需要吗？需要出现在 URL 里吗？剩下的就是本地状态。问题顺序不可颠倒——先问来源，再问范围，最后问位置。

图 20-2 状态选型决策树：先判来源（后端），再判范围（共享），最后判位置（URL / 本地）

决策问题是 → 状态去向否 → 下一步
这份数据来自后端 API 吗？服务端状态层：查询库管理缓存与刷新继续问问题 ②
被树中多个不相邻组件需要吗？共享状态层：Context / Zustand / RTK继续问问题 ③
需要出现在地址栏、可分享可刷新吗？URL 状态层：useSearchParams继续问问题 ④
以上都不符合本地状态层：useState / useReducer结束判断
 
// 决策流程的代码化表达（用于评审时快速对表，不是运行时函数）
function chooseLayer(state) {
  if (state.comesFromServer) return 'TanStack Query / RTK Query';
  if (state.isSharedAcrossTrees) return 'Context / Zustand / Redux Toolkit';
  if (state.mustBeInUrl) return 'useSearchParams';
  return 'useState / useReducer';
}
不要为「以后别的组件可能要用」提前把状态上提：抽象以真实需求为准。今天只被弹窗使用的开关，明天真被复用了再上提，成本只是移动几行代码；提前全局化的代价是当下就承担订阅与重渲染成本。
先分类，再选工具；工具是分层的结果，而不是信仰。没有任何一个全局状态库值得为本地状态服务。

20.6 跨框架与后端经验类比

从前端转全栈的读者大多熟悉 Vue 与 Java 后端概念，下表把相似心智一一对应，帮助你把已有经验迁移过来；但 React 生态更强调「状态归属分层」，概念映射不等于实现照搬。

概念React 体系Vue 体系（Pinia）Java 后端类比
全局状态容器Zustand store / Redux storePinia storeApplicationContext 中的单例 Bean
读取状态useStore(selector) / useSelectorstoreToRefs按类型注入 Bean
更新状态setState / dispatch + reduceraction 方法调用服务层 setter 方法
服务端数据TanStack Query / RTK QueryTanStack Query（Vue Query）后端本身即数据源，无前端缓存概念
派生值渲染时计算 / useMemocomputedDTO 的 getter 计算属性
注意差异：Java 单例 Bean 直接保存可变对象，而 React 状态必须遵守不可变更新（第 44 章展开）；Pinia 允许在 action 内直接修改 state，Zustand 与 Redux 都要求返回新对象或借助 Immer，不可想当然地类比写法。

本篇后续章节按「共享状态（第 21–23 章）→ 服务端状态（第 24–27 章）→ 状态可测试性（第 28 章）」的顺序展开，与图 20-1 的分层一一对应。

✓ 本章小结

要点一句话
六种出身本地 / 共享 / 服务端 / 表单 / URL / 派生，归属不同工具不同
分层原则状态尽量靠近使用方，能不上提就不上提
派生不入库能算出来的值不要存成 state，不要用 effect 同步

✎ 本章习题

A 基础为下列状态各选一层并说明理由：① 侧边栏折叠开关；② 订单列表；③ 表格当前页码与关键字；④ 表单校验错误；⑤ 购物车条目数量；⑥ 由单价、数量计算的总价。要求写出六行对照表。
B 进阶阅读这段 prop 钻取代码：App 把 theme 依次传给 Header、Nav、Logo，前两层不使用该值。判断它属于哪一类误配，改写为共享状态层方案，并说明上提后哪些组件可以不再接收 theme props。
C 挑战为「主题色 + 界面语言 + 当前登录用户 + 商品列表 + 购物车条目 + 侧边栏折叠 + 列表筛选与页码」这组需求画出状态分层图（可仿照图 20-1 的四层结构），为每项指定工具，并回答：主题与语言是否需要持久化到 localStorage？筛选条件为什么应放进 URL 而不是全局 store？
