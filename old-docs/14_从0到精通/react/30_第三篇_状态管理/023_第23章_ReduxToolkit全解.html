23.1 原始 Redux 的样板痛点

Redux 的核心思想——单一 store、不可变状态、action 驱动 reducer、单向数据流——至今仍是大型应用状态工程化的范本；但原始写法要求开发者手写 action type 常量、action creator、switch reducer，三处重复且容易出错。Redux Toolkit 2.x 正是官方推出的「标准写法封装」，把这些样板自动生成。
// 原始 Redux：一个计数动作要在三处重复维护
const INCREMENT = 'counter/increment';

function increment() {
  return { type: INCREMENT };
}

function counterReducer(state = { value: 0 }, action) {
  switch (action.type) {
    case INCREMENT:
      return { ...state, value: state.value + 1 };
    default:
      return state;
  }
}
环节原始 ReduxRedux Toolkit 2.x
action type手写字符串常量，易拼写错误createSlice 按 name/reducer 自动生成
action creator手写函数返回 { type, payload }由 slice 的 actions 自动导出
reducer 不可变更新手写展开运算符，深层嵌套极易漏写内置 Immer，可直接「原地写法」，自动产出新状态
store 配置手动组合 reducer、挂载中间件、DevToolsconfigureStore 一键配置，默认含 DevTools 与常用中间件
异步流程手写 redux-thunk 动作与状态分支createAsyncThunk 标准化三态 action
RTK 没有改变 Redux 的单向数据流，只是把重复劳动收进框架：action 描述「发生了什么」，reducer 决定「状态怎么变」，store 是唯一权威来源。

23.2 configureStore 与 Provider 挂载

store 装配分两步：configureStore 把各切片 reducer 组合成单一状态树，Provider 把 store 注入组件树；之后组件通过 Hook 读写，不再需要逐层传递状态。
npm install @reduxjs/toolkit react-redux

configureStore 接收一个 reducer 映射表，把各切片 reducer 组合成单一 store；react-redux 的 Provider 把 store 注入组件树，组件才能用 useSelector 读取。

// app/store.js
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './features/counter/counterSlice';
import userReducer from './features/user/userSlice';

export const store = configureStore({
  reducer: {
    counter: counterReducer,
    user: userReducer,
  },
});
// App.jsx
import { Provider } from 'react-redux';
import { store } from './app/store';

export default function App() {
  return (
    <Provider store={store}>
      <RootRoutes />
    </Provider>
  );
}
store 中的状态树与 reducer 映射表一一对应：state.counter 来自 counterReducer，state.user 来自 userReducer。这就是「按领域切片、组合成单一 store」的结构。

23.3 createSlice：状态、reducer 与自动 action

createSlice 接收 name、initialState 与 reducers 映射表，同时生成 reducer 与对应的 action creator。reducer 内部可以直接修改 state——RTK 用 Immer 把这种「原地写法」转换成不可变更新。

// features/counter/counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
    decrement(state) {
      state.value -= 1;
    },
    incrementByAmount(state, action) {
      state.value += action.payload;
    },
  },
});

// 自动生成 action creator：{ type: 'counter/increment' }
export const { increment, decrement, incrementByAmount } = counterSlice.actions;
export default counterSlice.reducer;
概念说明
name切片命名空间，自动作为 action type 前缀，保证全应用唯一
initialState切片初始状态，结构即状态树中该分支的形状
reducers同步更新逻辑；函数签名 (state, action) => void，action 携带 payload
导出的 actions每个 reducer 对应一个 action creator，组件内 dispatch 调用
导出的 reducer注册进 configureStore 的 reducer 映射表
Immer 的「原地写法」只在 slice 的 reducer 内部成立；在 action 外部、组件代码里仍然要遵守不可变更新规则，不要直接改状态对象。

23.4 createAsyncThunk 与 extraReducers 三态

异步逻辑（请求后端、读本地存储）不能放进同步 reducer。createAsyncThunk 接收一个类型前缀与异步函数，自动生成 pending、fulfilled、rejected 三个 action；slice 在 extraReducers 里用 builder 分支分别处理三种状态。

// features/user/userSlice.js
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

export const fetchUser = createAsyncThunk(
  'user/fetchById',
  async (userId, thunkAPI) => {
    const res = await fetch(`/api/users/${userId}`);
    if (!res.ok) return thunkAPI.rejectWithValue('加载失败');
    return res.json();
  }
);

const userSlice = createSlice({
  name: 'user',
  initialState: { data: null, status: 'idle', error: null },
  reducers: {},
  extraReducers(builder) {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.status = 'loading';
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = 'succeeded';
        state.data = action.payload;
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = 'failed';
        state.error = action.payload;
      });
  },
});

export default userSlice.reducer;
thunk 状态actionUI 对应表现
pendingfetchUser.pending显示加载中（spinner / 骨架屏），清空旧错误
fulfilledfetchUser.fulfilled写入 payload，渲染成功内容
rejectedfetchUser.rejected写入 error，渲染错误提示与重试入口
异步状态（loading / error）属于服务端状态的管理范畴。RTK 用 thunk 三态可以手写实现，但缓存、去重、失效、乐观更新等能力需要 RTK Query（第 24 章）或 TanStack Query（第 25 章）补齐。

23.5 组件内读写：useSelector 与 useDispatch

组件用 useSelector 从 store 提取切片，用 useDispatch 拿到 dispatch 函数派发 action。useSelector 默认按引用比较提取结果，selector 返回对象时应拆分字段或使用浅比较。

import { useSelector, useDispatch } from 'react-redux';
import { increment, decrement, incrementByAmount } from './counterSlice';

function Counter() {
  const value = useSelector((state) => state.counter.value);
  const dispatch = useDispatch();

  return (
    <div>
      <span>{value}</span>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(decrement())}>-1</button>
      <button onClick={() => dispatch(incrementByAmount(5))}>+5</button>
    </div>
  );
}

派生值需要跨多个切片计算时，使用 createSelector 生成记忆化选择器：输入不变时复用上次结果，避免每次渲染重复计算。

import { createSelector } from '@reduxjs/toolkit';

const selectItems = (state) => state.cart.items;

export const selectTotal = createSelector(
  [selectItems],
  (items) => items.reduce((sum, it) => sum + it.price * it.qty, 0)
);
useSelector 默认按引用比较返回结果：selector 直接返回新对象字面量会导致组件每次都重渲染。需要组合多字段时，拆分多个 selector 或使用浅比较，与第 22 章 useShallow 遇到的问题同源。

23.6 目录结构约定与切片组合

RTK 官方推荐「按功能领域组织目录」（feature-based），每个领域一个文件夹，内部包含 slice、组件、选择器与测试文件，而不是把所有 reducer、action、组件分别堆进三个全局目录。

文件 / 目录职责
app/store.jsconfigureStore 组合各切片 reducer，注册中间件
features/counter/counterSlice.js该领域的状态、同步 reducer、异步 thunk、选择器
features/counter/Counter.jsx该领域的展示组件，调用 useSelector / useDispatch
features/counter/counterSlice.test.jsreducer 与 action 的单元测试（第 28 章展开）
切片之间需要共享状态时，优先在 thunk 里通过 thunkAPI.getState() 读取其他切片，或把跨领域逻辑放到独立的服务层；避免在 reducer 里直接引用另一个切片的内部结构。
不要在一个切片的 reducer 里直接读取或修改另一个切片的内部结构：切片之间应通过 thunk 读取 getState 或独立服务层通信，保持切片边界清晰、可独立测试（第 28 章展开）。

23.7 RTK 与 Zustand 选型对照

两者都提供 selector 切片订阅与外部 store，差异主要在规范强度、样板量与生态中间件。下表用于团队评审时对照，而非二选一的绝对标准。

维度Redux Toolkit 2.xZustand v5
状态更新方式派发 action → reducer 集中处理，流程可追溯action 内直接调用 set，写法直接
样板代码中等：slice、thunk、目录约定极少：一个 create 调用
规范约束强：action 可序列化，适合多人协作与代码评审弱：约定依赖团队自觉
调试工具Redux DevTools 时间旅行、action 日志完善内置 DevTools 集成，能力较基础
服务端状态配套 RTK Query（第 24 章）需自行对接 TanStack Query
适用场景大型团队、业务状态复杂、要求可追溯与工程规范中小到中大型应用、追求开发速度与轻量依赖
选型判断：团队规模大、变更频繁、需要 action 审计与统一规范，选 RTK；个人项目或中小应用、追求少代码，选 Zustand。两者都不要用来管理服务端缓存。
