27.1 三种更新体验

写操作的用户体验分三类：悲观更新先等请求成功再改界面；乐观更新先改界面再发请求，失败再回滚；静默更新后台发送、界面只做轻微指示。选择取决于操作失败的代价与延迟容忍度。
类型流程优点典型场景
悲观更新点击 → 发请求 → 成功后改 UI；失败保持原状状态永远与后端一致，无需回滚逻辑表单提交、支付、删除等高代价操作
乐观更新点击 → 先改缓存与 UI → 发请求；失败回滚还原响应即时，无等待感；点赞、收藏常用点赞、收藏、关注、开关切换等轻量可逆操作
静默更新后台发送，界面仅显示轻量状态指示，不立即反映结果不打断用户当前操作草稿自动保存、埋点上报、批量后台同步
高代价操作不要乐观：删除、支付、转账一旦失败再回滚，用户已经看到「成功」的假象，二次确认成本很高。乐观更新只适合轻量、可逆、失败可静默还原的操作。

三类体验可以在同一个产品里并存：表单提交走悲观保证一致性，点赞收藏走乐观追求即时反馈，草稿保存走静默不打断当前输入。判断顺序：先问操作失败的代价——代价高（删除、支付、提交）直接悲观；代价低且可逆（点赞、收藏、关注）再考虑乐观；后台自动保存、上报类需求默认静默。

27.2 useMutation 生命周期钩子

mutation 的钩子链把乐观更新拆成可测试的固定步骤：请求前快照与预写、请求中等待、成功或失败分支处理、最终统一收尾。按钩子分工写代码，回滚逻辑就不会散落在组件事件回调里。

useMutation 在 mutationFn 前后提供一组钩子，正好对应乐观更新需要的每一步：onMutate 在请求发起前执行（快照与预写缓存），onSuccess 在成功后执行，onError 在失败后执行，onSettled 在成功或失败后都执行，用于收尾失效。

图 27-1 乐观更新生命周期：onMutate 预写缓存，成功或失败后由 onSettled 统一收尾

钩子职责
onMutate(variables)请求前执行；快照旧缓存、取消并发查询、预写乐观数据；返回值即 context
mutationFn(variables)实际发起后端请求，返回 Promise
onSuccess(data, variables, context)请求成功后执行，可做后续副作用（提示、跳转）
onError(error, variables, context)请求失败后执行，依据 context 快照回滚缓存
onSettled(data, error, variables, context)成功或失败都执行；统一失效相关查询，让缓存与后端对齐

27.3 标准乐观更新与回滚流程

以「文章点赞」为例，标准流程分四步：onMutate 中先取消进行中的同类查询避免覆盖快照，读取旧缓存作为回滚快照，再把新状态写入缓存；onError 用快照还原；onSettled 失效相关查询，以服务端数据为准完成对齐。

import { useMutation, useQueryClient } from '@tanstack/react-query';

function useLikePost(postId) {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: () =>
      fetch(`/api/posts/${postId}/like`, { method: 'POST' }).then((r) => r.json()),

    onMutate: async () => {
      // ① 取消进行中的同类查询，避免旧响应覆盖乐观数据
      await queryClient.cancelQueries({ queryKey: ['post', postId] });

      // ② 读取快照，失败时用于回滚
      const previous = queryClient.getQueryData(['post', postId]);

      // ③ 先写缓存：界面立即反映点赞状态
      queryClient.setQueryData(['post', postId], (old) =>
        old ? { ...old, liked: true, likes: old.likes + 1 } : old
      );

      return { previous };
    },

    onError: (error, variables, context) => {
      // ④ 失败：用快照还原缓存
      if (context?.previous) {
        queryClient.setQueryData(['post', postId], context.previous);
      }
    },

    onSettled: () => {
      // ⑤ 无论成败，失效缓存并以服务端数据重新对齐
      queryClient.invalidateQueries({ queryKey: ['post', postId] });
    },
  });
}
onMutate 返回的 context 会作为第三个参数传给 onError 与 onSettled；回滚快照必须从这里取，不要在闭包变量里存旧值——闭包在多次并发调用间会互相覆盖。

快照记录的是缓存中的旧列表对象引用，不是组件界面；回滚时直接把快照写回缓存，组件由缓存驱动重新渲染，不需要手动遍历 DOM 还原界面状态。

onSettled 统一失效的意义在于：失败回滚后也要让缓存与后端对齐——回滚只是临时还原界面，服务端真实状态仍需通过重取确认，避免乐观快照与后端长期不一致。

27.4 并发、竞态与防护写法

乐观更新的风险集中在「短时间内多次点击」与「操作途中数据又被查询刷新覆盖」。防护手段包括：onMutate 内 cancelQueries、提交期间禁用按钮、等待 mutateAsync 完成后再开放操作。

function LikeButton({ postId }) {
  const likePost = useLikePost(postId);

  const handleClick = async () => {
    // mutateAsync 等待请求结束，期间按钮禁用，防止重复点赞
    await likePost.mutateAsync();
  };

  return (
    <button onClick={handleClick} disabled={likePost.isPending}>
      {likePost.isPending ? '提交中…' : '点赞'}
    </button>
  );
}
风险场景后果防护手段
连点多次提交按钮多个 mutation 并发，状态互相覆盖isPending 期间禁用按钮，使用 mutateAsync 串行等待
操作途中后台查询返回旧数据乐观结果被旧响应覆盖onMutate 先 cancelQueries 取消进行中查询
失败后闭包里存的旧值已被后续调用覆盖回滚到错误状态快照放在 onMutate 返回的 context 中传递给 onError
切换路由 / 标签页后失败回滚回调在卸载组件上操作缓存缓存读写经 QueryClient 完成，与组件生命周期解耦；组件卸载后回滚仍作用于缓存层
乐观更新期间不要让用户离开当前上下文后再操作同一资源：组件卸载后按钮禁用状态随之消失；关键页面可在路由层锁定重复入口，或依赖 isPending 状态在重新挂载时恢复禁用。

27.5 失败回滚后的 UX 规范

乐观更新失败不等于把错误吞掉。回滚完成后必须让用户知道操作没成功：给出错误提示、保留重试入口，必要时提供「稍后重试」的引导。界面状态在 onError 后应回到操作前的样子。

function LikeButton({ postId }) {
  const likePost = useLikePost(postId);

  return (
    <div>
      <button onClick={() => likePost.mutate()} disabled={likePost.isPending}>
        {likePost.isPending ? '提交中…' : '点赞'}
      </button>
      {likePost.isError && (
        <span role="alert" style={{ color: '#b91c1c' }}>
          点赞失败，请稍后重试
        </span>
      )}
    </div>
  );
}
提示信息应来自 error 对应的业务状态，不要把网络错误堆栈直接展示给用户；后端返回的可读错误信息优先，通用失败兜底文案其次。
失败提示不要只显示「操作失败」而不说明资源与原因：用户需要知道是哪条内容、什么问题，才能决定重试还是稍后再试；提示文案应与后端业务错误码对应，而不是直接抛出网络异常文本。

重试入口可以直接复用同一个 mutation 的触发函数；回滚后的界面保持操作前状态，用户点击重试即重新发起请求，不需要先刷新页面。重试次数应有上限，避免接口故障时前端循环提交。

27.6 常见错误清单

现象原因与修正
点了点赞没反应，转圈很久写成了悲观更新：先等请求成功才改 UI；轻量操作应乐观预写缓存
失败后点赞数停留在错误值缺少 onError 回滚，或快照未通过 context 传递
回滚后界面与后端短暂不一致onSettled 未失效缓存；收尾调用 invalidateQueries 对齐服务端数据
多次连点产生重复请求与状态错乱未禁用按钮；用 isPending 禁用并以 mutateAsync 串行
乐观数据被后台旧响应覆盖onMutate 忘记 cancelQueries；先取消同类进行中查询再写缓存
删除操作也用了乐观更新高代价操作不应乐观；删除、支付等应走悲观流程并二次确认
判断一个操作是否适合乐观：可逆、轻量、失败可静默还原三个条件同时满足才选乐观；缺一就回到悲观更新，先请求成功再改变界面。
一句话总结：轻量可逆操作乐观、高代价操作悲观；快照走 context、取消先行、回滚在 onError、对齐在 onSettled、失败必须可见。

要点一句话
