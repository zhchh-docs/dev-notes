26.1 缓存生命周期时间轴

每个查询缓存条目都经历四个阶段：fresh（新鲜）→ stale（过期）→ inactive（无订阅）→ 被回收。两个时间阈值决定阶段切换：staleTime 决定多久算过期，gcTime 决定无订阅后保留多久。

图 26-1 缓存生命周期：staleTime 划分新鲜 / 过期，gcTime 划分无订阅保留 / 回收

阶段触发条件行为
fresh成功取数后 staleTime 内重新挂载、窗口聚焦都不重取，直接展示缓存
stale超过 staleTime 或被 invalidateQueries 标记当前活跃订阅组件后台重取；无订阅时等待下次挂载再取
inactive最后一个订阅组件卸载不再重取，缓存进入 gcTime 倒计时
已回收无订阅时长超过 gcTime缓存条目被删除；再次访问等同于首次加载

两个阈值的经验取值：staleTime 按数据新鲜度要求设定，低频配置可拉长到数分钟；gcTime 取 5 分钟左右即可，过短会导致用户返回页面时重复请求，过长则让长时间离开的页面残留旧缓存。阈值不是全局统一参数，先设全局默认，再按查询逐个覆盖。

两条时间线并行计数：fresh / stale 取决于上一次取数时间与 staleTime；inactive / 回收取决于最后一个订阅者卸载时刻与 gcTime。两者互不影响——缓存处于 fresh 但组件已卸载，照样进入回收倒计时。

26.2 主动失效：三个 API 的语义差异

主动操作缓存的三个 API 语义差别很大：一个负责「标记过期等重取」，一个负责「直接删除」，一个负责「直接写入」。混用是列表不刷新、旧数据残留的常见原因，先分清再调用。

需要在变更后手动干预缓存时，QueryClient 提供三个操作，语义不可混淆：invalidateQueries 标记过期并触发活跃组件重取；removeQueries 直接删除缓存；setQueryData 直接写入缓存（不触发重取，常用于乐观更新）。

import { useQueryClient } from '@tanstack/react-query';

function usePostActions() {
  const queryClient = useQueryClient();

  const afterCreate = () => {
    // ① 让 ['posts'] 前缀下的缓存全部过期，活跃组件后台重取
    queryClient.invalidateQueries({ queryKey: ['posts'] });
  };

  const resetPostCache = () => {
    // ② 直接删除缓存；下次挂载按首次加载流程取数
    queryClient.removeQueries({ queryKey: ['posts'] });
  };

  const patchPost = (id, updater) => {
    // ③ 直接写缓存：不发请求、不标记过期，乐观更新时使用
    queryClient.setQueryData(['post', id], (old) =>
      old ? { ...old, ...updater } : old
    );
  };

  return { afterCreate, resetPostCache, patchPost };
}
API语义典型场景
invalidateQueries把匹配缓存标记为 stale，活跃订阅组件自动重取；非活跃缓存等待挂载新增 / 修改 / 删除成功后刷新列表与详情
removeQueries直接删除匹配缓存，等同于从没访问过退出登录清空用户数据；切换账号清理旧缓存
setQueryData直接写入或更新缓存条目，不发请求、不改变 stale 状态乐观更新先改 UI；手动合并服务端返回的新数据
getQueryData同步读取当前缓存快照，不触发订阅乐观更新前读取旧值用于回滚（第 27 章）
键匹配规则：queryKey 按前缀匹配。['posts'] 会同时命中 ['posts']、['posts', userId]、['post', id] 之外同前缀条目；加 exact: true 才做精确匹配。失效前先确认前缀不会误伤其他数据。
失效前先把 queryKey 前缀画出来：['post'] 与 ['posts'] 仅差一个字母，前者不会命中后者；前缀写错时缓存静默不失效，表现为「新增后列表不更新」。

实践中变更动作集中放在 mutation 的 onSuccess / onSettled 钩子内调用失效 API，组件事件只负责触发 mutation；这样失效逻辑与业务操作绑定，不会因为漏写某个组件的成功回调而残留旧缓存。

26.3 自动刷新配置

除手动失效外，查询库提供一组声明式自动刷新开关，可在 QueryClient 全局默认配置，也可在单个 useQuery 上覆盖。v5 默认开启窗口聚焦与网络恢复重取。

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,
      refetchOnMount: true,          // 组件挂载时，stale 数据是否重取
      refetchOnWindowFocus: true,    // 窗口重新聚焦时重取
      refetchOnReconnect: true,      // 网络恢复时重取
      refetchInterval: false,        // 不开启轮询
    },
  },
});
配置项行为说明
refetchOnMount组件挂载时，缓存已 stale 是否重取；true 总是检查，false 只在无缓存时取数
refetchOnWindowFocus用户切走标签页再切回时，活跃查询自动重取，保证页面回到前台时数据新鲜
refetchOnReconnect网络断开后恢复连接时重取活跃查询
refetchInterval固定轮询间隔（毫秒）；看板、消息计数等实时场景使用
retry / retryDelay失败重试次数与退避延迟策略，接口抖动时避免用户立即看到错误
自动刷新不是越多越好：高频列表开启窗口聚焦重取会造成不必要的请求量；静态配置类数据应把 staleTime 拉长甚至永不失效。刷新策略要按页面业务选择，见 26.6。

全局默认只设基线，特殊查询在 useQuery 配置对象里逐项覆盖，避免把每个参数都复制到 hook 调用中。

function ProductList({ category }) {
  const list = useQuery({
    queryKey: ['products', category],
    queryFn: fetchProducts,
    // 单查询覆盖全局默认：该列表 20 秒内视为新鲜
    staleTime: 20_000,
    refetchOnWindowFocus: true,
  });
  // …
}

26.4 手动刷新与轮询

useQuery 返回的 refetch 函数用于手动触发一次取数，常见于「刷新」按钮与下拉刷新；refetchInterval 用于固定轮询，适合订单状态、实时看板这类需要主动跟踪变化的页面。

function OrderStatus({ orderId }) {
  const { data, isFetching, refetch } = useQuery({
    queryKey: ['order', orderId],
    queryFn: ({ signal }) =>
      fetch(`/api/orders/${orderId}`, { signal }).then((r) => r.json()),
    refetchInterval: 15_000,   // 每 15 秒轮询一次订单状态
    staleTime: 10_000,
  });

  return (
    <div>
      <p>当前状态：{data?.status}</p>
      <button onClick={refetch} disabled={isFetching}>
        {isFetching ? '刷新中…' : '手动刷新'}
      </button>
    </div>
  );
}
轮询间隔应结合业务变化频率选择：订单状态 10–30 秒可接受，实时消息通知才考虑秒级；长时间停留在页面上时可配合组件卸载停止轮询——refetchInterval 会随组件卸载自动停止。
轮询不要默认开启：只有订单状态、消息计数等需要主动跟踪变化的页面才使用 refetchInterval；普通列表依赖窗口聚焦与挂载重取即可，轮询会在后台持续消耗请求量。

refetch 的触发时机分两类：用户主动点击刷新按钮，或钩子检测到 stale 数据在挂载、聚焦、重连等时机被访问；轮询则是时间驱动，与用户操作无关。二者可以并存，但轮询间隔决定后台请求的最低频率。

26.5 两套失效体系对照

第 24 章讲过 RTK Query 的标签失效，本章讲的是 TanStack Query 的键前缀失效；两者思想相同（声明缓存归属、变更后通知归属集合），实现载体不同。下表并列对照，便于跨项目迁移。

维度RTK Query 标签体系TanStack Query 查询键
归属声明providesTags 把缓存挂到标签 / 实体 id 上queryKey 数组层级天然构成前缀归属
失效触发mutation 内 invalidatesTagsmutation 成功后 invalidateQueries 按前缀匹配
精准失效{ type: 'Post', id } 实体标签['post', id] 键路径 + exact: true
覆盖范围标签可跨多个 endpoint 共享归属前缀层级可跨多个查询共享归属
风险点标签漏声明导致缓存不失效前缀过宽导致一批无关缓存被重取
跨技术栈迁移时不要照搬标签名：RTK Query 的 providesTags 声明在 query 上，TanStack Query 的归属由键前缀天然形成；把前者的标签清单思维直接套到后者，容易漏掉前缀层级导致失效范围错误。

26.6 典型页面策略选型

下表把常见页面形态映射到具体参数组合，作为项目初始化时的默认值参考；页面特殊需求再在单查询上覆盖。

页面形态staleTime自动刷新倾向失效时机
后台列表（高频变动）0–30 秒开启窗口聚焦重取新增 / 修改 / 删除成功后 invalidate 前缀
详情页30–60 秒默认聚焦重取自身变更后按 id 精准失效
实时看板 / 订单状态5–10 秒refetchInterval 轮询状态推进后失效对应键
低频静态配置（字典、权限菜单）数分钟到永不失效关闭聚焦重取登录 / 切换角色时 removeQueries 清空
个人草稿 / 表单暂存不进入查询缓存—提交成功即移除本地草稿状态

落地顺序建议：先在 QueryClient 全局设定一组保守默认值（适中的 staleTime、开启聚焦重取、关闭轮询），再逐类页面覆盖；遇到反馈「数据旧」的页面先查 staleTime 与失效键，遇到「请求太多」的页面先查轮询与前缀范围。

  • 把全局 staleTime 设为 0：每次挂载都重取，缓存形同虚设；
  • 所有列表开启 refetchInterval：后台请求量随打开页面数量线性增长；
  • 失效键写成根前缀：一次失效清空全部模块缓存，应按业务模块组织前缀层级。
策略判断顺序：先问数据变化频率，再定 staleTime；先问用户是否需要看到最新值，再定自动刷新；先问变更影响哪些键，再定失效前缀。不要把 staleTime 全设为 0 换来每次挂载都请求。

✓ 本章小结

要点一句话
生命周期fresh → stale → inactive → 回收，阈值由 staleTime 与 gcTime 决定
invalidateQueries标记过期并让活跃组件重取，用于变更后刷新
removeQueries直接删除缓存，用于登出、切账号等场景
setQueryData直写缓存不发请求，用于乐观更新与手动合并
自动刷新挂载、窗口聚焦、网络恢复、轮询四类开关，按页面频率配置
策略选型频率定 staleTime，新鲜度要求定自动刷新，变更范围定失效前缀
