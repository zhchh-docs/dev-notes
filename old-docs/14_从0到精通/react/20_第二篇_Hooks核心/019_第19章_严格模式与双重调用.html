开发环境里组件函数跑两遍、effect 先建立再清理再建立，很多新手以为这是 React 的 bug。StrictMode 恰恰是故意如此：通过双执行把「渲染不纯」「cleanup 漏写」「订阅重复」这类问题在开发期放大暴露。本章讲清双跑的确切范围、背后意图、生产环境行为差异，以及让代码通过严格模式体检的适配清单。

19.1 StrictMode：在哪里开启、检查什么

StrictMode 是一个仅用于开发环境的包装组件：把需要体检的子树包起来，React 就在开发模式下对这棵树执行额外的检查与双执行。它不渲染任何可见 UI，也不影响生产构建。

// main.jsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(
  <StrictMode>
    <App />
  </StrictMode>
);

StrictMode 在开发期主要做两类事：双执行（本章重点）与弃用 API 警告（19.6 节）。它不会修改组件的真实行为，只是把潜在问题提前暴露在控制台里。

注意StrictMode 只包裹需要体检的子树即可，不必整站强制开启；包裹位置越高，双跑覆盖的组件越多。它是开发辅助工具，生产打包时这些额外检查自动失效，不会增加线上运行成本。
类比 Java 测试中的「重复执行用例检查幂等性」：同一个操作执行两次结果一致，说明逻辑纯净；React 的 StrictMode 把这套检查自动化地应用到组件渲染与副作用上。

19.2 开发期双重调用的确切范围

React 18 起，StrictMode 在开发环境中会对以下内容执行两次：

  1. 组件函数体：函数组件被调用两次，两次渲染结果必须一致；
  2. useState / useReducer 的初始化函数：惰性初始化函数被调用两次，结果应保持幂等；
  3. 渲染期间计算的派生函数：在 JSX 计算阶段被调用的纯函数会被双调用；
  4. effect 的 setup 与 cleanup 循环：首次挂载时按「setup → cleanup → setup」执行一遍，模拟「挂载 → 卸载 → 再挂载」。

图 19-1 StrictMode 开发期 effect 双跑时序：先建立、再清理、再建立，验证 cleanup 完整

function Profile({ userId }) {
  // 组件函数体在开发期执行两次
  console.log('render Profile', userId);

  const [data, setData] = useState(() => {
    // 惰性初始化函数也执行两次，必须幂等
    return loadCache(userId);
  });

  useEffect(() => {
    console.log('effect: 建立订阅');
    const sub = subscribe(userId);
    return () => {
      console.log('cleanup: 断开订阅');
      sub.unsubscribe();
    };
  }, [userId]);

  return <div>{data.name}</div>;
}

// cleanup: 断开订阅

19.3 为什么 React 要故意双跑

理解双跑的设计意图，就不会把开发期的重复日志当成框架 bug：React 主动模拟「执行两遍、挂载两次」，用最小代价检验代码是否满足「渲染纯净、副作用成对清理」两条基本要求。

双跑不是为了制造噪音，而是针对两类最常见的 React 缺陷设计的压力测试。

暴露渲染期的不纯操作

组件函数应该是纯函数：同样的 props 与 state 产出同样的 JSX，不修改外部变量、不产生可观察副作用。如果渲染期间读写了模块级变量、直接操作 DOM、发请求，双调用会让错误结果立刻显现。

暴露不完整的 cleanup

effect 先 setup 再 cleanup 再 setup，等价于在挂载瞬间模拟一次「卸载再挂载」。如果 cleanup 漏写，第一次 setup 建立的定时器、订阅、连接不会被释放，第二次 setup 又叠加一份——资源重复占用在开发期立刻暴露，而不是等到线上路由切换、组件反复挂载后才积累成内存泄漏。

StrictMode 双跑的本质：把「挂载 → 卸载 → 再挂载」压缩到首次渲染瞬间完成，专门检验你的 cleanup 是否真的把上一次同步彻底断开。
代码问题双跑下的表现对应原则
渲染期修改模块级计数器计数翻倍，两次渲染结果不一致渲染必须纯净
effect 未写 cleanup定时器/订阅建立两份，行为重复触发副作用成对清理（第 11 章）
初始化函数读外部随机源且不幂等两次初始化结果不同，界面闪烁初始化可重复执行
组件内直接操作外部 DOM双调用导致重复插入或覆盖DOM 操作走 effect 与 ref

19.4 哪些会双跑、哪些不会

把范围边界记清楚，才能解释控制台里哪些日志属于正常现象、哪些才是问题。

位置 / 代码开发期是否双调用说明
组件函数体是两次渲染结果必须一致
useState(init) 惰性初始化函数是init 必须幂等，不能依赖外部单次读取
effect setup 与 cleanup是（挂载时循环一次）验证 cleanup 能完整释放资源
事件处理函数否用户点击只执行一次，不在双跑范围
setTimeout / 异步回调内部逻辑否回调在渲染之外触发，不被重复执行
生产构建（production）否StrictMode 双跑只存在于开发环境
常见误解「我的接口在开发环境被请求了两次，是不是 React 的 bug？」——如果请求写在 effect 里，双跑确实会触发两次 setup；这恰恰提醒你：请求类副作用要配合 cleanup 取消旧请求（第 11 章），而不是把 StrictMode 关掉。生产环境不会重复请求。
事件处理函数里的逻辑不会被双跑：用户点击一次就执行一次。如果发现点击回调里的副作用重复触发，问题通常在组件被重复挂载、或回调被重复绑定，而不是 StrictMode。

19.5 适配清单：让代码通过严格模式体检

适配严格模式只需要守住三条底线：渲染函数保持纯净、初始化函数保持幂等、订阅与定时器成对清理。做到这三点，双跑日志只是确认；做不到，开发期暴露的问题正是线上隐患的提前预演。

① 组件函数体保持纯净

// ✗ 渲染期读写模块级变量，双调用下结果不可预测
let visitor = 0;
function Counter() {
  visitor += 1;
  return <span>访问次数：{visitor}</span>;
}

// ✓ 状态归组件所有，渲染只读取
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => { setCount((c) => c + 1); }, []);
  return <span>{count}</span>;
}

② 初始化函数保持幂等

// ✗ 初始化函数产生副作用，双调用会执行两次
const [token] = useState(() => {
  sessionStorage.setItem('token', createToken());
  return createToken();
});

// ✓ 副作用放进 effect；初始化只做纯读取
const [token, setToken] = useState(() => sessionStorage.getItem('token'));
useEffect(() => {
  if (!token) {
    const next = createToken();
    sessionStorage.setItem('token', next);
    setToken(next);
  }
}, [token]);

③ 订阅、定时器、连接成对清理

useEffect(() => {
  const socket = io(url);
  socket.on('message', appendMessage);
  return () => socket.disconnect();   // ✓ 双跑下第一次连接被彻底断开
}, [url]);

useEffect(() => {
  const id = setInterval(() => setTick((t) => t + 1), 1000);
  return () => clearInterval(id);      // ✓ 避免两个定时器叠加
}, []);

④ 避免模块级副作用

// ✗ 模块被引入时立刻执行连接，组件卸载也无法回收
const conn = createConnection();

// ✓ 连接在 effect 中建立，cleanup 中断；模块级只保留常量与纯函数
const API_BASE = '/api';
场景严格模式下的问题代码适配方式
渲染期发请求 / 改外部变量函数体内直接 fetch、累加全局计数移入 effect；显示数据用 state
定时器未清理双跑后两个 interval 同时触发cleanup 中 clearInterval
订阅未断开双跑后两条消息通道并存cleanup 中 unsubscribe / disconnect
初始化函数不幂等两次初始化产出不同随机值初始化只做纯计算，副作用进 effect
模块级建立连接引入即占用，无法随组件回收连接生命周期交给 effect 管理

19.6 附加检查与排查清单

除双跑外，StrictMode 还会在开发期检测不安全的遗留用法并给出警告，例如类组件中已弃用的生命周期方法、历史遗留的 findDOMNode 等。新项目使用函数组件时这些警告基本不会出现；维护老项目时，警告信息本身就是迁移清单。

  1. 控制台 effect 日志成对出现两次 → 先判断是否属于挂载时的正常双跑；再检查 cleanup 是否成对；
  2. 开发环境接口请求两次 → 请求写在 effect 中属预期双跑；按第 11 章加 cleanup 取消旧请求，生产环境只发一次；
  3. 计数、订阅、定时器重复叠加 → cleanup 遗漏，按 19.5 清单逐项补齐；
  4. 两次渲染结果不一致导致闪烁 → 渲染期存在不纯操作，定位函数体内的外部读写并移除；
  5. 不要用「移除 StrictMode」解决问题：它只是体检仪，真正要修的是被它照出来的代码缺陷。
StrictMode 不是调试开关，而是开发规范的一部分：组件纯净、副作用成对、初始化幂等，做到这三点，双跑日志就只是确认而非告警。

✓ 本章小结

要点一句话
开启位置在 createRoot 附近用 <StrictMode> 包裹组件树，仅影响开发环境
双跑范围组件函数体、state 初始化函数、render 期派生函数、effect 的 setup/cleanup 循环
核心意图暴露渲染不纯与 cleanup 遗漏，提前发现订阅、定时器、外部连接的重复占用
生产行为生产构建不双跑；事件处理函数与异步回调不会被 StrictMode 双调用
适配原则组件保持纯净、初始化幂等、副作用成对清理、不要在模块级与渲染期写副作用

✎ 本章习题

A 基础在入口文件用 StrictMode 包裹根组件；分别打开与关闭严格模式，观察一个挂载时 console.log('mount') 的组件在控制台的输出次数差异，并写出组件函数、effect、cleanup 各自的打印顺序。
