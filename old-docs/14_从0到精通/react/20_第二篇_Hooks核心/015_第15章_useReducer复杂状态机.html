第 15 章 useReducer：复杂状态机

教科书 第 15 章 / 共 64 章 · 预计 50 分钟 · 把状态转移规则集中成纯函数

当一个组件的状态开始出现多字段联动、多种操作类型、转移规则需要集中审计时，散落的 useState 会让事件处理函数越写越乱。useReducer 把「当前状态 + 动作」交给一个纯函数 reducer 计算新状态，天然形成状态机。本章讲清三件套、标准写法、TypeScript 类型约束、惰性初始化，以及它与 Redux 的血缘关系。

15.1 什么时候 useState 不够用

先用一组状态写个简单表单没问题。当字段超过三四个、操作超过五种，更新规则散落在各个事件回调里，很快会出现这些症状：同一个字段在不同回调里以不同方式更新；一段联动逻辑被复制粘贴到两处；调试时要在组件里翻找「到底是谁改了这个状态」。

useReducer 的思路是把「状态怎么变」从组件事件函数里抽走，集中到一个纯函数里描述：组件只负责发出动作（action），reducer 负责计算新状态。这与 Java 中把状态转移规则收敛到独立枚举状态机的思路一致。
信号useState 的表现useReducer 的表现
状态字段超过 3 个且互相联动多个 setter 分散，联动顺序靠人脑保证一次 action 派生完整新状态，规则集中可见
操作类型 5 种以上事件回调里堆叠 if/else 与字段更新reducer 内按 action.type 分支，一一对应
需要复盘「状态如何到达当前值」更新路径分散在各回调中action 历史可记录、可回放、可测试
简单开关、单个文本框一行 useState 最简洁引入 reducer 反而增加样板代码

15.2 三件套：reducer / action / dispatch

reducer 是一个纯函数：接收当前状态与动作，返回新状态。action 是描述「发生了什么」的普通对象，约定带 type 字段，其余数据放在 payload。dispatch 是组件拿到的分发函数，调用它把 action 送进 reducer。

图 15-1 useReducer 数据流：action 与旧状态进入 reducer，产出新状态并安排重渲染

import { useReducer } from 'react';

const initialState = { count: 0 };

function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT':
      return { ...state, count: state.count + 1 };
    case 'DECREMENT':
      return { ...state, count: state.count - 1 };
    case 'RESET':
      return { ...initialState };
    default:
      return state;   // 未知 action 返回原状态，不能返回 undefined
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: 'INCREMENT' })}>+1</button>
      <button onClick={() => dispatch({ type: 'DECREMENT' })}>-1</button>
      <button onClick={() => dispatch({ type: 'RESET' })}>重置</button>
    </div>
  );
}
reducer 必须返回新对象；default 分支原样返回旧状态。React 按状态引用是否变化决定是否重渲染，直接改写原状态会让界面不更新。

15.3 完整示例：登录表单状态机

状态机的价值在「阶段明确」时最大：空闲、提交中、成功、失败之间允许哪些转移、每个转移携带什么数据，都写在 reducer 分支里，事件处理函数只负责发起动作。

表单最典型的复杂之处是状态带有阶段（空闲、提交中、成功、失败），字段变更与阶段切换交织。用 reducer 把转移规则收拢到一处：

const initialState = {
  email: '',
  password: '',
  status: 'idle',            // idle | loading | success | error
  error: null,
};

function formReducer(state, action) {
  switch (action.type) {
    case 'FIELD_CHANGE':
      return { ...state, [action.field]: action.value };
    case 'SUBMIT_START':
      return { ...state, status: 'loading', error: null };
    case 'SUBMIT_SUCCESS':
      return { ...state, status: 'success' };
    case 'SUBMIT_ERROR':
      return { ...state, status: 'error', error: action.error };
    default:
      return state;
  }
}

function LoginForm() {
  const [state, dispatch] = useReducer(formReducer, initialState);

  async function handleSubmit(e) {
    e.preventDefault();
    dispatch({ type: 'SUBMIT_START' });
    try {
      await api.login(state.email, state.password);   // 副作用放在事件函数里
      dispatch({ type: 'SUBMIT_SUCCESS' });
    } catch (err) {
      dispatch({ type: 'SUBMIT_ERROR', error: err.message });
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={state.email}
        onChange={(e) => dispatch({ type: 'FIELD_CHANGE', field: 'email', value: e.target.value })}
      />
      <input type="password"
        value={state.password}
        onChange={(e) => dispatch({ type: 'FIELD_CHANGE', field: 'password', value: e.target.value })}
      />
      <button disabled={state.status === 'loading'}>
        {state.status === 'loading' ? '提交中…' : '登录'}
      </button>
      {state.status === 'error' && <p>{state.error}</p>}
    </form>
  );
}
边界reducer 是纯函数，发请求、读本地存储、写日志都不能放进去；副作用留在事件处理函数中，成功/失败后再 dispatch 对应 action。这与第 10 章「渲染与 effect 保持纯净」是同一条原则。
不要在 reducer 里用 if (action.type === 'SUBMIT_START') 顺手发请求：纯函数被 React 多次调用、StrictMode 双跑时，请求会被重复发出；网络行为必须留在组件层。

15.4 与 useState 对照、与 Redux 的关系

对比项useStateuseReducer
更新方式调用 setter，新旧状态由回调决定dispatch action，规则集中在 reducer
状态结构每个状态一份独立调用单对象状态，按字段组织
可测试性要通过组件交互间接测试reducer 是纯函数，可单独单测 action → 新状态
样板代码量少action 类型、reducer 分支带来额外代码
跨组件共享需要逐层 props 或 Context可与 Context 组合分发到深层组件

Redux 的核心思想——单一状态树、action 描述变更、纯 reducer 转移状态——在 useReducer 里都能看到。区别在于：useReducer 只服务当前组件（或配合 Context 做局部共享），没有中间件、时间旅行、选择器缓存等全局能力。

// useReducer + Context 的常见组合：reducer 放进 Provider，
// 后代组件通过自定义 Hook 同时拿到 state 与 dispatch。
// 这是 Redux 单一 store 模式的轻量内建版本，大型应用详见第 23 章 Redux Toolkit。
选型判断：状态字段少、转移规则直选 useState；联动多、动作类型多、需要把更新规则集中审计或单独单测时选 useReducer。复杂度是选 reducer 的理由，而不是架构偏好。
选型提醒：不要为了「看起来架构高级」给每个小组件都套 reducer。状态简单时，useState 是更诚实、更少样板的选择。

15.5 进阶：嵌套状态、TS 联合类型、惰性初始化

注意reducer 接收的 state 是只读快照：禁止直接改写它的属性或用 splice 改原数组；所有变更都要产出新对象/新数组，React 才能识别出状态变化。

嵌套状态必须逐层不可变更新

function cartReducer(state, action) {
  switch (action.type) {
    case 'ADD':
      return {
        ...state,
        items: [...state.items, action.item],
      };
    case 'UPDATE_QTY':
      return {
        ...state,
        items: state.items.map((it) =>
          it.id === action.id
            ? { ...it, qty: it.qty + action.delta }
            : it
        ),
      };
    default:
      return state;
  }
}

TypeScript action 可辨识联合类型

type FormAction =
  | { type: 'FIELD_CHANGE'; field: 'email' | 'password'; value: string }
  | { type: 'SUBMIT_START' }
  | { type: 'SUBMIT_SUCCESS' }
  | { type: 'SUBMIT_ERROR'; error: string };

function formReducer(state: FormState, action: FormAction): FormState {
  switch (action.type) {
    case 'FIELD_CHANGE':
      // 此处 action 自动收窄，可访问 action.field 与 action.value
      return { ...state, [action.field]: action.value };
    case 'SUBMIT_ERROR':
      return { ...state, status: 'error', error: action.error };
    default:
      return state;
  }
}

惰性初始化：把初始状态计算推迟到挂载时

useReducer(reducer, initialArg, init) 的第三个参数是初始化函数，用它从本地存储读取初始值，避免每次渲染都重复计算：

function init(initial) {
  const saved = localStorage.getItem('cart');
  return saved ? JSON.parse(saved) : initial;
}

const [state, dispatch] = useReducer(cartReducer, { items: [] }, init);
错误写法后果正确写法
reducer 里 state.count += 1引用未变，React 不安排重渲染返回 { ...state, count: state.count + 1 }
reducer 里发请求 / 调 localStorage纯函数被破坏，StrictMode 双调用引发重复请求副作用放事件函数，reducer 只算状态
default 分支返回 undefined未知 action 后状态丢失default 返回原状态
嵌套数组用 splice/pop 直接改原数组历史状态与新状态共享引用，难以排查map / 展开运算符生成新数组

15.6 常见坑与排查清单

  1. 界面不更新 → reducer 内直接改了原对象/数组；检查是否返回了新引用；
  2. 请求被发了两次 → 副作用写进了 reducer；StrictMode 下纯函数会被双调用，副作用会立刻暴露；
  3. action.type 拼写错误静默失效 → 未命中分支返回原状态；开启 TS 联合类型或在 default 中抛出未知类型错误；
  4. 组件内同时堆 useState 与 useReducer → 判断职责归属：联动状态进 reducer，纯展示字段留在 useState；
  5. 需要在多个组件共享同一份状态时，把本章模式与第 14 章 Context 组合；规模再大，转用第三篇介绍的 Zustand、Redux Toolkit。
reducer 的价值不在于多写代码，而在于把变更规则集中、可单测、可回放；反过来，为简单状态强行建模只会让团队的阅读成本上升。
小结口诀：state 复杂上 reducer，action 描述发生了什么；纯函数不改原状态，副作用留在组件层。
