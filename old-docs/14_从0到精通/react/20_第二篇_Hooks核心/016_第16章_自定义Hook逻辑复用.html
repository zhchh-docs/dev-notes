16.1 组件复用 UI，Hook 复用状态逻辑

一个按钮组件可以复用「按钮的外观与点击反馈」，但复用不了「跟随窗口尺寸变化、记住用户偏好、在卸载时清理监听」这类状态逻辑。过去要复用逻辑，必须借助组件形态的包装；React 16.8 引入 Hook 之后，状态逻辑终于可以封装成普通函数被反复调用。

类比 Java：组件像一个带界面的 Service，自定义 Hook 更像一个持有局部状态的工具类——区别在于 Hook 的状态生命周期与调用它的组件绑定，组件卸载时 Hook 的状态与副作用一并清理。

判断一段逻辑该不该抽成 Hook：它内部是否用到了 useState、useEffect、useRef 等 Hook，或将来可能用到？ 是，抽成自定义 Hook；纯计算、无状态的工具函数（格式化日期、金额换算）抽成普通函数即可，不要硬套 Hook 命名。

逻辑类型封装形式示例
纯函数计算，无状态无副作用普通工具函数formatCurrency(n)、clamp(x, min, max)
持有状态 + 副作用 + cleanup自定义 HookuseWindowSize、useLocalStorage
可复用的可见结构与交互组件<Modal />、<DataTable />

判断一段逻辑属于哪一类，可以顺着调用方式反推：如果复用的是「显示什么」，抽组件；如果复用的是「状态怎么管理、副作用怎么挂接与清理」，抽 Hook；两者常常组合出现——一个小组件内部调用若干自定义 Hook，组件负责外观，Hook 负责行为。

  • 纯工具函数：文件放 utils/ 目录，不调用任何 React API；
  • 自定义 Hook：文件放 hooks/ 目录，以 use 命名，内部可调用 state、effect、ref；
  • 展示组件：文件放 components/ 目录，接收 props，输出 JSX。

16.2 命名规则与合法性边界

自定义 Hook 的命名必须以 use 开头，后接大写字母开头的名词，例如 useWindowSize、useLocalStorage。这条规则不是审美约定：ESLint 的 react-hooks 插件靠命名识别 Hook，从而校验「只能在顶层调用」这条规则（第 18 章详述）。

合法性要点：自定义 Hook 内部可以调用其他 Hook；调用它的位置仍然必须是组件函数顶层，或另一个自定义 Hook 的顶层。条件分支、循环、普通工具函数里调用 Hook 同样违规。
// ✓ 合法的自定义 Hook
import { useState, useEffect } from 'react';

function useDocumentTitle(title) {
  useEffect(() => {
    document.title = title;
  }, [title]);
}

// 在组件顶层调用
function Profile() {
  useDocumentTitle('个人资料');
  return <h1>个人资料</h1>;
}
注意自定义 Hook 返回的是 Hook 管理的值与方法，不要在 Hook 内部返回一段组件 JSX 再让调用方渲染——那是 render props 时代的写法，会把组件层级与生命周期搅乱。UI 结构交给组件，状态逻辑交给 Hook。

16.3 第一个自定义 Hook：useWindowSize

写自定义 Hook 的套路与写组件一致：先确定 Hook 对外暴露什么状态与方法，再把 effect、ref、cleanup 这些内部细节藏在函数体里；调用方只关心返回值，不关心监听是何时建立、何时清理的。

需求：任意组件都能拿到当前窗口宽高，随 resize 自动更新，卸载时移除监听。把第 10、11 章学过的 effect + cleanup 规则打包进 Hook：

import { useState, useEffect } from 'react';

function useWindowSize() {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight,
  });

  useEffect(() => {
    const onResize = () => {
      setSize({ width: window.innerWidth, height: window.innerHeight });
    };
    window.addEventListener('resize', onResize);
    return () => window.removeEventListener('resize', onResize);
  }, []);

  return size;
}

// 调用方
function Sidebar() {
  const { width } = useWindowSize();
  const collapsed = width < 768;
  return <aside className={collapsed ? 'side mini' : 'side'}>…</aside>;
}

几个值得体会的设计点：Hook 的状态与调用它的组件实例一一对应；cleanup 随组件卸载自动执行；多个组件同时调用 useWindowSize，各自拥有独立的宽高状态与监听器（第 17 章会讨论共享同一份尺寸以避免重复监听的进阶做法）。

// 第二个 Hook：useDocumentTitle，演示「副作用本身就是 Hook 的全部职责」
function useDocumentTitle(title) {
  useEffect(() => {
    const prev = document.title;
    document.title = title;
    return () => { document.title = prev };   // 离开组件恢复旧标题
  }, [title]);
}
命名反模式：把内部调用了 useState 的函数写成 getWindowSize() 而不是 useWindowSize()，ESLint 会失去识别依据，条件调用等违规将不再被拦截——要么以 use 开头，要么退化成不含 Hook 的普通工具函数。

16.4 返回值设计与引用稳定化

自定义 Hook 的返回形态有三种常见模式，按调用方使用习惯选择：

模式返回内容示例
状态 + setter 元组模仿 useState 的 [value, setValue] 形态const [name, setName] = useLocalStorage('name', '')
方法对象返回聚合的方法集合，便于扩展参数{ toggle, setOn, setOff }
单一状态值Hook 内部自管副作用，外部只读最新值useWindowSize() 返回尺寸对象

当返回值包含函数或对象时，调用方常常把它放进 useEffect / useMemo 的依赖。若 Hook 每次渲染都返回新对象引用，会导致下游 effect 反复执行——需要在 Hook 内部用 useMemo、useCallback 稳定引用。

import { useState, useCallback, useMemo } from 'react';

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);

  const toggle = useCallback(() => setOn((v) => !v), []);
  const setOnTrue = useCallback(() => setOn(true), []);
  const setOnFalse = useCallback(() => setOn(false), []);

  const actions = useMemo(
    () => ({ toggle, setOn: setOnTrue, setOff: setOnFalse }),
    [toggle, setOnTrue, setOnFalse]
  );

  return [on, actions];
}
不要为了「稳定引用」给 Hook 的所有返回值无脑套 useCallback：只有被下游依赖、且反复重建会引发问题时才需要；本地组件内部直接调用的函数，稳定化只是多余成本。

16.5 复用方式演进：HOC / render props / Hook

在 Hook 普及之前，React 生态为复用状态逻辑演化出两种包装形式；理解它们有助于读懂老项目代码，也能反证自定义 Hook 的简洁性。

图 16-1 状态逻辑复用方式演进：HOC 与 render props 均以组件为包装载体，自定义 Hook 取消了中间层级

对比项HOCrender props自定义 Hook
复用载体返回包装组件的函数接收 render 函数的组件返回状态与方法的函数
组件层级多层嵌套包裹多组闭合标签嵌套无新增层级
props 冲突风险高：同名 props 覆盖难排查中：参数命名在回调里可控低：返回值自行命名
调用方代码形态withWindow(Component)<Tracker render={(w)=>…} />const size = useWindowSize()

对照同一段「跟随窗口尺寸」逻辑在两种形态下的调用方代码，层级差异非常直观：

// 旧写法（HOC）：多层包裹，props 需要在封装层与组件之间来回传递
const withWindow = (Component) => function Wrapped(props) {
  const size = useWindowSize();
  return <Component {...props} windowSize={size} />;
};
const PanelWithWindow = withWindow(Panel);

// 新写法（自定义 Hook）：组件内直接调用，无包裹层级
function Panel() {
  const size = useWindowSize();
  return <div>宽度 {size.width}</div>;
}
注意自定义 Hook 持有的状态属于「调用它的组件实例」；不要在 Hook 的模块顶层声明 let state 充当共享存储，否则多个组件实例会读到同一份被互相改写的数据。真正跨实例共享请走 Context 或状态管理库。
历史语境：第三方组件库偶尔仍导出 HOC 形式（如旧版路由的 withRouter）；新代码一律优先自定义 Hook，Hook 无法表达的可见结构才做成组件。

16.6 常见坑与排查清单

反模式后果正确做法
if 分支里调用 Hook调用顺序随条件变化，违反 Hooks 规则（第 18 章）条件外统一调用，把分支写进 Hook 内部逻辑
Hook 写成不以 use 开头的普通函数ESLint 无法识别，规则校验被绕过命名 useXxx，或拆成无状态工具函数
返回对象字面量直接交给下游依赖引用每次都变，effect 反复执行内部 useMemo 聚合，方法 useCallback 固化
Hook 内部持有跨组件共享的全局状态组件间状态互相污染共享状态上提至 Context 或状态库（第三篇）
把多个不相关逻辑塞进一个巨型 Hook职责混乱，复用与测试都变困难按职责拆分：useWindowSize、useLocalStorage 各自独立
  1. 报错「Rendered fewer hooks than expected」 → Hook 被条件调用；回到组件顶层检查 if/return 顺序（第 18 章完整解析）；
  2. 下游 effect 反复执行 → 检查 Hook 返回对象/函数引用是否稳定；
  3. 多个组件监听到的是同一份旧状态 → 不要在 Hook 模块级缓存状态；需要真正共享时引入 Context 或状态管理库；
  4. 下一章进入实战工具集：防抖、节流、上一次值、本地存储等高频 Hook 的标准实现。
好的自定义 Hook 有两个标准：调用方一眼看懂返回了什么，组件卸载时逻辑能自己收尾干净。
小结口诀：use 开头管状态，组件顶层才调用；返回对象要稳定，职责单一好复用。

✓ 本章小结

要点一句话
定位自定义 Hook 把状态、副作用、cleanup 打包复用，与组件分工不同
命名规则必须 use 开头；只能在组件或其他 Hook 顶层调用
合法边界内部自由调用 useState/useEffect/useRef 等，规则与组件内一致
返回值设计可返回状态、setter、方法对象；用 useMemo/useCallback 稳定引用
演进结论状态逻辑复用首选自定义 Hook；HOC 与 render props 仅作历史了解
