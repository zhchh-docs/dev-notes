第 12 章 useLayoutEffect 与绘制时机

教科书 第 12 章 / 共 64 章 · 预计 45 分钟 · 绘制前的最后一个同步窗口

useEffect 在浏览器绘制之后才异步执行，绝大多数场景这正是我们想要的；但当你需要「测量刚更新的 DOM、再在绘制前把位置/尺寸修正到位」时，就需要 useLayoutEffect。本章把组件提交的完整时序讲透，说清两个 Hook 的分工、典型场景、性能边界，以及容易混淆的 useInsertionEffect。

◆本章目标

  • 说清组件从「函数执行」到「像素上屏」之间的完整时序，明确浏览器绘制发生在哪一步；
  • 掌握 useLayoutEffect 的签名、执行时机与依赖规则，能与 useEffect 准确区分；
  • 识别三类必须在绘制前同步完成的场景：测量布局、修正位置、恢复滚动位置；
  • 知道 useInsertionEffect 的定位（库作者注入样式），业务代码不滥用；
  • 理解 useLayoutEffect 阻塞绘制的代价，能判断何时该退回 useEffect。

12.1 组件提交的四个阶段：绘制到底发生在哪

第 10 章我们建立了「effect 是提交之后的同步器」这一心智。要理解 useLayoutEffect，必须把「提交」再拆细：React 把组件函数执行完、生成新的 JSX 树之后，还要经过协调（reconcile）与提交（commit）两个内部阶段，最后才轮到浏览器把像素画到屏幕上。

浏览器绘制（paint）是一个独立的、异步的渲染步骤：React 更新完 DOM 节点并不等于用户已经看到；浏览器会把一帧内的 DOM 变更收集起来，在绘制阶段统一排版、合成、上屏。

把整条链路画出来，两个 Hook 的位置差异一目了然：

图 12-1 组件提交时序：useLayoutEffect 卡在浏览器绘制之前，useEffect 在绘制之后异步执行

可以类比 Java 里的同步代码块与异步回调：useLayoutEffect 是主线程上同步排队执行的代码，useEffect 是提交到任务队列里稍后再跑的回调。这个时序差异，决定了两者的用途边界。

12.2 useLayoutEffect：绘制之前同步执行

useLayoutEffect 的签名与 useEffect 逐参数相同：回调函数 + 可选依赖数组，回调返回 cleanup 函数。唯一区别是调度时机。

import { useLayoutEffect, useRef, useState } from 'react';

function Panel({ open }) {
  const bodyRef = useRef(null);

  useLayoutEffect(() => {
    // 此刻：DOM 已更新，浏览器尚未绘制
    const el = bodyRef.current;
    if (el) console.log('布局测量', el.scrollHeight);
  }, [open]);

  return (
    <div className="panel">
      <div ref={bodyRef} className="panel-body">内容</div>
    </div>
  );
}
对比项useEffectuseLayoutEffect
执行时机浏览器绘制之后，异步调度DOM 更新之后、浏览器绘制之前，同步执行
是否阻塞绘制不阻塞阻塞：回调没跑完，浏览器这一帧就不上屏
读取到的 DOM刚提交的新 DOM（与绘制前一致）刚提交的新 DOM
期间修改 DOM 的可见性用户已看到旧一帧，修改会造成第二帧闪烁修改与本次提交合并，用户看不到中间态
依赖 / cleanup 规则与第 11 章一致完全一致：依赖变化前先跑 cleanup，卸载时跑 cleanup
选型只看一个问题：这个回调会不会读取布局信息（尺寸、位置、滚动位置）并据此修改 DOM？ 会，就用 useLayoutEffect；不会，一律用 useEffect。
注意useLayoutEffect 里再次调用 setState，React 会同步重渲染一次，然后才允许浏览器绘制。如果在这里做了昂贵测量或多次状态更新，阻塞会被放大；后面 12.5 节专门讨论边界。
不要把 useLayoutEffect 当成「更可靠的 useEffect」：它的定位是绘制前的同步窗口，普通副作用放在这里只会平白延长每一帧的绘制时间。

12.3 典型场景：测量后立刻调整 DOM

凡是「测量刚提交的 DOM 布局 → 据此修改样式或位置」的需求，都属于 useLayoutEffect 的专属场景；事件触发后的命令式操作（如点击按钮聚焦输入框）无需进入布局副作用，普通 useEffect 即可。

场景一：展开/收起时测量内容高度，再设定过渡高度

手风琴、折叠面板动画要求先知道内容自然高度，才能从旧高度过渡到新高度。这个测量与赋值必须发生在绘制之前，否则会先出现一帧「高度为 0 的空白」或「旧高度的错位」。

function Collapsible({ open, children }) {
  const bodyRef = useRef(null);
  const [height, setHeight] = useState(0);

  useLayoutEffect(() => {
    const el = bodyRef.current;
    if (!el) return;
    setHeight(open ? el.scrollHeight : 0);
  }, [open]);

  return (
    <div className="collapsible" style={{ height, overflow: 'hidden' }}>
      <div ref={bodyRef}>{children}</div>
    </div>
  );
}

场景二：悬浮提示 / 弹窗根据锚点定位

function Tooltip({ anchorRef, text }) {
  const tipRef = useRef(null);

  useLayoutEffect(() => {
    const anchor = anchorRef.current;
    const tip = tipRef.current;
    if (!anchor || !tip) return;
    const rect = anchor.getBoundingClientRect();
    tip.style.top = rect.bottom + window.scrollY + 8 + 'px';
    tip.style.left = rect.left + window.scrollX + 'px';
  });

  return <div ref={tipRef} className="tooltip">{text}</div>;
}

场景三：滚动位置恢复（路由切换返回列表时还原滚动条）

function ScrollRestorer({ savedY }) {
  useLayoutEffect(() => {
    window.scrollTo(0, savedY);   // 绘制前归位，用户看不到先滚到底部再弹回的过程
  }, [savedY]);
  return null;
}
场景该用哪个 Hook理由
读取元素尺寸后设置动画高度useLayoutEffect测量结果必须赶在绘制前落到样式上
弹窗/气泡跟随锚点定位useLayoutEffect避免气泡先落在初始坐标再瞬移
页面返回时恢复滚动位置useLayoutEffect避免一帧内出现错误滚动位置
建立 WebSocket 连接、订阅事件useEffect不依赖布局结果，无需阻塞绘制
发起数据请求、上报埋点useEffect与布局无关，异步执行即可
关联章节：定位时频繁读取 getBoundingClientRect() 会触发强制同步布局，第 54 章「长列表与动画性能」会专门讲避免布局抖动（layout thrashing）的写法。

12.4 三个同类 Hook 对照：useEffect / useLayoutEffect / useInsertionEffect

React 还提供了 useInsertionEffect，它排在「提交 DOM 之后、useLayoutEffect 之前」，定位非常狭窄：供 CSS-in-JS 库作者向 <head> 注入样式。业务组件不需要使用它。

// 库作者视角的示意：组件库在布局测量之前把样式注入文档
useInsertionEffect(() => {
  const tag = document.createElement('style');
  tag.textContent = cssText;
  document.head.appendChild(tag);
  return () => tag.remove();
}, [cssText]);
对比项useEffectuseLayoutEffectuseInsertionEffect
执行阶段绘制之后提交后、绘制前（同步）提交后、布局 effect 之前
能否访问 ref / DOM能能能，但不推荐在里面操作 DOM 布局
典型用途订阅、请求、定时器、外部系统同步测量与位置修正、滚动恢复CSS-in-JS 注入样式（库作者）
业务代码是否常用最常用少数场景使用几乎不用
不要因为「时序更早」就把所有副作用搬进 useLayoutEffect。更早不等于更好：每一次同步执行都在延长这一帧的绘制时间，普通副作用延迟到绘制后执行反而是性能最优解。

12.5 什么时候不该用：性能边界与 SSR 注意事项

性能边界：同步阻塞会被用户直接感知为卡顿

useLayoutEffect 回调里每一句同步代码都挡在浏览器绘制前面。回调中出现网络请求、大循环、反复读写样式，就会让这一帧超过 16ms，用户感受到明显掉帧。

// ✗ 错误：在布局副作用里发请求、做重计算
useLayoutEffect(() => {
  fetch('/api/heavy').then(r => r.json()).then(setData);
  reportAnalytics();
}, []);

// ✓ 正确：与布局无关的动作放回 useEffect
useEffect(() => {
  fetch('/api/heavy').then(r => r.json()).then(setData);
  reportAnalytics();
}, []);

SSR 注意事项

服务端渲染阶段不存在浏览器、不存在布局，useLayoutEffect 在服务端执行会触发 React 的警告：「useLayoutEffect does nothing on the server」。库作者常用 useIsomorphicLayoutEffect 这类封装在 SSR 环境退化为 useEffect；业务组件则应尽量避免在首屏 SSR 的关键路径上依赖布局测量。

写法问题修正
所有 effect 都改成 useLayoutEffect不必要地阻塞每一帧绘制默认 useEffect，仅测量/定位场景升级
布局 effect 里调用 setState 触发二次渲染同步重渲染叠加测量耗时，帧率压力倍增合并测量结果；必须二次渲染时确认其必要性
SSR 首屏直接 useLayoutEffect 测量服务端报警告， hydration 时行为不一致测量逻辑放到客户端挂载后的 effect，或用 isomorphic 封装
回调内反复读 scrollHeight 再写 style触发强制同步布局（回流），动画卡顿先批量读完再批量写，详见第 54 章
常见疑问「既然 useLayoutEffect 更早，为什么官方文档说绝大多数代码不该用它？」——因为 React 推荐组件函数保持纯净，真正需要直接操作 DOM 布局的组件本来就不多；能用状态与声明式样式解决的，就不要退到命令式测量。
默认 useEffect；当且仅当你观察到「绘制后再修正导致的闪烁」，才把这一个副作用升级为 useLayoutEffect。

12.6 排查清单与本章呼应

  1. 界面先闪一下再到位（弹窗瞬移、高度跳变、滚动条回弹）→ 检查该副作用是否用了 useEffect，测量/定位类应换成 useLayoutEffect；
  2. 切换面板后这一帧明显变慢 → 看 useLayoutEffect 内是否混入了请求、重计算或多次 setState；
  3. SSR 控制台报 layoutEffect 警告 → 把测量逻辑移出服务端关键路径，或使用 isomorphic 封装；
  4. 依赖数组漏写导致定位读不到最新锚点 → 规则与第 11 章相同：用到的响应式值全部进依赖，交给 exhaustive-deps 校验；
  5. 需要持有 DOM 节点引用时，本章所有示例都依赖下一章的 useRef——第 13 章把 ref 的两种身份讲透。
小结口诀：不碰布局用 effect，测量定位用 layout；阻塞绘制要警惕，样式注入找 insertion。

✓ 本章小结

要点一句话
提交时序渲染 → 提交 DOM → useLayoutEffect 同步 → 浏览器绘制 → useEffect 异步
分工原则不读 DOM、不依赖布局结果的副作用用 useEffect；要在绘制前测量并修正用 useLayoutEffect
典型场景tooltip/弹窗定位、展开收起高度、滚动位置恢复、元素高亮滚动到可视区
useInsertionEffect只用于库作者注入样式，业务代码几乎用不到
性能边界useLayoutEffect 阻塞绘制，滥用会造成可见卡顿；SSR 下它会报警告
