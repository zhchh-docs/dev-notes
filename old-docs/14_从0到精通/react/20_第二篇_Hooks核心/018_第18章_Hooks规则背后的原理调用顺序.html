第 18 章 Hooks 规则背后的原理：调用顺序

教科书 第 18 章 / 共 64 章 · 预计 45 分钟 · 从「背规则」到「懂实现」

「不要在条件、循环里调用 Hook」「只在组件顶层调用」是人人会背的两条规则，但为什么 React 必须这样要求？本章从 Fiber 节点上的 Hook 队列讲起：状态不是按名字存储，而是按调用顺序的索引匹配。理解了这一点，违规代码为什么报错、如何重构，就不再需要死记硬背。

18.1 两条规则的原文与边界

React 文档对 Hooks 使用给出两条强制规则：

  1. 只在组件顶层（top level）调用 Hooks：不要在条件语句、循环、嵌套函数、try/catch 中调用 useState、useEffect 等；
  2. 只在 React 函数中调用 Hooks：可以在函数组件内部调用，也可以在自定义 Hook 内部调用；不要在普通 JavaScript 函数、事件处理函数、类组件方法中调用。
规则一保证「每次渲染 Hook 调用顺序完全一致」；规则二保证 Hook 能挂到某个组件实例的 Fiber 节点上，状态有归属、卸载能清理。第 16 章的自定义 Hook 之所以合法，正是因为它最终被组件顶层调用，规则在链路中保持延续。
位置能否调用 Hook原因
函数组件主体顶层可以属于 React 函数，每次渲染顺序稳定
自定义 Hook 主体顶层可以被组件顶层间接调用，链路合法
组件内 if / for 分支不可以渲染路径不同导致调用顺序变化
事件处理函数、普通工具函数不可以不属于 React 函数，没有组件实例归属
类组件 render 与生命周期方法不可以类组件使用 state 与生命周期 API

两条规则合起来回答两个问题：什么时候调用（每次渲染顺序一致）与在哪里调用（React 组件或自定义 Hook 内）。后续小节先用索引匹配原理解释规则一，再用重构方案解决条件调用问题。

18.2 状态按索引匹配：Hook 队列原理

很多人误以为 const [count, setCount] = useState(0) 的状态是按变量名 count 存进组件的。实际并非如此：React 在每个组件对应的 Fiber 节点上维护一条 Hook 队列（链表结构），每遇到一个 Hook，就把它对应的状态、effect 配置、依赖等信息挂到队列节点上。

图 18-1 Hook 队列按调用索引匹配：顺序一致才能找到正确状态，条件分支会让索引错位

用最朴素的模型理解：React 内部可以看成为每个组件准备了一个与调用顺序对齐的数组。渲染时第 1 个 useState 读数组下标 0，第 2 个读下标 1，依次类推；更新后把新值写回对应下标。只要每次渲染顺序不变，下标就能稳定对应同一个状态。

这就解释了为什么规则如此严格：React 没有能力知道你给状态起了什么名字，它只记得第几个 Hook。顺序一变，全部对应关系立刻失效。

18.3 三类违规写法与报错解析

违规代码的共同特征：Hook 的调用位置取决于运行时条件（props、数据、事件），导致两次渲染之间 Hook 队列长度或顺序不一致。下面三类写法在项目中出现频率最高，也最容易被 ESLint 第一时间拦截。

违规一：条件分支中调用 Hook

function Panel({ open }) {
  const [title, setTitle] = useState('');
  // ✗ open 为 false 时第二个 Hook 根本不执行，队列长度两次不一致
  if (open) {
    const [detail, setDetail] = useState('');
  }
  return null;
}

违规二：循环中调用 Hook

function QuestionList({ questions }) {
  // ✗ 列表条数每次都可能不同，Hook 数量随数据变化，索引无法对齐
  return questions.map((q) => {
    const [answer, setAnswer] = useState('');
    return <input value={answer} onChange={(e) => setAnswer(e.target.value)} />;
  });
}

违规三：嵌套在普通函数 / 事件回调中调用

function Login() {
  function validate(form) {
    // ✗ 这是普通函数，不是 React 函数，不能在这里调用 Hook
    const [rules, setRules] = useState([]);
    return form.email.length > 0;
  }

  function onSubmit() {
    // ✗ 事件处理函数在渲染之外触发，没有组件渲染上下文
    useDocumentTitle('提交中');
  }
}
报错信息条件分支导致 Hook 数量不一致时，控制台会出现 React has detected a change in the order of Hooks called 或 Rendered more hooks than during the previous render。报错描述的正是队列长度与本次渲染调用对不上；修改后必须连同条件调用一起删除，而不是靠重新挂载掩盖。

18.4 违规代码的重构策略

规则禁止的是「Hook 在分支里」，不是「组件根据条件显示不同内容」。条件展示完全合法，违规的只是状态也跟着条件走。四种标准重构策略按优先级选用：

策略做法适用场景
拆分子组件条件内容移入 <DetailPanel open={open} />，Hook 在子组件顶层调用条件内容自带一组状态与 UI，最清晰
合并为对象状态单个 useState 管理全部字段，条件只控制是否显示字段不多、联动简单的表单类场景
条件移入 Hook 内部Hook 顶层先调用，内部 if 决定是否执行 effect 逻辑订阅/监听类副作用需要按条件启停
提前计算派生值需要显示的内容由现有 props/state 直接算出，不新增 Hook本质不需要独立状态的展示分支
 
// 策略一：拆子组件（推荐）
function Panel({ open }) {
  const [title, setTitle] = useState('');
  return (
    <section>
      <h2>{title}</h2>
      {open && <DetailPanel />}   {/* Hook 在 DetailPanel 顶层调用 */}
    </section>
  );
}

function DetailPanel() {
  const [detail, setDetail] = useState('');
  return <textarea value={detail} onChange={(e) => setDetail(e.target.value)} />;
}
// 策略二：合并为对象状态，条件只管显示
function Panel({ open }) {
  const [form, setForm] = useState({ title: '', detail: '' });
  const update = (field) => (e) =>
    setForm((prev) => ({ ...prev, [field]: e.target.value }));

  return (
    <section>
      <input value={form.title} onChange={update('title')} />
      {open && <textarea value={form.detail} onChange={update('detail')} />}
    </section>
  );
}
// 策略三：条件移入 effect 内部，Hook 调用本身保持顶层
function LiveChart({ enabled }) {
  useEffect(() => {
    if (!enabled) return;          // 条件写在 effect 内部，合法
    const chart = initChart();
    return () => chart.dispose();
  }, [enabled]);
  return <canvas />;
}
注意「提前 return null」并不能消除违规 Hook：提前返回发生在 Hook 调用之后没问题，但返回之前不能跳过任何 Hook；把 Hook 放在 return 之后同样属于调用顺序不确定，应把子树拆成独立组件。
注意提前 return 的位置规则：所有 Hook 必须出现在 return null 之前；渲染早期判断「无数据则不显示」时，先把 Hook 调用完，再根据状态决定返回什么 JSX。

18.5 ESLint 保障与自定义 Hook 中的延续

人脑核对条件分支不可靠，官方提供 eslint-plugin-react-hooks，包含两条规则：rules-of-hooks 检查调用位置，exhaustive-deps 检查依赖数组。Vite、Create React App 等官方模板默认启用。

{
  "plugins": ["react-hooks"],
  "rules": {
    "react-hooks/rules-of-hooks": "error",
    "react-hooks/exhaustive-deps": "warn"
  }
}
# 在项目里定位违反 Hooks 规则的文件
npx eslint src --rule "react-hooks/rules-of-hooks: error"

规则在自定义 Hook 链路中同样成立：自定义 Hook 内部可以调用其他 Hook，但内部也必须保持顶层顺序。第 16 章的 useWindowSize 把条件判断写在 effect 内部，正是这条规则的实践。

把 rules-of-hooks 当作编译期防线而不是可选风格：它在打包前就指出「第几个 Hook 被条件跳过」，比运行时抛错早得多、定位也直接得多；团队不应为了消除警告而关闭规则。
检查点违规表现规则提示方向
调用位置if/for/回调/普通函数内出现 Hook把 Hook 提到组件或 Hook 顶层
命名识别普通函数内部调用 Hook 但函数未 use 开头重命名为 useXxx 或拆出 Hook 逻辑
依赖数组effect 内用到响应式值却未声明依赖按第 11 章规则补齐，不要 disable 警告
 
// ✗ 用注释关闭规则，等于绕过编译期检查
if (loggedIn) {
  // eslint-disable-next-line react-hooks/rules-of-hooks
  const [profile, setProfile] = useState(null);
}

// ✓ 正确方向：把条件内容拆成独立子组件，Hook 在子组件顶层调用
return loggedIn ? <ProfilePanel /> : <GuestPanel />;

18.6 与渲染原理衔接及排查清单

本章描述的「组件 Fiber 节点上的 Hook 队列」属于 React 渲染内部结构：第 39 章 Fiber 架构会讲节点如何可中断地工作，第 41 章函数组件执行过程会回到这里，看清组件函数执行时 Hook 队列如何被依次读取与更新。

  1. 出现 hooks order 报错 → 从报错指向的组件开始，逐层检查 if、三元表达式、map、回调内是否藏了 Hook；
  2. 条件渲染切换后状态串台 → 确认条件分支内没有挂载独立 Hook；用拆子组件方式把条件状态隔离；
  3. ESLint 规则被团队习惯性关闭 → 恢复规则，按提示重构；关闭规则等于删掉这道编译期防线；
  4. 自定义 Hook 内部条件调用了 useState → 把条件移入 effect 或整体拆成两个 Hook；
  5. 函数列表渲染时每个 <Item /> 内部各自持有状态 → 这是合法做法；违规的是在 map 回调里直接调用 Hook，应把状态下沉到 Item 组件内部。
  6. 下一章 StrictMode 会在开发环境把组件函数与 effect 跑两遍，正是对「渲染必须纯净、cleanup 必须完整」这条规则的自动化检查。
条件分支里「看起来只是多调了一次 Hook」并不会被 React 悄悄兼容：只要两次渲染路径不一致，队列索引就会错位；这类问题只靠运行时观察很难定位，务必在开发期让 ESLint 规则持续拦截。
小结口诀：Hook 状态按序排队，条件循环不能插队；规则交给 ESLint 兜底，条件内容拆成组件。

✓ 本章小结

要点一句话
两条规则只在顶层调用；只在 React 组件或自定义 Hook 内调用
原理每个 Fiber 节点维护 Hook 队列，状态按本次调用顺序的索引与上一次匹配
违规后果条件/循环/回调中调用导致索引错位，状态串台或直接报错
重构方向拆子组件、合并为对象状态、把条件移入 Hook 内部
工程保障eslint-plugin-react-hooks 的 rules-of-hooks 强制校验，不许关闭了事

✎ 本章习题

A 基础指出下面组件的违规点并改写为合法写法：function Panel({ open }) { const [title, setTitle] = useState(''); if (open) { const [detail, setDetail] = useState(''); } return null; }
B 进阶一个表格组件想在「编辑模式」下多挂载一组字段状态：把条件 Hook 重构为对象状态（单份 useState 管理全部字段，编辑模式仅控制字段是否显示），再对比「拆成 <EditForm /> 子组件」方案，说明两种方案的适用场景。
C 挑战用「索引匹配」原理解释这个现象：条件分支首次渲染走 A 路径挂了两个 Hook，第二次渲染走 B 路径只挂了一个 Hook，为什么第二个 Hook 会读到上一次的状态？写出两种修复方案，并说明 ESLint 规则在开发环境如何第一时间拦截这类错误。
