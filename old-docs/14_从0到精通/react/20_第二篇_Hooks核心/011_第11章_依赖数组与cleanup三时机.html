11.1 依赖数组的三种形态

写法何时执行 effect用途 / 风险
useEffect(fn)
（不传）		每次渲染后极少正确；通常意味着"忘了写依赖"，容易自激循环
useEffect(fn, [])仅挂载后（严格模式下还要吃一次双调用）一次性订阅、全局监听；注意它会捕获首次渲染的变量
useEffect(fn, [a, b])a 或 b 的引用/值变化后标准写法；依赖是自己声明的"同步条件"
 
// 场景演示：count 变化时的三种表现
useEffect(() => { console.log('每次都跑', count); });              // 每次渲染
useEffect(() => { console.log('只跑一次', count); }, []);          // count 永远停在初始值
useEffect(() => { console.log('count 变了才跑', count); }, [count]);
坑 1[] 不代表"只关心挂载"，而代表"我确定这里用到的值永远不会变"。若 effect 里读了 props/state 却写空数组，就必然产生陈旧闭包（读到的永远是第一次渲染的值）。

11.2 取依赖的唯一原则

原则：effect 内部用到的所有"响应式值"（props、state、以及由它们派生出的函数/对象）都必须出现在依赖数组中；不需要响应式的值（refs、模块级常量、setState 函数）不写。
function Timer({ interval, onTick }) {
  const [count, setCount] = useState(0);
  const len = interval.length;   // 派生变量

  useEffect(() => {
    const id = setInterval(() => {
      setCount(c => c + 1);     // setCount 稳定，不必写进依赖
      console.log(len);          // len 是派生值 → 必须进依赖
    }, interval);                // interval 来自 props → 必须进依赖
    return () => clearInterval(id);
  }, [interval, len]);           // ✓ 依赖 = effect 里用到的全部响应式值
}

判断某个东西要不要进依赖，只需问一句：它会随渲染变化吗？

值是否响应式进依赖？
props / state是✅
组件内计算出的对象/函数是✅
setXxx（useState 的 setter）否（引用稳定）❌
ref.current否（React 不追踪）❌
模块级常量、导入的函数否❌
工具：把 ESLint 插件 eslint-plugin-react-hooks（Vite 模板默认启用）的 exhaustive-deps 规则当作硬约束。它比人脑可靠得多。

11.3 函数依赖与对象依赖

对象/函数每次渲染都是新引用，放进依赖会导致 effect 每次都跑。三种正解：

方案一：把函数搬进 effect（首选，最简单）

// ✗ onTick 每次渲染都是新函数 → effect 每次都重建定时器
useEffect(() => {
  const id = setInterval(() => onTick(), 1000);
  return () => clearInterval(id);
}, [onTick]);

// ✓ 把逻辑搬进来
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);      // 直接用 setter，无需依赖外部函数
  }, 1000);
  return () => clearInterval(id);
}, []);

方案二：useCallback / useMemo 稳定引用

const fetchUser = useCallback(async () => {
  const r = await fetch(`/api/users/${id}`);
  setUser(await r.json());
}, [id]);                       // 只有 id 变才换新函数

useEffect(() => { fetchUser(); }, [fetchUser]);

方案三：把不需要触发重新同步的"最新值"放进 ref

function Chat({ toUser }) {
  const themeRef = useRef(theme);      // 只想读最新值，不希望它参与依赖
  useEffect(() => { themeRef.current = theme; }, [theme]);

  useEffect(() => {
    const conn = createConnection(toUser);
    conn.on('msg', m => showToast(themeRef.current, m));  // 不用进依赖
    return () => conn.disconnect();
  }, [toUser]);                          // 只有换人才重连 ✓
}
选择顺序：搬进来 > useCallback 稳定 > ref 兜底。不要为了消除 lint 警告而用 // eslint-disable-next-line 屏蔽规则——那等于关掉火警报警器。

11.4 cleanup 的三个时机

  1. 依赖变化前：先执行上一次 effect 的 cleanup，再执行新的 effect（断开旧连接 → 建立新连接）；
  2. 组件卸载时：执行最后一次 cleanup，且不再建立新 effect；
  3. 严格模式下的挂载前：开发环境中 React 会"挂载 → 卸载 → 再挂载"一次，因此你会看到 cleanup 在首次 effect 之后立刻被调用（第 19 章详解）。
useEffect(() => {
  console.log('effect: 建立');
  return () => console.log('cleanup: 断开');
}, [dep]);

// dep 从 a 变为 b 时的控制台顺序：
// cleanup: 断开      ← 清理 a 那次
// effect: 建立       ← 为 b 建立新的

// StrictMode 首次挂载时：
// effect: 建立 → cleanup: 断开 → effect: 建立

它解决了什么实际问题？看一个"不写 cleanup 就漏 table 请求"的例子：

useEffect(() => {
  const socket = io(url);
  socket.on('data', setData);
  // ✗ 没写 cleanup：切换路由后旧 socket 仍在收数据并 setState
  //    → 内存泄漏 + 报错 "Can't perform a React state update on an unmounted component"
  return () => socket.disconnect();   // ✓ 卸载/换依赖时断开
}, [url]);

记住：effect 里每建立一样东西（监听、订阅、timer、连接、第三方实例），cleanup 里就必须有对应的"反向操作"。

11.5 竞态：ignore 与 AbortController

快速输入关键词 abc → ab → a，三个请求几乎同时发出，但返回顺序不可控。若不加处理，后返回的老结果会覆盖先返回的新结果，界面显示与输入对不上。

// 方案一：布尔标记（最简洁）
useEffect(() => {
  let ignore = false;
  setLoading(true);
  api.search(keyword).then(res => {
    if (ignore) return;             // 已过期，丢弃
    setData(res); setLoading(false);
  });
  return () => { ignore = true; };  // 依赖变化/卸载时作废本次请求
}, [keyword]);
// 方案二：AbortController（真正取消请求，省流量）
useEffect(() => {
  const ctrl = new AbortController();
  api.search(keyword, { signal: ctrl.signal })
    .then(setData)
    .catch(e => { if (e.name !== 'CanceledError') report(e); });

  return () => ctrl.abort();        // 真正中断 HTTP 请求
}, [keyword]);
方式是否真正取消请求适用
ignore 标记否（只是不采纳结果）简单场景、fetch 封装不统一时
AbortController是请求体量大、弱网、需要省带宽
TanStack Query是（内建）第 25 章，生产默认方案

11.6 常见坑与排查清单

  1. effect 反复执行 → 依赖里有每次都变的对象/内联数组；把它提到外面、useMemo、或只依赖原始值（如 dep: obj.id）。
  2. 取到旧值 → 依赖漏写；开启 exhaustive-deps 并按提示修正。
  3. 自激循环 → effect 里 setState，而 state 又出现在依赖里；先判断是否根本不需要 effect（第 10 章 10.4）。
  4. StrictMode 下双调用 → 不是 bug，是在提醒你"cleanup 写得不干净"。
  5. 请求散落在各处 effect → 各自重写 loading/error/竞态逻辑，行为不一致且难维护；统一收敛到数据层（第 25 章）。
排查套路遇到 effect 异常，按三步定位：① 打印 console.log('run', deps) 看触发频率；② 检查 cleanup 是否成对；③ 临时把依赖数组写成 [] 若能修好，说明是引用不稳定问题而非逻辑问题。

✓ 本章小结

要点一句话
三种形态省略=每次渲染；[] =挂载一次；有值=依赖变化时
取依赖原则用到的响应式值全写进去；setter / ref 不用写
函数对象依赖搬进 effect → useCallback 稳定 → ref 兜底
cleanup 三时机依赖变化前、卸载时、StrictMode 首挂载
竞态ignore 标记或 AbortController 取消旧请求
lintexhaustive-deps 当作硬约束，不许 disable 了事

✎ 本章习题

A 基础说出下列三种写法下 effect 的触发时机：useEffect(fn)、useEffect(fn, [])、useEffect(fn, [a])；并说明 [] 里读 props 会有什么后果。
