主题、语言、当前用户这类「跨层级共享」的数据，一层层 props 往下传会让中间组件被迫接收自己根本不用的属性。useContext 与 Provider 提供了一条从祖先直接通向后代的数据通道。本章讲清三件套的用法、默认值规则、嵌套覆盖、TypeScript 类型约束，以及最容易被忽视的性能边界。

14.1 prop drilling：逐层传参的代价

React 组件树的数据流方向是单向向下：父组件通过 props 传给子组件。当一份数据需要从根组件传到第三层、第五层的后代组件时，中间每一层都要把这个 props 声明一遍、再往下透传，哪怕这一层完全用不到它。这就是 prop drilling。

类比 Vue 里的 provide / inject：两者解决的是同一类问题——跳过中间层级，把数据直接给到需要的后代。React 的 Context 机制与 Vue 的 provide/inject 心智相近。

图 14-1 左侧为逐层透传的 prop drilling，右侧为 Context 直接提供给消费后代

对比项逐层 propsContext
中间组件负担必须声明并透传无关 props完全不感知该数据
组件复用性脱离上层数据就无法独立使用在 Provider 包裹下可任意嵌套

14.2 三件套：createContext / Provider / useContext

第一步：在模块顶层创建 Context 对象。

// theme-context.js
import { createContext, useContext } from 'react';

const ThemeContext = createContext(null);

export { ThemeContext };
export function useTheme() {
  return useContext(ThemeContext);
}

第二步：在祖先组件用 Provider 包裹子树并通过 value 提供数据。

// App.jsx
import { useState } from 'react';
import { ThemeContext } from './theme-context';
import Sidebar from './Sidebar';

export default function App() {
  const [mode, setMode] = useState('light');
  const theme = {
    mode,
    toggle: () => setMode((m) => (m === 'light' ? 'dark' : 'light')),
  };

  return (
    <ThemeContext.Provider value={theme}>
      <Sidebar />
    </ThemeContext.Provider>
  );
}

第三步：任意后代组件通过自定义 Hook 读取。

// Menu.jsx（与 App 之间隔着 Layout、Sidebar）
import { useTheme } from './theme-context';

export default function Menu() {
  const theme = useTheme();
  if (!theme) return null;            // 未被 Provider 包裹时的兜底
  return (
    <nav className={`menu ${theme.mode}`}>
      <button onClick={theme.toggle}>切换主题</button>
    </nav>
  );
}
封装一个 useXxx() 自定义 Hook 把 useContext(XxxContext) 收进去，是项目惯例：消费方不需要知道 Context 存在，替换实现时也不用改消费组件。

14.3 默认值规则与嵌套覆盖

createContext(defaultValue) 的默认值只在当前组件树向上找不到任何匹配 Provider 时才会生效。一旦外层存在 Provider，默认值就被忽略。

const ThemeContext = createContext('light');   // 仅用于无 Provider 时的兜底

function BareButton() {
  const mode = useContext(ThemeContext);      // 读到 'light'
  return <button className={mode}>裸按钮</button>;
}

Provider 可以嵌套：内层 Provider 覆盖同一条 Context 的外层值，这就是「就近原则」。

<ThemeContext.Provider value={{ mode: 'dark' }}>
  <Header />
  <ThemeContext.Provider value={{ mode: 'light' }}>
    <Panel />   {/* 内层消费到 light */}
  </ThemeContext.Provider>
</ThemeContext.Provider>

TypeScript 下推荐把 Context 类型显式声明，避免 value 推断过宽：

import { createContext, useContext } from 'react';

interface Theme {
  mode: 'light' | 'dark';
  toggle: () => void;
}

const ThemeContext = createContext<Theme | null>(null);

export function useTheme(): Theme {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme 必须在 ThemeProvider 内使用');
  return ctx;
}
注意在 Provider 外部调用 useTheme 直接抛错，比返回 null 让深层组件在运行时崩溃更早暴露问题；自定义 Hook 里做断言是常见工程实践。
默认值只是「兜底缺口」而不是「初始状态」：组件是否使用默认值，取决于向上能否找到 Provider；嵌套 Provider 一律以内层就近提供的值为准。

14.4 典型上下文：主题、语言、当前用户

可以把 Context 理解成组件树内的一条「只读通道」：祖先提供值，后代直接订阅；它负责共享访问，不负责状态更新逻辑、异步缓存与服务端数据同步。

判断一份数据适不适合放进 Context，先看它是否满足：跨层级共享、变更频率低、多数深层组件都可能用到。

语言（i18n）上下文

interface LocaleCtx {
  lang: 'zh' | 'en';
  t: (key: string) => string;
}
const LocaleContext = createContext<LocaleCtx | null>(null);

// 消费处
const { lang, t } = useLocale();
return <h1>{t('welcome')}</h1>;

当前用户上下文

const AuthContext = createContext(null);

function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  useEffect(() => { fetchMe().then(setUser); }, []);
  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}
数据类型适合 Context？说明
主题模式、语言包适合低频变更、几乎全树消费
当前登录用户、权限角色适合跨路由共享，配合登录状态库演进
路由当前位置、全局弹窗开关适合由路由库或状态库封装后暴露
高频表单输入、动画进度不适合每次值变化引发大面积重渲染，性能差
服务器返回的列表数据不适合属于服务端状态，交给第 25 章 TanStack Query
关联章节：Context 解决的是「数据共享」，不负责异步缓存、去重与失效；那部分能力属于状态管理层，第三篇（第 20 章起）会系统讲解。

14.5 性能边界：谁消费谁重渲染

React 对 Context 的变更通知规则很直接：Provider 的 value 变化时，树中所有调用了 useContext 的组件都会重新渲染，无论它们实际用到的字段有没有变。

// ✗ 每次渲染都新建对象引用 → 即使 mode 没变，消费组件也被通知重渲染
const theme = { mode, toggle };
return <ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>

// ✓ value 用 useMemo 稳定引用；mode 真正变化时才重建
const theme = useMemo(() => ({ mode, toggle }), [mode]);

更精细的解法是拆分 Context：把「会变的值」与「稳定的回调」分开，或把大 Context 按领域拆成多个小 Context。第 21 章《Context 的正确粒度》会完整展开拆分原则、memo 包裹与选择器方案。

注意不要只靠 useMemo 掩盖粒度问题：value 引用稳定了，字段一变仍然会通知全部消费组件；当一个 Context 被多处独立使用时，拆分才是根治方案。
错误做法问题缓解方向
Provider value 是内联字面量对象每次渲染引用都变，消费组件无谓重渲染useMemo 稳定 value 引用
大而全的 Context 塞主题、用户、配置任一字段变化波及全部消费方按领域拆分多个 Context
重型展示组件直接消费 Context连带自身子树一起重渲染memo 包裹，或把消费下沉到小组件
用 Context 承载高频动画/输入状态每秒数十次全树通知，帧率崩溃局部 state 或 ref；状态管理库另选方案
Context 的性能问题不会在开发环境暴露——组件少时全部重渲染也看不出来；等到项目规模变大、页面变慢，再回头拆分成本很高。设计 Context 时就要想清楚粒度。

14.6 常见坑与排查清单

  1. 消费处读到默认值而非外层提供值 → 检查 Provider 是否真的包裹了该组件，或中间是否被另一个嵌套 Provider 覆盖；
  2. 页面毫无必要地反复重渲染 → 检查 Provider value 是否每次新建对象；先用 useMemo 稳定引用，再考虑拆分 Context；
  3. Context 里什么都放 → 对照 14.4 的表格归类：显示状态、服务端数据、表单状态各归其位；
  4. 自定义 Hook 未做 Provider 断言 → 脱离 Provider 时出现 null 读取错误，应在 Hook 内抛错给出明确提示；
  5. 下一章 useReducer 解决的是单个组件内部「复杂状态怎么转移」的问题，它常与 Context 组合，把 reducer 暴露给跨层组件调用。
Context 不是「全局状态仓库」：它没有内置缓存、请求去重、过期失效与选择器订阅；把服务端列表、高频输入塞进 Context，本质是用共享通道硬扛状态管理库的职责。
小结口诀：跨层共享找 Context，低频变更才适合；value 引用要稳定，粒度拆分留后手。
