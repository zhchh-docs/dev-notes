43.1 回顾：列表渲染中 key 的位置

第 6 章已经给出列表渲染的基本写法：map 出一组子节点，每个子节点带上 key。本章不再重复语法，而是回答第 6 章留下的原理问题：协调阶段到达一组同级子节点时，React 凭什么知道"新列表里的这一项对应旧列表里的哪一项"。

// 基础正例：使用数据自带的稳定 id 作为 key
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <TodoItem key={todo.id} todo={todo} />
      ))}
    </ul>
  );
}

本节代码是第 6 章写法的复习；43.4 节起进入原理与反例分析。如果还没建立"列表必须写 key"的习惯，建议先回看第 6 章。

43.2 没有 key 时：按位置配对

同一父节点下的一组子节点，如果元素类型相同且都没有 key，React 就按位置顺序把旧树第 1 个配新树第 1 个、旧树第 2 个配新树第 2 个……配对成功就复用 DOM 与组件 state，只更新 props。位置一变，配对关系就跟着错位。

图 43-1 无 key 按位置硬配；有稳定 key 按身份配对，顺序变化不造成错位

对照项无 key / 位置配对有稳定 key / 身份配对
配对依据新旧列表的位置下标同级范围内相同的 key 值
顺序变化时旧节点被错误配给新内容，state 与输入状态错位节点按身份找到彼此，移动位置而不销毁重建
DOM 操作量位置错位时大量节点被迫更新甚至重建只处理真正新增、删除的节点

43.3 key 的作用：身份标识与配对

带上 key 之后，协调阶段在同级范围内建立"旧节点 key → 旧 Fiber"的映射，再用新元素的 key 去查：查到了就复用对应 Fiber，把新 props 传进去；查不到就新建；旧映射里没被匹配到的节点标记为删除。

// 概念化：同级子节点按 key 配对（教学示意，非源码）
function reconcileChildren(oldChildren, newChildren) {
  const oldMap = new Map(oldChildren.map((c) => [c.key, c]));
  const result = newChildren.map((next) => {
    const old = oldMap.get(next.key);
    if (old) {
      oldMap.delete(next.key);
      return reuseFiber(old, next);   // 身份匹配：复用 DOM 与 state
    }
    return createFiber(next);         // 新身份：新建节点
  });
  // oldMap 中剩余的旧节点：标记删除
  oldMap.forEach((old) => markDeleted(old));
  return result;
}
不要跨层比对key 的映射表只在同一父节点的子节点之间建立；把两个不同父节点下的节点配上同一个 key 是没有意义的，协调阶段根本不会跨父节点查找，这与第 38 章"同层比较"的假设一致。
key 只在同一父节点的子节点之间作为身份标识；跨层级、跨两个列表不需要互相唯一。它的职责是"让 React 认人"，不是"给全局对象编号"。

43.4 index 作 key 的三类反例

把 map 的下标 index 直接当 key，等于让"位置"充当身份。列表只做尾部追加、内容顺序永远不变时碰巧不出问题；一旦发生头部插入、删除中间项、排序过滤，位置与身份脱节，错位就出现了。

反例一：头部插入新项

// ✗ index 作 key：新项插到头部，旧项全部后移一位
function NewsList({ items, onAdd }) {
  return (
    <div>
      <button onClick={onAdd}>在头部插入一条</button>
      {items.map((item, index) => (
        <NewsRow key={index} title={item.title} />
      ))}
    </div>
  );
}

插入后，旧第 1 项配到第 2 位、旧第 2 项配到第 3 位……每个 NewsRow 内部若持有展开状态、输入内容等 state，都会被"挪"到错误的标题上。

易错点新手常以为"key 只是为了让 React 少做几次 DOM 操作"。性能收益只是副产品：真正的后果是state、输入内容、展开状态等 Fiber 私有数据被配错到相邻项上，表现为界面与数据"看起来串了"，这类 bug 往往难以从页面现象直接定位。

反例二：删除中间项

// ✗ 删除中间项后，后面的节点全部前移，state 跟着错位
function EditableList({ items, onRemove }) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={index}>
          <EditableRow initial={item.note} />
          <button onClick={() => onRemove(item.id)}>删除</button>
        </li>
      ))}
    </ul>
  );
}

图 43-2 删除中间项后 index 前移，组件内部状态错配到相邻项

反例三：排序、过滤后顺序变化

// ✗ 按价格排序后顺序变化，index 身份全部失效
function ProductList({ products, sortKey }) {
  const sorted = [...products].sort((a, b) => a[sortKey] - b[sortKey]);
  return (
    <ul>
      {sorted.map((p, index) => (
        <ProductCard key={index} product={p} />
      ))}
    </ul>
  );
}
场景index 作 key 的表现稳定 id 作 key 的表现
尾部追加位置不变，通常不出问题（但仍不推荐）只新建新节点，其余复用
头部插入旧节点整体后移，state / 输入内容错位新节点插入，旧节点身份不变
删除中间项后续节点前移，内部状态错配到相邻项仅删除目标节点，其余 state 跟随身份保留
排序 / 过滤位置关系全变，大量节点被错误更新甚至重建节点按身份移动位置，DOM 与 state 跟随节点

43.5 节点复用时 DOM 与 state 的归属

配对成功后，复用的是同一个 Fiber 节点，也就是同一个 DOM 节点与同一个组件实例：组件内部的 useState、useRef、展开状态、输入框内容都挂在这个 Fiber 上，跟着身份走，而不是跟着屏幕位置走。配对失败才会销毁旧节点、新建节点，旧 state 随之消失。

判断"组件状态会不会重置"，只要看身份是否匹配：key 相同、类型相同 → 复用同一 Fiber，state 保留；key 或类型变化 → 旧 Fiber 销毁、新 Fiber 挂载，state 重新初始化。屏幕上的位置变化本身不会导致 state 丢失。
操作DOM 节点组件内部 state
身份匹配、仅 props 更新复用同一 DOM，更新变化的属性与文本保留，不重置
节点移动位置（排序）同一 DOM 被移动到新位置保留，不重置
身份不匹配（key 变 / 类型变）旧 DOM 销毁，新建 DOM旧 state 全部丢弃，组件重新挂载
易错点想"换一批全新的组件状态"时，正确做法是给组件换一个新的稳定 key（如 <Panel key={userId} />），让 React 判定身份变化并重建；这与第 10 章"用 key 重置子组件状态"的建议是同一条原理。

43.6 选 key 的规则与常见误解

规则 / 误解正确做法错误理解
来源数据自带的稳定唯一标识：数据库 id、唯一编码、业务编号用数组下标、用随机数、用时间戳当 key
唯一性范围只要求在同级兄弟节点之间唯一误以为要在整棵树、整个应用全局唯一
稳定性同一条数据在多次渲染间 key 保持不变每次渲染生成新随机值，等于强制全部重建
类型字符串或数字均可，保持一致即可混用对象、函数等非基本类型作为 key
无稳定 id 时为数据生成一次持久化的 id（如新增时分配），而不是用 index 顶替把"暂时没有 id"当成可以长期使用 index 的理由
选 key 的全部要求可以压缩成一句话：用同一条数据在多次渲染间稳定不变、同级内唯一的标识；index、随机数、时间戳都不满足"稳定"这一条。
// 无后端 id 的本地列表：新增时一次性生成稳定 id，之后不再变化
function useLocalTodos() {
  const [todos, setTodos] = useState(() => [
    { id: crypto.randomUUID(), text: '初始事项' },
  ]);

  function addTodo(text) {
    setTodos((prev) => [
      { id: crypto.randomUUID(), text },   // id 在创建时确定，之后稳定
      ...prev,
    ]);
  }

  return { todos, addTodo };
}
边界提醒key 不参与组件 props 传递：组件内部读不到 props.key。需要把标识传给组件时，另传一个普通属性（如 id={todo.id}）。

本章讲的是协调阶段的配对规则；组件 props 不变时 React 如何跳过整棵子树（memo），属于第六篇性能优化主题，见第 48 章。

✓ 本章小结

要点一句话
key 本质同级子节点的身份标识，用于配对旧 Fiber 与新元素
无 key 规则按位置顺序配对，顺序一变就错位
配对结果匹配则复用 DOM 与 state，不匹配则销毁重建
index 风险头部插入、删除中间项、排序过滤时位置与身份脱节，造成 state 错位
归属规则DOM 与 state 跟随身份（Fiber），不跟随屏幕位置
选 key 规则用稳定唯一 id，仅同级唯一；不用 index、随机值、对象；key 不进 props
