◆本章目标

  • 分清 render 阶段（协调）与 commit 阶段（提交）的职责、能否中断、是否触碰真实 DOM；

42.1 两阶段总览：协调与提交

React 处理一次更新分两大阶段：render 阶段（Reconcile，协调）在内存里遍历 Fiber 树、比较新旧描述、决定每个节点怎么处理；commit 阶段把收集好的副作用一次性应用到真实 DOM，并运行绑定在 DOM 上的钩子。

图 42-1 一次更新的完整流水线：协调产出副作用列表，commit 分三小段落地

对照项render 阶段（协调）commit 阶段（提交）
工作内容调用组件函数、比较新旧树、决定复用或新建、打副作用标记按列表修改真实 DOM、绑定/解绑 ref、执行布局阶段钩子
是否触碰真实 DOM不触碰，全部在内存 Fiber 树上进行直接读写真实 DOM 节点
能否中断可以暂停、恢复、丢弃（第 39 章）不可中断，必须连续执行完
纯净性要求组件渲染必须纯净（第 41 章）本阶段就是副作用执行阶段，允许操作 DOM
对应概念名beginWork / completeWorkcommit 三个小段（42.4 节）
记住这条分界线：render 阶段只在内存里打草稿、可以重来；commit 阶段才动真实 DOM、必须走完。后续所有可中断、可丢弃的能力都建立在这条分界线之上。

42.2 beginWork：复用、新建还是跳过

协调阶段到达每个 Fiber 节点时，beginWork 先判断旧 Fiber 与新元素描述的关系，得出三种结果之一：

结果判断条件（概念层）后续动作
复用已有 Fiber类型相同、key 相同，且本次 props 与 state 仍需更新在旧 Fiber 基础上更新待处理属性，继续协调其子节点
跳过本节点类型相同、key 相同，且 props、state 都未变化（如被 memo 包裹后比较通过，第 48 章）整棵子树沿用旧结果，不再向下遍历
新建 Fiber旧树没有对应节点，或类型 / key 不匹配创建新 Fiber，记录"插入"类副作用，再协调其子节点
 
// 概念化：beginWork 的判断顺序（教学示意，非源码）
function beginWork(oldFiber, newElement) {
  if (!oldFiber) return createFiber(newElement);          // 新建
  if (oldFiber.type !== newElement.type) {
    return createFiber(newElement);                        // 类型不同：重建
  }
  if (!propsChanged(oldFiber.memoizedProps, newElement.props)) {
    return bailOut(oldFiber);                             // 跳过整棵子树
  }
  return updateFiber(oldFiber, newElement.props);         // 复用并更新
}
跳过子树的判断条件在普通组件上比较简单；被 React.memo 包裹后会额外比较 props 引用，相关优化边界见第 48 章。本章只需记住"复用 / 跳过 / 新建"三种结果。
边界提醒下文出现的 Placement、Update 等标记名用于理解调试工具与源码资料，业务代码不会直接设置这些标记；不要在组件里手写"给节点打 Placement 标记"之类的逻辑。

42.3 completeWork：收集副作用标记

子节点协调完成后回到当前节点的 completeWork：此时新 Fiber 的结构已经确定，React 给节点打上本次需要提交的副作用标记，并把需要提交的节点汇总成一条链表式的提交列表。下面列出常见标记的概念含义，便于阅读 React 调试工具与源码资料时对照。

  • Placement：该节点需要插入到父节点中（新建节点，或移动到新位置）。
  • Update：已有节点需要更新属性、事件监听器或文本内容。
  • Deletion：旧节点需要从父节点移除，对应子树卸载与清理。
  • Ref：需要在提交阶段绑定新 ref 或解绑旧 ref。
  • Layout 类标记：该节点上存在需要在布局阶段执行的钩子（如 useLayoutEffect）。
// 概念化：completeWork 把带标记的节点挂到提交列表上
function completeWork(fiber) {
  if (fiber.effectTag === 'Placement') {
    commitQueue.push({ op: 'insert', fiber });
  } else if (fiber.effectTag === 'Update') {
    commitQueue.push({ op: 'update', fiber });
  } else if (fiber.effectTag === 'Deletion') {
    commitQueue.push({ op: 'delete', fiber });
  }
  // 继续回溯到父节点，把本节点的提交记录并入父节点列表
}
render 阶段只记录"要做什么"，不做；所有真实 DOM 变更都排队等待 commit 阶段统一执行。这样整棵树协调完后，React 才知道本次更新的完整变更集。

42.4 commit 阶段的三个小段

render 全部完成、副作用列表就绪后，commit 开始。它按固定顺序分三个小段执行，顺序不能颠倒：

图 42-2 commit 三小段顺序：准备 → 改 DOM → 布局钩子；之后才是绘制与 useEffect

小段主要工作对应开发者 API / 时机
变更前准备遍历提交列表收集节点；卸载组件解绑旧 ref；清理上一次布局钩子旧组件卸载时的清理逻辑在此之前完成
DOM 变更执行插入、删除、属性与文本更新，把内存中的新结构落到真实 DOM开发者通常不直接操作，由 React 完成
布局阶段钩子绑定新 ref；运行 useLayoutEffect；类组件的布局生命周期方法useLayoutEffect 在绘制前同步执行（第 12 章）
 
function Panel({ title }) {
  const ref = useRef(null);

  // useLayoutEffect 在 commit 第③小段同步执行，浏览器绘制之前
  useLayoutEffect(() => {
    const el = ref.current;
    // 此时 DOM 已更新完成，可以同步测量并调整样式，避免闪烁
    el.scrollTop = 0;
  }, [title]);

  // useEffect 在浏览器绘制之后异步执行
  useEffect(() => {
    console.log('画面已经画出来了');
  }, [title]);

  return <div ref={ref}>{title}</div>;
}
易错点useLayoutEffect 与 useEffect 的区别不只是"执行先后"：前者在 commit 第③小段、浏览器绘制之前同步执行，适合同步测量布局并调整样式；后者在绘制之后异步执行，适合不阻塞画面的副作用。混用容易造成可见的布局抖动（第 12 章有完整对照）。

42.5 为什么 commit 不可中断

关键边界render 阶段可以中断，是因为草稿只在内存里；commit 一旦开始改真实 DOM，界面就处于"旧结构与新结构混杂"的中间态。此时暂停让出主线程，用户看到的就是半截画面、不可用的控件，所以 commit 必须一口气执行完，不接受调度打断。
对照项render 阶段中断commit 阶段中断
界面状态真实 DOM 仍是上一版完整界面真实 DOM 处于新旧混杂的中间态
后果无感知，稍后继续或丢弃草稿即可可能出现闪烁、控件失效、事件绑定不一致
调度策略可被高优先级任务打断、丢弃重做排队等待当前任务完成，中途不可插队打断
推论因此优化方向是缩短 render 阶段耗时（组件拆分、memo、列表优化，第六篇主题），而不是指望 commit 也能被切片；commit 本身应当短小确定。

42.6 一次事件中的批量更新

在 React 18 及之后，事件回调、超时回调、Promise 回调等上下文里触发的多次 setState 会被 批处理（batching）合并：多次更新先登记到队列，等回调结束后只触发一次协调与提交，而不是每调一次就渲染一轮。

批处理改变的是渲染轮次，而不是状态取值：同一回调里多次 setState 先排队合并，组件函数只被重新调用一次；本次渲染快照仍然是回调执行前读到的旧值，需要基于前一次排队值计算时使用函数式更新。
function BatchDemo() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);

  function handleClick() {
    setA(1);
    setB(2);
    // 两次更新在同一批次内合并：只发生一次 render 与一次 commit
    console.log(a, b);   // 仍是本次渲染快照（0, 0）
  }

  return <button onClick={handleClick}>同时更新两个状态</button>;
}
对照项不批处理（假设逐次渲染）React 批处理（实际行为）
渲染轮次两次 setState 各触发一轮 render 与 commit合并为一轮 render 与一轮 commit
DOM 变更次数中间产生一次短暂的中间态更新直接提交最终状态，中间态不暴露给浏览器
函数式更新同一批次内多次更新同一状态时，使用 setN(prev => prev + 1) 保证基于最新排队值计算（第 7 章）
批处理的触发范围在 React 18 中已扩展到多数回调上下文；如果在原生事件监听、手动 setTimeout 等特殊场景遇到逐次渲染行为，优先确认上下文，而不是把它理解成"渲染机制出错"。
