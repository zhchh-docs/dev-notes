第 39 章 Fiber 架构：可中断的渲染

教科书 第 39 章 / 共 64 章 · 预计 55 分钟 · 从旧栈走向 Fiber

第 38 章末尾留下的问题是"递归渲染不可中断"。本章回答 Fiber 架构如何解决：把整棵界面树拆成一个个可独立处理的 Fiber 节点，用链表代替函数调用栈，在内存里同时维护两棵树（current 与 workInProgress），让渲染可以暂停、恢复，甚至丢弃重做。

◆本章目标

  • 说清旧栈协调器"递归一旦开始就停不下来"的结构性原因；
  • 理解 Fiber 节点是 React 内部的最小工作单元，以及 child / sibling / return 三个指针构成的链表关系；
  • 掌握双缓冲概念：界面展示用 current 树，正在渲染用 workInProgress 树，提交后两棵树指针交换；
  • 能描述可中断渲染的三种状态：暂停、恢复、丢弃重做，以及它们对主线程意味着什么；

39.1 旧栈为什么撑不住长任务

浏览器主线程在同一时刻只能做一件事：执行 JavaScript、处理样式布局、绘制画面、响应输入，彼此排队。旧栈协调器的递归遍历是一段不可分割的长任务，树越大，主线程被占住的时间越长。

旧栈协调器的执行方式与函数递归一致：处理根节点 → 处理第一个子节点 → 递归进入孙节点 → 回溯到兄弟节点……整棵树的遍历状态保存在 JavaScript 调用栈里。调用栈一旦压入，就必须一层层返回才能退出，中途没有"先停一下去响应用户输入"的位置。

对照项旧栈协调器（递归）Fiber 架构（链表）
遍历状态保存位置JavaScript 函数调用栈每个 Fiber 节点自身保存遍历指针与进度
能否中途暂停不能；递归返回前栈帧无法释放能；记录当前节点即可稍后从原地继续
能否丢弃重做中途放弃后状态难以恢复放弃 workInProgress 树，重新从根开始即可
对主线程的影响整段渲染期间阻塞输入与动画每个工作单元结束后可检查是否该让出主线程
场景感知在大列表、复杂表单、嵌套层级深的页面上，旧栈表现为：点击按钮后界面"冻"几百毫秒，输入框打字断断续续，动画明显掉帧。这不是业务代码写得慢，而是结构上没有让出主线程的机会。

39.2 Fiber 节点：链表化的工作单元

Fiber 架构把"一个组件实例 / 一个 DOM 元素"对应的内部记录称为 Fiber 节点。它不再只是一棵父子树，而是同时挂着三个指针：child 指向第一个子节点，sibling 指向下一个兄弟节点，return 指回父节点。有了这三个指针，遍历过程可以在任意节点停下，也能顺着指针回到上一层。

可以把 Fiber 链表理解成把递归调用栈"摊平"成节点上的指针：调用栈里"我是谁、我从哪来、下一个轮到谁"，分别落到 return、child、sibling 三个字段上，遍历进度因此不再受函数栈帧生命周期的约束。
// Fiber 节点概念字段（教学示意，非 React 源码结构）
const fiber = {
  type: 'section',          // 元素标签或组件类型
  key: 'list',              // 同级身份标识（第 43 章）
  stateNode: null,          // 对应的真实 DOM 节点或组件实例
  child: null,              // 第一个子 Fiber
  sibling: null,            // 下一个兄弟 Fiber
  return: null,             // 父 Fiber
  pendingProps: null,       // 本次渲染待处理的 props
  memoizedProps: null,      // 上一次提交时的 props
  memoizedState: null,      // 上一次提交时的 state 与 Hooks 队列
  effectTag: null,          // 本节点需要执行的副作用标记（第 42 章）
};

图 39-1 Fiber 的 child / sibling / return 三指针构成可暂停、可回退的链表

Fiber 的核心价值不是"换了一种数据结构"本身，而是把遍历进度外置到节点上，从而获得暂停与恢复的能力。

业务代码里你不会直接接触 Fiber 对象；它是 React 在渲染期间内部创建和维护的记录。本章按"是什么、为什么、行为表现"理解即可，不需要记忆内部字段名，更不要在组件里访问它们。

39.3 双缓冲：current 树与 workInProgress 树

界面上正在展示的内容对应一棵已经提交完成的 Fiber 树，称为 current 树。状态更新到来后，React 不会直接改动 current 树，而是在内存里另外构建一棵新树，称为 workInProgress 树（进行中的工作树）。两棵树通过对应 Fiber 上的指针互相引用，提交时再把 current 指针切换到新树。

图 39-2 双缓冲：current 树稳定展示，workInProgress 树允许随时重来

对照项current 树workInProgress 树
角色界面当前真实状态的镜像本次更新正在计算中的新镜像
能否被修改展示期间保持稳定，不会被中途改动可继续补全、也可整棵丢弃重建
完成后动作提交完成后被新树替换为新的 current提交成功后成为新的 current 树
对应的业务感受用户看到的始终是完整、旧的或新的一版界面用户看不到构建中的半成品
不要误解双缓冲不是"预渲染两页界面"，也不是为了视觉上的渐变过渡；它的真正目的是给可中断渲染提供一个可以安全扔掉的草稿本。草稿写坏了重写，桌面上的正式版本一直完好。

39.4 可中断：暂停、恢复、丢弃

基于链表进度与双缓冲，Fiber 渲染具备三种状态切换能力。理解它们，就能解释后续所有 Concurrent 行为（第 45、46 章）。

状态含义触发条件与结果
暂停当前工作单元处理完后，暂时不再继续向下遍历，把主线程交还给浏览器时间片用完，或发现有更高优先级任务等待；暂停位置记在 Fiber 指针里
恢复浏览器空闲后，从暂停的 Fiber 节点继续构建 workInProgress 树被让出的任务再次获得执行机会；已完成的节点不重复计算
丢弃本次渲染的 workInProgress 树被放弃，已做的协调工作作废出现更高优先级的新更新，旧草稿不再需要；重新从根开始构建新草稿
 
// 概念化的工作循环：每处理一个 Fiber 节点就检查一次是否该让出主线程
// 仅用于理解"暂停—恢复"的结构，不是 React 内部实现
function workLoop() {
  while (nextUnitOfWork !== null && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork !== null) {
    // 时间片用完：暂停，等待下一次调度再从 nextUnitOfWork 继续
    scheduleNextUnitOfWork(nextUnitOfWork);
  }
}
为什么 render 阶段可以丢弃、而提交阶段不行？因为草稿只存在于内存，不触碰真实 DOM；一旦开始改真实 DOM，界面就处于新旧混杂的中间态，必须一口气改完。这条分界线在第 42 章重点展开。

三种状态切换并不需要开发者显式调用：调度器在每个工作单元结束后检查时间片是否用完、有没有更高优先级任务等待，再决定继续、暂停还是丢弃。业务代码只通过 useTransition 等 API 表达"这次更新不紧急"（第 45 章），其余暂停、恢复与丢弃动作都由框架在内部自动完成。

还要注意"暂停"不是"后台并行执行"：Fiber 渲染仍然运行在浏览器主线程上，只是把长任务切成小段穿插进行，浏览器在小段之间获得机会去响应用户输入、绘制画面；它不会另开线程同时渲染两棵树。

39.5 render 阶段：beginWork 与 completeWork

单个 Fiber 节点的处理分两个方向。先从上往下（自顶向下）进入节点，这个动作在 React 内部称为 beginWork；处理完子节点后再从下往上回溯收尾，称为 completeWork。这两个名字是 React 内部使用的术语，本章先建立概念印象。

易错点beginWork 与 completeWork 是 React 内部术语，不是供业务代码调用的 API：组件函数里既不会出现这两个名字，也不需要手动触发。阅读源码时能说出"自上而下进入、自下而上收尾"即可，不要在组件代码里臆造同名函数或在文档里把它们写成公开接口。
动作方向与职责典型工作（概念层）
beginWork自顶向下进入节点；判断是复用、新建还是跳过该 Fiber读取最新 props / state，调用函数组件产出新元素树，比对类型与 key，决定子节点如何协调
completeWork自底向上回溯；给 Fiber 节点标记本次需要提交的副作用为 DOM 元素准备属性，收集插入、更新、删除等标记，把副作用汇总到提交队列
 
// 业务视角：Fiber 的创建、beginWork、completeWork 全部由 React 自动完成
// 开发者写的只是组件函数本身
function ProfileCard({ user }) {
  // 本次渲染时被调用，返回新的元素树供 beginWork 协调
  return (
    <article className="profile">
      <img src={user.avatar} alt={user.name} />
      <h3>{user.name}</h3>
      <p>{user.bio}</p>
    </article>
  );
}
整条 render 阶段都是纯计算：读状态、比新旧、打标记，不碰真实 DOM；正因如此它才可以被打断、被重做。真实 DOM 变更只发生在随后的 commit 阶段。

39.6 与其他框架调度思路对照

不同框架对"渲染不卡主线程"的解法方向相近，但程度与默认行为不同，对照着看更容易理解 React 的取舍。

对照项React Fiber其他框架常见思路
响应式追踪粒度由 React 重新渲染组件，再经 Fiber 链表协调Vue 等基于响应式系统收集依赖，精确到组件或细粒度效果
时间切片能力render 阶段可暂停、恢复、丢弃，配合优先级调度部分框架依赖微任务批量刷新，不做任务级时间切片
开发者可见控制通过 useTransition 等 API 声明非紧急更新（第 45 章）多数场景自动批量刷新，暴露给开发者的调度开关较少
设计动机兼顾组件模型的灵活性与主线程可响应性在各自响应式模型内追求更新合并与触发效率
边界提醒对照只是帮助建立直觉：不要把 Vue 的响应式收集与 React 的 Fiber 协调当成同一件事的两种说法。前者解决"谁该更新"，后者解决"更新过程如何被切片与调度"，二者在 React 体系里前后衔接。

本章讲的是 Fiber 的结构与可中断能力；"哪些更新先渲染、哪些可以等"由下一章的调度与优先级决定。
