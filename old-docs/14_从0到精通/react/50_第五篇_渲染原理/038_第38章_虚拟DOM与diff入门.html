38.1 为什么不能每次重绘整棵 DOM

浏览器里最贵的操作不是 JavaScript 计算，而是 DOM 操作：每一次 appendChild、setAttribute、文本改写都可能触发浏览器的样式计算、布局（reflow）与绘制（repaint），而且真实 DOM 节点是浏览器内部的重型对象，属性远多于开发者日常用到的部分。

如果状态一变就把整个界面用 innerHTML 重写一遍，哪怕界面只有一个数字变化，浏览器也要销毁旧节点、创建新节点、重新计算样式与布局，交互密集时主线程会被反复占用，表现为输入卡顿、动画掉帧。早期框架与原生 jQuery 时代的很多性能问题，都来自"命令式地逐节点手动改 DOM"：开发者既要保证改对，又要保证改得少，负担全压在业务代码上。

// 反例：命令式手动操作，节点一多就难以维护且容易漏改
function renderCount(n) {
  const el = document.getElementById('count');
  el.textContent = n;
  // 还要手动更新颜色、类名、相邻提示文字……每加一个状态就要改这里
  el.style.color = n >= 10 ? '#b45309' : '#1f2e1f';
}
对照项直接操作真实 DOM虚拟 DOM 方案
变更方式开发者手动选择节点、手动改属性框架根据新旧描述树自动算出最小变更集
比较成本无比较，直接改；但容易改多、改漏先在内存里比较两棵轻量对象树，再批量改 DOM
DOM 操作次数随代码写法波动，可能频繁触发布局变更被收集后批量提交，减少中间态布局抖动
开发心智命令式：关心"怎么一步步改"声明式：关心"状态对应什么界面"
注意：虚拟 DOM 并不比"手工优化到极致的直接 DOM 操作"绝对更快；它的价值在于让声明式开发成为可能，同时由框架兜底保证变更集尽量小。Vue 的虚拟 DOM 与 React 在这一点上思路一致，可对照《Vue 从 0 到精通》渲染篇阅读。

38.2 虚拟 DOM：一棵描述界面的对象树

所谓虚拟 DOM（Virtual DOM，简称 VDOM），本质就是普通 JavaScript 对象：用 type 描述节点类型，用 props 描述属性与事件，用 children 描述子节点，整棵树递归对应界面结构。组件函数被调用后返回的正是这样一棵树的描述，而不是浏览器里的真实节点。

// JSX 源码（第 3 章已讲过编译产物）
function Hello({ name }) {
  return (
    <section className="card">
      <h2>你好，{name}</h2>
      <p>欢迎来到 React 渲染原理篇</p>
    </section>
  );
}
// 编译后等价的对象描述（示意结构，字段名仅为讲解）
const vnode = {
  type: 'section',
  props: { className: 'card' },
  children: [
    { type: 'h2', props: {}, children: ['你好，', 'Alice'] },
    { type: 'p', props: {}, children: ['欢迎来到 React 渲染原理篇'] },
  ],
};

图 38-1 虚拟 DOM 在内存中完成比较，最后只把最小变更集交给真实 DOM

虚拟 DOM 不是"不渲染 DOM"，而是先用轻量对象树描述界面、在内存里完成比较，再把必要的变更同步到真实 DOM。

38.3 diff 的三个前提假设

两棵任意树之间做"最小移动距离"的比较，复杂度高到工程上不可接受。React 的 diff 算法在准确性与性能之间做了明确取舍，依赖三个经验假设：绝大多数界面变更都是局部的、层级不变的、组件类型稳定的。

假设含义推论 / 影响
① 同层比较只比较同一父节点下、同一层级的两个节点，不跨层移动子树若节点层级发生变化（如从 <div> 移到 <aside> 内），React 视为旧节点删除、新节点创建
② 类型不同直接重建旧节点类型与新节点类型不同（元素标签不同，或组件类型不同），直接销毁旧子树、挂载新子树类型相同才进入属性与子节点的逐项复用比较
③ 同层子节点用 key 标识身份一组同级子节点靠 key 配对旧节点与新节点，而不是按下标顺序硬配key 的规则在第 43 章专门展开；本章先建立"有身份才谈复用"的概念
易错点假设 ① 意味着：把一段 JSX 从外层 <div> 挪到内层另一个 <div>，即便内容完全相同，React 也会走"删除 + 新建"，组件内部状态一并丢失。需要保留状态时，应当保持层级位置不变，而不是指望 diff 帮你"搬运"。
为什么不做跨层比较两棵完整树的最优匹配在算法上代价很高，而真实业务里跨层搬移子树极少出现；React 用"放弃跨层复用"换取 O(n) 级别的同层比较速度，这是一个被实践验证过的工程取舍。

38.4 同层比较与组件类型判断

进入同层比较后，React 先看类型，再看 key，最后逐项比对属性与子节点。下表把最常见的几种配对结果列清楚：

比较顺序是固定的三道闸门：先比类型 → 再比 key → 最后逐项比对属性与子节点；前两道闸门任何一道不通过，就直接走"销毁旧节点、创建新节点"的分支，不会回头补救属性差异。
新旧节点关系React 动作状态与 DOM 表现
元素标签相同、key 相同复用同一 DOM 节点保留节点，只更新发生变化的属性、事件监听器与子节点
组件类型相同、key 相同复用同一组件实例保留组件 state 与内部 DOM，重新执行渲染函数，按新 props 调整输出
元素标签不同 / 组件类型不同销毁旧子树，挂载新子树旧组件卸载（执行 cleanup 等），新组件挂载；旧 state 不复用
标签相同但 key 不同判定为两个不同身份旧节点删除、新节点创建，不复用 DOM 与状态
 
// 类型不同 → 整棵子树重建（假设条件切换了外层标签）
{showCard
  ? <div className="card"><Panel /></div>
  : <aside className="side"><Panel /></aside>}

// 类型相同 → 复用 Panel 实例，state 保留
{showCard
  ? <div className="card"><Panel title="详情" /></div>
  : <div className="card"><Panel title="预览" /></div>}

"类型相同才可能复用，类型不同一律重建"是协调阶段的第一道闸门；key 是第二道闸门，决定同级一组节点里谁和谁配对。两道闸门都通过，才谈得上属性级的增量更新。

38.5 手写一个迷你 diff（示意）

下面用一小段 JavaScript 演示同层比较的核心思路：类型不同记为替换；类型相同则比对属性差异；子节点按 key 配对后递归比较。代码是教学简化版，不代表 React 内部真实实现，但足以把"比较两棵对象树、产出变更补丁"的过程讲清楚。

// 迷你 diff 示意：返回需要提交到 DOM 的变更描述
function diff(oldVnode, newVnode) {
  // ① 类型不同：直接替换整棵子树
  if (oldVnode.type !== newVnode.type) {
    return { op: 'replace', old: oldVnode, next: newVnode };
  }

  // ② 类型相同：比对属性差异
  const propPatches = {};
  const keys = new Set([
    ...Object.keys(oldVnode.props || {}),
    ...Object.keys(newVnode.props || {}),
  ]);
  keys.forEach((k) => {
    if (oldVnode.props?.[k] !== newVnode.props?.[k]) {
      propPatches[k] = newVnode.props?.[k];
    }
  });

  // ③ 子节点按 key 配对（简化：只处理同类型子节点数组）
  const oldMap = new Map((oldVnode.children || []).map((c) => [c.key, c]));
  const childPatches = (newVnode.children || []).map((child) => {
    const oldChild = oldMap.get(child.key);
    if (!oldChild) return { op: 'create', node: child };
    return diff(oldChild, child);
  });

  return { op: 'update', props: propPatches, children: childPatches };
}
// 触发一次重渲染的最小业务场景
function App() {
  const [count, setCount] = useState(0);
  return (
    <main>
      <h1>计数：{count}</h1>
      <button onClick={() => setCount((n) => n + 1)}>加一</button>
    </main>
  );
}
真实 React 的协调发生在 Fiber 节点上（第 39、42 章展开），子节点配对、删除、移动的规则比这段示意复杂得多；但"先比描述树、再产出补丁、最后提交 DOM"的整体方向与上面完全一致。
不要据此猜内部实现示意代码中的 oldVnode.props、key 字段名只是讲解命名。阅读本章时请记住"是什么、为什么、行为表现"，不要把示意结构当成 React 源码 API 去记忆或背诵。

38.6 旧栈的瓶颈：不可中断

在 Fiber 架构出现之前，React 用的是基于递归的协调器（旧栈协调器）：状态更新触发后，从根节点开始递归遍历整棵虚拟 DOM 树，组件函数一层层执行、子节点一层层比较，直到整棵树走完才回到主线程准备提交。这条递归链路一旦启动就无法中途暂停。

易错点旧栈的卡顿不能简单归因为"diff 算得慢"：真正的结构性问题是整棵树必须一口气走完才允许回到主线程，节点越多单次任务越长。排查长任务时要区分"比较算法耗时"与"任务不可分割"，下一章 Fiber 正是从"把遍历拆成可中断单元"入手解决后者。

图 38-2 旧栈递归必须一口气走完；Fiber 把渲染切分为可中断的工作单元

对照项旧栈协调器Fiber 架构（39 章起）
遍历方式函数递归调用栈可遍历、可回退的链表结构
中断能力一旦开始不能暂停工作间隙可让出主线程，稍后恢复
优先级感知所有更新一视同仁可按任务优先级安排执行顺序（第 40 章）
典型症状大列表渲染时输入卡顿、动画掉帧紧急交互保持响应，后台渲染可被打断
本章的落脚点：虚拟 DOM 与 diff 解决了"改什么"的问题；而怎么在不卡住浏览器的前提下把树走完，就是 Fiber 架构要解决的问题。

✓ 本章小结

要点一句话
虚拟 DOM 本质用 JavaScript 对象树描述界面，在内存里比较后再提交真实 DOM
方案价值让声明式开发成为可能，框架兜底产出尽量小的变更集
三个假设同层比较、类型不同重建、同级子节点靠 key 标识身份
复用闸门类型相同才可能复用，key 相同才确定配对，之后才做属性级增量更新
diff 流程旧树 / 新树比较 → 变更补丁 → 批量同步到真实 DOM
旧栈局限递归不可中断，长任务阻塞主线程，引出 Fiber 架构
