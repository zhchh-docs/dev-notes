◆本章目标

  • 理解为什么交互更新与后台更新不能使用同一种紧迫程度；
  • 说清 Scheduler 的角色：合作式调度、按时间片把主线程交还给浏览器；

40.1 更新不是平等的：为什么需要优先级

用户敲键盘、点击按钮这类更新必须立刻反映到界面，晚几十毫秒就会觉得"卡"；而搜索结果过滤、大列表重排、图表刷新这类更新晚一两百毫秒通常感知不到。把两类更新混在一个队列里按先来后到处理，紧急更新就会被后台任务堵在后面。

调度器的职责正是给每一次更新标注紧迫程度，并在主线程上安排执行顺序：先处理紧急更新，让界面保持响应；非紧急更新在空闲间隙推进，必要时让出主线程。这与操作系统里进程调度"前台任务优先、后台任务分时"的思路相通。

任务类型典型场景紧迫程度与期望表现
交互紧急更新输入框受控值、按钮点击切换开关、滚动位置相关状态必须立即渲染，界面不能有可感知延迟
过渡更新搜索词变化后过滤长列表、选项切换后刷新详情区可以延后一小段时间；旧界面保留到新界面准备好
后台 / 空闲更新离线统计、非可视区域内容预计算、低优先级刷新主线程空闲时再做，不影响交互响应
优先级调度的目标不是"让所有更新都更快"，而是让用户正在感知的那部分更新不被其他更新阻塞。

40.2 Scheduler：合作式调度与时间片

浏览器主线程不支持抢占式中断一段正在执行的 JavaScript：一旦函数开始跑，只能等它返回。React 内部的调度器（Scheduler）采用合作式调度思路：React 自己在每个工作单元结束后检查时间片是否用完，用完就主动把主线程交还给浏览器，让浏览器先处理输入、绘制与动画，下一轮再继续剩余单元。

图 40-1 合作式时间片：React 在单元边界主动让出主线程，浏览器穿插处理输入与绘制

// 概念化示意：Scheduler 在每个工作单元后检查是否该让出主线程
// 仅用于理解调度思路，不是 React 内部源码
function shouldYieldToHost(deadline) {
  // 本轮时间片剩余时间耗尽，或有更高优先级任务等待时返回 true
  return deadline.timeRemaining() <= 0 || hasHigherPriorityTask();
}

function schedulerLoop(deadline) {
  while (currentFiber && !shouldYieldToHost(deadline)) {
    currentFiber = performUnitOfWork(currentFiber);
  }
  if (currentFiber) {
    // 未完成：注册下一轮回调，稍后继续
    requestNextCallback(schedulerLoop);
  }
}
不要背内部参数具体时间片毫秒数、任务队列的内部数据结构会随 React 版本演进；面试与学习中讲到原理即可，不要把示意代码里的函数名当成公开 API。

这里的"合作"是相对于操作系统的"抢占"而言：浏览器不能在函数执行到一半时强行接管主线程，只能等 JavaScript 返回；React 因此选择在每个工作单元边界主动检查并交还控制权，配合浏览器的空闲回调机制完成分片。理解这一点就能明白：可中断性依赖 Fiber 先把渲染拆成独立单元（第 39 章），没有单元边界，合作式检查就无处下手。

40.3 优先级分层与 lane 概念

React 把更新任务划分为若干优先级档位。开发者日常能感知到的主要是两档：普通（同步紧急）更新与 过渡（Transition）更新；此外还有内部使用的空闲档位用于后台工作。React 内部用 lane（车道）这一概念给任务分组：每个 lane 对应一组具有相似紧迫程度的更新，便于批量判断"当前有没有高优先级任务等待""哪些 lane 的任务已经过期需要提升"。

优先级档位不是 React 暴露给开发者的"分数参数"，而是由更新的触发方式决定：事件回调里的普通 setState 自动归入紧急档，被 startTransition 包裹的更新归入过渡档；开发者能做的是选择用哪种方式发起更新，而不是手动指定档位高低。

图 40-2 优先级由高到低分层；lane 把相近紧迫程度的更新归为一组

档位典型触发方式能否被更高优先级打断过期策略
同步紧急普通事件回调中的 setState、受控输入基本不被打断；渲染与提交连贯完成不允许长时间排队，需要立即响应
过渡 Transition用 startTransition 或 useTransition 包裹的更新可以被新的紧急更新打断并丢弃草稿等待过久会被提升，避免任务永远排不上
空闲后台React 内部工作；业务侧无直接对应 API随时让位给前两档长时间饥饿后由内部策略提升优先级

关于 lane：可以把它理解为"用一组编号给任务分组"的调度思想，类似把任务分到不同车道。本章只需理解分组与比较的原理，不需要记忆内部 lane 的具体命名与位值；它们属于 React 实现细节，且会随版本调整。

40.4 一次更新如何进入调度队列

以组件内一次普通 setState 为例，更新从产生到被调度的过程可以概括为四步：记录新状态 → 标注优先级档位 → 加入对应队列 → 通知调度器安排执行。组件函数此时并不会立刻重新执行。

function SearchBox() {
  const [keyword, setKeyword] = useState('');

  // 输入：普通事件回调中的更新 → 同步紧急档位
  function onInput(e) {
    setKeyword(e.target.value);   // 记录更新、标注紧急优先级、进入队列
  }

  return (
    <input
      value={keyword}
      onInput={onInput}
      placeholder="输入关键词"
    />
  );
}
import { useTransition } from 'react';

function FilterPanel() {
  const [keyword, setKeyword] = useState('');
  const [list, setList] = useState([]);
  const [isPending, startTransition] = useTransition();

  function onChange(e) {
    setKeyword(e.target.value);   // 紧急：输入框立刻响应
    startTransition(() => {       // 过渡：过滤大列表归入低一档队列
      setList(filterHeavyList(e.target.value));
    });
  }

  return <input value={keyword} onChange={onChange} />;
}
步骤做什么对应第 39 章的结构
记录更新把新状态挂到组件对应的 Fiber 上，排队等待处理写入 memoizedState 对应的更新队列
标注档位按触发方式确定属于紧急还是过渡档位更新带上对应的 lane 分组信息
进入队列调度器按优先级把待处理任务纳入本轮调度与 workInProgress 树的构建衔接
执行渲染时间片内推进 Fiber 遍历，完成后统一提交beginWork / completeWork → commit 阶段

还要注意：一次事件回调里可能发起多次 setState，它们会被归入同一轮调度，而不是每次都触发一轮独立渲染。React 先把更新收集到队列，再统一安排一次协调与提交，这就是"批处理"的基本形态，第 42 章会结合 commit 阶段再展开。

// 同一个事件回调里的多次更新会被批量归入本轮调度
function onSearchChange(e) {
  const value = e.target.value;
  setKeyword(value);                 // 紧急：输入框立刻响应
  setSuggestions(quickMatch(value));
  startTransition(() => {
    setList(filterHeavyList(value)); // 过渡：大列表延后渲染
  });
}

40.5 行为表现：插队、过期提升、后台让位

理解调度后，可以解释界面上三类常见的实际表现：

① 紧急更新插队

正在渲染过渡内容时，用户开始打字。输入属于紧急档位，可以中断当前过渡渲染（workInProgress 草稿丢弃，见第 39 章），先把输入状态渲染到屏幕；输入稳定后，过渡任务再重新构建新草稿。用户看到的是输入立刻响应，而不是先等长列表刷完。

② 过期提升，避免饥饿

过渡任务如果一直排在后面迟迟轮不到，会等待过久。React 的内部策略会把等待时间过长的低优先级任务提升到较高档位尽快执行，避免低优先级任务被新任务无限挤出队列。业务上感知到的现象是：延后的内容最终一定会出现，不会永久停在旧界面。

③ 后台让位

低档位任务在主线程忙碌时主动等待，只在空闲间隙推进；紧急事件一来立刻让位。这保证了后台计算不会与交互争抢主线程时间片。

从用户视角看，三种表现叠加起来就是：打字、点击始终跟手；被推迟的长列表不会把界面卡死；排在后面的任务也不会被新任务永远挤出队列。这些行为默认开启，开发者只在需要区分紧急与过渡时才显式使用 useTransition（第 45 章）。

表现调度机制用户可观察到的现象
插队高优先级任务可中断进行中的低优先级渲染输入框打字流畅，长列表刷新被推迟
过期提升等待过久的低优先级任务被临时提高档位延后内容不会永久"卡住"，最终会显示出来
后台让位低档位任务在主线程忙碌时主动排队等待后台计算期间滚动、点击仍保持响应
调度器保证的是响应性：紧急操作不被阻塞；它并不承诺"低优先级任务总被推迟"，过期提升兜底保证它们最终被执行。

40.6 常见误解与边界

误解 1优先级不是开发者可以自由指定的分数。普通事件里的 setState 默认走紧急档位；只有用 startTransition / useTransition 显式包裹的更新才归入过渡档位。不存在"把这个 state 调到最高优先级"之类的手动参数。
误解 2调度只优化 render 阶段。一旦进入 commit 阶段（真实 DOM 变更，第 42 章），任务不可中断；调度的可中断能力止步于提交之前。
误解 3"用了 Transition 就一定会快"是错的。优先级调度只是让紧急操作不被长渲染阻塞；如果组件本身计算量巨大、列表缺少优化，过渡渲染仍然耗时。组件级优化（memo、useMemo、虚拟化）是第六篇的主题。

本章的 startTransition 代码仅用于说明优先级归属；API 的完整签名、isPending 用法与实际场景对照在第 45 章系统讲解。

✓ 本章小结

要点一句话
为什么要调度交互更新必须立即响应，后台更新可以等待，混在一个队列会互相阻塞
Scheduler 思路合作式调度：在工作单元边界主动检查时间片，用完交还主线程
优先级分层同步紧急 > 过渡 Transition > 空闲后台
lane 概念按紧迫程度把任务分组，便于比较先后与批量过期提升
更新流程记录状态 → 标注档位 → 进入队列 → 时间片内渲染并提交
三种表现紧急插队、过期提升防饥饿、后台主动让位
边界优先级由触发方式决定；commit 阶段不可中断；调度不替代组件优化
