第 44 章 不可变更新：为什么必须

教科书 第 44 章 / 共 64 章 · 预计 50 分钟 · 引用相等的底层约束

"不要直接修改 state"是最早背下的规则，本章回答为什么必须如此：React 用引用相等（Object.is）判断状态与 props 是否变化，原地修改让引用保持不变，协调阶段会认为没变化而跳过更新。本章讲清比较规则、正确的不可变写法、嵌套对象处理与常见误区。

44.1 状态快照与引用相等

第 41 章讲过，每次渲染都是一份独立快照。React 在 Fiber 上保存的不是对象内容的"深拷贝"，而是当时的值引用：基本类型保存值本身，对象与数组保存内存引用。下一次渲染比较新旧状态时，先比较引用是否相同。

图 44-1 引用相等则跳过更新；生成新引用才会触发协调与提交

不可变更新的核心要求：改变状态时给出一个新的引用，让 React 通过引用比较识别出"这一版变了"。

44.2 Object.is：React 的比较规则

React 在判断 state、props 是否变化时使用 Object.is 做相等比较。它与严格相等 === 绝大多数情况一致，只有两处特例需要了解：NaN 与自身相等；-0 与 +0 不相等。

比较规则只有一个朴素的事实：基本类型按值比，对象与数组按引用比；React 不会递归比较对象内部字段。所以"内容看起来一样"并不等于 React 认为状态没变，关键在于你交出的引用是不是同一个。
// Object.is 与 === 的两处差别（其余行为一致）
Object.is(NaN, NaN);     // true   —— === 为 false
Object.is(-0, +0);       // false  —— === 为 true
Object.is(1, 1);         // true
Object.is('a', 'a');     // true
const objA = { n: 1 };
const objB = { n: 1 };
Object.is(objA, objB);   // false  —— 内容相同但引用不同
Object.is(objA, objA);   // true   —— 同一引用
比较场景Object.is 结果=== 结果
NaN === NaN相等（true）不相等（false）
-0 === +0不相等（false）相等（true）
两个内容相同的对象 / 数组都按引用比较：引用不同即不相等
基本类型值相同两者一致，均判定相等
日常开发几乎不会遇到 NaN、-0 引发的更新判断问题；需要记住的重点是对象与数组按引用比较，这也是 44.3 节问题的根源。

44.3 原地修改为什么让更新失效

对象与数组是引用类型：push、splice、直接给属性赋值等操作改的是内存中同一个对象，变量里保存的引用没有变。此时即使调用 setState 传入同一个对象，Object.is(旧引用, 新引用) 结果为相等，React 判定没有变化，协调阶段跳过该节点，界面不刷新。

// ✗ 反例一：原地改对象后再 setState，界面不更新
function Profile() {
  const [user, setUser] = useState({ name: '张三', age: 20 });

  function growUp() {
    user.age = user.age + 1;   // 原地修改同一对象，引用未变
    setUser(user);             // 传入同一引用，React 判定未变化
  }

  return (
    <div>
      <p>{user.name} · {user.age} 岁</p>
      <button onClick={growUp}>长一岁</button>
    </div>
  );
}
// ✗ 反例二：push / splice 原地改数组
function Cart() {
  const [items, setItems] = useState(['牛奶']);

  function add() {
    items.push('面包');        // 原数组被修改，引用未变
    setItems(items);
  }

  function removeFirst() {
    items.splice(0, 1);        // 同样是原地修改
    setItems(items);
  }

  return (
    <ul>
      {items.map((it, i) => <li key={i}>{it}</li>)}
      <button onClick={add}>加入面包</button>
      <button onClick={removeFirst}>移除第一项</button>
    </ul>
  );
}
注意原地修改有时"看起来生效"，往往是因为另一次正常更新触发了整棵子树重渲染，巧合读到了被改过的内容；这掩盖了引用比较的问题，在 memo 等依赖引用跳过更新的场景下会立刻暴露 bug（第 48 章）。

44.4 正确写法：对象与数组的不可变更新

标准做法是基于旧值复制一份新对象 / 新数组，只改动需要变化的部分，再把新引用交给 setState。

对象：展开复制后覆盖目标属性

function Profile() {
  const [user, setUser] = useState({ name: '张三', age: 20 });

  function growUp() {
    setUser((prev) => ({ ...prev, age: prev.age + 1 }));
  }

  return (
    <div>
      <p>{user.name} · {user.age} 岁</p>
      <button onClick={growUp}>长一岁</button>
    </div>
  );
}

数组：追加、更新、删除的不可变写法

const items = [{ id: 1, text: '牛奶', done: false }];

// 追加：展开旧数组 + 新元素，返回新数组
const added = [...items, { id: 2, text: '面包', done: false }];

// 更新某一项：map 返回新数组，命中项生成新对象
const toggled = items.map((it) =>
  it.id === 1 ? { ...it, done: true } : it
);

// 删除某一项：filter 返回新数组
const removed = items.filter((it) => it.id !== 1);

// 头部插入：新元素 + 旧数组
const prepended = [{ id: 0, text: '鸡蛋' }, ...items];
操作意图可变方法（禁止用于 state）不可变替代（正确写法）
追加元素arr.push(x)[...arr, x]
头部插入arr.unshift(x)[x, ...arr]
删除指定项arr.splice(i, 1)arr.filter(...) 或 arr.slice(0, i).concat(arr.slice(i + 1))
更新指定项直接改 arr[i].x = varr.map(...)，命中项返回新对象
对象改属性obj.x = v{ ...obj, x: v }
删除对象属性delete obj.x展开后不复制该属性，再交给新状态
注意不要把不可变理解成"把整个对象深拷贝一遍"。未变化的字段继续复用旧引用，只让被改动的层级生成新对象：这既保证根引用发生变化，又减少复制开销，也是 44.5 节 Immer 结构共享的基本思路。
易错点展开只是浅复制：新对象的顶层属性是新引用，但嵌套对象仍与旧对象共享引用。更新到嵌套层时必须逐层展开（见 44.5）。

44.5 嵌套对象与 Immer 概念

状态嵌套较深时，逐层展开会写出很长的复制链。理解原理后，可以在复杂状态上使用 Immer 库：它用代理（Proxy）包裹状态，允许你"看起来原地修改"，最终产出一份结构共享的不可变新状态。

// 嵌套对象的不可变更新：逐层展开
const state = {
  profile: { name: '张三', address: { city: '成都', street: '春熙路' } },
  tags: ['前端'],
};

const next = {
  ...state,
  profile: {
    ...state.profile,
    address: { ...state.profile.address, city: '杭州' },
  },
};
// Immer 的 useImmer：写作风格接近原地修改，产出仍是不可变新状态
import { useImmer } from 'use-immer';

function Profile() {
  const [user, setUser] = useImmer({
    name: '张三',
    address: { city: '成都' },
  });

  function changeCity(city) {
    setUser((draft) => {
      draft.address.city = city;   // 在 draft 上"原地改"，Immer 生成新状态
    });
  }

  return (
    <div>
      {user.name} · {user.address.city}
      <button onClick={() => changeCity('杭州')}>搬到杭州</button>
    </div>
  );
}
对照项手工不可变更新Immer 方案
写法逐层展开复制，样板代码多在 draft 上直接赋值，由代理记录变更
产出新对象 / 新数组引用结构共享的新状态，未改动部分复用旧引用
适用场景扁平状态、浅层对象嵌套深、更新分支多的表单与聚合状态
学习成本无需第三方库，规则固定需要理解 draft 概念，引入额外依赖

图 44-2 不可变更新采用结构共享：改动路径生成新对象，未改动部分复用旧引用

Immer 是第三方库，不属于 React 内置能力；选择与否取决于状态复杂度。useMemo、useCallback 对引用相等的依赖，在第六篇第 49 章展开。
易错点Immer 的 draft 只能在传入它的更新函数内部修改：函数执行结束后 draft 失效，不要把 draft 引用保存下来在别处继续使用；脱离 draft 直接改原始 state 对象，同样会违反不可变规则。

44.6 常见误区清单

误区正确处理
push / splice / sort 后直接 setState先复制新数组再修改副本；排序也要先 [...arr].sort(...)
把外部可变对象直接存进 state存入时复制一份；外部对象后续变化不应影响组件快照
组件内修改 props 对象属性props 是只读快照；需要修改时先复制到本地 state，或由父组件回调更新
解构后忘记嵌套层仍是共享引用更新嵌套字段时逐层展开，保证被改层是新对象
数组元素直接改属性map 出命中项的新对象，未命中项保留原引用
在 setState 回调外部计算新对象却没基于前一次状态同批次多次更新使用函数式更新 setPrev => ...prev，避免读到旧快照
 
// 正确的函数式更新：基于前一次排队值计算，避免同批次覆盖
function CounterList() {
  const [list, setList] = useState([]);

  function addMany() {
    setList((prev) => [...prev, '项一']);
    setList((prev) => [...prev, '项二']);   // 基于上一次排队结果累加
  }

  return <button onClick={addMany}>连续追加两项</button>;
}
一句话规则：基本类型直接给新值；对象与数组永远给新引用；嵌套改动逐层生成新对象；同批次累加用函数式更新。

要点一句话
状态保存引用对象与数组按引用保存，比较先看引用是否相同
