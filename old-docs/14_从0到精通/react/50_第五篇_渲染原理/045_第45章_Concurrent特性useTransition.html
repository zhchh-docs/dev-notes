第 45 章 Concurrent 特性：useTransition

教科书 第 45 章 / 共 64 章 · 预计 50 分钟 · 非紧急更新可被打断

Fiber 与调度给"可中断渲染"打好了底层基础，useTransition 是开发者日常使用这套能力的主要 API：把一次状态更新声明为过渡更新，允许它被紧急交互打断，同时保留旧界面直到新内容准备好。本章讲清 API 签名、包裹边界、行为表现，并与 useDeferredValue 对照。

45.1 Concurrent：可中断渲染的产品化

前几章的底层结构——Fiber 链表（第 39 章）、调度与优先级（第 40 章）——让 React 有能力把渲染拆开、暂停、恢复。Concurrent 特性就是在这层能力之上提供给开发者的一组机制：让部分更新可以延后渲染、被紧急任务打断，而界面始终保持可响应。

需要澄清一点：React 18 及之后，通过 createRoot 创建的应用默认具备并发渲染能力，不再存在一个需要单独打开的"并发模式开关"；开发者通过 useTransition、useDeferredValue、Suspense 等 API 主动使用这套能力。本章聚焦 useTransition。

45.2 紧急更新与非紧急更新

把第 40 章的优先级分层落到业务代码上，就是下面两类典型场景：

对照项紧急更新（同步档位）过渡更新（Transition 档位）
典型场景受控输入框、按钮点击、开关切换、滚动位置搜索过滤、大列表重排、选项切换后渲染详情区、视图切换
渲染时机事件回调结束后立即协调提交排入过渡队列，空闲时间片推进，可被紧急更新打断
旧界面新状态就绪后直接替换旧界面保留到新内容准备好，期间用 isPending 提示
触发方式普通 setState 调用用 startTransition 包裹的 setState
可中断性渲染与提交连贯完成，不被其他更新插队打断render 阶段可中断、草稿可丢弃重做
判断标准：用户正在直接操作的控件状态必须紧急；由控件值派生、计算量大的结果可以过渡。输入框的值是紧急的，过滤后的商品列表是过渡的。

45.3 useTransition：isPending 与 startTransition

useTransition 从 react 导入，调用后返回一个二元组：

import { useTransition } from 'react';

function SearchPanel() {
  const [keyword, setKeyword] = useState('');
  const [results, setResults] = useState(ALL_ITEMS);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    // 紧急：输入框立刻反映按键内容
    setKeyword(e.target.value);

    // 过渡：过滤大列表归入低一档队列
    startTransition(() => {
      setResults(filterHeavyList(e.target.value));
    });
  }

  return (
    <div>
      <input value={keyword} onChange={handleChange} />
      {isPending && <span className="hint">筛选中…</span>}
      <ul>
        {results.map((item) => (
          <li key={item.id}>{item.title}</li>
        ))}
      </ul>
    </div>
  );
}
返回项含义与行为
isPending布尔值：当前是否有进行中的过渡更新。过渡被调度期间为 true，渲染完成后变为 false，可用于展示加载指示、禁用按钮等
startTransition函数：接收一个回调，回调内调用的 setState 被归入过渡档位；回调内可以依次调用多个状态更新
useTransition 与组件级状态绑定：它报告的是当前组件发起的过渡是否在进行中。需要在事件回调、定时器等非组件位置发起过渡时，也可以使用从 react 导入的 startTransition（全局版本），只是没有对应的 isPending。
易错点isPending 只反映过渡更新是否在进行中，不代表网络请求状态：接口返回、图片加载等等待由 Suspense 与各自加载状态管理（第 46 章）。不要用 isPending 充当请求 loading 指示。

45.4 startTransition 能包裹什么、不能包裹什么

startTransition 的定位是"声明一批状态更新属于过渡"，而不是"把任意异步工作塞进后台"。包裹边界决定了 API 的语义是否成立。
事项允许不允许 / 不应当
包裹内容一个或多个 setState 状态更新包裹事件处理函数本身、路由跳转回调之外的业务流程
读取新状态过渡完成后由新一轮渲染自然读到新值在 startTransition 回调内同步读取刚更新的 state 并据此判断分支
外部副作用状态更新完成后的副作用仍交给 useEffect把网络请求、订阅、直接 DOM 操作写进过渡回调当作"后台任务"
受控值非过渡的 setKeyword 保持紧急把输入框自身的受控值更新包进 transition
 
// ✗ 反例：在过渡回调里同步读取新状态（状态尚未提交，读到的是旧快照）
function BadExample() {
  const [tab, setTab] = useState('home');
  const [isPending, startTransition] = useTransition();

  function switchTab(next) {
    startTransition(() => {
      setTab(next);
      if (tab === 'me') {            // tab 仍是本次渲染的旧值，判断不可靠
        recordMeVisit();
      }
    });
  }
  return null;
}
// ✓ 正确：过渡只负责更新状态；需要在状态变化后做的事放进 useEffect
function GoodExample() {
  const [tab, setTab] = useState('home');
  const [isPending, startTransition] = useTransition();

  useEffect(() => {
    if (tab === 'me') recordMeVisit();
  }, [tab]);

  function switchTab(next) {
    startTransition(() => setTab(next));
  }

  return (
    <button disabled={isPending} onClick={() => switchTab('me')}>
      进入个人页
    </button>
  );
}
边界提醒startTransition 回调内的多个 setState 同属一轮过渡调度；不要把需要立即反映到界面的更新（如开关切换、弹窗显隐）也包进去，否则交互会因为等待过渡调度而出现可感知延迟。

易错点startTransition 不会让过滤本身变快。它只是让这次长渲染排在紧急任务之后、可被打断；如果列表巨大、组件计算昂贵，仍然需要配合第六篇的 memo、useMemo、列表虚拟化等手段压缩渲染成本。

45.6 useDeferredValue 对照与常见坑

React 还提供 useDeferredValue：接收一个值，返回它的"延迟版本"；当上游值频繁变化时，延迟版本会落后一步慢慢追赶，适合"没有机会发起状态更新"的场景，例如接收 props 值、第三方组件内部状态需要延后使用。

import { useDeferredValue } from 'react';

function FilterPanel({ keyword }) {
  // 传入的 keyword 是外部状态；deferredKeyword 是它的延迟副本
  const deferredKeyword = useDeferredValue(keyword);
  // 用延迟值计算大列表，受控输入仍由外部紧急更新驱动
  const results = filterHeavyList(deferredKeyword);

  return (
    <ul>
      {results.map((item) => <li key={item.id}>{item.title}</li>)}
    </ul>
  );
}
对照项useTransitionuseDeferredValue
控制粒度主动包裹指定的一批状态更新对某个传入值生成延迟副本，组件内部决定用它计算什么
进行中状态提供 isPending 可显示指示不提供进行中标记；新旧值比较可自行判断是否落后
典型场景事件回调里区分紧急输入与派生结果值来自 props 或外部状态，组件无法改写发起方式
打断行为新更新到达时旧过渡草稿可被丢弃重来延迟值按调度节奏追赶最新值
两者选择依据一句话：能控制状态发起方式就用 useTransition；只能被动接收外部值就用 useDeferredValue。它们解决的都是"长计算不阻塞紧急交互"，只是控制入口不同。
常见坑其一，把受控输入值本身放进 transition，导致打字延迟；其二，用 useDeferredValue 包裹一个普通 state 再手动回写，语义冗余且容易产生循环；其三，在过渡回调里发起异步请求并期待它"被调度器管理"——请求时序仍由业务代码控制。

本章与第 46 章 Suspense 同属 Concurrent 体验体系：Transition 处理"状态更新可延后"，Suspense 处理"等待资源期间显示 fallback"，两者可以组合使用。

✓ 本章小结

要点一句话
Concurrent 基础建立在 Fiber 可中断渲染与优先级调度之上，React 18 起由 createRoot 默认启用
两类更新输入、点击为紧急；过滤、重排、视图切换为过渡
useTransition返回 isPending 与 startTransition；startTransition 内的更新归入过渡档位
包裹边界只包裹状态更新；不同步读新值；外部副作用交给 useEffect；受控值保持紧急
行为表现过渡期间保留旧界面，isPending 提示，新结果就绪后一次性提交替换
useDeferredValue对传入值生成延迟副本，适合无法发起状态更新的组件内部场景
边界提醒过渡不降低计算成本，大列表仍需组件级优化配合
