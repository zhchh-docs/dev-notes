56.1 为什么选 Ant Design

第七篇进入生态实战。后台管理系统是 React 最典型的落地场景，而 Ant Design（下称 antd）是这套场景下社区成熟度最高、组件覆盖最完整的方案之一。选型先看三件事：覆盖度、稳定性、文档与迁移成本。

方案定位后台适用度典型场景
Ant Design 5中后台全组件库，含布局/表格/表单/图表配合高企业后台、管理平台、BI
MUI (Material UI)Google Material 风格，通用型中通用 Web 应用、官网、SaaS
Arco / Semi字节/抖音系设计语言组件库中高字节体系后台、自定义设计系统
Tailwind + 自建原子 CSS 风格视团队而定高度定制、组件偏轻的团队
选组件库不只看组件数量，要看文档完整度、版本稳定性、对受控表单/表格这类高频场景的封装深度——后台 80% 的页面由表格、表单、布局、弹窗四类构成，这四类的成熟度决定交付效率。

antd 的组件体系与 React 心智一致：绝大多数组件是受控组件，数据由外层 state 驱动、通过事件回调回写。这一点与前面章节讲的表单、状态分层完全打通——这也是它适合 React 后台的原因。

56.2 安装与按需：组件库接入方式

antd 5 配合 Vite 通常不需要额外配置即可按需编译。先安装核心包（以官方当前推荐为准）：

npm install antd @ant-design/icons
# 需要暗色/紧凑等内置主题时还可安装 @ant-design/cssinjs（antd 内部依赖，一般无需手动装）

antd 5 使用 CSS-in-JS 方案（基于 cssinjs），样式随组件自动注入，默认即可按需，无需手动配置 babel-plugin-import 之类旧式按需工具。这也意味着：app.css 中不应再手动 import antd 的全局样式文件。

版本提示：本章示例基于 antd 5.x 与 React 18。antd 的 API 在 5.x 内有持续演进，使用前请以 npm 上的实际版本与官方文档核对组件属性；书中 API 形状用于讲原理，落地时以你安装版本的文档为准。
import { ConfigProvider, Button } from 'antd';
import { PlusOutlined } from '@ant-design/icons';

export default function App() {
  return (
    <ConfigProvider>
      <Button type="primary" icon={<PlusOutlined />}>新建</Button>
    </ConfigProvider>
  );
}
不要为了"用了个 Button"就全量 import 整个库再交给打包器做 tree-shaking——直接使用具名 import（import { Button } from 'antd'），让打包器按需摇树；同时保持 CSS-in-JS 方案默认开启，避免额外引入全局样式文件造成体积膨胀。

56.3 ConfigProvider 与主题定制

ConfigProvider 是 antd 的"全局上下文"入口，通过 React Context 向其下所有组件注入配置。最常用的三件事：locale（语言）、theme（主题 token）、componentSize（尺寸）。它天然与前面学的 Context 机制契合——越靠近根越能全局生效。

import { ConfigProvider } from 'antd';
import zhCN from 'antd/locale/zh_CN';
import dayjs from 'dayjs';
import 'dayjs/locale/zh-cn';
dayjs.locale('zh-cn');

export default function Root() {
  return (
    <ConfigProvider locale={zhCN} componentSize="middle">
      <App />
    </ConfigProvider>
  );
}
locale 陷阱DatePicker、Calendar 等日期组件底层依赖 dayjs；只配 antd 的 locale 而不配 dayjs.locale('zh-cn')，会出现"组件文案中文但日期显示英文"的错位。两个 locale 必须一起配。

主题定制通过 theme={{ token }} 传入 Design Token（设计变量）。这是 antd 5 的核心变化：把以往覆盖 less 变量的做法换成运行时 token，改品牌色、圆角、间距都走统一入口：

const theme = {
  token: {
    colorPrimary: '#2d6a3f',
    colorInfo: '#2d6a3f',
    borderRadius: 6,
    fontSize: 14,
  },
};

<ConfigProvider theme={theme}>...</ConfigProvider>
antd 5 的主题体系分三层：seed token（种子）→ map token（映射）→ alias token（别名）。改 seed 里的 colorPrimary，antd 会自动派生出一整套相关色板（hover/active/禁用等），这是"改一个变量全局换肤"的原理。

56.4 Design Token 与暗色模式

暗色模式同样通过 algorithm 实现：antd 提供 theme.darkAlgorithm，把它放进 theme.algorithm，再配合 token 覆盖即可一键切换。多主题并存时，可把主题算法按分支计算后传入：

import { theme, ConfigProvider } from 'antd';

function App({ dark }) {
  const algorithm = dark ? theme.darkAlgorithm : theme.defaultAlgorithm;
  return (
    <ConfigProvider theme={{ algorithm, token: { colorPrimary: '#2d6a3f' } }}>
      <AppShell />
    </ConfigProvider>
  );
}

图 56-1 Design Token 三层派生与 algorithm 的作用

不要用"全局 CSS 覆盖 antd 类名"来做主题——antd 5 的类名带 hash 且 CSS-in-JS 优先级管理，手写 !important 覆盖既脆弱又难维护；品牌定制一律走 ConfigProvider theme 的 token 入口。

56.5 Layout 体系搭建后台骨架

后台骨架用 Layout、Menu、Breadcrumb、Dropdown 组合：Layout.Sider 放导航菜单，Layout.Content 放页面内容，顶部 Layout.Header 放面包屑与用户区。结合第七篇第 58 章的权限方案，菜单数据通常来自后端路由配置。

import { Layout, Menu, Breadcrumb, Avatar, Dropdown } from 'antd';
import { UserOutlined, SettingOutlined, LogoutOutlined } from '@ant-design/icons';
import { Outlet } from 'react-router-dom';

const { Sider, Header, Content } = Layout;

export default function AdminLayout({ menus }) {
  return (
    <Layout style={{ minHeight: '100vh' }}>
      <Sider collapsible>
        <Menu theme="dark" mode="inline" items={menus} />
      </Sider>
      <Layout>
        <Header style={{ display: 'flex', alignItems: 'center' }}>
          <Breadcrumb items={[{ title: '首页' }, { title: '订单' }]} />
          <Dropdown menu={{ items: userMenu }}>
            <Avatar icon={<UserOutlined />} />
          </Dropdown>
        </Header>
        <Content style={{ padding: 24 }}>
          <Outlet />   {/* 嵌套路由出口，见第 30 章 */}
        </Content>
      </Layout>
    </Layout>
  );
}
衔接说明：后台布局与第 29–31 章 React Router 的嵌套路由、Outlet 强相关；菜单项与路由表往往由同一份配置生成，避免手写两份导致权限与导航不同步。
Menu 的 items 是统一数据驱动的（含 key、label、icon、children），selectedKeys 来自当前路由路径——把路由 path 与菜单 key 对齐是后台导航的标准做法。

56.6 业务组件组合规范

组件库给的是"原子件"，业务页面要的是"组合件"。规范做法是：不直接散落使用原子组件，而是封装成业务语义的组件。例如"金额输入"应封装成 AmountInput，内部用 InputNumber + 前缀 + 校验规则，对外只暴露 value/onChange，保持受控。

import { InputNumber, Form } from 'antd';

function AmountInput({ value, onChange }) {
  return (
    <InputNumber
      value={value}
      onChange={onChange}
      min={0}
      precision={2}
      addonBefore="¥"
      style={{ width: '100%' }}
    />
  );
}

// 使用时放进 Form，name 由 Form 管理，见第 35 章 react-hook-form / antd Form
function OrderForm() {
  return (
    <Form>
      <Form.Item label="金额" name="amount" rules={[{ required: true }]}>
        <AmountInput />
      </Form.Item>
    </Form>
  );
}
封装层级内容是否暴露给业务
原子组件Button / Input / Table 原始组件少用，仅简单场景
业务组件AmountInput、StatusTag、UserSelect 等是，统一受控 value/onChange
页面组件OrderTable、CustomerForm 等是，组合数据与交互
封装的价值在"受控边界一致 + 校验规则内聚"：业务组件统一走 value / onChange 协议，放进任何表单都能协同；校验、格式化这类重复逻辑收进组件内部，一处维护。

56.7 组件库的边界与脱离

组件库不是银弹。使用边界要清醒：

  • 高度定制的品牌页（营销官网、可视化大屏）组件库帮助有限，常见做法是组件库只承载后台、前台自建；
  • 过度封装会引入理解成本，业务组件应薄而稳，不把不稳定的业务逻辑塞进底层组件；
  • 升级迁移：antd 4→5 是 API 与样式机制双变化，升级前评估受控组件与自定义样式的改动面；
  • 体积意识：组件库打包进首屏会显著增加体积，按第 51 章对后台框架可整体懒加载，或仅首屏需要的部分提前。
组件库解决的是"标准后台页面"的效率，不是"定制体验"的边界。认清这点，就不会在需要完全定制时被组件库的默认样式拖累，也不会在不该重造轮子时自造组件。
