62.1 为什么测组件：行为而非实现

React Testing Library 的核心哲学是：测用户能感知的行为，不测实现细节。即测试"点了这个按钮会出现什么、输入后会显示什么"，而不是"这个 state 是不是调用了 setX"。

该测的（行为）不该测的（实现）
渲染后能看到标题/按钮断言内部 state 的值
点击后出现弹窗/文案变化断言某函数被调用了几次、传了什么参数
输入触发校验提示断言组件返回的 JSX 结构
行为测试的好处是实现换了测试不用改：只要用户看到的行为不变，重构内部（换 state 方案、改组件拆分）不会让测试变红。这让测试成为重构的护航而非障碍。

62.2 工具链：Vitest + RTL + user-event

Vite 项目常用 Vitest（快、天然支持 ESM），配 jsdom 环境与 RTL。安装与配置：

npm install -D vitest @testing-library/react @testing-library/user-event @testing-library/jest-dom jsdom
// vitest.config.js 片段
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: ['./src/test/setup.js'], // 引入 jest-dom 匹配器
  },
});
Jest 同样可用（Create React App 历史默认）；Vitest 与 Jest 的 API 高度兼容，本章示例在 Vitest 上运行。项目若已用 Vite，优先 Vitest，省去 Babel/转换配置。

62.3 render 与查询元素

用 render(ui) 渲染组件，用 screen.getByRole/getByText 等查询元素。查询优先按 getByRole（按钮、heading、textbox 等语义角色），拿不到再退而按文本。断言用 jest-dom 的匹配器：

import { render, screen } from '@testing-library/react';
import { describe, it, expect } from 'vitest';
import OrderToolbar from './OrderToolbar';

describe('OrderToolbar', () => {
  it('渲染标题与保存按钮', () => {
    render(<OrderToolbar />);
    expect(screen.getByRole('heading', { name: /订单管理/ })).toBeInTheDocument();
    expect(screen.getByRole('button', { name: /保存/ })).toBeInTheDocument();
  });

  it('无权限时不渲染删除按钮', () => {
    render(<OrderToolbar canDelete={false} />);
    expect(screen.queryByRole('button', { name: /删除/ })).not.toBeInTheDocument();
  });
});
getBy 与 queryBy断言元素"存在"用 getBy*（找不到会抛错）；断言"不存在"用 queryBy*（返回 null 不抛错）。用错 API 会让测试意图反了还经常绿。

62.4 用 userEvent 模拟交互

模拟用户交互（点击、输入、选择）用 userEvent，它比 fireEvent 更贴近真实（触发 focus、按键序列等）。先 await userEvent.click(...) 再断言结果：

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import LoginForm from './LoginForm';

it('输入账号密码点击登录后调用 onLogin', async () => {
  const user = userEvent.setup();
  const onLogin = vi.fn();
  render(<LoginForm onLogin={onLogin} />);

  await user.type(screen.getByLabelText('用户名'), 'admin');
  await user.type(screen.getByLabelText('密码'), '123456');
  await user.click(screen.getByRole('button', { name: /登录/ }));

  expect(onLogin).toHaveBeenCalledWith({ username: 'admin', password: '123456' });
});
userEvent 的所有动作都是异步的，必须 await；漏掉 await 会导致断言在交互完成前执行、测试不稳定。统一 const user = userEvent.setup() 后复用。

62.5 异步：waitFor 与 findBy

组件里有异步（请求接口后显示数据）时，用 waitFor 轮询直到条件满足，或用 findBy*（内部带 waitFor）等元素出现：

import { render, screen, waitFor } from '@testing-library/react';

it('加载后显示订单列表', async () => {
  render(<OrderList />);

  // findBy* 会一直等到元素出现
  const row = await screen.findByText('订单 1001');
  expect(row).toBeInTheDocument();

  // 或显式 waitFor 断言某状态
  await waitFor(() => {
    expect(screen.getByText('共 3 条')).toBeInTheDocument();
  });
});
异步断言一律用 findBy/waitFor 等待，而不是固定 sleep 或立即 getBy。等待的目标是"出现预期结果"，而非"等固定时间"——这样测试既稳又不会慢。

62.6 mock 接口与模块依赖

测试不应打真实网络。用 vi.mock 替换接口模块，或把手写 fetcher 传入组件。常用模式：mock 返回固定数据，让组件只测渲染与交互逻辑：

import { render, screen } from '@testing-library/react';
import { vi } from 'vitest';
import OrderList from './OrderList';

vi.mock('./api', () => ({
  fetchOrders: vi.fn().mockResolvedValue({
    list: [{ id: 1, customer: '张三' }],
    total: 1,
  }),
}));

it('展示接口返回的订单', async () => {
  render(<OrderList />);
  expect(await screen.findByText('张三')).toBeInTheDocument();
});
接口方案对比：轻量场景用 vi.mock 按模块替换足够；更贴近真实（含网络层、可测错误分支）可上 MSW（Mock Service Worker）拦截请求。团队按需取舍，原则是测试不依赖真实后端。

62.7 测试覆盖与组织

  • 优先测关键路径：登录、鉴权、核心表单校验、列表分页联动这些高风险行为值得写；简单纯展示组件不必全覆盖；
  • 一个用例一个行为：每条 it 断言一个用户可感知的行为，失败时能快速定位；
  • describe 组织：按组件/行为分组，命名"渲染/交互/异步"三档便于读；
  • 覆盖率只是参考：行覆盖率达标但没测到关键行为，等于白测；以"关键行为被覆盖"为目标而非追求数字；
  • 随改动维护：组件行为变化时同步更新测试，测试不是一次写完就不管。
别为了覆盖率数字写"断言实现细节"的假测试——那既脆又在重构时拖后腿。RTL 的价值在于迫使你以用户视角思考组件行为，这是它优于浅层快照测试的地方。
