64.2 核心原理：必须能讲清楚的三个机制

1. 渲染与协调

React 通过虚拟 DOM 描述 UI，状态变化触发协调（reconciliation）：对比新旧虚拟树，算出最小更新量交给真实 DOM。Fiber 架构把协调拆成可中断的增量任务，这是并发特性（第 46 章）的基础。

2. state 与更新

setState 触发重渲染，函数组件通过 Hooks 持有状态。useState 的更新是异步批量的（自动批处理），所以多次 set 合并为一次渲染；值靠闭包捕获，这是闭包陷阱与依赖数组（第 11 章）的根源。

3. Context 与副作用

Context 让数据跨层级穿透（第 14 章），是主题/语言/鉴权的载体；useEffect 让组件与外部系统同步（第 10 章），其依赖数组决定何时重跑、清理函数负责取消订阅与防泄漏。

面试最忌"背名词说不清因果"。建议用"一个现象 → 一个机制"来讲：比如"为什么 React 要虚拟 DOM"→"最小化真实 DOM 操作"；"为什么 hooks 有依赖数组"→"effect 要声明它读取的外部值"。讲因果比报菜名得分高。

64.5 项目实战：把知识落成作品

第 63 章的管理后台就是最好的"作品集"落点。面试讲项目时按STAR + 技术点组织：背景（解决什么问题）→ 方案（技术选型与架构）→ 落地（关键实现）→ 结果（指标/收益），并主动引出你掌握的原理。

讲项目的推荐框架：
1. 背景：做一个电商订单管理后台，多角色、多语言、需权限控制
2. 方案：Vite + React + TS + AntD，路由菜单同源配置 + RBAC
3. 落地：三态列表模型、Auth 组件按钮级权限、ECharts 封装
4. 结果：…（性能提升/交付效率/稳定性，用数据佐证）
5. 引申原理：路由同源为何避免不同步？Context 为何适合鉴权？
只报"我用过 XX"没有价值，要能讲"为什么选它、坑在哪、怎么解决的"。把第 56–63 章里那些 pit-sentence 变成你自己的项目经历去讲。

64.6 全栈延伸路线

掌握了 React 前端，全栈转型的方向已经清晰。React 学到的状态管理、受控、测试、工程化心智，在后端同样适用（只是换了语言与场景）。延伸路线建议：

  • 接口与数据：把前端请求层接上真实后端（Java Spring / Node），理解鉴权协议与 REST 设计；
  • 工程化：Git 协作、CI/CD、部署（与第 97–104 章 Java 工程化、Git 教程衔接）；
  • 质量：把测试意识带到后端单元测试与接口测试；
  • 性能：前端渲染优化之外，理解网络层与数据库层（对应数据库教程）；
  • 深度：深入 TypeScript、设计模式、源码阅读，从"用库"走向"懂原理"。
前端到全栈不是"再学一门语言"，而是把已经建立的心智模型（状态、生命周期、数据流、测试、工程化）迁移到新的技术面。你在 React 里养成的"数据流清晰、组件化、可测试"习惯，是全栈最值钱的底座。

64.7 学习复盘与持续成长

  • 定期复盘：按七篇地图自查，哪些能"讲清原理"、哪些还停在"会用"；
  • 代码即笔记：把每章的示例改成自己项目的真实场景，加深理解；
  • 主动深挖：对高频考点读官方文档与源码，建立一手认知；
  • 写下来：把"为什么"写成自己的技术博客/笔记，讲清即掌握；
  • 项目驱动：持续迭代第 63 章项目，加入新特性，作为成长证据链。
学习的终点不是读完书，而是能独立讲清、能落地、能迭代。把这本书当作地图而非终点，用它去导航你接下来每一个真实项目。
