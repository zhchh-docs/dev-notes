第 58 章 权限方案：路由级与按钮级

教科书 第 58 章 / 共 64 章 · 预计 55 分钟 · 前端权限的两层粒度

后台权限在前端分两层：路由级（能不能进这个页面）与按钮级（页面上这个操作能不能点）。本章讲权限数据从哪来、如何与路由/菜单联动、如何用权限 Context 与组件封装按钮级控制，以及"前端权限只是体验，安全靠后端"这条边界。

◆本章目标

  • 理解 RBAC 模型（角色-权限-资源）在后台的落地，知道权限数据通常来自后端；

58.1 权限模型与数据来源

后台最常见的权限模型是 RBAC（基于角色的访问控制）：用户拥有角色，角色拥有权限点，权限点对应到"能否访问某路由 / 能否执行某操作"。登录后后端返回当前用户的权限点集合，前端据此渲染。

图 58-1 RBAC 权限模型

权限点的命名约定很关键：多用「资源:动作」的形如 order:edit，让权限点既可用于路由（order:view）又可用于按钮（order:delete），一套集合管两层粒度。

58.2 登录态与用户信息获取

登录后后端返回 token，前端存入 storage；用户信息（含 permissions）通过接口获取，放进全局 Context。这里不展开鉴权协议细节（JWT 见第 46 章），聚焦权限数据的前端管理：

import { createContext, useContext, useState } from 'react';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null); // { id, name, permissions: [...] }

  async function login(credentials) {
    const { token, user } = await loginApi(credentials);
    localStorage.setItem('token', token);
    setUser(user);
  }

  function logout() {
    localStorage.removeItem('token');
    setUser(null);
  }

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth 必须在 AuthProvider 内使用');
  return ctx;
}
不要把 token 和用户信息混存、也不要在多个地方各存一份权限；权限集合应只存在 AuthProvider 这一份权威状态，菜单、路由、按钮都从它派生，改一处全局生效，避免"菜单有权限但按钮漏了"的状态漂移。

58.3 路由级权限：守卫与动态路由

路由级权限用守卫组件实现：在渲染路由前检查"是否登录 + 是否拥有该路由所需权限"，不满足则重定向。结合 React Router 的 Navigate 与 Outlet：

import { Navigate, Outlet, useLocation } from 'react-router-dom';

function RequireAuth({ permission }) {
  const { user } = useAuth();
  const location = useLocation();

  if (!user) {
    return <Navigate to="/login" state={{ from: location }} replace />;
  }
  if (permission && !user.permissions.includes(permission)) {
    return <Navigate to="/403" replace />;
  }
  return <Outlet />;
}

// 路由配置里按需包裹
const routes = [
  {
    element: <RequireAuth />,
    children: [
      { path: '/orders', element: <OrderListPage /> },
      {
        element: <RequireAuth permission="finance:view" />,
        children: [{ path: '/finance', element: <FinancePage /> }],
      },
    ],
  },
];
403 与 404 别混没登录 → 跳登录页并记住来源；登录了但没权限 → 跳 403（不是 404）。把"未登录"和"无权限"混成一个重定向，用户会困惑"我明明登录了为什么又被踢回去"。

更灵活的方案是动态路由：登录后按权限点过滤出一份可见路由表再注册。适合"不同角色看到完全不同的菜单"的场景，代价是路由注册时机依赖登录态。

58.4 菜单与路由的同源过滤

后台最常见的维护痛点是菜单与路由表各写一份，加页面要改两处、权限要改两处。规范做法是同一份"路由配置"同时生成菜单与注册路由：每条配置带 path、label、icon、permission，渲染前统一按 permissions 过滤。

const routeConfig = [
  { path: '/dashboard', label: '仪表盘', icon: <DashboardOutlined />, permission: 'dashboard:view' },
  {
    path: '/orders', label: '订单', icon: <TableOutlined />, permission: 'order:view',
    children: [
      { path: '/orders/list', label: '订单列表', permission: 'order:view' },
      { path: '/orders/audit', label: '订单审核', permission: 'order:audit' },
    ],
  },
];

// 1) 按权限过滤出可见配置
function filterByPermission(configs, perms) {
  return configs
    .filter((c) => !c.permission || perms.includes(c.permission))
    .map((c) => ({
      ...c,
      children: c.children ? filterByPermission(c.children, perms) : undefined,
    }));
}

// 2) 可见配置 → 菜单项（antd Menu items）
// 3) 可见配置 → 路由表（createBrowserRouter）
"一份配置，两处消费"：菜单项和路由都由同一份 routeConfig 派生，权限过滤只做一次。这样加页面只改配置，删权限只改后端返回，前端不会出现"菜单不显示但直接输 URL 能进"这类不同步。

58.5 按钮级权限：Context + useAuth

按钮级权限粒度更细：同一页面内，有的用户能"删除"，有的只能"查看"。用 useAuth 拿权限集合判断即可：

function OrderActions({ record }) {
  const { user } = useAuth();
  const canEdit = user.permissions.includes('order:edit');
  const canDelete = user.permissions.includes('order:delete');

  return (
    <Space>
      {canEdit && <Button onClick={() => onEdit(record)}>编辑</Button>}
      {canDelete ? (
        <Button danger onClick={() => onDelete(record)}>删除</Button>
      ) : (
        <Tooltip title="无删除权限">
          <Button danger disabled>删除</Button>
        </Tooltip>
      )}
    </Space>
  );
}
显隐 vs 禁用：无权限时直接隐藏最简洁；但"用户知道有这个功能但没权限"的运营场景，更合适是显示但禁用 + Tooltip 提示。两种都保留判断能力，按产品语义选。

58.6 权限组件与指令封装

为让按钮级判断不散落在每个组件里，可封装一个 <Auth permission="order:delete"> 包裹组件：无权限时渲染 fallback 或不渲染，有权限时渲染 children。再配一个 usePermission hooks 返回判断函数：

function Auth({ permission, fallback = null, children }) {
  const { user } = useAuth();
  const ok = !permission || user.permissions.includes(permission);
  return ok ? children : fallback;
}

function usePermission() {
  const { user } = useAuth();
  return (p) => user.permissions.includes(p);
}

// 使用
function OrderActions({ record }) {
  const has = usePermission();
  return (
    <Auth permission="order:delete" fallback={<Tooltip title="无删除权限"><Button disabled>删除</Button></Tooltip>}>
      <Button danger onClick={() => onDelete(record)}>删除</Button>
    </Auth>
  );
}
衔接说明：权限判断本质是"根据 Context 中的权限集合做条件渲染"，与第 6 章条件渲染、第 14 章 Context 一脉相承；Auth 组件就是条件渲染在权限场景的封装。

58.7 边界：前端权限 vs 后端安全

铁律：前端权限只是交互体验，不是安全屏障。任何人打开 DevTools 都能改前端判断、伪造请求。真正的权限校验必须在后端：接口要校验操作人是否有该权限，数据行要校验所属权（越权访问他人数据）。前端只做"让界面符合权限的呈现"。

因此前端权限的定位是：提升体验与减少无效交互（没权限就不显示入口、不给按钮），但绝不依赖它保护数据。后端接口的 401/403 响应前端也要正确处理——权限点过期、被收回时，前端要根据接口错误刷新用户信息或踢回登录。

层级前端负责后端必须负责
路由级菜单/路由按权限过滤、守卫跳转接口鉴权，未授权返回 401/403
按钮级显隐/禁用操作入口对应接口校验操作权限
数据级展示当前用户可看的数据行级数据隔离与归属校验
前端"隐藏了删除按钮"不等于"用户不能删除"——只要后端没校验，他手动发一个 DELETE 请求照样成功。所有权限安全责任在后端，前端做的只是呈现。
