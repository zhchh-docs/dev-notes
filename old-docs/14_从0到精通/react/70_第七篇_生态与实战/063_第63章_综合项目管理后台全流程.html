63.1 项目需求与技术栈选型

先明确要做什么：一个「电商订单管理后台」，包含登录、仪表盘、订单列表/编辑、权限、销售图表、中英切换。据此选型，每一环都用前面章节讲过的方案：

需求模块技术选型对应章节
脚手架/构建Vite + React 18 + TypeScript第 16/44/51 章
路由React Router v7（嵌套 + 守卫）第 29–31 章
全局状态Zustand（或 Redux Toolkit）第 20–22 章
组件库Ant Design 5 + ConfigProvider第 56/57 章
鉴权token + AuthProvider（RBAC）第 58 章
图表ECharts 封装第 60 章
国际化react-i18next + antd locale第 59 章
测试Vitest + React Testing Library第 62 章
选型的顺序是需求驱动：每个模块的需求决定选哪套方案，而不是为了用某个库造需求。项目是知识的容器，不是库的堆砌。

63.2 工程目录结构

合理的目录让职责边界清晰、好维护。按"领域 + 分层"组织，页面、组件、状态、请求、工具分开：

src/
├─ api/              # 请求封装（axios 实例 + 各模块接口）
├─ components/       # 通用业务组件（Auth、Chart、AmountInput…）
├─ pages/            # 页面级组件（Login、OrderList、Dashboard…）
├─ router/           # 路由配置 + 守卫（RequireAuth）
├─ store/            # 全局状态（auth、language…）
├─ hooks/            # 自定义 hooks（usePagedQuery、usePermission…）
├─ i18n/             # 国际化资源与 i18next 初始化
├─ utils/            # 纯函数工具（format、sliceFile…）
├─ styles/           # 全局样式与主题 token
├─ test/             # 测试 setup 与通用 mock
└─ App.tsx / main.tsx
衔接说明：目录分层的原则在第 16 章工程化里讲过——"按职责分"而非"按技术分"混在一起。请求/状态/组件各归其位，页面只做编排。
避免"页面里塞一堆逻辑、组件里写请求"的意大利面式结构。判断标准：一个文件只解决一个问题，页面变厚就抽 hooks、抽组件。

63.3 鉴权与全局状态

登录流程：提交账号密码 → 后端返回 token 与用户信息 → 存 token、把 user（含 permissions）写进 Zustand/auth store。路由守卫 RequireAuth 在进入前读 auth 状态：未登录跳登录、无权限跳 403。

// store/auth.ts —— 用 Zustand 管理鉴权
import { create } from 'zustand';

export const useAuthStore = create((set) => ({
  user: null,
  token: localStorage.getItem('token'),
  login: async (credentials) => {
    const { token, user } = await loginApi(credentials);
    localStorage.setItem('token', token);
    set({ token, user });
  },
  logout: () => {
    localStorage.removeItem('token');
    set({ user: null, token: null });
  },
}));
鉴权的核心是"单一权威状态"：token 与 user 只在一个 store 里，路由守卫、权限判断、axios 拦截器都从这里读，避免多处各存一份导致不一致。

63.4 布局、菜单与路由同源

用第 56 章 Layout 搭骨架 + 第 58 章"路由与菜单同源"生成导航。一份 routeConfig 同时产菜单与路由，统一按 auth 的 permissions 过滤：

// router/config.tsx —— 一份配置两处消费
const routeConfig = [
  { path: '/dashboard', label: '仪表盘', icon: <DashboardOutlined />, permission: 'dashboard:view' },
  { path: '/orders', label: '订单管理', icon: <TableOutlined />, permission: 'order:view',
    children: [{ path: '/orders/list', label: '订单列表', permission: 'order:view' }] },
];

// 1) 菜单：按权限过滤后转 Menu items
// 2) 路由：按权限过滤后 createBrowserRouter
// AdminLayout 的 <Outlet /> 渲染子页面，见第 30 章嵌套路由
菜单与路由必须同一份配置派生——否则"菜单不显示但输 URL 能进"这类不同步问题就会反复出现（第 58 章已强调）。同源后权限只过滤一次，全局生效。

63.5 核心 CRUD 页面

订单列表用第 57 章的三态模型：搜索表单收集条件、分页受控、请求由唯一 useEffect 驱动。编辑用 Modal + Form 受控回填。这是后台最高频的页面模式，直接复用第 57 章封装的 usePagedQuery。

function OrderListPage() {
  const { data, loading, filters, pagination, setFilters, setPagination } =
    usePagedQuery(fetchOrders);

  function onSearch(v) {
    setFilters(v);
    setPagination((p) => ({ ...p, current: 1 })); // 重置页码
  }

  return (
    <>
      <SearchForm onSearch={onSearch} />
      <OrderTable data={data} loading={loading} pagination={pagination} onChange={setPagination} />
      <OrderEditModal ... />
    </>
  );
}
CRUD 页面的精髓是把"通用逻辑"抽走、把"业务差异"留页面：分页联动、请求竞态防护、弹窗受控这些共性进 hooks/组件，页面只写自己的列、表单与操作。

63.6 权限、图表与国际化整合

三个生态模块整合在一起：

  • 权限：按钮级用 <Auth permission> 组件 + usePermission，数据级交给后端；
  • 图表：仪表盘用第 60 章的 <Chart option /> 封装渲染销售趋势图；
  • 国际化：业务文案走 i18next 的 t()，antd 组件文案走 ConfigProvider locale，二者由同一个语言状态驱动（第 59 章）。
// App.tsx —— 语言状态驱动 i18next + antd locale
const localeMap = { 'zh-CN': zhCN, 'en-US': enUS };

function App() {
  const { i18n } = useTranslation();
  return (
    <ConfigProvider locale={localeMap[i18n.language]} theme={{ token: { colorPrimary: '#2d6a3f' } }}>
      <RouterProvider router={router} />
    </ConfigProvider>
  );
}
三个模块别各自为政：权限状态进 auth store、语言状态统一、图表走封装组件。整合时最容易乱的是"每个模块自己拿一份状态"，务必收敛到全局 store 与统一封装。

63.7 测试与构建部署

关键行为补测试：登录表单、权限按钮显隐、列表加载、守卫跳转——用第 62 章 RTL + vi.mock 隔离接口。构建用 Vite 产静态资源，配合第 51 章的体积优化（路由懒加载、按需 ECharts），最终部署到静态托管或 Nginx。

# 开发 / 构建 / 测试
npm run dev        # 本地开发
npm run build      # 产物输出 dist/
npm run test       # 跑 Vitest 测试

# 部署：把 dist/ 产物放到静态服务器（Nginx/OSS/CDN）即可
