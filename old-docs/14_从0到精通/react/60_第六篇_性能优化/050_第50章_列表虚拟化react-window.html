50.1 长列表的真实成本

后台系统常见的"表格翻页慢、滚动掉帧、切换筛选卡顿"，很多时候不是接口慢，而是一次性把几千上万条数据渲染成了 DOM。每条记录哪怕只是一行简单文本，浏览器也要为它创建节点、计算样式、参与布局、参与绘制；节点越多，首次渲染与后续重排的成本越高。

成本项全量渲染几千条数据时为什么会放大卡顿
DOM 节点数量每条记录若干节点，总量随条数线性增长节点越多，浏览器内存占用与事件分发成本越高
布局计算（Layout）节点插入后整棵树参与回流计算后续滚动、筛选、样式变更都会触发重新布局
协调与渲染函数执行React 要为每条记录执行组件函数、生成 JSX 树组件内部若还有派生计算，成本叠加（第 49 章）
绘制与合成大面积内容需要光栅化滚动时频繁重绘，主线程被占满就掉帧
内存占用节点、事件监听、组件状态长期驻留数据量极大时页面长时间占用内存，切换标签也变慢
关键认识：用户同一屏只能看到十几二十行，却为几千行付出了全部渲染成本。虚拟化的思路就是"看得见的才渲染，看不见的只占位"。
先确认瓶颈确实在列表渲染：用第 47 章 Profiler 与 Chrome Performance 面板看提交耗时与长任务，不要一上来就把普通几十行的小表格改造成虚拟化列表。

50.2 虚拟化原理：可视区 + 缓冲区 + 占位

虚拟化（virtualization，又称窗口化 windowing）把列表想象成一个固定高度的窗口：窗口内才挂载真实组件，窗口上下各留一小段缓冲区，避免快速滚动时出现白屏；列表总高度由"条数 × 行高"计算出一个占位元素撑开，浏览器滚动条行为与普通列表完全一致。

图 50-1 全量渲染与虚拟化的 DOM 节点对比

react-window 是 React 生态中体积很小的虚拟化库，封装了滚动位置计算、可视区间计算、节点回收复用等细节；我们只需要告诉它总条数、行高（或行高测量函数）、以及如何渲染每一行。

虚拟化成立的前提：列表项结构独立、可以按索引快速定位数据；如果行与行之间存在全局布局依赖（跨列合并、整体排序联动），要先把布局模型拆成独立行，再上虚拟化。

50.3 FixedSizeList：固定行高列表

每行高度一致时使用 FixedSizeList。它的核心 props 与渲染函数参数如下：

props / 参数含义注意点
height列表可视区高度（像素）必须给定固定值；自适应高度要自行测量容器尺寸
width列表可视区宽度（像素）横向填满时可传 "100%"
itemCount数据总条数决定滚动占位总高度
itemSize固定行高（像素）FixedSizeList 据此计算每条记录位置
itemData传给行渲染函数的数据对象避免在行渲染函数闭包里直接引用外部数组导致引用问题
children 渲染函数返回一行的 React 节点参数含 index、style、data、key
onItemsRendered可视区索引变化回调用于触底加载更多、记录可见区间
 
import { FixedSizeList } from 'react-window';

function Row({ index, style, data }) {
  const user = data[index];
  return (
    <div style={style} className="user-row">
      <span>{index + 1}. {user.name}</span>
      <span>{user.department}</span>
    </div>
  );
}

export default function UserList({ users }) {
  return (
    <FixedSizeList
      height={520}
      width="100%"
      itemCount={users.length}
      itemSize={56}
      itemData={users}
    >
      {Row}
    </FixedSizeList>
  );
}
style 必须透传行渲染函数返回的根节点必须带上传入的 style。react-window 通过 style 里的 position: absolute、top、height 等定位每一行；漏掉 style 会导致行全部堆叠在同一位置。

行渲染函数通常写成独立组件（如上面的 Row），而不是内联箭头函数：内联函数每次渲染都会新建，配合 memo 时引用不稳定；独立组件也便于单独做性能优化。

不要在行渲染函数里调用 setState 或读取组件自身外部的可变全局状态：可视区回收再挂载时，行组件会重新执行，副作用应放进 effect 并配好 cleanup（第 10 章规则不变）。

50.4 VariableSizeList：动态行高与测量

每行高度随内容变化（评论、消息、自适应文本）时使用 VariableSizeList。它通过 itemSize(index) 函数查询某一行的高度，并用 estimatedItemSize 给出估算行高，先撑开滚动占位，真实高度测量后再修正位置。

import { VariableSizeList } from 'react-window';

function MessageRow({ index, style, data }) {
  const msg = data[index];
  return (
    <div style={style} className="message-row">
      <div className="message-author">{msg.author}</div>
      <div className="message-body">{msg.content}</div>
    </div>
  );
}

export default function MessageList({ messages }) {
  // 根据消息内容估算行高；真实场景可结合内容长度与换行规则计算
  const getItemSize = (index) => {
    const lines = Math.ceil(messages[index].content.length / 28);
    return 64 + lines * 22;
  };

  return (
    <VariableSizeList
      height={520}
      width="100%"
      itemCount={messages.length}
      itemSize={getItemSize}
      estimatedItemSize={96}
      itemData={messages}
    >
      {MessageRow}
    </VariableSizeList>
  );
}

当某一行高度在运行时发生变化（图片加载完成、展开收起、内容刷新），需要调用列表实例的 resetAfterIndex(index, shouldForceUpdate) 通知虚拟化组件重新测量该行之后的位置；否则滚动占位与真实位置会错位。

import { useRef } from 'react';
import { VariableSizeList } from 'react-window';

function CollapsibleList({ items }) {
  const listRef = useRef(null);

  const handleToggle = (index) => {
    // 该行高度变化后，从 index 开始重新测量并强制刷新位置
    listRef.current.resetAfterIndex(index, true);
  };

  return (
    <VariableSizeList
      ref={listRef}
      height={520}
      width="100%"
      itemCount={items.length}
      itemSize={(index) => (items[index].expanded ? 160 : 56)}
      estimatedItemSize={56}
      itemData={{ items, onToggle: handleToggle }}
    >
      {CollapsibleRow}
    </VariableSizeList>
  );
}
对照项FixedSizeListVariableSizeList
行高来源固定 itemSize 数值itemSize(index) 函数逐行查询
位置计算直接用固定行高累加先按估算行高占位，测量后修正
运行时高度变化不存在该问题调用 resetAfterIndex 重新测量
适用场景表格行、固定卡片、通讯录条目评论、消息、可展开折叠的动态内容
性能特征计算简单，开销最小多一层测量与缓存，行高规则要尽量稳定

50.5 列表项尺寸、key 与常见问题

虚拟化列表与普通列表一样，需要稳定的 key；react-window 在渲染函数参数中提供 key，应透传到根节点，避免复用错位。

function Row({ index, style, data }) {
  const user = data[index];
  // key 由 react-window 提供，必须透传给根节点
  return (
    <div style={style} key={user.id} className="user-row">
      {user.name}
    </div>
  );
}

结合 onItemsRendered 可以实现"滚动到底部加载更多"：当可视区接近末尾时触发下一页请求，把新数据追加到数组，itemCount 随之增长。

function UserList({ users, onLoadMore }) {
  const handleItemsRendered = ({ visibleStopIndex }) => {
    // 可视区最后一行距离总条数不足 10 条时请求下一页
    if (visibleStopIndex >= users.length - 10) {
      onLoadMore();
    }
  };

  return (
    <FixedSizeList
      height={520}
      width="100%"
      itemCount={users.length}
      itemSize={56}
      itemData={users}
      onItemsRendered={handleItemsRendered}
    >
      {Row}
    </FixedSizeList>
  );
}
常见问题原因与处理
行全部堆叠在顶部根节点漏传 style；把传入 style 原样挂到根元素
滚动位置与内容错位动态行高变化后未调用 resetAfterIndex；或 itemSize 估算偏差过大
快速滚动出现白屏缓冲区不足；react-window 提供 overscanCount 调整上下预渲染行数
筛选后列表状态错乱key 不稳定或沿用了旧索引；用业务唯一 id 作为 key，并在数据刷新后重置滚动位置
横向列表渲染不出来纵向列表默认按行布局；横向场景使用 Column 组件并设置 itemWidth
容器高度无法确定先测量父容器尺寸（如 ResizeObserver），再把高度传给列表；不要写死后让外层滚动
三条铁律：style 必透传、key 用业务 id、动态高度变化后 resetAfterIndex。绝大多数虚拟化错位问题都出自这三条。
滚动容器选择react-window 默认在列表组件自身的容器内滚动；如果挂到页面级窗口滚动，需要选用对应的窗口滚动模式并把 height 与可视区高度对齐，两者混用会导致占位高度与滚动条计算错位。

50.6 何时用虚拟化与替代方案

虚拟化解决的是"单次渲染大量节点"的问题，但它也带来定位、滚动控制、动态测量的复杂度。决策时先看数据规模与交互需求：

方案适用条件代价与边界
原生全量渲染几十到一两百条，组件结构简单实现最简单，不需要引入虚拟化库
分页 / 无限滚动 + 服务端切片数据天然可分页，后端能按页返回不需要前端虚拟化，但跨页检索体验受限
react-window 虚拟化单次数百到数万条、行高规则明确、滚动浏览为主动态测量与滚动控制需要额外处理
其他虚拟化库需要更复杂的网格、多列、动态测量能力时再评估选型前确认维护状态与体积，不盲目引入
历史脉络：react-window 由 react-virtualized 的作者精简而来，体积更小、API 更窄；现代项目中也可了解 TanStack Virtual 等无头方案。本章以官方常见的 react-window 固定 API 为准，选型时以各库当前文档为准。
本章收口：虚拟化把 DOM 规模锁定在可视区，是长列表最直接的手段；但它解决不了单条记录内部的计算昂贵问题，那部分回到第 48、49 章的 memo 与 useMemo 处理。
