第 52 章 服务器渲染概念：SSR/SSG

教科书 第 52 章 / 共 64 章 · 预计 50 分钟 · HTML 何时生成、由谁生成

CSR 的空白外壳要等脚本与数据才出内容，SSR 在请求时由服务器生成 HTML，SSG 在构建时生成静态页面，ISR 在后台按需再生。本章用对照表理清四种模式在生成时机、数据时机、首屏速度、成本与适用场景上的差别，并明确 React 只是库、渲染模式由框架编排的边界。

◆本章目标

  • 说清客户端渲染（CSR）的完整流程，以及它在首屏时间、SEO 上的痛点；
  • 理解 SSR：请求到达时由服务器把 React 树渲染成 HTML，renderToString 与 renderToPipeableStream 的分工；

  • 明确 React 本身只是库，渲染模式由框架（如 Next.js）提供，并能在架构选型时做成本取舍。

52.1 CSR 流程与痛点

本书前面章节写的浏览器端应用属于客户端渲染（Client-Side Rendering，CSR）：服务器返回一个几乎空白的 HTML 外壳，浏览器下载 JS bundle，React 在浏览器里挂载、再请求业务数据，最后才渲染出界面。

  1. 浏览器请求页面，服务器返回带空 root 节点的 HTML；
  2. 浏览器下载、解析、执行 JS bundle；
  3. React 挂载完成后发起数据请求；
  4. 数据返回，组件渲染出首屏内容。
// 典型 CSR 入口：root 节点初始为空，等待 JS 执行后才有内容
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(<App />);

这套模式在内部后台系统表现良好，因为用户已经登录、对首屏白屏容忍度高。但在面向公网的内容型页面上，它带来两类典型问题：

痛点成因受影响场景
首屏可见时间长必须等 bundle 下载、执行、再等数据返回，页面才有内容弱网、低端机、bundle 体积大的站点
搜索引擎抓取困难初始 HTML 没有正文内容，爬虫未必等待 JS 执行与异步数据资讯、电商、文档、营销页等需要收录的站点
社交分享卡片缺失抓取初始 HTML 的社交平台读不到标题、摘要、封面图文章、商品、活动链接分享到 IM 与社交平台
初始骨架空档接口与脚本未就绪期间只能展示骨架或空白网络条件不稳定的移动端体验
SSR 与 SSG 都在解决同一个问题：让浏览器拿到 HTML 时里面已经有可见内容；区别只在于 HTML 是在"每次请求时"生成，还是在"构建时"生成。

补充理解两个首屏阶段的关系，便于后续判断优化方向：

  • 首屏可见（FCP/LCP）：浏览器第一次画出有意义内容的时间；CSR 要等脚本与数据，SSR/SSG 在 HTML 到达后即可绘制；
  • 可交互：页面事件能被响应的时间；无论哪种模式，都要等客户端 JS 完成水合（第 53 章）；
  • 因此"内容先到"与"可以操作"是两个阶段，选型时不要混为一谈。

52.2 SSR：请求时在服务器生成 HTML

服务器端渲染（Server-Side Rendering，SSR）指：用户请求某个路由时，服务器（Node.js 等运行时）把当前路由对应的 React 组件渲染成 HTML，连同初始数据一起返回；浏览器先展示这份 HTML，之后再下载 JS 并完成 hydration（水合，第 53 章），应用才具备交互能力。

// 服务端概念示例：把 React 树渲染成 HTML 字符串
import { renderToString } from 'react-dom/server';
import HomePage from './pages/HomePage';

export function renderHomePage(initialData) {
  // 服务器上渲染组件，得到一份包含标记的 HTML 字符串
  const html = renderToString(<HomePage data={initialData} />);
  // 把 html 嵌入页面模板，连同初始数据一并返回给浏览器
  return `
    <html>
      <body>
        <div id="root">${html}</div>
        <script>window.__INITIAL_DATA__ = ${JSON.stringify(initialData)}</script>
      </body>
    </html>
  `;
}

React 提供两套服务端渲染 API：

API行为特点与适用
renderToString同步把整棵 React 树渲染成一个 HTML 字符串实现简单；整棵树必须先渲染完才开始输出，请求耗时随页面规模增长
renderToPipeableStreamReact 18 提供的流式渲染，按结构分块把 HTML 推给响应流浏览器可先接收首块内容，配合 Suspense 边界实现流式下发（第 53 章展开）
renderToReadableStream面向 Web Streams 的流式服务端渲染 API适配边缘运行时等 Web 标准环境，概念与上一行同源
SSR 的核心收益：HTML 在响应里就带内容，浏览器不必等整份 JS 执行完才显示页面；代价是每次请求都要在服务器上完成一轮渲染，服务器成本与响应延迟随之上升。
数据与代码环境服务端渲染期间没有浏览器对象（window、document），直接访问会报错；浏览器相关 API 要推迟到客户端 effect 或交互阶段执行。本书第 10 章的 effect 时机模型在 SSR 下同样适用。

52.3 SSG：构建时生成静态 HTML

静态站点生成（Static Site Generation，SSG）在项目构建阶段就把每个路由渲染成静态 HTML 文件，部署到静态托管或 CDN。用户请求时直接返回现成 HTML，服务器不需要实时渲染；内容更新后重新构建，页面才随之刷新。

与 SSG 相关的进阶概念是 ISR（Incremental Static Regeneration，增量静态再生）：页面先以静态形式对外服务，后台在指定间隔或按需重新生成页面，生成成功后替换旧版本；兼顾静态缓存性能与内容时效性。这一能力由框架与托管层提供，React 本身不负责。

SSG 的取舍本质：用"重新构建才更新"换取"服务器几乎零渲染成本"；内容固定、可定期重建的页面最适合，强实时页面则应回到 SSR 或客户端取数。
概念HTML 生成时机内容新鲜度与缓存
CSR浏览器端，脚本执行后生成无服务端 HTML 缓存；每次加载走客户端渲染流程
SSR每次请求到达时，服务器实时生成数据最新；无法在边缘节点长期缓存完整页面
SSG构建时一次性生成静态文件内容随构建版本更新；可被 CDN 长期缓存，响应最快
ISR构建时生成初版，后台按需/定时再生在静态性能与数据新鲜度之间折中，过期后后台刷新
SSG 不等于"纯静态、没有 JS"：静态 HTML 只是首屏内容，交互仍然需要客户端 JS 完成 hydration；SSG 解决的是 HTML 生成时机，不消除客户端脚本体积。

52.5 框架层面：React 只是库

需要明确：React 本身只负责组件渲染与交互，路由约定、服务端打包、数据获取时机、页面缓存策略都不是 React 提供的。生产环境的 SSR/SSG 通常由框架统一编排，Next.js 是 React 生态中最常见的代表。

// Next.js Pages Router 概念示例：getStaticProps 在构建时取数并生成静态页
export async function getStaticProps() {
  const posts = await fetchPosts();
  return { props: { posts } };
}

export default function BlogList({ posts }) {
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}
// Next.js Pages Router 概念示例：getServerSideProps 在每次请求时取数（SSR）
export async function getServerSideProps() {
  const user = await fetchCurrentUser();
  return { props: { user } };
}

export default function Dashboard({ user }) {
  return <h1>欢迎，{user.name}</h1>;
}

在 Next.js App Router 等较新的体系中，组件默认可作为服务端组件运行，框架在服务端完成渲染与数据读取，再把结果下发；具体 API 与配置以对应框架官方文档为准，本章只建立概念层面的对应关系。

选型提示：阅读框架文档时，先判断它把页面归为 SSR、SSG 还是 ISR，再看数据获取函数与缓存配置；不要把框架约定误记为 React 核心 API。

52.6 取舍：什么时候不必上 SSR

SSR/SSG 不是默认最优解。引入服务端渲染会带来部署形态变化（Node 运行时或边缘环境）、数据获取链路改造、水合成本与调试复杂度。决策时对照下表：

判断问题倾向结论
是否需要搜索引擎收录与社交分享摘要需要 → 考虑 SSR/SSG；内部后台、登录后系统通常不需要
首屏慢是否由 JS 体积导致先做代码分割（第 51 章）与资源瘦身；未必需要服务端渲染
内容是否相对固定、可定期重建固定内容优先 SSG/ISR，服务器成本最低
页面是否强个性化、强实时SSR 更合适；但要评估服务器渲染耗时与并发成本
团队是否具备服务端部署与调试能力能力不足时，先用 CSR + 静态优化把体验做到位，避免架构过度设计
常见误解"上了 SSR 页面就一定快"并不成立：水合开销、服务端等待、流式配置不当都可能让整体体验不如优化充分的 CSR。选型与验收时要以真实指标（LCP、交互响应）为准，而不是模式名称。
内部后台、员工系统、登录后才能访问的页面通常不需要 SSR/SSG：用户身份与个性化状态在客户端才完整，强行服务端渲染只会增加部署复杂度，收益应让位于代码分割、资源压缩等 CSR 侧优化。
本章收口：CSR、SSR、SSG、ISR 的差别集中在 HTML 与数据"何时生成、由谁生成、缓存多久"；理解这张对照表，第 53 章再进入水合与流式渲染的细节。
