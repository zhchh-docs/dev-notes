第 48 章 memo：什么时候包

教科书 第 48 章 / 共 64 章 · 预计 50 分钟 · 记忆化不是免费午餐

父组件渲染会带动子组件默认重渲染，memo 提供了一层按 props 跳过渲染的屏障。本章讲清 memo 的浅比较语义与自定义比较函数，给出值得包与不值得包的对照场景，识别内联对象、函数、数组导致引用不稳定的根源，并梳理 Context 绕过、浅比较失效等边界。

◆本章目标

  • 说清 React 默认渲染规则：父组件渲染，子组件默认跟着渲染，与 props 是否变化无关；
  • 掌握 React.memo 的默认浅比较语义，以及第二个参数自定义比较函数的写法；
  • 能判断一个组件值得包还是不值得包，避免全项目无脑套 memo；
  • 识别 props 引用不稳定的根源（内联对象、内联函数、内联数组）及其配套解法；
  • 记住 memo 的边界：浅比较、Context 绕过、内部 state 不受影响等失效场景。

48.1 默认行为：父渲染带动子渲染

回顾第 41 章的组件执行过程：父组件每次渲染时，React 会重新执行父组件函数，返回新的 JSX；协调阶段遇到子组件时，默认不会比较 props 是否真的变了，而是直接让子组件也执行一次函数。子组件内部 state、ref 不会因此丢失，但函数体会重新跑一遍。

import { useState } from 'react';
import ProductCard from './ProductCard';

export default function ShopPage() {
  const [keyword, setKeyword] = useState('');

  return (
    <div>
      <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />
      {/* 即使 product 对象没变，父组件每次输入都会带动 ProductCard 重新执行 */}
      <ProductCard product={product} onAdd={handleAdd} />
    </div>
  );
}

输入框每敲一个字符，ShopPage 重新渲染，ProductCard 也跟着重新执行。如果页面上有几十上百个卡片，或者卡片内部有较重的 JSX 结构，这种"无辜重渲染"就会累积成可感知的卡顿——这正是第 47 章 Profiler 里常见的一类现象。

React 的默认选择是"先简单，再按需优化"：默认不做 props 比较，省去比较成本；当某个子树确实昂贵、且频繁被无辜带动时，再用 memo 给它加一层渲染屏障。
默认规则一句话：父渲染，子默认渲染；props 不变也会渲染。memo 改变的只是"是否跳过子组件渲染"这一个判断。

48.2 React.memo：默认浅比较

memo 是一个高阶组件：把组件包进去，返回一个新组件。新组件在父组件渲染时，会先用浅比较检查新旧 props，全部相等就跳过本次渲染，沿用上一次的渲染结果。

import { memo } from 'react';

function ProductCard({ product, onAdd }) {
  return (
    <article>
      <h3>{product.name}</h3>
      <p>{product.price} 元</p>
      <button onClick={() => onAdd(product.id)}>加入购物车</button>
    </article>
  );
}

// 默认行为：对 props 逐键做 Object.is 浅比较，全部相等则跳过渲染
export default memo(ProductCard);

默认浅比较的规则：遍历新旧 props 的每一个键，用 Object.is 比较对应值。原始值（数字、字符串、布尔值、null、undefined）比较值本身；对象、数组、函数比较引用——引用不同就视为 props 变了。

第二个参数：自定义比较函数

当默认浅比较不满足需求时，可以传入 areEqual(prevProps, nextProps)：返回 true 表示 props 相等、跳过渲染；返回 false 表示需要重新渲染。注意它与 React 内部约定相反：返回 true 才跳过。

const UserRow = memo(
  function UserRow({ user, selected }) {
    return (
      <tr>
        <td>{user.name}</td>
        <td>{user.email}</td>
        <td>{selected ? '✓' : ''}</td>
      </tr>
    );
  },
  // 只关心这两个字段，其余 props 变化不触发重渲染
  (prev, next) =>
    prev.user.id === next.user.id &&
    prev.user.name === next.user.name &&
    prev.selected === next.selected
);
对照项默认浅比较自定义 areEqual
比较方式逐键 Object.is，对象比引用由你决定比较哪些字段、怎么比
返回 true 的含义—（内部判断）props 相等，跳过渲染
返回 false 的含义—（内部判断）props 不同，重新渲染
适用场景props 以原始值为主的展示组件只需比较部分字段、或需要深比较个别字段
风险对象引用一变就失效比较逻辑写错会导致界面不更新，更难排查
自定义比较函数里不要做深比较（如递归遍历对象所有字段）：比较成本可能超过省下的渲染成本。只比较真正影响展示的少数字段。

48.3 什么时候值得包

memo 的收益 = 省下的渲染成本 − props 比较成本。当子组件渲染确实昂贵、且经常被无辜带动时，收益才为正。典型值得包的场景：

场景为什么值得
纯展示组件，JSX 结构较重卡片、表格行、面板等渲染内容多，重复执行函数与协调成本高
在长列表中被复用几十上百次单个组件便宜，但数量乘以重复渲染次数后总量可观（配合第 50 章虚拟化）
props 以原始值为主、引用稳定浅比较能真正命中"props 没变"，屏障才拦得住父组件渲染
父组件高频更新（输入、滚动、计时器）父组件每次渲染都可能带动子组件，屏障在高频场景下收益最明显
Profiler 已证实它被无辜重复渲染有度量数据支撑，而不是凭猜测包裹（第 47 章）

48.4 什么时候不要包

memo 本身有成本：每次父组件渲染都要执行一轮 props 比较；包裹后组件结构也多一层。以下场景包了往往得不偿失：

场景为什么不值得
组件本身很轻量（一两行文本、简单图标）渲染成本低于比较成本，包了反而变慢，代码还变绕
props 每次都是新对象/新函数/新数组浅比较永远不相等，memo 屏障形同虚设，只留下比较开销
组件几乎不被父组件重复渲染没有"无辜重渲染"可拦，优化没有目标
组件内部数据频繁变化（自己的 state 驱动更新）memo 只拦 props 变化，拦不住内部 state；收益与问题无关
为了"代码规范"全项目默认包裹增加阅读负担与比较开销，真正需要优化的组件反而被淹没在噪音里
反模式：给每个组件函数都套 memo，然后 props 里全是内联函数与内联对象。结果是比较环节每次都判不等，问题依旧、代码更乱。先解决引用稳定性，再谈 memo。
判断顺序拿到一个慢页面，先用第 47 章 Profiler 确认：是不是某个组件在被无辜重复渲染、它的渲染是否昂贵。两个条件都成立，才轮到这里动手包 memo。

48.5 props 不稳定的根源与配套手段

memo 失效最常见的原因不是 memo 写错，而是 props 引用每次都变。以下三种写法在父组件 JSX 里很常见：

// ✗ 每次渲染都生成新对象、新函数、新数组，浅比较必然不等
<ProductCard
  product={product}
  onAdd={(id) => addToCart(id)}
  style={{ padding: 8 }}
  tags={['hot', 'new']}
/>

对应的配套手段按推荐顺序排列：

不稳定来源解法说明
内联事件处理函数useCallback 固定引用（第 49 章）依赖稳定时，回调引用跨渲染保持不变
内联样式 / 配置对象提到组件外常量，或 useMemo静态配置直接移出 JSX；依赖派生对象用 useMemo
内联数组字面量提到组件外，或 useMemo同对象处理思路
只需要某个原始字段只把原始值传给子组件如传 product.id 而非整个 product 引用
回调只依赖 set 状态函数用函数式更新，回调内不读外部值setState 的 setter 引用本身稳定，无需 useCallback
 
import { memo, useCallback, useMemo } from 'react';

function ShopPage() {
  const [cart, setCart] = useState([]);

  // 引用稳定：依赖为空时函数跨渲染保持同一引用
  const handleAdd = useCallback((id) => {
    setCart((prev) => [...prev, id]);
  }, []);

  // 静态样式提到组件外；派生配置才用 useMemo
  const cardStyle = useMemo(() => ({ padding: 8 }), []);

  return (
    <ProductCard product={product} onAdd={handleAdd} style={cardStyle} />
  );
}
memo 与 useCallback/useMemo 是一套组合拳：memo 负责比较，useCallback/useMemo 负责让 props 引用稳定；只做前者而不解决后者，屏障拦不住任何东西。
提前说明：useMemo/useCallback 的适用边界在第 49 章展开；本章只需先建立"memo 需要稳定 props 配合"这一认识。

48.6 memo 的局限与失效场景

memo 只比较 props，它改变不了 React 渲染模型的其他规则。以下场景 memo 不会生效，需要换思路：

局限表现与替代思路
浅比较只比一层嵌套对象内部字段变了但外层引用没变，比较会误判相等；自定义比较函数里显式比较关键字段
Context 变化绕过 memo组件订阅的 Context 值更新时，即使 props 没变也会重渲染；应把 Context 粒度拆细（第 21 章）
内部 state 变化不受 memo 控制组件自己的 state 更新照常触发渲染；想减少内部重渲染要优化组件自身逻辑
ref 变化不触发渲染ref.current 变化本来就不渲染，与 memo 无关；不要把需要展示的值存进 ref
memo 不阻止父组件自身渲染父组件 state 变化导致的自身执行无法靠子组件 memo 消除；必要时把 state 下沉到更小的组件（第 55 章实战）
默认比较不识别函数内部行为两个不同函数即使做同样的事，引用不同也判不等；这正是需要 useCallback 的原因
不要忽略可读性成本每加一层 memo、useCallback、useMemo，组件就多一层引用追踪成本。优化后若 Profiler 复测收益很小，应把记忆化代码回退，保持组件简单。
本章收口：memo 是"按 props 跳过渲染"的开关，不是性能银弹。先用度量找到昂贵的展示组件，确认 props 可以稳定，再包裹；失效时回到 48.6 的局限清单逐条排查。

✓ 本章小结

要点一句话
默认规则父渲染，子默认渲染，不等 props 比较
memo 语义props 浅比较相等则跳过渲染，可用 areEqual 自定义
值得包渲染昂贵、props 稳定、被高频父组件带动、有度量依据
不要包组件轻量、props 引用每次新、很少被带动、内部 state 主导更新
配套手段useCallback 稳函数、useMemo 稳对象、只传原始值
边界浅比较一层、Context 绕过、拦不住内部 state 与父组件自身渲染
