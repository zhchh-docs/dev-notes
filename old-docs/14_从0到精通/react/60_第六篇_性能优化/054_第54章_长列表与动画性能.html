54.1 浏览器渲染管线

理解动画与列表卡顿，先要知道浏览器一帧画面是怎么产出的。一次更新通常经过五个阶段：JavaScript 执行 → 样式计算 → 布局 → 绘制 → 合成。改不同的属性，触发的后续阶段不同，成本差别很大。

图 54-1 浏览器渲染管线与各阶段成本关系

阶段做什么成本提示
JavaScript执行事件回调、动画更新、数据处理主线程长任务会挤占整帧时间，动画自然掉帧
样式计算把 CSS 规则应用到元素，计算最终样式选择器复杂、节点量大时成本上升
布局 Layout计算元素位置、尺寸与文档流关系成本最高；一个元素位置变化可能引起整页回流
绘制 Paint把背景、边框、阴影、文字等画到图层上大面积重绘在低端机上明显
合成 Composite把多个图层按顺序拼成屏幕画面可由 GPU 完成，不影响主线程布局
优化主线程的两个方向：减少 JavaScript 长任务（拆分、延迟、记忆化），减少动画触发的布局与绘制（见 54.3）。

54.2 长列表补充：content-visibility 与布局包含

第 50 章的虚拟化是用 JS 控制节点挂载；在不引入虚拟化库的场景下，CSS 也能帮浏览器跳过视口外内容的渲染工作。content-visibility: auto 让浏览器跳过屏幕外元素的布局与绘制，进入视口附近再渲染；配合 contain-intrinsic-size 给出占位尺寸，避免滚动条跳动。

.card-item {
  /* 视口外跳过布局与绘制，进入视口再渲染 */
  content-visibility: auto;
  /* 占位高度，避免滚动条高度突变 */
  contain-intrinsic-size: auto 96px;
}

/* 布局包含：声明该元素内部布局不影响外部，边界明确 */
.masonry-panel {
  contain: layout paint;
}
  • content-visibility: auto：跳过视口外节点的布局与绘制成本，必须配合占位尺寸，浏览器支持程度以目标环境为准；
  • contain: layout paint：隔离元素内部布局，避免内部变化影响外部回流；边界声明要符合实际，不要把需要溢出显示的内容裁掉；
  • 稳定 key：复用现有 DOM 节点，减少节点创建与销毁；key 用业务唯一 id，不要用数组下标（第 43 章）；
  • 分页 / 无限滚动：单屏 DOM 数量始终可控，配合服务端切片，适合数据天然可分页的场景（第 50 章）；
  • 避免每帧读写布局属性：防止反复触发回流（布局抖动），规则见 54.4 的读—写交替说明。
CSS 跳过渲染不等于不下载数据：content-visibility 只影响渲染层成本，列表数据量过大时仍需虚拟化或分页控制 DOM 规模；两者互补，不能互相替代。
占位尺寸要真实contain-intrinsic-size 给的估算高度与真实行高相差过大时，滚动条长度会在节点进入视口后跳动；行高规则明确时，先在 CSS 里写准占位值，动态行高再交给虚拟化库处理。

54.3 动画性能：只动合成层属性

动画每一帧都在更新样式。如果更新的属性触发布局，浏览器就要在每帧重算位置尺寸；触发绘制则要重画像素；只有 transform 与 opacity 可以只走合成阶段，由 GPU 处理，主线程负担最小。

属性类别代表属性动画建议
触发布局（最贵）top、left、width、height、margin、padding不要在高频动画里更新；改用 transform 位移、scale 缩放
触发绘制background、color、box-shadow、边框宽度低频切换可以；持续动画中尽量避免
只触发合成transform、opacity位移、缩放、淡入淡出优先使用，动画最流畅
 
/* ✗ 每帧改 left，触发布局回流 */
.slide-x-bad { transition: left 0.3s ease; }
.slide-x-bad:hover { left: 200px; }

/* ✓ 改 transform，只走合成层 */
.slide-x-good { transition: transform 0.3s ease; }
.slide-x-good:hover { transform: translateX(200px); }

/* 淡化效果同样走合成层 */
.fade-good { transition: opacity 0.3s ease; }
.fade-good:hover { opacity: 0.6; }
will-change 要克制will-change 可以提前提示浏览器创建图层，但每个合成层都占用显存；大量元素同时声明会让内存与图层管理成本上升。只给确有动画的元素短期使用，动画结束后移除声明。
实践准则：位移用 translateX/translateY，缩放用 scale，显隐用 opacity；需要位置变化的元素先脱离文档流（position: absolute 或 fixed），避免影响相邻元素布局。

54.4 requestAnimationFrame：帧级时机

JS 驱动的动画（拖拽、进度条、数字滚动）应把更新提交给 requestAnimationFrame（简称 rAF）：浏览器在下次重绘前执行回调，回调节奏与屏幕刷新对齐，不会在一帧内重复更新，也不会在后台标签页空跑。

对照项requestAnimationFramesetTimeout / setInterval
执行时机下次重绘前执行，与刷新节奏对齐定时器到期即执行，可能落在帧之间造成跳帧
后台标签页自动暂停，不占用资源继续按间隔触发，容易堆积回调
适用场景逐帧动画、拖拽跟随、滚动联动定时轮询、秒表等非画面同步场景
 
function animateProgress(el, target) {
  let start = null;

  function step(timestamp) {
    if (start === null) start = timestamp;
    const progress = Math.min((timestamp - start) / 800, 1);
    // 只更新合成层属性，不触发布局
    el.style.transform = `scaleX(${progress})`;
    if (progress < 1) {
      requestAnimationFrame(step);
    }
  }

  requestAnimationFrame(step);
}

同一帧内反复"读布局属性 → 写样式 → 再读再写"会造成布局抖动（layout thrashing）：每次写入都强制浏览器提前重新计算布局。正确做法是先批量读完需要的布局值，再统一批量写入样式。

// ✗ 读-写-读-写交替：每行写入都触发一次强制回流
rows.forEach((row) => {
  const h = row.offsetHeight;
  row.style.height = h + 8 + 'px';
});

// ✓ 先读完所有高度，再统一写入
const heights = rows.map((row) => row.offsetHeight);
rows.forEach((row, i) => {
  row.style.height = heights[i] + 8 + 'px';
});
rAF 规则：回调里只提交下一帧要做的更新；布局属性集中读、样式变化集中写；动画属性优先 transform/opacity。

54.5 防抖与节流：输入、滚动、缩放场景

输入框搜索、窗口 resize、页面滚动这类事件触发频率极高，回调里若做请求、计算或布局操作，主线程会被反复占用。防抖与节流是两类限流手段，目标相同、节奏不同。

对照项防抖 debounce节流 throttle
触发规则事件停止触发后等待 N 毫秒才执行一次每 N 毫秒最多执行一次，期间触发被合并
适用场景搜索建议、输入校验、窗口停止缩放后计算布局滚动位置上报、拖拽跟随、连续刷新进度
体感差异停止操作后才有结果，避免中途频繁请求过程中持续有反馈，不希望完全静默
 
// 防抖：延迟期内再次触发就重置计时
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const onSearch = debounce((keyword) => {
  fetchSuggestions(keyword);
}, 300);

input.addEventListener('input', (e) => onSearch(e.target.value));
// 节流：固定间隔内最多执行一次
function throttle(fn, interval) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

const onScroll = throttle(() => {
  reportScrollPosition(window.scrollY);
}, 200);

// passive: true 表示不调用 preventDefault，滚动监听不阻塞主线程
window.addEventListener('scroll', onScroll, { passive: true });
滚动与触摸监听加上 { passive: true }：浏览器知道回调不会阻止默认滚动行为，可以提前优化滚动响应；需要 preventDefault 的场景不要加 passive。

54.6 排查工具与卡顿清单

定位卡顿用 Chrome DevTools 的 Performance 面板录制一次慢操作：观察主线程任务条是否出现超过 50ms 的长任务、火焰图中紫色（布局）与绿色（绘制）是否占比异常、帧率是否跌破 60fps。对照下面清单逐项排除：

卡顿现象排查方向
动画一卡一卡检查是否改了 top/left/width 等布局属性；换成 transform/opacity；确认主线程是否有长任务挤占
滚动时页面掉帧滚动回调是否未节流；是否在回调里读写布局属性；监听是否缺少 passive
长列表滚动白屏或卡顿DOM 数量是否失控（第 50 章虚拟化）；是否启用 content-visibility；key 是否稳定
输入框响应迟钝搜索请求是否未防抖；每次输入是否触发整树重渲染（第 48、49 章）
切换标签页后动画堆积是否用 setInterval 驱动动画；改用 rAF 并在卸载时取消
大面积阴影/渐变闪烁绘制成本过高；简化阴影范围、减少重绘区域
工具边界：React 组件层重复渲染用第 47 章 Profiler；浏览器主线程与布局绘制用 Performance 面板；两者结论互相印证，不要只看其中一个面板就下结论。
本章收口：长列表控制 DOM 规模与渲染成本，动画控制在合成层，高频事件用防抖节流限流；所有手段都要在 Performance 面板上看到帧时间改善才算完成。

✓ 本章小结

要点一句话
渲染管线JS → 样式 → 布局 → 绘制 → 合成；布局最贵，合成最便宜
长列表补充content-visibility 跳过视口外渲染，contain 隔离布局，key 稳定复用节点
动画属性位移缩放用 transform，显隐用 opacity；避免高频改布局属性；will-change 克制
rAF与刷新节奏对齐，后台暂停；先批量读布局、再批量写样式，避免布局抖动
防抖节流防抖停手后执行一次（搜索），节流固定间隔执行一次（滚动上报）
排查Performance 面板看长任务、布局绘制占比与帧率，与 Profiler 结论互证
