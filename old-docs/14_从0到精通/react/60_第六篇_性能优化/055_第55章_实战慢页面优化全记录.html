55.1 案例背景：一个慢在哪的订单页

案例是一个内部后台的订单列表页：顶部搜索框可按关键词筛选订单，下方是表格化的订单卡片列表，右侧有金额汇总面板，页面内还挂着一个重型图表组件。反馈的问题有三条：

  • 搜索框每输入一个字符，页面明显卡顿、停顿一下才更新；
  • 滚动长列表时掉帧，偶发页面无响应；
  • 首次打开页面等待较久，才出现可操作界面。
先声明：本章出现的耗时、条数、体积数字均为示意口径，用于讲清排查流程；真实项目必须以第 47 章工具录制到的数据为准，不套用本章数字下结论。
本章写法上刻意还原真实排查顺序：先列症状，再用工具取证，最后才选择对应章节的手段；阅读时建议对照第六篇各章标题，把每一类问题映射回原知识点。

页面结构（优化前概念模型）：<OrderPage /> 持有搜索关键词与原始订单数据，内部依次渲染 <SearchBar />、<OrderList />、<SummaryPanel /> 与 <RevenueChart />；订单数据约两千条，搜索时在页面内完成筛选、排序与金额聚合。

排查纪律：不要拿到需求就开始拆组件、加 memo。先按第 47 章流程复现问题、录制数据，再决定每一刀砍在哪里。

55.2 度量定位：Profiler 与 Performance 双面板

复现动作固定为：输入关键词 → 等待列表更新 → 滚动到列表中段 → 返回顶部。分别用 React Profiler 与 Chrome Performance 面板录制两次：

  1. Profiler 排名图：输入一次关键词，OrderList 与其内部卡片组件重复渲染次数最高，SummaryPanel 并未使用新关键词却跟着重渲染；
  2. Performance 面板：输入回调期间主线程出现长任务，样式计算与布局占比偏高；滚动期间有周期性任务阻塞帧节奏；
  3. 包体积报告：图表库被打进首屏 bundle，与订单列表代码同包下载；
  4. 规则复核：搜索回调为内联箭头函数，传给列表组件的配置对象每次新建。
问题编号定位证据归因对应手段（章节）
问题一：整树无辜重渲染SummaryPanel 未用新关键词也被带动；Profiler 显示整棵子树重复执行搜索 state 放在父组件，父渲染带动全部子组件（第 48 章）状态下沉 + memo 包裹展示组件
问题二：列表 DOM 规模失控两千条记录一次性挂载，布局成本高，滚动掉帧全量 map 渲染，无虚拟化（第 50 章）react-window 虚拟化列表
问题三：派生计算与引用不稳定筛选、排序、聚合在每次渲染重复执行；配置对象、回调引用每次新建导致 memo 失效缺少 useMemo/useCallback（第 49 章）昂贵派生记忆化，引用稳定化
问题四：首屏代码与高频事件开销图表库进首包；滚动、回调未限流未做代码分割（第 51 章）；事件未防抖节流（第 54 章）组件级懒加载 + 防抖 + passive 滚动监听

55.3 问题一：状态下沉与 memo 屏障

优化前，关键词 state 位于 OrderPage：输入触发父组件渲染，OrderList、SummaryPanel、RevenueChart 默认跟着执行，即使它们并不读取关键词。优化思路是：把只跟搜索框相关的 state 下沉到搜索组件，让父组件无需每次输入都重渲染；需要随筛选结果变化的部分，再通过 props 显式传递。

// 优化前：父组件持有 keyword，输入带动整棵子树
export default function OrderPage() {
  const [keyword, setKeyword] = useState('');

  return (
    <main>
      <SearchBar keyword={keyword} onChange={setKeyword} />
      <OrderList orders={orders} keyword={keyword} />
      <SummaryPanel orders={orders} />
      <RevenueChart orders={orders} />
    </main>
  );
}
// 优化后：关键词由 OrderList 内部管理，SummaryPanel 不再被输入带动
const SummaryPanel = memo(function SummaryPanel({ orders }) {
  return <aside>合计金额：{orders.reduce(sum, 0)}</aside>;
});

export default function OrderPage({ orders }) {
  return (
    <main>
      <OrderList orders={orders} />
      <SummaryPanel orders={orders} />
      <RevenueChart orders={orders} />
    </main>
  );
}
状态下沉的判断标准：哪些组件真正需要这个 state，就把 state 放到它们最近的公共父组件；不需要的组件不进入 state 变化的传播路径。这比给所有子组件套 memo 更根本。

展示型卡片组件随后包上 memo，配合 55.5 的引用稳定手段，让 props 未变的行组件跳过渲染。

55.4 问题二：列表虚拟化接入

两千条订单的 DOM 规模是滚动掉帧的主因。按第 50 章方案，把全量 map 替换为 FixedSizeList，行高固定，订单数据通过 itemData 传入；筛选结果变化时 itemCount 自然跟随。

import { FixedSizeList } from 'react-window';
import { memo } from 'react';

const OrderRow = memo(function OrderRow({ index, style, data }) {
  const order = data[index];
  return (
    <div style={style} className="order-row">
      <span>{order.id}</span>
      <span>{order.customer}</span>
      <span>{order.amount}</span>
    </div>
  );
});

function OrderList({ orders }) {
  return (
    <FixedSizeList
      height={520}
      width="100%"
      itemCount={orders.length}
      itemSize={56}
      itemData={orders}
    >
      {OrderRow}
    </FixedSizeList>
  );
}
接入检查接入虚拟化后复核三条铁律（第 50 章）：行根节点透传 style、key 使用订单业务 id、若后续支持展开行高改为 VariableSizeList 并在高度变化后调用 resetAfterIndex。

列表外层容器补充 content-visibility 与布局包含，为页面内其他非可视区域减少渲染压力：

.order-row {
  content-visibility: auto;
  contain-intrinsic-size: auto 56px;
}

.summary-panel {
  contain: layout paint;
}

55.5 问题三：派生计算记忆化与引用稳定

筛选、排序、金额聚合原本在每次渲染时重新执行；配合 memo 子组件时，内联配置对象与内联回调又让浅比较始终不相等。按第 49 章边界处理：昂贵派生用 useMemo，传给 memo 子组件的回调用 useCallback。

import { useMemo, useCallback } from 'react';

function OrderList({ orders, keyword }) {
  // 昂贵派生：筛选 + 排序 + 聚合只在依赖变化时重算
  const visibleOrders = useMemo(
    () => orders
      .filter((o) => o.customer.includes(keyword))
      .sort((a, b) => b.amount - a.amount),
    [orders, keyword]
  );

  const summary = useMemo(
    () => visibleOrders.reduce((sum, o) => sum + o.amount, 0),
    [visibleOrders]
  );

  // 回调引用稳定，配合 memo 行组件的浅比较
  const handleToggle = useCallback((id) => {
    setExpandedIds((prev) => {
      const next = new Set(prev);
      if (next.has(id)) next.delete(id); else next.add(id);
      return next;
    });
  }, []);

  return (
    <OrderRowList
      orders={visibleOrders}
      summary={summary}
      onToggle={handleToggle}
    />
  );
}
记忆化判断本案例取值理由
筛选排序结果useMemo遍历两千条记录，计算成本可观，下游列表直接使用
聚合金额useMemo依赖 visibleOrders，避免每次渲染重复 reduce
行展开回调useCallback传给 memo 行组件，引用稳定才能跳过重渲染
普通样式常量提到组件外静态配置不需要 useMemo，避免依赖数组噪音
复盘时对照第 49.3 节：不要为简单拼接、仅内部使用的值套 useMemo；本案例记忆化的对象都满足"计算昂贵"或"下游引用敏感"两条之一，其余派生保持直接计算。

55.6 问题四：代码分割与高频事件限流

重型图表组件与订单列表同包，首屏必须下载完整图表库。按第 51 章做组件级懒加载，列表先出主体，图表在需要时再下载；搜索输入加防抖，滚动监听使用 passive: true。

import { lazy, Suspense, useEffect, useState } from 'react';

const RevenueChart = lazy(() => import('./RevenueChart'));

export default function OrderPage({ orders }) {
  const [keyword, setKeyword] = useState('');
  const debouncedKeyword = useDebounced(keyword, 300);

  return (
    <main>
      <SearchBar value={keyword} onChange={setKeyword} />
      <OrderList orders={orders} keyword={debouncedKeyword} />
      <Suspense fallback={<div className="chart-loading">图表加载中…</div>}>
        <RevenueChart orders={orders} />
      </Suspense>
    </main>
  );
}
// 防抖 Hook 概念实现：300ms 内连续输入只取最后一次值
function useDebounced(value, delay) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return debounced;
}

// 滚动上报：节流 + passive，不阻塞滚动主线程
window.addEventListener('scroll', throttle(reportScroll, 200), { passive: true });
衔接说明：防抖与节流实现、rAF 动画规则见第 54 章；代码分割与错误边界配合见第 51 章，图表加载失败时应由错误边界给出重试入口。

55.7 复测对比与经验总结

全部改动完成后，用同一套复现动作重新录制，对比基线与优化后的指标。下表数字为示意，仅用于说明记录格式，不代表真实项目基准：

指标（示意）优化前基线优化后复测对应改动
输入一次关键词的提交耗时较高（整树重渲染）明显下降状态下沉 + memo 屏障
同时挂载的列表 DOM 节点约两千个稳定在可视区数量级虚拟化 + content-visibility
筛选排序重复执行次数每次渲染重复依赖变化才重算useMemo 记忆化
首屏 bundle 体积含重型图表库图表 chunk 独立按需下载组件级懒加载
滚动帧节奏周期性掉帧主线程任务被限流节流 + passive + 布局隔离

复盘沉淀出的经验清单：

  1. 度量先行：没有 Profiler 排名图与 Performance 长任务证据，不动手改组件结构；
  2. 最小改动：先状态下沉，再 memo，再记忆化；顺序反了会留下大量无效包裹；
  3. 复测收尾：每改一类问题都回到同一复现动作录制，指标不改善就回退方案；
  4. 权衡可读性：记忆化代码增加依赖追踪成本，收益不明显的包裹在复盘时主动删除；
  5. 分层归因：组件层重渲染看 Profiler，主线程与布局看 Performance，首屏体积看包报告，互不替代。
本篇主线收束：Profiler 找问题，memo/useMemo/useCallback 控重复渲染，虚拟化控 DOM 规模，代码分割控首屏体积，动画与事件限流控主线程——它们分别解决不同层的问题，组合使用才形成完整优化闭环。
最后提醒性能优化没有终点：新功能接入后重新度量，基线指标随用户规模与数据量变化需要持续观察；不要把一次性优化当成永久结论。
