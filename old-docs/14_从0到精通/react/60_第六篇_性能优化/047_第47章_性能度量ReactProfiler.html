47.1 先度量，再优化

性能优化最常见的失败方式，是在没有度量数据的情况下凭经验动手：先给所有组件套上 memo、把所有计算塞进 useMemo，结果代码可读性下降、引用问题变多，页面却没有明显变快。React 官方对优化的建议顺序同样是：先找出瓶颈在哪，再决定用哪一章的手段。

本章是第六篇的"测量仪器"章节：第 48 章的 memo、第 49 章的 useMemo/useCallback、第 50 章的虚拟化，都是"药"，而 Profiler 与 DevTools 是"检查单"。没有检查单就开药，属于过早优化。

一次完整的性能闭环如下：提出假设 → 用工具录制复现 → 定位最耗时的组件与提交 → 做最小改动 → 复测对比 → 确认指标改善。React 生态里这套闭环主要由三类工具完成：

  • React Profiler（内置组件 + DevTools 面板）：度量 React 渲染与提交阶段的耗时；
  • Chrome Performance 面板：度量主线程长任务、布局、绘制、脚本执行等浏览器层面成本；
  • Web Vitals：度量面向用户体验的宏观指标（LCP、INP、CLS 等）。

图 47-1 性能优化闭环：度量驱动，复测收尾

原则：优化前先有基线数据，优化后必须有复测数据；没有前后对比数字的"优化"只是一次代码重构。

47.2 Profiler 组件：包裹与回调

React 内置了 <Profiler> 组件，可以包裹任意一段子树。每当这段子树发生一次提交（挂载或更新），React 会在渲染与提交完成后调用传入的 onRender 回调，并把耗时数据交给你。它不要求你停止应用、不破坏任何逻辑，适合在开发环境里定点采集。

import { Profiler } from 'react';

// id：这段子树的标识，同一次提交里可能有多个 Profiler，靠 id 区分
// onRender：渲染与提交完成后被调用的回调
function onRender(id, phase, actualDuration, baseDuration, startTime, commitDuration) {
  console.log('[Profiler]', {
    id,
    phase,                 // 'mount' 首次挂载 | 'update' 后续更新
    actualDuration,        // 渲染这段子树本次花费的毫秒数
    baseDuration,          // 假设不做任何记忆化时的估算耗时
    startTime,             // React 开始本次渲染的时间戳
    commitDuration,        // 提交阶段花费的毫秒数
  });
}

export default function OrderPage() {
  return (
    <Profiler id="order-page" onRender={onRender}>
      <OrderList />
      <OrderSummary />
    </Profiler>
  );
}

id 的作用是区分同一页面上多个被包裹区域：你可以把 <Profiler> 只包在某个表格或某个面板外，让日志里一眼看出慢在哪一块。包裹位置的选择本身就是定位动作——先怀疑哪里，就先包哪里。

注意：Profiler 可以嵌套使用，外层 Profiler 的耗时包含内层子树；不要把内层组件的耗时重复计入外层，否则会得到偏大的结论。

把日志攒起来而不是每次打印

交互过程中回调会触发很多次，直接 console.log 容易被刷屏淹没。更实用的做法是把数据收集到数组里，操作结束后统一汇总：

// 在模块作用域或页面组件外维护一份采集表
const samples = [];

export function recordRender(id, phase, actualDuration, baseDuration, commitDuration) {
  samples.push({ id, phase, actualDuration, baseDuration, commitDuration, time: Date.now() });
}

export function reportSlow(thresholdMs) {
  const slow = samples.filter((s) => s.actualDuration > thresholdMs);
  console.table(slow);
  // 按组件 id 汇总平均耗时，找出反复慢的区域
  const avg = {};
  for (const s of samples) {
    avg[s.id] = avg[s.id] || { total: 0, count: 0 };
    avg[s.id].total += s.actualDuration;
    avg[s.id].count += 1;
  }
  Object.entries(avg).forEach(([id, v]) =>
    console.log(id, '平均耗时(ms) =', (v.total / v.count).toFixed(2))
  );
}
与 DevTools 的关系：代码里手写 <Profiler onRender> 适合做长期采集、埋点上报；日常排查更常用的是 React DevTools 的 Profiler 面板（见 47.3），两者底层度量的是同一套提交数据。

47.3 React DevTools Profiler 面板怎么用

安装 React DevTools 浏览器扩展后，页面上会出现 Components 与 Profiler 两个面板。Profiler 面板的工作方式是：点击录制按钮 → 在页面上复现操作 → 停止录制，DevTools 会把这段时间内 React 的每一次提交整理成可视化视图。

  1. 打开 DevTools 的 Profiler 标签，点击圆形录制按钮；
  2. 在页面上完整复现慢操作（滚动、筛选、切换标签、输入搜索词）；
  3. 停止录制，左侧出现本次录制的提交列表，右侧是可视化视图；
  4. 先看排名图定位"谁最耗时"，再回到火焰图看"一次提交里谁在谁里面"。
视图展示内容适合回答的问题
火焰图（Flame Chart）一次提交中组件树的渲染嵌套关系，色块宽度表示耗时这次提交里谁渲染了谁？子树里哪一段最宽？
排名图（Ranked Chart）把组件按本次录制期间累计渲染耗时从高到低排序反复优化谁收益最大？哪些组件耗时异常突出？
组件树（Components）组件层级与当前 props、state、hooks 状态组件内部状态是什么？配合"为什么渲染"查看重渲染原因
交互图（Interactions）本次录制中关联的交互（如点击、输入）与其时间线用户的哪个动作触发了这一串提交？

Components 面板设置里还可以开启 "Why did this render?"（为什么渲染）开关：它会在每次渲染时用颜色高亮该组件是因为 props 变化、state 变化、父组件渲染，还是 Context 变化而更新。这正好对应第 48 章判断 memo 是否有效的依据。

# 开发环境必须使用未压缩的 React 开发版，Profiler 数据才完整
# 本地 npm run dev / npm start 默认即为开发构建；
# 在线演示站点若用了生产构建，DevTools 会提示 Profiling 不可用。
npm run dev
注意录制环境Profiler 数据反映的是开发构建的运行状态，开发版 React 包含额外的检查与警告，渲染耗时普遍高于生产构建。本章工具用来定位"哪个组件相对更慢、为什么重复渲染"，不要把开发版毫秒数当成生产性能结论。

47.4 onRender 回调参数逐项解读

手写 onRender 时，回调会收到一组固定参数。理解每个参数回答什么问题，才能把日志读成结论：

参数含义读它时关注什么
id被包裹区域在代码里声明的标识多次录制后按 id 分组统计，定位最慢区域
phasemount（首次挂载）或 update（后续更新）区分"首屏慢"与"交互后慢"两类问题
actualDuration本次提交中渲染该 Profiler 子树实际花费的毫秒数最常用来排序的核心指标，代表真实成本
baseDuration估算值：假设整棵子树不做任何记忆化（无 memo、无 useMemo）时的渲染耗时与 actualDuration 对比，判断现有记忆化带来了多少节省
startTimeReact 开始本次渲染的时间戳（页面计时起点）配合交互时间线判断提交先后顺序
commitDuration本次提交阶段（把 Fiber 变更写入 DOM）花费的毫秒数渲染快但 commitDuration 偏高，说明 DOM 变更本身重，方向在布局/节点数量
interactions与本次更新关联的交互集合在 DevTools 交互视图中用于动作归因
rootType / type根类型与提交类型的补充元信息排查特殊根（如 Suspense、水合）时参考
最有价值的一组对比是 actualDuration 与 baseDuration：如果两者很接近，说明记忆化几乎没起作用；如果 actualDuration 明显小于 baseDuration，说明现有 memo/useMemo 已经拦下了大部分重复渲染。
function onRender(id, phase, actualDuration, baseDuration) {
  // 记忆化节省比例：baseDuration 是"不记忆化"的估算基线
  const saved = baseDuration - actualDuration;
  const ratio = baseDuration > 0 ? Math.round((saved / baseDuration) * 100) : 0;
  console.log(`${id} [${phase}] 实际 ${actualDuration.toFixed(2)}ms，` +
    `基线 ${baseDuration.toFixed(2)}ms，记忆化约节省 ${ratio}%`);
}

需要强调：baseDuration 是 React 根据当前子树结构估算的参考值，不是真实跑出来的对照组；它适合相对比较，不适合作为对外汇报的精确数字。

47.5 其他度量手段与分工

React Profiler 只覆盖 React 自己的渲染与提交阶段。页面卡顿的原因可能在浏览器主线程、网络、布局绘制等任何环节，因此要知道其他工具度量的边界：

工具 / 指标度量范围典型用途
React Profiler（组件 + DevTools）React 渲染耗时、组件重渲染次数与原因、提交阶段耗时定位组件级重复渲染与子树瓶颈（本章主线）
Chrome Performance 面板主线程任务时间线、脚本执行、布局（Layout）、绘制（Paint）、合成、长任务判断卡顿来自 JS 计算还是布局绘制；看帧间隔是否掉帧
performance.mark / measure在代码任意位置打时间戳，测量自定义代码段耗时测量某个排序、筛选、深拷贝的真实毫秒数
Web Vitals（LCP、INP、CLS）面向用户体验的宏观指标：最大内容绘制、交互到下次绘制、累积布局偏移评价页面首屏、交互响应、视觉稳定度，适合线上监控
console.time / timeEnd临时测量两段代码之间的耗时开发期快速估算，不用于线上结论

代码内打点：performance.mark 与 measure

// 在昂贵计算前后打标，measure 汇总成一条性能条目
performance.mark('filter-start');

const filtered = users.filter((u) => u.status === 'active');
const sorted = filtered.sort((a, b) => b.score - a.score);

performance.mark('filter-end');
performance.measure('筛选+排序耗时', 'filter-start', 'filter-end');

// 在 DevTools Performance 面板或 Performance 面板的 Timings 中可以看到该条目
const entries = performance.getEntriesByName('筛选+排序耗时');
console.log(entries[0].duration.toFixed(2), 'ms');
指标口径：INP（Interaction to Next Paint）是当前 Web Vitals 中衡量交互响应的核心指标，替代了早期的 FID；学习与线上监控请以官方 Web Vitals 文档口径为准，不在本书展开。
分工原则：Profiler 告诉你 React 组件层慢在哪，Performance 面板告诉你浏览器主线程慢在哪，Web Vitals 告诉你用户主观感受如何。三者结论要互相印证，单一工具的读数不足以说明问题。

47.6 度量流程与常见误区清单

把工具用对，比记住工具参数更重要。下面是一次排查中应遵守的顺序与常见坑：

常见误区正确做法
没复现就录制：页面空闲时点开始录，录到的都是空闲提交先进入慢页面、完成复现动作后再开始录制；卡顿动作必须出现在录制区间内
用开发版毫秒数直接对比线上指标开发版只做相对定位；线上结论用生产构建配合 Web Vitals 或 RUM 采集
把"组件渲染次数多"等同于"性能差"次数多但每次耗时很低并不构成瓶颈；先看 actualDuration 排序，再看是否产生了昂贵子树
一次录制里混杂多个操作，事后分不清归属一次录制只复现一个动作；动作之间留停顿，便于在提交列表里切分
优化后不回测，凭感觉宣布"快了"保留优化前基线数据，用同一套操作复测，对比 actualDuration 与主观帧率
在 Profiler 日志里看到 mount 慢就先调 memomount 慢通常与子树规模、初始数据量相关，优先考虑虚拟化（第 50 章）与代码分割（第 51 章）
生产环境注意React 默认生产构建关闭了内部 Profiling 能力；若要在真实用户环境采集渲染数据，需要使用带 profiling 的构建并承担其性能开销，是否启用应由业务收益决定，不要在页面里默认包裹大量 Profiler 埋点。
本章结论先行：后续四章的优化手段，都要用本章的工具在动手前定位、在动手后复测。把"度量闭环"变成肌肉记忆，比背下任何优化 API 都重要。
