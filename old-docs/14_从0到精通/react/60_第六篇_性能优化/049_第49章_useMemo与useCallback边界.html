49.1 两个 Hook 各自缓存什么

useMemo 接收一个计算函数与依赖数组：依赖不变时，返回上一次缓存的计算结果；依赖变化时重新计算并缓存。useCallback 接收一个函数与依赖数组：依赖不变时，返回上一次缓存的函数引用；依赖变化时返回新函数。

import { useMemo, useCallback } from 'react';

// useMemo：缓存"值"
const sortedList = useMemo(
  () => users.filter(u => u.active).sort((a, b) => b.score - a.score),
  [users]
);

// useCallback：缓存"函数引用"
const handleSelect = useCallback((id) => {
  setSelectedId(id);
}, []);

二者在底层是等价的：useCallback(fn, deps) 等价于 useMemo(() => fn, deps)——useMemo 缓存一个返回函数的值，效果就是缓存函数引用。区别只在语义命名：需要稳定函数引用时用 useCallback，读起来更清楚。

对照项useMemouseCallback
缓存对象计算结果（值、对象、数组）函数定义（引用）
返回内容计算函数的返回值传入的函数本身
典型用途昂贵派生计算、稳定对象/数组引用稳定回调引用，传给 memo 子组件或其他 Hook 依赖
等价写法—useMemo(() => fn, deps)
不要用于简单字符串拼接、普通条件判断只在组件内部调用、不向下传递的事件函数

49.2 useMemo 什么时候用

官方建议：当计算本身昂贵，且依赖没有变化时，缓存结果才有意义。具体到 React 组件里，值得用 useMemo 的场景有三类：

① 昂贵的派生计算

const reportRows = useMemo(() => {
  // 数据量大时：筛选、分组、排序、聚合都在这一轮完成
  return records
    .filter((r) => r.dept === dept)
    .sort((a, b) => b.amount - a.amount)
    .map((r) => ({ ...r, total: r.qty * r.price }));
}, [records, dept]);

② 给 memo 子组件传稳定的对象 / 数组引用

const chartConfig = useMemo(() => ({
  theme: 'forest',
  series: seriesData,
  legend: { show: true },
}), [seriesData]);

// ChartPanel 已用 memo 包裹；配置对象引用稳定，屏障才能生效
return <ChartPanel config={chartConfig} />;

③ 作为其他 Hook 的依赖，避免下游反复执行

const queryKey = useMemo(() => ['orders', dept, status], [dept, status]);

useEffect(() => {
  // queryKey 引用稳定，effect 不会因数组字面量每次新建而反复触发
  fetchOrders(queryKey);
}, [queryKey]);
判断标准：这个值的计算贵不贵？它的引用稳不稳定，会不会影响下游 memo 或 Hook 依赖？两个问题有一个成立，才考虑 useMemo。
不要用 useMemo 缓存一个每次都需要全新对象的派生结果：如果下游只读取内容、不比较引用，缓存旧对象反而会在依赖遗漏时返回过期数据。派生逻辑应当始终基于当前依赖重新计算。

49.3 useMemo 什么时候不用

与值得用的场景相对，以下写法包裹 useMemo 属于负优化：

不值得用的场景原因
简单计算：字符串拼接、数值加减、条件表达式计算成本低于缓存判断与依赖比较成本，直接算即可
值只在当前组件内部使用，不传给子组件没有引用稳定性需求，缓存只是多一层状态追踪
对象/数组字面量没有被下游按引用比较下游每次都重新读取内容，引用新旧无所谓
依赖本身频繁变化缓存每次都失效，useMemo 退化为普通计算，还多一层开销
为了"规范"默认给所有派生值套上依赖数组写错的风险、阅读成本都大于收益
 
// ✗ 无意义：拼接成本极低，且没有下游引用稳定性需求
const fullName = useMemo(() => `${first} ${last}`, [first, last]);

// ✓ 直接派生
const fullName = `${first} ${last}`;
不要把 useMemo 当成"保证引用永远不变"的语义机制。React 可以在未来版本中丢弃缓存；官方口径是：useMemo 只是性能优化，不应依赖它做精确相等判断。需要稳定值时，优先把常量提到组件外部。
反模式提醒组件里出现大量 useMemo(() => ({...}), []) 时，先问自己：这些对象是不是本来就该是模块级常量？静态配置提到组件外，比记忆化更干净。

49.4 useCallback 什么时候用

useCallback 的价值只体现在"函数引用需要稳定"的下游。典型场景：

场景为什么需要稳定引用
传给 memo 包裹的子组件作为事件回调引用每次新建会导致 memo 浅比较失败，子组件照常重渲染（第 48 章）
作为其他 Hook 的依赖数组项引用变化会带动下游 effect / memo 反复执行
传给需要订阅外部系统的 effect（事件监听、定时器）回调引用稳定，effect 才不会反复解绑重绑
库 API 内部按引用缓存或去重外部实现要求引用稳定时配合使用
 
import { memo, useCallback } from 'react';

const Toolbar = memo(function Toolbar({ onRefresh }) {
  return <button onClick={onRefresh}>刷新</button>;
});

function Dashboard() {
  const [version, setVersion] = useState(0);

  // 依赖为空：setState 的 setter 引用稳定，回调跨渲染保持同一引用
  const handleRefresh = useCallback(() => {
    setVersion((v) => v + 1);
  }, []);

  return <Toolbar onRefresh={handleRefresh} />;
}

反过来，事件处理函数只在当前组件 JSX 里直接 onClick={handleClick} 使用、不向下传递时，不需要 useCallback：当前组件每次都会渲染，函数新建与否不影响任何下游比较。

useCallback 的决策顺序：先看函数有没有传给 memo 子组件、有没有进别的 Hook 依赖、有没有被订阅系统持有。三者都不沾边，就不要包。

49.5 依赖数组与缓存失效规则

两个 Hook 的依赖比较规则与 useEffect 一致：逐个用 Object.is 比较新旧依赖，全部相等才复用上一次缓存；任何一项不等就重新计算 / 重建函数。

依赖类型比较规则与注意点
原始值（number/string/boolean/null/undefined）按值比较；值相等即命中缓存
对象 / 数组 / 函数按引用比较；父组件每次新建字面量都会导致缓存失效
state 与 props正常写入依赖；setState 的 setter 引用稳定，不需要写
组件外部常量不需要写进依赖；模块级常量引用恒定
缺失依赖会读到旧闭包值；交给 eslint-plugin-react-hooks 的 exhaustive-deps 规则检查
 
// 依赖 users：users 引用不变 → 复用上一次排序结果
// users 引用变化（新数组、新对象）→ 重新排序并缓存
const sorted = useMemo(
  () => [...users].sort((a, b) => b.score - a.score),
  [users]
);

// 依赖 query：query 变了才重建回调；否则保持旧引用
const fetchList = useCallback(async () => {
  const res = await fetch(`/api/list?q=${query}`);
  return res.json();
}, [query]);
记忆化失效不是错误，而是规则：依赖变了就必须重新计算。真正要排查的是"依赖引用为什么每次都变"——回到第 48.5 节的 props 不稳定清单处理。
闭包旧值回调或计算函数内部读取了某个外部值却没写进依赖，缓存会一直返回旧闭包结果。这类问题与 useEffect 的陈旧闭包同源：把函数内引用到的响应式值全部补进依赖，再交给 lint 规则复核。
与 Vue 的对照：Vue 的 computed 自动追踪响应式依赖、无需手写依赖数组；React 的 useMemo 需要显式声明依赖，二者目标相同（缓存派生值），机制不同。

49.6 React Compiler 方向与常见坑清单

随着 React 工具链发展，React Compiler 可以在编译阶段自动分析组件并完成记忆化，在许多场景下开发者不再需要手写 memo/useMemo/useCallback。这是官方推荐的演进方向；本书当前阶段仍要求掌握手写边界，因为存量项目与线上版本普遍需要手动判断。遇到新项目评估编译器时，以官方发布状态与文档为准，不在本章展开配置细节。

常见坑排查与正确写法
useMemo 包了简单计算，依赖一长串删掉包裹，直接派生；把依赖维护成本留给真正昂贵的计算
useCallback 包了只在内部使用的函数移除包裹；只有向下传递或进入下游依赖时才需要
依赖里放了每次新建的对象上游用 useMemo 稳定对象，或只提取原始字段作为依赖
依赖数组漏写变量，读到旧值开启 exhaustive-deps，按提示补全；不要用 eslint-disable 压掉
把缓存结果用于精确相等判断改用模块级常量或 ref；不要假设 useMemo 引用恒定不变
嵌套使用多层 useMemo 才让引用稳定考虑状态分层：把派生逻辑移到数据层，减少组件内依赖网络
本章收口：useMemo 管值、useCallback 管函数，边界由"下游是否需要引用稳定 / 计算是否昂贵"决定；依赖规则与 effect 完全一致，性能收益要回到第 47 章的 Profiler 上复测确认。

✓ 本章小结

要点一句话
分工useMemo 缓存计算值，useCallback 缓存函数引用，二者等价
useMemo 适用昂贵派生、稳定对象引用、作为下游 Hook 依赖
useCallback 适用传给 memo 子组件、进入其他 Hook 依赖、被订阅系统持有
不适用简单计算、仅内部使用、依赖频繁变化、静态配置应提到组件外
依赖规则Object.is 逐键比较，依赖变则缓存失效，缺失依赖交 lint 检查
性质性能优化而非语义保证；React Compiler 是后续自动记忆化方向
