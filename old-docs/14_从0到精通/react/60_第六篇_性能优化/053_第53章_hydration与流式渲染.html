53.1 hydration 是什么

第 52 章已经讲过：SSR/SSG 让浏览器在初始 HTML 里就看到内容。但这份静态 HTML 还不能点击、不能响应输入——它需要 React 在浏览器端重新"认得"这棵 DOM 树，把事件监听、组件状态、更新逻辑绑定上去。这个把服务端 HTML 接管为 React 应用的过程，就叫 hydration（水合）。

水合与 CSR 的首次渲染看似相似，实则关键不同：

对照项CSR 首次渲染hydration 水合
初始 DOM空容器，React 从零创建节点服务端 HTML 已存在，React 沿现有节点绑定
首要目标生成界面结构建立内部 Fiber 树、绑定事件与状态，使后续更新生效
初始渲染校验无服务端产物可对照客户端首次渲染结果必须与服务端 HTML 一致，否则 mismatch 告警
入口 APIcreateRoot + renderhydrateRoot
 
// SSR/SSG 页面的客户端入口：在已有 HTML 上完成水合
import { hydrateRoot } from 'react-dom/client';
import App from './App';

hydrateRoot(
  document.getElementById('root'),
  <App initialData={window.__INITIAL_DATA__} />
);
API 版本口径：React 18 起客户端水合入口为 hydrateRoot（来自 react-dom/client）；旧版 react-dom 的 hydrate 已不再推荐使用。新项目统一使用 hydrateRoot。
一句话理解水合：HTML 负责"被看见"，JS 负责"被操作"；水合就是把静态 HTML 转成有状态、可交互的 React 树的过程。

53.2 水合成本与一次性水合问题

水合并不是"点一下按钮绑定事件"那么便宜：React 要在浏览器端重新执行整棵组件树的初始渲染、校验现有 DOM、构建 Fiber 结构、挂上事件系统。整棵树一次性完成水合时，用户虽然看到了 HTML，却要等 JS 下载、执行与整树水合结束后才能交互——这段空档表现为"看着有内容，点了没反应"。

水合阶段最常见的错误是 hydration mismatch：客户端首次渲染出的结构、文本与服务端 HTML 对不上，React 无法把事件正确绑定到现有节点。开发环境会输出 mismatch 警告，严重时会丢弃服务端 HTML 重新渲染。

// ✗ 服务端与客户端各算一次 Date.now()，两端结果通常不同
function Header() {
  const now = new Date();
  return <div>当前时间：{now.toLocaleTimeString()}</div>;
}

// ✗ 随机 id 两端不一致，节点属性文本对不上
function Card() {
  return <div data-id={Math.random()} />;
}
水合期间不要读取 window、document 或调用浏览器专有 API：服务端没有这些对象，初始渲染阶段条件分支就会与客户端分叉，直接造成 mismatch。浏览器相关逻辑推迟到 useEffect 或事件处理函数中执行。
成本来源表现与方向
JS bundle 下载与解析水合必须先等脚本就绪；代码分割（第 51 章）直接减少首脚本体积
整树初始渲染执行组件函数与构造逻辑全部在浏览器跑一遍；减少首屏组件复杂度与派生计算
事件系统绑定节点越多绑定成本越高；简化首屏 DOM 规模（第 50 章虚拟化）有帮助
长任务阻塞主线程水合过程被拆成多段才能让交互优先响应，见 53.3 选择性水合

53.3 选择性水合与水合优先级

React 18 的并发能力让水合不必"整树一次完成"：选择性水合（selective hydration）指 React 按用户最可能交互的优先级水合节点，把非关键区域推迟；用户点击某个区域时，React 优先水合该区域，被点击的内容能尽快响应。

对照项一次性水合选择性水合（React 18）
顺序整棵树从上到下绑定交互按交互优先级分批，先处理关键交互区域
主线程占用整段长任务阻塞后续动作可中断、可分段，让出主线程响应优先操作
触发方式脚本就绪后顺序执行结合流式 HTML 与 Suspense 边界，由框架与并发调度协同完成
开发侧重保证两端产物一致即可合理划分 Suspense 边界，标识关键交互区域
注意边界：选择性水合是 React 内核调度能力，实际页面是否生效、边界如何声明，仍由 SSR 框架（如 Next.js）在服务端下发与客户端配置中编排；本章只建立概念模型，不展开框架配置细节。
不要自行实现水合调度开发者通常不需要、也不应该手动拆分水合过程；页面是否能利用选择性水合，取决于框架的 SSR 输出与组件边界划分。强行在客户端分段挂载已水合的 HTML，容易造成事件绑定错乱。

53.4 流式 SSR：分块下发与 Suspense 边界

传统 SSR 用 renderToString 把整页 HTML 拼成一个字符串再返回：慢数据（接口、图片信息）会拖住整页输出。renderToPipeableStream 支持流式下发：先把已就绪的骨架与首块 HTML 推给浏览器，未就绪部分用 Suspense 边界标记占位，等内容准备好再分块追加，配合选择性水合完成交互绑定。

流式的核心收益：慢数据不再阻塞整页输出；骨架与关键内容先到达浏览器完成首屏绘制，未就绪区域保持占位，就绪后追加替换并完成水合。
// 服务端概念示例：流式渲染 + Suspense 边界
import { renderToPipeableStream } from 'react-dom/server';

function Page() {
  return (
    <main>
      <Header />
      {/* 评论区数据较慢：边界内先占位，就绪后再追加下发 */}
      <Suspense fallback={<div className="comments-skeleton" />}>
        <CommentsSection />
      </Suspense>
      <Footer />
    </main>
  );
}

export function streamPage(res) {
  const { pipe } = renderToPipeableStream(<Page />, {
    onShellReady() {
      // 首块 HTML 就绪后开始管道输出
      pipe(res);
    },
  });
}

53.5 常见 mismatch 原因与排查

mismatch 报错信息通常会指出组件与元素路径，按下面清单逐条核对，多数问题可以快速定位：

原因表现解法
时间、随机数两端各自生成文本或属性每次渲染不一致时间/随机值由服务端取数后作为初始数据下发，客户端复用；确需浏览器生成的内容挂到 effect 后再更新
服务端与客户端条件分支不同某节点一端渲染、另一端不渲染初始渲染不依赖 window 等浏览器对象；条件统一由初始数据决定
浏览器扩展修改 DOM开发环境偶发告警，节点被扩展插入属性或包裹标签在无痕窗口复现确认；避免在根节点上依赖易被扩展改动的结构
手动写入 innerHTML内容不经过 React 协调，水合时无法对应服务端渲染场景避免 dangerouslySetInnerHTML 与现有节点混用；必要时隔离在客户端组件内
格式化规则受时区/语言影响数字、日期格式两端不一致服务端与客户端使用统一 locale 与时区配置，格式结果作为初始数据下发
结构标签不合法如 <div> 嵌进 <p>，浏览器自动修正结构保证 JSX 标签嵌套符合 HTML 规范
 
// ✓ 时间由服务端取数作为 initialData 下发，两端共用同一值
export default function Header({ serverTime }) {
  return <div>当前时间：{serverTime}</div>;
}

// ✓ 浏览器端独有的状态放到 effect，初始渲染保持两端一致
function ClientOnlyPanel() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => { setMounted(true); }, []);
  if (!mounted) return <div className="placeholder" />;
  return <BrowserPanel />;
}
排查顺序先在报错堆栈里定位组件名与元素路径 → 对照服务端返回的 HTML 源码与客户端渲染产物差异 → 按上表归类是"两端取值不同""分支条件不同"还是"DOM 被外部改动"，不要直接用 suppressHydrationWarning 压掉告警了事。

53.6 度量水合体验与优化方向

水合体验要回答的问题是：用户看到内容后，多久能真正操作。相关指标与优化方向如下：

指标 / 手段关注内容优化方向
LCP最大内容何时可见（服务端 HTML 直接受益）优化服务端响应、首块 HTML 下发速度
INP交互到下次绘制的延迟，反映水合后的响应性减小首脚本体积、关键区域优先水合、避免水合期长任务
TTI（可交互时间）页面达到可稳定交互的时间拆分非关键脚本、延迟水合非关键区域
代码分割首脚本体积直接决定水合等待按第 51 章把非首屏代码拆出
组件复杂度首屏组件树越深、派生计算越多，水合越慢状态下沉、昂贵计算记忆化（第 48、49 章）
不要把"HTML 可见"等同于"水合完成"：排查交互延迟时，要看脚本执行与水合阶段的主线程任务，而不是只盯着首块 HTML 的到达时间。

实际记录水合体验时，可以按下面顺序在 Performance 面板上观察：

  1. 脚本下载与解析是否占满首屏早期时间，首脚本是否还有可拆分的部分（第 51 章）；
  2. 水合阶段主线程任务是否被切成多段，关键交互区域是否优先得到绑定；
  3. 组件初始渲染与派生计算是否重复耗时，必要时用第 48、49 章手段精简；
  4. 复测时保持同一网络条件与设备档位，对比 INP 与可交互时间的变化；
  5. 若 mismatch 告警反复出现，先回到 53.5 清单核对两端产物一致性，再讨论水合性能。
本章收口：水合是 SSR/SSG 架构里承上启下的一环——上游是第 52 章的 HTML 生成时机，下游是组件层的 memo、useMemo、虚拟化等渲染成本优化；理解 mismatch 与流式边界，才能在框架层方案里判断瓶颈位置。
