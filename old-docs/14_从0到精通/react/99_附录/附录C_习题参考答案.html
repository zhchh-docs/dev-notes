第一篇 入门与 JSX（第 1–9 章）

第 1 章 认识 React

AReact 是声明式、组件化的 UI 库。声明式指你描述"UI 应该长什么样"，由框架负责按状态渲染；组件化指 UI 拆成可复用、可组合的组件单元。它与 Vue 同为组件框架，但 React 更强调"一切皆 JS/函数"，Hooks 心智、状态由开发者用 JS 管理。
B声明式对比命令式：命令式（原生 DOM）手动写"如何一步步改 DOM"；声明式（React）只写"当前状态对应什么 UI"，React 对比并更新。React 的价值：代码与数据流更可预测、易维护，框架自动处理复杂 DOM 更新。
C把"count+1 并更新页面"分别用原生 JS（手动 getElementById 改 innerText）与 React（setState + JSX）实现；结论：原生要手动维护 DOM 变更点，React 只需改状态，由 reconcile 自动同步视图。这是声明式的核心收益。

第 2 章 JSX 与元素

AJSX 是 JavaScript 的语法扩展，编译（Babel）后变成 React.createElement 调用，最终是描述 UI 的普通 JS 对象（React 元素）。它不是字符串也不是 HTML。例：<div>hi</div> → React.createElement('div', null, 'hi')。
BJSX 中嵌入 JS 用花括号 {expr}。条件用三元/逻辑与：{ok ? <A/> : <B/>}；列表用 arr.map(...)，且每项要有稳定唯一 key。布尔 false、null、undefined 不渲染。
CJSX 防 XSS：React 默认转义所有嵌入文本，{userInput} 不会被当作 HTML 执行，因此普通场景安全。需渲染富文本时才用 dangerouslySetInnerHTML，但它会绕过转义、引入 XSS 风险，必须对内容做严格白名单清洗。

第 3 章 组件与 Props

A函数组件是接收 props 返回 JSX 的纯函数。props 是父传子的只读数据，子组件不能修改 props，只能通过回调（onEvent）通知父组件改数据。例：function Greet({ name }) { return <p>hi {name}</p> }。
Bprops 只读 + 单向数据流：数据自上而下，避免子组件随意改共享数据导致状态失控。拆分时把"数据与回调"作为 props 边界，父持状态、子纯展示，是组件复用的基础。
C受控回调模式：父组件持有 state，把 value 与 onChange 传子组件；子组件只调用 onChange(newVal)，由父更新 state。这保证数据"单一来源"，任何层级都能通过回调提升状态（状态提升，见第 19 章）。

第 4 章 状态与 useState

Aconst [count, setCount] = useState(0)。count 是当前值，setCount 是更新函数；调用 setCount 会安排一次重渲染，组件用新值重新执行函数体。初始值只在首次渲染用。
BsetState 在事件处理中异步批量执行：一次事件里的多次 set 合并为一次渲染。因此不能在 set 后立刻读新值；要基于旧值计算用函数式更新 setCount(c => c + 1)，多次调用也能正确累加。
C闭包陷阱：事件回调捕获的是该次渲染的 count 快照，若 set 前连续用旧值会丢更新。用函数式更新 setCount(c => c + 1) 让每次基于最新值计算，可正确累加（如连点 3 次得 +3）。

第 5 章 事件处理

AReact 事件是 onClick/onChange 等驼峰命名，传函数引用：onClick={handle} 而非 onClick={handle()}。绑定 this 或传参：onClick={() => handle(id)}。
BReact 用事件委托：事件统一挂到根容器，通过事件对象派发；跨浏览器统一。表单事件注意 onChange 的受控写法——值来自 event.target.value，回写到 state。
C合成事件（SyntheticEvent）是 React 对原生事件的封装，事件处理完成后被复用/释放。若在异步里读取 e.target.value 可能已失效，需先存值：const v = e.target.value 再在 setTimeout 里用。现代 React 合成事件并非"必定池化"，但先取值仍是安全习惯。

第 6 章 条件渲染与列表

A条件渲染用 &&、三元、if 分支。{loading && <Spin/>} 当 loading 为 true 渲染；为 false 时 false 不渲染。注意 0 && ... 会渲染 0，宜用 {count > 0 && ...}。
B列表用 items.map(item => <Item key={item.id} />)。key 帮助 React 协调时识别"哪些项复用、哪些移动"，稳定唯一的 key 让删除/重排不错乱。
C用数组 index 做 key 的坑：删除中间项或重排后，key 复用错位导致 state 错乱（如输入框内容串行）。key 必须用稳定唯一 id；无 id 时才退而求其次，并避免有状态子项。这是协调复用的直接后果。

第 7 章 表单与受控

A受控组件：输入框的 value 来自 state，onChange 回写 state，形成"值→UI→state"闭环。非受控用 defaultValue + ref 读取。受控让数据单一来源、便于校验。
B受控表单每个字段一个 state 或用对象 const [form, setForm] = useState({name:'',age:''})，onChange 里 setForm(f => ({...f, [name]: value})) 更新。校验在提交前遍历字段规则。
C受控 vs 非受控选型：需即时校验/联动/默认回填多用受控；简单无需校验的纯输入可用非受控减少渲染。实践中以受控为主、必要时混合；关键是不让两套状态源冲突。

第 8 章 生命周期与类组件

A类组件生命周期：componentDidMount（挂载后，适合请求/订阅）、componentDidUpdate（更新后）、componentWillUnmount（卸载前，适合清理）。state 用 this.state，更新用 this.setState。
B映射到函数组件：请求/订阅在 useEffect(fn, [])；依赖变化 useEffect(fn, [dep]) 对应 componentDidUpdate；清理函数 return 对应 componentWillUnmount。this 绑定差异是类组件易错点。
C类组件问题：this 绑定易错、逻辑难复用（mixin/HOC 复杂）、状态与逻辑分散在生命周期。Hooks 让逻辑按"关注点"聚合、可复用（自定义 hooks）、无 this。因此新代码用函数组件 + Hooks。

第 9 章 函数组件与 Hooks 心智

AHooks 是函数组件里"接入状态与副作用"的函数（useState/useEffect/useRef 等）。核心心智：每次渲染都是独立的一次"快照执行"，Hooks 在顶层按序调用，state 与 effect 绑定到该次渲染。
BHooks 规则：只在顶层调用（不放在条件/循环里）、只在函数组件或自定义 hooks 里调用。原因是 React 靠调用顺序为每个 hook 建立记忆槽，顺序变化会让状态错位。
C对比类组件生命周期，Hooks 把"关注点"（数据获取、订阅、计时器）聚合在同一段代码，而非拆散到多个生命周期方法；配合自定义 hooks 可在组件间复用有状态的逻辑，这是类组件难以做到的。

第二篇 Hooks 核心（第 10–19 章）

第 10 章 useEffect 同步器心智

AuseEffect 的定位是"与外部系统同步"：请求、订阅、DOM 操作、计时器。写法 useEffect(() => { ... }, [deps])。它不是"响应状态的函数"，而是"渲染后与外部对齐"的副作用。
B副效应在每次渲染后、deps 变化时运行；return 的函数是清理，在下一次 effect 前与卸载时执行。适合清理订阅、取消请求、清计时器，防泄漏。
C订阅窗口尺寸：useEffect 里 addEventListener('resize')，return 里 removeEventListener；deps 给 [] 表示只挂载/卸载一次。若漏掉清理，重复挂载会累积监听器导致内存泄漏与重复触发。

第 11 章 依赖数组与 cleanup 三时机

A依赖数组决定 effect 何时重跑：空数组只在挂载后跑一次；有依赖则在依赖变化后跑；不传则每次渲染后跑。effect 读取的所有响应式值都应进依赖数组，否则读到旧值。
Bcleanup（清理）执行三时机：① 卸载时；② 依赖变化、下一次 effect 运行前；③ 严格模式下开发期的模拟卸载/重挂载。设计 effect 时把"如何撤销这次副作用"写成 return，保证可逆。
C"闭包陷阱"与依赖数组：effect 捕获渲染时的值，依赖数组决定它"是否重新捕获"。如计数器中若 deps 为空，effect 闭包永远拿到初始 count。解法是把 count 加进 deps 或用函数式更新/ref 读最新值。

第 12 章 useLayoutEffect 与绘制时机

AuseLayoutEffect 与 useEffect 的执行时机不同：前者在浏览器绘制前同步执行，后者在绘制后异步执行。两者在 DOM 变更后都可用，但 layout 会阻塞绘制。
B需要"读取并修改布局后用户看不到中间态"的场景（测量 DOM 尺寸并据此定位）用 useLayoutEffect，避免闪烁；纯异步副作用（请求、订阅）用 useEffect，避免阻塞绘制。
C测量元素宽度并同步样式：useLayoutEffect(() => { const w = el.offsetWidth; setSize(w) }, [])——绘制前完成，用户不会看到"先旧后新"的闪烁。若用 useEffect 则可能先绘制旧布局再更新。

第 13 章 useMemo 与 useCallback

AuseMemo(() => 计算结果, [deps]) 缓存"计算值"，依赖不变则复用上次结果；useCallback(fn, [deps]) 缓存"函数引用"。二者都用于避免不必要的重复计算与重渲染。
B配合 React.memo：子组件用 memo 包裹后，只有 props 变化才重渲染；父传内联函数每次都是新引用会让 memo 失效，故用 useCallback 稳定回调引用。useMemo 用于昂贵的派生计算。
C滥用反而有害：useMemo/useCallback 本身有开销，且依赖数组维护成本。原则：只对昂贵计算（大数组过滤、复杂计算）或传给 memo 子组件的回调用；简单值/内部使用不必缓存。优化要先测再改（第 52 章）。

第 14 章 Context 与 Provider

AcreateContext(默认值) 创建；<Provider value> 提供；useContext(ctx) 消费。Context 让数据跨任意层级的组件传递，避免逐层 props 透传（prop drilling）。
B适合：主题、语言、登录用户、权限这类"全局或子树共享"数据。不适合频繁变化的数据——Provider value 变化会让所有消费者重渲染，且无细粒度选择（对比状态管理的选择器，见第 23 章）。
C主题 Context 实现：createContext({theme:'light'})，根 <ThemeProvider value={theme}>，任意子组件 useContext(ThemeContext) 读主题并据此切换样式。value 用 useMemo 缓存避免无谓更新。

第 15 章 useReducer 与状态逻辑

AuseReducer(reducer, initialState) 返回 [state, dispatch]。reducer 是纯函数 (state, action) => newState，通过 dispatch(action) 触发更新。适合多步、相互关联的状态转换。
B对比 useState：useState 适合简单独立状态；useReducer 把"如何转换"集中成可预测的 reducer，便于测试（纯函数）。表单多字段、购物车、游戏状态等复杂转换更适合 reducer。
C用 reducer 管理购物车（ADD/REMOVE/CLEAR）：reducer 根据 action.type 计算新数组，纯函数不改原状态。dispatch 进 state 可测试性：对 reducer 单独传入旧 state + action 断言输出，无需渲染。

第 16 章 refs 与 DOM

AuseRef(init) 返回可变 ref 对象，ref.current 存取值。用于：访问 DOM（<input ref={ref}>）、存跨渲染稳定的可变值、避免闭包陷阱。
Bref 不触发重渲染（改 current 不重渲），适合存"不需要 UI 反映"的值（计时器 id、上次值）。DOM 访问在 useEffect 里做，确保已挂载。受控场景优先 state，ref 只做命令式操作。
C用 ref 保存"最新值"以解决闭包陷阱：const latest = useRef(); latest.current = value，回调里读 latest.current 始终得最新值。计时器场景：const id = useRef(); useEffect(()=>{ id.current=setInterval(...); return ()=>clearInterval(id.current) },[])。

第 17 章 自定义 Hooks

A自定义 hook 是"以 use 开头、内部调用其他 hooks 的函数"，用于抽取可复用的有状态逻辑。例：useWindowWidth、useFetch、useLocalStorage。
B抽取判断：多个组件重复"同一种状态管理逻辑"（如监听窗口、轮询、防抖）就应抽自定义 hook。它复用的是"逻辑"而非"UI"，与组件复用互补。
C写 useFetch(url)：内部 useState 存 data/loading/error + useEffect 发请求 + cleanup 用 ignore 标志防竞态 + 依赖 url。调用方只拿 {data, loading, error}，逻辑被封装复用。这是 hooks 最典型的落地。

第 18 章 Hooks 规则与 lint

AHooks 三条规则：顶层调用（不嵌套在条件/循环/嵌套函数里）、只在函数组件/自定义 hooks 调用、按固定顺序调用。违背会导致 hooks 记忆槽错位、状态错乱。
Beslint-plugin-react-hooks 自动校验：rules-of-hooks 查调用位置，exhaustive-deps 查依赖数组是否覆盖 effect 用到的响应式值。违反会告警/报错。
C依赖数组 lint 给出补依赖建议，但盲目补依赖会导致 effect 频繁重跑。正确做法：分析 effect 真正依赖的响应式值，缺的补上，确实不需响应的用 ref 或函数式更新规避，避免"补全但引发重跑"。

第 19 章 状态提升与组合

A状态提升：当多个子组件共享同一份状态时，把 state 提升到它们共同的父组件，父持有 state 并把值 + 更新回调通过 props 传给子组件。保证"单一数据源"。
B示例：两个输入框共享"单位换算"——父组件持 unit state，一个输入框 onChange 回写父，父计算后把转换值传给另一个（只读）。任何改动经父统一，逻辑集中。
C组合优于继承：组件通过 children 或 render prop 组合，而非继承类。把"可变插槽"（如 <Layout><Header/><Content/></Layout>）用 children 传入，组件结构清晰、复用灵活。

第三篇 状态管理（第 20–28 章）

第 20 章 全局状态为什么难

A局部状态（useState）只属于某组件；全局状态要被多个不相关组件共享、跨页面读写。难点：如何"一处更新、处处同步"，避免层层 prop drilling 与多份副本不同步。
Bprop drilling 问题：深层组件要数据需层层传 props，中间层被迫转发与自己无关的 props，代码冗长难维护。解决方案：Context 穿透、或全局状态库（Zustand/Redux）。
C选型判断：仅少数子树共享用 Context 足够；真正的"跨页面全局状态"（用户信息、购物车、主题）用状态库更清晰——因为状态库提供选择器、持久化、中间件等能力，且避免 Context 全局重渲染。

第 21 章 Zustand

AZustand 创建 store：const useStore = create((set) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) }))。组件用 const count = useStore(s => s.count) 读取、用动作更新。
B对比 Context：Zustand 默认细粒度订阅——选择器只让"用到该字段"的组件重渲染，而 Context value 变化会让所有消费者重渲染。这让 Zustand 更适合高频/大范围全局状态。
C用 Zustand 管理购物车：create 里定义 items 数组 + add/remove/clear 动作，动作内用 set 生成新状态（不可变）。组件通过选择器取 items 与数量，跨页面共享一致。

第 22 章 Redux Toolkit

ARedux Toolkit 的 slice 组合 action/reducer：createSlice({ name, initialState, reducers })，configureStore 配置 store，Provider 包裹根，组件用 useSelector/useDispatch。
B对比 Zustand：RTK 更重、约定多（slice/action/reducer/selector），适合大型团队与复杂状态流、强规范；Zustand 轻、心智简单，适合中小项目快速落地。Zustand 更"小而美"，RTK 更"规范齐全"。
C选型考量：团队规范、状态复杂度、是否需要 devtools/中间件/不可变保证。中后台大型应用常用 RTK（生态与文档成熟）；追求轻量与上手快选 Zustand。二者都能做全局状态，差别在工程约定。

第 23 章 选择器与派生状态

A派生状态 = 从已有状态计算出的值，不应另存副本，应实时计算。例：const total = items.reduce((s,i)=>s+i.price,0) 直接算，而非另存 total state。
B选择器（selector）从 store 取/派生所需数据；在 Zustand useStore(s => s.filtered)、RTK useSelector(selectX)。好处是组件只订阅自己需要的数据，减少无关重渲染。
C选择器返回新对象会导致每次重渲染都"看起来变了"（引用不相等），引发重复渲染。优化：选择器返回原始值或派生计算 + useMemo 缓存，让"判定是否变化"基于稳定引用。

第 24 章 服务端状态与请求缓存

A服务端状态（远程数据）与本地 UI 状态不同：它由后端决定、需要请求获取、可能变化。不应把它当普通全局 state 硬塞 store，而应做"请求状态管理"（loading/error/data + 缓存）。
B普通请求的重复问题：多个组件都要同一数据，各自发请求导致重复拉取与竞态。缓存思路：按请求 key 缓存响应，已有缓存则复用，避免重复请求（可配失效策略）。
C手写简单缓存 hook：useQuery(key, fetcher) 内部用 Map 缓存，命中返回缓存不请求，未命中请求并写入；暴露 refetch/失效。工程上更成熟用 TanStack Query（第 25 章）自动做缓存、去重、失效。

第 25 章 React Query / TanStack Query

ATanStack Query 管理服务端状态：useQuery({ queryKey, queryFn }) 获取数据（含 loading/error/data），useMutation 执行写操作后 invalidateQueries 失效缓存重拉。核心是"缓存 + 自动重新获取"。
B对比手写：Query 自动处理缓存去重（同 key 只请求一次）、失效（mutate 后 invalidate）、重试、窗口聚焦刷新、GC 清理。业务代码大幅减少，且状态一致。
C写操作流程：useMutation(mutationFn) 提交成功后 queryClient.invalidateQueries(['orders'])，让相关 useQuery 自动重拉，UI 同步。乐观更新可在 mutation 的 onMutate 里暂改缓存、失败回滚。这消除了"手动刷新列表"的样板。

第 26 章 状态持久化

A持久化：把关键状态（token、语言、主题、偏好）写入 localStorage，刷新后恢复。Zustand 用 persist 中间件，RTK 手写或配插件。
BZustand persist 中间件：create(persist((set)=>({...}), { name:'app' }))——自动把 state 存 localStorage、初始化时回填。用 name 隔离命名空间。
C持久化注意：只存"需要跨刷新"的数据，敏感数据不入 localStorage（有 XSS 风险，token 放内存或 httpOnly cookie 更安全）；恢复时要校验结构（版本迁移）；大对象不宜全量持久化。

第 27 章 跨组件通信

A通信方式分层：父子用 props + 回调；兄弟用状态提升到共同父；深层/跨组件用 Context 或全局状态库；跨页面用全局 store；跨窗口/标签可用 localStorage/BroadcastChannel。
B选型：就近原则——能 props 提升就不上全局；只有"确实全局共享"才用 store/Context。过度用全局会让数据流失控，违背"就近状态"原则。
C表单子组件与父组件的受控通信：父持 form state，子组件只触发 onChange(name, value)，父更新。保证数据单一来源，任何嵌套都能统一走回调。这是"状态提升 + 受控协议"的组合。

第 28 章 状态管理选型

A三条路线：局部 useState（组件内）、Context（子树共享）、全局 store（跨页面）。选型顺序：先用局部，不够再提升，确实全局才上 store。
B对比：useState 简单但只限单组件；Context 穿透但整树重渲、无选择器；Zustand 轻、细粒度订阅；RTK 重、规范全。没有银弹，按"共享范围 + 更新频率 + 团队规范"选。
C给出选型决策表：① 仅父子共享 → props/提升；② 子树（主题/语言）→ Context；③ 跨页面高频全局 → Zustand；④ 大型团队复杂状态流 → RTK；⑤ 服务端数据 → TanStack Query（它和本地状态是两套）。这样各归其位。

第四篇 路由与数据（第 29–37 章）

第 29 章 React Router 基础

AReact Router 声明式路由：<BrowserRouter> 包裹，<Routes> 里 <Route path element> 匹配路径渲染组件，<Link to> 做页面跳转（避免整页刷新）。
B对比原生 <a href>：Link 用前端路由（history API）切换组件，无整页刷新；<a> 会刷新整页。SPA 用 Link 保持状态与流畅体验。
CBrowserRouter（history 模式）vs HashRouter（# 模式）：前者 URL 干净但部署需服务端把未知路径回退到 index.html；后者无需服务端配置但 URL 带 #。SPA 部署到静态服务器常用 BrowserRouter + 回退规则。

第 30 章 嵌套路由与 Outlet

A嵌套路由：父 Route 包子 Route，父组件用 <Outlet /> 渲染匹配到的子路由内容。适合"布局 + 内容页"结构（后台 Layout 包各页面）。
B后台布局：<Route element={<AdminLayout/>}> 包裹 <Route path="/orders" .../>，AdminLayout 里 <Outlet/> 是子页面出口。布局只写一次，各页面复用。
C布局与路由同源（第 63 章）：菜单项与路由都由 routeConfig 派生，父 Route 的 element 是 AdminLayout（含 <Outlet/> 与侧边菜单），子 Route 是具体页面；点击菜单切换 path，Outlet 渲染对应页，菜单与内容联动。

第 31 章 路由参数与查询

A路径参数：path="/user/:id"，组件用 useParams() 取 params.id。查询串：useSearchParams() 读写 ?page=2。
B选择：属于"资源的唯一标识"用路径参数（/user/123）；属于"过滤/分页等条件"用查询参数（?page=2&status=paid）。两者都能进 URL，利于分享与刷新保留。
C把分页与筛选同步到 URL 查询参数：页面用 useSearchParams 读取并 set（setSearchParams），组件卸载/刷新后状态从 URL 恢复。这实现了"列表状态可分享、可收藏"。注意 set 会触发路由更新，用 replace 避免历史堆叠。

第 32 章 导航与编程式跳转

ALink 用于声明式链接；编程式跳转（点击后/提交后）用 useNavigate() 返回 navigate(path)，或 navigate(path, { replace: true })。
B登录成功后跳转：navigate('/dashboard', { replace: true })，replace 避免把登录页留在历史里、用户返回又回到登录。携带来源：从守卫 state 读 location.state.from 跳回原页。
C导航误区：在 useEffect 里对"非用户操作"调用 navigate 会依赖导航状态、易循环；应在事件回调（点击/提交成功）中导航。区分"命令式跳转"与"路由驱动的渲染"，别让导航逻辑纠缠到渲染数据流。

第 33 章 路由守卫与懒加载

A路由守卫：渲染 Route 前检查登录/权限，不满足用 <Navigate> 重定向。未登录跳登录（记来源），无权限跳 403。实现为 RequireAuth 包裹组件（第 58 章）。
B懒加载：<Route path="/orders" element={<React.lazy(()=>import('./pages/Orders'))/>}>，配合 <Suspense fallback>。让非首屏页面按需加载，缩小首屏包体积（衔接第 44/51 章）。
C守卫 + 懒加载组合：RequireAuth 包裹一层（先鉴权），再 lazy 加载目标页（后取代码）。懒加载页在 Suspense 边界内显示 loading 占位。登录态先于页面代码判断，避免未登录也下载页面代码。

第 34 章 数据获取模式

A组件内获取数据用 useEffect + async：挂载后 fetch，设置 loading/data/error。要点：清理时用 ignore 标志防竞态，错误分支要捕获。
B竞态问题：快速切换参数/翻页时，旧请求晚到覆盖新数据。解法：ignore 标志（unmounted 丢弃）或请求序号（只采用最后一次）。这是列表/详情页最常见的异步坑。
C用请求序号防竞态：const seq = ++ref.current，响应里 if (seq !== ref.current) return（只采用最后一次）；或用 AbortController 取消旧请求。工程上更推荐直接交给 TanStack Query（第 25 章），它内置竞态与取消处理。

第 35 章 表单校验与提交

A受控表单校验：字段 rules（必填、格式），提交前遍历校验、不通过则提示。用 antd Form 或 react-hook-form 声明式校验更省事。
Breact-hook-form + zod：zod 定义 schema（z.string().min(2) 等），useForm({ resolver: zodResolver(schema) })，提交用 handleSubmit。类型安全、校验集中、性能好。
C异步校验（用户名查重）：rule 的 validator 内 async 调接口，返回错误即失败；设置 validateTrigger: 'onBlur' 避免每次 onChange 都发请求。提交统一 handleSubmit，成功后才进入业务（衔接第 57 章）。

第 36 章 请求层封装与错误处理

A请求层用 axios 实例统一配置：baseURL、超时、请求/响应拦截器。拦截器统一加鉴权 header、解析错误、统一提示，业务代码只写数据逻辑。
B统一错误处理：响应拦截器判 status——401 跳登录/清 token、403 提示无权限、5xx 提示服务异常。避免每个页面重复 try/catch 提示。
C设计请求层：axios.create 实例 + 拦截器（请求加 token、响应剥 data 层 + 统一抛错），API 模块按资源封装方法（orderApi.list(params)）。优点：鉴权/错误/loading 一处管理，换后端只改一处。

第 37 章 鉴权与数据安全

A前端鉴权流程：登录提交 → 后端验密返回 token → 存 token、请求带 Authorization → 路由守卫判断登录态放行/跳登录。token 常用 JWT（无状态、含过期）。
Btoken 存储位置权衡：localStorage 简单但有 XSS 风险；httpOnly cookie 防 XSS 读取、但防 CSRF 需 SameSite；内存存 token 刷新丢失。实践：敏感 token 优先 httpOnly cookie + SameSite，或不存高敏感数据。
C安全原则（衔接第 58 章）：前端权限与 token 只是体验与身份，真正的数据安全（接口鉴权、行级权限）在后端。前端只做"未登录不让进、无权限不显示"，绝不能把安全寄托在前端。

第五篇 渲染原理（第 38–46 章）

第 38 章 虚拟 DOM 与协调

A虚拟 DOM 是描述 UI 的普通 JS 对象树，是真实 DOM 的"内存映射"。渲染流程：render 生成虚拟树 → 协调（diff）对比新旧虚拟树 → 算出最小更新 → 应用到真实 DOM。
B价值：把"操作真实 DOM"（慢）抽象成"描述 UI"（快），React 负责批量、最小化地更新真实 DOM，提升性能与可预测性。虚拟 DOM 只是手段，核心是声明式 + 高效协调。
C协调与 key：diff 同层对比，key 帮助识别"哪些节点复用"。稳定唯一 key 让移动/删除不错位；用 index 做 key 会复用错位。key 改变会让节点重建而非复用。这是协调算法的直接推论。

第 39 章 Fiber 架构

AFiber 是 React 的调和与渲染执行单元，把协调拆成可中断、可增量的小任务，带链表结构以便调度。它让"大树的协调"可分批执行、可被更高优先级打断。
B对比旧 stack reconciler：旧版递归遍历不可中断，大树会阻塞主线程；Fiber 拆成可中断的增量工作，配合调度器（Scheduler）按优先级执行，是并发特性的基础。
CFiber 如何支撑并发：render 阶段可中断（计算 Fiber 树，不提交），提交阶段不可中断（一次性更新 DOM）。高优先级更新可打断低优先级渲染。理解这点就明白 why useTransition/useDeferredValue 能降级渲染。

第 40 章 渲染时机

AReact 何时重渲染：state 变化、父组件重渲染（默认子也重渲）、Context value 变化。触发条件是"状态或 props 引用变化"，React 默认从变化点向下重建。
Bprops 变化触发子重渲染：父 state 变了，父重渲染，传给子的 props 若引用变化，子也重渲染。这是"自上而下"的数据流。memo 可阻断（引用没变的子不重渲）。
C不必要的重渲染：父组件每次渲染都新建内联函数/对象传给子，即使子纯展示也重渲。缓解：useCallback 稳定回调、React.memo 包裹子、状态下沉（把变化的部分独立组件）。先测再优化。

第 41 章 不可变数据

A不可变更新：不直接修改 state，而是生成新对象/数组再 set。例：数组用 setItems([...items, newItem])，对象用 setUser({...user, name})。
BReact 判断"值是否变了"靠引用比较（===）：新引用 = 变了 = 重渲染。若直接 mutate 旧对象再 set，引用没变，React 可能跳过渲染，UI 不同步。不可变性让"变了与否"可被可靠判断。
C不可变性提升性能：memo 通过浅比较 props 引用快速跳过未变子组件；选择器/缓存也依赖引用稳定。代价是需展开对象；深层嵌套用 immer 简化（produce 生成新 draft）。"引用不变则不变"是 React 优化基石。

第 42 章 memo 与引用相等

AReact.memo(Comp) 让组件在 props 浅比较相等时跳过重渲染。前提是 props 引用稳定；若父每次传新引用，memo 失效。
B引用相等性：useState 每次渲染的数组/对象都是新引用；内联函数每渲染一个新引用。传给 memo 子组件时，用 useCallback 稳定函数、useMemo 稳定派生值，memo 才能生效。
Cmemo 适用与反例：适合"父频繁变、子渲染贵且 props 稳定"；不适合"props 每次都是新对象/函数"（memo 白费）或"子渲染很轻"（memo 检查本身有开销）。核心是让"引用不必要地变"变少。

第 43 章 Suspense 与并发

ASuspense 是"等待异步数据/代码"的声明式机制：<Suspense fallback={<Loading/>}><LazyComp/></Suspense>，子组件未就绪时显示 fallback。常用于懒加载与数据请求。
BSuspense + lazy：const Lazy = React.lazy(()=>import('./Comp'))，包裹在 Suspense 里，首次加载组件时显示 fallback，加载完渲染组件。是代码分割的配套。
C并发渲染（Concurrent）：React 可"边渲染边等待"，Suspense 让慢的部分先挂起、快的部分先展示；配合 startTransition 把非紧急更新标记为可中断。这让"大更新不阻塞交互"成为可能，是 Fiber + 调度的产物。

第 44 章 代码分割懒加载

A代码分割：按路由/组件把 bundle 拆成多份，需要时再加载。React 用 React.lazy + Suspense，构建工具（Vite/Webpack）按动态 import 切分包。
B路由懒加载：每个页面 lazy(()=>import('./pages/OrderList'))，路由级分割，首屏只加载需要的页面 chunk，首屏体积显著下降。
C避免"懒加载过度"：把首屏必须的代码留在主包，只把低频/非首屏页拆出去；别把超小组件也 lazy（反而加请求往返）。衡量指标是首屏关键路径字节数而非 chunk 数量。

第 45 章 渲染性能分析

A分析手段：React DevTools Profiler 看每次渲染耗时与触发原因；console.count 或日志看组件渲染次数；Production build 分析 bundle 体积。
B读 Profiler：点击一次操作，看火焰图哪些组件渲染耗时、高亮黄色/红色的昂贵更新，定位"谁在频繁重渲染"。据此决定是否需要 memo/状态下沉。
C优化先测再改：先记录"改前"性能数据，再针对性改（memo、useCallback、抽子组件、状态下沉），再记录"改后"对比。没有度量就优化是盲改。

第 46 章 React 18 新特性

AReact 18 关键新特性：并发渲染（Concurrent）、createRoot、自动批处理（automatic batching）、startTransition、useId、Suspense 强化。
B自动批处理：React 18 在 promise、setTimeout、原生事件里也自动批量合并 setState（之前只在 React 事件里批处理）。多次 set 一次渲染，减少不必要的渲染次数。
CstartTransition：把非紧急更新标记为可被中断的过渡，如"输入关键词过滤大列表"——输入（紧急）优先，过滤结果（过渡）可延迟。它把并发渲染落地为可感知的优先级。

第六篇 性能优化（第 47–55 章）

第 47 章 性能瓶颈识别

A识别流程：先用 DevTools Performance/Profiler 定位"卡在渲染还是网络/交互"，再量化（渲染次数、耗时、首屏字节）。常见瓶颈：不必要重渲染、大列表、大图片、未分包的 bundle。
B归类：渲染类（重渲染、协调耗时）→ memo/useMemo/状态下沉；数据类（请求慢、无缓存）→ 缓存/懒加载；体积类（首屏 bundle 大）→ 代码分割、按需引入。先归类再对症。
C可衡量的优化指标：LCP、FPS、渲染次数、TTI。优化前后用同一指标对比，用数据验证收益而非感觉。没有基线就没有"优化成功"。

第 48 章 useTransition 与 useDeferredValue

AuseTransition 返回 [isPending, startTransition]，用 startTransition 包裹非紧急更新，让它可被更高优先级打断；useDeferredValue(value) 延迟派生"滞后值"，在后台渲染。
B对比：startTransition 标记"更新"为可中断；useDeferredValue 标记"某个值"的消费可滞后。都用于"紧急输入 + 非紧急昂贵派生"分离，避免输入卡顿。
C输入框过滤大列表：输入 onChange 是紧急更新（立即回显）；const deferred = useDeferredValue(query) 过滤列表用 deferred，让输入流畅、过滤在后台完成。isPending 显示轻量 loading。

第 49 章 列表虚拟化

A虚拟化（windowing）：只渲染可视区域内的列表项，滚出视口的不渲染，用占位撑起总高度。解决大列表"渲染所有项"的性能问题。
Breact-window：<FixedSizeList height itemCount itemSize> 渲染定高列表，VariableSizeList 处理不定高。它通过滚动定位 + 只渲染可视项大幅减少 DOM。
C何时需要虚拟化：列表项很多（千级以上）且行结构固定时收益明显；行内含复杂组件/状态时注意行复用（key）。虚拟化让首屏与滚动都只处理可见部分。

第 50 章 图片与资源优化

A图片优化：合适尺寸（不要 4000px 图显示 200px）、懒加载（loading="lazy"）、格式（webp/avif）、CDN 与缓存、占位（避免布局偏移 CLS）。
B懒加载图片：<img loading="lazy"> 或 IntersectionObserver 在进入视口时再加载。避免一次性下载所有图，改善首屏与流量。
C给图片设宽高 / 固定容器比例防止 CLS（布局偏移），用 aspect-ratio 或 padding-top 占位；配 srcSet/sizes 响应式选尺寸；大图走 CDN 缩略。

第 51 章 包体积与代码分割

A控制包体积：路由级代码分割（lazy）、组件库/库按需引入（如 ECharts 用 echarts/core 只注册用到的，antd CSS-in-JS 自动按需）、移除未用依赖。
B分析 bundle：Vite build --report 或 rollup-plugin-visualizer 生成体积报告，看哪些 chunk 大、哪些依赖占大头，针对性分割或按需。
C第三方库策略：大库（ECharts、日期库）按需注册或用较轻替代；不用的别 import；把首屏用不到的 chunk 提出主包。目标是让"首屏关键路径"体积可控。

第 52 章 记忆化策略

A记忆化用 React.memo / useMemo / useCallback 缓存"不必要变的东西"，避免重复渲染/计算。前提是"引用稳定才有效"。
B组合策略：子组件 memo + 父传的 props 引用用 useCallback/useMemo 稳定；昂贵派生用 useMemo。三者配合让"引用不变 → 跳过重渲/重算"。
C适用边界：只对"渲染贵且变化不频繁/引用可稳定"的场景；滥用会增加依赖维护与比较开销。先用 Profiler 确认某组件确实在重复渲染且耗时，再加记忆化。

第 53 章 长列表与动画性能

A长列表优化：虚拟化 + 行组件 memo + key 稳定 + 避免行内大状态；滚动时避免触发布局（layout thrashing）。
B动画用 transform/opacity 而非 top/left/width（合成线程，不触发布局/重绘），配合 will-change 提示；requestAnimationFrame 批量操作避免每帧多次布局。
C动画与 React 结合：动画相关值用 ref/transform 而非 state 每帧 setState（避免每帧重渲染整树）；用 CSS 动画或 Framer Motion 让帧走合成线程。

第 54 章 服务端渲染 SSR

ASSR：组件在服务端渲染成 HTML 返回，首屏更快且利于 SEO；随后客户端 hydrate 接管交互。对比纯 CSR（空壳 + JS 渲染）首屏慢、SEO 弱。
B权衡：CSR 部署简单、交互流畅、适合强交互后台；SSR 首屏快、SEO 好，但引入服务端渲染/水合复杂度与 TTI 权衡。后台多选 CSR，内容型/公开站点用 SSR 或 SSG。
Chydrate（水合）：服务端已输出 HTML，客户端把交互/事件绑定到现有 DOM，而非重建。水合不匹配会告警。Next.js 把 SSR/SSG 一体化；纯 React SSR 需自行搭 renderToString + hydrate。

第 55 章 实战慢页面优化全记录

A优化流程模板：① 用 Profiler/Performance 定位卡点（渲染 or 网络 or 体积）；② 量化基线；③ 对症改（memo/懒加载/虚拟化/按需引入）；④ 复测对比，验证收益。
B常见组合拳：路由懒加载降首屏、ECharts/组件按需降体积、大列表虚拟化、重复渲染用 memo + 稳定引用、图片懒加载。每一招都对应一个明确瓶颈。
C复盘记录：记录"现象→定位工具→根因→措施→效果（指标对比）"，形成可复用的优化经验。面试讲优化项目时按这个结构，最有说服力。

第七篇 生态与实战（第 56–64 章）

第 56 章 组件库：Ant Design 体系

Aantd 5 用 CSS-in-JS（cssinjs），样式随组件自动注入，默认即可按需，无需旧式 babel-plugin-import。最小配置：<ConfigProvider locale={zhCN} theme={{token:{colorPrimary:'#2d6a3f'}}}>...</ConfigProvider>，并配 dayjs.locale('zh-cn')。
BDesign Token 分 seed（种子，如 colorPrimary）→ map（映射，派生 colorPrimaryHover/Active）→ alias（别名，如 colorBgContainer）三层。只改 seed 的 colorPrimary，antd 按算法派生整套色板。DatePicker"文案中文日期英文"是因 antd locale 与 dayjs.locale 两套只配了一处，须一起配。
C后台骨架：<Layout> 里 Sider 放 Menu，Content 放 <Outlet/> 渲嵌套路由；菜单与路由表由同一份 routeConfig 派生。暗色切换：<ConfigProvider theme={{algorithm: dark ? theme.darkAlgorithm : theme.defaultAlgorithm}}>，语言/主题状态放全局 store，切换时同步 ConfigProvider。

第 57 章 表格与表单页实战

A三态：查询条件 filters、分页 pagination（current/pageSize/total）、数据列表 dataSource。搜索条件变化必须把 current 重置为 1，否则从第 3 页搜，返回的是新条件的第 3 页，页面像"跳到奇怪位置"。
B编辑流程：点编辑 → form.setFieldsValue(record) 回填 → await form.validateFields() 校验 → 提交保存 → 刷新列表。关键差异：initialValues 只在首次挂载生效、二次打开不重置；编辑场景用 setFieldsValue（或 useEffect 按 open/record 分支 resetFields）。
C页码回退：删除最后一条后响应 total 变了，若 current > 总页数则 setCurrent(Math.max(1, lastPage)) 再请求。防竞态：用 ignore 标志或请求序号 seq（if (seq !== ref.current) return）只采用最后一次；或交给 TanStack Query。

第 58 章 权限方案：路由级与按钮级

ARBAC：用户→角色→权限点→资源。权限点用「资源:动作」如 order:delete，一套集合同时管路由（order:view）与按钮（order:delete）。守卫：未登录 <Navigate to="/login" state={{from}} />；无权限 <Navigate to="/403" />。
B同源：routeConfig 每条含 path/label/icon/permission，先 filterByPermission 过滤，再同一份转 Menu items 与 createBrowserRouter。不同源会导致"菜单不显示但输 URL 能进"（菜单与路由各一份、权限各过滤一次不同步）。
C<Auth permission="order:delete" fallback=...> 内部 const ok = !permission || user.permissions.includes(permission); return ok ? children : fallback；usePermission 返回 (p)=>permissions.includes(p)。权限被收回：请求层拦截 403，清 token + 重置 auth store + 跳登录或刷新用户信息。

第 59 章 国际化：react-i18next

Ai18next 是翻译核心，react-i18next 是 React 绑定（useTranslation）。初始化：i18n.use(initReactI18next).init({ resources, lng:'zh-CN', fallbackLng:'en-US', interpolation:{escapeValue:false} })。
B插值：资源 "greeting":"你好，{{name}}"，调用 t('greeting',{name})。复数：资源写 itemCount_one/_other，调用 t('itemCount',{count})。拼接应避免——语言语序不同，拆开拼接会坏；用插值把变量交给 t 处理。
C持久化：初始化时 lng: localStorage.getItem('lang') || 'zh-CN'；切换 i18n.changeLanguage(lng) 并 localStorage.setItem('lang', lng)。根组件 const {i18n}=useTranslation()，<ConfigProvider locale={localeMap[i18n.language]}> 让 antd 组件语言与业务文案同源切换。

第 60 章 图表集成：ECharts 封装

AECharts 命令式、option 驱动：echarts.init(dom) 操作真实 DOM，生命周期开发者管。init 只跑一次（useEffect 空依赖），return 里 dispose；若把 init 放进依赖 option 的 effect，option 一变就重复 init/dispose，产生多实例、闪烁、泄漏。
B数据更新 effect：useEffect(()=>{ chartRef.current?.setOption(option, true) }, [option])，true 表示不合并、按新 option 重建，避免残留旧 series，且判空防实例未就绪/已销毁。resize 用 ResizeObserver(()=>chart.resize()) observe 容器。
C封装 <Chart option height theme />：init 一次（deps [theme]）、setOption 更新（deps [option]）、ResizeObserver resize、return dispose。按需引入：import * as echarts from 'echarts/core' + 注册 Bar/Line/Pie 与 Tooltip/Grid/Legend + CanvasRenderer，漏注册会报 "not found: XXXChart"。

第 61 章 上传与文件处理

A上传本质：把 File 放进 FormData 作为 multipart 请求体发给接口（fetch/xhr）。手设 Content-Type 会丢 boundary 导致后端解析失败，body 是 FormData 时让浏览器自动设。
BcustomRequest：{file,onSuccess,onError,onProgress} 内用 xhr 发请求、setRequestHeader 带 token、upload.onprogress 算 percent 回调 onProgress、200 时 onSuccess、否则 onError。用 xhr 而非 fetch 是为拿上传进度事件。beforeUpload：校验 file.type/file.size，不符返回 Upload.LIST_IGNORE。
C分片续传：按 2MB 用 file.slice(start,start+CHUNK) 切片；每片带 fileHash + chunkIndex；限制并发（如 3）；先查"已有片"跳过已传、续传剩余；全传完调合并接口按 hash 重组。前端抽独立工具模块，与后端约定协议。

第 62 章 测试：React Testing Library

A测行为不测实现：该测"渲染出标题/点按钮出弹窗/输入触发校验提示"；不该测"断言内部 state 值、某函数被调用几次、JSX 结构"。骨架：render(<Comp/>) + expect(screen.getByRole('heading',{name:/标题/})).toBeInTheDocument()。
B登录测试：const user=userEvent.setup()；await user.type(getByLabelText('用户名'),'admin')；await user.click(getByRole('button',{name:/登录/}))；expect(onLogin).toHaveBeenCalledWith({username,password})。userEvent 动作必须 await（否则断言在交互完成前跑）。getBy 找不到抛错（断言存在用），queryBy 找不到返回 null（断言不存在用）。
C列表加载测试：vi.mock('./api',()=>({fetchOrders: vi.fn().mockResolvedValue({list:[{customer:'张三'}],total:1})}))；await screen.findByText('张三') 等数据出现。何时用 MSW：需更贴近真实网络层/测错误分支时。一个用例一个行为，失败时能快速定位是哪个交互出了问题。

第 63 章 综合项目：管理后台全流程

A选型表（需求驱动）：脚手架 Vite+React+TS；路由 React Router；状态 Zustand（本地）/TanStack Query（服务端）；组件 antd 5；鉴权 token+AuthProvider；图表 ECharts；国际化 react-i18next；测试 Vitest+RTL。需求驱动 = 每个模块需求决定方案，而非为用库造需求。
B目录结构：api / components / pages / router / store / hooks / i18n / utils / styles / test，各司其职，一文件一问题。auth store（Zustand）：create((set)=>({user:null, token:localStorage.getItem('token'), login:async(c)=>{...}, logout:()=>{...}}))，token 与 user 单一权威。
C主流程串联：登录 submit → auth store 存 token/user → RequireAuth 守卫放行 → routeConfig 同源过滤生成菜单+路由 → 订单列表三态加载（usePagedQuery）→ 编辑弹窗 setFieldsValue 回填 → Auth 组件按钮级权限 → Dashboard Chart 图表 → i18next+ConfigProvider 切语言。各模块统一读 auth store 的 token/user，保证一致。

第 64 章 面试知识体系梳理与延伸路线

A七篇地图：入门与 JSX（组件/JSX/状态/事件）→ Hooks 核心（useEffect/ref/自定义 hooks）→ 状态管理（Context/全局 store/请求缓存）→ 路由与数据（Router/表单/请求层/鉴权）→ 渲染原理（虚拟 DOM/Fiber/并发）→ 性能优化（memo/懒加载/虚拟化）→ 生态实战（AntD/权限/图表/测试/项目）。每篇一句话总结学习目标。
B三个机制用"现象→机制"讲：为什么需要虚拟 DOM→最小化真实 DOM 操作；为什么 useState 更新异步批量→多次 set 合并一次渲染、闭包捕获旧值；为什么 useEffect 要依赖数组→effect 声明它读取的外部值、决定何时重跑与重新捕获。
C项目介绍用 STAR+技术点：背景（订单后台，多角色/多语言/需权限）→ 方案（Vite+React+TS+AntD，路由菜单同源+RBAC）→ 落地（三态列表、Auth 按钮权限、ECharts 封装）→ 结果（数据佐证）→ 引申原理。全栈路线：接真实后端理解接口与鉴权、补工程化（Git/CI/CD/部署）、把测试意识带向后端、深入 TypeScript 与源码。
