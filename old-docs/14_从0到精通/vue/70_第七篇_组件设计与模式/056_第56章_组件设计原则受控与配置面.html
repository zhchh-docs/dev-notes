56.1 props 即"配置面"：受控与非受控

写通用组件的第一件事，不是画 UI，而是决定：这个组件的状态由谁持有。由父级持有、父级通过 props 喂进来，就是受控；由组件自己内部维护一份默认状态，就是非受控。

把 props 理解成组件的"配置面"（configuration surface）：父组件不关心你内部怎么实现，只通过这一组参数告诉你"长什么样、怎么行为"。一个设计良好的组件，配置面应该小而稳。

受控组件：值由父级给，组件是"纯展示 + 转发"

<!-- 子组件：不持有状态，只接收 value、把 change 事件抛回去 -->
<!-- CounterInput.vue -->
<script setup>
const props = defineProps({ value: { type: Number, default: 0 } })
const emit  = defineEmits(['update:value'])
function inc() { emit('update:value', props.value + 1) }
</script>

<template>
  <button @click="inc">当前值：{{ value }}</button>
</template>
<!-- 父组件：状态唯一来源在这里 -->
<script setup>
import { ref } from 'vue'
import CounterInput from './CounterInput.vue'
const count = ref(0)          // 唯一数据源
</script>

<template>
  <CounterInput :value="count" @update:value="v => count = v" />
  <!-- 等价于 -->
  <CounterInput v-model:value="count" />
</template>

非受控组件：内部维护默认值

<!-- SearchBox.vue：父级不传 modelValue 时，自己维护关键词 -->
<script setup>
import { ref } from 'vue'
const props = defineProps({
  modelValue: { type: String, default: undefined }
})
const inner = ref(props.modelValue ?? '')
const text = computed({
  get: () => (props.modelValue ?? inner.value),
  set: (v) => { inner.value = v; emit('update:modelValue', v) }
})
</script>

受控的本质不是"不能有内部状态"，而是当父级传入值时，组件必须以父级的值为准；不传时才用内部默认值兜底。

维度受控（Controlled）非受控（Uncontrolled）
状态来源父组件单一数据源组件内部 ref/默认值
可预测性高：任何时刻都能从父级读出中：内部状态对父级不可见
灵活度低：父级要写更多胶水代码高：拿来即用
典型场景表单、弹窗开关、需要跨组件联动的值一次性搜索框、纯展示微交互

56.2 v-model / defineModel 的受控语义

第 13 章我们见过 v-model。从组件设计角度再看一次：v-model 就是受控语义的语法糖——它同时做了"传值"和"监听更新"两件事。

<script setup>
// Vue 3.4+：defineModel 是稳定 API（3.4 起为稳定）
const visible = defineModel({ type: Boolean, default: false })

function close() { visible.value = false }   // 直接赋值 => emit('update:modelValue')
</script>

<template>
  <div v-if="visible" class="dialog">
    <button @click="close">关闭</button>
  </div>
</template>

<!-- 使用方 -->
<MyDialog v-model="show" />          <!-- show 由父级持有 -->

这里有一个常被忽略的细节：defineModel 返回的是一个可写的 ref，但它"写"的效果是触发 update:modelValue 事件，真正改值的仍是父级。父级如果不更新，组件内再怎么赋值也不会变（配合 default 才形成非受控兜底）。

56.3 单向数据流与"禁止改 props"

Vue 的铁律：父级 props 变化会自然流向子级，但子级永远不能直接修改 props。原因有两层：

  • 语义层：props 是父级的"配置输入"，子组件改它会破坏"谁拥有谁负责"，让状态来源变得不可追溯；
  • 实现层：当父级重新渲染时，props 会被父级的新值覆盖，你在子组件里改的"临时值"会一闪而过，造成"时灵时不灵"的假象。
// ✗ 反例：直接改 props
const props = defineProps({ count: Number })
function bad() { props.count++ }          // 开发环境会报警告

// ✓ 正确：想"通知父级"就 emit；想"本地派生"就用局部 ref/computed
const emit = defineEmits(['update'])
function good() { emit('update', props.count + 1) }
常见误判有人以为"props 是对象/数组时，改它的属性不算改 props"。技术上 Proxy 不会拦你，但语义上同样是在偷偷改父级状态，调试时极难追踪。要改就 emit 出去。

56.4 组件 API 三面：props / 事件 / 插槽

一个组件对外暴露的接口，可以整齐地分成三面。设计新组件时，先把这三面想清楚，再动手写模板。

面承载回答的问题 / 示例
props（配置）静态/动态参数"它长什么样？"——title、width、loading
事件（通知）emits / v-model"它什么时候告诉我？"——change、close、select
插槽（结构注入）默认 / 具名 / 作用域插槽"哪部分内容允许我自定义？"——#title、#footer、#cell="{ row }"
 
<!-- 一个把三面都用对的弹窗骨架 -->
<MyDialog
  :title="'编辑用户'"            <!-- props：配置面 -->
  :visible="show"              <!-- v-model：受控开关 -->
  @confirm="onConfirm"         <!-- 事件：行为通知 -->
>
  <!-- 默认插槽：主体内容由父级注入 -->
  <UserForm />
  <!-- 具名插槽：连按钮都允许父级替换 -->
  <template #footer>
    <el-button @click="show = false">取消</el-button>
  </template>
</MyDialog>

判断组件是否"可复用"，就看一点：把它放到另一个业务场景里，需不需要改它内部的代码。需要改 → 插槽/事件/配置面没留够。

56.5 配置项合并：默认值与 attrs 透传

通用组件不可能穷举父级传的所有属性。工程上的做法是两层合并：

  1. props 默认值：用 withDefaults 给合理兜底；
  2. attrs 透传：父级传的、没有在 props 里声明的属性（class/style/事件/普通 HTML 属性）会自动落到组件根节点；多根组件则用 v-bind="$attrs" 显式指定。
<script setup>
const props = withDefaults(
  defineProps({ size: { type: String, default: 'middle' } }),
  { size: 'middle' }
)
defineOptions({ inheritAttrs: false })   // 不想自动落到根节点时关掉
</script>

<template>
  <!-- 手动把 attrs 接到真正的 input 上，而不是外层 div -->
  <div class="field">
    <input class="real-input" v-bind="$attrs" />
  </div>
</template>

这样父级写 <MyInput maxlength="10" placeholder="姓名" @focus="..." />，这些"非声明属性"全部透传到 <input> 上，组件不用为每个原生属性都开一个 props。

56.6 组件分类与设计侧重

不是所有组件都该追求"高度可配置"。按职责分四类，设计侧重各不相同：

分类职责设计侧重
展示型（Presentational）把数据渲染成 UIprops 多、事件少、不碰请求；越"傻"越好
容器型（Container）取数、编排子组件几乎无 UI，负责把数据喂给展示组件
布局型（Layout）栅格、间距、结构插槽为主，props 只管 gutter/列数
表单型（Form）取值、校验、联动v-model + validate，是受控重灾区

56.7 API 稳定性与设计评审清单

组件一旦被多个页面复用，改 props 名字就是破坏性变更。评审一个组件 API 是否成熟，过一遍这张清单：

  • 评审 1 props 是否都有合理默认值？必填项是否真的必须？
  • 评审 2 值类接口是否统一用 v-model，而不是各自发明 visible/v-show/open 三套？
  • 评审 3 凡是父级可能要"替换一块结构"的地方，是否留了插槽？
  • 评审 4 有没有把"业务逻辑"硬编码进通用组件（如写死某个接口地址）？
  • 评审 5 事件名是否用动词/名词（select/close），而不是 onClickButton 这种内部视角？

最常见的设计债：组件刚写时只服务一个页面，三个月后被七个页面复用，才发现 props 里塞了某个页面才需要的开关——通用组件的抽象要在"第二次复用时"再做，而不是第一次。

56.8 常见坑

  • 坑 1在子组件里直接改 props，开发环境报警告、生产环境状态错乱。
  • 坑 2受控组件又自己存了一份同步副本（watch(props) 同步 inner），两份状态迟早打架。
  • 坑 3把所有原生属性都开成 props，配置面爆炸。应该用 v-bind="$attrs" 透传。
  • 坑 4组件对外方法不暴露，父级想用 formRef.validate() 却调不到——需要 defineExpose。
  • 坑 5多根节点忘记处理 attrs，class 不知道挂到哪个根上。

✓ 本章小结

要点一句话
受控 / 非受控值由父级持有 = 受控；组件内部维护默认 = 非受控，props 即配置面
v-model 语义v-model = 传值 + 监听更新的语法糖，defineModel(3.4+稳定) 只做转发
单向数据流props 只能下行，要改就 emit，绝不直接改 props
API 三面props 配置 / 事件通知 / 插槽结构注入，三者齐全才可复用
配置合并withDefaults 兜底 + v-bind="$attrs" 透传原生属性
组件分类展示 / 容器 / 布局 / 表单，设计侧重各不相同
设计评审默认值、统一 v-model、留插槽、不写死业务、语义化事件名
