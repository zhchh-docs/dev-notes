61.1 为什么要二次封装

直接用 Element Plus 不是不行，但项目一大，问题就来了：每个页面都写一遍 size="small"、都自己处理 loading、都忘记统一空态。二次封装就是把这些重复约定收敛到一层。

痛点封装后
业务默认值散乱统一 size、统一空态文案、统一表格边框风格
接口不统一业务表格都用 columns 配置 + 一个 request 函数
升级组件库要改 N 处只改封装层，业务页面零改动
新人不知道规范用 ProXxx 就是规范，没得选

二次封装的本质是"锁定默认值、统一接口、隔离变化"，而不是再发明一套组件。

61.2 基础封装：透传一切

<!-- PButton.vue：在 ElButton 之上统一默认尺寸 -->
<script setup>
defineOptions({ inheritAttrs: false })
</script>
<template>
  <ElButton size="small" v-bind="$attrs">
    <slot />            <!-- 默认插槽透传 -->
  </ElButton>
</template>
<!-- PInput.vue：连具名插槽与事件一起透传 -->
<template>
  <ElInput clearable v-bind="$attrs">
    <template v-for="(_, name) in $slots" #[name]="slotData">
      <slot :name="name" v-bind="slotData" />
    </template>
  </ElInput>
</template>

关键：inheritAttrs:false + v-bind="$attrs"，让父级传的 props/事件/HTML 属性全部落到真正的 ElButton 上，封装层不拦截。

61.3 业务级封装：ProTable / ProForm

<!-- ProTable：把列配置 + 请求函数 + 分页一次封装 -->
<script setup>
import { ref, onMounted } from 'vue'
const props = defineProps({
  columns: { type: Array, required: true },
  request: { type: Function, required: true }   // (query)=>Promise<{list,total}>
})
const list = ref([]), total = ref(0), loading = ref(false)
const query = reactive({ page: 1, pageSize: 20 })
async function load() {
  loading.value = true
  const res = await props.request(query)
  list.value = res.list; total.value = res.total
  loading.value = false
}
onMounted(load)
defineExpose({ refresh: load })
</script>
<template>
  <ElTable v-loading="loading" :data="list" />
  <ElPagination v-model:current-page="query.page" v-model:page-size="query.pageSize"
                :total="total" @current-change="load" />
</template>
<!-- 业务页面：只关心列和接口，不再写分页逻辑 -->
<ProTable :columns="userColumns" :request="api.getUsers" />

61.4 样式定制：CSS 变量与 :deep

/* 全局改主题色：Element Plus 暴露了大量 CSS 变量 */
:root {
  --el-color-primary: #2d6a3f;
  --el-border-radius-base: 6px;
}
/* 局部改某个组件内部：用 :deep 穿透 scoped */
<style scoped>
.pro-table :deep(.el-table__header) { background: #f0f5e6; }
</style>
升级风险组件库升级时，内部类名（如 .el-table__header）可能改名。优先用官方 CSS 变量改主题，:deep 改内部样式只做补丁，并集中在一处维护。

61.5 按需导入、类型与常见坑

  • 按需导入：配 unplugin-vue-components + resolver，只打包用到的组件，首屏体积更小（第 10 章）。
  • 类型：封装 ProTable 时用 TypeScript 声明 columns 与 request 的类型，否则父级传错列名无提示。
  • 坑 1封装层把 $attrs 吃了：忘记透传，父级传的 clearable/disabled 全部失效。
  • 坑 2在封装层硬编码业务接口地址，导致这个"通用组件"只能在一个业务用。
  • 坑 3为每个 EP 组件都包一层：没有业务价值的纯包装徒增维护面。

二次封装的价值在于「收敛默认值」：业务里所有表格都要分页、都要加载态、都要空态，封装一次 ProTable 后业务页只传 columns 与 request。错误处理也收敛——request 抛错时统一显示错误提示，业务页不用每个都写 try/catch。

// ProTable：列配置 + request + 错误边界（工程骨架）
const props = defineProps({ columns: Array, request: Function })
async function load() {
  loading.value = true
  try {
    rows.value = await props.request({ page, pageSize })
  } catch (e) {
    error.value = '加载失败，请重试'
  } finally { loading.value = false }
}
升级风险EP 内部类名随版本变化，:deep 选择器要集中维护，升级时回归表格样式。

二次封装最怕「锁死样式」：业务想改个字号，却被 :deep 里写死的类名挡住。正确做法是把主题色/字号抽到 CSS 变量，业务覆盖变量即可，不去碰内部类名。

// CSS 变量主题覆盖（工程骨架）
/* ProTable 内部用变量 */
.pro-table{ --pt-color:#2d6a3f; --pt-radius:6px; }
/* 业务侧只覆盖变量，不改内部类名 */
.pro-table{ --pt-color:#1d4ed8; }
要点说明
收敛默认值分页/加载/空态一次封装
错误边界request 抛错统一提示
主题CSS 变量覆盖，不碰内部类名

二次封装的文档要写清「哪些 props 透传、哪些被默认值覆盖」。业务传 size 时若默认值是 small，应尊重业务传入——封装是收敛，不是锁死。用 v-bind="$attrs" 透传未声明属性。

// props 透传（工程骨架）
要点业务传入优先，封装只补默认值，不覆盖显式传参。

ProTable 的 request 函数约定入参出参：入参 { page, pageSize, ...filters }，出参 { list, total }。业务侧只实现这个契约，组件负责分页、加载、空态。

// request 契约（工程骨架）
// request({page,pageSize,kw}) => { list, total }
async function queryUser({page,pageSize,kw}){
  const { data } = await api.user.list({ page, page_size:pageSize, kw })
  return { list: data.list, total: data.total }
}
要点契约清晰，业务只实现数据获取。

二次封装的升级风险要提前写进文档：底层组件改 props 名时，封装层做一次适配，业务侧无感。升级前跑组件测试快照，防止默认值悄悄变。

// 升级适配层（工程骨架）
// 旧: el-input.attr → 新: el-input.prop
// 封装层映射一次，业务不改
const props = mapProps({ size:'size' })
要点说明
收敛默认值业务侧零胶水
升级适配封装层挡一次
