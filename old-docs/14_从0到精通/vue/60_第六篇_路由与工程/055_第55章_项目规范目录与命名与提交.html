55.1 src 目录分层规范

src/
├── views/            # 页面级组件（与路由一一对应）
│   └── user/
│       ├── UserList.vue
│       ├── UserDetail.vue
│       └── components/   # 只属于本页面的子组件
├── components/       # 跨页面复用的通用组件
│   ├── base/         # BaseButton、BaseInput 等基础组件
│   └── business/     # 业务复用组件
├── composables/      # 组合式函数（useXxx.js）
├── stores/           # Pinia store
├── router/           # 路由表与守卫
├── i18n/             # 国际化语言包
├── utils/            # 纯函数工具（格式化、校验）
├── api/              # 接口请求封装
├── types/            # TS 类型声明
├── assets/           # 样式、图片等静态资源
└── main.js           # 入口
目录放什么 / 不放什么
views/路由页面；不放纯展示组件
components/被多页面复用的组件；只服务单页的子组件放该页的 components/
composables/可复用逻辑；不放组件
stores/Pinia；不写视图逻辑
utils/无副作用纯函数；不碰 DOM、不引组件

55.2 文件与组件命名

场景约定示例
组件文件名PascalCaseUserCard.vue
模板里用组件PascalCase<UserCard />
组合式函数文件/函数camelCase，use 开头useUser.js / useUser()
工具/普通 js 模块camelCase 或 kebab-caseformatDate.js
store 文件camelCase，use 开头useUserStore.js
CSS 类名（BEM 风格）kebab-caseuser-card__title

命名规范的价值不是"好看"，而是让新人不看文档也能猜到文件在哪、组件叫什么。一致性比选哪种风格更重要。

55.3 ESLint + Prettier

ESLint 管"对错与坏味道"（未使用变量、== 滥用），Prettier 管"格式"（缩进、分号、换行）。两者配合，团队不必在代码评审里争论风格。

// .prettierrc.json（节选）
{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all"
}
# 安装
npm install -D eslint prettier eslint-plugin-vue eslint-config-prettier

# 一键修复
npx eslint . --fix
npx prettier --write "src/**/*.{vue,js,ts}"
用 eslint-config-prettier 关闭 ESLint 里与 Prettier 冲突的格式规则，让两者分工明确：ESLint 管质量，Prettier 管格式。

55.4 husky + lint-staged：提交前自动检查

不能指望人人自觉。用 Git 钩子在提交时自动对改动的文件跑检查：

# 安装与初始化 husky
npm install -D husky lint-staged
npx husky init
echo "npx lint-staged" > .husky/pre-commit
// package.json
{
  "lint-staged": {
    "*.{vue,js,ts}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["prettier --write"]
  }
}

只检查暂存区改动（lint-staged），而不是全量跑——否则老项目接规范时会被海量历史问题卡死。

55.5 Conventional Commits 提交规范

提交信息结构化，便于自动生成 changelog、定位回滚：

# 格式：<type>(<scope>): <subject>
feat(user): 新增用户批量导出功能
fix(router): 修复刷新后动态路由丢失
refactor(store): 拆分 user store 为三个模块
docs: 补充第 53 章权限流程图
chore: 升级 vite 到 5.4
type含义
feat新功能
fix修 bug
refactor重构（不改行为）
docs / style / chore文档 / 格式 / 构建与杂项
perf / test性能优化 / 测试

用 commitlint 在提交时校验格式，不规范的提交直接拦下：

npm install -D @commitlint/cli @commitlint/config-conventional
echo "module.exports = { extends: ['@commitlint/config-conventional'] }" > commitlint.config.cjs
npx husky add .husky/commit-msg "npx --no-install commitlint --edit"

55.6 分支模型与 Code Review 清单

分支模型做法适合
Trunk-based所有人短分支合回 main，频繁集成小团队、CI 成熟、发布频繁
Git Flowmain/develop/feature/release/hotfix 多层分支有固定版本周期、多版本并行维护

Code Review 检查清单

  • 逻辑：边界条件、空值、异步错误处理是否覆盖；
  • 安全：有没有硬编码密钥、有没有把用户输入直接渲染到模板；
  • 性能：明显的不必要重渲染、大列表无 key、多余请求；
  • 规范：命名、目录、提交信息是否符合本章约定；
  • 可测：核心逻辑是否抽成了可单测的纯函数/composable。
规范的目的是降低协作成本，不是增加仪式感。任何让团队觉得繁琐、开始想办法绕开的规则，都该被简化。

55.7 本章常见坑

  • 坑 1views 里塞满可复用组件：别处要用时只能复制粘贴。
  • 坑 2ESLint 与 Prettier 规则打架：没配 eslint-config-prettier，保存后反复横跳。
  • 坑 3lint-staged 写成全量检查：老项目提交慢到没人想用。
  • 坑 4提交信息随心所欲：回滚和找 changelog 时抓瞎。
  • 坑 5规范只写在文档里：没有 husky/commitlint 兜底，全靠自觉必失效。
