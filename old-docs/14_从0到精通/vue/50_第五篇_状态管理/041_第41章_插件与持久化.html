41.1 插件机制：pinia.use

Pinia 插件是一个函数，每次 store 初始化时都会被调用一次：

function myPiniaPlugin({ store, app, options }) {
  // store: 刚创建的 store 实例
  // app: 当前应用实例（app.use(pinia) 时传进来的）
  // options: defineStore 时的选项（一般用不到）

  // 你可以：
  // 1. 给 store 加新属性
  store.$hello = 'world'

  // 2. 订阅 store 的变化
  store.$subscribe(() => {})

  // 3. 返回要注入 store 的对象（会被合并到 store 上）
  return {
    someState: ref(0)
  }
}

// 注册：
const pinia = createPinia()
pinia.use(myPiniaPlugin)

插件能做什么

  • 给所有 store 加统一的字段/方法（比如 $reset、$log）；
  • 全局监听所有 store 的变化（埋点、日志、持久化）；
  • 注入第三方库实例（比如把 axios 包成 $http 挂到 store 上）；
  • SSR 下的状态注水/脱水。

41.2 手写 localStorage 持久化插件

// plugins/persistedState.js
export function persistedStatePlugin(options = {}) {
  return ({ store }) => {
    // 1. 初始化时：从 localStorage 读，写回 store
    const storageKey = options.key || `pinia-${store.$id}`
    const saved = localStorage.getItem(storageKey)
    if (saved) {
      store.$patch(JSON.parse(saved))
    }

    // 2. 订阅：state 变化时写回 localStorage
    store.$subscribe((_mutation, state) => {
      localStorage.setItem(storageKey, JSON.stringify(state))
    })
  }
}

// 使用：
const pinia = createPinia()
pinia.use(persistedStatePlugin({ key: 'my-app-state' }))

这个插件干了两件事：

  1. store 初始化时，从 localStorage 读上次保存的 state，$patch 进去；
  2. 订阅 state 变化，每次变化就序列化写回 localStorage。

就这么简单。但真实项目里你会遇到：序列化大对象性能差、敏感数据不该存、SSR 环境没有 localStorage——下一节的成熟插件都处理了这些。

41.3 pinia-plugin-persistedstate

社区成熟的插件，处理了各种边界：

npm i pinia-plugin-persistedstate
// main.js
import { createPinia } from 'pinia'
import piniaPluginPersistedstate from 'pinia-plugin-persistedstate'

const pinia = createPinia()
pinia.use(piniaPluginPersistedstate)
// stores/user.js
export const useUserStore = defineStore('user', {
  state: () => ({
    name: '',
    token: '',
    tempForm: {}
  }),

  // 开启持久化
  persist: {
    key: 'user-store',              // localStorage 的 key
    storage: localStorage,           // 存哪（默认 localStorage）
    pick: ['name', 'token']         // 只持久化这些字段（不写则全存）
    // 注：具体 API 以官方文档为准，不同版本字段名略有差异
  }
})
配置作用示例
keylocalStorage 的键名'user-store'
storage存到哪（localStorage/sessionStorage/自定义）localStorage
pick / paths只持久化指定字段['name', 'token']
serializer自定义序列化（默认 JSON）压缩、加密

41.4 SSR 下的持久化

SSR 环境有两个问题：

  1. 没有 localStorage：服务端跑 Node，浏览器 API 不存在——直接 localStorage.setItem 会报错；
  2. 每个用户请求是独立的 store 实例：要在服务端把初始 state 注水（hydrate），客户端再接管。

应对

  • 插件里判断 import.meta.env.SSR，服务端不跑 localStorage 逻辑；
  • 用成熟插件（pinia-plugin-persistedstate 已经处理 SSR）；
  • 服务端把 state 序列化成 HTML 里的 window.__PINIA_STATE__，客户端启动时读它注水。
提醒不要自己写 SSR 持久化——Nuxt/SSR 框架都有现成的 pinia 集成方案（如 @pinia/nuxt），用官方方案。

41.5 选择性持久化与敏感数据

不是所有 state 都该持久化。下面这些不要持久化：

  • 敏感数据：token、密码、身份证号——localStorage 是明文存的，XSS 一拿就走；token 应该用 httpOnly Cookie；
  • 大对象：整个购物车、长列表——每次序列化都卡；
  • 临时状态：表单草稿、UI 开关——刷新后没意义；
  • 服务端缓存：接口返回的数据——直接刷新接口比读缓存更快更新。

选择性持久化

persist: {
  key: 'user',
  pick: ['name', 'avatar']   // 只存这两个
  // token、tempForm、isLoggingIn 都不持久化
}

把 token 存 localStorage 是最常见的安全反模式。真要持久化登录态，用 httpOnly Cookie + 服务端校验，别让 JS 能拿到 token。

✎ 本章习题

A 基础给你的 userStore 接上 pinia-plugin-persistedstate，只持久化 name 和 avatar（不持久化 token）。刷新页面验证 state 能恢复。
B 进阶不依赖任何插件，手写一个持久化插件：支持 ① 配置 key ② pick 哪些字段 ③ 序列化失败时 catch 不崩。
C 挑战为什么 token 不应该存 localStorage？从 XSS 攻击的角度解释：攻击者拿到页面 JS 执行权后，能怎么读 localStorage？对比 httpOnly Cookie 为什么能防住这种攻击。
