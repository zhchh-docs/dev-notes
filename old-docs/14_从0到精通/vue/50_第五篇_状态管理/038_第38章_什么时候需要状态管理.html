38.1 局部状态 vs 全局状态

先给一个简单判断：你的状态是不是"只有这一个组件用"？

状态类型归属例子
UI 瞬时状态组件内弹窗开不开、hover 高亮、表单草稿
局部业务状态页面级组件当前列表的筛选条件、当前 tab
跨组件共享状态全局 store当前登录用户、购物车、主题
跨路由共享状态全局 store下单流程的中间数据（跨多页）
服务端缓存全局 store用户信息字典、全局配置

判断的核心问题："这个状态如果只属于一个组件，硬拆给它会不会更简单？" 如果答案是"会"，它就不该进全局 store。

38.2 不上 Pinia 的四种替代方案

① props + emit（父子组件）

<!-- 父 -->
<Child :value="x" @update="x = $event" />

<!-- 子 -->
<script setup>
const props = defineProps({ value: Number })
const emit = defineEmits(['update'])
</script>

适用：直接父子。缺点：隔代传递要一层层透传（prop drilling）。

② provide / inject（祖孙组件）

// 祖先
provide('user', userRef)
// 后代
const user = inject('user')

适用：跨多级但只在一个子树里共享。缺点：依赖关系隐式（看不到谁提供、谁消费），类型推导弱。

③ 组合式函数（同页面多组件共享）

// useCart.js
const cart = reactive([])    // 模块级单例
export function useCart() {
  function add(item) { cart.push(item) }
  return { cart, add }
}

注意：上面这个写法因为 cart 定义在模块顶层，所有组件 import 后拿到的是同一份——这就是"模块单例"。它和 Pinia 的差别是：没有 devtools、没有插件机制、没有 $subscribe、没有持久化。

④ 模块单例

上面 useCart 就是。它能解决 80% 的"跨组件共享"问题，但你失去了 Pinia 提供的：

  • devtools 时间旅行（state 变化回放）；
  • 插件系统（持久化、日志、跨 tab 同步）；
  • $subscribe 监听整个 store 变化；
  • SSR 下的状态隔离（模块单例在 SSR 会串用户！）。
方案跨组件范围类型推导SSR 安全
props/emit直接父子好安全
provide/inject一个子树弱安全
组合式函数（模块单例）整个应用好不安全（串用户）
Pinia store整个应用好安全（每个请求新建 pinia）

38.3 什么时候必须上全局 store

下面三个硬信号中任意一个命中，就别再用 props/emit 硬扛了：

  1. 跨路由共享：用户在 A 页面填了一半表单，跳到 B 页面再回来还得保留——这种状态属于整个"流程"，不属于某个组件。
  2. 深层嵌套 + 跨多级共享：prop drilling 已经透传到第四、五层，每层组件都只是"传话筒"——这时候 provide/inject 也救不了，类型和来源都不清。
  3. 需要副作用能力：要持久化到 localStorage、要在 devtools 看 state 变化、要跨 tab 同步、要监听整个 store 变化做日志——这些是 store 库的能力，自己写组合式函数要重新造一遍。

38.4 "什么都塞 store"的坏味道

上 store 容易上瘾，下面这些是典型坏味道：

  • 坏味道 1把每个表单字段都塞进 store：一个"新建订单"表单有 20 个字段，全进 store。结果 store 里全是"只在当前表单页有意义"的临时状态，离开页面还要手动 reset——不如直接在页面组件里 reactive 一个 form 对象。
  • 坏味道 2把 UI 状态塞进 store："侧栏开不开"、"当前 hover 的卡片"。这些只在当前布局组件里有意义，进 store 会让任何组件都能改它——调试时你不知道是谁改的。
  • 坏味道 3用 store 做"跨组件通信"而不是"共享状态"：比如 store 里塞一个 globalEventBus，任何组件都能 emit——这不是状态管理，是事件总线，调试时根本不知道谁触发了谁。
  • 坏味道 4一个巨大的 store 装所有东西：user store 里既装登录用户、又装购物车、又装主题、又装搜索历史——任何字段变化都 $subscribe 到所有组件。应该按业务域拆 store。

判断标准："这个状态如果被任何组件随意改，会不会引入难以追踪的 bug？" 如果会，它就不该是全局的。

38.5 引入状态管理的成本

Pinia 不是免费的。引入前估算一下：

成本说明应对
心智负担团队要懂 store 拆分、action 规范约定目录、命名、action 边界
调试链路变长组件 → store → action → 接口，跨文件靠 devtools 追踪
测试成本store 本身要单测、组件测试要 mock store第 45 章专门讲
SSR 安全模块单例会串用户，Pinia 要每个请求新建用 Pinia 就对了
包体积Pinia ~ 10KB gzip对绝大多数应用可忽略

小项目（< 10 个页面、没有跨路由流程）用 props/emit + 组合式函数就够；中大型项目（> 20 个页面、有共享业务域）上 Pinia。

✓ 本章小结

要点一句话
