42.1 setup store 写法

// stores/counter.js（setup 写法）
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useCounterStore = defineStore('counter', () => {
  // state：ref / reactive
  const count = ref(0)
  const history = ref([])

  // getters：computed
  const double = computed(() => count.value * 2)

  // actions：普通函数
  function increment() {
    count.value++
    history.value.push('+1')
  }

  function incrementBy(n) {
    count.value += n
  }

  // 返回要暴露的东西（必须 return，不 return 的就是私有）
  return { count, history, double, increment, incrementBy }
})

和选项式的对应关系

概念选项式setup 写法
statestate: () => ({...})ref() / reactive()
gettersgetters: {...}computed()
actionsactions: {...}普通 function
私有字段没有（都在 this 上）不 return 就是私有
thisthis 指向 store没有 this，直接用闭包变量

42.2 两种写法的选择

没有绝对优劣，看场景：简单 CRUD 用选项式，复杂逻辑用 setup。

用选项式的场景

  • store 结构简单（几个 state + 几个 action）；
  • 团队习惯 Vue2/Vuex 风格；
  • 需要 $reset（选项式原生支持）。

用 setup 的场景

  • store 里有复杂逻辑（多个 ref 互相关联、watch、组合式函数）；
  • 需要私有变量（不暴露给组件）；
  • 要和组合式函数配合（useXxx() 内部逻辑直接搬进 store）；
  • TS 类型推导更自然（不用在 getters 里写 this.xxx）。
实际建议：新项目里我推荐默认用 setup 写法——和 <script setup> 思路一致，学习成本低。选项式留给老项目维护。

42.3 在 store 里调另一个 store

一个 store 需要用到另一个 store 时，直接在 action 或 getter 里调用：

// stores/cart.js
import { defineStore } from 'pinia'
import { useUserStore } from './user'

export const useCartStore = defineStore('cart', () => {
  const items = ref([])

  async function checkout() {
    // ❌ 不要在顶层调 useUserStore() —— store 还没初始化完
    // const userStore = useUserStore()

    // ✅ 在 action 里调：此时 pinia 已经就绪
    const userStore = useUserStore()
    if (!userStore.isLoggedIn) {
      throw new Error('请先登录')
    }

    const res = await fetch('/api/checkout', {
      method: 'POST',
      body: JSON.stringify({
        items: items.value,
        userId: userStore.id
      })
    })
    return res.json()
  }

  return { items, checkout }
})

为什么不能在顶层调

setup 函数在 store 第一次被使用时执行。这时候 pinia 实例可能还没完全就绪，或者另一个 store 还没初始化。在顶层调 useOtherStore() 会拿到 undefined 或报错。

正确做法：在 action / getter 内部调——那时候 pinia 已经完全初始化，哪个 store 都能拿到。

42.4 跨 store 依赖与循环引用

常见的依赖关系

// userStore：存登录用户
// cartStore：购物车，checkout 时需要 userStore 的 userId
// orderStore：下单后要更新 cartStore 和 userStore 的积分

// 依赖图：
// cartStore  ──>  userStore
// orderStore ──>  cartStore
// orderStore ──>  userStore

循环引用长什么样

// ❌ 坏味道：A 调 B、B 又调 A
// storeA.action: 调 storeB.doXxx()
// storeB.action: 调 storeA.doYyy()

这通常意味着职责没划清。解法：

  1. 把共享逻辑抽到第三个 store：A 和 B 都依赖它，互不依赖；
  2. 用事件总线：A 改 state，B 订阅它的变化（$subscribe）；
  3. 在组件层编排：组件依次调 A.action() 和 B.action()，不让 store 互调。
模式适用风险
B 单向依赖 A常见低
A 和 B 都依赖 C共享逻辑抽出来低
A 调 B、B 又调 A职责不清的信号高（循环）
$subscribe 跨 store 同步解耦中（调试难）

发现 store 之间循环引用时，不要硬着头皮修——退一步看：是不是把这两个 store 拆错了？正确的拆法往往能自然打破循环。

42.5 本章常见坑

  • 坑 1在 setup store 顶层调 useOtherStore()：拿到 undefined。放进 action/getter 里调。
  • 坑 2setup store 里没 return ref：组件访问不到。setup 写法必须显式 return。
  • 坑 3setup store 解构 state 没 storeToRefs：和选项式一样的坑。任何 store 都要 storeToRefs。
  • 坑 4跨 store 直接改对方的 state：比如 cartStore 里写 userStore.points += 10。应该调 userStore 的 action，而不是直接改。
  • 坑 5循环引用没发现：本地跑得好好的，某个边缘路径才死循环。code review 时画一下依赖图。
