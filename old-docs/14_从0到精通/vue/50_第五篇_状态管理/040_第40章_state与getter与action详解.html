40.1 state：$patch、$reset、直接赋值

三种改 state 的方式

const store = useCounterStore()

// ① 直接改：简单，但多个字段要分多次
store.count = 1
store.history.push(1)

// ② $patch 对象式：一次合并多个字段
store.$patch({
  count: 1,
  history: [...store.history, 1]   // 注意 history 要整体替换（因为不能直接改引用）
})

// ③ $patch 函数式：最灵活，能拿到 state 直接 mutate
store.$patch((state) => {
  state.count = 1
  state.history.push(1)   // 直接 push，不用整体替换
})
方式适用注意
直接赋值改 1-2 个简单字段数组/对象要整体替换
$patch 对象式一次性改多个顶层字段嵌套对象要手动展开
$patch 函数式改嵌套、需要计算最灵活，推荐复杂场景

$reset

store.$reset()   // 把 state 重置回初始值（state() 返回的那个对象）

注意：setup store 不支持 $reset（因为没有"选项式 state 函数"可以重新调）。选项式 store 才能用。setup store 要自己写一个 reset action。

TS 自动推断

export const useUserStore = defineStore('user', {
  state: () => ({
    name: 'unknown',     // 自动推断为 string
    age: 0,              // 自动推断为 number
    tags: [] as string[] // 空数组要显式标注，否则推断为 never[]
  })
})

40.2 getters：缓存与参数化

getter 的 this 与缓存

getters: {
  // 方式一：参数 state（推荐，TS 推导好）
  double: (state) => state.count * 2,

  // 方式二：用 this 访问其他 getter
  doublePlusOne() {
    return this.double + 1
  },

  // 访问整个 store 的其他 state 也行
  recentHistory() {
    return this.history.slice(-5)
  }
}

getter 和 computed 一样有缓存：依赖没变，多次读只算一次。

参数化 getter：返回一个函数

getters: {
  // 根据 id 找商品 —— 返回一个函数，调用时传参
  getProductById: (state) => (id) => {
    return state.products.find(p => p.id === id)
  }
}

// 组件里：
store.getProductById(42)   // 找到 id=42 的商品
提醒参数化 getter 没有缓存——每次调用都会重新执行那个返回的函数。高频调用、大数组查找时要注意性能；这时候不如直接在 action 里写或用普通函数。

40.3 actions：this 与异步

this 指向 store 本身

actions: {
  increment() {
    this.count++               // this 就是 store
    this.history.push('+1')
    this.double                // 也能读 getter
  },
  incrementBy(n) {
    this.count += n
  }
}

异步 action

actions: {
  async fetchUser(id) {
    const res = await fetch(`/api/users/${id}`)
    const data = await res.json()
    this.name = data.name
    this.age = data.age
    return data        // 返回 Promise，调用方可以 await
  },

  // action 里调另一个 action
  async loadAndSetName(id) {
    const data = await this.fetchUser(id)   // 直接 this 调
    this.history.push(`loaded ${id}`)
  }
}
// 组件里调用
async function onClick() {
  try {
    const data = await userStore.fetchUser(1)
    console.log('loaded', data)
  } catch (e) {
    console.error('加载失败', e)
  }
}
场景怎么写说明
同步改 state直接 this.xxx最简单
异步请求后改 stateasync actionawait 之后 this.xxx
action 调另一个 actionthis.otherAction()同一 store 内
action 调其他 storeuseOtherStore()（在 action 内调）第 42 章展开

40.4 $subscribe / $onAction / $dispose

$subscribe：监听 state 变化

const unsubscribe = userStore.$subscribe((mutation, state) => {
  // mutation: { type, storeId, events } —— 本次变化的描述
  // state: 当前最新 state
  console.log('user store 变了', mutation.type)
  // 典型用途：持久化、日志、广播
  localStorage.setItem('user', JSON.stringify(state))
})

// 不再需要时取消订阅
unsubscribe()

$onAction：监听 action 调用

const stop = userStore.$onAction(({
  name,        // action 名
  store,       // store 实例
  args,        // 调用参数
  after,       // 注册"action 成功后"的回调
  onError      // 注册"action 失败"的回调
}) => {
  const start = Date.now()
  after((result) => {
    console.log(`action ${name} 耗时 ${Date.now() - start}ms`)
  })
  onError((err) => {
    console.error(`action ${name} 失败`, err)
  })
})

$dispose

// 默认情况下，$subscribe / $onAction 在组件卸载时不会自动停
// 要手动停：
userStore.$subscribe(cb, { detached: true })   // 组件卸载后还在
// 或者组件卸载时自己调 unsubscribe()
$subscribe 监听"数据变了"，$onAction 监听"方法被调了"——前者做持久化/日志，后者做埋点/性能监控。

40.5 本章常见坑

  • 坑 1数组直接改索引：state.arr[0] = x 在 Pinia 里是 OK 的（Vue3 Proxy 能感知），但读代码的人可能以为不响应——用 $patch 函数式更清晰。
  • 坑 2setup store 调 $reset：报错。setup store 要自己写 reset action。
  • 坑 3异步 action 里忘了 try/catch：未捕获的 rejection 会冒泡，可能导致整个组件崩溃。
  • 坑 4参数化 getter 被高频调用：每次都重算。大数组查找时改用 computed + Map 索引。
  • 坑 5$subscribe 里直接改 state：会触发新一轮 $subscribe（无限循环）。要改 state 应该在 action 里改。

✎ 本章习题

A 基础给 userStore 写三个 action：① fetchUser（async，请求接口）② setName（同步改 name）③ reset（重置 state）。在组件里调用 fetchUser，然后 await 之后读 userStore.name 验证。
B 进阶给 userStore 加一个参数化 getter getOrderById（在 orders 数组里按 id 找）。然后 $subscribe 这个 store，把 state 持久化到 localStorage。刷新页面后验证 state 能恢复。
C 挑战用 $onAction 实现一个简单的"action 性能监控"：把每个 action 的耗时打在控制台。然后故意制造一个失败的 action（接口 404），验证 onError 回调能捕获。
