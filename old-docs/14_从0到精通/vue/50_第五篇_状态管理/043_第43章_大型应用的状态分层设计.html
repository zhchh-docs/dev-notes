43.1 状态的四种分类

类别例子归属
UI 瞬时状态弹窗开关、hover、当前 tab、表单草稿组件内 / 页面级 composable
领域状态用户信息、购物车、订单列表、权限Pinia store
服务端缓存字典数据、配置项、接口返回的列表Pinia store（带缓存策略）
会话状态登录 token、当前工作流步骤、临时 tokenPinia store（敏感的用 Cookie）

判断一个状态属于哪类，问自己三个问题："跨不跨组件？跨不跨路由？刷不刷新还要保留？"

43.2 store 模块划分原则

按业务域拆，不按"技术类型"拆

// ❌ 坏味道：按"数据类型"拆
stores/
  users.js        // 所有和用户相关的
  products.js     // 所有和商品相关的
  orders.js       // 所有和订单相关的

// ✅ 好味道：按业务域拆（电商场景）
stores/
  user/
    profile.js      // 当前登录用户
    auth.js         // 登录、token、权限
  shop/
    catalog.js      // 商品列表、筛选
    cart.js         // 购物车
  order/
    checkout.js     // 下单流程
    history.js      // 历史订单

拆 store 的信号

  • 两个 state 经常一起被同一个 action 改 → 可以放一个 store；
  • 两个 state 被不同组件、不同页面独立用 → 拆开；
  • 一个 store 超过 200 行 → 考虑拆；
  • 一个 store 被超过 10 个组件 import → 考虑拆。
坏味道原因解法
一个 store 装所有任何字段变化都通知所有组件按业务域拆
store 之间大量互调职责不清抽共享逻辑到第三个 store
组件直接改 store state绕过 action，难追踪约定必须通过 action 改

43.3 store 与组合式函数的边界

第三篇的组合式函数（composable）和 Pinia store 都能装"可复用逻辑"，怎么分？

维度composablePinia store
状态共享每次调用都新建一份全局单例，所有组件共享
是否需要 devtools不需要需要
是否需要持久化不需要需要
是否跨路由否是
典型例子useMouse、useFetch、useFormuseUserStore、useCartStore

判断流程

  1. 这个状态要不要被多个组件同时看到？不要 → composable；
  2. 要的话，要不要跨路由？不要 → 可能还是 composable（provide 即可）；
  3. 要不要 devtools / 持久化 / 插件？要 → store。

常见的中间态：一个 composable 内部用了模块级 ref（单例），这本质上就是"手写的迷你 store"——没有 devtools、没有插件。如果逻辑变复杂，建议直接迁到 Pinia store。

43.4 状态形状：扁平化

坏味道：深层嵌套

// ❌ 深层嵌套：找一个商品的评论要绕三层
state: () => ({
  categories: [
    {
      id: 1,
      name: '数码',
      products: [
        {
          id: 101,
          name: '键盘',
          reviews: [
            { id: 1, content: '好用' }
          ]
        }
      ]
    }
  ]
})

好味道：扁平化 + 索引

// ✅ 扁平化：每个实体一张表，用 id 关联
state: () => ({
  categories: {
    byId: {
      1: { id: 1, name: '数码', productIds: [101] }
    }
  },
  products: {
    byId: {
      101: { id: 101, name: '键盘', reviewIds: [1] }
    }
  },
  reviews: {
    byId: {
      1: { id: 1, content: '好用' }
    }
  }
})

为什么要扁平化

  • 查找快：按 id 直接取，不用递归遍历；
  • 更新简单：改一条评论只动 reviews.byId[1]，不用找到它在 categories 里的路径；
  • 响应式友好：深层嵌套会导致 reactive 的代理链很长，性能差。

中小型应用（< 10 个实体）可以不严格扁平化；但一旦有"订单→商品→评论→用户"这种多对多关系，强烈建议用 byId 索引。

43.5 目录与命名约定

src/
├── stores/
│   ├── index.js              # 导出所有 store 的入口
│   ├── user/
│   │   ├── profile.js        # useUserProfileStore
│   │   └── auth.js           # useAuthStore
│   ├── shop/
│   │   ├── catalog.js
│   │   └── cart.js
│   └── order/
│       ├── checkout.js
│       └── history.js
├── composables/              # 局部可复用逻辑（不进 store）
│   ├── useForm.js
│   └── useMouse.js
└── ...
约定规则例子
文件名camelCase，业务域小写user/profile.js
store id和文件名一致defineStore('profile', ...)
导出函数名useXxxStoreuseUserProfileStore
action 命名动词开头fetchUser、resetCart

C 挑战把一个嵌套 3 层的 state（categories → products → reviews）重构成扁平化 byId 结构。写两个 helper：getProductReviews(productId) 和 addReview(productId, review)，对比嵌套写法的复杂度。
