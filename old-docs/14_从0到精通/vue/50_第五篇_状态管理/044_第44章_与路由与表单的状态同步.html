44.1 URL query 作为外部状态

URL 是用户能看到、能分享、能书签的"外部状态"。筛选条件放 URL 比放 store 更合理——因为它要被分享、要被刷新恢复。

// 从 URL 读：
import { useRoute, useRouter } from 'vue-router'

const route = useRoute()
const router = useRouter()

// 当前 URL: /products?category=phone&page=2
const category = route.query.category   // 'phone'
const page = Number(route.query.page || 1)

// 写回 URL（不刷新页面）：
router.replace({ query: { ...route.query, category: 'laptop' } })
// 新 URL: /products?category=laptop&page=2
数据放 URL放 store
列表筛选条件✅ 分享/刷新可恢复❌ 刷新丢失
当前 tab看产品需求看产品需求
登录 token❌ 安全问题✅ store + Cookie
购物车内容❌ 太大✅ store

44.2 列表筛选与 URL 双向同步

典型场景：商品列表页，用户选分类、改搜索词、翻页。这些变化要：

  1. 立即触发接口请求；
  2. 写回 URL（让链接可分享）；
  3. 用户改 URL（前进/后退）时，store 状态跟着变。
<script setup>
import { useRoute, useRouter } from 'vue-router'
import { useProductStore } from '@/stores/product'
import { watchDebounced } from '@vueuse/core'

const route = useRoute()
const router = useRouter()
const productStore = useProductStore()

// 1. 初始化：从 URL 读筛选条件到 store
productStore.setFilters({
  category: route.query.category || '',
  keyword: route.query.keyword || '',
  page: Number(route.query.page || 1)
})

// 2. store 变化 → 防抖写回 URL
watchDebounced(
  () => productStore.filters,
  (filters) => {
    router.replace({
      query: {
        category: filters.category || undefined,
        keyword: filters.keyword || undefined,
        page: filters.page > 1 ? filters.page : undefined
      }
    })
  },
  { debounce: 300 }
)

// 3. URL 变化（前进/后退）→ store 跟着变
watch(
  () => route.query,
  (query) => {
    productStore.setFilters({
      category: query.category || '',
      keyword: query.keyword || '',
      page: Number(query.page || 1)
    })
  }
)
</script>

写回 URL 一定要防抖（300ms）：否则用户每输一个字母就 router.replace 一次，历史栈爆炸，浏览器性能也卡。

44.3 表单与 store 的同步

表单数据和 store 同步有三种模式，按"提交时序"选：

模式 A：v-model 直连 store

<!-- 简单表单：直接绑 store 字段 -->
<input v-model="userStore.name" />

适用：小表单、不需要"取消"按钮、不需要 dirty 检测。

问题：用户改了但没提交，store 已经变了——其他组件看到"半成品"。

模式 B：表单本地维护，提交时才写 store

<script setup>
import { reactive, watch, computed } from 'vue'
import { useUserStore } from '@/stores/user'

const userStore = useUserStore()

// 表单本地副本
const form = reactive({ ...userStore.profile })
const original = JSON.stringify(form)   // 用于 dirty 检测

// store 变（比如接口刷新后）→ 同步到表单
watch(
  () => userStore.profile,
  (val) => Object.assign(form, val),
  { deep: true }
)

const isDirty = computed(() => JSON.stringify(form) !== original)

function submit() {
  userStore.updateProfile(form)   // 提交时才写 store
}

function reset() {
  Object.assign(form, userStore.profile)   // 取消时回滚
}
</script>

模式 C：watch store 到表单

和模式 B 类似，但方向反了：store 是真源，表单只是"展示层"。store 变（接口返回、其他组件改）→ watch 同步到表单。表单改完直接提交（不本地维护）。

模式适用问题
A 直连 store简单表单半成品会暴露给其他组件
B 本地副本需要取消/dirty 检测要同步双向
C store 是真源表单只是展示改了没提交就丢

44.4 刷新后状态恢复

用户刷新页面后，哪些状态要恢复？按优先级：

  1. URL 里的（筛选条件）：自动恢复，因为 URL 没变；
  2. 持久化的 store（用户信息、购物车）：用 pinia-plugin-persistedstate 从 localStorage 读；
  3. 服务端数据（列表、详情）：刷新后重新发请求拉。

典型恢复链路

// main.js 启动时
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import piniaPersist from 'pinia-plugin-persistedstate'

const pinia = createPinia()
pinia.use(piniaPersist)   // 插件会在每个 store 初始化时从 localStorage 读

const app = createApp(App)
app.use(pinia)
app.mount('#app')

// 组件挂载时再根据 URL 拉接口数据
// onMounted(() => productStore.fetchList())
提醒不要把"刷新后恢复"和"跨路由保留"混为一谈：跨路由保留靠 store 单例（不刷新页面），刷新恢复靠持久化或重新拉接口。

44.5 本章常见坑

  • 坑 1筛选变化不防抖写回 URL：每次输入都 router.replace，历史栈爆炸。
  • 坑 2v-model 直连 store 但没提交按钮：用户改了一半，其他组件看到半成品。
  • 坑 3watch route.query 没做防抖：用户快速翻页时，接口请求乱序返回（参考第 34 章 onCleanup）。
  • 坑 4把大对象塞 URL query：URL 超长、被截断。只放简单类型（数字、字符串、id）。
  • 坑 5刷新后不重新拉接口：靠 localStorage 读旧数据，但服务端数据已变。

✓ 本章小结

要点一句话
URL 是外部状态筛选条件放 URL，可分享、可刷新恢复
双向同步store 防抖写回 URL；URL 前进后退同步到 store
表单模式直连 / 本地副本 / store 真源，按场景选
dirty 检测JSON.stringify 对比初始值

✎ 本章习题

A 基础给一个"商品列表页"实现筛选与 URL 同步：选分类（手机/电脑）、翻页。URL 变化时 store 跟着变；store 变化时防抖 300ms 写回 URL。
B 进阶给一个"用户设置表单"实现：本地副本、dirty 检测、取消按钮（回滚）、提交按钮（写 store）。测试：改了不提交直接离开，store 不变。
C 挑战为什么 URL 里不要放敏感数据（如 token）？从 ① 浏览器历史记录 ② 服务端访问日志 ③ Referer 头 三个角度解释。
