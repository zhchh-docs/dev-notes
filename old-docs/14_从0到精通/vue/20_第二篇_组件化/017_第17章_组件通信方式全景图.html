◆本章目标

  • 列出 Vue 中全部八种通信方式及其适用距离；
  • 能针对任意场景选出最合适的一种（并说明理由）；
  • 掌握跨层通信 provide/inject 与"父调子"的 ref + defineExpose；
  • 知道全局状态与事件总线的适用边界与代价；
  • 避免两种极端：props 疯狂透传与什么都塞进全局。

17.1 八种方式一览

方式方向 / 距离传什么典型场景
props父 → 子（一层）数据所有父子传值
emit子 → 父（一层）事件 + 参数子组件报告用户操作
v-model父子双向（一层）数据（语法糖）表单控件、弹窗显隐
插槽父 → 子（内容）模板结构布局、卡片、表格单元格
作用域插槽子 → 父（渲染数据）数据 + 结构表格行、列表项定制
provide / inject祖先 → 任意后代（跨层）数据 / 方法主题、表单上下文、组件库内部
ref + expose父 → 子（命令式）调用子组件方法表单校验、播放器控制、重置
Pinia / 事件总线任意组件之间全局状态 / 消息登录态、购物车、跨页面通知

17.2 父子：props / emit / v-model

这三者已在第 11-13 章详讲，这里只给选型要点：

方式用在哪反模式
props父给子"输入"子组件直接改 props
emit子向父"报告"用 emit 同步一份本可用 computed 的值
v-model父子需要双向（表单、显隐）双向绑太多导致状态分散
 
<!-- 典型组合：父持有数据，子受控渲染 -->
<template>
  <UserForm
    v-model:name="form.name"
    :loading="loading"
    @submit="onSubmit"
  />
</template>

父子通信的黄金组合：props 向下、emit 向上。90% 的需求到这里就解决了。

17.3 父到子内容：插槽

插槽解决的是"结构的传递"，而不是数据。判断标准：

  • 要传的是一段模板（按钮组、表头、空状态）→ 插槽；
  • 要传的是一个值（字符串、数字、对象）→ props。
<!-- ❌ 用 props 传结构：只能靠 v-html，危险且不可交互 -->
<Card :footer-html="'<button>确定</button>'" />

<!-- ✅ 用插槽：真实组件，可绑定事件 -->
<Card>
  <template #footer>
    <button @click="submit">确定</button>
  </template>
</Card>

作用域插槽（第 15 章）则是"子把数据交给父渲染"，是表格/列表组件的标准解法。

17.4 祖孙跨层：provide / inject

当组件层级很深（如 表单 → 表单项 → 输入框 → 图标），层层透传 props 会让中间组件变成"传声筒"。provide/inject 让祖先直接"投放"数据，任意后代按需"注入"。

<!-- 祖先：Form.vue -->
<script setup>
import { provide, ref } from 'vue'
const formData = ref({})
const errors = ref({})

// 投放：key + value
provide('form-context', { formData, errors, validate })
function validate() { /* ... */ }
</script>

<!-- 任意后代：FormInput.vue（中间隔了多少层都行） -->
<script setup>
import { inject } from 'vue'
const { formData, errors } = inject('form-context')
</script>
维度props 透传provide / inject
层级逐层传递跨任意层
依赖可见性显式（看 props 就知道）隐式（需搜索 inject）
重构安全高（改名会报错）低（字符串 key 易写错）
适用通用组件强耦合的组件族（Form/FormItem、Tabs/TabPane）

provide/inject 会隐藏依赖关系，是"耦合度较高"的方案。它最适合同一组件族内部（你自己写的 Form 与 FormItem），不适合跨业务模块共享数据——那是 Pinia 的活。第 18 章详讲。

17.5 父调子：ref + expose

props/emit 是"声明式"的；有时父组件需要命令式地调用子组件方法（校验表单、播放视频、重置状态）。

<!-- 子组件：显式暴露接口 -->
<script setup>
import { ref } from 'vue'
const value = ref('')
function validate() { return value.value.length > 0 }
function reset() { value.value = '' }

// 只暴露这两个方法（不写则父组件拿不到任何东西）
defineExpose({ validate, reset })
</script>

<!-- 父组件 -->
<template>
  <MyInput ref="inputRef" />
  <button @click="onSubmit">提交</button>
</template>

<script setup>
import { ref } from 'vue'
const inputRef = ref(null)

async function onSubmit() {
  const ok = inputRef.value?.validate()   // 调用子组件方法
  if (!ok) return
  // 提交...
}
</script>
注意在 <script setup> 下组件默认是封闭的：父组件通过 ref 拿到的实例里没有内部方法，必须 defineExpose 显式开放。这是 Vue3 的封装性改进（Vue2 中默认全暴露）。

把 ref + expose 当作"逃生舱"：能用 props/emit 声明式解决的，就别用命令式调用——后者让父子耦合变紧，且难以单测。

17.6 全局共享：Pinia

当数据被多个不相邻的组件共享，或需要跨路由/页面保留时，提升到 Pinia（第五篇详讲）。

// stores/user.js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useUserStore = defineStore('user', () => {
  const token = ref(localStorage.getItem('token') || '')
  const profile = ref(null)
  const isLogin = computed(() => !!token.value)

  async function login(payload) {
    const res = await fetch('/api/login', { method: 'POST', body: JSON.stringify(payload) })
    const data = await res.json()
    token.value = data.token
    profile.value = data.user
  }
  function logout() { token.value = ''; profile.value = null }

  return { token, profile, isLogin, login, logout }
})
<!-- 任意组件：无需层层传递 -->
<script setup>
import { useUserStore } from '@/stores/user'
const user = useUserStore()
</script>

<template>
  <span v-if="user.isLogin">{{ user.profile.name }}</span>
  <button v-else @click="user.login({ ... })">登录</button>
</template>
判断问题结论
这个数据只有父子两层用？用 props/emit，不要上 Pinia
兄弟组件要共享？提升到最近公共父组件；层级太深才考虑 Pinia
跨页面/刷新后仍需保留？Pinia（+ 持久化插件）
是服务端数据（列表、详情）？通常不需要 Pinia，用请求缓存（第 43 章）

17.7 事件总线：mitt 及其代价

Vue3 移除了实例上的 $on/$off/$emit，官方推荐用 mitt 之类的库做全局事件总线。

// utils/bus.js
import mitt from 'mitt'
export const bus = mitt()

// A 组件（任意位置）
bus.emit('refresh-list', { id: 1 })

// B 组件
import { onMounted, onUnmounted } from 'vue'
onMounted(() => bus.on('refresh-list', handler))
onUnmounted(() => bus.off('refresh-list', handler))   // 必须清理！
事件总线的三大问题：
  • 不可追踪：不知道谁发的、谁收的，调试时只能全局搜索事件名；
  • 生命周期风险：忘记 off 会内存泄漏，且回调可能作用于已销毁的组件；
  • 时序依赖：组件还没挂载就 emit，消息直接丢失。

判断：需要"状态共享"用 Pinia；只有"一次性通知"（如"刷新一下"）才适合事件总线，且用完即弃、务必在卸载时 off。

17.8 选型决策树

要传的东西是什么？
├─ 一个值 / 对象 ────────────► 父子？props（+ emit 回传）
│                              跨多层？provide/inject（同组件族）
│                              任意组件？Pinia
├─ 一段模板结构 ─────────────► 插槽（普通 / 作用域）
├─ 双向同步（表单、显隐）────► v-model（modelValue / defineModel）
├─ 调用子组件方法 ───────────► ref + defineExpose（逃生舱）
├─ 一次性通知（刷新/跳转）───► 事件总线（mitt，务必 off）
└─ 服务端数据 ──────────────► 请求层 + 缓存（不一定需要 Pinia）

优先级（从高到低）：
props/emit > v-model > 插槽 > provide/inject（组件族内） > Pinia > 事件总线

记住这条经验：方案越"远"，耦合越隐蔽、越难重构。先用最近的方案，不行再往远走。

17.9 本章常见坑

  • 坑 1props 透传地狱：中间组件只为转发 props 而存在。解决：用 provide/inject、插槽，或把状态提升到更合理的层级。
  • 坑 2什么都塞进 Pinia：本地 UI 状态（某个弹窗是否展开）也放全局，导致 store 膨胀、组件不可复用。
  • 坑 3inject 拿到 undefined：祖先没有 provide，或 key 写错（大小写/空格）。建议 provide 时给默认值或用 Symbol 作 key。
  • 坑 4ref 拿不到子组件方法：忘了 defineExpose；或子组件是异步组件还没加载完。
  • 坑 5事件总线忘记 off：组件反复挂载导致回调重复执行 N 次。
  • 坑 6用 emit 在兄弟间通信：emit 只能向上到直接父组件，兄弟之间要走父组件中转或 Pinia。
