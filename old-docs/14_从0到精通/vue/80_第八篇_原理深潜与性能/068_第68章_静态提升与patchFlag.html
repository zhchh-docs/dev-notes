68.1 静态提升 hoistStatic

模板里有大量永远不变的节点（如纯文字标题、静态图标）。每次 render 都新建 VNode 是浪费。静态提升把它们提到 render 函数外，只创建一次、反复复用。

// 模板里：<div><span>静态标题</span> {{ msg }}</div>

// 未提升：每次 render 都新建 span 的 VNode
// 提升后（编译产物简化）：
const _hoisted_1 = /*#__PURE__*/_createElementVNode("span", null, "静态标题", -1)
export function render(_ctx) {
  return (_openBlock(), _createElementBlock("div", null, [
    _hoisted_1,                 // 直接复用，不再新建
    _toDisplayString(_ctx.msg)  // 动态部分
  ]))
}

那个 -1 表示这个节点是静态的，diff 时可以直接跳过。

68.2 patchFlag：标记哪里是动态的

静态节点跳过了，动态节点也要精确知道"哪一部分动了"。patchFlag 是编译期打上的位标记，运行时只比较标记出的那部分 props。

patchFlag含义
TEXT只有文本内容是动态的
CLASS只有 class 动态
STYLE只有 style 动态
PROPS某些属性动态（且会记录具体是哪几个）
FULL_PROPS动态属性名（如带动态 key），无法静态追踪
KEYED_FRAGMENT / UNKEYED_FRAGMENTv-for 列表是否带 key
 
// <div :class="box">{{ msg }}</div>
// 编译产物：只有 class 与 text 是动态
_createElementVNode("div", { class: _ctx.box }, _toDisplayString(_ctx.msg),
  1 /* CLASS */ + 8 /* TEXT */)
// 运行时 diff：知道只需比对 class 和 text，不用全 props 扫描

68.3 cacheHandlers 与 block tree

  • cacheHandlers：事件处理函数在模板里会被缓存（_cache[0]），避免每次 render 新建函数造成不必要的 props 更新；
  • block tree：block 是"收集动态节点"的容器。render 返回 block，block 只记录动态子节点（dynamicChildren），diff 时跳过所有静态子树，直接遍历动态节点。

图 68-1 block tree 的动态收集（示意）

这三项优化合起来的效果：静态节点不建、动态节点精确定位、事件函数不重复，diff 的工作量被压到最小。

// 对比：没有优化时，每次 render 都重新创建所有 VNode
// 优化后：静态 span 复用 _hoisted_1，动态 div 带 patchFlag(8=TEXT)
_createElementVNode("span", null, "静态标题", -1)   // -1=静态
_createElementVNode("div", null, _toDisplayString(msg), 8) // 8=TEXT
注意使用 v-if / v-for 这类结构性指令会让节点变成 fragment，动态追踪范围变大——这也是为什么列表一定要写稳定 key。

68.4 block tree 与 dynamic children 的边界

block 的设计是"收集整棵子树里的动态节点"，让 diff 不必遍历静态子树。但 v-if / v-for 这类结构性指令会改变树的形态，编译器会把这些位置标记出来，避免 block 漏追踪。

模板写法对 block 的影响为什么
纯静态 <p>a</p>整棵提升，diff 跳过无动态绑定
{{ msg }} 插值该节点打 TEXT 标记只追踪文本
v-if / v-else生成 block fragment，两端都纳入追踪结构会增删
v-for 列表整块 KEYED_FRAGMENT，按 key 复用顺序变化时靠 key 识别身份
 
// v-for 编译后带 KEYED_FRAGMENT(=12)
// <div v-for="u in list" :key="u.id">{{ u.name }}</div>
_createElementBlock(_Fragment, null,
  (openBlock(true), createElementBlock(_Fragment, null, renderList(list, u =>
    (openBlock(), createBlock("div", { key: u.id }, toDisplayString(u.name), 1 /* TEXT */))
  ), 12 /* KEYED_FRAGMENT */))

68.5 如何观察编译产物与验证优化效果

优化是否真的生效？不要靠猜，直接看构建产物里的 render 函数。Vite 构建时会把 SFC 编译成 render，产物落在 dist/assets 的 js 里。

# 构建并查看编译产物里的 render 函数
npm run build
# 在 dist/assets/*.js 里搜：_createElementBlock / _hoisted_1 / patchFlag
grep -o "_hoisted_[0-9]*" dist/assets/*.js | head     # 静态提升的数量
grep -o "TEXT\|CLASS\|STYLE\|PROPS" dist/assets/*.js | head  # patchFlag 标记

验证优化的标准动作：构建后搜 _hoisted_（静态提升）与 patchFlag 数字（动态标记）是否出现。

现象说明处理
产物里有 _hoisted_N静态提升生效正常
节点带 patchFlag 数字动态追踪生效正常
该静态的没提升节点里混了插值/事件拆分静态子树
事件函数反复新建cacheHandlers 未命中检查是否内联箭头函数

block tree 只收集动态节点，静态子树整棵跳过。但 v-if/v-for 这类结构性指令会改变树形态，编译器把它们标成 fragment，纳入动态追踪——这也是列表必须写稳定 key 的原因。验证优化是否生效：构建后搜 _hoisted_ 与 patchFlag。
