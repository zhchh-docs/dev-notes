71.1 三件套：Performance / Network / Devtools

工具看什么
Performance 面板录制一次操作，找 >50ms 的长任务；看 FCP/交互延迟
Network 面板请求是否过多/过大、是否阻塞首屏、懒加载是否生效
Vue Devtools组件树、各组件渲染耗时、状态变化 timeline

性能优化的第一原则：先量化，再动手。没有数据的优化都是瞎猜。

71.2 常见瓶颈分类

  • 渲染频率过高：输入时全表重渲染、滚动时触发大量响应式更新——用防抖/shallowRef；
  • 大列表：一次渲染几万行 DOM——虚拟列表（第 72 章）；
  • 内存泄漏：全局事件、定时器、订阅未清理，页面久开内存上涨；
  • 事件泄漏：addEventListener 不 remove，组件反复挂载后监听器累积；
  • 包体积：未按需引入组件库、大依赖全量打进首屏。
// 典型泄漏：组件卸载后监听器还在
onMounted(() => window.addEventListener('resize', onResize))
// ✗ 没有 remove，反复挂载后监听器累积
// ✓ 在卸载时移除
onBeforeUnmount(() => window.removeEventListener('resize', onResize))
// 渲染频率过高：输入时不要全表重渲染
// 用防抖 + shallowRef 让大列表跳过深度响应式
import { shallowRef } from 'vue'
const rows = shallowRef([])

71.3 排查方法论与收益

  1. 复现：在 Performance 里录制用户抱怨的那个操作；
  2. 定位：找最长的任务栈，看是 JS 计算、渲染还是请求；
  3. 假设：猜是哪个组件/哪段数据导致；
  4. 验证：用 Devtools 渲染耗时或注释局部代码确认；
  5. 优化：只改定位到的点，再录制对比。
// 定位到具体组件耗时后，可用注释法二分：
// 注释掉某段子树 → 重新录制 → 看耗时是否骤降
// 骤降 = 问题就在被注释的部分

71.4 一个完整排查案例

把方法论走一遍真实场景：列表页输入筛选框时，整个表格跟着每敲一个字卡一下。

步骤动作发现
① 复现Performance 录制输入过程每次 keystroke 出现 80ms 长任务
② 定位看调用栈根组件 render → 表格子树全量 diff
③ 假设输入框值驱动了整表重渲染rows 是普通 reactive，深度监听拖慢
④ 验证把 rows 改 shallowRef长任务从 80ms 降到 12ms，卡顿消失
⑤ 优化输入加 300ms 防抖 + shallowRef只在停顿后请求一次
 
// 修复：shallowRef 跳过深度响应式 + 防抖
import { shallowRef } from 'vue'
const rows = shallowRef([])
// 输入停顿 300ms 后才触发请求与渲染
const onInput = debounce(fetchList, 300)

案例结论：先录制拿到长任务，再沿调用栈定位到"谁在重渲染"，最后用 shallowRef + 防抖把渲染次数压下来。

71.5 性能预算与持续监控

优化不是一次性动作。给项目定一条"性能预算"，并在 CI 里卡住超预算的构建，避免性能随迭代悄悄退化。

指标参考预算（首屏）超了先查什么
FCP 首次内容绘制< 1.8s首屏 JS 体积、阻塞请求
包体积 gzip核心包 < 250KB未按需引入、重依赖
长任务单任务 < 50ms同步大计算、深层响应式
内存增长切换路由不持续上涨事件/订阅泄漏
