20.1 setup：组合式 API 的入口

选项式 API 的组件长这样：data、methods、computed、watch 各占一个选项，Vue 内部把它们挂到 this 上。组合式 API 把这一切收进一个函数——setup()：

// 显式 setup() 写法（看得清"组合式到底是什么"）
export default {
  setup() {
    const count = ref(0)          // 状态：相当于 data() { return { count: 0 } }
    function inc() { count.value++ }   // 方法：相当于 methods: { inc() {} }

    return { count, inc }          // return 出去 = 暴露给模板
  }
}

第 10 章说过，<script setup> 是这段代码的语法糖：你写在顶层的 const count = ref(0)，编译器自动把它 return 出去。所以日常开发中 setup 这个词你几乎看不到，但理解它的存在很重要：

  • 顶层绑定自动暴露：<script setup> 里所有顶层变量/函数/组件 import，模板都能直接用；
  • 每实例独立执行：组件每挂载一次，setup() 就跑一遍，里面声明的变量是这个实例私有的；
  • setup 阶段没有 this：这是组合式与选项式最大的分水岭——没有 this.xxx，一切都是函数里的普通闭包变量。

组合式 API 不是"换了个位置写代码"，而是把组件的状态与逻辑变成了普通 JS 闭包——这是它能被抽成函数、自由组合的根本原因（第 23 章展开）。

20.2 为什么需要 ref：普通 let 拦不住

先把"响应式到底要什么"想清楚。Vue 在 count 变化后要做两件事：重新跑渲染函数更新 DOM、通知所有依赖了它的 watcher。要做到这一点，框架必须能在你"读 count"和"写 count"的时候插入自己的逻辑。

普通 let 变量能被拦截吗？不能：

let count = 0
count++          // JS 引擎内部直接改值，Vue 完全无感
// 框架没有任何机会知道"count 变了"

但 JS 对象的属性可以拦截——给一个对象套上 getter/setter，读写属性时就会触发函数：

// Vue 的 ref 内部大致就是这个结构（简化）
const count = {
  _value: 0,
  get value() {
    track(this)     // 读：记录"谁在用我"（依赖收集）
    return this._value
  },
  set value(newVal) {
    this._value = newVal
    trigger(this)   // 写：通知所有依赖者更新
  }
}

count.value = 1      // 触发 setter → trigger → 页面更新
console.log(count.value)  // 触发 getter → track

这就是"为什么要包一层"的答案：ref 是一个对象容器，只有把数据放进对象的 .value 属性里，Vue 才有地方挂 getter/setter。包这一层不是多余，而是 JS 语言层面唯一能拦截"变量读写"的抓手。

Vue 3 用 Proxy 代理整个对象来实现 reactive，原理同根——都是"拦截"。第 29 章开始会把 Proxy 这套原理逐层拆开，这里先记住结论。

20.3 .value：JS 里必须手动，模板自动

既然 ref 是个容器对象，在 <script> 的 JS 上下文里读写它，就必须显式写 .value：

<script setup>
import { ref, computed } from 'vue'

const count = ref(0)
const doubled = computed(() => count.value * 2)   // JS 里：必须 .value

function inc() {
  count.value++          // 写：必须 .value
  console.log(count)     // 不写 .value → 打印的是整个 ref 对象！
  console.log(count.value)   // 0 或 1，才是值
}
</script>

<template>
  <!-- 模板里：直接用，不要写 count.value -->
  <p>{{ count }} × 2 = {{ doubled }}</p>
  <button @click="inc">+1</button>
</template>

规则总结成三条：

  1. JS 上下文（script、事件处理、普通函数）：必须写 .value，否则操作的是容器对象本身；
  2. 模板上下文：自动解包——编译器知道模板里的 count 是个 ref，渲染时自动取 .value；
  3. ref 被嵌套进 reactive 对象时：自动解包，像普通属性一样访问：
import { ref, reactive } from 'vue'

const count = ref(0)
const state = reactive({ count })   // ref 放进 reactive

console.log(state.count)   // 0，不是 ref 对象——自动解包了
state.count = 5            // 也等价于 count.value = 5，响应式照常
console.log(count.value)    // 5

// 例外：模板顶层返回的数组/对象不解包
const list = reactive([{ n: ref(1) }])
list[0].n.value             // 嵌套在深层结构里，仍要手动 .value

新手第一周最常见的报错来源：xxx.value is undefined——多半是在已经解包的地方又写了 .value，或在模板里写了 {{ count.value }}（虽然模板也能跑，但写法错误，review 会打回）。

20.4 ref 传参与解构：为什么不会丢

这里藏着 ref 设计最精妙的一点。假设你写了一个组合式函数（第 23 章详讲），组件把状态传给它：

// 组件里
const keyword = ref('')

// 把 ref 本身（不是 keyword.value）传进函数
useSearch(keyword)

function useSearch(keywordRef) {
  // 函数内部改 keywordRef.value，组件里的 keyword 同步变化
  // ——因为两边引用的是同一个容器对象
  keywordRef.value = 'hello'
}

console.log(keyword.value)   // 'hello'

对比一下 reactive（下一章详讲）：reactive 是对象代理，一旦解构，拿到的就是普通值，响应性当场丢失。而 ref 是"把值包进对象再传引用"，整个对象在到处传，容器里的值始终在被同一个 getter/setter 看守——这就是 ref 作为组合式函数参数的天然优势。

一句话总结这层价值：

ref 传的是同一个容器，谁拿到容器改 .value 都走同一个拦截器——响应性因此可以自由穿越函数边界。

20.5 ref 与 reactive 怎么选

维度refreactive
能装什么任何类型：数字、字符串、布尔、对象、数组仅对象/数组/Map/Set（原始类型不行）
取值方式JS 里要 .value，模板自动解包直接 state.x，无 .value
解构传容器不丢响应（20.4）解构即丢失，需 toRefs（第 21 章）
整体替换list.value = newList 直接换，响应性保留state = newObj 直接断，要改属性（第 21 章）
工程主流推荐：Vue 官方文档与 VueUse 默认风格适合整块表单/配置对象

实用建议：状态一律先用 ref；一个明显的"表单对象/配置对象"用 reactive 更顺手。两者不是对立关系——reactive 的字段里照样可以放 ref（自动解包）。

20.6 常见坑

  • 坑 1模板里写 {{ count.value }}：虽然能渲染，但这是错误写法。模板里 ref 自动解包，直接写 count。
  • 坑 2JS 里忘了 .value：console.log(count) 打出来是个 Ref 对象；if (count) 永远为真（对象恒真）。这类 bug 隐蔽又高发，建议开 ESLint 的 vue/ref-unref 规则。
  • 坑 3把 ref 对象整个替换：count = ref(5) 重新赋值一个新 ref 不会报错，但如果别处持有旧容器引用，它们不会跟着变。需要换值就 count.value = 5。
  • 坑 4原始类型硬用 reactive：reactive(0) 根本不存在——reactive 只接受对象。单个数字/布尔就是 ref(false)。
  • 坑 5在 setup 顶层之外声明变量：模块顶层的 const data = ref(...) 会被所有组件实例共享，改一个全变。状态必须写在 setup 内部（<script setup> 顶层）。
