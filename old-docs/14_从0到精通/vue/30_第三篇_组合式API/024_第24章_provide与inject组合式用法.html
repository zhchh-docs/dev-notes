24.1 回顾第 18 章，升级到组合式视角

第 18 章你已经会：祖先 provide(key, value)，后代 inject(key)，跨任意层级传依赖。本章要回答的问题是：每次写 provide/inject 都要在祖先和后代各写一遍，怎么封装得像个正经 API？

回忆一下原始写法的痛点：

  • 祖先组件里散落着 provide('theme', ...)，与业务逻辑混在一起；
  • 后代组件里 inject('theme') 拿到的是裸值，没有类型、没有默认值、不知道"必须在谁下面用"；
  • key 是字符串，拼写错误不会报错。

组合式视角的目标：把"提供上下文"和"消费上下文"都变成一个函数调用，祖先调一个 useThemeProvider()，后代调一个 useTheme()，key、类型、默认值全部收口在一个文件里。

图 24-1 provide/inject 收口为一对组合式函数（示意）

24.2 把 provide/inject 封装成组合式函数

以主题切换为例。把 provide 逻辑收进 useThemeProvider，把 inject 逻辑收进 useTheme：

// composables/useTheme.js
import { provide, inject, ref, readonly } from 'vue'

const THEME_KEY = Symbol('theme')

// 祖先调用：提供上下文
export function useThemeProvider() {
  const theme = ref('light')
  function toggle() { theme.value = theme.value === 'light' ? 'dark' : 'light' }

  // 对外暴露 readonly + 修改方法，禁止后代直接改 theme.value
  provide(THEME_KEY, { theme: readonly(theme), toggle })
  return { theme, toggle }
}

// 后代调用：消费上下文
export function useTheme() {
  const ctx = inject(THEME_KEY)
  if (!ctx) throw new Error('useTheme 必须在 ThemeProvider 内使用')
  return ctx
}
<!-- 祖先：App.vue -->
<script setup>
import { useThemeProvider } from '@/composables/useTheme'
useThemeProvider()
</script>

<!-- 后代：任意深度的组件 -->
<script setup>
import { useTheme } from '@/composables/useTheme'
const { theme, toggle } = useTheme()
</script>

<template>
  <p>当前主题：{{ theme }}</p>
  <button @click="toggle">切换</button>
</template>

对比 18 章的裸写法：key 是 Symbol（拼错不冲突）、后代拿到的是"数据 + 方法"的完整上下文、改不了 theme.value（readonly）。

24.3 inject 的默认值与错误兜底

后代可能不在 Provider 下面被单独使用（比如在 Storybook 里孤立渲染）。inject 的第二个参数是默认值，需要工厂函数时第三个参数传 true：

import { inject } from 'vue'

// ① 简单默认值
const theme = inject(THEME_KEY, { theme: 'light', toggle: () => {} })

// ② 需要计算/新对象时，第三参 true 表示用工厂函数
const theme = inject(THEME_KEY, () => ({ theme: 'light', toggle: () => {} }), true)

// ③ 更严格：没有 Provider 直接抛错，开发期尽早暴露
const ctx = inject(THEME_KEY)
if (!ctx) throw new Error('useTheme 必须在 ThemeProvider 内使用')

三种策略按"上下文是否可独立运行"选择：

策略写法适用
直接抛错inject 后判空 throw组件必须在 Provider 下才有意义（如 FormItem）
给默认值inject(key, 默认值)组件可独立使用，缺省走降级行为
工厂默认值inject(key, fn, true)默认值需要新建对象/计算时

24.4 createContext：provide/inject 成对导出

如果你要写多个上下文（主题、表单、弹窗……），每个都手写一遍 provide/inject 样板很烦。社区的通用做法是写一个 createContext 工厂：一次调用，成对得到 provider hook 与 consumer hook：

// composables/createContext.js
import { provide, inject } from 'vue'

export function createContext(name) {
  const key = Symbol(name)
  return {
    provider(context) { provide(key, context) },
    consumer() {
      const ctx = inject(key)
      if (!ctx) throw new Error(`${name} 缺失：必须在对应 Provider 下使用`)
      return ctx
    }
  }
}
// 业务侧：一行声明上下文
const { provider: useFormProvider, consumer: useFormContext } = createContext('form')

// 祖先
useFormProvider({ model, errors, register })

// 后代
const ctx = useFormContext()

这种模式在 React 生态是标准做法（Context + useContext），Vue 里同样成立。它把"跨层共享一组 API"做成了类型安全、错误明确、来源清晰的工程组件。

TypeScript 下还可以给 InjectionKey<T> 泛型化，让 inject 返回值自动带上类型——这是 provide/inject 在大型项目里的最大红利之一。

24.5 与 Pinia 的边界

既然 provide/inject 能跨层共享状态，什么时候该上 Pinia？判断标准：

维度provide/injectPinia
共享范围组件树内部（Provider 的后代）全局任意组件
典型用途组件族（Form/FormItem、Theme 包裹层）跨业务模块的全局状态（用户、购物车、权限）
能否多实例天然支持（包几层 Provider 就几套）单例，多实例要手动拆 store
devtools / 持久化无有官方 devtools、持久化插件
类型推导需自己写 InjectionKey开箱即用

一句话边界：组件族内部上下文用 provide/inject；跨业务、跨路由的全局状态用 Pinia。别用 provide 搭全局商店，也别把每个表单上下文都塞进 Pinia。

24.6 常见坑

  • 坑 1provide 在 await 之后调用：setup 里异步之后再 provide，后代 inject 不到。必须在 setup 同步段 provide。
  • 坑 2后代直接改 inject 来的 ref.value：破坏"谁 provide 谁修改"的约定。对外暴露 readonly + 修改方法。
  • 坑 3inject 字符串 key 拼错：用 Symbol 或 createContext 工厂，别用裸字符串。
  • 坑 4把 provide 当全局状态用：跨业务模块共享请用 Pinia，provide 只服务组件族。
  • 坑 5在没有 Provider 的地方 useXxx 不报错：consumer 函数里做判空 throw，开发期尽早暴露。
  • 坑 6provide 出去的是 reactive 对象却被后代解构：解构即丢响应（第 21 章）。对外给 ref 或整个 readonly 对象。
