31.1 trigger 的基本过程

有了上一章的 targetMap，trigger 的逻辑就很直白：

function trigger(target, key, type) {
  const depsMap = targetMap.get(target)
  if (!depsMap) return                       // 这个对象没人依赖过

  // 收集要执行的 effects（可能多个来源）
  const effects = new Set()

  const add = (dep) => {
    if (dep) dep.forEach(e => effects.add(e))
  }

  add(depsMap.get(key))                      // 1. 这个 key 的依赖

  // 2. 如果是新增 / 删除，还要通知"枚举类"依赖（ownKeys 收集的）
  if (type === 'ADD' || type === 'DELETE') {
    add(depsMap.get(ITERATE_KEY))
  }
  // 3. 如果是数组且改了 length，也要通知 length 相关的依赖
  if (type === 'ADD' && Array.isArray(target)) {
    add(depsMap.get('length'))
  }

  // 4. 挨个执行
  effects.forEach(effect => {
    if (effect.scheduler) {
      effect.scheduler(effect)               // 有自定义调度器：交给他
    } else {
      effect.run()                           // 没有：直接跑
    }
  })
}

注意第 4 步的分叉：effect 有一个可选的 scheduler 字段，trigger 不直接 effect.run()，而是先问"你要不要自己决定怎么跑"。组件的渲染 effect 就是带 scheduler 的——它把自己塞进队列而不是立刻执行。

为什么要拆出 ITERATE_KEY

当 effect 内部用了 Object.keys(state) 或 for...in，它不关心任何具体 key，只关心"键的集合变了没有"。Vue 用一个特殊的 Symbol ITERATE_KEY 作为这类依赖的"key"。只有 ADD / DELETE（或数组的 length 变化）才会通知它——普通改一个已有字段，键集合没变，不用通知。

31.2 为什么不能同步立刻执行

假设 trigger 就是同步 effect.run()，看下面这段代码会发生什么：

const state = reactive({ count: 0 })

effect(() => {
  console.log('render, count =', state.count)
})

for (let i = 0; i < 100; i++) {
  state.count++        // 每次 ++ 都触发一次 render
}
console.log('done')

同步执行的后果：

  • render 跑 100 次：虚拟 DOM diff 100 次、patch 100 次，而最终页面只需要反映最后一次 count=100 的结果；
  • render 卡在循环中间：用户看到的中间态是 count=1,2,3...，而不是最终的 100；
  • 后续代码被阻塞：console.log('done') 要等 100 次 render 跑完才执行。
策略连续改 100 次问题
同步立即执行render 100 次浪费、卡顿、中间态闪烁
同轮批处理（队列）render 1 次（在下一个微任务）用户只看到最终态，性能最优

Vue 的响应式更新默认是异步的、同轮批处理的：同一轮同步代码里触发的所有变更，攒成一批，在下一个微任务里统一刷一次。

31.3 scheduler：每个 effect 的"自定义执行器"

scheduler 是创建 effect 时传入的一个函数：

const ef = new ReactiveEffect(
  () => console.log('effect 跑了，count =', state.count),
  {
    // 这个调度器决定：trigger 时怎么执行这个 effect
    scheduler(effect) {
      console.log('trigger 来了，但我不立刻跑')
      // 把 effect 放进队列，等下一个微任务统一跑
      queueJob(effect)
    }
  }
)

谁在用 scheduler

  • 组件的渲染 effect：scheduler 把组件的更新任务塞进"组件更新队列"，同一组件一轮内只更新一次；
  • watch 的回调：默认调度到 post（DOM 更新完之后）再跑；
  • computed：见第 33 章，它的 scheduler 把自己标记为 dirty 而不是立刻重算。

自定义 scheduler 的实际意义

对普通业务代码，你几乎不会手写 scheduler；但理解它存在的意义是："什么时候跑副作用"和"副作用是什么"是分开的。trigger 只负责说"依赖变了"，至于"立刻跑 / 下帧跑 / 队列去重跑 / 防抖跑"，由每个 effect 自己的 scheduler 决定。

用户层面的对应物：watch(source, cb, { flush: 'post' }) 里的 flush 选项、组件更新的 nextTick——本质都是在配置"这个 effect 何时执行"。

31.4 queueJob 与微任务 flush

组件更新队列的极简实现：

const queue = []          // 当前等待执行的 job 列表
let isFlushing = false    // 是否已经安排过 flush

function queueJob(job) {
  // 去重：同一个 job 已经在队列里就不重复加
  if (!queue.includes(job)) {
    queue.push(job)
  }
  if (!isFlushing) {
    isFlushing = true
    // 关键：把 flush 排到微任务，而不是立即执行
    Promise.resolve().then(flushJobs)
  }
}

function flushJobs() {
  // 按 id 排序（父组件先于子组件更新），避免重复渲染
  queue.sort((a, b) => a.id - b.id)
  while (queue.length) {
    const job = queue.shift()
    job()                   // 实际执行组件的 render effect
  }
  isFlushing = false
}

31.5 nextTick 与调度器的关系

你写过的这段代码：

import { nextTick, ref } from 'vue'

const count = ref(0)
count.value = 1
console.log(document.querySelector('#count').textContent)   // 还是 '0'
await nextTick()
console.log(document.querySelector('#count').textContent)  // 已经是 '1'

为什么必须 await nextTick 才能读到新 DOM？因为：

  1. count.value = 1 只是把更新任务塞进了队列（微任务还没跑）；
  2. 同步代码继续往下走，DOM 还没 patch；
  3. nextTick(cb) 本质是 Promise.then(cb)——把 cb 排到当前 flush 的后面，保证 cb 跑的时候 DOM 已经更新完。
时机DOM 状态能否读到新值
同步改完立刻读未 patch否（旧值）
await nextTick 后读已 patch是（新值）
在 watch flush:'post' 回调里已 patch是（等同于 nextTick）
onUpdated 钩子里已 patch是

常见错觉："改完数据立刻读 DOM，怎么还是旧值？"——不是 Vue 慢，是更新本来就被批处理到微任务里去了。读 DOM 新值要先 await nextTick() 或进 onUpdated。

31.6 本章常见坑

  • 坑 1同步代码里连续读 DOM：以为改完就生效，读到旧值。用 nextTick 或 onUpdated。
  • 坑 2在 effect 内部又改响应式数据：改完又 trigger 自己，可能造成无限循环。Vue 通过"effect 正在执行时不再把它重新入队"做防护，但业务代码里尽量避免 render 期间改 state。
  • 坑 3以为 watch 默认就能拿到更新后的 DOM：watch 默认 flush: 'pre'（DOM 更新前跑），要拿 DOM 用 flush: 'post'。
  • 坑 4在循环里改 ref 又同步读 ref.value：ref.value 本身是同步的（数据已经改了），但 DOM 没更新，别混淆"数据变了"和"视图变了"。
  • 坑 5自己用 setTimeout 模拟 nextTick：setTimeout 是宏任务，比微任务晚得多；用 Promise.then / nextTick。
