29.1 为什么用 Proxy 替换 defineProperty

Vue2 的响应式建立在 Object.defineProperty 之上：在初始化时遍历对象的每一个属性，把它们改成 getter/setter。这套方案能用，但有三个绕不过去的短板。

三个根本性短板

  • ① 新增属性感知不到：defineProperty 劫持的是"初始化时已经存在"的属性。后加的 obj.newKey = 1 不会触发更新——这就是 Vue2 里必须用 this.$set(obj, key, val) 的原因。
  • ② 数组下标与 length 感知不到：arr[0] = 1 直接赋值、arr.length = 0 都不劫持。Vue2 只能靠重写 7 个数组变异方法（push/pop/shift/unshift/splice/sort/reverse）来兜底，这是一个补丁式方案。
  • ③ 必须递归遍历：初始化时要把对象整棵树的属性都 defineProperty 一遍，深层大对象的初始化成本高，且天生没法拦截"整个对象被替换"这类操作。

Proxy 怎么补上

// defineProperty：劫持"属性"，初始化时一次性埋点
Object.defineProperty(obj, 'count', {
  get() { /* ... */ },
  set(v) { /* ... */ }
})

// Proxy：劫持"整个对象"，任何对它的读取/写入/枚举都会先过一遍陷阱
const proxy = new Proxy(obj, {
  get(target, key, receiver) { /* 读任何 key 都进来，包括后来新增的 */ },
  set(target, key, value, receiver) { /* 写任何 key 都进来，包括 arr[0] */ }
})

关键差别：defineProperty 管的是"属性"，Proxy 管的是"对象"这一层"访问动作"。新增属性、数组下标、for...in、in 操作、delete 操作——这些统统不需要 $set，因为它们都是"对对象的操作"，天然被拦截。

维度Vue2 definePropertyVue3 Proxy
拦截粒度逐个属性的 getter/setter整对象的 13 种拦截陷阱
新增属性感知不到，需 $setset 陷阱天然拦截
数组下标/length需重写 7 个变异方法兜底set 陷阱按 key 区分处理
初始化成本递归遍历整棵树惰性：访问到嵌套层才代理
对象整体替换难以感知代理引用不变，天然支持
浏览器兼容IE8+IE 全系不支持（Vue3 放弃 IE）

defineProperty 是"给每个属性装门铃"，Proxy 是"给整栋楼装门禁"——前者门牌号变了要重新登记，后者谁进门都得过门禁。

提醒Proxy 无法被 polyfill。这就是 Vue3 放弃 IE 的根本原因：IE 没有 Proxy，任何转译工具都补不上这个底层能力。

29.2 Proxy 与 Reflect 的基本配合

一个能用的最小响应式雏形长这样：

function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key)                 // 依赖收集（下一章细讲）
      const res = Reflect.get(target, key, receiver)
      if (isObject(res)) return reactive(res)   // 惰性代理嵌套对象
      return res
    },
    set(target, key, value, receiver) {
      const oldValue = target[key]
      const success = Reflect.set(target, key, value, receiver)
      if (hasChange(oldValue, value)) trigger(target, key)  // 触发更新
      return success
    }
  })
}

这里有两个新手最容易问的问题。

为什么不直接写 target[key]，而要用 Reflect.get / Reflect.set？

  • 返回值与异常行为一致：Reflect.set 会返回布尔值表示"是否写成功"（比如对象被 Object.freeze 时严格模式会抛错），而赋值语句没有返回值可拿。set 陷阱要求你返回 true/false，否则在严格模式抛错。
  • receiver 参数：第三个参数 receiver 指向"最初被访问的那个代理对象"。当属性的 getter 定义在原型链上时，直接 target[key] 会让 getter 里的 this 指向原始对象而非代理，导致响应式断裂。Reflect.get(target, key, receiver) 会把 this 修正为 receiver。

receiver 是干嘛的——一个原型链陷阱案例

const proto = {
  get name() { return this._name }   // 注意 this
}
const obj = Object.create(proto)
obj._name = 'vue'

const p = new Proxy(obj, {
  get(target, key, receiver) {
    // 写法一：直接 target[key] —— getter 内部 this 指向原始 obj
    // 写法二：Reflect.get(target, key, receiver) —— this 指向 receiver（代理 p）
    return Reflect.get(target, key, receiver)
  }
})

真实场景：组件继承、reactive 嵌套代理、class 实例做响应式时，这个细节决定依赖收集会不会丢。Vue 源码里所有拦截器都用 Reflect，就是为了把 receiver 正确传下去。

记住一个规则：只要写了 Proxy 陷阱，内部对原始对象的读写一律走 Reflect，并把 receiver 原样传进去。

29.3 各拦截器的触发时机与场景

Proxy 一共 13 个陷阱。Vue 响应式里真正用到的只有 6 个左右，其余是给框架调试、沙箱、拦截器库准备的。下表是 Vue3 当前用到的几个核心陷阱：

拦截器触发时机在 Vue 里的用途
get读取属性 obj.a、obj['a']依赖收集 track；返回嵌套代理
set写属性 obj.a = 1、arr[0]=1、arr.length=0触发更新 trigger；区分"新增"与"修改"
has'a' in obj、with(obj) 内的标识符检索v-if / hasOwnProperty 等隐式判断的收集（少数场景）
deletePropertydelete obj.a删除属性后触发更新
ownKeysObject.keys、for...in、Object.getOwnPropertyNames动态枚举的依赖收集（v-for 列表）
getOwnPropertyDescriptorObject.getOwnPropertyDescriptor边缘场景，极少用

set 陷阱内部要区分"新增"还是"修改"

set(target, key, value, receiver) {
  const hadKey = Object.prototype.hasOwnProperty.call(target, key)
  const oldValue = target[key]

  // 已经是响应式的新值就直接写
  const result = Reflect.set(target, key, value, receiver)

  if (!hadKey) {
    trigger(target, key, 'ADD')      // 新增：还需要触发 for...in 相关的 ownKeys 收集
  } else if (hasChanged(value, oldValue)) {
    trigger(target, key, 'SET')      // 修改：只通知 key 本身
  }
  return result
}

这个区分不是吹毛求疵：v-for="item in list" 这种依赖"键的集合"的渲染，只有在 ADD（或 DELETE）时才需要重跑；普通修改一个值，只通知关心这个 key 的副作用即可。

29.4 代理对象与原始对象

Proxy 最反直觉的一个事实：代理对象和原始对象不是同一个引用。

const raw = { name: 'vue' }
const proxy = reactive(raw)

console.log(proxy === raw)          // false —— 不是同一个对象
console.log(proxy.name)             // 'vue'
console.log(raw.name)              // 'vue' —— 数据是共享的

raw.name = 'new'
console.log(proxy.name)            // 'new' —— 改原始对象会反映到代理

proxy.name = 'again'
console.log(raw.name)              // 'again' —— 改代理也会改原始
  • 数据共享：代理只是在原始对象外面套了一层"拦截壳"，读/写最终都落到原始对象上；
  • 引用不同：所以 reactive(raw) === reactive(raw) 也是 false——Vue 内部用一个 WeakMap（raw → proxy 缓存）保证同一个原始对象每次 reactive 都返回同一个代理，这个缓存叫 reactiveMap；
  • 解构丢响应式：const { name } = proxy 拿到的是原始值 'vue'，不是代理——这就是第三篇反复强调"reactive 不能解构赋值"的原因（第 21 章）。

toRaw：拿回原始对象

import { toRaw, reactive } from 'vue'

const raw = { name: 'vue' }
const proxy = reactive(raw)
console.log(toRaw(proxy) === raw)   // true —— 拿回没有代理壳的原始对象

什么时候要用 toRaw？① 把响应式对象存入大列表/Map 做查找（绕过代理，省内存）；② 做不需要响应式的深比较；③ 持久化时去掉代理壳再序列化。下一章讲 markRaw 时还会再碰到。

操作是否触发响应式说明
proxy.name = 1是走 set 陷阱
raw.name = 1否（不触发副作用）原始对象没有拦截壳；数据会变，但界面不知道
reactive(raw) 再次调用—命中缓存，返回同一个代理
toRaw(proxy)—拿回原始对象，之后的写入不再触发更新
const { name } = proxy—拿到原始值，不是响应式

新手坑：以为"改了 raw 对象页面也会更新"。数据确实共享，但只有经过代理壳的 set 才会通知副作用——直接改 raw 是个静默的坑。

29.5 惰性代理与嵌套代理

回想 29.2 节的 get 拦截里有一行：if (isObject(res)) return reactive(res)。这就是"惰性"的关键——嵌套对象是访问到的时候才代理，不是 reactive() 时一次性代理整棵树。

为什么要惰性

const state = reactive({
  user: { name: 'vue', profile: { age: 3 } },
  list: new Array(10000).fill(0).map((_, i) => ({ id: i }))
})
// 此时：user、user.profile、list、list[0..9999] —— 全都还没被代理！
// 只有当你 state.user 时，才对 user 套代理；state.user.profile 时才再套一层
  • 省初始化成本：深层大对象如果一次性递归代理，首次 reactive() 会卡顿；惰性把代理成本摊到"实际访问"时；
  • 省内存：从没被访问过的嵌套分支，根本不需要代理壳；
  • 配合缓存：同一个 raw 嵌套对象第一次访问时建代理、写进 reactiveMap，之后再访问直接命中缓存。

惰性带来的两个推论

  1. 嵌套得越深，首次访问越慢一点：每次 obj.a.b.c 都要在每一层 get 陷阱里查缓存、必要时建新代理。这是真实的开销，所以大对象上"链状深层访问"在热路径里要谨慎；
  2. 没有被 get 过的嵌套对象不参与依赖收集：如果模板里从没写过 state.user.profile.age，那 age 的修改不会触发任何更新——这不是 bug，是"访问才收集"的自然结果（下一章展开）。

markRaw：告诉 Vue"这个对象别代理"

import { markRaw, reactive } from 'vue'

class Editor {
  constructor() { this.plugins = [] }
}

const state = reactive({
  editor: markRaw(new Editor())   // 这个对象永远不被代理
})
// state.editor 拿到的就是原始 Editor 实例

适合场景：第三方库实例（地图、图表、编辑器、大型类实例）、不需要响应式的大对象、只读常量表。markRaw 和它的产物会进一个 rawToReactive 的"反查缓存"，之后对它的访问直接返回原值，不套壳。

设计哲学：Vue 的响应式不是"数据变了就更新"，而是"被读过的数据变了才更新"。Proxy 只是拦截层，真正决定"谁该更新"的是下一章的依赖收集。

29.6 本章常见坑

  • 坑 1set 陷阱里忘了返回 true：严格模式下会抛 TypeError: 'set' on proxy: trap returned falsish。必须 return Reflect.set(...) 的结果。
  • 坑 2get 陷阱里直接 target[key] 而不是 Reflect.get：属性在原型链上时 this 指错，依赖收集丢失。
  • 坑 3把 raw 存到组件 state 里又指望它更新：raw 没有拦截壳，改它页面不动。要么用代理，要么改完手动 trigger。
  • 坑 4对 class 实例做 reactive 后把它换出：如果对象整体被替换成新实例，要确保新实例也走 reactive（或在 get 陷阱里惰性建代理）。
  • 坑 5误以为 Proxy 是为了性能：恰恰相反，Proxy 每次访问都过陷阱，比裸对象慢。它的价值是"能力完整"，性能靠惰性 + 缓存控制。
