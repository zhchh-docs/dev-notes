33.1 lazy：computed 不立即求值

先回忆 computed 的日常：

const count = ref(1)
const double = computed(() => {
  console.log('getter 跑了')   // 这行什么时候打印？
  return count.value * 2
})

// 此时：没有任何打印 —— computed 定义时不跑 getter

这和普通函数完全不同。普通函数定义完不会执行，但你一调用就执行。computed 是"惰性"的：

  • 定义时：啥也不做；
  • 第一次被读（double.value）：才跑 getter，算出结果并缓存；
  • 之后再读：只要依赖没变，直接返回缓存，不再跑 getter。

为什么必须 lazy

如果 computed 定义时就跑 getter，会有两个问题：

  1. 可能根本没人用它：定义了一个 computed 但模板里没引用过，白白算了一次；
  2. 依赖可能还没准备好：computed 在 setup 里定义，此时其他 ref 可能刚初始化，跑 getter 时序不对。

computed 的第一性原理："被读到才计算，依赖没变就别重算"。

33.2 dirty 标志与缓存

核心是两个内部字段：

class ComputedRefImpl {
  constructor(getter, setter) {
    this._getter = getter
    this._setter = setter

    this._value = undefined    // 缓存值
    this.dirty = true           // ← 关键：脏标志

    // 关键：内部包一个 effect，scheduler 不是立刻重跑 getter
    // 而是：把 dirty 设回 true，并通知下游依赖
    this.effect = new ReactiveEffect(
      () => this._getter(),
      {
        scheduler: () => {
          if (!this.dirty) {
            this.dirty = true     // 依赖变脏，下次读要重算
            trigger(this, 'value') // 通知"下游读了我"的那些 effect
          }
        }
      }
    )
  }

  get value() {
    track(this, 'value')        // 我自己也被当成一个响应式源，让下游收集
    if (this.dirty) {
      this._value = this.effect.run()  // 脏才重算
      this.dirty = false               // 算完变干净
    }
    return this._value
  }

  set value(newVal) {
    this._setter && this._setter(newVal)
  }
}

完整流程

  1. computed(getter) 定义 → dirty = true；
  2. 第一次 double.value → track(this, 'value') → dirty 为 true → 跑 effect.run() → getter 执行 → 读到 count.value 触发 track（count 的 dep 里加上 computed 内部的 effect）→ 结果缓存、dirty = false；
  3. 第二次 double.value → dirty 为 false → 直接返回缓存，不跑 getter；
  4. count.value = 5 → trigger count 的 dep → 通知 computed 内部那个 effect → 但因为有 scheduler，不是立刻重跑 getter，而是 dirty = true + trigger(this, 'value') → 通知"读过 double 的那些下游 effect"（比如组件 render）；
  5. 下游 effect 重跑 → 再读 double.value → dirty 为 true → 重算 getter。

33.3 同时是被观察者与观察者

上面流程图里有两个关键身份：

  • 对上游 ref（count）：computed 是观察者。它的内部 effect 读过 count.value，所以被登记进 count 的 dep。count 变了，computed 收到通知；
  • 对下游 effect（组件 render）：computed 是被观察者。render 读过 double.value，所以 track(this, 'value') 把 render 登记进 computed 自己的 dep。computed 脏了，render 收到通知。

这就是为什么 computed 能在依赖链中间"缓存"：上游变了，它只标脏、不重算；等下游真的来读时才重算一次。

为什么不立刻重算 getter

如果上游一变就立刻重算 getter，那可能出现"上游连改 N 次、下游根本没在读"的情况——白算了 N 次。Vue 选的是：上游变 → 只标 dirty + 通知下游"我脏了"，下游什么时候真读什么时候算。这是"读时计算"的核心。

问题dirty 前dirty 后
下游读 .value返回缓存，不跑 getter跑 getter，更新缓存，dirty=false
上游 ref 变—scheduler：dirty=true + trigger(this)
下游读 .value 但没人在跑 effect直接返回缓存重算一次（无所谓有没有 effect）

33.4 链式依赖与可写 computed

链式依赖

const a = ref(1)
const b = computed(() => a.value * 2)        // b 依赖 a
const c = computed(() => b.value + 1)        // c 依赖 b

a.value = 10
// 链路：a 变 → b 标 dirty → b trigger → c 收到通知也标 dirty
// 下游读 c.value → c dirty 重算 → c 内部读 b.value → b dirty 重算

dirty 标志是顺链传递的：上游一个变，整条链上所有 computed 都被标脏，但只有被下游读到的那一层才真的重算。

可写 computed

const firstName = ref('Vue')
const lastName = ref('3')

const fullName = computed({
  get: () => firstName.value + ' ' + lastName.value,
  set: (newVal) => {
    [firstName.value, lastName.value] = newVal.split(' ')
  }
})

fullName.value = 'React 18'
console.log(firstName.value)  // 'React'
console.log(lastName.value)   // '18'

可写 computed 的 setter 本质是"写一个值，反向同步多个源 ref"。它不是缓存逻辑的一部分——setter 触发时就是直接改上游 ref，再由上游 ref 的 trigger 让自己 dirty。

常见场景：表单的"读写双向"场景——v-model 一个 computed，get 返回展示值，set 拆成多个字段更新。

33.5 常见误用：在 computed 里写副作用

// ❌ 反例：computed 里写副作用
const fullName = computed(() => {
  document.title = this.firstName + ' ' + this.lastName  // 副作用！
  return this.firstName + ' ' + this.lastName
})

// ❌ 反例：computed 里发请求
const user = computed(() => {
  fetch('/api/user')       // 副作用！
  return cache
})

为什么是反模式？

  • computed 会被多次求值（首次 + 每次 dirty 后），副作用会被执行多次；
  • 求值时机不确定（被谁读、什么时候读都可能），副作用时机不可控；
  • 违反"computed 应该是纯函数"的语义：给同样的输入应该返回同样的输出。

正确做法：副作用用 watch / watchEffect 显式表达。

// ✅ 正例：computed 只做派生，副作用交给 watch
const fullName = computed(() => firstName.value + ' ' + lastName.value)

watch(fullName, (val) => {
  document.title = val     // 副作用显式、时机可控
})

computed 是"派生状态"，watch 是"副作用"。把它们混在一起会让你在某个莫名其妙的时机发现请求发了两次、标题被改了两次。

33.6 本章常见坑

  • 坑 1以为 computed 不依赖 ref 也能缓存：computed 的缓存依赖 track——如果 getter 里读的不是响应式数据，它根本不知道自己脏没脏，缓存也就没意义。
  • 坑 2在 computed getter 里改 ref：和"写副作用"同类，会导致无限循环（改自己的依赖 → 自己标脏 → 重算 → 又改）。
  • 坑 3需要"每次读都重算"却用了 computed：那应该用普通函数 function calc() { ... }，不要套 computed。
  • 坑 4可写 computed 里 setter 不写上游 ref：只是改了缓存值，源头没变——下次 get 又把你的 set 覆盖了。
  • 坑 5链式 computed 里某一层依赖了非响应式数据源：那一层的 dirty 永远不会被通知，缓存永远不刷新。

lazy 求值computed 定义时不跑 getter，第一次被读才跑
