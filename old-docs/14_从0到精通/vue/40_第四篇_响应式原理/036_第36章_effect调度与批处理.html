36.1 job 队列结构与去重

组件更新本质上是一个 job（一个 effect 的 run）。Vue 内部维护几个队列：

let isFlushing = false          // 是否正在 flush
let isFlushPending = false       // 是否已安排微任务 flush
const queue = []                 // 当前待执行的 job 列表（pre 队列）
const activePreFlushCbs = []    // pre watch 回调
const activePostFlushCbs = []    // post watch 回调
let currentFlushPromise = null   // 当前 flush 的 Promise（nextTick 用它）

queueJob 的去重

function queueJob(job) {
  // 1. 同一 job 不能在队列里重复
  if (!queue.includes(job)) {
    // 2. 如果正在 flush 中，且当前 job.id 比"正在跑的位置"大，插到末尾
    //    否则插到"正在跑的位置"之前——保证新 job 在当前位置之后执行
    queue.push(job)
  }
  // 3. 安排一次微任务 flush（幂等）
  queueFlush()
}

function queueFlush() {
  if (!isFlushing && !isFlushPending) {
    isFlushPending = true
    currentFlushPromise = Promise.resolve().then(flushJobs)
  }
}

去重的关键：queue.includes(job)——同一个组件的渲染 effect 被多次 trigger，只入队一次。这就是"循环 ++ 100 次只渲染一次"的实现根源。

36.2 同步修改多次 → 一次渲染

<script setup>
import { ref } from 'vue'
const count = ref(0)

// 同步代码：连续改 100 次
function onClick() {
  for (let i = 0; i < 100; i++) {
    count.value++
  }
  // 此时：count 已经是 100，但 DOM 还没更新
  // 队列里只有 1 个 job（组件的渲染 effect），去重过了
}
</script>

36.3 pre / post 队列与组件顺序

组件更新顺序：父先于子

flushJobs 里有一句关键：queue.sort((a, b) => a.id - b.id)。每个组件的渲染 job 有一个递增的 id（父组件先创建，id 小）。排序后：

  • 父组件先 render、先 patch，再子组件；
  • 避免"子组件先更新、父组件又更新导致子组件被重复渲染"。

pre / post 队列

队列内容执行时机
pre watch 回调watch(cb, { flush: 'pre' })所有组件 render 之前
组件 render job组件的渲染 effect父先子后
post watch 回调watch(cb, { flush: 'post' })所有组件 render + patch 之后
onUpdated 钩子组件生命周期组件 patch 后立即跑（在 post 之前）

Vue 的整个响应式更新是一次微任务里的一轮批处理：pre cb → 父 render → 子 render → patch → onUpdated → post cb。用户永远不会看到中间态。

36.4 自定义 scheduler 的用法

虽然业务代码很少直接手写 scheduler，但理解它能帮你看懂 watch 的 flush 选项是怎么实现的：

// watch(cb, { flush: 'post' }) 等价于：
new ReactiveEffect(getter, {
  scheduler(effect) {
    // 不是立刻跑，而是塞进 post 队列
    activePostFlushCbs.push(() => {
      const newVal = effect.run()
      cb(newVal, oldVal)
    })
    queueFlush()
  }
})

// flush: 'sync' 等价于：
new ReactiveEffect(getter, {
  scheduler(effect) {
    const newVal = effect.run()   // 同步立刻跑
    cb(newVal, oldVal)
  }
})

业务场景：自定义节流

// 你可以自己写一个"防抖的 watch"
import { watch } from 'vue'

watch(
  searchKeyword,
  (kw) => fetch(kw),
  {
    flush: 'post',
    // 注：Vue 没暴露直接配 scheduler 的选项，但 flush 已经覆盖 99% 场景
    // 真要完全自定义调度，可以用 watch 源 + 自己节流
  }
)
实际建议：业务代码用 flush: 'pre' / 'post' / 'sync' + await nextTick 就够了；手写 scheduler 是框架级的事（Pinia、VueUse 某些工具会用到）。

36.5 批处理与 watch 回调时机

把"批处理"和"watch 回调"放在一张表里：

代码位置DOM 状态说明
同步改完立刻读 DOM旧批处理还没跑
watch(cb, { flush: 'pre' }) cb 里旧cb 在 patch 前跑
watch(cb, { flush: 'post' }) cb 里新cb 在 patch 后跑
onUpdated 钩子里新组件 patch 后立即跑
await nextTick() 之后新等当前 flush 完成

新手最常见的困惑："为什么我在 watch 里改了 state，页面没立刻更新？"——因为 watch cb 跑完之后还要进下一轮 flush（pre cb → render → patch），不是 cb 里改完就同步 patch。

36.6 本章常见坑

  • 坑 1以为 watch pre cb 里能读到新 DOM：不能，pre cb 在 patch 前。要新 DOM 用 post 或 onUpdated。
  • 坑 2在 watch pre cb 里改 state：会触发新一轮 flush（又一轮 pre cb → render）——如果改的 state 又被 watch，可能引起额外渲染。能用 computed 就别用 watch。
  • 坑 3用 setTimeout 等 DOM 更新：setTimeout 是宏任务，比微任务晚得多。用 nextTick 或 post watch。
  • 坑 4以为组件更新顺序是子先父后：默认父先子后。如果你的代码依赖"子组件先更新"，要重新设计。
  • 坑 5在同步代码里多次 nextTick：每次 nextTick 都排到队列后面，但当前 flush 只跑一轮，多次 nextTick 回调都在同一轮 flush 后跑。

要点一句话
