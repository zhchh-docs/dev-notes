45.1 从 Core 到 ORM：声明式映射

第 44 章我们用 text() 手写 SQL；ORM 要做的，是把"表"变成一个 Python 对象，让你操作对象，而不是拼字符串。

SQLAlchemy 2.x 的推荐写法是声明式映射（Declarative Mapping）：一个继承 DeclarativeBase 的基类，加上 Mapped[...] 类型注解，类名即表名（可覆盖），属性即列。

from datetime import datetime
from sqlalchemy import String, DateTime, ForeignKey
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    """所有模型的基类，同时也是 metadata 的持有者"""
    pass

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50), unique=True)
    email: Mapped[str] = mapped_column(String(120))
    created_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.now)

    def __repr__(self) -> str:
        return f"User(id={self.id}, name={self.name!r})"

几个关键点：

  • Mapped[str] 告诉 ORM"这一列是字符串"；显式给出 mapped_column(String(50)) 可以控制长度、约束等细节。省略 mapped_column 时，2.x 也会根据注解推断列类型。
  • 主键列类型 Mapped[int] 会被自动推断为 INTEGER AUTO_INCREMENT（MySQL 方言下）；
  • __tablename__ 缺省时类名小写即表名（User → user），显式指定更稳；
  • default=datetime.now 是 Python 侧默认值（插入时执行），不是数据库默认值——想要数据库侧的 DEFAULT 应写 server_default=text("CURRENT_TIMESTAMP")。
常见坑老教程里的 class User(Base): 其中 Base 是 declarative_base() 函数造的；2.x 推荐 class Base(DeclarativeBase)。两者不可混用。GitHub 上大量 1.x 风格的 db.Column、db.Integer 在 2.x 里仍然能跑（兼容层），但新代码请用注解风格。

图 45-1 声明式映射：类 → 表 → 行 三个层次

ORM 不消灭 SQL，它把"你写 SQL"变成"框架替你翻译 SQL"——代价是你必须懂背后的 SQL，否则写不出高效查询。

45.2 类型映射与约束

列类型、约束、索引都写在 mapped_column 的参数里。先看常用映射表，再看一个带外键的完整模型。

Python 注解类型默认列类型常用 mapped_column 参数
intINTEGERprimary_key=True、autoincrement
strVARCHAR（默认 255）String(50) 定长、unique=True、index=True
datetimeDATETIMEdefault=、server_default=、onupdate=
boolBOOLEAN/TINYINTdefault=False（服务端默认见方言）
floatFLOAT/DOUBLENumeric(10,2) 精确小数用这个
DecimalNUMERICNumeric(precision, scale) 金额必须用它
UUIDCHAR(32) 等Uuid 类型（2.0+）
list[str] / dictJSONsqlalchemy.JSON；MySQL 5.7+ 支持 JSON 列
dateDATE只存日期用 Date

外键与关系的"物理一半"写在列上：

from sqlalchemy import Boolean, Text
from sqlalchemy.orm import Mapped, mapped_column, relationship

class Todo(Base):
    __tablename__ = "todos"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(100))
    detail: Mapped[str] = mapped_column(Text, default="")
    done: Mapped[bool] = mapped_column(Boolean, default=False)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)

    user: Mapped["User"] = relationship(back_populates="todos")
  • ForeignKey("users.id")：字符串指向"表名.列名"，不关心 Python 类名——这是 SQL 层的事实；
  • index=True：外键列默认不建索引，而按外键过滤是高频查询，手动加索引是常见优化；
  • 金额、分数等精确数值一律 Numeric，别用 float——MySQL 书里讲过浮点误差，这里同样成立。
常见坑Mapped[str] = mapped_column() 与 name: Mapped[str] = "ada" 完全不同：后者是类属性默认值，不是列！列必须经过 mapped_column()。同理，__tablename__ 写错（比如带空格）会在建表时报错。

关键建立模型后，用 Base.metadata.create_all(engine) 可以快速建表（开发期利器，生产请用 Alembic——45.5 节）。

45.3 relationship：关系的另一半

外键是"物理"关系，relationship 是"逻辑"关系——它让你写 user.todos 这样的导航，而不是自己 join。

一对多：User.todos 是集合，Todo.user 是单个对象。两个方向用 back_populates 互相指认：

class User(Base):
    __tablename__ = "users"
    # ...列省略...
    todos: Mapped[list["Todo"]] = relationship(back_populates="user")

class Todo(Base):
    __tablename__ = "todos"
    # ...列省略，含 user_id 外键...
    user: Mapped["User"] = relationship(back_populates="todos")

多对多需要一张关联表，用 secondary 参数挂上去：

from sqlalchemy import Table, Column

# 关联表：只有外键，不需要独立模型
user_role = Table(
    "user_roles", Base.metadata,
    Column("user_id", ForeignKey("users.id"), primary_key=True),
    Column("role_id", ForeignKey("roles.id"), primary_key=True),
)

class Role(Base):
    __tablename__ = "roles"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(30), unique=True)
    users: Mapped[list["User"]] = relationship(secondary=user_role, back_populates="roles")

class User(Base):
    __tablename__ = "users"
    # ...
    roles: Mapped[list["Role"]] = relationship(secondary=user_role, back_populates="users")

使用关系最自然的方式是"追加对象"：

with Session(engine) as session:
    ada = session.query(User).filter_by(name="ada").one()  # 1.x 风格，仍可用
    ada.todos.append(Todo(title="写第 45 章"))
    session.commit()

关系是"导航的便利"，不是"表的真相"：数据库里只有外键和关联表，relationship 只是让你少写 join。

懒加载（lazy load）：访问 user.todos 时才发第二条 SQL。列表场景用 selectinload() 提前加载，避免 N+1 查询：

from sqlalchemy.orm import selectinload
from sqlalchemy import select

stmt = select(User).options(selectinload(User.todos))
users = session.scalars(stmt).all()  # 两条 SQL：查用户 + 一次 IN 查 todos
选项作用适用
默认（lazy）访问时逐条查询单个对象，避免浪费
selectinload()一次 IN 查询批量加载集合列表页取子集合
joinedload()LEFT JOIN 一次取出多对一、单行场景
lazy="selectin"关系上直接声明默认策略集合常用时写在模型上
常见坑N+1：循环里访问 u.todos 会产生"1 条用户查询 + N 条 todo 查询"。日志里看到成串 SELECT 就是它。列表接口一律配 selectinload 或直接写 join。

45.4 增删改查：Session 的正确用法

Session 是"工作单元"：你在会话里改对象，最后 commit() 一次性落库。它对应第 44 章讲过的事务边界。

from sqlalchemy import select, delete
from sqlalchemy.orm import Session

# 创建（INSERT）
with Session(engine) as session:
    session.add(User(name="ada", email="ada@example.com"))
    session.commit()          # 事务提交，自增 id 在此后可用

# 读取（SELECT）：2.x 推荐 select() 风格
with Session(engine) as session:
    user = session.scalars(select(User).where(User.name == "ada")).one()
    # scalars() 拿实体；scalar() 只拿单个值
    users = session.scalars(select(User).order_by(User.id.desc()).limit(10)).all()

# 更新（UPDATE）：拿到对象直接改属性
with Session(engine) as session:
    todo = session.get(Todo, 3)          # 按主键取
    todo.done = True
    session.commit()

# 删除（DELETE）
with Session(engine) as session:
    todo = session.get(Todo, 3)
    session.delete(todo)
    session.commit()

事务与回滚：

  • with Session(engine) as session: 正常退出时若未 commit() 会自动回滚——所以"读多写少"的代码段可以省略 commit；
  • 写入类操作必须显式 commit()，否则退出即回滚，数据丢失；
  • flush() 把 SQL 发到数据库但不提交——当你需要在同一事务里立即拿到主键时用。
# 批量删除：不遍历对象，直接构造 DELETE
with Session(engine) as session:
    session.execute(delete(Todo).where(Todo.done == True))
    session.commit()
常见坑三个"以为提交了"的瞬间：① 只 add() 不 commit()；② 改完对象忘了 commit；③ 在 with 块外面用 session 对象（Session 已关闭，抛 DetachedInstanceError 或莫名失效）。Web 场景的规范做法：每个请求开一个 Session，结束时提交/回滚并关闭——第 43 章依赖注入 + 第 50 章实战会给出完整写法。

进阶只读路径可以用 session.scalars(...) 后立即退出；要返回给 FastAPI 的模型对象，若需要在会话关闭后访问，要么在会话内先把属性读出来（或 expunge），要么用第 42 章的 Pydantic model_validate 转成响应模型——ORM 对象离开 Session 后是"脱管"状态。

45.5 Alembic：让表结构像代码一样演进

开发期 create_all() 够了；上线后改表要可回滚、可审计——这就是迁移（migration）工具 Alembic 的职责。

# 1) 安装并初始化（在项目根目录）
pip install alembic
alembic init alembic

# 2) 让 Alembic 认识我们的模型：编辑 alembic/env.py
#    from models import Base  # 导入你的 Base
#    target_metadata = Base.metadata

# 3) 自动生成迁移脚本（对比 models 与数据库差异）
alembic revision --autogenerate -m "create users and todos"

# 4) 应用迁移
alembic upgrade head

# 5) 回滚一步
alembic downgrade -1

迁移脚本长什么样：

"""create users and todos

Revision ID: 1a2b3c
Revises:
Create Date: 2026-10-20
"""
from alembic import op
import sqlalchemy as sa

def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.Integer(), primary_key=True),
        sa.Column("name", sa.String(length=50), nullable=False),
        sa.Column("email", sa.String(length=120), nullable=False),
        sa.Column("created_at", sa.DateTime(), nullable=False),
    )

def downgrade() -> None:
    op.drop_table("users")

Alembic 的边界，务必记住：

场景autogenerate 能否发现
新增表 / 新增列 / 删列能。生成对应的 create/drop 操作
改列类型 / 改长度大多能（生成 alter_column），但缩长度等风险操作要人工确认
重命名表 / 重命名列不能，会被识别成"删+增"，数据会丢——必须手写 op.rename_table
改默认值 / 索引 / 约束部分能，索引常能生成；默认值变更需人工核对
常见坑线上环境的 downgrade 会删表/删列。生产回滚前先备份；大多数团队对"破坏性迁移"的纪律是：预发环境演练 + 评审 downgrade 脚本。

迁移文件就是"表结构的 git 提交记录"：谁、何时、改了什么、能否回退——这也是第 50 章项目实战里模型演进的标准姿势。
