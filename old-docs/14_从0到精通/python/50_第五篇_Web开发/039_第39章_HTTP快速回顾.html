39.1 报文结构：一次请求到底长什么样

HTTP 本质是一段纯文本（或二进制帧）的"请求-响应"对话：客户端发一段请求，服务端回一段响应，两段都是"行 + 头 + 空行 + 体"。

打开浏览器访问任意接口，DevTools 里看到的都是经过美化的 JSON；但协议在 TCP 字节流上跑的原始形态是这样的——请求报文：

POST /items?page=1 HTTP/1.1
Host: api.example.com
Content-Type: application/json; charset=utf-8
Content-Length: 32
Authorization: Bearer eyJhbGciOi...
Accept: application/json

{"name":"算法图解","price":39.5}

对应地，服务端返回的响应报文：

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 47
Cache-Control: no-cache
Set-Cookie: session=abc123; HttpOnly; Path=/; SameSite=Lax

{"id":101,"name":"算法图解","price":39.5}

拆开看，两者结构完全对称：

  • 起始行：请求侧是 方法 路径 HTTP版本（请求行），响应侧是 HTTP版本 状态码 原因短语（状态行）；
  • 首部（headers）：若干 键: 值 行，每行一个，传递元信息（类型、长度、认证、缓存策略）；
  • 空行：一个独立的换行，标志首部结束——这是协议里最容易被初学者忽略的一个分隔符；
  • 主体（body）：可选，承载实际数据（JSON、表单、文件）。GET 请求通常没有 body。

图 39-1 HTTP 请求与响应的对称结构

FastAPI 框架替你做的事，就是把"请求行里的路径、请求头、请求体"解析成 Python 函数参数，再把函数返回值序列化成这段响应报文。理解了报文，就理解了框架在干什么。

39.2 方法与语义：动词、幂等性与安全方法

HTTP 方法（method）不是"CRUD 的别名"，而是一组有精确定义的语义约定。后端设计接口时，方法选错，客户端和代理（CDN、缓存）的行为就会错。

方法语义幂等典型用途
GET获取资源，安全、幂等是查列表、查详情；可被缓存
HEAD只要响应头，不要体是探活、检查文件是否存在
POST创建资源 / 执行一个非幂等动作否新增、提交订单、登录
PUT整体替换某个已知 URI 的资源是全量更新（客户端提供完整对象）
PATCH部分更新通常否只改几个字段（如改密码）
DELETE删除指定 URI 的资源是删一行；重复删结果相同
OPTIONS询问该 URI 支持哪些方法 / CORS 预检是浏览器跨域预检（第 43 章）

两个必须建立的概念

  • 幂等（idempotent）：同一个请求发一次和发 N 次，服务端状态与响应都相同。DELETE /items/1 删三次，结果都是"没了"；但 POST /orders 发三次会建三个订单。幂等性决定了网络超时重试用哪个方法是安全的——这是分布式系统的命门；
  • 安全（safe）：方法本身不修改服务端状态。GET / HEAD / OPTIONS 是安全的，因此 CDN、浏览器才敢缓存、预取它们。
常见坑前端老项目里常见的"用 GET 提交删除、用 POST 做查询"是历史包袱。现代后端 API 里：带副作用的操作不要用 GET——爬虫、预加载、CDN 刷新会意外触发它。FastAPI 里 @app.get 与 @app.post 的区别，语义就在这里。

39.3 状态码族：后端为什么总在返 4xx/5xx

状态码是三位数字，第一位决定大类。后端的基本功就是：每个失败分支，都能说出"我该返 4xx 还是 5xx，具体是哪个"。

族含义你必须背下来的常见值
2xx 成功请求被正常处理200 OK（查询成功）；201 Created（POST 创建成功，应返回 Location 头指向新资源）；204 No Content（DELETE 成功，无返回体）
3xx 重定向需要客户端进一步动作301 永久搬家；302 临时跳转；304 Not Modified（协商缓存，本地缓存还能用，不返 body）
4xx 客户端错问题在客户端发的请求400 报文格式错；401 未认证（没登录/令牌失效）；403 已登录但没权限；404 资源不存在；422 语义错（FastAPI 校验失败默认值）；429 请求太频繁（限流）
5xx 服务端错问题在服务端自己500 内部异常；502 网关拿到上游坏响应（如 uvicorn 挂了）；503 服务暂不可用（维护/过载）

后端视角的三个易错点

  1. 401 vs 403：401 是"你是谁？"（没登录），403 是"我知道你是谁，但你不配"（登录了没权限）。FastAPI 里用 HTTPException(status_code=401) 与 403 区分；
  2. 422 vs 400：400 是报文本身非法（不是合法 JSON），422 是 JSON 合法但字段不满足业务约束（age 是负数、缺必填字段）。FastAPI 的 Pydantic 校验失败自动返 422，这也是它和老框架最大的体感差异；
  3. 500 是兜底，不是默认答案：业务校验失败永远不该抛 500——抛 500 等于告诉监控"我的代码炸了"，而实际上只是用户输入不合法。

一条黄金法则：4xx 是用户/客户端的错，你要把错误信息说清楚；5xx 是你的错，要记日志、修 bug，不要把堆栈直接甩给用户。

39.4 常用请求头与响应头

首部是协议里最"杂"的部分——几十个头各管一件事。后端日常打交道的就那六七个，先认全它们。

首部方向作用
Host请求目标主机名（一台服务器托管多个站点，靠它区分）；HTTP/1.1 必填
Content-Type双向body 的格式：application/json、application/x-www-form-urlencoded（表单）、multipart/form-data（文件上传）、text/html; charset=utf-8
Content-Length双向body 字节数；服务端靠它知道"什么时候读完"（除非用分块传输）
Accept请求客户端说"我能接受什么格式"：Accept: application/json
Authorization请求认证凭证，最常见形式 Authorization: Bearer <token>（第 46 章 JWT 专题）
Cache-Control双向缓存指令：max-age=3600（可缓存 1 小时）、no-cache（每次要协商）、no-store（彻底不存）
Set-Cookie响应服务端往客户端种 Cookie，可带 HttpOnly（JS 读不到，防 XSS 偷）、Secure（只走 HTTPS）、SameSite=Lax
User-Agent请求客户端标识（浏览器/curl/爬虫）；日志里常用它识别调用方
FastAPI 会自动处理 Content-Type 与序列化，但 Authorization、Cache-Control、Set-Cookie 这些需要你在代码里显式声明——后面章节会逐个用到。

39.5 无状态、Cookie 与 Session

HTTP 是无状态协议：服务端默认不记得你上一次请求说了什么。这句话是所有登录机制的设计原点。

"无状态"意味着每个请求都必须自带全部上下文。但用户登录一次、后续每个请求都带账号密码显然不现实，于是演化出两条主流路线：

  • Cookie + Session：登录成功后，服务端在内存/数据库里存一份会话，把会话 ID 通过 Set-Cookie 种给浏览器；之后浏览器每次自动带上 Cookie: session=abc123，服务端凭这个 ID 找到会话。状态留在服务端；
  • Token（JWT）：服务端登录时发一个自包含的签名令牌（里面装着用户 ID、过期时间），之后客户端在 Authorization: Bearer ... 里带上它；服务端只验签名、不存任何东西。状态完全留在客户端，这才是"真无状态"。

图 39-2 会话存储位置决定了架构形态

为什么 Cookie 要设 HttpOnly？因为它能被 JS（document.cookie）读取；一旦有 XSS 漏洞，攻击者就能偷走会话 ID。现代 API 优先用 Authorization 头传 Token，Cookie 留给浏览器自动场景。

39.6 HTTP/1.1、2、3：你用的是哪一代

你不需要自己处理协议版本细节，但"为什么 HTTP/2 更快"是面试与排查性能问题时绕不开的常识。

版本年份关键特征与痛点
HTTP/1.11997文本协议；默认长连接（keep-alive），但同一连接上同一时刻只能处理一个请求（队头阻塞），靠开多个 TCP 连接并发（浏览器限制 6 个）
HTTP/22015二进制分帧；多路复用——一个 TCP 连接上并发多个请求/响应流；头部用 HPACK 压缩；支持服务端推送。但 TCP 层丢包仍会阻塞所有流
HTTP/32022基于 QUIC（跑在 UDP 上），把多路复用做到传输层，解决 TCP 队头阻塞；连接迁移（切 WiFi/4G 不断连）。目前主流浏览器与 CDN 已支持
对 FastAPI 开发者而言：uvicorn 直接对客户端说的是 HTTP/1.1；HTTP/2、HTTP/3 通常由前置的 Nginx / CDN 终结——应用层代码完全无感，这也是"协议升级不用改业务代码"的好处。

39.7 REST 资源设计与 curl 实操

REST 不是标准，是一套设计风格：把一切建模成"名词资源"，用 HTTP 动词表达操作，用 URI 定位资源。FastAPI 的路由设计默认就鼓励你这么做。

四条实用原则

  • URI 是名词，不是动词：/items 而不是 /getItems；操作由方法表达（GET /items 就是"查"）；
  • 集合用复数，嵌套表达从属：/shops/42/orders（42 号店的订单）；
  • 层级别太深，超过两层就要考虑是否该直接 /orders?shop_id=42；
  • 版本号放 URI 或头：/v1/items 是最省心的做法。

用 curl 把本章串起来

下一章我们会起一个 FastAPI 服务，但现在你可以先在任意已跑服务上练观察。curl -v 会把字节流上的完整报文打印出来：

# -v 显示通信全过程；-i 把响应头也打出来
curl -v http://127.0.0.1:8000/items/1

# POST 一个 JSON 创建资源
curl -X POST http://127.0.0.1:8000/items `
  -H "Content-Type: application/json" `
  -d '{"name":"算法图解","price":39.5}'

# 带 Bearer 令牌
curl http://127.0.0.1:8000/me `
  -H "Authorization: Bearer eyJhbGciOi..."

在 -v 输出里，> 开头的行是你发出去的请求报文，< 开头的行是服务端返回的响应报文——对照 39.1 节的骨架逐行读，十分钟就能建立"协议直觉"。

前端看 DevTools 是"结果"，后端用 curl -v 是"协议本身"。往后每一章写的 FastAPI 接口，你都应该用 curl 亲手打一次——这是建立后端手感最快的方式。
