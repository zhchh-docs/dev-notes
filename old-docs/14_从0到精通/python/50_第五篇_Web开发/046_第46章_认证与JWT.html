46.1 认证 vs 授权：先分清两个词

面试和设计评审里第一个被考的就是这个区分。认证回答"你是谁"，授权回答"你能做什么"。

概念回答的问题典型实现
认证 Authentication你是谁？（验证身份）密码校验、OAuth 登录、短信验证码、Authorization 头里的凭证
授权 Authorization你能干什么？（判定权限）角色（admin/user）、权限位、Depends 里的权限检查
会话 Session登录状态存在哪边？服务端存 session、Cookie 只存 session id
Token 令牌凭证怎么携带？JWT 放进 Authorization: Bearer <token>

前端同学对"登录后把 token 存 localStorage、请求时塞进 header"很熟——那就是无状态认证的客户端一侧。服务端一侧要做的：签发 token、校验 token、从 token 还原"当前用户"。

图 46-1 登录签发 JWT、之后请求携带并验签的完整闭环

"登录"是认证，"加餐按钮只有会员可见"是授权。两者常在同一接口里先后发生，但代码上必须分开检查。

46.2 密码存储：哈希，而不是加密

数据库被拖走是迟早的事，你的底线是：攻击者拿到密码表，也倒推不出任何明文。

加密是可逆的——有密钥就能还原明文，所以存加密密码等于把钥匙和锁放在一起。哈希是不可逆的，但普通哈希（MD5、SHA-1、快速 SHA-256）太快，GPU 可以每秒算几十亿次，字典攻击分分钟破掉。正确的做法是加盐 + 慢哈希：

存储方案是否可逆结论
明文—绝对禁止，任何泄密都是裸奔
MD5 / SHA-1不可逆但可暴力秒破，禁止
快速哈希 + 固定盐不可逆但可彩虹表同一密码产生同一结果，仍可批量破解
慢哈希 + 随机盐（bcrypt / argon2）不可逆且极慢✅ 业界标准：passlib / bcrypt / argon2-cffi
 
# 安装（FastAPI 官方教程的搭配）
pip install "passlib[bcrypt]"
# 或更现代的 argon2
pip install argon2-cffi
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(raw: str) -> str:
    return pwd_context.hash(raw)

def verify_password(raw: str, hashed: str) -> bool:
    return pwd_context.verify(raw, hashed)

用法要点：

  • hash() 每次都会生成新的随机盐，所以同一密码两次哈希结果不同——这是特性不是 bug；
  • verify() 负责从哈希串里取出盐并重新计算、比对，且实现是恒定时间比较，避免时序侧信道；
  • bcrypt 有 72 字节长度上限，超长密码会静默截断——超长输入先做一层普通哈希再交给 bcrypt 是通行做法。
常见坑不要把 hash(password) 内置函数（返回的是内存地址哈希）跟密码哈希混为一谈；也不要用 base64、"异或加密"之类 DIY 方案。密码学没有"自定义加密"的余地。

46.3 JWT 的结构：三个用点号分开的段

JWT 不是"加密"的——Payload 是 Base64Url 编码，任何人解码都能读。它靠 签名保证"没被篡改"，靠 HTTPS 保证"传输中没人看"。

常见坑有人把敏感信息（手机号、身份证）塞进 payload——Payload 只是编码，解码即可见。放进去等于明文。payload 只放 sub（用户 id）这类可索引的标识。

46.4 签发与校验：PyJWT 实操

库选 PyJWT（官方文档同款）。签发、校验、过期，三件事十行代码。

import jwt
from datetime import datetime, timedelta, timezone

SECRET_KEY = "dev-only-secret"   # 生产必须来自环境变量，见 46.5 节
ALGORITHM = "HS256"

def create_access_token(user_id: int, expires_minutes: int = 30) -> str:
    payload = {
        "sub": str(user_id),                      # subject：用户标识
        "iat": datetime.now(timezone.utc),        # 签发时间
        "exp": datetime.now(timezone.utc) + timedelta(minutes=expires_minutes),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> dict:
    return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
token = create_access_token(1)
print(token)

payload = decode_token(token)
print(payload["sub"])        # "1"

# 过期：decode 抛 jwt.ExpiredSignatureError
# 篡改：decode 抛 jwt.InvalidSignatureError
  • jwt.encode 在 PyJWT 2.x 返回 str（不是 bytes），别再 .decode("utf-8")；
  • exp 在 PyJWT 2.x 要求时区感知的 datetime（上面用 timezone.utc），传 naive 时间会报错；
  • 校验时 algorithms=[ALGORITHM] 必须显式给出——不给等于允许攻击者改 header 里的 alg 降级攻击。

进阶刷新令牌（refresh token）：短期 access token（如 30 分钟）+ 长期 refresh token（如 7 天）。access 过期后拿 refresh 换新的，refresh 只在专门的 /refresh 端点使用，泄露面更小。注销（登出）则靠黑名单：服务端记下已注销 token 的 jti（JWT ID），校验时先查黑名单——无状态由此退化为"半状态"，但业务上值得。

46.5 接进 FastAPI：OAuth2PasswordBearer 与 current_user

FastAPI 官方教程的认证闭环：登录端点发 token，依赖注入解 token，路由函数声明"我要当前用户"。

from fastapi import FastAPI, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from sqlalchemy import select
from sqlalchemy.orm import Session

app = FastAPI()
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")   # 指向登录端点

def get_db():
    with Session(engine) as session:
        yield session

def get_current_user(token: str = Depends(oauth2_scheme),
                     db: Session = Depends(get_db)) -> User:
    credentials = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="凭证无效",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = decode_token(token)
        user_id = int(payload["sub"])
    except Exception:
        raise credentials
    user = db.scalar(select(User).where(User.id == user_id))
    if user is None:
        raise credentials
    return user
from fastapi.security import OAuth2PasswordRequestForm

@app.post("/token")
def login(form: OAuth2PasswordRequestForm = Depends(), db: Session = Depends(get_db)):
    user = db.scalar(select(User).where(User.name == form.username))
    if user is None or not verify_password(form.password, user.password_hash):
        raise HTTPException(status_code=401, detail="用户名或密码错误")
    return {"access_token": create_access_token(user.id), "token_type": "bearer"}

@app.get("/users/me")
def read_me(current_user: User = Depends(get_current_user)):
    return {"id": current_user.id, "name": current_user.name}

跑起来之后：

  • OAuth2PasswordRequestForm 需要 python-multipart（pip install python-multipart），否则 /docs 上登录表单会报错；
  • tokenUrl="token" 是相对路径——告诉 Swagger UI 去哪里取 token，让 /docs 自动出现"Authorize"按钮；
  • 依赖函数返回 User，路由只要写 current_user: User = Depends(get_current_user)，FastAPI 会先跑依赖链再进路由——这就是第 43 章依赖注入在真实安全场景的用法。

把"如何拿到当前用户"写成一个依赖，整个应用就统一了校验入口——审计、换算法、加黑名单都只改一处。

46.6 安全边界：密钥、传输与常见坑

代码能跑 ≠ 安全。上线前逐条过这份清单。

风险正确做法反面教材
SECRET_KEY 泄露环境变量 / 密钥管理服务注入，不同环境不同密钥写死在代码里、提交进 git
明文传输生产强制 HTTPS（第 49 章 Nginx 配证书）HTTP 下 token 被中间人截走
payload 泄密只放 sub/iat/exp/jti放手机号、身份证、密码哈希
算法混淆攻击decode(..., algorithms=["HS256"]) 显式锁定不传 algorithms 或依赖 header
token 被盗短过期 + refresh 轮换；敏感操作二次验证30 天有效期的长 token
登录爆破限流（IP/账号维度）、失败延迟无节流随便打
常见坑本地开发时 SECRET_KEY = "dev" 凑合能用，忘了改就上线——全站 token 都能被伪造。另一个高频坑：把 token 存在 localStorage 且不过期，被 XSS 一锅端；更稳的是 HttpOnly Cookie + CSRF 防护，但那是另一套取舍。

认证体系的安全强度，取决于最弱的一环——而最弱的一环通常是密钥管理，其次才是算法本身。
