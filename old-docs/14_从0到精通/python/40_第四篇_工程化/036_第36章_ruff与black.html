第 36 章 ruff 与 black：规范自动化

教科书 第 36 章 / 共 60 章 · 预计 25 分钟 · 需写过多个 Python 文件

团队为"单引号还是双引号、换行放哪、import 顺序"争论过吗？规范自动化的思路是：这些问题不该由人来吵，交给工具。black 是"零意见"的格式化器，ruff 是用 Rust 写的极速 linter + 格式化器，二者配合，让代码风格从 Code Review 的聊天话题变成机器自动执行的流水线。

◆本章目标

  • 理解为什么格式化不该靠人：风格争论的本质是"没有权威"；
  • 会用 black 格式化代码，说清它的零配置哲学与 88 列、双引号等默认规则；
  • 会用 ruff check / ruff format，认识规则码 E/F/W/I/UP/B；
  • 能在 pyproject.toml 里配置 [tool.black] 与 [tool.ruff]；
  • 会用 pre-commit 把检查挂到 git 提交前，实现"不规范的代码根本提交不上去"。
前置要求：用过 pip、有 git 基础（第 31 章）。前端同学可类比 ESLint + Prettier——ruff ≈ ESLint，black ≈ Prettier。

36.1 为什么要把风格交给机器

代码风格争论浪费的不是"几行代码"，而是团队的注意力与评审带宽。

早期 Python 社区靠 PEP 8（官方风格指南）统一约定，但 PEP 8 只是"建议"，没人强制执行，于是出现了 flake8、isort、autoflake 等一堆工具，各管一摊，配置还互相打架。现代做法是：

  • 格式化（format）：工具直接改代码，引号、缩进、换行全自动——black、ruff format；
  • 静态检查（lint）：工具指出"有问题"（未用变量、导入顺序、明显 bug），部分可自动修——ruff；
  • 把两者挂进提交钩子：代码不合规，连 commit 都做不了。

图 36-1 规范自动化流水线

当风格由机器统一，Code Review 的注意力才能集中在"逻辑对不对、设计好不好"，而不是"你这里为什么用单引号"。

36.2 black：零意见格式化器

black 的哲学是"少做选择"：它不提供一堆可配置项，而是直接规定一种唯一正确的写法，团队照用即可。

安装与运行

pip install black

# 格式化当前目录所有 py 文件（直接改文件）
black .

# 只检查不改（CI 里用）：格式不符就报错退出
black --check .

# 只看会改什么，不落盘
black --diff .

它的默认规则（记住几个高频的）

规则black 的做法
行宽默认 88 列（不是 PEP 8 的 79，是 black 自己定的）
字符串引号统一双引号 "..."（除非内部有双引号才用单引号）
括号爆炸参数太多一行放不下时，每个参数独占一行，尾逗号收尾
缩进4 空格，绝不混用 Tab
尾部逗号多行结构强制尾逗号，让 git diff 更干净

格式化前后对比：

# 你写的
def greet(name,times=1):return 'hello,'+name*times

# black 格式化后
def greet(name: str, times: int = 1) -> str:
    return "hello," + name * times
常见坑black 故意"不可配置"——它只有 --line-length 等极少数开关。想自定义风格？社区的回答是"别，接受 black 的默认值，把争论省下来"。真要改，说明你在为风格投入不该投入的精力。

36.3 ruff：一个工具顶六个

ruff 用 Rust 重写了整个 Python lint 生态，速度比 flake8 快几十到上百倍，一个二进制就替代 flake8 + isort + autoflake + pyupgrade 等多个工具。

安装与子命令

pip install ruff

# 静态检查：报问题
ruff check .

# 自动修复能修的问题（未用 import、未用变量等）
ruff check --fix .

# 格式化（black 兼容风格）
ruff format .

# 检查 + 格式化一把梭
ruff check . && ruff format .

规则码速查

ruff 的每条规则有一个字母前缀 + 编号，前缀代表它替代的旧工具：

规则码来源管什么
Epycodestyle格式错误（缩进、空格、行宽）
Wpycodestyle风格警告（非致命）
Fpyflakes真 bug：未用 import、未定义名字、重复参数
Iisortimport 排序与分组
UPpyupgrade把旧语法升级到新写法（如 Union → |）
Bflake8-bugbear常见陷阱：可变默认参数、except 太宽等

默认 ruff 只开了 E4/E7/E9/F 这一小撮；要全套，得在配置里显式启用（见下一节）。

# 看某条规则长什么样
ruff rule F401
# F401: 导入但未使用的模块

ruff 既是 linter 又是 formatter：ruff check 抓"错"，ruff format 管"美"。新项目甚至可以只用 ruff，不再单独装 black——它的 format 模式与 black 风格兼容。

36.4 pyproject 里固化团队规则

把规则写进 pyproject.toml，提交进 git，团队所有人、CI 跑的都是同一份配置。

[tool.black]
line-length = 88
target-version = ["py312"]

[tool.ruff]
line-length = 88
target-version = "py312"
src = ["src", "tests"]

# 启用哪些规则集
[tool.ruff.lint]
select = [
    "E",    # pycodestyle 格式错误
    "W",    # pycodestyle 警告
    "F",    # pyflakes 真 bug
    "I",    # isort import 排序
    "UP",   # pyupgrade 语法升级
    "B",    # bugbear 常见陷阱
]
# 排除个别不想管的规则
ignore = ["E501"]   # 行宽交给 formatter，lint 不重复报

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["B011"]   # 测试里允许某些写法
black 与 ruff format 二选一：两者风格高度兼容，但不要同时跑——它们在少数边界情况会互相"打架"。新项目推荐只用 ruff format；老项目已用 black 就保留 black，ruff 只做 check。

36.5 pre-commit：提交前自动跑

光有配置还不够——开发者可能忘记跑。pre-commit 把检查挂到 git commit 之前，不合规的代码根本提交不上去。

三步接入

pip install pre-commit

# 在项目根目录写 .pre-commit-config.yaml（见下）
pre-commit install     # 装到 git 钩子
pre-commit run --all-files   # 手动全量跑一次

.pre-commit-config.yaml：

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/psf/black
    rev: 24.8.0
    hooks:
      - id: black

之后每次 git commit，钩子自动对暂存区文件跑 ruff + black：

  • 能自动修的，直接改好文件，你重新 git add 再提交；
  • 修不了的问题（比如真 bug），commit 被拦下，必须先解决。

36.6 规范自动化的团队收益

把风格交给机器，省下来的是三样最贵的东西：人的注意力、评审带宽、协作摩擦。

维度没有自动化有 ruff + black + pre-commit
风格争论PR 里来回吵引号、换行零争论，工具说了算
评审重点一半在挑格式只看逻辑与设计
问题发现时机Code Review 甚至线上commit 前当场拦下
新人上手要背 PEP 8 细节工具自动纠正，边写边学
仓库历史混着各种风格统一、diff 干净

规范自动化的终极目标：让"写出不合规代码"这件事在物理上变得不可能——不是靠自觉，而是靠流水线。

✎ 本章习题

A 基础写出三条命令：① 用 black 格式化当前项目；② 用 ruff 检查并自动修复；③ 在 CI 里只检查不修改。并说明 --check 与 --fix 的区别。
B 进阶为一个新项目写一份 pyproject.toml 片段：black 行宽 88、目标 Python 3.12；ruff 启用 E/W/F/I/UP/B 规则集，但忽略 E501（行宽交给 formatter）。解释为什么要把 E501 从 lint 里排除。
