52.1 Thread：创建、启动、等待

多线程的三种打开方式：手搓 Thread、继承 Thread、用线程池（下一章）。先看前两种。

import threading
import time

def download(url: str):
    print(f"[{threading.current_thread().name}] 开始 {url}")
    time.sleep(1)                    # 模拟网络 IO
    print(f"[{threading.current_thread().name}] 完成 {url}")

# 方式一：传目标函数
t1 = threading.Thread(target=download, args=("http://a.example/1",), name="worker-1")
t2 = threading.Thread(target=download, args=("http://a.example/2",), name="worker-2")

t1.start()                            # 启动：线程进入可运行状态
t2.start()
t1.join()                             # 主线程等待 t1 结束
t2.join()
print("全部下载完成")
  • start() 只负责"让线程跑起来"，立即返回；真正干活在线程函数里；
  • join() 阻塞主线程直到该线程结束——"等它干完"；
  • name= 给线程起名，日志里可读性大增；
  • 两个线程各 sleep(1) 是并发的：总耗时约 1 秒而不是 2 秒（第 51 章的 IO 结论）。

daemon 参数：daemon=True 的线程不会阻止进程退出——主线程结束时，守护线程直接被杀。适合"心跳、日志、监控"这类不保证收尾的任务；需要收尾的活不要设 daemon，用 join() 等它。

常见坑Python 程序"退不出去"常常是某个非 daemon 线程还挂着（比如一个永不结束的轮询）。排查方法：threading.enumerate() 列出所有线程，看谁没退。

52.2 竞态条件与 Lock

共享可变状态是线程的万恶之源。看一个经典事故：100 个线程各加 10000 次，结果不是 100 万。

import threading

counter = 0
N_THREADS, N_PER = 100, 10_000

def add():
    global counter
    for _ in range(N_PER):
        counter += 1          # ← 这一行不是原子的！

threads = [threading.Thread(target=add) for _ in range(N_THREADS)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)                # 往往小于 1000000，每次跑结果还不一样

为什么？counter += 1 是"读 → 算 → 写"三步。线程 A 读到 100，线程 B 也读到 100，A 写回 101、B 写回 101——两次递增只涨了 1。这就是竞态条件（race condition）。

修复：把"读-算-写"包进锁，同一时刻只允许一个线程执行这段临界区。

import threading

counter = 0
lock = threading.Lock()

def add_safe():
    global counter
    for _ in range(N_PER):
        with lock:            # 临界区：互斥访问
            counter += 1

# 同上创建线程后运行
print(counter)                # 稳定输出 1000000

锁的作用不是"让代码变快"，而是"让并发的正确性可预期"——临界区要尽量短，锁才便宜。

常见坑GIL 让很多人误以为"字节码之间原子，不需要锁"——只有极少数操作（如 list.append、dict.get 单步）在 CPython 里恰好原子，复合操作一律要锁。原则：共享可变状态，必须锁；拿不准，就锁。

52.3 RLock 与死锁

同一线程重复拿同一把 Lock 会把自己卡死；RLock（可重入锁）允许同一线程多次获取。

import threading

lock = threading.Lock()
lock.acquire()
lock.acquire()      # 死锁！同一线程第二次拿普通 Lock，永远等不到
lock.release()
rlock = threading.RLock()
rlock.acquire()
rlock.acquire()     # 可以：RLock 记录"持有线程 + 次数"
rlock.release()
rlock.release()     # 释放次数与获取次数相等才真正解锁

RLock 的典型场景：函数 A 加锁后调用同样加锁的函数 B（嵌套调用）。更常见的死锁是两把锁交叉等待：

同步原语用途一句话
Lock互斥访问临界区同一线程只能拿一次
RLock可重入互斥同一线程可嵌套获取，按次数释放
Event一对多通知set() 唤醒所有 wait() 者
Semaphore限流最多 N 个线程同时进入（连接池）
Condition条件等待等某个条件成立再继续（队列空/满）
Barrier汇合N 个线程到齐才放行（并行阶段同步）
常见坑两把锁、两个方向：线程 A 持有锁 1 等锁 2，线程 B 持有锁 2 等锁 1——经典死锁。规避三招：① 所有线程按同一顺序拿锁；② 用 lock.acquire(timeout=...) 带超时拿锁，拿不到就放弃重试；③ 用 queue 把共享数据收进单队列，少用多把锁。

锁是"并发正确性"的杠杆：加对了稳，加少了错，加多了慢还容易死锁——最好的锁是没有锁（用队列、不可变数据、线程私有数据替代）。

52.4 通信：queue.Queue 与 Event

线程间共享数据的最佳姿势是队列：生产者往里放，消费者往外取，queue 内部自带锁，你不用碰锁。

import queue
import threading
import time

q = queue.Queue(maxsize=5)          # 有界队列：放满会阻塞

def producer():
    for i in range(10):
        q.put(f"任务 {i}")           # 队列满时阻塞等待
        time.sleep(0.1)
    q.put(None)                     # 哨兵：告诉消费者结束

def consumer(name: str):
    while True:
        item = q.get()              # 队列空时阻塞等待
        if item is None:
            q.task_done()
            break
        print(f"[{name}] 处理 {item}")
        time.sleep(0.2)
        q.task_done()               # 标记完成（配合 q.join()）

threading.Thread(target=producer).start()
for i in range(2):
    threading.Thread(target=consumer, args=(f"worker-{i}",)).start()

要点：

  • get()/put() 默认阻塞：队列空则消费者等，队列满则生产者等——天然实现"背压"；
  • 哨兵值（None）是结束消费者线程的常用协议；
  • task_done()/join() 让主线程能等待队列被消费完。

Event 做"发信号"：一个线程等待条件，另一个线程到点 set()。

import threading, time

start_gate = threading.Event()

def worker(name: str):
    print(f"[{name}] 就绪，等待发令枪")
    start_gate.wait()               # 阻塞直到 set()
    print(f"[{name}] 起跑！")

for i in range(3):
    threading.Thread(target=worker, args=(f"选手-{i}",)).start()
time.sleep(1)
start_gate.set()                    # 同时唤醒所有等待者

52.5 threading.local：线程私有数据

有些数据就该"每个线程各一份"——比如数据库连接。共享一个连接给所有线程用会互相踩踏，每个线程维护自己的连接才是正解。

import threading

local = threading.local()

def get_conn():
    if not hasattr(local, "conn"):     # 本线程还没有连接
        local.conn = "新连接"          # 每个线程第一次调用才建
        print(f"[{threading.current_thread().name}] 建立 {local.conn}")
    return local.conn

def worker():
    c1 = get_conn()
    c2 = get_conn()                    # 同一线程内复用
    assert c1 is c2

for i in range(3):
    threading.Thread(target=worker).start()
# 输出三行"建立新连接"——三个线程互不干扰

关键Web 框架（FastAPI 的依赖、Flask 的 request）底层大量使用 thread-local 保存"本次请求的上下文"。你写并发代码时，能用局部变量就别用全局；必须"每线程一份"时用 threading.local。

常见坑把 threading.local 当全局变量用是误区——它恰恰是"反全局"：让每个线程各有一份，避免共享竞争。真正的全局可变状态，还是需要锁。

52.6 多线程的常见坑

坑表现与对策
print 输出交错多个线程同时 print，行被撕碎。对策：日志加锁、或用 queue 汇总后统一打印
共享状态无锁结果随机。对策：能局部就局部，能队列就队列，必须共享就 with lock
死锁程序挂起。对策：锁顺序统一 / 带超时获取 / 少用多锁
线程泄漏每请求一个线程，服务越来越卡。对策：用线程池（下一章）而不是裸 Thread
异常静默线程函数抛异常默认只打 traceback，主线程不知道。对策：用 queue 回传结果/异常，或 concurrent.futures（第 53 章）
CPU 任务开多线程以为加速实则更慢。对策：回到第 51 章选型——CPU 用进程

多线程代码难的不是写，是"并发的正确性"——先想清楚共享什么、怎么保护，再动手。
