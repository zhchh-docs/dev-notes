10.1 为什么提交信息值得认真写

提交信息是 Git 里唯一由人书写、解释"为什么"的文本——代码本身只说明"现在是什么样"。

使用场景好信息带来的收益
事故定位git log -S / bisect 找到坏提交后，信息直接说明意图，省去读代码推测
代码评审评审者先看标题就明白改动范围，评审更快更准
自动生成 CHANGELOG规范前缀可让工具自动分类（feat/fix/…）并发布（第 34 章）
自动判定版本号feat → 次版本号 +1；fix → 修订号 +1；BREAKING → 主版本号 +1（第 33 章）
新人接手一条清晰的半年历史，胜过任何口头交接

提交信息不是写给 Git 看的，是写给半年后的你和接手的人看的；顺带还能让机器自动发版。

10.2 Conventional Commits 规范

<type>(<scope>): <subject>        ← 标题行（必填，≤50 字符为宜）

<body>                            ← 正文（可选，解释"为什么"）

<footer>                          ← 脚注（可选，关联 issue / 破坏性变更）
type含义示例
feat新功能feat(auth): 支持手机验证码登录
fix修复缺陷fix(order): 修复金额四舍五入误差
docs仅文档改动docs(readme): 补充安装步骤
style格式（不影响语义）style: 统一缩进为 2 空格
refactor重构（不增功能不修 bug）refactor(user): 抽离权限校验逻辑
perf性能优化perf(list): 首屏渲染改为虚拟滚动
test测试相关test(api): 补充登录接口用例
build构建/依赖build: 升级 vite 到 5.x
ciCI 配置ci: 增加 Node 20 测试矩阵
chore杂项chore: 更新 .gitignore
revert回滚revert: 撤销 feat(auth) 验证码登录

标题行规则：

  • 祈使句："添加…"而非"添加了…" / "adds…"（与 git merge 自动生成的语气一致）；
  • 首字母不大写、结尾不加句号；
  • 中文项目可用中文标题（feat(登录): 支持验证码），关键是全队统一；
  • 长度控制在 50 字符内（GitHub 列表、--oneline 都更友好）。

10.3 正文与脚注：写什么、怎么换行

fix(auth): 修复刷新令牌过期后未重试的缺陷

问题：access token 过期时，请求拦截器直接抛出 401，
导致用户被强制登出，即使 refresh token 仍有效。
原因：拦截器只在响应为 401 且 URL 非 /login 时刷新，
但未处理"刷新请求本身也返回 401"的情况。
方案：刷新失败时清理本地会话并跳转登录页，
同时补上对并发请求的队列化处理，避免重复刷新。

Refs: #482
Reviewed-by: Li Si

结构解读：

  1. 标题说"做了什么"（扫描时看这一行就够）；
  2. 正文说"为什么改、原来错在哪、方案取舍"——这部分是未来最值钱的信息；
  3. 脚注放关联与元信息：Refs #482 / Closes #482（平台会自动关闭 issue）、BREAKING CHANGE: ...（触发主版本升级）。
# 破坏性变更的两种写法（等价）
feat(api)!: 移除 v1 版用户接口

BREAKING CHANGE: /api/v1/users 已删除，请迁移到 /api/v2/users，
响应字段 id 由数字改为字符串。
编辑器配置：用 git commit（不带 -m）会打开编辑器，方便写多行；设置默认编辑器：git config --global core.editor "code --wait"（VS Code）。标题与正文之间必须空一行，否则 Git 会把它们当成同一段。

10.4 场景演练：把烂信息改成好信息

烂信息问题改写
修改不知道改了什么fix(cart): 修复优惠券叠加时金额计算错误
改bug哪个 bug？fix(login): 修复 Safari 下验证码图片不刷新
finish完成了什么？feat(export): 支持导出 Excel 报表
临时提交会永久留在历史里先 git stash 或 wip: 前缀，合并前用 rebase 清理（第 15 章）
代码格式化（改了 300 个文件）淹没真实改动单独一条 style: 全量格式化，与业务改动分开提交
 
# 已经提交了的烂信息怎么改（未推送时）
git commit --amend -m "fix(cart): 修复优惠券叠加时金额计算错误"   # 第 21 章
# 已推送的提交改信息属于历史改写，需团队协调（第三篇）

10.5 用工具强制规范：模板 + commitlint + hook

靠自觉不可靠，靠工具才稳定。三层防线：

① 提交模板（提示该写什么）

# ~/.gitmessage 或项目内 .gitmessage
# <type>(<scope>): <subject>  类型: feat fix docs style refactor perf test build ci chore revert
# 标题 ≤50 字，祈使句，结尾无句号
#
# 正文：为什么改？原来有什么问题？方案取舍？每行 ≤72 字
#
# 脚注：Refs #issue / BREAKING CHANGE: ...

git config --global commit.template ~/.gitmessage

② commit-msg hook + commitlint（拦截不合格）

# 安装（Node 项目）
npm i -D @commitlint/cli @commitlint/config-conventional husky
npx husky init
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg

# commitlint.config.js
module.exports = { extends: ['@commitlint/config-conventional'] };

# 效果：
git commit -m "改bug"
# ✘ subject may not be empty / type may not be empty
# ⚠ commit-msg hook failed

③ CI 侧校验（防止绕过本地 hook）

# .github/workflows/commitlint.yml 片段
- name: Lint commit messages
  run: npx commitlint --from=origin/main --to=HEAD --verbose
别过度严格：规范的目的是信息可读、机器可用，不是折磨同事。允许 chore、允许中英混排、允许偶尔的 wip（合并前清理），比"一刀切拒绝"更容易真正落地。

10.6 提交粒度：一次提交应该多大

粒度表现评价
太粗一周一次"本周改动"，涉及 40 个文件无法 bisect、无法回滚单个功能、评审困难
合适一个逻辑完整的改动：一个功能、一个修复、一次重构可独立回滚、可独立评审、历史可读
太细改一个变量名一次提交、加一行注释一次提交历史噪音；但本地开发期无所谓（rebase 整理即可）

三条实操建议：

  • 本地随便提交，推送前整理：开发期用 wip: 频繁存档（保命），push 前用交互式 rebase 合并成几条语义清晰的提交（第 15 章）；
  • 一次提交只做一件事：格式化与逻辑改动分开、重命名与内容改动分开（第 7 章）；
  • 能独立回滚是检验标准：问自己"这条提交单独 revert 会不会破坏其他功能"。

⚠ 常见坑清单

  • 坑 1：git commit -m "..." 写不了多行 → 不带 -m 用编辑器，或用两个 -m（第一个标题、第二个正文）；
  • 坑 2：中文提交在其他平台乱码 → 确保终端与 Git 均 UTF-8（git config i18n.commitEncoding utf-8）；
  • 坑 3：装了 commitlint 后 CI 挂了 → CI 里的 fetch-depth 不够，需 fetch-depth: 0；
  • 坑 4：脚注 Closes #123 只关了当前仓库的 issue → 跨仓库需写全称 Closes owner/repo#123；
  • 坑 5：把密钥、密码写进提交信息 → 信息同样进历史且无法局部删除，务必先检查再提交。

✓ 本章小结与第一篇回顾

要点一句话
格式type(scope): subject + 空行 + 正文 + 脚注
内容分工标题写"做了什么"，正文写"为什么"
破坏性变更! 或 BREAKING CHANGE: 脚注
落地手段模板提示 + commitlint 拦截 + CI 兜底
粒度标准一个逻辑完整改动，能独立回滚
