第 7 章 删除与移动文件

教科书 第 7 章 / 共 40 章 · 预计 35 分钟 · 动手章

删文件要单独学吗？要——因为 Git 里的"删除"有两种完全不同的含义：从工作区删、从仓库里停止跟踪。而"重命名"在 Git 里根本不是一个动作，而是靠内容相似度推断出来的。本章理清 git rm、git mv、--cached 与重命名识别。

7.1 删除的两条路：rm 与 git rm

两条路最终效果一样（都记录一次删除），区别只在"要不要再敲一次 add"：

# 路线 A：系统命令删除 → 再 add 记录删除
rm old.txt
git status -s
#  D old.txt           # 右列 D：工作区删了，暂存区还没记录
git add -A old.txt     # （或 git add -u）把"删除"这个动作暂存
git status -s
#D  old.txt            # 左列 D：删除已暂存
git commit -m "chore: 移除废弃文件 old.txt"

# 路线 B：git rm 一步到位（删文件 + 暂存删除）
git rm old.txt
git commit -m "chore: 移除废弃文件 old.txt"

强制删除场景（文件被改动过，Git 怕你误删）：

git rm -f 有改动的文件.txt     # -f = force
git rm -r docs/                # -r 递归删目录
git rm -r --cached build/      # 见 7.2：只停跟踪，不动硬盘
git rm 的价值：省一次 add，且在删除量大、路径复杂时（git rm -r）更不容易漏。日常删一两个文件，rm + git add -A 完全够用。

7.2 --cached：把文件踢出仓库但留在硬盘

这是最容易被误解的参数。它做的是：从暂存区/仓库中移除该文件的跟踪记录，但保留硬盘上的实体文件。

# 典型场景：不小心把本地配置文件提交了，想"以后别再跟踪它"
git rm --cached config.local.json
git status -s
#D  config.local.json   # 仓库中将删除
#?? config.local.json   # 但文件还在硬盘 → 变成未跟踪

# 立刻补上忽略规则，避免下次又被 add 回来
echo "config.local.json" >> .gitignore
git add .gitignore && git commit -m "chore: 停止跟踪本地配置文件"
命令硬盘文件仓库跟踪
rm f删除仍跟踪（需再 add 才记录删除）
git rm f删除删除（已暂存）
git rm --cached f保留删除（已暂存）
git rm -r --cached dir/保留整目录停止跟踪

坑：git rm --cached 不会让历史里已有的内容消失——别人 clone 后仍能从前几个提交里翻出这个文件。要真正抹掉历史里的敏感内容，需要 git filter-repo（第 27 章），并立即轮换密钥。

7.3 场景演练：误提交文件后的补救

场景：把 .env（含数据库密码）提交进了仓库，还没 push。

# 1. 先确认影响范围
git log --oneline -- .env
git show HEAD --stat

# 2A. 如果 .env 只是"上一次提交"里加进去的、且没推送 → 用 reset 撤回提交
git reset --soft HEAD~1        # 提交撤销，改动回到暂存区
git restore --staged .env      # 把 .env 挪出暂存区
echo ".env" >> .gitignore
git add .gitignore
git commit -m "feat: 原本那次提交的内容（已剔除 .env）"

# 2B. 如果 .env 已经在好几个提交里、且已推送 → 停止跟踪 + 轮换密钥
echo ".env" >> .gitignore
git rm --cached .env
git commit -m "chore: 停止跟踪 .env 并加入忽略"
# ⚠ 历史中的密钥仍可被检出 → 立即去改数据库密码 / 吊销 token
铁律：密钥一旦进过仓库，就当作已经泄露——停止跟踪只是止损，真正的安全动作是轮换（rotate）凭据。

7.4 移动与重命名：git mv 的真相

git mv old-name.js new-name.js
git status -s
#R  old-name.js -> new-name.js    # R = renamed

git commit -m "refactor: 重命名 old-name.js"

但 Git 里并没有存储"重命名"这个动作。git mv 只是三个动作的糖：

# 上面那条 git mv 完全等价于：
mv old-name.js new-name.js     # 1. 文件系统改名
git rm old-name.js             # 2. 记录删除旧路径
git add new-name.js            # 3. 记录新增新路径

# 所以你也可以先手工改名，再 add：
mv a.js b.js && git add -A
git status -s
#R  a.js -> b.js                # Git 自动识别为重命名

为什么敢这么做：因为 Git 按内容寻址。改名不改内容 → blob 哈希不变 → Git 一看"删了一个 blob，加了一个一模一样的 blob"，就推断出这是重命名。

7.5 重命名识别与 -M 参数

推断需要相似度阈值：改名同时又改了内容，Git 就不一定认得出来了。

# 提高/降低相似度阈值（默认 50%）
git diff -M40%          # 相似度 ≥40% 就算重命名
git log --follow -M30% -- new-name.js   # 跟踪改名前的历史

# 关闭重命名检测（把它当成"删+增"）
git diff --no-renames

# 查看某文件跨重命名的完整历史
git log --follow --oneline -- new-name.js
# 3c1a8f0 refactor: 重命名 old-name.js
# 9d8e7c6 feat: 实现核心逻辑     ← 改名前的历史也能看到
团队协作提示：如果你把"重命名"和"大量内容修改"放在同一个提交里，Git 与评审者都难以识别。规范做法：一次提交只改名，内容改动放下一个提交。

7.6 找回被删的文件

只要删除曾经提交过，文件就还在对象库里，随时能捞回来：

# 情况一：删了但还没提交 → 从仓库恢复
git restore 被删文件.txt

# 情况二：删除已提交 → 从"删除前那次提交"取回
git log --oneline --diff-filter=D -- 被删文件.txt   # 找到删除它的提交 X
git restore --source=X~1 -- 被删文件.txt            # X~1 = 删除前的版本

# 情况三：只记得文件名片段
git log --all --oneline --name-status | grep -i "关键字"

# 情况四：整个目录被删，批量恢复
git checkout 删除前提交 -- 目录/      # 老写法仍好用

Git 几乎不真正删除对象——"删除"只是"新提交里不再包含它"。因此已提交的删除几乎总能恢复，这也是"频繁提交"最重要的保险价值。

⚠ 常见坑清单

  • 坑 1：git rm --cached 后文件变未跟踪，下次 git add . 又被加回来 → 必须同步写 .gitignore；
  • 坑 2：以为删除能让历史里的密钥消失 → 不能，只能停止跟踪；敏感信息立即轮换；
  • 坑 3：改名 + 大改内容在同一提交 → 历史断裂、评审困难；拆成两次提交；
  • 坑 4：git mv 到已存在的目标路径会覆盖 → 用 git mv -f 前先确认目标内容不再需要；
  • 坑 5：git rm -r .（手滑）→ 立刻 git reset 取消全部暂存，再 git restore . 恢复文件。
