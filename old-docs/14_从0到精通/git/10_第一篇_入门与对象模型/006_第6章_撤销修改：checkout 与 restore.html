6.1 撤销决策表：先看改动在哪

所有"撤销"问题都可以归结为一个问题：你的改动现在停在哪个区。

你想撤销什么命令（Git 2.23+）改动还在吗安全等级
工作区的修改（未 add）git restore <file>❌ 丢失🔴 高危
暂存区的内容（已 add）git restore --staged <file>✅ 回到工作区🟢 安全
工作区 + 暂存区一起回退git restore --source=HEAD --staged --worktree <file>❌ 丢失🔴 高危
把文件还原到旧提交git restore --source=<commit> -- <file>❌ 覆盖当前🔴 高危
撤销"上一次提交"（保留改动）git reset --soft HEAD~1✅ 全保留🟡 见第 22 章
撤销"上一次提交"（丢弃改动）git reset --hard HEAD~1❌ 丢失🔴 高危

口诀：带 --staged 的撤销是安全的（只是把内容挪回工作区）；不带 --staged、只动工作区的撤销是危险的（内容直接蒸发）。

6.2 场景一：撤销工作区改动

# 初始化场景
echo "原始内容" > a.txt && git add a.txt && git commit -m "feat: 新增 a.txt"
echo "写错了的一段" >> a.txt

git status -s
#  M a.txt                  # 右列 M：工作区改动，未暂存

# 撤销：用暂存区（= 最新提交）的内容覆盖工作区
git restore a.txt

cat a.txt
# 原始内容                  # 刚才加的那行没了

# 老写法（等价，仍可用）
git checkout -- a.txt
不可恢复：被 restore 丢弃的工作区改动从未进入对象库，因此 reflog（第 23 章）也救不回来。动手前务必确认这段改动真的不要了。

如果只想"先放着等等看"，用 stash 而不是丢弃：

git stash push -m "临时存档：a.txt 的实验改动"   # 存起来（第 25 章详解）
git stash list                                  # 确认已存
# 需要时：git stash pop

6.3 场景二：撤销暂存（add 后悔了）

echo "新功能代码" >> a.txt
git add a.txt

git status -s
#M  a.txt                   # 左列 M：已进暂存区

# 撤销暂存：内容回到工作区，文件本身不变
git restore --staged a.txt

git status -s
#  M a.txt                  # 变回"未暂存"，代码还在！
cat a.txt                   # 新功能代码  ← 内容完好

# 老写法（等价）
git reset HEAD a.txt

这是最安全的撤销：它只改 index，不碰文件。想"全部取消暂存"用 git restore --staged . 或 git reset（不带参数即取消所有暂存）。

6.4 场景三：把文件恢复到历史某版本

常见需求："这个文件被我改坏了，想回到三天前那版"——注意只还原这一个文件，不动其他文件：

# 1. 先找到目标版本
git log --oneline -- a.txt
# 9f8e7d6 (3 天前) feat: 重构 a.txt 逻辑
# 1a2b3c4 feat: 新增 a.txt

# 2. 只把 a.txt 还原到那一版（工作区覆盖）
git restore --source=9f8e7d6 -- a.txt

# 3. 若同时要更新暂存区（直接就能提交）
git restore --source=9f8e7d6 --staged --worktree -- a.txt
git commit -m "revert: 将 a.txt 回退到 9f8e7d6 版本"

# 另一种"只读不改"的查看方式（安全）
git show 9f8e7d6:a.txt          # 打印那一版内容到终端
git show 9f8e7d6:a.txt > /tmp/old_a.txt   # 另存为文件慢慢比对

坑：不要用 git checkout 9f8e7d6 来"看旧版本"——那会把 HEAD 移到那次提交（进入分离 HEAD 状态），新手随后提交的代码会悬空，极难找回（第 22 章讲如何脱困）。

6.5 checkout 的三种人格与现代替代

git checkout 是 Git 里最"人格分裂"的命令——同一个名字干三件完全不同的事，这也是它在新版本被拆分的原因：

checkout 用法实际含义现代替代（推荐）
checkout <branch>切换分支git switch <branch>
checkout -b <new>新建并切换分支git switch -c <new>
checkout -- <file>丢弃工作区改动git restore <file>
checkout <commit> -- <file>用某版本覆盖文件git restore --source=<commit> -- <file>
checkout <commit>移动 HEAD（分离）git switch --detach <commit>
 
# 推荐：语义清晰、不易误伤
git switch main                # 切分支
git switch -c feature/x        # 新建并切
git restore src/app.py         # 丢弃该文件工作区改动
git restore --staged src/app.py

新命令的收益：switch 只管分支、restore 只管文件，名字即语义，误操作的概率大幅下降。

6.6 安全等级与"先存档再冒险"

面对任何"高危撤销"，养成三步习惯：

  1. 先看清楚要丢什么：git status -s + git diff --stat；
  2. 先存档：优先 git stash push -m "描述"（可恢复），其次临时 commit（git commit -m "wip"，随时 reset 回来）；
  3. 再执行撤销：确认无误后 git stash drop 或删掉临时 commit。
# 一套安全的"试错"流程
git stash push -m "尝试前存档"     # 1. 存档
git restore a.txt                  # 2. 撤销
# ... 验证效果 ...
git stash pop                      # 3. 发现撤错了？一键回来
git stash drop                     # 4. 确认不要了，清理存档
关于已提交的撤销：reset 三档（soft/mixed/hard）与 revert（生成反向提交）属于历史改写范畴，分别在第 22 章与第 21 章详解。本章只处理"未提交"的改动。

⚠ 常见坑清单

  • 坑 1：git restore . 把整个目录改动清空，半天白干 → 加 --staged 才是安全的；不确定就先 stash；
  • 坑 2：git checkout <commit> 后继续开发 → 分离 HEAD，提交悬空；发现后立刻 git switch -c 新分支 保住；
  • 坑 3：误以为 restore --staged 会删代码 → 它只取消暂存，代码仍在；
  • 坑 4：撤销后又想恢复 → 未进库的改动 Git 无法找回，只能靠编辑器本地历史或文件系统备份；
  • 坑 5：在合并冲突状态用 restore 乱覆盖 → 冲突标记被冲掉但问题仍在；应先正确解决冲突（第 13 章）。
