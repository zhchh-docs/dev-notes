  • 能画出三区流转图，并说出每个箭头对应的命令；
  • 看到一个文件，能判断它处于未跟踪/已修改/已暂存/已提交四种状态中的哪一种；

  • 会用 git add -p 做"一次改动拆成两个提交"。
核心心智：Git 的每一次"移动"都是在区域间搬内容，命令名不重要，方向才重要。

4.1 三个区域各是什么

图 4-1 三区模型：所有日常命令都是这四个箭头之一

区域物理位置特点
工作区项目目录（除 .git 外）你看到、编辑的文件；改动尚未被 Git 记录
暂存区.git/index（二进制索引）记录"下一次提交包含哪些内容"的清单
仓库.git/objects + refs提交后的历史对象，内容寻址、基本不可变

4.2 文件的四种状态

Git 视角下，一个文件永远处于四态之一（git status 就是在报这个）：

状态status 中的分组含义与下一步
未跟踪 UntrackedUntracked files新文件，Git 从未记录；git add 后进入暂存
已修改 ModifiedChanges not staged已跟踪文件被改动，但没 add；可 add 或 restore 丢弃
已暂存 StagedChanges to be committed已在 index 中；git commit 即入库
已提交 Committed（不显示）与仓库中最新版本一致，工作区"干净"
 
# 短格式查看（左列 = 暂存区状态，右列 = 工作区状态）
git status -s
#  M README.md     # 右列 M：工作区改了，未 add
# M  README.md     # 左列 M：已 add 到暂存区
# MM README.md     # 两列都 M：暂存后又改了一次
# ?? NEW.md        # 未跟踪
# A  added.md      # 新文件已暂存
# D  deleted.md    # 删除已暂存

记住 -s 的两列口诀：左列是"暂存区 vs 仓库"，右列是"工作区 vs 暂存区"。

4.3 场景演练：三区流转实操

同一个文件连续改两次，观察它如何"分裂"到暂存区与工作区：

echo "第一行" > demo.txt
git add demo.txt && git commit -m "feat: 新增 demo.txt"   # C1 入库：内容=第一行

echo "第二行" >> demo.txt
git add demo.txt          # 暂存：index 里现在是"第一行+第二行"

echo "第三行" >> demo.txt  # 工作区又改了，但没 add

git status -s
# MM demo.txt             # 暂存区比仓库多一行，工作区比暂存区又多一行

# 三种对比，一次看懂
git diff              # 工作区 vs 暂存区   → 显示"第三行"
git diff --staged     # 暂存区 vs 仓库(HEAD) → 显示"第二行"
git diff HEAD         # 工作区 vs 仓库(HEAD) → 显示"第二行+第三行"

git commit -m "feat: 追加两行"
git status -s
#  M demo.txt            # 注意：第三行没进提交！它还在工作区
这是新手最常踩的坑：以为 add 过一次，后面所有改动都会自动进提交。事实上提交的内容是"执行 commit 那一刻的暂存区"，之后的工作区改动不参与本次提交。

4.4 为什么要有暂存区

直接 commit -a 一步到位不是更省事吗？暂存区换来的是三样东西：

  1. 精确挑选：一个文件里改了三处——两处是功能、一处是调试日志，可以只把功能改动的 hunks 放进提交（4.6 的 add -p）；
  2. 分批提交：半天改了五个文件属于两个需求，用暂存区分两次提交，历史就变成两条清晰的记录而不是一坨"今天改了很多"；
  3. 提交前预览：git diff --staged 让你在写入历史之前最后检查一遍要提交什么，避免把密码、临时文件、调试代码写进历史。

暂存区不是"多余的一步"，它是把"我改了什么"翻译成"我要提交什么"的编辑器——历史质量由此而来。

4.5 区际移动命令速查

方向命令效果
工作区 → 暂存区git add <file> / git add -A把改动（含新文件）写入 index
暂存区 → 仓库git commit [-m "msg"]把 index 快照写入历史
暂存区 → 工作区git restore --staged <file>取消暂存（文件改动仍在）
仓库 → 工作区/暂存区git restore --source=HEAD --staged --worktree <file>用某提交的内容覆盖（丢弃改动）
仓库 → 暂存区git reset <commit> -- <file>把 index 中该文件回退到指定版本
 
# 取消暂存（最常用，安全的"反悔"）
git restore --staged README.md

# 丢弃工作区改动（危险：不可恢复）
git restore README.md

# 一步回到 HEAD 状态：暂存区与工作区都重置
git restore --source=HEAD --staged --worktree README.md
命名史：老教程里的 git checkout -- <file> 与 git reset HEAD <file> 已被 Git 2.23+ 的 restore 取代，语义更清晰。第 6 章完整对比。

4.6 部分暂存：git add -p

# 交互式挑选"代码块（hunk）"进入暂存区
git add -p src/app.py
# Git 展示每个改动块并等待指令：
# y  暂存这一块
# n  不暂存这一块
# s  把这一块再切小
# e  手工编辑要暂存的行
# q  退出
# a  暂存本文件剩余所有块

# 挑选完成后分别提交
git commit -m "feat: 实现登录校验"        # 只含功能改动
git add src/app.py && git commit -m "chore: 补充调试日志"  # 剩下的

结果是两条语义清晰的提交，而不是一条混杂的"改了登录相关的一堆东西"。评审者、未来的你、以及 git bisect 都会感谢你。

⚠ 常见坑清单

  • 坑 1：add 后又改，commit 少了最新改动 → 提交前 git status -s 确认没有 MM；
  • 坑 2：git restore <file> 丢了半天工作量 → 它不可撤销；拿不准就先 git stash（第 25 章）或提交一个临时 commit；
  • 坑 3：git add . 把不想提交的文件也加进去了 → 用 .gitignore（第 8 章）+ git restore --staged 撤回；
  • 坑 4：以为删除文件要单独命令 → 直接 rm 后 git add -A 也能记录删除，或用 git rm（第 7 章）；
  • 坑 5：暂存区内容忘了提交就切分支 → index 是仓库级的，切换分支可能冲突；先提交或 stash。
