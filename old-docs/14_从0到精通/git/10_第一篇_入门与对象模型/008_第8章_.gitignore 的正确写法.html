第 8 章 .gitignore 的正确写法

8.1 规则语法全解

写法含义
# 注释注释行；空行被忽略
*.log忽略任意目录下所有 .log 文件
/debug.log只忽略仓库根的 debug.log（子目录里的不忽略）
build/忽略任意层级名为 build 的目录（含其下所有内容）
/dist只忽略根目录的 dist（文件或目录）
doc/*.txt忽略 doc 目录下（不含更深层级）的 .txt
doc/**/*.pdf** 匹配任意层级目录
!important.log取反：不忽略该文件（前面被忽略时救回来）
[Tt]emp/字符类，匹配 Temp/ 与 temp/
?oo? 匹配单个字符（foo、aoo）
取反的重要限制：如果某个目录被整目录忽略（logs/），那么该目录下的任何 ! 取反规则都不会生效——Git 根本不会进这个目录去检查。要取反必须先"放行目录本身"：
logs/            # 忽略整个目录
!logs/           # ✘ 无效：目录已忽略，Git 不再进入
logs/            # ✔ 正确写法：
!logs/*.keep     #   仍无效
# 正确做法：忽略目录内容而非目录本身
logs/*
!logs/.gitkeep   # 这样 .gitkeep 才能被保留

8.2 三层忽略：仓库 / 全局 / 本地

层级位置用途
仓库级（共享）项目根的 .gitignore，也可是子目录里的 .gitignore团队共识：构建产物、依赖目录、日志
全局级（个人）core.excludesfile 指向的文件，如 ~/.gitignore_global个人环境垃圾：.DS_Store、Thumbs.db、IDE 配置
本地级（私有）.git/info/exclude只在本仓库生效、不进版本控制的临时忽略
 
# 配置全局忽略文件
git config --global core.excludesfile ~/.gitignore_global
echo ".DS_Store
Thumbs.db
.idea/
.vscode/
*.swp" > ~/.gitignore_global

# 本地私有忽略（不提交、不影响他人）
echo "my-local-scratch/" >> .git/info/exclude

分工原则：与项目有关的写仓库级（大家共享），与个人机器有关的写全局级（不要污染团队仓库）。

8.3 场景演练：给一个前端项目写忽略文件

# ---------- 依赖 ----------
node_modules/
.pnpm-store/
.yarn/cache/

# ---------- 构建产物 ----------
dist/
build/
out/
*.tsbuildinfo

# ---------- 环境变量（含密钥！）----------
.env
.env.local
.env.*.local

# ---------- 日志与临时文件 ----------
logs/
*.log
npm-debug.log*
.cache/
.temp/

# ---------- 编辑器与系统 ----------
.vscode/*
!.vscode/settings.json      # 团队共享的编辑器配置保留
!.vscode/extensions.json
.idea/
.DS_Store

# ---------- 测试与覆盖率 ----------
coverage/
.nyc_output/

# ---------- 保留空目录占位 ----------
uploads/*
!uploads/.gitkeep

要点解读：

  • .vscode/* 后再用 !settings.json 取反——因为这里忽略的是目录内容而不是目录本身，取反才有效；
  • uploads/* + !.gitkeep：让 Git 保留空目录（Git 不跟踪空目录，靠占位文件）；
  • 环境文件 .env 必须忽略——这是泄露密钥的头号通道。
偷懒的正确方式：github.com/github/gitignore 提供各语言/框架的标准模板；git init 时也可用第三方工具（如 gi node,vue）生成。生成后一定要自己审一遍，别盲目照抄。

8.4 疑难杂症：规则不生效的四个原因

  1. 文件已被跟踪（最常见）：.gitignore 只对未跟踪文件生效，已经入库的文件无视忽略规则。解法见 8.5。
  2. 目录被整体忽略：logs/ 内的一切都不再检查，! 取反失效。改成 logs/* 再取反。
  3. 规则写在了错误的位置：/dist 只匹配根目录；子目录里的规则用相对该子目录的路径。
  4. 被其他层级覆盖：仓库级规则 vs 全局 vs .git/info/exclude；另外后写的规则覆盖先写的（同文件内后者优先）。
# 快速自查：这个文件到底被谁忽略了？
git check-ignore -v dist/app.js
# .gitignore:3:dist/    dist/app.js     ← 第 3 行的 dist/ 规则命中

8.5 已跟踪文件如何改为忽略

三步走：停止跟踪 → 写规则 → 提交（与第 7 章衔接）。

# 1. 停止跟踪（保留硬盘文件）
git rm --cached --ignore-unmatch  dist/app.js      # 单个文件
git rm -r --cached --ignore-unmatch dist/          # 整个目录

# 2. 写忽略规则
echo "dist/" >> .gitignore

# 3. 提交这次"清理"
git add .gitignore
git commit -m "chore: 停止跟踪构建产物并加入忽略"

# 验证：以后改动 dist 不再出现在 status
git status -s        # 应看不到 dist 相关条目
对协作者的影响：你这次提交会删除别人本地（更新后）的对应文件——因为他们 pull 后，这些路径在仓库里已被标记为删除。务必提前在群里说明："我要清理构建产物，pull 后本地 dist 会被删，重新 build 即可"。

如果只想在自己机器上"暂时看不见改动"、又不想影响他人，用 --skip-worktree（高级，谨慎）：

git update-index --skip-worktree config.local.js   # Git 假装没看见它的改动
git update-index --no-skip-worktree config.local.js # 恢复

8.6 调试工具：check-ignore 与 status --ignored

# 列出所有被忽略的文件（排查"是不是忽略过头了"）
git status --ignored
git status --ignored -s        # 短格式：!! 开头即被忽略

# 查某文件被哪条规则忽略（-v 显示来源文件与行号）
git check-ignore -v node_modules/react/index.js
# .gitignore:2:node_modules/    node_modules/react/index.js

# 批量检查
git check-ignore -v a.log b.log c.txt

# 列出被忽略目录中"仍会被提交"的文件（验证取反是否生效）
git ls-files --cached --others --exclude-standard

⚠ 常见坑清单

  • 坑 1：忽略规则写了但文件仍出现在 status → 文件已被跟踪，先 git rm --cached；
  • 坑 2：!keep.txt 取反无效 → 父目录被整目录忽略了，改成忽略目录内容；
  • 坑 3：把 .env.example 也一起忽略了 → 用 .env* + !.env.example 精准取反；
  • 坑 4：全局忽略写了项目相关内容 → 队友机器上不生效，导致规则"时灵时不灵"；
  • 坑 5：忽略 *.log 导致需要的日志样本丢失 → 需要保留的样例用 !sample.log。

✓ 本章小结与习题

要点一句话
语法要点前缀 /=根目录、后缀 /=目录、!=取反、**=任意层级
三层来源仓库 .gitignore（共享）/ 全局（个人）/ .git/info/exclude（私有）
只对未跟踪生效已跟踪文件需 git rm --cached 再忽略
取反限制整目录被忽略时，目录内的 ! 无效
调试git check-ignore -v 文件 直接指出命中的规则与行号
A 基础为自己常用技术栈写一份 .gitignore，要求包含：依赖目录、构建产物、环境变量、日志、编辑器配置（含一条取反）。
B 进阶制造"已跟踪文件加忽略不生效"的场景，用 git rm --cached 修复，并用 git check-ignore -v 验证规则命中。
C 挑战设计一套团队忽略规范：哪些必须进仓库级 .gitignore、哪些属于个人全局、哪些用 .git/info/exclude，并说明"清理构建产物"这类提交应如何在团队内同步。
