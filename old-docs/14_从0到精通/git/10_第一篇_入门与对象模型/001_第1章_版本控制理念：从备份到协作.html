1.1 没有 VCS 的世界：你一定干过这些事

回想（或想象）这样的项目文件夹：

my-project/
  简历_最终版.doc
  简历_最终版2.doc
  简历_真最终版_改.doc
  简历_打死不改版_张三改过.doc
  src-备份0417/
  src-备份0418-能用/
  src-千万别删/
  src-最新(其实是旧的)/

这套"文件名版本学"有四个致命缺陷：

缺陷表现后果
历史不可信不知道每个副本改了什么、谁改的、为什么改想回退却不知道回到哪一版
并行困难两个人不能同时改同一个文件夹靠 U 盘 / 网盘来回倒，覆盖别人的改动
全量冗余每存一版复制整个目录磁盘爆炸，大项目每版几个 GB
合并靠手两人各改一份，只能肉眼逐行比对漏掉一处就是线上事故

版本控制系统的存在意义，就是把"历史、并行、恢复、合并"这四件事从人的记忆力转移到机器里。

1.2 VCS 管什么：三大职责

  1. 历史（History）：每次改动形成一个"提交"，记录谁、何时、改了什么、为什么改。历史可以浏览、对比、检索。
  2. 并行（Branching）：每人、每个功能、每次实验各开一条独立工作线，互不干扰，完成后合回主线。
  3. 恢复（Recovery）：任何时刻都能精确回退到任意历史状态——不是"恢复到昨天凌晨 3 点的备份"，而是"恢复到第 42 次提交"。

图 1-1 提交链：历史中的每一站都完好保存，任何一站都能随时抵达

1.3 集中式与分布式：一条线上的两种哲学

版本控制系统有三代：本地式（RCS）、集中式（CVS / SVN）、分布式（Git / Mercurial）。关键差别在"仓库在哪"：

维度集中式（SVN）分布式（Git）
仓库位置只有中央服务器一份完整历史每个人本地都有完整历史，服务器只是"同步 hub"
提交方式必须联网，直接提交到中央先在本地提交，联网后再推送同步
断网工作只能改文件，不能提交、不能看历史提交、看历史、开分支、对比全部可用
分支成本分支昂贵，团队少用分支几乎零成本，"随手开分支"是常态
单点风险中央服务器坏了 = 历史可能丢失任何一台有 clone 的机器都是完整备份

核心区别：Git 里"提交"和"发布"是两件事——本地 commit 只影响你自己的仓库，push 才分享给别人。这个解耦让开发者敢频繁提交，历史因此更细、更有价值。

1.4 Git 的四个设计决定

2005 年，Linux 内核社区与 BitKeeper 授权谈判破裂，Linus Torvalds 花约十天写出 Git。它有四个影响深远的设计决定——现在只需混个脸熟，第一篇后几章会逐一展开：

  1. 快照，不是差异：每次提交记录项目整体的"快照"（借助对象去重，未变文件不重复存储），而不是"第 N 版相对第 N-1 版的补丁"。这让回退、对比、分支合并的模型简单一致。
  2. 内容寻址：每个对象用其内容的 SHA-1 哈希命名。内容变了，名字必变——等于给每个版本盖了防伪章，任何篡改都会被发现。
  3. 绝大多数操作只碰本地：commit、branch、diff、log 不走网络，所以快得像本地文件操作。这是 Git 手感好的根本原因。
  4. 三个区域：工作区、暂存区、仓库。改动不是"一杆子进历史"，而是分步挑选、确认、入库——第 4 章专题。
常见误解："Git = GitHub"。Git 是版本控制工具，装在你电脑上、离线可用；GitHub/GitLab/Gitee 是托管 Git 仓库的网站。第 9 章会正式区分。

1.5 Git 在团队协作里的位置

现代软件交付流水线上，Git 处于最上游，几乎所有环节都挂在它的动作上：

  • 提交（commit）触发代码检查与测试——CI 集成（第 35 章）；
  • 分支（branch）定义并行工作与发布节奏——分支模型（第 31-32 章）；
  • 合并（merge / PR）是代码评审的物理载体（第 19-20 章）；
  • 标签（tag）标记可发布版本，驱动发版流程（第 17、33 章）；
  • 历史（log）自动生成变更日志、支持事故定位（第 34、26 章）。

学 Git 不是学一条命令集，而是学一套团队协作的通用协议——写代码之外的半个工程师职责都在这里。

✓ 本章小结

要点一句话
VCS 三大职责历史可查、并行可分支、任意时刻可恢复
手工管版本的死穴历史不可信、无法并行、全量冗余、合并靠肉眼
分布式 vs 集中式每人一份完整历史；提交在本地，推送才共享
四个设计决定快照存储 / 内容寻址 / 本地优先 / 三区模型
Git ≠ GitHubGit 是工具，GitHub 是托管平台
