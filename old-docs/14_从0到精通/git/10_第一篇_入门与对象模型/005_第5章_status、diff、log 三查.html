第 5 章 status/diff/log 三查

演练数据：为便于练习，先造一个 5 次提交的小仓库（脚本见 5.3）。

5.1 git status：我在哪

git status                 # 完整输出（含提示语，适合新手）
git status -s              # 短格式（老手默认）
git status -sb             # 短格式 + 当前分支名与追踪信息
git status -uall           # 展开未跟踪目录里的具体文件（默认只显示目录）
git status --ignored       # 同时列出被 .gitignore 忽略的文件

# 只看某目录/文件
git status -- src/

-sb 的输出第一行形如 ## main...origin/main [ahead 2]——一眼看出：当前分支 main、追踪 origin/main、本地领先 2 个提交。这是判断"该不该 push"最快的信号。

-s 状态码含义
??未跟踪（新文件）
A 新增并已暂存
M（右列）工作区已改，未暂存
M （左列）已暂存待提交
MM暂存后工作区又改了
D / R删除 / 重命名（Git 靠内容相似度识别重命名）
UU冲突未解决（第二篇详解）

5.2 git diff：改了什么

diff 的本质是"两个版本之间的补丁"。基准不同，结果完全不同：

命令对比基准
git diff工作区 vs 暂存区（默认）
git diff --staged（同 --cached）暂存区 vs HEAD
git diff HEAD工作区 vs HEAD（前两者之和）
git diff <c1> <c2>两次提交之间
git diff branchA..branchB两分支尖端之间（... 三点语法为共同祖先起）
 
# 限定文件/目录
git diff -- src/app.py
git diff HEAD~1 -- src/

# 只看改动统计（适合大改动先总览）
git diff --stat
git diff HEAD~3 --stat

# 忽略纯空白改动（CRLF/缩进大战时救命）
git diff -w

# 词级高亮：看清一行内改了哪几个词
git diff --word-diff

# 生成补丁文件（可邮件发给同事 / 存档）
git diff HEAD~1 > fix.patch
git apply fix.patch        # 在别处应用

# 重命名识别与相似度阈值
git diff -M --find-renames=40%

坑：git diff 什么都不显示，不代表没改动——很可能改动已经 add 进暂存区了。此时要看 git diff --staged。

5.3 git log：从哪来

# 造练习数据（可跳过）
mkdir -p ~/git-lab/ch05 && cd ~/git-lab/ch05 && git init
for i in 1 2 3; do echo "v$i" >> app.txt; git add .; git commit -m "feat: 第 $i 次改动"; done
git checkout -b feature-login
echo "login" >> app.txt; git add .; git commit -m "feat: 登录功能"
git checkout main
echo "hotfix" >> app.txt; git add .; git commit -m "fix: 紧急修复"
git merge feature-login -m "merge: 合并登录功能"

基础三件套：--oneline（一行一条）+ --graph（画分支线）+ --decorate（显示分支/标签指向）：

git log --oneline --graph --decorate --all
# *   7a3f1c2 (HEAD -> main) merge: 合并登录功能
# |\
# | * 5b2e9d1 (feature-login) feat: 登录功能
# * | 3c1a8f0 fix: 紧急修复
# |/
# * 9d8e7c6 feat: 第 3 次改动
# * 4a5b6c7 feat: 第 2 次改动
# * 1f2e3d4 feat: 第 1 次改动
常用参数用途
-n / -3只看最近 n 条
-p展开每次提交的完整补丁
--stat / --shortstat改动统计
--name-only / --name-status只列文件名（含 A/M/D 状态）
--author="Zhang"按作者过滤
--since="2 weeks ago"按时间过滤（支持 --until）
--grep="登录"按提交信息关键字过滤
-S"函数名"按内容变化检索（pickaxe，见 5.5）
--follow 文件跟踪文件改名前的历史
--first-parent只看主线（跳过合并进来的分支细节）
 
# 查看某次提交本身（等价于 git show）
git show 5b2e9d1
git show HEAD --stat          # 最近一次提交改了哪些文件
git show HEAD:src/app.py      # 查看某提交里某文件的内容（不检出！）

5.4 场景演练：调查一次"不明改动"

需求：线上发现 app.txt 里多了一行怪内容，要查谁、哪次提交、为什么。

# 1. 先总览该文件最近改动
git log --oneline -5 -- app.txt
# 5b2e9d1 feat: 登录功能
# 9d8e7c6 feat: 第 3 次改动

# 2. 看具体改了什么
git log -p -1 5b2e9d1 -- app.txt
# +login

# 3. 逐行溯源：每一行最后是谁改的
git blame app.txt
# 5b2e9d1 (Zhang San 2026-06-10 14:22:03 +0800 4) login
#   ^提交号  ^作者      ^时间                    ^行号 ^内容

# 4. 只要某几行
git blame -L 4,6 app.txt

git blame 常被误解为"甩锅工具"，实际用途是：找到改动对应的提交号，再用 git show 看当时的完整上下文与提交信息——那里通常写着"为什么这么改"。

5.5 检索历史：按内容、按作者、按时间

# pickaxe：找出"某字符串被加入或删除"的提交
git log -S"maxRetry" --oneline
git log -S"maxRetry" --oneline -- src/      # 限定目录
git log -G"regex.*pattern" --oneline         # -G 支持正则

# 组合查询：张三在最近两周里改过登录相关代码
git log --author="Zhang" --since="2 weeks ago" --grep="登录" --oneline

# 只看某个作者的代码量统计（团队周报常用）
git shortlog -sn --since="1 month ago"
#    42  Zhang San
#    17  Li Si

# 查"某提交之后到现在"的范围
git log feature..main --oneline      # 在 main 但不在 feature 的提交
git log main..feature --oneline      # 在 feature 但不在 main 的（即将合并的）

A..B 读作"在 B 里且不在 A 里"，是分支对比、发布前检查的万能语法（第 18、33 章反复用到）。

5.6 值得抄走的别名组合

git config --global alias.st "status -sb"
git config --global alias.df "diff"
git config --global alias.dfs "diff --staged"
git config --global alias.dfst "diff --stat"
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.last "log -1 --stat"
git config --global alias.who "shortlog -sn --since=1 month ago"

# 自定义格式：一行里放 短哈希 | 相对时间 | 作者 | 标题
git config --global alias.lp "log --color --graph --pretty=format:'%Cred%h%Creset -%C(yellow)%d%Creset %s %Cgreen(%cr) %C(bold blue)<%an>%Creset' --abbrev-commit"
pretty format 占位符速记：%h 短哈希、%H 全哈希、%an 作者名、%ar/%ad 相对/绝对时间、%s 标题、%d 引用装饰（分支/标签）。

⚠ 常见坑清单

  • 坑 1：git diff 空输出 → 改动已进暂存区，改用 git diff --staged；
  • 坑 2：git log 看不到刚提交的分支 → 加 --all，或检查是否在其他分支；
  • 坑 3：git log 文件 只显示"到 HEAD 为止"的历史，改名前的记录要用 --follow；
  • 坑 4：合并提交挤爆 log → 用 --first-parent 看主线，或 --no-merges 过滤掉合并节点；
  • 坑 5：blame 看到的全是"格式化整个文件"的人 → 先 git log -w（忽略空白）或用 -C 检测跨文件搬运。

✓ 本章小结与习题

要点一句话
status-sb 看分支与 ahead/behind；-uall 展开未跟踪
diff 三基准默认工作区vs暂存区；--staged 暂存区vsHEAD；diff HEAD 全量
log 三件套--oneline --graph --decorate（建议别名 lg）
溯源三板斧log -p -- 文件 看改动 → blame 定位行 → show 看上下文
范围语法A..B = 在 B 不在 A；发布前必查
A 基础配置 git lg 别名，在练习仓库里观察分支分叉与合并的图形输出，指出哪条线是 feature 分支。
B 进阶在任意仓库用 git log -S"某个函数名" --oneline 找出该函数被引入和被删除的两次提交，并说明改动背景。
C 挑战用 git log main..origin/main 与 git log origin/main..main 分别判断"我落后多少 / 领先多少"，并说明为什么两者都要看。
