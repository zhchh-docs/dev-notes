第 14 章 rebase：换基的艺术

rebase 是 Git 里最强大也最容易用错的工具：它能让历史变成一条直线，也能让同事的工作一夜蒸发。本章讲清 rebase 的机制、与 merge 的取舍、pull --rebase 的坑，以及那条必须刻进肌肉的黄金法则。

◆本章目标

  • 能用一句话解释 rebase：把一串提交"重新播放"到新的基底上；
  • 独立完成 git rebase main 并处理其中的冲突；
  • 判断何时用 merge、何时用 rebase（团队规范的核心决策之一）；
  • 牢记黄金法则并理解违反它的后果。
先记结论：rebase 会改写提交哈希（因为提交的父变了、内容时间戳变了）。任何已经推送且别人可能基于它工作的提交，都不要 rebase。

14.1 rebase 做了什么

git rebase main（在 feature 分支上执行）的内部步骤：

  1. 找到 feature 与 main 的共同祖先；
  2. 把 feature 上"从共同祖先之后"的所有提交临时存为补丁；
  3. 把 feature 指针重置到 main 的尖端（相当于 reset --hard main）；
  4. 把刚才的补丁逐个重新应用，生成一批新的提交（内容相同、哈希不同）。

14.2 场景演练：把功能分支搬到新基底

cd ~/git-lab && rm -rf ch14 && mkdir ch14 && cd ch14 && git init
echo "base" > app.js && git add . && git commit -m "feat: 初始化"

# ① 功能分支开发两个提交
git switch -c feature/pay
echo "pay-1" >> app.js && git commit -am "feat(pay): 支付第一步"
echo "pay-2" >> app.js && git commit -am "feat(pay): 支付第二步"

# ② 主线被别人推进
git switch main
echo "hotfix" >> app.js && git commit -am "fix: 紧急修复"

# ③ 功能分支 rebase 到最新主线
git switch feature/pay
git rebase main
# Successfully rebased and updated refs/heads/feature/pay.

git log --oneline --graph --all
# * 8a1b2c3 (HEAD -> feature/pay) feat(pay): 支付第二步
# * 7f6e5d4 feat(pay): 支付第一步
# * 3c1a8f0 (main) fix: 紧急修复
# * 9d8e7c6 feat: 初始化        ← 一条直线！

# ④ 此时合回主线就是 fast-forward（无合并提交）
git switch main && git merge feature/pay
# Fast-forward

rebase 的收益：功能分支的历史像"它就是在最新主线上开发的"，主线永远一条直线，git log --first-parent 极其干净，bisect 也不会被合并提交干扰。

14.3 rebase 中的冲突处理

rebase 是逐个提交重放，所以同一个文件可能冲突多次（每个提交一次）——这是它比 merge 麻烦的地方（merge 只解决一次）。

git rebase main
# CONFLICT (content): Merge conflict in app.js
# error: could not apply 7f6e5d4... feat(pay): 支付第一步

git status
# interactive rebase in progress; onto 3c1a8f0
# Unmerged paths: both modified: app.js

# 1. 解决冲突（编辑文件 → 删除标记 → 写出正确内容）
# 2. 标记解决
git add app.js
# 3. 继续重放下一个提交（不是 commit！）
git rebase --continue

# 想跳过这个提交（放弃它带来的改动）
git rebase --skip

# 彻底放弃整个 rebase
git rebase --abort
关键差别：rebase 冲突解决后用 git rebase --continue，不是 git commit。另外 rebase 时 HEAD/ours 指的是新基底（main），theirs 是你正在重放的提交——与 merge 相反（第 13 章强调过）。
# 减少重复劳动：开启 rerere（记住你解决过的冲突，下次自动复用）
git config --global rerere.enabled true

14.4 merge 还是 rebase：决策表

维度mergerebase
历史形状保留分叉与合并节点（真实记录发生过什么）一条直线（更像"顺序发生"）
提交哈希不变（安全）改变（危险，若已推送）
冲突次数一次性解决逐提交解决（可能多次）
可追溯性能看出"这个功能是一批提交"丢失分支边界（可用 --no-ff 补回）
适用公共分支合并、需要审计的场景个人/未推送分支整理、同步主线

团队常用组合拳：本地用 rebase 同步主线（保持干净），合入主干时用 merge --no-ff（保留功能边界与合并记录）。

14.5 黄金法则：不要 rebase 已推送的公共分支

黄金法则：只对尚未推送、或确认无人基于其工作的本地提交使用 rebase。 一旦提交已经推送到共享仓库，rebase 后你就必须强推，而强推会覆盖远程历史，导致：
  • 队友的本地历史与远程分叉，拉取时产生大量"幽灵冲突"；
  • 队友基于旧提交做的工作可能被静默丢弃；
  • CI、发布标签、PR 关联全部错乱。
# 万一必须强推（仅限个人分支，且已通知相关人）
git push --force-with-lease origin feature/pay
# --force-with-lease 比 --force 安全：若远程已有你没见过的新提交，它会拒绝推送

# 队友在"你强推之后"如何恢复（假设他本地还是旧的 feature/pay）
git fetch origin
git switch feature/pay
git reset --hard origin/feature/pay    # ⚠ 会丢弃本地未推送改动，确认后执行

14.6 pull --rebase 与配置

git pull 默认是 fetch + merge，会产生一条 "Merge branch 'main'" 的合并提交——每天同步几次，历史里就全是这种噪音。改用 rebase：

git pull --rebase            # fetch + rebase（把本地提交接到远程尖端之后）

# 全局默认（推荐个人开发）
git config --global pull.rebase true
# 或只对新建分支自动生效（老仓库的分支不动）
git config --global pull.rebase merges

# 自动 stash 未提交改动后再 rebase（避免"有改动不能 rebase"）
git pull --rebase --autostash
git config --global rebase.autoStash true
团队建议：pull.rebase=true 适合"个人分支 + 频繁同步"的开发者；共享长期分支（main/release）仍用 merge，避免改写已发布历史。第 37 章会把这条写进团队规范模板。

⚠ 常见坑清单

  • 坑 1：rebase 了已推送的公共分支 → 队友历史错乱；只 rebase 本地/个人分支；
  • 坑 2：冲突后用了 git commit 而非 --continue → rebase 卡住；用 git rebase --abort 重来；
  • 坑 3：rebase 时 ours/theirs 判断反 → 以文件内容为准，开 diff3；
  • 坑 4：rebase 后忘了强推，本地与远程分叉 → 确认分支归属后再 --force-with-lease；
  • 坑 5：rebase 丢失了合并提交 → 默认 rebase 会丢弃合并提交，需要保留用 --rebase-merges。

✓ 本章小结与习题

要点一句话
rebase 机制存补丁 → 重置到新基底 → 逐个重放，生成新哈希
冲突处理解决 → add → rebase --continue（不是 commit）
取舍本地整理用 rebase；公共合入用 merge（可 --no-ff）
黄金法则已推送且他人可能基于其工作的提交，绝不 rebase
pull --rebase避免无意义的 merge 噪音，配 autoStash 更顺手
A 基础按 14.2 脚本演练一次 rebase，对比 rebase 前后 git log --graph 的形状，并验证合回主线是 fast-forward。
B 进阶制造一个"每个提交都会冲突"的场景（连续两次改同一行），练习多次 --continue，并开启 rerere 体会它复用解决方案的效果。
C 挑战模拟"误 rebase 已推送分支"：在两台目录间还原事故，练习用 --force-with-lease 与队友侧 reset --hard origin/xxx 恢复，并写出事故复盘的三个改进项。
