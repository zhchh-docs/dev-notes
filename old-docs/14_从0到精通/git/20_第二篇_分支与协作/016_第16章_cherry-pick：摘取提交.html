第 16 章 cherry-pick：摘取提交

教科书 第 16 章 / 共 40 章 · 预计 35 分钟 · 实用技巧章

"只要那一个修复，不要把整条分支合进来"——这就是 cherry-pick 的用武之地：把某个提交单独复制到当前分支。本章讲清它的机制、四个典型场景、连续区间的用法，以及为什么滥用它会埋下隐患。

◆本章目标

  • 理解 cherry-pick 是"复制提交"而非"移动提交"（原提交仍在原地）；
  • 能把某个修复单独搬到发布分支/主干；
  • 掌握连续区间 A..B 的摘取与 -n、-x 参数；
  • 知道 cherry-pick 的三大隐患，以及何时该改用 merge/rebase。

16.1 cherry-pick 做了什么

git switch release/1.4
git cherry-pick 3f2e1d0
# [release/1.4 8a7b6c5] fix(order): 修复金额四舍五入
#  Date: Mon Jun 10 14:22:03 2026 +0800
#  1 file changed, 3 insertions(+)

机制：Git 取出该提交相对其父提交的改动（补丁），应用到当前分支，生成一个新提交：

  • 内容改动相同，但提交哈希不同（父提交、提交时间不同）；
  • 原分支上的那个提交依然存在，不受影响；
  • 新提交默认沿用原作者与原提交信息（提交者 committer 是你）。

图 16-1 cherry-pick 是复制而非移动：两条分支各有一个内容相同、哈希不同的提交

16.2 场景演练：热修复搬到发布分支

cd ~/git-lab && rm -rf ch16 && mkdir ch16 && cd ch16 && git init
echo "v1" > app.js && git add . && git commit -m "feat: 初始化"

# ① 从 v1.0 切出发布分支
git tag v1.0
git switch -c release/1.0

# ② 主干继续开发（含一个必须回移植的紧急修复）
git switch main
echo "feature-a" >> app.js && git commit -am "feat: 新功能 A"
echo "SECURITY-FIX" >> app.js && git commit -am "fix(sec): 修复越权漏洞"
FIX=$(git rev-parse --short HEAD)      # 记下这个修复的哈希

# ③ 把修复搬到发布分支
git switch release/1.0
git cherry-pick $FIX
# [release/1.0 9a8b7c6] fix(sec): 修复越权漏洞

git log --oneline -3
# 9a8b7c6 fix(sec): 修复越权漏洞      ← 复制品
# 1f2e3d4 feat: 初始化

# ④ 打补丁版本标签（第 17 章）
git tag v1.0.1

典型场景：把主干上的修复回移植（backport）到已冻结的发布分支，而不把主干的新功能一起带过去。

16.3 连续区间与多个提交

# 摘取多个不连续的提交（按顺序应用）
git cherry-pick 3f2e1d0 5b2e9d1 7a8b6c5

# 摘取一个区间（左开右闭：不含 A，含 B）
git cherry-pick A..B
# 等价：git cherry-pick A^..B（含 A 本身）

# 例：把 feature 分支上最近的 3 个提交搬到当前分支
git cherry-pick feature~3..feature

# 只把改动放进工作区/暂存区，不自动提交（便于合并成一条）
git cherry-pick -n A B C
git commit -m "fix: 合并搬来的三个修复"
语法含义
A..B(A, B] —— 不含 A，含 B
A^..B[A, B] —— 含 A 与 B
branch~3..branch该分支最近 3 个提交
--abort / --continue / --quit中止 / 继续 / 退出但保留已完成部分

16.4 常用参数：-n / -x / -e / --allow-empty

参数作用何时用
-n / --no-commit只应用改动，不生成提交想把多个摘取合成一条提交
-x在提交信息里追加 (cherry picked from commit ...)强烈推荐：留下溯源线索
-e / --edit应用前编辑提交信息需要改写以适应目标分支语境
--allow-empty允许产生空提交改动已在目标分支上，需要占位记录
-s / --signoff追加 Signed-off-by 行开源贡献规范（DCO）
--strategy-option theirs冲突时采用被摘取方的改动明确要以原提交为准时
 
git cherry-pick -x 3f2e1d0
git log -1
# fix(sec): 修复越权漏洞
# (cherry picked from commit 3f2e1d0a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e)

16.5 冲突处理与中止

git cherry-pick 3f2e1d0
# error: could not apply 3f2e1d0... fix(sec): 修复越权漏洞
# hint: after resolving the conflicts, mark the corrected paths
# hint: with 'git add <paths>' and run 'git cherry-pick --continue'

git status          # 查看冲突文件
# ...编辑解决冲突...
git add 冲突文件
git cherry-pick --continue      # 继续（会打开编辑器确认信息）

# 放弃这一个，继续序列中的下一个
git cherry-pick --skip

# 全部放弃，回到 cherry-pick 之前
git cherry-pick --abort

冲突的原因：被摘取的改动依赖的上下文在目标分支上不同（函数已被重构、文件被重命名）。冲突越多，说明两个分支差异越大——这本身是"该分支不宜长期分叉"的信号。

16.6 滥用的代价与替代方案

cherry-pick 的三大隐患：
  1. 历史重复：同一个修复在两个分支各有一份（哈希不同），日后 merge 时可能出现"重复应用"的困惑；
  2. 关联断裂：看不出"这个修复原本属于哪条分支"（除非用了 -x）；
  3. 依赖丢失：摘取 C3 但没摘它依赖的 C2 → 代码能提交但跑不起来。
需求不推荐推荐
把整个功能合入主干逐个 cherry-pick 它的 10 个提交merge / rebase
发布分支要一个热修复从主干 cherry-pick（可接受）更好：先修发布分支，再合并回主干（第 31 章分支模型）
把一堆提交搬到另一分支多次 cherry-pickrebase --onto（精准搬家，见下方）
 
# rebase --onto：把 feature 上从 base 之后的一段提交，搬到新基底上
git rebase --onto 新基底 旧基底 要搬的分支
# 例：把 feature 从 main 分出后的提交，搬到 release/2.0 上
git rebase --onto release/2.0 main feature
# 结果：feature 的独有提交整体"搬家"，且不会产生重复副本

⚠ 常见坑清单

  • 坑 1：以为 cherry-pick 会"移动"提交 → 原提交仍在原分支，可能重复；
  • 坑 2：摘了提交但漏了它依赖的前置提交 → 代码不完整；用 git show 检查改动范围；
  • 坑 3：区间写成 A..B 却发现 A 没被包含 → 用 A^..B；
  • 坑 4：cherry-pick 一个合并提交 → Git 不知以哪个父为基准，需 -m 1 指定主线父；
  • 坑 5：摘取后没跑测试 → 上下文不同，语法通过但逻辑失败。

✓ 本章小结与习题

要点一句话
本质复制某提交的改动到当前分支，生成新哈希
典型场景热修复回移植到发布分支
区间语法A..B=不含 A；A^..B=含 A
推荐参数-x 留溯源；-n 合并成一条
三大隐患历史重复、关联断裂、依赖丢失
A 基础按 16.2 脚本演练一次 cherry-pick，用 git log --graph --all 观察"两份内容相同、哈希不同"的提交。
B 进阶用 cherry-pick -n 摘取三个提交并合成一条提交，再用 -x 单独摘一次，对比两者提交信息的差别。
C 挑战构造"摘取后代码能编译但功能缺失"的场景（摘了 C3 漏了 C2），说明如何用 git show 与测试发现这类问题，并给出团队层面的防范措施。
