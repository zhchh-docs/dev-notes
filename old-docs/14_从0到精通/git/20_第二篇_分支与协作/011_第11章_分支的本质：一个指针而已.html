第 11 章 分支的本质：一个指针而已

教科书 第 11 章 / 共 40 章 · 预计 40 分钟 · 概念核心章

"开分支"在很多人的想象里是"复制一份代码"——所以他们不敢频繁开分支。真相是：Git 的分支只是一个 40 字节的指针文件。理解这一点，你就理解了 Git 为什么快、为什么轻量，也理解了切换分支时到底发生了什么。

◆本章目标

  • 能用 cat .git/refs/heads/... 亲眼看到"分支 = 一个哈希值文件"；
  • 理解 HEAD 是指向分支的指针（两级间接），以及分离 HEAD 的成因；
  • 知道切换分支时 Git 做的三件事，以及"有未提交改动时不能切换"的原因；
  • 能手工创建一个分支（不借助 git branch），从底层理解分支成本。

11.1 分支的物理形态

# 分支列表与当前分支
git branch
# * main
#   feature-login

# 分支在磁盘上是什么？
ls .git/refs/heads/
# feature-login  main

cat .git/refs/heads/main
# 3f2e1d0a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e   ← 就一行，一个提交哈希

# 用底层命令把任意哈希变成一个分支名
git branch demo-branch 3f2e1d0     # 不需要任何复制操作

图 11-1 分支是指针，不是容器：C1~C3 这些提交对象才是真正的内容

创建分支的代价 = 在 .git/refs/heads/ 里写一个 40 字符的文件。这就是为什么 Git 团队敢说"早分支、常分支"。

11.2 HEAD：当前分支的游标

cat .git/HEAD
# ref: refs/heads/main        ← 正常状态：HEAD 指向一个分支

# 在 main 上提交一次
git commit -m "feat: 新改动"
cat .git/refs/heads/main      # 变成新提交哈希（分支自动前进）
cat .git/refs/heads/feature   # 不变（其他分支不动）

于是有清晰的两级间接：HEAD → 分支名 → 提交。这带来一个重要性质：

  • 提交时前进的是HEAD 指向的那个分支，其他分支原地不动；
  • 切换分支只是把 HEAD 指向另一个分支名，再把工作区文件换成该提交的内容。
# 常用：查看 HEAD 的最终指向（解析两级）
git rev-parse HEAD            # 当前提交的完整哈希
git rev-parse --abbrev-ref HEAD  # 当前分支名（分离 HEAD 时输出 HEAD）
git symbolic-ref HEAD         # refs/heads/main（分离时会报错）

11.3 场景演练：手工造一个分支

不用 git branch，直接写文件——验证"分支就是指针"：

cd ~/git-lab/ch11
git log --oneline
# 3f2e1d0 (HEAD -> main) feat: 第三次改动

# 方式一：用底层命令 update-ref
git update-ref refs/heads/handmade 3f2e1d0
git branch
#   handmade
# * main

# 方式二：直接写文件（教学演示，实际别这么干）
echo 3f2e1d0a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e > .git/refs/heads/handmade2
git branch --list 'handmade*'
#   handmade
#   handmade2

# 验证：切过去，工作区内容一致
git switch handmade
git log --oneline -1          # 3f2e1d0 ... 与 main 相同
命令对比：git branch <name>（在当前提交建分支）、git branch <name> <起点>（在指定提交建分支）、git switch -c <name>（建并切换）、git switch -c <name> <起点>。后两者最常用。

11.4 切换分支时到底发生了什么

git switch feature 做了三件事：

  1. 移动 HEAD：把 .git/HEAD 内容改成 ref: refs/heads/feature；
  2. 更新暂存区（index）：把 index 替换为 feature 尖端提交的树；
  3. 更新工作区：把工作区文件替换成该提交的内容——删除只存在于旧分支的文件、创建只存在于新分支的文件、覆盖两边都有但内容不同的文件。

第 3 步解释了那个经典报错：

git switch feature
# error: Your local changes to the following files would be overwritten by checkout:
#         src/app.py
# Please commit your changes or stash them before you switch branches.

Git 拒绝切换，是因为切换会覆盖你未提交的改动，而这些改动还没进对象库、丢了找不回。三种合法选择：

# A. 提交（最稳妥，改动进入历史）
git add -A && git commit -m "wip: 临时存档"

# B. 暂存（stash，第 25 章）
git stash push -m "切分支前存档"
git switch feature
# ...干完活回来...
git switch main && git stash pop

# C. 带走改动一起切（Git 会尝试合并，可能冲突）
git switch feature            # 若两边改动不冲突，Git 允许带着改动切

未被任何分支引用的"未跟踪文件"不会被切换影响——它们不属于任何提交，Git 切换时不动它们。所以新建的文件可以"跟着你"跨分支存在（这有时会造成困惑）。

11.5 分离 HEAD（detached HEAD）

当 HEAD 直接指向某个提交而不是分支名时，就叫分离 HEAD：

git switch --detach 3f2e1d0
# 或老写法：git checkout 3f2e1d0
cat .git/HEAD
# 3f2e1d0a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e   ← 直接是哈希，不是 ref:

git status
# HEAD detached at 3f2e1d0
危险点：在分离 HEAD 状态下可以继续提交，但这些提交不被任何分支引用。一旦你 git switch main 切走，这些提交就成了"悬空对象"，只能靠 reflog（第 23 章）找回，且 30 天后可能被垃圾回收。
# 已经在分离 HEAD 上提交了有用代码？立刻建分支保住它！
git switch -c rescue-work

# 只是想看看旧版本，看完就走（不提交任何东西）
git switch --detach 3f2e1d0     # 看
git switch main                 # 回来（安全，因为没提交）

分离 HEAD 的正当用途：临时查看历史版本、基于某提交做实验（决定保留就建分支）。git bisect（第 26 章）也工作在分离 HEAD 状态。

⚠ 常见坑清单

  • 坑 1：在分离 HEAD 上开发 → 提交悬空；发现后立刻 git switch -c 新分支；
  • 坑 2：git checkout <commit> 误以为只是"看看" → 用 git show 或 git switch --detach 明确意图；
  • 坑 3：切分支失败提示覆盖 → 先 commit 或 stash，别用 -f 强切；
  • 坑 4：git branch -D 删掉了未合并工作 → 用 reflog 找回（第 23 章）；
  • 坑 5：分支名与文件名冲突（如分支叫 src）→ 命令歧义，用 git switch -- src 或改名规避。

✓ 本章小结与习题

要点一句话
分支本质.git/refs/heads/ 里存哈希的小文件，创建成本≈0
HEAD指向"当前分支"的指针（两级间接）；提交只推进当前分支
切换分支改 HEAD + 换 index + 换工作区文件三步
切换被拒有未提交改动会被覆盖 → commit / stash / 带着走
分离 HEADHEAD 直接指向提交；提交会悬空，用 switch -c 保住
A 基础用 cat .git/refs/heads/分支名 与 cat .git/HEAD 观察仓库，画出当前分支与 HEAD 的指向关系。
B 进阶用 git update-ref 手工在某历史提交上建分支并切换，验证工作区内容确实回到了那个版本。
C 挑战进入分离 HEAD 状态并提交两次，然后切回 main 观察"提交消失"，再用 git reflog 找回它们并建立分支（预习第 23 章）。
