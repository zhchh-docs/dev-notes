第 13 章 冲突解决全流程

教科书 第 13 章 / 共 40 章 · 预计 45 分钟 · 必会技能章

冲突不是 Git 出错了，而是 Git 在说"这两处改动我无法确定你的意图，请你决定"。本章给出一套标准化解决流程：读懂冲突标记、用三方对比判断取舍、验证结果、收尾提交——照做即可，不必再怕冲突。

◆本章目标

  • 说出冲突产生的唯一条件：两边改了同一文件的同一区域；
  • 能读懂 <<<<<<< / ======= / >>>>>>> 标记，并知道三段分别是什么；
  • 掌握六步法解决流程，包括解决后必须做的验证（编译/测试）；
  • 会用 --ours/--theirs、git checkout --conflict、合并工具（mergetool）提效。
心态：冲突是协作的常态。Git 已经自动合并了绝大多数改动，只有它无法判断意图时才停下来问你——这恰恰是它在保护你。

13.1 冲突是怎么产生的

合并时 Git 逐文件、逐块（hunk）比较三方：共同祖先、我们的版本（当前分支 HEAD）、他们的版本（被合并分支）。只有一种情况会冲突：

两边修改了同一文件的同一段相邻行——Git 无法自动判断该留谁的，于是停下。

情况结果例子
改了不同文件自动合并 ✅A 改 a.js，B 改 b.js
改了同文件不同位置自动合并 ✅A 改第 1 行，B 改第 100 行
改了同文件相邻行冲突 ⚠A 与 B 都改第 10 行附近
一边删、一边改冲突 ⚠A 删除文件，B 修改它（见 13.6）
二进制文件两边都改冲突 ⚠图片、Excel（Git 无法逐行合并）

13.2 读懂冲突标记

<<<<<<< HEAD                    ← ① 我们的版本（当前分支，merge 时是目标分支）
const timeout = 3000;
=======                            ← ② 分隔线
const timeout = 5000;              ← ③ 他们的版本（被合并进来的分支）
>>>>>>>> feature/optimize
标记块merge 时rebase 时（注意会互换！）
<<<<<<< HEAD（ours）当前分支（如 main）上游分支（被 rebase 到的基底，如 main）
>>>>>>> xxx（theirs）被合并分支（如 feature）你正在重放的提交（你的改动）
rebase 时 ours/theirs 会互换——这是最容易搞反的地方。原因：rebase 是"先把 HEAD 切到新基底，再逐个重放你的提交"，所以 HEAD（ours）指的是新基底，而 theirs 是你的改动。始终以文件内容判断，不要只依赖 ours/theirs 字样。
# 想看更完整的三方内容（含共同祖先版本）
git checkout --conflict=diff3 -- src/app.js
# <<<<<<< ours
# ||||||| base        ← 共同祖先原本的内容
# =======
# >>>>>>> theirs
# 有了 base，判断"谁改了什么"就容易多了

# 配置默认使用 diff3（推荐）
git config --global merge.conflictStyle diff3

13.3 标准解决流程（六步法）

  1. 看全局：git status —— 列出所有冲突文件（标为 UU）；
  2. 看冲突点：打开每个冲突文件，读 diff3 三段内容，判断业务上应该保留什么；
  3. 改写文件：删除冲突标记，写出正确的最终代码（注意：往往是"两者结合"，不是二选一）；
  4. 验证：编译 / 跑测试 / 手工验证——这一步最常被跳过，也最容易埋雷；
  5. 标记解决：git add 文件（add 即表示"这个文件我处理好了"）；
  6. 完成合并：git commit（merge 会自动带默认信息）或 git rebase --continue。
git status
# Unmerged paths:
#   both modified:   src/app.js        ← UU 状态

# ...编辑 src/app.js 解决冲突...

git add src/app.js
git status
# All conflicts fixed but you are still merging.
#   (use "git commit" to conclude merge)

git commit                    # 用默认合并信息
# 或
git commit -m "merge: 合并 feature/optimize，超时统一为 5000"

解决冲突的本质不是"选一边"，而是写出两边意图融合后的正确代码。冲突标记只是 Git 给你的原材料。

13.4 场景演练：制造并解决一次冲突

cd ~/git-lab && rm -rf ch13 && mkdir ch13 && cd ch13 && git init
printf 'line1\nline2\nline3\n' > f.txt
git add . && git commit -m "feat: 初始文件"

# ① 分支 A 改第 2 行
git switch -c feature-a
printf 'line1\nA-feature\nline3\n' > f.txt
git commit -am "feat: A 改第 2 行"

# ② 主线也改第 2 行
git switch main
printf 'line1\nmain-hotfix\nline3\n' > f.txt
git commit -am "fix: 主线改第 2 行"

# ③ 合并 → 冲突
git merge feature-a
# Auto-merging f.txt
# CONFLICT (content): Merge conflict in f.txt
# Automatic merge failed; fix conflicts and then commit the result.

cat f.txt
# line1
# <<<<<<< HEAD
# main-hotfix
# ||||||| 4a5b6c7
# line2
# =======
# A-feature
# >>>>>>> feature-a
# line3

# ④ 解决：业务上两边都要 → 手工合并为最终内容
printf 'line1\nmain-hotfix + A-feature\nline3\n' > f.txt

# ⑤ 标记 + 完成
git add f.txt && git commit -m "merge: 合并 feature-a，第 2 行融合两边改动"

# ⑥ 复盘
git log --oneline --graph --all
git show HEAD          # 确认最终内容正确

13.5 工具与策略：ours / theirs / mergetool

# 直接采用某一边的完整文件（慎用：会丢失另一边）
git checkout --ours   f.txt     # 用当前分支版本
git checkout --theirs f.txt     # 用被合并分支版本
git add f.txt

# 合并策略：冲突时自动选一边（批量，慎用）
git merge -Xours   feature      # 冲突处一律用我们的
git merge -Xtheirs feature      # 冲突处一律用他们的

# 图形化合并工具（VS Code / Beyond Compare / Meld 等）
git mergetool                   # 逐个文件打开工具
# 配置（以 VS Code 为例）
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'
git config --global mergetool.keepBackup false

# VS Code 原生：打开冲突文件即有 "Accept Current / Incoming / Both" 按钮
code f.txt
-Xours / -Xtheirs 是"投降键"：它会静默丢弃另一边的冲突改动（非冲突改动仍会保留）。只在明确知道该丢弃哪边时使用（例如"配置文件一律以主线为准"），并在提交信息里说明。
# 中止：不解决了，回到合并前
git merge --abort
# rebase 中：
git rebase --abort

13.6 特殊冲突：删除 vs 修改、二进制文件

删除 / 修改冲突

git status
# Unmerged paths:
#   deleted by us:     old-module.js      # 我们删了，对方改了
#   added by them:     new-module.js

# 决定保留删除（对方改动也一起丢）
git rm old-module.js
# 决定保留文件（撤销我们的删除）
git add old-module.js

二进制文件冲突

# Git 无法合并图片/Office 文档，报：
# CONFLICT (binary): Merge conflict in logo.png
# 只能二选一：
git checkout --ours logo.png    && git add logo.png
# 或
git checkout --theirs logo.png  && git add logo.png

# 预防：用 .gitattributes 标记二进制，避免 Git 尝试文本合并
echo "*.png binary" >> .gitattributes

团队协作建议：二进制资源（图片、设计稿、Excel）尽量由单一负责人修改，或用 LFS（大文件存储）管理；多人同时改同一张图必然冲突且难解决。

⚠ 常见坑清单

  • 坑 1：解决冲突后忘了 git add 就 commit → Git 会提示仍有未解决路径；用 git status 确认无 UU；
  • 坑 2：把冲突标记 <<<<<<< 留在代码里提交了 → 代码直接语法错误；解决后全局搜索 <<<<<<< 确认清零；
  • 坑 3：rebase 时把 ours/theirs 理解反了 → 以文件内容为准，多用 --conflict=diff3；
  • 坑 4：解决完不跑测试直接提交 → 语义冲突（两边都合法但组合起来是 bug）最致命；
  • 坑 5：一次合并几十个冲突文件就慌 → 分批解决、逐个 add，中途可用 git status 看剩余；必要时 --abort 重新来。

✓ 本章小结与习题

要点一句话
冲突条件两边改了同一文件的同一区域
三段标记ours（HEAD）/ base（共同祖先）/ theirs（对方）
六步法看 → 读 → 改 → 验证 → add → commit
diff3 样式merge.conflictStyle diff3 显示共同祖先，判断更容易
ours/theirs 互换merge 与 rebase 下含义相反，以内容为准
A 基础按 13.4 脚本完整制造并解决一次冲突，提交后用 git show 验证最终文件内容是你期望的融合结果。
B 进阶开启 merge.conflictStyle diff3，重做一次冲突，体会 base 段对判断"谁改了什么"的帮助；再练习一次 git mergetool。
C 挑战设计一次"删除 vs 修改"的冲突场景并解决；随后说明：为什么语义冲突（代码能编译但逻辑错）比文本冲突更危险，团队该用什么手段防范（提示：评审 + 测试 + 小步合并）。
