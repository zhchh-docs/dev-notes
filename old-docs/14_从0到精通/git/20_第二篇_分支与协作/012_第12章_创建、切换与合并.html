12.1 创建与切换：branch / switch / checkout

# 创建（不切换）
git branch feature/login
git branch feature/login 3f2e1d0        # 指定起点提交
git branch feature/login origin/main    # 以远程追踪分支为起点

# 创建并切换（最常用）
git switch -c feature/login
git switch -c hotfix/login-500 main     # 从 main 分出

# 切换
git switch main
git switch -                # 回到"上一个分支"（相当于 cd -）

# 从远程分支创建本地分支（clone 后常见）
git switch -c develop origin/develop    # 或简写：git switch develop（自动匹配）

# 老写法对照（checkout 的历史负担，见第 6 章）
git checkout -b feature/login    # ≡ git switch -c feature/login
场景推荐命令
开新功能分支git switch -c feature/xxx main
回主线git switch main
在两个分支间来回切git switch -
只看看历史版本（不提交）git switch --detach <commit>
误建分支想删git branch -d 名字（未合并用 -D）

12.2 快进合并 fast-forward

当你在 main 上切出 feature，期间 main 没有任何新提交，合并时 Git 只需把 main 指针"快进"到 feature 的位置——不需要计算任何差异，也不会产生新提交。

git switch main
git merge feature/login
# Updating 3f2e1d0..5b2e9d1
# Fast-forward
#  src/login.js | 12 ++++++++++++
#  1 file changed, 12 insertions(+)

git log --oneline --graph -5
# * 5b2e9d1 (HEAD -> main, feature/login) feat: 登录功能   ← 一条直线
# * 3f2e1d0 feat: 第三次改动

图 12-1 fast-forward：指针前移，零冲突风险，历史干净但没有"分支曾经存在"的痕迹

快进的前提：被合并分支是当前分支的直接后继（即当前分支没有分叉出去的新提交）。

12.3 三方合并与合并提交

若 main 在 feature 分出后也有新提交（典型：期间别人修了个 bug），就无法快进。Git 会做三方合并：

  1. 找共同祖先（merge base）：两个分支分开的那个提交；
  2. 比较 main 相对祖先的改动、feature 相对祖先的改动；
  3. 把两边改动合并成一个结果，并生成一个有两个父提交的合并提交（merge commit）。
git switch main
git merge feature/login
# Merge made by the 'ort' strategy.
#  src/login.js | 12 +++++++
#  1 file changed, 12 insertions(+)

git log --oneline --graph -6
# *   7a3f1c2 (HEAD -> main) Merge branch 'feature/login'
# |\
# | * 5b2e9d1 (feature/login) feat: 登录功能
# * | 3c1a8f0 fix: 紧急修复
# |/
# * 9d8e7c6 feat: 第 3 次改动

# 看合并提交的两个父
git cat-file -p HEAD
# parent 3c1a8f0...     ← 第一父：被合入的分支（main）
# parent 5b2e9d1...     ← 第二父：被合并进来的分支（feature）
ort 策略：Git 2.34+ 的默认合并策略（原 recursive 的继任者），能处理重命名、多个共同祖先等复杂情况。绝大多数场景无需手动指定。

第一父/第二父很重要：git log --first-parent 只看主线（顺着第一父走），是阅读"主干历史"的利器（第 5 章提过）。

12.4 场景演练：完整走一遍分支生命周期

mkdir -p ~/git-lab/ch12 && cd ~/git-lab/ch12 && git init
echo "v1" > app.js && git add . && git commit -m "feat: 初始化"

# ① 开功能分支
git switch -c feature/cart
echo "cart" >> app.js && git commit -am "feat(cart): 购物车功能"

# ② 同时主线被别人修了 bug（制造分叉）
git switch main
echo "hotfix" >> app.js && git commit -am "fix: 紧急修复支付"

# ③ 回到功能分支继续开发
git switch feature/cart
echo "coupon" >> app.js && git commit -am "feat(cart): 优惠券"

# ④ 合并前先看差异（好习惯）
git log --oneline main..feature/cart      # 我将带入什么
git diff main...feature/cart --stat       # 三点语法：从共同祖先起

# ⑤ 合回主线（此时无法快进 → 三方合并）
git switch main
git merge feature/cart -m "merge: 合并购物车功能"

# ⑥ 清理已合并的分支
git branch -d feature/cart
git log --oneline --graph --all

演练中的关键点：第 ④ 步的 main..feature（两点）看"feature 独有的提交"，而 main...feature（三点）在 diff 里表示"从共同祖先到 feature 的改动"。log 与 diff 的两点/三点含义不同，这是常被混淆的一组语法。

12.5 --no-ff 与 --squash 的战略选择

方式结果适用
merge（默认）能快进就快进，否则三方合并个人项目、小步快跑
merge --no-ff总是生成合并提交，保留分支形状需要"这个功能是一批提交"的可视边界；Git Flow
merge --squash把对方所有改动压成一个改动放进暂存区，不生成合并提交，需自己 commit功能分支有 20 条 wip 提交，只想在主线留一条干净记录
rebase 后快进历史一条直线，无合并提交第 14 章详解
 
# 保留分支边界
git merge --no-ff feature/cart -m "merge: 合并购物车功能"

# 压成一条（注意：不会自动提交！）
git merge --squash feature/cart
git status -s        # 改动都在暂存区
git commit -m "feat(cart): 购物车与优惠券功能"
git branch -D feature/cart    # 该分支已"被吸收"，可强制删除
--squash 的代价：原分支的逐条提交历史不会进入主线（它们仍存在于对象库直至 GC，但主线上只有一条）。若日后需要精细 bisect 该功能内部某次提交，就找不到了。适合"过程混乱、结果清晰"的分支。

12.6 中止与撤销合并

# 合并中出现冲突，想"算了，先不合"
git merge --abort          # 回到合并前状态（Git 1.7.4+）

# 老版本或无冲突但想反悔：
git reset --hard HEAD      # ⚠ 会丢弃工作区所有改动，确认无未提交内容再用

# 合并已完成并推送 → 不要 reset，用 revert 反向提交（保留历史）
git revert -m 1 HEAD       # -m 1 表示保留第一父（main）的改动，撤销第二父带来的

冲突怎么办：合并冲突是正常现象而非错误，解决流程见下一章（第 13 章）——本章只需记住：冲突时 Git 会停下来等你，此时 git status 会明确列出冲突文件，千万别慌着 --abort。

⚠ 常见坑清单

  • 坑 1：忘了自己在哪个分支就提交 → 提交前 git status -sb，或用 git branch --show-current；
  • 坑 2：合错了方向（把 main 合进 feature）→ 合并前确认 git switch 目标分支 再 merge；
  • 坑 3：--squash 后以为合并完成了 → 它只改暂存区，必须再 commit；
  • 坑 4：合并冲突后直接 git add . 提交，没真正解决冲突 → 必须删除冲突标记、确认逻辑正确；
  • 坑 5：长期不合并导致冲突爆炸 → 主干每天同步（第 14 章 rebase 或第 32 章 trunk-based）。
