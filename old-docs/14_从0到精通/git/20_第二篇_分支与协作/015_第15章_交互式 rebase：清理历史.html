第 15 章 交互式 rebase：清理历史

教科书 第 15 章 / 共 40 章 · 预计 45 分钟 · 高危高能章

本地开发时我们盯着"能跑就行"，可以随便 wip；但在推送给同事评审之前，历史应该像一篇写好的文章。交互式 rebase（git rebase -i）就是这支"橡皮 + 钢笔"：合并、拆分、重排、改写、删除——本章逐个动作演示。

◆本章目标

  • 会用 git rebase -i HEAD~n 打开交互界面，并读懂每个字段；
  • 掌握 pick / reword / edit / squash / fixup / drop 六大动作；
  • 能把一堆 wip 提交整理成若干条语义清晰的提交；
  • 会用 edit 拆分一个大提交，以及用备份分支/reflog 给自己留后路。
适用边界：交互式 rebase 同样改写哈希，只应在未推送或明确属于自己的分支上使用（遵循第 14 章的黄金法则）。

15.1 进入编辑界面：读懂那张清单

git rebase -i HEAD~4          # 整理最近 4 条提交

编辑器里出现（注意顺序：从上到下是从旧到新，与 git log 相反）：

pick 1a2b3c4 feat: 初始化登录页面
pick 5d6e7f8 wip
pick 9a8b7c6 fix 一下
pick 3e4f5a6 wip: 又改了点东西

# Rebase 7c1d2e3..3e4f5a6 onto 7c1d2e3 (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup <commit> = like "squash", but discard this commit's log message
# x, exec <command> = run command (the rest of the line) using shell
# b, break = stop here (continue rebase later with 'git rebase --continue')
# d, drop <commit> = remove commit
# l, label <label> = label current HEAD with a name
# t, reset <label> = reset HEAD to a label
# m, merge [-C <commit> | -c <commit>] <label> [# <oneline>]
#
# These lines can be re-ordered; they are executed from top to bottom.

两个易错点：① 顺序是旧的在上；② 移动行就能改变提交顺序（重排），但重排可能引发冲突（后面的改动依赖前面的代码）。

15.2 六大动作逐个演示

动作作用典型用途
pick原样保留默认动作；不动它
reword保留改动，改写提交信息修正错别字、补全规范前缀（第 10 章）
edit停在该提交，允许改内容/拆分拆分提交、补文件、删掉误提交的文件
squash合并到上一条，保留两条信息供编辑把相关提交合成一条，信息需要重新组织
fixup合并到上一条，丢弃本条信息吸收 wip / typo 这类无意义提交
drop（或删掉整行）删除该提交丢弃实验性/已废弃的改动
 
pick   1a2b3c4 feat: 初始化登录页面
fixup  5d6e7f8 wip                 # 吸收进上一条，丢掉 "wip" 这条信息
squash 9a8b7c6 fix 一下            # 合并进上一条，稍后编辑合并后的信息
drop   3e4f5a6 wip: 又改了点东西    # 丢弃（或干脆删掉这一行）

保存退出后，Git 会顺序执行：遇到 squash 会再次打开编辑器让你写合并后的提交信息；遇到 edit 会停下来等你操作。

15.3 场景演练：把 6 条 wip 整理成 2 条

cd ~/git-lab && rm -rf ch15 && mkdir ch15 && cd ch15 && git init
echo "v1" > app.js && git add . && git commit -m "feat: 初始化"

git switch -c feature/user
echo "a" >> app.js && git commit -am "wip"
echo "b" >> app.js && git commit -am "wip: 继续"
echo "c" >> app.js && git commit -am "feat(user): 用户列表"
echo "d" >> app.js && git commit -am "fix typo"
echo "e" >> app.js && git commit -am "wip: 收尾"
echo "f" >> app.js && git commit -am "test: 补测试"

git log --oneline
# 6 条杂乱提交

# 整理最近 6 条
git rebase -i HEAD~6

编辑器中改为：

pick   aaa111 wip
fixup  bbb222 wip: 继续
pick   ccc333 feat(user): 用户列表
fixup  ddd444 fix typo
fixup  eee555 wip: 收尾
pick   fff666 test: 补测试

保存后（第一条需要改写信息，Git 会再次打开编辑器）：

# 第一次弹出：为 "wip + wip继续" 写新信息
feat(user): 用户列表页面骨架

# 第二次弹出：squash 汇总信息（本例没有 squash，只有 fixup，故只弹一次）

git log --oneline
# 3f2e1d0 test: 补测试
# 5b2e9d1 feat(user): 用户列表页面骨架   ← 吸收了 3 条 wip
# 9d8e7c6 feat: 初始化

整理后的历史：一条功能 + 一条测试，评审者一眼看懂；而代码内容完全没变。

15.4 拆分提交（edit / break）

场景：一条提交里混了"功能代码 + 调试日志"，想拆成两条。

git rebase -i HEAD~3
# 把目标那行的 pick 改成 edit，保存退出

# Git 停在那个提交上：
git status
# interactive rebase in progress; onto xxx
# Stopped at 3f2e1d0... feat(user): 混在一起的改动

# ① 把提交"拆回"工作区（保留内容，撤销提交）
git reset HEAD~1            # mixed：改动回到工作区

# ② 分两次暂存与提交
git add src/user.js
git commit -m "feat(user): 用户列表接口"
git add src/debug-log.js
git commit -m "chore: 调试日志"

# ③ 继续重放剩余提交
git rebase --continue
更省事的写法：新版 Git（2.20+）在 rebase -i 的清单里直接把该行写成 break，或用 git rebase -i --exec 插入命令；拆分思路不变：reset HEAD~1 → 分批 add/commit → --continue。

15.5 安全网：abort、备份分支与 reflog

任何改写历史的操作，动手前先做一件事：打个备份分支——成本为零，救急价值极高。

# ① 备份（强烈推荐）
git branch backup/feature-user        # 记住当前尖端

# ② 放心改写
git rebase -i HEAD~6

# ③ 搞砸了？一键回退
git reset --hard backup/feature-user

# 或者用 reflog 找回（第 23 章详解）
git reflog
git reset --hard HEAD@{5}

# ④ 进行中想中止
git rebase --abort

心理安全：rebase 之后旧提交并没有立即消失，它们变成悬空对象，可通过 reflog 找回（默认保留 30/90 天）。所以"改错了"在短期内几乎总是可恢复的。

15.6 推送整理后的历史

# 从未推送过的分支：正常推
git push -u origin feature/user

# 之前推过（自己独占的功能分支）：需要强推，用安全版
git push --force-with-lease origin feature/user

# ❌ 危险：--force 会无视他人新提交
git push --force

强推前检查清单：

  • 该分支只有你一个人在推（PR 未创建或尚未有人基于它开分支）；
  • 本地已 git fetch 过，确认远程没有你不知道的新提交（--force-with-lease 会帮你验证）；
  • 若已开 PR：GitHub/GitLab 的 PR 通常能自动跟随强推更新（评论不会丢），但仍建议在 PR 里留一句说明。
绝对不要：git push --force origin main（强推主干）。一旦发生，立即通知全队停止推送，用 reflog 定位强推前的尖端并恢复（第 36 章有完整事故复盘）。

⚠ 常见坑清单

  • 坑 1：清单顺序看反（以为上面是最新的）→ 记住"上旧下新"，可用 git log --oneline 对照；
  • 坑 2：把 fixup 写在第一条上 → 它必须"跟随"某条 pick，第一行是 fixup 会报错；
  • 坑 3：重排提交后冲突不断 → 尽量避免跨依赖重排；冲突时逐个解决再 --continue；
  • 坑 4：edit 后忘了 --continue 就去干别的 → 仓库处于 rebase 中；用 git status 检查；
  • 坑 5：整理完直接 --force → 用 --force-with-lease，且先确认分支归属。

✓ 本章小结与习题

要点一句话
入口git rebase -i HEAD~n；清单上旧下新
六动作pick / reword / edit / squash / fixup / drop
整理套路wip 用 fixup 吸收，功能用 squash 重组，信息用 reword
拆分edit 停住 → reset HEAD~1 → 分批提交 → --continue
安全网先建 backup 分支；出错用 --abort / reset --hard backup / reflog
A 基础造 5 条 wip 提交，用 fixup 整理成 1 条，并用 git show 验证代码内容未变。
B 进阶练习 edit 拆分：把一次"功能 + 日志"的提交拆成两条；再练习 reword 把所有信息改成 Conventional Commits 格式。
C 挑战设计你自己的"推送前整理清单"：备份 → fetch → rebase -i → 逐条验证（编译/测试）→ --force-with-lease → PR 说明，并说明每步防的是什么事故。
