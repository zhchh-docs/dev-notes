12.1 UNION 与 UNION ALL

UNION 把多个 SELECT 的结果竖向堆叠。区别只有一个：UNION 会对整行去重，UNION ALL 直接拼。

-- 场景：站内消息中心，"我的待办" = 订单通知 + 系统通知
SELECT id, title, created_at
FROM msg_order
WHERE user_id = 42
UNION ALL
SELECT id, title, created_at
FROM msg_system
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
写法行为成本
UNION ALL直接堆叠，保留重复行低：两张表各扫各的，拼起来完事
UNION堆叠后对整行去重（临时表 + 排序/哈希）高：数据量越大去重越贵
默认写 UNION ALL，只有业务确实要求"两行完全相同只留一条"时才用 UNION——这是 SQL 性能清单里性价比最高的一个习惯。
分表合并：按月份分表的 order_202609、order_202610 做跨月查询时，UNION ALL 是标准姿势；这也是第 60 章分库分表中间件背后的思路。

12.2 列对齐与类型规则

竖向堆叠的硬性规则：每个 SELECT 的列数必须一致，同位置列的类型要兼容。

-- 合法：列数一致、对应类型兼容
SELECT id, name, price FROM product WHERE category_id = 3
UNION ALL
SELECT id, name, price FROM product_backup WHERE category_id = 3;

-- 报错示例一：列数不一致
SELECT id, name FROM product
UNION ALL
SELECT id, name, price FROM product_backup;     -- The used SELECT statements have a different number of columns

-- 报错/隐式转换示例二：类型不兼容（能跑但结果可能不是你想的）
SELECT id FROM product
UNION ALL
SELECT name FROM product;       -- id 是数字、name 是字符串 → 按规则统一成字符串
  • 列名以第一个 SELECT 为准：结果集的列名看第一句，后面 SELECT 的列名被忽略；
  • 类型向上兼容：同位置数字与字符串混用时，MySQL 按数据类型优先级统一（通常变成字符串或 DOUBLE）——别依赖这种隐式转换，手工 CAST 对齐；
  • 行去重按"整行所有列"比较：UNION 的去重是逐列等值，NULL 与 NULL 在 UNION 里视为相等（与 WHERE 里的三值逻辑不同，这是集合运算的定义）。

12.3 ORDER BY 与 LIMIT 的位置

这是 UNION 语句第二大坑：排序和分页作用于"堆叠后的整体"还是"单个 SELECT"？

-- 正确：最后一个 SELECT 后面写 ORDER BY，作用于 UNION 合并后的整体
SELECT id, title, created_at FROM msg_order   WHERE user_id = 42
UNION ALL
SELECT id, title, created_at FROM msg_system  WHERE user_id = 42
ORDER BY created_at DESC                      -- 对合并后的所有行排序
LIMIT 20;                                    -- 对合并后的整体分页

-- 错误认知：给单个 SELECT 排序（不加括号时不生效/不符合预期）
-- 想给子集先排：需要括号（MySQL 支持带括号的 SELECT）
(SELECT id, title FROM msg_order  ORDER BY created_at DESC LIMIT 10)
UNION ALL
(SELECT id, title FROM msg_system ORDER BY created_at DESC LIMIT 10);
跨子集分页是经典大坑："每个子查询各 LIMIT 10，再整体 LIMIT 20" 不等于"整体的前 20 条"。真要做整体分页，必须把 UNION 结果当派生表再包一层 ORDER BY/LIMIT。

12.4 INTERSECT 与 EXCEPT（8.0.31+）

标准 SQL 里的另外两个集合运算：交集（INTERSECT）与差集（EXCEPT），MySQL 直到 8.0.31 才正式支持。

-- 版本前提：SELECT VERSION(); 需 >= 8.0.31

-- INTERSECT：既在订单通知里、又在系统通知里出现过的人（实际业务少用）
SELECT user_id FROM msg_order  WHERE created_at > '2026-10-01'
INTERSECT
SELECT user_id FROM msg_system WHERE created_at > '2026-10-01';

-- EXCEPT：下过单但从没被系统通知过的用户集合
SELECT user_id FROM msg_order
EXCEPT
SELECT user_id FROM msg_system;

-- 旧版本（8.0.31 之前）的等价写法：
-- INTERSECT → INNER JOIN / EXISTS；EXCEPT → NOT EXISTS（第 11 章）
运算数学含义旧版本替代写法
UNION [ALL]并集一直支持，无替代问题
INTERSECT交集（同时在两边）INNER JOIN / EXISTS
EXCEPT差集（在 A 不在 B）NOT EXISTS / LEFT JOIN IS NULL
版本差异显式标注：INTERSECT/EXCEPT 是 8.0.31（2022 年末）才进入语法的。线上若版本低于此，用 JOIN/EXISTS 改写，本书后续报表章节也统一用兼容写法。

✓ 本章小结

要点一句话
UNION ALL vs UNION默认 ALL；UNION 的整行去重要付出排序/哈希成本
列对齐列数一致、类型兼容；列名看第一个 SELECT
排序分页写在最后，作用于合并后的整体；子集分页要各自括号包起来
INTERSECT/EXCEPT8.0.31+ 才有；旧版本用 EXISTS/NOT EXISTS 改写
典型场景分表合并、消息流、日志归集

✎ 本章习题

A 基础把 order_202609 与 order_202610 两张结构相同的分表合并，查出两月所有已支付订单的 id、order_no、amount，按金额降序取前 50。
B 进阶把 A 的结果再包装一层派生表，实现"按月分别各取金额前 3，再合并且整体按金额降序"，对比"不包一层直接写"的结果差异。
C 挑战在 MySQL 版本低于 8.0.31 的前提下，用 NOT EXISTS 写出"下过单但从未被系统通知过的用户"，并说明为什么不用 NOT IN。
