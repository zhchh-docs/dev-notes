第 11 章 EXISTS 与 IN 的选择

教科书 第 11 章 / 共 72 章 · 预计 35 分钟

"查下单过的用户"这个需求，IN 能写、EXISTS 也能写，MySQL 8.0 的优化器大多能把它们改写成同一种半连接。但 NOT IN 遇到 NULL 会悄悄返回空表——这是线上报表莫名少数据的头号嫌疑犯，本章把它讲透。

11.1 EXISTS 怎么工作

EXISTS 不关心子查询返回什么列，只关心"有没有行返回"——找到第一行匹配就立刻停（短路）。

-- 需求：查"下过单的用户"
SELECT c.id, c.name
FROM customer c
WHERE EXISTS (
  SELECT 1                       -- 列写什么都行，习惯写 1
  FROM orders o
  WHERE o.customer_id = c.id
    AND o.status = 'PAID'
);

执行逻辑：外层逐行拿 customer.id 代入子查询，只要 orders 里能找到一行匹配，这行用户就算"下过单"，立即跳去下一个用户——子查询的 SELECT 列表因此写 1、*、'x' 效果完全相同。

相关子查询 + 短路：EXISTS 是相关子查询（引用外层 c.id），但短路特性让它平均成本低；对大表，子查询侧的连接列 orders.customer_id 必须有索引，否则每行用户都全扫一次 orders。

11.2 IN vs EXISTS：性能对比

老经验说"小表用 IN、大表用 EXISTS"——那是 MySQL 5.x 时代的事。8.0 的半连接优化已经把大多数写法拉平。

-- IN 版本：先把已支付订单的 customer_id 当成集合，再筛用户
SELECT c.id, c.name
FROM customer c
WHERE c.id IN (SELECT customer_id FROM orders WHERE status = 'PAID');

-- 两条语句在 8.0 里通常被优化器改写成同一种执行计划：
-- Semi Join（半连接）：用户表与订单表走索引连接，命中即止、不重复放大行数
维度INEXISTS
语义值在子查询结果集合中子查询至少返回一行
8.0 优化可被改写成半连接可被改写成半连接
关联列 NULL右列含 NULL 时结果异常不受影响
可读性集合语义直白，首选表达"存在性"更自然
结论先行：8.0 上 IN 与 EXISTS 性能基本同档（都被半连接优化）；选择看语义——"在集合里"用 IN，"存在/不存在"用 EXISTS。真正的分水岭在 NOT（见下一节）。

11.3 NOT IN 的 NULL 陷阱

这是本章最重要的一节：NOT IN 子查询结果里只要有一个 NULL，整条查询返回空表，还不报错。

-- 复现：假设 orders.customer_id 存在 NULL（脏数据/测试残留）
-- 需求：找出"从没下过单"的用户
SELECT c.id, c.name
FROM customer c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
-- 返回：0 行！但表里明明有用户从没下过单

-- 原因拆解：对某个用户 id=10，判断 10 NOT IN (1, 2, NULL)
--   10 <> 1  AND 10 <> 2  AND 10 <> NULL
--   UNKNOWN（10 和 NULL 比较得 UNKNOWN）
-- NOT (10 IN (...)) 里一旦出现 UNKNOWN，整体永远不是 TRUE
-- WHERE 只留 TRUE → 这行被丢弃 → 全部行都被丢弃
线上"报表突然少了一半数据"，先查子查询列能不能为 NULL。两个保命动作：① 关联列建表时尽量 NOT NULL；② 实在控不住，NOT IN 一律改 NOT EXISTS（下节）。

11.4 反连接：NOT EXISTS 改写

表达"没有"的安全写法：NOT EXISTS（不吃 NULL 那一套），或第 9 章的 LEFT JOIN ... IS NULL。

-- 写法一：NOT EXISTS（推荐，语义最清晰）
SELECT c.id, c.name
FROM customer c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
);

-- 写法二：LEFT JOIN + IS NULL（第 9 章的反连接）
SELECT c.id, c.name
FROM customer c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 写法三：逼 NULL 现形后再 NOT IN（不推荐，但知道有这回事）
SELECT c.id FROM customer c
WHERE c.id NOT IN (
  SELECT customer_id FROM orders
  WHERE customer_id IS NOT NULL     -- 先把 NULL 剔掉
);
写法优点注意
NOT EXISTS不受 NULL 影响；8.0 优化为反连接关联列要有索引
LEFT JOIN IS NULL与第 9 章反连接同构，可复用上一章思路右表一对多时先去重（DISTINCT/子查询），否则行数膨胀
NOT IN + 过滤 NULL老代码里常见易遗忘过滤条件，新代码别用
给前端转全栈的你：这和 JS 里 arr.includes(null) 的语义是相通的——集合里藏个"未知值"，所有判断都失真。数据库只是把这个坑放大到了全表。

✓ 本章小结

要点一句话
EXISTS找到一行就短路；列写什么都行，习惯 SELECT 1
IN vs EXISTS8.0 半连接优化拉平性能；按语义选：集合用 IN、存在用 EXISTS
NOT IN 陷阱子查询列含 NULL → 恒返回空表，不报错
表达"没有"首选 NOT EXISTS 或 LEFT JOIN ... IS NULL

✎ 本章习题

A 基础分别用 IN 和 EXISTS 写出"下过已支付订单的用户"，并说明两条 SQL 在 MySQL 8.0 里大致被优化成什么执行计划。
B 进阶构造实验：向 orders 表插一行 customer_id 为 NULL 的记录，执行 SELECT * FROM customer WHERE id NOT IN (SELECT customer_id FROM orders)，观察返回行数；然后改成 NOT EXISTS 版本，对比结果差异并解释原因。
C 挑战写出"从未购买过 3 号类目商品的用户"（三张表：customer/orders/order_item/product），要求用 NOT EXISTS 实现；并用 EXPLAIN 验证关联列上的索引是否被用上。
