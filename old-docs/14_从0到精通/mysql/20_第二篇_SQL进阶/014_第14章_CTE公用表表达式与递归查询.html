第 14 章 CTE 公用表表达式与递归查询

教科书 第 14 章 / 共 72 章 · 预计 40 分钟

"上一章那种子查询包子查询"——嵌套三层之后谁都读不懂。CTE（WITH 子句）让你把中间结果起名字、层层叠上去；它还有一个杀手锏：RECURSIVE 递归，遍历部门树、菜单树、生成连续日期序列全靠它。

14.1 非递归 CTE：先起名再用

CTE = Common Table Expression：在主查询之前用 WITH 定义一批"临时视图"，主查询里随便引用。

-- 上一章组内 TopN 的 CTE 写法：可读性碾压嵌套子查询
WITH cat_sales AS (
  SELECT
    category,
    product,
    SUM(amount) AS total_amount
  FROM sales_demo
  GROUP BY category, product
),
ranked AS (
  SELECT
    category, product, total_amount,
    ROW_NUMBER() OVER (PARTITION BY category ORDER BY total_amount DESC) AS rn
  FROM cat_sales
)
SELECT category, product, total_amount
FROM ranked
WHERE rn <= 3
ORDER BY category, rn;
  • 每个 CTE 像一条"命名的变量"：第一步算完叫 cat_sales，第二步 ranked 直接引用它；
  • 一条 WITH 里可以定义多个 CTE，用逗号分隔；后面的可以引用前面的（链式，见下一节）；
  • CTE 只在当前这条语句里有效，语句结束就消失——不建表、不存数据，纯语法糖 + 可读性。
CTE 对性能几乎无影响（8.0 会做合并/下推优化），它的真正价值是可读性：报表 SQL 超过两层嵌套就该换 CTE 拆步骤。

14.2 链式 CTE

后一步引用前一步的结果，像流水线一样——这是 CTE 最常用的形态。

-- 业务：算"本月每日本类目的累计销售额环比"
WITH daily AS (                       -- 第一步：按日按类目汇总
  SELECT sale_date, category, SUM(amount) AS day_amount
  FROM sales_demo
  GROUP BY sale_date, category
),
cum AS (                             -- 第二步：在 daily 基础上算累计
  SELECT
    sale_date, category, day_amount,
    SUM(day_amount) OVER (
      PARTITION BY category ORDER BY sale_date
    ) AS cum_amount
  FROM daily
)
SELECT * FROM cum ORDER BY category, sale_date;

-- CTE 还能被引用多次（子查询做不到，FROM 派生表也只能用一次）
WITH stats AS (SELECT AVG(amount) AS avg_a FROM sales_demo)
SELECT * FROM sales_demo CROSS JOIN stats
WHERE amount > stats.avg_a;

14.3 递归 CTE：遍历树

WITH RECURSIVE 是 SQL 处理"自引用结构"（部门树、菜单树、评论楼中楼）的唯一优雅解。

-- 准备：员工表（manager_id 指向本表 id）
DROP TABLE IF EXISTS emp_tree;
CREATE TABLE emp_tree (
  id        INT PRIMARY KEY,
  name      VARCHAR(20),
  manager_id INT
);
INSERT INTO emp_tree VALUES
  (1, 'CEO',      NULL),
  (2, '技术总监', 1),
  (3, '产品总监', 1),
  (4, '前端组长', 2),
  (5, '后端组长', 2),
  (6, '前端工程师', 4);

-- 递归 CTE：从 CEO 出发，向下逐层找到所有下属
WITH RECURSIVE org AS (
  -- ① 锚点：起点行（谁都不是下属的人）
  SELECT id, name, manager_id, 1 AS depth
  FROM emp_tree
  WHERE manager_id IS NULL

  UNION ALL

  -- ② 递归步：把上一步的结果 join 回原表，找"它的下属"
  SELECT e.id, e.name, e.manager_id, o.depth + 1
  FROM emp_tree e
  JOIN org o ON e.manager_id = o.id
)
SELECT * FROM org ORDER BY depth, id;
反向遍历：从某员工出发找全部上级，把 JOIN 条件反过来：JOIN org o ON e.id = o.manager_id 改成 JOIN org o ON e.id = o.manager_id 锚点换成"该员工"，递归步 JOIN emp_tree e ON o.manager_id = e.id 即可一路找到 CEO。

14.4 递归的终止与深度限制

递归不是死循环——它靠"递归步再也产不出新行"自然停止，但 MySQL 给它兜了一层强制上限。

-- 查看/调整递归深度上限（默认 1000）
SHOW VARIABLES LIKE 'cte_max_recursion_depth';
SET SESSION cte_max_recursion_depth = 100;

-- 构造死循环（自引用成环）的后果：
WITH RECURSIVE loop_cte AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM loop_cte WHERE n < 5000   -- 没有其他终止条件
)
SELECT * FROM loop_cte;
-- 跑到 1000 层（默认上限）直接报错：Recursive query aborted after 1001 iterations
生产纪律：① 递归步的 JOIN 条件必须收敛（manager_id 指向一定收敛到锚点），环数据要先清掉；② 无限序列（如生成日期）必须显式写终止条件 WHERE n < 某上限；③ cte_max_recursion_depth 是保险丝，别为了跑大递归把它调到天上去。

14.5 实战：日期序列

报表常见需求：没下单的日期也要显示 0——先生成连续日期表，再 LEFT JOIN 真实数据。

-- 生成 2026-10-01 ~ 2026-10-07 的连续日期序列
WITH RECURSIVE dates AS (
  SELECT CAST('2026-10-01' AS DATE) AS d
  UNION ALL
  SELECT d + INTERVAL 1 DAY FROM dates WHERE d < '2026-10-07'
)
SELECT d FROM dates;

-- 实战：10 月每天订单数，没单的日期显示 0
WITH RECURSIVE dates AS (
  SELECT CAST('2026-10-01' AS DATE) AS d
  UNION ALL
  SELECT d + INTERVAL 1 DAY FROM dates WHERE d < '2026-10-31'
),
day_order AS (
  SELECT DATE(created_at) AS d, COUNT(*) AS cnt
  FROM orders
  WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01'
  GROUP BY DATE(created_at)
)
SELECT d.d, COALESCE(o.cnt, 0) AS order_cnt
FROM dates d
LEFT JOIN day_order o ON o.d = d.d
ORDER BY d.d;
"日期表 LEFT JOIN 业务表，COALESCE 补 0" 是报表 SQL 的经典范式——没有 CTE 之前，这个需求要建日历表或者递归嵌套半天。
