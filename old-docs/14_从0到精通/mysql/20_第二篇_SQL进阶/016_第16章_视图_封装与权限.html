第 16 章 视图：封装与权限

教科书 第 16 章 / 共 72 章 · 预计 30 分钟

视图是一张"不存数据的表"：它把一条 SELECT 固化下来，像表一样查询。好处有两个——常用报表不用每次重写 SQL，以及配合权限把敏感列藏起来。本章讲什么时候该用视图、什么时候它反而拖慢系统。

◆本章目标

  • 掌握 ALTER/DROP VIEW 的维护动作。

16.1 创建与查询视图

视图 = 一条被命名、被存储的 SELECT。查视图就是在跑它背后的 SELECT。

-- 建视图：把"订单列表联表"固化下来
CREATE VIEW v_order_list AS
SELECT
  o.id,
  o.order_no,
  c.name    AS customer_name,
  o.amount,
  o.status,
  o.created_at
FROM orders o
INNER JOIN customer c ON c.id = o.customer_id
WHERE o.is_deleted = 0;

-- 之后就像查表一样用它
SELECT * FROM v_order_list
WHERE status = 'PAID'
ORDER BY created_at DESC LIMIT 20;

-- 看视图定义
SHOW CREATE VIEW v_order_list;

16.2 可更新视图与 WITH CHECK OPTION

简单视图（单表、不含聚合/DISTINCT/GROUP BY）可以直接 INSERT/UPDATE——但有一条防线叫 WITH CHECK OPTION。

-- 建一个"只看未删除用户"的视图
CREATE VIEW v_customer_active AS
SELECT id, name, phone, level
FROM customer
WHERE is_deleted = 0
WITH CHECK OPTION;          -- 关键：通过视图改的数据必须仍能被视图查出来

-- 通过视图插入：is_deleted 没给值 → 默认 0 → 能被视图查到 → 成功
INSERT INTO v_customer_active (name, phone) VALUES ('新用户', '13900000000');

-- 反面：试图通过视图把一行"软删掉"
UPDATE v_customer_active SET is_deleted = 1 WHERE id = 42;
-- 没有 is_deleted 列（视图里没查它），但如果通过别的方式：
-- WITH CHECK OPTION 会拒绝"改完就从视图消失"的行
情形是否可更新
单表、列一一对应、无聚合可 INSERT/UPDATE/DELETE
含 JOIN / GROUP BY / DISTINCT / 聚合函数只读（UPDATE 报错）
WITH CHECK OPTION强制"通过视图写入的数据必须满足视图的 WHERE 条件"

16.3 视图与权限控制

视图最有价值的落地场景：给第三方/运营方提供"脱敏后的查询入口"，他们根本接触不到原始表。

-- 建一个"对外脱敏版"用户视图：手机号打码、不带余额
CREATE VIEW v_customer_public AS
SELECT
  id,
  name,
  CONCAT(LEFT(phone, 3), '****', RIGHT(phone, 4)) AS phone_masked,
  level,
  created_at
FROM customer;

-- 授权：外部账号只能 SELECT 这个视图，没有原表权限
CREATE USER 'bi_read'@'%' IDENTIFIED BY '强密码';
GRANT SELECT ON shop.v_customer_public TO 'bi_read'@'%';
FLUSH PRIVILEGES;

-- 该账号执行：
SELECT * FROM v_customer_public LIMIT 10;   -- 正常
SELECT * FROM customer;                      -- 报错：没有权限
视图不是安全边界的全部，但"原表不授权、只给视图授权"是最省心的脱敏方案——比在应用层到处做脱敏一致得多。

16.4 视图的性能误区

两个关于视图的常见误会，先澄清：

  • 视图不会加速：它不存数据、不建索引，每次查视图都是在跑背后的 SQL。指望"建个视图查询就变快"是完全错误的——快的索引在原表上；
  • 嵌套视图是深渊：视图 B 查视图 A，再被视图 C 引用，调试时谁也看不出最终执行了什么。建议最多一层，报表场景直接用 CTE（第 14 章）更透明。
MySQL 8.0 有"视图合并（MERGE）"优化器：简单视图会被展开合并进外层 SQL，几乎无开销；但带复杂子查询的视图会被物化成临时表，性能可能不如手写。拿不准就 EXPLAIN 看一眼。

16.5 修改与删除视图

-- 改视图定义（相当于替换）
CREATE OR REPLACE VIEW v_order_list AS
SELECT o.id, o.order_no, o.amount, o.created_at
FROM orders o
WHERE o.is_deleted = 0;

-- 改名
RENAME TABLE v_order_list TO v_orders;

-- 删除
DROP VIEW IF EXISTS v_orders;
用 CREATE OR REPLACE VIEW 而不是先 DROP 再 CREATE——前者原子、不打断权限（GRANT 的是视图名，定义替换不影响授权）。

✓ 本章小结

要点一句话
本质命名的 SELECT，不存数据，查视图 = 展开背后的 SQL
可更新单表简单视图可写；JOIN/聚合视图只读
WITH CHECK OPTION通过视图写入的数据必须仍满足视图的 WHERE
权限原表不授权、只给视图授权，是最省心的脱敏方案
性能视图不加速；避免嵌套视图，报表用 CTE
