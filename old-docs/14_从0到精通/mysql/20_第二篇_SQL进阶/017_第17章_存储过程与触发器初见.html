第 17 章 存储过程与触发器初见

教科书 第 17 章 / 共 72 章 · 预计 40 分钟

存储过程是"存在数据库里的函数"，触发器是"增删改自动触发的钩子"。它们让数据库从"被动查表"变成"能跑逻辑"。本章带你看懂语法、会写简单样例，更重要的是知道——现代互联网公司为什么大多不写这两样东西。

17.1 DELIMITER 与 CREATE PROCEDURE

存储过程体里满是分号，而客户端默认以分号当语句结束——所以要先临时换一个结束符。

-- 第一步：把语句结束符临时改成 //
DELIMITER //

-- 第二步：创建过程（括号里可以带参数）
CREATE PROCEDURE p_order_count(IN p_date DATE)
BEGIN
  SELECT COUNT(*) AS order_cnt
  FROM orders
  WHERE DATE(created_at) = p_date;
END //

-- 第三步：改回分号
DELIMITER ;

-- 调用
CALL p_order_count('2026-10-01');
DELIMITER 是客户端命令，不是 SQL：它只告诉 mysql 客户端"现在什么字符算一句结束"，数据库本身不知道这条命令。在 Navicat/DBeaver 里通常有"执行整段"按钮，写法一样。

17.2 参数：IN / OUT / INOUT

三种参数方向，和编程语言里的值传递/引用传递对应。

DELIMITER //

CREATE PROCEDURE p_calc_rate(
  IN  p_order_cnt INT,        -- IN：传入（默认）
  OUT p_rate       DECIMAL(5,2), -- OUT：由过程回填给调用方
  INOUT p_extra    INT          -- INOUT：进得去也回得来
)
BEGIN
  -- 用 INTO 把查询结果写进 OUT 变量
  SELECT COUNT(*) INTO p_extra FROM orders WHERE status = 'PAID';

  SET p_rate = p_extra / NULLIF(p_order_cnt, 0) * 100;
END //

DELIMITER ;

-- 调用：OUT/INOUT 需要用"用户变量"（@开头）接
SET @cnt = 100;
CALL p_calc_rate(100, @paid_rate, @cnt);
SELECT @paid_rate, @cnt;
方向语义类比
IN（默认）调用方传入，过程内可读函数参数
OUT过程内写值，调用后由调用方取回出参/多返回值
INOUT传入初始值，过程修改后带回引用传递

17.3 流程控制：IF / CASE / 循环

过程体就是一段过程式代码：变量、分支、循环全有。

DELIMITER //

CREATE PROCEDURE p_level_up(IN p_user_id INT)
BEGIN
  DECLARE v_amount DECIMAL(10,2);   -- DECLARE 声明局部变量（必须放在最前）

  SELECT COALESCE(SUM(amount), 0) INTO v_amount
  FROM orders WHERE customer_id = p_user_id AND status = 'PAID';

  -- IF 分支
  IF v_amount >= 10000 THEN
    UPDATE customer SET level = 'VIP'  WHERE id = p_user_id;
  ELSEIF v_amount >= 1000 THEN
    UPDATE customer SET level = 'GOLD' WHERE id = p_user_id;
  ELSE
    UPDATE customer SET level = 'NORMAL' WHERE id = p_user_id;
  END IF;
END //

DELIMITER ;
知道有循环就够：MySQL 有 WHILE / REPEAT / LOOP 三种循环语法，但生产存储过程里写循环遍历大表基本等于自己实现"低效游标"，本书不展开——真要批量处理，用批量 SQL 或应用层循环。

17.4 触发器：BEFORE / AFTER

触发器 = 表上的钩子：INSERT/UPDATE/DELETE 发生时自动执行一段 SQL，无需手动调用。

-- 场景：订单支付后自动扣减库存
DELIMITER //

CREATE TRIGGER trg_after_order_paid
AFTER UPDATE ON orders              -- 时机：orders 被 UPDATE 之后
FOR EACH ROW                        -- 每受影响一行触发一次
BEGIN
  -- OLD：变更前的行；NEW：变更后的行
  IF NEW.status = 'PAID' AND OLD.status <> 'PAID' THEN
    UPDATE product
    SET stock = stock - 1
    WHERE id = NEW.product_id;
  END IF;
END //

DELIMITER ;
  • 时机组合：BEFORE/AFTER × INSERT/UPDATE/DELETE 六种；BEFORE 常用于校验/补默认值，AFTER 常用于联动更新；
  • OLD / NEW：分别代表变更前/后的行；INSERT 只有 NEW、DELETE 只有 OLD；
  • 一行一触发：FOR EACH ROW 意味着批量更新 1 万行，触发器跑 1 万次。

17.5 什么时候该用、什么时候不该

这是本章最值钱的一节。传统企业（银行、ERP）重度使用存储过程；互联网公司则普遍把逻辑放应用层。

维度存储过程/触发器应用层代码（Java/Go/Node）
部署与版本逻辑藏在库里，改一次要 DBA 发版随应用发布，CI/CD 成熟
调试print 日志难、单测难断点、单测、链路追踪全套
扩缩容数据库是单点瓶颈，逻辑往里堆只会更慢应用无状态，随便加机器
触发器风险批量 SQL 悄悄被放大副作用，锁与日志暴涨联动逻辑显式写在代码里，看得见
适合场景报表批量任务、数据修复、跨库归档绝大多数业务逻辑
给前端转全栈的结论：看得懂老系统里的存储过程就够了，新业务一律把逻辑放应用层——数据库只负责存和查，不负责"想"。
触发器的隐性成本：线上一次批量 UPDATE，可能触发 N 次联动写，主从延迟、行锁范围、binlog 量全部放大。接手老系统先 grep 一遍 information_schema.triggers。

✓ 本章小结

要点一句话
DELIMITER客户端级命令，过程体写完别忘记改回分号
参数IN 传入、OUT 回填、INOUT 双向
流程DECLARE 变量 + IF/CASE；批量逻辑别靠循环
触发器BEFORE/AFTER × INSERT/UPDATE/DELETE；OLD/NEW 代表变更前后
工程观业务逻辑放应用层；存储过程只留给批量任务
