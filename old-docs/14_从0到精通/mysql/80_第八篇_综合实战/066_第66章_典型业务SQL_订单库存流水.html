66.1 下单：一个事务干四件事

下单 = 建订单、扣库存、记流水，必须一个事务，要么全成要么全回滚。

START TRANSACTION;

-- ① 建订单主表
INSERT INTO orders (order_no, user_id, total_amount, status)
VALUES ('NO202610230001', 1001, 199.00, 'CREATED');

-- ② 写明细（快照价格）
INSERT INTO order_item (order_id, product_id, product_name, price, quantity)
VALUES (LAST_INSERT_ID(), 55, '机械键盘', 199.00, 1);

-- ③ 乐观锁扣库存：version 不匹配就扣失败
UPDATE inventory
SET stock = stock - 1, version = version + 1
WHERE product_id = 55 AND stock >= 1 AND version = 0;
-- 影响行数 = 0 说明并发竞争或库存不足，要 ROLLBACK

-- ④ 记资金流水
INSERT INTO wallet_flow (user_id, order_id, amount, type)
VALUES (1001, LAST_INSERT_ID(), -199.00, 'PAY');

COMMIT;
坑：LAST_INSERT_ID() 在一个事务里多次调用会返回"最近一次"，第二次 insert orders 后已经变了。正确做法是先拿订单 ID 存变量再复用。
-- 正确写法：先拿订单 ID
INSERT INTO orders (order_no, user_id, total_amount, status)
VALUES ('NO202610230002', 1001, 199.00, 'CREATED');
SET @oid = LAST_INSERT_ID();

INSERT INTO order_item (order_id, product_id, product_name, price, quantity)
VALUES (@oid, 55, '机械键盘', 199.00, 1);

UPDATE inventory SET stock = stock - 1, version = version + 1
WHERE product_id = 55 AND stock >= 1 AND version = 0;

INSERT INTO wallet_flow (user_id, order_id, amount, type)
VALUES (1001, @oid, -199.00, 'PAY');

66.2 幂等：防重复下单

网络重试、用户狂点都会产生重复订单，靠唯一约束兜底。

-- order_no 有唯一索引：同一请求号重复插入直接报错，应用捕获后返回"已下单"
INSERT INTO orders (order_no, user_id, total_amount, status)
VALUES ('NO202610230001', 1001, 199.00, 'CREATED');
-- Duplicate entry 'NO202610230001' → 应用层查已有订单返回，不重复扣库存
幂等的本质：让"同一个操作执行 N 次"等于执行 1 次。数据库唯一约束是最便宜、最可靠的幂等手段。

66.3 订单列表与详情

-- 我的订单列表：走 (user_id, created_at) 联合索引
SELECT o.order_no, o.total_amount, o.status, o.created_at
FROM orders o
WHERE o.user_id = 1001 AND o.is_deleted = 0
ORDER BY o.created_at DESC
LIMIT 20;

-- 订单详情：主表 + 明细
SELECT o.order_no, o.status, i.product_name, i.price, i.quantity
FROM orders o
JOIN order_item i ON i.order_id = o.id
WHERE o.order_no = 'NO202610230001';
查询用到的索引/注意点
我的订单列表idx_user_created 覆盖 user_id 过滤 + created_at 排序
订单详情uk_order_no 定位主表，idx_order 拉明细，小结果集
资金对账wallet_flow 按 user_id+created_at 聚合，别 SELECT *

66.4 对账：订单金额 vs 流水

-- 找出"有订单但流水对不上"的异常单
SELECT o.id, o.order_no, o.total_amount,
       COALESCE(SUM(f.amount),0) AS flow_sum
FROM orders o
LEFT JOIN wallet_flow f ON f.order_id = o.id AND f.type = 'PAY'
WHERE o.status = 'PAYED'
GROUP BY o.id, o.order_no, o.total_amount
HAVING ABS(o.total_amount + COALESCE(SUM(f.amount),0)) > 0.001;

66.5 并发下单的边界情况

真实高并发下，乐观锁会失败，要重试而不是直接报错。

# 乐观锁扣库存失败（影响 0 行）时，有限次重试
def place_order(pid, uid):
    for attempt in range(3):
        if try_dec_stock(pid):
            commit_order(uid, pid)
            return True
    raise BusinessError("下单繁忙，请重试")
坑：重试必须有限次（3 次内），且整体是幂等的（order_no 不变），否则重试本身会制造重复订单。

66.6 订单状态机

订单 status 不是自由文本，而是有限状态机，流转要受控。

-- 状态：CREATED → PAYED → FINISHED，或 → CANCELLED
-- 合法流转用更新条件约束，防止跳状态
UPDATE orders
SET status='PAYED', payed_at=NOW()
WHERE order_no='NO202610230001' AND status='CREATED';
-- 影响 0 行说明状态不对（已支付/已取消），应用侧提示
当前状态允许的下一状态
CREATEDPAYED（支付成功）/ CANCELLED（超时取消）
PAYEDFINISHED（确认收货）/ REFUNDING（退款）
CANCELLED / FINISHED终态，不再流转
坑：应用层直接 UPDATE status 不校验当前状态，会把 FINISHED 改回 CREATED——流转条件必须写在 WHERE 里。

✓ 本章小结

要点一句话
下单事务建订单→写明细→乐观锁扣库存→记流水，一个事务
LAST_INSERT_ID先存变量再复用，别在事务里反复调
幂等order_no 唯一约束兜底，重复插入捕获后返回已有订单
对账订单 LEFT JOIN 流水，HAVING 找金额不平的异常单
订单状态机状态流转用约束+注释固定，别让业务乱写
