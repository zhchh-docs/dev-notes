71.1 sysbench 快速上手

sysbench 是 MySQL 压测事实标准：建表、灌数据、跑 OLTP、出报告。

# 1) 准备：16 张表，每张 100 万行
sysbench oltp_read_write --db-driver=mysql   --mysql-host=127.0.0.1 --mysql-user=root --mysql-password=***   --tables=16 --table-size=1000000 prepare

# 2) 压测：32 线程，跑 60 秒
sysbench oltp_read_write --db-driver=mysql   --mysql-host=127.0.0.1 --mysql-user=root --mysql-password=***   --tables=16 --table-size=1000000   --threads=32 --time=60 --report-interval=10 run

# 3) 清理
sysbench oltp_read_write ... cleanup
报告关键行：queries: xxx (yyy per sec) 就是 QPS；latency (ms) avg/95th/max 是延迟分布——盯 95 分位而不是平均。

71.2 读压测结果

指标怎么看
QPS/TPS随线程数上升到拐点后不涨甚至下降，拐点就是最优并发
95th 延迟比平均值更能代表用户体验，拐点处应 < 业务容忍线
CPU/IO 利用率CPU 打满是计算瓶颈，IO 打满是存储瓶颈，对应不同扩容方向
坑：压测数据量太小时（比如只有 1 万行），全在 Buffer Pool 里，结果虚高——必须用接近生产的数据量，跑前先预热。

71.3 容量规划

-- 容量估算示例
压测得到：单实例在 95 延迟 < 50ms 时 QPS = 3000
业务预估峰值：每秒 2000 个读请求
冗余系数：2（应对翻倍与突发）
需要实例数 = ceil(2000 × 2 / 3000) = 2 个读实例
  • 原则：按"目标延迟下的 QPS"做规划，不按峰值压测最大值；
  • 冗余：留 2 倍余量，一台挂了另一台能扛；
  • 误区：用裸库压测代表线上——缓存、连接池、慢查询都会拉低真实水位。
容量规划的口径：目标延迟内的 QPS × 业务峰值 × 2 倍冗余 ÷ 单实例能力 = 需要的实例数。

71.4 压测报告怎么写

一份能指导决策的报告，不只是 QPS 数字。

报告要素：
1. 环境：机型、CPU核数、内存、数据量（行数/GB）
2. 场景：oltp_read_write，预热时长
3. 结果：不同线程数下的 QPS 与 P95/P99 延迟
4. 拐点：QPS 不再上升的并发数
5. 结论：目标延迟内单实例能力 + 建议实例数
压测报告的价值在"可复现"：环境、数据量、预热都写清，下次扩容才有依据。
压测前提再强调：生产级数据量 + 预热，否则 Buffer Pool 全命中、结果虚高 2~3 倍。
# 预热：先跑 60 秒让热数据进 Buffer Pool，丢弃该轮结果
sysbench oltp_read_write --threads=16 --time=60 run
# 再正式记录拐点与 P95

71.5 sysbench 压测脚本与读数

把压测固化成一个脚本，每次扩容前直接跑，不用临时拼命令。

#!/bin/bash
# oltp.sh：预热 + 正式压测，结果落盘
HOST=127.0.0.1; USER=root; PW=***; TBL=16; SIZE=1000000

# 1) 灌数据（只在第一次）
sysbench oltp_read_write --db-driver=mysql   --mysql-host=$HOST --mysql-user=$USER --mysql-password=$PW   --tables=$TBL --table-size=$SIZE prepare

# 2) 预热 30s，丢弃结果
sysbench oltp_read_write --db-driver=mysql   --mysql-host=$HOST --mysql-user=$USER --mysql-password=$PW   --tables=$TBL --table-size=$SIZE --threads=16 --time=30 run > /dev/null

# 3) 正式：32 线程跑 60s，输出存盘
sysbench oltp_read_write --db-driver=mysql   --mysql-host=$HOST --mysql-user=$USER --mysql-password=$PW   --tables=$TBL --table-size=$SIZE --threads=32 --time=60   --report-interval=10 run | tee result_$(date +%F).log
报告字段怎么读
queries: ... per sec即 QPS，随线程上升到拐点后趋平
latency 95th percentile用户体验的真实水位，写进报告
threads fairness过低说明资源竞争不均，换小实例更划算
脚本化的价值：下次扩容直接改线程数复跑，三次压测放一张表就是容量曲线。

71.6 压测报告模板

一份能指导扩容的报告，不只是 QPS 数字。

报告要素：
1. 环境：机型/CPU核数/内存/数据量(行数+GB)
2. 场景：oltp_read_write，预热 30s
3. 结果：8/32/64/128 线程下 QPS 与 P95
4. 拐点：QPS 不再上升的并发数
5. 结论：目标延迟内单实例能力 + 建议实例数
报告的价值在可复现：环境、数据量、预热写清，下次扩容才有依据。
压测结论要落到数字：单实例在 P95<50ms 时 QPS=xxxx，业务峰值 yyyy，留 2 倍冗余需 z 个实例。
容量规划的终点是一行可执行的扩容决策，不是一堆图表。

✓ 本章小结

要点一句话
工具sysbench oltp_read_write：prepare/run/cleanup 三步
读数盯 95th 延迟与 QPS 拐点，不是平均值和最大并发
前提生产级数据量 + 预热，否则结果虚高
规划目标延迟 QPS × 峰值 × 2 冗余 ÷ 单实例 = 实例数
sysbench 脚本三步脚本跑通，盯住 per-segment 报告里的 QPS 与 95th 延迟
报告模板环境/数据量/拐点/结论四要素
