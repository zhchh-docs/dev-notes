5.1 INSERT 的四种姿势

-- 姿势一：指明列名再插值（推荐：列顺序变了也不出错）
INSERT INTO customer (name, phone) VALUES ('张三', '13800000001');

-- 姿势二：一次插多行（批量写入比循环单条快得多）
INSERT INTO customer (name, phone) VALUES
  ('李四', '13800000002'),
  ('王五', '13800000003'),
  ('赵六', '13800000004');

-- 姿势三：只插部分列，其余走默认值
INSERT INTO product (name, price) VALUES ('机械键盘', 399.00);

-- 姿势四：INSERT ... SELECT，从别的表筛出来直接灌进来
INSERT INTO customer_archive (id, name, phone)
SELECT id, name, phone FROM customer WHERE id <= 3;

拿到刚生成的自增 ID

INSERT INTO customer (name, phone) VALUES ('孙七', '13800000005');
SELECT LAST_INSERT_ID();   -- 返回本次连接最近一次插入的自增值

应用代码里这条更重要：各语言的驱动都提供了等价物，如 JDBC 的 Statement.RETURN_GENERATED_KEYS、MyBatis 的 useGeneratedKeys——先插客户、再用它的 ID 建订单，就是靠这个串起来的。

列名清单是自我保护：不写列名（INSERT INTO t VALUES (...)）要求值与表列一一对应，表加一列整个语句就废了。永远显式写出列名。

5.2 UPDATE 与安全更新

-- 单行更新：主键定位
UPDATE product SET price = 349.00 WHERE id = 1;

-- 表达式更新：在原值基础上算（想加 10 元就写表达式，别先查后写）
UPDATE product SET price = price + 10 WHERE status = 1;

-- 多列一起改，还可以引用别的列
UPDATE product
SET price    = price * 0.9,
    stock    = stock - 1,
    updated_note = '双十一直降'
WHERE id = 2;

-- 跨表更新（EXISTS 写法，安全且直观）
UPDATE orders o
SET o.amount = o.amount * 0.95
WHERE EXISTS (SELECT 1 FROM customer c
              WHERE c.id = o.customer_id AND c.level = 'VIP');

UPDATE 是本书目前最危险的语句，两个保命习惯：

  1. 先 SELECT 后 UPDATE：把 WHERE 子句原封不动拿到 SELECT 里跑一遍，确认影响范围正确，再换成 UPDATE 执行；
  2. 开启安全更新模式：SET sql_safe_updates = 1; 之后不带 WHERE（或不带键列条件）的 UPDATE/DELETE 会被直接拒绝——命令行手滑的最后一道保险。
MySQL 8.0.31 之前的 UPDATE/DELETE 不支持 LIMIT 子句的某些场景且行为有版本差异；批量更新大表应按主键分批（每次几千行），一口气 UPDATE 千万行会造成长事务（第 35 章展开）。

5.3 DELETE 与软删除

DELETE FROM product WHERE id = 5;              -- 物理删除单行
DELETE FROM customer_archive WHERE created_at < '2020-01-01';  -- 按条件删

物理删除的问题：数据没了就真没了——误删、审计、恢复全都是灾难。所以业务表的标配是软删除：

  • 表上加 is_deleted TINYINT NOT NULL DEFAULT 0（或 deleted_at DATETIME NULL）；
  • "删除"变成 UPDATE t SET is_deleted = 1 WHERE id = ?;
  • 所有业务查询都补上 WHERE is_deleted = 0——这就是为什么第 4 章模板里要有这一列。
-- 软删
UPDATE customer SET is_deleted = 1 WHERE id = 4;

-- 业务查询统一过滤
SELECT id, name FROM customer WHERE is_deleted = 0;

-- 真想清数据时，由归档程序把 is_deleted = 1 且超过保留期的行搬走（第 61 章）
软删的隐藏成本：所有查询都要记得过滤标记，漏一处就"诈尸"；唯一索引也会把已删记录算进去（手机号唯一列上，删过的老用户挡住新注册）——常用解法是把唯一索引改成 (phone, is_deleted) 组合或在唯一列拼接 deleted_at。

5.4 冲突处理三兄弟对比

插入时撞上唯一键怎么办？三种策略，行为差异很大：

写法撞唯一键时的行为副作用
INSERT IGNORE静默忽略报错，旧行保留把"数据非法"等其他错误也一并吞掉，难排查
REPLACE INTO删掉旧行、插入新行自增 ID 变了；触发 DELETE 语义；关联数据成孤儿
ON DUPLICATE KEY UPDATE把指定列更新为给定值语义最明确，批量导入首选
 
-- 例：每日统计表，当天已有记录就累加
INSERT INTO daily_stats (stat_date, pv, uv)
VALUES ('2026-10-19', 1, 1)
ON DUPLICATE KEY UPDATE pv = pv + 1, uv = uv + 1;
记住一句话：IGNORE 慎用（吞错误），REPLACE 少用（删了重来），UPSERT（ON DUPLICATE KEY UPDATE）最常用。

5.5 常见坑清单

  • 坑UPDATE 漏 WHERE：全表被改。安全模式 + 先 SELECT 是双保险；
  • 坑字符串没加引号：WHERE name = 张三 会把"张三"当列名报 Unknown column；
  • 坑隐式类型转换：WHERE phone = 13800000001（数字没引号）在字符列上会导致索引失效（第 23 章）；
  • 坑UPDATE 影响 0 行不算错：matched 0 / changed 0 时要分清"没找到"还是"值没变"，应用层判断别只看是否抛异常。
