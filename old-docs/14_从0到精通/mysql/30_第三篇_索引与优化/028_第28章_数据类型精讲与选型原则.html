28.1 整数类型：够用就好

整数有五档，按取值范围挑最小的那档——省空间就是省 IO。

类型字节取值范围（有符号）典型用途
TINYINT1-128 ~ 127状态、布尔、类型码
SMALLINT2-3 万 ~ 3 万小计数
INT4约 ±21 亿普通计数
BIGINT8约 ±9.2×10¹⁸主键、海量计数
 
-- 状态码：TINYINT 足够（0/1/2 三值）
status TINYINT NOT NULL DEFAULT 0

-- 主键：统一 BIGINT UNSIGNED（无符号，上限翻倍）
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT

-- 注意：INT(n) 里的 n 只是"显示宽度"，不影响存储范围，8.0 已弱化
常见误区：INT(11) 的 11 不是范围、不是字节，只是 SELECT 时的显示宽度。8.0.17 之后整数的显示宽度已废弃，别再用它判断能存多大。

28.2 小数：钱必须用 DECIMAL

浮点数存钱，早晚会出对账不平的事故。

-- ❌ 错误：用 DOUBLE 存金额，二进制浮点有精度误差
amount DOUBLE;
-- 0.1 + 0.2 在浮点里不等于 0.3，对账时差几分钱

-- ✅ 正确：DECIMAL(精度, 小数位)，精确十进制
amount DECIMAL(12,2) NOT NULL;   -- 最多 12 位、其中 2 位小数 → 9999999999.99

原理：FLOAT/DOUBLE 是二进制浮点，无法精确表示 0.1 这类十进制小数，累加后误差放大；DECIMAL 是定点十进制，按字符串一样精确存，钱、利率、计费一律用它。

铁律：凡是和钱有关的列，一律 DECIMAL，FLOAT/DOUBLE 只用于科学计算、统计这类允许误差的场景。

28.3 字符串：CHAR / VARCHAR / TEXT

定长用 CHAR、变长用 VARCHAR、超长用 TEXT，别一律 VARCHAR(255)。

类型特点适用
CHAR(n)定长，不足补空格，最多 255长度固定：手机号(11)、性别、编码
VARCHAR(n)变长，按实际长度存 +1~2 字节长度前缀长度不定：姓名、标题、地址
TEXT最大 64KB，不能有默认值长文、评论、正文（副表）
 
-- 手机号固定 11 位：CHAR 定长更整齐
phone CHAR(11) NOT NULL

-- 用户名长度不定：VARCHAR
user_name VARCHAR(32) NOT NULL

-- 注意 VARCHAR(n) 的 n 是"字符数"不是字节数：
-- utf8mb4 下 VARCHAR(255) 最多占 255×4 = 1020 字节
VARCHAR 长度别贪大：长度是给索引/内存临时表算上限用的。VARCHAR(255) 让内存临时表按 255×4 字节分配，小查询也占大内存。按业务真实长度定（姓名 32、标题 100）。

28.4 时间类型：DATETIME 与 TIMESTAMP

两者都能存时间，关键差别在时区和范围。

-- DATETIME：范围 1000-01-01 ~ 9999-12-31，存"字面上的时间"，不带时区
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

-- TIMESTAMP：范围 1970 ~ 2038（2038 问题），存 UTC、按会话时区转换
-- 省空间（4 字节 vs DATETIME 8 字节），但有 2038 上限

-- 8.0.19+ 支持小数秒精度：
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
  ON UPDATE CURRENT_TIMESTAMP(3)   -- 毫秒级
维度DATETIMETIMESTAMP
范围1000 ~ 9999 年1970 ~ 2038 年
时区不带，字面时间UTC 存储，按时区显示
空间8 字节4 字节
推荐业务时间首选（无 2038 焦虑）跨时区、省空间时用
2038 问题：TIMESTAMP 到 2038-01-19 就溢出。新业务表的时间列直接用 DATETIME，别给十年后埋雷。

28.5 ENUM、JSON 与选型总表

两个"看起来很香"的类型，用之前先知道它们的坑。

-- ENUM：枚举，看起来整齐，但加值要 ALTER TABLE、排序按内部编号
status ENUM('待付款','已完成','已取消') NOT NULL DEFAULT '待付款'
-- 坑：插入写错值会变成空串；排序不是按中文而是按编号

-- 更推荐：TINYINT + 应用层字典
status TINYINT NOT NULL DEFAULT 0   -- 0待付款 1已完成 2已取消，灵活

-- JSON：8.0 对 JSON 优化很好，能建多值索引
extra JSON;
-- 适合半结构化数据（扩展字段），但高频查询字段别塞 JSON，要拆列
需求首选类型一句话理由
金额DECIMAL(12,2)精确，不浮点
状态码TINYINT够用、省 1 字节、可加值
主键BIGINT UNSIGNED短、自增、防溢出
固定长度字符串CHAR(n)整齐无长度前缀
变长文本VARCHAR(n) 按真实长度别一律 255
业务时间DATETIME无 2038 焦虑
半结构化扩展JSON8.0 支持索引
选型总原则：够用就好、能短不长、能精确别浮点、业务时间用 DATETIME——类型越省，索引越高效、IO 越省。

✓ 本章小结

要点一句话
整数按范围挑最小档；INT(n) 的 n 只是显示宽度，8.0 已废弃
金额永远 DECIMAL，FLOAT/DOUBLE 有浮点误差会对账不平
字符串定长 CHAR、变长 VARCHAR 按真实长度、长文 TEXT 放副表
时间业务首选 DATETIME（无 2038 问题）；TIMESTAMP 省空间但有上限
选型原则够用就好、能短不长、能精确别浮点
