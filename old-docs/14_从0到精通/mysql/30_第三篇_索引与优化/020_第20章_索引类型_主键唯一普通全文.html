20.1 主键索引：聚簇索引

InnoDB 的表是"按主键组织的 B+ 树"——这就是聚簇（clustered）两个字的含义。

一张 InnoDB 表只有一个聚簇索引，它就是主键。说"聚簇"是因为：表数据本身就按主键顺序存在 B+ 树的叶子节点里，数据和索引是一体的——按主键查一行，走到叶子就直接拿到整行，没有"回表"这一步。

CREATE TABLE user_profile (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name       VARCHAR(32)     NOT NULL,
  phone      VARCHAR(20)     NOT NULL,
  created_at DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id)               -- 主键 = 聚簇索引，叶子存整行数据
) ENGINE=InnoDB;

-- 按主键查：一次走到叶子页，直接读出整行
SELECT * FROM user_profile WHERE id = 1024;

两个连带规则，面试和建表都会碰到：

  • 没显式建主键：InnoDB 会挑第一个非空唯一索引当聚簇索引；都没有，就偷偷生成一个 6 字节的隐藏主键——这也是为什么 DBA 强制要求"每张表必须显式建自增主键"；
  • 主键尽量短且单调递增：主键值会被所有二级索引的叶子携带（第 22 章），越长二级索引越胖；自增主键顺序插入，避免页分裂（第 27 章细讲）。
MyISAM 的对照：MyISAM 里数据和索引是分开存的，主键索引叶子存的是"行的物理地址"，不是整行。理解这一点，就理解了为什么"InnoDB 表即索引组织表"这句话是 InnoDB 优化思想的根基。

20.2 唯一索引：加速 + 约束二合一

唯一索引是"免费"的约束：既保证列不重复，又能当查询入口。

唯一索引（UNIQUE）在结构上也是一棵 B+ 树，额外语义是不允许出现两行键值相等。写入时引擎要先在 B+ 树里查一遍有没有相同的键——正因为查了，它天然就是一个可用的查询索引。

-- 建表时声明唯一键
CREATE TABLE account (
  id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  email VARCHAR(128)    NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_email (email)      -- 唯一索引：email 不重复 + 可按 email 查
) ENGINE=InnoDB;

-- 事后补建
ALTER TABLE account ADD UNIQUE KEY uk_email (email);

-- 重复值写入会被直接拒绝（Duplicate entry）
INSERT INTO account (email) VALUES ('a@x.com');
INSERT INTO account (email) VALUES ('a@x.com');   -- ERROR 1062

三个容易答错的细节：

  1. NULL 可以出现多次：NULL 不等于 NULL，唯一索引允许多个 NULL（这在"手机号可空"的表里很常见）；
  2. 唯一索引比普通索引写起来略贵：写入都要查重，但读路径几乎一样快；业务上"能唯一就唯一"，约束价值远大于那点写入成本；
  3. 建唯一索引前先查重复数据：表上已有重复值时，ADD UNIQUE 会直接失败，得先清洗。
唯一索引是 DBA 最爱用的索引：一行 DDL，同时买到"数据正确性"和"查询性能"。

20.3 普通二级索引与建索引 DDL

除了主键之外的所有索引，都叫二级索引（Secondary Index），叶子存的是"索引列值 + 主键值"。

普通索引没有唯一约束语义，纯粹为查询服务。一张表可以建任意多个二级索引，但每个索引都要占存储、拖慢写入（INSERT/UPDATE/DELETE 都要同步维护这些树），所以"按需建、宁少勿多"。

-- 方式一：CREATE INDEX
CREATE INDEX idx_user_city ON user_profile (city);

-- 方式二：ALTER TABLE（推荐，语义明确）
ALTER TABLE user_profile ADD INDEX idx_user_city (city);

-- 查看表上所有索引：键名、列、顺序、唯一性一目了然
SHOW INDEX FROM user_profile;

-- 删索引
ALTER TABLE user_profile DROP INDEX idx_user_city;
-- 或：DROP INDEX idx_user_city ON user_profile;
索引类型叶子节点存什么附加约束典型用途
主键索引（聚簇）完整行数据非空且唯一，全表一个按 id 直取整行
唯一索引索引列值 + 主键值键值不重复邮箱/手机号登录查询
普通索引索引列值 + 主键值无常用筛选列（city、status）
全文索引倒排索引（非 B+ 树）无大段文本的关键词检索
MySQL 8.0 建大表索引默认走在线 DDL（ALGORITHM=INPLACE、LOCK=NONE），不阻塞读写；但 8.0 之前或特殊场景仍可能锁表。给千万级表加索引，务必在低峰期并先测 `pt-online-schema-change` 之类方案（第 55 章）。

20.4 前缀索引：给长字符串建索引

VARCHAR(255)、TEXT 整列建索引太胖，只索引前 N 个字符——这就是前缀索引。

文章内容、URL、JSON 串这类长文本，整列建索引会让 B+ 树的键又大又长，扇出下降、树变高（第 19 章的代价）。做法是只索引列的前若干字符：

-- 只索引 email 的前 20 个字符
ALTER TABLE account ADD INDEX idx_email_prefix (email(20));

-- 怎么选前缀长度？看"区分度"：长度 L 下不重复值的比例尽量接近整列
SELECT
  COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS sel10,
  COUNT(DISTINCT LEFT(email, 20)) / COUNT(*) AS sel20,
  COUNT(DISTINCT email)           / COUNT(*) AS sel_full
FROM account;
-- 原则：找那个"再加几个字符区分度几乎不再涨"的拐点
前缀索引的两个代价：一是排序与 ORDER BY 用不上它（前缀无法确定完整顺序）；二是覆盖索引失效（第 22 章）——索引里没有完整列，查询永远要回表。它只适合"等值/前缀匹配检索"，不适合要排序的列。

20.5 全文索引与中文分词

LIKE '%keyword%' 对大文本是全表扫描，全文索引（FULLTEXT）才是正解。

全文索引不是 B+ 树，而是倒排索引：把文本拆成词，记录"每个词出现在哪些行"。MySQL 8.0 的 InnoDB 原生支持 FULLTEXT，配合 WITH PARSER ngram 才能正确处理中文（中文没有空格分词）。

-- 建带中文分词的全文索引（ngram 按字符切分，默认 2 元分词）
ALTER TABLE article
  ADD FULLTEXT INDEX ft_title_body (title, body) WITH PARSER ngram;

-- 中文分词器参数：ngram_token_size 默认 2
SHOW VARIABLES LIKE 'ngram_token_size';

-- 用 MATCH ... AGAINST 检索，不用 LIKE
SELECT id, title
FROM article
WHERE MATCH(title, body) AGAINST('数据库 索引' IN NATURAL LANGUAGE MODE);

-- 布尔模式：+必须包含 -必须排除
SELECT id FROM article
WHERE MATCH(title, body) AGAINST('+B+树 -二叉树' IN BOOLEAN MODE);
方式LIKE '%kw%'FULLTEXT + ngram
底层结构B+ 树，但前导通配无法走索引倒排索引
大表性能全表扫描，百万行秒级毫秒级
中文支持按字节匹配，可用但慢ngram 分词，专业检索
适用场景小表、模糊匹配少量使用站内搜索、文章检索
什么时候不上 MySQL 全文索引：数据量百万级以上、要相关度排序、多字段聚合搜索时，专业方案是 Elasticsearch（第 66 章）。MySQL FULLTEXT 是"轻量够用"，不是"检索终局"。

✓ 本章小结

要点一句话
聚簇索引主键即数据组织方式，叶子存整行；每表一个，务必显式自增主键
唯一索引同时是约束与查询入口；允许多行 NULL；建前先清重复数据
普通二级索引叶子存"索引列+主键值"；按需建，写入有维护成本
前缀索引按区分度选长度；省空间但失去排序与覆盖能力
全文索引倒排索引 + ngram 中文分词；百万级以上交给 Elasticsearch

✎ 本章习题

A 基础给 user_profile 的 phone 列建唯一索引，再故意插入两条相同手机号，记录报错编号与信息；最后用 SHOW INDEX FROM user_profile; 观察索引的列名与 Non_unique 值。
B 进阶在一张含 VARCHAR(255) URL 列的表上，用区分度查询找出"足够区分又最省空间"的前缀长度，并把这个长度写进 ADD INDEX url(n) 建前缀索引；再思考为什么这条索引不能用于 ORDER BY url。
C 挑战建一张 article 表（title、body），灌入 20 条测试文章，给 (title, body) 建带 ngram 的 FULLTEXT 索引，分别用 LIKE '%索引%' 与 MATCH ... AGAINST 检索同一个词，对比返回结果与执行计划差异。
