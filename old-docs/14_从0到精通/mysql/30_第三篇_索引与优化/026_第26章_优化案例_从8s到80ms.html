26.1 案发：一条 8 秒的订单列表查询

业务场景：运营后台按用户查订单列表，按时间倒序翻页，一页 20 条。

-- 表结构（简化）：订单表 1000 万行
CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id     BIGINT UNSIGNED NOT NULL,
  status      TINYINT         NOT NULL,          -- 1待付款 2已完成 3已取消
  amount      DECIMAL(12,2)   NOT NULL,
  created_at  DATETIME        NOT NULL,
  PRIMARY KEY (id)
  -- （初期）除主键外，没有任何二级索引！
) ENGINE=InnoDB;

-- 出事的 SQL：运营后台"我的订单"列表
SELECT * FROM orders
WHERE user_id = 10086 AND status = 2
ORDER BY created_at DESC
LIMIT 50000, 20;          -- 翻到深页

业务反馈：列表页打开要 8 秒多，越往后翻越慢。慢日志把它记了下来——这就是第 25 章定位到的那条 SQL。

26.2 第一步 EXPLAIN：问题出在哪

先别动手，让 EXPLAIN 告诉你病根。

EXPLAIN SELECT * FROM orders
WHERE user_id = 10086 AND status = 2
ORDER BY created_at DESC
LIMIT 50000, 20;

-- 优化前输出：
-- type: ALL              ← 全表扫描！1000 万行
-- possible_keys: NULL    ← 没有任何索引可选
-- key: NULL              ← 一个索引都没用上
-- rows: 10000000         ← 估算要扫 1000 万行
-- Extra: Using where; Using filesort
--                              ↑ 还要额外排序

病根一目了然：没索引（key=NULL）+ 全表扫（type=ALL）+ 额外排序（filesort）。1000 万行里捞某个用户的几百条，还要全表扫一遍再排一遍——8 秒就是这么来的。

图 26-1 一条订单列表查询的优化全程：8.2 秒 → 76 毫秒，提速约 108 倍

26.3 第二步：加联合索引

WHERE 是 user_id + status 等值，ORDER BY 是 created_at——按第 21 章列序原则设计。

-- 设计：等值列 user_id、status 在前，排序列 created_at 垫底
ALTER TABLE orders
  ADD INDEX idx_user_status_time (user_id, status, created_at);

-- 加完索引再 EXPLAIN：
-- type: ref                ← 终于走索引了
-- key: idx_user_status_time ← 用上了
-- rows: 几百                ← 扫的行数从 1000 万降到几百
-- Extra: Using where; Using index condition

这一步直接把 8.2 秒砍到约 1.5 秒——全表扫没了，定位到这个用户已完成的几百条订单。但 ORDER BY created_at 的 filesort 还在（索引虽然带了 created_at，但 LIMIT 深分页仍要排序翻找），而且 SELECT * 还在逐行回表。

26.4 第三步：消除 filesort 与回表

索引已经把 user_id+status 等值锁定，created_at 也在索引里有序——为什么还在排序？

-- 问题在 SELECT *：索引里只有 user_id, status, created_at, 主键
-- 你要 *（全部列），所以索引不能覆盖，要回表；
-- 而且深分页 LIMIT 50000,20 要先在索引里数过 5 万行再取 20 行

-- 改造 1：列表页只查真正需要的列（别 SELECT *）
SELECT id, user_id, status, amount, created_at
FROM orders
WHERE user_id = 10086 AND status = 2
ORDER BY created_at DESC
LIMIT 20;
-- 浅分页时：(user_id, status, created_at) 取出即按时间有序，filesort 消失
索引带排序列的价值：WHERE 等值锁定后，索引叶子本身就按 created_at 有序——取出即排序，filesort 自然消失。

26.5 第四步：延迟关联治深分页

真正把 1.5 秒砍到 76 毫秒的，是深分页改造。

-- 慢：LIMIT 50000,20 要先在索引里数过 5 万行、再回表取整行
SELECT * FROM orders
WHERE user_id = 10086 AND status = 2
ORDER BY created_at DESC
LIMIT 50000, 20;

-- 快：延迟关联。先在覆盖索引上只取这 20 个主键，再回表
SELECT t.* FROM orders t
JOIN (
  SELECT id FROM orders
  WHERE user_id = 10086 AND status = 2
  ORDER BY created_at DESC
  LIMIT 50000, 20
) AS tmp ON tmp.id = t.id;

-- 优化后 EXPLAIN：
-- 子查询：type=ref，只在索引上取 20 个 id（Using index，不回表）
-- 外层：type=eq_ref，按 20 个 id 回表取整行（只回 20 次）
-- 总耗时：76 毫秒
阶段typerows耗时
优化前ALL1000 万8.2 s
加联合索引ref几百1.5 s
消除 SELECT *ref几百0.4 s
延迟关联ref + eq_ref≈2076 ms
复盘三句话：①没索引先加匹配 WHERE 的联合索引（等值在前、排序垫底）；②杜绝 SELECT *，让列表查询走覆盖索引；③深分页用延迟关联，回表次数 = 一页行数。

✓ 本章小结

要点一句话
先 EXPLAINtype=ALL、key=NULL、filesort 是三大病根，先看清再动手
联合索引等值列在前、排序列垫底，一次解决筛选 + 排序
杜绝 SELECT *只查需要的列，让索引覆盖、减少回表
延迟关联深分页先在覆盖索引上取主键、再回表，回表次数压到一页
优化节奏每加一步都跑 EXPLAIN + 计时，对比前后 rows 与耗时
