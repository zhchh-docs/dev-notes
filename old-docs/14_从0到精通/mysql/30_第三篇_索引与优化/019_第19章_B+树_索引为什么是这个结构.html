19.1 从磁盘 IO 说起：为什么不能用二叉树

索引不是为了"算得快"，而是为了"少读几次盘"。结构设计的全部约束都来自这一句话。

先把数量级摆出来：内存一次随机访问约 100 纳秒，机械磁盘一次随机读约 10 毫秒，两者相差 十万倍；SSD 随机读虽然快到几十微秒，但仍然比内存贵上千倍。数据库的数据长期放在磁盘上，查询要做的事就是把"要读的磁盘块"压到最少。

二叉搜索树、AVL、红黑树这类"瘦高"结构的问题就在这里：每个节点只放一个关键字，N 行数据的树高约为 log₂N。一张 1 亿行的表，树高约 27——最坏情况下一次查询要走 27 个节点，而每个节点都在磁盘不同位置，就是 27 次随机 IO，按机械盘算是 0.3 秒起步，完全不可接受。

-- 感受一下量级：1 亿行 = 100,000,000，log2(N) ≈ 26.6
-- 二叉树：最坏 27 次磁盘 IO
-- B+ 树（多路）：每页放约 1000 个键，log(1000, N) ≈ 2.7 → 3 次 IO 封顶

结论朴素而硬核：要让树"矮胖"——每个节点存很多关键字，一次磁盘读（一个页）就能拿到成百上千个键，靠"扇出"把树高压到 3~4 层。这就是多路平衡搜索树（B 树家族）的设计动机。

为什么节点要等于"页"：InnoDB 读写磁盘的最小单位不是行，而是页（Page），默认 16KB。索引节点直接对齐一个页，读一次盘就把整个节点读进内存——IO 次数=树高，一次都不浪费。

19.2 B 树与 B+ 树：差的那三刀

B 树已经是多路平衡树，但 MySQL 最终选了它的变种 B+ 树。三处改造，每一处都对应一个真实业务痛点。

B 树（Balanced Tree）的每个节点既存关键字、也存完整数据，找到键就停。它比二叉树矮得多，但还有三个问题：数据散落在各层节点里，每个节点存的数据一多，单页能放的关键字就变少，扇出上不去，树又变高了；范围查询要在树里中序遍历、来回回溯；节点不连在一起，顺序扫描没保障。

维度B 树B+ 树（InnoDB）
数据存放位置每个节点都存键 + 数据数据只存叶子节点，非叶子节点只存键
扇出（单页键数）小（数据占地方）大（非叶子页只放键与指针，可达上千）
范围查询需中序遍历，回溯父节点叶子节点双向链表相连，找到起点后一路向右扫到底
查询稳定性键在非叶子就可能提前命中，耗时不稳定一律走到叶子，任意查询路径等长，性能稳定
B+ 树的精髓：非叶子"只指路、不装货"，叶子"装货且手拉手"。树更矮、范围更快、查询耗时更稳。

19.3 解剖一棵 InnoDB B+ 树

把一棵真实的 B+ 树摆在眼前：根页、内部页、叶子页，各存什么、怎么连，一次查询走哪条线。

图 19-1 一棵三层 B+ 树：非叶子页只存键与指针，叶子页存完整数据行并双向相连

三个零件逐个说：

  • 关键非叶子节点（内部页）：只存"键 + 指向子页的指针"。一个页 16KB，主键按 BIGINT（8 字节）算，加页指针约 6 字节，单页能装 上千个键——这就是扇出。
  • 关键叶子节点：聚簇索引（主键）的叶子直接存完整行数据；二级索引的叶子存"索引列值 + 主键值"（第 20、22 章展开回表）。
  • 关键双向链表：相邻叶子页用 prev/next 指针串起来，且页内键值有序。BETWEEN、ORDER BY、> 这类范围条件，找到起点后顺着链表扫即可，不用回树。
-- 查看 InnoDB 页大小（默认 16384 = 16KB）
SHOW VARIABLES LIKE 'innodb_page_size';

-- 建一张演示表，主键即聚簇索引
CREATE TABLE bpt_demo (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(32) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

-- root 页常驻在内存缓冲池里，所以绝大多数查询实际只走 2 次磁盘 IO

19.4 树高与千万行：为什么三层层级能存上亿行

做一道除法题，你就理解为什么 DBA 说"B+ 树一般不会超过 4 层"。

粗算一遍：非叶子页扇出约 1000（保守取 1200），叶子页按行均长 1KB 算、一页约放 16 行（保守，实际紧凑行能到上百行）。

-- 高度估算（粗算）
-- 第 1 层（根）：1 页，指向 1000 个内部页
-- 第 2 层（内部）：1000 页 × 每页再分 1000 → 指向 100 万个叶子页
-- 第 3 层（叶子）：100 万页 × 每页约 100 行 ≈ 1 亿行
-- 结论：树高 3 层，装 1 亿行；一次主键查询 = 2~3 次 IO

这就是为什么千万级、甚至上亿行的表，按主键查一行仍然飞快——数据量翻 100 倍，树只多一层。也解释了两个日常现象：往表上插数据为什么不会让查询越来越慢（树高基本不变）；为什么联合索引的列不宜太多（索引页同样是 16KB，列越多、单页能放的键越少，扇出下降、树变高，第 21 章细讲）。

主键查一行 = 2~3 次磁盘 IO，这就是 B+ 树给千万级表开出的"便宜"。

19.5 为什么不用哈希索引

哈希表等值查找 O(1)，比 B+ 树还快，为什么 InnoDB 不拿它当默认？

哈希索引确实是等值查询的天花板：算一次哈希值直接定位。但它有三个硬伤，恰好全踩在业务 SQL 的痛点上：

  1. 不支持范围查询：哈希打散后，连续键值在物理上乱序，WHERE age > 20 无从下手；
  2. 不支持排序与最左前缀：ORDER BY、联合索引左侧匹配（第 21 章）全部失效；
  3. 不支持部分列匹配：LIKE 'abc%' 这类前缀扫描做不了。

MySQL 中哈希索引真实存在于 MEMORY 引擎，以及 InnoDB 的自适应哈希索引（AHI）——引擎监测到某些索引值被频繁等值访问时，自动为其在内存中建哈希，无需人工干预。

-- 查看自适应哈希索引是否开启（默认 ON，由引擎自控）
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';

-- 注意：CREATE INDEX 建不出哈希索引；USING HASH 仅适用于 MEMORY 引擎
常见误解："B+ 树比哈希快"——错。等值点查哈希更快，但业务里大量是范围、排序、联合条件，InnoDB 选择"全能的 B+ 树"，再用 AHI 把热点等值查询加速补回来。

✓ 本章小结

要点一句话
索引的本质减少磁盘 IO；节点对齐 16KB 页，一次盘读拿整页
为什么不用二叉树瘦高，1 亿行要走 27 层 ≈ 27 次随机 IO，不可接受
B+ 树三刀非叶子只存键（扇出大）、数据只在叶子、叶子双向链表
树高扇出约 1000，3 层存约 1 亿行；主键查询 = 2~3 次 IO
哈希索引只擅长等值；不支持范围/排序/最左前缀，靠 AHI 内存加速补位
