23.1 列上套函数或运算

索引存的是列的原始值；你对列套了函数，等于让索引存的值"对不上"查询条件。

-- ❌ 失效：对索引列套函数，索引值无法直接匹配
SELECT * FROM user WHERE DATE(created_at) = '2026-10-23';
SELECT * FROM user WHERE YEAR(created_at) = 2026;
SELECT * FROM orders  WHERE id + 1 = 100;        -- 列上做运算
SELECT * FROM user WHERE LEFT(name, 3) = '张';

-- ✅ 改写：把运算挪到右边，左边保持原始列
SELECT * FROM user
WHERE created_at >= '2026-10-23 00:00:00'
  AND created_at <  '2026-10-24 00:00:00';

SELECT * FROM orders WHERE id = 99;              -- 别写 id+1=100

为什么套函数就失效？B+ 树按 created_at 原始值排序；你要查的是"created_at 转成日期后等于某天"——树里存的是带时分秒的时间戳，没法直接和"2026-10-23"对齐，只能逐行算 DATE() 再比，退化为全表扫描。

铁律：索引列永远裸放在左边，任何函数、运算、类型转换都堆到常量那一侧去。

23.2 隐式类型转换（最隐蔽的坑）

列是字符串、你给了数字——MySQL 悄悄帮你转类型，代价是索引失效。

-- phone 是 VARCHAR，但 WHERE 里写成了数字（没加引号）
SELECT * FROM user WHERE phone = 13800000001;   -- ❌ 失效

-- MySQL 实际执行的是：把每一行 phone 转成数字再比较
-- WHERE CAST(phone AS UNSIGNED) = 13800000001
-- 等价于对索引列套了函数 → 索引失效，全表扫

-- ✅ 给字符串列正确加引号
SELECT * FROM user WHERE phone = '13800000001';  -- ✅ 走索引

这条坑为什么最隐蔽？因为 SQL 不报错、结果也正确——它只是慢。你在命令行看不出任何异常，只有 EXPLAIN 的 type 列变成 ALL（全表扫）才暴露。第 5 章提过的"隐式类型转换导致索引失效"，根因就在这。

列类型错误写法正确写法
VARCHAR phonephone = 13800000001phone = '13800000001'
VARCHAR codecode = 10086code = '10086'
INT ageage = '25'（一般能走，但建议对齐）age = 25
记住：字符串列一定要带引号。隐式转换不报错但慢，是线上最昂贵的"沉默的错误"。

23.3 LIKE 前导通配符与 OR

两个书写习惯，让 LIKE 和 OR 把索引直接废掉。

-- ❌ 前导通配符：% 开头，索引无从下手
SELECT * FROM user WHERE name LIKE '%三';        -- 全表扫

-- ✅ 前缀匹配：% 在右边，能用索引
SELECT * FROM user WHERE name LIKE '张%';         -- 走 idx_name

-- ❌ OR 两边有一个列没索引 → 整句退化为全表扫
SELECT * FROM user WHERE city = '成都' OR age = 25;  -- age 没索引

-- ✅ 两个条件各自有索引，OR 才可能走索引合并（index_merge）
-- 或改写为 UNION ALL 分别走两条索引再合并
SELECT * FROM user WHERE city = '成都'
UNION ALL
SELECT * FROM user WHERE age = 25 AND city <> '成都';

LIKE '%xx%'（两头都通配）在 B+ 树里永远没法定位起点——前缀索引只支持"从左开始确定"。要做大段文本模糊检索，回到第 20 章的 FULLTEXT 全文索引，别指望普通 B+ 树。

MySQL 8.0 对 OR 的优化比 5.x 智能（能做 index_merge 索引合并），但仍不如"两条独立索引 + UNION"稳定可靠。OR 涉及的列越多，越要逐个检查有没有索引。

23.4 违反最左前缀与范围断档

前两章已经讲透，这里作为失效清单的一员汇总——它们不是"语法错"，是"索引用错"。

-- 联合索引 idx_city_age(city, age)

-- ❌ 跳过最左列
WHERE age = 25                       -- 不知道 city 是哪个，失效

-- ❌ 范围列右边断档（idx(city, age, name)）
WHERE city='成都' AND age>25 AND name='王五'
--  name 无法用索引（第 21 章），但 city、age 仍能走

-- ❌ != / NOT IN / IS NOT NULL：通常让优化器放弃索引
WHERE status != 1                    -- 大部分情况全表扫

把这一节和第 21 章对照看：失效不是"索引坏了"，是你的查询条件没按索引的排序逻辑来。

23.5 优化器主动放弃索引

有些时候"不走索引"不是写错了，而是优化器算过账，全表扫更便宜——这不是 bug，是明智。

-- 一张 100 万行的表，gender 只有 男/女 两个值
SELECT * FROM user WHERE gender = '男';   -- 全表扫，优化器没看错

-- 原理：男占 50% = 50 万行。走索引要回表 50 万次，
-- 还不如直接顺序全表扫一遍（顺序 IO 比随机回表便宜）。
场景原因怎么办
低选择性列（gender、status）命中行数占比过大，回表比全表扫还贵别在这种列上单独建索引
小表（几百行）全表扫本来就很快不必加索引
统计信息过期优化器估算行数严重失真ANALYZE TABLE t 更新统计
用了索引却仍慢命中太多行、回表太多覆盖索引 / 延迟关联
 
-- 统计信息失真时：手动刷新，让优化器重新估算
ANALYZE TABLE user;

-- 万不得已强制走某个索引（只是临时排查手段，不是方案）
SELECT * FROM user FORCE INDEX(idx_city) WHERE city = '成都';
"索引失效"分两种：你的 SQL 写错了（函数/隐式转换/最左前缀）要改写；优化器主动弃索引（低选择性）要从设计上解决——后者不是病。

✓ 本章小结

要点一句话
函数/运算索引列永远裸放左边，运算挪到常量侧
隐式转换字符串列忘加引号 = 对列套 CAST，不报错但全表扫
LIKE / OR前导通配符、OR 含无索引列，都会废掉索引
最左前缀跳左列、范围断档、!= 都会让索引用不上
主动弃索引低选择性列命中太多行时，全表扫反而更便宜
