第 27 章 表设计规范与反范式权衡

教科书 第 27 章 / 共 72 章 · 预计 35 分钟

好表是优化出来的底子。三范式要遵守，但互联网高并发场景又常要"反范式"——冗余几个字段换查询不 JOIN。本章给出一套可落地的建表规范：主键、字符集、NOT NULL、命名、大字段垂直拆分，以及什么时候该故意冗余。

◆本章目标

  • 理解三范式的核心：每张表只说一件事，消除冗余更新异常；
  • 掌握一套可落地的建表规范（主键、NOT NULL、必备字段）；
  • 会用垂直拆分把大字段（TEXT/BLOB）从主表剥离；
  • 判断什么时候该反范式（故意冗余）换取查询性能；
  • 统一命名与字符集规范，避免团队协作踩坑。

27.1 三范式：先守住底线

范式不是教条，是防止"改一处漏三处"的设计底线。

  • 第一范式（1NF）：每列原子不可再分。别在一个 address 列里塞"省+市+区"，拆开成 province/city/district；
  • 第二范式（2NF）：每张表只描述一件事。订单表里别塞收货地址快照的冗余字段，地址归地址表；
  • 第三范式（3NF）：列不依赖其他非主键列。"学生表"里别同时存系名（系名只跟系 ID 有关，跟学生是传递依赖）。
范式解决的是更新异常：冗余会让"改学生的系"要同时改学生表和系表，漏改一处数据就自相矛盾。先守住范式，再谈要不要为性能妥协。

27.2 建表通用规范

一套线上表模板，照着建基本不出错。

CREATE TABLE biz_order (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  -- 业务字段…
  status       TINYINT         NOT NULL DEFAULT 0      COMMENT '状态',
  -- 三必备审计列：谁、什么时候、改没改
  created_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  is_deleted   TINYINT         NOT NULL DEFAULT 0      COMMENT '软删标记(第5章)',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
  • 关键主键：BIGINT UNSIGNED 自增。短、单调递增、避免页分裂（第 19 章）；
  • 关键字段尽量 NOT NULL：NULL 让索引、比较、统计都变复杂，占额外位，业务上能给默认值就给；
  • 关键必带 created_at / updated_at / is_deleted：排查与软删的基础（第 5 章）；
  • 点每个字段写 COMMENT：半年后你自己会感谢现在写注释的自己。

27.3 大字段与垂直拆分

TEXT/BLOB 这类大列别跟高频列挤一张表——它们会拖慢整页的缓存效率。

-- 反例：主表塞了 content（长文），每次查列表都带着它
CREATE TABLE article (
  id    BIGINT,
  title VARCHAR(100),
  content TEXT,        -- 长文，占几 KB 到几 MB
  PRIMARY KEY (id)
);

-- 正例：垂直拆分。高频列留主表，大字段拆到副表
CREATE TABLE article (
  id    BIGINT,
  title VARCHAR(100),
  PRIMARY KEY (id)
);
CREATE TABLE article_content (
  article_id BIGINT,
  content    TEXT,
  PRIMARY KEY (article_id)   -- 与主表同主键，按需 JOIN
);

为什么？InnoDB 按 16KB 页缓存，一行里有大字段会让一个页塞的行数变少、缓冲池利用率下降。列表查询（只要 title）本可以很轻，却被 content 拖着每次回表读大页。拆开后，列表页只碰小主表，读正文才去副表。

经验值：单行平均长度超过 1KB、或有 TEXT/BLOB 的表，做垂直拆分。冷热分离，主表轻装上阵。

27.4 反范式：该冗余就冗余

范式守到底，JOIN 会多到性能扛不住——关键查询场景要故意冗余。

经典例子：订单列表页要显示"用户名"。范式做法是 orders 存 user_id，列表 JOIN user 表拿名字。但订单是千万级、列表是高频接口，每次 JOIN user 表代价高。反范式做法：在 orders 里冗余一份 user_name 快照。

-- 反范式：订单表冗余用户名（建订单时写死快照）
CREATE TABLE orders (
  id         BIGINT,
  user_id    BIGINT,
  user_name  VARCHAR(32) NOT NULL,   -- 冗余：下单时的用户名快照
  amount     DECIMAL(12,2)
);

-- 好处：列表查询不用 JOIN user，直接拿 user_name
-- 代价：用户改名后，历史订单里的快照不变（但这正是"订单快照"想要的语义）
权衡范式（不冗余）反范式（冗余）
查询要 JOIN，慢免 JOIN，快
写一次写冗余字段要同步更新
数据一致性永远一致可能不一致（改名场景）
适用一致性要求高读多写少的高频列表
反范式不是偷懒，是"用写的代价换读的性能"——专门花在读多写少、JOIN 昂贵的高频查询上，并接受冗余字段是"快照"语义。

27.5 命名与字符集规范

这些小事决定团队协作的摩擦成本。

  • 点表名/列名小写 + 下划线：order_item 不是 OrderItem（跨平台大小写敏感不同，统一小写最安全）；
  • 点不用 MySQL 保留字：别把列取名 order、desc、status 勉强可以但 order 是致命的，用 order_no、order_status 绕过；
  • 关键字符集统一 utf8mb4：MySQL 的 utf8 是残缺的（最多 3 字节，存不了 emoji 和生僻字），utf8mb4 才是真 UTF-8，默认用它；
  • 关键排序规则 utf8mb4_0900_ai_ci（8.0 默认）：ai=不区分重音、ci=不区分大小写。
线上最常见的字符集坑：建表时用了默认 latin1 或残缺 utf8，存中文变乱码。新表一律显式 DEFAULT CHARSET=utf8mb4，别依赖默认值。
表设计的总原则：先守范式保正确，再按高频查询反范式换性能；主键短、字段省、大字段拆、字符集统一——这些底子打好，后面索引、锁、主从都省心。
范式 vs 反范式没有绝对答案：互联网读多写少，普遍偏反范式（冗余快照）；金融、对账系统写少、一致性要求高，普遍偏范式。判断依据永远是"这条表的读写比例与一致性要求"。
主键首选 BIGINT 自增：有序插入让 B+ 树叶子页顺序写、页分裂少；UUID 虽然全局唯一，却会随机插入导致频繁页分裂、二级索引也更大，除非有分布式分库需求，否则别用 UUID 当主键。
