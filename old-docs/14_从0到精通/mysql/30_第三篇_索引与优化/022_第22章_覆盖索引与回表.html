第 22 章 覆盖索引与回表

22.1 回表：二级索引为什么要查两次

二级索引的叶子存的不是整行，而是"索引列值 + 主键值"——拿主键再去聚簇索引取整行，这一跳就是回表。

回顾第 20 章：普通索引 idx_city(city) 的叶子节点，每条记录存的是 ('成都', 主键 id=1001)。当执行 SELECT * FROM user WHERE city='成都' 时：

  1. 在 idx_city 的 B+ 树里定位到 city='成都' 的叶子页，读出一堆主键值（1001、1008、1033……）；
  2. SELECT * 要 name、phone、age 等整行，这些列不在二级索引里，只能拿每个主键值回聚簇索引（主键 B+ 树）再查一次；
  3. 每回一次表 = 多一次 B+ 树查找。命中 1000 行 = 1000 次随机回表，这就是慢的根源。

22.2 覆盖索引：一次索引查询就拿全所有列

如果查询要的列，索引叶子里全都有，就不用回表了——这叫覆盖索引（Covering Index）。

二级索引的叶子天然存了"索引列 + 主键"。所以只要 SELECT 的列、WHERE 用到的列，加起来都 ≤ 索引列，引擎读完索引叶子就齐活，连聚簇索引都不用碰。

-- 索引：idx_city_age (city, age)
SELECT city, age FROM user WHERE city = '成都' AND age = 25;
--  ↑索引要的列 = city、age，索引叶子里全有 → 不回表

SELECT * FROM user WHERE city = '成都';
--  ↑还要 name、phone……索引里没有 → 每行都回表
覆盖索引的本质：把要查的列"塞进"联合索引里，让索引叶子 = 查询结果的全部数据，回表归零。

实战技巧：给高频查询建联合索引时，把 WHERE 列 + 真正会 SELECT 的列 一起排进去。比如列表页只要显示用户名和城市，idx_city_name(city, name) 就顺手覆盖了"按城市筛、取名称"这条查询。

22.3 EXPLAIN 里的 Using index

EXPLAIN 的 Extra 列直接告诉你有没有回表——这是你判断覆盖索引的唯一权威依据。

-- 覆盖索引命中：Extra 显示 Using index
EXPLAIN SELECT city, age FROM user WHERE city = '成都';
-- Extra: Using index   → 索引覆盖，没回表，性能拉满

-- 非覆盖：Extra 只有 Using where（没有 Using index）
EXPLAIN SELECT * FROM user WHERE city = '成都';
-- Extra: Using where   → 走了索引但逐行回表

-- 配合 ICP 的形态：Using index condition 仍可能回表，要区分（第 21、24 章）
Extra 关键值含义回表
Using index索引覆盖，查询列全在索引里不回表
Using index condition索引下推，断档列在引擎层先筛只对命中行回表
Using whereServer 层再过滤，可能逐行回表按命中行回表
记法：Extra 里出现 Using index（不带 condition）才是教科书式覆盖索引；只要出现回表的迹象，rows 乘以回表成本就是这条查询的真实开销。

22.4 为什么杜绝 SELECT *

SELECT * 会把"所有列"都变成回表触发条件，直接扼杀覆盖索引。

很多人图省事写 SELECT *，对覆盖索引是灾难：你原本只要 name、city 两列，建了 (city, name) 能覆盖；一旦 SELECT *，还要 phone、age、email……索引里没有，只能全部回表，再好的联合索引都白搭。

-- 反面：要 10 列，索引只能覆盖 2 列 → 8 列要回表
SELECT * FROM user WHERE city = '成都';

-- 正面：只写真正用到的列，让索引刚好覆盖
SELECT name, city FROM user WHERE city = '成都';
生产规范：永远不写 SELECT *。列名显式列出，既避免回表，又防止表结构加列后应用读到多余数据、还能利用覆盖索引——一举三得。

22.5 延迟关联：深度分页的回表优化

LIMIT 100000, 20 为什么慢？因为它要先回表捞出 10 万行、再丢掉 99980 行。

-- 慢：深分页。回表取前 10 万行，再往后翻 20 行
SELECT * FROM user
WHERE city = '成都'
ORDER BY id
LIMIT 100000, 20;

-- 快：延迟关联。先用覆盖索引只取这 20 个主键，再回表
SELECT t.* FROM user t
JOIN (
  SELECT id FROM user
  WHERE city = '成都'
  ORDER BY id
  LIMIT 100000, 20
) AS tmp ON tmp.id = t.id;

原理：子查询 SELECT id FROM user ... LIMIT 100000,20 只要 id——在 (city, id) 或覆盖索引上就能完成，不回表；拿到的只有 20 个主键，外层 JOIN 再回表取 20 行整行。回表次数从 10 万次降到 20 次，这就是深度分页的标准答案。

深分页优化口诀：先在覆盖索引上把"要哪几个主键"算出来，再用这几个主键回表——回表次数 = 一页行数，不是偏移量。

✓ 本章小结

要点一句话
回表二级索引叶子存"索引列+主键"，取整行要拿主键再查聚簇索引
覆盖索引查询列全在索引里，读完叶子即得结果，不回表
Using indexEXPLAIN Extra 出现它 = 教科书式覆盖索引命中
SELECT *触发不必要回表，扼杀覆盖索引；永远显式列名
延迟关联深分页先在覆盖索引上取主键、再回表，回表次数从偏移量降到一页
