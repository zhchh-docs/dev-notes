第 24 章 EXPLAIN 全字段解读

EXPLAIN 是优化 SQL 的照妖镜：一条查询加两个字，就能看到优化器打算走哪个索引、扫多少行、要不要临时表。本章用一份真实输出，逐列把 id、select_type、type、key、rows、Extra 讲透——type 列从好到坏的等级、Extra 里每个"Using"的含义，看完你就能独立诊断任何慢查询。

24.1 一份真实的 EXPLAIN 输出

先看一行真实输出长什么样，再逐列拆开。

-- 建表演示：订单表，按用户 + 状态筛单
EXPLAIN SELECT o.id, o.amount
FROM orders o
JOIN user u ON u.id = o.user_id
WHERE u.city = '成都' AND o.status = 2
ORDER BY o.created_at DESC LIMIT 20;

典型输出（8.0 文本格式）：

+----+-------------+-------+------+-------------------+-------------+---------+
| id | select_type | table | type | possible_keys     | key         | rows    |
+----+-------------+-------+------+-------------------+-------------+---------+
|  1 | SIMPLE      | u     | ref  | PRIMARY,idx_city  | idx_city    |     150 |
|  1 | SIMPLE      | o     | ref  | idx_user_status   | idx_user    |      10 |
+----+-------------+-------+------+-------------------+-------------+---------+
Extra:
u:  Using index condition
o:  Using where; Using filesort
列含义（一句话）
idSELECT 的序号；多表/子查询时越大越先执行（NULL 为派生表）
select_typeSIMPLE（无子查询）/ PRIMARY / SUBQUERY / DERIVED 等
table这一行在查哪张表
type最重要：访问类型，直接反映走索引的好坏（见 24.2）
possible_keys优化器"可选"的索引清单
key实际选中的索引；NULL 表示没走索引
key_len索引用到的字节数，越长 = 用了索引的越多列
ref与索引列比较的是常量还是哪个表的列（const / u.id）
rows优化器估算要扫描的行数（越大越慢）
filtered扫描后剩余行占比（%），100 表示基本无浪费
Extra附加信息：回不回表、排不排序、用不用临时表（见 24.4）

24.2 type 列：从好到坏的等级

type 是判断"这条查询走没走索引"的第一指标，从好到坏分七档。

-- 从好到坏（性能依次下降）：
-- system > const > eq_ref > ref > range > index > ALL
type含义出现场景
system表只有一行系统表，极少见
const主键/唯一索引等值匹配，最多一行WHERE id = 1（主键）
eq_refJOIN 时用主键/唯一索引，每表匹配一行多表关联主键关联
ref普通索引等值匹配，可能多行WHERE city = '成都'
range索引范围扫描BETWEEN、>、IN
index整棵索引树都扫一遍（比 ALL 稍好）覆盖索引扫全索引
ALL全表扫描，最坏档没走索引 / 索引失效
红线：看到 type=ALL 就要警惕（小表除外）；Using filesort、Using temporary 出现也要扣分。生产 SQL 的 type 至少要达到 ref 或 range。
看 EXPLAIN 先扫 type：const/eq_ref 优秀，ref/range 及格，index/ALL 必须回去查索引。

24.3 key / key_len / ref / rows

这四列回答三个问题：走了哪个索引、用了几列、比什么、扫多少行。

-- key：实际用的索引。NULL = 没走
-- key_len：判断联合索引用到了第几列
--   BIGINT 主键 = 8 字节；VARCHAR(20) utf8mb4 ≈ 20*4+2 = 82 字节
--   若 (city, age) 索引 key_len=82，说明只用了 city 这一列

-- ref：索引列在跟什么比
--   const  → 跟常量比（WHERE city='成都'）
--   u.id   → 跟 u 表的 id 列比（JOIN ON o.user_id = u.id）

-- rows：估算扫描行数，是粗估不是精确值
--   rows=150 比 rows=100000 好一个数量级

实战用法：联合索引 (a, b, c) 的 key_len 告诉你最左前缀走到了哪一列——key_len 只算到 a 的字节数，说明 b、c 断档了（第 21 章）。这是验证"索引到底用了几列"的硬证据。

24.4 Extra 列：每个 Using 的含义

Extra 是执行计划的"隐藏代价表"，每个关键字都对应一笔开销。

Extra 值含义代价
Using index覆盖索引，不回表优秀
Using whereServer 层再过滤（回表后判断）可接受
Using index condition索引下推（第 21 章）已优化
Using filesort额外排序（没走索引顺序）扣分
Using temporary用了临时表（常见于 GROUP BY / DISTINCT）扣分
Using join buffer关联没走索引，用了内存缓冲要加索引
 
-- Using filesort 怎么治：ORDER BY 的列要能走索引
SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at;
-- 索引 (user_id, created_at) 让取出即有序，filesort 消失

-- Using temporary 怎么治：GROUP BY 的列尽量走联合索引
SELECT city, COUNT(*) FROM user GROUP BY city;
-- idx_city 让分组有序，免临时表
两个必治的信号：Using filesort（排序没走索引）、Using temporary（建了临时表）。数据量大时它们是慢查询的直接凶手。

24.5 JSON / TREE 格式与实战排查

文本表格看不全时，8.0 给了 JSON 与 TREE 两种格式，还能看真实耗时。

-- 8.0：结构化 JSON，能看到代价数字
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 1;

-- 8.0.18+：TREE 树形输出，多表关联一眼看清驱动顺序
EXPLAIN FORMAT=TREE SELECT ... ;

-- 8.0.18+ 王炸：EXPLAIN ANALYZE 真实执行并报每步耗时
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;
-- 输出里每一步带 actual time=0.123..0.456 ms，慢在哪一步一目了然

排查心法：先 EXPLAIN 看 type 是不是 ALL、key 是不是 NULL；再看 Extra 有没有 filesort/temporary；最后拿 EXPLAIN ANALYZE（8.0.18+）看真实耗时定位到具体那一步。

版本提示：EXPLAIN ANALYZE 是 MySQL 8.0.18 才引入的老版本（5.7）没有；5.7 用户用 EXPLAIN FORMAT=JSON 看 cost_info。

✓ 本章小结

要点一句话
type 等级system>const>eq_ref>ref>range>index>ALL，ALL 是红线
key / key_len看走了哪个索引、联合索引用到第几列
rows / filtered估算扫描行数与剩余占比，评估浪费程度
ExtraUsing index 好；filesort、temporary、join buffer 要治
EXPLAIN ANALYZE8.0.18+ 真实执行并报每步耗时，慢在哪一步直接可见

✎ 本章习题

A 基础对任意一条 SELECT * FROM orders WHERE user_id=1 执行 EXPLAIN，指出 type、key、rows、Extra 四列的值，并判断这条查询走没走索引。
B 进阶造一张带 ORDER BY 的查询表，先让它的 Extra 出现 Using filesort，再设计一条联合索引让 filesort 消失，用 EXPLAIN 验证前后差异。
