21.1 联合索引的排序逻辑：先按谁、再按谁

联合索引不是把几列各建一棵树，而是把几列的值拼成"复合键"、按字典序排在同一棵 B+ 树上。

以 (city, age, name) 为例，索引叶子节点的排序规则是：先按 city 排；city 相同再按 age 排；city、age 都相同最后按 name 排。像电话簿"先按姓排、同姓按名排"一样。

CREATE INDEX idx_city_age_name ON user (city, age, name);

-- 索引叶子里的键值（示意）按此顺序物理排列：
-- ('成都', 25, '张三')
-- ('成都', 25, '李四')
-- ('成都', 30, '王五')
-- ('北京', 22, '赵六')
-- ('北京', 28, '孙七')
-- ... 先排 city，city 相同才看 age，再相同才看 name

图 21-1 联合索引 (city, age, name) 的物理排序：块间按 city，块内按 age，末尾按 name

这个"先排谁"的规则是所有后续结论的根：只有当先决列等值锁定后，后列的有序性才成立。

21.2 最左前缀原则：能用与不能用

查询要用上这棵树，必须从索引最左列开始，且连续等值匹配到哪一列，就能用哪一列。

拿 idx_city_age_name (city, age, name) 当样本，逐条对：

-- ✅ 全命中：三列都等值，定位到 ('成都', 25, '张三') 这一个键
WHERE city = '成都' AND age = 25 AND name = '张三'

-- ✅ 命中前两列：city、age 等值，name 没给也行
WHERE city = '成都' AND age = 25

-- ✅ 命中第一列：只给 city 也能走索引（在成都的块内扫）
WHERE city = '成都'

-- ❌ 跳过最左列，直接从 age 开始：整块"成都"你不知道在哪，用不上树
WHERE age = 25

-- ❌ 从中间开始同理失效
WHERE age = 25 AND name = '张三'
最左前缀铁律：索引按列序从左到右生效，一旦断档（没给左列、或左列是范围），右边的列就全部失去有序性、帮不上忙。

一个反直觉的好消息：条件的书写顺序无所谓。MySQL 优化器会自动把 WHERE age = 25 AND city = '成都' 重排成索引需要的 (city, age) 顺序——你按啥顺序写 WHERE，树都按列序理解。所以"最左前缀"说的是列有没有出现，不是书写顺序。

21.3 范围查询断档：> 后面的列为什么失效

范围列本身能用上，但它右边的列——索引的"断档点"——就全部失效了。

原理回到图 21-1：当 city = '成都' 等值锁定后，块内 age 是有序的，所以 age > 25 能在块内二分定位起点。但 age 是范围（>25），在"age>25"这个开区间里，name 不再有序——25 以上可能有张三、也可能有李四穿插。所以 name = '王五' 这一条条件，索引帮不上忙，只能逐行回表判断。

-- (city, age, name) 上：
WHERE city = '成都' AND age > 25 AND name = '王五'
--  ↑等值可用   ↑范围可用  ↑断档：索引无法直接定位，只能回表逐行比对

-- 对比：把范围列放最后（设计索引时就该这么排）
-- 若高频查询是 city=? AND name=? AND age>?，索引应建成 (city, name, age)
WHERE 条件能用的索引列结果
city='a' AND age=25 AND name='x'三列全用精确点查
city='a' AND age=25city、age索引定位到范围
city='a' AND age>25 AND name='x'city、age（范围）name 断档，回表判断
age=25无跳过最左，全表扫
设计列序的实战口诀：等值列在前、范围列在后、排序列最后。把高频等值的列放左边，把范围/排序的列放右边——反过来写（范围列在中间）等于自废右列。

21.4 索引下推 ICP：8.0 的回表救命功能

断档了也不一定要全部回表——索引下推（Index Condition Pushdown）在引擎层就把断档列的条件先筛一遍。

还是 city='成都' AND age>25 AND name='王五'：没有 ICP 时，存储引擎沿着索引把"city=成都且 age>25"的每一行主键都捞出来、全部回表取出整行，再由 Server 层用 name 过滤——回表次数 = 成都 age>25 的行数。

有 ICP（MySQL 5.6 引入，8.0 默认开启）：因为 name 这一列本来就在索引键里（联合索引叶子存了 name），引擎层在索引上就顺手把 name='王五' 比对掉，只对真正命中的行回表。

-- 确认 ICP 开关（5.6+ 引入，8.0 默认 ON）
SET optimizer_switch = 'index_condition_pushdown=on';

-- EXPLAIN 的 Extra 列会告诉你有没有用上：
-- Using index condition  → 已下推，引擎层先筛，回表次数大减
-- 没有该行                → 断档条件全量回表（第 24 章详解 Extra）
ICP 不改变"断档"这个事实，但把断档条件的过滤从"回表后"提前到"索引上"——能在索引页解决的，绝不回表。

21.5 列序设计与常见误区

联合索引不是越多列越好，列序错了等于白建。

  • 坑把区分度最低的列放最左：status 只有 0/1/2 三值，放第一列等于没筛掉几行（第 23 章低选择性）；高频等值列、区分度高的列优先左置；
  • 坑重复建冗余索引：已有 (a, b) 再建 (a) 就是冗余——最左前缀已经能用到 (a)；反过来 (a) 已存在再建 (a, b) 是必要的扩展；
  • 坑索引列超过 4~5 列：索引键越长、单页能放的键越少（扇出下降），树变高、写放大；联合索引控制在 3~4 列性价比最高；
  • 点一条联合索引常能覆盖多条查询：(city, age, name) 同时服务"只按 city"、"city+age"、"city+age+name"三种查询——这是联合索引最香的地方。
-- 业务场景：高频查询 WHERE user_id=? AND status=? ORDER BY created_at LIMIT 20
-- 设计列序：等值的 user_id、status 在前，范围/排序的 created_at 垫底
ALTER TABLE orders ADD INDEX idx_user_status_time (user_id, status, created_at);

-- 一条索引同时覆盖：user_id 单查 / user_id+status / 带排序的分页查询

✓ 本章小结

要点一句话
排序逻辑复合键按列序字典序排列：先 a，a 同再 b，b 同再 c
最左前缀从最左列连续等值匹配才生效；跳过左列即失效
范围断档范围列右边的列失去有序性；设计时把范围列放最后
索引下推 ICP断档条件若在索引键内，引擎层先筛再回表（Using index condition）
列序原则等值在前、范围在后、排序垫底；一条索引覆盖多类查询
