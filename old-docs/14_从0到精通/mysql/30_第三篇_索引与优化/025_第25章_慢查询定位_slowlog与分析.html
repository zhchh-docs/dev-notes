第 25 章 慢查询定位：slow log 与分析

教科书 第 25 章 / 共 72 章 · 预计 35 分钟

数据库慢了，先别急着加索引——先让数据库自己告诉你"谁最慢"。慢查询日志（slow query log）就是这台记录仪：怎么开、阈值设多少、8.0 的 performance_schema 怎么按语句聚合，最后把最值得优化的那几条 SQL 筛出来。

25.1 开启慢查询日志

慢查询日志是一个开关，打开后 MySQL 把"超过阈值的 SQL"逐条记进文件。

-- 动态开启（8.0，无需重启）
SET GLOBAL slow_query_log = ON;

-- 指定日志文件位置（生产一般放独立磁盘）
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 查看当前状态
SHOW VARIABLES LIKE 'slow_query_log%';
想永久生效：把这两行写进 my.cnf 的 [mysqld] 段；动态 SET 只在当前实例存活期有效，重启后丢失。

25.2 阈值与相关开关

阈值定多高，决定了你抓什么级别的"慢"。

-- 超过 1 秒的查询记入慢日志（生产常用 1s；默认 10s 太宽松）
SET GLOBAL long_query_time = 1;

-- 管理类开关：没走索引的查询也记下来（对排查索引问题很有用）
SET GLOBAL log_queries_not_using_indexes = ON;

-- 查看
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
参数默认值生产建议
long_query_time10 秒1 秒（核心库 0.5 秒）
log_queries_not_using_indexesOFFON（索引问题早发现）
slow_query_logOFFON（基本不开白不开）
阈值别设太小（比如 0.1 秒）：大量"正常但略慢"的 SQL 会把日志撑爆、反而淹掉真正的慢查询。1 秒是大多数业务的平衡点。

25.3 日志分析工具：mysqldumpslow 与 pt-query-digest

慢日志是一条条原文，直接读能把人淹死——先聚合成"按 SQL 模板统计"再看。

-- mysqldumpslow：MySQL 自带，开箱即用
-- -s t 按总耗时排序；-t 10 取前 10 条；-g 带正则过滤
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

-- 输出把相似 SQL 归并成一类，给出：次数、总耗时、平均耗时、扫描行数
-- 你一眼就看到"哪类 SQL 最慢、被调用多少次"
-- pt-query-digest（Percona Toolkit）：业界事实标准，更专业
pt-query-digest /var/log/mysql/slow.log --limit 20

-- 它输出：整体统计（多少类 SQL）、TOP 慢查询指纹、每条的执行画像
-- 还能按时间维度看哪类 SQL 在哪个时间段突然变慢

为什么要"聚合"？同一条 SQL（比如 WHERE user_id=?）一天跑几万次，参数不同但模板一样；聚合后你看到的是"这条模板 SQL 总共花了多少时间"，而不是淹没在几万条原文里。

-- mysqldumpslow 典型输出长这样（已归并）：
-- Count: 1200  Time=8.2s (9840)  Lock=0.1s  Rows=0.5
--   SELECT * FROM orders WHERE user_id=? AND status=?
-- Count: 3     Time=4.1s (12)   Lock=0.0s  Rows=100000
--   SELECT * FROM orders ORDER BY created_at
-- 先看 Count×Time 的总量，第一条 1200 次×8.2s 才是大头

25.4 performance_schema：8.0 的 SQL 聚合视图

不想落慢日志文件？8.0 直接在数据库里就能按 SQL 模板查统计。

-- 8.0 自带：按 SQL 模板（digest）聚合的语句历史
SELECT
  digest_text,                 -- 聚合后的 SQL 模板
  count_star,                  -- 执行次数
  round(sum_timer_wait/1e12, 2)  AS total_sec,   -- 总耗时(秒)
  round(avg_timer_wait/1e12, 2)  AS avg_sec,     -- 平均耗时
  rows_examined                -- 扫描行数
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC
LIMIT 20;

-- 这张表实时维护，不用专门开慢日志，直接查"谁最慢"
定位慢 SQL 的两条路：慢日志（落盘、可事后追溯）+ performance_schema（实时、直接查）。生产环境两者一起用，互为补充。

25.5 慢查询日志格式解读

慢日志里每一条"慢"到底记了什么？拆开看一眼，下次抓现场才知道关键指标在哪。

-- 一条典型慢日志长这样（精简后）：
-- # Time: 2026-10-23T10:15:30
-- # User@Host: app[app] @ 10.0.0.5 []
-- # Query_time: 8.123  Lock_time: 0.020  Rows_sent: 20  Rows_examined: 1000000
-- SET timestamp=1729673730;
-- SELECT * FROM orders WHERE user_id=10086 ORDER BY created_at DESC LIMIT 20;
字段含义与排查价值
Query_timeSQL 总耗时，超过 long_query_time 才会被记录
Lock_time等锁花了多久；异常高说明是锁等待而非 SQL 本身慢
Rows_sent真正返回给客户端的行数
Rows_examined扫描的行数；与 Rows_sent 差距越大，越可能缺索引
重点看 Rows_examined 与 Rows_sent 的比值：返回 20 行却扫了 100 万行，基本就是"全表扫 + 缺索引"的铁证，直接去翻 EXPLAIN 即可。

25.6 定位到单条 SQL 后的动作

揪出最慢的那条 SQL 之后，固定走三步：

  1. EXPLAIN 看执行计划：type 是不是 ALL、key 是不是 NULL（第 24 章）；
  2. 对照失效清单：是索引没建，还是建了没用（第 23 章）；
  3. 动手优化：加索引 / 改写法 / 覆盖索引 / 延迟关联，优化前后各跑一次 EXPLAIN 对比。
别陷入"为优化而优化"：先看慢 SQL 的总耗时占比（次数 × 平均耗时）——一条每天跑一次、偶尔 5 秒的报表 SQL，不如每天跑十万次、每次 0.2 秒的列表 SQL 值得优化。资源要花在总耗时最高的地方。
-- 慢日志轮转：日志会越滚越大，定期清理避免撑满磁盘
-- 生产一般按天切割，用 logrotate 或数据库参数自动归档
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 长期留存的慢样本，集中到日志系统（如 ELK）做趋势分析
-- 比临时翻文件更能看出"哪类 SQL 在恶化"
定位慢 SQL 的完整闭环：慢日志按模板聚合 → performance_schema 按耗时排序 → EXPLAIN 看清病根 → 按总耗时排优先级动手。慢查询治理是个持续动作，不是一次性项目。
慢日志开太细（阈值 0.1 秒）会撑爆磁盘、反而淹没真慢查询；开太粗（默认 10 秒）又抓不住"每天跑十万次、每次 0.3 秒"的隐形耗时王。1 秒是多数业务的平衡点。

✓ 本章小结

要点一句话
开慢日志slow_query_log=ON，动态可开；生产写进 my.cnf 永久生效
阈值long_query_time 生产设 1 秒；log_queries_not_using_indexes 建议开
分析工具mysqldumpslow 自带、pt-query-digest 专业，都按 SQL 模板聚合
performance_schema8.0 直接查 events_statements_summary_by_digest，实时看谁最慢
慢日志字段看 Rows_examined / Rows_sent 比值判断是否缺索引
优化优先级按 次数×平均耗时 排，总耗时最高的先治

✎ 本章习题

A 基础动态开启慢查询日志（SET GLOBAL slow_query_log=ON），把阈值设为 1 秒，执行几条故意慢的 SQL（比如对百万行表全表扫），再用 mysqldumpslow -s t -t 5 看结果。
B 进阶查询 performance_schema.events_statements_summary_by_digest，按总耗时降序取 TOP 5，写出每条 SQL 的执行次数与平均耗时，判断哪条最值得优化。
C 挑战给 log_queries_not_using_indexes=ON 后，故意跑一条没走索引的 SQL 观察是否被记录；思考：为什么这个开关对核心库是"必开"，但对小表又可能产生噪音？
