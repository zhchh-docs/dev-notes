第 41 章 主从延迟：测量与缓解

教科书 第 41 章 / 共 72 章 · 预计 40 分钟

主从架构最大的痛点不是"搭不起来"，而是"从库追不上"。用户刚下单立刻查不到订单、提现后余额没变——背后都是主从延迟。本章讲怎么量它、为什么产生它、以及几招缓解它。

◆本章目标

  • 说清主从延迟的三个主要来源：单线程重放、大事务、从库压力；
  • 会用 Seconds_Behind_Source 与心跳表两种方式测延迟；
  • 了解并行复制（relay_log_recovery、基于组提交的并行）在 8.0 的做法；
  • 知道应用层"写后读"如何强制走主库；
  • 能给"下单后查不到订单"这类线上问题定位到延迟。

41.1 延迟从哪里来

主库写 binlog 很快，但从库"重放"这个慢动作才是延迟的主战场。

  • 重放慢传统复制从库 SQL 线程单线程重放 relay log，主库高并发并行写入，从库一个人慢慢追，天然跟不上；
  • 大事务主库一个事务改了几百万行，binlog 里是一条巨事件，从库必须一口气重放完才轮到下一条——期间延迟一直涨；
  • 从库忙从库同时扛报表、后台查询，IO 与 CPU 被占满，重放优先级被挤到一边；
  • 网络抖动跨机房跨地域时，IO 线程拉 binlog 本身就慢。

41.2 测量延迟

最现成的是 SHOW REPLICA STATUS 的秒数，但它有盲区；更准的是心跳表。

-- 方法一：Seconds_Behind_Source（简称 SBS）
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: 12   ← 从库 SQL 线程当前重放位置比主库慢 12 秒

-- 盲区：从库 IO 线程断了，这个值会显示 0 或 NULL，不代表没延迟
-- 方法二：心跳表（主库定时更新，从库查时间差）
-- 主库每分钟执行一次：
CREATE TABLE IF NOT EXISTS repl_heartbeat(ts DATETIME);
REPLACE INTO repl_heartbeat VALUES (NOW(6));

-- 从库查询：
SELECT TIMESTAMPDIFF(MICROSECOND, (SELECT MAX(ts) FROM repl_heartbeat), NOW(6)) / 1000 AS delay_ms;
Seconds_Behind_Source 是"SQL 线程正在执行的事件的时间戳与现在的差"，IO 线程断开时它直接变 NULL——别看到 0 就放心，监控里要同时看两个线程是否 Yes。

41.3 缓解手段

核心思路：让从库"多线程"追、把大事务拆小、给从库减压。

手段做法效果
并行复制8.0 默认基于组提交（MTS），同组事务可在从库并行重放追平速度成倍提升
拆大事务批量 UPDATE/DELETE 按主键每几千行一批提交避免单事件堵死队列
从库专用报表查询迁到独立从库，不与复制重放抢资源重放不被挤压
半同步下一章内容：主库至少等一个从库收到 binlog 才返回降低"写后读不到"
 
-- 查看并行复制相关参数
SHOW VARIABLES LIKE 'replica_parallel%';
SHOW VARIABLES LIKE 'binlog_transaction_dependency%';

-- 8.0 默认 replica_parallel_workers = 4 左右，按 CPU 核数调整
-- 并确认基于组提交模式：
SHOW VARIABLES LIKE 'replica_parallel_type';
缓解延迟没有银弹：并行复制解决"追得慢"，拆事务解决"堵一件"，应用层走主库解决"读不到"——三者要一起上。

41.4 应用层怎么应对

业务侧最常用的招："刚写完的请求，接下来一小段时间内强制读主库"。

  • 写后读绑定主库：用户下单后跳转订单页，这个请求直接路由到主库（或带 read-from-master 标记）；
  • 短暂延迟窗口：写完后等待几百毫秒再切回从库读，覆盖大多数延迟；
  • 关键链路读主：余额、库存这类强一致要求，别赌从库；
  • 监控告警：SBS 超过阈值（如 10 秒）报警，而不是等用户投诉。
这也是后面"读写分离中间件"（第 48 章）要解决的核心问题：怎么智能判断这个请求该读主还是读从。

41.5 常见坑清单

  • 坑SBS 为 0 就以为没延迟：IO 线程断开时它是 NULL；心跳表更可靠；
  • 坑大事务迁移数据：用一个事务导千万行，从库卡半小时——迁数据必须分批提交；
  • 坑在从库上跑大报表：报表把从库 IO 打满，重放排队，延迟从秒涨到分钟；
  • 坑以为加从库就能分摊写压力：复制是"数据同步"不是"分担写"，写压力永远在主库。

41.5 延迟监控阈值怎么定

不是延迟越低越好，而是要给业务设一条告警线。

  • 普通业务：SBS > 10 秒告警，> 60 秒严重；
  • 关键链路（余额、刚下单）：读主库，不依赖从库；
  • 监控要同时看两个线程 Running=Yes，防止 IO 断开时 SBS 误报 0。
告警要接值班，而不是堆指标：延迟超阈值时自动把读流量切回主库。

✓ 本章小结

要点一句话
延迟来源单线程重放 + 大事务 + 从库压力 + 网络
测量SBS 看秒数，心跳表更准，同时盯两个线程状态
缓解并行复制、拆大事务、从库减压、半同步
应用层写后读走主库，关键链路别赌从库
认知复制分担读、不分担写；延迟是结构问题只能缓解
