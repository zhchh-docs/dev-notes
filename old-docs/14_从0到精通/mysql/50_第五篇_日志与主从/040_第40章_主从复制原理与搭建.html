第 40 章 主从复制原理与搭建

教科书 第 40 章 / 共 72 章 · 预计 50 分钟

主库写、从库读，这个在简历上出现率极高的架构，底层只是三件事：主库写 binlog、从库拉 binlog、从库重放。本章把原理讲透，并给一套能照着敲的搭建步骤。

◆本章目标

  • 说清主从复制由哪三个线程协作完成，各自跑在哪台机器；
  • 理解 binlog 位点（文件 + offset）与 relay log 的作用；
  • 能独立写出主库 my.cnf 关键片段、创建复制账号；
  • 会用 8.0 的 CHANGE REPLICATION SOURCE TO（老写法 CHANGE MASTER TO）把从库接上；
  • 会用 SHOW REPLICA STATUS 判断复制是否真的在跑。

40.1 复制的三个线程

MySQL 复制不是"主库推数据"，而是从库主动来拉，中间经过 relay log 转手。

  • Binlog Dump 线程在主库上：主库为每个连过来的从库开一个线程，按位点把 binlog 发给它；
  • IO 线程在从库上：负责拉取主库的 binlog 事件，写入本地的 relay log（中继日志）；
  • SQL 线程在从库上：读取 relay log，把事件重放一遍，数据就和主库对齐了。

图 40-1 主从复制三线程：Dump（主）→ IO（从）→ SQL（从）

从库上记录自己读到哪个位点用两个值：binlog 文件号 + 字节偏移。这就是后面配置时要填的 SOURCE_LOG_FILE / SOURCE_LOG_POS。

40.2 主库配置与复制账号

主库要做三件事：开 binlog、设唯一 server-id、建一个专门用于复制的账号。

第一步：修改主库配置 my.cnf

# 主库 my.cnf [mysqld] 段关键配置
[mysqld]
server_id = 1
log_bin = mysql-bin
binlog_format = ROW
# 8.0 默认开启 binlog，显式写出更清晰；5.7 需要 log_bin 才生效
gtid_mode = OFF           # 本章先用传统位点，下一章再讲 GTID
enforce_gtid_consistency = OFF

第二步：在主库创建复制账号

-- 复制账号只需要 REPLICATION SLAVE 权限（最小授权）
CREATE USER 'repl'@'10.0.0.%' IDENTIFIED BY 'Repl@2026';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.0.0.%';
FLUSH PRIVILEGES;

-- 查看主库当前 binlog 位点，从库接入时要照着填
SHOW MASTER STATUS;

SHOW MASTER STATUS 会输出类似 File=mysql-bin.000003、Position=1574。如果主库已有数据，还要先用 mysqldump（下一章详讲）把全量备份导给从库，再从这个位点开始追。

server-id 必须全网唯一：主库是 1，每个从库分别是 2、3……复制的第一步排错永远是看两边 server-id 是否冲突。

40.3 从库接入与启动复制

从库也设好 server-id，然后用一条 CHANGE REPLICATION SOURCE TO 告诉它主库在哪。

# 从库 my.cnf [mysqld] 段
[mysqld]
server_id = 2
relay_log = relay-bin
read_only = 1          # 从库只读，防止业务误写
-- 8.0 推荐语法（CHANGE MASTER TO 仍兼容，但官方已改名）
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST     = '10.0.0.11',
  SOURCE_PORT     = 3306,
  SOURCE_USER     = 'repl',
  SOURCE_PASSWORD = 'Repl@2026',
  SOURCE_LOG_FILE = 'mysql-bin.000003',   -- 照 SHOW MASTER STATUS 的 File
  SOURCE_LOG_POS  = 1574;                 -- 照 Position

-- 老版本等价写法（5.7 及以前）：
-- CHANGE MASTER TO MASTER_HOST='10.0.0.11', ... MASTER_LOG_FILE=..., MASTER_LOG_POS=...;

-- 启动复制
START REPLICA;

-- 查看状态（8.0）
SHOW REPLICA STATUS\G
8.0.22 起官方把 START SLAVE / STOP SLAVE 改名为 START REPLICA / STOP REPLICA；旧语法仍兼容，但新机器上建议直接用新名。

40.4 验证复制状态

光 START REPLICA 不算完，要确认两个线程都在跑、延迟在缩小。

-- 关键看这几行（\G 竖排更易读）
SHOW REPLICA STATUS\G
-- Slave_IO_Running: Yes
-- Slave_SQL_Running: Yes
-- Seconds_Behind_Source: 0
-- 8.0 字段名是 Replica_IO_Running / Replica_SQL_Running，意思相同

-- 在主库造一条数据，去从库看是否出现
-- 主库： INSERT INTO t(name) VALUES('test-repl');
-- 从库： SELECT * FROM t WHERE name='test-repl';
现象含义与处理
IO Running = No连不上主库：账号/网络/server-id 错，看 Last_IO_Error
SQL Running = No重放报错：从库被写过、或 SQL 语句不兼容，看 Last_SQL_Error
Seconds_Behind_Source 很大主从延迟，下一章专门讲
判断复制是否健康的唯一标准：Slave_IO_Running 与 Slave_SQL_Running 两个 Yes，且你刚在主库插的数据在从库能查到。

40.5 常见坑清单

  • 坑从库没设 read_only：业务直连从库写了数据，下次重放就主键冲突，SQL 线程直接停；
  • 坑忘了先做全量备份就接位点：主库已有数据，从库空表从某个位点开始追，中间缺的历史数据永远补不回来；
  • 坑用 ROW 模式却在从库手改数据：重放时行镜像对不上，报错 1032；
  • 坑server-id 撞车：两台机器 server-id 相同会导致复制行为异常，这是最隐蔽也最常见的部署错误。

✓ 本章小结

要点一句话
三线程主库 Dump 发 binlog，从库 IO 写 relay log，SQL 线程重放
主库配置server_id 唯一、开 binlog、建 REPLICATION SLAVE 账号
从库接入CHANGE REPLICATION SOURCE TO 指定主库与位点，再 START REPLICA
健康检查SHOW REPLICA STATUS 两个 Yes + 数据可见
铁律从库保持 read_only，server-id 全局唯一

✎ 本章习题

A 基础写出主库 my.cnf 中复制必需的三行配置，并说明 server-id 为什么不能两台机器都写 1。
B 进阶在本机起两个 MySQL 实例（或 Docker 起一主一从），照本章步骤完成搭建，并把 SHOW REPLICA STATUS 里的 Replica_IO_Running、Replica_SQL_Running 截图记录为两个 Yes。
C 挑战故意在从库上 INSERT 一条与主库主键冲突的数据，再在主库插入同主键记录，观察从库 SQL 线程报错。查阅 Last_SQL_Error，写出你会如何用 SET GLOBAL sql_replica_skip_counter = 1;（或 GTID 方式）绕过这一条并说明风险。
