38.1 日志家族全景

先建立全局观：一次 UPDATE 从客户端落到磁盘，路上会"签字画押"三次。

MySQL 是分层的：Server 层负责解析、优化、执行，存储引擎层（默认 InnoDB）负责真正存取数据。三类日志分属两层，各管一段：

  • redo logInnoDB 引擎层的物理日志，记"某页某偏移改成了什么"，保证宕机后已提交事务不丢；
  • undo logInnoDB 引擎层的逻辑日志，记"改之前是什么"，用于回滚和 MVCC；
  • binlogServer 层的逻辑日志，记所有修改事件，用于主从复制与数据恢复。

图 38-1 一次写操作在两层之间留下的三类日志

记住这个分层：redo/undo 是引擎的"家事"，binlog 是 Server 的"公报"。主从复制只认 binlog，崩溃恢复靠 redo，二者在下一章用"两阶段提交"串起来。

38.2 redo log：崩溃恢复的底气

数据页在内存里改完，可以先不落盘；但"改了什么"必须先顺序写进 redo log——这就是 WAL。

InnoDB 的数据以页（默认 16KB）为单位存在表空间里。如果每改一行都把脏页刷回磁盘，那就是海量随机写，机械盘根本扛不住。WAL 的做法是：修改先记到顺序写入的 redo log 文件，脏页以后再慢慢刷盘。宕机时只要 redo log 还在，重启就能把"已提交但还没刷盘"的页重放一遍（这步叫 redo）。

-- 查看 redo 相关关键参数（MySQL 8.0 已用 innodb_log_file_size 命名）
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_log_files_in_group';

-- 8.0 还可以直接看 redo 状态
SHOW ENGINE INNODB STATUS\G

innodb_flush_log_at_trx_commit 是 redo 最经典的取舍参数：

  • =1（默认，最安全）：每次事务提交都把 redo log 刷到磁盘，宕机最多丢未提交的事务；
  • =0：提交时只写内存，每秒刷一次——宕机最多丢 1 秒事务；
  • =2：提交时写操作系统页缓存，OS 崩才丢，MySQL 崩不丢。
redo log 保证的是"已提交事务不丢"（持久性 Durability）；它是顺序写、固定大小、循环复用的，写满了就要强迫刷脏页，这就是大名鼎鼎的"checkpoint"。
双 1 配置：金融级要求 innodb_flush_log_at_trx_commit=1 且 sync_binlog=1，二者缺一，宕机都可能丢数据或主从不一致——第 39 章会讲为什么这两个参数必须一起看。

38.3 undo log：回滚与 MVCC

redo 记"新的长什么样"，undo 记"旧的长什么样"——一正一反，一个管持久，一个管回滚。

事务中途 ROLLBACK，或者被事务隔离性要求"读到旧版本"，InnoDB 都要靠 undo log 里的反向操作把数据还原。它存在回滚段（rollback segment）中，有两个用途：

  1. 回滚：提交前失败，按 undo 里的反向日志把行改回去；
  2. MVCC 历史版本链：每行都有隐藏列 trx_id（最近修改它的事务）和 roll_pointer（指向 undo 里的上一版本）。读视图要哪个版本，就顺着这条链往前找。
-- 查看 undo 相关信息
SHOW VARIABLES LIKE 'innodb_undo%';

-- 长事务为什么危险：它持有的 undo 不能 purge，undo 会越来越大
SELECT trx_id, trx_started, trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC LIMIT 5;
长事务是 undo 的天敌：只要还有一个老事务未提交，它可见的旧版本就不能清理（purge），undo 段持续膨胀，磁盘和性能一起遭殃。线上 SQL 执行前先评估它会不会变成长事务（第 35 章）。

38.4 binlog：Server 层的大事记

binlog 不关心 InnoDB 内部怎么改页，它只记录"这个库发生了哪些修改事件"——所以它能给任何引擎用，也是复制的根基。

binlog 在 MySQL 8.0 默认开启（5.7 之前需要手动加 log-bin）。它有三种记录格式：

-- 查看与临时调整
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW BINARY LOGS;                 -- 当前有哪些 binlog 文件
SHOW BINLOG EVENTS IN 'binlog.000001' LIMIT 10;   -- 查看事件内容
  • ROW行模式（8.0 默认）：记录每行被改成什么样。幂等、主从一致，缺点是日志体积大；
  • STATEMENT语句模式：记原始 SQL。日志小，但 NOW()、UUID() 这类函数在从库重放结果会不同，容易主从不一致；
  • MIXED混合模式：一般用 STATEMENT，判定不安全时自动切 ROW。

sync_binlog=1 表示每次提交都把 binlog 刷盘；=0 交给 OS，=N 表示攒 N 次事务刷一次。高并发场景下 N 能换性能，但宕机最多丢 N 个事务。

binlog 是"追加写"的文件，用 RESET MASTER / PURGE BINARY LOGS 清理。别手动删目录里的文件，会让 mysql-bin.index 与实际脱节。

38.5 三大日志对比

日志所属层记录内容主要用途生命周期
redo logInnoDB 引擎层物理页修改（页号+偏移）崩溃恢复，保证已提交不丢固定大小，循环覆盖
undo logInnoDB 引擎层行的旧版本（反向操作）事务回滚 + MVCC被 purge 后清理
binlogServer 层逻辑修改事件（语句/行）主从复制、时间点恢复按文件滚动，可保留清理
一句话记忆：redo 管"不丢"，undo 管"能退、能读旧版"，binlog 管"别人能跟上"。

38.6 常见坑清单

  • 坑把 redo 和 binlog 搞混：redo 是引擎私有、循环写；binlog 是 Server 层、追加滚动。复制只吃 binlog，跟 redo 无关；
  • 坑为了性能把双 1 关掉：innodb_flush_log_at_trx_commit=2 且 sync_binlog=0 是宕机丢数据的常客，报表库可以，交易库不行；
  • 坑STATEMENT 模式下用函数：INSERT ... VALUES(NOW()) 在从库重放时间不同，排查了半天主从不一致；
  • 坑binlog 只开不清：磁盘被撑爆前没人提醒，记得配 expire_logs_days（8.0 用 binlog_expire_logs_seconds）。

✓ 本章小结

要点一句话
WAL先记日志（顺序写）再刷脏页（随机写），用顺序写换性能
