39.1 为什么需要两阶段提交

假设没有固定顺序：先写 redo 后写 binlog，或者反过来——宕机点不同，主库与从库的数据就可能分叉。

问题的根源在于两份日志由不同层负责、各自刷盘。考虑两种错误顺序：

  • 先 redo 后 binlog：redo 写完、事务在主库提交成功，binlog 还没来得及写就宕机。从库没有这条事件，主库却有——主从不一致；
  • 先 binlog 后 redo：binlog 写了，从库已经重放这条修改，redo 还没落盘主库就宕机，主库恢复后回滚了该事务——又是两边不一致。

MySQL 的解法不是"选一个先写"，而是让事务在 redo 里先打一个 prepare 标记，把 binlog 写完后，再把 redo 改成 commit 标记。这样崩溃点落在两步之间时，恢复程序有一个客观的判据：binlog 里有没有这个事务。

39.2 prepare 与 commit 两步

理解每一步"写在哪、刷不刷盘"，崩溃恢复才讲得通。

  1. prepare 阶段：InnoDB 把事务回滚信息、修改页先记进 redo log，并打上 TRX_MARKED_PREPARE 的状态；此时事务对其他会话还不可见；
  2. binlog 写入：Server 层把这个事务的修改事件写入 binlog（是否刷盘由 sync_binlog 决定）；
  3. commit 阶段：InnoDB 把 redo 里的事务状态改为 commit，写一条 commit 日志，事务才算真正完成。

关键设计：binlog 的事务内容里带有一个 XID（事务 ID），redo 的 prepare/commit 日志里也记着同一个 XID。恢复时两边靠 XID 对得上号。

-- 查看当前 binlog 内部的事务位点（每秒/每事务都会推进）
SHOW MASTER STATUS;

-- 8.0 推荐用 REPLICA 语法查看复制状态
SHOW REPLICA STATUS\G

39.3 崩溃恢复怎么判事务

MySQL 重启后先重放 redo，再逐个处理处于 prepare 状态的事务。

恢复程序扫描 redo log，把所有"已 commit"的事务重放回来；遇到处于 prepare 状态的事务时，按 XID 去 binlog 里查：

  • binlog 里存在这个 XID：说明 binlog 已经写完，从库可能已经重放了它——主库必须提交，否则主从分叉；
  • binlog 里不存在这个 XID：说明事务还没写到 binlog，从库看不到——主库直接回滚。
两阶段提交的本质：用"binlog 里有没有这个 XID"作为事务是否对外可见的唯一裁判，让引擎层与 Server 层在崩溃后依然能对齐。
这也解释了为什么主从复制要求 binlog 必须完整可靠：它不只是"复制用的日志"，它是崩溃恢复时判定事务去留的证据。

39.4 关键参数与安全边界

双 1 的真正含义：redo 刷盘与 binlog 刷盘都在提交时硬刷。

参数设为 1 的效果妥协代价
innodb_flush_log_at_trx_commit=1提交即把 redo 刷到磁盘每次提交多一次 fsync，写并发下降
sync_binlog=1提交即把 binlog 刷到磁盘同样增加刷盘次数
两者同时 =1崩溃最多丢"未提交"事务，主从不分叉金融级配置，性能换安全
 
-- 查看当前双 1 状态
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';

-- 生产环境写在 my.cnf [mysqld] 段：
-- innodb_flush_log_at_trx_commit = 1
-- sync_binlog = 1
只开一个等于没开：innodb_flush_log_at_trx_commit=1 但 sync_binlog=0，宕机时 binlog 里没有的事务在主库却被提交——从库少数据，且无法自动修复。

39.5 常见坑清单

  • 坑把"两阶段提交"和"分布式 XA 事务"混为一谈：本章讲的是 MySQL 内部为了对齐 redo/binlog 的内部两阶段；第 54 章的 XA 是跨多个数据库实例的外部协议，名字像，对象不同；
  • 坑以为 crash 后会自动重放 binlog：binlog 是"输出"，恢复靠的是 redo 重放 + XID 判定；
  • 坑大事务让 prepare 阶段挂很久：一个事务改了几百万行才提交，prepare→commit 之间窗口拉长，崩溃恢复时间也跟着长；
  • 坑用 SET GLOBAL 改双 1 参数不生效：这两个参数在 8.0 可以动态改，但重启后想持久必须写配置文件。

39.6 与分布式 XA 的区别

本章的两阶段提交是 MySQL 内部为对齐 redo/binlog 的机制，别和跨库 XA 事务混淆。

内部两阶段提交的"参与者"是同一个实例的引擎层与 Server 层，目的是让本地事务在崩溃后可判定；而第 54 章的 XA 是跨多个独立数据库实例的外部协议，由协调者驱动多个分支 prepare/commit。两者都叫两阶段，但对象与作用域完全不同。

面试常问：MySQL 内部两阶段提交解决的是"本地 redo 与 binlog 顺序"，不是"跨库事务一致性"。
