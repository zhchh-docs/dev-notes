45.1 为什么订阅 binlog

双写的痛点：业务接口里既要写 MySQL 又要写 ES，漏写、失败、顺序错乱全靠代码兜。

  • 双写在业务代码里同时写多个存储——耦合高、重试难、一致性靠人力；
  • 订阅 binlog把"数据变更"这件事统一从源头捞出来，下游各自消费——业务代码只写 MySQL；
  • 典型下游：Elasticsearch（搜索）、Redis（缓存失效/刷新）、数仓（离线分析）。
binlog 订阅的本质：把"数据发生了什么"变成一条可靠的事件流，让系统从"业务主动推送"变成"下游按位点消费"。

45.2 Canal 的工作链路

Canal（阿里开源）假装自己是 MySQL 的从库：收到 binlog dump、解析成变更对象、再投出去。

图 45-1 Canal 订阅链路：主库 binlog → Canal 解析 → MQ → 各下游消费

Canal 内部拆两层：instance（对应一个主库的解析实例，负责伪装从库、拉 binlog）与 adapter/投递器（把解析结果写到 MQ 或直接到下游）。它自己会记消费到哪个位点，挂了重启能接着拉。

45.3 主库侧准备

Canal 要做"从库"，主库就得按从库复制那套来配。

-- 1) 主库 binlog 必须是 ROW（Canal 需要行镜像）
SET GLOBAL binlog_format = ROW;

-- 2) 建一个与复制同权限的账号
CREATE USER 'canal'@'%' IDENTIFIED BY 'Canal@2026';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';

-- 3) 确认主库可连、binlog 可拉
SHOW MASTER STATUS;
Canal 的 instance 配置里填主库地址、端口、上面的账号密码，以及要监听的库表白名单（如 mydb.order.*）。解析出来的事件包含：表名、操作类型（INSERT/UPDATE/DELETE）、行数据的前后镜像。
ROW 格式下一条 UPDATE 的 binlog 体积可能很大（整行前后镜像都记），Canal 同步大表变更时注意主库 binlog 与网络带宽。

45.4 常见坑清单

  • 坑主库用了 STATEMENT 格式：Canal 拿不到行镜像，解析失败；
  • 坑以为 binlog 订阅是实时强一致：有秒级延迟，ES 搜索"刚下单立刻搜到"要接受这个窗口；
  • 坑下游消费失败不重试：Canal 投递到 MQ 后要保证 MQ 持久化，否则事件丢了下游永久缺数据；
  • 坑Canal 实例挂了位点乱了：要监控 instance 运行状态，重启后从记录位点继续。

45.4 Canal 自身的高可用

Canal 实例也会挂，它靠位点持久化与主备切换保证不丢事件。

  • Canal 把消费到的 binlog 位点定期写存储（ZK/文件）；
  • 实例挂了重启后从记录位点继续拉，不重复不丢；
  • 投递到 MQ 必须开启持久化，下游失败可重放。
Canal 只是"搬运工"，真正保证不丢的是 MQ 持久化 + 下游重试，不是 Canal 本身。
