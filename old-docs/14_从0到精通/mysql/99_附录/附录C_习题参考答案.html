第 1 章 数据库是什么：从 Excel 到关系型

A 基础

题干：用不超过四句话，向一位只会 Excel 的同事解释：为什么公司要把订单数据从 Excel 搬进 MySQL？至少说出两个具体痛点。

答案：①并发：Excel 多人同时编辑会锁文件、版本互相覆盖，MySQL 支持多连接事务并发写入；②容量：订单涨到几十万行后 Excel 打开卡顿、筛选变慢，MySQL 靠索引毫秒级查询；③一致性：Excel 公式手改、跨表复制容易出错，MySQL 用主键/唯一/非空约束与事务保证数据不矛盾；④权限与审计：Excel 谁都能整表导出，MySQL 可按库/表/列授权并记录操作日志。（说出任意两点即可）

B 进阶

题干：判断以下需求分别属于 SQL 的哪个分类（DDL/DML/DCL/TCL）：①新建一张“会员等级”表；②把某用户的手机号改成新号；③给运营组开通只读权限；④撤销本次转账操作。

答案：①DDL（CREATE TABLE，定义结构）；②DML（UPDATE，操作数据行）；③DCL（GRANT，授权）；④TCL（ROLLBACK，事务控制）。

C 挑战

题干：画一张图（纸笔即可）：从“你在 DBeaver 里按下回车”到“数据从磁盘返回”，标出客户端、Server 层、InnoDB 三个环节。下一章装好环境后，你会用 SHOW ENGINES 验证第三层。

答案：链路为 DBeaver（客户端发 SQL）→ MySQL Server 层（连接器接管连接、分析器解析语法、优化器选执行计划、执行器调用引擎接口）→ InnoDB 存储引擎（先查 Buffer Pool 内存页，未命中再从磁盘 .ibd 文件读页，结果逐层原路返回客户端）。装好环境后执行 <code>SHOW ENGINES</code>，可看到 InnoDB 为 DEFAULT。

第 2 章 安装与客户端：Docker 起库与 DBeaver

A 基础

题干：完成本章全部实操：Docker 起库、命令行登录、DBeaver 连接，记下 SELECT VERSION() 的结果。

答案：用 Docker 一条命令起 mysql:8.0（挂载数据卷、映射 3306、设置 root 密码）；docker exec 进入容器用 mysql -uroot -p 命令行登录；DBeaver 新建 MySQL 连接填 host/port/账号/密码；执行 <code>SELECT VERSION();</code> 返回形如 8.0.xx（如 8.0.36），记录该版本号。

B 进阶

题干：创建用户 reader，只授予 bookshop 的 SELECT 权限；用 reader 登录尝试 CREATE DATABASE test2;，观察并解释报错。

答案：

CREATE USER 'reader'@'%' IDENTIFIED BY '强密码';
GRANT SELECT ON bookshop.* TO 'reader'@'%';

用 reader 登录执行 CREATE DATABASE test2; 会报 <code>ERROR 1044 (42000): Access denied for user 'reader'@'%' to database 'test2'</code>——reader 只被授予 bookshop 库的 SELECT，建库需要全局 CREATE 权限，DCL 未授予自然拒绝。

C 挑战

题干：把容器端口映射改成 3307 重建，分别用命令行和 DBeaver 连上它；再执行 docker volume ls 找到数据卷，思考：删容器（不删卷）后重跑同名容器，数据还在吗？动手验证。

答案：端口映射改为 <code>-p 3307:3306</code> 重建后，本机用 3307 端口连接。<code>docker volume ls</code> 可见 mysql 命名卷；删容器（docker rm，不加 -v 删卷）后用同一卷名重新挂载启动同名容器，数据还在——因为数据持久化在 volume 里，容器本身无状态，删容器只删文件系统层、不删卷。

第 3 章 库、表、行与数据类型选型

A 基础

题干：为“图书”设计字段并列出类型：书名、作者、价格、库存、出版日期、内容简介。写出所选类型并说明理由。

答案：

CREATE TABLE book (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(100) COMMENT '书名',
  author VARCHAR(50) COMMENT '作者',
  price DECIMAL(10,2) COMMENT '价格',
  stock INT UNSIGNED COMMENT '库存',
  pub_date DATE COMMENT '出版日期',
  intro TEXT COMMENT '内容简介'
);

理由：变长中文字符串用 VARCHAR；金额用 DECIMAL 精确、避免浮点；库存非负用 UNSIGNED；日期用 DATE 而非字符串；长简介用 TEXT。

B 进阶

题干：建一张 t_demo，金额列误用 FLOAT，插入 0.1 三次后 SELECT SUM(amount) 观察误差；再 ALTER TABLE 改成 DECIMAL(10,2)，看值是否恢复精确。

答案：

CREATE TABLE t_demo (amount FLOAT);
INSERT INTO t_demo VALUES (0.1),(0.1),(0.1);
SELECT SUM(amount) FROM t_demo;   -- 约 0.300000011920929（浮点误差）
ALTER TABLE t_demo MODIFY amount DECIMAL(10,2);
SELECT SUM(amount) FROM t_demo;   -- 0.30

FLOAT 二进制无法精确表示 0.1，三次累加误差被放大；改 DECIMAL 后按两位小数精确存储，求和为 0.30。

C 挑战

题干：解释：为什么“手机号”推荐 CHAR(11) 而不是 VARCHAR(20)？如果要存国际号码（带国家码、可含 + 和空格），你的选择会变吗？

答案：国内手机号恒为 11 位数字、长度固定，用 CHAR(11) 定长无 VARCHAR 的长度字节开销，比较也更直接；VARCHAR 是为“长度会变”准备的，固定长度用它反而白占余量。国际号码长度不一、可含 + 与空格，应改为 VARCHAR(32)，且不要当数字存。

第 4 章 建库建表：DDL 与约束

A 基础

题干：按本章模板建一张 book 表：书名、作者、价格、库存、上架状态，含完整注释与审计字段；用 SHOW CREATE TABLE 回看成果。

答案：

CREATE TABLE book (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  title VARCHAR(100) NOT NULL COMMENT '书名',
  author VARCHAR(50) DEFAULT NULL COMMENT '作者',
  price DECIMAL(10,2) NOT NULL DEFAULT 0 COMMENT '价格',
  stock INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '库存',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '上架状态 1上架 0下架',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  is_deleted TINYINT NOT NULL DEFAULT 0 COMMENT '软删',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='图书表';

执行 <code>SHOW CREATE TABLE book\G</code> 回看列、约束、字符集与注释是否齐全。

B 进阶

题干：给 book 表的 price 加 CHECK（price >= 0），插入 -1 与 0 各试一次，记录数据库的反应；再试试向 NOT NULL 的 title 插入 NULL。

答案：MySQL 8.0.16 起才真正强制 CHECK。加约束：<code>ALTER TABLE book ADD CONSTRAINT chk_price CHECK (price >= 0);</code> 插入 -1 报 <code>ERROR 3819 (HY000): Check constraint 'chk_price' is violated</code>；插入 0 通过；向 NOT NULL 的 title 插 NULL 报 <code>ERROR 1048 (23000): Column 'title' cannot be null</code>。（8.0.16 之前 CHECK 只解析不生效。）

C 挑战

题干：分别用 DELETE、TRUNCATE 清空 book 表各一次，观察 AUTO_INCREMENT 的行为差异；思考：为什么 TRUNCATE 更快？（提示：它不逐行删，也不写 undo）

答案：<code>DELETE FROM book;</code> 逐行删除后，AUTO_INCREMENT 继续从断点自增、不会重置；<code>TRUNCATE TABLE book;</code> 清空后自增计数器重置为初始值 1。TRUNCATE 快是因为它本质是 DDL：直接 drop 表再按原定义重建，不逐行记录删除、不写 undo log、不产生逐行 redo，因此无论多大表都几乎瞬时；DELETE 是 DML，要逐行删、写 undo 与 redo，大表很慢。

第 5 章 增删改：INSERT/UPDATE/DELETE 与软删

A 基础

题干：向 product 表一次插入 5 条商品；然后用 SET sql_safe_updates = 1 后执行一条不带 WHERE 的 UPDATE，记录报错内容，再恢复 SET sql_safe_updates = 0。

答案：

INSERT INTO product (name, price, stock) VALUES
  ('商品A', 10.00, 100),
  ('商品B', 20.00, 200),
  ('商品C', 30.00, 300),
  ('商品D', 40.00, 400),
  ('商品E', 50.00, 500);
SET sql_safe_updates = 1;
UPDATE product SET price = 100;   -- 报错
SET sql_safe_updates = 0;

安全更新模式下该语句报 <code>ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column</code>——防止手滑全表更新。

B 进阶

题干：给 customer 的 phone 建唯一索引（ALTER TABLE customer ADD UNIQUE KEY uk_phone(phone)），分别用 INSERT IGNORE、REPLACE INTO、ON DUPLICATE KEY UPDATE 插入重复手机号，观察三者的返回信息与表内数据差异（注意 REPLACE 后的自增 ID）。

答案：<code>ALTER TABLE customer ADD UNIQUE KEY uk_phone(phone);</code> 后：INSERT IGNORE 撞唯一键静默忽略，返回 0 row affected，旧行原样保留（但会吞掉其他错误）；REPLACE INTO 先 DELETE 旧行再 INSERT 新行，新行自增 id 变大，并触发 DELETE 语义、可能留下孤儿关联数据；ON DUPLICATE KEY UPDATE 改为执行更新子句，旧行 id 不变、只更新指定列。三者中 UPSERT 语义最明确。

C 挑战

题干：把 customer 表加上 is_deleted 列并软删一行；思考：此时手机号还能再注册吗？动手验证，并给出你的唯一索引改造方案。

答案：不能。软删只是 UPDATE is_deleted=1，行仍留在表里，phone 唯一索引照样把它算进去，同手机号再注册会撞 Duplicate entry。改造方案：把唯一索引改为 (phone, is_deleted) 组合——同一手机号可有多条 is_deleted=1 的记录互不冲突、但 is_deleted=0 只能有一条；更稳妥的做法是改为 (phone, deleted_at)，deleted_at 非空时每条已删记录时间戳不同，互不冲突。

第 6 章 基础查询：WHERE 与运算符

A 基础

题干：从 product 表查出类目为 3 或 7、价格在 100 到 500 元之间、未软删的商品，只返回 id、name、price 三列并起中文别名。

答案：

SELECT id AS 编号, name AS 商品名, price AS 价格
FROM product
WHERE category_id IN (3, 7)
  AND price BETWEEN 100 AND 500
  AND is_deleted = 0;
B 进阶

题干：插入 level 为 NULL 的 customer，分别执行 WHERE level = NULL 与 WHERE level IS NULL，对比行数；再试 NOT IN (1, NULL)。

答案：WHERE level = NULL 永远 0 行（NULL 与任何值比较得 UNKNOWN）；WHERE level IS NULL 能查出该用户。NOT IN (1, NULL) 因集合含 NULL，每行比较都产生 UNKNOWN，整体返回 0 行——UNKNOWN 取反仍为 UNKNOWN，WHERE 只留 TRUE。

C 挑战

题干：写出"名称含键盘、库存非 0、状态上架或预售、价格 ≥200"的查询，OR 组合用括号。

答案：

SELECT id, name, price
FROM product
WHERE name LIKE '%键盘%'
  AND stock <> 0
  AND status IN (1, 2)
  AND price >= 200;

（若状态必须写成 OR：AND (status = 1 OR status = 2)。）慢的原因：LIKE '%键盘%' 前导通配符不走索引，必全表扫描；百万行时这是主要成本。

第 7 章 排序与分页：ORDER BY/LIMIT

A 基础

题干：查出销量前 20 商品（id、name、sales、price），排序稳定带主键。

答案：

SELECT id, name, sales, price
FROM product
WHERE is_deleted = 0
ORDER BY sales DESC, id DESC
LIMIT 20;
B 进阶

题干：改写成游标分页并解释为何不能只用 sales 当游标。

答案：

-- 第 2 页（假设第 1 页最后一行 sales=1200, id=88）
SELECT id, name, sales, price
FROM product
WHERE (sales, id) < (1200, 88)
ORDER BY sales DESC, id DESC
LIMIT 10;

只用 sales 当游标时，销量相同的多行在翻页边界会重复或漏掉；加上 id 才让游标唯一确定。

C 挑战

题干：后台流水列表只支持上一页/下一页，给建索引建议与两页 SQL。

答案：索引 idx_created_id (created_at DESC, id DESC)（8.0 支持降序索引）。下一页：

SELECT * FROM orders
WHERE (created_at, id) < (上一页末行的 created_at, 上一页末行的 id)
ORDER BY created_at DESC, id DESC LIMIT 50;

上一页方向把 < 改为 > 并按 ASC 排序后再在应用侧反转。EXPLAIN 希望看到 type=range、key=idx_created_id、Using where，无 Using filesort。

第 8 章 聚合与分组：GROUP BY/HAVING

A 基础

题干：每类目商品数、平均价、总库存，未软删且上架，按商品数降序取前 10。

答案：

SELECT category_id,
       COUNT(*) AS product_cnt,
       AVG(price) AS avg_price,
       SUM(stock) AS total_stock
FROM product
WHERE is_deleted = 0 AND status = 1
GROUP BY category_id
ORDER BY product_cnt DESC
LIMIT 10;
B 进阶

题干：只保留商品数 ≥5 且均价 ≥100 的类目；先体验错误写法。

答案：错误写法把 COUNT(*) >= 5 塞进 WHERE 会报"聚合函数不能出现在 WHERE"（Illegal use of aggregate）。正确：

SELECT category_id, COUNT(*) AS product_cnt, AVG(price) AS avg_price
FROM product
WHERE is_deleted = 0 AND status = 1
GROUP BY category_id
HAVING COUNT(*) >= 5 AND AVG(price) >= 100;
C 挑战

题干：按日统计订单数、GMV、客单价，只保留 GMV 高于全店日均的日期。

答案：组间比较可用子查询取全店日均作基准：

SELECT DATE(created_at) AS d,
       COUNT(*) AS order_cnt,
       SUM(amount) AS gmv,
       SUM(amount)/COUNT(*) AS aov
FROM orders
WHERE status='PAID' AND is_deleted=0
GROUP BY DATE(created_at)
HAVING SUM(amount) > (
  SELECT AVG(daily_gmv) FROM (
    SELECT DATE(created_at) AS d, SUM(amount) AS daily_gmv
    FROM orders WHERE status='PAID' AND is_deleted=0
    GROUP BY DATE(created_at)
  ) x
)
ORDER BY d;

更优写法用窗口函数（第 13 章后）：在子查询里 AVG(SUM(amount)) OVER () 与每日 GMV 比较。

第 9 章 多表连接：INNER/LEFT JOIN

A 基础

题干：订单列表：order_no、创建时间、用户名、金额，只看已支付未软删，按时间倒序 50 条。

答案：

SELECT o.order_no, o.created_at, c.name AS customer_name, o.amount
FROM orders o
INNER JOIN customer c ON c.id = o.customer_id
WHERE o.status = 'PAID' AND o.is_deleted = 0
ORDER BY o.created_at DESC
LIMIT 50;
B 进阶

题干：所有用户都要出现，有订单显示最近一笔，没订单显示 NULL。

答案：

SELECT c.id, c.name, o.order_no, o.amount, o.created_at
FROM customer c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.status = 'PAID' AND o.is_deleted = 0;

右表 status 条件必须写在 ON 里；写 WHERE 会把"右列全 NULL"的用户行过滤掉，LEFT JOIN 退化成 INNER JOIN。"最近一笔"可用窗口函数 ROW_NUMBER 按用户分区取 rn=1。

C 挑战

题干：找出从不买 3 号类目的用户（LEFT JOIN 版本）。

答案：

SELECT c.id, c.name
FROM customer c
LEFT JOIN orders o ON o.customer_id = c.id
LEFT JOIN order_item oi ON oi.order_id = o.id
LEFT JOIN product p ON p.id = oi.product_id AND p.category_id = 3
WHERE p.id IS NULL;

最贵的一步是三表连接后的分组/去重——订单一对多会让行数膨胀；改写为 NOT EXISTS 更直观（第 11 章）。

第 10 章 子查询：标量/行/表子查询

A 基础

题干：查出价格高于全站均价的 3 号类目商品。

答案：

SELECT id, name, price
FROM product
WHERE category_id = 3
  AND price > (SELECT AVG(price) FROM product WHERE is_deleted = 0);
B 进阶

题干：用 IN 写出买过 3 号类目商品的用户。

答案：

SELECT id, name FROM customer
WHERE id IN (
  SELECT o.customer_id
  FROM orders o
  JOIN order_item oi ON oi.order_id = o.id
  JOIN product p ON p.id = oi.product_id
  WHERE p.category_id = 3 AND o.status = 'PAID'
);
C 挑战

题干：用行构造器查每类目最贵商品，再改 JOIN 版本对比。

答案：

-- 行构造器版
SELECT id, name, category_id, price
FROM product
WHERE (category_id, price) IN (
  SELECT category_id, MAX(price)
  FROM product WHERE is_deleted = 0
  GROUP BY category_id
);

-- JOIN 版
SELECT p.id, p.name, p.category_id, p.price
FROM product p
JOIN (
  SELECT category_id, MAX(price) AS max_price
  FROM product WHERE is_deleted = 0
  GROUP BY category_id
) m ON m.category_id = p.category_id AND m.max_price = p.price;

行构造器版更紧凑；JOIN 版在"并列最高价"时会返回多行（行构造器版同样），这是业务口径问题，不是语法问题。

第 11 章 EXISTS 与 IN 的选择

A 基础

题干：IN 与 EXISTS 两版"下过已支付订单的用户"，说明 8.0 执行计划。

答案：

-- IN
SELECT id, name FROM customer
WHERE id IN (SELECT customer_id FROM orders WHERE status='PAID');
-- EXISTS
SELECT id, name FROM customer c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status='PAID');

MySQL 8.0 优化器通常把两者都改写成 Semi Join（半连接）：以 customer 为驱动表、orders 走 customer_id 索引命中即止，EXPLAIN 可见 SEMI JOIN / Start temporary 类提示。

B 进阶

题干：插入 orders.customer_id = NULL 的行，对比 NOT IN 与 NOT EXISTS。

答案：NOT IN 版本返回 0 行——customer_id NOT IN (..., NULL) 中每行与 NULL 比较得 UNKNOWN，整体恒非 TRUE。NOT EXISTS 版本正常返回"没下过单"的用户，不受 NULL 影响。

C 挑战

题干：用 NOT EXISTS 写"从未买过 3 号类目商品的用户"。

答案：

SELECT c.id, c.name

第 19 章 B+ 树：索引为什么是这个结构

A 基础

题干：执行 SHOW VARIABLES LIKE 'innodb_page_size'; 确认页大小；然后口算：若扇出为 1000、每叶子页放 100 行，两层、三层 B+ 树各能装多少行？

答案：页大小默认 16384（16KB）。两层：根页 1000 个指针 × 每个叶子页 100 行 = 10 万行。三层：1000（根）× 1000（内部页）× 100（叶子行）= 1 亿行。

B 进阶

题干：画出"按主键 id=5000000 查一行"在 B+ 树中的完整路径，并说明读几个页。

答案：从根页开始，按键值在内部页的有序键中二分定位到对应指针，下钻到下一层内部页，继续二分定位，再下钻到叶子页，命中 id=5000000 的叶子记录读出整行。读页次数 = 树高（通常 2~3 个页），其中根页常驻内存，实际磁盘 IO 约 2 次。

C 挑战

题干：为什么联合索引列数越多、索引扇出越小、树越高？从"一个 16KB 索引页能放多少个键"推导，并给出控制索引列数的两条原则。

答案：索引键 = 多列拼接，列越多键越长，一个 16KB 页能放的键越少，扇出下降，要装同样多行就需要更多层、树变高、查询 IO 变多。两条原则：① 联合索引控制在 3~4 列以内；② 索引列尽量用短类型（BIGINT 优于长 VARCHAR），并把高频等值、高区分度列放最左。

第 21 章 联合索引与最左前缀

A 基础

题干：表 t(a,b,c,d) 有 idx_abc(a,b,c)，判断四条 WHERE 的命中情况。

答案：① a=1 AND b=2 AND c=3：三列全命中；② b=2 AND a=1：仍命中 a、b（优化器自动重排列序）；③ c=3：不命中（跳过最左列 a）；④ a=1 AND c=3：只命中 a（b 断档，c 无法用索引）。

B 进阶

题干：建 orders(user_id,status,created_at) 灌数据，建 idx_user_status_time，执行两条查询看 EXPLAIN 的 key 与 rows。

答案：WHERE user_id=1 AND status=2 与带 created_at 范围的查询，key 都应为 idx_user_status_time；对比单 WHERE status=2（不带 user_id）应退化为 ALL 或扫描更多行，验证最左前缀。

C 挑战

题干：三条查询 ① city=? AND age>=18 ② city=? AND name=? ③ city=? AND age=? AND name=?，设计联合索引列序并说明覆盖与断档。

答案：建 (city, name, age) 或 (city, age, name)。① city 等值 + age 范围，city 命中、age 范围扫；② city+name 等值全命中；③ 三列全命中。若把范围列 age 放中间（city,age,name），则 ②③ 中 name 会在 age 范围后断档——故等值列 name 应在范围列 age 之前。

题干：按模板建 biz_order（id 主键、NOT NULL 业务列、三审计列、utf8mb4、每列 COMMENT）。

答案：CREATE TABLE biz_order(id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键', status TINYINT NOT NULL DEFAULT 0 COMMENT '状态', created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间', updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间', is_deleted TINYINT NOT NULL DEFAULT 0 COMMENT '软删', PRIMARY KEY(id)) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';

B 进阶

题干：article 主表垂直拆成 article + article_content，写出建表与两种查询的 JOIN。

答案：article(id,title)；article_content(article_id, content, PRIMARY KEY(article_id))。列表查标题只碰主表；读正文 SELECT c.content FROM article a JOIN article_content c ON c.article_id=a.id WHERE a.id=?。

C 挑战

题干：订单列表显示用户名，范式 JOIN 还是反范式冗余？

答案：读多写少、高频、JOIN 昂贵 → 反范式在 orders 冗余 user_name 快照；用户改名属低频且历史订单本应保持下单时快照，一致性可接受。若要求用户名实时一致（如后台管理页），则走范式 JOIN user 表。

第 28 章 数据类型精讲与选型原则

A 基础

题干：为商品表选类型：id 主键、price 金额、status 三态、title 商品名、created_at 业务时间。

答案：id BIGINT UNSIGNED AUTO_INCREMENT；price DECIMAL(12,2)；status TINYINT；title VARCHAR(100)；created_at DATETIME。

B 进阶

题干：对比 0.1+0.2 与 DECIMAL(10,2) 的 0.1+0.2，解释金额为何不用 DOUBLE。

答案：SELECT 0.1+0.2 在浮点下得 0.30000000000000004；DECIMAL 精确得 0.30。DOUBLE 二进制浮点无法精确表示十进制小数，累加误差放大导致对账不平，故金额必须用 DECIMAL。

C 挑战

题干：用户偏好 5~20 键值对、未来会新增，选 JSON 还是拆固定列？

答案：半结构化、低频读、键不定 → 用 JSON（8.0 支持多值索引）；若某键成为高频查询/排序条件，则把它拆成独立列加索引。折中：主数据拆列，长尾扩展塞 JSON。

四第四篇 事务与锁（第 29-37 章）

第 29 章 事务与 ACID

A 基础

题干：account(id,balance) 两行，BEGIN 包两条转账 UPDATE，COMMIT 验证；再演示回滚撤销。

答案：BEGIN; UPDATE account SET balance=balance-100 WHERE id=1; UPDATE account SET balance=balance+100 WHERE id=2; COMMIT; 验证总额不变；故意少转则 ROLLBACK 后余额恢复。

B 进阶

题干：用 SAVEPOINT 分段事务，ROLLBACK TO SAVEPOINT 只撤销后半段。

答案：BEGIN; UPDATE 前半; SAVEPOINT sp1; UPDATE 后半; ROLLBACK TO SAVEPOINT sp1; COMMIT;——前半保留、后半撤销。

C 挑战

题干：把 HTTP 调用放进事务，分析三个风险并改进。

答案：① HTTP 期间行锁一直占着；② 对方读到的可能是你未提交数据；③ 远程超时把事务拖成长事务。改进：先完成数据库必要写并提交，再发远程调用；或事务只包核心扣减，远程调用放到 COMMIT 之后。

第 30 章 四个隔离级别与现象实验

A 基础

题干：两会话都设 RC，复现不可重复读。

答案：会话 A 两次读 balance，中间会话 B UPDATE ...; COMMIT;，A 两次读到不同值——RC 下不可重复读发生。

B 进阶

题干：同操作在 RR 下复现，观察两次结果是否一致并解释。

答案：RR 下 A 两次读同一行结果一致（都是第一次读的快照），因为 RR 只在第一次 SELECT 建 ReadView、之后复用，B 的提交对 A 不可见。

C 挑战

题干：对比 RC 与 RR 在范围查询下的行为，分析为何高并发常把默认 RR 降到 RC。

答案：RC 每次读都建快照，能读到最新已提交值，但无间隙锁、锁范围更小、并发更高、死锁更少；RR 靠 MVCC 快照 + 临键锁保证可重复读，但锁范围大、并发略低。互联网读多写多、追求吞吐，常降到 RC，业务上可接受"读到稍旧已提交值"。

第 31 章 MVCC：多版本并发控制

A 基础

题干：用自己的话解释 RR 下同一事务两次读同一行为何结果一样。

答案：RR 只在事务第一次 SELECT 时建一次 ReadView（快照），之后所有读都复用这份快照；别的事务的提交对该 ReadView 不可见，故两次读结果一致。

B 进阶

题干：RR 下 A 第一次读 100，B 改成 50 提交，A 分别跑普通 SELECT 与 FOR UPDATE，对比差异。

答案：普通 SELECT（快照读）仍读 100；SELECT ... FOR UPDATE（当前读）读到 50（最新已提交值）并加锁。

C 挑战

题干：画一行被三事务依次修改后的版本链（标 trx_id），模拟 ReadView（活跃=[200,300]）判断能看到哪个版本。

答案：版本链如 当前行(trx=400) → undo(trx=300) → undo(trx=200) → undo(trx=100)。活跃事务=[200,300]、min=200、max=400。trx=400 ≥ max 不可见；trx=300 在活跃列表不可见；trx=200 在活跃列表不可见；trx=100 < min 可见——故读到 trx=100 的版本。

第 32 章 锁的分类：全局/表/行

A 基础

题干：会话 A 锁 id=1 不提交，会话 B 改 id=2 是否等待、改 id=1 是否阻塞。

答案：B 改 id=2（不同行）立即执行、不等待；B 改 id=1 被 A 的行锁阻塞。

B 进阶

题干：用兼容矩阵解释为何两个事务可同时给不同行加排他行锁、表写锁会被 IX 挡住。

答案：IX 与 IX 互相兼容（意向锁只是表级路标），故多个事务可并发加不同行的排他行锁；但表写锁与 IX 冲突，故有人想锁整表时被所有 IX 挡住。

C 挑战

题干：复现 MDL 事故：会话 A 慢 SELECT 不结束，会话 B 执行 ALTER，观察会话 C 的 SELECT 是否被堵。

答案：A 的慢 SELECT 占着该表 MDL 读锁；B 的 ALTER 要拿 MDL 写锁，排在 A 的读锁后；之后 C 的新 SELECT 要拿读锁，又排在 B 的写锁后——一张表被全线堵死。这是 MDL 读锁/写锁排队逻辑。

第 33 章 行锁、间隙锁与临键锁

A 基础

题干：主键 5/10/15/20，标出 WHERE id>=10 AND id<=15 FOR UPDATE 的临键锁区间。

答案：临键锁左开右闭：锁住 (5,10]、(10,15]、(15,20]（含 10、15 记录及其左侧间隙）。

B 进阶

题干：主键 10/20/30，会话 A WHERE id=25 FOR UPDATE（未命中），会话 B 插 15、25、35 哪些被挡。

答案：唯一等值未命中退化成间隙锁，锁住 (20,30)。插 25 落在 (20,30) 被挡；插 15 落 (10,20) 不受影响、插 35 落 (30, +∞) 不受影响。

C 挑战

题干：对比唯一索引等值命中与普通索引范围扫描的加锁差异，从防幻读必要性推导。

答案：唯一索引等值命中确定只有一行，唯一约束已防同键再插，退化为纯记录锁（不加间隙锁）；普通索引范围扫描无法确定边界，为防范围插入幻读，必须加临键锁（记录+间隙）。

第 34 章 死锁：复现、分析与避免

A 基础

题干：复现死锁：两会话交叉更新 id=1 与 id=2，看哪个会话报 1213，再看 LATEST DETECTED DEADLOCK。

答案：交叉更新时一个会话报 ERROR 1213 (40001) Deadlock；SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段列出两事务各持锁、等锁，并说明回滚了哪一个。

B 进阶

题干：改成两会话都按 id 升序（先 1 后 2）更新，还死锁吗？为何固定顺序打破循环等待。

答案：不再死锁。两事务都先拿 id=1 再拿 id=2，第一个拿到 id=1 后第二个等 id=1，形不成"A 等 B、B 等 A"的环，故无循环等待。

C 挑战

题干：8.0 用 data_locks / data_lock_waits 三表 JOIN 查出"当前谁阻塞谁"。

答案：JOIN data_lock_waits（requesting_engine_transaction_id=等待方, blocking=被等方）与 data_locks（按事务 id 取锁详情），输出等待方、被等方、锁住的表与值；配合 innodb_trx 看事务状态。

第 35 章 长事务的危害与治理

A 基础

题干：一会话 BEGIN 不提交，另一会话查 innodb_trx 读 trx_started 与已运行秒数。

答案：另开会话 SELECT trx_id,trx_started,TIMESTAMPDIFF(SECOND,trx_started,NOW()) FROM information_schema.innodb_trx; 读到那个未提交事务及其运行时长。

B 进阶

题干：写 SQL 查出所有运行超 10 秒的事务（trx_id、当前 SQL、已运行秒数）。

答案：SELECT trx_id,trx_query,TIMESTAMPDIFF(SECOND,trx_started,NOW()) AS run_sec FROM information_schema.innodb_trx WHERE TIMESTAMPDIFF(SECOND,trx_started,NOW())>10 ORDER BY run_sec DESC;

C 挑战

题干：代码在事务里调外部支付接口，分析风险并重构。

答案：风险：远程调用拉长事务、行锁长占、undo 膨胀、主从延迟。重构：事务内只做数据库核心扣减并尽快提交，把外部支付调用放到 COMMIT 之后（或用本地消息表/最终一致方案），避免远程网络不可控拖长事务。

第 36 章 undo 与 redo 的分工

A 基础

题干：对比 undo / redo 记旧值还是新值、各支撑 ACID 哪个字母。

答案：undo 记旧值，支撑 A 原子性（回滚）与 MVCC 版本链；redo 记新值，靠 WAL 支撑 D 持久性（崩溃不丢）。

B 进阶

题干：查 innodb_flush_log_at_trx_commit 并解释设 1 与设 2 的宕机差异。

答案：设 1 每次提交都把 redo 刷盘，宕机不丢已提交数据；设 2 只写操作系统缓存、每秒刷盘，宕机（断电）最多丢最后 1 秒已提交数据。

C 挑战

题干：描述一次提交完整流程，并说明"redo prepare 后、binlog 写完前"宕机如何判断提交/回滚。

答案：流程：改内存缓冲池 → 写 undo 旧值 → redo prepare → 写 binlog → redo commit → 数据页异步刷。恢复时：redo prepare 但 binlog 不完整/未写完 → 回滚该事务；redo prepare 且 binlog 已完整写入 → 提交（重做）该事务——靠两阶段提交对齐 redo 与 binlog。

第 37 章 锁等待实战：谁卡住了谁

A 基础

题干：模拟锁等待：会话 A 锁 id=1 不提交，会话 B 更新 id=1 卡住，用 SHOW PROCESSLIST 找 B 的连接 Id 与 State。

答案：SHOW PROCESSLIST 找到 B 的连接 Id（在等锁），State 显示锁等待相关（如 Updating 但 Time 很大）。

B 进阶

题干：用 innodb_trx 找元凶事务（trx_query 为 NULL），拿 trx_mysql_thread_id 并 KILL，观察 B 是否解除。

答案：SELECT trx_id,trx_mysql_thread_id,trx_query FROM information_schema.innodb_trx; 找到 trx_query=NULL（开事务睡觉）却持锁的元凶，KILL 其 trx_mysql_thread_id；元凶回滚、行锁释放，B 的 UPDATE 立刻继续。

C 挑战

题干：8.0 用 data_locks 与 data_lock_waits 写出"等待方→被等方→锁住表与值"的 JOIN 查询。

答案：JOIN data_lock_waits（等待方 requesting_engine_transaction_id、被等方 blocking_engine_transaction_id）与 data_locks（按事务 id 取 lock_table、lock_data、lock_mode），输出三列，即完整等待链。

五第五篇 日志与主从（第 38-45 章）

第 38 章 三大日志：redo/undo/binlog

A 基础

题干：用 SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';、SHOW VARIABLES LIKE 'binlog_format';、SHOW VARIABLES LIKE 'sync_binlog'; 查出本机实例的三个值，并记录它是"双 1"配置还是妥协配置。

答案：三个值分别是 innodb_flush_log_at_trx_commit、binlog_format（8.0 默认 ROW）、sync_binlog。若前两者（redo 刷盘=1、binlog 刷盘=1）同时为 1 即双 1；任一为 0/2 或 sync_binlog=N 都是妥协配置，宕机可能丢数据或主从不一致。

B 进阶

题干：在 ROW 格式下执行 UPDATE product SET price = price * 0.9 WHERE id = 2;，再用 SHOW BINLOG EVENTS 观察该事件记录的是语句还是行镜像，并解释为什么 ROW 在从库上更安全。

答案：ROW 格式记录的是改行前后的行镜像（整行数据），不是原始 SQL。从库重放行镜像时，无论原语句含 NOW()/UUID() 等函数，结果都与主库一致，避免 STATEMENT 模式下函数重放结果不同导致的主从不一致。

C 挑战

题干：打开一个事务 BEGIN; UPDATE ...; 故意不提交，在另一个会话查询 information_schema.INNODB_TRX，思考：这条长事务如果持续一小时，undo log 会发生什么？写一段话说明 purge 为什么被它挡住。

答案：长事务持有最早的读视图（ReadView），它"可见"的旧版本必须保留。purge 线程只能清理所有事务都不再需要的旧版本；只要长事务未提交，它的 ReadView 覆盖那些旧版本，purge 就不能删，undo log 段持续膨胀，最终吃磁盘并拖慢性能。

第 39 章 两阶段提交与崩溃恢复

A 基础

题干：用 SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; 与 SHOW VARIABLES LIKE 'sync_binlog'; 确认本机是否双 1，并用自己的话写出"只开其中一个"为什么不够。

答案：双 1 = redo 提交即刷盘 + binlog 提交即刷盘。只开 redo 不开 binlog：宕机时 binlog 未含的事务在主库却已提交，从库少数据且无法自动修复；只开 binlog 不开 redo：引擎崩溃恢复时已提交事务可能丢。两者必须一起为 1 才能既不丢已提交事务、又保证主从不分叉。

B 进阶

题干：假设某个事务停在 prepare 阶段、binlog 尚未写入，此时机器断电重启。请描述恢复程序会对该事务做什么，以及为什么这样做主库和未来的从库不会分叉。

答案：恢复程序重放 redo 后，扫描到处于 prepare 的事务，按 XID 去 binlog 查——查不到，说明 binlog 未落盘、从库不可能收到该事件，于是回滚该事务。主库回滚、从库也没有这条事件，两边一致，不会分叉。

C 挑战

题干：思考：为什么两阶段提交能容忍"prepare 后崩溃"，却不能容忍"commit 后立刻崩溃"？如果 commit 日志写一半宕机，恢复程序凭什么敢再提交一次？

答案：prepare 后崩溃时事务对外不可见，回滚它无损；commit 后崩溃时，由于 redo 的 commit 日志与 binlog 的 XID 对应，恢复程序只要发现 binlog 里有该 XID（说明 binlog 已写完、从库可能已重放），就敢再次提交——因为不提交反而会造成主从分叉。binlog 是否存在是事务对外可见的唯一裁判。

第 40 章 主从复制原理与搭建

A 基础

题干：写出主库 my.cnf 中复制必需的三行配置，并说明 server-id 为什么不能两台机器都写 1。

答案：server_id=1、log_bin=mysql-bin、binlog_format=ROW（8.0 GTID 另配 gtid_mode）。server-id 在复制组内必须唯一；两台机器同为 1 会导致复制协议无法区分实例、 Dump 线程行为异常，是最隐蔽的部署错误。

B 进阶

题干：在本机起两个 MySQL 实例（或 Docker 起一主一从），照本章步骤完成搭建，并把 SHOW REPLICA STATUS 里的 Replica_IO_Running、Replica_SQL_Running 截图记录为两个 Yes。

答案：关键结果 = Replica_IO_Running: Yes 且 Replica_SQL_Running: Yes，且主库插入的数据在从库可查到。常见失败：IO=No 多为账号/网络/server-id；SQL=No 多为从库被写过或语句不兼容。

C 挑战

题干：故意在从库上 INSERT 一条与主库主键冲突的数据，再在主库插入同主键记录，观察从库 SQL 线程报错。查阅 Last_SQL_Error，写出你会如何用 SET GLOBAL sql_replica_skip_counter = 1;（或 GTID 方式）绕过这一条并说明风险。

答案：用 sql_replica_skip_counter=1 跳过下一条事件。风险：跳过意味着该事务在从库缺失，主从数据从此不一致，仅用于救急；事后必须补数据并核对。GTID 方式是注入空事务补 GTID。

第 41 章 主从延迟：测量与缓解

A 基础

题干：在你的主从环境执行 SHOW REPLICA STATUS\G，记录 Seconds_Behind_Source 的值，并解释 IO 线程断开时这个值会变成什么。

答案：SBS = SQL 线程正在执行事件的时间戳与现在之差。IO 线程断开、不再拉 binlog 时，SBS 会显示 0 或 NULL，不代表没延迟——监控必须同时看 Replica_IO_Running 与 Replica_SQL_Running 是否都 Yes。

B 进阶

题干：在主库建 repl_heartbeat 心跳表，用事件调度器或脚本每分钟更新一次；在从库写查询算出毫秒级延迟，对比它与 SBS 的差异。

答案：心跳表 REPLACE INTO repl_heartbeat VALUES(NOW(6)); 从库 SELECT TIMESTAMPDIFF(MICROSECOND,(SELECT MAX(ts) FROM repl_heartbeat),NOW(6))/1000 AS delay_ms。心跳表更贴近真实延迟，SBS 在 IO 断开时失真。

C 挑战

题干：在主库执行一条改百万行的大事务，观察从库延迟曲线；然后把它拆成每批 5000 行的循环小事务，再测一次。写一段话说明为什么"分批"能让延迟曲线变得平缓。

答案：大事务是一条巨大 binlog 事件，从库必须一口气重放完，期间延迟一路上涨；分批小事务让从库能在批次间消化队列，延迟被切成一段段小峰，整体曲线平缓，不会堆积成分钟级延迟。

第 42 章 半同步复制

A 基础

题干：写出主库与从库各自需要安装的半同步插件名，并说明 rpl_semi_sync_master_timeout 默认值与退化行为。

答案：主库装 rpl_semi_sync_master（semisync_master.so），从库装 rpl_semi_sync_slave（semisync_slave.so）。rpl_semi_sync_master_timeout 默认 10000 毫秒（10 秒），超时后主库自动退化为异步复制，不再等从库 ACK。

B 进阶

题干：在你已搭好的主从上开启半同步，用 SHOW STATUS LIKE 'Rpl_semi_sync_master_status'; 确认 ON；然后在从库执行 STOP REPLICA; 观察主库写延迟变化，再恢复。

答案：开启后 Rpl_semi_sync_master_status=ON。STOP REPLICA 后从库不再 ACK，主库写延迟上升，直到超时退化为异步，延迟回落——验证了退化机制。

C 挑战

题干：半同步的 AFTER_SYNC 与 AFTER_COMMIT 两种等待点有何差别？查资料后写一段话：为什么 AFTER_SYNC 下所有客户端看到的提交状态是一致的，而 AFTER_COMMIT 下主库宕机切换时可能出现"刚提交却查不到"的窗口？

答案：AFTER_SYNC 先把 binlog 同步到从库、再返回客户端，所有客户端在提交返回后看到一致状态；AFTER_COMMIT 是先在引擎提交、再通知客户端，主库宕机切换时，刚提交的事务可能尚未被从库收到，新主上查不到，出现"刚提交却查不到"的窗口。

第 43 章 GTID 与复制拓扑

A 基础

题干：写出 GTID 的结构，并解释 server_uuid 从哪里来、为什么不要手动改它。

答案：GTID = server_uuid:transaction_id。server_uuid 是实例首次启动时自动生成、存在 data_dir/auto.cnf 的唯一标识。手动改它会破坏 GTID 集合的连续性，导致复制认为事务缺失或重复。

B 进阶

题干：在你已搭的主从上开启 GTID（先开 WARN 观察），然后用 SOURCE_AUTO_POSITION=1 重建复制，用 SHOW REPLICA STATUS 查看 Executed_Gtid_Set 是否推进。

答案：配置 gtid_mode=ON、enforce_gtid_consistency=ON；CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION=1；START REPLICA；Executed_Gtid_Set 随事务推进即成功。

C 挑战

题干：假设主库 A 宕机，你要把从库 B 提升为新主、其余从库改指向 B。写出完整切换命令序列，并说明为什么 AUTO_POSITION=1 让"找到缺哪些事务"这一步不用人工算位点。

答案：在 B 上 STOP REPLICA；用 GTID 确认 B 已追平 A（Retrieved/Executed_Gtid_Set 覆盖 A 的最后位点）；SET GLOBAL read_only=OFF 提升 B 为新主；其余从库 CHANGE REPLICATION SOURCE TO SOURCE_HOST='B'... SOURCE_AUTO_POSITION=1；START REPLICA。AUTO_POSITION=1 让从库上报自己已执行的 GTID 集合，新主自动补发缺失事务，无需人工算 binlog 文件号与偏移。

第 44 章 备份与恢复：mysqldump/xtrabackup

A 基础

题干：用 mysqldump 导出本机 mydb，新建一个空库后把 SQL 导入进去，验证两边 SELECT COUNT(*) 一致。

答案：mysqldump -uroot -p --single-transaction mydb > mydb.sql；新建空库后 mysql -uroot -p mydb_new < mydb.sql；两边 COUNT(*) 相等即成功。

B 进阶

题干：写出 --single-transaction 与 --master-data=2 各自的作用，并说明备份文件里 CHANGE MASTER TO MASTER_LOG_POS=... 这行为什么对 PITR 重要。

答案：--single-transaction 在 InnoDB 下开一致性快照备份、不锁表；--master-data=2 把备份时 binlog 位点以注释写进文件。这行位点是时间点恢复（PITR）的起点：恢复全量后从该位点重放 binlog 到误操作前一秒。

C 挑战

题干：模拟"凌晨全量 + 上午误删"场景：恢复全量后，用 mysqlbinlog --stop-datetime 重放到误操作前一秒。写出完整命令序列，并解释为什么恢复期间要先停业务写入。

答案：恢复全量备份后，mysqlbinlog --start-position=<备份位点> --stop-datetime="误操作前一秒" binlog.0000xx | mysql -uroot -p。恢复期间先停业务写入，避免新写入与重放混在一起造成数据错乱，也防止覆盖恢复中的数据。

第 45 章 binlog 的应用：Canal 数据同步

A 基础

题干：画出 Canal 同步一条 INSERT 的完整链路（MySQL → Canal → MQ → 下游），并说明主库为什么必须用 ROW 格式。

答案：MySQL 主库（ROW binlog）→ Canal Server（伪装从库、解析 binlog、记位点）→ Kafka/RocketMQ（变更事件队列）→ ES/Redis/数仓。主库必须 ROW，因为 Canal 需要行镜像才能解析出"哪行被改成什么样"。

B 进阶

题干：在本机 MySQL 建 canal 账号、确认 binlog_format=ROW，并用一句话写出 Canal instance 配置里需要填哪几项（地址/端口/账号/监听表）。

答案：CREATE USER 'canal'@'%' IDENTIFIED BY ...; GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.*；确认 binlog_format=ROW。instance 配置填：主库地址、端口、canal 账号密码、要监听的库表白名单（如 mydb.order.*）。

C 挑战

题干：如果 Canal 投递到 MQ 后，某个下游（ES）消费失败积压了一天，你会怎么保证数据最终对齐？思考"业务双写"与"binlog 订阅"在故障恢复上各要付出什么代价。

答案：保证 MQ 持久化与重试，下游消费失败可重放；用 Canal 记录的位点重放缺失事件。binlog 订阅把"数据变更"统一在源头，下游失败只需重放，业务无侵入；业务双写则要在每个接口里处理失败重试，耦合高、易漏写，故障恢复成本分散在各处。

六第六篇 高可用与分库分表（第 46-54 章）

第 46 章 高可用架构总览

A 基础

题干：用自己的话写出高可用要做的三段事，并解释 RTO 与 RPO 分别指什么。

答案：三段事 = 故障检测 → 选主提升 → 客户端切换。RTO（恢复时间目标）是主库挂到恢复服务的时间；RPO（恢复点目标）是最多能容忍丢多少数据。高可用 = 复制（数据冗余）+ 故障转移（自动切换）+ 客户端寻址（应用无感）。

B 进阶

题干：列出至少三种"让应用连到新主"的手段（VIP/中间件/DNS），并说明为什么 DNS 生效慢、不适合做秒级切换。

答案：VIP（虚拟 IP 漂移到新主）、中间件（ProxySQL 知道新主）、DNS（改域名指向）。DNS 有缓存与 TTL，生效需要秒到分钟级，不适合秒级切换，只做兜底。

C 挑战

题干：什么是脑裂？为什么"两个节点都认为自己是主"会造成数据错乱？查资料后写一段话，说明多数派仲裁（如 3 节点集群选 2 票）如何防止脑裂。

答案：脑裂是网络分区后两边都认为自己是主、同时接受写，导致数据分叉。多数派仲裁要求主必须拿到多数节点投票（3 节点需 2 票）；分区后少数派那侧凑不齐多数，自动降级为只读，无法当选主，从而避免两个主同时被写。

第 47 章 MHA 与 MGR

A 基础

题干：写出 MHA Manager 与 MHA Node 的分工，并说明 MHA 选新主时依据什么挑从库。

答案：MHA Manager 独立部署、监控整个主从集群并做故障判定与切换；MHA Node 装在每台 MySQL 机器上、被 Manager 调用执行具体操作。选新主时 Manager 对比各从库的 relay log/binlog 位点，挑数据最新（最接近主库）的那台提升为新主。

B 进阶

题干：列出 MGR 单主模式与多主模式的区别，并解释为什么 MGR 天然不容易脑裂。

答案：单主模式组里只有一个主接受写、其余只读，主挂了组自动选新主（最常用）；多主模式多节点都可写，冲突由内部检测解决。MGR 每个事务提交要组内多数派认可，分区后少数派凑不齐多数、无法提交，天然防脑裂。

C 挑战

题干：你的团队有一套跑了三年的一主三从系统，主库偶尔抖动。现在要加自动高可用，你会选 MHA 还是 MGR？写出三点理由，并说明为什么节点数要保持奇数。

答案：倾向 MHA：① 对现有主从侵入小、平滑升级；② MGR 需至少 3 节点且对网络延迟敏感，存量系统改造大；③ MHA 直接挑选数据最新从库升主，契合现有 GTID 复制。节点数保持奇数（3/5）是为了多数派能达成——偶数节点（如 2）分区后两边都凑不齐多数，集群直接不可用。

第 48 章 读写分离与路由中间件

A 基础

题干：写出读写分离的基本路由规则，并指出哪两类 SELECT 必须走主库。

答案：写走主库、普通 SELECT 走从库。两类必须走主：① 事务内的读（前面写了后面读，否则读不到自己刚写的）；② 写后读（刚下单就查订单，避免主从延迟坑）。

B 进阶

题干：对比 ProxySQL（代理层）与 ShardingSphere-JDBC（应用层）的优缺点，说明你会怎么选型。

答案：代理层（ProxySQL）独立部署、应用无感、统一治理，但多一跳且自身要高可用；应用层（ShardingSphere-JDBC）嵌进 Java 应用、无额外部署、性能好，但要随应用升级。多语言栈选代理层，Java 单栈、追求性能选 JDBC。

C 挑战

题干：主库故障自动切换到新主后，为什么中间件的路由表必须跟着更新？如果不更新会发生什么？结合"脑裂"与"写旧主"写一段话。

答案：中间件若仍把写路由到已失效的旧主地址，写会失败或落到错误节点；若旧主实际已降级却仍被写，等于两个主同时被写——脑裂，数据分叉。所以切换后中间件必须通过心跳/主动命令把路由表更新到新主，否则写旧主与脑裂风险并存。

第 49 章 为什么分库分表：容量与并发

A 基础

题干：说出单库的两条天花板，并说明为什么读写分离只能缓解读、缓解不了写。

答案：容量天花板（单表行数）与并发天花板（写 QPS）卡在单机。读写分离把读分摊到从库，但写永远在主库，主库写 QPS 顶到单机上限后，读写分离救不了写增长。

B 进阶

题干：列出分库分表带来的至少四个代价（跨库 join、分布式事务、全局 ID、扩容迁移），并各用一句话解释。

答案：跨库 join 没了，要应用层组装或冗余；分布式事务跨分片，本地事务不够用；全局唯一 ID，分片间自增会撞车；扩容迁移难，分片数定了再加要搬数据。

C 挑战

题干：你的业务现在单表 200 万行、写 QPS 800，老板说"上分库分表显得技术先进"。你会怎么劝阻？写出拆分前应该先做哪几件事（索引/SQL 优化、读写分离、增长预估）。

答案：200 万行远未到天花板，分库分表只会白背复杂度。先做：① 索引与 SQL 优化（消除全表扫描、回表）；② 读写分离把读分摊到从库；③ 按年增速预估容量，确认两三年内真会撞天花板再拆。能靠优化扛住的阶段，不要急着拆。

第 50 章 拆分策略：垂直/水平/分片键

A 基础

题干：用自己的话区分垂直拆分与水平拆分，并说明为什么垂直拆通常是第一步。

答案：垂直拆是按业务域把大库切成用户库/订单库/商品库，表还是那些表；水平拆是按分片键把同一表切成 N 份分表。垂直拆是第一步，因为它先做业务解耦，发现某个核心表（订单流水）仍太大，再对它做水平拆分。

B 进阶

题干：为订单表选择分片键：候选有 user_id、status、create_time。按"均匀/高基数/查询必带"三个标准评判，选出最合适的并说明理由。

答案：选 user_id。status 只有几种取值（低基数），按它分片永远只有几个分片有数据；create_time 是范围、新数据压最新分片（热点）。user_id 取值散、高基数，且"按用户查订单"是高频查询、必带 user_id，符合分片键三标准。

C 挑战

题干：按 create_time 范围分片时，为什么最新数据会全压最后一个分片？设计一个方案（叠加哈希打散）让时间维度既保留范围能力又不产生热点。

答案：按 create_time 范围分片，新数据都落在最新时间区间，即最后一个分片，写集中。方案：在时间范围分片上再叠加一层 user_id 哈希打散——同一时间区间的数据按哈希散到多个分片，既保留按时间范围查询的能力，又把写热点分散到多分片。

第 51 章 ShardingSphere 实战

A 基础

题干：解释逻辑表、真实分片、分片键、分片算法四个概念，并举一个 order 表分片配置的例子。

答案：逻辑表 = 应用写的统一表名（order）；真实分片 = 实际数据所在的物理表（order_0..order_3）；分片键 = 路由依据的列（user_id）；分片算法 = 怎么按分片键算落点（MOD 取模）。配置里 actualDataNodes 列真实分片、shardingColumn 指分片键、shardingAlgorithm 指算法。

B 进阶

题干：写出"order 表按 user_id 对 4 取模分片"的 ShardingSphere 配置骨架，并指出 shardingColumn 与 shardingAlgorithm 各起什么作用。

答案：order 表 actualDataNodes=ds${0..1}.order_${0..3}，tableStrategy.standard.shardingColumn=user_id，shardingAlgorithms.order_mod type=MOD、sharding-count=4。shardingColumn 指定用哪列路由；shardingAlgorithm 指定用什么算法（MOD=取模）算落点。

C 挑战

题干：为什么分片后不能再用数据库自增主键？如果某条 SQL 没带 user_id，ShardingSphere 会怎么做？这种广播查询在大分片下有什么风险？

答案：分片后每个分片库都从 1 自增，跨分片主键会撞车。SQL 不带 user_id 时，ShardingSphere 只能把查询广播到所有分片再归并结果。广播在大分片下会让所有分片都执行该查询，延迟暴涨、拖垮集群——所以业务查询必须带分片键。

第 52 章 分布式 ID：雪花算法

A 基础

题干：画出雪花算法 64 位的四段结构，并说明为什么它是"趋势递增"的。

答案：64 位 = 符号 1bit + 时间戳 41bit + 机器 10bit + 序列号 12bit。高位是时间戳，随时间增大，所以生成的 ID 整体随时间递增（趋势递增），对 B+ 树索引写入友好。

B 进阶

题干：比较雪花算法与 UUID 作为主键的差异，说明为什么无序主键对 B+ 树索引写入不友好。

答案：雪花趋势递增、本地生成、高性能；UUID 无序、长度长。无序主键插入 B+ 树时新页位置随机，导致页频繁分裂、碎片多、索引体积膨胀，写入性能下降。

C 挑战

题干：如果两台机器的机器位配成了相同值，会发生什么？进一步思考：NTP 把某台机器时钟往回拨 5 秒，雪花发号器该如何处理才能避免重复发号？

答案：机器位相同会导致两台机器在同一毫秒序列号区间发重复 ID，撞主键。时钟回拨时，发号器必须检测到当前时间小于上次发号时间，拒绝继续发号、等待时钟追上或报错，而不是照发——否则会生成已发过的 ID。

第 53 章 扩容与数据迁移

A 基础

题干：写出平滑迁移的四步，并说明为什么不能停机重导数据。

答案：四步 = 存量搬运 + 增量同步 + 一致性校验 + 灰度切流。停机重导时间长、风险大，还丢迁移期间的增量数据；平滑迁移让新老并行，追平后再切流，不丢数据、可回滚。

B 进阶

题干：设计一个校验方案：对比老库与新库同一分片的数据一致性（行数 + 抽样字段），写出你会用的 SQL。

答案：SELECT COUNT(*) FROM order_0（老库）与新库同表对比行数；再按主键分段抽样 SELECT order_id,user_id,amount FROM order_0 WHERE order_id BETWEEN ? AND ? ORDER BY order_id，两边比对。行数对得上不代表字段值一致，必须抽样核对内容。

C 挑战

题干：为什么预分片（一开始就建 128 个逻辑分片）能让未来扩容几乎不迁移数据？结合"路由 vs 数据分布"写一段话。

答案：预分片把数据分布提前定好（128 个逻辑分片），扩容只是增加物理库、调整路由映射，把某几个逻辑分片的路由指向新库——数据本身不用搬动，因为它从一开始就按逻辑分片组织。扩容从"重排数据"变成"改路由"，几乎零迁移。

第 54 章 跨库查询与分布式事务

A 基础

题干：写出跨库 join 的两种替代方案（冗余字段、应用层组装），并说明为什么在线跨库 join 不可取。

答案：冗余字段把高频关联字段（商品名）冗余进订单表；应用层组装分别查订单、查用户再内存拼接。在线跨库 join 要把多分片数据拉到一起归并，数据量大时极慢，不可取。

B 进阶

题干：列出分布式事务的三种思路，并比较 MySQL XA 与柔性事务（TCC/Saga）在一致性与性能上的取舍。

答案：三思路 = XA 强一致、柔性事务（最终一致）、本地事务+补偿。XA 两阶段提交强一致但阻塞、性能差，适合小流量高一致；柔性事务（TCC/Saga）允许短暂不一致、可补偿，高可用，适合高并发业务。

C 挑战

题干：设计"下单扣库存加积分"的事务方案：它要写订单库、扣库存库、加积分库。你会选 XA 还是本地事务+消息表对账？写出理由与补偿流程。

答案：选本地事务+消息表对账。理由：XA 两阶段提交阻塞、性能差，高并发下单顶不住。流程：本地事务写订单与消息表（同一事务）；异步投递扣库存、加积分；定时对账任务扫描消息表，对失败/未补偿的下游重试或人工介入，保证最终一致。

七第七篇 运维调优（第 55-63 章）

第 55 章 核心参数调优

A 基础

题干：用 SHOW VARIABLES 查出 max_connections、innodb_buffer_pool_size、long_query_time 的当前值，并说明每个是动态还是只读参数。

答案：执行 SHOW VARIABLES LIKE 'max_connections'; 等。max_connections 是动态变量（SET GLOBAL 即时生效）；innodb_buffer_pool_size 在 8.0 支持在线调整大小（动态，异步 resize）；long_query_time 是动态变量（SET GLOBAL 立即生效）。区分方法：查 performance_schema.variables_info 的 MIN/MAX 与 SET_TIME，或看官方文档的 Variable Type。

B 进阶

题干：在线用 SET PERSIST 把 long_query_time 从默认改为 0.5，再从 persisted_variables 确认，最后 RESET PERSIST 撤销。

答案：SET PERSIST long_query_time = 0.5; → SELECT VARIABLE_NAME,VARIABLE_VALUE FROM performance_schema.persisted_variables WHERE VARIABLE_NAME='long_query_time'; 应能看到该记录 → RESET PERSIST long_query_time; 撤销并恢复编译默认。

C 挑战

题干：16G 内存机器，sort_buffer_size 调到 8M、max_connections 调到 2000，上线即 OOM，算最坏每连接内存并说明估算。

答案：sort_buffer_size 是每连接分配，最坏内存 = max_connections × sort_buffer_size = 2000 × 8M ≈ 16G（仅 sort_buffer 一项），再加上 join_buffer、read_buffer、net_buffer 与线程栈，远超物理内存。正确做法：每连接 buffer 保持默认几百 K，max_connections 按"应用实例数 × 池大小 + 预留"估算，而不是盲目调大；内存预算要乘连接数。

第 56 章 Buffer Pool 与内存

A 基础

题干：说出 Buffer Pool 的两个职责，并从 SHOW ENGINE INNODB STATUS 找 hit rate。

答案：两个职责：读缓存（热数据页/索引页常驻内存，命中免磁盘 IO）与写缓冲（先改内存脏页，异步合并刷盘）。SHOW ENGINE INNODB STATUS\G 中 "Buffer pool hit rate xxxx / xxxx" 即命中率。

B 进阶

题干：32G 数据库服务器给出推荐 innodb_buffer_pool_size 与 instances，并解释为什么不留 90%。

答案：buffer pool 约占 60% 物理内存 ≈ 19G（如 18~20G）；instances 按每实例 1~2G 拆，建议 8~10 个。不留 90% 是因为要给 OS page cache、连接内存、其他进程留 25% 左右，否则一旦发生 swap，整机性能崩溃。

C 挑战

题干：为什么全表扫描在改良 LRU 下不会冲掉热数据？结合 innodb_old_blocks_pct 与 old_blocks_time 说明页流转。

答案：InnoDB LRU 分年轻区与老年代（innodb_old_blocks_pct 默认 37% 老年代）。新读入的页先进入老年代头部，只有在 innodb_old_blocks_time（默认 1000ms）之后再次被访问，才会晋升到年轻区。全表扫描的页只在批量读时被碰一次，驻留老年代且不会被二次命中晋升，因此热数据所在的年轻区不被冲掉。

第 57 章 连接池配置与排查

A 基础

题干：写出后端总连接数估算公式，说明为什么 maximumPoolSize 不是越大越好。

答案：后端总连接 ≈ 应用实例数 × maximumPoolSize。池越大不是越快：每个连接在服务端要分配线程、栈与每连接 buffer，连接过多反而上下文切换频繁、内存暴涨，数据库有最优并发拐点，超过即下降。

B 进阶

题干：6 个实例、每实例池 25，max_connections 该设多少？

答案：峰值总连接 = 6 × 25 = 150，预留 30% 给运维/复制/监控，max_connections 设 200~250 足够，而非 2000。

C 挑战

题干：用 PROCESSLIST 与 INNODB_TRX 分别找运行超 60 秒的查询和开启超 5 分钟的事务，说明为何常是同一批会话。

答案：长查询：SELECT ID,USER,TIME,INFO FROM information_schema.PROCESSLIST WHERE COMMAND='Query' AND TIME>60 ORDER BY TIME DESC; 长事务：SELECT trx_id,trx_started,trx_mysql_thread_id FROM information_schema.INNODB_TRX WHERE TIMESTAMPDIFF(SECOND,trx_started,NOW())>300;。二者常是同一批：事务里跑慢查询、或事务开了不提交，连接被长期占用，既出现在 PROCESSLIST 的长 Query，也出现在 INNODB_TRX 的长寿事务。

第 58 章 监控指标体系

A 基础

题干：写出 QPS 的采样计算方法。

答案：两次采样 SHOW GLOBAL STATUS LIKE 'Com_select'（或累加 Com_xxx），差值除以两次采样时间间隔（秒）即 QPS。对慢查询数、Threads_running 等同理做增量/突刺监控。

B 进阶

题干：从 events_statements_summary_by_digest 找平均耗时最高 5 条 SQL，并判断真慢还是偶尔慢。

答案：按 AVG_TIMER_WAIT DESC 取前 5，看 COUNT_STAR：调用次数多且 avg 高 = 真慢（高频贵）；调用次数极少但 avg 高 = 偶尔慢（偶发大查询），优化优先级前者更高。

C 挑战

题干：为什么 Seconds_Behind_Source 会在 IO 线程断开时误报 0？设计更可靠的延迟口径。

答案：从库 IO 线程断开后不再追 binlog，Seconds_Behind_Source 无法计算常被显示为 NULL/0，造成"无延迟"假象。更可靠口径：比较主库当前 binlog 位点与从库已回放位点（Seconds_Behind 结合 IO_Running/SQL_Running 是否 Yes），或用主库写入时间戳与从库数据时间戳做 heart-beat 表差值。

第 60 章 大表 DDL：online schema change

A 基础

题干：写出 8.0 原生加列走 INSTANT 的前提，并用 ALGORITHM=INPLACE, LOCK=NONE 约束加索引 SQL。

答案：前提：8.0.12+，在表末尾加列（8.0.29+ 支持更多位置），不改数据类型/不重排。加索引：ALTER TABLE orders ADD INDEX idx_user_created(user_id,created_at), ALGORITHM=INPLACE, LOCK=NONE; 若不支持会报错而非默默锁表。

题干：2 亿行订单表加普通索引的完整选型决策。

第 66 章 典型业务 SQL：订单/库存/流水

A 基础

题干：完成一次完整下单事务。

第 67 章 报表实战：窗口函数综合运用

A 基础

题干：写最近 7 天每日 GMV。

答案：SELECT DATE(payed_at) dt, SUM(total_amount) gmv, COUNT(*) orders FROM orders WHERE status='PAYED' AND payed_at >= DATE_SUB(CURDATE(),INTERVAL 7 DAY) GROUP BY DATE(payed_at) ORDER BY dt;

B 进阶

题干：用 LAG 算每天 GMV 环比，挑出环比增长超 50% 的日期。

答案：WITH daily AS(...) SELECT dt,gmv, ROUND((gmv-LAG(gmv) OVER w)/LAG(gmv) OVER w*100,1) mom FROM daily WINDOW w AS (ORDER BY dt) HAVING mom>50;（或子查询包一层过滤）

题干：用窗口函数写下单金额 Top5 用户，解释 ROW_NUMBER 与 RANK 并列差异。

答案：WITH u AS(SELECT user_id,SUM(total_amount) amt FROM orders WHERE status='PAYED' GROUP BY user_id) SELECT * FROM (SELECT user_id,amt,ROW_NUMBER() OVER(ORDER BY amt DESC) rn FROM u) t WHERE rn<=5;。ROW_NUMBER 并列时强制给不同名次（1,2,3）；RANK 并列同名次并跳号（1,1,3），DENSE_RANK 并列不跳号（1,1,2）。

第 68 章 与 Redis 配合的读写模板

A 基础

题干：画出 Cache-Aside 读路径两条分支。

答案：读→查 Redis：命中则返回；未命中→查 MySQL→把结果（含空值短缓存）回填 Redis→返回。写→先 UPDATE MySQL→再 DELETE Redis key。

B 进阶

题干：为什么写要"先更库后删缓存"而非"先更缓存后更库"？说一种脏读时序。

答案：先更缓存后更库时，若缓存更新成功但库更新失败/延迟，缓存里是新值而库是旧值，期间所有读都拿到脏新值。先更库后删缓存，下次读自然回源加载最新值，把不一致窗口降到最小（删缓存失败需重试）。

C 挑战

题干：为热点商品详情设计防击穿互斥锁重建方案（伪代码）。

答案：def get(pid): v=redis.get(key); if v: return v; if redis.setnx(lock,1,ex=5): try: row=db.query; redis.setex(key,ttl,row); finally: redis.delete(lock); return row; else: sleep(50ms); return get(pid)。即缓存未命中时只让一个请求回源重建，其余等待重试读缓存。

A 基础

题干：用 sysbench 跑 oltp_read_write（32 线程 30 秒）贴 QPS 与 95th 延迟。

答案：sysbench oltp_read_write --db-driver=mysql --mysql-host=127.0.0.1 --mysql-user=root --tables=16 --table-size=1000000 --threads=32 --time=30 run，报告中 queries 的 per sec 即 QPS，latency 的 95th percentile 即 P95 延迟（按本机实测填写）。

B 进阶

题干：用 8/32/64/128 线程压测画 QPS 曲线指出拐点。

答案：分别跑 --threads=8/32/64/128，记录 QPS；曲线随线程上升到拐点后趋平甚至下降，拐点即最优并发——超过拐点后增加并发只会增加排队延迟。

C 挑战

题干：单实例目标延迟内 QPS 2500，业务峰值 4000，留 2 倍冗余，需几个读实例？

答案：需要处理量 = 4000 × 2 = 8000；实例数 = ceil(8000 / 2500) = 4 个读实例。

第 72 章 面试知识体系梳理与延伸路线

A 基础

题干：用自己的话画 B+树索引为何比哈希适合范围查询。

答案：B+树叶子节点按键有序并通过链表相连，范围查询只需定位起点再沿链表扫描；哈希是散列结构，键值无序，做范围（BETWEEN/>/<）必须全量遍历。故数据库索引用 B+树而非哈希。

B 进阶

题干：把"MVCC 怎么实现"讲成 3 分钟口述（含 undo log 与 read view）。

答案：MVCC 让读写不互相阻塞：每行有隐藏版本列，修改前旧版本写入 undo log 形成版本链；查询时生成 read view（可见性快照），按事务 ID 与活跃事务列表判断哪个版本对当前事务可见。RC 每次语句生成新 read view（不可重复读），RR 事务开始时生成一次（可重复读）。

C 挑战

题干：结合十年前端经验按 STAR 讲一个数据库真实案例。

答案：STAR 结构——Situation（如商品列表慢）、Task（需优化 P95 延迟）、Action（抓慢查询发现缺联合索引/加缓存）、Result（QPS 提升、RT 下降）。要求真实、有数据、体现"定位→方案→验证"闭环。
