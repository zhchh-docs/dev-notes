第 32 章 锁的分类：全局/表/行

教科书 第 32 章 / 共 72 章 · 预计 40 分钟

MySQL 的锁不是一种，是一套体系：全局锁冻住整个库、表锁锁住整张表、行锁只锁一行。粒度越细并发越高。本章把这套体系分层讲清——什么时候用全局锁、表锁和元数据锁 MDL 在哪种场景会坑你、行锁为什么是 InnoDB 并发的底气。

32.1 全局锁：FLUSH TABLES WITH READ LOCK

全局锁把整个数据库变成"只读"——所有写操作、DDL 全部冻结。

-- 加全局只读锁：整个库不再接受写
FLUSH TABLES WITH READ LOCK;

-- 此时所有会话的 INSERT/UPDATE/DDL 全部阻塞

-- 解锁
UNLOCK TABLES;

用途：做一致性备份——在加锁那一刻 mysqldump 导出，能保证数据时间点一致（不备份中途还在写）。但代价是：加锁期间整个库不能写，业务全面停摆。

生产几乎不用全局锁做备份：现代方案是用支持一致性快照的备份工具（如 mysqldump --single-transaction，靠 MVCC 而非锁），把备份对业务的影响降到最低。

32.2 表级锁：表锁与元数据锁 MDL

表锁锁住整张表；而更隐蔽、却更常出事的是元数据锁 MDL。

-- 显式表锁（MyISAM 时代的用法，InnoDB 很少用）
LOCK TABLES user READ;     -- 只读锁
LOCK TABLES user WRITE;    -- 写锁
UNLOCK TABLES;

-- 元数据锁 MDL：InnoDB 在你访问一张表时自动加的
-- 普通 SELECT → 加 MDL 读锁
-- ALTER TABLE → 要拿 MDL 写锁

MDL（MetaData Lock）是 5.5 引入的隐形锁：事务在读表时自动加 MDL 读锁，DDL 改表结构时要拿 MDL 写锁。读锁不阻塞读，但阻塞写；写锁要等所有读锁释放。

经典线上事故：一个慢查询占着某表的 MDL 读锁不释放，此时你执行 ALTER TABLE 想拿 MDL 写锁，就得排队；它后面所有新的 SELECT 也跟着排队等 MDL 写锁——一张表瞬间被全部堵死。加索引前先确认没有长事务占着该表。

32.3 意向锁：IS / IX 的兼容矩阵

行锁之前，InnoDB 先在表上挂一把"意向锁"，告诉你"这张表有人要改行"。

问题：表锁要判断"整张表能不能锁"，得逐行扫行锁吗？太蠢。于是有了意向锁——事务准备加行锁前，先在表上挂意向锁：

  • IS（意向共享锁）：我打算给某些行加共享锁；
  • IX（意向排他锁）：我打算给某些行加排他锁。
表读锁表写锁ISIX
表读锁兼容冲突兼容冲突
表写锁冲突冲突冲突冲突
IS（意向共享）兼容冲突兼容兼容
IX（意向排他）冲突冲突兼容兼容

关键结论：意向锁之间互不冲突（IS 与 IX 兼容），所以多个事务可以同时给不同行加行锁；只有当有人想拿整张表的写锁时，才被 IX 挡住。意向锁是"表级快速路标"，让表锁不必逐行检查。

32.4 行锁：InnoDB 并发的底气

行锁只锁要改的那一行，不同事务改不同行互不干扰——这是 InnoDB 高并发的根本。

-- 会话 A：改 id=1
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;   -- 只锁 id=1 这行

-- 会话 B：改 id=2（不同行，不冲突，能并发执行）
BEGIN;
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- 立刻执行，不等待

对比 MyISAM：它只能锁整张表，两个写操作必须排队。InnoDB 的行锁把并发粒度降到行级——100 个事务同时改 100 个不同的用户，互不阻塞。这就是为什么高并发互联网几乎只用 InnoDB。

-- 反面教材：UPDATE 的 WHERE 没走索引
UPDATE account SET balance = 0 WHERE name = '张三';
-- name 没有索引 → InnoDB 只能全表扫，给每一行都加行锁
-- 等于锁了整张表，别的事务想改行都被挡——并发瞬间归零
锁的粒度定律：粒度越粗（表锁）越简单但并发越差；粒度越细（行锁）并发越高但管理越复杂。InnoDB 选择行锁，把并发做到极致。
行锁是加在索引上的：InnoDB 的行锁锁的是索引记录。如果 UPDATE 的条件没走索引，行锁会退化成锁全表（下一章展开间隙锁）。

32.5 自增锁与 AUTO-INC

往自增列插数据时，InnoDB 要保证生成的 id 连续不重复，用的是自增锁。

-- 插入带 AUTO_INCREMENT 的表时，引擎在语句级加自增锁
-- 保证并发插入时 id 不重号、尽量连续
INSERT INTO user (name) VALUES ('甲'), ('乙'), ('丙');

-- 8.0 对自增锁做了优化：插入前先一次性预留一批 id，
-- 避免每条都等锁，批量插入快很多

自增锁是一种特殊的表级轻锁，只在生成自增值时短暂持有，语句结束就释放。它的存在是为了让"并发插入不重号"，平时不用你操心，但建表时选了自增主键，就隐式用了它。

32.6 锁粒度与性能权衡

锁锁住范围并发典型场景
全局锁整个库只读最差一致性备份（已少用）
表锁整张表差DDL、MyISAM
MDL表元数据—自动加，防 DDL/DML 打架
行锁某一行好InnoDB 日常 DML

理解这套体系，后续三章（行锁/间隙锁、死锁、锁等待）就有了坐标系。

一句话记住这张锁地图：全局锁冻整库、表锁冻整表、MDL 防 DDL/DML 打架、意向锁当路标、行锁才是并发主角。排查任何锁问题，先定位到是哪一层的锁在起作用。
MyISAM 的对照：MyISAM 引擎只有表锁，没有行锁，两个写操作必须整表排队——这也是它在高并发写场景下被 InnoDB 全面取代的根本原因。你现在用的 InnoDB，默认就是行锁主导。
意向锁是给"表级锁"看的：事务在加行锁前，先在表上加一把意向 IX 锁；这样别人想锁整表时，一看表上有 IX 就知道"有行正在被锁"，不必逐行扫描判断——它是个性能路标，不是真锁数据。

✓ 本章小结

要点一句话
全局锁整库只读，用于一致性备份，代价是业务停写
MDL隐形元数据锁；慢查询占着读锁会让后续 DDL/SELECT 全排队
意向锁表级路标，IS/IX 互相兼容，让行锁并发成为可能
行锁只锁改行的那一行，不同行并发，是 InnoDB 高并发的底气
粒度定律锁越细并发越高；行锁锁在索引上，没走索引会退化

✎ 本章习题

A 基础开两个会话：会话 A 对 id=1 加行锁（UPDATE ... WHERE id=1 不提交），会话 B 改 id=2，观察 B 是否需要等待；再让 B 改 id=1，观察是否被阻塞。
B 进阶用兼容矩阵解释：为什么两个事务可以同时给不同行加排他行锁（IX 与 IX 兼容），而一个事务想拿表写锁时会被所有 IX 挡住。
C 挑战复现 MDL 事故：会话 A 对一张大表跑一个故意慢的 SELECT（不结束），会话 B 此时执行 ALTER TABLE，再观察会话 C 的普通 SELECT 是否被堵。说出这背后 MDL 读锁/写锁的排队逻辑。
