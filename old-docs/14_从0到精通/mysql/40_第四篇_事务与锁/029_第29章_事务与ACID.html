29.1 事务是什么：一次转账

事务（Transaction）是一组"要么全做、要么全不做"的操作单元。

经典转账：A 给 B 转 100 元，要执行两条 UPDATE——A 扣 100、B 加 100。如果扣完 A 就宕机、B 还没加，钱就凭空消失了。事务的意义就是：这两条 UPDATE 绑成一个原子单元，中间任何一步失败，已做的全部撤销。

-- 转账：两条 UPDATE 必须同生共死
BEGIN;
  UPDATE account SET balance = balance - 100 WHERE id = 1;  -- A 扣 100
  UPDATE account SET balance = balance + 100 WHERE id = 2;  -- B 加 100
COMMIT;   -- 两条都成功才提交；任一步出错就 ROLLBACK 全部撤销

29.2 BEGIN / COMMIT / ROLLBACK

三个动词构成事务的一生：开始、提交、回滚。

-- 开始一个事务
BEGIN;                 -- 或 START TRANSACTION;

-- 期间执行的所有写操作，都还在"未提交"状态
UPDATE ... ;
INSERT ... ;

-- 一切正常：提交，永久生效
COMMIT;

-- 发现异常：回滚，BEGIN 之后的所有写操作全部撤销
ROLLBACK;

这三个动作的关键在未提交状态：COMMIT 之前，你的修改对其他会话不可见（隔离性，下一章），且可以一键撤销；一旦 COMMIT，就永久落盘、不可回滚。

29.3 ACID 拆解：四个字母背后的机制

ACID 是事务的四大特性，每个字母背后都有具体的存储引擎机制撑着。

字母特性靠什么实现（InnoDB）
A原子性 Atomicityundo log：每步修改前记下反向操作，回滚时照着 undo 撤销（第 36 章）
C一致性 Consistency数据库从一个合法状态转到另一个合法状态；是 AID 三者共同保证的结果
I隔离性 Isolation锁 + MVCC：并发事务互不干扰（第 30、31、32 章）
D持久性 Durabilityredo log：提交前先把修改顺序写进日志（WAL），宕机后靠 redo 恢复（第 36 章）

记法：A（原子）配 undo，D（持久）配 redo，I（隔离）配锁和 MVCC，C 是前三者合力达成的"数据始终合法"。

29.4 自动提交与保存点

MySQL 默认 autocommit=1：你不显式 BEGIN，每条 SQL 都是独立事务。

-- 查看自动提交（默认 ON）
SHOW VARIABLES LIKE 'autocommit';

-- 关闭自动提交后，不写 COMMIT 所有修改都不算数
SET autocommit = 0;
UPDATE ... ;          -- 此时还没提交
COMMIT;               -- 手动提交才算

-- 保存点：一个事务里分段回滚
BEGIN;
  UPDATE account SET balance = balance - 100 WHERE id = 1;
  SAVEPOINT sp1;                 -- 打个点
  UPDATE account SET balance = balance + 100 WHERE id = 2;
  -- 出问题时只回滚到 sp1，前面那步保留
  ROLLBACK TO SAVEPOINT sp1;
COMMIT;
应用层的真相：Java 里 @Transactional、MyBatis 的事务，本质就是帮你在方法前后包了 BEGIN 和 COMMIT。理解了手动三步，框架自动事务就是这三步的封装。

29.5 事务的状态与常见误区

  • 坑事务里夹远程调用：事务还没提交，就发起 HTTP/RPC 调用——对方读到的可能是你未提交的数据，且远程调用慢会拉长事务（第 35 章长事务）；
  • 坑忘了 COMMIT：autocommit=0 的环境里只写不提交，数据一直处于未提交状态、行锁一直占着；
  • 坑事务太大：一个事务塞几十条 UPDATE，持锁太久、回滚成本高（第 35 章专门治理）；
  • 点只读查询不必开事务：纯 SELECT 不写数据，包在事务里是白占资源。
事务使用的总原则：边界要小（只包必须同生共死的写操作）、动作要快（别在事务里干别的）、提交要早（能不持有锁就不持有）。
COMMIT 之前修改对别人不可见：这正是隔离性的体现（第 30 章）。你在事务里改了半天，别的会话看不到，直到你 COMMIT——所以事务开得越久，别人等你的一致性状态越久。
autocommit=1 的隐藏行为：不显式 BEGIN 时，每条单条 SQL 自动是一个独立事务——很多人以为自己"没开事务"，其实引擎已经帮你开了又提了。这也是为什么批量插入要自己 BEGIN 包住。
事务里别放耗时操作：HTTP 调用、发邮件、第三方支付回调，都要挪到 COMMIT 之后；它们不产生 undo/redo，却会拉长持锁时间，是长事务的头号来源（第 35 章）。
SAVEPOINT 用在哪：流程里有"试探性修改"时才用（比如先扣库存再决定是否下单）；绝大多数业务直接 BEGIN/COMMIT/ROLLBACK 三件套就够，别把简单流程复杂化。

✓ 本章小结

要点一句话
事务一组操作同生共死，要么全成功要么全回滚
三动词BEGIN 开始、COMMIT 落盘、ROLLBACK 撤销
A 原子性undo log 记反向操作，回滚照着撤销
D 持久性redo log 先写日志再落盘，宕机可恢复
I 隔离性锁 + MVCC，并发事务互不干扰
autocommit默认每条 SQL 独立成事务；显式 BEGIN 才把多条绑一起
