第 33 章 行锁、间隙锁与临键锁

33.1 记录锁：锁住单条索引记录

记录锁（Record Lock）是最直观的行锁：精确锁住你命中的那一条索引记录。

-- 表的主键索引排好序：... 10 | 20 | 30 | 40 ...
-- 会话 A：等值命中 id=20，给这一条加记录锁
BEGIN;
SELECT * FROM account WHERE id = 20 FOR UPDATE;
-- 锁住：{20} 这一条

-- 会话 B：想改 id=20 → 被挡；改 id=30 → 不受影响
UPDATE account SET balance=0 WHERE id = 20;   -- 阻塞

记录锁锁的是索引上的一条记录，不是物理行。没走索引的查询，会把整个索引的记录都锁上（退化成表级）。

33.2 间隙锁：锁住行与行之间的空当

光锁现有行不够——别人往"空当"里插入新行，范围查询就会幻读。间隙锁锁的是"行之间的开区间"。

-- 主键排好序：... 10 | 20 | 30 ...
-- 会话 A 做范围查询并加锁
SELECT * FROM account WHERE id BETWEEN 15 AND 25 FOR UPDATE;
-- 不仅锁住 20，还锁住 (10, 20) 和 (20, 30) 这两个间隙

-- 会话 B 想往间隙里插：
INSERT INTO account VALUES (15, 100);   -- 阻塞！(10,20) 被间隙锁锁了
INSERT INTO account VALUES (25, 100);   -- 阻塞！(20,30) 被间隙锁锁了
间隙锁（Gap Lock）的唯一使命：阻止别的事务在这个范围里插入新行——这正是 RR 级别基本杜绝幻读的关键。

33.3 临键锁：左开右闭的区间

InnoDB 默认的行锁形态是临键锁（Next-Key Lock）= 记录锁 + 前面的间隙，区间"左开右闭"。

规则：InnoDB 在 RR 下，对索引范围扫描加锁时，默认给扫描到的每个索引记录加临键锁——锁住该记录 + 它左边的间隙。这样无论别的事务往哪个间隙插入，都会被挡住，幻读无从发生。

33.4 唯一索引的退化规则

不是所有情况都加临键锁——唯一索引等值查询会"退化"。

唯一索引等值查询命中结果加什么锁
等值查询且命中唯一记录找到该行退化成记录锁（不加间隙锁）
等值查询且未命中找不到退化成间隙锁（锁住该位置间隙）
 
-- 唯一索引等值命中 id=20 → 只锁记录锁，不加间隙
SELECT * FROM account WHERE id = 20 FOR UPDATE;   -- {20}

-- 唯一索引等值未命中 id=25（表里没有 25）
SELECT * FROM account WHERE id = 25 FOR UPDATE;
-- 退化成间隙锁：锁住 (20,30)，防止别人插 25 进来
退化的逻辑：唯一索引等值命中时，确定只有这一行，不需要防"同一键再插入"（唯一约束已经挡住），所以不用间隙锁；未命中时为了防止幻读同一键，才退化成间隙锁。

33.5 实战：为什么插入被莫名挡住

线上最常见的困惑：明明没锁那一行，为什么 INSERT 报锁等待超时？

-- 会话 A（RR）跑了一个范围查询加锁
BEGIN;
SELECT * FROM account WHERE id >= 20 AND id <= 30 FOR UPDATE;
-- 加了临键锁：锁住 (10,20]、(20,30]、(30,40] …

-- 会话 B 想插入 id=25
INSERT INTO account VALUES (25, 100);
-- 报错锁等待：25 落在 (20,30) 这个被临键锁锁住的间隙里
ERROR 1205 (HY000): Lock wait timeout exceeded
排查口诀：插入被挡，先看目标值落在哪个间隙——它的前一个记录和后一个记录之间，大概率被别的事务的临键锁锁住了。用 SHOW ENGINE INNODB STATUS 或 performance_schema.data_locks 看具体锁区间（第 37 章）。
-- 查看当前到底加了哪些锁（8.0）
SELECT lock_mode, lock_type, lock_table, lock_data
FROM performance_schema.data_locks;
-- lock_mode: X（排他记录锁）/ X,GAP（间隙锁）/ X,Next-Key（临键锁）
-- lock_data 直接告诉你锁住的是哪个值或哪个间隙
三种锁的记忆法：记录锁锁"点"、间隙锁锁"空当"、临键锁锁"点+空当"的左开右闭区间。RR 靠它们组合，既防修改冲突、又防范围插入的幻读。
RC 级别下没有间隙锁：因为 RC 不靠快照防幻读（它本来就允许不可重复读），所以行锁只锁记录、不锁间隙，并发更高、死锁更少——这也是很多互联网公司把默认 RR 降到 RC 的原因之一。

插入意向锁

往被间隙锁锁住的区间里 INSERT 时，插入方会先加一把"插入意向锁"——它本质是在告诉别人"我打算插这儿"。插入意向锁之间不互斥（多个事务可往不同间隙插入），但会与那个间隙的间隙锁冲突，所以 INSERT 必须等间隙锁释放。这就是"插入被挡"的锁层面细节。

排查锁问题时，先分清锁的是"点"（记录锁）还是"区间"（临键锁）——后者的范围往往比你想的大，插入被挡十有八九是撞上了临键锁的间隙。
记忆口诀：唯一命中退记录、唯一落空退间隙、范围扫描加临键。三种退化规则背熟，遇到锁区间问题就不会发懵。
等值命中为什么能退化成记录锁：唯一索引等值命中确定只有一行，唯一约束已经保证"同样的键插不进第二行"，再加间隙锁是浪费——所以 InnoDB 退化成纯记录锁，把并发让出来。
范围扫描为什么必须加临键锁：范围条件没有确定的右边界，你不知道下一条该锁到哪；为了防止别的事务在你扫描的区间里插入新行（幻读），InnoDB 必须用"左开右闭"的临键锁把整个区间罩住。
RC 级别下几乎没有间隙锁：RC 本就允许不可重复读、不靠 MVCC 快照防幻读，所以行锁只锁记录、不锁间隙，并发更高、死锁更少——这也是高并发互联网库把默认 RR 降到 RC 的主要动因。
