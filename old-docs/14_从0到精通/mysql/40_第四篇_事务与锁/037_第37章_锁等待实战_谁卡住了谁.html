第 37 章 锁等待实战：谁卡住了谁

教科书 第 37 章 / 共 72 章 · 预计 40 分钟

一条 UPDATE 忽然卡住不动、业务报"Lock wait timeout"——怎么揪出是谁的锁卡住了你的语句？本章从模拟锁等待开始，一步步用 PROCESSLIST、innodb_trx、8.0 的 data_locks / data_lock_waits 把"等待链"查清楚，最后 KILL 掉元凶。这是锁问题的完整排查手册。

37.1 模拟一次锁等待

先在实验环境把锁等待演出来，后面每一步都对着它查。

-- 会话 A（持有锁的元凶）
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
-- 锁住 id=1，且一直不 COMMIT（故意的）

-- 会话 B（被卡住的受害者）
UPDATE account SET balance = balance + 50 WHERE id = 1;
-- 卡在这：等 A 释放 id=1 的行锁
-- 超过 innodb_lock_wait_timeout（默认50秒）→ ERROR 1205 Lock wait timeout

37.2 第一步：PROCESSLIST 找卡住的语句

业务报"语句卡住"，先看当前所有连接在干嘛。

SHOW PROCESSLIST;
-- 重点看几列：
-- Id        连接 ID（KILL 用它）
-- State     状态：Sending data / Updating / 锁等待时多为 Waiting for table metadata lock 或 Sleep
-- Time      该状态持续了多少秒（Time 很大的就是卡住的）
-- Info     正在执行的 SQL

-- 更全的写法
SELECT * FROM performance_schema.processlist ORDER BY time DESC;

一眼挑出 Time 列很大、State 异常、Info 是那条卡住 UPDATE 的连接——它就是受害者；但元凶（那个开了事务不提交的）往往 State 是 Sleep（闲着但占着锁），这才是要揪出来的。

37.3 第二步：innodb_trx 找事务

PROCESSLIST 只告诉你谁卡着，innodb_trx 告诉你"谁的事务持着锁"。

-- 所有 InnoDB 事务：谁开了、开了多久、在干嘛
SELECT
  trx_id,
  trx_mysql_thread_id,        -- 对应 PROCESSLIST 的 Id
  trx_state,
  trx_started,
  trx_query                   -- 当前 SQL（NULL = 事务开着但在 Sleep）
FROM information_schema.innodb_trx;

-- 你会看到：
-- 元凶：trx_query = NULL（开了事务在睡觉），trx_started 很早
-- 受害者：trx_query = 那条卡住的 UPDATE
-- 用 trx_mysql_thread_id 就能关联到 PROCESSLIST 的连接
锁等待排查链条：PROCESSLIST 找卡住的连接 → innodb_trx 关联到事务 → 找到那个 trx_query 为 NULL、却还占着锁的元凶。

37.4 第三步：data_locks 看具体锁

8.0 直接告诉你：谁拿着哪把锁、谁在等哪把锁。

-- 当前所有锁
SELECT
  lock_id, lock_trx_id, lock_mode, lock_type, lock_table, lock_index_id, lock_data
FROM performance_schema.data_locks;
-- lock_data: 锁住的具体值（如 '1'）；lock_mode: X（排他）/ X,GAP（间隙）

-- 锁等待关系：谁在等谁
SELECT
  requesting_engine_transaction_id,   -- 等待方
  blocking_engine_transaction_id      -- 被等方（元凶）
FROM performance_schema.data_lock_waits;

-- 三表一 JOIN，完整还原"等待链"：
-- 受害者事务 → 等 data_lock_waits → 元凶事务 → 持 data_locks
视图回答的问题
PROCESSLIST哪个连接、跑哪条 SQL、卡了多久
innodb_trx哪些事务开着、谁在睡觉却占锁
data_locks当前有哪些锁、锁在哪个值、什么模式
data_lock_waits等待链：谁在等谁

37.5 一条 SQL 看清等待链

把三张视图 JOIN 起来，一条查询直接输出"谁在等谁、锁在哪行"。

-- 完整等待链查询（MySQL 8.0）
SELECT
  waiting.trx_mysql_thread_id    AS 受害者线程,
  waiting.trx_query             AS 受害者SQL,
  blocking.trx_mysql_thread_id   AS 元凶线程,
  blocking.trx_query            AS 元凶SQL,
  l.lock_table                  AS 锁的表,
  l.lock_data                   AS 锁住的值,
  l.lock_mode                   AS 锁模式
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks l
  ON l.lock_id = w.requesting_engine_lock_id
JOIN information_schema.innodb_trx waiting
  ON waiting.trx_id = w.requesting_engine_transaction_id
JOIN information_schema.innodb_trx blocking
  ON blocking.trx_id = w.blocking_engine_transaction_id;
结果怎么读：一行就是一条等待关系。看到"受害者SQL"是你报障的那条、"元凶SQL"为 NULL（空事务），把"元凶线程"KILL 掉即可。
data_locks / data_lock_waits 是 8.0 才有的视图；5.7 没有这两张表，只能靠 innodb_trx + SHOW ENGINE INNODB STATUS 里的 TRANSACTIONS 段手工找。

37.6 解开：KILL 元凶与预防

定位到元凶事务，KILL 它的连接，等待链立刻解开。

-- 从 innodb_trx 拿到元凶的 trx_mysql_thread_id（假设是 12）
KILL 12;
-- 元凶事务被回滚，它持有的行锁释放，
-- 会话 B 那条卡住的 UPDATE 立刻继续执行
KILL 元凶前先确认它是不是长事务、有没有做大量修改——回滚需要时间。如果只是"开了事务在睡觉"的空事务，KILL 得很干脆。

预防习惯（前面各章的汇总）：

  • 点事务尽早 COMMIT，别开着连接去干别的（第 35 章长事务）；
  • 点所有事务按固定顺序访问行（第 34 章防死锁）；
  • 点UPDATE/DELETE 必须走索引，否则锁全表（第 33 章）；
  • 点给 innodb_lock_wait_timeout 设合理上限（默认 50 秒，核心库可调小到 5~10 秒快速失败）。
第四篇收官：到这里，事务（ACID、隔离级别、MVCC）、锁（分类、行锁间隙锁、死锁、长事务、undo/redo）就闭环了。下一篇进入日志与主从：redo、undo、binlog 三大日志与主从复制怎么配合。
锁等待排查三步走：PROCESSLIST 定位卡住的连接 → innodb_trx 找到占锁不提交的元凶 → data_locks / data_lock_waits 看清锁区间与等待链 → KILL 元凶。
别急着 KILL：先看元凶的 trx_query 和 trx_rows_modified——如果它正在批量改数据，KILL 后回滚也要花时间，反而可能更久。确认是"开着事务睡觉"的空事务，再果断 KILL。
