第 35 章 长事务的危害与治理

教科书 第 35 章 / 共 72 章 · 预计 35 分钟

一个事务开了半小时不提交，危害远不止"慢"：undo 版本链越堆越长、purge 不推进、行锁一直占着、主从延迟越拉越大。本章把长事务的危害摊开，再给一套监控阈值与治理动作——怎么发现它、怎么 kill 它、怎么从代码上杜绝它。

35.1 什么是长事务

一个事务从 BEGIN 到 COMMIT 持续的时间，超过了合理范围，就是长事务。

-- 典型长事务：BEGIN 后跑了一堆查询/计算，半小时才 COMMIT
BEGIN;
  SELECT ...;   -- 查了一堆数据，应用层慢慢算
  -- 中间还夹了 HTTP 调用、调了第三方接口（网络慢）
  UPDATE ...;
COMMIT;         -- 这才提交，前面所有行锁、undo 都压了半小时

生产经验值：单个事务控制在秒级（建议 < 1 秒）。超过几秒就要警惕；几十秒、几分钟的事务，基本是事故苗子。

35.2 长事务的四大危害

长事务危害的根源是一件事：它不提交，它的快照就得一直有效。

危害原理
undo 版本链膨胀事务的 ReadView 要看老版本，undo log 里的旧版本不能清理，越堆越长
purge 不推进清理线程要等所有活跃事务都不用这些旧版本了才能删，长事务把它卡死
行锁长期占用事务不提交，它持有的行锁一直不释放，别的事务排队等
主从延迟长事务占着的行，从库回放要等它提交，主库越写越快、从库越追越远
一句话：长事务让 undo 不敢删、行锁不敢放、从库不敢追——它一个人慢，拖累整个数据库。
-- 配套监控：information_schema.innodb_trx 里几个有用的列
-- trx_started        事务开始时间
-- trx_rows_modified  这个事务改了多少行（越多回滚越久）
-- trx_lock_structs  它持有多少把锁
-- trx_query          当前 SQL（NULL = 在睡觉）
-- 排查时先看 trx_rows_modified 大不大，决定 KILL 后回滚多久

35.3 如何发现长事务

InnoDB 把当前所有事务都登记在 innodb_trx 里，按持续时间排一下就抓到了。

-- 查当前所有事务，按运行时长排序（秒）
SELECT
  trx_id,
  trx_started,                          -- 事务开始时间
  TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS run_sec,   -- 已运行秒数
  trx_state,
  trx_query                            -- 当前在跑的 SQL
FROM information_schema.innodb_trx
ORDER BY trx_started ASC;

-- 抓超过 10 秒的长事务
SELECT * FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 10;
监控化：把"长事务数"做成告警——每隔几秒跑上面这条查询，一旦有事务超过阈值（比如 30 秒）没提交，立刻通知 DBA。这是核心库必备的监控项。

35.4 如何处理：KILL 与阈值

发现失控的长事务，直接 KILL 掉它的连接。

-- 先从 innodb_trx 或 SHOW PROCESSLIST 找到连接 ID（Id 列）
SHOW PROCESSLIST;

-- KILL 掉那个连接（会回滚它未提交的事务）
KILL 12345;

-- 配套参数：防止事务无限期等锁
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';   -- 默认 50 秒，可调小
KILL 会触发回滚：如果长事务已经改了很多行，回滚也要花相应时间。所以要在它还没做大量修改时尽早发现、尽早 KILL——这就是为什么要监控"运行时长"而不是等它把库拖垮。

35.5 从代码上杜绝长事务

治本要回到代码：事务里只放数据库操作，把慢的、不可控的东西挪出去。

  • 关键事务里不放远程调用：HTTP/RPC/发消息这类网络操作挪到 COMMIT 之后；
  • 关键大改动分批：一次 UPDATE 100 万行改成每批几千行、按主键循环提交（第 5 章）；
  • 点事务里不放重计算：应用层算好再进事务，事务只做必要的读写；
  • 点设置事务超时：框架层面（如 Spring 的 @Transactional timeout）给事务兜一个上限。
-- 反面：一个事务里批处理 100 万行，锁与 undo 全压在一个事务里
BEGIN;
  UPDATE big_table SET flag = 1 WHERE id <= 1000000;   -- 跑几分钟
COMMIT;

-- 正面：按主键分批，每批一个小事务
-- 应用层循环：每 5000 行提交一次
-- BEGIN; UPDATE ... WHERE id BETWEEN ? AND ?; COMMIT;
-- 持锁时间短、undo 压力小、失败了重跑这一批
治理长事务的心法：事务里只放数据库读写，把网络调用、重计算、大改动全部挪出去、拆成小批。让每个事务"进来就干活、干完就走"。
-- 分批脚本的骨架（应用层循环，伪代码）
-- 每批按主键区间切，单批一个事务
-- long_id = 起始 id；batch = 5000
WHILE 还有数据:
  BEGIN;
    UPDATE big_table SET flag=1
    WHERE id >= long_id AND id < long_id + 5000 AND flag = 0;
  COMMIT;
  long_id = long_id + 5000;
-- 每批持锁毫秒级，undo 压力可控，失败了从断点续跑
框架兜底：Spring 等框架的 @Transactional(timeout = 5) 能在秒级自动回滚超时事务；微服务里则要配合链路监控，把事务耗时画进看板，而不是等它拖垮库才发现。
KILL 之前先看修改量：trx_rows_modified 越大，回滚越久；如果它正在批量刷数，KILL 完还要等回滚完才能放锁——这时候与其 KILL，不如等它自然 COMMIT。
