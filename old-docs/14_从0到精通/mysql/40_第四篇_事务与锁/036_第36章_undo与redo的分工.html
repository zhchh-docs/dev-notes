36.1 undo log：回滚日志与版本链

undo log 记的是"修改前的旧值"，一份日志干两件事。

-- 把 id=1 的 balance 从 100 改成 0 之前，undo 记下：
--   旧值 = 100，对应 id=1
-- 作用一（回滚）：事务 ROLLBACK 时，照 undo 把 0 改回 100
-- 作用二（MVCC）：第 31 章的版本链，快照读靠它找历史版本
undo 的职责说明
回滚（原子性）事务失败时，按 undo 反向撤销已做的修改
多版本（MVCC）保存旧版本，供别的事务快照读（版本链）
清理时机等所有活跃事务都不再需要这些旧版本，purge 线程才删
长事务为什么拖垮 undo？它的 ReadView 一直引用某个旧版本，purge 线程就不敢删那段 undo——undo 越堆越多，这就是第 35 章"undo 膨胀"的根源。

36.2 redo log：WAL 与崩溃恢复

redo log 记的是"修改后的新值"，靠预写日志保证宕机不丢。

问题：数据修改先写在内存缓冲池，还没落盘就宕机，修改就丢了。如果每次提交都把数据页刷盘，又太慢（随机 IO）。WAL（Write-Ahead Logging）的解法：先把修改顺序写进 redo log（顺序 IO，快），再慢慢刷数据页。

-- 提交时：
-- 1. 修改写进内存缓冲池（数据页）
-- 2. 同一份修改顺序写进 redo log（持久，先落盘）
-- 3. COMMIT 返回成功（哪怕数据页还没刷盘）

-- 宕机恢复：重启时读 redo log，把"已提交但没落盘"的修改重做一遍
--  → 数据不丢（持久性 D）
WAL 精髓：提交只保证 redo log 落盘（顺序写），数据页异步刷（随机写）——既快又不丢。

36.4 两阶段提交：redo 与 binlog

InnoDB 既要 redo（崩溃恢复），Server 层又要 binlog（主从复制）——两份日志要保证一致，靠两阶段提交。

-- 一次事务提交的两阶段：
-- 阶段 1：redo log 置为 prepare 状态（已写，但未定）
-- 阶段 2：写 binlog（Server 层的日志，主从同步靠它）
-- 阶段 3：redo log 置为 commit 状态

-- 为什么要这样？保证 redo 和 binlog 要么都有、要么都没有
-- 宕机恢复时：redo prepare 但 binlog 没写完 → 回滚；
--             redo prepare 且 binlog 已写完 → 提交（重做）
binlog 是 Server 层的日志，用于主从复制（第五篇展开）。两阶段提交（XA）是让"InnoDB 的 redo"与"Server 的 binlog"在崩溃时保持一致的经典设计。
undo 与 redo 一句话分清：undo 往回退（旧值、回滚、版本链），redo 往前冲（新值、重做、不丢）。一个保原子，一个保持久。

崩溃恢复时 InnoDB 会扫描 redo log：把所有"已提交"的修改重做（哪怕数据页还没落盘），把"未提交"的事务用 undo 回滚——最后数据库回到"该提交的都提交了、该回滚的都回滚了"的一致状态。这就是 D（持久性）和 A（原子性）在宕机后同时兜底的过程。

两阶段提交为什么必须：如果 redo 与 binlog 不一致（比如 redo 提交了但 binlog 没写），主从复制时从库就会缺这笔变更，主从数据分叉。两阶段提交就是为了让两份日志在崩溃时能对齐。
性能与安全的取舍：innodb_flush_log_at_trx_commit 设为 0 或 2 能提升写入吞吐，但宕机可能丢最后 1 秒数据。核心交易库永远设 1，只有日志、埋点这类可丢数据的库才考虑放宽。

WAL（Write-Ahead Logging）的含义：先写日志、再改数据页。哪怕数据页还没刷盘就宕机，redo log 也能把它重做回来——这就是为什么"提交了就不会丢"，而不用每次提交都把整页刷盘（那太慢了）。
checkpoint 在干嘛：checkpoint 是 InnoDB 定期把内存脏页真正刷到磁盘、并推进 redo log 可回收位点的动作；它让 redo log 文件能循环复用，不会无限膨胀。
doublewrite 双写缓冲：页写到磁盘前先落一份到 doublewrite 区，防止"写了一半页"（partial page write）。这是 redo log 能成立的前提——redo 记录的是页的物理修改，页本身坏了它也救不回来。

✓ 本章小结

要点一句话
undo log记旧值，负责回滚（A）与 MVCC 版本链
redo log记新值，WAL 先落盘，崩溃恢复保持久性（D）
WAL提交只保证 redo 落盘，数据页异步刷，又快又不丢
两阶段提交redo prepare → binlog → redo commit，保证两日志一致
刷盘参数innodb_flush_log_at_trx_commit=1 核心库必设
