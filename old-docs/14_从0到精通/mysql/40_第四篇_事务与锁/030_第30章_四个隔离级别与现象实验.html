第 30 章 四个隔离级别与现象实验

教科书 第 30 章 / 共 72 章 · 预计 50 分钟

两个并发事务同时读写同一份数据，会出现三种"乱象"：脏读、不可重复读、幻读。SQL 标准给了四个隔离级别逐级挡住它们。本章在两个会话里动手实验，每个级别分别看到什么现象、InnoDB 的 REPEATABLE READ 为什么几乎杜绝幻读。

30.1 三种乱象：脏读/不可重复读/幻读

并发事务同时读写同一份数据时，可能出现三种"读得不对"。

现象含义举个例子
脏读读到了别的事务未提交的修改A 转走 100 还没提交，B 就读到余额少了 100
不可重复读同一事务内，两次读同一行，结果不一样（被人改了）B 两次读余额，中间 A 提交了，两次值不同
幻读同一事务内，两次按范围查询，行数变了（被人插/删了）B 两次查"余额>100 的人"，中间 A 插入一行，第二次多了一条

注意区分：不可重复读针对"改过的行"，幻读针对"新增/消失的行"。隔离级别就是逐级把这些现象锁在门外。

30.2 四个隔离级别与实验准备

SQL 标准定义四个级别，级别越高、现象越少、并发越差。

隔离级别脏读不可重复读幻读并发
读未提交 RU可能可能可能最高
读已提交 RC不可能可能可能较高
可重复读 RR（默认）不可能不可能InnoDB 基本杜绝中等
串行化 Serializable不可能不可能不可能最低
 
-- 查看当前隔离级别（8.0 默认 REPEATABLE-READ）
SELECT @@transaction_isolation;    -- 5.7 是 tx_isolation

-- 设置本会话的隔离级别（实验时用）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 实验用表
CREATE TABLE account (id INT PRIMARY KEY, balance INT);
INSERT INTO account VALUES (1, 100);
开两个会话：本实验需要两个数据库连接（会话 A、会话 B）。同一个客户端开两个查询窗口，分别代表两个并发事务。

30.3 读未提交 RU 实验

RU 是最低级别：别人没提交的修改你也能读到——脏读发生。

-- 会话 A（转账方）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;   -- 扣到 0，还没 COMMIT
-- 此刻：balance=0，但未提交

-- 会话 B（读取方）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM account WHERE id = 1;   -- 结果：0  ← 脏读！读到 A 未提交的 0

-- 会话 A 回滚
ROLLBACK;   -- balance 恢复 100
-- 会话 B 刚才读到的 0 是"脏数据"，压根没真实发生过
脏读的危害：B 基于"0"做了判断（比如给用户发提醒"余额不足"），结果 A 回滚了，数据根本没变——B 做出了错误决策。RU 几乎没有生产价值。

30.4 读已提交 RC 实验

RC 只允许读到"已提交"的数据，脏读被挡住，但不可重复读仍在。

-- 会话 A
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;

-- 会话 B
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;

-- 会话 A 第一次读
SELECT balance FROM account WHERE id = 1;   -- 100

-- 会话 B 中途修改并提交
-- 会话 B: UPDATE account SET balance = 50 WHERE id = 1; COMMIT;

-- 会话 A 第二次读同一行
SELECT balance FROM account WHERE id = 1;   -- 50  ← 不可重复读！同一事务内两次读不一样

RC 挡住了脏读（B 没提交时 A 读到的还是 100），但挡不住"已提交的新值"——A 在同一个事务里两次读同一行，被 B 的提交改了结果。RC 是 Oracle、PG 等很多数据库的默认级别。

30.5 可重复读 RR 实验与幻读

RR 是 MySQL 默认级别：同一事务内多次读同一行，结果一致。

-- 会话 A（RR 默认）
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT balance FROM account WHERE id = 1;   -- 100

-- 会话 B 修改并提交
-- 会话 B: UPDATE account SET balance = 50 WHERE id = 1; COMMIT;

-- 会话 A 再读
SELECT balance FROM account WHERE id = 1;   -- 100  ← 可重复读！还是第一次的快照

-- 会话 A 整个事务期间，看到的都是"第一次读那一刻"的快照

这就是 MVCC 的威力（下一章细讲）：RR 下，事务第一次读会拍下一个一致性快照，之后无论别人怎么提交，你读的都是这个快照——所以同一行两次读结果一样。

InnoDB 的 RR 靠 MVCC 的 ReadView 快照 + 临键锁（next-key lock），基本杜绝了幻读——这是它比 SQL 标准的 RR 更强的地方，也是 MySQL 敢把 RR 当默认的底气。

30.6 串行化与级别选择

Serializable 让所有事务排队执行，彻底杜绝一切现象，但并发性能最差。

-- 串行化：一个事务在读时，别的事务写同一行会被锁住排队
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- 几乎退化为"一条接一条执行"，只在对一致性要求极高、并发很低的场景用
级别什么时候用
RU几乎不用（脏读不可接受）
RC对一致性要求稍低、追求高并发的互联网业务（很多公司从 RR 降到 RC）
RR（默认）多数业务的默认值：可重复读 + 基本杜绝幻读，并发与一致平衡
Serializable银行对账等极少数强一致、低并发场景

✓ 本章小结

要点一句话
三种现象脏读（读未提交）、不可重复读（同行被改）、幻读（范围行数变）
四级别RU 全有、RC 挡脏读、RR 挡到幻读、Serializable 全挡
默认级别InnoDB 默认 REPEATABLE READ，且基本杜绝幻读
实验方法开两个会话，SET SESSION 隔离级别，对照两次读的差异
级别选择多数用 RR；追求高并发降到 RC；强一致才上 Serializable

✎ 本章习题

A 基础开两个会话，把隔离级别都设为 RC，复现"不可重复读"：会话 A 两次读 balance，中间会话 B 修改并提交，观察 A 两次结果不同。
B 进阶同样的操作在 RR 级别下复现：会话 A 两次读 balance，中间 B 提交修改，观察 A 两次结果是否一致，并解释为什么（提示：一致性快照）。
C 挑战对比 RC 与 RR 在"同一事务内连续两次范围查询"的行为差异，思考：为什么互联网高并发系统常把默认 RR 降到 RC？从并发性能与业务一致性要求两个角度分析代价与收益。
