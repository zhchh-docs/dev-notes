第 34 章 死锁：复现、分析与避免

会话 A 等会话 B 的锁、会话 B 又等会话 A 的锁——两个事务僵在原地，这就是死锁。本章先动手复现一个教科书死锁，再用 SHOW ENGINE INNODB STATUS 和 8.0 的 performance_schema 把它拆解，最后给出四条能从根上减少死锁的实践原则。

34.1 死锁的四个必要条件

四个条件同时满足才死锁，破坏任意一个就能避免。

  1. 互斥：资源（行锁）同一时刻只能被一个事务持有；
  2. 持有并等待：事务拿着已拿到的锁，又等别人手里的锁；
  3. 不可剥夺：锁不能被强行抢走，只能持有者主动释放；
  4. 循环等待：A 等 B、B 等 A，形成环。

数据库里互斥、不可剥夺是改不了的，所以实践上从破坏"持有并等待"（缩短事务、一次拿全锁）和破坏"循环等待"（按固定顺序访问行）入手。

34.2 复现一个教科书死锁

两个会话，交叉更新对方手里的行，三秒僵死。

-- 会话 A
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;  -- 锁住 id=1

-- 会话 B
BEGIN;
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- 锁住 id=2

-- 会话 A 再更新 id=2（被 B 锁着，等待）
UPDATE account SET balance = balance - 100 WHERE id = 2;  -- 等 B 释放 id=2

-- 会话 B 再更新 id=1（被 A 锁着，等待）
UPDATE account SET balance = balance + 100 WHERE id = 1;  -- 等 A 释放 id=1
-- ❌ 死锁！InnoDB 检测到循环等待，主动回滚其中一个事务
-- ERROR 1213 (40001): Deadlock found when trying to get lock

34.3 死锁检测与日志

InnoDB 有死锁检测器，主动发现循环等待并回滚一方；日志里能看到完整现场。

-- 查看最近一次死锁的完整现场（LATEST DETECTED DEADLOCK 段）
SHOW ENGINE INNODB STATUS;

-- 输出关键内容：
-- *** (1) TRANSACTION: 会话 A 在等什么锁
-- *** (2) TRANSACTION: 会话 B 持有什么锁
-- *** WE ROLL BACK TRANSACTION (n): 决定回滚哪一个

-- 把每次死锁都记进日志（不止最近一次）
SET GLOBAL innodb_print_all_deadlocks = ON;

回滚哪一方？InnoDB 选回滚代价最小的那个（修改行数少的），让另一个继续。所以应用层要对 1213 Deadlock 错误做重试——被回滚的那个事务，代码里重新跑一遍往往就好了。

34.4 8.0 的锁诊断视图

8.0 把锁信息搬进了 performance_schema，不用再盯着那段文本。

-- 8.0：当前所有锁（5.7 的 information_schema.innodb_locks 已废弃）
SELECT * FROM performance_schema.data_locks;

-- 锁等待关系：谁在等谁
SELECT * FROM performance_schema.data_lock_waits;

-- 配合：当前还在跑的事务
SELECT * FROM information_schema.innodb_trx;

-- 三表 JOIN：一眼看出"哪个事务、等哪个锁、被谁阻塞"
-- data_lock_waits: requesting_engine_transaction_id  ← 被谁阻塞
--                  blocking_engine_transaction_id
版本提示：MySQL 8.0 把锁/锁等待统一到 performance_schema.data_locks 和 data_lock_waits；5.7 用户用旧的 information_schema.innodb_locks / innodb_lock_waits。

34.5 如何避免死锁

四条原则，能消灭绝大多数死锁。

  • 关键固定顺序访问行：所有事务都按同一顺序（比如按主键升序）更新多行，从根上打破循环等待；
  • 关键缩短事务、尽早提交：事务越短，持锁时间越短，撞上的概率越小（第 35 章）；
  • 点保证 UPDATE/DELETE 走索引：不走锁会退化成锁全表，死锁概率暴涨；
  • 点降低隔离级别：RC 级别没有间隙锁，锁范围更小，死锁更少；
  • 坑应用层对 1213 重试：死锁被回滚是正常的，代码捕获后重试，别当致命错误。
避免死锁的第一原则：所有事务按同一个顺序拿锁——只要没有"我先拿 1 再拿 2、你先拿 2 再拿 1"，就形不成环。
应用层要对 1213 做重试：死锁被 InnoDB 回滚是正常现象，不是程序 bug。把 1213（或 40001）异常捕获后、让整个事务重跑一遍，绝大多数情况第二次就能成功。
-- 死锁重试的伪代码（应用层）
-- for attempt in range(3):
--   try:
--     开事务 ... 写操作 ... 提交
--     break;
--   catch (DeadlockFound 1213):
--     sleep(短暂随机退避)；继续重试
-- 最多重试 3 次，避免无限循环
