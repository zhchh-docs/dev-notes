第 31 章 MVCC：多版本并发控制

为什么读和写能互不阻塞？答案是 MVCC：每行数据背后藏着一串"版本"，读的人挑自己快照那一刻的版本看，写的人只管追加新版本。本章拆解隐藏列、undo 版本链、ReadView 三件套，把"可重复读"从现象变成原理。

31.1 一句话理解 MVCC

MVCC（Multi-Version Concurrency Control）= 一行数据保留多个版本，读操作挑合适的版本看，不加锁。

没有 MVCC 时，写的人给行加锁，读的人就得等——读写互相阻塞。有了 MVCC：写操作不覆盖旧值，而是追加一个新版本；读操作根据自己的快照，挑历史版本读。于是读不阻塞写、写不阻塞读，并发性能大幅提升。

MVCC 的核心：读快照、写新版。读的人永远不被写的人挡住，因为它读的是"自己那一刻"的版本。

31.2 隐藏列与 undo 版本链

InnoDB 偷偷给每一行加了两个隐藏列，版本链就靠它们串起来。

  • 关键trx_id：最后修改这一行的事务 ID。谁改的，记在这；
  • 关键roll_pointer：指向这一行的上一个版本（存在 undo log 里）。

每次 UPDATE，旧值被写进 undo log 存一份，新行的 roll_pointer 指向这份旧值。多次修改，旧版本用 roll_pointer 一环扣一环，形成一条版本链。

31.3 ReadView：快照的判定规则

版本链上挂着好几个版本，读操作怎么知道"我能看哪个"？靠 ReadView。

ReadView 是事务在某个瞬间拍下的"活跃事务清单"，核心记录四个值：

  • m_ids：此刻还没提交的事务 ID 列表；
  • min_trx_id：m_ids 里最小的 ID；
  • max_trx_id：下一个要分配的事务 ID；
  • creator_trx_id：我自己的事务 ID。

判定规则（沿版本链从新往旧找）：

-- 对版本链上某个版本的 trx_id：
-- ① trx_id == 我自己            → 可见（自己改的）
-- ② trx_id < min_trx_id        → 可见（快照前已提交）
-- ③ trx_id >= max_trx_id       → 不可见（快照后才开始）
-- ④ trx_id 在 m_ids 里          → 不可见（拍下时它还没提交）
-- 不可见就顺着 roll_pointer 找下一个更老的版本，直到找到可见的
一句话：在我拍快照那一刻已经提交的版本我能看，还没提交的、以及之后才改的我都看不见——于是同一事务里多次读，看到的永远是同一份快照。

31.4 RC 与 RR 的差别：何时拍快照

两个级别用的是同一套 MVCC，差别只在于"多久拍一次 ReadView"。

隔离级别ReadView 何时建结果
RC 读已提交每次 SELECT 都新建 ReadView每次读都能看到最新已提交值 → 不可重复读
RR 可重复读事务第一次 SELECT 时建，之后复用整个事务看同一份快照 → 可重复读
RC 和 RR 底层都是 MVCC，唯一区别：RC 每读一次拍一张快照，RR 只读第一次、以后一直用它。这就是为什么 RR 能重复读、RC 不能。

延伸理解：RC 每次 SELECT 都新建 ReadView，所以它能读到"别的事务刚提交的新值"——这正是 RC 叫"读已提交"的原因。RR 只建一次快照，所以整个事务看到的世界冻结在开始那一刻，别的提交它统统"看不见"。

ReadView 不是无限保存的：事务一结束（COMMIT/ROLLBACK），它的 ReadView 就销毁，它引用的旧版本如果再没有别人需要，purge 线程就能清理了——这就是长事务拖住 undo 的完整链条。

31.5 快照读与当前读

MVCC 只对"快照读"生效；某些语句必须读最新数据，叫"当前读"。

-- 快照读：普通 SELECT，走 MVCC 快照，不锁、不阻塞
SELECT * FROM account WHERE id = 1;

-- 当前读：必须读最新已提交版本，并且要加锁
SELECT * FROM account WHERE id = 1 FOR UPDATE;   -- 加排他锁
SELECT * FROM account WHERE id = 1 LOCK IN SHARE MODE;  -- 加共享锁（8.0 用 FOR SHARE）
UPDATE account SET balance = balance - 100 WHERE id = 1;  -- 写，天然当前读
DELETE FROM account WHERE id = 1;                         -- 写，当前读

为什么写操作是当前读？因为你要基于"最新值"改，不能基于快照——否则两个事务都基于旧值更新，会丢更新。这也解释了 RR 下幻读为什么基本被杜绝：快照读看快照，当前读靠 next-key 锁挡住新插入（第 33 章）。

易混点：RR 下普通 SELECT 是快照读（看不到新插入），但 SELECT ... FOR UPDATE 或 UPDATE 是当前读（能看到新插入）。同一条范围查询，两种读法结果可能不同，排查幻读时先分清你用的是哪种读。
MVCC 的收益一句话：读操作走快照、不加锁，写操作追加新版本、不阻塞读。这就是 InnoDB 读写并发远高于"锁表"年代的根本原因。
代价也要知道：MVCC 不是免费的——版本链要靠 undo log 维持，长事务不提交就会让旧版本清理不掉（第 35 章长事务治理）。所以 MVCC 高效的前提，仍是事务要短。
读类型哪些语句读的是
快照读普通 SELECTMVCC 快照，不加锁
当前读SELECT ... FOR UPDATE / UPDATE / DELETE最新已提交版本，加锁
ReadView 不是永久免费：事务一结束（COMMIT/ROLLBACK），它的 ReadView 就销毁；它引用的旧版本如果再没有别人需要，purge 线程才能清理。长事务不提交，整串旧版本都被它"钉住"不敢删——这就是 MVCC 副作用的完整链条。
快照读 vs 当前读混着用：同一个事务里，普通 SELECT 看快照、FOR UPDATE/UPDATE 看最新值。代码里若先 SELECT 再 FOR UPDATE 同一行，结果可能不同，这是 MVCC 的设计而非 bug。

✓ 本章小结

要点一句话
MVCC读快照、写新版；读不阻塞写、写不阻塞读
隐藏列trx_id 记谁改的、roll_pointer 指向上个版本
版本链undo log 把旧值串成链，读操作沿链找可见版本
ReadView按活跃事务清单判断版本是否可见
RC vs RRRC 每次 SELECT 建快照，RR 只在第一次建、复用
快照读/当前读普通 SELECT 读快照；FOR UPDATE / 写操作读最新并加锁
