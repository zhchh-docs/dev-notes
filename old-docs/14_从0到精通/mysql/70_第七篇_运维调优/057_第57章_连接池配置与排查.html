57.1 为什么需要连接池

每次 TCP + 认证 + 会话变量初始化要花几毫秒到几十毫秒，高并发下比业务 SQL 本身还贵。

关键恒等式：后端总连接数 ≈ 应用实例数 × maximumPoolSize。这个乘积一旦超过 max_connections，应用侧拿不到连接、库侧报 too many connections，双向死锁。

57.2 池参数怎么配

池不是越大越快：HikariCP 官方建议 maximumPoolSize 远小于直觉值。

# Spring Boot + HikariCP 典型配置（application.yml）
spring:
  datasource:
    hikari:
      maximum-pool-size: 20        # 单实例池上限，不是越大越好
      minimum-idle: 5              # 常驻空闲连接
      connection-timeout: 3000     # 拿不到连接等 3s 就报错
      idle-timeout: 600000         # 空闲 10 分钟回收
      max-lifetime: 1800000        # 连接最长活 30 分钟（< wait_timeout）
      keepalive-time: 120000       # 每 2 分钟保活探测
参数经验值与逻辑
maximumPoolSizeCPU 密集型按核数×2~4；IO 型 20~50。200 个并发请求 ≠ 200 个连接
maxLifetime必须小于 MySQL 的 wait_timeout，否则池里拿着一条已被服务端杀掉的连接
connectionTimeout短一点（2~3s），快速失败比排队 30s 好，配合熔断
连接池的目标不是"满足全部并发"，而是把后端并发压在数据库能扛住的水位——排队在应用侧，别让它排到数据库连接上。

57.3 现场排查三板斧

线上报"数据库连接失败"时，按这三步定位，不要急着重启。

-- ① 总连接数与上限
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Max_used_connections';   -- 历史峰值，判断是否真打满过

-- ② 按维度分组：谁占的、在干嘛
SELECT USER, HOST, DB, COMMAND, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
GROUP BY USER, HOST, DB, COMMAND
ORDER BY cnt DESC;

-- ③ 揪出运行超过 30s 的会话（COMMAND=Query 的都是活跃查询）
SELECT ID, USER, HOST, DB, TIME, STATE, INFO
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Query' AND TIME > 30
ORDER BY TIME DESC;

-- 杀掉肇事会话
KILL 12345;
现象真正原因
Threads_connected 接近 max_connections连接池泄漏：应用借了不还，或池配太大 × 实例数太多
少数 Query 会话 TIME 几百秒慢查询/锁等待拖死，占用连接不放，先 KILL 再抓 SQL
应用侧报 timeout，库侧连接却很空网络/代理层问题，或连接池参数过小，不是库的锅
KILL 一个正在写事务的会话会触发回滚（undo 越大越慢），回滚期间连接依然占着。生产上先确认不是主写入链路再动手。

57.4 连接泄漏与长事务的识别

连接泄漏的本质是：事务开了不提交，连接被业务线程"忘了"还回来。

-- 8.0 看活跃事务：这些会话即使没在跑 SQL，也占着连接和锁
SELECT trx_id, trx_started, trx_mysql_thread_id,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS alive_sec,
       trx_query, trx_rows_modified
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC;

-- 配合：长事务 = 连接泄漏最大元凶
-- 应用侧规范：@Transactional 方法里严禁远程调用/发消息/做人机交互
  • 坑池配置 removeAbandoned（Druid）能强制回收泄漏连接，但它是创可贴，不是治疗；
  • 规范事务方法只做数据库操作，RPC/HTTP 一律挪到事务外。

57.5 连接数规划示例

把前面的恒等式落成一次真实决策。

-- 场景：4 个应用实例，每实例 HikariCP maximumPoolSize=20
-- 峰值总连接 = 4 × 20 = 80，留 30% 给运维/主从复制/监控
-- max_connections 设 200 足够，而不是 2000
SET PERSIST max_connections = 200;

✓ 本章小结

要点一句话
恒等式后端总连接 ≈ 实例数 × 池大小，乘积必须远小于 max_connections
池参数maximumPoolSize 克制（20~50），maxLifetime < wait_timeout，快速失败
排查三板斧看总量 → 按维度分组 → 抓长 Query/KILL，先定位再重启
长事务INNODB_TRX 查长寿事务，事务方法里禁 RPC，泄漏靠规范不靠创可贴
