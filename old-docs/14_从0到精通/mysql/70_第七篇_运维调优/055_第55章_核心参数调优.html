55.1 调优从哪里入手：先看清现状

参数调优的第一步永远不是"改"，而是"读"：把线上配置、负载特征、瓶颈指标三件事摆在桌上。

MySQL 的配置分两层：编译期硬编码、运行时系统变量。运行时变量又分动态变量（可在线 SET GLOBAL 立即生效）与只读变量（必须改配置文件重启才生效）。动手前先查清楚：

-- 看某个参数当前值与是否可动态修改
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'max_connections';

-- 8.0 推荐：从 performance_schema 看参数的可修改性与来源
SELECT VARIABLE_NAME, VARIABLE_VALUE,
       DEFAULT_VALUE, MIN_VALUE, MAX_VALUE, SET_TIME
FROM performance_schema.variables_info
WHERE VARIABLE_NAME IN ('max_connections','innodb_buffer_pool_size')\G

-- 已经在线改过但没写进配置文件？这里能看到 SET_TIME（NULL 表示从启动未动过）
SELECT * FROM performance_schema.variables_info
WHERE VARIABLE_NAME = 'long_query_time'\G
调优不是抄配置，是科学方法：基线、单变量、对照、写回配置文件，四步缺一不可。

55.2 连接与并发类参数

连接数打满是中小业务最常见的"假死"原因：应用报 too many connections，库本身却 CPU 不高。

-- 最大连接数（默认 151，线上常见 500~2000）
SET GLOBAL max_connections = 1000;

-- 每个连接的内存开销：sort_buffer / join_buffer / read_buffer 是"每连接"分配
-- 别把它们设太大：max_connections × 每连接 buffer = 内存炸弹
SHOW VARIABLES LIKE 'sort_buffer_size';      -- 默认 256K
SHOW VARIABLES LIKE 'join_buffer_size';       -- 默认 256K

-- 空闲连接多久断开（秒），防止连接池泄漏把连接占死
SET GLOBAL wait_timeout = 28800;              -- 默认 8 小时，生产建议 600~1800
SET GLOBAL interactive_timeout = 28800;

-- 看连接到底都被谁占了
SELECT USER, HOST, DB, COMMAND, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
GROUP BY USER, HOST, DB, COMMAND ORDER BY cnt DESC;
参数默认值调优逻辑
max_connections151按"应用连接池总数 × 实例数 + 预留"估算，不是越大越好——连接本身吃内存
wait_timeout28800连接池会保活，反把它调小到 600s 让空闲连接快速回收
max_allowed_packet64M(8.0)导大字段/批量数据报 packet too large 时才调，平时别动
thread_cache_size自动8.0 在线程池模型下保持默认即可
坑：sort_buffer_size / join_buffer_size / read_buffer_size 是每个连接各自一份，把它们从 256K 改成 4M，1000 个连接最坏瞬间多吃 4G——这类"全局"参数从来不是越大越快。

55.3 InnoDB 核心参数速览

这一组是 InnoDB 的"骨架参数"，下一章会专门展开 Buffer Pool，这里先建立全局图。

-- Buffer Pool：数据页 + 索引页的内存缓存，最重要的一个参数（60% 以上问题都归它）
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- redo 日志容量（8.0.30+ 用 innodb_redo_log_capacity 统一管理）
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';

-- 脏页刷新与刷盘策略
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';  -- 1=最安全，0/2=更快但丢数据风险
SHOW VARIABLES LIKE 'sync_binlog';                     -- 1=最安全

-- 锁与死锁监控
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';        -- 默认 50s，业务侧建议 5~10s
双 1 配置：innodb_flush_log_at_trx_commit=1 配合 sync_binlog=1 是金融级 durability 标配，绝不为了"快"改成 0/2——那意味着掉电丢 1 秒事务。

55.4 慢查询与优化器参数

参数调优的 ROI 之王永远是慢查询：一条没走索引的 SQL 吃掉的资源，抵得过十个参数的微调。

-- 开启慢日志（动态）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;            -- 超过 1 秒记为慢查询
SET GLOBAL long_queries_not_using_indexes = ON;  -- 没走索引的全部记录

-- 看慢日志采样（performance_schema 版本更准）
SELECT DIGEST_TEXT, COUNT_STAR, ROUND(AVG_TIMER_WAIT/1e9,2) AS avg_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY AVG_TIMER_WAIT DESC LIMIT 10;

-- 优化器成本常数：别乱改，8.0 自带的引擎常量表已足够好
SHOW VARIABLES LIKE 'optimizer_switch';
场景建议
老业务全表扫描多开 long_queries_not_using_indexes，先抓贼再谈参数
EXPLAIN 走错索引先 ANALYZE TABLE 刷新统计信息，再考虑 OPTIMIZER_TRACE，最后才是 index hint
批量导数据临时跑会话级 SET unique_checks=0 / foreign_key_checks=0，导完恢复，绝不全局改

55.5 在线修改与配置持久化

8.0 的持久化特性让"在线改完忘写配置文件"这类事故大大减少。

-- 只改内存，重启即丢（实验阶段用这个）
SET GLOBAL max_connections = 1000;

-- 改内存 + 写 mysqld-auto.cnf，重启不丢（8.0 推荐）
SET PERSIST max_connections = 1000;

-- 撤销某个 PERSIST，回到编译默认
RESET PERSIST max_connections;

-- 查看已持久化的参数
SELECT VARIABLE_NAME, VARIABLE_VALUE FROM performance_schema.persisted_variables;
  • 原则SET GLOBAL 用于临时验证，SET PERSIST 用于确认后的固化；
  • 坑只改 my.cnf 不重启 = 没改；只 SET GLOBAL 不持久化 = 重启回滚，两种错误各背一次就记住了；
  • 规范变更走变更单：记录"改前值/改后值/回滚语句/观察窗口"，贴在工单里。

✓ 本章小结

要点一句话
调优方法论先测量建立基线，一次只改一个参数，对照验证后再固化
连接参数max_connections 按连接池估算；每连接 buffer 乘连接数才是内存真相
双 1innodb_flush_log_at_trx_commit=1 + sync_binlog=1 是 durability 底线
慢查询开 slow_query_log + not_using_indexes，抓贼比调参 ROI 高得多
持久化SET GLOBAL 做实验，SET PERSIST 做固化，RESET PERSIST 做回滚

✎ 本章习题

A 基础用 SHOW VARIABLES 查出本机 max_connections、innodb_buffer_pool_size、long_query_time 的当前值，并说明每个是动态还是只读参数。
B 进阶在线用 SET PERSIST 把 long_query_time 从默认改为 0.5，再从 performance_schema.persisted_variables 确认它已落盘，最后用 RESET PERSIST 撤销。
C 挑战一台 16G 内存的服务器上，DBA 把 sort_buffer_size 调到 8M、max_connections 调到 2000，结果上线即 OOM。请算最坏情况下的每连接内存总和，并说明应该如何合理估算。
