63.1 案例一：连接数打满，应用大面积超时

现象：APP 下单接口 504，监控显示库 Threads_connected 打满。

-- 定位
SHOW STATUS LIKE 'Threads_connected';
SELECT USER, HOST, COMMAND, COUNT(*) FROM information_schema.PROCESSLIST
GROUP BY USER, HOST, COMMAND ORDER BY 4 DESC;
-- 发现：某个新上线服务 20 个实例，每实例池配了 100，总连接 2000 > max_connections 500

根因：连接池大小 × 实例数超过 max_connections（第 57 章恒等式）。止血：临时调高 max_connections + 下线问题服务。复盘：连接池配小、max_connections 按乘积重算。

63.2 案例二：慢查询把 CPU 打满

现象：白天 11 点 CPU 100%，业务 RT 飙升。

-- 用 digest 抓元凶
SELECT LEFT(DIGEST_TEXT,100), COUNT_STAR,
       ROUND(AVG_TIMER_WAIT/1e9,1) avg_ms, SUM_ROWS_EXAMINED
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 5;
-- 发现：一条新上线的"搜索"SQL 没走索引，扫了 800 万行

根因：上线评审漏了 SQL 审核。止血：KILL 会话 + 紧急加索引。复盘：把"上线前 EXPLAIN"加入发布门禁。

故障复盘不问"谁写的"，问"哪道流程没拦住"——改流程比骂人有用。

63.3 案例三：主从延迟导致读到旧数据

现象：用户刚下单，订单列表却查不到（读走从库）。

SHOW REPLICA STATUS\G
-- Seconds_Behind_Source = 120，且在跑一个大事务批量更新

根因：批量脚本在主库跑大事务，从库单线程回放跟不上。止血：关键读请求临时切主库。复盘：批量任务拆小、从库开启并行复制（8.0 支持 WRITESET 并行）。

63.4 案例四：磁盘写满，库只读

现象：凌晨业务全部写失败，报"no space left"。

根因：binlog 保留策略过久 + 慢日志堆积。止血：清理过期 binlog（PURGE BINARY LOGS BEFORE ...），不是删文件。复盘：binlog 保留 3~7 天、磁盘告警 70% 预警。

千万不要直接 rm 删 binlog 文件——MySQL 的索引还记着它们，会导致主从崩溃。一律用 PURGE BINARY LOGS。

63.5 案例五：误删表，靠 binlog 恢复

现象：开发在测试库执行错了库，DROP 了一张表。

根因：测试与生产同名库，连接串点错。止血：用最近全量备份 + binlog 重放到误操作前一秒。复盘：生产库账号 DROP 权限收回、DML 前置确认。

63.6 故障应对 Checklist

把五个案例浓缩成一张现场动作表。

现象第一步动作
大面积超时看 Threads_connected，分组 PROCESSLIST 找占用大户
CPU 飙高digest 抓最近最贵 SQL，KILL 肇事会话
读到旧数据看主从延迟，关键读临时切主库
写入失败查磁盘空间，PURGE 过期 binlog
误删数据停止写入，准备备份 + binlog 重放
现场原则：先恢复业务可用性，再保留现场（日志、状态），最后做根因复盘。
复盘会纪律：对事不对人，产出是"流程改进项"而非"责任归属"。
  • 每次故障记录：时间线、影响面、止血动作、根因、改进项；
  • 改进项要有 owner 和截止日期，否则等于没复盘。

63.7 复盘记录模板

复盘不是开会，是填一张结构化的表。

故障记录单
时间：2026-xx-xx  影响面：下单接口 RT 飙升
时间线：
  14:02 监控告警 Threads_running 飙到 80
  14:03 KILL 肇事慢查询，业务恢复
  14:10 定位为新上线搜索 SQL 未走索引
根因：上线评审未做 SQL 审核
改进项：
  [ ] 发布门禁加入 EXPLAIN 检查（owner: 张三，截止 11-01）
  [ ] 慢查询告警阈值下调（owner: 李四，截止 11-05）
改进项必须有 owner 和截止日期，否则复盘会开完就等于没开。

63.8 故障分级响应

故障不是越大越慌，按影响面定级，动作标准化。

级别现象第一步
P0全站不可用切灾备/限流，拉群通报
P1核心链路 RT 飙升KILL 慢查询，读请求切主
P2局部功能慢抓 digest，定位 SQL
分级的意义：半夜被叫醒时不用临场判断，按表执行。

✓ 本章小结

要点一句话
通用套路现象 → 指标定位 → 根因 → 止血 → 流程复盘
先止血连接打满/CPU 飙高/磁盘满，先恢复业务再查根因
复盘对象复盘的是"哪道流程没拦住"，不是哪个人
恢复手段全量备份 + binlog 重放是误删误改的最终保险
复盘模板每次故障填一张表，沉淀成组织资产
分级响应按影响面定级，止血动作标准化
