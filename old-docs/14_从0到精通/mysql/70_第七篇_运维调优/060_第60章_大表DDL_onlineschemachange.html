60.1 为什么大表 ALTER 这么痛

传统 COPY 算法要整表复制：500G 的表 ALTER 一次锁几小时，业务直接停摆。

-- 直接在大表上加索引：8.0 之前可能锁表数小时
ALTER TABLE orders ADD INDEX idx_user_created(user_id, created_at);

-- 先看这次 ALTER 到底用什么算法、加什么锁（8.0 支持 EXPLAIN 格式预演）
ALTER TABLE orders ADD INDEX idx_user_created(user_id, created_at), ALGORITHM=INPLACE, LOCK=NONE;
-- 若服务端不支持 LOCK=NONE 会直接报错而不是默默锁表——这是关键保护
算法行为对业务影响
COPY建临时表，整表复制读写都受限，大表灾难
INPLACE在原表上改，不整表复制多数加索引/加列可用，仍有短暂元数据锁
INSTANT（8.0.12+）只改元数据加列（末尾）瞬时完成，毫秒级
8.0.12 起加列走 INSTANT；8.0.29 起 INSTANT 支持更多位置。但删列、改类型、重排列仍可能走 INPLACE/COPY——每个 DDL 前都用 ALGORITHM=... LOCK=NONE 显式约束，不支持就报错，别让它默默锁表。

60.2 pt-online-schema-change 原理

当原生方案不够用时，pt-osc 的思路：影子表 + 触发器追平增量。

# 给 orders 加列（实际改成新表结构），每批 1000 行，看进度
pt-online-schema-change   --alter "ADD COLUMN remark VARCHAR(255)"   --host=127.0.0.1 --user=root --ask-pass   D=shop,t=orders --print --progress=time,10 --chunk-size=1000
坑：pt-osc 靠触发器追增量——原表上已有触发器时它会直接拒绝运行；且触发器本身在高写入下是开销。这就是 gh-ost 出现的原因。

60.3 gh-ost：无触发器方案

gh-ost 由 GitHub 开源，不建触发器，改为解析 binlog 把原表变更流式应用到影子表。

维度pt-online-schema-changegh-ost
追增量方式原表建触发器读 binlog 流式应用
对原表侵入有触发器开销无触发器
暂停/控制有限可动态暂停、限速、切换
前置条件原表无触发器binlog 格式 ROW
 
# gh-ost 典型命令（需 ROW 格式 binlog）
gh-ost --host=127.0.0.1 --user=root --ask-pass   --database=shop --table=orders   --alter="ADD INDEX idx_user_created(user_id, created_at)"   --max-load=Threads_running=50   --chunk-size=1000 --allow-on-master --execute
选型顺序：先试原生 INSTANT/INPLACE + LOCK=NONE（零成本）；不够用再 gh-ost（无触发器、可控）；pt-osc 作为兼容兜底。

60.4 排期与止损

  • DDL 排在业务低峰，先在从库验证耗时；
  • 改前备份表结构与数据（至少逻辑导出）；
  • gh-ost 支持 --postpone-cut-over-flag-file，切换时机可人工控制；
  • 监控Threads_running、主从延迟，飙高就暂停。

60.5 DDL 风险清单

每次在线改表前，按这张单子过一遍，避免"改完才想起"。

-- 改前预估：该表大小与行数
SELECT table_name, table_rows,
       ROUND((data_length+index_length)/1024/1024/1024,2) AS gb
FROM information_schema.TABLES
WHERE table_schema='shop' AND table_name='orders';

-- 改中：盯主从延迟，飙高就 gh-ost 暂停
SHOW REPLICA STATUS\G
  • 风险元数据锁排队：长事务会让 DDL 等待并堵住后续查询；
  • 动作改前确认无长事务（INNODB_TRX），低峰执行；
  • 回滚gh-ost/pt-osc 中途可中止，已建影子表可丢弃，不影响原表。
一句话选型：能 INSTANT 就 INSTANT，其次 INPLACE+LOCK=NONE，大改表用 gh-ost，pt-osc 兜底。
-- 执行前最后确认：无长事务
SELECT * FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30;
