61.1 表无界增长的代价

一张表从 100 万行涨到 1 亿行，不只是"变大"，而是全链路变慢：备份、DDL、查询、缓存命中率一起恶化。

61.2 归档边界怎么定

归档不是"删旧数据"，是"按业务规则把不常访问的行整体搬走"。

维度示例规则注意点
时间订单完成超过 180 天归档以"业务结束时间"为准，不是创建时间
状态已取消且未支付 30 天的订单先确认无退款/申诉流程依赖
租户/项目已下线项目的数据整库归档外键关联表要一并搬
 
-- 归档前：先看候选数据量与边界
SELECT COUNT(*) FROM orders
WHERE status = 'FINISHED' AND finished_at < '2026-04-01';

-- 归档后必须保留回查路径：归档库保留同构表，或在应用层加"查不到去冷库找"逻辑
-- 不要物理 DELETE 后不留副本——合规审计随时可能要三年前的订单
归档前必须确认：这条线还会不会被业务查询命中？客服、对账、风控都可能翻历史单。没走通"回查路径"之前，只搬不删（双写一段时间）。

61.3 落地：pt-archiver 跑批

把候选行从热库搬到归档库，逐批删除源行。

# 每月凌晨跑一次：把完成满 180 天的订单搬到归档库
pt-archiver   --source h=prod-mysql,D=shop,t=orders   --dest h=archive-mysql,D=archive,t=orders   --where "status='FINISHED' AND finished_at < DATE_SUB(CURDATE(), INTERVAL 180 DAY)"   --limit 2000 --commit-each   --bulk-insert --bulk-delete   --progress 5000 --statistics --no-check-charset
  • 要点--commit-each 每批提交，避免大事务；
  • 监控看 --statistics 输出的耗时与吞吐；
  • 坑忘记在低峰跑，归档任务本身会和业务抢 IO。

61.4 冷热分离的终局

归档库也只是中间态，真正的冷库是列存或对象存储。

  • 一年以上的数据：导出 Parquet 到对象存储，配合 Hive/Spark 做分析；
  • 需要偶尔在线回查：归档库保留同构 MySQL 表；
  • 热库则永远保持"近期数据"，索引小、备份快、恢复快。
归档的目标不是省磁盘，是让热库保持小而快——备份以小时计、DDL 以分钟计、查询以毫秒计。

61.5 归档常见问答

几个被反复问到的边界问题。

-- Q：归档要不要保留自增 ID 连续？
-- A：不需要。归档表用原 id 即可，业务靠 order_no 查，不靠 id 连续。
-- Q：归档后自增主键会冲突吗？
-- A：不会，归档库是独立库表，自增从原 id 起也不会与热库新行冲突。

-- 回查示例
SELECT * FROM archive.orders WHERE order_no='NO202610230001';
归档不是删除，是"换一个地方放"：可回查、可对账、合规可追溯，三可缺一不可。
归档节奏：先双写过渡一个月确认回查无误，再切删除；不要第一步就物理删。
-- 过渡期间：归档库与热库并存，客服系统按时间路由
-- 2026 年订单查 archive.orders，其余查 shop.orders
SELECT * FROM archive.orders WHERE order_no='NO..' AND created_at < '2025-10-01';

61.6 归档后校验脚本

归档任务跑完不要立刻下班，做一次行数对账才算闭环。

-- ① 热库应已无 180 天前的 FINISHED 订单
SELECT COUNT(*) AS residual FROM orders
WHERE status='FINISHED'
  AND finished_at < DATE_SUB(CURDATE(), INTERVAL 180 DAY);
-- 期望：0

-- ② 归档库本次新增行数 = 源库候选行数（脚本启动时记下）
SELECT COUNT(*) FROM archive.orders
WHERE archived_at BETWEEN '2026-11-01 02:00' AND '2026-11-01 04:00';

-- ③ 抽 10 个 order_no 双侧各查一次，金额一致即通过
对账失败先别删归档库数据：用 order_no 把缺失行从 binlog 或备份补回，再决定重跑。

61.7 归档常见问答

几个被反复问到的边界问题，一次说清。

-- Q1：归档后自增主键会冲突吗？
-- A：不会。归档库是独立库表，原 id 照搬，热库新行从更大自增值起步。
-- Q2：靠 order_no 查历史单要去哪？
-- A：先热库，查不到再去归档库同构表。
SELECT * FROM archive.orders WHERE order_no='NO202610230001';
归档不是删除，是换个地方放：可回查、可对账、可审计。
