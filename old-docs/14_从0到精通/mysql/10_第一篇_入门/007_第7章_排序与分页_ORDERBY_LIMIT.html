第 7 章 排序与分页：ORDER BY/LIMIT

7.1 ORDER BY：升降序与多列

ORDER BY 决定结果集的行先后顺序——没有它，MySQL 返回行的顺序是不保证的（别依赖"看起来是主键顺序"）。

-- 单列升序（ASC 可省略，但建议显式写）
SELECT id, name, price FROM product
WHERE category_id = 3
ORDER BY price ASC;

-- 多列排序：先按类目升序，同类目下价格降序，再按销量升序
SELECT id, name, category_id, price, sales
FROM product
WHERE is_deleted = 0
ORDER BY category_id ASC, price DESC, sales ASC;

-- 按表达式排序：按"折扣价"排序
SELECT id, name, price, price * 0.85 AS promo_price
FROM product
ORDER BY price * 0.85 DESC;

-- 按列在 SELECT 列表里的位置排序（不推荐，仅知道有这回事）
SELECT id, name, price FROM product ORDER BY 3 DESC;  -- 按第 3 列 price

三个要点：

  • 默认是 ASC：只写 ORDER BY price 就是升序；线上代码里显式写 ASC/DESC，读代码的人不用猜；
  • 多列排序逐列生效：只有前一列值相等时才比较下一列，和 JS 的 sort((a,b)=>...) 链式比较 完全一样；
  • ORDER BY 可以用 SELECT 里的别名：ORDER BY promo_price DESC 直接可用（这是它和 WHERE 的区别）。

7.2 LIMIT：切片与分页

LIMIT 从"排好序的结果集"里切一段——它是列表页的核心。

-- 取前 10 条：商品列表第一页
SELECT id, name, price, sales
FROM product
WHERE is_deleted = 0
ORDER BY sales DESC, id DESC
LIMIT 10;

-- 第 2 页：跳过 10 条，再取 10 条（page=2, size=10）
SELECT id, name, price, sales
FROM product
WHERE is_deleted = 0
ORDER BY sales DESC, id DESC
LIMIT 10 OFFSET 10;

-- 等价的老写法（MySQL 方言，能读即可）
SELECT ... LIMIT 10, 10;

-- 业务常客：TopN（销量前 3 的商品）
SELECT id, name, sales FROM product
ORDER BY sales DESC LIMIT 3;
分页查询的排序键必须"唯一且稳定"：ORDER BY 的最后一列一定带上主键（如 ORDER BY sales DESC, id DESC），否则同一销量的行在翻页时会被重复或漏掉。

7.3 深分页问题与游标分页

LIMIT 100000, 10 不是"跳过 10 万行再取 10 条"那么便宜——数据库真的要把前 10 万行都读出来、再扔掉。

-- 反面教材：第 10001 页，OFFSET = 100000
SELECT id, name, price FROM product
ORDER BY id
LIMIT 100000, 10;

-- 游标分页（keyset pagination）：记住上一页最后一行的"游标值"，下次从它接着读
-- 第 1 页
SELECT id, name, price FROM product
ORDER BY id LIMIT 10;            -- 假设最后一行 id = 100

-- 第 2 页：不用 OFFSET，直接"大于上一页的最后一个游标"
SELECT id, name, price FROM product
WHERE id > 100
ORDER BY id LIMIT 10;

-- 按非唯一列排序时，游标用"(排序列, 主键) 联合"
SELECT id, sales, name FROM product
WHERE (sales, id) < (1234, 88)   -- 上一页最后一行的 (sales,id)
ORDER BY sales DESC, id DESC
LIMIT 10;

为什么游标分页快？WHERE id > 100 ORDER BY id LIMIT 10 可以直接从索引的 100 号位置开始读 10 行，全程只读 10 行；而 OFFSET 要先扫过 10 万行。代价是：游标分页不支持"跳到第 N 页"，只支持"下一页"和"上一页"——这对 App 无限滚动、后台流水列表完全够用，电商"跳到第 50 页"的功能本来就极少有人点。

后台管理系统常见的"每页 50 条、共 1 万页"用 OFFSET 是常态（管理后台量级不大），但 C 端列表、日志流水、消息记录这类千万级表，从第一天就该用游标分页，否则数据量上来后就是定时炸弹。

7.4 排序与索引的关系

排序有两条路径，成本天差地别：

方式触发条件成本
索引有序扫描ORDER BY 的列顺序、方向与某个索引完全一致，且 WHERE 条件能用上该索引的前缀几乎为零，按索引顺序读即可
filesort没有合适索引，或索引方向对不上（如 ORDER BY a ASC, b DESC 但索引是 a ASC, b ASC）把满足 WHERE 的行捞出来在内存/磁盘排，数据量越大越慢
 
-- 有索引 idx_category_sales (category_id, sales)：
-- 下面这条查询直接沿索引顺序读，不需要 filesort
SELECT id, name FROM product
WHERE category_id = 3
ORDER BY sales LIMIT 10;

-- 但换个方向就排不上：索引是 (category_id, sales ASC)，
-- 这里要求 sales DESC，MySQL 8.0 之前只能 filesort（8.0 支持降序索引）
SELECT id, name FROM product
WHERE category_id = 3
ORDER BY sales DESC LIMIT 10;

第 19 章会从 B+ 树结构讲清"为什么索引天然有序"；现在先记住：EXPLAIN 结果里 Extra 出现 Using filesort 就要警觉——配合 LIMIT 的 TopN 场景，filesort 往往意味着"为了 10 条返回结果排了十万行"。

7.5 排序稳定性与 NULL

两个实战细节：

  • NULL 的位置：MySQL 中升序时 NULL 排在最前，降序时排在最后——这是固定行为，但如果你希望 NULL 一律排最后，用表达式兜底：ORDER BY (level IS NULL), level ASC；
  • 排序不稳定：ORDER BY 某列时，值相等的两行谁先谁后不保证。这就是 7.2 强调"排序键最后带上唯一主键"的原因——不带，翻页时就会出现"上一页见过的人又出现在下一页"。
-- level 为 NULL 的用户排最后，其余按 level 字母序
SELECT id, name, level FROM customer
ORDER BY (level IS NULL) ASC, level ASC, id ASC;
前端转全栈的你会发现这很像 JS 的 Array.sort 不稳定问题（ES2019 后 V8 稳定了）——数据库这边只能自己用唯一列兜底。

✓ 本章小结

要点一句话
ORDER BY默认升序；多列逐列比较；最后一列务必带唯一主键保证分页稳定
LIMITLIMIT n 取前 n 条；OFFSET 翻页；TopN 就是 LIMIT n
深分页OFFSET 越大越慢；千万级表用游标分页（WHERE 游标 > 上次最后一行）
filesort排序列与索引对不上时触发，EXPLAIN 看到 Using filesort 要警觉
NULL 排序升序排最前、降序排最后；可用表达式把 NULL 强制沉底
