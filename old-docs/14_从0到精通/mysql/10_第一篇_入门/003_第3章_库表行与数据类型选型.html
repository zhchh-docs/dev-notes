3.1 库：数据的第一层隔离

一个 MySQL 服务实例里可以建多个库（Database / Schema）。库是组织数据的第一层文件夹，也是权限隔离（第 2 章 GRANT ON bookshop.*）和备份单位（mysqldump 通常按库导）。典型分法：

  • 按业务域分：订单库、商品库、用户库各一个，微服务架构下每个服务一个库；
  • 按环境分：生产上 dev / test / prod 通常使用不同实例，而不是同一实例里的不同库。
CREATE DATABASE IF NOT EXISTS bookshop
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

SHOW CREATE DATABASE bookshop;   -- 回看库的字符集配置
DROP DATABASE bookshop;          -- 危险操作：连表带数据一起删，无确认、难恢复
为什么强调 utf8mb4：MySQL 的 utf8 实际只支持 1-3 字节，存不了 emoji 和部分生僻字。utf8mb4 才是完整 UTF-8。8.0 默认已是 utf8mb4，但 5.7 遗留库仍常见 utf8——接手旧库先查字符集。

3.2 表与行：结构化存储的单元

表是行的集合，行是字段的集合。与 Excel 不同，表结构（有哪些列、什么类型）必须先定义后使用，每行都遵守同样的结构——这正是数据库能做一致性检查的原因。

USE bookshop;

-- 先建一张最简单的表练手（语法细节下一章展开）
CREATE TABLE student (
  id     INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name   VARCHAR(50)  NOT NULL,
  age    TINYINT UNSIGNED NULL,
  score  DECIMAL(5,2) NULL
);

INSERT INTO student (name, age, score) VALUES ('张三', 20, 88.50);
INSERT INTO student (name, age, score) VALUES ('李四', 21, 92.00);

SELECT * FROM student;   -- 看到的每一行就是一条记录

三个关键认知：

  • 行没有固有顺序：两次 SELECT 的返回顺序可能不同，要顺序必须显式 ORDER BY；
  • NULL 不是 0 也不是空串：它表示"未知/未填写"，比较时要用 IS NULL；
  • 行数没有硬上限：单表千万行很常见，但到达一定量级仍要考虑分表（第 49 章展开）。

3.3 常用数据类型速览

类别类型范围 / 说明典型用途
整数TINYINT有符号 -128~127；UNSIGNED 0~255状态、开关、年龄
INT约 ±21 亿；UNSIGNED 约 0~42 亿一般 ID、数量
BIGINT约 ±9.2×10^18订单号、分布式 ID
小数DECIMAL(M,D)精确定点数，DECIMAL(10,2) 可到亿级金额带 2 位小数金额、费率
字符串CHAR(N)定长，不足补空格手机号、固定编码
VARCHAR(N)变长，N 为字符数姓名、标题、地址
TEXT长文本，不能设默认值文章正文、JSON 串
时间DATE只有日期生日、账期
DATETIME日期+时间，与时区无关，范围 1000~9999 年业务发生时间（推荐）
TIMESTAMPUTC 存储、读时转会话时区，只到 2038 年创建/更新时间戳

还有两个"枚举"工具：ENUM('男','女') 与 SET('a','b')。能用，但不推荐——每加一个选项都要改表结构（DDL），用 TINYINT 状态列 + 字典表（或应用层枚举）更灵活。

3.4 选型原则与经典坑

铁律一：钱永远用 DECIMAL。FLOAT/DOUBLE 是二进制浮点，存 0.1 就不精确，累计对账必然对不上：

SELECT 0.1 + 0.2;   -- 0.30000000000000004（浮点的锅）
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2));  -- 0.30，精确

铁律二：时间想清楚时区。DATETIME 存"字面时间"（你写 8 点就是 8 点），TIMESTAMP 存 UTC、按会话时区转换。业务字段（下单时间、发货时间）用 DATETIME 直观省心；TIMESTAMP 的 2038 上限是真实风险。

铁律三：字符串长度够用就好，但别抠到没余地。VARCHAR(N) 的 N 影响索引长度与内存临时表，常用经验值：姓名 50、手机号 CHAR(11)、邮箱 100、地址 255、标题 255。上千字符的长文本考虑 TEXT 或拆表。

其他经典坑：

  • 坑INT(11) 的 11 只是显示宽度，不代表存储范围；范围只看类型本身，8.0 已弃用显示宽度写法；
  • 坑类型管不了内容合法性：VARCHAR 手机号列能存进 "abc"，内容约束靠 CHECK 约束或应用层校验（下一章）；
  • 坑用 VARCHAR 存逗号分隔标签（"a,b,c"）再 LIKE 查询——无法走索引、无法统计，多值关系应拆成关联表。

3.5 查看结构的三板斧

DESC student;              -- 快速看列名、类型、是否可空、键
SHOW COLUMNS FROM student; -- 等价于 DESC
SHOW CREATE TABLE student; -- 完整建表语句（含引擎、字符集、索引）——最有用

-- 想知道表有多少行、多大：
SELECT COUNT(*) FROM student;
SHOW TABLE STATUS LIKE 'student';   -- Rows / Avg_row_length / Data_length

SHOW CREATE TABLE 是排障神器：线上表"看起来不对"时先看真实定义，90% 的疑问（字符集、默认值、索引缺失）在这里直接现形。今后每接手一张陌生表，第一件事就是跑它。

表结构是"合同"：一旦被程序依赖，改它就要付出代价。上线前的类型选型，值得多花十分钟。

✓ 本章小结

要点一句话
