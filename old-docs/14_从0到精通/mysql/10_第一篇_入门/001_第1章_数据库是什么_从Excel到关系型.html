1.1 从 Excel 说起：数据放哪里

几乎所有初学者都管过一张 Excel 表：学员名单、订单记录、库存台账。Excel 已经是"表格"了，为什么全世界还要再造一个叫"数据库"的东西？

设想你在一家电商公司管订单。最开始订单放在一个 Excel 文件里，随着业务增长，你会依次撞上四堵墙：

  1. 并发墙：你正在改第 3 行，同事也打开了同一个文件——Excel 网络共享只允许一个人编辑，第二个人只能"只读"。而真实的业务系统里，成百上千个用户同时下单、退款、查询，数据必须支持高并发读写。
  2. 容量墙：Excel 单表约 104 万行就到顶了。而一个中型电商一天就能产生几百万条订单明细，几年的历史数据动辄数十亿行。
  3. 一致性墙：Excel 没有强制约束。你在"性别"列里写个"nan"没人拦你；下单时库存减了、订单却没记上（比如中途断电），Excel 也不会帮你回滚。数据库用约束和事务系统性地解决这两个问题——这是本书第四篇的主题。
  4. 权限与审计墙：Excel 只能设"打开密码"，无法做到"财务组能看金额、客服组只能看姓名"。数据库提供到表级甚至列级的权限控制，并记录每一次操作的日志。
一句话总结：Excel 是"一个人记录数据"的工具，数据库是"很多程序同时、安全、海量地读写数据"的基础设施。

再看一个技术上的差别：Excel 文件是一个黑盒二进制文件，程序想读写它必须依赖 Excel 本身；而数据库是一个常驻运行的软件服务，任何语言（Java、Python、Go……）都能通过网络连接它，用统一的语言（SQL）读写数据。这也是它能成为"系统底座"的原因。

1.2 "关系型"的"关系"指什么

关系型数据库（RDBMS）的"关系"不是指"表之间有关联"这么宽泛，而是来自 1970 年 E.F. Codd 提出的关系模型：数据被组织成一张张二维表，数学上每张表就是一个"关系（Relation）"。这套模型有几个铁律：

  • 行（Row / 记录）：一行代表一个完整的"实体"，比如一个学生、一张订单。行没有先后顺序——这点和 Excel 直觉不同，想要顺序必须用 ORDER BY 明确指定；
  • 列（Column / 字段）：每一列有名字和数据类型，同一列的所有值类型一致。"手机号"这一列要么全是字符串，要么干脆报错，不允许混着来；
  • 主键（Primary Key）：能唯一标识一行的列（或列组合），比如学号、订单号。没有主键的表在关系模型里是残缺的；
  • 关系（表间联系）：通过"外键引用另一张表的主键"来表达。订单表里不复制客户的全部信息，只存一个 customer_id，需要时去客户表查——这就是"关系"的日常用法。
-- 感受一下两张表如何用"关系"组织数据（第 4 章会逐行讲解语法）
CREATE TABLE customer (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(50)  NOT NULL,
  phone       CHAR(11)     NOT NULL
);

CREATE TABLE orders (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  customer_id  BIGINT      NOT NULL,   -- 只存引用，不复制客户资料
  amount       DECIMAL(10,2) NOT NULL,
  created_at   DATETIME    NOT NULL
);
为什么这样设计：客户改了手机号，只需要改 customer 表一行；如果订单表里复制了手机号，就要改一万条订单——这种"改一处"的设计思想叫规范化，第 27 章会展开它的收益与代价。

1.3 SQL：和数据库对话的语言

SQL（Structured Query Language，结构化查询语言）是操作关系型数据库的标准语言。它最大的特点是声明式：你只说"要什么"，不说"怎么拿"——怎么扫表、走不走索引、以什么顺序关联，由数据库的优化器自己决定。这是它和 Java、Python 等命令式语言最本质的区别。

SQL 按功能分为四大类，这个分类贯穿全书，务必记住：

分类全称与职责代表语句本书对应
DDL数据定义：定义结构CREATE / ALTER / DROP第 4、16 章
DML数据操作：读写数据INSERT / UPDATE / DELETE / SELECT第 5-14 章
DCL数据控制：权限与事务GRANT / REVOKE / COMMIT第 29、62 章
TCL事务控制BEGIN / COMMIT / ROLLBACK第四篇
 
-- 一条典型的 SELECT：从订单表里查 2024 年金额最大的 5 笔订单
SELECT o.id, c.name AS customer_name, o.amount
FROM orders AS o
JOIN customer AS c ON c.id = o.customer_id
WHERE o.created_at >= '2024-01-01'
  AND o.created_at <  '2025-01-01'
ORDER BY o.amount DESC
LIMIT 5;

先混个脸熟：上面这条 SQL 覆盖了 SELECT 的六个基本子句——SELECT / FROM / JOIN / WHERE / ORDER BY / LIMIT。你不需要现在看懂，只需要知道：SQL 读起来接近英语，写代码的过程更像"描述需求"。第 6 章开始我们会逐个拆解。

1.4 MySQL 的位置与常见兄弟们

数据库按"数据模型"分两大阵营。MySQL 属于关系型阵营，而且是世界上使用最广泛的开源关系型数据库之一（LAMP 技术栈中的 M）。同阵营的主要选手：

数据库特点典型场景
MySQL开源、轻量、生态成熟、互联网公司标配Web 业务、中小型系统到大型互联网
PostgreSQL开源、功能更强（复杂查询/JSON/地理信息）对标准兼容和复杂特性要求高的系统
Oracle商业旗舰，功能全面但昂贵银行、电信等传统大型核心系统
SQL Server微软系商业数据库.NET 技术栈、Windows 生态

另一个阵营是非关系型（NoSQL），它们不是为了取代关系型，而是各守一块场景：

  • Redis：内存键值库，做缓存、计数器、分布式锁（本书第 68 章讲它与 MySQL 的配合）；
  • MongoDB：文档库，存结构灵活的 JSON 文档；
  • Elasticsearch：搜索引擎，做全文检索与日志分析（第 69 章）；
  • HBase / Cassandra：宽列存储，海量写入场景。
真实系统几乎都是"组合拳"：MySQL 做权威数据源，Redis 挡读流量，ES 做搜索——而不是用某一个包打天下。

最后交代 MySQL 的版本：本教程以 MySQL 8.0 为基准（当前主流版本），它相比 5.7 增加了窗口函数、CTE、更好的默认字符集 utf8mb4 等关键特性，这些正是第二篇要用到的。看到"5.7 不支持窗口函数"的旧资料时要注意区分。

1.5 数据库系统的三层结构

当你敲下一条 SQL，中间到底发生了什么？先建立三层结构的地图：

  1. 客户端（Client）：命令行 mysql、图形工具 Navicat / DBeaver，或你写的程序。它们只负责"把 SQL 发出去、把结果显示回来"；
  2. 服务端（mysqld）：真正干活的常驻进程。内部又分两层——Server 层（连接管理、SQL 解析、优化器、各种内置函数）和存储引擎层（真正读写数据的组件）。你执行的每条 SQL 都先过 Server 层，再落到引擎；
  3. 存储引擎（Storage Engine）：MySQL 的可插拔设计，同一台服务器上的不同表可以用不同引擎。默认引擎是 InnoDB——支持事务、行级锁、崩溃恢复，本书第三、四篇的所有底层原理都基于它。
-- 查看当前 MySQL 版本与默认存储引擎（装好库后可以立刻跑这两条）
SELECT VERSION();
SHOW ENGINES;        -- InnoDB 一行标着 DEFAULT 的就是默认引擎
为什么现在讲这个：网上大量旧资料把 MyISAM（不支持事务的旧默认引擎）和 InnoDB 混着讲，导致初学者学到"事务"时一脸懵。从第一天起请记住：MySQL = Server 层 + InnoDB，除非明确说明，本书所有内容都默认 InnoDB。
常见误区："MySQL 很慢"。真相是：绝大多数"数据库慢"都是 SQL 写得差或没建索引，Server 层和 InnoDB 本身的单机能力远超一般业务的负载。优化方法正是第三篇的主题。
