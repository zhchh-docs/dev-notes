6.1 SELECT 的基本形态

SELECT 决定"看哪些列"，FROM 决定"从哪张表看"——这是查询的地基。

-- 1. 列出明确的列（永远别用 SELECT *，生产环境与网络传输都吃亏）
SELECT id, name, price, stock
FROM product;

-- 2. 带表达式：SELECT 列表里可以直接写计算
SELECT id,
       name,
       price,
       price * 0.9        AS discount_price,   -- AS 起别名，结果集列名就叫这个
       stock * price      AS stock_value      -- 库存货值
FROM product;

-- 3. 常量与函数也能出现在列表里
SELECT id,
       name,
       '京东自营'          AS source,           -- 字符串常量列
       CURRENT_TIMESTAMP  AS query_time        -- 函数列
FROM product;

-- 4. DISTINCT 对整行去重（常用于"查过哪些类目"）
SELECT DISTINCT category_id
FROM product;

几个约定俗成的写法：

  • AS 可省略，但强烈建议显式写——price*0.9 discount_price 这种靠空格区分的写法容易在重构时读错；
  • 别名一旦起好，WHERE 里不能引用它（SELECT 子句的执行顺序在 WHERE 之后，下一节的执行顺序图会解释），但 ORDER BY、GROUP BY、HAVING 里可以；
  • DISTINCT 作用于后面所有列的组合：SELECT DISTINCT a, b 是 (a,b) 组合去重，不是只对 a 去重。
SELECT * 的三个问题：① 网络/内存多传不需要的列；② 表结构一变应用就崩（依赖列顺序）；③ 可能用上索引覆盖不了的列，让执行计划变差。练习可以偷懒，生产一律写列名。

6.2 WHERE：比较与逻辑运算

WHERE 是"行级过滤器"：逐行判断，真的留下，假的丢弃——它决定了扫描之后哪些行能进入下一步。

-- 比较运算：= 等于、!= 或 <> 不等于、> >= < <=
SELECT id, name, price
FROM product
WHERE price >= 100;

-- 逻辑组合：AND / OR / NOT
SELECT id, name, price, category_id
FROM product
WHERE category_id = 3
  AND price >= 100
  AND price <= 500
  AND is_deleted = 0;

-- NOT 取反：排除"已下架"和"无库存"
SELECT id, name
FROM product
WHERE NOT (status = 0 OR stock = 0);

要点：

  • MySQL 里 != 与 <> 完全等价，团队约定一种即可（本书示例混用，读到别意外）；
  • AND 优先级高于 OR，混写时永远加括号：a OR b AND c 实际是 a OR (b AND c)；
  • 多个 AND 条件之间，优化器会自动挑能用索引的先走（第 23 章 EXPLAIN 展开），你不必手写顺序。

6.3 IN / BETWEEN / LIKE 三件套

三个最常用的范围匹配写法，各有各的适用边界，混用会既慢又错。

-- IN：离散值集合（等价于一串 OR，可读性好得多）
SELECT id, name, category_id
FROM product
WHERE category_id IN (3, 7, 12);

-- BETWEEN：闭区间，含两端
SELECT id, name, price
FROM product
WHERE price BETWEEN 100 AND 500;   -- 等价于 price >= 100 AND price <= 500

-- LIKE 模糊匹配：% 任意多字符（含 0 个），_ 恰好一个字符
SELECT id, name
FROM product
WHERE name LIKE '%机械键盘%';       -- 包含"机械键盘"四字

-- 日期也可以 BETWEEN（注意 datetime 的右端含时分秒陷阱）
SELECT id, order_no, created_at
FROM orders
WHERE created_at BETWEEN '2026-10-01' AND '2026-10-31';
写法语义能否走索引典型场景
IN (a,b,c)等于集合中任意一个能（每个值都走索引）类目枚举、订单状态清单
BETWEEN x AND y闭区间 [x,y]能（范围扫描）价格段、日期段
LIKE '前缀%'以某串开头能（最左前缀）手机号前缀、商品名前缀搜索
LIKE '%中缀%'包含某串不能（全表扫）站内全文搜索应换 FULLTEXT
BETWEEN datetime 的右端是闭区间：BETWEEN '2026-10-01' AND '2026-10-31' 会漏掉 10-31 当天 00:00:00 之后的所有订单（因为 '2026-10-31' 被当作 2026-10-31 00:00:00）。日期范围查询统一写成 >= 当天 AND < 次日，最稳妥。
LIKE 里的转义：当要匹配的字符串本身含 % 或 _ 时，用 ESCAPE 指定转义符：WHERE name LIKE 'A\_%' ESCAPE '\' 表示字面量下划线。

6.4 NULL 的三值逻辑

SQL 里 NULL 不是"0"也不是"空字符串"，而是"未知"。任何与 NULL 的比较都不会得到 TRUE 或 FALSE，而是第三个值：UNKNOWN。

-- 错误写法：NULL 永远不等于任何东西（包括另一个 NULL）
SELECT * FROM customer WHERE level = NULL;     -- 一行都查不到！

-- 正确写法：IS NULL / IS NOT NULL
SELECT id, name
FROM customer
WHERE level IS NULL;                            -- 新注册还没分层的用户

-- <=>：NULL 安全等于（MySQL 方言，两个 NULL 视为相等）
SELECT id, name
FROM customer
WHERE level <=> NULL;

-- COALESCE：把 NULL 替换成默认值再比较
SELECT id, name, level
FROM customer
WHERE COALESCE(level, 'NORMAL') = 'NORMAL';

三值逻辑的真值表只有一条要背：WHERE 只保留结果为 TRUE 的行，UNKNOWN 一律丢弃。这直接解释了两个经典坑：

  1. NOT IN (含 NULL 的集合) 永远返回空——因为集合里有 NULL 时，每个值的比较结果都是 UNKNOWN，取反还是 UNKNOWN；
  2. LEFT JOIN 后 WHERE 右表列 = 某值 会把没匹配上的行（右表全是 NULL）全部丢掉，LEFT JOIN 退化成 INNER JOIN——第 9 章还会见到这个坑。
判断 NULL 只能用 IS NULL / IS NOT NULL / <=>；业务列尽量设默认值（NOT NULL DEFAULT ...），让 NULL 只出现在真正"未知"的地方。

6.5 运算符优先级与括号

MySQL 运算符从高到低的常用层级（节选）：乘除 > 加减 > 比较 > NOT > AND > OR。看这个真实需求："查 3 号类目下、价格满 100 元的商品，或者全部满 500 元的商品"。

-- 错误写法：AND 比 OR 先结合，实际语义全错
SELECT * FROM product
WHERE category_id = 3 AND price >= 100 OR price >= 500;
-- MySQL 实际按 (category_id = 3 AND price >= 100) OR (price >= 500) 执行
-- 后半句把所有类目下满 500 的都捞出来了，不是我们要的

-- 正确写法：括号显式表达意图
SELECT * FROM product
WHERE category_id = 3
  AND (price >= 100 OR price >= 500);

给从前端转全栈的你一个类比：JS 里 && 优先于 ||，写复杂条件也习惯性加括号——SQL 完全一样。养成"条件复杂就加括号"的肌肉记忆，比背优先级表可靠得多。

可读性建议：每个 AND/OR 条件单独一行、左对齐起头，评审和排错时一眼看清组合关系。这也是本书所有示例的排版风格。

6.6 常见坑清单

  • 坑WHERE col = NULL 查不到：用 IS NULL；见 6.4；
  • 坑LIKE '%关键词%' 拖垮系统：前导通配符不走索引，大数据量应上 FULLTEXT 搜索引擎；
  • 坑BETWEEN 日期漏掉最后一天：datetime 右端写次日零点；
  • 坑字符串列用数字比较：WHERE phone = 13800000001（漏引号）触发隐式转换、索引失效；
  • 坑OR 混写不打括号：AND 优先于 OR，条件悄悄变形。
