◆本章目标

  • 说清取模分片扩容为什么会让大量数据重排；
  • 掌握双写迁移的四步：存量搬运、增量同步、校验、切流；
  • 理解预分片与一致性哈希如何减少扩容迁移量；
  • 知道迁移期间如何保证不丢数据、可回滚；
  • 建立"先验证再切流"的迁移纪律。

53.1 扩容为什么难

分片数从 N 变 2N，取模结果全变——老分片的数据几乎都要搬到新分片。

  • 按 user_id % 4 分片，扩到 % 8，原来落在分片 0 的数据一半要去分片 4；
  • 迁移不能停业务，又不能让用户读到半截数据；
  • 成熟做法不是"停机重导"，而是平滑迁移：新老并行，追平后切流。

53.2 双写迁移法

标准四步：存量初始化、增量同步、一致性校验、灰度切流。

  1. 存量搬运：把老库历史数据按新分片规则导到新库；
  2. 增量同步：迁移期间的新写入同时写老库与新库（或用 binlog 同步，见第 45 章 Canal）；
  3. 一致性校验：对比两库行数、抽样关键字段，确认无差异；
  4. 灰度切流：先切一小部分读流量到新库，观察无误再全量切，老库保留一段观察期。
-- 校验两库同一分片的行数是否一致
SELECT COUNT(*) FROM order_0;          -- 老库
SELECT COUNT(*) FROM order_0;        -- 新库（同表名，不同数据源）

-- 抽样核对关键字段：按主键分段抽查
SELECT order_id, user_id, amount
FROM order_0
WHERE order_id BETWEEN 100000 AND 100100
ORDER BY order_id;
迁移的纪律：先影子写（双写不读）、再灰度切读、最后下线老库；任何一步不一致就回滚，老库始终可切回。

53.3 一致性哈希与预分片

从源头减少未来迁移量：预先多分很多分片，扩容只是"拆分片"而非"重排"。

  • 预分片一开始就建 64/128 个逻辑分片，物理库慢慢扩——扩容只改路由，不动数据；
  • 一致性哈希把节点和数据都哈希到环上，扩一个节点只影响环上一段，迁移量从全量降到 1/N；
  • 这两种都是"用预先规划换未来迁移成本"，初期就该想清楚。
迁移最怕"边迁边改"：迁移期间业务还在加表改字段，新老规则对不上。迁移窗口要冻结 schema 变更，或在迁移工具里兼容双方。

53.4 常见坑清单

  • 坑停机重导数据：时间长、风险大，还丢增量；用双写平滑迁移；
  • 坑切流后老库立刻下线：没观察期，发现不一致回不去；
  • 坑只比行数不比内容：行数对得上不代表字段值一致，要抽样核对；
  • 坑迁移期间改 schema：新老规则脱节，数据迁过去对不上。

53.4 迁移的回滚预案

切流不是单向的，每一步都要能切回老库。

  • 双写期间老库始终是权威，发现不一致立刻切回；
  • 灰度切读：先 1% 流量到新库，观察无误再放大；
  • 老库保留一个月观察期，确认稳定再下线。
迁移的纪律：先影子写、再灰度切读、老库保留观察期——任何一步不一致就回滚。

速记 一句话要点

把本章最容易忘的结论压成一句话。

  • 要点平滑迁移 = 双写 + 追平 + 校验 + 灰度，任何一步跳步都可能造成不可逆的数据错乱。
