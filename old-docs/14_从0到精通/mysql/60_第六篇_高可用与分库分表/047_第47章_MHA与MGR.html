47.1 MHA：外挂式自动切换

MHA（Master High Availability）由一个 Manager 管理多台 Node，主库挂了它来挑数据最新的从库升主。

  • MHA Manager独立部署，监控整个主从集群，负责故障判定与切换；
  • MHA Node装在每台 MySQL 机器上，被 Manager 调用做具体操作；
  • 切换时它会对比各从库的 relay log，把最接近主库的那台选作新主，并让其他从库追上新主。
MHA 依赖 GTID 或位点复制，切换通常在几十秒级。它的优点是对现有主从侵入小，缺点是 Manager 本身要高可用、且项目维护节奏慢。

47.2 MGR：原生组复制

MGR（MySQL Group Replication）把多台 MySQL 组成一个组，事务提交要组内多数派认可。

  • 组复制：每个事务的提交要在组内广播，多数节点认可才算成功——天然防脑裂；
  • 单主模式组里只有一个主接受写，其余只读，主挂了组自动选新主（最常用）；
  • 多主模式多节点都可写，冲突由内部检测解决，性能与复杂度都高。
-- MGR 单主模式关键配置（my.cnf，组内每台类似）
# transaction_write_set_extraction = XXHASH64
# loose-group_replication_group_name = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee'
# loose-group_replication_local_address = '10.0.0.11:33061'
# loose-group_replication_group_seeds = '10.0.0.11:33061,10.0.0.12:33061,10.0.0.13:33061'
# loose-group_replication_single_primary_mode = ON

-- 启动组复制（在已建组的节点上）
START GROUP_REPLICATION;
MGR 的核心价值：选主与一致性由 MySQL 原生保证，不依赖外部管家；代价是至少 3 节点、网络要求高、吞吐受多数派投票影响。

47.3 MHA vs MGR 选型

维度MHAMGR
定位外挂式管理传统主从MySQL 原生组复制
选主Manager 挑选数据最新从库组内 Paxos 多数派自动选
脑裂靠 Manager 仲裁，有误判风险多数派机制，天然防脑裂
节点数一主多从即可至少 3 节点
适用存量主从平滑加 HA新建、想要原生强一致
别为了"新"而盲目上 MGR：它对网络延迟敏感、写吞吐受投票制约。存量主从系统用 MHA 平滑升级往往更划算；新项目且愿意接受 3 节点最小规模再考虑 MGR。

47.4 常见坑清单

  • 坑MHA Manager 单点：Manager 自己挂了就没人管切换，要给它做高可用；
  • 坑MGR 节点数为偶数：2 节点组一旦分裂两边都凑不齐多数派，集群直接不可用，务必 3/5 奇数；
  • 坑MGR 跨机房网络差：多数派投票跨高延迟网络，写性能骤降；
  • 坑把 MGR 当传统主从写：它要求统一的引擎、binlog 格式与一致性约束，配置不全会起不来组。

47.5 MGR 为什么要求奇数节点

组复制靠多数派达成共识，偶数节点在网络分区时会两边都凑不齐多数。

  • 3 节点：挂 1 台剩 2 票，仍超半数（2/3）可服务；
  • 4 节点：挂 2 台剩 2 票，未过半（2/4），集群不可用；
  • 所以生产用 3/5 奇数，而不是 2/4。
多数派机制同时是防脑裂的武器：少数派那侧无法当选主，自然不会双主并写。
