第 50 章 拆分策略：垂直/水平/分片键

50.1 垂直拆分

垂直拆是"按业务把库切开"：用户库、订单库、商品库各管一摊。

  • 把原本一个大库按业务模块拆成多个库：用户相关表进 user_db，订单相关进 order_db；
  • 它本质是业务解耦，不是为了撑单表行数——每库里表还是那些表；
  • 垂直拆后，跨库 join 消失，关联改为应用层组装或冗余。
垂直拆分通常是分库分表的第一步：先按业务拆库，发现某个核心表（如订单流水）还是太大，再对它做水平拆分。

50.2 水平拆分

水平拆是"按某个键把同一张表切成 N 份"：订单表变成 order_0 … order_N。

图 50-1 水平拆分：同一张订单表按 user_id 散到多张分表

水平拆后，读写都按分片键路由到对应分表；不带分片键的查询要扫全部分片（广播），代价大。

50.3 分片键怎么选

分片键是整个方案的地基：选歪了，数据倾斜、查询广播，全来了。

标准说明
均匀数据能分散到各分片，不集中到一两个分片（不倾斜）
高基数取值多，如 user_id 而非 status（status 只有几种，必倾斜）
查询必带绝大多数业务查询都会带上它，避免全分片扫描
稳定选不常更新的列，分片键变了等于这条数据要搬家
选分片键就是选"最常用来查、取值又足够散"的那列：订单表按 user_id 分片，同用户的订单落同一分片，按用户查订单就是单分片命中。

50.4 常见分片算法

  • 哈希/取模分片 = user_id % N，分布均匀；缺点是扩容要迁移大量数据（一致性哈希可缓解）；
  • 范围分片按时间或 ID 区间切，利于范围查询；缺点是新数据全压最新分片（热点）；
  • 基因法/嵌套把 user_id 的哈希"嵌"进订单号，让按订单号查也能定位分片，避免广播。
范围分片的热点陷阱：按创建时间切分，最新数据全进最后一个分片，写集中在这——这就是为什么纯时间分片常常要再叠加一层哈希打散。

50.5 常见坑清单

  • 坑拿低基数字段当分片键：如按 status 分片，永远只有几个分片有数据；
  • 坑分片键会被更新：update 分片键等于跨分片搬家，极易出错；
  • 坑业务查询不带分片键：每次都广播扫所有分片，延迟暴涨；
  • 坑分片数拍脑袋定死：扩分片要迁移数据，初始就要给未来留余量（第 53 章）。

50.5 分片键的三个反模式

分片键选错，拆了等于没拆。

  • 反模式低基数字段：如 status 只有几种取值，永远只有几个分片有数据；
  • 反模式会更新的列：update 分片键等于跨分片搬家；
  • 反模式查询不带它：每次都广播扫所有分片，延迟暴涨。
分片键 = 最常用来查、取值又足够散、还不常改的那一列。
