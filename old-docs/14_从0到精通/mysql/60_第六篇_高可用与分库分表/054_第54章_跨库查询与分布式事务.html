54.1 跨库查询的应对

拆库后 join 跨库基本不可行，思路是"少 join、靠冗余、在应用层拼"。

  • 冗余字段把高频关联字段（如商品名）冗余进订单表，免去 join；
  • 应用层组装分别查订单、查用户，在内存里拼结果集；
  • 宽表/汇总把报表类查询做成宽表或提前聚合，别在线跨库 join；
  • 坑ShardingSphere 能广播归并跨分片查询，但数据量大时极慢，只应急用。
拆分设计时就要预判：哪些查询需要跨表 join，提前把冗余字段加上——这是"用空间换查询简单"。

54.2 分布式事务的三种思路

跨库写要同时成功或同时失败，但网络不可靠——三种思路在一致性与可用性间取舍。

54.3 XA 与柔性事务

MySQL XA 是原生分布式事务，但它是两阶段提交，性能与可用性代价不小。

-- MySQL XA 事务的基本流程（跨多个库实例）
XA START 'tx1';
INSERT INTO order_db.order(user_id, amount) VALUES (1001, 99.00);
XA END 'tx1';
XA PREPARE 'tx1';
-- 协调者确认所有分支都 OK 后
XA COMMIT 'tx1';
-- 任一分支失败则 XA ROLLBACK 'tx1';
方案特点适用
MySQL XA两阶段提交，强一致但慢、阻塞对一致性要求极高、量不大
TCCTry/Confirm/Cancel，业务自己实现三接口资金类，需显式补偿
Saga长事务拆系列本地事务，失败反向补偿跨多服务、流程长
本地消息表本地事务写消息表，异步投递下游+对账互联网绝大多数场景
选型直觉：能用本地事务+消息表对账解决的，就别上 XA；XA 的强一致代价是性能与可用性，大多数业务要的是"最终一致+可补偿"。
分布式事务没有免费午餐：强一致（XA）牺牲可用性与性能，最终一致（柔性）要接受短暂不一致并做好对账补偿。下单扣库存这类核心链路，主流是本地事务+消息表+定时对账。

54.4 常见坑清单

  • 坑在线跨库 join：数据量大时慢到不可用，提前冗余字段；
  • 坑迷信 XA 强一致：两阶段提交阻塞、性能差，高并发业务顶不住；
  • 坑柔性事务不做对账：只投递不补偿，失败后数据永久不一致；
  • 坑跨库事务跨分片写：一个请求写多个分片，本来就该拆，用最终一致串起来。

54.4 本地消息表：最实用的最终一致

大多数业务要的不是强一致 XA，而是"本地事务 + 消息表 + 对账"。

-- 同一本地事务里：写业务数据 + 写消息表
BEGIN;
INSERT INTO order(user_id, amount) VALUES (1001, 99);
INSERT INTO msg_out(topic, payload, status)
VALUES ('order_created', '{"order_id":123}', 'NEW');
COMMIT;
-- 后台任务扫描 status=NEW，投递下游，成功后标记 DONE
能用本地事务+消息表对账解决的，就别上 XA——强一致的代价是性能与可用性。
