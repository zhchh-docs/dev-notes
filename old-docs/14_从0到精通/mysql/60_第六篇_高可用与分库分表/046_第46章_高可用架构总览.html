46.1 高可用要解决什么

单机数据库的命门：主库是单点。高可用就是把"单点故障"变成"可自动恢复"。

  • RTO（恢复时间目标）：主库挂了到恢复服务要多久——手动切换可能几十分钟，自动目标是几十秒；
  • RPO（恢复点目标）：最多能容忍丢多少数据——半同步/双 1 配置越严，RPO 越小；
  • 高可用不是"永不宕机"，而是宕机后自动、快速、尽量不丢数据地顶上。
高可用 = 复制（数据冗余）+ 故障转移（自动切换）+ 客户端寻址（应用无感），三者缺一角都不完整。

46.2 三个核心组件

一次自动切换要走过三步：发现主库挂了、选出新主、让应用连到新主。

图 46-1 自动故障转移的三段：检测 → 选主 → 切换

第③步的常见做法：把主库地址放在一个浮动 VIP（虚拟 IP）上，切换时把 VIP 飘到新主；或应用统一连 ProxySQL/中间件，由中间件知道新主；再或改 DNS（生效慢，少用）。

46.3 主流方案全景

方案特点适用
MHA第三方管理器，监控主库、故障时自动提升数据最新的从库传统一主多从，经典方案
MGRMySQL 组复制，多主基于 Paxos 协议，原生支持自动选主想要原生、强一致、多节点
Orchestrator可视化拓扑管理与自动故障转移大规模复制拓扑运维
云 RDS 高可用版云厂商托管，主备切换全自动不想自己搭 HA 的团队
本篇后面两章会细讲 MHA 与 MGR：MHA 是"外挂式"管理传统主从，MGR 是 MySQL 原生的"组复制"思路——对比着学最清楚。

46.4 常见坑清单

  • 坑只搭了主从没做切换：主库挂了还要人手工上，等于没高可用；
  • 坑脑裂：两个节点都认为自己是主，同时接受写——所以选主要用仲裁/多数派；
  • 坑探活太敏感：网络抖一下就切换，频繁抖动比宕机更伤；
  • 坑切换后从库没重指向：新主起来了，旧从库还在追旧主，拓扑乱掉。

46.5 高可用的评估指标

谈高可用先谈数字：全年可用性换算成允许宕机多久。

可用性年允许宕机典型 RTO
99.9%约 8.7 小时分钟级
99.99%约 52 分钟秒级自动切换
RTO 靠自动故障转移压短，RPO 靠半同步/双 1 压缩，两者是高可用的两个独立旋钮。
