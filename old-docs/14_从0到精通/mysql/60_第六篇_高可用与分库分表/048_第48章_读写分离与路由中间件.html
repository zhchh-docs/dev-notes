◆本章目标

  • 说清读写分离的基本规则：写走主库、读走从库；
  • 理解"事务内读主、写后读主"的路由约束；
  • 分清代理层中间件（ProxySQL）与应用层路由（ShardingSphere-JDBC）；
  • 知道中间件如何感知主库切换；
  • 能判断自己的项目该不该引入中间件。

48.1 读写分离怎么路由

规则看似简单：INSERT/UPDATE 走主，SELECT 走从。但有两类 SELECT 必须走主。

  • 普通读：路由到从库，分摊主库读压力；
  • 坑事务内的读：一个事务里前面写了、后面读，必须一直走主库，否则读不到自己刚写的；
  • 坑写后读：刚下单就查订单，走从库会被主从延迟坑到。

48.2 中间件在哪一层

两大阵营：独立部署的代理层，和嵌进应用的 JDBC 层。

类型代表特点
代理层ProxySQL、MySQL Router独立进程，应用无感连接它；统一治理、可热配
应用层ShardingSphere-JDBC以 jar 形式嵌进应用，无额外部署、性能好
代理层省事统一但多一跳；JDBC 层轻量高性能但要随应用升级。读多写少、多语言栈选代理，Java 单栈、追求性能选 JDBC。

48.3 常见中间件

  • ProxySQL开源代理层，按规则把查询路由到主/从，支持连接池与读写拆分；
  • MySQL RouterMySQL 官方轻量路由，常配合 InnoDB Cluster；
  • ShardingSphere下一章的主角，既能做读写分离也能做分库分表。
中间件要"知道"谁是主：主库切换后，中间件必须通过心跳或主动切换命令把路由表更新到新主——否则它还往旧主地址发写。

48.4 常见坑清单

  • 坑把事务内 SELECT 路由到从库：读不到自己刚改的数据，业务逻辑错乱；
  • 坑中间件成了新单点：ProxySQL 挂了全站断，要多实例 + 负载均衡；
  • 坑主从延迟下盲信从库读：关键链路（余额、刚下单）应读主；
  • 坑中间件看不懂的 SQL：存储过程、注释带 hint 可能导致误路由，要用强制走主的标记。

48.4 中间件自己的高可用

中间件是新单点：它挂了全站断，必须多实例 + 负载均衡。

  • ProxySQL 多实例部署，前面挂 VIP 或 LB；
  • 中间件要实时感知主库切换，更新路由表；
  • 配置热更新，避免改路由要重启。
中间件挂了比数据库挂了更致命——所有连接瞬间中断，务必多实例冗余。

把本章最容易忘的结论压成一句话。

  • 要点读写分离最大的坑不是路由错，而是"写后读"读旧数据：订单刚下单就查，从库还没同步到。
