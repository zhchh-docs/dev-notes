52.1 为什么需要全局 ID

每个分片库都从 1 开始自增，分到不同库的两条记录主键会一模一样——这在分布式系统里是灾难。

  • 单库 AUTO_INCREMENT 在每个分片各自计数，跨分片会撞；
  • 业务需要全局唯一的主键，且最好趋势递增（利于 B+ 树写入、索引紧凑）；
  • 雪花算法（Snowflake）是 Twitter 开源的发号方案，也是分库分表的事实标准。

52.2 雪花算法的位结构

一个 64 位长整数，从高位到低位切成四段：时间戳、机器标识、序列号。

图 52-1 雪花算法 64 位结构：符号 1 + 时间 41 + 机器 10 + 序列 12

  • 时间戳位（41bit）：从选定纪元起算的毫秒数，决定 ID 随时间增大；
  • 机器位（10bit）：一般拆成机房 5bit + 机器 5bit，最多 1024 台机器不重复；
  • 序列号位（12bit）：同一毫秒内自增，最多 4096 个/毫秒，即单机每秒约 400 万。
雪花 ID 的两个红利：趋势递增（索引写入友好）、本地发号（不依赖中心服务，性能极高）。

52.3 常见方案对比

方案优点缺点
雪花算法趋势递增、本地生成、高性能依赖时钟同步，时钟回拨会重复
UUID本地生成、无中心无序、长度长、索引写入差
数据库号段简单可靠、趋势递增依赖号段表，发号是中心服务
Redis 发号原子计数、性能高引入 Redis 依赖，要持久化
雪花算法最怕时钟回拨：机器时钟被 NTP 往回拨，可能生成已发过的 ID。生产上要检测回拨、等待或报错，而不是照发。

52.4 常见坑清单

  • 坑多台机器配了相同机器位：发出来的 ID 会重复，机器位必须全局唯一；
  • 坑时钟回拨没处理：NTP 校时往回拨，重复 ID 直接撞主键；
  • 坑拿 UUID 当主键：无序导致 B+ 树页频繁分裂、索引碎片；
  • 坑雪花 ID 暴露业务量：ID 可推算出发单号与时间，对外暴露时注意脱敏。

52.4 时钟回拨的应对

雪花算法最怕 NTP 把时钟往回拨，会生成已发过的 ID。

  • 记录上次发号时间，发现当前时间小于它即判定回拨；
  • 回拨幅度小就等待时钟追上，幅度大则报错告警；
  • 多台机器的机器位必须全局唯一，否则同毫秒序列号撞车。
时钟回拨不是理论风险，NTP 校时天天在做——不处理就会重复发号撞主键。
