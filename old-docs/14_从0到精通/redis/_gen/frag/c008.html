8.1 ZSet 命令全景（先会再懂）

ZSet（有序集合）= Set 的"去重" + List 的"有序"，排序依据是一个 double 分数 score；member 唯一，score 可重复。

127.0.0.1:6379> ZADD rank:daily 100 u1 250 u2 80 u3 175 u4
(integer) 4                       # 新增 4 个成员
127.0.0.1:6379> ZADD rank:daily XX CH 300 u2      # XX=只更新存在的; CH=返回被改动的数量
(integer) 1
127.0.0.1:6379> ZADD rank:daily NX 999 u9         # NX=只新增不更新
(integer) 1
127.0.0.1:6379> ZADD rank:daily INCR 10 u1        # 累加 10 分，返回新分数
"110"

# —— 按排名查（下标从 0 开始，支持负数倒着数）——
127.0.0.1:6379> ZRANGE rank:daily 0 2 WITHSCORES        # 分数从低到高前 3
1) "u3"  2) "80"
3) "u1"  4) "110"
5) "u4"  6) "175"
127.0.0.1:6379> ZREVRANGE rank:daily 0 2 WITHSCORES     # 分数从高到低前 3（排行榜常用）
1) "u9"  2) "999"
3) "u2"  3) "300"
...

# —— 按分数区间查 ——
127.0.0.1:6379> ZRANGEBYSCORE rank:daily 100 200 WITHSCORES          # [100,200]
127.0.0.1:6379> ZRANGEBYSCORE rank:daily (100 +inf WITHSCORES        # (100, +∞)
127.0.0.1:6379> ZRANGEBYSCORE rank:daily -inf +inf LIMIT 0 10        # 分页前 10
127.0.0.1:6379> ZREVRANGEBYSCORE rank:daily +inf 200 LIMIT 0 10      # 反向：200 以上的前 10

# —— 成员视角 ——
127.0.0.1:6379> ZSCORE rank:daily u1
"110"
127.0.0.1:6379> ZRANK rank:daily u1       # 正序名次（第几名，从 0 开始）
(integer) 1
127.0.0.1:6379> ZREVRANK rank:daily u1    # 倒序名次（榜里最爱用的那个）
(integer) 3
127.0.0.1:6379> ZINCRBY rank:daily 5 u1   # 加分
"115"

# —— 统计与删除 ——
127.0.0.1:6379> ZCARD rank:daily                    # 总人数 O(1)
(integer) 5
127.0.0.1:6379> ZCOUNT rank:daily 100 500           # 分数区间人数 O(logN)
(integer) 3
127.0.0.1:6379> ZREM rank:daily u9                  # 删除成员
(integer) 1
127.0.0.1:6379> ZREMRANGEBYRANK rank:daily 0 -101   # 保留 Top100：删掉排名在 100 之后的所有人
(integer) 0
127.0.0.1:6379> ZREMRANGEBYSCORE rank:daily 0 59    # 删掉低于 60 分的
(integer) 1
版本注意：Redis 6.2 起官方推荐统一的 ZRANGE key min max BYSCORE|BYLEX REV LIMIT ... 语法，老命令（ZREVRANGEBYSCORE 等）仍然可用。新项目建议用新写法，语义更统一。

8.2 跳表：为什么能又快又有序

ZSet 用 一个跳表 + 一个哈希表 实现：跳表负责"按分数排序地遍历"，哈希表负责"按 member 秒查分数"（O(1)）。

跳表的核心思想：给链表建立多级"快速通道"。就像地铁有站站停（慢车）和大站快车，查询时先坐快车，接近了再换慢车。

图 8-1 跳表查找示意

为什么不用红黑树/AVL？因为跳表实现简单、支持高效的范围查询（找到起点后沿底层链表一路走），插入删除的锁粒度也更友好——范围查询正是排行榜最需要的。

8.3 排行榜四种查法

一个真实排行榜要支持四件事，正好对应四条命令：

需求命令复杂度
① 榜单 Top NZREVRANGE key 0 N-1 WITHSCORESO(logN + M)
② 查我第几名ZREVRANK key memberO(logN)
③ 更新我的分ZINCRBY key delta member / ZADDO(logN)
④ 看我周围的人ZREVRANGE key start end（start=rank-2）O(logN + M)
 
# ① 全服积分榜 Top10（含分数）
127.0.0.1:6379> ZREVRANGE board:score 0 9 WITHSCORES
 1) "u8842"   2) "98210"
 3) "u1024"   4) "97500"
 ...

# ② u231 自己的名次（注意 0-based，展示时 +1）
127.0.0.1:6379> ZREVRANK board:score u231
(integer) 4762                  → 展示：第 4763 名
127.0.0.1:6379> ZSCORE board:score u231
"3210"

# ③ 完成一局得 50 分（存在则加，不存在则建 → ZINCRBY 自动处理）
127.0.0.1:6379> ZINCRBY board:score 50 u231
"3260"
# 或者直接设置为绝对值（如赛季重置）
127.0.0.1:6379> ZADD board:score 3260 u231

# ④ 看我前后各 2 名（竞技场常见的"附近玩家"）
127.0.0.1:6379> ZREVRANGE board:score 4760 4764 WITHSCORES

周期榜：daily / weekly / 历史

key = "board:score:" + today          # board:score:2026-10-19
ZINCRBY key 50 u231
EXPIRE key 604800                     # 保留 7 天；注意：ZINCRBY 新建时要补 TTL

# 周榜：按周合并日榜（ZUNIONSTORE，权重 1）
ZUNIONSTORE board:week:2026W42 7 board:score:2026-10-13 ... board:score:2026-10-19
# 总分榜：一个不带日期的永久 key
ZUNIONSTORE board:total 2 board:total board:week:2026W42 WEIGHTS 1 1 AGGREGATE SUM

8.4 分数设计与并列名次

ZSet 的分数是 double（64 位浮点）：整数精确的范围是 ±2^53，超过就丢精度——这是分数设计的第一条红线。

技巧一：同分时按时间先后排

ZSet 在 score 相同时，会按 member 的字典序排。想让"同分时先达成的人排前面"，可以把时间戳的小数部分塞进去：

# 方案A：整数=主分数，小数=越早越大（用 (MAX_TS - now) 的小数部分）
score = 主分数 + (1 - now / MAX_TS) * 0.0001
# 方案B：把时间戳直接拼到双精度能表示的范围内（推荐第一位 dallogruga 用毫秒 + 倒序）
score = 主分数 * 1e10 + (MAX_MS - now_ms)     # 主分数左移，时间戳做低位（毫秒级 + 倒序）
ZADD board 32100000001234 u231
# 展示时记得把丰度反解出来：real = score / 1e10
边界：上面这招要求 主分数 * 1e10 不超过 2^53 ≈ 9.0e15，即主分数最多到 1e5 级别。分数跨度大时请改用具代表性的量级，或者干脆把 title(并列) 交给应用层处理。

技巧二：真正的"并列名次"（第 1 名有 3 个人）

ZSet 本身只有 rank（下标）没有 rank-with-ties。标准解法：

# ① 用 Hash 记录每个分数对应的人数
HINCRBY board:score:tie 3260 1
# ② 展示名次时，第 N 名 = ZREVRANK + 该分数之前的人数统计
ZCOUNT board:score (3260 +inf      # 严格大于 3260 的人数 → +1 即名次

技巧三：分数本身就是时间戳（延迟队列 & 时间序）

把"执行时间戳"当分数，就能得到一个天然有序的待办队列——这是第 40 章延迟队列的基础：

# 订单 15 分钟后取消：score = 到期时间戳
ZADD delay:order 1761235200000 "order:9001"
# 轮询到期任务
ZRANGEBYSCORE delay:order 0 $(date +%s000) LIMIT 0 100

8.5 底层编码与时间复杂度账

127.0.0.1:6379> CONFIG GET zset-max-listpack-*
1) "zset-max-listpack-entries"   2) "128"
3) "zset-max-listpack-value"     4) "64"

127.0.0.1:6379> ZADD small 1 a 2 b
(integer) 2
127.0.0.1:6379> OBJECT ENCODING small
listpack                  # 小规模 + 短值：紧凑存储，查找 O(N)
127.0.0.1:6379> CONFIG SET zset-max-listpack-entries 1
127.0.0.1:6379> ZADD big 1 a 2 b
127.0.0.1:6379> OBJECT ENCODING big
skiplist                  # 真正的跳表+字典
操作复杂度说明风险
ZADD / ZREMO(logN)跳表插入安全
ZSCOREO(1)走 dict安全
ZRANK / ZREVRANKO(logN)累计 span 得到名次安全
ZCARDO(1)—安全
ZCOUNTO(logN)两端各求一次 rank 后做差安全
ZRANGE start stopO(logN + M)M=返回个数M 太大会慢
ZRANGEBYSCOREO(logN + M)M=命中个数范围太宽会全量返回
ZREMRANGEBYSCOREO(logN + M)M=删除个数一次删百万会阻塞

唯一需要警惕的就是返回/删除个数 M：ZRANGEBYSCORE 到 +inf 不限 LIMIT、ZREMRANGEBYSCORE 一次删一百万，都会把单线程卡住。

8.6 常见坑

坑 1：以为 ZSet 有序是"按插入顺序"。它是按 score 排序（score 相同时按 member 字典序），没有 tie-break 保证。
坑 2：ZINCRBY 对不存在的 key 会自动创建，但它不会自动带 TTL —— 日榜 key 会在实例里堆积。首次写入时补 EXPIRE（或用 Lua 一起做）。
坑 3：score 精度。double 精确表示整数到 2^53；更大的值（如 18 位订单号、纳秒时间戳）会悄无声息地丢精度，导致名次错乱。
坑 4：ZREM 一个百万级 ZSet 中很小的一部分其实很快；但 ZREMRANGEBYSCORE 0 +inf 等于删全部，务必加 LIMIT 或分批。
坑 5：把一整个大对象 JSON 作为 member。member 有大小就算一份内存拷贝，且比较成本上升；member 放 id，详情另存。
坑 6：Cluster 模式下 ZUNIONSTORE 要求所有源 key 在同一个 slot，否则报 CROSSSLOT；聚合操作前确认 hash tag（第 47 章）。
坑 7：用 ZREVRANGE 做深分页（比如第 500 页）。虽然命令本身复杂度可控，但一次性拉回大偏移量仍在服务端累积，分页建议配合 LIMIT 限制每页条数（≤100）。

要点一句话
结构member 唯一 + score(double) 排序；底层 = 跳表 + 字典
