10.1 设置过期：五种写法

命令语义场景
EXPIRE key secondsn 秒后过期（相对时间）缓存、锁 TTL
PEXPIRE key msn 毫秒后过期秒级不够精确时（如短锁）
EXPIREAT key ts到某个 Unix 秒过期（绝对时间）活动到今晚 24:00 结束
PEXPIREAT key ms绝对毫秒内部最终都转成它
SETEX key sec val创建时就带 TTL（原子）缓存写入首选
PSETEX key ms val毫秒版 SETEX同上
 
127.0.0.1:6379> SET cache:a 1 EX 60            # 最常用：一条命令搞定值 + TTL
OK
127.0.0.1:6379> SETEX cache:b 60 1             # 等价写法
OK
127.0.0.1:6379> EXPIREAT promo:end 1767196800  # 2026-01-01 00:00:00 UTC 到期
(integer) 1
127.0.0.1:6379> TTL promo:end
(integer) 8234567
127.0.0.1:6379> PERSIST promo:end              # 取消过期（如果活动要延期）
(integer) 1

原则：能一条命令写完就别两条。先 SET 再 EXPIRE 在极端情况下（进程崩溃）会留下一个永不过期的 key——缓存体系里的经典内存泄漏。

Redis 7 的条件过期（很实用）

EXPIRE session:u1 1800 NX      # NX：仅当「还没有 TTL」时才设
EXPIRE session:u1 1800 XX      # XX：仅当「已有 TTL」才更新
EXPIRE session:u1 1800 GT      # GT：新 TTL 更长才生效（防止误把长期会话续短）
EXPIRE session:u1 1800 LT      # LT：新 TTL 更短才生效

10.2 过期信息存在哪：expires 字典

Redis 的数据库结构里有两个字典：

  • dict：真正存数据的 key → value；
  • expires：只存 key → 过期毫秒时间戳（注意它存指针，不重复存字符串，所以开销很小）。
127.0.0.1:6379> SET a 1 EX 60
OK
127.0.0.1:6379> OBJECT ENCODING a
int
# 内部大致这样（伪代码）：
  dict    = { "a" : robj(int 1) }
  expires = { "a" : 1761235260000 }   # 绝对毫秒时间戳

图 10-1 过期字典结构

由此推出两条经验：

  1. 不是所有 key 都带 TTL 更省内存（每个有 TTL 的 key 多一个字典条目开销）；但整体而言，没有 TTL 的 key 是内存泄漏的主要来源，远比这点开销重要。
  2. 可以用 TTL 排查"谁忘了设过期"：-1 就是永不过期的嫌疑犯。

10.3 三种删除策略

Redis 实际采用 惰性删除 + 定期删除 的组合，没有"定时删除"（不会给每个 key 配一个定时器）。

策略做法CPU内存
定时删除给每个 key 建定时器，到期立刻删极差（要处理百万级定时器）最友好
惰性删除访问时才检查是否过期，过期则删并返回不存在几乎免费不友好（没人访问就永远躺着）
定期删除每隔一段时间抽查一批带 TTL 的 key 并清理可控较友好

定期删除的工作方式（源码里的 activeExpireCycle）

  1. 默认每秒运行 10 次（配置项 hz 10，Redis 7 里还可以在闲时用 active 模式加速）；
  2. 每次从 expires 字典随机抽样 20 个 key，删掉其中已过期的；
  3. 如果这批里过期 key 占比超过 25%，就再抽一轮（形成循环）；
  4. 每次循环有时长上限（默认 25ms 内），防止上次循环卡住主线程。
推论：过期 key 不是"到期那一瞬间消失"，而是"到期后的一段时间内被清理"。所以 TTL 返回负数并不代表它一定已被删除——只是逻辑上不可见。
# 观察：写一个秒级 TTL 的 key，然后 INFO 看 expired_keys 计数器增长
127.0.0.1:6379> SET probe 1 PX 1
127.0.0.1:6379> INFO stats | grep expired_keys
expired_keys:12483          # 定期删除清理的总数（累计值）
127.0.0.1:6379> INFO stats | grep expired_stale_perc
expired_stale_perc:12.34    # 抽样时过期占比（越高说明堆积越多）

10.4 过期 key 的三条命运线

① 主库上的过期

  • 读/写访问时：惰性删除（GET 一个过期 key 返回 nil 并顺手删掉）。
  • 后台扫描：定期删除逐步清理。结果：主库上的过期 key 最终会被删。

② RDB / AOF 里的过期

环节过期 key 的处理说明
生成 RDB已过期的不会被写入BGSAVE 时会检查
加载 RDB（主库）会再检查一次，过期的不载入安全
加载 RDB（从库）全部载入，之后靠主库的 DEL 命令同步短暂不一致，最终一致
AOF 写入过期时不写 AOF；惰性/定期删除时会追加一条 DEL让重放后状态一致
AOF 重写已过期的 key 不写入新 AOF—

③ 主从复制中的过期（最容易踩坑）

从库不会主动删除过期 key —— 它要等主库真正删除后，收到传播过来的 DEL 命令才删。所以：

# 主库
127.0.0.1:6379> SET probe:x 1 PX 100
OK
# 立刻在从库读（100ms 后）—— 主库还没来得及定期删除，DEL 还没同步过来
127.0.0.1:6380> GET probe:x
"1"                          # ← 可能仍能读到已过期数据！
# 但如果是【惰性删除】，从库在 Redis 3.2+ 会返回 nil（版本相关，别依赖）
Redis GET 到过期数据不是 bug，是主从异步复制 + 惰性/定期删除共同导致的设计结果。
应对：
① 业务不要把 Redis 当作强一致的判重/开关（它的 TTL 有误差）；
② 对一致性敏感的校验（如验证码是否过期）在 value 里再存一个过期时间戳，由应用层判断。

10.5 为什么内存没有降下来

"我明明删了一半数据，used_memory 怎么一点没变？" —— 三个原因分开看。

现象原因判断与处理
删了数据但内存不降内存碎片：jemalloc 不会把页立刻还给 OS看 mem_fragmentation_ratio（第 19 章）
key 过期了但不降惰性删除未被触发：没人访问就还在内存里等定期删除；或访问一次触发删除
主从都不降从库没收到 DEL（网络/同步 backlog 问题）看 INFO replication 的 slave_repl_offset
删完反而涨COW 期间 fork 复制页（RDB/AOF 重写）看 latest_fork_usec（第 12 章）
 
# 一套标准体检命令
127.0.0.1:6379> INFO memory | grep -E "used_memory_human|used_memory_rss_human|mem_fragmentation_ratio"
used_memory_human:2.31G         # Redis 自己统计的（逻辑）用量
used_memory_rss_human:3.02G     # 操作系统看到的实际物理内存
mem_fragmentation_ratio:1.31    # RSS / used，1.0-1.5 健康，>1.5 碎片偏多，<1 说明换出了 swap！
127.0.0.1:6379> INFO stats | grep -E "expired_keys|evicted_keys"
expired_keys:841203             # 累计过期删除数
evicted_keys:0                  # 累计淘汰数（非 0 说明已经碰到 maxmemory 上限了）

10.6 常见坑

坑 1：SET（不带 KEEPTTL）覆盖已存在的 key → TTL 归零变成永久。这是缓存内存缓慢增长的头号原因。
坑 2：INCR / HSET / LPUSH / ZADD 等更新类命令不会改变 TTL（好消息），但 RENAME 会把 TTL 一起转移给新 key（注意别丢）。
坑 3：批量写入时给所有 key 相同的 TTL → 到期在同一个时间点集体失效 → 缓存雪崩（第 25 章：基础TTL + random(0, 300)）。
坑 4：TTL 返回 -1（永久） vs -2（不存在）混淆，导致"'key 不存在'时误判为'永不过期'从而继续用"。务必显式判断 -2。
坑 5：依赖 Redis TTL 做业务强校验（验证码/支付超时）。主从异步延迟下可能读到过期值，业务自己再校验时间戳。
坑 6：把 EXPIRE 当"删除"用：EXPIRE key 1 之后 key 还能被读到 1 秒；需要立刻失效请用 DEL/UNLINK。
坑 7：Cluster 下 EXPIRE 只能在拥有该 key 的节点执行 —— 交给客户端路由即可，别手动 assumption。

✓ 本章小结

要点一句话
设置方式EXPIRE/PEXPIRE/EXPIREAT/SETEX/PSETEX；优先一条命令完成值+TTL
存储结构独立的 expires 字典，存绝对毫秒时间戳（字典里的 key 是共享指针）
删除策略惰性删除 + 定期删除；没有给每个 key 挂定时器
定期删除每秒 10 次（hz=10），每次抽 20 个，过期占比 >25% 继续抽，单循环上限约 25ms
持久化RDB 不写入过期 key；AOF 通过追加 DEL 保持一致
主从从库不主动删，等主库 DEL 同步 —— 从库可能短暂读到过期数据
内存不降碎片 / 未被惰性删除 / 从库未收到 DEL / fork COW
头号坑SET 覆盖写会清 TTL → 用 KEEPTTL
