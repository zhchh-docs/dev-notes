5.1 Hash 命令全景

Hash = 一个 key 里面有若干 field→value 的小字典：key → {field: value}。value 只能是字符串（没有嵌套结构）。

127.0.0.1:6379> HSET user:1001 name "张三" age 28 city "杭州"
(integer) 3                      # 返回新建 field 数
127.0.0.1:6379> HGET user:1001 name
"张三"
127.0.0.1:6379> HMGET user:1001 name city
1) "张三"
2) "杭州"
127.0.0.1:6379> HSETNX user:1001 vip 1       # field 不存在才设
(integer) 1
127.0.0.1:6379> HEXISTS user:1001 vip
(integer) 1
127.0.0.1:6379> HLEN user:1001
(integer) 4
127.0.0.1:6379> HKEYS user:1001
1) "name"
2) "age"
3) "city"
4) "vip"
127.0.0.1:6379> HVALS user:1001
1) "张三"
2) "28"
3) "杭州"
4) "1"
127.0.0.1:6379> HINCRBY user:1001 age 1      # 只对整型 field 自增
(integer) 29
127.0.0.1:6379> HINCRBYFLOAT user:1001 score 0.5
"0.5"
127.0.0.1:6379> HDEL user:1001 vip score
(integer) 2
127.0.0.1:6379> HSTRLEN user:1001 name       # field 值长度
(integer) 6

几个容易忽略的细节：

  • HSET 已经支持一次写多个 field，HMSET 从 4.0 起只是它的别名（新代码统一用 HSET）。
  • Hash 里的 value 没有类型，都是二进制字符串。HINCRBY 遇到非数字会报错 ERR hash value is not an integer。
  • HSETNX 是field 级的 NX，和第 4 章的 key 级 NX 是两个层级。
# 购物车是 Hash 的经典用法：key=用户购物车，field=商品ID，value=数量
127.0.0.1:6379> HSET cart:u1001 sku:88 2 sku:99 1
(integer) 2
127.0.0.1:6379> HINCRBY cart:u1001 sku:88 1     # 加一件
(integer) 3
127.0.0.1:6379> HDEL cart:u1001 sku:99          # 移除商品
(integer) 1
127.0.0.1:6379> HLEN cart:u1001                 # 商品种类数
(integer) 1
127.0.0.1:6379> HGETALL cart:u1001              # 展示全部（注意第 5.4 节风险）
1) "sku:88"
2) "3"

5.2 存对象：Hash vs String(JSON) 的胜负清单

这是本篇最有价值的一张表，答案不是"永远用 Hash"：

维度String 存 JSONHash 存字段
读取单个字段要 GET 整个对象 + 反序列化HGET 只读一个 field，网络量小
更新单个字段读 → 改 → 写全量（有并发覆盖风险）HSET 一个 field，天然局部
内存开销小对象时略省（一个 dict entry）每个 field 都要 redisObject+SDS，但 listpack 编码下非常紧凑
嵌套结构支持（JSON 天然嵌套）不支持（value 只能是字符串）
序列化开销CPU 上有 JSON 编解码成本无
批量读全部一次 GET 拿全对象HGETALL 或 HMGET
字段级 TTL同样不支持不支持（第 5.5 节）

选择口诀：整体读写、结构嵌套 → String(JSON)；频繁改单字段、希望省网络 → Hash。例如：商品详情/文章详情（整条缓存）用 String 存 JSON；购物车/用户配置/计数器（字段独立变动）用 Hash。

内存实测：小 Hash 比你想象的省

# 100 万个小 Hash（每个 10 个短 field），用 listpack 编码时的对比
# 用一百万个 String key 存同样数据：约 200MB+
# 用几千个大 Hash 分段存（每 Hash 500 个 entry）：可能降到 50-80MB
# 原因：listpack 紧凑存储 + 大量减少 dict 元数据与 key 字符串
redis-cli INFO memory | grep used_memory_human
redis-cli --bigkeys    # 看看实例里最占地的结构

5.3 底层编码：什么时候会从 listpack 变成 hashtable

Hash 有两种底层实现，Redis 自动切换：

  • listpack（Redis 7 起，6.x 及以前叫 ziplist）：所有 field/value 紧凑排在一块连续内存里，查找是 O(N) 线性扫描。省内存到极致，但 field 多了就慢。
  • hashtable：真正的哈希表，查找 O(1)，但每个 entry 都有指针/key/value 的额外开销，内存占用大得多。
127.0.0.1:6379> CONFIG GET hash-max-listpack-*
1) "hash-max-listpack-entries"
2) "128"                    # field 数量 > 128 → 转 hashtable
3) "hash-max-listpack-value"
4) "64"                     # 任一 field/value 长度 > 64 字节 → 转 hashtable

127.0.0.1:6379> HSET h1 f1 aaa f2 bbb
(integer) 2
127.0.0.1:6379> OBJECT ENCODING h1
listpack
127.0.0.1:6379> CONFIG SET hash-max-listpack-entries 1
OK
127.0.0.1:6379> HSET h2 f1 aaa f2 bbb
(integer) 2
127.0.0.1:6379> OBJECT ENCODING h2
hashtable
重要：编码转换是不可逆的。一个 Hash 从 listpack 转成 hashtable 之后，就算你把 field 删到只剩 1 个，它也不会变回 listpack。所以：临时写入超阈值数据会把 Hash 永久"撑胖"，长期累积的内存浪费不可回收。

由此得出一条重要优化（也是大 key 治理的核心）

把"一个巨大的 Hash（100 万 field）"拆成"多个小 Hash（每个 ≤128 field）"，让它们都能保持 listpack 编码，可以省下可观的内存：

# 拆分方案：key = 原key + ":" + (hash(field) % 分片数)
slot = crc32(userId) % 1024
key  = "user:profile:" + slot
HSET key userId profileJson
# 这样每个分片平均 ~1000/u 个 field —— 注意：分片数要按预期总量算，
# 让每个分片 field 数控制在 128（listpack 阈值）附近，才能保持紧凑编码

5.4 HGETALL 不能乱用：HSCAN 与分批读取

HGETALL / HKEYS / HVALS 都是 O(N)（N = field 数），对一个 50 万 field 的 Hash 执行它，等同于第 1 章说的 KEYS * 事故。

# ❌ 危险
redis.call('HGETALL', 'user:index')      # 一次性拉几十万个 field：阻塞 + 内存暴涨 + 网络打满

# ✅ 安全：HSCAN 游标分批
127.0.0.1:6379> HSCAN user:index 0 MATCH "u1*" COUNT 200
1) "152"                 # 下一个游标
2) 1) "u1001"
   2) "{...}"
   3) "u1002"
   4) "{...}"

# ✅ 也安全：只需要部分字段时，用 HMGET 精确取
127.0.0.1:6379> HMGET user:index u1001 u1002 u1003

# ✅ 或限制范围（20 个一组）
127.0.0.1:6379> HRANDFIELD user:index 20 WITHVALUES     # 随机抽样，做巡检很有用

客户端侧的标准分批读取伪代码：

cursor = 0
seen = set()
while True:
    cursor, batch = redis.hscan(key, cursor=cursor, count=500)
    for f, v in batch.items():
        if f not in seen:            # SCAN 可能返回重复，必须去重
            seen.add(f)
            process(f, v)
    if cursor == 0:
        break
坑：Cluster 模式下，Hash 的所有 field 都在同一个 slot（因为 key 就一个），所以 HSCAN 不受 split 影响——这正是 Hash 相比"拆成一堆独立 String key"在多 key 操作上的优势（第 47 章 hash tag）。

5.5 field 级过期做不到，怎么办

Redis 的过期只能作用于 key，Hash 里的 field 没有过期时间。这不是 bug，是设计约定——因为过期字典只挂在 key 上。

真实需求举例："购物车里的每个商品 7 天没动就自动消失"、"用户的每条浏览记录在 30 天后过期"。三种可行方案：

方案做法取舍
整体 key 过期整个 Hash 设 TTL，每次有变动就 EXPIRE 续期最简单；粒度粗（整个对象一起活/死），首选
ZSet 辅助field→过期时间戳存 ZSet，定时 ZRANGEBYSCORE 捞出到期的再 HDEL精确到 field；要写清理任务
拆成独立 key不用 Hash，每个条目一个 String key 各自 EXPIRE最简单精确；但 key 数量暴涨、不可原子整批操作
 
# 方案二示例：购物车 item 单独过期
127.0.0.1:6379> HSET cart:u1001 sku:88 2
(integer) 1
127.0.0.1:6379> ZADD cart:u1001:expire 1761235200 sku:88    # 到期时间戳
(integer) 1

# 清理任务每 5 分钟跑一次
127.0.0.1:6379> ZRANGEBYSCORE cart:u1001:expire 0 $(date +%s)
1) "sku:88"
127.0.0.1:6379> HDEL cart:u1001 sku:88
(integer) 1
127.0.0.1:6379> ZREM cart:u1001:expire sku:88
(integer) 1
小提示：Redis 7.4 起原生 HEXPIRE 系列命令（TTL 到 field 级），但生态支持还不普及，本书仍以通用方案为主。

5.6 常见坑

坑 1：认为 Hash 省内存就无脑用。field 超过 128 个或 value 超过 64 字节会转成 hashtable，内存反而更贵，且不可逆。
坑 2：HGETALL 当成"读取常规操作"。生产必须 HSCAN / HMGET。
坑 3：把 Hash 当关系型表做"按 value 查 field"（比如"找出城市=杭州的用户"）。Redis 无二级索引，这种需求要么自己维护倒排索引（ZSet/Set），要么交给数据库。
坑 4：HSET 一个已经存在的 field 时会静默覆盖，不会告诉你是新建还是更新。需要区分时用 HSETNX 或先 HEXISTS。
坑 5：误把 field 名字设计成动态值（时间戳、随机 UUID）导致 HLEN 无限增长（等于创建了一个永不清理的大 key）。
坑 6：Hash 嵌套需求用 JSON 字符串塞进某个 field，然后又想对这个子结构做原子操作 —— 不如直接用 String 存 JSON 或拆层。

✓ 本章小结

要点一句话
结构key → {field: value}，value 只能是字符串，无嵌套
核心命令HSET/HGET/HMGET/HGETALL/HDEL/HLEN/HINCRBY/HSETNX/HSCAN
