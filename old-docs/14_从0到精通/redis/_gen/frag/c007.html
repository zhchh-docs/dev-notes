7.1 Set 命令全景

Set = 无序、去重的字符串集合；单个元素增删查芯是 O(1)。

127.0.0.1:6379> SADD tags:post:1 redis 缓存 ceph
(integer) 3                        # 返回新增成功数（已存在的不算）
127.0.0.1:6379> SADD tags:post:1 redis
(integer) 0                        # 去重生效
127.0.0.1:6379> SISMEMBER tags:post:1 redis
(integer) 1
127.0.0.1:6379> SMISMEMBER tags:post:1 redis mysql      # 7.0+：批量判断
1) (integer) 1
2) (integer) 0
127.0.0.1:6379> SCARD tags:post:1
(integer) 3
127.0.0.1:6379> SMEMBERS tags:post:1      # 全部成员（大集合危险！见 7.6）
1) "ceph"
2) "redis"
3) "缓存"
127.0.0.1:6379> SREM tags:post:1 ceph
(integer) 1
127.0.0.1:6379> SMOVE tags:post:1 tags:post:2 缓存      # 原子地把成员迁移到另一个集合
(integer) 1

随机家族：抽奖全靠它

127.0.0.1:6379> SADD lottery:users u1 u2 u3 u4 u5
(integer) 5

# SRANDMEMBER：随机返回，【不删除】（可以做多次抽，可重复出现）
127.0.0.1:6379> SRANDMEMBER lottery:users 2        # 正数：互不重复的 2 个
1) "u3"
2) "u1"
127.0.0.1:6379> SRANDMEMBER lottery:users -3       # 负数：允许重复的 3 个
1) "u2"
2) "u2"
3) "u5"

# SPOP：随机返回并【删除】（等额抽奖、抽完不重姓名单）
127.0.0.1:6379> SPOP lottery:users 2
1) "u4"
2) "u2"
127.0.0.1:6379> SCARD lottery:users
(integer) 3

抽奖口诀：不剔除（可重复中奖）用 SRANDMEMBER；要剔名额（抽完即走）用 SPOP。两者都是原子操作，不需要自己加锁做"防重复中奖"。

7.2 集合运算：SINTER/SUNION/SDIFF

运算命令含义复杂度
交集SINTER k1 k2 ...同时在所有集合里O(N×M)，M=最小集合规模
并集SUNION k1 k2 ...任一集合里有的全部O(N)，N=全体成员数
差集SDIFF k1 k2 ...在 k1 但不在 k2.. 里O(N)，N=成员总数
带存储SINTERSTORE dest ...算完存到 dest 而不返回同上 + 写入开销
 
127.0.0.1:6379> SADD follow:u1 a b c d
(integer) 4
127.0.0.1:6379> SADD follow:u2 b c e
(integer) 3

127.0.0.1:6379> SINTER follow:u1 follow:u2        # 共同关注
1) "b"
2) "c"
127.0.0.1:6379> SDIFF follow:u1 follow:u2         # u1 关注了但 u2 没关注 → 推荐候选
1) "a"
2) "d"
127.0.0.1:6379> SUNION follow:u1 follow:u2        # 合并
1) "a" 2) "b" 3) "c" 4) "d" 5) "e"

# 结果要留给下次用：用 STORE 版本（返回存进去的元素个数）
127.0.0.1:6379> SINTERSTORE mutual:u1:u2 follow:u1 follow:u2
(integer) 2
127.0.0.1:6379> EXPIRE mutual:u1:u2 600           # 记得给结果一个 TTL！
复杂度陷阱：SINTER 的复杂度是 O(N×M)，要对两个各 10 万成员的集合求交集，Redis 要遍历小集合的成员去大集合里查——这是毫秒到秒级的操作，且阻塞所有其它请求。
三个对策：
① 在从库上做（不能接受实时一致性时）；
② 结果用 SINTERSTORE 缓存起来复用，而不是每次实时算；
③ 把"好友关系"这类需要实时运算的数据放回 SQL/图数据库，Redis 只存热点。

7.3 底层编码：intset 到 hashtable

127.0.0.1:6379> SADD nums 1 2 3 4 5
(integer) 5
127.0.0.1:6379> OBJECT ENCODING nums
intset                     # 全是整数时，用紧凑的有序整数数组，极省内存

127.0.0.1:6379> SADD nums hello
(integer) 1
127.0.0.1:6379> OBJECT ENCODING nums
hashtable                  # 一加入非整数就转 hashtable，【不可逆】

127.0.0.1:6379> CONFIG GET set-max-intset-entries
1) "set-max-intset-entries"
2) "512"                   # 纯整数元素超过 512 个也会转 hashtable
# 另有 set-max-listpack-entries 128 / set-max-listpack-value 64（7.2 起的过渡编码）
编码适用特点
intset全整数 且 ≤512 个最省内存；查找 O(logN)（内部有序，二分）
listpack少量短字符串成员紧凑；查找 O(N)
hashtable其它查找 O(1)；内存开销最大

启示：用 Set 存一大堆用户 ID（如签到名单、黑名单），保持纯整数 ID 会很省内存；一旦混进一个非数字字符串，整个集合变成 hashtable，内存可能翻几倍且不可逆。

7.4 四个高频业务场景

① 抽奖 / 随机推荐

# 参与资格写入（活动结束记得删）
SADD lottery:2026:participants 1001 1002 1003 ...
# 一等奖 1 名（抽出后移除）：SPOP
SPOP lottery:2026:participants 1
# 二等奖 10 名（可重复参与池、不移除）：SRANDMEMBER
SRANDMEMBER lottery:2026:participants 10

② 共同关注 / 好友推荐（二度人脉）

# 每个用户的关注列表一个 Set
SADD follow:u1 u2 u3 u4
SADD follow:u2 u3 u5
# 共同关注
SINTER follow:u1 follow:u2                  # → u3
# 你可能认识的人（我对 x 的关注 ∩ x 的关注者 → 简化版：差集 + 随机）
SDIFF follow:u2 follow:u1                   # u2 关注了但 u1 没关注的 → 推荐给 u1

③ 标签 / 反向索引

# 正向：这篇文章的标签
SADD tags:article:1 redis 性能 缓存
# 反向：这个标签下有哪些文章（便于筛选）
SADD tagidx:redis article:1 article:5 article:9
SADD tagidx:性能 article:1 article:7
# 「同时有 redis 和 性能 标签的文章」
SINTER tagidx:redis tagidx:性能

注意：Redis 没有"查询"能力，所谓筛选=自己维护反向索引。关联数据复杂时请交给 ES / MySQL。

④ 去重 / 幂等 / UV 辅助

# 一天内已处理过的消息 ID（幂等）
SADD dedup:2026-10-19 msgid1 msgid2
SISMEMBER dedup:2026-10-19 msgid1      # 已处理过？跳过
EXPIRE dedup:2026-10-19 172800         # 留两天（注意：SADD 后补 TTL 才能保证过期）

# UV（精确）—— 基数一亿请不要这样存，见第 9 章 HyperLogLog
SADD uv:2026-10-19 uid1 uid2 uid3
SCARD uv:2026-10-19                    # = UV 数

7.5 大型集合的运算策略

百万级成员的集合是运维事故常客，处理原则：

  1. 避免一次性返回全集：SMEMBERS / SUNION 直出都可能导致阻塞与客户端 OOM；用 SSCAN 分批。
    2. 127.0.0.1:6379> SSCAN follow:u1 0 COUNT 500
1) "832"                       # 下一批游标
2)  1) "u2"
    2) "u7"
    ...
  2. 大集合运算放到从库：主库只承接实时写，（注意从库也有淘汰/延迟）。
  3. 化整为零：把超大 Set 拆成分片（如按 uid % 64），运算时逐片 SUNIONSTORE 累积；虽然复杂但可控。
  4. 结果复用：SINTERSTORE + TTL，把"共同好友"这种低频变动的结果缓存 5-10 分钟。
  5. 必要时别用 Redis：社交图谱这种图数据，图数据库/关系库更合适。

7.6 常见坑

坑 1：SMEMBERS 一个百万 Set（O(N) 且返回全部）——一步到位的阻塞堵塞。替代：SSCAN。
坑 2：实时 SINTER 两个大集合。O(N×M)，务必评估数据量或提前算好缓存。
坑 3：忘了给 SINTERSTORE 产生的 dest key 设 TTL —— 它是"一次性结果"，不设过期会变成垃圾。
坑 4：把 Set 里塞完整的业务对象而不是 ID → 既浪费内存，也无法去重（对象内容变了就重fanée）。Set 里一律放 id。
坑 5：误以为 Set 有序。Set 无顺序，需要按分数/时间排序用 ZSet（第 8 章）或 List。
坑 6：用 Set 存亿级 UV。SCARD 精确但内存爆炸（1 亿 uid ≈ 数 GB）；该用 HyperLogLog 时别硬撑（第 9 章）。
坑 7：Python/Java 客户端返回类型混淆：SISMEMBER 返回的是 0/1 整数，有些语言里 false 与 null 混淆，注意判空。

✓ 本章小结

要点一句话
结构无序去重集合，单元素操作 O(1)
随机SRANDMEMBER（不删）vs SPOP（删除），抽奖核心
三大运算SINTER(O(N×M)) / SUNION(O(N)) / SDIFF(O(N))，带 STORE 可缓存结果
编码intset（纯整数≤512，最省）→ hashtable，不可逆
典型场景抽奖、共同关注、标签反向索引、幂等去重、精确 UV
大集合SSCAN 分批、从库运算、分片化、结果缓存
误用Set 里放大对象、把它当查询引擎、亿级基数硬存
