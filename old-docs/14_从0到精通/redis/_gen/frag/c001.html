1.1 Redis 的一句话定义

Redis（REmote DIctionary Server）= 一个用 C 写的、基于内存的、支持多种数据结构的键值网络服务。

这个定义里每个词都有分量，逐个拆：

  • 基于内存：数据主要存放在 RAM 里，读写都是纳秒/微秒级。这是 Redis 快的根本，也是它贵的根本——内存比磁盘贵一个数量级。
  • 多种数据结构：value 不只是字符串，还可以是 Hash、List、Set、ZSet、Bitmap、HyperLogLog、Stream、GEO。这是 Redis 与"只支持 String 的缓存"最本质的区别（第 4-9 章逐一深入）。
  • 键值：没有表、没有字段定义、没有 SQL 优化器。你拿一个字符串 key 去换一个 value，就这么简单——代价是不支持按 value 里的字段做条件查询。
  • 网络服务：Redis 天生就是给多机访问用的。哪怕本机部署，也是 TCP 通信（unix socket 除外），所以网络往返时间（RTT）在 Redis 的性能账里不可忽略（第 50 章专题）。

一段简短的身世

2009 年，意大利工程师 Salvatore Sanfilippo（网名 antirez）为了解决自己公司一个实时网站分析工具的瓶颈，写出了 Redis 的第一版。2010 年 VMware 雇了他专职维护；2015 年 Redis Labs 接手；2020 年 Redis 6.0 发布，引入多线程网络 IO 与 ACL；2022 年 Redis 7.0 发布，用 listpack 全面替代 ziplist、AOF 改为多 part 目录结构。

版本号怎么读：主线版本用 odd/even 的老习惯早废了，现在大版本 6/7 是稳定版；生产环境推荐 Redis 7.0+，最低不低于 6.2。

1.2 它到底解决了什么问题

如果你的系统只有一台服务器、几百个用户，你不需要 Redis。Redis 是为了解决规模上来之后的三个具体痛点：

痛点一：数据库扛不住重复读

一个商品详情页，每次请求要查商品表、库存表、评价表、商家表……这些数据几乎不变，但每来一个用户就要重新算一遍。MySQL 单实例扛 3000 QPS 左右就开始吃力，而这类读often占系统总请求的 80% 以上。

把结果缓存进 Redis：一次数据库查询，N 次毫秒内返回。这是 Redis 最主流的用法（第三篇 12 章都在讲这件事）。

# 伪逻辑：Cache-Aside（旁路缓存）模板，第三篇第 21 章会讲透
1. 查 Redis: GET product:1001
2. 命中(name / price / stock)? -> 直接返回，不走数据库
3. 未命中?   -> 查 MySQL -> SET product:1001  EX 3600
4. 更新 MySQL 时 -> DEL product:1001（删缓存而非改缓存）

痛点二：多个服务之间要共享状态

你部署了 4 个订单服务实例，用户在 A 实例登录、下一次请求落到 B 实例。各自内存里的登录态互不相认，用户就会被反复踢出登录。把会话搬进 Redis，四个实例访问同一个地方，问题消失（第 41 章实战）。

同类场景：限流器的计数器（不能让每台机器各限自己的流）、幂等表扣库存/防重复提交、签到、排行榜、全局唯一的生成序列号。

痛点三：需要"实时"的计算能力

排行榜要在毫秒级更新排序、在线人数要秒级刷新、附近 3 公里的车要实时返回。这些事情用 MySQL 也能算，但要全表扫描+排序，几秒钟一次 SQL 就能把数据库拖死；Redis 的 ZSet 天生有序，HyperLogLog 用 12KB 内存估算亿级 UV，GEO 内建了地理位置索引。这类"算得快"而不是"存得多"的需求，正是 Redis 的舒适区。

一句话归纳：Redis 干的活，本质是"把高频、共享、需要实时反馈的那部分数据和计算，从磁盘搬进内存、从各服务私有搬到一个共享中心"。

1.3 与 MySQL、Memcached 的定位分工

很多人初学时的一句话是"Redis 就是缓存"，这句话只对了一半：Redis 是缓存 + 数据结构服务器 + 消息管道的合体。定位分工看这张表：

结论：MySQL 是"唯一真相（Source of Truth）"，Redis 是它的"高速前台"。数据最终以 MySQL 为准，Redis 里的任何东西都可以被删掉重建——只要这条铁律立住，后面的穿透/击穿/雪崩/一致性问题才有解。

与 Memcached 怎么选

今天新项目基本直接选 Redis，但要知道差异，面试常问：

  • Memcached 是多线程：理论上利用多核更好；Redis 命令执行是单线程（1.4 解释为什么这不慢），但 6.0 起网络 IO 可开多线程。
  • Memcached value 只能是 String：要存对象就得自己序列化一坨 JSON；取一个字段要把整个对象拉回来。Redis 的 Hash 可以只读写一个字段。
  • Memcached 没有持久化、没有原生集群（靠客户端分片）；Redis 有 RDB/AOF、主从/哨兵/Cluster。
  • 仍有团队用 Memcached 做超大 value 的简单缓存，因为它在某些纯 KV 场景下内存利用率更稳定。但作为学习投资，Redis 回报率明显更高。

1.4 单线程为什么还能快

准确表述：Redis 命令执行是单线程的（时至今日依然如此）；网络 IO 从 6.0 起可以多线程。

很多人听到"单线程"的第一反应是"那不就慢死了吗"。真相是——决定 Redis 速度的是内存访问，不是 CPU 并发：

  1. 纯内存操作：一次内存随机读约 100 纳秒，一次 SSD 随机读约 100 微秒（慢 1000 倍），一次机械盘寻道约 10 毫秒（慢 10 万倍）。Redis 把数据放 RAM，意味着它不需要等磁盘。
  2. 没有锁竞争：单线程执行天然没有写共享数据的争用问题，不需要加锁/解锁/上下文切换的开销。多线程数据库光是锁开销 + 上下文切换就可能吃掉一半吞吐。
  3. I/O 多路复用：单线程用一个 epoll（Linux）/ kqueue（macOS）同时盯几万个 socket，谁的数据到了就处理谁——不是"一次只能服务一个连接"，而是"一次只执行一条命令"。多个客户端的请求只是被串行且快速地处理。
  4. 高效的数据结构：SDS 动态字符串、哈希表（渐进式 rehash）、跳表、压缩列表/listpack，都是为内存紧凑而定制的 C 实现。

单线程的代价（务必记住）

单线程意味着一条慢命令会阻塞后面所有请求。以下都是真实事故制造机：

KEYS *                  # O(N) 全库扫描，百万 key 时直接卡死其它请求，生产禁用
HGETALL huge_hash       # 一次拉回几十万个 field
SMEMBERS big_set        # 同上
SORT / SINTER 大集合    # 复杂聚合消耗 CPU
DEL a_ten_million_list  # 删除本身也很贵
FLUSHALL / DEBUG SLEEP 30  # 人为制造灾难

# 替代方案（第 3 章、第 17 章详述）
SCAN 0 MATCH user:* COUNT 500   # 游标分批，不阻塞
HSCAN / SSCAN / ZSCAN           # 各结构的分批版本
UNLINK big_key                  # 后台异步删除

1.5 Redis 的能力边界

知道它不能干什么，和知道它能干什么同样重要。四件事别指望 Redis：

  1. 不能当主数据库用：没有 SQL、没有 JOIN 聚合、没有真正的完整事务回滚、容量受限于内存、挂了可能丢秒级数据。任何数据必须有磁盘上的落地方（MySQL/ES/Mongo）。
  2. 不适合做复杂查询：想"找出价格在 100-200 且上架超过 30 天的商品"，Redis 只能自己在客户端枚举 key 或用 Search 模块（Redis Search 另说）。按条件检索是数据库的活。
  3. 不适合存大 value：单个 value 超过 10KB 就该警惕，超过 100KB 基本是设计错误（第 17 章大 key）。大 value 会让网络带宽、序列化延迟成倍上升。
  4. 不是消息队列的完全替代：Redis Stream / List 队列能用，但比不了 RabbitMQ、Kafka 的 ACK、重投、持久化、消费组语义。用它做专业 MQ 要非常清楚自己在放弃什么（第 6、40 章）。

1.6 常见坑：新手最容易搞错的五件事

坑 1：把 Redis 当数据库，只写不落盘。服务重启后用户数据全没了才发现没配 appendonly yes。铁律：只用 Redis 的数据必须有其他持久化来源，除非它是可重算的缓存。
坑 2：没有设置 maxmemory。默认 0（不限制），内存用满后 Redis 会根据 OS 行为被 OOM Kill，或者直接换出到 swap 慢到死。生产必须显式配置 maxmemory + 淘汰策略（第 16 章）。
坑 3：线上执行 KEYS * 排查问题。以为"就看看有多少 key"，结果一个 O(N) 把服务阻塞到所有接口超时。检查 key 一律 SCAN 或 DBSIZE（第 3 章）。
坑 4：没有任何过期时间。业务代码写了缓存但从没设 TTL，三个月后 Redis 里堆了两千万个再也用不到的 key，缓存变 RocksDB。每个 key 都要问一句：它什么时候该死？
坑 5：开放公网且无密码。Redis 默认无密码、端口 6379，公网暴露 + 空口令 = 几分钟内被植入挖矿脚本的经典事故。bind、requirepass、防火墙三件套缺一不可（第 53 章）。
