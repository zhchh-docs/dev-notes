9.1 Bitmap：把每个 bit 都用在刀刃上

Bitmap 不是一种新类型，它就是 String（SDS）按 bit 位操作——所以最大容量仍是 512MB（约 42.9 亿 bit）。

127.0.0.1:6379> SETBIT sign:2026-10:u1001 0 1     # 第 0 位（1 号）设为 1 = 已签到
(integer) 0                    # 返回该位原来的值
127.0.0.1:6379> SETBIT sign:2026-10:u1001 1 1     # 2 号签到
(integer) 0
127.0.0.1:6379> SETBIT sign:2026-10:u1001 3 1     # 4 号签到（3 号没签）
(integer) 0
127.0.0.1:6379> GETBIT sign:2026-10:u1001 2       # 3 号签了吗 → 0
(integer) 0
127.0.0.1:6379> BITCOUNT sign:2026-10:u1001       # 这个月签到几次 → 3
(integer) 3
127.0.0.1:6379> BITCOUNT sign:2026-10:u1001 0 1   # 前 2 个字节内的签到数（按 BYTE 范围）
(integer) 2
127.0.0.1:6379> BITPOS sign:2026-10:u1001 1       # 第一次签到是第几位
(integer) 0
127.0.0.1:6379> STRLEN sign:2026-10:u1001         # 占用了几个字节 → 1
(integer) 1

内存账（为什么签到必须用它）

方案1000 万用户/月的签到存储备注
MySQL 一行一条~1.5GB+（含索引）还要 I/O 成本
Set 存 sign:{date}（一天一个 key）1000 万/天 ≈ 数百 MB/天每个 userId 都要完整存一份
Bitmap 每人一个 key~4MB（1000万 × 31bit ÷ 8） 31 天只需 4 字节/人
 
# 每位运营经理都想看的：本月签到总人数 → BITOP 把所有人 OR 起来再 BITCOUNT
BITOP OR sign:2026-10:all sign:2026-10:u1 sign:2026-10:u2 ...   # 实际要分批 + Lua 聚合
BITCOUNT sign:2026-10:all
# 连续签到人数 = 每天签到 bitmap AND
BITOP AND sign:consecutive sign:2026-10-18 sign:2026-10-19
BITCOUNT sign:consecutive

BITOP 支持 AND / OR / XOR / NOT，且结果存到 dest key。它是把"批量布尔运算"从数据库搬到内存的利器，但要留意：超大 Bitmap 的 BITOP 同样是 O(N) 阻塞操作。

9.2 签到场景的完整实现

# key 设计：sign:{userId}:{yyyyMM}
# offset 设计：0 = 当月第 1 天 → offset = day - 1
127.0.0.1:6379> SETBIT sign:1001:202610 18 1     # 19 号签到
(integer) 0

# 幂等天然保证：同一天重复 SETBIT 返回原值，不影响计数
127.0.0.1:6379> SETBIT sign:1001:202610 18 1
(integer) 1

# 查询某天是否签到
127.0.0.1:6379> GETBIT sign:1001:202610 18
(integer) 1

# 本月签到总天数
127.0.0.1:6379> BITCOUNT sign:1001:202610
(integer) 5

# 首次签到日（有的产品这里发额外奖励）
127.0.0.1:6379> BITPOS sign:1001:202610 1
(integer) 2                     → 第 3 天

# 「连续签到天数」——Bitmap 不好算，通常改用另一种设计：
#   维护一个计数器 + 上次签到日期（Hash/JSON），见下
统计需求Bitmap 能否更好方案
某天是否签到完美 O(1)GETBIT
本月签到总数完美BITCOUNT
首次签到日可以BITPOS
连续签到天数麻烦（要反解 bit 序列）额外维护 last_sign_date + streak 计数器
某天全部签到用户名单要遍历所有人的 bitmap当天再维护一个 Set
设计结论：Bitmap 适合"按主体（用户）聚合、以时间/整数为下标"的查询；反过来"按时间查主体名单"就需要额外的倒排索引。

9.3 HyperLogLog：亿级 UV 只要 12KB

HLL = 概率算法数据结构：用固定约 12KB 内存估算集合基数（去重后的元素个数），标准误差 0.81%。

127.0.0.1:6379> PFADD uv:2026-10-19 u1 u2 u3 u4 u5
(integer) 1                          # 返回 1 = 内部估计值可能变了；0 = 没变化
127.0.0.1:6379> PFCOUNT uv:2026-10-19
(integer) 5
127.0.0.1:6379> PFADD uv:2026-10-19 u1 u2 u3      # 重复元素不影响
(integer) 0
127.0.0.1:6379> PFCOUNT uv:2026-10-19
(integer) 5

# 合并多天 → 一周 UV（去重，不是简单相加）
127.0.0.1:6379> PFMERGE uv:week42 uv:2026-10-13 uv:2026-10-14 ... uv:2026-10-19
OK
127.0.0.1:6379> PFCOUNT uv:week42
(integer) 27

127.0.0.1:6379> MEMORY USAGE uv:2026-10-19
(integer) 12304                      # ≈12KB，无论里面装 1 万还是 1 亿个元素

三种实现模式（重要）

  • 稀疏（sparse）：元素少时用，内存可能只有几百字节。
  • 稠密（dense）：元素多时自动转稠密，固定 ~12KB。转换由 hll-sparse-max-bytes 3000 控制，不可逆。
维度HyperLogLogSet
内存（1 亿元素）~12KB数 GB
精确度估算，误差 0.81%精确
能取出单个元素吗不能（只有哈希）可以（SMEMBERS）
能判断某元素是否存在吗不能SISMEMBER 可以
支持合并PFMERGE（去重合并）SUNION（更贵）
适用UV、IP 数、搜索词去重总数需要名单/判重时

一句话选型：只要一个数字 → HLL；要"某用户今天访问过吗"这种判重/名单 → 必须用 Set 或 Bitmap。

9.4 GEO：附近的人与外卖距离

Redis GEO 底层就是 ZSet：把经纬度通过 Geohash 编码成一个 52 位整数当 score，所以 GEO 的所有 key 都能用 ZSET 命令操作。

127.0.0.1:6379> GEOADD drivers:gps 120.155070 30.274080 driver:1 120.200000 30.260000 driver:2
(integer) 2
127.0.0.1:6379> GEOPOS drivers:gps driver:1        # 取坐标
1) 1) "120.15507048368453979"
   2) "30.27407993550386663"
127.0.0.1:6379> GEODIST drivers:gps driver:1 driver:2 km   # 两点距离
"4.4630"
127.0.0.1:6379> GEOHASH drivers:gps driver:1
1) "wtmkqe1t210"

# 核心：找附近（6.2 起推荐 GEOSEARCH，老版用 GEORADIUS）
127.0.0.1:6379> GEOSEARCH drivers:gps FROMLONLAT 120.15 30.27 BYRADIUS 5 km ASC COUNT 10 WITHDIST WITHCOORD
1) 1) "driver:1"
   2) "0.5619"                       # 距离 km
   3) 1) "120.15507048368453979"
      2) "30.27407993550386663"
2) 1) "driver:2"
   2) "4.4630"

# 也可以按矩形 BOX 搜
127.0.0.1:6379> GEOSEARCH drivers:gps FROMLONLAT 120.15 30.27 BYBOX 10 10 km ASC COUNT 20

# 结果存起来复用
127.0.0.1:6379> GEOSEARCHSTORE near:cache drivers:gps FROMLONLAT 120.15 30.27 BYRADIUS 3 km ASC

典型业务：附近的车辆/门店

# ① 司机端每 5 秒上报位置（单个 key 会变得很大 → 按城市分片）
GEOADD drivers:city:hangzhou 120.15 30.27 driver:8801
# ② 用户打车请求 → 搜周边 3km 最近 20 个
GEOSEARCH drivers:city:hangzhou FROMLONLAT ${lng} ${lat} BYRADIUS 3 km ASC COUNT 20 WITHDIST
# ③ 司机下线时要删除（别忘了，否则会给出已下线的司机）
ZREM drivers:city:hangzhou driver:8801        # 注意：用 ZREM 而不是 GEO 命令！
# ④ 活跃度过滤：GEOSEARCH 只能按位置，业务还要过滤"是否接单中" → 取回后自己在应用层过滤
关键限制：GEO 只能按地理范围检索，不能加任何其它条件（无法"3 公里内评分 4.8 以上的店"）。解决方式：GEO 粗筛 → 应用层/ 数据库再过滤；或者用专门的搜索引擎。

9.5 三者横向对比与选型

结构底层空间精确典型场景
BitmapString(SDS)1 bit/标记位精确签到、活跃标记、布隆过滤自实现
HyperLogLogString(HLL 编码)~12KB估算 ±0.81%UV、IP 数、搜索词总数
GEOZSet(Geohash score)~成员数 × 几十字节精确的距离计算附近的车辆/门店/人

速记：想知道"有没有"→ Bitmap；想知道"多少个"→ HyperLogLog；想知道"多远/在哪附近"→ GEO。

9.6 常见坑

坑 1（Bitmap）：offset 从 0 开始，很多人把"日期 day-1"写漏，导致 1 号和 2 号错位。
坑 2（Bitmap）：SETBIT key 1000000000 1 会把 String 撑成 ~125MB 并立刻分配 —— 稀疏但超大的 offset 是内存杀手。用人的 id 当 offset 时必须先做连续编号映射（如自增代理主键）。
坑 3（Bitmap）：BITCOUNT 整个大 bitmap 是 O(N)；范围参数按字节不是 bit。
坑 4（HLL）：以为能"判断某用户今天是否来过"。HLL 做不到（不存原始元素），需要名单/判重请用 Set/Bitmap。
坑 5（HLL）：PFCOUNT 单次约几毫秒，高频调用会累积开销；可以每次读本地缓存化。
坑 6（GEO）：忘记删除下线对象（用 ZREM），导致用户打到不存在的司机。
坑 7（GEO）：GEORADIUS 在大半径、大集合下是 O(N)，且结果 COUNT 只是"返回上限"不是"提前终止"（会算完再排序）。半径设小、集合分片。
坑 8（GEO）：经纬度的合法范围（经度 ±180，纬度 ±85.05112878），传错会报错 invalid longitude,latitude pair。

✓ 本章小结

要点一句话
BitmapString 按 bit 操作；31 天签到只要 4 字节/人
Bitmap 命令SETBIT / GETBIT / BITCOUNT / BITOP / BITPOS / BITFIELD
