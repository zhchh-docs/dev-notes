4.1 SET 的完整参数表

官方签名：SET key value [NX|XX] [GET] [EX seconds|PX milliseconds|EXAT ts|PXAT ms|KEEPTTL]

127.0.0.1:6379> SET user:1001 '{"name":"张三"}' EX 3600 NX
OK                          # NX：key 不存在才设置（分布式锁的基础）
127.0.0.1:6379> SET user:1001 'new' EX 3600 NX
(nil)                       # 已存在 → 什么都不做，返回 nil

127.0.0.1:6379> SET user:1001 'new' XX
OK                          # XX：只在 key 存在时更新（适合"必须已加载过"的场景）

127.0.0.1:6379> SET user:1001 'new' KEEPTTL
OK                          # 更新值但保留原来的剩余 TTL（第 3 章强调过）

127.0.0.1:6379> SET user:1001 'new' GET
"{\"name\":\"张三\"}"       # 返回被覆盖的旧值（原子地"读旧写新"）

127.0.0.1:6379> SETNX user:1001 'other'
(integer) 0                 # 老 setnx 命令仍在，但没有原子设过期的能力 → 不要用
开关含义典型用途不存在/不满足时
NXNot eXists 才写加锁、幂等占位、防重复返回 nil
XXeXists 才写只更新不新建（如只续已有会话）返回 nil
EX / PX秒 / 毫秒级过期缓存、锁超时—
EXAT / PXAT指定绝对过期时刻活动到某个整点结束—
KEEPTTL保留原 TTL更新值但不延长生命周期—
GET返回旧值读改写（CAS 的读半边）返回 nil

配套的读取/追加/截取：

127.0.0.1:6379> APPEND log:today "line-1\n"      # 追加，返回新长度
(integer) 7
127.0.0.1:6379> STRLEN log:today
(integer) 7
127.0.0.1:6379> GETRANGE user:1001 0 3           # 子串 [start,end]，负索引支持
"{\"na"
127.0.0.1:6379> SETRANGE user:1001 5 "XX"        # 从偏移量覆写
(integer) 11
127.0.0.1:6379> SET http:hit 1
OK
127.0.0.1:6379> GETDEL http:hit                  # 取走并删除（一次性 ticket）
"1"
127.0.0.1:6379> GETEX http:hit EX 60             # 取值并设置/更新 TTL
(nil)
注意：SETRANGE 对不存在的 key 会用 "\x00" 填充到 offset，容易产生巨大而稀疏的 value，别误用。

4.2 INCR 家族：Redis 最香的原子自增

因为命令执行是单线程，一条命令天然是原子的——所以 INCR 不需要任何锁就线程安全。

127.0.0.1:6379> SET pv:home 0
OK
127.0.0.1:6379> INCR pv:home          # +1，返回新值
(integer) 1
127.0.0.1:6379> INCRBY pv:home 100    # +N
(integer) 101
127.0.0.1:6379> DECR pv:home          # -1
(integer) 100
127.0.0.1:6379> DECRBY pv:home 10
(integer) 90
127.0.0.1:6379> INCRBYFLOAT pv:home 0.5   # 浮点（注意精度！）
"90.5"
127.0.0.1:6379> SET notanumber abc
127.0.0.1:6379> INCR notanumber
(error) ERR value is not an integer or out of range      # 非数字直接报错

典型计数器场景

  1. 全局计数：文章阅读数、视频播放次数、点赞数。10 万 QPS 的 INCR 完全没问题。
  2. 限流：INCR + EXPIRE 做固定窗口（第 38 章会做成完整 Lua）。
  3. 发号器：INCRBY seq:order 1000，应用拿走 1000 个号在内存里本地分发，大幅减少 Redis 压力（批量号段思想）。
  4. 库存扣减：DECRBY stock:sku 1 结果为负则回滚 INCRBY（配合 Lua 更稳妥，第 42 章秒杀）。
# 固定窗口限流（朴素版，第 38 章会指出它的边界缺陷并给出 Lua 版）
-- 每分钟每个用户最多 100 次
key = "rate:uid:" .. uid .. ":" .. os.date("%Y%m%d%H%M")
local n = redis.call("INCR", key)
if n == 1 then redis.call("EXPIRE", key, 65) end   # 多给 5 秒容忍跨窗口误差
return n <= 100
坑：INCR 一个没有 TTL 的计数器（如每个凌晨重置的日活）会无限增长最终溢出（Redis 整数上限是 2^63-1，超过会报 "increment or decrement would overflow"）。要么设合理 TTL，要么用分段 key（pv:20261019）让旧数据自然过期。

4.3 MSET/MGET 与 Pipeline 的区别

127.0.0.1:6379> MSET k1 v1 k2 v2 k3 v3
OK
127.0.0.1:6379> MGET k1 k2 k3
1) "v1"
2) "v2"
3) "v3"
127.0.0.1:6379> MSETNX k1 x k4 v4        # 只要有一个 key 存在，整批全部不执行
(integer) 0
对比MSET/MGETPipeline普通多次 GET
网络往返一次一次N 次
命令原子性单条命令，天然原子批量，不保证事务原子不保证
跨 slotCluster 下必须同 slotCluster 下可路由到多节点（客户端拆分）随意
可混合命令只能同类任意命令任意

一次网络往返能省多少？假设 RTT=0.3ms，一次 GET 0.05ms：

1000 次独立 GET   ≈ 1000 × 0.35ms = 350ms
一次 MGET 1000 个 ≈ 0.3ms + 1000 × 0.05ms ≈ 50ms     （快 7 倍）
一次 Pipeline 1000 条 GET ≈ 同上量级
# 用 redis-benchmark 实测对比（第 51 章）
redis-benchmark -t get,set -n 100000 -q
redis-benchmark -t get,set -n 100000 -P 16 -q      # 加管道后通常提升 5-10 倍
坑：MGET 别一次传几万个 key——它是单条命令，仍然会阻塞后续请求。建议每批 100-500 个，超大批量用 pipeline 分批。

4.4 SETNX → SET NX PX：锁的雏形

分布式锁的最小可实现：抢到一个带 TTL 的标记位，用完删掉。这里有四个必须遵守的约束，违反任何一个都会出事故。

第一版：错误示范（用 SETNX + EXPIRE 两条命令）

127.0.0.1:6379> SETNX lock:pay:7788 "client-A"
(integer) 1
127.0.0.1:6379> EXPIRE lock:pay:7788 30        # ← 如果这一步之前进程崩了会怎样？
(integer) 1
致命缺陷：SETNX 成功之后、EXPIRE 之前，进程崩溃或网络断开 → 锁永不释放，其它节点永久等待（死锁）。两条命令不是原子的。

第二版：正确的最小实现（一条命令搞定）

# 加锁：值与过期一起设，原子完成
127.0.0.1:6379> SET lock:pay:7788 "client-A-uuid-7f3e" NX PX 30000
OK                       # 抢到锁
127.0.0.1:6379> SET lock:pay:7788 "client-B-uuid-9a2c" NX PX 30000
(nil)                    # 已被占 → 业务应 sleep+重试或快速失败

# 释放：必须"先比对 owner，再删"，且必须原子（第 34 章讲）
127.0.0.1:6379> EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 lock:pay:7788 client-A-uuid-7f3e
(integer) 1

四个约束（缺一不可）

  1. 加锁与设过期必须原子：SET key val NX PX ms，一条命令。
  2. value 必须唯一（UUID / 线程标识）：防止 A 的锁超时后被 B 抢到，A 醒来把 B 的锁删了这个经典事故。
  3. 释放必须校验 owner：GET 比对 → DEL，两步要放进 Lua（上面的 EVAL 就是这个作用）。
  4. TTL 要大于业务最大耗时：不够就要续期（第 35 章看门狗）。
这一节只给你"锁的雏形"。真正的生产级锁还要解决：重入、续期、集群 failover 期间的失效（RedLock 争议在第 36 章）。不要在生产自己手撸第二版——用 Redisson。

4.5 四位语义开关的组合拳

把 NX/XX/GET/EX 组合起来，能替代很多"先读再写"的非原子操作：

需求一次命令写法替代的（有竞态的）老写法
不存在才建SET k v NX EX 60EXISTS + SET（两步有竞态）
存在才更新SET k v XX EX 60EXISTS + SET
取,更,新值SET k v GETGET + SET
更新值保 TTLSET k v KEEPTTLTTL + SET + EXPIRE
原子 CAS（单值）Lua: GET 比对后 SETGET 判断后再 SET（必有竞态）

一个真实的 CAS 例子（乐观并发更新余额）：

-- KEYS[1]=余额键 ARGV[1]=期望旧值 ARGV[2]=新值
local cur = redis.call('GET', KEYS[1])
if cur == ARGV[1] then
  redis.call('SET', KEYS[1], ARGV[2])
  return 1
else
  return 0            -- 调用方看到 0 → 说明被别人改过 → 重读重试
end

4.6 常见坑与大 value 红线

坑 1：大 value。经验红线：10KB 必须警惕，100KB 禁止，1MB 是灾难。它放大序列化耗时、网络耗时、碎片、fork 时的 COW 开销。拆分或用 Hash 分 field。
坑 2：把整个对象 JSON 塞进 String。只改一个字段也要全量读写+反序列化，且无法单独设置某字段。字段频繁变动的对象应该用 Hash（第 5 章）。
坑 3：用 String 做自增却不设上限。溢出会直接报错失败，业务要有降级。
坑 4：INCRBYFLOAT 有精度问题。它基于 long double，且多次累加会误差累积。金额场景存最小单位整数（分）用 INCRBY。
坑 5：SET NX 抢锁后设了 30 秒过期，业务跑了 40 秒。锁提前失效，第二个线程进来。必须续期（第 35 章）。
坑 6：用 TTL 判断锁是否还活着做业务决策。TTL 会变（-1/-2/剩余秒），别把它当"续期与否"的依据，owner 标志才是。
