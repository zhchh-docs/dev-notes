6.1 List 命令与方向约定

List = 有序、可重复的字符串序列，两端 O(1) 增删，中间下标访问 O(N)。

127.0.0.1:6379> RPUSH feed:user:1 a b c      # 右端插入 a,b,c → [a b c]
(integer) 3
127.0.0.1:6379> LPUSH feed:user:1 z          # 左端插入 z → [z a b c]
(integer) 4
127.0.0.1:6379> LRANGE feed:user:1 0 -1      # 0 到末尾：全部
1) "z"
2) "a"
3) "b"
4) "c"
127.0.0.1:6379> LPOP feed:user:1             # 左弹出
"z"
127.0.0.1:6379> RPOP feed:user:1             # 右弹出
"c"
127.0.0.1:6379> LLEN feed:user:1
(integer) 2
127.0.0.1:6379> LINDEX feed:user:1 0         # 按索引读，O(N)，别用来遍历
"a"
127.0.0.1:6379> LPOS feed:user:1 a           # 查值位置（6.0+，还有 RANK/COUNT 选项）
(integer) 0
127.0.0.1:6379> LINSERT feed:user:1 BEFORE b x   # 在 b 前插入 x
(integer) 3
127.0.0.1:6379> LREM feed:user:1 1 x         # 删除 1 个值为 x 的元素（负=从尾，0=全部）
(integer) 1
127.0.0.1:6379> LSET feed:user:1 0 A         # 按下标改值
OK
127.0.0.1:6379> LTRIM feed:user:1 0 99       # 只保留前 100 个 —— 限长列表神器
OK
记方向：LPOP+RPUSH（或 LPUSH+RPOP）= 队列 FIFO；LPUSH+LPOP = 栈 LIFO。画图记：把 List 想成一条横向队列，L 是 Left(左端/头部)，R 是 Right(右端/尾部)。
组合语义典型场景
LPUSH + RPOP队列 FIFO任务队列（生产在左，消费在右）
RPUSH + LPOP队列 FIFO同上，更常见的写法
LPUSH + LPOP栈 LIFO撤销栈、最新优先
LPUSH + LTRIM固定长度最新列表最新动态、最近浏览

6.2 四种典型用法

① 最新动态（Feed 最新-N 条）

# 用户发新动态：插到最左 + 只保留最近 100 条（原子地做这两件事用 Lua 或 pipeline）
127.0.0.1:6379> LPUSH feed:latest:u1 "post:9021"
(integer) 101
127.0.0.1:6379> LTRIM feed:latest:u1 0 99      # 砍掉超出的
OK
127.0.0.1:6379> LRANGE feed:latest:u1 0 9       # 取最新 10 条
# 完整对象另存：每条动态详情存 String/Hash post:9021，List 里只放 id（避免大 value 重复）

② 简单任务队列

# 生产者
127.0.0.1:6379> LPUSH queue:email '{"to":"a@b.com","tpl":"welcome"}'
(integer) 1
# 消费者（多个实例同时跑，RPOP 是原子的，不会重复拿到同一条）
127.0.0.1:6379> RPOP queue:email
"{\"to\":\"a@b.com\",\"tpl\":\"welcome\"}"
# 改进：用 BRPOP 避免空转轮询（下一节）

③ 栈（撤销历史）

127.0.0.1:6379> LPUSH undo:doc:7 "type:hello" "del:3" "paste:xx"
(integer) 3
127.0.0.1:6379> LPOP undo:doc:7        # 撤销一步：同端进出
"paste:xx"

④ 分页（谨慎使用）

127.0.0.1:6379> LRANGE comments:post:1 0 19     # 第 1 页
127.0.0.1:6379> LRANGE comments:post:1 20 39    # 第 2 页
# 坑：LRANGE 是 O(N)，N 是返回的偏移量范围。
#    取第 1000 页意味着扫描到那里 —— 深分页请用 ZSet(按时间/分数排序)

6.3 BLPOP/BRPOP：真正的阻塞队列

轮询 RPOP 会浪费 CPU 和连接；BRPOP 让 Redis 在队列为空时挂起连接，有元素再唤醒。

# 语法：BRPOP key [key ...] timeout（秒，Redis 6+ 支持小数；0 = 永久阻塞）
127.0.0.1:6379> BRPOP queue:email 5
(nil)                       # 5 秒内没数据则返回 nil
(5.03s)

127.0.0.1:6379> BRPOP queue:email 30
1) "queue:email"            # 返回 [key, value]，因为可以一次监听多个队列
2) "{\"to\":\"x@y.com\"}"
(2.41s)

# 多队列优先级示例：高并发队列优先
127.0.0.1:6379> BLPOP queue:high queue:low 0     # 0 = 无限等待
1) "queue:high"             # high 非空时优先返回它 → 天然优先级
注意点说明
连接占用阻塞期间这条连接不能复用；每个阻塞消费者至少占一条连接，连接池要算够
timeout=0永久阻塞；若连接闲置过久会被中间网络设备断开，需客户端心跳或设较大 timeout（如 30s）
公平性多个消费者阻塞时，谁先阻塞谁先获得（FIFO），可用于简单负载均衡
主从切换阻塞期间主库挂掉，客户端会收到错误连接，需要重连重试逻辑

一个健壮的消费循环伪代码：

while True:
    try:
        item = redis.brpop("queue:email", timeout=30)
        if item is None:
            continue                 # 超时重试（顺便给连接保活）
        _, payload = item
        handle(payload)              # 业务处理（失败要自己补偿，见下节）
    except RedisError as e:
        sleep(1)                     # 网络/切换异常：退避重连
        reconnect()

6.4 可靠队列：LMOVE + 备份队列

普通 List 队列的致命问题：RPOP 之后消费者崩了，消息就永久丢失了。没有 ACK 机制。

LMOVE（Redis 6.2 起，替代老的 RPOPLPUSH）可以原子地把元素从一个 List 移到另一个 List，于是有了标准的"处理中备份"模式：

# ① 消费者：原子地把任务从主队列移到 processing（处理中）队列
127.0.0.1:6379> LMOVE queue:email queue:email:processing:worker-1 RIGHT LEFT
"{\"to\":\"a@b.com\"}"

# ② 业务处理成功后：从 processing 里删除（相当于 ACK）
127.0.0.1:6379> LREM queue:email:processing:worker-1 1 "{\"to\":\"a@b.com\"}"
(integer) 1

# ③ 监视器扫描：worker 挂掉后，把超时未完成的 processing 任务移回主队列
#    LPOS / LRANGE 找出超过 60 秒的 → LMOVE 回 queue:email
127.0.0.1:6379> LRANGE queue:email:processing:worker-1 0 -1

图 6-1 LMOVE 可靠队列模型

即便如此，List 依然没有：消息重试计数、死信队列、多消费者组、消息广播、持久化回放。这些都做一遍，你就重新发明了一个残缺版的 RabbitMQ —— 所以用 Redis Stream（5.0+）或 Redisson DelayQueue，而不是硬造。

6.5 quicklist 底层与内存调优

Redis 的 List 底层是 quicklist：它是一个双向链表，但每个节点内部是一个 listpack（紧凑数组）。这样兼顾了两头的 O(1) 和内存紧凑。

127.0.0.1:6379> CONFIG GET list-max-listpack-size
1) "list-max-listpack-size"
2) "-2"      # 正数=每个 listpack 节点最多几个 entry（如 512）
             # -1=每个节点≤4KB  -2=每个节点≤8KB  -3=每个节点≤16KB … 默认是 -2
127.0.0.1:6379> CONFIG GET list-compress-depth
1) "list-compress-depth"
2) "0"       # 0=不压缩；1=头尾各1个节点不压缩其余压缩；2=头尾各2个…
参数调小的效果调大的效果
list-max-listpack-size节点更小更碎，内存略增但随机写更快更省内存，但插入要搬运更多数据
list-compress-depth几乎不压缩（推荐 0，除非你是纯追加型大列表）中间节点 LZF 压缩，节省内存但访问要解压

绝大多数场景保持默认。只有当你的 List 主要作为"追加日志 + 极少读中间元素"时，list-compress-depth 1~2 才有明显内存收益。

6.6 常见坑与 List vs Stream

坑 1：LRANGE key 0 -1 拉一个大列表 ⟶ 等同于 KEYS * 事故。分批或用 LRANGE 限定范围。
坑 2：LINDEX/LREM/LINSERT 都是 O(N)，别在循环里对每个元素调用。
坑 3：del 一个百万元素的 List 会阻塞主线程 → 用 UNLINK 或惰性删除配置。
坑 4：忘了 LTRIM， feed 列表无限增长 —— 每次 LPUSH 都要同步 LTRIM（可以放进 Lua 保证原子）。
坑 5：List 没有去重能力，同一条消息可能被多次 LPUSH（幂等要靠 Set/String 额外判重）。
坑 6：把 List 当成"可以随机读第 N 个元素"的数组。它不是，用后立即转向 ZSet 或真正的存储。
维度ListStream（5.0+）
消费组无（所有消费者抢同一队列）有（同组负载均衡，不同组广播）
ACK 机制需自己造（LMOVE）原生 XACK + PEL 重试
消息持久化/回放消费即消失保留在流里，可按 ID 回放
自动 ID无服务器生成时间戳序号 ID
适用轻量队列、最新列表、栈真正的事件流、可靠 MQ

✓ 本章小结

要点一句话
结构有序可重复序列，两端 O(1)，中间 O(N)
方向RPUSH+LPOP=队列；LPUSH+LPOP=栈；LPUSH+LTRIM=最新 N 条
阻塞消费BRPOP/BLPOP，timeout=0 永久阻塞；每消费者占一条连接
可靠队列LMOVE 到 processing 队列，成功后 LREM；监控超时移回
底层quicklist = 双向链表 of listpack；一般保持默认配置
何时换 Stream需要 ACK、消费组、历史回放时
Lua 组合LPUSH+LTRIM 应放进 Lua 保证原子，否则可能写到一半崩溃
