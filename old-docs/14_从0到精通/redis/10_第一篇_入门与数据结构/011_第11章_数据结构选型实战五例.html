◆本章目标与选型方法论

  • 把前九章的结构知识落到五个真实业务里，每个都给出命令 + 理由 + 坑；

选型四问（先问再选）

  1. 怎么查？——按 key 精确查（所有结构都行）、按 member 查（Set/ZSet/Hash）、按范围/排序查（ZSet/List）、根本不支持（嵌套查询）。
  2. 怎么改？——整块覆盖（String JSON）、局部字段（Hash）、加减数值（INCR/HINCRBY/ZINCRBY）。
  3. 量多大？——百万/亿级要用特殊结构（Bitmap/HLL），且必须考虑分片避免大 key。
  4. 要什么性质？——去重（Set/ZSet）、有序（ZSet/List）、抢占式唯一（String NX）、时间衰减（TTL）。

11.1 例一：购物车（Hash + String 的取舍）

需求：每个用户一个购物车；加入商品、改数量、删商品、查全部商品与数量、显示总价。

# ✅ 主结构：Hash —— field = skuId, value = 数量
127.0.0.1:6379> HSET cart:u1001 sku:88 2 sku:99 1
(integer) 2
127.0.0.1:6379> HINCRBY cart:u1001 sku:88 1        # 加一件，原子
(integer) 3
127.0.0.1:6379> HINCRBY cart:u1001 sku:88 -1       # 减一件
(integer) 2
127.0.0.1:6379> HDEL cart:u1001 sku:99             # 删除某个商品
(integer) 1
127.0.0.1:6379> HGETALL cart:u1001                 # 展示全部（购物车商品通常 < 100，安全）
127.0.0.1:6379> HLEN cart:u1001                    # 商品种类数（小红点角标）
(integer) 1
问题方案说明
选中/未选中状态额外一个 Set：cart:chk:u1001Set 存选中的 skuId
价格总额读 HGETALL 后在应用层算，或维护一个 Hash field _total价动态变，别在 Redis 里做本该 DB 做的事
数量上限校验HINCRBY 后判断返回值是否 > 库存/上限超限再 HINCRBY 减回来
TTL登录用户可不过期；游客购物车必须设 30 天EXPIRE cart:guest:xxx 2592000
为什么不用 String 存 JSON？因为购物车频繁修改单个商品的数量，用 JSON 要"读全部→反序列化→改→序列化→写回"，既慢又有并发覆盖风险（A 改数量时 B 的改动被覆盖）。频繁改单个字段 = Hash 的典型特征。
坑：把整个商品对象（图片、标题、价格）也塞进 Hash 的 value → 一是违反"value 只放最小必要信息"，二是价格更新后购物车里就是脏数据。购物车只存「skuId + 数量」，展示时再去查商品服务/缓存。

11.2 例二：用户签到与活跃标记（Bitmap）

需求：记录某用户当月哪几天签到了；支持补签、连续签到天数、显示整月日历。

# key：sign:{userId}:{yyyyMM}   offset = 日期 - 1
127.0.0.1:6379> SETBIT sign:1001:202610 0 1       # 1 号签到
(integer) 0
127.0.0.1:6379> SETBIT sign:1001:202610 18 1      # 19 号补签
(integer) 0
127.0.0.1:6379> BITCOUNT sign:1001:202610         # 本月签到次数
(integer) 2
127.0.0.1:6379> GETBIT sign:1001:202610 18        # 19 号签到了吗
(integer) 1
需求方案理由
日历展示一次 GET 整个 bitmap，客户端按 bit 解析一个月仅 4 字节
连续签到天数另存 Hash：HSET sign:meta:1001 streak 5 last 20261019Bitmap 不擅长连击计算
今天全站签到人数另存当天 Set 或按天一个 bitmap + BITCOUNT反查需要倒排
跨月按月分 key，天然便于归档清理旧月份自动失去访问
坑：把 userId 直接当 offset。userId 若是不连续的大数值（如雪花 ID = 18 位），SETBIT key 123456789012345 1 会直接分配 15TB 内存。Bitmap 的 offset 必须是小而连续的编号。

11.3 例三：Feed 信息流（List vs ZSet）

需求：用户首页展示关注的人发的最新动态；支持下拉刷新（拉最新）、上翻加载更多。

方案做法适用
推模式（List）每个用户一个 List，作者发文时推给所有粉丝粉丝量小、读多写少（朋友圈）
拉模式（ZSet）每个作者一个 ZSet（score=时间戳），读时合并大 V、百万粉丝（推模式会炸）
推拉结合普通用户推，大 V 单独拉（业界主流）真实互联网规模
 
# 推模式：粉丝 feed list 里只放动态 id，详情另存 String/Hash
127.0.0.1:6379> LPUSH feed:u1001 post:9901 post:9902
(integer) 2
127.0.0.1:6379> LTRIM feed:u1001 0 999            # 只保留最新 1000 条（必须！）
OK
127.0.0.1:6379> LRANGE feed:u1001 0 9             # 前 10 条
127.0.0.1:6379> MGET post:9901 post:9902          # 批量取详情

# 拉模式：作者自己一栏 ZSet（score = 发布时间戳）
127.0.0.1:6379> ZADD author:feed:u777 1761235260000 post:9901
127.0.0.1:6379> ZREVRANGEBYSCORE author:feed:u777 +inf 1761200000000 LIMIT 0 20
坑 1：只 LPUSH 不 LTRIM → 活跃用户 feed list 变成几十万元素的大 key（第 17 章）。把 LPUSH + LTRIM 放进一个 Lua 保证原子。
坑 2：List 深分页。用户翻到第 500 页时 LRANGE key 5000 5009 依然要走到那个偏移；ZSet 按时间戳做游标分页（ZREVRANGEBYSCORE + 上一页最小 score）才是正解。
坑 3：把动态正文塞进 List。同一条动态被推给 1000 个粉丝就是 1000 份拷贝。List 里只放 id。

11.4 例四：点赞 / 收藏 / 关注（Set + ZSet）

需求：判断某用户是否点过赞；统计点赞总数；展示点赞用户列表（前 20 个）；热点要防刷。

# 每个动态一个 Set：member = userId
127.0.0.1:6379> SADD like:post:9901 u1001 u1002
(integer) 2
127.0.0.1:6379> SISMEMBER like:post:9901 u1001      # 我点过吗 → 1
(integer) 1
127.0.0.1:6379> SCARD like:post:9901                # 点赞总数
(integer) 2
127.0.0.1:6379> SREM like:post:9901 u1001           # 取消点赞
(integer) 1
127.0.0.1:6379> SRANDMEMBER like:post:9901 20       # 随机展示 20 个头像

# 需要"按时间排序展示最新点赞" → 换 ZSet（score = 时间戳）
127.0.0.1:6379> ZADD like:postsorted:9901 1761235260000 u1001
127.0.0.1:6379> ZREVRANGE like:postsorted:9901 0 19 WITHSCORES
升维需求做法说明
点赞总数要快额外 INCR like:count:9901 计数SCARD 其实 O(1)，但跨 key 聚合时计数更省
共同关注SINTER follow:u1 follow:u2见第 7 章
关注上限/防刷Set 自然去重 + SCARD 判上限幂等免费
亿级点赞数用 String counter + 异步落库Set 存 member 会爆炸
危机场景：一条爆款动态有 500 万点赞，SCARD 依然是 O(1) 没问题，但 SMEMBERS / SUNION / 迁移备份时会产生大 key 问题。
对策：① 热门内容拆分为多个 Set（like:post:9901:{slot}）；② 总数用独立 counter；③ 老数据定期归档到 DB。

11.5 例五：搜索联想与热门榜单（ZSet + String）

需求：输入框联想（输入"red" → redis redisson…）；搜索热榜 Top10。

# ① 热<｜hy_place▁holder▁no▁813｜>：每个词一个分数，实时累加（ZINCRBY）
127.0.0.1:6379> ZINCRBY search:hot 1 redis
"1024"
127.0.0.1:6379> ZREVRANGE search:hot 0 9 WITHSCORES       # Top10 热搜
1) "redis"      2) "1024"
3) "redisson"   4) "886"
127.0.0.1:6379> ZREMRANGEBYRANK search:hot 0 -101         # 只留 Top100，定期瘦身

# ② 联想词：按词前缀分组（这里是 ZSet + 成员自身字典序的组合用法）
127.0.0.1:6379> ZADD suggest 0 redis 0 redisson 0 redis-cli 0 spring
(integer) 4
# 用 ZRANGEBYLEX 做前缀匹配（分数都为 0 时，按成员字典序）
127.0.0.1:6379> ZRANGEBYLEX suggest "[red" "[red\xff" LIMIT 0 10
1) "redis"
2) "redis-cli"
3) "redisson"

# ③ 更好的做法：给每个联想词一个热度分，并用 ZRANGEBYLEX + 客户端排序，
#    或者干脆按前缀建立独立 key（suggest:red / suggest:redis）避免全量扫描
需求结构命令
实时热榜ZSetZINCRBY + ZREVRANGE
历史热榜(昨日/上周)ZSet + 定时归档ZUNIONSTORE 或 RENAME 换 key
前缀联想ZSet + ZRANGEBYLEX注意成员必须是同前缀、分数相同
专业搜索别用 RedisES / Lucene / 倒排索引
坑：ZRANGEBYLEX 要求所有成员分数相同才能按字典序排；一旦你给联想词加了热度分，就必须用"前缀专用 key"（suggest:red）或者改用 ZRANGEBYSCORE。Redis 没有真正的"前缀 + 排序"复合索引。

11.6 通用选型速查表与常见坑

如果你需要…首选次选千万别
整块对象缓存String(JSON)Hash把对象拆成几十个独立 key
频繁改对象的某字段Hash—String 全量读写
计数器String INCRHash HINCRBYMySQL count(*)
去重 + 判是否存在SetBitmap（整数 id）HLL（不支持判存在）
只要去重后的总数（亿级）HyperLogLog—Set（内存爆炸）
排行榜 / 按权重排序ZSetList（仅按插入序）Set（无序）
最新 N 条List + LTRIMZSet（需要 score 排序时）只用 List 不 LTRIM
轻量队列List(BRPOP)Stream（需要 ACK）把 List 当可靠 MQ
二值标记（签到）BitmapSetBitmap + 大 offset
地理位置GEO—自己在应用层算球面距离
最后一句：真实业务往往是 2-3 个结构协作——Hash 存主体、ZSet 做索引/排行、Set 做标记、String 做计数。硬要用单一结构实现所有需求，是把 Redis 用歪的开始。

✓ 本章小结

案例结构组合与要点
购物车Hash（skuId→数量）+ Set（选中项）；只存最小信息，价格详情去别处查
签到Bitmap（按月 key）+ Hash（存连续天数）；offset 必须小而连续
FeedList 推模式 / ZSet 拉模式 / 推拉结合；LPUSH 必配 LTRIM
点赞Set（判存在+去重）+ counter（计数）；大爆款要拆分
搜索联想ZSet(ZINCRBY 热榜) + ZRANGEBYLEX(前缀)；专业搜索用 ES
选型四问怎么查 / 怎么改 / 量多大 / 要什么性质
