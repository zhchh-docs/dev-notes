3.1 通用命令：这一页能覆盖你 60% 的操作

通用命令是"对所有类型都生效"的那批命令，它们操作的是 key 本身，而不是 value 内容。

127.0.0.1:6379> SET user:1001 '{"name":"张三","age":28}' EX 3600
OK

127.0.0.1:6379> EXISTS user:1001        # 存在几个（可接受多个 key，返回总数）
(integer) 1
127.0.0.1:6379> TYPE user:1001          # 类型
string
127.0.0.1:6379> TTL user:1001           # 剩余秒数；-1=永不过期 -2=不存在
(integer) 3592
127.0.0.1:6379> PTTL user:1001          # 毫秒精度
(integer) 3591877
127.0.0.1:6379> EXPIRE user:1001 60     # (重)设 60 秒过期
(integer) 1
127.0.0.1:6379> PERSIST user:1001       # 去掉过期，变永久
(integer) 1
127.0.0.1:6379> EXPIREAT user:1001 1756800000   # 指定到某个 Unix 秒到期
(integer) 1
127.0.0.1:6379> TOUCH user:1001         # 只更新访问时间(LRU/LFU)，不改 TTL
(integer) 1
127.0.0.1:6379> DEL user:1001           # 同步删除
(integer) 1

批量与时髦命令：

# 一次删多个（返回真正删掉的个数）
127.0.0.1:6379> DEL k1 k2 k3
(integer) 2

# 异步删除：大 key 一定要用它，避免阻塞主线程（第 17 章）
127.0.0.1:6379> UNLINK big:list
(integer) 1

# 原子改名：目标存在则覆盖
127.0.0.1:6379> RENAME user:1001 user:1002
OK
127.0.0.1:6379> RENAMENX user:1002 user:1003     # 目标不存在才改（NX）
(integer) 1

# 其它
127.0.0.1:6379> EXISTS a b c            # 多个一起判存在
127.0.0.1:6379> COPY src dst DB 1       # 6.2+：复制到另一个库
127.0.0.1:6379> DUMP user:1001          # 序列化导出（配合 RESTORE 迁移）
127.0.0.1:6379> RANDOMKEY               # 随机返回一个 key（调试/抽样用）
127.0.0.1:6379> OBJECT IDLETIME user:1001   # 空闲秒数（需 maxmemory-policy 为 LRU）

过期相关的三条"条件型"命令（Redis 7 新增，做限时任务很顺手）：

127.0.0.1:6379> EXPIRE order:9001 600 NX    # NX：仅当 key 没有 TTL 时才设置
127.0.0.1:6379> EXPIRE order:9001 600 XX    # XX：仅当已有 TTL 才覆盖
127.0.0.1:6379> EXPIRE order:9001 600 GT    # GT：新 TTL 更长才生效
127.0.0.1:6379> EXPIRE order:9001 600 LT    # LT：新 TTL 更短才生效
易错：对一个已经存在的 key 执行 SET（不带 KEEPTTL），会清掉原有 TTL，让它变成永不过期！这是一个极其常见的内存泄漏源头。
127.0.0.1:6379> SET token:abc xyz EX 300
OK
127.0.0.1:6379> TTL token:abc
(integer) 297
127.0.0.1:6379> SET token:abc newval        # ← TTL 没了！
OK
127.0.0.1:6379> TTL token:abc
(integer) -1
127.0.0.1:6379> SET token:abc newval2 KEEPTTL   # ← 正确写法：保留剩余 TTL
OK

3.2 TYPE 与 OBJECT ENCODING：看清 key 的真身

TYPE 看的是对外类型（string/hash/list/set/zset/stream…），OBJECT ENCODING 看的是底层实现。同一个对外类型可能有两种甚至三种底层编码，Redis 会根据大小自动切换——这是 Redis 省内存的秘密。

127.0.0.1:6379> SET s1 12345
OK
127.0.0.1:6379> TYPE s1
string
127.0.0.1:6379> OBJECT ENCODING s1
int                      # 能表示为整数时，直接用整数存，省去 SDS 开销

127.0.0.1:6379> SET s2 hello-world-this-is-a-long-normal-string
OK
127.0.0.1:6379> OBJECT ENCODING s2
embstr                   # ≤44 字节用 embstr：一次内存分配，redisObject+SDS 连续

127.0.0.1:6379> SET s3 <60 字节以上的字符串>
127.0.0.1:6379> OBJECT ENCODING s3
raw                      # 超过阈值（3.2 起是 44 字节）用 raw：两次分配

127.0.0.1:6379> RPUSH small 1 2 3
(integer) 3
127.0.0.1:6379> OBJECT ENCODING small
listpack                 # 小列表：紧凑连续内存，无需指针
127.0.0.1:6379> CONFIG SET list-max-listpack-size 2
OK
127.0.0.1:6379> RPUSH small 4 5 6 7
127.0.0.1:6379> OBJECT ENCODING small
quicklist                # 超阈值后转 quicklist（linked list of listpack）
对外类型紧凑编码（省内存）标准编码（快）切换阈值配置项
Stringint / embstrraw字符串 44 字节
Hashlistpack（原 ziplist）hashtablehash-max-listpack-entries 128 / -value 64
Listlistpack / quicklistquicklist + 节点list-max-listpack-size -2
Setintset / listpackhashtableset-max-intset-entries 512
ZSetlistpackskiplist + dictzset-max-listpack-entries 128 / -value 64

记住这条：【小数据用紧凑编码省内存，大数据换回标准编码保性能】。这也解释了为什么"把大 Hash 拆成多个小 Hash"（第 17 章大 key 治理）在 Redis 里是有效的优化手段。

另外两个常用：

127.0.0.1:6379> OBJECT REFCOUNT s1     # 引用计数（共享整数对象时 > 1）
(integer) 2147483647
127.0.0.1:6379> MEMORY USAGE user:1001  # 估算这个 key 占多少字节
(integer) 128
127.0.0.1:6379> MEMORY USAGE user:1001 SAMPLES 10   # 采样更准（聚合类型）

3.3 为什么 KEYS 是生产禁令

一句话：KEYS 是 O(N) 且不可中断，Redis 单线程会在它执行期间停止响应一切请求。

127.0.0.1:6379> KEYS *
1) "user:1001"
2) "user:1002"
... （返回全部，假如有 2000 万个，它要遍历完才肯干活）
127.0.0.1:6379> KEYS user:1*          # 注意：不是服务端过滤后才返回，是全遍历后模式匹配
真实的量级账：1000 万 key 的实例，KEYS user:* 大约要几百毫秒到数秒。这期间：
  • 所有业务请求超时 → 上游重试 → 流量翻几倍 → 雪崩（第 25 章）；
  • 哨兵的心跳收不到 → 误判主库下线，触发一次不必要的故障切换（第 44 章）；
  • 返回结果还会撑爆客户端内存。

那怎么"看看有多少个 user: 开头的 key"？三个安全选项：

方法做法适用
DBSIZEDBSIZE 直接读计数只想知道总量，O(1)，随便跑
SCANSCAN 0 MATCH user:* COUNT 500要真的遍历/统计/处理，标准答案
自己维护业务侧用 Hash/Set 记录索引长期需要按模式查询的设计（推荐）

还应该在团队层面做防护：

# redis.conf：把危险命令改名或禁用
rename-command KEYS ""
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG "CONFIG-8f3a2b"    # 改名：自己人可用，脚本小子猜不到

3.4 SCAN 家族的正确用法

SCAN 是游标式增量迭代：每次只扫一小片，返回一个新游标，客户端分批推进。它不会阻塞，代价是：

  • 可能返回重复元素：客户端要去重（用 Set 或业务幂等）；
  • 迭代期间有改动时可能漏/可能多：它是"某时刻快照的一致性弱保证"；
  • COUNT 不是"每次返回 COUNT 个"，而是"每批扫描的桶数提示值"，默认 10；返回 0 个也很正常。
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 500
1) "176"                     # ① 下一批的游标
2) 1) "user:1001"            # ② 本批结果
   2) "user:1007"
127.0.0.1:6379> SCAN 176 MATCH user:* COUNT 500
1) "0"                       # 游标回到 0 = 一轮遍历结束
2) 1) "user:1012"

每种结构都有自己的 SCAN（不要用 SCAN 去遍历 Hash 的 field，用 HSCAN）：

命令遍历对象示例
SCANkey 空间SCAN 0 MATCH order:* COUNT 1000
HSCANHash 的 fieldHSCAN user:1001 0 MATCH addr* COUNT 100
SSCANSet 成员SSCAN tags:global 0 COUNT 100
ZSCANZSet 成员+分数ZSCAN rank:daily 0 COUNT 100

安全删除"某前缀的全部 key"的标准写法（用 UNLINK 且分批，千万不要 redis-cli KEYS x | xargs DEL）：

# 方式一：一行搞定（redis-cli 内置 --scan，走的就是游标）
redis-cli --scan --pattern "cache:product:*" --count 1000 | xargs -L 200 redis-cli UNLINK

# 方式二：Lua 分批删除（几百个一组，避免单次命令过大）
# 注意：Cluster 下要逐节点执行，且 Lua 里的 key 必须在同一 slot（第 47 章）
redis-cli EVAL "local ks=redis.call('SCAN',ARGV[1],'MATCH',ARGV[2],'COUNT',1000)
if ks[2] and #ks[2]>0 then redis.call('UNLINK',unpack(ks[2])) end
return {ks[1], #ks[2]}" 0 0 "cache:product:*"
坑：在生产的一次性脚本里用 Lua 做全库 SCAN+DEL，如果 key 上千万，脚本执行时间依然很长；Redis 的 Lua 脚本是原子执行的，同样会阻塞。务必在外层按游标分批、每批 1000-5000 个、批间 sleep 几十毫秒。

3.5 key 命名规范：一套用三年的约定

命名规范的三个目标：可读（人能猜出是什么）、可管（能批量操作与统计）、可控（长度合适、有 TTL）。

① 结构：业务:子对象:标识[:子标识]

user:profile:1001            用户 1001 的资料（Hash）
user:token:abc123            登录 token（String，TTL）
order:detail:20240915:7788   订单详情（含业务日期，便于按天管理）
product:stock:1001           商品库存（String）
rank:weekly:2026W42          周榜（ZSet）
lock:order:pay:7788          分布式锁（String，短 TTL）
cache:api:/v1/home?city=bj   接口级缓存（Hash key + field=参数 hash）

② 四条硬规则

  1. 统一小写 + 冒号分隔：Redis 的 key 是二进制安全的，但团队约定统一最省心；冒号是事实标准（Spring Cache / 各种可视化工具都按冒号分层显示）。
  2. 长度控制在 40 字符内：1000 万个 key，每个多 10 字节就多 ~100MB 内存（还要算 SDS 与 dict 开销）。用缩写：product → prd，detail → dtl。
  3. 必带业务前缀：没有前缀 = 无法统计、无法批量删除、无法拆分。强烈反感 SET 1001 xxx 这种写法。
  4. 每个 key 都要有 TTL：除非它是必须从硬盘恢复的基础数据（即便如此也建议用永不过期 + 主动管理的白名单）。

③ 用命名空间表固化下来

前缀类型TTL 策略归属服务
cache:*Hash/String10-30 分钟 + 随机抖动all（可随时删）
session:*Hash30 分钟滑动续期auth-service
lock:*String10-30 秒各服务（禁止误删）
rank:*ZSet按周期 + 定期归档activity-service
mq:*List/Stream视消费情况job-service

把这张表放进 README / Confluence，并在 Code Review 清单里加一条："新加的 Redis key 有没有前缀？有没有 TTL？"（第 29 章会给出完整模板）。

④ 命名里不要做的事

  • 不要在 key 里放可能变化的业务值（如用户名），否则改名时缓存追踪不到；用稳定的 id。
  • 不要在 key 里塞完整 URL 或未转义的参数：太长且可能含特殊字符。用 md5/crc32 摘要（cache:api:a1b2c3d4）。
  • 不要依赖 SELECT 分库做业务隔离（见第 2 章），Cluster 模式下会直接失效。

3.6 常见坑：命令与命名的雷区

坑 1：EXISTS 传多个 key 返回的是存在的总数而不是逐个结果，别当成 [0,1,1] 用。
坑 2：TTL 返回 -1（永久）和 -2（不存在）是两个完全不同的含义；很多 bug 来自"if ttl < 0 then 续期"，结果对不存在的 key 做了无效操作。
坑 3：EXPIRE 之后又 SET 同 key，TTL 被清。修复用 SET ... KEEPTTL 或先读 TTL 再设。
坑 4：以为 DEL 很快就用它删几十万元素的集合。释放内存本身有成本，一律 UNLINK 或配置 lazyfree-lazy-user-del yes。
坑 5：删除主键忘了删索引/辅助 key，产生"孤儿缓存"。把所有相关 key 放进同一个 Lua 脚本或一个事务删。
坑 6：key 里用中文/emoji。技术上支持（二进制安全），但排查、可视化、迁移工具都容易出问题。
坑 7：不同环境（dev/test/prod）共用同一个 Redis 实例且 key 前缀相同 → 数据互相污染。至少加 {env}: 前缀，或直接分开实例。
