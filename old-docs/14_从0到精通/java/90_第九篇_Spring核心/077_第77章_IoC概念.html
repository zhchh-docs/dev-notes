77.1 从 new 的烦恼说起

// 第 74 章的组装代码——问题在"new 的传染性"
public class OrderService {
    // 每个 Service 都要自己 new 依赖；依赖一深就是连环 new
    private UserDao userDao = new UserDaoJdbc(new HikariDataSource(buildCfg()));
    private PayClient payClient = new PayClient("https://pay.example.com", "key");
    private MailSender mailSender = new SmtpMailSender("smtp.example.com", "pwd");
    // 想换实现？想共享同一个连接池？想在测试时替换？——处处要改代码
}
  • 重复创建：每个 new 都造一份新实例，连接池等重资源无法共享；
  • 强耦合：类名写死在代码里，换实现要改源码重编译；
  • 难测试：单测 UserService 就真的连上了数据库（第 99 章会修）；
  • 装配散落：谁依赖谁散布在几十个文件里，心智负担大。
解决思路一句话：把"对象的创建与装配"从业务类里抽出去，交给一个专门的容器统一管理——这就是控制反转。

77.2 IoC 与 DI：概念辨析

一句话定位：IoC（Inversion of Control）是思想——把控制权交给容器；DI（Dependency Injection，依赖注入）是实现该思想的主要手段——容器把依赖"塞"进对象。

图 77-1 控制反转：从主动创建到被动接收

好莱坞原则的类比："别打电话给我们，我们会打给你"——你不来找我创建，我把依赖送上门。

77.3 容器做什么：一个迷你 IoC

import java.util.*;
import java.util.function.Supplier;

/** 迷你 IoC 容器：注册 → 创建 → 注入 → 复用（Spring 的灵魂简化版） */
public class MiniContainer {
    private final Map<Class<?>, Supplier<?>> factories = new HashMap<>();
    private final Map<Class<?>, Object> singletons = new HashMap<>();

    public <T> void register(Class<T> type, Supplier<T> factory) {
        factories.put(type, factory);
    }
    @SuppressWarnings("unchecked")
    public <T> T get(Class<T> type) {
        if (singletons.containsKey(type))          // 单例缓存
            return (T) singletons.get(type);
        T obj = (T) factories.get(type).get();     // 创建
        singletons.put(type, obj);
        return obj;
    }
    public static void main(String[] args) {
        MiniContainer c = new MiniContainer();
        c.register(UserDao.class, () -> new UserDaoJdbc(PoolHolder.get()));
        c.register(UserService.class, () ->           // 装配：注入依赖
            new UserService(c.get(UserDao.class)));
        UserService svc = c.get(UserService.class);    // 使用者不 new，只索取
        System.out.println(svc.getClass());
    }
}

容器的三大职责：注册（知道有哪些类）、装配（知道谁依赖谁）、管理（单例复用、生命周期）。Spring 容器做的就是这三件事的豪华版。

77.4 Spring 容器初见

import org.springframework.context.annotation.*;

@Configuration                     // 配置类：容器的"装配图纸"
@ComponentScan("demo")             // 扫描 demo 包下带注解的组件
public class AppConfig { }

@Component                          // 组件：注册进容器的 Bean
public class UserService {
    private final UserDao userDao;
    public UserService(UserDao userDao) {   // 单构造器自动注入，无需 @Autowired
        this.userDao = userDao;
    }
}

public class Main {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
            UserService svc = ctx.getBean(UserService.class); // 容器取用
            System.out.println(svc);
        }
    }
}
  • ApplicationContext 是 Spring IoC 容器的代表接口；
  • @Component/@Service/@Repository/@Controller 是语义化分层组件注解（本质相同）；
  • getBean 可以按类型、按名称取；实际开发中你几乎从不手动 get——组件自己被注入（下一章）。

77.5 Bean 注册的四种方式

方式写法适用
组件扫描@Component + @ComponentScan自己写的业务类（主流）
Java 配置@Configuration + @Bean 方法第三方类、需要定制构造过程
自动装配条件@ConditionalOnXxx（Boot 章节）starter 生态
XML / @Import遗留或批量导入老项目兼容
 
@Configuration
public class DataConfig {
    @Bean                                    // HikariDataSource 是第三方类，用 @Bean 注册
    public HikariDataSource dataSource() {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl("jdbc:mysql://localhost:3306/jdbc_demo");
        cfg.setMaximumPoolSize(10);
        return new HikariDataSource(cfg);
    }
    @Bean                                    // 依赖另一个 @Bean：参数注入，自动装配
    public UserDao userDao(DataSource ds) { return new UserDaoJdbc(ds); }
}

常见坑：@Bean 方法之间不要互相直接调用（userDao(dataSource()) 会绕过代理造成重复实例），要靠参数注入让容器接手——CGLIB 代理已保证配置类内部调用也走单例，但显式参数注入最清晰。

✓ 本章小结

要点一句话
IoC 是什么对象创建与装配的控制权交给容器；业务类只声明需要
IoC vs DIIoc 是思想，DI（构造器/字段注入）是实现手段
容器职责注册、装配、管理（单例与生命周期）
注册方式组件扫描（业务）+ @Bean（第三方/定制）为主
装配心智写代码时不 new；组装发生在容器启动时
