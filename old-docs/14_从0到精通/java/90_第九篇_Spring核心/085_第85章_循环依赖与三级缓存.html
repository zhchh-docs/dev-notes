85.1 什么是循环依赖

一句话定位：两个或多个 Bean 之间形成依赖闭环——A 需要 B，B 又需要 A，容器创建 A 时被要求先给 B，创建 B 时又回头要 A。

// 形态一：字段注入循环（Spring 可解，单例 + setter/字段）
@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService;
}

@Service
public class PaymentService {
    @Autowired
    private OrderService orderService;
}

// 形态二：构造器注入循环（Spring 无法解决，启动直接报错）
@Service
public class OrderService {
    private final PaymentService paymentService;
    public OrderService(PaymentService paymentService) { this.paymentService = paymentService; }
}

@Service
public class PaymentService {
    private final OrderService orderService;
    public PaymentService(OrderService orderService) { this.orderService = orderService; }
}

// 形态三：三方以上环：A → B → C → A；原理与双方环相同，只是链路更长
版本提醒：Spring Boot 2.6 起默认禁止循环依赖（spring.main.allow-circular-references=false），即使是字段/setter 循环也会启动失败；需要显式在配置中开启该开关才能沿用旧行为。新项目的正确做法是重构解耦，而不是打开开关掩盖设计问题。

85.2 构造器注入为什么无解

一句话定位：构造器注入要求对象在诞生那一刻依赖就必须到位；而循环双方都还没诞生，谁也拿不出一个完整对象交给对方——逻辑上不存在"先有鸡还是先有蛋"的出路。

// 容器视角推演构造器循环：
// 1. 要创建 OrderService → 调用构造器，参数需要 PaymentService
// 2. 去创建 PaymentService → 调用构造器，参数需要 OrderService
// 3. OrderService 尚在创建中，连实例都还没 new 出来，无法作为参数传入
// 4. 死锁式等待：双方都卡在构造器参数上，容器抛出
//    BeanCurrentlyInCreationException: Error creating bean ...

// 对比字段注入：
// 1. 先 new OrderService()（无参构造，对象先诞生，字段暂为 null）
// 2. 把"半成品 OrderService"登记起来，再去注入它的字段
// 3. 创建 PaymentService，注入字段时拿到那个半成品 OrderService 引用
// 4. PaymentService 完成；回到 OrderService 注入 PaymentService，闭环解除
// 关键区别：对象创建与依赖装配被拆成两步，中间允许"半成品"先被引用
注入方式创建与装配的关系循环依赖可解性
构造器注入对象诞生即完成装配，二者不可分割不可解，启动期报错
setter 注入先创建对象，再调 setter 装配单例场景可被三级缓存解开
字段注入先创建对象，反射填字段同上可解（但不推荐作为解法依赖）
prototype 作用域容器不缓存实例，无早期暴露机制不可解，启动报错
金句：构造器注入"循环依赖直接报错"其实是优点——它在启动期就暴露设计耦合；字段注入能被缓存掩盖问题，不代表循环依赖是合理的。

85.3 三级缓存结构与创建流程

一句话定位：Spring 用三个 Map 分层存放"成品 Bean、早期暴露对象、对象工厂"，让循环双方在对象尚未装配完成时就能拿到一个合法引用。

缓存（Map）别名存放内容
singletonObjects一级缓存（成品池）装配完成、可对外使用的单例 Bean；正常 getBean 先查这里
earlySingletonObjects二级缓存（早期对象池）已创建但尚未装配完成的 Bean 引用；循环依赖中被提前引用过的对象在此停留
singletonFactories三级缓存（对象工厂池）生成早期引用的 ObjectFactory；需要时调用其 getObject() 产出早期对象（可能是代理）

图 85-1 三级缓存协作：半成品先入工厂池，被循环方引用时提升到早期对象池，最终入成品池

// 三级缓存查找顺序（容器 getBean 的简化逻辑）：
Object getSingleton(String beanName) {
    Object bean = singletonObjects.get(beanName);          // ① 先查成品
    if (bean == null) {
        bean = earlySingletonObjects.get(beanName);        // ② 再查早期对象
        if (bean == null) {
            ObjectFactory<?> factory = singletonFactories.get(beanName);
            if (factory != null) {
                bean = factory.getObject();                // ③ 工厂产出早期引用
                earlySingletonObjects.put(beanName, bean); // 提升到二级缓存
                singletonFactories.remove(beanName);
            }
        }
    }
    return bean;
}

85.4 为什么是三级而不是两级

一句话定位：如果所有 Bean 都不需要代理，两级缓存（成品池 + 早期对象池）就够了；正因为 AOP 可能为 Bean 生成代理，必须先缓存一个"工厂"，等到真正需要早期引用时才决定暴露原始对象还是代理对象，保证全程引用一致。

85.4.1 两级缓存的设想与缺口

假设只有一级成品池和二级早期对象池：A 刚 new 出来就直接放进二级缓存。若 A 需要被 AOP 增强（例如带事务、日志切面），真正对外暴露的应该是 A 的代理对象，而不是原始 A。问题在于：代理通常在 Bean 初始化完成后的后置处理器阶段才创建——循环引用发生时，A 还没走到那一步，此时放进二级缓存的到底是原始对象还是代理？

85.4.2 三级缓存的解法

// 三级缓存存的是 ObjectFactory（lambda 形式）：
// 第一次被循环方需要时才执行 getObject()，在其中调用 BeanPostProcessor
// 完成 AOP 代理创建；结果（代理或原始对象）放入二级缓存，之后所有引用拿到同一个。
//
// 时序保证：
// 1. A 无代理需求 → factory.getObject() 返回原始 A，二级缓存存原始对象；
// 2. A 有代理需求  → factory.getObject() 返回代理对象，二级缓存存代理；
// 3. 无论哪种，B 注入的早期引用与 A 最终成品对外暴露的引用是同一个，
//    不会出现"B 拿着原始 A、容器里却是代理 A"的错乱。
//
// 一句话：第三级缓存把"是否需要代理"的决策推迟到第一次被引用时，
// 并用二级缓存锁定结果，保证代理只创建一次、引用全程一致。
层级解决什么没有它会怎样
一级 singletonObjects成品复用，正常取用路径每次返回新对象，单例语义破坏
二级 earlySingletonObjects缓存已暴露的早期引用，避免重复创建代理同一 Bean 可能被创建出多个代理对象，引用不一致
三级 singletonFactories延迟决策暴露原始对象还是代理对象循环发生时被迫提前创建代理，时序与普通 Bean 不一致

85.5 替代方案：@Lazy 与 @DependsOn

一句话定位：遇到循环依赖，工程上优先用 @Lazy 推迟一方的注入时机；@DependsOn 只用于强制初始化顺序，不解决循环本身。

// 方案一：@Lazy 标注注入点，注入代理占位，首次方法调用时才解析真实 Bean
@Service
public class OrderService {
    @Lazy
    @Autowired
    private PaymentService paymentService;
}
// 容器创建 OrderService 时不立即创建 PaymentService，闭环在启动期被打破；
// 运行期首次调用 paymentService 方法时才完成真实装配。

// 方案二：@DependsOn 只控制初始化先后，不解除依赖关系
@Service
@DependsOn("paymentService")
public class OrderService { /* ... */ }
// 语义：先初始化 PaymentService 再初始化 OrderService；
// 对真正的双向循环无效，仅用于单方向上的启动顺序约束。

// 方案三（推荐）：抽取公共逻辑到第三个 Bean，打断环
@Service
public class OrderService {
    private final CommonBizService common;     // 双方都依赖第三方，互不直接依赖
}
@Service
public class PaymentService {
    private final CommonBizService common;
}
注意：@Lazy 只是把循环依赖推迟到运行期，耦合关系依然存在；真正健康的设计是把环拆开——提取公共服务、引入事件机制（第 84 章）、或用回调接口解耦。循环依赖通常是职责划分不清的信号，而不是需要用框架机制去"修好"的技术问题。

85.6 报错定位与工程纪律

一句话定位：启动期循环依赖报错会给出 Bean 创建链，顺着"正在创建的 Bean → 被要求注入的 Bean"逐层向上找，即可定位闭环。

// 典型启动报错（构造器循环 / Boot 2.6+ 字段循环）：
// BeanCurrentlyInCreationException: Error creating bean with name
// 'orderService': Requested bean is currently in creation: Is there an
// unresolvable circular reference?
//
// 另一条常见链：
// UnsatisfiedDependencyException: Error creating bean with name 'orderService':
//   Bean instantiation via constructor failed;
//   nested: BeanCurrentlyInCreationException ...
//
// 定位步骤：
// 1. 看最外层异常对应的 Bean 是谁；
// 2. 沿 nested / Caused by 逐层查看被注入的下一个 Bean；
// 3. 形成 "A → B → … → A" 的链路即闭环；
// 4. 判断注入方式：构造器 → 无法靠缓存解开；字段/setter → 重构或临时 @Lazy。
纪律做法原因
优先构造器注入循环依赖在启动期直接暴露，不被缓存掩盖早失败优于运行期隐患
不要打开开关掩盖设计spring.main.allow-circular-references 仅遗留项目临时使用耦合不会因配置开关消失
闭环即重构信号抽公共 Bean、用事件回调、接口回调打断环保持依赖关系无环、单向
prototype 不参与缓存原型 Bean 之间或原型依赖单例的循环直接报错容器不缓存原型，无早期暴露机制

✓ 本章小结

要点一句话
循环依赖Bean 间依赖形成闭环；构造器注入不可解，字段/setter 单例场景可被缓存解开
三级缓存一级成品、二级早期对象、三级对象工厂；查找顺序一→二→三
三级必要性推迟"暴露原始对象还是代理对象"的决策，保证 AOP 代理唯一且引用一致
替代方案@Lazy 推迟闭环；@DependsOn 只管顺序；抽公共 Bean / 事件机制才是解耦正道
工程纪律Boot 2.6+ 默认禁止循环依赖；报错沿创建链定位闭环；循环是设计信号不是技术补丁问题

✎ 本章习题

A 基础按顺序写出三级缓存的名称、内容与查找顺序；解释构造器循环依赖为什么无法被缓存机制解开。
B 进阶写一对字段注入循环的 Service，在 Spring Boot 2.6+ 默认配置下复现启动报错；再分别用 @Lazy 与 allow-circular-references=true 两种方式让应用启动，对比两种处理的本质区别。
C 挑战为其中一个 Service 添加 @Transactional 使其被代理，推演三级缓存中工厂 getObject() 返回原始对象还是代理对象；再把三方循环 A→B→C→A 重构为抽取公共组件 D 的无环结构，画出重构前后的依赖图。
