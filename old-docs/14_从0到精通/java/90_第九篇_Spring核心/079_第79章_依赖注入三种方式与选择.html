79.1 三种注入方式写法

// ① 构造器注入（推荐）：依赖在创建时一次到位
@Service
public class OrderService {
    private final PayClient pay;               // final：不可变
    private final OrderDao orderDao;
    public OrderService(PayClient pay, OrderDao orderDao) {  // 单构造器可省 @Autowired
        this.pay = pay;
        this.orderDao = orderDao;
    }
}

// ② Setter 注入：可选依赖或需要后期替换
@Service
public class ReportService {
    private MailSender mailSender;             // 可选依赖
    @Autowired(required = false)
    public void setMailSender(MailSender mailSender) { this.mailSender = mailSender; }
}

// ③ 字段注入：一行最省，但问题最多（见 79.2）
@Service
public class LegacyService {
    @Autowired
    private PayClient pay;      // 反射注入，绕过构造器——不推荐新代码使用
}

79.2 横向对比与推荐

维度构造器Setter字段
不可变性可 final ✓✗✗
必填保障缺依赖启动即失败 ✓启动正常，运行时 NPE同左
脱离容器测试直接 new ✓需先调 setter反射才能填 ✗
循环依赖启动即报错（早暴露）✓能被三级缓存掩盖同左
可选依赖不擅长required=false ✓可但别用
结论：默认构造器注入；真正的可选依赖用 Setter；字段注入只留给测试代码或老项目维护。构造器注入的"缺点"——依赖太多构造器很长——其实是设计警报：这个类该拆了。

79.3 多实现与集合注入

public interface Notifier {
    String channel();                 // 每个实现自报渠道
    void send(String to, String msg);
}
@Component public class SmsNotifier implements Notifier {
    public String channel() { return "sms"; }
    public void send(String to, String msg) { /* ... */ }
}
@Component public class MailNotifier implements Notifier {
    public String channel() { return "mail"; }
    public void send(String to, String msg) { /* ... */ }
}

@Service
public class NotifyService {
    // 注入集合：容器把所有 Notifier 实现收拢成 Map（key=beanName）或 List
    private final Map<String, Notifier> notifiers;
    public NotifyService(Map<String, Notifier> notifiers) { this.notifiers = notifiers; }

    public void notify(String channel, String to, String msg) {
        Notifier n = notifiers.get(channel);        // 按 key 路由
        if (n == null) throw new IllegalArgumentException("未知渠道 " + channel);
        n.send(to, msg);
    }
}
// 策略模式的天然落点：新增渠道=新增一个 @Component，零修改（开闭原则）

79.4 @Primary / @Qualifier / @Value

// 同类型多实现时按类型注入会报 NoUniqueBeanDefinitionException，三种解法：

// ① @Primary：默认实现
@Component @Primary
public class MailNotifier implements Notifier { /* ... */ }

// ② @Qualifier：按名点选
public OrderService(@Qualifier("smsNotifier") Notifier notifier) { ... }

// ③ @Value：注入配置值（配合第 88 章配置体系）
@Service
public class CaptchaService {
    @Value("${captcha.expire-seconds:300}")       // 冒号后是默认值
    private int expireSeconds;
    // 构造器参数同样可 @Value；推荐构造器注入配置
    public CaptchaService(@Value("${app.name}") String appName) { /* ... */ }
}

常见坑：@Value 里的 key 拼错不会启动报错（注入 null/原样字符串），改成 @ConfigurationProperties 绑定类型化配置类可提前暴露问题——第 88 章展开。

79.5 注入的四个纪律

  1. 优先构造器注入，依赖个数 > 5 时反思类职责是否过大；
  2. 面向接口：注入类型用接口，别写死实现类；
  3. 不要把容器当全局变量：避免 ApplicationContextAware 满天飞（78.4）；
  4. prototype 注入 singleton 的坑：单例里注入原型，原型只在创建时注入一次——需要"每次新实例"用 ObjectProvider<T> 或 @Lookup 方法。
// ObjectProvider：每次要的时候现取（ prototype 语义保留）
@Service
public class TaskRunner {
    private final ObjectProvider<TaskContext> ctxProvider;
    public TaskRunner(ObjectProvider<TaskContext> p) { this.ctxProvider = p; }

    public void run() {
        TaskContext ctx = ctxProvider.getObject();  // 每次调用拿新实例
        // ...
    }
}

✓ 本章小结

要点一句话
三方式构造器主选、Setter 补充可选依赖、字段注入 legacy
构造器优势final 不可变、缺依赖早失败、裸 new 可测、循环依赖早暴露
多实现Map/List 集合注入 + 自报 channel，策略模式零修改扩展
选择工具@Primary 定默认，@Qualifier 点名，@Value 进配置
prototype 坑单例中注入原型只注入一次；用 ObjectProvider 修正
