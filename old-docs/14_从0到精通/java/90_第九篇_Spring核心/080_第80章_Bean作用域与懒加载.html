80.1 作用域总览：singleton 与 prototype

一句话定位：作用域（Scope）定义了 Bean 在容器中的存活时长与复用规则——是整个容器一份，还是每次取用都新建一份。

前面章节我们默认"容器里每个 Bean 只有一份"，这就是 Spring 容器默认的 singleton 作用域：容器启动时创建、整个应用生命周期内全局唯一，每次注入或 getBean 返回同一个实例。另一个非 Web 环境下常用的是 prototype：容器不持有实例，每次取用都创建一个全新对象，用完即弃，容器也不负责后续清理。

import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;
import org.springframework.context.annotation.ScopedProxyMode;

// 单例：不显式声明就是这个作用域，全局唯一
@Component
public class CounterService {
    private int count = 0;
    public void hit() { count++; }
    public int get() { return count; }
}

// 原型：每次 getBean / 注入都返回新实例
@Component
@Scope("prototype")
public class PrototypeCart {
    private final java.util.List<String> items = new java.util.ArrayList<>();
    public void add(String item) { items.add(item); }
    public java.util.List<String> getItems() { return items; }
}

// 启动演示：两次获取比较实例地址
// AnnotationConfigApplicationContext ctx = ...;
// CounterService a = ctx.getBean(CounterService.class);
// CounterService b = ctx.getBean(CounterService.class);
// System.out.println(a == b);                 // true  —— 单例同一对象
// PrototypeCart c1 = ctx.getBean(PrototypeCart.class);
// PrototypeCart c2 = ctx.getBean(PrototypeCart.class);
// System.out.println(c1 == c2);                // false —— 原型两个新对象
作用域存活边界实例数量容器是否持有
singleton容器生命周期，全局一份1是，缓存于一级缓存
prototype每次取用新建，交给调用方管理N否，不缓存实例
request单个 HTTP 请求周期每请求 1 份由 Web 上下文代理持有
session单个用户会话周期每会话 1 份绑定 Session
applicationServletContext 生命周期每应用 1 份绑定全局上下文
金句：绝大多数业务 Service、DAO、配置类都是 singleton；prototype 适合有状态、不能共享的临时对象（购物车、请求上下文、工具会话）。给无状态的 Bean 加 prototype，只会白白浪费内存与创建时间。

80.2 @Scope 与 Web 作用域

一句话定位：Web 作用域把 Bean 的存活边界绑定到 HTTP 生命周期上——请求一份、会话一份、应用一份，它们只能在 Web 应用上下文中使用。

import org.springframework.web.context.annotation.RequestScope;
import org.springframework.web.context.annotation.SessionScope;
import org.springframework.web.context.annotation.ApplicationScope;
import org.springframework.stereotype.Component;

// 每个 HTTP 请求一个实例：存放本次请求的跟踪信息
@Component
@RequestScope
public class RequestTrace {
    private String traceId;
    private long startAt = System.currentTimeMillis();
    // getter / setter 省略
}

// 每个浏览器会话一个实例：用户登录态、购物车的常见落点
@Component
@SessionScope
public class UserSession {
    private Long userId;
    private String nickname;
    // getter / setter 省略
}

// 整个 Web 应用一份：和 singleton 类似，但语义上绑定 ServletContext
@Component
@ApplicationScope
public class GlobalCounter {
    private long visits = 0;
    public void inc() { visits++; }
}

三个注解本质上就是 @Scope("request"/"session"/"application") 的语义化写法，便于一眼看出存活范围。它们依赖 Web 环境（DispatcherServlet 所在的上下文），在普通单元测试中直接注入会抛 ScopeNotActiveException——测试 Web 组件时要用 @WebMvcTest 或 RequestContextHolder 模拟请求上下文。

注意：request/session 作用域的 Bean 不能直接注入给 singleton Bean（启动时请求与会话尚不存在）。这正是下一节 scoped-proxy 要解决的问题。

80.3 @Lazy 懒加载与代理占位

一句话定位：默认情况下 singleton 在容器启动时完成实例化与注入；加了 @Lazy 后，实例推迟到第一次被真正使用时才创建。

80.3.1 标注在 Bean 定义上

import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Component;

// 启动时不创建；首次注入或 getBean 时才实例化
@Lazy
@Component
public class ReportGenerator {
    public ReportGenerator() {
        System.out.println("ReportGenerator 实例化（首次使用时才发生）");
    }
    public String render(String data) { return "report:" + data; }
}

80.3.2 标注在注入点上：代理占位

当 @Lazy 写在依赖的注入点时，行为更值得琢磨：容器不会立即去解析真实 Bean，而是往字段里塞一个轻量代理对象；代理内部持有"将来该解析哪个 Bean"的信息，等到第一次调用代理的方法时，才向容器取得真实 Bean 并转发调用。

@Service
public class DashboardService {
    private final ReportGenerator generator;

    // @Lazy 加在构造器参数上：注入点拿到的是代理，真实 Bean 延后解析
    public DashboardService(@Lazy ReportGenerator generator) {
        this.generator = generator;
    }

    public String show(String data) {
        // 代理方法调用时才触发 ReportGenerator 的真实创建
        return generator.render(data);
    }
}
  • 启动加速：重量级 Bean（报表引擎、第三方 SDK 封装、定时任务）推迟初始化，缩短应用启动时间；
  • 打破初始化链：两个 Bean 互相独立但初始化顺序耦合时，注入点 @Lazy 可错开启动期的创建顺序；
  • 循环依赖预警：@Lazy 能掩盖一部分循环依赖（第 85 章展开），但只是把问题推迟，不是设计上的解药。
常见坑：@Lazy 不会让单例变成多例。真实 Bean 一旦创建，仍然只此一份；@Lazy 改变的是"创建时机"，不是"创建份数"。需要每取新建，请用 prototype 或 ObjectProvider。

80.4 单例注入原型的经典坑与解法

一句话定位：单例 Bean 在启动时被创建一次，它注入的 prototype Bean 也只在那一刻被注入一次——之后单例一直握着那同一个原型实例，原型的"每次新建"承诺就此失效。

80.4.1 复现问题

@Component
@Scope("prototype")
public class TaskContext {
    private final long seq = System.nanoTime();
    public long seq() { return seq; }
}

@Service
public class TaskRunner {
    private final TaskContext ctx;
    // 单例创建时注入一次 prototype —— 此后 ctx 永远是同一个对象
    public TaskRunner(TaskContext ctx) { this.ctx = ctx; }

    public void run() {
        System.out.println("当前上下文 seq = " + ctx.seq());
    }
}

// 启动后连续调用 runner.run() 三次：
// 当前上下文 seq = 47291833012
// 当前上下文 seq = 47291833012   ← 完全相同，prototype 失效
// 当前上下文 seq = 47291833012

80.4.2 解法一：ObjectProvider 延迟获取（推荐）

import org.springframework.beans.factory.ObjectProvider;

@Service
public class TaskRunner {
    private final ObjectProvider<TaskContext> ctxProvider;

    public TaskRunner(ObjectProvider<TaskContext> provider) {
        this.ctxProvider = provider;
    }

    public void run() {
        TaskContext ctx = ctxProvider.getObject();   // 每次调用现取新实例
        System.out.println("当前上下文 seq = " + ctx.seq());
    }
}
// 三次调用 seq 各不相同；容器知道目标作用域，自动走 prototype 创建逻辑

80.4.3 解法二：@Lookup 方法注入

@Service
public abstract class TaskRunner {
    // @Lookup 注解的方法：容器在运行时生成子类覆盖它，返回新 prototype
    @Lookup
    protected abstract TaskContext createContext();

    public void run() {
        TaskContext ctx = createContext();
        System.out.println("当前上下文 seq = " + ctx.seq());
    }
}
// 注意：类需为 abstract 或留可覆盖方法；纯构造器注入的场景优先选 ObjectProvider

80.4.4 解法三：scoped-proxy（Web 作用域必备）

对于 request/session 作用域，若被单例注入，仅靠 ObjectProvider 还不够——启动期请求根本不存在。Spring 提供代理模式：容器给 Web 作用域 Bean 包一层 CGLIB 代理，单例持有的是这个代理；代理在每次方法调用时从当前请求/会话中取出真实 Bean 再转发。

@Component
@RequestScope(proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestTrace {
    private String traceId;
    public String getTraceId() { return traceId; }
    public void setTraceId(String id) { this.traceId = id; }
}

@Service
public class OrderQueryService {
    // 单例注入代理：代理内部按当前请求解析真实 RequestTrace
    private final RequestTrace trace;
    public OrderQueryService(RequestTrace trace) { this.trace = trace; }

    public void query() {
        System.out.println("trace=" + trace.getTraceId());
    }
}
解法适用场景要点
ObjectProvider<T>prototype 注入单例（首选）每次 getObject() 现取，类型安全、不污染类结构
@Lookup 方法希望保留"取新实例"语义封装在类内类需可被子类覆盖；XML 配置时代常用，注解项目较少见
scoped-proxyrequest/session 被单例注入代理绑定当前上下文；@RequestScope 等默认 TARGET_CLASS 代理
常见坑：排查"原型不新"问题时，先确认持有方是不是 singleton。Spring 文档原话：作用域 Bean 之间直接注入时，短生命周期作用域（request/session/prototype）会被长生命周期（singleton）"钉死"，必须借助代理或 ObjectProvider 才能维持各自边界。

80.5 作用域选型表

一句话定位：选型第一原则——默认 singleton，只有当对象携带请求级或会话级状态、且不能共享时，才升级到 Web 作用域；只有"每次使用都必须全新状态"时才用 prototype。

典型对象推荐作用域理由
Service、Repository、配置类、工具 Beansingleton无状态，可并发共享；启动一次创建成本低
请求跟踪号、本次请求表单校验结果request状态只属于当前 HTTP 请求，跨请求必须隔离
登录用户信息、会话内购物车session同一会话共享，不同会话隔离；需注意序列化与集群 Session 共享
全局访问计数器、应用级配置快照application语义等同全局单例，强调绑定 ServletContext
携带可变状态的任务上下文、一次性工作对象prototype状态不可共享；用 ObjectProvider 在需要处现取
金句：作用域选错通常有两种症状——共享了不该共享的状态（该用 request/session 却用 singleton，A 用户看到 B 用户的数据），或新建了不该新建的对象（无状态工具类用 prototype，启动与内存双重浪费）。判断标准只有一条：对象内部状态是否允许被并发/多人共享。
注意：prototype Bean 由容器创建后交由调用方持有，容器不执行其 destroy 回调；若原型持有数据库连接、文件句柄等资源，必须由调用方显式关闭，否则会泄漏。

✓ 本章小结

要点一句话
默认作用域singleton 全局唯一；prototype 每次取用新建且容器不缓存
Web 作用域request/session/application 分别绑定请求、会话、应用上下文，需 Web 环境
@Lazy 语义推迟创建时机而非改变份数；注入点 @Lazy 注入代理，首调真实对象
经典坑单例注入原型只注入一次；ObjectProvider、@Lookup、scoped-proxy 依次修复
选型原则默认 singleton；有状态隔离用 Web 作用域；一次性新对象才用 prototype
