83.1 编程式事务 vs 声明式事务

一句话定位：编程式事务由代码显式开启、提交、回滚；声明式事务把这些样板交给注解与代理，业务方法只写业务。

83.1.1 编程式：TransactionTemplate

import org.springframework.transaction.support.TransactionTemplate;

@Service
public class OrderService {
    private final TransactionTemplate txTemplate;
    private final OrderRepository orderRepo;
    private final InventoryClient inventory;

    // TransactionTemplate 由容器按 PlatformTransactionManager 构建注入
    public OrderService(TransactionTemplate txTemplate,
                        OrderRepository orderRepo,
                        InventoryClient inventory) {
        this.txTemplate = txTemplate;
        this.orderRepo = orderRepo;
        this.inventory = inventory;
    }

    public Order createOrder(OrderRequest req) {
        // 显式包裹：回调内抛 RuntimeException 自动回滚，正常返回自动提交
        return txTemplate.execute(status -> {
            Order order = orderRepo.save(req.toOrder());
            inventory.deduct(req.getSku(), req.getCount());
            return order;
        });
    }
}

83.1.2 声明式：@Transactional

import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    @Transactional                          // 方法进入前开启事务，退出时提交/回滚
    public Order createOrder(OrderRequest req) {
        Order order = orderRepo.save(req.toOrder());
        inventory.deduct(req.getSku(), req.getCount());
        return order;
    }
}
维度编程式声明式
事务边界代码显式控制，可精确到代码片段方法级边界，注解标注即生效
灵活性高：同一方法内多段事务、嵌套事务可精细编排低：粒度固定在方法上
样板代码多：模板回调、状态处理散落在业务代码中少：一行注解，业务纯净
典型场景复杂事务编排、需要分段提交的批处理绝大多数 Service 方法（主流选择）

83.2 @Transactional 工作机制

一句话定位：@Transactional 本身不产生事务，它是一个标记；Spring 为标注方法所在的 Bean 生成代理，由事务切面在方法前后调用事务管理器完成 begin / commit / rollback。

图 83-1 事务切面：代理拦截方法调用，事务管理器在前后完成提交与回滚

  • 事务管理器抽象：Spring 用 PlatformTransactionManager 统一接口屏蔽持久层差异；JDBC/JPA 各自提供实现（DataSourceTransactionManager、JpaTransactionManager）；Spring Boot 按依赖自动装配。
  • 连接绑定线程：开启事务后，数据库连接绑定到当前线程（ThreadLocal），方法内各 Repository 取用的是同一连接，从而共享同一事务。
  • 事务切面顺序：事务通知包裹在业务方法最外层，先开事务，再进入日志、权限等其他切面。
注意：单体应用只配置一个事务管理器即可；引入多个数据源或 JTA 分布式事务时，需要在 @Transactional(transactionManager = "xxx") 显式指定管理器，否则可能命中默认管理器造成事务错乱。

83.3 七种传播行为详解

一句话定位：传播行为（Propagation）回答"外层已有事务时，当前方法如何参与；外层没有事务时，当前方法如何自立门户"。默认 REQUIRED。

传播行为外层已有事务时外层无事务时
REQUIRED（默认）加入外层事务，内外同生共死新建一个事务，自成一个事务
REQUIRES_NEW挂起外层事务，开启全新独立事务；两个事务分别提交回滚新建事务
NESTED在现有事务内开保存点（嵌套事务），子事务回滚只回退到保存点，外层仍可继续提交等价于 REQUIRED，新建事务
SUPPORTS加入外层事务，无事务也照跑以非事务方式执行
NOT_SUPPORTED挂起外层事务，以非事务方式执行非事务方式执行
MANDATORY加入外层事务抛异常：必须在已有事务中运行
NEVER抛异常：不允许在事务中运行非事务方式执行
 
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AccountService {

    // 默认 REQUIRED：订单服务调用它，二者在同一事务里，任一失败整体回滚
    @Transactional
    public void transfer(Long from, Long to, BigDecimal amount) {
        accountDao.deduct(from, amount);
        accountDao.credit(to, amount);
    }

    // REQUIRES_NEW：独立新事务。例如"扣款失败也要记录一条审计日志并提交"
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void writeAuditLog(String message) {
        auditDao.save(message);
        // 无论外层订单事务最终是否回滚，这条审计记录都已独立提交
    }

    // NESTED：嵌套保存点。子流程失败回滚到保存点，外层可捕获后继续主流程
    @Transactional(propagation = Propagation.NESTED)
    public void applyCoupon(Coupon coupon) {
        couponDao.bind(coupon);
    }
}
常见坑：NESTED 依赖数据库保存点（SAVEPOINT）能力，JDBC 驱动需支持；它与 REQUIRES_NEW 的本质区别：NESTED 仍属外层事务，外层回滚子事务必然回滚；REQUIRES_NEW 是两个物理连接、两个独立事务，互不影响。

83.4 隔离级别、readOnly 与超时

一句话定位：隔离级别解决并发读写的可见性问题；readOnly 告诉事务管理器这是只读事务，允许数据库优化；timeout 限制事务最长占用时间。

import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

@Transactional(
        isolation = Isolation.READ_COMMITTED,   // 隔离级别，见下表
        readOnly = true,                       // 只读事务：不加写锁，可做快照优化
        timeout = 5,                           // 秒级超时；超时回滚并抛 TransactionTimedOutException
        rollbackFor = Exception.class           // 回滚规则，见 83.5
)
public Page<Order> queryOrders(OrderQuery query) {
    return orderDao.search(query);
}

// 隔离级别取值：
// DEFAULT            跟随数据库默认级别（MySQL InnoDB 默认 REPEATABLE_READ）
// READ_UNCOMMITTED   读未提交：可读到脏数据，性能最高，几乎不用
// READ_COMMITTED     读已提交：避免脏读，Oracle 默认；常见生产选择
// REPEATABLE_READ    可重复读：同一事务内两次读结果一致；MySQL 默认
// SERIALIZABLE       串行化：最强隔离，并发最差，极端一致性场景才用
隔离级别解决的问题残留风险
READ_UNCOMMITTED无脏读、不可重复读、幻读全部存在
READ_COMMITTED脏读不可重复读、幻读
REPEATABLE_READ脏读、不可重复读幻读（InnoDB 间隙锁可部分缓解）
SERIALIZABLE三类问题全部避免并发性能显著下降
金句：readOnly = true 是语义声明而非强制——只读方法写库仍会报错，但标注它能让事务管理器与连接池做只读优化；查询类方法统一标注 @Transactional(readOnly = true) 是好习惯。

83.5 rollbackFor 与回滚规则

一句话定位：Spring 默认只对 RuntimeException 与 Error 回滚；受检异常（checked Exception）默认不回滚，需要 rollbackFor 显式指定。

@Service
public class PaymentService {

    // 默认规则：抛出 RuntimeException / Error → 回滚；
    // 抛出 IOException、SQLException 等受检异常 → 仍然提交！
    @Transactional
    public PayResult pay(PayRequest req) throws PayException {
        payDao.saveRecord(req);
        if (!remoteGateway.ok()) {
            // 受检异常：按默认规则事务不会回滚，已保存的记录残留
            throw new PayException("网关不可用");
        }
        return PayResult.success();
    }

    // 正确写法：显式声明需要回滚的异常类型
    @Transactional(rollbackFor = {PayException.class, IOException.class})
    public PayResult payFixed(PayRequest req) throws PayException, IOException {
        payDao.saveRecord(req);
        if (!remoteGateway.ok()) {
            throw new PayException("网关不可用");
        }
        return PayResult.success();
    }

    // noRollbackFor：指定某些异常即使抛出也不回滚（如可降级的业务告警）
    @Transactional(rollbackFor = Exception.class,
                   noRollbackFor = {RateLimitException.class})
    public void createWithFallback(OrderRequest req) { /* ... */ }
}
注意：项目团队常约定 rollbackFor = Exception.class 统一兜底，避免受检异常漏配；这比记住"默认只回滚运行时异常"更省心，代价是把原本该保留的受检异常场景一并回滚，需要结合业务判断。

83.6 事务失效四大坑排查

一句话定位：事务依托 AOP 代理，第 82 章的代理失效规律在这里全部重演；再加上回滚规则与异常处理两个业务层陷阱，构成四大高频事故现场。

83.6.1 坑一：同类自调用绕过代理

@Service
public class OrderService {

    public void batchCreate(List<OrderRequest> list) {
        for (OrderRequest req : list) {
            this.createOrder(req);          // ❌ this 直连目标对象，事务切面不触发
        }
    }

    @Transactional
    public void createOrder(OrderRequest req) { /* SQL */ }
}
// 修复：自注入代理、拆到独立 Bean，或 AopContext.currentProxy()（同 82.6.1）

83.6.2 坑二：方法非 public / final / 静态

@Service
public class OrderService {

    @Transactional
    private void internalCreate(OrderRequest req) { /* ❌ private 代理拦截不到 */ }

    @Transactional
    public final Order createOrder(OrderRequest req) { /* ❌ final 方法无法覆写 */ }
}
// Spring 事务代理要求目标方法为 public 非 final；static 方法同样不纳入代理

83.6.3 坑三：catch 吞掉异常，回滚规则无从触发

@Transactional
public void createOrder(OrderRequest req) {
    try {
        inventory.deduct(req.getSku(), req.getCount());
    } catch (InventoryException ex) {
        log.warn("库存不足：{}", ex.getMessage());
        // ❌ 异常被吞：代理看不到异常抛出，事务按"正常返回"提交，脏数据落库
    }
    orderDao.save(req.toOrder());
}
// 修复一：catch 后手动标记回滚
// TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
// 修复二：捕获后重新抛出，让事务切面感知；不要吞异常是第一纪律

83.6.4 坑四：REQUIRES_NEW 被同一事务"吞掉"的误解

常见误区：REQUIRES_NEW 的独立事务只在通过代理对象调用时才成立。若在同类方法内直接 this.writeAuditLog() 调用，走的是目标对象而非代理，REQUIRES_NEW 不会生效，审计记录仍绑在外层事务里——外层回滚时日志一并消失。修复方式同自调用：注入自身代理后调用。
失效现场根因修复方向
同类内部调用事务方法this 引用目标对象，不经过代理自注入代理 / 拆 Bean / AopContext
private、final、static 方法标注事务代理无法覆写该方法提升为 public 非 final；静态逻辑独立成 Bean
try-catch 后异常未重抛代理感知不到异常，按正常提交重抛异常或 setRollbackOnly() 手动标记
受检异常未配 rollbackFor默认只回滚 RuntimeException / ErrorrollbackFor = Exception.class 兜底或显式列出

✓ 本章小结

要点一句话
事务形态声明式注解为主，编程式 TransactionTemplate 处理复杂编排
工作机制代理 + 事务切面 + PlatformTransactionManager；连接绑定线程共享事务
传播行为默认 REQUIRED 并入同事务；REQUIRES_NEW 独立新事务；NESTED 保存点嵌套；其余四种约束执行方式
隔离与只读READ_COMMITTED 常见选择；查询方法标 readOnly=true；timeout 防止长事务
回滚纪律默认只回滚运行时异常；异常不能吞；自调用、非 public、受检异常是四大失效点
