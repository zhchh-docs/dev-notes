◆本章目标

  • 说清基线与"快照"的区别：基线 = 正常态的量化画像；
  • 为服务采集一张六维基线卡（流量/延迟/GC/内存/线程/CPU）；

68.1 基线的定义与内容

一句话定位：性能基线是服务在"设计容量内正常运行"时各项指标的范围记录。没有基线，所有异常判断都靠感觉；有基线，异常是"偏离画像"的量化事实。

"我们服务卡了"不可行动；"老年代水位比基线高 30%，P99 从 80ms 涨到 300ms，发生时间与 X 版本发布吻合"才可行动。基线是排障的坐标系。

一张完整基线应覆盖六个维度：

维度指标采集来源
流量QPS/TPS、连接数网关日志、监控平台
延迟P50/P95/P99、接口分级耗时APM（Skywalking/Prometheus）
GCYGC 频率、单次停顿、FGC 次数/天GC 日志 + jstat
内存堆水位、老年代占比、元空间、堆外jstat / exporter
线程线程总数、各状态数量、线程池活跃度jstack / arthas
资源CPU 使用率、Load、IO、带宽top / node_exporter

68.2 采集：一张基线卡

在正常工作日高峰（不是深夜也不是全空）采集 30 分钟，填写基线卡：

==================== 服务基线卡 v1.0 ====================
服务: order-service        实例: 2C4G × 3        日期: 2026-01-05
JVM: JDK 21 · G1 · -Xms4g -Xmx4g      版本: v2.3.1

[流量]    峰值 QPS: 850        日常 QPS: 300~500
[延迟]    P50: 18ms   P95: 45ms   P99: 85ms（核心接口 /orders）
[GC]      YGC: 2~4 次/分钟, 单次 8~15ms   FGC: 0 次/天
[内存]    堆稳态水位: 45%~60%   老年代: 40%~50%   Metaspace: 180M
[线程]    总数: 210±20（tomcat 200 + 自定义 8 + GC 2）
          BLOCKED: 0    WAITING(tomcat idle): ~190
[资源]    CPU: 30%~50%   Load: <2   磁盘 IO 稳定无毛刺

异常判定红线（超出即告警）：
  P99 > 200ms 或 YGC > 15 次/分钟 或 单次 GC > 100ms
  老年代 > 75% 且持续上涨 或 FGC ≥ 1 次/天
  BLOCKED > 5 持续 1 分钟 或 CPU > 80% 持续 5 分钟
========================================================

常见坑：用平均数做基线会被长尾掩盖问题——延迟基线必须看 P95/P99 分位数；同理，CPU 看 5 分钟滑动窗口而不是瞬时值。

68.3 常见服务的"正常"参考值

不同服务形态的合理画像差异巨大，先对照再定制：

服务形态画像特点重点盯
Web API 服务YGC 频繁但短（<20ms）、FGC=0、线程数与 Tomcat 配置相当P99、YGC 频率、线程池活跃度
批处理任务CPU 高、吞吐优先、允许长 GC总耗时、吞吐、OOM
消息消费者内存平稳、LAG 稳定不增长消费延迟（LAG）、重试率
网关类CPU 相对低、连接数高、内存小连接数、FD 数、GC 停顿（影响全局）
计算型服务CPU 贴满、堆分配速率高CPU 与吞吐的比值、分配速率
通用健康线（经验值，需按业务校准）：FGC 每天 > 0 次要查；YGC 单次 > 50ms 要查（G1）；老年代稳态 > 70% 要查；线程数 > 1000 要查。基线卡里的红线应以这些为起点，而不是拍脑袋。

68.4 基线的对比与告警

  1. 环比异常检测：当前指标 vs 基线区间，超出即触发；比静态阈值更能适应流量波动；
  2. 版本变更绑定：每次发版后自动对比发布前后 24h 指标——性能回退在发布时刻最容易被抓到；
  3. 容量预警：基线 + 增长率可以推算扩容时间点，而不是等 OOM 了才扩；
  4. 排障入口：偏离哪个维度就从哪个维度进（第 65 章的 SOP）。
# 手工巡检脚本骨架（cron 每 10 分钟）
PID=$(pgrep -f order-service)
OUT=$(jstat -gcutil $PID 1000 5 | tail -1)
O=$(echo $OUT | awk '{print $4}')
if (( $(echo "$O > 75" | bc -l) )); then
  echo "$(date) 老年代水位 $O% 超红线，转储快照" >> /ops/alert.log
  jcmd $PID GC.heap_dump /dumps/heap-$(date +%s).hprof
fi
# 生产建议换成 Prometheus + Grafana + 告警规则，脚本仅用于小规模兜底

68.5 基线的生命周期

  • 建立：新服务上线稳定一周后首次采集；
  • 更新：大版本发布、JVM 升级、参数调整、流量翻倍后重测；
  • 废弃：架构变更（单体→微服务）后旧基线作废；
  • 归档：基线卡进版本库随代码演进，与发版记录关联——出问题时能查"当时基线是什么"。
第七篇总结：内存区域是地图，GC 是天气，工具是导航，基线是"正常天气"的气象档案。掌握四者，你对 JVM 就从"背概念"进入了"会运维"。

✓ 本章小结

要点一句话
基线定义正常态的六维量化画像；异常=偏离画像的量化事实
采集纪律工作日高峰 30 分钟；延迟看分位数，CPU 看滑动窗口
健康红线FGC=0、YGC<20ms、老年代<70%、BLOCKED=0 为起点
使用方式环比告警、发版对比、容量推算、排障入口
生命周期随版本更新重测，随代码归档
