案例一 静态缓存只进不出

现象：服务上线一周后逐渐变慢，GC 频率升高，最终 OutOfMemoryError: Java heap space 重启后暂时恢复。

public class CacheBuggy {
    // 坑：只进不出的静态缓存——GC Roots 永远可达
    private static final Map<String, User> CACHE = new HashMap<>();

    public static User get(String key) {
        return CACHE.computeIfAbsent(key, k -> loadFromDb(k));
    }
    private static User loadFromDb(String id) { /* ... */ return new User(id); }
}
// 正确做法：有界 + 过期
private static final Map<String, User> CACHE =
    new LinkedHashMap<String, User>(1024, 0.75f, true) {
        protected boolean removeEldestEntry(Map.Entry<String, User> e) {
            return size() > 1000;                    // LRU 上限
        }
    };
// 或直接用 Caffeine：Caffeine.newBuilder().maximumSize(1000)
//     .expireAfterWrite(Duration.ofMinutes(10)).build(...)

定位过程：jstat 看 O 列阶梯上涨 → jmap -dump 取 hprof → MAT 支配树顶端是 HashMap$Node 数组 → Path to GC Roots 显示由 CacheBuggy.CACHE（静态字段）持有 → 定位到代码。

凡是"时间越长内存越高、重启就好"，优先怀疑 GC Roots（静态集合、ThreadLocal、监听器注册）上的滞留对象。

案例二 一次 SELECT 全量捞表

现象：导出报表接口偶发 OOM，日志显示 Java heap space，错误栈停在 ArrayList.grow 与 MyBatis 结果集处理。

// 坑：500 万行一次性映进内存
List<Order> all = orderMapper.selectAll();     // OOM 高危

// 方案 A：分页批量处理（推荐，通用）
long lastId = 0;
List<Order> batch;
while (!(batch = orderMapper.selectBatch(lastId, 1000)).isEmpty()) {
    for (Order o : batch) { export(o); }
    lastId = batch.get(batch.size() - 1).getId();
}

// 方案 B：流式读取（MyBatis Cursor / JDBC fetchSize）
try (Cursor<Order> cursor = orderMapper.scanAll()) {
    for (Order o : cursor) { export(o); }      // 逐行消费，内存恒定
}

定位过程：MAT 支配树顶端是巨型 ArrayList 与 Order 数组 → 查看对象数量级远超预期 → 结合 GC 日志中 OOM 前的分配速率突增 → 对应接口调用时间点。

常见坑：MySQL 驱动默认会把整个结果集读进内存，fetchSize 只有在流式模式（Integer.MIN_VALUE）下才生效——光设置 fetchSize=1000 是无效的。

案例三 无界线程池堆积请求

现象：突发流量时 OutOfMemoryError: unable to create new native thread 或堆里塞满排队任务对象。

// 坑一：Executors.newFixedThreadPool —— 无界 LinkedBlockingQueue
//      任务消费慢时队列无限堆积 → 堆 OOM
ExecutorService bad = Executors.newFixedThreadPool(8);

// 坑二：Executors.newCachedThreadPool —— 最大 Integer 线程数
//      突发流量疯狂建线程 → 本机内存耗尽，无法建线程
ExecutorService worse = Executors.newCachedThreadPool();

// 正确：手动 new ThreadPoolExecutor，有界队列 + 拒绝策略
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),                     // 有界
    new ThreadPoolExecutor.CallerRunsPolicy());          // 打回去减慢生产

定位过程：jstack 发现上千个自定义线程名 WAITING → jmap 直方图线程对象数量异常 → 修复为有界队列。

OOM 类型 速查与预防清单

错误信息区域首要排查
Java heap space堆hprof 支配树、缓存/全量查询
GC overhead limit exceeded堆GC 98% 时间回收不到 2% 空间——同 heap space
Metaspace方法区动态类生成（CGLIB/Groovy 脚本）
unable to create new native thread线程/OS线程数、ulimit、cgroup 限制
Direct buffer memory直接内存NIO 缓冲未释放、MaxDirectMemorySize
Requested array size exceeds VM limit堆离谱的数组长度参数
预防清单：① 必配 HeapDumpOnOutOfMemoryError；② 所有缓存有上限；③ 所有线程池有界；④ 大数据量接口强制分页/流式；⑤ CI 加大对象数量级告警（如一次返回 > 1 万行直接打回）；⑥ 定期用 jstat 巡检 O 列。

复盘方法 从 hprof 到结论

  1. MAT 打开 hprof，先看 Leak Suspects 自动报告；
  2. Dominator Tree 按 Retained Heap 排序，找霸占内存的"头部对象"；
  3. Path to GC Roots（exclude weak refs）：谁让它活着——静态字段？ThreadLocal？线程池队列？
  4. 回到代码：在持有链对应类里找塞数据的逻辑；
  5. 修复并回归：同样的压测脚本复跑，对比 GC 日志确认水位回落。

结论要能写成一句话闭环："X 接口把 Y 数据缓存进了静态 Map，持有链是 CACHE，修复为有界过期后 O 列稳定在 40%"。写不出闭环，说明分析还没做完。

✓ 本章小结

案例核心教训
静态缓存泄漏GC Roots 上的集合必须有界、会过期
全量捞表任何"一次性读全量"都是定时炸弹；分页或流式
无界线程池禁止 Executors 工厂方法；队列必须有界
通用流程jstat 趋势 → hprof 支配树 → GC Roots 持有链 → 代码闭环
