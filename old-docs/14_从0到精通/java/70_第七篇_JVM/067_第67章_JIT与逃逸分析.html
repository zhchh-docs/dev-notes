67.1 解释器与 JIT 的分工

一句话定位：HotSpot = 解释器（立刻能跑）+ JIT 编译器（跑得多了编译成机器码）+ 分层编译（两者结合取长补短）。

层级含义特点
第 0 层解释执行无编译开销，启动快
第 1~2 层C1 编译（-client）快速编译 + 少量优化
第 3 层C1 + 性能探针收集热点信息为 C2 服务
第 4 层C2 编译（-server）深度优化：内联、逃逸分析、向量化
 
public class WarmUp {
    static long sum(int n) {
        long s = 0;
        for (int i = 1; i <= n; i++) s += i;
        return s;
    }
    public static void main(String[] args) {
        for (int i = 0; i < 5; i++) {
            long t0 = System.nanoTime();
            sum(10_000_000);
            long ms = (System.nanoTime() - t0) / 1_000_000;
            System.out.println("第 " + (i + 1) + " 轮耗时：" + ms + " ms");
        }
    }
}
// 典型输出：第 1 轮 8ms → 第 2 轮 4ms → 第 3 轮起稳定 2ms
// 前 1~2 轮是解释执行；热点积累后被 C2 编译，速度翻倍以上
这就是JVM 预热（Warm Up）：服务刚启动时 QPS 低、延迟高，是 JIT 还没把热点编译完。生产上常用"启动后空跑几分钟流量预热"或网关限流缓解。

67.2 热点探测与编译触发

HotSpot 用计数器探测热点：

  • 方法调用计数器：调用次数达到 -XX:CompileThreshold（C2 默认 10000，分层编译下阈值动态调整）就触发编译；
  • 回边计数器：统计循环体往回跳的次数——循环热点即使方法只被调用一次（比如 main 里的大循环）也能触发栈上替换（OSR），循环跑到一半换成编译版继续；
  • 计数器有半衰期（-XX:CounterHalfLifeTime），一段时间没调用的热度会衰减，冷代码不会永久占着编译缓存。
# 观察 JIT 行为
java -XX:+PrintCompilation WarmUp        # 打印每次编译事件
java -Xlog:jit+compilation* WarmUp       # JDK 9+ 统一日志写法

# 输出示例：
#    187  145       4       WarmUp::sum (16 bytes)
#    ↑时间戳  ↑编译编号 ↑层级4=C2  ↑方法与字节码长度

67.3 逃逸分析三大优化

一句话定位：逃逸分析判断对象的作用域是否会"逃出"方法或线程——不逃逸的对象，JVM 可以放心做激进优化。

图 67-1 逃逸级别与可优化空间

三种优化展开

public class EscapeOpt {
    // ① 标量替换（栈上分配的落地形式）：对象被拆成局部"标量"
    static int pointSum() {
        Point p = new Point(1, 2);   // p 不逃逸 → 不进堆！
        return p.x + p.y;            // JIT 等价于 return 1 + 2;
    }
    // ② 锁消除：锁对象不逃逸，锁整个被删掉
    static String concat() {
        StringBuffer sb = new StringBuffer();  // sb 不逃逸
        sb.append("a").append("b");            // 内部 synchronized 被消除
        return sb.toString();
    }
    // ③ 同步省略的前提同上——共享才需要同步
}
// 观察：-XX:+PrintEliminateAllocations（debug 版 JDK）
// 生产版可用 -XX:+PrintInlining 看内联，间接推断优化是否发生

常见坑：逃逸分析在 C2 上才开（-XX:+DoEscapeAnalysis 默认开）。但对象只要被 return、存字段、抛异常携带、传给未知方法就逃逸——很多"性能优化代码"（如频繁 new 中间对象再 return）逃逸分析帮不了。

67.4 JIT 时代的基准测试纪律

为什么手写循环计时不可信：

  1. 预热干扰：前几轮解释执行，后几轮编译执行，平均值没有意义；
  2. 死代码消除：JIT 发现计算结果没人用，整段删掉——你测了个寂寞；
  3. 常量折叠：sum(10_000_000) 入参是常量，结果被直接算成常量；
  4. DCE/GC 交叉：GC 与 CPU 频率漂移都会污染结果。
// 正确姿势：JMH（Java Microbenchmark Harness）
// Maven: org.openjdk.jmh:jmh-core + jmh-generator-annprocess:1.37
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)
@Warmup(iterations = 5, time = 1)     // 显式预热
@Fork(2)                              // 多进程隔离，抵消 JIT 差异
public class SumBenchmark {
    @Benchmark
    public long loopSum() {
        long s = 0;
        for (int i = 1; i <= 1_000_000; i++) s += i;
        return s;                     // 返回值防止死代码消除
    }
}
// mvn clean package && java -jar target/benchmarks.jar

67.5 观察 JIT：日志与反编译

# 看内联决策（C2 内联是优化的起点，方法体 <35 字节默认内联）
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining WarmUp

# 热点方法排名
java -XX:+PrintCompilation -XX:+PrintInlining WarmUp 2>> jit.log

# 配合 hsdis 可以输出汇编码（了解即可）
java -XX:+PrintAssembly -XX:+UnlockDiagnosticVMOptions WarmUp
给写代码的启示：① 小方法值得保持小——内联是万优之母；② 热路径少 new 中间对象——逃逸分析不一定救得了；③ 不要用"聪明"的反射/动态调用写热循环——无法内联。微观优化交给 JIT，人把精力放在算法与架构上。

✓ 本章小结

要点一句话
分层编译解释器快启动，C1 快编译，C2 深优化；热点逐层晋升
热点探测方法调用计数器 + 回边计数器（OSR 循环中途换编译版）
逃逸分析不逃逸对象可标量替换、锁消除；return/存字段即逃逸
基准测试手写计时不可信：预热、DCE、常量折叠；用 JMH
编码启示小方法利内联；热路径少 new；架构优化优先于字节码优化
