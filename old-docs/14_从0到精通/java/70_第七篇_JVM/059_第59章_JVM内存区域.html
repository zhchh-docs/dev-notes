59.1 运行时数据区总览

一句话定位：JVM 运行一个 Java 程序时，把内存划分成若干用途明确的区域——这份"分区规划图"就是《Java 虚拟机规范》定义的运行时数据区（Runtime Data Areas）。

图 59-1 运行时数据区：三私有两共享

记忆口诀：私有三兄弟（PC、虚拟机栈、本地方法栈）跟着线程走，共享两巨头（堆、方法区）跟着进程活。线程私有意味着它们随线程创建而生、随线程消亡而灭，不需要垃圾回收。

59.2 程序计数器与虚拟机栈

程序计数器：最小也最稳

程序计数器（Program Counter Register）是一块很小的内存，记录当前线程正在执行的字节码指令地址。Java 多线程靠 CPU 时间片轮转实现，线程被切走前必须记住"我执行到哪了"，切回来才能接着跑——每个线程都要有自己的计数器。

程序计数器是唯一一个在《JVM 规范》中不会发生任何 OutOfMemoryError 的区域。

虚拟机栈：方法调用的舞台

每调用一个方法，JVM 就在当前线程的虚拟机栈中压入一个栈帧（Stack Frame）；方法执行完，栈帧弹出。栈帧里装着：

  • 局部变量表：方法参数和方法内定义的局部变量（基本类型存值，引用类型存地址）；
  • 操作数栈：字节码指令的工作台，算 a + b 就是先把两个值压栈再执行加法指令；
  • 动态链接、方法返回地址等附加信息。
public class StackDemo {
    static int depth = 0;
    static void recurse() {   // 无限递归：只进栈不出栈
        depth++;
        recurse();
    }
    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("爆栈时递归深度 ≈ " + depth);
        }
    }
}
// 典型输出（数值因机器与参数而异）：爆栈时递归深度 ≈ 10880

常见坑：StackOverflowError 触发点是栈深度超过上限（默认约 512KB~1MB，可用 -Xss 调整），与堆大小无关。递归没写终止条件、或者单方法局部变量表过大，都会爆栈。

59.3 本地方法栈与堆

本地方法栈

与虚拟机栈作用几乎一样，区别只有一个：虚拟机栈服务Java 方法（字节码），本地方法栈服务本地方法（native 方法，即 C/C++ 实现）。HotSpot 把两者合二为一。

堆：对象的常驻地

堆（Heap）是 JVM 管理的最大一块内存，所有 new 出来的对象实例和数组都在这里分配，也是垃圾回收的主战场——所以堆也常被叫作"GC 堆"。

import java.util.ArrayList;
import java.util.List;

public class HeapDemo {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();
        try {
            while (true) {
                list.add(new byte[10 * 1024 * 1024]); // 每次 10MB，往堆里塞
            }
        } catch (OutOfMemoryError e) {
            System.out.println("堆内存耗尽：" + e.getMessage());
            System.out.println("成功塞入 " + list.size() + " 个 10MB 数组");
        }
    }
}
// 运行：java -Xmx100m HeapDemo
// 输出示例：堆内存耗尽：Java heap space  成功塞入 8 个 10MB 数组

堆在物理上可以处于不连续的内存空间，逻辑上视为连续即可。通过 -Xms（初始大小）与 -Xmx（最大大小）控制；生产环境通常把两者设成一样，避免运行期扩容抖动。

注意：引用存在栈里（或别的对象字段里），对象本体在堆里——"栈上引用 + 堆上对象"是理解一切引用类型行为的基础。第 67 章会讲 JIT 逃逸分析，某些对象其实可以不进堆。

59.4 方法区与运行时常量池

一句话定位：方法区存储每个类的结构信息——类元数据、运行时常量池、静态变量、JIT 编译后的代码缓存。

方法区是规范，实现一直在变

JDK 版本方法区实现关键变化
JDK 6永久代（PermGen，在堆内）字符串常量池也在永久代
JDK 7永久代字符串常量池、静态变量移到堆
JDK 8+元空间（Metaspace）方法区落在本机内存，不再受 -XX:MaxPermSize 约束，改用 -XX:MaxMetaspaceSize

面试高频题："永久代为什么被元空间取代？"核心答案：永久代大小难以调准，容易 OOM；元空间用本机内存，容量上限宽松，且与 HotSpot 内部结构解耦。

运行时常量池

class 文件里有一张常量表（字面量 + 符号引用），类加载后进入方法区的运行时常量池。其中字符串字面量的行为比较特殊：

String a = "hello";        // 字面量进堆内字符串常量池（JDK7+）
String b = "hello";
String c = new String("hello");  // 堆上新对象，不进池
System.out.println(a == b);        // true：指向池中同一对象
System.out.println(a == c);        // false：c 是堆上新对象
System.out.println(a == c.intern()); // true：intern 把引用指回池中对象

常见坑：方法区溢出报错在 JDK 8+ 是 OutOfMemoryError: Metaspace。典型场景是动态生成大量类（CGLIB 代理、反射框架 bug），而不是普通业务代码。

59.5 直接内存与常见误区

直接内存（Direct Memory）

直接内存不是运行时数据区的一部分，也不是《JVM 规范》定义的内存，但被频繁使用：NIO 的 DirectByteBuffer 通过 allocateDirect 在本机内存中开辟空间，配合 Channel/Buffer 实现"零拷贝式"读写，避免数据在 Java 堆与本地内存之间来回复制。

import java.nio.ByteBuffer;

public class DirectMemDemo {
    public static void main(String[] args) {
        ByteBuffer buf = ByteBuffer.allocateDirect(64 * 1024 * 1024); // 64MB 本机内存
        for (int i = 0; i < 64 * 1024 * 1024; i += 4096) {
            buf.put(i, (byte) 1);       // 直接写入本机内存
        }
        System.out.println("直接内存容量：" + buf.capacity() / 1024 / 1024 + "MB");
    }
}
// 受 -XX:MaxDirectMemorySize 控制，默认约等于 -Xmx

三个高频误区

  1. 误区一"堆外内存很安全所以随便用"——直接内存总量也有限，OutOfMemoryError: Direct buffer memory 同样会让进程死掉；
  2. 误区二"静态变量在元空间"——JDK 8 起静态变量指向的对象在堆里，元空间只存类结构信息（Class 对象里的引用关系）；
  3. 误区三"new String("a") 只有一个对象"——若池中没有 "a"，这句会创建两个对象：池中一个、堆上一个。

✓ 本章小结

区域存什么典型错误
程序计数器当前字节码执行位置无（唯一不 OOM）
虚拟机栈栈帧：局部变量表、操作数栈StackOverflowError
本地方法栈native 方法调用StackOverflowError
堆对象实例、数组（GC 主战场）OutOfMemoryError: Java heap space
方法区/元空间类元数据、运行时常量池OutOfMemoryError: Metaspace
直接内存NIO 缓冲区（规范之外）OutOfMemoryError: Direct buffer memory

一句话收束：线程私有三件套跟线程同生共死；堆和方法区全局共享、由 GC 与类卸载机制兜底。后面所有 JVM 话题——GC、调优、排障——都发生在这张分区图上。
