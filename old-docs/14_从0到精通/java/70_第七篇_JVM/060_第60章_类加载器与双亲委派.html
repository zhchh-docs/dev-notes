60.1 类加载的五个阶段

一句话定位：类的一生是 加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载；前五步合称"类加载过程"。

阶段做什么易考点
加载（Loading）读 class 字节流，生成 Class 对象放入方法区来源可以是 jar、网络、动态生成
验证（Verification）校验字节码合法性：魔数、版本、指令合规防恶意字节码
准备（Preparation）为静态变量分配内存并赋零值static int a = 1 此时 a=0，不是 1
解析（Resolution）符号引用替换为直接引用可推迟到首次使用
初始化（Initialization）执行静态变量赋值与 static{} 块（clinit）只执行一次，线程安全
 
public class InitOrder {
    static int a = 1;            // 准备阶段 a=0，初始化阶段才 a=1
    static final int B = 2;      // 编译期常量：准备阶段就直接赋 2
    static { System.out.println("静态块执行"); }

    static class Holder {        // 利用内部类实现线程安全的单例（第 78 章呼应）
        static final InitOrder INSTANCE = new InitOrder();
    }
    public static void main(String[] args) {
        System.out.println(InitOrder.B);   // 只触发加载，不触发 InitOrder 初始化！
    }
}
六种触发初始化的场景：new、读写静态字段（非编译期常量）、调用静态方法、反射 Class.forName、子类初始化连带父类、main 方法所在类。其余情况都是"只加载不初始化"。

60.2 四种类加载器

JDK 8 及之前的层次；JDK 9 模块化后 Extension 更名为 Platform，职责微调但层次思想不变。

类加载器负责加载Java 类
Bootstrap ClassLoaderJAVA_HOME/lib 核心库（rt.jar 等）C++ 实现，Java 里表示为 null
Extension / Platformlib/ext 扩展库（9+ 平台模块）ExtClassLoader / PlatformClassLoader
Application ClassLoaderclasspath 上的类（你写的代码）AppClassLoader，默认加载器
自定义 ClassLoader任意来源：网络、加密文件、热部署继承 ClassLoader 重写 findClass
 
public class LoaderChain {
    public static void main(String[] args) {
        Class<?> c = LoaderChain.class;
        ClassLoader cl = c.getClassLoader();
        while (cl != null) {
            System.out.println(cl);
            cl = cl.getParent();          // 沿父链向上
        }
        System.out.println("Bootstrap（C++ 实现，Java 中为 null）");
    }
}
// 典型输出：
// jdk.internal.loader.ClassLoaders$AppClassLoader@...
// jdk.internal.loader.ClassLoaders$PlatformClassLoader@...
// Bootstrap（C++ 实现，Java 中为 null）

常见坑：String.class.getClassLoader() 返回 null——不是"没有加载器"，而是加载它的 Bootstrap 加载器在 Java 层不可见。

60.3 双亲委派模型

一句话定位：收到类加载请求时，先交给父加载器去办；父加载器办不了（在自己搜索范围里找不到），子加载器才自己动手。

图 60-1 双亲委派：保证核心类唯一与安全

它解决了两个问题：

  1. 唯一性：同一个类在委派链上只会被加载一次，两个加载器加载的同名类在 JVM 里也算不同的类（Class 对象不相等）；
  2. 安全性：有人自己写一个 java.lang.String 想投毒，委派机制会让 Bootstrap 先加载官方版本，恶意代码根本没有出场机会。
// JDK 9+ ClassLoader#loadClass 的双亲委派核心逻辑（简化）
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);      // 1. 查缓存：已加载过？
        if (c == null) {
            try {
                ClassLoader parent = getParent();
                if (parent != null) {
                    c = parent.loadClass(name, false); // 2. 委派给父加载器
                }
            } catch (ClassNotFoundException e) { /* 父级找不到，继续 */ }
            if (c == null) {
                c = findClass(name);              // 3. 父级办不了，自己找
            }
        }
        return c;
    }
}

60.4 打破双亲委派的场景

委派模型不是铁律，主流框架都动过刀：

  • SPI（JDBC 驱动）：核心库 DriverManager 需要加载 classpath 上的驱动类，Bootstrap 加载器"够不着"应用类路径——用 线程上下文类加载器 反向委派给 Application 加载器；
  • Tomcat：每个 webapp 一个独立 WebappClassLoader，实现应用隔离与依赖版本隔离（A 应用用 Log4j1，B 应用用 Log4j2 互不干扰）；先自己加载（本地优先），找不到才委派父级；
  • OSGi / 热部署：网状委派 + 模块化，支持运行期替换类；
  • 加密保护：自定义加载器解密自研 class 文件后再 defineClass。
import java.io.*;
import java.nio.file.*;

public class MyLoader extends ClassLoader {
    private final Path dir;
    public MyLoader(Path dir, ClassLoader parent) { super(parent); this.dir = dir; }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        Path f = dir.resolve(name.replace('.', '/') + ".class");
        try (InputStream in = Files.newInputStream(f)) {
            byte[] bytes = in.readAllBytes();
            return defineClass(name, bytes, 0, bytes.length);  // 字节 → Class 对象
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
    public static void main(String[] args) throws Exception {
        MyLoader loader = new MyLoader(Paths.get("target/classes"),
                MyLoader.class.getClassLoader());
        Class<?> c = loader.loadClass("demo.Hello");
        System.out.println(c.newInstance());       // 调用 Hello 的 toString
        System.out.println("加载器：" + c.getClassLoader());
    }
}

自定义加载器只需要重写 findClass，不要重写 loadClass——保留双亲委派骨架，只替换"去哪里找字节"这一步。

60.5 动手验证类加载

# 观察类加载顺序与来源
java -verbose:class MyApp | head -20

# 查看 JDK 9+ 中某个类由谁加载（jcmd 需要目标进程）
jcmd <pid> VM.class_hierarchy java.lang.String

# 热排查利器（第 65 章详讲）
# arthas: sc -d com.demo.User   显示类加载信息与来源 jar
生产坑位：ClassNotFoundException（运行期显式加载失败）与 NoClassDefFoundError（编译期存在、运行期丢包）原因不同：前者查 classpath 与依赖冲突，后者常见于 fat jar 里 exclude 误伤或拆包部署漏文件。

✓ 本章小结

要点一句话
类加载五阶段加载→验证→准备→解析→初始化；静态赋值发生在初始化而非准备
加载器层次Bootstrap / Platform / Application / 自定义，逐层父链
双亲委派先委派父级再自己加载，保证核心类唯一、防投毒
打破委派SPI 线程上下文加载器、Tomcat 应用隔离、OSGi 模块化
同名不同类不同加载器加载的同名类不相等——排查 ClassCastException 时先看加载器
