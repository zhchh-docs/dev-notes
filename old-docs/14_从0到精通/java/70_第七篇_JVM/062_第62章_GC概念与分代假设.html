62.1 对象已死？两种判定法

一句话定位：回收之前必须先判定对象"不可达"。主流方案是引用计数与可达性分析，Java 用后者。

引用计数：简单但有洞

给每个对象挂一个计数器，被引用 +1、引用失效 -1，为 0 即可回收。判定快、开销小，但无法处理循环引用：

public class Cycle {
    Cycle partner;
    public static void main(String[] args) {
        Cycle a = new Cycle();   // a 计数 1
        Cycle b = new Cycle();   // b 计数 1
        a.partner = b;           // b 计数 2
        b.partner = a;           // a 计数 2
        a = null; b = null;      // 局部引用失效
        // 若用引用计数：两个对象计数各剩 1，永远回收不掉 → 内存泄漏
        System.gc();             // Java 的可达性分析能正常回收它们
        System.out.println("结束后堆仍可正常回收，无泄漏");
    }
}

可达性分析：从根出发

从一组 GC Roots 出发，沿着引用链走，能走到的对象是活的，走不到的就是垃圾——循环引用自然被解掉：互相引用但谁也够不着根，照样回收。

注意：可达性分析要求"冻结现场"——分析期间所有线程停摆（STW）。现代收集器做的各种优化（三色标记、增量更新），本质都是在减少这段时间。

62.2 GC Roots 有哪些

GC Roots举例
虚拟机栈中的引用各线程栈帧的局部变量表参数、临时变量
本地方法栈中的引用JNI 引用的对象
方法区的类静态变量static User cache 指向的对象
方法区的常量引用字符串常量池中的引用
同步锁持有的对象synchronized 锁住的对象
JVM 内部引用基本类型 Class 对象、异常对象、系统类加载器

实战联想：静态集合（如 static Map cache）只进不出，是最常见的"GC 认为它活着、你以为它死了"的内存泄漏——第 66 章 OOM 案例会用到。

62.3 引用强弱与对象自救

import java.lang.ref.*;

public class RefDemo {
    public static void main(String[] args) {
        // 软引用：内存不足才回收（适合缓存）
        SoftReference<byte[]> soft = new SoftReference<>(new byte[1024]);
        // 弱引用：下次 GC 必回收（适合 WeakHashMap 元数据）
        WeakReference<byte[]> weak = new WeakReference<>(new byte[1024]);
        // 虚引用：随时回收，仅用于跟踪回收事件（配合 ReferenceQueue）
        PhantomReference<byte[]> phantom =
            new PhantomReference<>(new byte[1024], new ReferenceQueue<>());

        System.out.println(soft.get() != null);   // true
        System.out.println(weak.get() != null);   // true
        System.out.println(phantom.get());        // 永远 null

        System.gc();
        System.out.println("GC 后弱引用：" + (weak.get() == null ? "已回收" : "存活"));
        System.out.println("GC 后软引用：" + (soft.get() == null ? "已回收" : "存活"));
    }
}
强度回收时机典型用途
强可达就不回收普通变量、集合元素
软内存不足才回收图片缓存、缓存框架
弱下次 GC 必回收WeakHashMap、ThreadLocal 的 key
虚不影响生命周期堆外内存回收通知（DirectByteBuffer）

对象的最后自救：finalize

可达性分析判死的对象若重写过 finalize() 且未执行过，会进入 F-Queue 执行一次——执行后若重新被引用即可"复活"。但 finalize 不保证执行、耗时且危险，JDK 9 起已标记废弃，新代码一律用 try-with-resources 或 Cleaner。

62.4 分代假设与堆的形状

一句话定位：两条经验规律——弱分代假设：绝大多数对象朝生夕死；强分代假设：熬过多次 GC 的对象往往长寿。整个堆的设计都由此推导。

图 62-1 分代堆结构：8:1:1 的 Eden 与 Survivor

  • 新生代用复制算法：朝生夕死的对象占多数，只复制少量存活者，代价小、速度快；
  • 老年代用标记-清除或标记-整理：存活率高，复制太浪费；
  • 两个 Survivor 交替使用，解决复制算法的碎片与空间浪费；
  • 晋升年龄阈值默认 15（对象头 Mark Word 只有 4 bit 存年龄）。

62.5 一次 Minor GC 的全过程

  1. Eden 满了，触发 Minor GC，所有应用线程 STW；
  2. GC Roots 扫描 Eden + 当前使用的 Survivor，标记存活对象；
  3. 存活对象复制到另一个空 Survivor（年龄 +1），年龄达标或 Survivor 放不下的晋升老年代；
  4. Eden 与旧 Survivor 整体清空，恢复线程。
# 观察 Minor GC 与 Full GC 频率、耗时
java -Xlog:gc* -jar app.jar          # JDK 9+ 统一日志
java -XX:+PrintGCDetails -jar app.jar  # JDK 8 传统参数

# 典型输出解读
# [gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause)
#      238M->28M(1024M) 12.345ms     ← 回收前后堆占用与暂停时长

常见坑：Minor GC 本身很快（毫秒级），但若存在跨代引用多、Survivor 太小导致过早晋升，会引发频繁老年代回收——那才是慢的根源。调优第一步永远是看 GC 日志，而不是拍脑袋改参数。

✓ 本章小结

要点一句话
死亡判定可达性分析替代引用计数，天然解决循环引用
GC Roots栈帧局部变量、静态变量、常量、JNI、锁对象、JVM 内部
四种引用强不收、软缺收、弱必收、虚只通知
分代假设弱分代：多数早死；强分代：熬过的长寿 → 8:1:1 新生代 + 老年代
Minor GC复制存活对象到 Survivor，毫秒级；晋升才是慢的来源
