65.1 排障总路线：先定位区域

图 65-1 四步排障 SOP

安全红线：生产进程慎用 jmap -dump 的默认模式——它会长时间 STW。优先使用 -XX:+HeapDumpOnOutOfMemoryError 事前埋点，或用 jcmd GC.heap_dump（同样 STW 但更稳），并在低峰期操作。

65.2 jstat：GC 健康速查

# 每 2 秒打印一次 GC 概况，共 10 次
jstat -gcutil <pid> 2000 10

#  S0     S1     E      O      M     CCS    YGC    YGCT   FGC  FGCT   GCT
# 0.00  45.83  88.12  62.40  95.10  90.22   214   1.032     2  0.412  1.444

读法：
E=88  Eden 使用 88%（正常，满了才 GC）
O=62  老年代使用 62%（关键！持续上涨=泄漏或缓存过大）
M=95  元空间 95%（类加载基本稳定即可）
YGC=214  FGC=2   FGCT=0.412s → 单次 Full GC 平均 200ms

判断口诀：看 O 列趋势，不看绝对值。连续采样 10 次老年代水位阶梯式上涨、YGC 后回不去，基本可断定存在滞留对象。

65.3 jstack：线程与死锁

jstack <pid> > thread-dump.txt
# 建议隔 2 秒连抓 3 次，对比线程状态变化

# 死锁时 jstack 直接给出结论：
# "Found one Java-level deadlock:"
#   "Thread-1": waiting to lock monitor 0x... (object 0x..., a java.lang.Object)
#   which is held by "Thread-0"

CPU 100% 定位五步

top                       # ① 找到高 CPU 的 java 进程 pid
top -Hp <pid>             # ② 找到该进程内高 CPU 的线程 tid
printf "%x\n" <tid>       # ③ 线程号转 16 进制（如 1a2b）
grep -A 20 "nid=0x1a2b" thread-dump.txt   # ④ jstack 里按 nid 找栈
# ⑤ 看栈顶：是业务循环？正则回溯？还是 GC 线程？
# 若栈顶是 GC 线程 → 回到 jstat 查堆，而不是查代码
线程状态含义排查方向
RUNNABLE正在执行或等待 CPU结合 nid 查是否 CPU 热点
BLOCKED等 synchronized 锁大量 BLOCKED=锁瓶颈，找持锁线程
WAITINGwait()/join()/park线程池等待正常；核心线程全 WAITING 且任务堆积是异常
TIMED_WAITING带超时等待轮询间隔过短会吃 CPU

65.4 jmap：堆转储与直方图

# ① 轻量查看对象直方图（不转储，先看排名）
jmap -histo:live <pid> | head -20
#  num     #instances  #bytes  class name
#  1:     1520000     97000000 [B (byte[])     ← byte[] 占 97MB 可疑

# ② 完整堆转储（hprof 文件，用 MAT/VisualVM 分析）
jmap -dump:live,format=b,file=heap.hprof <pid>
jcmd <pid> GC.heap_dump /dumps/heap.hprof    # 等价的现代写法

# ③ MAT 里看两样东西：
#   Dominator Tree  谁霸占了内存（按 retain size 排序）
#   Leak Suspects   自动泄漏怀疑报告

常见坑：-histo:live 与 -dump:live 都会先触发一次 Full GC——大堆服务高峰期执行会把服务顿住几秒。日常巡检用不带 live 的 histo，转储务必低峰期。

65.5 arthas：在线诊断瑞士军刀

# 启动并连接目标进程
java -jar arthas-boot.jar      # 选择目标 java 进程编号

# 高频命令
threads -n 5              # 最忙的 5 个线程（内含 CPU 占用）
thread --state BLOCKED    # 所有阻塞线程及锁链
dashboard                 # 实时面板：线程/内存/GC 一屏总览
sc -d com.demo.User       # 类从哪个 jar 加载（排查依赖冲突神器）

# watch：观察方法入参/返回值/异常——不用加日志不用重启
watch com.demo.OrderService create "{params, returnObj, throwExp}" -x 2

# trace：方法内部各调用耗时分布——慢在哪一层一目了然
trace com.demo.OrderService create '#cost > 200'

# 临时改日志级别（排查完记得改回）
logger --name ROOT --level DEBUG

arthas 最大的价值：不改代码、不重启、不发版，直接在生产环境观察方法级行为。它用字节码增强实现，增强本身有开销，诊断完建议 stop 退出。

权限纪律：arthas 能改代码级行为（redefine），生产环境必须限定可登录人员与操作审计，用完即退。

✓ 本章小结

工具一句话定位
jstat30 秒判断 GC 健康；盯 O 列趋势
jstack线程快照：死锁/BLOCKED 风暴/CPU 热点栈
jmap直方图初判 + hprof 转储 + MAT 支配树定性
arthas在线观察方法入参、耗时、类来源；watch/trace/sc 三板斧

排障的元能力是"先假设区域，再选工具"：CPU 问题查线程栈，内存问题查堆，类冲突查加载器。工具会过时，路线不会。
