63.1 收集器总览与评估指标

收集器目标算法特点现状
Serial / Serial Old单线程简单复制 / 标记-整理，全程 STW客户端小内存场景
ParNew并行新生代Serial 的多线程版随 CMS 一起退场
Parallel Scavenge/Old吞吐量并行复制 + 并行整理JDK 8 默认，批处理友好
CMS低停顿并发标记-清除JDK 14 移除
G1可控停顿Region 化、标记-整理JDK 9+ 默认，首选
ZGC / Shenandoah亚毫秒停顿着色指针 / 读屏障超大堆低延迟首选
吞吐量 = 运行用户代码时间 / 总时间；停顿 = 单次 STW 时长。两者天然矛盾：并发收集把活儿挪到后台，吞吐让给停顿。先问业务要什么，再选收集器。

63.2 Parallel：吞吐量优先

JDK 8 默认组合（Parallel Scavenge + Parallel Old）：多条 GC 线程并行工作，停顿相对长但总开销最小，适合后台计算、批处理这类"不怕顿一下，就怕干得慢"的场景。

# JDK 8 显式指定
java -XX:+UseParallelGC -XX:MaxGCPauseMillis=200 -jar batch-job.jar
# 两个自动调节旋钮
#   -XX:MaxGCPauseMillis=200   目标最大停顿
#   -XX:GCTimeRatio=99         吞吐目标：GC 时间不超过 1/99

63.3 CMS：并发低停顿及其退场

一句话定位：CMS（Concurrent Mark Sweep）把最耗时的标记与清除工作挪到与用户线程并发执行，是第一款"以停顿换吞吐"的老年代收集器。

四阶段流程

  1. 初始标记（STW，短）：只标记 GC Roots 直接关联的对象；
  2. 并发标记：沿引用链走，与用户线程并发，耗时最长但不停顿；
  3. 重新标记（STW，短）：修正并发期间引用变化的部分；
  4. 并发清除：与用户线程并发回收垃圾。

三个致命缺陷（为什么被移除）

  • CPU 敏感：并发线程抢走应用 CPU，核少时反而拖慢业务；
  • 浮动垃圾：并发标记期间产生的新垃圾本轮收不掉；并发期内存只减不增，预留不足就退化成 Serial Old 全停整理（Concurrent Mode Failure）；
  • 内存碎片：标记-清除不整理，碎片多了大对象放不下，同样触发 Full GC。

这些问题在 G1 上都有了系统性答案，所以 JDK 9 起 CMS 弃用、JDK 14 移除。

63.4 G1：区域化与停顿预测

一句话定位：G1 把堆切成数百到数千个等大 Region（1~32MB），每个 Region 可任意扮演 Eden/Survivor/Old/Humongous——回收从"整代回收"变成"挑性价比最高的 Region 集合回收"。

图 63-1 G1 的 Region 化堆

  • 停顿预测模型：G1 追踪每个 Region 的回收价值（能腾出多少空间 / 花多久），在 -XX:MaxGCPauseMillis（默认 200ms）预算内挑收益最高的 Region 集合（CSet）来回收；
  • Young GC：Eden 满即触发，全程 STW 复制；
  • Mixed GC：老年代占比超过 -XX:InitiatingHeapOccupancyPercent（默认 45%）后，新生代回收顺带捎上部分老年代 Region——这是"增量整理"，替代了 CMS 的整段 Full GC；
  • Full GC 兜底：回收速度跟不上分配速度时退化为单线程 Full GC（G1 的最坏情况，日志出现 to-space exhausted / Full GC 时要警惕）。
# 典型 4C8G 服务配置
java -Xms4g -Xmx4g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=100 \
     -XX:InitiatingHeapOccupancyPercent=40 \
     -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m \
     -jar app.jar
G1 调参建议：不要把 MaxGCPauseMillis 设太小（如 20ms），G1 会把新生代压得过小导致 GC 过于频繁，吞吐崩塌。先看日志，再动参数。

63.5 ZGC/Shenandoah：亚毫秒时代

ZGC（JDK 11 实验性，21 转正）目标：停顿时间与堆大小无关——8MB 和 16TB 的停顿都在亚毫秒级。两项核心技术：

  • 着色指针（Colored Pointers）：把 GC 元信息直接存进 64 位指针的空闲位，标记/转发状态随指针走；
  • 读屏障（Load Barrier）：应用线程读引用时由 JVM 插入一小段逻辑，发现指针"过期"就自愈并更新——标记、搬移全程并发。

代价：吞吐量比 G1 略低（屏障开销），且不压缩指针。选型经验：常规服务用 G1；单机大堆（几十 GB+）且要求极低延迟的用 ZGC；Shenandoah 思路类似（Brooks 转发指针），由 Red Hat 主导，国内生产相对少见。

java -Xms16g -Xmx16g -XX:+UseZGC -Xlog:gc -jar app.jar
# JDK 21+ 支持分代 ZGC（推荐）：-XX:+ZGenerational

✓ 本章小结

收集器一句话定位
Parallel并行全 STW，吞吐最高；批处理默认
CMS并发清除低停顿，但有浮动垃圾与碎片；已移除，懂原理即可
G1Region 化 + 停顿预测，Mixed GC 增量整理；JDK 9+ 默认首选
ZGC着色指针 + 读屏障，停顿亚毫秒且与堆无关；大堆低延迟首选

选型三步：默认 G1 → 日志显示停顿/晋升异常再调参 → 堆超过几十 G 或延迟极敏感才考虑 ZGC。没有"最好的收集器"，只有"匹配业务指标的收集器"。
