87.1 为什么需要 SpringBoot：配置地狱的终结

一句话定位：Spring 本身功能极强，但"怎么把 Spring、SpringMVC、MyBatis、数据库连接池、日志、视图解析器一个个配起来"在 SSM 时代全靠人手写 XML 与 web.xml；SpringBoot 的目标是约定优于配置——常用组合开箱即用，需要改的地方才开口。

作为有前端经验的工程师，你可以类比：写 Vue 2 时要手动选 webpack、vue-loader、babel 版本并写几十行配置；Vue CLI / Vite 把这些版本与默认配置打包成一条命令。SpringBoot 在后端做的就是同样的事。

对比维度传统 SSM（Spring + SpringMVC + MyBatis）SpringBoot 3.x（Java 17 基线）
依赖管理手动引入 spring-context、spring-webmvc、mybatis、mybatis-spring、HikariCP 等，版本自己对齐，极易冲突一个 starter 拉入整套兼容组合，版本由 BOM 统一锁定
容器配置web.xml、Spring 上下文 XML、SpringMVC 调度器 XML 逐个编写内嵌 Tomcat/Jetty/Undertow，main 方法直接启动，无 web.xml
Bean 注册XML bean 定义或注解扫描，事务、视图、消息都要显式开配置自动配置类按条件注册常见 Bean，约定默认值
外部服务器打成 war 包部署到独立 Tomcat打成可执行 jar，内嵌服务器，java -jar 启动
生产特性监控、健康检查、指标采集需自行集成第三方组件Actuator 起步依赖提供端点，配置即接入
 
<!-- 传统 SSM 的一个片段：光依赖就要十几个，版本号必须手工对齐 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-webmvc</artifactId>
    <version>5.3.27</version>
</dependency>
<dependency>
    <groupId>org.mybatis</groupId>
    <artifactId>mybatis-spring</artifactId>
    <version>2.1.1</version>
</dependency>
<!-- 还要配 web.xml 中的 DispatcherServlet、ContextLoaderListener、
     spring-mvc.xml 视图解析器、spring-dao.xml 数据源与 SqlSessionFactory…… -->
核心思想SpringBoot = Spring 全家桶的版本协调者 + 默认配置提供者 + 内嵌运行时。它没有替代第九篇讲的 IoC/AOP/事务，而是把这些能力按默认规则提前装配好。

87.2 starter 起步依赖与版本锁定

一句话定位：starter 是一份"功能套餐"的依赖清单——你声明 spring-boot-starter-web，它通过 Maven 传递依赖把 Spring MVC、内嵌 Tomcat、Jackson 等一整套兼容版本一起拉进来，你不需要逐个选版本。

<!-- pom.xml：父 BOM 先锁定所有 Spring 相关版本 -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.4</version>
    <relativePath/>
</parent>

<dependencies>
    <!-- 一个 starter = Web 开发所需的整套依赖与默认配置引导 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-jdbc</artifactId>
    </dependency>
    <!-- starter 里没有 spring-jdbc 的 version：由父 BOM 的 dependencyManagement 统一管理 -->
</dependencies>

starter 背后发生了什么

  • 依赖传递：Maven 会把 starter 自身 pom 里列出的 compile 作用域依赖一并拉入，版本取 starter 声明或 BOM 管理的值；
  • BOM 锁定：spring-boot-dependencies 在 dependencyManagement 里登记了数百个组件的经过测试的兼容版本，子项目写依赖时省略 <version>，自动继承；
  • 配置引导：starter 通常还携带自己的自动配置类（见 87.4），依赖进来，默认行为也跟着进来。
常用 starter（3.x 基线）拉入的能力
spring-boot-starter-webSpring MVC、内嵌 Tomcat、Jackson JSON 序列化、校验校验框架接入（web 服务开发主套餐）
spring-boot-starter-jdbcJdbcTemplate、数据源与事务管理自动配置（含 HikariCP）
spring-boot-starter-validationjakarta.validation 接口与 Hibernate Validator 实现（第 90 章）
spring-boot-starter-aopAOP 联盟 API 与 AspectJ 织入支持（呼应第九篇 AOP）
mybatis-spring-boot-starterMyBatis 与 Spring 集成的自动配置（第 92 章），由 MyBatis 官方提供
spring-boot-starter-actuator健康检查、指标、日志级别热调整等生产端点

常见坑不要在子项目里手动给 Spring 组件写 <version>。一旦版本与 BOM 管理值不一致，就会出现"同一 JAR 两个版本""NoSuchMethodError"这类经典依赖冲突；真要覆盖版本，应显式在 properties 里改 BOM 预留的版本属性（如 spring.version），而不是在单条依赖上改号。

87.3 @SpringBootApplication 组合注解拆解

一句话定位：启动类上这一个注解，其实打包了三件事——声明这是配置类、开启自动配置、扫描当前包及其子包下的组件。

package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.*;

@SpringBootApplication          // 组合注解：见下方拆解
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@RestController
class HelloController {
    @GetMapping("/hello")
    public String hello() {
        return "Spring Boot 3.x 启动成功";
    }
}
组合注解职责
@SpringBootConfiguration本质是 @Configuration 的特化标注：本类可作为 Java 配置类，方法上的 @Bean 会被容器识别
@EnableAutoConfiguration开启自动配置机制：从 classpath 读取候选自动配置类，按条件注册 Bean（87.4 详讲）
@ComponentScan默认扫描启动类所在包及其子包，注册 @Component/@Service/@Repository/@RestController 等组件；未显式指定 basePackages
注意启动类必须放在顶层包（例如 com.example.demo），业务类都在它的子包下。若把启动类放进 com.example.demo.app，默认扫描范围就缩到 app 包，外层 com.example.demo.service 下的组件不会被注册——这是新手最常见的"Bean 找不到"原因之一。需要扩大扫描范围时显式写 @ComponentScan("com.example")。

87.4 自动配置原理：条件装配的三段链路

一句话定位：自动配置不是魔法——启动时读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 里登记的配置类，每个配置类上用 @ConditionalOnXxx 判断"类路径里有没有这个类""容器里有没有这个 Bean"，条件满足才注册对应的 Bean。

图 87-1 自动配置三段链路

条件注解常用成员

条件注解成立条件
@ConditionalOnClass(Class)指定类出现在类路径上才注册（starter 没引入相关依赖时整段不生效）
@ConditionalOnMissingBean(Class)容器中还没有同类型 Bean 才注册默认实现——业务自己定义了实现，就覆盖默认
@ConditionalOnProperty(prefix, name)配置项取值满足要求（matchIfMissing 决定缺省时是否生效）
@ConditionalOnWebApplication当前是 Web 应用上下文才注册 Web 相关 Bean
 
/** 演示一个自定义自动配置类长什么样（真实 starter 放在独立模块中） */
@AutoConfiguration
@ConditionalOnClass({ RestTemplate.class })          // 类路径有 RestTemplate 才生效
@ConditionalOnProperty(prefix = "demo.client", name = "enabled", havingValue = "true",
                       matchIfMissing = true)        // 配置可关闭
public class DemoClientAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                       // 用户自己声明了就不覆盖
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}
# 该类被登记在模块资源目录：
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
# 每行一个配置类全限定名，启动时由自动配置选择器读取：
com.example.demo.DemoClientAutoConfiguration
呼应第九篇条件注册的 Bean 进入的还是第九篇讲的 ApplicationContext 容器：单例、生命周期、依赖注入、AOP 代理全部沿用，自动配置只是"在容器启动前多写了一批带条件的 @Configuration"。

87.5 SpringApplication.run 启动流程

一句话定位：SpringApplication.run 不是黑盒 new 一个 Tomcat，它按固定步骤准备环境、创建容器、执行自动配置、刷新上下文、启动内嵌服务器，并在各节点发布事件供监听者介入。

图 87-2 SpringApplication.run 启动时序

  1. 推断应用类型：依据类路径是否存在 Servlet 组件决定创建 Web 上下文还是普通上下文；
  2. 准备 Environment：命令行参数、系统属性、环境变量、application.yml 按优先级汇成配置源；
  3. 创建 ApplicationContext：注册启动类、调用 prepareContext 执行初始化器与监听器；
  4. refreshContext 刷新：扫描组件、执行自动配置、实例化单例 Bean、完成 AOP 代理与事务织入（对应第九篇生命周期）；
  5. 启动内嵌服务器：Web 应用在此阶段把 DispatcherServlet 等接入 Tomcat 并监听端口；
  6. 发布就绪事件：ApplicationReadyEvent 之后，应用正式对外服务；退出时由 ShutdownHook 优雅关闭。
// 显式创建 SpringApplication 并定制行为，等价于直接调用 run
public class Demo {
    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(DemoApplication.class);
        app.setBannerMode(Banner.Mode.OFF);          // 关闭默认 Banner
        app.addListeners(new ApplicationEnvironmentPreparedListener() {
            @Override
            public void onApplicationEvent(ApplicationEnvironmentPreparedEvent event) {
                // 环境准备完成后可读取、校验配置
            }
        });
        app.run(args);
    }
}

87.6 常见坑与排查清单

排查：自动配置没生效按顺序检查：① starter 是否真的引入（mvn dependency:tree 看依赖树）；② 配置类上的条件是否满足（类路径缺类、配置开关关闭、用户已定义同名 Bean 导致 @ConditionalOnMissingBean 跳过）；③ 启动类包位置导致组件扫描漏掉；④ 排查时加 --debug 启动参数，控制台会打印条件评估报告（CONDITIONS EVALUATION REPORT），直接显示每条自动配置命中或跳过的原因。

坑：版本被手动写死子 pom 里给 Spring/MyBatis 组件单独标版本号，绕过 BOM 协调，启动期出现 NoSuchMethodError、ClassNotFoundException。正确做法：版本号交给父 BOM；需要整体升级时改父工程的 Boot 版本。

坑：启动类放错包启动类与业务类不在包含关系的包下，默认 @ComponentScan 扫不到，控制器返回 404、Service 注入失败。先核对包路径再怀疑其他原因。

版本差异如实标注：Spring Boot 3.x 基线为 Java 17，自动配置清单文件从 2.x 时代的 spring.factories 迁移到了 3.x 的 AutoConfiguration.imports；Java EE 命名空间整体迁移到 jakarta.*（第 90 章校验注解即使用 jakarta.validation）。

要点一句话
