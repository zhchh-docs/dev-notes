◆本章目标

  • 设计字段稳定的 Result<T> 响应体，区分成功码与业务错误码；
  • 用 BizException 携带错误码抛出业务异常，错误码集中在枚举中管理；
  • 使用 @RestControllerAdvice + @ExceptionHandler 集中接管控制器层异常；
  • 把参数校验、404、405、500 等异常映射为统一 JSON 并配合 HTTP 状态码；
  • 避开异常被 catch 吞掉、响应结构不一致、advice 不生效三类实战坑。

91.1 统一响应体 Result

一句话定位：响应结构固定为 code / message / data：code=0 表示成功，非 0 表示业务失败；HTTP 状态码表达传输层结果，body 内 code 表达业务结果，两者分工不同。

package com.example.demo.common;

/** 统一响应体，泛型承载业务数据 */
public record Result<T>(Integer code, String message, T data) {

    public static <T> Result<T> ok(T data) {
        return new Result<>(0, "success", data);
    }

    public static <T> Result<T> fail(ErrorCode errorCode) {
        return new Result<>(errorCode.getCode(), errorCode.getMessage(), null);
    }

    public static <T> Result<T> fail(Integer code, String message) {
        return new Result<>(code, message, null);
    }
}
# 成功：HTTP 200，code=0
{ "code": 0, "message": "success", "data": { "id": 123, "name": "张三" } }

# 业务失败：HTTP 200 或对应状态码，code 非 0
{ "code": 10002, "message": "用户不存在", "data": null }

# 参数校验失败：HTTP 400，code 非 0，message 聚合字段错误
{ "code": 10001, "message": "name: 姓名不能为空；email: 邮箱格式不正确", "data": null }
前端约定前端拦截器只判 response.status 是否可达、再判 body.code 是否为 0；字段名长期稳定，不因接口不同而变，这是统一响应体最大的价值。

91.2 业务异常与错误码枚举

一句话定位：业务代码不返回错误字符串，而是抛出携带错误码的 BizException；错误码集中在枚举中分段管理，便于前端对照、日志检索与国际化扩展。

package com.example.demo.common;

import lombok.Getter;

@Getter
public enum ErrorCode {

    SUCCESS(0, "success"),
    PARAM_INVALID(10001, "参数校验失败"),
    USER_NOT_FOUND(10002, "用户不存在"),
    ORDER_NOT_FOUND(10003, "订单不存在"),
    STATUS_CONFLICT(10004, "当前状态不允许该操作"),
    UNAUTHORIZED(10005, "未登录或登录已过期"),
    FORBIDDEN(10006, "无权限执行该操作"),
    SYSTEM_ERROR(99999, "系统繁忙，请稍后重试");

    private final Integer code;
    private final String message;

    ErrorCode(Integer code, String message) {
        this.code = code;
        this.message = message;
    }
}
package com.example.demo.common;

/** 业务异常：由 Service / Controller 主动抛出，携带错误码 */
public class BizException extends RuntimeException {

    private final ErrorCode errorCode;

    public BizException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }

    public BizException(ErrorCode errorCode, String detail) {
        super(errorCode.getMessage() + "：" + detail);
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() { return errorCode; }
}
// Service 层抛出业务异常，不关心 HTTP 与响应格式
@Service
public class UserService {

    public UserVO getById(Long id) {
        User user = userMapper.selectById(id);
        if (user == null) {
            throw new BizException(ErrorCode.USER_NOT_FOUND);
        }
        return UserVO.from(user);
    }
}
码段含义示例
0成功SUCCESS
10001–19999参数与校验类错误PARAM_INVALID
20001–29999资源不存在 / 状态冲突类业务错误USER_NOT_FOUND、STATUS_CONFLICT
30001–39999权限与认证类错误UNAUTHORIZED、FORBIDDEN
99999兜底系统错误，不向前端暴露堆栈SYSTEM_ERROR

91.3 @RestControllerAdvice 处理体系

一句话定位：@RestControllerAdvice 标注的类会被 Spring MVC 识别为全局控制器增强；类内每个 @ExceptionHandler(异常类型) 方法负责把对应异常转成 Result 返回，逻辑上像一张全局 catch 表。

图 91-1 全局异常分发链路

package com.example.demo.common;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.*;

import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    /** 业务异常：使用枚举中的错误码 */
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException ex) {
        log.warn("业务异常：{}", ex.getMessage());
        return Result.fail(ex.getErrorCode());
    }

    /** 参数校验失败：聚合字段错误信息 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Result<Void>> handleValid(MethodArgumentNotValidException ex) {
        String msg = ex.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getField)
                .collect(Collectors.joining("；"));
        String detail = ex.getBindingResult().getFieldErrors().stream()
                .map(e -> e.getField() + ": " + e.getDefaultMessage())
                .collect(Collectors.joining("；"));
        log.warn("参数校验失败：{}", detail);
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .body(Result.fail(ErrorCode.PARAM_INVALID.getCode(), detail));
    }

    /** 兜底：未列明的异常统一包装，不向客户端暴露堆栈 */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception ex) {
        log.error("系统异常", ex);
        return Result.fail(ErrorCode.SYSTEM_ERROR);
    }
}

91.5 处理顺序与响应细节

  • 最具体优先：Spring 按异常类型继承关系选择最匹配的 @ExceptionHandler；Exception 兜底处理器放最后，只接住前面都没匹配上的异常；
  • 多 advice 排序：项目存在多个全局处理器时，用 @Order 或 @Priority 指定顺序，避免同类型异常被抢先兜底；
  • HTTP 状态码与 body 分工：需要语义化状态码时返回 ResponseEntity 携带 status；业务异常若团队约定全部 200 + body.code，也可直接返回 Result，但要前后端统一口径；
  • 日志分级：业务异常 warn，校验异常 warn，兜底异常 error 并打印完整堆栈；响应体只返回脱敏后的友好提示；
  • 静态资源与页面 404：接口 advice 不处理视图解析异常；前后端分离项目把 SPA 路由与静态资源交给服务器配置。
// 补充：路径不存在抛出 NoHandlerFoundException 的配置（application.yml）
spring:
  mvc:
    throw-exception-if-no-handler-found: true
  web:
    resources:
      add-mappings: false          # 接口工程不启用默认静态资源映射，404 才抛异常

91.6 常见坑排查

坑：异常被 catch 吞掉Service 里写了 try { ... } catch (Exception e) { log.error(e); } 却不抛出，控制器拿到 null，前端收到 200 + null data，既无错误码也无日志线索。catch 后要么转换为 BizException 重抛，要么确认确实属于可降级场景。

坑：响应结构不一致部分控制器手动返回 Map、部分返回 Result、部分直接抛异常走默认错误页；前端要写三套解析逻辑。纪律：控制器方法返回值统一 Result<T>，错误路径全部交给全局 advice。

坑：advice 不生效常见原因：① 全局类没被组件扫描到（启动类包位置问题，呼应第 87 章）；② 异常在控制器之外（如过滤器、拦截器内抛出），@RestControllerAdvice 管不到，需注册 HandlerExceptionResolver 或在过滤器内直接写响应；③ 自定义异常继承了错误的父类，匹配不到对应处理器。

安全纪律兜底处理器绝不能把 ex.getMessage() 与堆栈直接塞进响应体；SQL 错误、类名、内部路径会随异常消息泄露给前端。统一返回 SYSTEM_ERROR 的友好文案，细节只进服务端日志。

✓ 本章小结

要点一句话
统一响应体code/message/data 固定结构，0 为成功，非 0 为业务失败
业务异常BizException 携带 ErrorCode 枚举，Service 抛出，不拼响应
全局处理器@RestControllerAdvice + @ExceptionHandler 按类型集中映射异常
异常清单校验失败 400、资源不存在 404、方法不允许 405、兜底 500 统一包装
