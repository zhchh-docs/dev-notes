44.1 什么是 SPI

SPI（Service Provider Interface）是 JDK 内置的可插拔机制：一方定义接口，另一方按约定注册实现，使用方运行期自动发现——解耦"定义"与"实现"。

// 经典场景：JDBC 4.0 之前，你只写 DriverManager.getConnection()
// MySQL 驱动怎么被找到的？靠 SPI

src/main/resources/META-INF/services/java.sql.Driver
  └─ 文件内容：com.mysql.cj.jdbc.Driver        # 一行一个实现类全类名
  • 约定目录：classpath 下 META-INF/services/接口全类名，内容是实现类的全类名清单；
  • 发现方式：ServiceLoader.load(接口.class)，迭代拿到所有实现；
  • 其他用户：JDBC、CharsetProvider、Logger、SLF4J 绑定、以及无数框架的插件机制。

44.2 手写 SPI 全流程

// ① 定义接口（放在"核心"工程）
public interface Payment {
    void pay(BigDecimal amount);
}

// ② 第三方提供实现（放在各自的 jar 里）
public class AliPay implements Payment {
    public void pay(BigDecimal a) { System.out.println("支付宝支付 " + a); }
}
public class WechatPay implements Payment {
    public void pay(BigDecimal a) { System.out.println("微信支付 " + a); }
}

// ③ 在实现方 jar 的 src/main/resources 下建文件：
// META-INF/services/com.example.Payment
// 内容：
// com.example.AliPay
// com.example.WechatPay

// ④ 使用方运行期发现
ServiceLoader<Payment> loader = ServiceLoader.load(Payment.class);
for (Payment p : loader) {          // 懒加载：迭代时才实例化
    p.pay(new BigDecimal("99.9"));
}
  • ServiceLoader 是懒加载的：load() 不实例化，遍历/iterator 时才通过无参构造创建——实现类必须有 public 无参构造；
  • 多个实现按 services 文件里的行顺序返回，不排序、不去重；
  • Spring 的 spring.factories / AutoConfiguration.imports 本质是同款思想：一个文件登记一批实现类，启动时扫出来装配。

44.3 SPI 与双亲委派的恩怨

悖论出现了：java.sql.Driver 接口由 Bootstrap 加载，而 MySQL 驱动类在 classpath（Application 层）。Bootstrap 看不见 classpath——自己定义的接口，加载不了别人写的实现。

// JDK 的解法：线程上下文类加载器
ClassLoader ctx = Thread.currentThread().getContextClassLoader();
// ServiceLoader 内部用的就是它——Application 层加载器
// 于是 Bootstrap 定义的标准，能"借" Application 的加载器找到 classpath 里的实现
  • ServiceLoader 可由调用方指定 ClassLoader，默认用线程上下文类加载器——这是双亲委派模型的官方"后门"；
  • 场景串起来：JDBC 用 SPI 找驱动 → SPI 靠上下文类加载器 → 上下文类加载器由容器（Tomcat/Spring）设置——三章知识（加载器/SPI/线程）在这一页闭环；
  • 自定义框架设计插件时照抄这套：约定目录 + ServiceLoader + 文档写明"实现类无参构造"。
SPI = 接口与实现的分离注册表；线程上下文类加载器 = JDK 为 SPI 打破双亲委派的合规后门。
