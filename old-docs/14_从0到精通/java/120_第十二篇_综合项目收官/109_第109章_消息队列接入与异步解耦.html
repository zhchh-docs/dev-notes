审批通过后要通知提交人、写站内信、推消息——这些动作不必卡在主请求里同步完成。本章用 RabbitMQ 把通知链路异步化：讲清削峰、解耦、异步三大价值，落地 Spring AMQP 收发消息，并处理幂等、重复投递与消息堆积三类可靠性问题。

◆本章目标

  • 说出消息队列的削峰、解耦、异步三大价值与各自代价；
  • 理解 RabbitMQ 的 exchange、queue、binding、routing key 模型与四种交换机类型；
  • 用 Spring AMQP 完成队列声明、消息发送、监听消费的完整链路；
  • 掌握 confirm、手动 ack、死信队列等可靠性手段；
  • 落地消费幂等，能识别重复消息与消息堆积并给出处理方案。

109.1 为什么需要消息队列

审批动作完成后，主请求原本要同步做三件事：给提交人发站内信、推送消息通知、记录通知流水。任何一个下游慢或挂掉，都会拖累主接口；引入消息队列后，主流程只负责把事件丢进队列就返回，通知由消费者慢慢处理。

价值说明本项目场景代价 / 注意
异步非核心动作延后处理，主接口 RT 下降、用户等待变短审批通过后异步发通知、写通知流水消息不保证实时到达；需要接受最终一致
解耦生产者只发事件，不关心谁消费；新增通知渠道不改主流程代码以后加短信、邮件渠道，新增消费者即可系统间契约（消息格式）需要长期维护
削峰突发流量先堆在队列里，消费者按自身能力匀速拉取批量导入需求后的通知洪峰队列积压期间延迟上升；需要限流与堆积监控

图 109-1 同步串行调用与队列异步解耦对比

引入代价消息队列带来额外复杂度：系统可用性依赖 MQ 本身、消息可能重复或丢失、排障链路变长。能用同步调用解决的小项目不必硬上 MQ；本项目引入它，是为了在教学中把异步链路与可靠性问题完整走一遍。

109.2 RabbitMQ 核心概念模型

RabbitMQ 是 AMQP 协议的消息代理：生产者不直接把消息投递到队列，而是先发给交换机（Exchange），交换机按绑定（Binding）规则与 routing key 把消息路由到一个或多个队列（Queue），消费者从队列取消息。

图 109-2 RabbitMQ 路由模型

交换机类型路由规则本项目用途
directrouting key 精确匹配绑定键审批通知按事件类型精确投递到站内信队列
topicrouting key 按词段通配（* 一个词，# 多个词）通知事件分级：notify.approval、notify.reject 由订阅方按前缀收取
fanout忽略 routing key，广播到所有绑定队列系统公告类消息同时推给多个渠道
headers按消息头属性匹配，不常用教学项目不展开

109.3 Spring AMQP 配置与声明

引入 spring-boot-starter-amqp 后，连接配置走 spring.rabbitmq；队列、交换机、绑定关系用 @Bean 声明，应用启动时由 RabbitAdmin 自动创建到 Broker。

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
# application-dev.yml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: guest
    password: guest
    virtual-host: /
    publisher-confirm-type: correlated   # 开启发布确认（109.6）
    publisher-returns: true              # 交换机无法路由时返回消息
    listener:
      simple:
        acknowledge-mode: manual        # 手动 ack（109.6）
        prefetch: 10                    # 每个消费者一次最多未确认条数
        concurrency: 2                  # 初始消费者线程数
        max-concurrency: 6
// config/RabbitMqConfig.java —— 声明交换机、队列与绑定关系
@Configuration
public class RabbitMqConfig {

    public static final String EXCHANGE_NOTIFY = "notify.exchange";
    public static final String QUEUE_APPROVAL = "notify.approval.queue";
    public static final String QUEUE_EMAIL    = "notify.email.queue";
    public static final String ROUTING_APPROVAL = "notify.approval";
    public static final String ROUTING_EMAIL    = "notify.email.#";

    @Bean
    public TopicExchange notifyExchange() {
        return new TopicExchange(EXCHANGE_NOTIFY, true, false);
    }

    @Bean
    public Queue approvalQueue() {
        return new Queue(QUEUE_APPROVAL, true);   // durable 持久化
    }

    @Bean
    public Queue emailQueue() {
        return new Queue(QUEUE_EMAIL, true);
    }

    @Bean
    public Binding approvalBinding(Queue approvalQueue, TopicExchange notifyExchange) {
        return BindingBuilder.bind(approvalQueue)
                .to(notifyExchange).with(ROUTING_APPROVAL);
    }

    @Bean
    public Binding emailBinding(Queue emailQueue, TopicExchange notifyExchange) {
        return BindingBuilder.bind(emailQueue)
                .to(notifyExchange).with(ROUTING_EMAIL);
    }
}

109.4 消息发送：RabbitTemplate

生产者在审批事务提交之后发送事件消息；消息体用 JSON 序列化，携带业务 id、事件类型、操作人与时间戳，消息头里放全局唯一消息 id 供消费方做幂等。

// dto/NotifyMessage.java —— 消息体契约（前后端与多消费者共用）
public class NotifyMessage implements Serializable {
    private String messageId;        // 全局唯一，幂等键
    private String eventType;         // APPROVE / REJECT / PROGRESS
    private Long requirementId;
    private Long receiverId;
    private String content;
    private Long operatorId;
    private LocalDateTime occurTime;
    // getter / setter 省略
}

// service/impl/ApprovalServiceImpl.java —— 审批通过后异步发通知
@Service
public class ApprovalServiceImpl implements ApprovalService {
    private final RequirementMapper requirementMapper;
    private final ApprovalRecordMapper recordMapper;
    private final RabbitTemplate rabbitTemplate;

    public ApprovalServiceImpl(RequirementMapper r, ApprovalRecordMapper a,
                               RabbitTemplate rabbitTemplate) {
        this.requirementMapper = r; this.recordMapper = a;
        this.rabbitTemplate = rabbitTemplate;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void approve(Long requirementId, Long approverId, String comment) {
        Requirement req = requirementMapper.selectById(requirementId);
        if (req == null) throw new BizException(ErrorCode.REQUIREMENT_NOT_FOUND);
        RequirementStatus.from(req.getStatus())
                .transition(RequirementStatus.APPROVED);
        req.setStatus(RequirementStatus.APPROVED.name());
        requirementMapper.updateById(req);

        ApprovalRecord record = new ApprovalRecord();
        record.setRequirementId(requirementId);
        record.setApproverId(approverId);
        record.setAction("APPROVE");
        record.setComment(comment);
        recordMapper.insert(record);

        // 事务提交后再发消息：避免事务回滚但消息已发出（见 109.7 与 108.4 同理）
        NotifyMessage msg = buildMessage("APPROVE", req, approverId);
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    rabbitTemplate.convertAndSend(
                        RabbitMqConfig.EXCHANGE_NOTIFY,
                        RabbitMqConfig.ROUTING_APPROVAL,
                        msg,
                        m -> {
                            m.getMessageProperties().setMessageId(msg.getMessageId());
                            return m;
                        });
                }
            });
    }
}
发送时机与"事务提交后删缓存"同理：消息必须在数据库事务提交成功之后再发；事务回滚而消息已发出，消费者会收到一条数据库里根本不存在的事件。

109.5 消息消费：监听器与手动确认

消费者用 @RabbitListener 绑定队列；手动确认模式下，业务处理成功后调用 channel.basicAck，处理失败按场景选择 basicNack 重回队列或转入死信队列。

// listener/NotifyApprovalListener.java
@Component
@Slf4j
public class NotifyApprovalListener {

    private final NotifyService notifyService;
    private final RedisTemplate<String, Object> redisTemplate;

    public NotifyApprovalListener(NotifyService n, RedisTemplate<String, Object> r) {
        this.notifyService = n; this.redisTemplate = r;
    }

    @RabbitListener(queues = RabbitMqConfig.QUEUE_APPROVAL)
    public void onApproval(NotifyMessage msg, Channel channel,
                           Message message) throws IOException {
        String messageId = message.getMessageProperties().getMessageId();
        long deliveryTag = message.getMessageProperties().getDeliveryTag();
        try {
            // ① 幂等检查：消息 id 已处理过则直接 ack 丢弃（109.7）
            if (alreadyHandled(messageId)) {
                channel.basicAck(deliveryTag, false);
                return;
            }
            // ② 执行业务：写站内信、落通知流水
            notifyService.sendInApp(msg);
            markHandled(messageId);
            // ③ 处理成功，手动确认
            channel.basicAck(deliveryTag, false);
        } catch (Exception e) {
            log.error("审批通知消费失败, messageId={}", messageId, e);
            // 失败不重回队列无限重试：拒绝并转入死信队列（109.6）
            channel.basicNack(deliveryTag, false, false);
        }
    }

    private boolean alreadyHandled(String messageId) {
        return Boolean.TRUE.equals(redisTemplate.hasKey("mq:handled:" + messageId));
    }

    private void markHandled(String messageId) {
        // 幂等记录保留 7 天，覆盖消息重复投递窗口
        redisTemplate.opsForValue()
                .set("mq:handled:" + messageId, "1", Duration.ofDays(7));
    }
}

同一队列的多个消费者之间是竞争消费关系：一条消息只会被其中一个消费者取走；需要广播给多个渠道时，用多个队列分别绑定交换机，而不是指望一条消息被多个消费者重复拿到。

109.6 消息可靠性与死信队列

消息链路有三段都可能丢：生产者到 Broker、Broker 自身、Broker 到消费者；可靠性手段分别对应确认机制、持久化与手动确认。

环节风险手段
生产者 → Broker网络闪断导致消息没到 Brokerpublisher confirm（correlated）回调确认；失败后重发或落库补偿
Broker 存储Broker 重启丢失未持久化消息交换机与队列 durable=true；消息投递时设置持久化模式
Broker → 消费者消费者处理中途宕机，消息被当成功消费手动 ack：处理成功才确认；异常时 nack 重回队列或进死信
反复失败的消息毒消息无限重试，占满队列与线程转入死信队列（DLX）人工干预或定时重放

死信队列（Dead Letter Exchange，DLX）一句话带过：队列可以绑定一个备用交换机，消息被拒绝、过期或队列长度超限后转入死信交换机，再路由到死信队列单独排查；本项目配置中预留 notify.dlx.exchange，后续可在队列声明时通过 x-dead-letter-exchange 参数接入。

109.7 幂等、重复消息与堆积

坑一：消费端必须幂等MQ 在重试、网络抖动、ack 丢失时会重复投递同一条消息。消费代码不能假设"消息只来一次"：以业务唯一键或消息 id 去重，重复消息直接 ack 跳过（109.5 的 Redis 标记即为教学版实现）。
坑二：生产端重复发送confirm 超时或业务重试导致同一事件发两次；生产者生成全局唯一 messageId，消费端以它为幂等键，比在数据库业务字段上做唯一约束更通用。
坑三：消息堆积消费者处理速度跟不上生产速度时队列长度持续增长。排查顺序：先看消费者线程数与 prefetch 是否过小；再看单条处理是否有慢 SQL、外部调用超时；必要时横向扩容消费者、拆分队列；长期堆积要回溯生产端是否需要限流。
设计纪律消息体只放事件事实与业务 id，不放大对象与敏感字段；消费者按消息 id 能回数据库查到所需详情。事件命名用"过去时"（Approved、Rejected），语义上表达"已经发生的事实"。

✓ 本章小结

要点一句话
三大价值异步缩短主链路、解耦新增下游、削峰缓冲突发流量；代价是引入可用性与一致性复杂度
核心模型生产者发交换机，按 routing key 与绑定关系路由到队列，消费者竞争消费
收发实现@Bean 声明队列/交换机/绑定；RabbitTemplate 发送，@RabbitListener 监听手动 ack
可靠性confirm 保送达、持久化防 Broker 重启、手动 ack 保消费、死信隔离毒消息
幂等与堆积消息可能重复，消费端按 messageId 去重；堆积先查并发与单条耗时，再扩容与限流

A 基础说出消息队列的三大价值与各自代价；解释 exchange、queue、binding、routing key 的关系，以及 direct 与 topic 交换机的区别。
B 进阶为本项目新增"驳回通知"链路：声明 topic 绑定键 notify.reject，消费者写站内信；验证审批通过与驳回消息分别进入不同队列，重复投递同一条消息不产生重复通知。
