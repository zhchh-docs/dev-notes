108.1 starter 引入与连接配置

Spring Boot 通过 spring-boot-starter-data-redis 自动装配 Lettuce 连接池与 RedisTemplate；配置集中在 spring.data.redis 节点下，本地开发指向本机 6379。

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<!-- Lettuce 连接池需要 commons-pool2 -->
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-pool2</artifactId>
</dependency>
# application-dev.yml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password: ""              # 本地无口令；生产通过配置中心注入
      database: 0               # 逻辑库编号，教学项目统一用 0
      timeout: 2000ms
      lettuce:
        pool:
          enabled: true
          max-active: 20        # 最大连接数
          max-idle: 10
          min-idle: 2
          max-wait: 2000ms

# 本项目缓存键前缀约定：模块:业务:标识
# 例：req:hot:list、req:detail:1001、user:token:101
键命名约定项目内所有缓存键统一 模块:业务:标识 三段式，便于排查、批量清理与后续按前缀统计；不要在代码里散落 user101、hotList 这类无前缀键名。

108.2 模板对象与 JSON 序列化

自动装配提供两个模板：StringRedisTemplate 专管字符串键值；RedisTemplate<Object, Object> 可存对象，但默认 JDK 序列化会产生不可读的二进制乱码，必须自定义为 JSON 序列化。

模板适用内容说明
StringRedisTemplate字符串、计数器、验证码、token 黑名单键值均为 String，无需额外序列化配置
RedisTemplate<String, Object>缓存 VO、列表、对象集合需配置 key 用 String、value 用 Jackson JSON 序列化
 
// config/RedisConfig.java
@Configuration
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);

        StringRedisSerializer stringSerializer = new StringRedisSerializer();
        Jackson2JsonRedisSerializer<Object> jsonSerializer =
                new Jackson2JsonRedisSerializer<>(Object.class);

        ObjectMapper mapper = new ObjectMapper();
        // 反序列化时保留类型信息，否则 List<RequirementVO> 会变成 LinkedHashMap
        mapper.activateDefaultTyping(
                mapper.getPolymorphicTypeValidator(),
                ObjectMapper.DefaultTyping.NON_FINAL);
        mapper.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        jsonSerializer.setObjectMapper(mapper);

        template.setKeySerializer(stringSerializer);          // 键：字符串
        template.setHashKeySerializer(stringSerializer);
        template.setValueSerializer(jsonSerializer);          // 值：JSON
        template.setHashValueSerializer(jsonSerializer);
        template.afterPropertiesSet();
        return template;
    }
}
// 注入使用：热门需求列表缓存（service 层）
@Service
public class RequirementCacheService {
    private static final String HOT_KEY = "req:hot:list";
    private static final Duration HOT_TTL = Duration.ofMinutes(10);

    private final RedisTemplate<String, Object> redisTemplate;
    public RequirementCacheService(RedisTemplate<String, Object> t) { this.redisTemplate = t; }

    public void saveHotList(List<RequirementVO> list) {
        redisTemplate.opsForValue().set(HOT_KEY, list, HOT_TTL);
    }

    @SuppressWarnings("unchecked")
    public List<RequirementVO> getHotList() {
        Object cached = redisTemplate.opsForValue().get(HOT_KEY);
        return cached == null ? null : (List<RequirementVO>) cached;
    }

    public void evictHotList() {
        redisTemplate.delete(HOT_KEY);
    }
}
序列化坑不配置 JSON 序列化直接存对象，redis-cli 里看到的是带 \xac\xed 的二进制；反过来只配 value 序列化、忘了配 key 序列化，键名同样乱码。改配置后旧缓存要清空再测，避免新旧格式混存。

108.3 Cache-Aside 旁路缓存策略

项目最常用的是 Cache-Aside（旁路缓存）：缓存由业务代码旁路维护，不依赖缓存层自动联动。读路径先查缓存、未命中再查库并回填；写路径先更新数据库、再删除缓存。

图 108-1 Cache-Aside 标准读写流程

// service/impl/RequirementServiceImpl.java —— 详情接口接入缓存
@Override
public RequirementVO detail(Long id) {
    String key = "req:detail:" + id;
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached instanceof RequirementVO vo) {
        return vo;                                   // 命中直接返回
    }
    Requirement req = requirementMapper.selectById(id);
    if (req == null) {
        // 空值也缓存一小段时间，防穿透（见 108.5）
        redisTemplate.opsForValue().set(key, EMPTY_MARK, Duration.ofMinutes(2));
        throw new BizException(ErrorCode.REQUIREMENT_NOT_FOUND);
    }
    RequirementVO vo = RequirementVO.from(req);
    redisTemplate.opsForValue().set(key, vo, Duration.ofMinutes(15));  // 回填带 TTL
    return vo;
}

// 更新草稿：先更库，再删缓存（顺序见 108.4）
@Override
@Transactional(rollbackFor = Exception.class)
public void updateDraft(Long id, RequirementUpdateDTO dto, Long userId) {
    Requirement req = requireById(id);
    if (!req.getCreatorId().equals(userId)) throw new BizException(ErrorCode.NO_PERMISSION);
    RequirementStatus.from(req.getStatus())
            .transition(RequirementStatus.DRAFT);   // 状态校验
    req.setTitle(dto.getTitle());
    req.setDescription(dto.getDescription());
    requirementMapper.updateById(req);
    redisTemplate.delete("req:detail:" + id);       // 删除旧缓存，而非覆盖写入
}

108.4 缓存一致性与延迟双删

缓存与数据库不可能强一致：两次写并发、缓存过期回源都可能读到旧值。工程上追求最终一致 + 窗口期可控，而不是追求毫秒级一致。

策略动作顺序问题与适用
先更库后删缓存（默认）更新数据库 → 删除缓存 → 下次读回填实现简单；并发读在删缓存前可能读到旧值，窗口很短；本项目默认方案
先删缓存后更库删除缓存 → 更新数据库删缓存后、更库前有读请求回源并回填旧值，脏数据留存到过期，不推荐
延迟双删更库 → 删缓存 → 延迟数百毫秒 → 再删一次缓存压低并发回填旧值概率；需异步任务或延时队列，强一致场景才上
订阅 binlog / 消息队列数据库变更经 MQ 通知缓存删除方解耦与最终一致的进阶做法，109 章消息队列可承接
 
// 延迟双删示意：第二次删除用线程池异步延时执行（教学版）
private final ScheduledExecutorService scheduler =
        Executors.newScheduledThreadPool(2, new NamedThreadFactory("cache-del"));

private void updateWithDoubleDelete(Long id, RequirementUpdateDTO dto, Long userId) {
    Requirement req = requireById(id);
    // ① 先更新数据库
    req.setTitle(dto.getTitle());
    requirementMapper.updateById(req);
    // ② 第一次删缓存
    redisTemplate.delete("req:detail:" + id);
    // ③ 延迟 500ms 再删一次，覆盖并发读回填旧值的窗口
    scheduler.schedule(() -> redisTemplate.delete("req:detail:" + id),
            500, TimeUnit.MILLISECONDS);
}
缓存与事务的边界删除缓存不要放在 @Transactional 方法中间：事务未提交时删缓存，并发读会从库中读到未提交前的旧值并回填。正确做法：事务提交之后再删缓存（方法返回后删除，或注册 TransactionSynchronization.afterCommit 回调）。

108.5 穿透、击穿、雪崩与应对

三类问题都表现为"缓存没挡住、压力打到数据库"，但成因不同，应对手段也不同；面试与排查时先分清属于哪一类。

问题成因应对手段本项目落地
穿透查询根本不存在的数据（如不存在的 id、恶意构造参数），缓存挡不住，每次直达数据库空值短 TTL 缓存；布隆过滤器前置拦截；入参合法性校验详情接口缓存空值标记 2 分钟（见 108.3）
击穿单个热点键过期瞬间，大量并发同时回源同一把钥匙，数据库瞬时压力尖峰热点键永不过期（后台异步刷新）；分布式锁/互斥回源；随机偏移 TTL热门列表不设短 TTL，由定时任务刷新
雪崩大批缓存键同时过期，或 Redis 整体宕机，请求集中压垮数据库TTL 加随机偏移；多级缓存；服务降级兜底；Redis 集群高可用；限流各键 TTL 在基准值上随机 ±20%，列表接口预留空兜底
 
// 互斥回源示意：热点键未命中时，先抢分布式锁再查库，避免并发穿透
public RequirementVO detailWithLock(Long id) {
    String key = "req:detail:" + id;
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached instanceof RequirementVO vo) return vo;

    String lockKey = "lock:req:" + id;
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", Duration.ofSeconds(5));
    try {
        if (Boolean.TRUE.equals(locked)) {
            // 抢到锁：查库并回填；双重检查，防止前一个线程刚回填完
            cached = redisTemplate.opsForValue().get(key);
            if (cached instanceof RequirementVO vo2) return vo2;
            // ... 查库、回填逻辑
        } else {
            // 没抢到锁：短暂自旋后重读缓存
            Thread.sleep(50);
            return detail(id);
        }
    } finally {
        if (Boolean.TRUE.equals(locked)) redisTemplate.delete(lockKey);
    }
    return null;
}
记忆线索穿透是"查不存在"，击穿是"一个热点过期"，雪崩是"一片同时过期或缓存宕机"——按请求特征（是否存在、数量多少）区分，再套对应方案。

108.6 注解缓存与高频坑

Spring Cache 注解（@Cacheable、@CachePut、@CacheEvict）在方法级声明缓存行为，底层仍由 Redis 承载；简单查询可以用，复杂一致性与互斥回源仍需手写模板代码。

// 开启注解缓存：启动类或配置类上
@EnableCaching
@Configuration
public class CacheConfig { }

// 方法级声明：第一次调用查库并缓存，后续命中缓存
@Cacheable(cacheNames = "req:hot", key = "'list'", sync = true)
public List<RequirementVO> hotList() {
    return requirementMapper.selectHotList(PageRequest.of(0, 10));
}

// 变更后清空缓存集合
@CacheEvict(cacheNames = "req:hot", allEntries = true)
public void refreshHotList() { }

// 注意：@Cacheable 同类内部方法调用不生效（代理自调用问题，见第 78 章），
// 且缓存对象需要可序列化；复杂 TTL 策略需自定义 CacheManager

108.6.1 本章两个高频坑回顾

坑一：序列化乱码键或值用默认 JDK 序列化，redis-cli 肉眼不可读、跨语言无法消费；务必显式配置 String 键序列化 + Jackson 值序列化，并处理泛型类型信息。
坑二：缓存删除混在事务内事务提交前删缓存会让并发请求回填旧值；把删缓存动作放到事务提交后（afterCommit 回调或方法外层），是 106 章事务边界在缓存场景的延伸。

✓ 本章小结

要点一句话
接入配置starter-data-redis 自动装配；StringRedisTemplate 管字符串，RedisTemplate 配 JSON 序列化存对象
Cache-Aside读：先缓存未命中回源回填；写：先更库后删缓存，不直接覆盖缓存值
一致性追求最终一致；先库后删为默认，延迟双删应对并发回填；删缓存放在事务提交之后
三大问题穿透缓存空值/布隆，击穿互斥回源/热点不过期，雪崩 TTL 随机 + 降级兜底
注解缓存@Cacheable 适合简单查询；注意代理自调用失效与序列化要求
