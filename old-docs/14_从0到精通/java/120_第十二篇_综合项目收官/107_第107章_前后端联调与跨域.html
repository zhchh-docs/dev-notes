107.1 同源策略与 CORS 原理

同源策略是浏览器的安全护栏：页面脚本只能读取同协议、同域名、同端口下的响应；跨域请求其实发得出去，只是响应被浏览器拦住、不给页面脚本读。

107.1.1 什么叫同源

页面地址 https://web.example.com:5173请求地址是否同源
https://web.example.com:5173/other同协议同域名同端口同源 ✓
http://web.example.com:5173/api协议不同（http vs https）跨域 ✗
https://api.example.com:5173域名不同（子域不同）跨域 ✗
https://web.example.com:8080/api端口不同跨域 ✗
https://localhost:8080/api本地开发前后端分离跨域 ✗

107.1.2 简单请求与预检请求

CORS（Cross-Origin Resource Sharing，跨域资源共享）是浏览器与后端之间的一套协商机制：后端在响应头里声明"允许哪个来源、哪些方法、哪些头"，浏览器据此决定是否把响应交给页面脚本。

  • 简单请求：方法为 GET / HEAD / POST，头只含 Accept、Content-Type（限 text/plain、multipart/form-data、application/x-www-form-urlencoded）等安全头——直接发请求，响应头里带 Access-Control-Allow-Origin 即可；
  • 预检请求：PUT / DELETE、带 application/json、自定义头（如 Authorization）等"非安全"请求，浏览器先发一个 OPTIONS 请求询问服务器是否允许，拿到放行响应后才发真正的业务请求。

107.2 Spring 两种跨域配置

Spring MVC 提供两个粒度的跨域开关：注解级 @CrossOrigin 挂在控制器上；全局级 WebMvcConfigurer.addCorsMappings 统一配置。项目用全局配置，注解只在个别接口需要特殊来源时临时覆盖。

维度@CrossOrigin（注解）WebMvcConfigurer（全局）
粒度单个类 / 单个方法按路径模式批量生效
适用场景个别接口对外开放、第三方回调地址固定项目统一前后端分离、一组接口同一套规则
维护位置散落在 controller 源码里集中在配置类，环境差异放配置文件
权限叠加多个方法规则不同，容易遗漏一处修改全局生效，便于审计白名单
 
// ① 注解级：只给登录接口放开本地开发来源
@RestController
@RequestMapping("/api/auth")
@CrossOrigin(origins = "http://localhost:5173",
             allowedHeaders = {"Authorization", "Content-Type"},
             methods = {RequestMethod.GET, RequestMethod.POST, RequestMethod.OPTIONS})
public class AuthController { /* ... */ }
// ② 全局级：config/WebConfig.java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Value("${app.cors.allowed-origins:http://localhost:5173}")
    private List<String> allowedOrigins;

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins(allowedOrigins.toArray(new String[0]))
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("Authorization", "Content-Type")
                .exposedHeaders("Authorization")     // 前端可读回的响应头
                .allowCredentials(true)                // 携带 Cookie / 凭证时必须为 true
                .maxAge(3600);                         // 预检结果缓存时长（秒）
    }
}
# application-dev.yml：开发环境白名单，生产环境在配置中心另配
app:
  cors:
    allowed-origins:
      - http://localhost:5173
      - http://127.0.0.1:5173
关键约束设置 allowCredentials(true) 时，allowedOrigins 不能写 *——浏览器规范禁止通配来源携带凭证；需要多来源就逐个枚举。

107.3 开发代理：前端视角

前端工程师更熟悉的另一条路：开发服务器（Vite / Webpack Dev Server）在本机起代理，浏览器请求自己同源的 /api，由开发服务器在服务端转发到后端 8080。跨域发生在浏览器到后端这一段，代理转发在本机服务端，不经过浏览器同源策略。

// vite.config.ts —— 前端工程开发代理配置
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    port: 5173,
    proxy: {
      // 前端代码里写相对路径 /api，命中后转发到后端
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,          // 修改请求头 Host 为后端域名
        rewrite: (path) => path     // 本项目后端同样以 /api 开头，无需重写
      },
      '/ws': {                       // 预留：后续 WebSocket / SSE 代理
        target: 'ws://localhost:8080',
        ws: true
      }
    }
  }
})
// 前端请求封装（axios）：baseURL 留空，走同源 + 开发代理
import axios from 'axios'

const request = axios.create({
  baseURL: '/api',
  timeout: 10000
})

// 请求拦截器：附加 JWT
request.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截器：统一拆 R<T>，code !== 0 走错误提示
request.interceptors.response.use(
  (resp) => {
    const body = resp.data
    if (body.code !== 0) {
      return Promise.reject(new Error(body.message))
    }
    return body.data
  },
  (error) => Promise.reject(error)
)

export default request
两种方案怎么选本地开发优先用代理：后端可以保持默认不放开跨域，生产环境由 Nginx 同源反代；后端 CORS 配置保留，用于独立部署前端站点、第三方页面直连后端的场景。开发期两套机制并存不冲突，但要清楚当前请求走的是哪一条。

107.4 联调流程与字段对齐

联调不是"前后端各写完再连线"，而是按接口清单逐个打通：先文档、再 mock、后对接、最后联调异常路径。越早对齐字段，返工越少。

步骤动作负责方产出 / 验收
① 接口评审按 105.6 接口表确认方法、路径、入参、出参、错误码前后端 + 产品签字确认的接口文档
② 后端出桩先返回固定 mock 数据，字段结构与文档一致后端可访问的假接口
③ 前端 mock前端按文档用 mock 数据开发页面，不依赖后端真实实现前端页面静态流程可点通
④ 对接联调逐个接口切换真实后端，核对状态码、字段名、类型、枚举值双方正常路径全部打通
⑤ 异常路径覆盖参数错误、未登录、无权限、业务驳回等分支提示双方错误文案与错误码对应一致

107.4.1 字段对齐检查表

核对项正确做法常见不一致
命名风格JSON 统一 camelCase（realName、expectDate）后端实体下划线、前端直接绑定导致 undefined
数字类型id、viewCount 用 number；大数字 id 超 2^53 用字符串雪花 id 被前端 Number 精度截断
日期格式字符串 yyyy-MM-dd HH:mm:ss，ISO 日期 yyyy-MM-dd直接返回时间戳或 LocalDateTime 序列化格式各异
空值表达可选字段缺失时给 null，列表空给 []，不给字符串 "null"null 与 "" 混用导致前端判断分支报错
枚举取值状态/优先级字符串枚举前后端共用一份清单前端写死中文展示，后端改英文枚举后全部错乱

107.5 OpenAPI 接口文档

手写文档最容易过期。引入 springdoc-openapi-starter-webmvc-ui 后，启动应用访问 /swagger-ui.html 即可看到自动生成的接口清单、入参出参模型与在线调试；文档从代码注解生成，改动代码文档自动跟随。

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.6.0</version>
</dependency>
// 接口上补充说明注解（教学项目按需添加，不必每个方法都写满）
@Operation(summary = "登录", description = "校验账号口令后签发 JWT")
@PostMapping("/login")
public R<LoginVO> login(@Valid @RequestBody LoginDTO dto) { /* ... */ }

@Schema(description = "登录入参")
public class LoginDTO {
    @Schema(description = "登录名", example = "zhang.wei")
    private String username;
    @Schema(description = "口令")
    private String password;
}

生产环境可在配置中关闭 Swagger 入口或加访问鉴权，避免接口结构暴露；联调期它是前后端对齐字段的第一参考。

107.6 联调高频坑与排查顺序

坑一：预检 OPTIONS 被拦截Spring Security 过滤链若默认拦截所有方法，OPTIONS 会被 401 挡掉，真实请求自然发不出去。排查顺序：浏览器 F12 → Network → 找到 OPTIONS 请求 → 看状态码（401/403/404）与响应头是否含 Access-Control-Allow-Origin；放行 OPTIONS 方法或在 CORS 配置中允许预检通过。
坑二：白名单过宽留下安全隐患图省事写 allowedOrigins("*") 又放开 allowCredentials(true)，浏览器直接拒绝；即便不带凭证，通配来源也意味着任意站点页面都能调你的接口。生产环境必须枚举受信域名，禁止通配。
坑三：字段类型与枚举不一致后端返回字符串状态、前端按数字比较；日期返回时间戳、前端按字符串格式化；id 是长整型、前端按字符串展示。这类问题不报跨域错，但页面渲染异常。排查方式：先在 Network 看原始 JSON，再对照接口文档逐项核对类型。
排查口诀页面报错先看 F12：红条 CORS 字样 → 预检或响应头问题；请求没发出 → 看 OPTIONS；请求发出但报错 → 看状态码与响应体；数据显示不对 → 核对字段类型与枚举。不要一上来改后端代码。

✓ 本章小结

要点一句话
同源与 CORS浏览器拦截跨域响应；CORS 靠响应头声明允许的来源、方法与头
预检请求非简单请求先发 OPTIONS 协商，预检不过真实请求不会发出
两种配置注解级临时覆盖，全局配置统一白名单；带凭证时来源不能写通配
开发代理Vite 代理在本机服务端转发，绕开浏览器同源策略；生产由 Nginx 同源反代
联调纪律先文档后 mock 再对接；字段命名、类型、日期、枚举、空值逐一核对
