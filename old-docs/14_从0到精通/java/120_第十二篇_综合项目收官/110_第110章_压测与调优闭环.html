110.1 压测目标与核心指标

压测不是"把并发调大看崩不崩"，而是带着目标施压：在约定的业务量级下，接口要达到什么吞吐、响应多快、错误率多低。指标先写进测试计划，压测结果才好判断达标与否。

指标含义本项目目标（示例）为什么重要
QPS / TPS每秒成功处理的请求数（接口吞吐）需求列表 ≥ 300 QPS衡量系统处理能力上限
平均 RT全部请求响应时间的算术平均< 120ms反映整体体验，但会被少数快请求掩盖长尾
TP99 / P9999% 请求的响应时间上限（长尾）< 400ms比平均值更接近真实用户最差体验
TP9595% 请求的响应时间上限< 250ms常用服务等级约定口径
错误率失败请求数 / 总请求数（5xx、超时、断言失败）< 0.1%压测期间吞吐再高，错误率失控也不达标
并发数同时在途的请求线程 / 用户数200 线程阶梯加压施压手段，不是服务能力本身
指标纪律对外承诺性能时用 TP99 而不是平均值：平均 RT 好看可能是大量缓存命中请求把长尾平均掉了；压测报告要同时给出吞吐、分位时延、错误率三组数字，缺一不可。

110.2 JMeter 使用与结果解读

JMeter 是 Java 桌面压测工具，本项目对登录、需求列表、详情三个接口施压。核心组件：线程组（并发与节奏）→ HTTP 请求默认值 → 采样器（具体接口）→ 监听器（聚合报告、查看结果树）。

110.2.2 聚合报告列怎么读

列名含义关注点
Label采样器名称，按接口分组统计一个接口一行，不要多个接口混在同一采样器
# Samples发出的请求总数与预期样本量核对，排除中途退出
Average平均响应时间（ms）整体参考，配合分位值看
90% Line / 99% LineTP90 / TP99 响应时间上限长尾指标，主要调优依据
Throughput吞吐量，约等于 QPS随并发上升到拐点后不再增长即瓶颈初现
Error %错误请求占比压测中优先清零错误，再谈时延

命令行非 GUI 模式适合正式压测（GUI 本身消耗内存，结果偏小）：先在 GUI 调好脚本保存为 req-test.jmx，再用命令行运行并导出报告。

# 非 GUI 压测并生成 HTML 报告（压测机执行）
jmeter -n -t req-test.jmx ^
  -Jtoken=eyJhbGciOiJIUzI1NiJ9... ^
  -l result/result.jtl ^
  -e -o result/report

110.3 压测流程与环境纪律

压测结论可信的前提是环境可控：共享环境上压测，别人的干扰会让你的数据毫无参考价值。按"准备 → 预热 → 阶梯加压 → 采集 → 复测"的顺序执行。

  1. 环境隔离：专用压测环境，数据库独立，数据量与生产同量级（如 10 万条需求记录）；不要在共享开发库上跑压测；
  2. 数据准备：账号提前登录取令牌；列表筛选条件覆盖真实分布；详情接口参数化读取真实存在的 id，避免大面积 404 干扰统计；
  3. 预热：先跑 1–2 分钟让 JIT 编译完成、缓存填充、连接池建立，正式统计从稳定阶段开始；冷启动数据不纳入报告；
  4. 阶梯加压：50 → 100 → 200 → 300 线程逐级提升，每级观察吞吐拐点与时延突变点，而不是一步拉满；
  5. 同步采集：压测期间采集服务器 CPU、内存、GC、线程数、数据库慢查询与连接池状态，事后才能把现象对应到资源；
  6. 复测留档：每次调优后在相同环境、相同脚本、相同数据上复测，指标前后可比。
环境纪律压测机与被压对象分开部署，避免 JMeter 进程和应用争抢同一台机器的 CPU；压测机带宽与连接数也要留出余量，否则瓶颈在客户端而不在服务端。

110.4 瓶颈定位五个方向

RT 升高、吞吐上不去时，按"外部观测 → 资源指标 → 代码链路"逐层收窄：先确认瓶颈在服务端还是数据库，再定位到具体资源与方法。

方向典型现象排查手段常见根因
CPUCPU 使用率打满、上下文切换高top / htop 看进程；jstack 抓线程栈；看是否有死循环、正则回溯、频繁序列化热点方法、日志过载、循环内对象创建
内存 / GCRT 周期性毛刺、频繁 Full GCjstat 看 GC 频率与耗时；jmap 导出堆直方图；VisualVM / JConsole 观察大对象缓存、内存泄漏、无界集合
IO / 数据库CPU 不高但 RT 高，连接池等待数据库慢查询日志、EXPLAIN 执行计划；看锁等待与索引命中缺索引、联表过多、N+1 查询、大事务
锁 / 并发线程长时间 BLOCKED / WAITING，吞吐卡在某个并发数jstack 看锁竞争栈；线程池队列长度；synchronized / Lock 竞争点锁粒度太粗、共享状态竞争、线程池过小
下游 / 连接外部调用超时拉高整体 RT接口耗时拆分日志；连接池监控；网络与 DNS 解析耗时未设超时、连接耗尽、重试风暴
 
-- 排查慢查询：需求列表按状态 + 优先级 + 时间倒序，先看执行计划
EXPLAIN SELECT id, title, status, priority, creator_id, view_count, create_time
FROM requirement
WHERE status = 'PENDING'
  AND priority = 'P1'
ORDER BY create_time DESC
LIMIT 20;

-- 若 type 为 ALL（全表扫描），补联合索引覆盖过滤 + 排序
CREATE INDEX idx_status_priority_time
    ON requirement (status, priority, create_time);

110.6 压测高频坑

坑一：压测环境失真本机 IDE 启动 + 开发库 + 没预热，测出来的是"冷启动单机演示值"，不能作为上线容量依据。正式结论必须在隔离环境、生产同规格配置、同量级数据上得出。
坑二：GC 干扰与测量错位预热不足时 JIT 未编译、缓存未填充，前几轮请求 RT 畸高被计入平均；一次调多组变量（索引 + 缓存 + 线程池同时改），事后无法归因；报告只贴平均 RT 不贴 TP99 与错误率。
坑三：长连接与连接池误配Tomcat 线程数、Hikari 连接数拍脑袋调大：数据库连接数超过 MySQL max_connections 反而互相等待；长事务占住连接不释放，并发上来连接池先耗尽。容量参数要与数据库最大连接、下游超时一起核算。
复盘要求每轮调优留下三件证据：压测脚本（jmx）、结果报告（jtl / HTML）、变更记录（改了什么、为什么改、指标前后对比）。面试讲项目时，这就是最有说服力的性能故事素材。

✓ 本章小结

要点一句话
指标体系QPS 看吞吐、TP99 看长尾体验、错误率看稳定性；三者一起达标才算通过
JMeter 流程线程组施压、采样器定义接口、聚合报告读数；正式压测用命令行非 GUI 模式
环境纪律隔离环境、同量数据、先预热后统计、压测机与服务端分离、阶梯加压
瓶颈定位按 CPU、内存 GC、IO 数据库、锁、下游连接五个方向逐层收窄，证据先行
调优闭环一次一个变量，复测同环境对比；脚本、报告、变更记录留档，循环到达标
