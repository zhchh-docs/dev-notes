112.1 单体与微服务对比

需求管理系统是典型单体：一个进程、一个数据库、一套部署包。微服务不是单体的"高级形态"，而是为了解决规模增长后的协作与扩展问题付出额外复杂度的架构选择；小团队、小体量项目强行拆服务，往往得不偿失。

维度单体架构微服务架构
部署单元一个应用整体打包部署，启动简单多个独立服务分别部署、独立发布
扩展方式整体水平扩容，资源利用率受最薄弱模块限制按服务粒度独立扩容，热点模块单独加机器
故障隔离一个模块 OOM 可能拖垮整个进程单服务故障可被隔离与降级，不直接波及全局
团队协作模块边界靠代码约定，多人并行开发易冲突服务按业务边界划分，团队自治、独立迭代
运维复杂度监控、部署、配置集中，链路简单需要服务发现、配置管理、链路追踪、灰度发布等配套体系
数据一致性本地数据库事务即可保证一致性跨服务调用引入分布式事务与最终一致问题
适用阶段业务早期、团队小、功能边界尚在收敛业务规模与团队规模增长、模块差异显著时再拆
演进顺序先把单体写清楚（分层、模块边界、数据库设计规范），再在真实压力点上拆服务：先拆读写压力最大的模块、再拆协作最独立的模块，而不是按目录平均切成十几个服务。
架构判断面试中被问"为什么我们项目用单体"，标准答案不是"不会微服务"，而是：业务体量、团队规模、发布频率都未到拆分门槛；单体优先保证交付效率与可维护性，把复杂度留给真正需要的时刻。

112.2 Spring Cloud 核心组件

Spring Cloud 是一套围绕 Spring Boot 的微服务工具箱，组件对应分布式系统的各个职责：服务注册发现、统一入口、配置分发、服务间调用、熔断限流。本项目单体中这些职责由进程内约定承担，演进后由下表组件承接。

职责主流组件作用一句话
注册中心Nacos / Eureka服务启动时登记自己的地址，调用方从注册表找到目标服务实例；服务上下线实时感知
网关Spring Cloud Gateway系统统一入口：路由转发、鉴权校验、限流、跨域与日志前置处理，替代单体中的前置控制器
配置中心Nacos Config / Spring Cloud Config各服务配置集中管理、动态刷新，不再逐个改本地配置文件重启
服务调用OpenFeign声明式 HTTP 客户端：写接口加注解即可调用另一个服务，把远程调用伪装成本地方法
熔断限流Sentinel / Resilience4j下游故障时快速失败、降级兜底，限制单服务并发与流量，防止故障沿调用链蔓延（一句话了解即可）
 
# 服务端 application.yml：注册到 Nacos 并携带服务名
spring:
  application:
    name: requirement-service        # 服务名，调用方按此名寻址
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
      config:
        server-addr: localhost:8848
        file-extension: yaml
// 服务间调用示例：OpenFeign 声明式接口
@FeignClient(name = "user-service")
public interface UserClient {

    // 调用 user-service 的 /api/users/{id} 接口，如同调用本地方法
    @GetMapping("/api/users/{id}")
    UserVO getUserById(@PathVariable("id") Long id);
}

// 业务服务中注入使用，方法内部完成负载均衡、超时与重试配置
@Service
public class RequirementQueryService {
    private final UserClient userClient;
    public RequirementQueryService(UserClient c) { this.userClient = c; }

    public RequirementVO withCreatorName(Long requirementId) {
        RequirementVO vo = requirementMapper.toVO(requirementId);
        vo.setCreatorName(userClient.getUserById(vo.getCreatorId()).getRealName());
        return vo;
    }
}

112.3 分布式三大难题

单体里"一句话调用、一个本地事务、一把 JVM 锁"就能解决的事，拆到多服务、多实例后会变成三类经典难题；了解问题与解法方向，比背组件 API 更重要。

难题单体对应物分布式解法方向常见技术
链路追踪本地方法调用栈 + 日志时间线跨服务生成统一 traceId，串联网关、各服务、数据库与 MQ 的调用链，按链路排查慢请求与错误SkyWalking、Zipkin、Spring Cloud Sleuth
分布式事务@Transactional 本地事务跨服务写操作无法放进一个本地事务：强一致用补偿协议，最终一致用消息驱动的本地事务表 / 状态机对账Seata（AT / TCC）、本地消息表、TCC 模式
分布式锁synchronized / ReentrantLock（单 JVM）多实例部署时本地锁互斥失效，需要跨实例抢占同一把锁，注意锁过期、误删与续期问题Redis 锁（Redisson）、ZooKeeper 临时节点
延伸线索108 章的 Redis 缓存一致性、109 章的消息幂等，正是分布式事务与最终一致思想在单体项目里的预演；110 章压测留下的慢日志，未来要靠链路追踪才能定位到跨服务的真实耗时点。

112.4 云原生概念版图

云原生是一套"面向云环境设计与运行应用"的方法论：把应用打包成标准化镜像，交给编排平台调度部署，用自动化流水线交付，再以日志、指标、链路三套观测体系盯住运行状态。

概念作用与本项目的对应
容器（Docker）把应用与运行环境打包成镜像，开发、测试、生产环境一致运行110 章环境失真问题，本质就是缺少标准化镜像；进阶时为本项目写 Dockerfile
编排（Kubernetes）管理容器副本、扩缩容、服务发现、故障重启与滚动发布替代手工启停脚本：声明期望副本数，平台自动调度
DevOps / CI-CD提交代码后自动构建、测试、打包、部署，流水线可追溯第十一篇工程化内容的线上化延伸：单测与构建纳入流水线
可观测性日志（Logs）、指标（Metrics）、链路（Traces）三件套覆盖运行时排障110 章压测采集的 CPU、GC、慢查询指标是可观测性的雏形
 
# Dockerfile：把需求管理系统打成镜像（进阶练习用）
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/req-manage-system.jar app.jar
EXPOSE 8080
# 接入 JVM 堆参数与容器内存感知；GC 日志输出到标准输出交给平台采集
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
# k8s 部署清单片段：声明 2 个副本与端口映射（了解结构即可）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: requirement-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: requirement-service
  template:
    metadata:
      labels:
        app: requirement-service
    spec:
      containers:
        - name: app
          image: req-manage-system:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "0.5"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"

112.5 进阶学习路线图

不建议直接跳入微服务与 K8s 深水区：顺序是先把后端基础与单体工程打扎实，再学服务化组件，最后进入容器编排与平台工程。每个阶段都要有可演示的产出物，而不是只看视频收藏教程。

阶段三容器化、K8s 部署、CI/CD、可观测三件套写 Dockerfile 与部署清单，搭最小流水线，接入指标与链路面板提交代码后镜像自动构建并部署到集群，故障可观测

112.6 全书主线回顾与寄语

走到第 112 章，回头看这条主线：我们从语法与程序结构出发，经过面向对象、集合与核心 API，进入异常与 IO，再到反射、注解与函数式编程；随后攻下并发与 JVM 两大硬骨头，接入数据库与持久层，用 Spring 把对象装配起来，在 Spring Boot 与 Web 章节搭建应用骨架，再用工程化与测试保证质量，最终在需求管理系统里把所有知识拧成一根绳。

  • 基础篇（一至五篇）：Java 语法、OOP、集合、异常 IO、反射注解、函数式——写出规范程序的语言底座；
  • 运行篇（六至七篇）：并发编程与 JVM——理解程序在多线程与内存模型下如何真实运行；
  • 存储篇（第八篇）：SQL、索引、事务与持久层——让程序可靠地读写数据；
  • 框架篇（第九至十篇）：Spring IoC/AOP/事务、Spring Boot 自动装配与 Web 链路——用主流框架组织应用；
  • 工程篇（第十一篇）：构建、日志、配置、测试与性能入门——让代码经得起协作与线上考验；
  • 实战篇（第十二篇）：需求管理系统——分层实现、跨域联调、缓存、消息队列、压测闭环，再到面试梳理与进阶展望。
收官寄语书本上的章节到此结束，但工程能力的养成是长期过程：保持"先跑通、再讲清、后优化"的节奏，把每个项目都留下可复盘的文档与数据，遇到新问题先回到基础概念定位原理，再选择工具与组件。愿你在全栈路上持续迭代，代码质量与架构判断力一起升级。

✓ 本章小结

要点一句话
单体与微服务微服务用运维与分布式复杂度换协作与扩展弹性；规模未到前单体是更优解
Spring Cloud注册中心、网关、配置中心、OpenFeign、熔断限流各司其职，配套体系缺一不可
三大难题链路追踪串联跨服务请求；分布式事务靠补偿或最终一致；分布式锁解决多实例互斥
云原生容器标准化交付、K8s 调度编排、CI/CD 自动部署、日志指标链路三件套观测
进阶顺序基础单体 → 服务化 → 云原生，阶段式推进，每阶段以可运行产出验收
