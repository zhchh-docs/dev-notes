111.3 项目亮点：STAR 法则与话术

面试官问"介绍一下你的项目"，最怕听到流水账模块罗列。用 STAR 组织回答：Situation（背景）、Task（任务）、Action（动作与技术取舍）、Result（量化结果），落到本项目就是缓存、消息队列、压测调优三个可展开的亮点。

# STAR 结构骨架（每个亮点写一份 200 字以内的口头稿）
S 背景：业务场景是什么，体量与痛点是什么
T 任务：你负责解决什么具体问题，目标指标是什么
A 行动：技术方案怎么选、为什么选、放弃了什么备选；关键实现细节
R 结果：量化指标前后对比；遇到过什么问题、怎么复盘的

# 亮点一：热门需求列表缓存（108 章对应素材）
S: 需求列表是首页高频读接口，早期每次直接查 MySQL，并发上来后数据库压力集中
T: 在不引入新组件的前提下把读时延压下来，保证列表接口 TP99 达标
A: 采用 Cache-Aside 旁路缓存，热点列表 10 分钟 TTL；
   空值短缓存防穿透，互斥锁防击穿，TTL 加随机偏移防雪崩；
   写路径先更新库再在事务提交后删缓存，避免脏回填
R: 列表接口 QPS 从约 96 提升到 342，TP99 从 860ms 降到 310ms；
   过程中踩过序列化乱码与缓存删除混在事务里两个坑，复盘后沉淀成规范

# 亮点二：审批通知异步化（109 章对应素材）
S: 审批通过后要写站内信、推通知，同步调用导致主接口 RT 受下游拖累
T: 把通知链路异步化，主接口不等待通知完成，同时保证消息不丢、不重复
A: 接入 RabbitMQ，topic 交换机按事件类型路由；confirm + 手动 ack + 死信队列；
   消费端按 messageId 做幂等；消息在数据库事务提交后再发出
R: 审批接口 RT 下降，通知链路独立扩容；重复投递不产生重复通知，毒消息进入死信可重放

# 亮点三：压测调优闭环（110 章对应素材）
S: 功能完成后需要验证系统在目标并发下是否达标
T: 按 QPS 300、TP99 400ms、错误率 0.1% 的目标做压测与调优
A: JMeter 阶梯加压，同步采集 CPU / GC / 慢查询；
   定位到列表接口全表扫描与 N+1 查询；补联合索引、缓存热点、去掉循环查库
R: 复测 QPS 342、TP99 310ms、错误率 0.02%，形成可复用的压测脚本与报告模板
表达要领Action 部分要讲"为什么这样选、备选方案为什么没要"；Result 部分必须有数字与前后对比。没有量化结果时，讲清"服务了多少用户量 / 解决了什么线上问题 / 沉淀了什么规范"。

111.4 系统设计题答题套路

设计题不问标准答案，而看思路是否完整、取舍是否合理。按四步走：先澄清需求与边界，再估算量级，然后画架构，最后深入关键细节；每一步主动向面试官确认，不要一上来堆技术名词。

# 系统设计题四步框架（以"设计一个需求管理系统"为例示范）

第一步：需求澄清（先问清楚，避免答错方向）
- 核心功能：提交、审批、跟踪、通知；哪些本期不做（报表、复杂 RBAC）
- 用户规模：内部团队还是公网开放；日活、峰值并发估计量级
- 非功能要求：可用性、时延、数据一致性强度、是否需要离线统计

第二步：量级估算（把定性需求变成数字）
- 假设日活 1000、人均浏览 20 次页面；列表接口峰值 QPS = ？
- 需求数据量：年新增万级；通知消息量与审批动作同量级
- 据此判断：单体可支撑，缓存接热点，消息队列解耦通知；暂不需要分库分表

第三步：架构草图（分层 + 中间件 + 数据流）
- 前端 / 网关 → 应用层（controller/service/mapper）→ MySQL
- 旁路缓存挡热点读；MQ 承接通知异步链路；定时任务刷新热门列表
- 画出：请求主链路、异步链路、数据存储与失效策略

第四步：关键细节深挖（面试官追问的方向）
- 状态流转合法性如何保证 → 状态机枚举表（106.6）
- 缓存一致性怎么保证 → 先库后删 + 事务提交后删（108.4）
- 消息重复 / 丢失怎么办 → 幂等 + confirm + 手动 ack + 死信（109.6）
- 容量与瓶颈 → 压测指标、连接池与线程池核算（110）
- 取舍说明：为什么没上微服务、为什么没做读写分离（体量未到，先保简单可维护）
阶段该做什么常见失分动作
需求澄清确认功能边界、用户量级、非功能指标直接假设全部需求都要做，最后方案撑不住
量级估算由用户量推出 QPS、数据量、存储增长只画架构图不做估算，选型没有依据
架构设计分层、模块划分、数据流、中间件位置堆砌 Redis / MQ / 微服务而不说明引入理由
细节深挖一致性、并发、可用性、缓存失效、故障兜底被追问到存储细节时回答不出"边界情况怎么处理"

111.5 查漏补缺学习路线

对照 111.2 清单标记薄弱点后，按"基础题先归零、框架题讲透链路、项目题补量化"的顺序补，而不是按章节顺序重读一遍全书。

薄弱类型复习动作验收标准
概念记不准（集合、锁、隔离级别）重读对应章节，手写对比表，把易混点列成一行一条不看资料写出对比表，并各举一个代码示例
框架链路说不清（MVC、Bean 生命周期、自动装配）画时序图 / 流程图，标注关键接口与扩展点能对着图把请求或启动过程讲满 5 分钟
中间件只懂配置不懂原理回到 108、109 章补穿透 / 击穿 / 雪崩与可靠性链路，结合项目讲方案能回答"不用这个组件会怎样、换一个怎么取舍"
项目讲不出细节与数字完善 111.3 的 STAR 稿子，补压测指标与踩坑复盘每个亮点 2 分钟讲完，含背景、取舍、结果、复盘
系统设计无框架每周精练一道公开设计题，按四步框架白板作答并找人追问30 分钟内完成需求澄清、估算、草图、细节分层
对前端转全栈的背景补充一句：前端经历中的组件状态管理、工程化、联调排障经验不是废稿——它们对应后端的状态设计、构建测试与接口对齐能力，面试时主动把两边经验连成一条成长线。

111.6 面试表达常见坑

坑一：背书式回答把博客定义原文背出来，一追问"在你项目里怎么用的"就接不上。正确做法：概念之后立刻跟一个自己项目的例子，被追问细节时往实现与取舍上引；记不清的边界诚实说"这个点我在 XX 章节看过，当前项目还没遇到，我的理解是……"。
坑二：忽略项目细节简历写了"使用 Redis 优化性能"，但缓存什么数据、TTL 多少、一致性怎么保证、遇到什么问题全答不出——这类描述反而暴露项目深度不足。写进简历的每一个技术点，都要能展开三层细节：方案、理由、结果。
表达自检三问回答任何项目问题前先过一遍：背景痛点是什么？方案取舍是什么？量化结果是什么？三问答不出来，就说明这个点还没准备到位，需要回去补数据与复盘。
