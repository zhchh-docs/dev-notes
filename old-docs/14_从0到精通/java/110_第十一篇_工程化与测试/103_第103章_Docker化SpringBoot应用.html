103.1 Docker 基础概念

一句话定位：Docker 把应用与运行环境打包成镜像，镜像启动即容器；镜像分层存储、可复用缓存，仓库负责分发，解决"我机器上能跑"的环境漂移问题。

概念含义对照
镜像 Image只读模板，内含基础系统、JRE、应用 jar 与配置；分层叠加构建前端 npm 打包产物 dist 的环境级版本
容器 Container镜像运行后的隔离实例，文件系统可写；启停、删除互不影响一次 npm run serve 启动的进程实例
仓库 Registry镜像托管与分发服务（Docker Hub、私有 Harbor）npm registry
Dockerfile逐行声明构建步骤的脚本，docker build 生成镜像构建配置 + 运行环境声明
分层 Union FS每条指令生成一层；内容不变时该层命中缓存，加速重复构建webpack 缓存产物分片

图 103-1 自下而上叠加分层；上层不变下层全部复用缓存

# 常用镜像 / 容器命令
docker images                          # 列出本地镜像
docker ps                              # 列出运行中容器（-a 含已停止）
docker build -t bookstore-service:1.0 .
docker run -d -p 8080:8080 --name app bookstore-service:1.0
docker logs -f app                     # 跟踪容器日志
docker exec -it app bash               # 进入容器排障
docker rm -f app                       # 删除容器

103.2 Dockerfile 多阶段构建

一句话定位：第一阶段用 Maven 基础镜像编译打包，第二阶段只把 fat jar 复制进精简 JRE 镜像；构建工具与源码不进入运行镜像，产物体积与攻击面同时缩小。

# ---------- 阶段一：构建 ----------
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build

# 先复制 pom 与依赖清单，利用分层缓存：依赖不变时不重复下载
COPY pom.xml .
RUN mvn -B dependency:go-offline

# 再复制源码并打包
COPY src ./src
RUN mvn -B clean package -DskipTests

# ---------- 阶段二：运行 ----------
FROM eclipse-temurin:17-jre
WORKDIR /app

# 精简 JRE 默认不含 curl 与时区数据：安装健康检查所需工具与 tzdata，随后清理缓存层
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl tzdata \
    && rm -rf /var/lib/apt/lists/*

# 非 root 用户运行，遵循最小权限原则
RUN groupadd -r app && useradd -r -g app app

# 从构建阶段只复制产物 jar
COPY --from=builder /build/target/*.jar app.jar

USER app
EXPOSE 8080

# 数组形式 ENTRYPOINT：PID 1 直接是 java 进程，可正确接收 SIGTERM
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
  • 阶段命名：AS builder 给构建阶段起名，运行阶段用 COPY --from=builder 取产物；
  • 分层顺序：先 COPY pom.xml 下载依赖、后 COPY 源码，依赖层在代码改动时保持缓存命中；
  • 非 root 用户：容器内应用以普通用户运行，避免容器逃逸后获得 root 权限；
  • ENTRYPOINT 数组形式：避免 shell 层吞掉信号，保证 java 进程成为 PID 1 并接收停机信号（见 103.5）。

103.3 镜像分层与瘦身

一句话定位：配合第 102 章分层 jar，把依赖、加载器、代码分别 COPY 成独立层；选精简 JRE 基础镜像、排除无关文件，把镜像体积压到最小。

# 先在构建阶段解出分层 jar
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests
RUN java -Djarmode=layertools -jar target/*.jar extract

FROM eclipse-temurin:17-jre
WORKDIR /app
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl tzdata \
    && rm -rf /var/lib/apt/lists/*
RUN groupadd -r app && useradd -r -g app app

# 按从不变到易变的顺序逐层 COPY，最大化缓存命中
COPY --from=builder /build/layers/dependencies/          ./
COPY --from=builder /build/layers/spring-boot-loader/   ./
COPY --from=builder /build/layers/snapshot-dependencies/ ./
COPY --from=builder /build/layers/application/          ./

USER app
EXPOSE 8080
# 分层解包后没有独立 jar，由加载器 JarLauncher 引导启动
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
# .dockerignore：排除不进入构建上下文的文件
.git
.idea
.vscode
target/
*.md
node_modules/
logs/
Dockerfile
docker-compose.yml
基础镜像特点适用
eclipse-temurin:17-jre精简运行时，无编译工具；体积适中生产运行首选
eclipse-temurin:17-jdk含编译器与调试工具，体积更大排障镜像、需要 jcmd/jstack 的场景
alpine + JRE体积最小，但 musl libc 与部分本地库行为不同对体积极致敏感且验证过兼容性
maven:3.9-eclipse-temurin-17含 Maven 与 JDK，只用于构建阶段不进入运行镜像
瘦身检查：构建后用 docker images 看体积，docker history <镜像> 看每层大小；发现异常大层通常是源码、测试资源或依赖被误打入，回到 Dockerfile 调整 COPY 顺序与 .dockerignore。

103.4 docker-compose 编排 app + MySQL

一句话定位：compose 用一份 YAML 声明多个服务、端口、环境变量、数据卷与启动依赖关系；本地开发与演示环境一键拉起完整链路。

services:
  app:
    build: .
    container_name: bookstore-app
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: prod
      TZ: Asia/Shanghai
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/bookstore?useUnicode=true&characterEncoding=utf8
      SPRING_DATASOURCE_USERNAME: root
      SPRING_DATASOURCE_PASSWORD: root123
    depends_on:
      mysql:
        condition: service_healthy      # 等 MySQL 健康检查通过再启动 app
    volumes:
      - app-logs:/app/logs
    restart: on-failure

  mysql:
    image: mysql:8.4
    container_name: bookstore-mysql
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: bookstore
      TZ: Asia/Shanghai
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 10

volumes:
  mysql-data:
  app-logs:
  • 服务发现：compose 网络内服务名即主机名，app 用 jdbc:mysql://mysql:3306/... 连接数据库；
  • depends_on 条件化等待：仅启动顺序不够，MySQL 就绪需要时间；condition: service_healthy 配合 healthcheck 保证 app 启动时数据库可连；
  • 数据卷：mysql-data 持久化数据库文件，app-logs 把日志落到宿主机，容器删除后数据与日志不丢；
  • 环境变量覆盖：Spring Boot relaxed binding 支持 SPRING_DATASOURCE_URL 映射 spring.datasource.url，配置不进镜像。
docker compose up -d --build        # 构建并后台启动全部服务
docker compose ps                   # 查看服务状态与健康状态
docker compose logs -f app          # 跟踪应用日志
docker compose down                 # 停止并删除容器（保留数据卷）
docker compose down -v              # 连数据卷一起清空（本地重置用）

103.5 健康检查与优雅停机

一句话定位：健康检查让编排系统知道容器是否真的就绪；优雅停机让收到 SIGTERM 的应用先处理完在途请求再退出，避免请求被硬切断。

<!-- pom.xml：引入 Actuator 提供健康端点 -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
# application-prod.yml：暴露健康端点并开启优雅停机
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      probes:
        enabled: true            # 开启 readiness / liveness 探针

server:
  shutdown: graceful          # 收到停机信号后停止接收新请求，等待在途完成

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 停机宽限 30 秒，超时强制结束
# Dockerfile 内健康检查：调用 Actuator 健康端点（curl 已在运行镜像中安装）
HEALTHCHECK --interval=10s --timeout=3s --start-period=30s --retries=3 \
  CMD curl -f http://localhost:8080/actuator/health || exit 1

常见坑eclipse-temurin:17-jre 这类精简基础镜像默认不带 wget 也不带 curl，直接在 HEALTHCHECK 里调用会报 executable not found、健康检查永远 unhealthy；必须先在镜像中安装其中一个工具，或改用不含网络工具依赖的探针方案（如让应用自写健康文件、配合 Docker HEALTHCHECK 读取本地状态文件）。

停机时序：编排系统发送 SIGTERM → Spring Boot 标记就绪探针为不通过、停止接入新流量 → 在途请求在 30 秒宽限内完成 → 关闭线程池与连接池 → 进程退出；宽限到期仍未结束则被 SIGKILL 强杀。生产编排平台（Kubernetes）还会配合 preStop 钩子与 terminationGracePeriodSeconds，先摘流量再等待应用退出。

信号链路要点ENTRYPOINT 使用数组形式、java 进程为 PID 1，SIGTERM 才能直达 JVM；shell 形式 ENTRYPOINT java -jar ... 会由 shell 作为父进程转发信号，优雅停机可能失效。

103.6 常见坑：时区、字体与容器内存

① 时区偏差

JRE 基础镜像默认 UTC，日志时间与业务时间差 8 小时。三种对策叠加使用：compose 环境变量 TZ=Asia/Shanghai；JVM 参数 -Duser.timezone=Asia/Shanghai；需要系统级时间时在镜像中安装 tzdata 并挂载 /etc/localtime。

② 中文字体缺失

精简 JRE 镜像不含中文字体，导出图片、生成 PDF、验证码渲染会出现方块或乱码。需要图形输出时在运行镜像安装字体包（如 fonts-noto-cjk），纯接口服务一般无需处理。

③ 容器内存限制识别错误

Java 10 起默认开启 UseContainerSupport，JVM 自动识别容器 cgroup 内存限制并据此设定堆上限；但仍建议显式设置比例参数，避免堆外内存挤占导致 OOM：

ENTRYPOINT ["java",
  "-XX:MaxRAMPercentage=75.0",
  "-XX:InitialRAMPercentage=50.0",
  "-Dfile.encoding=UTF-8",
  "-Duser.timezone=Asia/Shanghai",
  "-jar", "/app/app.jar"]
坑现象对策
时区错误日志与数据库时间差 8 小时TZ 环境变量 + -Duser.timezone + tzdata
字体缺失图片/PDF 中文方块安装 fonts-noto-cjk 等字体包
堆大小写死容器限制 512M 而 -Xmx1024m，反复 OOM 重启用 MaxRAMPercentage 按容器比例分配，不写死 -Xmx
日志写容器层容器重建后日志丢失日志目录挂载数据卷，或由日志采集组件接管
密钥进镜像镜像被拉取后泄露数据库密码密钥经环境变量 / 密钥管理服务注入，不写进 Dockerfile 与镜像层

常见坑构建上下文过大：docker build 会把宿主机当前目录全部发送给守护进程，target/、.git、日志目录不排除会显著拖慢构建；.dockerignore 是镜像瘦身的第一道开关。
