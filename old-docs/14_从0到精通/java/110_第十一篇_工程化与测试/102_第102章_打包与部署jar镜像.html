102.1 从源码到可执行产物

一句话定位：Maven package 阶段把编译产物、配置资源与第三方依赖组装成一个可运行产物；Spring Boot 默认产出内嵌 Tomcat 的 fat jar，直接 java -jar 即可启动。

前端构建把 TS、Vue、静态资源编译压缩到 dist/ 目录交给 Nginx；后端对应的产物就是构建目录 target/ 下的 jar 文件。两者都经历"编译 → 资源处理 → 打包 → 环境配置"的流水线，区别在于后端产物自带运行时（内嵌 Servlet 容器）。

  • 普通 jar：只含本项目编译类与资源，第三方依赖需要在启动 classpath 上另行提供；
  • fat jar（可执行 jar）：本项目类 + 第三方依赖 + 启动加载器全部打入单个 jar，自带运行环境；
  • war：传统部署形态，产物放入外部 Tomcat 容器；Spring Boot 内嵌容器模式下很少使用。
# 清理 → 编译 → 测试 → 打包，产物输出到 target/
mvn clean package -DskipTests

# 直接启动可执行 jar，--spring.profiles.active 指定环境
java -jar target/bookstore-service-1.0.0.jar --spring.profiles.active=prod

102.2 可执行 jar 内部结构

一句话定位：fat jar 由启动加载器、本项目类、依赖库三部分组成；MANIFEST.MF 指明 Main-Class 与 Start-Class，加载器先把依赖 jar 挂到类路径再启动主类。

图 102-1 fat jar 内部布局与启动加载流程

# 查看 jar 内部结构（jar 本质是 zip）
jar tf target/bookstore-service-1.0.0.jar | head -30

# 解包查看 MANIFEST.MF 中的两个关键入口
unzip -p target/bookstore-service-1.0.0.jar META-INF/MANIFEST.MF
# Main-Class: org.springframework.boot.loader.launch.JarLauncher
# Start-Class: com.example.bookstore.BookstoreApplication
条目说明
Main-ClassJVM 真正调用的启动类（JarLauncher），Boot 3.x 位于 loader.launch 包下，Boot 2.x 为 loader 包下同名类
Start-Class业务主类，加载器构造好类路径后反射调用其 main 方法
BOOT-INF/classes本项目编译产物与资源文件，类加载顺序优先于 lib
BOOT-INF/lib全部第三方依赖 jar，由自定义 LaunchedClassLoader 加载，避免与 JDK 类冲突

常见坑fat jar 内部的 application.yml 被压缩在 jar 内，直接修改不生效；运行期配置应通过外置文件、命令行参数或环境变量覆盖（见 102.5）。

102.3 spring-boot-maven-plugin 与 repackage

一句话定位：插件在 package 阶段执行 repackage，把普通 jar 重写成可执行 fat jar；原普通 jar 备份为 .original，多模块工程中只有最终可启动模块配置该插件。

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
        <mainClass>com.example.bookstore.BookstoreApplication</mainClass>
        <!-- 排除不打入产物的编译期工具 -->
        <excludes>
          <exclude>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
          </exclude>
        </excludes>
      </configuration>
      <executions>
        <execution>
          <goals><goal>repackage</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
  • repackage：默认绑定 package 阶段；没有显式 mainClass 时插件自动探测带有 public static void main 的类；
  • .original 备份：repackage 前的普通 jar 改名为 bookstore-service-1.0.0.jar.original，供其他模块作为依赖引用普通构件；
  • 多模块纪律：common、domain、service 等库模块不要配该插件，否则会把依赖打进库 jar，上层模块重复携带；
  • 常用目标还有 run（开发期 mvn spring-boot:run 直接启动）与 build-info（生成构建元数据供 Actuator 展示版本）。

102.4 打包瘦身：分层 jar 与外置依赖

一句话定位：fat jar 体积主要来自 BOOT-INF/lib；分层打包把依赖与代码拆成独立层，配合 Docker 构建缓存让代码改动只重建小层；外置目录方案则把依赖放到容器/服务器本地。

<!-- 开启分层 jar（Spring Boot 3.x 默认已开启，此处显式声明层级） -->
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <layers>
      <enabled>true</enabled>
    </layers>
  </configuration>
</plugin>
# 列出 jar 内各层内容：依赖层、Spring Boot 加载器层、项目代码层
java -Djarmode=layertools -jar target/bookstore-service-1.0.0.jar list

# 按层解包到独立目录，供 Dockerfile 分别 COPY（第 103 章实操）
java -Djarmode=layertools -jar target/bookstore-service-1.0.0.jar extract

分层顺序（从底层到上层）：dependencies（第三方普通依赖）→ spring-boot-loader（加载器）→ snapshot-dependencies（开发快照）→ application（本项目代码与资源）。依赖层不变时，镜像构建命中缓存，代码改动只重建 application 层。

方案做法适用场景
fat jar 全包单 jar 内含全部依赖中小服务、部署简单、镜像体积可接受
分层 jar层内容独立切分，Docker COPY 分层复用缓存持续部署、镜像构建频繁、CI 时长敏感
外置依赖目录依赖 jar 放在服务器 lib 目录，启动时 -cp 引入多实例共享本地依赖、历史服务器环境
Thin Launcher（可选）运行期按需下载依赖，产物极小对产物体积极致敏感，需保证运行环境仓库可达

102.5 多环境打包与配置外置

一句话定位：开发、测试、生产环境用不同配置；运行期通过 profile 激活对应配置文件，敏感与环境相关配置外置到 jar 之外，做到"同一产物走完全部环境"。

# src/main/resources/application.yml（公共配置，可被环境文件覆盖）
spring:
  application:
    name: bookstore-service
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}   # 环境变量未设置时默认 dev

# application-prod.yml：生产专属配置
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://mysql.internal:3306/bookstore
    hikari:
      maximum-pool-size: 20
logging:
  file:
    name: /var/log/bookstore/service.log
<!-- 可选：Maven profile 把环境属性过滤进 application.yml -->
<profiles>
  <profile>
    <id>prod</id>
    <properties><env.active>prod</env.active></properties>
    <activation><activeByDefault>false</activeByDefault></activation>
  </profile>
</profiles>
<build>
  <resources>
    <resource>
      <directory>src/main/resources</directory>
      <filtering>true</filtering>
    </resource>
  </resources>
</build>
# ① 命令行激活 profile（优先级高于配置文件内默认值）
java -jar app.jar --spring.profiles.active=prod

# ② 外置配置目录：file:./config/ 下的 application-prod.yml 覆盖 jar 内同名文件
java -jar app.jar --spring.config.location=classpath:/,file:./config/ --spring.profiles.active=prod

# ③ Maven 打包期绑定环境（构建进产物，适合 CI 分环境出包）
mvn clean package -Pprod -DskipTests
优先级纪律：命令行参数 > 环境变量 > 外置配置文件 > jar 内 application-{profile}.yml > application.yml。数据库密码、密钥不进入代码仓库与 jar；生产环境通过环境变量或配置中心注入。

102.6 部署方式、JVM 参数与常见坑

一句话定位：服务器部署从轻量 nohup 到 systemd 服务化管理；JVM 堆、编码、时区等参数随启动命令给出；端口占用、堆大小失配、日志丢失是上线三类高频问题。

方式做法特点
前台运行java -jar app.jar，终端保持打开调试用；终端关闭进程即退出
nohup 后台nohup java -jar app.jar > app.log 2>&1 &简单临时部署；崩溃不自动拉起，日志易失控
systemd 服务unit 文件管理启动、重启、日志、开机自启服务器生产推荐；日志进 journalctl 体系
容器化Docker 镜像 + compose / 编排平台环境一致、弹性伸缩，第 103 章展开
 
# /etc/systemd/system/bookstore.service
[Unit]
Description=Bookstore Service
After=network.target

[Service]
Type=simple
User=app
WorkingDirectory=/opt/bookstore
ExecStart=/usr/bin/java \
  -Xms512m -Xmx1024m \
  -Dfile.encoding=UTF-8 \
  -Duser.timezone=Asia/Shanghai \
  -XX:+UseG1GC \
  -Xlog:gc*:file=/var/log/bookstore/gc.log:time,uptime:filecount=10,filesize=20m \
  -jar /opt/bookstore/bookstore-service-1.0.0.jar \
  --spring.profiles.active=prod
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
# systemd 操作命令
sudo systemctl daemon-reload
sudo systemctl start bookstore
sudo systemctl enable bookstore          # 开机自启
sudo systemctl status bookstore          # 查看状态
sudo journalctl -u bookstore -f          # 跟踪服务日志
sudo journalctl -u bookstore --since "1 hour ago"
JVM 参数作用与建议
-Xms / -Xmx初始堆 / 最大堆；服务器上建议二者相等避免动态扩缩；大小结合物理内存与实例数核算
-XX:+UseG1GCJava 17 默认即为 G1GC；大堆低延迟场景保持默认，无需手动切换回收器
-Dfile.encoding文件与控制台编码，统一 UTF-8，避免中文乱码
-Duser.timezone时区显式指定；容器与服务器时区不一致时从根源消除时间偏差
-Xlog:gc*GC 日志输出到指定文件，按文件数与大小轮转，供性能复盘

上线高频坑

  • 端口占用：启动报 Port 8080 was already in use，用 lsof -i:8080 或 netstat -ano | findstr 8080 定位旧进程后停掉再启动；
  • 堆大小失配：服务器内存有限却把 -Xmx 设得过大，或未考虑堆外内存与元空间，触发 OOM 被系统杀死；容器环境的堆大小策略见第 103 章；
  • 启动日志丢失：nohup 默认输出到 nohup.out 长期膨胀；systemd 方式日志进入 journalctl；生产务必由日志 appender 落盘并轮转（第 100 章）；
  • 环境配置残留：打包期写死 dev 配置上线；纪律是同一产物、运行期激活 profile，环境差异不进构建期。

✓ 本章小结

要点一句话
产物形态普通 jar 只含本项目类；Spring Boot fat jar 内嵌依赖与启动加载器，java -jar 直接运行
内部结构MANIFEST 双入口（Main-Class 加载器 / Start-Class 业务主类），classes 与 lib 分置 BOOT-INF
repackagespring-boot-maven-plugin 在 package 阶段重写产物；库模块不配置该插件
瘦身分层layertools 切分依赖层与代码层，Docker 复用缓存；外置依赖目录作为补充方案
多环境同一产物运行期激活 profile；命令行/环境变量/外置配置优先于 jar 内配置；密钥外置
部署运维systemd 服务化管理；堆、编码、时区、GC 日志参数随启动命令；端口占用与堆失配高频排查
