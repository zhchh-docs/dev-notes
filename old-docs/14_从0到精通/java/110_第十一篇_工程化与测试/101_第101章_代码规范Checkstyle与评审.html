101.1 代码规范的价值

一句话定位：规范的目标是降低团队整体的阅读与评审成本，让新成员能快速在统一心智模型下工作；格式类问题交给工具，人类评审聚焦逻辑与设计。

前端团队对这套机制非常熟悉：ESLint 管代码质量规则，Prettier 管格式化，提交前 husky 钩子自动跑检查。Java 生态的对应物是 Checkstyle / Spotless（格式与命名）+ SonarQube（质量扫描）+ 代码评审（MR/PR）（人来判断设计与边界）。

  • 可读性优先：后续阅读代码的人远多于最初写代码的人；一致的命名与结构减少理解摩擦；
  • 评审去情绪化：格式问题由工具拦截，评审评论只讨论业务正确性与设计取舍，避免"风格之争"；
  • 新人上手快：按同一套规则写，目录、类名、方法名具有可预期性；
  • 规范是团队契约：规则经团队评审后落地，不是上级强加的个人偏好；规则不合理时先改规则，再改代码。

图 101-1 规范落地流水线：工具自动拦截格式问题，人工评审聚焦设计取舍

分工原则机器能机械判断的（缩进、命名大小写、导入顺序、未用变量）交给静态检查工具；机器判断不了的（抽象是否合理、边界是否完备、异常是否得当）交给代码评审。

101.2 命名、格式与注释规范清单

一句话定位：命名见名知意，格式保持一致，注释解释"为什么"而不是复述"做什么"；先在团队内固化这份清单，再交给工具执行。

类别规则正例 / 反例
类 / 接口大驼峰，名词或名词短语；接口不加 I 前缀正例 OrderService；反例 OrderServ、IOrderService
方法小驼峰，动词开头；查询返回 is/has/can 时用布尔前缀正例 createOrder、isExpired；反例 orderGet、check
变量 / 参数小驼峰，表达含义；避免 data、obj、temp 这类空名正例 discountAmount；反例 a、value2、tempList
常量大写下划线分隔正例 MAX_RETRY_TIMES；反例 maxRetryTimes
格式缩进 4 空格；行宽建议 120；花括号跟随不另起行；导入不使用通配符正例 import java.util.List；反例 import java.util.*
注释类与公共方法写 Javadoc；复杂规则注释动机；不复述代码见下方正反例
暴露面成员变量默认 private；方法参数只在必要时校验；包结构按业务域组织—
 
// ---- 反例：命名空洞 + 注释复述代码 ----
public void process(List<Order> l) {
    for (Order o : l) {
        // 如果状态是 1 就执行下一步
        if (o.getStatus() == 1) {
            o.setPrice(o.getPrice() * 0.8);   // 打八折
        }
    }
}

// ---- 正例：命名自解释，注释解释业务动机 ----
/**
 * 对待支付订单执行新人首单折扣。
 * 折扣规则来自运营活动 A202405；后续活动规则变更时集中修改本方法。
 */
public void applyNewUserDiscount(List<Order> pendingOrders) {
    for (Order order : pendingOrders) {
        if (order.isStatus(OrderStatus.PENDING_PAYMENT)) {
            BigDecimal discounted = order.price().multiply(NEW_USER_DISCOUNT_RATE);
            order.updatePrice(discounted);
        }
    }
}
注释纪律注释应该回答"为什么这样设计、为什么绕开常规做法"；i++ // 自增 这类复述性注释只会过期成误导。坏味道代码（超长方法、深层嵌套、参数过多）优先重构，而不是加注释解释。

101.3 Checkstyle 配置与 Maven 插件集成

一句话定位：Checkstyle 读取一份规则集 XML，在 Maven 构建中扫描命名、格式、注释与导入；违反规则可在 verify 阶段让构建失败，或仅输出警告供人工处理。

<!-- src/main/resources/checkstyle.xml：团队规则集 -->
<?xml version="1.0"?>
<!DOCTYPE module PUBLIC
    "-//Checkstyle//DTD Checkstyle Configuration 1.3//EN"
    "https://checkstyle.org/dtds/configuration_1_3.dtd">
<module name="Checker">
  <property name="severity" value="error"/>
  <!-- 基础风格（sun_checks.xml / google_checks.xml）由插件 configLocation 指定，
       本文件只声明项目叠加规则 -->

  <module name="FileTabCharacter"/>
  <module name="LineLength">
    <property name="max" value="120"/>
    <property name="ignorePattern" value="^package.*|^import.*|http.*"/>
  </module>
  <module name="UnusedImports"/>
  <module name="ImportOrder"/>

  <module name="TreeWalker">
    <module name="ClassNaming"/>
    <module name="MethodNaming"/>
    <module name="MemberName"/>
    <module name="ParameterName"/>
    <module name="ConstantName"/>
    <module name="JavadocMethod">
      <property name="scope" value="public"/>
      <property name="allowMissingJavadoc" value="false"/>
    </module>
    <module name="FinalLocalVariable"/>
    <module name="NestedIfDepth">
      <property name="max" value="3"/>
    </module>
  </module>
</module>
<!-- 父 pom：把 Checkstyle 绑定到 verify 阶段 -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-checkstyle-plugin</artifactId>
  <version>3.4.0</version>
  <configuration>
    <configLocation>checkstyle.xml</configLocation>
    <consoleOutput>true</consoleOutput>
    <failOnViolation>true</failOnViolation>       <!-- 违反即构建失败 -->
    <violationSeverity>warning</violationSeverity>
    <excludePattern>**/dto/.*</excludePattern>    <!-- DTO 等特殊包排除规则 -->
  </configuration>
  <executions>
    <execution>
      <phase>verify</phase>
      <goals><goal>check</goal></goals>
    </execution>
  </executions>
</plugin>
  • 规则集来源：可继承 sun_checks.xml 或 google_checks.xml 作为基线，再叠加团队规则，避免从零写规则；
  • 阻断级别：新项目建议 failOnViolation=true 把纪律落到构建；存量项目先 warning 观察一轮，再逐步升级为 error；
  • 报告产物：扫描结果输出到 target/checkstyle-result.xml，可被 CI 质量平台收集展示；
  • 豁免机制：Suppressions 或包级排除用于生成代码、DTO、第三方适配层，不要用注释 @SuppressWarnings 大面积压制规则。

101.4 IDEA 本地导入规则实时检查

一句话定位：在提交前就让规则在编辑器内标红，而不是等 CI 构建失败返工；IDEA 通过 Checkstyle-IDEA 插件加载同一份规则集。

  1. 安装插件：Settings → Plugins 搜索 Checkstyle-IDEA 并重启；
  2. 添加规则集：Settings → Tools → Checkstyle，点 + 选择项目内 checkstyle.xml，勾选为激活配置；
  3. 项目视图中打开 Checkstyle 工具窗口，点击绿色三角扫描当前模块，违规行在编辑器内以波浪线提示；
  4. 配合 IDEA 自身的 Settings → Editor → Code Style（缩进、行宽、空格风格），让自动格式化与 Checkstyle 规则一致。
一致性要点本地插件、Maven 插件、CI 流水线加载同一份 checkstyle.xml；不要在 IDE 里私调一套格式，导致"本地好看、CI 报错"。配合保存时自动格式化（Reformat on Save），格式问题在编写瞬间消除。

101.5 代码评审清单与流程

一句话定位：评审是人与人之间的设计与边界核对；按固定清单逐类检查，评论对代码不对人，结论落到修改项而非风格偏好。

维度检查项高危信号
可读性命名是否自解释；方法长度与嵌套层级；职责是否单一；重复代码是否抽取方法超 80 行、三层以上嵌套、同名变量多处遮蔽
边界与空值入参校验、集合空判断、Optional 使用、null 返回值是否清晰约定可能为 null 的对象直接解引用；空集合返回 null
异常处理异常是否分类捕获；是否吞掉异常堆栈；错误信息是否面向排障；事务边界内异常回滚catch 后只 printStackTrace；捕获 Exception 大网
性能与资源集合初始化容量；IO 流与连接是否关闭；是否存在 N+1 查询；线程池是否复用循环内查库；资源未 try-with-resources；每请求新建线程池
并发安全共享可变状态、缓存竞态、复合操作原子性、锁粒度static 非线程安全集合；双重检查锁定写法错误
安全SQL 拼接、入参注入、权限校验、敏感信息日志、错误页信息泄露字符串拼 SQL；密码/手机号打 INFO 日志
测试新分支是否有对应单测；异常路径是否覆盖；断言是否落到业务规则只补快乐路径测试；测试互相依赖顺序
 
// ---- 评审会指出的典型问题：吞异常 + 资源未关闭 ----
public Order queryOrder(Long id) {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        ResultSet rs = stmt.executeQuery("select * from orders where id=" + id);
        if (rs.next()) return mapToOrder(rs);
        return null;
    } catch (Exception e) {
        System.out.println("error");     // 吞堆栈、无日志级别、无业务语义
        return null;                    // 调用方无法区分"不存在"与"系统错误"
    }
}
// 修改方向：try-with-resources 关闭资源；参数化 SQL；异常分类抛出；
// 查询空结果返回 Optional.empty()；失败路径抛 BizException 并写 ERROR 日志

评审流程建议：提交者先按清单自查一遍并附上改动说明；评审者在约定时限内反馈；评论区分"必须修改 / 建议优化 / 疑问讨论"三级；作者修改后回评；评审记录沉淀到知识库，规则反哺到 Checkstyle 与 Sonar 规则中。

101.6 SonarQube 简介与常见坑

一句话定位：SonarQube 是持续静态质量平台，扫描 Bug、坏味道、安全漏洞、重复率与测试覆盖率，按质量门禁决定代码是否允许合并；Checkstyle 管格式规则，Sonar 管更深的代码质量。

指标 / 工具CheckstyleSonarQube
关注点命名、格式、注释、导入顺序等机械规则潜在 Bug、坏味道、漏洞、重复代码、覆盖率
典型规则行宽、常量命名、Javadoc、未用导入空指针风险、资源未关闭、硬编码密码、条件恒真
运行时机Maven verify 阶段本地与 CI 均可CI 流水线独立扫描任务，结果汇总到平台
阻断方式构建失败（failOnViolation）质量门禁（Quality Gate）不通过阻断合并
 
# CI 中执行 Sonar 扫描；覆盖率由 JaCoCo 报告提供输入
mvn clean verify org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
  -Dsonar.host.url=http://sonar.example.com \
  -Dsonar.projectKey=bookstore \
  -Dsonar.java.coveragePlugin=jacoco

常见坑

  • 规范教条化：为满足行宽把合理表达式拆成多行、为凑覆盖率写无效断言——规则服务于可读性，而不是反过来；
  • checkstyle 阻断构建引发对抗：存量项目一次性开启严格模式导致 CI 大面积变红，团队倾向于直接关闭插件；正确节奏是先观察、分批修复、再升级阻断；
  • 为过扫描而禁用规则：大面积 @SuppressWarnings、关闭质量门禁规则；每条豁免都应在评审中说明理由并记录；
  • 覆盖率数字迷信：100% 覆盖不代表高质量；核心业务分支与异常路径覆盖才是评审重点（呼应第 99 章纪律）。

常见坑把规范评审变成风格争论：评审记录中只应引用团队已固化的规则条目；新风格诉求先补充进规则集并团队确认，再在代码中执行。

✓ 本章小结

要点一句话
规范价值降低阅读与评审成本；机械判断交给工具，设计判断留给评审
规范清单命名见名知意、格式统一、注释解释动机；正例代码可作为评审基准
Checkstylecheckstyle.xml 规则集 + maven-checkstyle-plugin 绑定 verify，failOnViolation 控制阻断
本地联动IDEA 插件加载同一份规则集，保存即格式化，本地与 CI 规则一致
评审清单可读性、边界空值、异常、性能资源、并发、安全、测试七维逐类核对
SonarQube扫描 Bug/坏味道/漏洞/重复率/覆盖率，质量门禁阻断合并；避免教条化与豁免泛滥
