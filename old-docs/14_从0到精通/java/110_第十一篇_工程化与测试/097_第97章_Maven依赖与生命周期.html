97.1 Maven：从手动导包到构建工具

一句话定位：Maven 是 Java 世界的项目管理与构建工具——用一份声明式配置（pom.xml）描述依赖、构建步骤与产物，工具自动完成下载、编译、测试、打包。

在没有构建工具的年代，Java 项目要把第三方 jar 一个个手动拖进 WEB-INF/lib，版本冲突靠肉眼比对，打包靠 IDE 导出。前端同学对这套痛点不陌生：package.json 与 node_modules 解决的就是同类问题，Maven 在后端扮演的角色可粗略对照如下：

概念前端对照（npm / vite）Maven 对应物
依赖清单文件package.json 的 dependenciespom.xml 的 dependencies
本地缓存目录node_modules（项目内）~/.m2/repository（本机全局）
公共仓库npm registry（npmjs.com）Maven Central（中央仓库）+ 私服
构建脚本npm run build / vite build生命周期阶段 + 插件目标
锁版本文件package-lock.json依赖树由 pom 版本与仲裁规则确定

Maven 的核心哲学是约定优于配置（Convention over Configuration）：源码固定放在 src/main/java、测试放在 src/test/java、资源放在 src/main/resources，目录结构不用声明，工具按约定找文件。基线环境：Java 17、Maven 3.9.x、Spring Boot 3.x。

核心概念Maven 做两件事：管依赖（下载、解析、仲裁、打包进产物）与管构建（按生命周期顺序调用插件完成编译、测试、打包、安装、部署）。

97.2 坐标与 pom.xml 结构

一句话定位：每个项目、每个依赖都用三元坐标 groupId:artifactId:version 唯一标识；pom.xml 是项目的"说明书 + 组装图纸"。

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <!-- ① 项目坐标：本项目在仓库中的唯一身份证 -->
  <groupId>com.example.bookstore</groupId>
  <artifactId>order-service</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>   <!-- jar / war / pom，默认 jar -->

  <!-- ② 统一版本变量，集中管理便于升级 -->
  <properties>
    <java.version>17</java.version>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <!-- ③ 依赖清单 -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
      <groupId>com.h2database</groupId>
      <artifactId>h2</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
  • groupId：组织或项目域，通常是倒置域名 com.example.bookstore；
  • artifactId：模块名，一个 groupId 下区分具体产物；
  • version：版本号；-SNAPSHOT 表示开发中快照，Maven 会定期拉取最新快照；1.0.0 是正式发布版，发布后不可变；
  • packaging：产物类型，jar（默认，普通后端服务）、war（传统 Servlet 容器部署）、pom（聚合父工程，见第 98 章）。

图 97-1 Maven 仓库层次与解析顺序

常见坑坐标写错（groupId 或 artifactId 多一个连字符、版本号拼错）会直接报 Could not resolve dependencies；报错信息里的坐标就是排查入口，可去 Central 仓库网站按坐标核对。

97.3 依赖 scope 五档

一句话定位：<scope> 决定依赖参与哪个 classpath（编译、测试、运行）以及是否随包传递，默认 compile。

scope可见性（编译/测试/运行）传递性典型用途
compile（默认）编译 ✓ 测试 ✓ 运行 ✓随 compile 传递业务库、Spring starter、工具类
provided编译 ✓ 测试 ✓ 运行 ✗不传递Servlet API、JDK 自带或部署环境提供的包
runtime编译 ✗ 测试 ✓ 运行 ✓随 runtime 传递JDBC 驱动实现、日志实现、JSON 运行时库
test编译 ✗ 测试 ✓ 运行 ✗不传递JUnit、Mockito、H2 测试库、断言库
system同 provided，jar 用 systemPath 指定本地路径不传递遗留特殊场景，不推荐，构建不可移植
 
<dependencies>
  <!-- compile：默认，三方业务库直接进入产物 -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>

  <!-- provided：编译期需要 Servlet 注解，运行时由 Tomcat 提供，不再打包进 jar -->
  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>
  </dependency>

  <!-- runtime：代码里只面向 java.sql 接口，MySQL 驱动实现运行时加载即可 -->
  <dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
  </dependency>

  <!-- test：只在 src/test 下可见，不会进最终产物 -->
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>
记忆法对照前端 devDependencies 理解 test（构建/测试需要、产物不需要）；provided 像 peerDependencies——由宿主环境提供；runtime 是"编译期只看接口、运行期才换实现"的策略。

97.4 依赖传递与冲突仲裁

一句话定位：A 依赖 B、B 依赖 C，A 会间接拿到 C；当多条路径引入同一构件的不同版本时，Maven 按最近路径优先、同路径先声明先赢两条规则仲裁。

假设项目直接依赖 spring-boot-starter-web，它又依赖 spring-web，spring-web 再依赖 spring-core——你不需要手写 spring-core，Maven 沿依赖树把 compile 范围的传递依赖全部解析到本项目 classpath。运行下面命令可以看清整棵树：

# 打印完整依赖树，重点看 "omitted for conflict with" 与 "omitted for duplicate"
mvn dependency:tree

# 列出被仲裁省略的版本，定位冲突来源
mvn dependency:tree -Dincludes=org.apache.logging.log4j:*

# 分析哪些依赖实际没被代码使用（声明了却没用到）
mvn dependency:analyze

仲裁规则按顺序生效：

  • 最短路径优先：项目 → A → C:1.1（路径 2 层）与项目 → B → D → C:1.2（路径 3 层），选择路径更短的 C:1.1；
  • 路径相同，先声明先赢：两条路径深度一致时，pom.xml 中靠前声明的依赖所带版本胜出；
  • dependencyManagement 锁定：父工程在 dependencyManagement 中指定的版本对全模块生效，子模块声明时可不写版本（第 98 章细讲）；
  • exclusions 显式排除：对某个传递依赖不满意，可以在引入处把它整棵剪掉。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <!-- 排除旧日志实现，避免与 Logback 重复（示例：显式剔除某传递构件） -->
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>
版本冲突的识别信号：类找不到（NoClassDefFoundError）、方法找不到（NoSuchMethodError）、日志框架被压成黑方块或双实现告警，先用 dependency:tree 定位引入路径，再决定升级、排除还是在父 pom 统一锁定版本。

常见坑本地仓库被污染（下载中断留下残缺 jar，或旧 SNAPSHOT 缓存了过期版本）会表现为诡异的编译错误。处理方式：删除 ~/.m2/repository 下对应构件目录，加 -U 强制刷新快照：mvn clean compile -U。

97.5 三套生命周期与常用命令

一句话定位：Maven 把构建过程切成三套互不重叠的生命周期，每套由若干阶段（phase）组成；执行某个阶段会按顺序执行它之前的所有阶段。

图 97-2 default 生命周期阶段流水线

生命周期 / 阶段职责常用命令示例
clean删除 target 目录及全部构建产物mvn clean
validate校验 pom 配置、依赖完整性随其他阶段自动执行
compile编译 src/main/java 到 target/classesmvn compile
testsurefire 插件执行 src/test 下单元测试mvn test
package按 packaging 打成 jar/war 放入 targetmvn clean package
install把产物装入本地仓库，供本机其他模块引用mvn clean install
deploy把产物发布到远程仓库/私服，供团队共享mvn deploy（CI 环境使用）
site生成项目报告文档站点（较少使用）mvn site
 
# 清理后打包；-DskipTests 跳过测试执行（仍编译测试代码）；-Dmaven.test.skip=true 连测试编译一起跳过
mvn clean package -DskipTests

# 多模块工程中只构建当前模块及其依赖模块（第 98 章展开）
mvn clean install -pl order-service -am

# 离线模式：只走本地仓库，排查网络与仓库问题
mvn clean compile -o
关键理解阶段是顺序执行的：mvn package 不会只打包，它会先把前面的 validate、compile、test 全部跑一遍；想跳过测试要显式加参数，而不是删掉 test 阶段。

97.6 常用插件与构建配置

一句话定位生命周期阶段本身只定义"该做什么"，真正干活的是绑定到阶段上的插件目标；Spring Boot 工程靠三个插件完成编译、测试与可执行打包。

<build>
  <plugins>
    <!-- ① 编译插件：指定 Java 版本与编码 -->
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <release>17</release>
        <encoding>UTF-8</encoding>
      </configuration>
    </plugin>

    <!-- ② 测试插件：绑定 test 阶段，发现并执行 JUnit5 测试 -->
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <configuration>
        <!-- 测试失败即中断构建；报告输出到 target/surefire-reports -->
        <testFailureIgnore>false</testFailureIgnore>
      </configuration>
    </plugin>

    <!-- ③ Spring Boot 打包插件：把普通 jar 重打成可执行 fat jar -->
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
        <excludes>
          <exclude>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
          </exclude>
        </excludes>
      </configuration>
    </plugin>
  </plugins>
</build>
  • maven-compiler-plugin：绑定 compile 阶段，<release>17</release> 同时约束源码与目标字节码版本；
  • maven-surefire-plugin：绑定 test 阶段，默认匹配 *Test、*Tests、Test* 命名的测试类；JUnit5 需要 starter 自动适配；
  • spring-boot-maven-plugin：在 package 阶段执行 repackage，把依赖 jar 一并塞进产物（第 102 章详解内部结构）。

常见坑Spring Boot 父工程（spring-boot-starter-parent）已经统一管理了插件版本与默认配置，业务 pom 里一般只覆盖参数、不要重复写版本号；脱离父工程时才需要显式声明插件版本。

✓ 本章小结

要点一句话
Maven 定位声明式管理依赖 + 按生命周期驱动插件完成构建，约定优于配置
坐标groupId:artifactId:version 唯一标识构件，packaging 决定产物类型
scopecompile 默认全参与；provided 运行期由容器提供；runtime 编译期不可见；test 仅测试期
冲突仲裁最近路径优先，同路径先声明先赢；dependencyManagement 锁版本，exclusions 剪枝
生命周期clean / default / site 三套；执行某阶段会顺序跑完其前序阶段
插件compiler 编译、surefire 测试、spring-boot repackage 打包，绑定到对应阶段

✎ 本章习题

A 基础复述 compile、provided、runtime、test 四种 scope 在编译期、测试期、运行期的可见性差异，各举一个典型依赖。
B 进阶新建一个 Maven 工程引入 spring-boot-starter-web，执行 mvn dependency:tree，找出 spring-core 经过哪条路径引入、最终版本是多少。
C 挑战人为在 pom 中引入两个不同版本的同一构件（如 logback-classic），用依赖树观察仲裁结果；再用 exclusions 排除其中一条路径，对比前后变化。
