99.1 为什么写单元测试

一句话定位：单元测试把一段业务逻辑与其外部依赖隔离起来，用自动断言在代码改动后立刻回答"这段逻辑还对不对"。

第 77 章的 UserService 内部 new 了 UserDaoJdbc，测试时就被迫真实连库；第 79 章改成构造器注入后，测试时就可以不把真实 Dao 递进去，而是递一个"按剧本返回数据"的替身。这正是单元测试成立的前提：依赖可替换。

图 99-1 测试金字塔：单元测试是地基，数量最多、执行最快

  • 回归保护：改代码、升依赖、重构后一键跑测试，行为是否破坏立刻可见；
  • 设计反馈：一个类难以测试，往往意味着依赖过多、职责过重——测试是最好的设计体检；
  • 文档作用：测试用例本身就是可执行的使用示例，比注释更不容易过期；
  • 前端对照：JUnit5 ≈ Jest 的测试运行器 + 断言库；Mockito ≈ Jest 的 mock 函数与 spy；@BeforeEach 对应 beforeEach。
单元测试边界只测当前类的业务规则，不连数据库、不发 HTTP、不读真实配置文件；外部协作者一律用替身替换。连真实数据库的是集成测试，属于金字塔中间层。

99.2 JUnit5 结构、断言与参数化

一句话定位：JUnit5 由引擎、API 与平台组成；业务代码使用 org.junit.jupiter.api 包下的注解与断言，Spring Boot Test 已默认集成。

注解 / API作用执行时机 / 说明
@Test标记一个测试方法方法无参数、void 返回、public 可省略
@BeforeEach每个测试方法前执行初始化替身、构造被测对象
@AfterEach每个测试方法后执行释放临时资源、清理状态
@BeforeAll当前类所有测试前执行一次方法必须 static（除非 @TestInstance(Lifecycle.PER_CLASS)）
@AfterAll当前类所有测试后执行一次同上，用于关闭重量级资源
@DisplayName自定义测试报告中的中文名称支持空格与中文，不影响方法名
@Disabled临时跳过该测试报告中标注为跳过，不要长期保留
@Nested组合同类场景的内部类按业务场景分组组织测试方法
@ParameterizedTest同一逻辑喂多组数据重复执行配合 @ValueSource / @CsvSource / @MethodSource
 
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class DiscountCalculatorTest {

    private DiscountCalculator calculator;

    @BeforeEach
    void setUp() {                       // 每个测试前重建被测对象，保证相互独立
        calculator = new DiscountCalculator();
    }

    @Test
    @DisplayName("满 1000 打八折，不足 1000 不打折")
    void shouldApplyDiscountOnlyAboveThreshold() {
        assertEquals(800.0, calculator.discount(1000.0), 0.001);
        assertEquals(500.0, calculator.discount(500.0), 0.001);
    }

    @Test
    @DisplayName("负数金额应抛出 IllegalArgumentException")
    void shouldRejectNegativeAmount() {
        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> calculator.discount(-10.0));
        assertTrue(ex.getMessage().contains("金额不能为负"));
    }

    @AfterEach
    void tearDown() {
        // 单测通常无需清理；涉及临时文件、临时目录时在此回收
    }
}
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.junit.jupiter.api.Assertions.assertEquals;

class DiscountParameterizedTest {
    private final DiscountCalculator calculator = new DiscountCalculator();

    @ParameterizedTest(name = "金额 {0} → 折后 {1}")
    @CsvSource({
        "0,    0",
        "500,  500",
        "1000, 800",
        "2000, 1600"
    })
    void discountTable(double amount, double expected) {
        assertEquals(expected, calculator.discount(amount), 0.001);
    }
}

常用断言：assertEquals(expected, actual, delta)（浮点容差）、assertTrue/False、assertNull/NotNull、assertThrows(异常类, 可执行代码)、assertAll(...) 聚合多个断言一次性报告全部失败项、assertTimeout(Duration, ...) 验证耗时上限。

99.3 Mockito：替身、打桩与行为验证

一句话定位：Mockito 创建接口/类的替身对象；when(...).thenReturn(...) 给替身设定返回剧本（打桩 stub）；verify(...) 验证被测对象是否以正确方式调用过替身。

概念 / API作用类比 Jest
mock(接口.class)创建替身，方法默认返回 null / 0 / falsejest.fn()
when(mock.method()).thenReturn(x)设定命中条件时的返回值mockReturnValue
thenThrow(e) / thenAnswer(..)抛异常 / 动态计算返回值mockImplementation
verify(mock, times(n)).method(..)验证被调用次数与参数expect(fn).toHaveBeenCalledTimes(n)
verifyNoInteractions(mock)验证替身从未被调用expect(fn).not.toHaveBeenCalled()
@Mock字段级替身声明，需 MockitoExtension 激活describe 内 jest.fn()
@InjectMocks把 @Mock 替身按构造器/setter/字段注入被测对象—
ArgumentCaptor捕获调用参数做断言，适合复杂入参对象mock.calls[0][0]
 
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;
import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.*;

@ExtendWith(MockitoExtension.class)          // 激活 @Mock / @InjectMocks 注解
class UserRepositoryMockTest {

    @Mock                                     // 替身：不碰数据库
    private UserRepository userRepository;

    @Test
    void stubAndVerifyDemo() {
        // ① 打桩：findById(10L) 返回预置用户
        when(userRepository.findById(10L))
                .thenReturn(Optional.of(new User(10L, "Tom")));

        // ② 执行被测代码（此处简化，直接演示替身行为）
        Optional<User> found = userRepository.findById(10L);

        // ③ 断言返回值
        assertTrue(found.isPresent());
        assertEquals("Tom", found.get().name());

        // ④ 行为验证：确实用 10L 调过一次 findById，未调过其他参数
        verify(userRepository, times(1)).findById(10L);
        verifyNoInteractions(userRepository.findAll());
    }
}
区分两类断言状态断言检查返回值与对象状态（assertEquals）；行为验证检查协作者被如何调用（verify）。业务规则以状态断言为主；涉及"是否通知外部、是否落库"的副作用，才用行为验证兜底。

99.4 @MockBean 与 Spring 测试切片

一句话定位：需要启动 Spring 上下文的测试中，用 @MockBean 把替身注册进 ApplicationContext，替换真实 Bean；@SpyBean 则保留真实实现、按需打桩个别方法。

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.mock.mockito.MockBean;

@SpringBootTest
class OrderServiceSpringTest {

    @Autowired
    private OrderService orderService;          // 真实 Service，由容器装配

    @MockBean                                    // 替换上下文中的 PayClient 为替身
    private PayClient payClient;

    @Test
    void payOrderShouldCallGateway() {
        orderService.pay(new Order(1L, 99.0));
        verify(payClient, times(1)).charge(argThat(req -> req.amount() == 99.0));
    }
}
  • @MockBean 只在 Spring 上下文测试中使用；纯单元测试用 @Mock + @InjectMocks 即可，启动上下文慢一个数量级；
  • 同类型已有 Bean 时，@MockBean 会替换它；上下文被替换行为标记为 dirty，测试类间共享上下文时留意缓存失效；
  • 测试切片注解（@WebMvcTest、@DataJpaTest）只加载部分上下文，配合 @MockBean 做分层测试，速度优于全量 @SpringBootTest；
  • 依赖坐标：spring-boot-starter-test 已打包 JUnit5、Mockito、AssertJ、Hamcrest，scope 为 test，业务代码不要直接 import 测试断言类。

版本差异Spring Boot 3.4 起，org.springframework.boot.test.mock.mockito.MockBean 与 @SpyBean 被标记为废弃，官方推荐改用 org.springframework.test.context.bean.override.mockito.MockitoBean（注解名同为 @MockitoBean）与新包下的 @SpyBean；本书基线 3.2/3.3 仍以本节写法为准，升级到 3.4+ 时按 IDE 提示替换包名即可，用法不变。

99.5 Service 层完整单测示例

一句话定位：被测 Service 依赖 Repository 与加密器，单测中两者全部替身；按 Given（布置依赖与数据）→ When（调用被测方法）→ Then（断言状态与行为）三段组织。

// ---- 被测业务代码（bookstore-service） ----
@Service
public class UserService {
    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public UserService(UserRepository userRepository, PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    public User register(String name, String rawPassword) {
        if (rawPassword == null || rawPassword.length() < 6) {
            throw new IllegalArgumentException("密码长度至少 6 位");
        }
        if (userRepository.existsByName(name)) {
            throw new IllegalStateException("用户名已存在");
        }
        String encoded = passwordEncoder.encode(rawPassword);
        User user = new User(name, encoded);
        return userRepository.save(user);
    }
}
// ---- 单元测试（src/test/java，同包名便于访问包内成员） ----
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock private UserRepository userRepository;
    @Mock private PasswordEncoder passwordEncoder;
    @InjectMocks private UserService userService;   // 构造器注入两个替身

    @Test
    @DisplayName("注册成功：密码加密后入库，返回持久化用户")
    void registerSuccess() {
        // Given：布置替身剧本
        when(passwordEncoder.encode("secret123")).thenReturn("ENC-secret123");
        when(userRepository.existsByName("Tom")).thenReturn(false);
        when(userRepository.save(any(User.class)))
                .thenAnswer(invocation -> {
                    User u = invocation.getArgument(0);
                    u.setId(7L);
                    return u;
                });

        // When：调用被测方法
        User result = userService.register("Tom", "secret123");

        // Then：状态断言
        assertEquals(7L, result.getId());
        assertEquals("ENC-secret123", result.getPassword());

        // Then：行为断言——捕获入库参数，确认入库的是加密后的密码而非明文
        ArgumentCaptor<User> captor = ArgumentCaptor.forClass(User.class);
        verify(userRepository, times(1)).save(captor.capture());
        assertEquals("ENC-secret123", captor.getValue().getPassword());
        verify(userRepository).existsByName("Tom");
    }

    @Test
    @DisplayName("密码不足 6 位：抛异常且不访问数据库")
    void registerTooShortPassword() {
        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> userService.register("Tom", "12345"));
        assertTrue(ex.getMessage().contains("密码长度"));
        verifyNoInteractions(userRepository);        // 短路在访问仓库之前
        verifyNoInteractions(passwordEncoder);
    }

    @Test
    @DisplayName("用户名已存在：抛业务异常")
    void registerDuplicateName() {
        when(userRepository.existsByName("Tom")).thenReturn(true);
        assertThrows(IllegalStateException.class,
                () -> userService.register("Tom", "secret123"));
        verify(userRepository, never()).save(any());
    }
}

三个用例分别覆盖：正常路径、参数校验短路、业务规则冲突。每个用例独立构造数据，互相不共享状态——这是 @BeforeEach 重建被测对象的意义。

99.6 测试纪律与常见坑

① mock 与真实依赖混用

@InjectMocks 只会注入已声明的 @Mock 替身；未被 mock 的协作者保持 null，被测方法一旦访问就 NPE。排查顺序：先确认构造器参数是否都有替身，再看是否有通过 setter / 字段补充依赖。

② verify 滥用：测实现而不是测行为

逐行 verify 每个内部方法调用，会让测试与实现细节死死绑定——重构内部实现就要改测试，测试从保护变成阻力。纪律：verify 只覆盖"对外产生副作用"的调用（发消息、落库、调外部接口）；内部私有方法、内部转换不值得验证。

③ 断言缺失与弱断言

方法跑过没抛异常就算测试通过，等于没有断言；只断言 assertNotNull 而不校验字段，脆弱且漏检。每个用例至少一条与业务规则对应的状态断言。

④ 测试顺序依赖与共享可变状态

JUnit5 默认不保证测试方法执行顺序；用例间靠静态字段、成员变量缓存中间结果，随机顺序下必然偶发失败。纪律：每个用例自行布置 Given 数据，@BeforeEach 重建被测对象。

⑤ mock 值对象与 DTO

纯数据对象（DTO、记录类、枚举）不需要替身，直接 new 出真实实例传入；替身留给有外部副作用的协作者（Repository、客户端、发送器）。

覆盖率提醒：JUnit5 + Mockito 单测追求的是业务分支覆盖，不是 IDEA 覆盖率数字；把一行行 getter/setter 凑到 100% 没有工程价值，核心规则分支（校验、异常、并发边界）才需要重点覆盖。覆盖率工具（JaCoCo）在 CI 中作为参考指标使用。

常见坑使用 when(mock.method()) 对未打桩的 void 方法、或在 MockitoExtension 严格模式下声明了未使用的打桩，会报 UnnecessaryStubbingException；严格模式鼓励只写真正被走到的打桩，测试失败时也更容易定位。

✓ 本章小结

要点一句话
单测定位隔离外部依赖验证当前类业务规则，快、多、独立，是测试金字塔地基
JUnit5@Test/@BeforeEach/@AfterAll 生命周期，Assertions 断言，@ParameterizedTest 喂多组数据
Mockitomock 替身 + when/thenReturn 打桩 + verify 行为验证；@Mock/@InjectMocks 字段装配
Spring 测试@MockBean 替换上下文 Bean；@WebMvcTest/@DataJpaTest 切片优先于全量上下文
Given-When-Then布置剧本 → 调用被测方法 → 状态断言为主、副作用行为验证为辅
纪律不测实现细节、不断言缺失、不共享状态、不 mock 值对象

✎ 本章习题

A 基础列出 @Test、@BeforeEach、@BeforeAll、@AfterAll 的执行时机差异；说明参数化测试适合解决什么问题。
B 进阶为 99.5 的 UserService 补充「邮箱格式校验」分支：合法邮箱通过、非法邮箱抛异常且不访问仓库，用 ArgumentCaptor 复核入库对象字段。
C 挑战把 99.5 改造为 @SpringBootTest + @MockBean 版本，对比两种方式的启动耗时与适用场景，记录差异原因。
