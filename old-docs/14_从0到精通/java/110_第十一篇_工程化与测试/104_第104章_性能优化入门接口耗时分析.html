104.1 性能基线：先有指标再谈优化

一句话定位：性能优化的前提是量化——接口当前 RT、吞吐、资源利用率是多少，优化后是否改善；没有基线的优化只是主观感受。

第 68 章建立过并发与性能的基本概念，本章落到接口级场景。常用指标先固定下来：

指标含义关注点
RT 响应时间请求从进入到返回的耗时，分平均、P95、P99、P999长尾比平均值更接近用户体验
QPS / TPS每秒处理请求数 / 每秒事务数与 RT 共同刻画吞吐能力
并发数同时在途处理的请求数量线程池、连接池承载上限的依据
错误率失败请求占比性能爬坡阶段优先观察错误率而非压垮为止
资源利用率CPU、堆内存、IO、网络、数据库连接使用率定位瓶颈在应用还是外部依赖
  • 先定目标：例如"下单接口 P95 < 300ms、峰值 QPS 500、错误率 < 0.1%"，目标来自业务要求而非拍脑袋；
  • 压测环境：尽量贴近生产的数据量、索引规模、依赖环境；空库上压测得出的结论不能直接外推；
  • 记录基线：改动前把接口 RT 分布、线程池队列、数据库慢查询、GC 情况记录归档，作为优化前后对照依据；
  • 监控先行：Actuator + Micrometer 指标、日志打点、链路追踪覆盖核心接口，问题出现时有迹可循。
第一纪律性能优化不是"把代码写得更快"，而是"用数据找到最慢的那一段，把它改掉并证明指标变好了"。

104.2 耗时分析方法与工具选型

一句话定位：从粗到细四层手段——日志打点看阶段耗时、Actuator 指标看分布与趋势、Arthas 看方法调用链、JFR 做 CPU 与事件级复盘；按问题阶段选择，不堆砌工具。

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.util.StopWatch;

@Service
public class OrderQueryService {
    private static final Logger log = LoggerFactory.getLogger(OrderQueryService.class);

    public OrderDetail query(Long orderId) {
        StopWatch sw = new StopWatch("order-query");
        sw.start("loadOrder");
        Order order = orderRepository.findById(orderId).orElseThrow();
        sw.stop();

        sw.start("loadItems");
        List<OrderItem> items = orderItemRepository.findByOrderId(orderId);
        sw.stop();

        sw.start("assemble");
        OrderDetail detail = OrderDetail.of(order, items);
        sw.stop();

        // 分阶段耗时写日志，定位到底是数据库慢还是组装慢
        if (sw.getTotalTimeMillis() > 200) {
            log.warn("慢查询 orderId={} elapsed={} stages={}", orderId,
                    sw.getTotalTimeMillis(), sw.prettyPrint());
        }
        return detail;
    }
}
手段能力边界适用场景
日志打点（StopWatch / currentTimeMillis）记录预先划分好的阶段耗时，依赖人工埋点线上长期观测、慢请求分阶段归因、基线对照
Actuator + Micrometer 指标HTTP 接口 RT 分布、线程池/连接池指标聚合，可接 Prometheus + Grafana日常监控、趋势告警、容量评估
Arthas在线查看方法调用链耗时（trace）、入参返回（watch）、线程栈（thread）、生成火焰图（profiler）线上复现问题、定位热点方法与阻塞线程，无需重启
JFR（Java Flight Recorder）录制 CPU、内存分配、锁竞争、GC 事件生成 .jfr，JMC 离线分析周期性复盘、复杂问题留档、火焰图深度分析
 
# Arthas 常用命令（attach 到运行中的 JVM 进程）
as.sh                                   # 选择目标进程进入 Arthas
trace com.example.bookstore.OrderService createOrder -n 5
# 输出方法调用链每一层耗时，找出最慢的子调用
watch com.example.bookstore.OrderService createOrder '{params, returnObj}' -x 2
thread -b                               # 找出阻塞其他线程的线程
profiler start                          # 开始采集火焰图
profiler stop --file /tmp/order.jfr     # 结束并导出

# JFR 录制（Java 11+ 内置，jcmd 按 PID 操作）
jcmd <pid> JFR.start duration=60s filename=/tmp/order.jfr
# 用 JMC（Java Mission Control）打开 .jfr 文件分析 CPU 与锁事件

常见坑线上直接开启高频率 trace 或 profiler 会带来额外开销；先在测试环境复现，线上操作控制时长与采样范围，结束后及时停止。

104.3 常见瓶颈分类与识别信号

一句话定位：接口慢通常落入四类——外部 IO、锁竞争、慢 SQL、GC 停顿；每类有对应的资源信号，先归类再下手，避免盲目改代码。

类别典型原因识别信号
IO / 网络外部 HTTP 调用串行、未设超时、下游慢；文件读写阻塞；数据库往返次数多线程大量 WAITING/TIMED_WAITING；日志显示外部调用耗时；CPU 不高但 RT 高；网络指标升高
锁竞争synchronized 粒度大、共享集合并发冲突、缓存写竞争、分布式锁等待线程状态 BLOCKED；CPU 利用率不高；Arthas thread 显示锁持有链；JFR 锁事件集中
慢 SQL缺索引、索引失效、回表过多、N+1 查询、大事务、批量操作未分批慢查询日志；数据库 CPU 高；接口阶段耗时集中在 loadOrder 类步骤；连接池占用时间长
GC 停顿堆过小频繁 Young GC；大对象短命分配；内存泄漏导致 Full GC；元空间不足GC 日志频繁；RT 出现周期性尖刺；堆内存波动剧烈；Arthas dashboard 观察到 GC 次数与停顿时间

104.4 线程池与连接池调参

一句话定位：池化资源的大小决定并发承载与排队行为；线程数不是越大越好——过多线程放大上下文切换与内存开销，连接池过大反而压垮数据库。

@Configuration
public class PoolConfig {

    @Bean("businessExecutor")
    public ThreadPoolTaskExecutor businessExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);          // 常驻线程数
        executor.setMaxPoolSize(16);          // 队列满后允许扩到的上限
        executor.setQueueCapacity(200);          // 排队队列长度
        executor.setKeepAliveSeconds(60);
        executor.setThreadNamePrefix("biz-");
        // 队列满时由调用线程回退执行，起到背压作用（避免静默丢弃任务）
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}
参数调参思路
corePoolSize常驻线程；CPU 密集型接近核数，IO 密集型可高于核数，起步值由压测确定
maximumPoolSize队列满后才扩容；配合有界队列防止任务无限堆积占满内存
queueCapacity有界队列承载短时突发；过大让排队延迟被掩盖，过小则快速触发拒绝策略
拒绝策略AbortPolicy 抛异常（默认）；CallerRunsPolicy 回退背压；Discard 类策略仅允许在可丢弃任务上使用
线程命名threadNamePrefix 让日志与线程栈可归属到业务池，排障必备
 
# application-prod.yml：HikariCP 连接池参数
spring:
  datasource:
    hikari:
      maximum-pool-size: 15            # 连接池上限，小池快速排队优于大池争抢
      minimum-idle: 5                  # 最小空闲连接
      connection-timeout: 3000          # 获取连接超时 3 秒
      idle-timeout: 600000
      max-lifetime: 1800000
      pool-name: BookstoreHikariCP
连接池反直觉点：数据库连接数过大反而增加数据库上下文切换与锁竞争；HikariCP 官方建议池规模偏小、排队等待，公式起步值约为 核数 * 2 + 有效磁盘数，再按压测微调。池打满时先看慢 SQL 是否长期占用连接，而不是盲目加大池。

104.5 慢 SQL 与索引问题

一句话定位：数据库是后端最常见的瓶颈点；先用 EXPLAIN 确认是否走索引，再排查索引失效场景与 N+1 查询，最后用批量查询或缓存削减往返次数。

# 查看执行计划：重点关注 type、key、rows、Extra
EXPLAIN SELECT * FROM orders WHERE user_id = 1001 AND status = 'PENDING';
# type=ALL 表示全表扫描；key 为 NULL 表示未命中索引；rows 预估扫描行数过大需警惕
  • 索引失效场景：索引列上使用函数或运算（WHERE DATE(create_time) = ?）；隐式类型转换（字符串列用数字查询）；前导模糊 LIKE '%abc'；OR 两侧存在无索引列；联合索引未满足最左前缀；
  • N+1 查询：先查出订单列表，循环内逐个查商品/用户，一次请求产生几十上百次 SQL；改为批量 IN 查询后内存分组，或使用 fetch join / 缓存；
  • 大事务与长连接占用：事务内夹杂远程调用、循环查询，连接被长时间持有；把非数据库操作移出事务边界；
  • 复核顺序：慢查询日志定位语句 → EXPLAIN 看执行计划 → 补索引或改写 SQL → 压测对比 RT 与数据库 CPU。
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.function.Function;
import java.util.stream.Collectors;

// 反例：循环内逐条查询，N+1 问题
public List<OrderDetail> listByUser(Long userId) {
    List<Order> orders = orderRepository.findByUserId(userId);
    List<OrderDetail> result = new ArrayList<>();
    for (Order order : orders) {
        User buyer = userRepository.findById(order.buyerId()).orElseThrow(); // 每条一次 SQL
        result.add(OrderDetail.of(order, buyer));
    }
    return result;
}

// 正例：批量取出用户，内存分组装配，SQL 次数从 N+1 降到 2
public List<OrderDetail> listByUserOptimized(Long userId) {
    List<Order> orders = orderRepository.findByUserId(userId);
    Set<Long> buyerIds = orders.stream().map(Order::buyerId).collect(Collectors.toSet());
    Map<Long, User> userMap = userRepository.findAllById(buyerIds)
            .stream().collect(Collectors.toMap(User::id, Function.identity()));
    return orders.stream()
            .map(o -> OrderDetail.of(o, userMap.get(o.buyerId())))
            .toList();
}

104.6 优化闭环与常见反模式

一句话定位：基线 → 定位 → 优化 → 复测是一个闭环；每次改动都要有前后指标对照，优化后回归测试保证正确性，热点之外的代码保持可读优先。

图 104-2 基线 → 定位 → 优化 → 复测的持续闭环

常见反模式

  • 过早优化：业务尚未跑通就追求极致性能，把代码写成不可读的"技巧堆"；先保证正确性、可读性与测试覆盖，只对压测确认的热点下手；
  • 压测环境失真：空数据库、单条测试数据、本地网络压测得出"性能很好"的结论；生产数据量、索引规模、外部依赖条件必须尽量贴近；
  • 只看平均耗时：平均 RT 正常不代表长尾正常；P95/P99 才反映边缘用户体验，监控面板必须展示分位数；
  • 优化无对照：改完代码无法证明 RT 下降；基线数据、改动内容、复测结果要一并记录归档；
  • 优化破坏正确性：缓存不一致、异步化丢消息、连接池参数调整影响事务隔离；性能改动同样需要单元测试与回归验证。
收官视角工程化的完整链路是：Maven 组织依赖与构建（97）→ 多模块划分边界（98）→ 单元测试保障行为（99）→ 日志支撑观测排障（100）→ 规范与评审守住协作质量（101）→ 打包部署交付上线（102）→ 容器化标准化运行（103）→ 数据驱动持续优化（104）。质量不是某一步的动作，而是贯穿全程的体系。

✓ 本章小结

要点一句话
基线先行先定 RT/P95/QPS/错误率目标并留档，无基线无法证明优化有效
分析手段日志打点看阶段、Actuator 看分布、Arthas 看调用链、JFR 做事件复盘
瓶颈归类IO 等待、锁竞争、慢 SQL、GC 停顿四类，先看资源信号再选工具深挖
池化调参线程池有界队列 + 拒绝策略背压；连接池偏小排队，压测微调而非盲目加大
慢 SQLEXPLAIN 查执行计划；规避索引失效；批量查询消除 N+1；长事务移出非 DB 操作
闭环纪律基线→定位→优化→复测；避免过早优化、环境失真、只看平均、无对照与破坏正确性
