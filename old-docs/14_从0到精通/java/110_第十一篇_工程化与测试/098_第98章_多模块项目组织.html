98.1 单模块项目的痛点

一句话定位：所有类塞进一个 jar 时，编译范围、复用边界、部署粒度、依赖隔离全部失效；多模块是把工程按职责切成可独立编译、可单独复用的小构件。

前端同学可以对照 monorepo 里按 package 拆分目录的思路理解：一个仓库内多个独立包，各自有自己的 package.json，通过包名互相引用。Maven 多模块是同一思想在后端的落地。单模块工程常见的失控信号：

  • 编译耦合：改一行工具类，整个工程全量重编译，反馈越来越慢；
  • 复用困难：想把通用工具给另一个服务用，只能复制粘贴，两边各改各的；
  • 边界模糊：Controller 直接调 Mapper、Service 里写视图对象，分层形同虚设；
  • 依赖臃肿：一个模块里堆了报表、定时任务、对外接口所有依赖，jar 越来越大；
  • 部署粒度粗：只想发布业务层改动，却不得不把整个工程重新打包上线。
拆分目标多模块不是为了形式上的目录好看，而是获得四样东西：清晰的依赖方向、可复用的公共构件、独立的编译单元、可控的打包边界。

98.2 父 pom 与 modules 聚合

一句话定位：父工程是一个 packaging=pom 的特殊模块，它不产出 jar，只通过 <modules> 把子工程组织成一次构建的反应堆（reactor）。

<!-- bookstore/pom.xml：父工程（聚合根） -->
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example.bookstore</groupId>
  <artifactId>bookstore-parent</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>pom</packaging>   <!-- 关键：父工程只做聚合与配置，不打 jar -->

  <!-- 聚合：列出所有子模块目录名，反应堆按依赖关系排序后依次构建 -->
  <modules>
    <module>bookstore-common</module>
    <module>bookstore-api</module>
    <module>bookstore-domain</module>
    <module>bookstore-service</module>
    <module>bookstore-web</module>
  </modules>

  <properties>
    <java.version>17</java.version>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
</project>
<!-- bookstore-service/pom.xml：子模块声明自己的父工程 -->
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <parent>
    <groupId>com.example.bookstore</groupId>
    <artifactId>bookstore-parent</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <relativePath>../pom.xml</relativePath>  <!-- 默认值，指向父 pom 所在目录 -->
  </parent>

  <artifactId>bookstore-service</artifactId>
  <packaging>jar</packaging>
</project>

98.3 dependencyManagement 与依赖继承

一句话定位：父 pom 里 <dependencies> 会被所有子模块直接继承；<dependencyManagement> 只登记"版本与坐标约束"，子模块需要时再声明、且不必写版本号。

对比项dependencies（父 pom）dependencyManagement（父 pom）
是否自动引入是，所有子模块 classpath 直接拥有否，仅登记版本，子模块显式声明才引入
版本写法子模块继承父 pom 中的版本子模块不写 version 时采用父 pom 登记版本
典型用途所有模块都要用的基础库（lombok、slf4j-api、jackson）统一锁定第三方库版本，避免子模块各写各的
风险子模块被迫继承不需要的依赖，边界变脏漏写声明时不会引入，需逐一核对
 
<!-- 父 pom：统一版本登记，不直接引入 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.2.5</version>
      <type>pom</type>
      <scope>import</scope>   <!-- 导入 Spring Boot BOM，批量托管其生态版本 -->
    </dependency>
    <dependency>
      <groupId>org.projectlombok</groupId>
      <artifactId>lombok</artifactId>
      <version>1.18.32</version>
      <scope>provided</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 父 pom：所有子模块默认拥有的基础依赖 -->
<dependencies>
  <dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
  </dependency>
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
  </dependency>
</dependencies>
<!-- 子模块：只写 groupId + artifactId，版本由父 pom 的 dependencyManagement 锁定 -->
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- 不写 version：继承 BOM 托管版本 -->
  </dependency>
  <dependency>
    <groupId>com.example.bookstore</groupId>
    <artifactId>bookstore-domain</artifactId>
    <version>1.0.0-SNAPSHOT</version>
  </dependency>
</dependencies>
实践纪律版本号集中在父 pom 一处维护；子模块 pom 只描述"我需要什么能力"，不重复写版本。升级第三方库时只改父工程一处，这就是多模块统一版本的收益。

98.4 模块划分原则与依赖方向

一句话定位按"谁被谁调用"分层切模块：上层依赖下层，下层永远不知道上层存在；跨层契约放在 api 模块，避免下层反向引用上层类型。

模块职责典型内容
bookstore-common与业务无关的公共能力工具类、常量、通用异常、分页对象、枚举基类
bookstore-api对外契约与跨层 DTO请求/响应 DTO、接口定义、枚举、对外事件模型
bookstore-domain数据层与领域模型实体类、Mapper / Repository、数据库映射
bookstore-service业务逻辑编排Service 类、事务边界、规则校验、外部客户端封装
bookstore-web接入层与装配入口Controller、全局异常处理、配置类、启动类、静态资源
  • 允许的方向：web → service → domain → common；service / web 可引用 api；api 与 common 不依赖任何业务模块；
  • 禁止的方向：domain 依赖 service、common 依赖业务模块、service 依赖 web——一旦出现，分层就被击穿；
  • DTO 边界：Controller 不直接返回数据库实体；入参出参使用 api 模块中的 DTO，避免实体泄漏到接入层；
  • 启动类位置：Spring Boot 启动类放在 web 模块，扫描包覆盖 service、domain 所在根包（或显式声明扫描路径）。
// bookstore-web：启动类只负责装配，业务代码在下层模块
@SpringBootApplication
@ComponentScan(basePackages = "com.example.bookstore")
public class BookstoreApplication {
    public static void main(String[] args) {
        SpringApplication.run(BookstoreApplication.class, args);
    }
}

// bookstore-service：只依赖 domain 与 api，不认识 Controller 的存在
@Service
public class OrderService {
    private final OrderMapper orderMapper;   // domain 模块
    private final OrderDtoConverter converter; // api 模块提供的转换工具
    public OrderService(OrderMapper orderMapper, OrderDtoConverter converter) {
        this.orderMapper = orderMapper;
        this.converter = converter;
    }
}

98.5 构建顺序与 -pl / -am

一句话定位反应堆根据模块间依赖关系做拓扑排序，先构建被依赖的底层模块，再构建上层；-pl 圈定目标模块，-am 连带构建其依赖，-amd 反向连带依赖它的模块。

# 在父工程根目录执行：按拓扑顺序构建全部模块
mvn clean install

# 只构建 bookstore-web 及其依赖链（common/api/domain/service 一起构建）
# -pl, --projects <模块名>；-am, --also-make 同时构建被依赖模块
mvn clean install -pl bookstore-web -am

# 只构建 common，并连带构建所有依赖 common 的模块（-amd, --also-make-dependents）
mvn clean install -pl bookstore-common -amd

# 跳过测试打包 web 模块，用于本地快速验证启动
mvn clean package -pl bookstore-web -am -DskipTests

# 查看反应堆将按什么顺序构建：控制台先输出 "Reactor Build Order" 清单
mvn validate -pl bookstore-web -am
  • install 的必要性：反应堆内模块间引用直接走内存产物；跨工程或单独打包 web 模块时，被依赖模块需要先 install 进本地仓库；
  • CI 流水线：全量 mvn clean install 跑测试；增量排查时用 -pl ... -am 缩短反馈；
  • 产物归属：只有 web 模块最终产出可执行 fat jar；其余模块产出普通 jar 供上层引用。

98.6 常见坑：父路径、循环依赖与 common 膨胀

① parent relativePath 写错或缺失

子模块 <parent> 中不写 <relativePath> 时默认查找 ../pom.xml；若父工程不在上一级目录，Maven 会先去本地/远程仓库找父 pom，报 Non-resolvable parent POM。正确做法是显式写出相对路径，或把父工程先 install 到本地仓库。

② 模块循环依赖

web 依赖 service、service 又依赖 web，或 common 依赖 domain、domain 又依赖 common，Maven 在反应堆排序阶段直接失败：

[ERROR] The projects in the reactor contain a cyclic reference:
  bookstore-web -> bookstore-service -> bookstore-web
  解决方案：把被双向引用的类型下沉到 api / common，切断环，而不是调整模块顺序。

③ common 模块沦为垃圾桶

所有不想归类的类都塞进 common，结果 common 反向依赖了数据库、Redis、Spring 上下文，底层模块被业务污染，其他服务引入 common 时被迫带上一堆用不到的依赖。纪律：common 不 import 任何业务模块与框架专属类；业务公共代码放 api，领域公共代码放 domain。

拆分节奏建议：新工程不必一开始就拆五个模块；先按 web + service + common 起步，当复用需求、编译速度、边界问题真实出现时再拆分。过度拆分同样是成本——模块越多，构建配置与跨模块沟通越重。

常见坑子模块之间互相引用时，version 必须与父工程统一；手写版本号会在升级时留下漏网之鱼。模块坐标统一使用 ${project.version} 引用父版本最稳妥。

✓ 本章小结

要点一句话
拆分动因单模块编译耦合、复用困难、边界模糊、部署粒度粗，多模块按职责切分构件
父工程packaging=pom，modules 聚合子模块形成反应堆，统一构建入口
版本管理dependencyManagement 只锁版本不引入；dependencies 父级声明被全模块继承
分层方向web → service → domain → common；api 承载契约；禁止反向依赖
构建命令-pl 指定模块，-am 连带依赖模块，-amd 反向连带；底层模块先 install
硬伤规避relativePath 指对父 pom；循环依赖靠下沉类型解环；common 保持无业务依赖
