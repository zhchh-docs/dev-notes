37.1 对象与字节的往返

序列化（Serialization）把对象图变成字节流，用于持久化（存文件、进缓存）和网络传输（RMI、RPC 的早期底座）。

public class User implements Serializable {   // 标记接口，无方法
    private String name;
    private int age;
    // 建议显式写 serialVersionUID（见 37.2）
}

// 写对象
try (ObjectOutputStream oos =
        new ObjectOutputStream(new FileOutputStream("user.bin"))) {
    oos.writeObject(new User("张三", 25));
}

// 读对象
try (ObjectInputStream ois =
        new ObjectInputStream(new FileInputStream("user.bin"))) {
    User u = (User) ois.readObject();      // 返回 Object，需要强转
}
  • 序列化会递归处理对象引用的整个图：User 里的 Address 也会被写进去；同一个对象出现两次不会写两份，用引用序号去重；
  • transient 修饰的字段不参与序列化（如密码、数据库连接）；static 字段属于类，本来就不序列化；
  • JDK 之后有 Externalizable（自己控制读写）和记录在案的无数框架：JSON/Protobuf/Hessian——跨语言场景早已不用 JDK 序列化。

37.2 serialVersionUID：版本兼容的钥匙

序列化字节里藏着类的"指纹"：类名、字段名、方法签名等算出的一个 long。反序列化时比对指纹，不一致就抛 InvalidClassException。

public class User implements Serializable {
    private static final long serialVersionUID = 1L;   // 亲手钉死版本号
    private String name;
    private int age;
    // 后来新增字段：private String email;   // 旧数据读进来 email = null，兼容！
}
  • 不显式声明时，JVM 自动算 UID——改任何字段/方法都可能变 UID，老文件全部读不了；
  • 显式写 1L 并保持不变：加字段可兼容（新字段给默认值），删字段会丢数据但不报错；改字段类型/类名才会炸；
  • IDE 都会提示"Serializable class without serialVersionUID"，不是警告着玩的。
serialVersionUID 是类的"数据格式版本号"：固定它，你控制的是数据兼容；交给 JVM 算，编译器控制你的数据命运。

37.3 反序列化漏洞：Java 安全史上的深渊

反序列化的危险在于：它执行的代码不止来自你的类，还来自字节流里能构造出的任意对象。攻击者构造一段恶意字节流，readObject 时沿着 gadget 链一路调用，最终触发 Runtime.exec()——这就是著名的 Apache Commons Collections 反序列化漏洞（CVE-2015-7501 等）。

// 危险信号：字节流来自不可信输入
ObjectInputStream ois = new ObjectInputStream(socket.getInputStream());
Object obj = ois.readObject();      // 这里可能执行任意代码！

// 自 Java 9 起的安全改进：JEP 290 过滤
// 通过 jdk.serialFilter 系统属性/ API 限定允许反序列化的类白名单
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "com.example.User;!*");     // 只放行 User，其余全部拒绝
ois.setObjectInputFilter(filter);
  • 防御第一原则：永不反序列化不可信数据；跨系统传输改用 JSON/Protobuf 这类纯数据格式；
  • 必须用 JDK 序列化时：启用 JEP 290 过滤、给 RMI/HTTP 入口加白名单；
  • 自定义 readObject 时对字段做校验，别让恶意对象"看起来合法"；
  • 依赖升级：很多 gadget 链依赖老版本 commons-collections 等库，保持依赖最新。
常见坑缓存里"顺手"存了个 Java 对象（JDK 序列化进 Redis），等哪天缓存被污染或运维误读，就是一次远程代码执行。Redis 存对象优先 JSON，别存 .bin。
