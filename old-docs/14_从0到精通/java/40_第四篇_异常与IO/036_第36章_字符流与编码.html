36.1 字符 = 字节 + 编码表

磁盘上只有字节。"中"这个字符存到文件里是几个字节？取决于字符集（Charset）——一张字符到字节的映射表：

"中".getBytes(StandardCharsets.UTF_8);     // 3 字节：E4 B8 AD
"中".getBytes(StandardCharsets.GBK);      // 2 字节：D6 D0
"中".getBytes(StandardCharsets.UTF_16);   // 4 字节：FE FF 4E 2D（含 BOM）
  • 解码：字节 → 字符（读文件）；编码：字符 → 字节（写文件）；
  • 两端用不同编码表，就会乱码——读的人按 GBK 解一段 UTF-8，解出来全是"锟斤拷"；
  • Java 的 char 是 UTF-16 的一个代码单元；String 内部就是 UTF-16 字节序列（Java 17 起紧凑字符串优化，Latin-1 字符每字符仅 1 字节）；
  • 实践铁律：读写两端显式指定同一个编码，不要依赖平台默认值。
乱码从来不是"字坏了"，而是"读的人用错了字典"。所有 IO 边界（文件、网络、数据库）都要约定编码。

36.2 Reader/Writer 家族与桥接流

字符流和字节流一一对应，顶层是 Reader/Writer：

Reader                        Writer
 ├─ FileReader              ├─ FileWriter
 ├─ BufferedReader          ├─ BufferedWriter
 ├─ InputStreamReader(桥)   ├─ OutputStreamWriter(桥)
 └─ StringReader            └─ StringWriter

桥接流把字节流包起来，负责按指定编码翻译：

// 读：字节流 + UTF-8 字典 = 字符流
try (Reader r = new BufferedReader(
        new InputStreamReader(
            new FileInputStream("note.txt"), StandardCharsets.UTF_8))) {
    String line;
    while ((line = r.readLine()) != null) {   // readLine 不含换行符
        System.out.println(line);
    }
}

// 写：字符按 UTF-8 编码成字节落盘
try (Writer w = new BufferedWriter(
        new OutputStreamWriter(
            new FileOutputStream("out.txt"), StandardCharsets.UTF_8))) {
    w.write("你好，字符流");
    w.newLine();   // 跨平台换行，别硬写 "\n"
}
常见坑FileReader/FileWriter 是"叛徒"：名字像字符流很方便，但只能使用平台默认编码，跨环境必出乱码。新代码一律用 InputStreamReader + 显式 UTF-8，或直接用 NIO.2 的 Files.newBufferedReader(path, UTF_8)。

36.3 UTF-8 乱码四大来源

  • ① 用了默认编码：没指定 Charset 的 API（FileReader、new String(bytes)、字节→字符的默认转换）随 JVM 语言环境漂移——开发机 UTF-8、生产容器 POSIX locale 直接翻车；
  • ② 写读编码不一致：上游系统写 UTF-8，下游按 GBK 读；或反过来；
  • ③ 截断了多字节字符：按字节长度硬切 UTF-8 文本（比如 bytes.length > 100 就截断），把一个汉字 3 字节的序列切一半，尾部出现 U+FFFD"�"；
  • ④ BOM 作怪：Windows 记事本保存的"UTF-8 with BOM"，文件头多了 EF BB BF，读出来第一个字符是 \uFEFF，破坏 JSON 解析、CSV 表头比较。
// 排查三板斧
new String(bytes, StandardCharsets.UTF_8);          // 显式解码，别用 new String(bytes)
StandardCharsets.UTF_8.name();                      // 确认字典
new String(bad, GBK).getBytes(UTF_8);               // 经典"错编错解"抢救：当初按 GBK 读的，就按 GBK 读回来再转 UTF-8

还有一类"乱码"其实是显示层问题：字节是正确的 UTF-8，但终端/数据库连接/HTTP 响应头没声明 charset——检查 Content-Type: text/html; charset=utf-8 与 JVM 的 file.encoding。

要点一句话

字符流Reader/Writer 家族与字节流一一对应

✎ 本章习题

A 基础把字符串"你好，Java"分别按 UTF-8 和 GBK 写入两个文件，用十六进制打印两个文件的字节，观察同一个字符的编码差异。
B 进阶用 BufferedReader 逐行读取一个大文本文件，过滤出包含指定关键词的行并写入输出文件；要求显式指定 UTF-8，并用 newLine() 写换行。
C 挑战模拟修复一个"乱码文件"：先把正常文本按 GBK 写入，再按 UTF-8 读入制造乱码，然后写一个修复函数把乱码恢复为原文；最后思考为什么"按 GBK 读、按 UTF-8 写"这一步是正确的抢救姿势。
