72.1 事务四性质 ACID

性质含义由谁保证
原子性 A事务内操作全做或全不做undo log（本章主角）
一致性 C事务前后数据满足业务约束靠 A、I、D 共同达成
隔离性 I并发事务互不干扰锁 + MVCC（下一节）
持久性 D提交后断电也不丢redo log

一个直观反例：A 转账 100 给 B，若"扣 A"成功、"加 B"失败且不回滚——钱凭空消失。事务保证两条语句同生共死。

72.2 JDBC 事务三步 API

一句话定位：JDBC 默认每条语句自动提交（autoCommit=true）。开启事务只需三步：关自动提交 → 干活 → 提交；出异常则回滚。

// 事务三步的标准写法（模板）
try (Connection conn = ds.getConnection()) {
    conn.setAutoCommit(false);          // ① 开启事务
    try {
        // ② 业务 SQL（多条，同一 conn）
        debit(conn, fromId, amount);    // 扣款
        credit(conn, toId, amount);     // 入账
        conn.commit();                  // ③ 全部成功 → 提交
    } catch (Exception e) {
        conn.rollback();                // 任一步失败 → 全部撤销
        throw new RuntimeException("转账失败已回滚", e);
    }
}
所有 SQL 必须使用同一个 Connection——事务上下文绑定在连接上。跨连接的两条 SQL 不可能在一个事务里，这是初学者最高频的错误。

72.3 实战：转账与回滚验证

import java.sql.*;

public class TransferDemo {
    private static void transfer(DataSource ds, long from, long to, int amount) {
        try (Connection conn = ds.getConnection()) {
            conn.setAutoCommit(false);
            try {
                exec(conn, "UPDATE account SET balance = balance - ? WHERE id = ?",
                     amount, from);
                // 模拟入账环节抛异常（如余额校验失败、程序崩溃）
                if (to < 0) throw new IllegalStateException("非法账户");
                exec(conn, "UPDATE account SET balance = balance + ? WHERE id = ?",
                     amount, to);
                conn.commit();
                System.out.println("转账成功");
            } catch (Exception e) {
                conn.rollback();                       // 扣款被撤销！
                System.out.println("失败已回滚：" + e.getMessage());
            }
        } catch (SQLException e) { throw new RuntimeException(e); }
    }
    private static void exec(Connection conn, String sql, Object... args)
            throws SQLException {
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            for (int i = 0; i < args.length; i++) ps.setObject(i + 1, args[i]);
            ps.executeUpdate();
        }
    }
}
// 验证：to 传 -1，查询发现 from 的余额没有减少——原子性生效

常见坑：DDL（CREATE/ALTER）与部分工具语句会隐式提交当前事务，混进事务块等于事务失效。事务里只放 DML。

72.4 隔离级别与并发副作用

隔离级别脏读不可重复读幻读性能
READ UNCOMMITTED可能可能可能最高
READ COMMITTED避免可能可能高
REPEATABLE READ（MySQL 默认）避免避免InnoDB 基本避免中
SERIALIZABLE避免避免避免最低
 
// 查看与设置隔离级别
int lvl = conn.getTransactionIsolation();
conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);

// 数据库层面查看（MySQL）
// SELECT @@transaction_isolation;
  • 脏读：读到别人未提交的数据，对方回滚你就读了"从未存在"的数据；
  • 不可重复读：同一事务两次读同一行，值变了（别人 update 提交了）；
  • 幻读：两次相同范围查询，行数变了（别人 insert 提交了）；
  • InnoDB 用 MVCC（多版本快照）+ 锁，在 RR 级别下已消除大部分幻读场景。

72.5 保存点与事务规范

// Savepoint：大事务里的"局部后悔药"
conn.setAutoCommit(false);
insertLogs(conn);                    // 步骤 1：日志（可以局部回滚）
Savepoint sp = conn.setSavepoint("before-core");
try {
    updateCore(conn);                // 步骤 2：核心更新
    conn.commit();
} catch (Exception e) {
    conn.rollback(sp);               // 只撤销步骤 2，步骤 1 保留
    conn.commit();                   // 提交保留下来的部分
} finally {
    conn.releaseSavepoint(sp);
}
事务使用五条纪律：① 事务尽量短，别包 RPC/HTTP 调用；② 只包 DML；③ 必须配 rollback；④ 连接必须归还前结束事务状态；⑤ 大批量写入拆小事务（下一章）。

✓ 本章小结

要点一句话
ACID原子靠 undo，持久靠 redo，隔离靠锁+MVCC，一致是结果
JDBC 三步setAutoCommit(false) → SQL → commit/rollback；同连接
隔离级别RC 读已提交 / RR 可重复读（MySQL 默认）/ Serializable
隐式提交DDL 会打断事务——事务块内只放 DML
规范短事务、必回滚、大写拆小

✎ 本章习题

A 基础默写 JDBC 事务三步模板，并解释为什么必须同一个 Connection。
B 进阶复现本章转账回滚：故意在第二步抛异常，查表验证余额未变；再把 rollback 注释掉看后果。
C 挑战开两个连接模拟"不可重复读"：连接 A 两次读同一行之间，连接 B update 并提交；分别在 RC 与 RR 级别下对比两次读的结果。
