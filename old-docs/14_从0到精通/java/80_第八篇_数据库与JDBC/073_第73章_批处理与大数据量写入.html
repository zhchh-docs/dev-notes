73.1 为什么逐条 insert 慢

一句话定位：慢不在数据库执行，而在"每行一次完整对话"——每条 SQL 都是独立的网络往返、独立解析、（默认）独立提交。

成本层逐条时的开销批量化收益
网络往返每条 1 次 RTT（局域网 0.5ms，跨机房 20ms+）打包后接近 0
SQL 解析每条完整解析一遍预编译复用 + 改写成多值
事务刷盘autoCommit 下每条一次 redo 刷盘一批一次 fsync

实测感知：本机 MySQL 插 10 万行，逐条约 60~90 秒，正确批处理后 3~5 秒——差距来自上表三层，缺一层就回到慢速档。

73.2 addBatch/executeBatch 正确用法

public long batchInsert(Connection conn, List<User> users) throws SQLException {
    String sql = "INSERT INTO user(name, email) VALUES(?, ?)";
    long total = 0;
    try (PreparedStatement ps = conn.prepareStatement(sql)) {
        conn.setAutoCommit(false);                  // 批处理必须配手动事务
        int count = 0;
        for (User u : users) {
            ps.setString(1, u.name());
            ps.setString(2, u.email());
            ps.addBatch();                          // 攒进批次，不执行
            if (++count % 1000 == 0) {              // 每 1000 条刷一次
                total += sum(ps.executeBatch());
                ps.clearBatch();
            }
        }
        total += sum(ps.executeBatch());            // 收尾零头
        conn.commit();
    } catch (SQLException e) {
        conn.rollback();
        throw e;
    }
    return total;
}
private static int sum(int[] arr) { int s = 0; for (int n : arr) s += n; return s; }
  • executeBatch 返回每条语句的受影响行数数组；
  • 批大小 500~2000 是常见甜点区：太小往返多，太大单包超限（max_allowed_packet）与回滚代价大；
  • 批内循环要 clearBatch（或依赖驱动自动清），否则内存与行为都可能异常。

73.3 两个决定性开关

JDBC 批处理默认只是"攒起来逐条发"——真正提速必须开这两个：

# ① MySQL 驱动：把批改写成多值 INSERT（性能差 10~50 倍的关键）
jdbc:mysql://localhost:3306/jdbc_demo?rewriteBatchedStatements=true

# ② 关自动提交（代码里）：一批一次 fsync，而不是每条一次
conn.setAutoCommit(false);   # 已在第 73.2 节代码中

73.4 分批提交与失败恢复

  • 可重跑：导入任务要能"从断点续传"——用唯一键 + INSERT IGNORE / ON DUPLICATE KEY UPDATE 让重复执行幂等；
  • 分批事务：10 万行不要一个事务到底（undo 膨胀、锁窗口过长），按 1 万行一个事务；
  • 失败样本留存：单行格式错误不要让整批失败——错误行落文件/表，继续跑；
  • 限速：线上导入注意主从延迟，必要时批间 sleep 控制复制压力。
// 幂等批量的常用模板（可重跑、可恢复）
String sql = "INSERT INTO user(id, name, email) VALUES(?, ?, ?) " +
             "ON DUPLICATE KEY UPDATE name = VALUES(name), email = VALUES(email)";
// 断了再跑一遍也不会产生重复数据

73.5 更快的路：LOAD DATA 与替代方案

方案适用与要点
JDBC 批处理通用首选；十万级 3~5 秒可接受
LOAD DATA INFILECSV 大导入最快（百万级分钟内）；需 LOCAL INFILE 权限，注意字符集
导入临时表 + 迁移先快速入临时表，再分批 INSERT...SELECT 校验清洗，回滚友好
消息队列削峰实时链路的大批量入库：先落 MQ，消费者按自身节奏批量写
LOAD 时禁索引超大导入可先删二级索引、导完重建（离线库专用，慎用于生产主库）
 
mysql> LOAD DATA LOCAL INFILE '/tmp/users.csv'
    -> INTO TABLE user FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n'
    -> (name, email);
# 需要连接参数 allowLoadLocalInfile=true 与服务端 local_infile=ON

✓ 本章小结

要点一句话
慢的根源往返 + 解析 + 刷盘三层各自独立；批量同时消掉三层
正确姿势addBatch + executeBatch + 手动事务 + 每 1000 条刷
致命开关rewriteBatchedStatements=true；不开等于白批
可靠性分批事务、幂等重跑（ON DUPLICATE KEY）、错误行留存
更大体量LOAD DATA 最快；实时链路用 MQ 削峰
