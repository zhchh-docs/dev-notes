76.1 手写 JDBC 的四宗"重复"

重复点每段代码都要写的谁来自动化
资源管理getConnection / try / close 归还连接池 + 模板（Spring 管理）
参数绑定ps.setXxx(1,..)(2,..)…下标硬编码注解/占位符自动映射
结果映射rs.getXxx + new User(...) 逐字段列名→属性名自动/配置映射
异常翻译catch SQLException → 自定义异常框架统一翻译（Spring 体系）

第 74 章的 DAO 已经把结构捋顺了，但每个方法仍有 10 行仪式代码。MyBatis 的价值：保留 SQL 控制权，同时消灭仪式代码。

76.2 MyBatis 最小可用示例

/** Mapper 接口：只有接口，没有实现类！ */
public interface UserMapper {
    @Select("SELECT id, name, email FROM user WHERE id = #{id}")
    User findById(long id);

    @Insert("INSERT INTO user(name, email) VALUES(#{name}, #{email})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(User user);          // 插入后自动回填 user.id

    @Update("UPDATE user SET email = #{email} WHERE id = #{id}")
    int updateEmail(@Param("id") long id, @Param("email") String email);
}

// 使用（配合第 74 章的 DataSource）
try (SqlSession session = sqlSessionFactory.openSession()) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    User u = mapper.findById(1);     // 直接得到映射好的对象！
    System.out.println(u);
}
<!-- 复杂 SQL 写 XML：UserMapper.xml -->
<mapper namespace="demo.dao.UserMapper">
  <select id="findByNameLike" resultType="demo.entity.User">
    SELECT id, name, email FROM user
    WHERE name LIKE CONCAT('%', #{kw}, '%')
  </select>
</mapper>
  • #{}：预编译参数（安全，第 75 章）；${}：字符串替换（注入风险，禁用于值）；
  • 列名与属性名不一致时用 resultMap 显式映射或 map-underscore-to-camel-case=true；
  • insert 回填主键由 @Options(useGeneratedKeys) 声明——第 70 章的手工回填被配置化。

76.3 Mapper 接口背后的代理魔法

// 你没有写 UserMapperImpl，为什么 mapper.findById 能用？
// 核心就是第 42 章的 JDK 动态代理（简化示意）：
public class MapperProxy<T> implements InvocationHandler {
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) {
        // 1. 取出方法上的 SQL（注解或 XML 里按 namespace+id 定位）
        // 2. 解析 #{xxx} 参数名，用反射从 args 中取值
        // 3. 底层执行 PreparedStatement（第 70 章那套流程）
        // 4. 结果集映射回方法返回类型（第 70.5 节的行映射）
        return sqlSession.selectOne(statementId, param);
    }
}
// getMapper 内部：Proxy.newProxyInstance(loader, {UserMapper.class}, new MapperProxy(...))

你写的每个 Mapper 都是"接口即契约"，代理在运行时按注解/XML 元数据生成实现——这就是第 39~42 章反射、注解、动态代理三件套的工业级应用。

76.4 动态 SQL：if/where/foreach

<!-- 多条件动态查询：非空才拼条件，杜绝手写 where 拼接地狱 -->
<select id="search" resultType="demo.entity.User">
  SELECT id, name, email FROM user
  <where>
    <if test="name != null and name != ''">
      AND name LIKE CONCAT('%', #{name}, '%')
    </if>
    <if test="email != null"> AND email = #{email} </if>
    <if test="ids != null and ids.size() > 0">
      AND id IN
      <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
      </foreach>
    </if>
  </where>
  ORDER BY id
</select>

动态 SQL 帮你处理了开头 where / 多余 and / 括号配对等细节。排序字段这类"结构级动态"仍要回到白名单（第 75.3 节），MyBatis 不豁免安全原则。

76.5 选型坐标：JdbcTemplate / MyBatis / JPA

方案定位适用场景
Spring JdbcTemplate薄模板层SQL 少而简单、工具脚本；消灭资源与异常样板，SQL 仍手写
MyBatisSQL 映射框架国内主流：复杂 SQL 可控、DBA 可审；报表/多表关联友好
Spring Data JPAORM 全自动CRUD 为主的中小系统；对象图导航，但复杂查询退化为调优黑洞
经验法则：需要"看得见摸得着每一条 SQL"选 MyBatis；团队 ORM 经验深、模型简单可选 JPA；两者混用也可（不同模块不同 Mapper）。不要用 ORM 的"自动"掩盖"不会写 SQL"。

✓ 本章小结

要点一句话
痛点清单资源、参数、映射、异常四类重复——框架全部接管
MyBatis 心智接口即 DAO，SQL 在注解/XML；SQL 控制权保留
底层原理Mapper = 动态代理；执行核心仍是 JDBC 那套
动态 SQLif/where/foreach 处理条件拼装；结构级动态仍走白名单
选型薄工具 JdbcTemplate，复杂 SQL MyBatis，对象驱动 JPA

第八篇收官：从驱动加载到批量写入，从 DAO 分层到框架选型——你已经具备"数据层"的完整语言。第九篇 Spring 核心，将把这些手工组装的层交给容器。
