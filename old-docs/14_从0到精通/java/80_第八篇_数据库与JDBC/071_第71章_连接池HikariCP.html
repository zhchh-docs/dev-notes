71.1 为什么需要连接池

一句话定位：连接池 = 预先建好一批连接，请求来时"借用"，用完"归还"，由池统一管理数量与健康状况。

  • 建连太贵：TCP 三次握手 + TLS + 认证 + 会话初始化，每次几毫秒起步；池化后摊销为零；
  • 数量失控：没有池时，1000 个并发就开 1000 条连接——数据库连接是稀缺资源，会直接把 DB 打挂；
  • 健康巡检：MySQL 默认 8 小时无活动断开连接（wait_timeout），池负责"保活与报废"，业务代码永远拿到可用连接。
常见池特点现状
HikariCP字节码精调、FastList、无锁快路径Spring Boot 默认，事实标准
Druid内置 SQL 监控页面、WallFilter国内运维生态丰富
DBCP2 / C3P0老牌新项目基本不用

71.2 HikariCP 的借还模型

图 71-1 连接池借还模型

连接池世界的 close() 不是关闭，而是归还——HikariCP 返回的是包装代理，close 被拦截后把物理连接放回 Bag。忘记 close 的连接永远不会自动回来（直到 leakDetectionThreshold 报警）。

71.3 核心参数详解

import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;

public class PoolSetup {
    public static HikariDataSource create() {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl("jdbc:mysql://localhost:3306/jdbc_demo?serverTimezone=Asia/Shanghai");
        cfg.setUsername("app");
        cfg.setPassword("App#123456");

        cfg.setMaximumPoolSize(10);          // 最大连接数（默认 10）
        cfg.setMinimumIdle(10);              // 固定池大小（官方建议 max=idle）
        cfg.setConnectionTimeout(3000);      // 借不到连接等多久（默认 30s，太长！）
        cfg.setMaxLifetime(25 * 60 * 1000);  // 连接寿命，必须 < MySQL wait_timeout
        cfg.setIdleTimeout(5 * 60 * 1000);   // 空闲回收（固定池时可不管）
        cfg.setKeepaliveTime(60 * 1000);     // 空闲保活探测
        cfg.setConnectionTestQuery("SELECT 1"); // 驱动支持 JDBC4 可不设
        cfg.setPoolName("demo-pool");
        return new HikariDataSource(cfg);
    }
    public static void main(String[] args) throws Exception {
        try (var ds = create(); var conn = ds.getConnection()) {
            System.out.println("池名：" + conn.getMetaData().getUserName());
        }
    }
}
参数建议值说明
maximumPoolSize小！ CPU×2 起池不是越大越好：数据库端连接切换有成本，Hikari 官方实测小池吞吐更高
connectionTimeout1~3s默认 30s 会让故障雪崩拖 30s 才报错；快速失败更健康
maxLifetime小于 DB wait_timeout连接主动报废重建，避免被服务端单方面掐断
leakDetectionThreshold生产 60s 可开借出超过该时长未归还 → 打出持有堆栈（抓泄漏神器）

常见坑："数据库报 too many connections，我把池调到 200 好了"——错。3 个实例 × 200 = 600，直接压垮库。正确解法是限流、缓存、拆库，池大小仍保持小。

71.4 手写一个迷你连接池

理解原理最好的方式是自己造一个（生产请勿使用）：

import java.sql.*;
import java.util.concurrent.*;

public class MiniPool implements AutoCloseable {
    private final BlockingQueue<Connection> idle;
    private final String url, user, pass;
    private final int size;

    public MiniPool(String url, String user, String pass, int size) throws SQLException {
        this.url = url; this.user = user; this.pass = pass; this.size = size;
        this.idle = new LinkedBlockingQueue<>(size);
        for (int i = 0; i < size; i++) idle.offer(newConnection());  // 预热
    }
    private Connection newConnection() throws SQLException {
        return DriverManager.getConnection(url, user, pass);
    }
    /** 借：超时快速失败 */
    public Connection getConnection(long timeoutMs) throws InterruptedException, SQLException {
        Connection c = idle.poll(timeoutMs, TimeUnit.MILLISECONDS);
        if (c == null) throw new SQLException("借连接超时，池满或泄漏");
        return c;
    }
    /** 还：包装 Connection，拦截 close 改为归还 */
    public void release(Connection c) { idle.offer(c); }

    @Override public void close() throws SQLException {
        Connection c;
        while ((c = idle.poll()) != null) c.close();   // 真关闭
    }
}
// 不足之处（也是 Hikari 解决的）：无泄漏检测、无健康检查、
// 状态变更（事务未回滚）不复位、并发借还的细节处理粗糙。

✓ 本章小结

要点一句话
池化动机摊销建连成本、限制总量、保活巡检
借还模型close 即归还；池小吞吐高（Hikari 实测）
关键参数max 小（10~20）、timeout 快失败、maxLifetime < wait_timeout
泄漏排查leakDetectionThreshold 打持有点堆栈；根因几乎都是没 try-with-resources
容量账池大小 × 实例数 × 数据库副本数 = 总连接，预算要算清
