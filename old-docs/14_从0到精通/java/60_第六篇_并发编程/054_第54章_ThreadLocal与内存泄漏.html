54.1 线程私有存储

static ThreadLocal<SimpleDateFormat> fmt =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

// 每个线程调 fmt.get() 拿到的是自己的实例——互不干扰
public String formatDate(Date d) {
    return fmt.get().format(d);      // 线程 A 和 B 拿到不同的 SimpleDateFormat
}
  • 动机：有些对象线程不安全（SimpleDateFormat、Random），全局共享要加锁；每个线程一个实例则无锁高效；
  • 另一类用途：上下文传递——一次请求中在过滤器存 userId，后面任意层直接 get，不用层层传参（Spring 的 RequestContextHolder、事务上下文都这么干）；
  • 语义记住一句话：ThreadLocal 不是"共享变量的并发方案"，而是"空间换线程隔离"——每线程一份副本，根本不共享，何来冲突。

54.2 原理：Thread 里的 Map

很多人以为数据存在 ThreadLocal 对象里——错了，存在线程对象里：

// 结构关系
Thread.currentThread()
  └─ ThreadLocalMap threadLocals        // 线程对象自带的 Map
       ├─ Entry[ weakRef(tl1) -> value1 ]   // key 是 ThreadLocal 的弱引用
       └─ Entry[ weakRef(tl2) -> value2 ]

// 简化源码
public T get() {
    Thread t = Thread.currentThread();
    ThreadLocalMap map = t.threadLocals;      // 拿当前线程的 map
    Entry e = map.getEntry(this);             // 以 ThreadLocal 实例为 key
    return e != null ? e.value : initialValue();
}
  • get/set 都以当前线程为起点——天然线程隔离的根因；
  • Entry 的 key 是弱引用指向 ThreadLocal 对象：外部没有强引用时，ThreadLocal 实例可以被 GC；
  • hash 冲突用开放寻址（线性探测），不像 HashMap 拉链。

54.3 内存泄漏与线程池传染

弱引用救了 key，救不了 value：

threadLocal = null;   // 外部强引用断开
// GC 后：Entry.key 被回收 → 变成 key=null 的"脏 Entry"
// 但 value 还被 Entry 强引用，Entry 被 Thread 的 map 强引用
// → 只要线程活着，value 就一直无法回收！
//
// ThreadLocalMap 的兜底：get/set 时顺路清理脏 Entry（探测式清理）
// 但如果之后再也没碰过这个 ThreadLocal → value 永远躺着
  • 线程池线程永不死亡，脏 value 长期驻留——这就是"ThreadLocal 内存泄漏"的完整链条；
  • 规范：finally { threadLocal.remove(); }——用完必须显式清理；
  • 线程池传染：任务 A set 了 userId 没清理，任务 B 是另一个用户请求，get 到的是 A 的 userId——权限越界级事故，比泄漏更严重；
  • 跨线程传递上下文：用 InheritableThreadLocal 只能传给"新建"的子线程，线程池复用失效；生产用阿里的 TransmittableThreadLocal（TTL）包装任务解决池化传递。
ThreadLocal 三件套：withInitial 定义初始值、try/finally 里 remove、线程池场景警惕脏数据传染。

✓ 本章小结

要点一句话
语义线程私有副本，隔离而非共享；用于线程不安全对象与上下文传递
存储位置Thread 对象内的 ThreadLocalMap，ThreadLocal 实例当 key
弱引用key 弱引用可被 GC，value 强引用链仍在——脏 Entry 会泄漏
removefinally 里显式 remove 是唯一可靠方案
线程池不清理会"传染"给下一个任务；跨池传递用 TTL
