50.1 JMM 与工作内存

为什么线程 A 改了变量，线程 B"看不见"？JMM 规定：所有变量存于主内存，每条线程有自己的工作内存（对应 CPU 缓存/寄存器），线程只操作自己的工作内存，何时同步回主内存没有约定——这就是可见性问题的根源。

static boolean running = true;   // 只在主内存，没有同步保证

Thread t = new Thread(() -> {
    while (running) { }          // 工作线程可能一直读缓存的旧值
});
t.start();
Thread.sleep(1000);
running = false;                 // 主线程改了，工作线程可能永远看不到！
  • 更狠的是 JIT：循环里 running "不会变"，可能被优化成 if (running) while(true);——程序直接卡死；
  • JMM 用 happens-before 定义可见性规则：volatile 写 happens-before 后续的 volatile 读、解锁 happens-before 加锁、线程 start/join 都有规则；
  • 没被 happens-before 覆盖的跨线程读写，结果都是"未定义行为"——不报错，但结果不可信。

50.2 volatile 管两件事

private volatile boolean running = true;

// ① 可见性：写 volatile 立刻刷回主内存；读 volatile 强制从主内存拿
//    → 主线程 running=false 后，工作线程立刻看到，循环退出

// ② 禁止指令重排：编译器和 CPU 不能把 volatile 读写与周围代码乱序
//    → 底层是插入内存屏障（LoadLoad/StoreStore/LoadStore/StoreLoad）
  • volatile 不保证原子性：volatile int count; count++ 照样丢更新——++ 是"读-改-写"三步，volatile 只保证每步可见；
  • 要原子计数用 AtomicInteger（第 55 章）或 synchronized；
  • 典型场景：① 状态标志（running/initialized/shutdown）；② 一次性安全发布；③ DCL 的实例字段；
  • 64 位 long/double 加 volatile 还能防"字撕裂"（32 位 JVM 分两次写）。
volatile = 轻量可见性 + 有序性，没有互斥。一句话选型：一个线程写、多个线程读的状态标志，用它；要原子改，换 AtomicInteger 或锁。

50.3 DCL 单例的正确写法

public class Singleton {
    // 必须 volatile！原因见下
    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                    // ① 一检：无锁快速路径
            synchronized (Singleton.class) {
                if (instance == null) {            // ② 二检：防止重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

没有 volatile 会怎样？new Singleton() 是三步，可能被重排：

// 正常：①分配内存 ②执行构造器初始化 ③instance 指向内存
// 重排：①分配内存 ③instance 指向内存（对象还没初始化！）②执行构造器
//
// 线程 B 在"③已执行、②未执行"的瞬间进入一检：
// 看到 instance != null → 直接返回一个"半成品对象"（字段全是默认值）
  • volatile 的写屏障禁止重排，保证"初始化完成"先于"引用可见"——半成品问题根治；
  • 更省心的替代：静态内部类（JVM 保证类初始化线程安全且懒加载）或枚举（Effective Java 推荐，防反射/反序列化破坏）；
  • 历史注脚：JSR-133（JDK 5）修复旧内存模型后，DCL + volatile 才真正成立——老资料里"DCL 不可靠"的结论针对 JDK 1.4 及以前。
常见坑把 volatile 当锁用：两个线程同时 count++（volatile int）依然丢更新；volatile 数组只保证引用可见，元素读写没保证（要 AtomicIntegerArray）；DCL 忘了第二次判空导致重复 new。

✓ 本章小结

要点一句话
JMM主内存 + 线程工作内存；无同步保证的跨线程读写不可信
可见性volatile 写立即刷主内存，读强制从主内存取
有序性内存屏障禁止指令重排
不管原子性count++ 照样丢更新；要原子用 AtomicInteger/锁
DCLvolatile 防半成品对象；首选静态内部类或枚举单例

✎ 本章习题

A 基础复现可见性问题：写一个 while(running) 空转线程，主线程 1 秒后置 running=false，观察程序是否退出；然后加 volatile 再跑一次，对比结果并解释。
B 进阶证明 volatile 无原子性：volatile int count，两线程各 ++ 50000 次，多跑几次统计丢失量；再换 AtomicInteger 对比。写三行注释说明两者适用边界。
C 挑战实现三种单例：DCL+volatile、静态内部类、枚举；用反射尝试破坏构造器私有（setAccessible(true) 后 newInstance），观察哪种能防住；再给 DCL 版本补上"反射防御"（构造器里检查实例已存在则抛异常）。
