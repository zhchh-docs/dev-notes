55.1 CAS 三要素

CAS（Compare And Swap）是一条 CPU 原子指令（x86 的 cmpxchg）：给定内存位置 V、期望值 E、新值 N——仅当 V 的当前值等于 E 时，才把 V 改成 N；否则失败。整个过程是硬件级原子的，不需要加锁。

AtomicInteger count = new AtomicInteger(0);

// 自增就是"乐观重试"：猜旧值 → CAS → 失败就重读再猜
public void incr() {
    int old;
    do {
        old = count.get();              // ① 读当前值
    } while (!count.compareAndSet(old, old + 1));   // ② 尝试改，失败重试
}
  • 底层：Unsafe.compareAndSwapInt → CPU 指令；JDK 9+ 用 VarHandle，语义相同；
  • AtomicInteger.incrementAndGet 就是 JDK 帮你写好的"自旋 CAS"；
  • 乐观锁思想：假设没有冲突，失败了再试——synchronized 是悲观锁（先锁再动），CAS 是乐观锁（先动，冲突再重来）；
  • CAS 三个代价：① 自旋空转耗 CPU（竞争激烈时反复失败）；② 只能保证单个变量的原子性；③ ABA 问题。
synchronized 是"排队进门"，CAS 是"抢座位，抢不到再试"——低冲突场景 CAS 快得多，高冲突场景自旋反而空耗 CPU。

55.2 ABA 问题

CAS 只比较"值相等"，不关心中间发生了什么：

// 时间线
线程1 读到 A（准备改成 C）
线程2 把 A 改成 B，又改回 A
线程1 CAS(A → C) 成功！       // 值确实等于 A，但"此 A 非彼 A"
// 对栈/链表这类结构，A 被移走又放回，节点指向可能已乱——逻辑出错

解法：加版本号，改一次号涨一次：

AtomicStampedReference<String> ref =
        new AtomicStampedReference<>("A", 0);   // 初始值 + 初始版本

int[] stamp = new int[1];
String cur = ref.get(stamp);                       // 同时拿到值和版本
ref.compareAndSet(cur, "C", stamp[0], stamp[0] + 1);   // 版本不匹配就失败
// 值一样但版本不一样 → CAS 失败，ABA 现形
  • 数值型场景 ABA 一般无害（1→2→1 数学上等价），引用型（节点复用）才有事——别过度防御；
  • AtomicMarkableReference 是简化版：版本号换成 boolean 标记。

55.3 原子类家族与 LongAdder

// ① 基本类型：AtomicInteger / AtomicLong / AtomicBoolean
counter.incrementAndGet();     // ++i
counter.getAndAdd(5);          // i += 5，返回旧值
counter.updateAndGet(x -> x * 2);   // 函数式更新（JDK 8）

// ② 引用类型：AtomicReference —— 让整个对象引用的替换变原子
AtomicReference<Config> configRef = new AtomicReference<>(oldConfig);
configRef.compareAndSet(oldConfig, newConfig);   // 配置热更新

// ③ 数组：每个元素独立 CAS
AtomicIntegerArray arr = new AtomicIntegerArray(10);
arr.incrementAndGet(3);

// ④ 字段更新器：不侵入类定义，反射 + CAS 更新普通对象的 volatile 字段
AtomicIntegerFieldUpdater<User> upd =
        AtomicIntegerFieldUpdater.newUpdater(User.class, "score");
upd.incrementAndGet(user);     // score 字段必须 volatile

// ⑤ 高并发累加器：LongAdder（JDK 8）
LongAdder adder = new LongAdder();
adder.increment();             // 分段累加，读时求和
long total = adder.sum();

LongAdder 为什么快？AtomicLong 所有线程 CAS 同一个变量，高并发下自旋冲突爆炸。LongAdder 把计数拆成 base + Cell[] 数组：线程哈希到不同 Cell 各加各的（空间换时间），sum() 时汇总。牺牲"实时精确读"换写吞吐——统计场景的标配，JDK 8 的 ConcurrentHashMap.size() 用的就是这思路。

  • 选型：计数且高并发写 → LongAdder；要 CAS 做条件更新 → AtomicLong；对象引用原子替换 → AtomicReference。

✓ 本章小结

要点一句话
CASV、E、N：值等于期望才更新；CPU 原子指令，无锁
乐观锁失败自旋重试；低冲突快、高冲突空转耗 CPU
ABA值回原样但历史已变；版本号 AtomicStampedReference 解
家族基本/引用/数组/字段更新器，按场景选
LongAdderbase+Cell 分段累加，写吞吐高、sum 弱一致

✎ 本章习题

A 基础用 CAS 自旋手写 AtomicInteger 的 addAndGet（get + compareAndSet 循环），8 线程各加 10000 次，验证结果恒为 80000；对比第 49 章 synchronized 版的耗时。
B 进阶用 AtomicStampedReference 复现 ABA：线程 2 把值 A→B→A，线程 1 用带版本号的 CAS 失败；换无版本的 AtomicReference 则成功。写 3 行注释说明"什么时候 ABA 才真的危险"。
C 挑战压测对比：8 线程各 increment 100 万次，分别用 AtomicLong 和 LongAdder，记录耗时与 sum() 精确性；然后把线程数改成 2 再跑，观察 LongAdder 优势是否消失——写出"分段累加何时值得"的结论。
