58.1 死锁：条件与排查

死锁产生的四个必要条件（Coffman）：互斥、持有并等待、不可剥夺、循环等待——破坏任意一个即可预防：

// 经典死锁：线程1 锁 A 等 B；线程2 锁 B 等 A
synchronized (a) {
    Thread.sleep(100);        // 制造交叉窗口
    synchronized (b) { }      // 若对方持有 b，永远等下去
}
// 破解：所有线程按【全局固定顺序】加锁（先 A 后 B）→ 循环等待不存在

排查手段：

# 方法一：jstack 直接报死锁
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
# 输出会给出互相持锁的两个线程与锁地址

# 方法二：jconsole / VisualVM 的"检测死锁"按钮
# 方法三：代码层面 tryLock 超时放弃（预防式）
if (lockA.tryLock(1, SECONDS) && lockB.tryLock(1, SECONDS)) { ... }
else { lockA.unlock(); retry later; }   # 拿不到就全退，让出资源
  • 数据库死锁同理：MySQL 会自动选牺牲者回滚，应用要捕获死锁异常重试；
  • 线程池饿死（thread starvation deadlock）：池内任务互相等待对方任务的结果，而池已满——嵌套 submit 的经典坑。

58.2 CPU 飙升定位四步

线上告警 CPU 100%，标准动作（Linux）：

# ① 找到最吃 CPU 的 Java 进程
top
#   → pid = 12345 的 java 进程 300%（多核叠加）

# ② 找到进程内最吃 CPU 的线程（top -H 显示线程级）
top -Hp 12345
#   → 线程 12400 占 98%

# ③ 线程号转十六进制（jstack 里的 nid 是 16 进制）
printf "%x\n" 12400        # → 3070

# ④ 抓线程栈，搜 nid=0x3070
jstack 12345 | grep -A 30 "nid=0x3070"
#   → 定位到具体类的具体行！

常见元凶：

  • 自旋死循环：while 条件写错、volatile 标志没生效（第 50 章的可见性问题在 CPU 上的显形）；
  • 大量 CAS 失败重试：高并发下 AtomicLong 自旋风暴——换 LongAdder；
  • JDK 7 HashMap 并发扩容：环形链表导致 get 死循环（历史名场面）；
  • 正则回溯、序列化大对象：单线程把一个核跑满，多实例并发则整机飙升。
四步口诀：top 找进程、top -Hp 找线程、printf 转 16 进制、jstack 按 nid 定位——背下来，现场不慌。

58.3 排障工具箱与预防

jstack <pid>              # 线程栈快照：死锁、BLOCKED 堆积、WAITING 分布
jcmd <pid> Thread.print   # 新版推荐，等价 jstack
jcmd <pid> VM.uptime      # 基本信息
jstat -gcutil <pid> 1000  # GC 频率/耗时（CPU 飙升可能是 GC 风暴）
jconsole / VisualVM       # 图形界面：线程状态、死锁检测、MBean
Arthas（阿里）            # 线上热更新级诊断：thread -n 3 直接列最忙线程

预防清单（评审并发代码时过一遍）：

  • 锁顺序全局统一；能用 tryLock 超时就不无限等；
  • 共享可变状态最少化：能不可变就不可变，能 ThreadLocal 就封闭；
  • 线程池参数显式、队列有界、按业务隔离（第 52 章）；
  • Compound 操作用并发容器的原子方法，别 check-then-act；
  • 压测必须做：低并发下正确的代码，高并发下才见真章。
常见坑只看平均 CPU 不看 p99；把 GC 线程的 CPU 当业务 bug（先 jstat -gcutil）；jstack 一次定论——连续抓 3 次（间隔 10 秒）对比才可信；生产环境随便 kill -9 或 attach 探针造成二次故障。
