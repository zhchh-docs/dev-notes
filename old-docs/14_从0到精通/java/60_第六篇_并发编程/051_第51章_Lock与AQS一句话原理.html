51.1 Lock 比 synchronized 多什么

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account to, long amount) {
    lock.lock();                       // 手动加锁
    try {
        // 临界区
    } finally {
        lock.unlock();                 // 必须在 finally 里解锁！
    }
}

synchronized 是"语言内置、自动释放"；Lock 是"API 显式、手动管理"，换来四个能力：

  • 可中断：lockInterruptibly()——等锁时能响应 interrupt，synchronized 等锁是 BLOCKED，喊不醒（死锁只能重启）；
  • 可超时：tryLock(3, TimeUnit.SECONDS)——3 秒拿不到就放弃，避免无限等待；tryLock() 立即返回；
  • 公平锁：new ReentrantLock(true)——按排队顺序给锁（吞吐下降），synchronized 只有非公平；
  • 读写锁：ReentrantReadWriteLock/StampedLock——读多写少场景读读并行，性能远超一把大锁。
常见坑unlock 不在 finally 里——临界区抛异常锁永远不释放，系统卡死；lock 与 unlock 之间 return/continue 跳出也要 unlock；lock.lock() 写在 try 里第一行不算错，但标准写法是 lock 在 try 外。

51.2 Condition：精准的等待/唤醒

synchronized 配 wait/notifyAll 只有一个等待队列；一把锁可以挂多个 Condition，定向唤醒：

ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();   // 队列没满
Condition notEmpty = lock.newCondition();   // 队列非空

public void put(E e) throws InterruptedException {
    lock.lock();
    try {
        while (isFull())
            notFull.await();                // 满了就等"不满"条件
        enqueue(e);
        notEmpty.signal();                   // 只唤醒"等非空"的消费者
    } finally { lock.unlock(); }
}

public E take() throws InterruptedException {
    lock.lock();
    try {
        while (isEmpty())
            notEmpty.await();
        E e = dequeue();
        notFull.signal();                    // 只唤醒"等不满"的生产者
        return e;
    } finally { lock.unlock(); }
}
// 对比 Object.notifyAll：一次唤醒所有等待者再重新竞争——ArrayBlockingQueue 就是这么写的
  • await 前必须持有锁；await 会释放锁并进入等待队列，被唤醒后重新抢锁；
  • 虚假唤醒存在，条件判断必须用 while 不能用 if——和 wait 的规则一致。

51.3 AQS 一句话原理

JUC 半壁江山的地基是 AbstractQueuedSynchronizer（AQS）——ReentrantLock、Semaphore、CountDownLatch、ThreadPoolExecutor 的 Worker 都是它。

// 一句话：一个 volatile int state + 一个 CLH 双向等待队列 + 模板方法
//
//  state：同步状态，含义由子类定义
//    - ReentrantLock：0=无锁，1=重入一次，2=重入两次…
//    - Semaphore：剩余许可数
//    - CountDownLatch：还剩几个闸门
//
//  CLH 队列：抢不到锁的线程包装成 Node 入队（CAS 保证并发安全）
//            队首节点释放锁后，唤醒下一个节点重试 CAS
//
//  模板方法：子类只实现 tryAcquire/tryRelease（独占）或
//            tryAcquireShared/tryReleaseShared（共享），排队/唤醒/AQS 全包
  • 加锁主流程：CAS 尝试改 state → 成功则持有；失败则入 CLH 队列挂起（LockSupport.park）；
  • 解锁主流程：改 state → 队列非空则 unpark 后继节点，它醒来重新 CAS；
  • 公平/非公平的区别就一句话：非公平新来者直接 CAS 插队，公平者先看队列有没有人排队；
  • 面试画图：state 变化 + 队列进出，两条线讲清任意一个同步器的行为。
AQS = state（状态）+ CLH 队列（排队）+ 模板方法（子类定义 state 语义）。读懂它，Semaphore/CountDownLatch/ReentrantLock 是同一道题的三种解。

✎ 本章习题

A 基础用 ReentrantLock 实现 synchronized 版的计数器（add/get），要求 lock/unlock 范式正确；再制造一个"unlock 忘写 finally"的版本，观察临界区抛异常后第二个线程会发生什么。
B 进阶用两个线程分别 tryLock 对方的锁构造死锁，然后对比：synchronized 版只能重启；ReentrantLock 版用 tryLock(1, SECONDS) 拿不到就释放已有锁重试——验证死锁被打破。再试试 lockInterruptibly + interrupt。
C 挑战基于 AQS 自己实现一个简版 Semaphore（继承 AbstractQueuedSynchronizer，state 表示许可，实现 tryAcquireShared/tryReleaseShared），并用 10 线程并发验证最多 3 个同时进入临界区。
