11.1 正向代理 vs 反向代理

角色代理的对象用户感知
正向代理代理客户端（VPN、科学上网、爬虫代理池）服务器不知道真实客户端是谁
反向代理代理服务端（Nginx 站在服务前面）用户以为 Nginx 就是服务本身，看不到内部结构

反向代理给服务端带来的能力：统一入口与 TLS、隐藏拓扑、负载均衡、缓存、限流、灰度——第二篇逐章展开，全部建立在 proxy_pass 这一个指令之上。

11.2 最小可用的反代配置

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;

        # 透传三件套（见 11.4，缺一不可）
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时基线（见 11.5）
        proxy_connect_timeout 5s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;
    }
}

先在本地起一个假上游验证：python3 -m http.server 8080，然后 curl http://127.0.0.1/——Nginx 80 收到的请求被原样转给 8080 并把响应带回来。

11.3 proxy_pass 的四种写法

location /api/ {
    proxy_pass http://backend;              # ① 不带 URI：原样透传
    proxy_pass http://backend/;             # ② 带根 URI：替换 location 前缀
    proxy_pass http://backend/v2/;          # ③ 带路径 URI：前缀替换为该路径
    proxy_pass http://$upstream_var;        # ④ 变量化（需 resolver，第 10 章）
}
写法请求 /api/user 的转发结果适用
① 无 URI/api/user 原样发给上游默认选择，上游认识原路径
② 带 //user（/api/ 被剥掉）上游挂在根路径，网关层剥前缀
③ 带 /v2//v2/user路由到不同版本的 API
④ 变量运行时决定动态路由、灰度（第 29 章）

①②③ 的差异全部来自 proxy_pass 是否带 URI——这是第 12 章的主题，先把"默认写 ①"刻进习惯，能避开 80% 的斜杠事故。

11.4 请求头透传三件套

proxy_pass 默认只透传部分头，Host 会被改成 upstream 名、客户端 IP 信息全部丢失。三件套各自补一块拼图：

头作用不配的后果
Host $host把原始域名带给上游上游按域名路由的应用（虚拟主机）全部 404/错站点
X-Real-IP $remote_addr直连客户端 IP上游看到的全是 Nginx 的 IP，风控/日志失真
X-Forwarded-For $proxy_add_x_forwarded_for追加到 XFF 链尾多层代理时丢失链路，第 13 章详析
X-Forwarded-Proto $scheme告知原始协议TLS 终结后上游误判 http，生成 http:// 的跳转/资源链接

团队实践：把三件套写进 snippets/proxy-common.conf，各 location 统一 include（注意 3.6 数组型指令的坑：include 片段本身就是完整的一组 set_header，不要在 location 再零散追加后忘记片段）。

11.5 超时与缓冲参数全景

指令默认语义
proxy_connect_timeout60s与上游建立 TCP 的时间上限，内网建议 3-5s
proxy_send_timeout60s向上游发送请求的相邻写操作间隔上限
proxy_read_timeout60s等上游响应的相邻读操作间隔上限（不是总时长！）
proxy_bufferingon响应缓冲：上游回得快慢不均时 Nginx 先攒后发
proxy_buffer_size4k/8k响应头缓冲区，上游响应头巨大时需调大
proxy_next_upstreamerror timeout何种失败切换下一个上游节点（第 14 章配合）
  • read_timeout 是"间隔"不是"总时长"：SSE/长轮询会被 60s 静默切断，第 15 章专门处理；
  • 502 vs 504：连接被拒/失败 → 502 Bad Gateway；超时 → 504 Gateway Timeout。排障先分清这两个码。

11.6 常见坑

  1. 忘配 Host 头：上游 Spring 应用 context 路由依赖域名，表现为"直连正常、走 Nginx 404"；
  2. 大文件上传 413：默认 client_max_body_size 1m——在 http 或 location 调大（如 100m）；
  3. 上游重定向后 URL 变内网地址：上游返回的 Location 头是内部域名，用 proxy_redirect 重写；
  4. 响应头超缓冲区：上游塞了巨型 Set-Cookie，报 upstream sent too big header，调 proxy_buffer_size 与 proxy_buffers；
  5. HTTP/1.0 回源：默认 proxy_http_version 1.0 且无 keepalive，长连接场景（第 14/15 章）要改 1.1。

✓ 小结与习题

要点一句话
proxy_pass 本质不带 URI 原样透传；带 URI 做前缀替换（第 12 章细讲）
三件套Host / X-Real-IP / X-Forwarded-For（+Proto），统一进 snippets
超时三兄弟connect 管握手、send/read 管间隔；502=连接失败，504=超时
上传大小client_max_body_size 默认 1m，生产必调
A 基础用 python3 -m http.server 8080 当上游，完成 11.2 最小配置，用 curl 验证并观察 8080 端收到的请求头。
B 进阶注释掉 Host 头再请求一个依赖域名的上游（可用 hosts + 两个 server 模拟），复现"错站点"现象。
C 挑战写一个 sleep 3 秒的假上游，把 read_timeout 调到 1s，观察 504 与 error.log 的 upstream timed out。
