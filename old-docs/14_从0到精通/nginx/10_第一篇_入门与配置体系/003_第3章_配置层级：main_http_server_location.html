第 3 章 配置层级：main/http/server/location

教科书 第 3 章 / 共 32 章 · 预计 35 分钟 · 全书地基

nginx.conf 不是一堆指令的堆砌，而是一棵四层树：main → events/http → server → location。理解每一层"管什么、能放什么指令、怎么继承"，你就具备了读懂任何一份线上配置的能力。

3.1 四层树：一张图看懂 nginx.conf

图 3-1 nginx.conf 的四层树状结构

每层只答一个问题

层回答的问题典型指令
main进程以谁的身份跑、跑几个、日志写哪user / worker_processes / error_log / pid
events每个 worker 最多接多少连接worker_connections / use epoll
http所有 HTTP 站点共享的默认值include mime.types / gzip / sendfile / keepalive_timeout
server"哪个域名/端口"算一个站点listen / server_name / root
location"这个路径"怎么处理proxy_pass / try_files / expires

3.2 main 层：进程与全局

# main 层（文件最外层，不在任何 {} 内）
user  nginx;                  # worker 进程运行身份：别用 root！
worker_processes  auto;       # worker 数：auto = CPU 核数（第 22 章详讲）
error_log  /var/log/nginx/error.log warn;   # 全局错误日志与级别
pid        /run/nginx.pid;    # master 进程号文件，systemd 依赖它

events {
    worker_connections  1024; # 每个 worker 的最大连接数
    use epoll;                # Linux 高效事件模型（新版自动选，可省略）
}

http {
    ...
}
  • user：master 以 root 启动（要绑 80/443 特权端口），随后把 worker 降权为这里指定的普通用户——这是安全底线；
  • error_log 可在 main/http/server/location 任何一层重设，级别从 debug 到 emerg，生产常用 warn；
  • events 块必须存在（哪怕为空），否则启动报错。

3.3 events 层：连接数预算

单机理论并发上限 = worker_processes × worker_connections。例如 4 核 × 1024 = 4096 并发连接。注意一个浏览器请求往往占 2 个连接（客户端侧 + 上游侧），预算要除以 2 才是"用户数"。

这一层指令极少，99% 的配置就两行：worker_connections 与 use。容量规划与内核配合在第 22-23 章展开。

3.4 http 层：全局默认值

http 层是"所有站点的公共默认值"，server/location 未覆盖的指令都从这里继承：

http {
    include       /etc/nginx/mime.types;   # Content-Type 映射，别删
    default_type  application/octet-stream; # 未知类型的兜底

    log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
                      '$status $body_bytes_sent "$http_referer" '
                      '"$http_user_agent" "$http_x_forwarded_for"';
    access_log  /var/log/nginx/access.log  main;

    sendfile        on;      # 零拷贝发送文件，静态站点必开
    tcp_nopush      on;      # 配合 sendfile 优化包发送
    keepalive_timeout  65;   # 连接保活 65s
    server_tokens   off;     # 响应头隐藏版本号（安全加固，第 26 章）

    gzip  on;                # 压缩默认值，server/location 可覆盖（第 20 章）
    gzip_types  text/css application/javascript application/json;

    include /etc/nginx/conf.d/*.conf;   # 站点配置全部拆到这里
}
  • http 层放"默认"，server 层放"差异"——这是配置不失控的第一原则；
  • log_format 只能定义在 http 层；access_log 可以下放到 server/location 分别指定；
  • 官方包的 nginx.conf 末尾 include conf.d/*.conf，所以站点文件写在这里就够，不需要也不应该改动 nginx.conf 本身（除非加全局参数）。

3.5 server 层：一台虚拟主机

一个 server {} = 一个"站点"。Nginx 靠 listen（端口/IP）+ server_name（域名）决定请求落进哪个 server：

# 站点一：官网
server {
    listen       80;
    server_name  example.com www.example.com;   # 可写多个
    root         /usr/share/nginx/html;
}

# 站点二：管理后台（同机不同域名）
server {
    listen       80;
    server_name  admin.example.com;
    root         /var/www/admin;
}

# 兜底：谁都不匹配时用它（default_server 每个端口唯一）
server {
    listen       80 default_server;
    server_name  _;
    return 404;
}
  1. 先按 listen 的 IP:端口筛出候选 server 组；
  2. 组内按 server_name 精确匹配 → 前缀 *. 通配 → 正则 → 兜底 default_server；
  3. 没写 default_server 时，该端口的第一个 server 隐式成为兜底——这就是"用 IP 访问怎么进了 A 站点"的由来。

3.6 继承与覆盖：数组型指令的陷阱

继承的基本规则很简单：子层写了用子层的，没写用父层的，一直向上追溯到 http 层。但有例外：

大坑：数组型指令是"整体替换"而不是"合并"。代表：gzip_types、proxy_set_header、add_header、expires。只要在 location 里写了任意一条 add_header，http/server 层的所有 add_header 全部失效。
http {
    add_header X-Frame-Options SAMEORIGIN;   # 想全局加的安全头

    server {
        location /api/ {
            add_header X-Api-Version v1;     # 一旦写这行，
            # X-Frame-Options 在 /api/ 下消失了！必须在这里重复写一遍
            add_header X-Frame-Options SAMEORIGIN;
        }
    }
}

规避策略（按推荐度排序）：

  1. 全局头集中放 server 层，location 尽量不加 header；
  2. 确需 location 级 header 时，用第三方 headers-more 模块的 more_set_headers（支持继承合并）；
  3. 团队规范：凡下放 add_header 的 location，注释声明"已复制全局头"。

这是面试与生产事故的双料高频题："为什么我加的安全响应头只对首页生效？"——标准答案就在这一节。

3.7 include：把配置拆开组织

/etc/nginx/
├── nginx.conf                  # 只留 main/events/http 骨架 + include
├── conf.d/
│   ├── upstream-backend.conf   # upstream 定义（第 14 章）
│   ├── site-www.conf           # 主站 server
│   └── site-admin.conf         # 后台 server
└── snippets/                   # 可复用片段
    ├── proxy-common.conf       # 公共 proxy_set_header 集
    └── ssl-example.com.conf    # 证书路径（第 16 章）
  • include 支持 glob：include conf.d/*.conf;，按字典序加载；
  • snippets 片段用 include snippets/xxx.conf; 嵌入任意 server/location，一处修改多处生效；
  • 每改一个文件都要 nginx -t——include 链上的语法错误，报错行会精确到被 include 的文件。

✓ 小结与习题

要点一句话
四层树main 管进程、events 管连接、http 管默认、server+location 管站点与路径
继承规则就近覆盖、逐层上溯；数组型指令（add_header 等）下放即整体替换
server 匹配listen 定端口，server_name 定域名，default_server 是兜底
组织方式nginx.conf 留骨架，站点进 conf.d，公共片段进 snippets
A 基础默写一份只含 main/events/http 三层的最小 nginx.conf，用 nginx -t 验证。
B 进阶复现 3.6 的坑：http 层加一个自定义响应头，location 里再加一个不同的，用 curl -I 观察 location 命中的请求丢了哪个头。
C 挑战同一台机器用两个 server 块配两个"伪域名"（编辑本机 hosts 指向 127.0.0.1），验证 server_name 分流与 default_server 兜底行为。
