第 9 章 rewrite 重写规则

教科书 第 9 章 / 共 32 章 · 预计 30 分钟 · 核心必学

rewrite 是"无条件改写 URL"的手术刀：域名统一、协议跳转、旧路径兼容都靠它。本章讲透四个 flag 的差异、执行阶段与循环机制，并明确 return 与 rewrite 的分界线。

◆本章目标

  • 背出 rewrite 四个 flag（last / break / redirect / permanent）的行为差异；
  • 理解 rewrite 在 server 与 location 两个阶段的执行时机与 10 次循环上限；
  • 独立完成 http→https、www 统一、旧路径兼容三个高频场景；
  • 明确什么时候该用 return 而不是 rewrite。

9.1 语法与四个 flag

rewrite regex replacement [flag];
flag行为典型场景
last停止当前 location 的后续指令，用新 URI 重新走一遍 location 匹配改写后要换处理逻辑（最常用）
break停止 rewrite 指令集，留在当前 location 继续处理改写后仍在原地处理（如映射磁盘路径）
redirect返回 302 临时重定向临时跳转
permanent返回 301 永久重定向域名迁移、协议统一

关键区分：last/break 是内部改写（用户地址栏不变，服务端换路径处理），redirect/permanent 是外部跳转（地址栏真的变，多一次往返）。

9.2 执行阶段与循环机制

  1. server 阶段：请求进入 server 后、匹配 location 之前执行 server 层的 rewrite；
  2. location 阶段：命中 location 后执行其中的 rewrite，flag 为 last 时重新走 location 匹配；
  3. 循环上限：内部重定向累计 10 次仍未终结 → 返回 500（error.log 关键字 rewrite or internal redirection cycle）。
# 经典循环事故：互相改写踢皮球
location /old/ { rewrite ^/old/(.*)$ /new/$1 last; }
location /new/ { rewrite ^/new/(.*)$ /old/$1 last; }   # 10 次后 500

排障手段：临时把 rewrite 换成 return 200 "uri=$uri"; 观察实际 URI，或把 error_log 开到 notice 看内部重定向轨迹。

9.3 三个经典场景

# 场景一：HTTP 全部跳 HTTPS（第 18 章会用 308/497 精化）
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

# 场景二：www 统一到裸域
server {
    listen 443 ssl;
    server_name www.example.com;
    return 301 https://example.com$request_uri;
}

# 场景三：旧路径兼容（内部改写，不跳转）
server {
    location / {
        rewrite ^/product/(\d+)$ /items?id=$1 last;
    }
    location /items {
        proxy_pass http://backend;
    }
}
  • 跳转场景永远把 $request_uri（含查询串的原始 URI）拼回去，丢参数是常见事故；
  • 内部改写用 $1 捕获组；replacement 以 ? 结尾可丢弃原查询串。

9.4 return 与 rewrite 的分界线

用 return用 rewrite
整体跳转（301/302/307/308）需要正则捕获重组 URI
直接给响应（文本/状态码）内部路径映射且要重新匹配 location
域名统一、协议统一（无重组逻辑）旧 URL 结构到新结构的批量转换

性能与可读性铁律：能用 return 就不用 rewrite。return 一条指令终结请求，rewrite 要走正则引擎并可能触发重新匹配。

9.5 if 的危险性

社区名言 "if is evil" 并非夸张——if 在 location 内与部分指令组合会产生反直觉行为：

# 安全用法：if 里只写 return 或 rewrite ... last
location /download/ {
    if ($arg_debug) { return 200 "debug\n"; }
    try_files $uri =404;
}

# 危险用法（勿模仿）：if 内配 proxy_pass / root
location / {
    if ($host = old.example.com) {
        proxy_pass http://legacy;   # 行为异常的著名温床
    }
}

纪律：if (...) 里只允许 return 或 rewrite ... last；其它判断需求改用 map（第 10 章）。

9.6 常见坑

  1. 跳转丢参数：return 301 https://example.com; 把路径和查询串全丢了——要拼 $request_uri；
  2. replacement 里的查询串：新 URI 带 ? 时原查询串被丢弃，想保留要显式拼接；
  3. 正则小括号没转义：URI 里的字面量 ( 要写成 \(；
  4. last 与 break 选错：映射磁盘路径用 break，换处理逻辑用 last；
  5. 循环 500：互相改写或改写到自己，看 error.log 的 cycle 关键字。
