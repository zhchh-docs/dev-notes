  • 说出 location 的五种语法形态及各自含义；

  • 用 curl 实验验证任意 location 组合的真实命中；
  • 掌握一套生产可用的"静态 + API"路由骨架。

6.1 location 的五种写法

写法含义典型用途
location = /path精确匹配，URI 完全相等首页、健康检查，最高优先级
location ^~ /static/前缀匹配，命中后跳过正则检查静态资源目录，防正则劫持
location ~ \.php$区分大小写的正则按扩展名分发
location ~* \.(png|jpg)$不区分大小写的正则图片扩展名的事实标准写法
location /path普通前缀匹配目录级分发，如 /api/

易混点：/path 也命中 /pathology，/path/ 只命中以其为前缀的路径；正则用 PCRE，支持捕获组 $1 $2。

6.2 优先级决策图

图 6-1 location 匹配的四步决策

背诵版：精确 > ^~ > 正则（先到先得）> 最长前缀。正则之间不看长短，只看书写顺序。

6.3 对照实验：亲眼看优先级

server {
    listen 80;
    server_name loc.example.com;

    location = /       { return 200 "exact /\n"; }          # ① 精确
    location /static/  { return 200 "prefix /static/\n"; }  # ④ 普通前缀
    location ^~ /img/  { return 200 "caret /img/\n"; }      # ② ^~ 前缀
    location ~ \.png$  { return 200 "regex png\n"; }        # ③ 正则
    location ~* \.(jpg|jpeg)$ { return 200 "regex jpg\n"; } # ③ 正则
}
curl http://127.0.0.1/              # exact /
curl http://127.0.0.1/img/a.png     # caret /img/   ——^~ 拦下了正则
curl http://127.0.0.1/logo.PNG      # 404：~ 区分大小写，.PNG 不匹配 \.png$

再看关键请求 /static/a.png：它同时命中普通前缀 /static/ 和正则 \.png$——前缀没加 ^~，正则优先，返回 regex png。想让静态目录说了算，必须写 ^~。

^~ 的意义就在这里：把某个前缀目录从正则手中"抢"回来。纯静态目录建议一律 ^~。

6.4 嵌套 location

location /api/ {
    proxy_set_header Host $host;          # 外层公共配置

    location /api/public/ {
        proxy_pass http://public_svc;     # 内层继承外层的 proxy_set_header
    }

    location /api/admin/ {
        allow 10.0.0.0/8;                 # 内层叠加访问控制
        deny  all;
        proxy_pass http://admin_svc;
    }
}
  • 嵌套只允许"前缀套前缀"，正则 location 内不能再嵌；
  • 普通指令可继承；数组型指令（add_header 等）嵌套即整体替换（3.6 节的坑同样适用）；
  • 嵌套两层封顶，再深可读性骤降。

6.5 实战：标准站点路由骨架

server {
    listen 80;
    server_name app.example.com;
    root /var/www/app;

    # 健康检查：精确匹配，成本最低
    location = /healthz { access_log off; return 200 "ok\n"; }

    # 静态资源：^~ 防正则劫持 + 长缓存
    location ^~ /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # API：前缀转发
    location /api/ {
        proxy_pass http://backend;
        include snippets/proxy-common.conf;
    }

    # 图片：不区分大小写正则
    location ~* \.(png|jpg|jpeg|gif|webp|svg|ico)$ { expires 7d; }

    # SPA 兜底：其余全部回 index.html（第 8 章细讲）
    location / {
        try_files $uri $uri/ /index.html;
    }
}

自问三题：为什么 healthz 用 =？为什么 assets 加 ^~？图片正则放在 /api/ 之前为什么会误伤 /api/xxx.png？（答案都藏在 6.2 的四步里。）

6.6 常见坑

  1. 正则顺序想当然：宽泛的正则写在前面会截胡窄的——正则先写具体的；
  2. 以为 location / 永远兜底：只有所有正则都未命中时才轮到最长前缀；
  3. 大小写：扩展名匹配用 ~*，写 ~ 时 .JPG 会漏；
  4. location /api（无尾斜杠）会命中 /api-docs——要么写 /api/，要么明确接受；
  5. location 里换 root 时忘记 alias 语义差异——下一章专门对比。

✓ 小结与习题

要点一句话
优先级口诀= > ^~ > ~ / ~*（按顺序）> 最长前缀
^~ 的价值保护前缀目录不被正则截胡
正则规则只看书写顺序；扩展名匹配用 ~*
生产骨架= 健康检查、^~ 静态、前缀 API、正则图片、/ 兜底
A 基础复现 6.3 的 curl 实验，逐一解释返回值。
B 进阶把 /static/ 改成 ^~ 后再请求 /static/a.png，观察变化并说明原因。
C 挑战交换骨架中图片正则与 /api/ 的顺序，构造一个会被误伤的 URL 并验证，再给出修复方案。
