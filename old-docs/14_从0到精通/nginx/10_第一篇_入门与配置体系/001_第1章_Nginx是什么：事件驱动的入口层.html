1.1 它站在流量链路的入口

一句话定义：Nginx（读作 "engine-x"）是一款高性能的 Web 服务器 / 反向代理服务器，绝大多数情况下，它是用户请求进入你系统后第一个被打交道的软件。

看一次真实的请求是怎么流动的：

图 1-1 Nginx 作为流量入口：静态自己扛，动态往后转

拆开"入口层"三个职责：

  • 接收：监听 80/443 端口，完成 TCP 握手与 TLS 解密，把用户请求变成 Nginx 内部的结构化请求；
  • 分流：按 URL、域名（server_name）、请求头判断——图片 CSS 直接到磁盘拿，/api/ 开头的转发给后端；
  • 保护与加速：限流防刷、缓存热门响应、压缩传输内容、统一做 HTTPS。这些能力后面每篇都会展开。

记住这张图：全书 32 章，本质上都在回答一个问题——"流量到了 Nginx，怎么接、怎么转、怎么又快又稳地送出去"。

1.2 事件驱动：又快又省内存的秘密

同样是 Web 服务器，传统模型（如 Apache 经典的 prefork/worker 模式）采用"一个连接一个进程或线程"：每来一个请求，操作系统分配一条执行线程专职服务它，请求结束线程才释放。

这条路线直观、好写，但有两个天花板：

  • 内存随连接数线性增长：每条线程默认要占几 MB 栈空间，1 万个连接就是几十 GB——服务器还没干活就先被"站票"挤爆；
  • 上下文切换开销：几千条线程来回切换，CPU 大量时间花在"换人"而不是"干活"上。

Nginx 的答案是事件驱动 + 异步非阻塞 I/O：worker 进程不傻等任何一个请求，而是像前台接待员一样，谁的事办好了就处理谁。

图 1-2 两种并发模型的本质差异

三句话总结这个模型

  1. Master-Worker 架构：master 进程只负责读配置、管理 worker；真正干活的 worker 通常与 CPU 核数相同（第 22 章细讲）；
  2. 非阻塞：worker 遇到"后端还没响应"时不死等，先去处理别的连接，事件就绪后再回来——所以慢后端不会拖垮 Nginx；
  3. 内存占用低：一个空闲连接在 Nginx 里只占几 KB 状态，单机数万并发连接是常规操作。
常见误区："Nginx 快是因为用了多线程"——错。Nginx 的 worker 是单线程的，快是因为不等：把"等 I/O"的时间省下来处理别的连接。

1.3 它能扮演的五种角色

同一个 Nginx 二进制，按配置不同可以承担五类工作。这五类也正是全书三篇的骨架：

角色做什么关键指令对应章节
静态站点服务器直接把磁盘上的 HTML/CSS/JS 发给浏览器root / location第 4-8 章
反向代理替后端服务接请求、回响应，对用户隐藏内部结构proxy_pass第 11-13 章
负载均衡器把流量按策略分发给多台后端upstream第 14 章
HTTPS 网关统一持有证书、终结 TLS、强制跳转listen 443 ssl第 16-18 章
API 网关（轻量）按路径路由到不同服务，附加限流/鉴权/缓存location + limit_req第 21、28 章

生产环境里，一套 nginx.conf 往往同时干这五件事——比如一个典型站点：443 端口持证书，/ 返回前端静态资源，/api/ 反代到 Spring Boot 集群，/ws/ 升级为 WebSocket，静态资源加 7 天缓存并开启限流。

学这本书的姿势：不要背指令，而是记住"这个需求对应哪个角色"——角色清楚了，查哪个章节、用哪组指令就一目了然。

1.4 与 Apache、Node、云网关怎么选

vs Apache httpd

  • Apache 的 .htaccess 目录级配置和丰富模块生态是它的优势，PHP 传统架构（mod_php）里也离不开它；
  • 但在高并发静态内容、反向代理、TLS 终结场景，Nginx 的事件驱动模型内存与吞吐优势明显；
  • 现实中很常见的组合是"Nginx 在前 + Apache 在后"：Nginx 处理静态与代理，动态请求转给 Apache。

vs Node.js / Java 自带服务器

  • Spring Boot 内嵌 Tomcat、Node 的 http 模块都能直接监听端口，为什么前面还要架 Nginx？因为入口层的三件事它们不擅长：TLS 证书统一管理、静态资源高效服务、多实例负载均衡；
  • 让业务进程回归业务，把入口层职责交给 Nginx，是纵深防御与弹性扩容的基础。

vs 云负载均衡 / K8s Ingress

方案适合代价
自建 Nginx自主可控、配置精细、成本低的入口层自己负责高可用与证书续期
云 SLB/ALB免运维、天然高可用、与安全组联动配置能力受限、按量计费
K8s Ingress（Nginx Ingress）容器集群统一入口、声明式路由需要集群运维能力（第 31 章专题）
真相：云 SLB 的七层转发、Nginx Ingress 的核心，底层都是 Nginx（或其分支）。学会 Nginx，等于同时学会了它们的"方言"。

1.5 本书的路线图与学习方法

全书三篇 32 章，路线设计遵循"先能跑、再走稳、最后跑快"：

  1. 第一篇（第 1-10 章）入门与配置体系：装起来、跑起第一个静态站、吃透配置层级 / location / rewrite / 内置变量——这是读懂任何 nginx.conf 的地基；
  2. 第二篇（第 11-21 章）反向代理与 HTTPS：proxy_pass 与斜杠陷阱、upstream、WebSocket、证书与 HTTP/2、缓存与限流——生产环境 80% 的入口层需求都来自这一篇；
  3. 第三篇（第 22-32 章）调优与实战：进程模型与内核参数、排障方法论、安全加固、动静分离 / API 网关 / 灰度三个实战、Docker 与 K8s 配合，最后梳理面试知识体系。

学习方法每章的配置示例都可直接复制到你的 nginx.conf 运行。强烈建议准备一台 Linux 虚拟机或 Docker 环境（第 2 章搭环境、第 30 章讲 Docker 方案），每章动手验证一遍——Nginx 配置是"改一行看一行"的技能，只读不练等于没学。

章末"常见坑"是本书的价值密度所在：斜杠差一个就是 404、缓存配错导致用户看到旧页面……这些坑全部来自真实事故。读到坑，先记住现象，再记原因。
