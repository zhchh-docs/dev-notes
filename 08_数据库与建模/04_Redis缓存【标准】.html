Redis 缓存

标准 定位：内存级 KV——给热点数据、会话、计数加速

Redis 是最常用的内存数据库，单线程内存操作带来微秒级读写，常挡在 MySQL 前面扛住热点读。本页讲清它的五大数据结构分别适合什么场景、过期与淘汰策略、RDB/AOF 持久化，以及最经典的缓存读写模式（旁路缓存）。以 业务系统 的真实缓存落地收尾——热点数据、会话黑名单、计数器各用得其所。

1技术点概览

一句话定位：Redis 是内存键值数据库——数据在内存所以极快，还能当分布式锁、计数器、排行榜、消息队列用。

  • 它解决什么：MySQL 扛不住高频读时，热点数据放内存挡在前面，读走 Redis、miss 才回源 MySQL 并回填。
  • 代价：引入了缓存一致性问题——这是用缓存必须面对的。

2核心概念

2.1 五大数据结构与适用场景

一句话定位：String/Hash/List/Set/ZSet 五种结构各有主场——选对结构就是选对数据模型。

结构特点典型场景
String最简单的 key-value缓存对象(JSON)、计数器、分布式锁
Hashfield-value 散列表存对象（用户信息），改单字段方便
List双向链表，可做栈/队列简单消息队列、最新列表
Set无序不重复集合标签、共同好友（交并差）
ZSet带分数的有序集合排行榜、延时队列

2.2 过期与淘汰策略

一句话定位：key 设 EXPIRE 到期自动删；内存满了由淘汰策略（常用 allkeys-lru）决定丢谁。

  • 推论：缓存本就该"可丢"——丢了回源重建即可。
  • 淘汰策略全集：maxmemory 满后由 maxmemory-policy 决定，默认是 noeviction（写报错、不淘汰）；做缓存常用 allkeys-lru，4.0+ 还提供 allkeys-lfu（按频次）、volatile-lru/volatile-lfu/volatile-ttl（只在设了过期的 key 里淘汰）等。

2.3 持久化：RDB 与 AOF

一句话定位：RDB 是定时快照（恢复快但可能丢最后一次快照后数据），AOF 记每条写命令（耐丢但文件大恢复慢）。

  • 当缓存用：数据丢了能从 MySQL 重建，持久化要求没那么高。
  • 当主存储用：才要认真配 AOF。生产常两者混用。

图 1 RDB vs AOF（示意）

2.4 缓存更新：旁路缓存（Cache-Aside）

一句话定位：读——先读缓存，没有再读库并写回；写——先更库，再删缓存（不是更新缓存）。

  • 为什么写是"删"不是"更"：并发写时更新缓存容易算错，删了等下次读重建更简单可靠。

3工作原理与流程

3.1 旁路缓存的读写流程

图 2 旁路缓存：读时回填、写时删缓存（示意）

  1. 读：先查 Redis；命中即返回；未命中查 MySQL，把结果写回 Redis（带过期时间）。
  2. 写：先更新 MySQL，再删除对应缓存 key。
  3. 兜底：缓存过期时间是最后防线——即使删缓存失败，过期后也会重建。

4核心语法与 API 要点

4.1 Spring Data Redis 常用操作

String key = "req:" + id;
// 读缓存
ReqVO vo = (ReqVO) redisTemplate.opsForValue().get(key);
if (vo == null) {
    vo = requirementMapper.selectVo(id);          // 回源
    redisTemplate.opsForValue().set(key, vo, 30, TimeUnit.MINUTES); // 回填+过期
}
// 写：更库后删缓存
requirementMapper.update(req);
redisTemplate.delete(key);

4.2 计数器与分布式锁基础

// 原子计数（incr 是原子的，不用先读后写）
Long cnt = redisTemplate.opsForValue().increment("alert:unread:count");

// 简单锁：setnx + 过期（生产建议用 Redisson，见下一页）
Boolean ok = redisTemplate.opsForValue()
    .setIfAbsent("lock:req:" + id, "1", 10, TimeUnit.SECONDS);

4.3 序列化选择

// 默认 JDK 序列化可读性差、体积大；生产常配 JSON 序列化
// 配置 RedisTemplate 的 valueSerializer 为 Jackson2JsonRedisSerializer
// 好处：缓存里的值是可读 JSON，跨语言/排查方便，体积更小。
经验：序列化方式要和缓存可读性、版本兼容一起考虑——改了类字段后旧的 JSON 反序列化可能失败，要留版本号或容忍旧数据过期自然淘汰。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 用 Redis 做热点数据缓存、登录会话/黑名单与计数器，减轻 MySQL 压力。

  • 业务量级：字典/权限/热点配置读多写少；登录态与计数频繁访问。

2 我的角色与职责

  • 分工：接入 Redis，设计缓存 key、过期策略与缓存更新方式。

3 技术栈

  • 组合：SpringBoot Data Redis + Redisson + MySQL。

4 落地设计

  • 热点缓存：字典/配置先查缓存，miss 再查库并回写。
  • 会话/黑名单：JWT 黑名单、refresh token 存 Redis，带过期时间。
  • 计数：浏览量/计数用 incr，不落库实时算。

5 关键实现要点

public Dict getDict(String code) {
    String key = "dict:" + code;
    String json = redis.get(key);
    if (json != null) return JSON.parse(json, Dict.class);
    Dict d = dictMapper.selectByCode(code);   // miss 查库
    redis.setex(key, 3600, JSON.stringify(d)); // 回写 + 1h 过期
    return d;
}

6 真实问题与解法

  • 坑缓存与库不一致：更新库后忘了删缓存——写操作后删缓存（Cache-Aside）而非更新缓存。
  • 坑序列化：对象直接存 JDK 序列化体积大、跨语言不可读——用 JSON 字符串。
  • 要点必设过期：key 不设 TTL 会无限堆积。

7 量化成果

  • 热点字典查询大部分命中缓存，MySQL 读压力下降（缓存命中率约九成，估算）。

8 协作与排期过程

  • key 命名规范后端统一；缓存失效策略与数据变更点一起评审。

9 复盘与可复用经验

  • Cache-Aside + 删缓存：读穿透、写删缓存。
  • JSON 序列化 + TTL。

10 面试讲法

"业务系统 实践中常采用 Redis 做字典缓存、JWT 黑名单和计数，Cache-Aside 读穿透写删缓存，踩过库更新后缓存不一致和序列化的坑。"

6易错点与面试重点

6.1 缓存不设过期

一句话定位：脏数据永久驻留，内存也只增不减——每个缓存 key 都要设过期。

  • 正解：每个缓存 key 都设过期时间。

6.2 写库后更新缓存而非删缓存

一句话定位：并发写时更新缓存易错乱——写库后删缓存、下次读重建。

  • 正解：写库后删缓存，下次读重建。

6.3 把 Redis 当唯一数据源却没配好持久化

一句话定位：Redis 重启丢数据——当缓存可丢，当主存储要配 AOF、重要数据仍落库。

  • 正解：当缓存可丢；当主存储要配 AOF，重要数据仍要落库。

6.4 计数器先 get 再 set

一句话定位：并发下计数丢失——用 INCR 原子操作。

  • 正解：用 INCR 原子操作。

6.5 大 key / 热 key 问题

一句话定位：超大 hash 占大量内存、超热点 key 把单线程 Redis 打满。

  • 正解：大 key 拆分/压缩，热 key 本地缓存兜底（进阶话题，见下一页）。
