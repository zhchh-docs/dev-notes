Redis 进阶：缓存策略与分布式锁

1技术点概览

一句话定位：本页两块——缓存三大问题（穿透/击穿/雪崩）让"加缓存"反而变成打垮数据库的放大器；分布式锁让多实例能跨进程互斥。

  • 缓存策略：缓存不是加上就万事大吉，恶意/异常请求会绕过缓存打垮数据库。
  • 分布式锁：单体时一个 JVM 锁就够；多实例后跨进程互斥要靠大家都认的协调者，Redis 就是最常用那个。

2核心概念

2.1 缓存穿透

一句话定位：查根本不存在的数据，缓存永远 miss、每次都打 DB——应对是缓存空值或布隆过滤器。

  • 应对：查空也缓存一个短过期空值；前面加布隆过滤器，明显不存在的 key 直接挡掉。

2.2 缓存击穿（热点 key）

一句话定位：极热点 key 过期那一刻，成千上万个并发同时 miss、同时回源。

  • 应对：热点数据逻辑不过期（后台异步刷新）；或重建加锁，只放一个请求查库重建、其余等。

2.3 缓存雪崩

一句话定位：大量 key 同一时刻集中过期（或 Redis 宕机），瞬时全部回源压垮 DB。

  • 应对：过期时间加随机抖动错峰失效；Redis 集群高可用兜底。

2.4 为什么需要分布式锁

一句话定位：JVM 锁只管一个进程，多实例后两个实例同时执行临界代码就管不到——需要大家共享的锁。

  • 典型场景：同一需求的并发提交、库存扣减。

2.5 setnx 手写锁的坑

一句话定位：最朴素的 SET key NX EX 手写会踩一串坑——所以生产直接用 Redisson。

  • 坑一：value 不是自己的就误删别人锁（判断+删除要原子，得用 Lua）。
  • 坑二：业务没执行完锁就过期了（要自动续期）。
  • 坑三：不可重入。

2.6 Redisson 可重入锁与看门狗

一句话定位：可重入=同线程多次加同一把锁不锁死自己；看门狗=后台定时续期直到业务释放。

  • 解决：看门狗解决"业务没干完锁先过期"的问题。

2.7 Lua 脚本保证原子

一句话定位：加锁、判断 value、删锁要"多步原子"，Redisson 用 Lua 合成一次调用。

  • 原理：Redis 单线程执行 Lua，天然原子，不会被中途插入别的命令。

2.8 公平锁、读写锁、红锁的取舍

一句话定位：默认可重入锁够用；红锁理论抗单点但争议大，绝大多数场景单实例主从+Redisson 就够。

  • 公平锁：按请求顺序排队避免饥饿，代价是吞吐略低。
  • 红锁（RedLock）：向多个独立节点加锁、多数成功才算成功；争议大（Kleppmann 与 antirez 有著名争论），不必盲目上。

3工作原理与流程

3.1 Redisson 加锁 / 看门狗续期 / 释放

图 2 Redisson 可重入锁与看门狗续期（示意）

  1. 加锁：Lua 脚本原子地"key 不存在则设置，存在则计数+1（可重入）"。
  2. 续期：未指定 leaseTime 时，Redisson 的 lockWatchdogTimeout 默认 30000ms（即加锁默认 TTL=30 秒），看门狗每隔 30/3=10 秒执行一次续期、每次把 TTL 续回 30 秒，直到业务显式释放锁。
  3. 执行：业务在锁内执行，锁不会中途过期。
  4. 释放：Lua 脚本判断是自己的锁才删，并停掉看门狗。

4核心语法与 API 要点

4.1 Redisson 加锁标准写法

@Autowired
private RedissonClient redisson;

public void submitReq(Long reqId) {
    RLock lock = redisson.getLock("lock:req:" + reqId);
    try {
        // 不指定 leaseTime → 看门狗自动续期
        lock.lock();
        // 业务：并发提交同一条需求，串行化执行
        requirementService.doSubmit(reqId);
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock(); // 只解自己持有的锁
    }
}

4.2 对比：手写 setnx 锁的问题

// 朴素写法的坑：
// 1) setIfAbsent 有过期，但业务没跑完锁就到点释放了

// 结论：直接用 Redisson，别手写。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 需求并发操作（如同一需求被多人同时处理、幂等提交）需要分布式锁保证一致性，用 Redisson。

  • 业务量级：后端虽为单体部署多实例时，临界区操作必须跨实例互斥（估算多实例）。

2 我的角色与职责

  • 分工：用 Redisson 实现可重入分布式锁，处理需求并发提交与接口幂等。

3 技术栈

  • 组合：SpringBoot + Redisson（基于 Redis）+ MySQL。

4 落地设计

  • 锁粒度：按需求 id 加锁 lock:req:{id}，同一需求串行处理，不同需求并行。
  • 看门狗：用 Redisson 默认看门狗自动续期，避免业务没执行完锁先过期。
  • 幂等：关键提交接口先抢锁/查幂等键，防重复提交。

5 关键实现要点

RLock lock = redisson.getLock("lock:req:" + reqId);
try {
    if (!lock.tryLock(3, 30, TimeUnit.SECONDS)) {
        throw new BizException("该需求正在被处理，请稍后", 40909);
    }
    // 临界区：查最新状态 → 校验 → 更新
    doReview(reqId, cmd);
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();  // 只解自己持有的锁
}

6 真实问题与解法

  • 坑手写 setnx 锁不释放：进程持锁后崩溃没删 key——用 Redisson 带过期 + 看门狗，不手写裸 setnx。
  • 坑解锁解到别人的锁：锁过期后被别人抢到，自己 finally 误删——isHeldByCurrentThread 判断。
  • 要点锁内别做长事务：持锁做重活会拉长临界区，锁内只做必要更新。

7 量化成果

  • 同一需求并发提交不再出现状态覆盖，重复提交被挡在锁/幂等层（冲突被拦截，估算）。

8 协作与排期过程

  • 与前端约定 409"正在处理"提示并引导刷新；锁 key 规范与超时参数后端统一评审。

9 复盘与可复用经验

  • 用成熟客户端：Redisson 而非手写 setnx，续期/可重入都解决了。
  • 锁内要短。

10 面试讲法

"业务系统 实践中常采用 Redisson 按需求 id 加可重入锁、靠看门狗续期保证并发一致性，踩过手写 setnx 不释放和误删别人锁的坑，所以一律用成熟客户端。"

6易错点与面试重点

6.1 手写 setnx 锁不判断 value 就 delete

一句话定位：误删别人的锁——用 Redisson（Lua 原子判断+删除），别手写。

  • 正解：用 Redisson（Lua 原子判断+删除），别手写。

6.2 指定了 leaseTime 却依赖看门狗续期

一句话定位：传了 leaseTime、业务没跑完锁就没了——显式指定 leaseTime 后看门狗不生效。

  • 正解：不确定执行时长就别传 leaseTime，交给看门狗。

6.3 缓存不过期/过期时间都一样

一句话定位：大量 key 同时失效造成雪崩——过期加随机抖动。

  • 正解：过期加随机抖动。

6.4 对不存在数据每次都查库

一句话定位：缓存穿透——缓存空值或布隆过滤器。

  • 正解：缓存空值 / 布隆过滤器。

6.5 盲目上红锁

一句话定位：红锁复杂且有争议，多数场景过度设计。

  • 正解：单主从 + Redisson 够用；确有跨多节点强一致需求再评估。

6.6 锁范围过大、把锁当万能

一句话定位：临界区包太大、把慢操作也锁进去，并发暴跌。

  • 正解：锁只包真正需要互斥的最小临界区。
