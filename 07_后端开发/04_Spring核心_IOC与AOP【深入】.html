Spring 核心：IOC 与 AOP

深入 定位：整个 Spring 生态的内核——对象容器 + 动态代理切面

Spring 的一切都建立在两块地基上：IOC（控制反转）把对象的创建与装配从代码里抽走，交给容器；AOP（面向切面）用动态代理把日志、事务、鉴权这类横切逻辑从业务代码里抽走。本页源码级讲透 BeanFactory 与 ApplicationContext 的分工、Bean 完整生命周期、JDK 与 CGLIB 两种动态代理、三级缓存如何解决循环依赖，并用 业务系统 的分层架构与切面落地收尾——重点包括面试必问的 @Transactional 失效场景。

1技术点概览

一句话定位：Spring 内核 = IOC（对象容器，负责创建/装配 Bean）+ AOP（动态代理织入横切逻辑）；本项目用 Spring 6（对应 Spring Boot 3，最低 Java 17）。

  • IOC 解决什么：没有它时 Service 里 new Dao()，类与类硬编码耦合，换实现、做单测都要改业务代码；IOC 把"谁创建谁"反转给容器，业务类只声明依赖、由容器注入。
  • AOP 解决什么：没有它时每个方法都手写"记日志、开事务、校验权限"，重复且易漏；AOP 把这些收敛成一个切面，声明式切到所有匹配方法上。

横向对比：Spring IOC/AOP 与替代方案的取舍

方案做法取舍

Spring IOC/AOP容器托管 Bean + 注解/JavaConfig 装配 + 动态代理切面生态最大、注解声明式、切面与事务开箱即用；代价是启动慢、理解成本高、"魔法"出问题难调。本套技术栈选型。

2核心概念

2.1 IOC 与 DI（Inversion of Control / Dependency Injection）

一句话定位：IOC 是"把对象创建权交给容器"的设计思想，DI（依赖注入）是它的实现手段。

  • 构造器注入（推荐）：依赖 final 不可变、启动时缺依赖直接报错、便于单测。Spring 4.3+ 单构造器可省略 @Autowired。
  • Setter 注入：用于可选依赖。
  • 字段注入：@Autowired 直接标字段，最省事，但不利于测试与不可变。

2.2 BeanFactory 与 ApplicationContext

一句话定位：BeanFactory 是底层极简容器，ApplicationContext 是它的企业级增强版——项目组日常用的是后者。

  • BeanFactory：最顶层接口，提供 getBean、依赖解析，懒加载、功能精简。
  • ApplicationContext：启动时一次性实例化所有单例 Bean，额外提供国际化、事件发布、AOP、注解驱动（@ComponentScan）。

关系：BeanFactory 是底层 SPI，ApplicationContext 是面向应用的增强版。

2.3 Bean 定义与作用域（BeanDefinition & Scope）

一句话定位：容器里的对象不是直接 new 出来的，而是先有一份"Bean 定义"，容器按定义再实例化。

  • BeanDefinition：描述这个 Bean 的类、作用域、构造参数、依赖、是否懒加载等元信息。
  • singleton（默认）：整个容器一个实例。
  • prototype：每次 getBean 都 new 新的；Web 环境还有 request/session/application。

记住"默认 singleton"——这是后面很多坑（单例注入 prototype 不生效）的前提。

2.4 Bean 生命周期（Bean Lifecycle）

一句话定位：实例化 → 属性填充 → Aware 回调 → 初始化 → 后置处理（这里生成 AOP 代理）→ 就绪 → 销毁。

  • 关键节点顺序：new → 注入依赖 → BeanNameAware 等回调 → @PostConstruct/init → BeanPostProcessor 后置（生成代理）→ 就绪 → 容器关闭时 @PreDestroy。

AOP 代理是在"初始化后的后置处理"阶段才生成的——所以在 @PostConstruct 里调本类的 @Transactional 方法不会走代理。

2.5 AOP 与连接点模型（Aspect & Join Point）

一句话定位：用切点表达式选出一批方法，再把通知（前置/后置/环绕）切上去。

  • Aspect（切面）：横切逻辑的模块；JoinPoint（连接点）：可被拦截的方法调用。
  • Pointcut（切点）：用表达式选出一批连接点（如"所有 Service 方法"）。
  • Advice（通知）：切上去做什么——Before/After/Around/AfterThrowing。

@Around 最强大，能控制是否执行原方法、改参数、改返回值；@Transactional 本质就是一个环绕通知。

2.6 动态代理：JDK 代理 vs CGLIB

一句话定位：Spring AOP 运行期给目标 Bean 生成代理对象；JDK 代理基于接口，CGLIB 基于继承。

  • JDK 动态代理：目标类必须实现接口，代理实现同一组接口。
  • CGLIB：生成目标类的子类，无需接口，但不能代理 final 类/方法。
  • Spring Boot 2.x+ 默认 CGLIB（proxyTargetClass=true），即使类实现了接口也走子类代理。

2.7 循环依赖与三级缓存（Circular Dependency & Three-level Cache）

一句话定位：A 依赖 B、B 又依赖 A 时，Spring 用三级缓存放"早期引用"打破循环；但构造器注入的循环依赖无解。

  • 三级缓存：一级 singletonObjects（成品）、二级 earlySingletonObjects（早期半成品）、三级 singletonFactories（对象工厂）。
  • 破解过程：A 实例化后先把"能产出 A 的工厂"放进三级缓存，B 反过来要 A 时就拿 A 的早期引用（需要代理则工厂里提前生成）。

构造器注入的循环依赖无解（对象还没实例化就互相要），Spring Boot 2.6+ 默认直接报错。

2.8 自动装配的歧义与限定符

一句话定位：同一接口有多个实现时，@Autowired 不知道注哪个，会抛 NoUniqueBeanDefinitionException。

  • 解决手段：@Primary 标首选、@Qualifier("name") 指定名字、或配合 @Named。

这是多数据源、多策略实现里每天都要面对的问题。

3工作原理与流程

3.1 Bean 完整生命周期：从 BeanDefinition 到就绪

一句话定位：这是 Spring 内核面试的核心图——理解它，就能解释"为什么 @PostConstruct 里拿不到代理""为什么 @Async 自调用不生效"。

图 2 Bean 生命周期与 AOP 代理生成时机（示意）

  1. 实例化：用构造器 new 出对象（此时属性还没填）。这一步若发生在循环依赖里，三级缓存就开始介入。
  2. 属性填充：按 @Autowired/构造器参数解析并注入依赖。注入 B 时会触发 B 的完整生命周期。
  3. Aware 与初始化：回调 BeanNameAware 等，再执行 @PostConstruct。此时对象仍是原始对象，代理还没生成。
  4. 后置处理生成代理：AbstractAutoProxyCreator 判断这个 Bean 是否需要切面（有 @Transactional/@Aspect 切点命中），需要就用 JDK/CGLIB 生成代理对象替换原始对象。
  5. 投入使用：放入 singletonObjects，业务拿到的其实是代理。只有走代理调用，切面逻辑才会执行。

4核心语法与 API 要点

4.1 构造器注入：Spring 推荐的装配方式

@Service
public class RequirementService {
    private final RequirementMapper requirementMapper;
    private final EventPublisher eventPublisher;

    // 单构造器可省略 @Autowired：Spring 自动按类型注入
    // 用 final + 构造器：依赖不可变、启动时缺依赖直接报错、便于 new 出来单测
    public RequirementService(RequirementMapper requirementMapper,
                              EventPublisher eventPublisher) {
        this.requirementMapper = requirementMapper;
        this.eventPublisher = eventPublisher;
    }
}

4.2 声明一个切面：日志/鉴权/事务通知

@Aspect
@Component
public class WebLogAspect {
    // 切点：切到 controller 包下所有 public 方法
    @Pointcut("execution(public * com.dcp.controller..*.*(..))")
    public void controllerPoint() {}

    @Around("controllerPoint()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();                 // 放行到真实方法
        } finally {
            long cost = System.currentTimeMillis() - start;
            log.info("{} 耗时 {}ms", pjp.getSignature().toShortString(), cost);
        }
    }
}

4.3 @Transactional：声明式事务（及其失效边界）

@Service
public class RequirementService {
    // 只有"通过代理对象调用"且方法是 public、抛 RuntimeException 才回滚
    @Transactional(rollbackFor = Exception.class)   // 默认只回滚 RuntimeException，受检异常要显式 rollbackFor
    public void changeStatus(Long id, Status next) {
        mapper.updateStatus(id, next);
        eventPublisher.publish(new StatusChanged(id, next));
        // 若这里抛 RuntimeException → 上面 updateStatus 一并回滚
    }
}

传播行为：@Transactional(propagation = ...) 决定事务如何嵌套——默认 REQUIRED（有事务就加入、无则新建）；REQUIRES_NEW 挂起外层事务、新开独立事务（如记录操作日志要独立提交，不受外层回滚牵连）；NESTED 基于保存点做部分回滚。注意 REQUIRES_NEW 同样必须走代理对象，自调用时一样失效。

4.4 两种写法对比：自调用 vs 注入自身代理

// 坏：this.changeStatus() 走原始对象，事务切面被绕过，不回滚
public void batchChange(List<Long> ids, Status next) {
    for (Long id : ids) {
        this.changeStatus(id, next);   // ← this 不是代理！
    }
}

// 好：注入自身代理（或 AopContext.currentProxy()），让调用走切面
public void batchChange(List<Long> ids, Status next) {
    for (Long id : ids) {
        self.changeStatus(id, next);  // self 是注入进来的代理对象
    }
}
// 注入自身：@Lazy @Autowired private RequirementService self;
经验：Spring Boot 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false）。如果启动报 " circular references between beans"，优先重构拆依赖，而不是开回这个开关——构造器注入的循环依赖本就该在设计上消除。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 与数据编排平台后端都是 Spring 容器托管的分层应用，IOC 组装 Bean、AOP 横切日志/鉴权/事务。

  • 业务量级：需求流转、团队权限、工作流节点，涉及多处"进接口先鉴权、写操作加事务、关键操作记日志"。

2 我的角色与职责

  • 分工：负责分层架构落地（Controller/Service/Mapper），编写鉴权切面、日志切面与事务边界。

3 技术栈

  • 组合：SpringBoot 3 + Java 17 + MyBatis + Redis；AOP 用 Spring 自带代理。

4 落地设计

  • 构造器注入：Service 依赖用构造器注入，字段注入 @Autowired 仅在测试临时用，保证可测试与不可变。
  • 切面横切：登录态校验、操作日志、事务分别抽成切面/注解，业务代码不写样板。

5 关键实现要点

@Service
@RequiredArgsConstructor                       // 构造器注入，依赖不可变
public class ReqService {
    private final ReqMapper reqMapper;
    private final ReqAssembler assembler;

    @Transactional(rollbackFor = Exception.class)   // 状态流转加事务
    public void review(Long id, ReviewCmd cmd) {
        Req r = reqMapper.selectById(id);
        r.apply(cmd);
        reqMapper.updateById(r);
    }
}

6 真实问题与解法

  • 坑@Transactional 自调用失效：同类内 this.otherMethod() 调带注解方法，代理不生效、事务没开——把调用拆到另一个 Bean 或注入自己。
  • 坑默认只回滚 RuntimeException：受检异常不回滚——显式 rollbackFor = Exception.class。
  • 坑JDK 动态代理只代理接口：CGLIB 代理的类不能是 final；两者选择影响切面能否织入。

7 量化成果

  • 鉴权/日志/事务横切抽成切面后，业务 Service 方法不再夹带样板，单个方法平均少写 5-8 行重复代码（估算）。

8 协作与排期过程

  • 切面统一在后端模块内维护，前端/接口定义不变；事务边界与 DBA 在评审"状态流转"用例时确认。

9 复盘与可复用经验

  • 横切一律切面化：日志/鉴权/事务不进业务方法。
  • 事务边界要清醒：自调用、异常类型是最高频失效点。

10 面试讲法

"业务系统 用构造器注入做分层，把鉴权/日志/事务抽成切面；实践中常见的坑包括过 @Transactional 自调用失效和默认不回滚受检异常的坑，靠 rollbackFor 与拆 Bean 解决。"

6易错点与面试重点

6.1 @Transactional 为什么失效（最常考）

一句话定位：事务失效的根因是"没走代理"或"异常没抛出来"——五种典型场景要能逐条说出为什么。

  • 坑自调用：this.method() 绕过代理。
  • 坑方法不是 public：代理增强不到非 public 方法。
  • 坑异常被 catch 吞掉没抛出。
  • 坑受检异常没配 rollbackFor：默认只回滚 RuntimeException，需显式 rollbackFor=Exception.class。
  • 坑存储引擎不支持事务：如 MyISAM。

6.2 循环依赖：三级缓存只解单例 setter/字段注入

一句话定位：构造器互相注入，三级缓存也插不进手——只能重构，别盲目开开关。

  • 现象：A、B 互相构造器注入，Spring 直接报循环依赖错误。
  • 原因：构造器注入时对象还没实例化就要对方引用，三级缓存需要对象先实例化才有早期引用。
  • 正解：抽公共服务、用 @Lazy 延迟一方、改 setter 注入，而不是开 allow-circular-references=true。

6.3 JDK 代理 vs CGLIB 怎么选

一句话定位：JDK 代理只能增强接口方法，CGLIB 靠继承覆写——所以 final 方法加 @Transactional 不生效。

  • 考点：目标类有接口默认走 JDK 代理（Spring Boot 2.x+ 默认 CGLIB）。
  • 坑final 类/方法加 @Transactional 不生效：CGLIB 靠继承覆写，final 覆写不了。

6.4 singleton 里注入 prototype 不生效

一句话定位：单例只在启动时注入一次 prototype，之后拿到的永远是同一个实例。

  • 现象：单例 Bean 里注入了 prototype Bean，每次拿到的还是同一个实例。
  • 原因：单例只被创建一次，注入发生在启动时。
  • 正解：用 ObjectFactory<T> 或 @Lookup 每次取新实例。

6.5 切面顺序：多个切面谁先谁后

一句话定位：多个 @Aspect 默认顺序不确定，要用 @Order(n) 指定——数值小的在外层。

  • 现象：日志切面与事务切面叠加时，日志没记到事务内的异常。
  • 正解：用 @Order(n) 指定优先级，数值小的先进入（外层）；事务切面包住业务、日志切面再包住事务。

6.6 @PostConstruct 里调本类切面方法不生效

一句话定位：@PostConstruct 在生成代理之前执行，此时 self 还是原始对象。

  • 现象：初始化方法里调本类 @Transactional/@Async 方法，切面没起作用。
  • 原因：@PostConstruct 在 BeanPostProcessor 生成代理之前执行。
  • 正解：初始化逻辑放到 ApplicationReadyEvent，或注入自身代理后再调。
