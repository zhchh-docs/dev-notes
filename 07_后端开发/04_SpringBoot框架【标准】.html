Spring Boot 框架

标准 定位：Spring 的"开箱即用"封装——自动配置 + Starter + 可执行 jar

Spring Boot 不重写 Spring，而是在 IOC/AOP 之上做"约定优于配置"的封装：按类路径下有什么依赖自动装配对应 Bean、把常用技术栈打包成 Starter、内嵌 Web 容器让一个 jar 直接跑起来。本页讲清自动配置原理、Starter 机制、配置绑定与 Profile，并用 业务系统 与数据编排平台两个项目的实际搭建过程收尾。

1技术点概览

一句话定位：Spring Boot 不提供新编程模型，而是"约定优于配置"——Starter 打包依赖、按类路径自动配置、内嵌容器打成可执行 jar。本项目用 Spring Boot 3.x（Spring 6，最低 Java 17，javax→jakarta）。

  • 三个核心动作：① Starter 起步依赖把一类技术的库打包成一个；② 按类路径条件自动配置 Spring 上下文；③ 内嵌 Tomcat/Jetty，打成可 java -jar 运行的 fat jar。
  • 它解决什么：传统 SSH/SSM 要手写大量 XML 配数据源/事务/视图服务器，依赖版本还常冲突；Boot 把这些"样板配置"按默认值自动做掉。

代价是"魔法"——当自动配置不符合预期时，必须知道它背后做了什么（见板块 3）。

2核心概念

2.1 约定优于配置（Convention over Configuration）

一句话定位：Spring Boot 不是"零配置"，而是"把 90% 场景的合理默认值替你配好"，要改再覆盖。

  • 默认约定：静态资源放 static/、配置文件叫 application.yml、端口默认 8080。
  • 边界：它降低的是"决策与样板"，不是"配置能力"——需要改时在配置文件覆盖即可。

2.2 自动配置（Auto-Configuration）

一句话定位：启动时读取所有 jar 里的自动配置类，逐个用条件注解判断该不该装配——这是 Boot 的核心魔法。

  • 条件注解：@ConditionalOnClass/@ConditionalOnMissingBean/@ConditionalOnProperty 判断"类路径有没有这个类、容器里有没有同类型 Bean、配置项开没开"。
  • 典型例子：类路径里有 DataSource 相关类且配了 url，就自动建一个 HikariCP 数据源 Bean。

"加一个 Starter，能力自动就有了"——靠的就是这套条件装配。

2.3 Starter 起步依赖

一句话定位：Starter 本身不含代码，而是把"做某件事需要的一整套库及兼容版本"打包在一起。

  • 例子：spring-boot-starter-web = Spring MVC + 内嵌 Tomcat + Jackson；spring-boot-starter-data-redis = Lettuce + Spring Data Redis。
  • 解决两个老问题：依赖版本对齐（BOM 统一管版本）、依赖不全导致的 NoClassDefFound。

2.4 配置绑定与 Profile

一句话定位：配置写在 yml，零散值用 @Value、整组用 @ConfigurationProperties；Profile 做多环境隔离。

  • @ConfigurationProperties（推荐）：整组绑定到一个配置类，可校验、结构化。
  • Profile：application-dev.yml/application-prod.yml，用 spring.profiles.active 激活，开发库与生产库互不污染。

2.5 内嵌容器与可执行 jar

一句话定位：把 Tomcat 打进 fat jar，java -jar 直接启动一个自带 Web 服务器的进程——也是 Docker 的天然搭档。

  • 变化：部署单元从"war + 外部容器"变成"一个进程"。
  • 可换：内嵌容器默认 Tomcat，可换成更轻的 Jetty。
  • 监控：生产环境常加 spring-boot-starter-actuator，暴露 /actuator/health 健康检查等端点；默认仅开放 health/info，其余需用 management.endpoints.web.exposure.include 显式开放。

3工作原理与流程

3.1 自动配置：从 main 方法到 DataSource 装配成功

一句话定位：理解这条链，才能解释"为什么加了 Redis 依赖却连不上""为什么排除自动配置要用 exclude=..."。

图 2 自动配置：加载候选 → 条件判断 → 装配 Bean（示意）

  1. 入口：@SpringBootApplication 是个组合注解，内含 @EnableAutoConfiguration（开启自动配置）、@ComponentScan（扫描本包及子包）。
  2. 加载候选：Spring Boot 3 从每个 starter 的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 读取自动配置类清单（旧版是 spring.factories）。
  3. 条件过滤：每个自动配置类上都标着条件注解，只有类路径真有 HikariDataSource、配置里真有 spring.datasource.url，数据源配置才生效。
  4. 可覆盖：自动配置里的 Bean 大多标了 @ConditionalOnMissingBean——你自己写了一个同类型 Bean，默认的就退让。这是"开箱即用又可改"的关键。

4核心语法与 API 要点

4.1 主类与最小可运行应用

@SpringBootApplication
public class RmpApplication {
    public static void main(String[] args) {
        SpringApplication.run(RmpApplication.class, args);
    }
}

4.2 配置绑定：@ConfigurationProperties 整组映射

# application.yml
rmp:
  app-name: requirement-platform
  page-size: 20
  ai:
    endpoint: https://ai.internal/api
    timeout-ms: 3000
@Component
@ConfigurationProperties(prefix = "rmp")   // 比散落的 @Value 更可维护、可校验
public class RmpProps {
    private String appName;
    private int pageSize;
    private Ai ai = new Ai();
    // getter/setter 省略
    public static class Ai {
        private String endpoint;
        private int timeoutMs;
        // getter/setter 省略
    }
}

4.3 Profile 多环境

# application.yml 通用配置
spring:
  profiles:
    active: dev            # 默认开发环境；生产用启动参数 --spring.profiles.active=prod 覆盖

# application-dev.yml：开发库
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/rmp_dev

# application-prod.yml：生产库（不同 host/账号）

4.4 自定义 Starter 的核心写法（理解机制）

// 自动配置类：条件满足才生效
@AutoConfiguration
@ConditionalOnClass(Client.class)
@EnableConfigurationProperties(ClientProps.class)
public class ClientAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean   // 用户自己定义就不盖默认
    public Client client(ClientProps props) {
        return new Client(props.getEndpoint());
    }
}
经验：业务系统 把"统一返回结构、全局异常、鉴权拦截器"抽成一个内部 starter（Monorepo 公共包），各微服务引入即用，避免每个项目复制一遍相同的 Web 配置——这正是 Starter 机制在团队内的价值。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 与数据编排平台后端都基于 SpringBoot 3 + Java 17，靠自动配置与 Starter 快速起服务。

  • 业务量级：从一个 main 方法起服务，连上 MySQL、Redis，对外提供 REST 接口。

2 我的角色与职责

  • 分工：负责服务搭建、配置管理、接入 MyBatis/Redis 与接口暴露。

3 技术栈

  • 组合：SpringBoot 3 + Web Starter + MyBatis Starter + Redis(Redisson) Starter；多环境配置 application-{dev,prod}.yml。

4 落地设计

  • 约定优于配置：靠 starter 自动装配数据源/Redis/JSON，少写样板 XML。
  • 配置外置：数据库地址、密钥走环境变量/多环境 profile，不硬编码。

6 真实问题与解法

  • 坑配置不生效：写错 profile 或 key，自动配置用了默认值——开 --debug 看 condition 报告。
  • 坑Starter 版本冲突：手动引旧版依赖与 Boot 3 BOM 冲突——统一靠 parent BOM 管版本。
  • 要点Boot 3 包名变更：javax.* → jakarta.*，老依赖不兼容要换适配版。

7 量化成果

  • 新模块从建工程到跑通"数据库→接口"约半天（估算），自动配置省去手写数据源/事务管理器样板。

8 协作与排期过程

  • 公共配置（数据源/Redis）由后端统一维护，各业务模块只加自己的业务配置；上线时由运维注入环境变量。

9 复盘与可复用经验

  • 版本交给 BOM：不自管依赖版本。
  • 敏感配置外置：密钥从不进 git。

10 面试讲法

"两个后端都是 SpringBoot 3，我靠 starter 自动装配 + 多环境 profile 搭服务，踩过 javax→jakarta 迁移和配置不生效的坑，学会用 condition 报告排查自动配置。"

6易错点与面试重点

6.1 自动配置不生效：包没扫到

一句话定位：Bean 写了 @Service 却注入报找不到——多半是主类不在根包，@ComponentScan 扫不到。

  • 现象：Bean 明明写了 @Service，启动后注入报找不到。
  • 正解：主类放最外层包，或显式 @SpringBootApplication(scanBasePackages="com.dcp")。

6.2 @Value 与 @ConfigurationProperties 怎么选

一句话定位：零散单值用 @Value，一组相关配置用 @ConfigurationProperties。

  • 误区：到处 @Value("${...}")，配置散落在各个类里。
  • 正解：一组相关配置用 @ConfigurationProperties（结构化、可 JSR-303 校验、配置变更友好）。

6.3 Profile 没生效

一句话定位：配了 prod 却连 dev 库——启动参数没传对，或 yml 里 active 写死覆盖了。

  • 正解：启动用 --spring.profiles.active=prod 或环境变量 SPRING_PROFILES_ACTIVE，容器里后者更常用。

6.4 Starter 版本冲突

一句话定位：引入三方 starter 后报 NoSuchMethodError——传递依赖版本对不上，用依赖树查。

  • 正解：mvn dependency:tree 看依赖树，用 dependencyManagement/BOM 对齐版本。

6.5 Spring Boot 3 的 javax → jakarta 迁移

一句话定位：Boot 3 全面转向 Jakarta EE 9+，包名从 javax.* 变 jakarta.*，旧 starter 必须升级。

  • 现象：Boot 3 项目里 import javax.servlet 报错。
  • 正解：javax.servlet/persistence/validation/annotation 全改成 jakarta.*，旧 starter 升到支持 Boot 3 的版本。
