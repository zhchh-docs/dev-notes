SSH 框架（Struts2 + Spring + Hibernate）

基础 定位：已退役的 Java EE 经典组合——理解后端分层与演进脉络

SSH 是 2010 年代前后 Java Web 的主流组合：Struts2 做控制层、Spring 做业务与依赖注入、Hibernate 做 ORM 持久层。它早已被 SSM（SpringMVC+Spring+MyBatis）乃至 Spring Boot 取代，但理解它，就理解了"后端为什么要分层、ORM 解决什么痛点、配置为什么要从 XML 走向注解与自动装配"。本页入门导向，诚实说明其现状。

1技术点概览

一句话定位：SSH = Struts2（控制层）+ Spring（业务层 IoC）+ Hibernate（持久层 ORM），是 Java EE 时代"用成熟框架拼出分层 Web 应用"的典型范式。

  • 它解决什么：SSH 之前要直接写 Servlet + JDBC，代码里 HTML、SQL、业务逻辑混在一起；SSH 把应用切成三层，每层各司其职，可维护性大幅提升。
  • 历史价值：确立了 MVC 与分层架构在 Java 后端的主流地位。

需要诚实说明：这一组合在今天的新项目里已基本退役——本页目的是理解分层思想与演进脉络，不是要在新项目里用它。

2核心概念

2.1 MVC 三层分工

一句话定位：SSH 把一个 Web 应用切成"接请求—管业务—碰数据库"三层，各层只干一件事——这套分层至今没变。

  • 控制层（Struts2 Action）：接收 HTTP 请求、调用业务、选择返回哪个视图。
  • 业务层（Spring Service）：承载领域逻辑，并用声明式事务包起来。
  • 持久层（Hibernate DAO/实体）：把对象映射到数据库表，负责数据存取。

"请求 → 业务 → 数据"的分层思路是 SSH 留给今天的核心遗产——现在 Spring Boot 里的 Controller / Service / Mapper 就是它的直系后代。

2.2 ORM：对象关系映射（Hibernate）

一句话定位：ORM 让你用 Java 对象操作数据库，把"一行记录"当"一个对象"用，免手写 JDBC。

  • 目标：数据库一行 ↔ Java 一个对象，开发者面向对象编程，不再拼 SQL 字符串。
  • Hibernate 是全自动 ORM：实体加注解映射表，框架自动生成 SQL、管主键、做关联。
  • 好处：CRUD 写得极快，样板代码少。
  • 代价：复杂查询不灵活，自动生成的 SQL 偶尔很慢。

图 2 Hibernate vs MyBatis（示意）

全自动 ORM 的"黑盒生成 SQL"正是国内后来普遍选 MyBatis（半自动、手写 SQL）的原因——可控性优先。

2.3 Spring 在 SSH 中的角色

一句话定位：三个框架里只有 Spring 活到今天，它是把另外两块"粘"起来的容器。

  • IoC 装配：用容器把 Action、Service、DAO 组装起来，而不是互相 new。
  • AOP 事务：提供声明式事务，@Transactional 的前身就是 XML 配置。

理解了 Spring 的 IoC/AOP，就理解了 SSH 的骨架——这也是为什么 Struts2、Hibernate 退役了，Spring 还在。

3工作原理与流程

一句话定位：一个请求在 SSH 里的流转，和今天高度相似，只是把"注解/自动装配"换成了"XML 配置"。

以"提交一个表单"为例：浏览器请求先到 Struts2 的前端控制器（FilterDispatcher），按 struts.xml 路由到 Action；Action 由 Spring 注入 Service；Service 用 Hibernate 操作数据库；最后由 Struts2 选 JSP 视图渲染。今天 Spring Boot 里是 DispatcherServlet 接请求、@RequestMapping 路由、Controller 调 Service——骨架一致。

图 3 SSH 请求流转（示意）

  1. 请求接入：Struts2 前端控制器拦截请求，查配置文件路由到 Action。
  2. 业务处理：Action 调 Spring 注入的 Service，Service 在声明式事务里用 Hibernate 读写对象。
  3. 数据持久化：Hibernate 把实体对象自动转成 SQL，提交到数据库。
  4. 视图渲染：Struts2 跳转到 JSP，把数据填充进 HTML 返回浏览器。

4核心语法与 API 要点

下面是 SSH 时代典型配置的样子，用于对照今天的注解写法，直观感受"配置从 XML 走向约定"。

4.1 struts.xml：请求路由（已被 @RequestMapping 取代）

<!-- struts.xml：一个 Action 的路由与视图配置 -->
<action name="req_*" class="reqAction" method="{1}">
    <result name="success">/req/list.jsp</result>
    <result name="input">/req/form.jsp</result>
</action>
<!-- 今天：一个 @RequestMapping("/req") 注解就替代了这段 XML -->

4.2 Hibernate 实体映射（注解版）

@Entity                       // 这个类映射一张表
@Table(name = "t_requirement")
public class Requirement {
    @Id @GeneratedValue
    private Long id;          // 主键，自动生成
    private String title;
    @ManyToOne                // 多对一关联团队
    private Team team;
    // getter/setter 省略
}
对照：今天 MyBatis 里同样的事，是写一个 RequirementMapper 接口 + XML/注解 SQL，SQL 由人控制。两种 ORM 路线的取舍见 MyBatis 专题。

5实战项目经验（自学 + 自建 Demo）

定位说明：SSH（Struts2 + Spring + Hibernate）是 Java Web 早期经典组合，实际项目已演进到 SpringBoot + MyBatis，未在近年项目使用 SSH。本节为最小骨架复刻与演进理解笔记，非生产环境项目。

1 自学背景与动机

一句话定位：补"现代 SpringBoot 之前 Java Web 长什么样"的历史认知，理解框架为何从 SSH 演进到注解 + 自动配置。

  • 缺口：直接上手 SpringBoot，不清楚 XML 重配置、Struts2 拦截器栈、Hibernate ORM 映射的来龙去脉。

2 搭建的 demo 是什么

  • 技术栈：Struts2 + Spring + Hibernate 三框架整合的最小 Web 工程，一个登录 + 列表查询。
  • 规模：单体 war 包跑在 Tomcat，一张用户表，走"Action→Service→DAO(Hibernate)"。

3 落地步骤

<!-- Spring 托管 Bean，Hibernate SessionFactory 由 Spring 管理 -->
<bean id="sessionFactory"
      class="org.springframework.orm.hibernate5.LocalSessionFactoryBean">
  <property name="dataSource" ref="dataSource"/>
</bean>
<!-- Struts2 把请求映射到 Spring 容器里的 Action -->
<action name="login" class="loginAction" method="execute">
  <result name="success">/list.jsp</result>
</action>

4 自学过程中遇到的坑与解决

  • 坑配置量大：数据源、SessionFactory、事务、Action 全在 XML，改一处翻半天——这正是 SpringBoot 自动配置要消灭的痛点。
  • 坑Struts2 版本安全漏洞：早期版本有远程命令执行历史，复现时刻意用归档版本仅本地学习。

5 成果

  • 跑通后能讲清"请求→Struts2 拦截器→Spring 托管的 Action→Hibernate 操作数据库"整条链路，并对比出 SpringBoot 删掉了哪些配置。

6 与真实项目的差异

  • 这是理解性 demo，未上生产；近年项目用 SpringBoot + MyBatis，SSH 仅作演进脉络参考。

7 面试讲法

"实践中常采用最小工程复刻过 Struts2+Spring+Hibernate，理解了 XML 重配置和 ORM 映射的代价，这也是我快速接受 SpringBoot 自动配置的原因。"

6易错点与面试重点

6.1 Struts2 的安全漏洞历史

一句话定位：Struts2 历史上多次爆出 RCE，这是它被淘汰的重要原因之一。

  • 现象：著名的 S2-045，基于 Content-Type 解析的 OGNL 注入导致远程代码执行。
  • 原因：Struts2 用 OGNL 表达式解析参数，设计过于强大，易被绕过。
  • 正解：遗留系统升级到最后版本或迁移；新系统不再选用。

6.2 Hibernate 的 N+1 查询问题

一句话定位：查 100 条再逐条查关联，发出 1+100 条 SQL——全自动 ORM 的经典痛点。

  • 现象：查出 100 条需求，每条又单独查一次关联团队，共 101 条 SQL。
  • 原因：全自动 ORM 遍历关联对象时懒加载，逐个触发 SQL。
  • 正解：用 fetch join 一次性查出，或在集合上配置批量抓取。

N+1 是全自动 ORM 的通病，也是 MyBatis 更受国内团队欢迎的现实原因之一。

6.3 XML 配置臃肿

一句话定位：几百行 XML 找一个 Bean 定义要翻半天——这正是注解化、自动装配要消灭的。

  • 现象：工程里 XML 巨大，改一个路由、找一个 Bean 都要翻文件。
  • 原因：早期框架没有注解与约定，一切都靠 XML 声明。
  • 正解：这正是 Spring 注解化、再到 Spring Boot 自动装配要解决的问题。
