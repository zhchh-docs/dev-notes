Java 基础

标准 定位：后端业务开发的母语——语法、集合、泛型、函数式、异常与 IO

Java 是一门编译为字节码、跑在 JVM 上的静态强类型语言。本页以 业务系统（Spring Boot 3 + Java 17）日常开发为背景，讲清集合框架、泛型与类型擦除、函数式 Stream、异常体系与 try-with-resources、以及 Java 17 的现代语法（record/sealed/var），重点落在"每天都在写、却最容易写错"的那一层。

1技术点概览

一句话定位：Java = 编译成字节码、跑在 JVM 上的静态强类型语言；本套技术栈用 Java 17 LTS（Spring Boot 3 的硬性基线）。

  • 怎么跑起来：源码 .java 经 javac 编译成平台无关的字节码 .class，再由各系统的 JVM 解释 + JIT 即时编译执行。
  • 它解决什么：编译期类型检查在上线前挡住一大类错误；内存交给 GC，业务开发者不用手动 free；"一次编写到处运行"让同一套服务在开发机/测试服务器/容器里一致运行。

代价是启动慢、内存占用偏高——这正是后面 JVM 调优与并发专题要解决的问题。

2核心概念

2.1 字节码与平台无关（Bytecode & JVM）

一句话定位：Java 不编译成任何 CPU 的机器码，而编译成 JVM 的指令集——同一份 .class 到处跑。

  • 字节码：.java 经 javac 编译成 .class，是供 JVM 消费的中间指令集，与具体 CPU 无关。
  • 跨平台：同一份 .class 丢到 Windows/Linux/容器里的 JVM 都能跑，即"一次编写、到处运行"。
  • JIT 优化：运行时边解释边把热点代码编译成本地机器码，所以服务启动后越跑越快。

理解这点就懂了"为什么 Java 服务要预热、为什么容器里要按实际内存配堆"。

2.2 静态强类型与基本类型/引用类型

一句话定位：变量类型编译期就定死；基本类型存值、引用类型存地址——这是 == 与 equals() 区别的根源。

  • 静态强类型：每个变量类型编译期确定，不能随意赋不兼容的值。
  • 基本类型（int/long/double/boolean/byte/char/float/short）：直接存值，在栈上。
  • 引用类型（对象、数组）：变量存的是堆中对象的地址。
  • 别名现象：赋基本类型是复制值，赋引用类型是复制地址——两个引用可指向同一个对象。
  • 装箱/拆箱：Integer/Long 与基本类型自动转换，但有开销且暗藏缓存坑（见板块 6）。

2.3 集合框架（Collections Framework）

一句话定位：集合是业务里出现频率最高的 API——List 管顺序、Set 管去重、Map 按键查。

  • 两大根接口：Collection（单列，下分 List 有序可重复、Set 去重）与 Map（键值对）。
  • ArrayList：动态数组，随机读快、尾部插快、中间插慢。
  • HashMap：数组+链表+红黑树，读写平均 O(1)；负载因子 0.75，链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树，扩容为 2 倍。
  • ConcurrentHashMap：线程安全的 Map，并发环境用它；Hashtable 是 JDK 1.0 的遗留类（legacy），类级并未标注 @Deprecated，但并发场景应改用 ConcurrentHashMap。

选型心智：要顺序用 List、要去重用 Set、要按键查用 Map、并发环境一律用并发容器。

2.4 泛型与类型擦除（Generics & Type Erasure）

一句话定位：泛型是编译期约束，编译后被擦除——List<String> 和 List<Integer> 在字节码里是同一个 List。

  • 作用：编译期约束容器装什么类型，List<String> 放不进 Integer，避免运行时 ClassCastException。
  • 擦除带来的限制：不能 new T()、不能 instanceof List<String>。
  • PECS 原则：? extends T（上界，只读）、? super T（下界，只写）——Producer Extends, Consumer Super。

2.5 函数式编程与 Stream（Functional & Stream API）

一句话定位：Lambda + Stream 把集合处理写成声明式流水线，Optional 把"可能为空"写进类型签名。

  • 行为参数化：Java 8 起的 Lambda 与 Function/Consumer/Supplier/Predicate，让行为像数据一样传递。
  • Stream 流水线：filter → map → collect 替代手写 for 循环与临时变量。
  • Optional：显式表达"可能没有值"，逼调用方处理空值，减少 NPE。
  • Java 17 新语法：record（不可变数据载体）、sealed（受限继承）、var（局部类型推断）进一步压薄样板代码。

3工作原理与流程

3.1 一段 Java 代码从源码到运行的完整链路

一句话定位：平时写业务不用想这条链路，但排查"类找不到、版本冲突、启动慢"时它是地图。

图 2 Java 从源码到执行引擎的链路与运行时数据区（示意）

  1. 编译期：javac 做词法/语法分析、类型检查、泛型擦除，生成字节码。编译期就能发现类型不匹配、缺少返回值等错误——这是 Java 相比动态语言的第一道安全网。
  2. 类加载：JVM 首次用到某个类时，类加载器把 .class 字节码读入、验证合法性、把符号引用解析成直接引用、执行 <clinit> 静态初始化。类只加载一次，缓存在方法区。
  3. 内存分配：new 出来的对象在堆上分配（线程共享），方法内的基本类型与引用本身在栈帧的局部变量表（线程私有）。
  4. 执行与 JIT：解释器逐条执行字节码，同时监控热点方法（被高频调用的方法、循环），JIT 把它编译成本地机器码缓存起来，下次直接跑本地码——这就是"预热后变快"。
  5. GC：堆中不再被任何栈帧引用的对象由垃圾回收器自动回收，开发者不用手动 free。GC 的选择与调优见并发与 JVM 专题。

4核心语法与 API 要点

4.1 集合初始化与 Stream 流水线

// 不可变集合（Java 9+）：List.of / Map.of，比 Arrays.asList 更安全
List<String> owners = List.of("zhangsan", "lisi", "wangwu");

// 需求单按状态分组、再统计数量，一条 Stream 完成（替代多层 for + Map.put）
Map<RequirementStatus, Long> stat = requirements.stream()
    .filter(r -> r.getPriority() != Priority.LOW)          // 过滤
    .collect(Collectors.groupingBy(
        Requirement::getStatus,                            // 分组键
        Collectors.counting()));                           // 下游收集器：计数

// 提取 id 列表，供后续批量查询 in(...) 使用
List<Long> ids = requirements.stream()
    .map(Requirement::getId)
    .distinct()
    .toList();                                             // Java 16+ 直接返回不可变 List

4.2 Optional：显式处理"可能为空"

// 坏：返回 null，调用方忘记判空 → NPE
public Requirement findById(Long id) { ... return null; }

// 好：返回 Optional，把"可能为空"写进类型签名
public Optional<Requirement> findById(Long id) {
    return Optional.ofNullable(mapper.selectById(id));
}
// 调用方被迫处理：有值就用，没值给默认值或抛业务异常
Requirement r = repo.findById(id)
    .orElseThrow(() -> new BizException("需求不存在: " + id));

4.3 try-with-resources：IO/连接的安全关闭

// 老式写法：finally 里关流，还要判空，容易漏关 → 连接泄漏
BufferedReader br = null;
try { br = new BufferedReader(new FileReader(path)); ... }
finally { if (br != null) br.close(); }

// Java 7+ try-with-resources：AutoCloseable 自动关闭，即使抛异常也关
try (BufferedReader br = Files.newBufferedReader(Paths.get(path))) {
    return br.lines().filter(line -> !line.startsWith("#")).toList();
} // br 在此自动 close，无需 finally

4.4 Java 17 现代语法：record 与 var

// record：一行声明不可变数据载体，自动生成构造器、getter、equals、hashCode、toString
public record RequirementDTO(Long id, String title, RequirementStatus status) {}

// var：局部变量类型推断，右侧类型明确时省去重复写泛型
var active = requirements.stream().filter(r -> r.isActive()).toList();

// sealed：限制哪些类可以继承它，配合模式匹配做穷举
public sealed interface Event permits Created, Updated, Closed {}

4.5 异常体系：受检 vs 非受检

// Throwable 分两支：Error（JVM 级，别捕）/ Exception
//   Exception 里 RuntimeException 及其子类 = 非受检（编译器不强制 catch）
//   其余 Exception = 受检（必须 throws 或 try-catch）
// 业务惯例：自定义业务异常继承 RuntimeException，避免层层 throws 污染签名
public class BizException extends RuntimeException {
    private final String code;
    public BizException(String code, String msg) { super(msg); this.code = code; }
}
经验：Spring 生态里统一用 @RestControllerAdvice 兜底捕获 BizException，业务代码只管 throw new BizException(...)，不要在 Service 里吞异常（catch(Exception e){}）——吞掉的异常线上最难查。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统（需求管理平台）后端是 SpringBoot 3 + Java 17 的单体服务，Java 语法特性贯穿日常每个接口的编写。

  • 业务量级：需求/团队/工作流/AI 集成多模块，服务端日均处理数百次需求流转与评审操作（估算）。

6 真实问题与解法

  • 坑自动拆箱 NPE：Integer 状态值为 null 时直接 == 比较拆箱 NPE——改 Objects.equals(a,b)。
  • 坑equals 写反：用可能为 null 的变量调 .equals() 空指针——常量或枚举放前面。
  • 要点Stream 别滥用：简单循环里硬套 Stream 反而难读，只在分组/映射/过滤时用。

7 量化成果

  • 用 record + Stream 后，单个需求列表接口的 DTO 转换代码行数下降约一半（估算），可读性提升。

8 协作与排期过程

  • 接口出入参随 OpenAPI 文档与前端对齐字段名，DTO 一改就同步文档，避免前后端字段名不一致返工。

9 复盘与可复用经验

  • 空安全优先：所有外部入参先判空，业务异常集中抛。
  • 不可变优先：DTO 用 record，减少可变状态。

6易错点与面试重点

6.1 == 与 equals：Integer 缓存坑

一句话定位：== 比地址，值比较永远用 equals()——Integer 对 -128~127 做了缓存。

  • 现象：Integer a=127,b=127; a==b 为 true；但 a=200,b=200 为 false。
  • 原因：Integer 对 -128~127 缓存复用，超出范围每次 new 新对象。
  • 正解：值比较用 equals()（或拆箱成 int 再比）。

面试高频：equals 与 hashCode 必须同时重写——只重写 equals，对象进 HashMap/HashSet 后按 hashCode 散列错位、找不到。

6.2 ConcurrentModificationException：边遍历边删

一句话定位：for-each 里 list.remove() 会抛并发修改异常——要用 removeIf。

  • 现象：for-each 遍历 List 时调 list.remove()，抛并发修改异常。
  • 原因：for-each 底层是 Iterator，它有 expectedModCount 校验，手动 remove 让 modCount 对不上。
  • 正解：用 Iterator.remove()，或 Java 8+ 直接 list.removeIf(r -> r.isX())。

6.3 异常吞噬：catch 了却什么都不做

一句话定位：catch(Exception e){} 吞掉异常 = 丢掉唯一现场，线上最难查。

  • 现象：try{...}catch(Exception e){}，线上出问题时日志一片空白。
  • 原因：吞掉异常等于丢掉了唯一的现场信息。
  • 正解：要么 throw new BizException(msg, e) 带上 cause 往上抛，要么至少 log.error("xxx 失败", e)。

6.4 Stream 的两个隐蔽坑

一句话定位：流只能消费一次；lambda 里不能修改外部可变变量。

  • 坑流只能消费一次：terminal 后流水线关闭，复用同一 Stream 抛 IllegalStateException，需要时重新 collection.stream()。
  • 坑lambda 里改外部变量：lambda 捕获的局部变量必须 final/等效 final；累加计数用 mapToInt().sum() 或 summingInt，别写 int count=0; forEach(x->count++)（编译不过且线程不安全）。

6.5 自动装箱的性能与 NPE

一句话定位：Integer i=null; int j=i; 拆箱时对 null 调 .intValue() 直接 NPE。

  • 现象：Integer i=null; int j=i; 抛 NPE。
  • 原因：基本类型与包装类型混用，自动拆箱在 null 上爆炸。
  • 正解：DTO 里可能为空的数值用包装类型、计算前判空；热点循环避免反复装箱，用 LongAdder 或 mapToLong。
