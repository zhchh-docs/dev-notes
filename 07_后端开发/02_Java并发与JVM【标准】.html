Java 并发与 JVM

标准 定位：吞吐与稳定性的底层——线程池、并发容器、JVM 内存与 GC 调优

后端服务的"快"与"稳"都落在这一页：并发决定一次请求能否把多个慢 IO 并行起来把总时长压到最长一条，JVM 决定服务在容器里会不会 OOM、会不会频繁 Full GC 停顿。本页以大屏分布式数据聚合并发、以及线上 JVM 内存与 GC 调优通用实践为背景，讲清线程池参数、JUC 并发工具、堆分代与垃圾回收选择。

1技术点概览

一句话定位：并发管多线程怎么并行跑，JVM管这些线程与对象怎么在内存里活下来——两者决定后端的吞吐、延迟与稳定性。

  • 并发靠什么：Thread + java.util.concurrent（JUC）提供线程池、锁、并发容器、同步器。
  • JVM 靠什么：堆/栈内存布局 + 垃圾回收器（GC）自动管理对象生命周期。
  • 为什么要并行：一次大屏聚合要查 5~8 个数据源，串行耗时相加；线程池并行后总耗时约等于最慢那一段。
  • 为什么要 GC 调优：对象不回收会涨到 OOM；但回收时的 "Stop The World" 停顿又拖慢响应，需按业务选堆大小与回收器。

2核心概念

2.1 线程与线程生命周期（Thread & States）

一句话定位：线程是 OS 调度的最小单位；理解它的状态流转，是排查"线程卡住、死锁"的前提。

  • 状态流转：NEW → RUNNABLE → 运行 → BLOCKED（等锁）→ WAITING/TIMED_WAITING（wait/sleep/join）→ TERMINATED。
  • 坑sleep 不释放锁：sleep 只让线程休眠，synchronized 持有的锁不会释放；真正释放锁的是 Object.wait()。

2.2 线程池（ThreadPoolExecutor）

一句话定位：线程池复用线程、控制并发度；七个参数里最容易被忽略的是"队列"和"拒绝策略"。

  • 核心参数：corePoolSize、maximumPoolSize、keepAliveTime、unit（TimeUnit，keepAliveTime 的时间单位）、workQueue、threadFactory、handler（拒绝策略），共 7 个。
  • 提交流程：核心线程未满先开核心线程 → 满了进队列 → 队列满了开到最大线程 → 还满触发拒绝策略。

队列若是无界的，最大线程数永远不生效——这是 Executors.newFixedThreadPool 用无界队列导致 OOM 的根源。

2.3 JUC 并发容器与同步器

一句话定位：多线程共享数据时，普通 HashMap/ArrayList 会错乱——要用并发容器 + 同步器。

  • 并发容器：ConcurrentHashMap（读几乎无锁）、CopyOnWriteArrayList（读多写少）。
  • 同步协调：CountDownLatch（等 N 个子任务）、CompletableFuture（异步编排）、Semaphore（限流）。
  • 锁：synchronized（内置、自动释放）与 ReentrantLock（可中断、可超时、可公平）。
  • volatile：保证可见性与禁止指令重排，但不保证复合操作原子性。

2.4 JVM 内存区域（Runtime Data Areas）

一句话定位：JVM 内存分"线程共享"与"线程私有"——OOM 高发位置就散落在这几块里。

  • 堆 Heap（共享）：对象实例分配处，GC 主战场，分新生代（Eden+Survivor）与老年代。
  • 方法区/元空间 Metaspace（共享）：存类元信息，Java 8 后挪到本地内存。
  • 虚拟机栈 / 程序计数器 / 本地方法栈（私有）：每线程一份，栈帧存局部变量表。
  • OOM 常见位置：堆溢出（对象太多/泄漏）、元空间溢出（动态生成类过多）、栈溢出（递归太深）。

2.5 垃圾回收（GC）与垃圾回收器

一句话定位：GC 从 GC Roots 出发做可达性分析回收垃圾；回收时业务线程暂停（STW），选回收器就是在吞吐与停顿间取舍。

  • 判定垃圾：从 GC Roots（栈引用、静态变量、常量）出发不可达的对象即垃圾。
  • 两类回收：Minor GC（清新生代，频繁快）vs Major/Full GC（清整堆，慢、停顿长）。
  • STW：回收时所有业务线程暂停。
  • JDK 9 起默认 G1：堆划成多 Region，可预测停顿（MaxGCPauseMillis），兼顾吞吐与低延迟（JDK 8 可用 G1 但非默认）；超大堆低延迟才上 ZGC。

调优核心 = 减少对象朝生暮死、避免对象意外进老年代、让 Full GC 尽量少。

3工作原理与流程

3.1 线程池的任务流转：为什么要理解队列与拒绝策略

一句话定位：只配 core/max 两个数是坑——忽略队列与拒绝策略，线上要么 OOM、要么任务被悄悄丢弃。

图 2 ThreadPoolExecutor 任务调度判断链（示意）

  1. 核心线程优先：任务来了先看核心线程数是否满，没满就开新核心线程直接跑——核心线程默认不回收。
  2. 队列缓冲：核心线程满了，任务进 workQueue 排队。用有界队列（如 ArrayBlockingQueue）才能在压力大时触发后面的拒绝，而不是无限堆任务。
  3. 扩容到最大：队列也满了，才临时开到 max 线程数。注意顺序——是"先排队再扩容"，不是"先扩容再排队"。
  4. 拒绝兜底：max 也满了就执行拒绝策略：默认 AbortPolicy 抛异常，常用 CallerRunsPolicy（退回调用线程自己跑，反压）。

3.2 JVM 堆分代与对象晋升

一句话定位：新对象先在 Eden 分配，熬过一次 Minor GC 年龄+1，到阈值晋升老年代——设计依据是"大多数对象朝生暮死"。

  • 晋升路径：Eden 满触发 Minor GC → 存活对象复制到 Survivor → 每熬过一次年龄+1 → 达阈值（默认 15）晋升老年代。
  • 大对象直达：超过 -XX:PretenureSizeThreshold 的大对象直接进老年代。
  • 算法分工：短命对象集中在新生代用复制算法快速回收，长寿对象放老年代用标记-整理。

"对象意外进老年代"会让老年代快速填满、触发 Full GC——这是调优要盯的核心。

4核心语法与 API 要点

4.1 手动规范构建线程池（禁止直接用 Executors）

// 禁止：Executors.newFixedThreadPool 用无界 LinkedBlockingQueue，任务堆积 → OOM
// 正解：手动 new ThreadPoolExecutor，显式定核心数、有界队列、拒绝策略
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                                   // core：CPU 密集约 N+1，IO 密集可更大
    16,                                  // max
    60L, TimeUnit.SECONDS,               // 闲线程回收
    new ArrayBlockingQueue<>(200),       // 有界队列！
    new ThreadFactoryBuilder().setNameFormat("agg-worker-%d").build(),  // 有意义的线程名，便于 dump
    new ThreadPoolExecutor.CallerRunsPolicy());  // 满了退回调用线程，形成反压

说明：业务代码不应直接 newFixedThreadPool，而应封装统一线程池工厂（有界队列 + 命名线程工厂 + 拒绝策略）；后文实战示例中为简洁起见出现的 Executors 写法仅用于演示并发提交，落地生产时请替换为本节规范构建。

4.2 CompletableFuture：并行聚合多数据源

// 并行查多个源，任意异常不影响其他路，全部完成后汇总
CompletableFuture<LoadVO> load   = CompletableFuture.supplyAsync(() -> loadClient.query(), pool);
CompletableFuture<AlarmVO> alarm = CompletableFuture.supplyAsync(() -> alarmClient.query(), pool);
CompletableFuture<DeviceVO> dev   = CompletableFuture.supplyAsync(() -> deviceClient.query(), pool);

// 等全部完成；orTimeout 给每路兜底超时，避免一个慢源拖死整页
CompletableFuture.allOf(load, alarm, dev)
    .orTimeout(2, TimeUnit.SECONDS)
    .thenApply(v -> new AggregateVO(load.join(), alarm.join(), dev.join()))
    .exceptionally(ex -> AggregateVO.fallback(ex));   // 某路失败给降级数据，不整页报错

4.3 线程安全计数与并发 Map

// 多线程统计：不要用普通 HashMap + synchronized，用 ConcurrentHashMap + LongAdder
ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
public void inc(String key) {
    counters.computeIfAbsent(key, k -> new LongAdder()).increment();
}
// LongAdder 分段计数，高并发下比 AtomicLong 竞争更小（示意用法）

4.4 关键 JVM 参数（容器内）

# Spring Boot 3 / Java 17，容器内按限制内存配堆
java -jar app.jar \
  -Xms512m -Xmx512m \                 # 堆大小固定，避免运行时扩缩
  -XX:+UseG1GC \                      # JDK 11+ 默认即 G1，显式写出更清晰
  -XX:MaxGCPauseMillis=200 \          # 目标停顿 200ms
  -XX:+HeapDumpOnOutOfMemoryError \   # OOM 时自动 dump，事后分析
  -XX:HeapDumpPath=/logs/heap.hprof
容器里最常见的坑：JVM 默认按宿主机内存算堆，而不是按容器 cgroup 限制。Java 10 起支持 -XX:+UseContainerSupport（JDK 17 默认开）会读容器限制，但仍建议显式 -Xmx，否则多个容器挤在一台宿主机上一起 OOM。

5实战项目经验（实战落地）

1 项目背景

一句话定位：数据可视化大屏项目（智能监控大屏 智能监控，Java + 前端）需要后端在短时间内聚合多个采集源的数据，供大屏高频刷新。

  • 业务量级：一屏要汇总多个监控点位/设备的实时指标，后端要并行拉取再合并（估算并发：数十路采集源）。
  • 痛点：串行逐个查采集源，一屏数据要等所有源依次返回，刷新延迟高。

2 我的角色与职责

  • 分工：负责大屏数据聚合后端接口，设计并行拉取与结果合并；前端由他人开发大屏图表。

3 技术栈

  • 组合：Java + 线程池 + 并发容器；JVM 部署在应用服务器，用 G1/默认垃圾回收。

4 落地设计

  • 并行拉取：用固定大小线程池并发调用各采集源，CountDownLatch 或 CompletableFuture 等齐后合并。
  • 结果收集：多线程写结果用线程安全容器，避免 HashMap 并发丢数据。

5 关键实现要点

ExecutorService pool = Executors.newFixedThreadPool(8);
List<CompletableFuture<Metric>> fs = sources.stream()
    .map(s -> CompletableFuture.supplyAsync(() -> fetch(s), pool))
    .toList();
Map<String, Metric> merged = fs.stream()
    .map(CompletableFuture::join)
    .collect(Collectors.toConcurrentMap(Metric::getSource, m -> m));
// 任一采集源超时不能拖垮整屏：给 supplyAsync 加超时兜底

6 真实问题与解法

  • 坑线程池无界 OOM：用 newCachedThreadPool 在高峰期线程暴涨——改用有界队列 + 拒绝策略。
  • 坑一个采集源卡住拖垮整屏：并行拉取没设超时，某个源慢导致整屏等待——给每个 future 加超时降级（取不到用上次缓存）。
  • 要点JVM Full GC 卡顿：大屏接口高峰期偶发停顿，调大堆、用 G1 降低单次停顿。

7 量化成果

  • 聚合接口从串行的约 3 秒降到并行的约 800ms（估算，随采集源数量变化），大屏高频刷新不再明显卡顿。

8 协作与排期过程

  • 与前端约定"超时降级返回上一帧缓存"，避免大屏空白闪烁；联调时固定一个模拟慢采集源压测。

9 复盘与可复用经验

  • 并行必配超时：任何外部调用并行化都要带超时与降级。
  • 线程池要定型：核心/最大线程、队列、拒绝策略显式配，不依赖默认。

10 面试讲法

"大屏多源聚合实践中常采用线程池 + CompletableFuture 并行拉取并加超时降级，接口从约 3 秒降到约 800ms；踩过无界线程池和单源超时拖垮整屏的坑。"

6易错点与面试重点

6.1 用 Executors 快捷工厂导致 OOM

一句话定位：Executors.newFixedThreadPool 用无界队列，压测时任务无限堆积直至 OOM。

  • 现象：用 newFixedThreadPool 或 newSingleThreadExecutor，压测时队列无限增长直至 OOM。
  • 原因：内部用无界 LinkedBlockingQueue，生产快于消费时队列无上限堆积。
  • 正解：手动 new ThreadPoolExecutor + 有界队列 + 明确拒绝策略。

6.2 synchronized 与 volatile 的边界

一句话定位：volatile 只保证可见性与禁重排，挡不住 i++ 这种复合操作。

  • 误区：以为 volatile 能保证 i++ 原子性。
  • 真相：i++ 是"读-改-写"三步复合操作，volatile 挡不住并发写丢失。
  • 正解：复合操作用 synchronized/ReentrantLock 或 AtomicInteger/LongAdder；volatile 只适合"一写多读"的状态标志位。

6.3 死锁的四条件与排查

一句话定位：两线程互持对方要的锁双双卡住、CPU 却不高——jstack 一眼定位。

  • 四条件：互斥、持有并等待、不可剥夺、循环等待。
  • 排查：jstack 抓线程 dump，找 Found one Java-level deadlock。
  • 正解：所有线程按相同顺序加锁、用 tryLock(timeout) 替代无限等待。

6.4 Full GC 频繁与 STW 停顿

一句话定位：接口偶尔毛刺几秒、GC 日志频繁 Full GC，多半是老年代被意外填满。

  • 现象：接口偶尔毛刺几秒，GC 日志里频繁 Full GC。
  • 原因：老年代被意外填满（大对象、短命对象提前晋升、内存泄漏），触发整堆回收。
  • 正解：-XX:+HeapDumpOnOutOfMemoryError 或 jstat 看 GC 频率与各代占用，定位是泄漏还是分配过快。

6.5 线程池线程名不规范，dump 看不懂

一句话定位：jstack 全是 pool-1-thread-3 分不清哪个池——建池时就要命名。

  • 现象：线上 jstack 全是默认线程名，分不清哪个业务池。
  • 正解：建池时用 ThreadFactoryBuilder().setNameFormat("agg-worker-%d") 命名——小事，但出问题时省的是排查时间。
