RESTful API 设计

标准 定位：用"资源 + HTTP 方法"统一接口语义，前后端约定的通用语言

一个写得好的 API，新人看 URL 和方法就知道干什么；写得烂的 API，每个接口都是一个动词路径、全返回 200 加 body 里的 code。本页讲清 REST 的资源视角、HTTP 方法与状态码的正确用法、版本/分页/错误结构的统一约定，并用 业务系统/数据编排平台的真实规范落地，最后对比 REST 与 RPC 的取舍。

1技术点概览

一句话定位：REST 把一切操作对象抽象成资源——URL 定位资源、HTTP 方法表达动作、状态码表达结果，JSON 是事实标准。

  • 它解决什么：不按 REST 时接口是"一堆动词路径"（/createUser、/getUserById、/updateUser、/deleteUser），命名全凭习惯、靠文档逐个对。
  • 核心收益：统一约定（名词 URL + 方法 + 状态码）让接口自解释，新接口无需额外解释即可被理解。

横向对比：REST 风格 vs RPC 风格的接口

维度REST 风格RPC 风格
URL 形态资源名词：/users、/users/1动作动词：/getUser、/createOrder
语义表达靠 HTTP 方法（GET/POST/PUT/DELETE）靠路径里的方法名
状态表达HTTP 状态码（404/409…）多在 body 里放自定义 code
适用资源型 CRUD、开放 API、前后端分离复杂业务动作、内部高性能调用（gRPC）

2核心概念

2.1 资源与名词 URL

一句话定位：URL 是名词复数表资源集合，动作交给 HTTP 方法，不要在 URL 里写动词。

  • 集合与单项：/requirements（列表）、/requirements/12（id=12）。
  • 子资源表归属：/requirements/12/comments（该需求的评论）。

2.2 HTTP 方法即语义

一句话定位：方法选对了，接口语义就清晰——GET 只读、POST 建、PUT 全量改、DELETE 删。

  • 幂等性：GET/PUT/DELETE 幂等，POST 非幂等（重复提交会建多条）；注意 PATCH 是局部增量更新、不保证幂等（如自增计数类 patch，多次调用结果不同）。
  • PATCH：局部更新（区别于 PUT 全量替换）。

2.3 状态码

一句话定位：用 HTTP 状态码表达结果，而不是一律 200 再在 body 里塞 code。

  • 成功类：200 成功、201 已创建、204 无内容（DELETE 成功）。
  • 客户端错：400 参数错、401 未认证、403 无权限、404 不存在、405 方法不允许、409 冲突（如重复创建）、415 不支持的媒体类型、422 语义校验失败、429 请求过多。注：字段级参数校验业界惯例直接用 400 承载，严格语义上 422 Unprocessable Entity 更贴切。
  • 用途：给网关、监控、客户端做通用判断（如 401 统一跳登录）。

2.4 版本、分页、过滤

一句话定位：统一约定比每个接口自定义更重要——版本、分页、过滤都要全项目一套。

  • 版本：/api/v1/... 前缀，破坏性升级到 v2。
  • 分页：统一 ?page=1&size=20（或 pageNum/pageSize，全项目只选一种）。
  • 过滤排序：query 参数 ?status=OPEN&sort=-createTime。

2.5 统一错误结构

一句话定位：body 里仍要有结构化错误（错误码+可读消息+字段级错误），与状态码互补。

  • 业界做法：状态码表 HTTP 层成败，body 带业务码与消息——REST 与统一 body 包装不冲突。

3工作原理与流程

3.1 一个 REST 请求的处理链路

一句话定位：REST 不是特殊框架，而是一套约定——链路与普通 Spring MVC 完全一致。

链路：网关/Nginx → DispatcherServlet → 按 URL + 方法路由到 Controller → Service 处理 → 返回 JSON 与状态码。约定只体现在三处：URL 怎么起名、用哪个方法、返回什么状态码与错误结构。下图是"创建一个需求"这个动作从请求到标准响应的完整约定。

  1. 请求：POST /api/v1/requirements，body 是需求字段 JSON。
  2. 校验：参数不合法 → 直接返回 400 + 字段错误。
  3. 处理：成功创建 → 返回 201 Created，body 带回新资源 id。
  4. 异常：重复创建冲突 → 409；未登录 → 401。
关键在于：客户端不需要读文档里的"业务码对照表"，看 HTTP 状态码就能对成功/未授权/不存在/冲突做出通用处理（如 401 统一跳登录）。这就是 REST 的工程价值。

4核心语法与 API 要点

4.1 一套资源 CRUD 的标准写法

# 集合
GET    /api/v1/requirements?status=OPEN&page=1&size=20
       # 列表（过滤+分页）
POST   /api/v1/requirements   # 新建 → 201
# 单个资源
GET    /api/v1/requirements/12   # 详情 → 200
PUT    /api/v1/requirements/12   # 全量更新 → 200
PATCH  /api/v1/requirements/12  # 局部更新 → 200
DELETE /api/v1/requirements/12  # 删除 → 204

4.2 统一响应与错误结构

// 成功（200）
{
  "code": 0,
  "message": "ok",
  "data": { "id": 12, "title": "登录页改版" }
}

// 失败（HTTP 400，body 带可读错误）
{
  "code": 40001,
  "message": "参数校验失败",
  "errors": [ { "field": "title", "msg": "标题不能为空" } ]
}
@RestController
@RequestMapping("/api/v1/requirements")
public class RequirementController {

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)  // 201，不是默认 200
    public Result<Long> create(
            @Valid @RequestBody ReqCreateDTO dto) {
        return Result.ok(requirementService.create(dto));
    }
}

4.3 动作类接口怎么办

有些动作对不上标准 CRUD（如"提交审批""关闭需求"），不要硬塞进 PUT。可以在子资源下放动作：POST /api/v1/requirements/12/submit——用 POST 表达"对该资源执行 submit 动作"，这是 REST 实践中可接受的折中。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 与数据编排平台后端对外都走 REST 风格 HTTP 接口，资源命名、状态码、分页、错误结构需要统一约定。

  • 业务量级：需求/团队/配置等资源的增删改查，前端与大屏都在调。

2 我的角色与职责

  • 分工：参与制定接口规范，落地资源命名、统一响应包装与错误结构。

3 技术栈

  • 组合：SpringBoot REST + 统一 Result 包装 + OpenAPI 文档。

4 落地设计

  • 资源用名词：/api/requirements，操作用 HTTP 动词，不用 /listReq。
  • 统一响应：所有接口包 {code, message, data}，分页返回 {list, total}。
  • 错误结构：业务错误返回约定 code + message，不抛栈。

5 关键实现要点

GET    /api/requirements?page=1&size=20&status=REVIEW
POST   /api/requirements
GET    /api/requirements/123
PUT    /api/requirements/123
PATCH  /api/requirements/123/status     # 状态流转用 PATCH
DELETE /api/requirements/123
{ "code": 0, "message": "ok",
  "data": { "list": [ ... ], "total": 138 } }

6 真实问题与解法

  • 坑动作型接口硬凑 REST："审批通过"不是资源 CRUD——用 PATCH 子资源 /status 或受控动作路径，别发明 /api/passReq。
  • 坑分页参数不统一：有的 pageNo/pageSize、有的 page/size——全局统一一套。

7 量化成果

  • 接口风格统一后，前端按约定即可猜出路径，新资源接口文档阅读成本下降（估算）。

8 协作与排期过程

  • 与前端约定分页参数与错误码字典，配合 OpenAPI 生成客户端，风格不一致的接口在评审时纠正。

9 复盘与可复用经验

  • 名词 + 动词：资源名词，动作用 HTTP method。
  • 统一包装：分页与错误结构全项目一套。

10 面试讲法

"业务系统 在实践中落地 REST 规范：资源用名词、状态流转用 PATCH、统一 Result 与分页结构，和 OpenAPI 生成客户端配合，前后端对接口不再靠口头约定。"

6易错点与面试重点

6.1 URL 里塞动词

一句话定位：/api/getUserList、/api/deleteReqById——URL 用名词资源，动作用 HTTP 方法表达。

  • 正解：URL 用名词资源，动作交给 HTTP 方法。

6.2 全部返回 200

一句话定位：找不到也返回 200 靠 body.code 判断——网关、监控、前端拦截器无法按状态码做通用处理。

  • 正解：该 404 就 404、该 400 就 400，body 再带业务码与消息。

6.3 GET 用于修改数据

一句话定位：GET 会被浏览器/缓存/爬虫自动触发，用它改数据可能被意外执行。

  • 正解：任何有副作用的操作用 POST/PUT/DELETE，GET 严格只读。

6.4 分页/错误结构不统一

一句话定位：每个 Controller 自己定分页参数和错误格式，前端要写多套适配。

  • 正解：全局统一分页参数、统一 Result 包装与错误结构（可由全局异常处理器兜底）。

6.5 盲目追求"纯 REST"

一句话定位：复杂业务动作硬套 CRUD 很别扭——资源型用 REST，复杂动作用折中，不必为 REST 而 REST。

  • 正解：资源型 CRUD 用 REST；复杂动作用 POST /资源/{id}/动作；内部高性能调用可直接上 gRPC（RPC）。
