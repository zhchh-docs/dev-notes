Monaco 与 CodeMirror 编辑器

深入 定位：嵌入式代码编辑器——VS Code 内核 vs 轻量可扩展

Monaco Editor 是 VS Code 的内核（开源部分），提供语法高亮、智能补全、Diff 编辑器，能力强但体积大；CodeMirror 是轻量可嵌入的代码编辑器，灵活、体积小，适合组件配置/轻量脚本编辑。数据编排平台用 Monaco 承载 SQL/脚本编辑，低代码平台用 CodeMirror 做组件配置与自定义编辑。本页对比两者架构、补全与 Diff，并给出选型与落地。

1简介与阅读指引

1.1 定位

本篇讲的是让网页里的"写代码"体验接近 IDE 的两个编辑器：Monaco（VS Code 浏览器版内核——高亮/补全/错误标记/DiffEditor 全，重）与 CodeMirror 6（轻量可扩展嵌入式编辑器——extension 组合能力，轻）。本篇的核心命题是选型与集成：什么场景用哪个、Monaco 的 worker 怎么配、两个编辑器各自的"必知坑"。

1.2 痛点

  • 普通 textarea 写 SQL/脚本：没有高亮、补全、行号、缩进——可用性差；
  • Monaco 引入后高亮失效/控制台报 worker 加载失败——worker 配置是集成第一关；
  • 轻量的表达式输入框也上 Monaco——包体积白白多几 MB。

1.3 选型：Monaco vs CodeMirror

维度MonacoCodeMirror
能力高亮/补全/Diff/错误标记全高亮为主，补全需扩展自接
体积大（含 web worker）小，按需扩展
Diff内置 DiffEditor需配合第三方 Diff 视图
取舍重度脚本/SQL 编辑轻量配置/表达式输入

判断口诀：重脚本（SQL/转换脚本/大 JSON）选 Monaco——要的是完整 IDE 体验；轻配置（表达式/小片段）选 CodeMirror——要的是体积与定制自由。同一项目两者并存很正常（按编辑场景分工）。

1.4 学习目标与阅读指引

  1. 为项目做出正确的编辑器选型，并说出理由；
  2. 完成 Monaco 的 Vite worker 配置（MonacoEnvironment），让高亮补全真正工作；
  3. 用 registerCompletionItemProvider 接入业务词表补全（字段名/变量名）；
  4. 守住两个生命周期纪律：dispose 成对、大文档 applyEdits 增量。

前置知识：Web Worker 概念（10 模块）；Vite 构建。难度：★★★☆☆（API 简单，worker 与工程化配置是难点）。务必动手：第 6 章 Demo——worker 不亲手配一遍，坑记不住。

2核心模型

Monaco 侧四个核心模型（Model/语言/补全/Worker），CodeMirror 侧一个（extension 体系）。

2.1 Model：内容与编辑器分离

Monaco 把文本内容放在 Model 里（文本 + 语言 + uri），编辑器只是 Model 的视图——多个编辑器可共享同一 model（如同时打开的编辑与 diff 视图）。基本操作：monaco.editor.create(dom, options) 创建；setValue/getValue 读写；onDidChangeModelContent 监听变化（接自动保存/校验）。

2.2 语言与主题：内置 + 自定义

Monaco 内置主流语言（SQL/JS/JSON/HTML…）的高亮与基础语言服务；自定义语言用 Monarch 定义 token 规则（正则式的词法描述）。主题：monaco.editor.defineTheme('my-dark', {...}) 定义品牌主题，theme 选项启用。CodeMirror 对应物是 language package 与 theme extension。

2.3 补全 Provider：业务词表的注入点

monaco.languages.registerCompletionItemProvider('sql', {...})——配置编辑器的补全本质是接业务数据：字段名、变量名、函数名从接口/上下文取，在 provideCompletionItems 里返回 suggestions。这是配置型编辑器的灵魂能力：用户不用背字段，光标处 Ctrl+Space 弹业务词表。

2.4 Worker：语言服务在后台线程

Monaco 的校验、部分补全、tokenize 放在 web worker 里跑（不卡主线程）——这也是它"重"的原因。Vite 集成两步：①worker 文件引入（?worker&inline 或 vite-plugin-monaco-editor）；②设置 self.MonacoEnvironment = { getWorker(_, label) {...} } 按语言 label 返回对应 worker——漏了第二步运行时照样报 worker 加载失败（坑 1）。

2.5 CodeMirror 6 的 extension 体系

CodeMirror 6 的一切能力都是 extension：语言（@codemirror/lang-javascript）、主题、自动补全、lint……new EditorView({ extensions: [basicSetup, javascript(), myTheme], parent: el }) 组合挂载。轻且可裁——只用到的进产物，与 Monaco 的"全家桶 + worker"形成鲜明对照。

3核心用法（按场景）

3.1 场景一：Monaco 最小嵌入（SQL 编辑器）

import * as monaco from 'monaco-editor';
const editor = monaco.editor.create(el, {
  value: 'SELECT * FROM t',
  language: 'sql',
  theme: 'vs-dark',
  automaticLayout: true,          // 容器尺寸变化自适应（坑 3）
  minimap: { enabled: false }
});
editor.onDidChangeModelContent(() => save(editor.getValue()));

3.2 场景二：CodeMirror 轻量嵌入（表达式输入）

import { EditorView, basicSetup } from 'codemirror';
import { javascript } from '@codemirror/lang-javascript';
new EditorView({
  extensions: [basicSetup, javascript()],
  parent: el
});

3.3 场景三：业务词表补全（配置编辑器的灵魂）

monaco.languages.registerCompletionItemProvider('sql', {
  provideCompletionItems: (model, position) => ({
    suggestions: tableFields.map(f => ({
      label: f,
      kind: monaco.languages.CompletionItemKind.Field,
      insertText: f
    }))
  })
});

进阶：词表按光标上下文动态给（如表别名后的字段）——在 provider 里解析 model 已有文本判断上下文，返回过滤后的建议。

3.4 场景四：Diff 编辑器（版本对比）

const diff = monaco.editor.createDiffEditor(el);
diff.setModel({
  original: monaco.editor.createModel(oldText, 'json'),
  modified: monaco.editor.createModel(newText, 'json')
});

与 v-code-diff 的分工（衔接本模块 10 篇）：只读展示用 v-code-diff（轻）；要可编辑的对比合并（解决冲突）用 Monaco DiffEditor（重）。

4进阶知识点【进阶】

首次学习可整章跳过。前置：Monaco 已跑通（worker 配好）。

4.1 Vite 集成 Monaco 的完整配方

// main.js：worker 环境（两步缺一不可）
import editorWorker from 'monaco-editor/esm/vs/editor/editor.worker?worker&inline'
import jsonWorker from 'monaco-editor/esm/vs/language/json/json.worker?worker&inline'
import cssWorker from 'monaco-editor/esm/vs/language/css/css.worker?worker&inline'
import htmlWorker from 'monaco-editor/esm/vs/language/html/html.worker?worker&inline'
import tsWorker from 'monaco-editor/esm/vs/language/typescript/ts.worker?worker&inline'
self.MonacoEnvironment = {
  getWorker(_, label) {
    if (label === 'json') return new jsonWorker()
    if (label === 'css' || label === 'scss' || label === 'less') return new cssWorker()
    if (label === 'html') return new htmlWorker()
    if (label === 'typescript' || label === 'javascript') return new tsWorker()
    return new editorWorker()
  }
}

体积优化：默认引入全语言——按需 monaco-editor/esm/vs/... 只引需要的语言特性；worker 同理只配用到的。

4.2 大文档的性能纪律：增量编辑

外部变更同步到编辑器时，setValue(全文) 会重置光标与撤销栈、大文档卡顿——用 model.applyEdits() 按变更区间增量替换（配合 onDidChangeModelContent 的 change 事件做双向同步）。双向同步的经典架构：外部状态 → applyEdits；编辑器 → change 事件回写——注意防循环（同步标志位）。

4.3 生命周期纪律：dispose 与多实例

组件卸载必须 editor.dispose()（同时 dispose 自建 model）；弹窗/Tab 复用场景尤其容易漏——每开一次泄漏一个实例。批量创建（列表页 N 个小编辑器）要评估：多个 Monaco 实例共享 worker 但各有渲染成本——超过 3~5 个就考虑 CodeMirror 或懒创建（滚动到可视区再 init）。

4.4 自定义语言的 Monarch 入门

业务 DSL（规则表达式、模板语法）高亮：monaco.languages.register({ id: 'mydsl' }) + monaco.languages.setMonarchTokensProvider('mydsl', { tokenizer: {...} })——正则定义关键字/字符串/注释的 token 规则即可获得高亮；配合 completion provider + 校验 worker 可做成完整的"业务脚本 IDE"。CodeMirror 侧对应 Lezer 语法包（门槛更高但类型安全）。

6最小可运行 Demo

一个"SQL 编辑器"组件（Vue3 封装）：worker 配置 + 业务词表补全 + 自动保存 + dispose。

6.1 组件代码

<template><div ref="el" style="height:400px"></div></template>

<script setup lang="ts">
import { ref, onMounted, onUnmounted } from 'vue'
import * as monaco from 'monaco-editor'
import { getTableFields } from '@/api'

const el = ref<HTMLElement>()
let editor: monaco.editor.IStandaloneCodeEditor | null = null

onMounted(async () => {
  editor = monaco.editor.create(el.value!, {
    value: 'SELECT * FROM orders',
    language: 'sql',
    theme: 'vs-dark',
    automaticLayout: true,
    minimap: { enabled: false },
  })

  // 业务词表补全：字段名从后端取
  const fields = await getTableFields('orders')
  monaco.languages.registerCompletionItemProvider('sql', {
    provideCompletionItems: () => ({
      suggestions: fields.map(f => ({
        label: f.name,
        kind: monaco.languages.CompletionItemKind.Field,
        detail: f.comment,
        insertText: f.name,
      })),
    }),
  })

  // 变化自动保存（防抖）
  let t: any
  editor.onDidChangeModelContent(() => {
    clearTimeout(t)
    t = setTimeout(() => save(editor!.getValue()), 800)
  })
})

onUnmounted(() => editor?.dispose())    // ⭐ 生命周期纪律
</script>

6.2 逐段解析

  • automaticLayout: true：容器随弹窗/分栏变化自适应（省掉手动 layout）；
  • 补全接业务数据：字段名+注释来自后端——用户不用背 schema；
  • 自动保存走防抖：onDidChangeModelContent 高频触发，直接发请求是事故；
  • onUnmounted dispose：弹窗反复开关也不泄漏（worker 配置在应用入口做一次，见 4.1）。

6.3 生产改造扩展方向

  1. 接入 SQL 语法校验（后端 explain 或 sqlparser，错误标到行上 marker API）；
  2. 只读对比场景挂 DiffEditor（3.4）；
  3. 按需引入裁体积（4.1），产物做 bundle 分析。

7常见坑 & Debug

五条高频坑，每条五要素。

7.1 坑 1：Monaco worker 未配置

  • 现象：控制台报 worker 加载失败，高亮/校验/补全静默失效；
  • 根因：Vite/打包器没配 worker 入口，或只做了第一步（引入 worker）没做第二步（MonacoEnvironment.getWorker）；
  • 复现：删掉 MonacoEnvironment 配置重启；
  • 修复：按 4.1 完整配方两步都做；
  • 规避：Monaco 集成 checklist 第一项就是 worker——新项目先跑通 worker 再写业务。

7.2 坑 2：忘记 dispose 导致内存泄漏

  • 现象：弹窗反复开关后页面越来越卡；
  • 根因：编辑器实例持有 DOM 与 worker 通信通道，不 dispose 不释放；
  • 复现：Memory 面板对比开关前后快照；
  • 修复：卸载钩子里 editor.dispose()（自建 model 一并 dispose）；
  • 规避：封装组件内建生命周期（6.1 形态），业务层不裸调 create。

7.3 坑 3：容器尺寸变化不自适应

  • 现象：窗口/分栏拖动后编辑器出现滚动条或留白；
  • 根因：Monaco 不自动感知容器尺寸；
  • 修复：automaticLayout: true，或手动监听 ResizeObserver 调 editor.layout()；
  • 规避：封装组件默认开 automaticLayout。

7.4 坑 4：大文档全量 setValue 卡顿

  • 现象：同步外部变更时编辑器卡顿、光标丢失、撤销栈清空；
  • 根因：setValue 全量重建内容；
  • 修复：model.applyEdits() 按变更区间增量替换（4.2）；
  • 规避：外部→编辑器的同步一律增量，setValue 只用于首次初始化。

7.5 坑 5：轻量输入用了 Monaco（选型过重）

  • 现象：页面有 10 个表达式输入框，全上 Monaco——首屏多几 MB、初始化慢；
  • 根因：没有按编辑场景分层选型；
  • 修复：重脚本（少而精）用 Monaco，轻配置（多而碎）用 CodeMirror 或富文本化的输入；
  • 规避：选型口诀（1.3）——按"数量 × 深度"定编辑器，评审时对照。

8重点讲解

Q1：Monaco 和 CodeMirror 怎么选？两者并存冲突吗？

参考答案：按"编辑深度 × 实例数量"选——重度编辑（SQL/脚本/大 JSON，需要补全校验 Diff，实例少）选 Monaco；轻量嵌入（表达式/配置片段，实例多）选 CodeMirror（体积小、多实例成本低）。并存不冲突：同一项目按场景分工是常态——数据平台的脚本编辑用 Monaco、组件配置里的表达式用 CodeMirror。判断时再算两笔账：体积账（Monaco 几 MB + worker）与体验账（DiffEditor/错误标记是硬需求吗）。

Q2：Monaco 为什么大？它的架构怎么支撑大文档？

参考答案：重的来源：完整语言服务体系 + 多语言 worker（每个语言的校验/tokenize 在独立 web worker）。架构三件：渲染层（虚拟滚动，大文档只渲染可视行）、Model 层（文本+语言+uri，与视图分离、可共享、增量变更事件）、语言服务 worker（不阻塞主线程）。

追问：worker 配置失败的后果？——编辑器基本能打字，但校验、部分补全静默失效——这也是为什么 worker 配置必须作为集成 checklist 第一项，并用行为验证（造一个语法错误看有没有红线）而非只看 console。

Q3：配置编辑器的"补全字段名"怎么实现？

参考答案：registerCompletionItemProvider 注册语言级 provider，provideCompletionItems 返回 suggestions（label/kind/insertText/detail）。工程要点：①词表来自业务数据（接口/上下文），不是静态写死；②按光标上下文过滤（如表别名后只给该表字段）；③detail 给注释提升可用性；④词表变化时 provider 需重新注册或用可变引用。

本质：编辑器能力 + 业务数据 = 配置体验——补全 provider 就是两者的注入点。
