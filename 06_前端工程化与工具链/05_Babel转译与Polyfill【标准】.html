Babel 转译与 Polyfill

标准 定位：语法转译与 API 补齐——新代码跑进老浏览器的两条正交链路

Babel 管语法转译（箭头函数/可选链 → ES5），Polyfill 管 API 补齐（Promise/Array.includes 的运行时实现）——两者正交：转译解决"老引擎看不懂的写法"，polyfill 解决"老引擎没有的方法"，只配一个就漏一半。核心配置是 @babel/preset-env + browserslist：按目标浏览器按需转译与注入，避免全量 polyfill 体积爆炸。

1简介与阅读指引

1.1 定位：两条正交链路

转译（transpile）：Babel 把新语法（箭头函数/解构/可选链）改写成等价旧语法——纯代码文本变换；Polyfill（垫片）：用 JS 实现缺失的运行时 API（Promise/Map/Array.prototype.includes）挂到全局——代码不变、方法有了。两件事独立发生：箭头函数转译掉了，Promise 还是 undefined——只配转译不配 polyfill 是最经典的配置漏洞。

1.2 横向对比：Babel vs esbuild（Vite 时代）

维度Babelesbuild（Vite 默认）
实现JS 编写，插件生态最大Go 编写，快 10-100 倍
转译完整（插件可自定义 AST 变换）覆盖主流语法，无自定义插件
Polyfillpreset-env 按需注入不做（配 @vitejs/plugin-legacy 走 Babel）
JSX/TS全支持支持（仅转译不做类型检查）
适用老 Vue CLI/Webpack 项目、需要自定义 AST 变换新项目 dev 转译与压缩

本套技术栈：老项目（数据编排/低代码）Vue CLI 内置 Babel；新项目 Vite 用 esbuild，仅 plugin-legacy 场景才回头用 Babel。

1.3 学习目标与阅读指引（诚实声明）

  1. 建立"转译 vs polyfill 正交"的核心心智；
  2. 看懂 preset-env + browserslist + useBuiltIns 三件套配置；
  3. 理解 transform-runtime vs 全局 polyfill 的取舍；
  4. 会排查"老浏览器白屏"的兼容性故障链。

诚实声明：Babel 配置在生产项目由脚手架（Vue CLI）生成，本篇是配置级理解与故障排查视角（知道每个配置在干什么、出问题去哪查），非手写插件层面。前置知识：04 篇 Webpack。难度：★★★☆☆。

2核心模型

五个核心模型：三步管线→ preset-env→ browserslist→ Polyfill 注入策略→ transform-runtime。

2.1 三步管线：parse → transform → generate

parse（@babel/parser）把源码解析成 AST → transform（插件/预设遍历 AST 改写节点，箭头函数节点换成普通函数）→ generate（@babel/generator）输出代码+sourcemap。本质：与 ESLint 同构——都在 AST 上做变换，只是 ESLint 只读检查、Babel 改写。

2.2 preset-env：一个预设替代几十个插件

每个 ES 新语法对应一个 plugin（transform-arrow-functions/…），手排必漏；@babel/preset-env 按 browserslist 目标自动启用需要的插件——目标越新，转译越少、产物越接近源码、体积越小。

2.3 browserslist：一份声明，全工具链共享

package.json 或 .browserslistrc 声明目标浏览器（如 defaults, not dead, Chrome >= 80）——Babel/Autoprefixer/eslint-plugin-compat/postcss 共享同一份。纪律：改兼容范围只改这里一处；不配则 preset-env 走默认全量（体积爆炸的根源）。

2.4 Polyfill 注入策略：useBuiltIns

  • false：不注入 polyfill（目标浏览器很新时）；
  • entry：入口手动 import core-js，按 browserslist 整体替换——注入全量目标所需；
  • usage：按代码实际用到的 API 逐文件注入——最小体积，默认首选。

polyfill 源是 core-js@3 + regenerator-runtime（async/await 的运行时）。

2.5 transform-runtime：库作者的另一种姿势

把 polyfill 从"改全局对象"改为"从 @babel/runtime 按需 import 辅助函数"——不污染全局（库/SDK 场景必须，改全局会与宿主冲突）、辅助函数去重。业务应用可全局注入（usage 更简单）；npm 库必须 runtime。

3核心用法（按场景）

3.1 场景一：标准 babel.config.js（业务应用）

module.exports = {
  presets: [
    ['@babel/preset-env', {
      targets: '> 0.5%, last 2 versions, not dead',  // 也可由 browserslist 文件统一管
      useBuiltIns: 'usage',        // 按代码用到的 API 注入 core-js@3
      corejs: 3,                   // 声明 core-js 大版本（决定注入来源）
      modules: false               // 交给 Webpack 处理 import（保留 ESM 才能摇树）
    }]
  ]
};

modules: false 是隐形必配：preset-env 默认把 ESM 转成 CommonJS，Webpack 的 tree-shaking 只认 ESM——不关就摇不掉。

3.2 场景二：browserslist 声明（package.json）

{
  "browserslist": [
    "Chrome >= 80",
    "Firefox ESR",
    "last 2 Safari versions",
    "not dead"
  ]
}

验证生效：npx browserslist 列出解析后的目标清单；npx browserslist --coverage 看全球覆盖率。

3.3 场景三：npm 库的 runtime 模式

module.exports = {
  presets: [['@babel/preset-env', { targets: { node: 'current' } }]],
  plugins: [
    ['@babel/plugin-transform-runtime', {
      corejs: 3,             // polyfill 改为从 @babel/runtime-corejs3 import
      helpers: true,         // 辅助函数复用 _classCallCheck 等，不每文件内联
      regenerator: true
    }]
  ]
};

库不用 useBuiltIns：它改全局对象，装进宿主会覆盖宿主的 Promise 版本——事故级冲突。

3.4 场景四：排查"老浏览器白屏"

# 1. 找出产物里残留的新语法（转译漏网）
npx esbuild dist/js/*.js --target=es5 --bundle=false 2>&1 | head
# 2. 定位是哪个依赖发的未转译代码：console 报错的模块名 + source map
# 3. 修复：把该依赖加进转译范围（见 7.3）或升级依赖版本

4进阶知识点【进阶】

首次学习可整章跳过。前置：三件套配置已会用。

4.1 依赖未转译问题（被 exclude 的坑）

babel-loader 惯例 exclude: /node_modules/（提速）——但npm 包发布的就是 ES6+ 源码时，它不经过转译直接进产物，老浏览器崩。解法：①include 白名单把发 ES6 的依赖纳入转译；②要求依赖提供 ES5 产物（main/module 双入口）；③Monorepo 内部包天然参与转译（workspace 源码）。

4.2 插件与预设的执行顺序

plugins 先于 presets 执行；plugins 按声明顺序正序，presets 按声明顺序倒序（后声明的先跑）。排查转译顺序问题时用得上——多数业务场景只需记住"preset-env 里 modules:false 交 Webpack"。

4.3 babel-loader 缓存

转译是大头开销：loader: 'babel-loader', options: { cacheDirectory: true }——按文件内容+配置 hash 缓存转译结果，二次构建大幅提速（与 04 篇 filesystem cache 配合）。

4.4 Vite 时代的兼容方案

Vite dev 用 esbuild（不插 polyfill，假定现代浏览器）；build 目标 build.target: 'es2015' 由 esbuild 转译；需要兼容老浏览器时上 @vitejs/plugin-legacy——自动生成双份产物（现代版+SystemJS legacy 版）并用 browserslist 决定 legacy 范围——本质是"把 Babel 再请回来"。

4.5 只转译不检查的边界

esbuild/Babel 转译 TS 时只删类型不做类型检查——类型安全靠 IDE+tsc --noEmit/CI 单独跑；理解这个边界才不会以为"构建过了=类型没错"。

6最小可运行 Demo

性质（诚实声明）：配置验证性 demo——本地跑通 preset-env 三件套并验证 polyfill 注入行为；生产配置由 Vue CLI 脚手架生成，本 demo 目的是"知道每行配置在干什么"。

6.1 落地步骤

  1. npm i -D @babel/core @babel/cli @babel/preset-env core-js@3，写 3.1 配置；
  2. 写一段含 ?. 可选链 + Promise.allSettled + Array.flat 的源码；
  3. 先配 targets: chrome 90 转译：产物几乎原样（目标新，不转译不注入）；
  4. 改 targets: ie 11 再转译：观察可选链被改写、文件头多出 core-js import（usage 注入）；
  5. 删掉 useBuiltIns 再转 ie11：语法转了但 allSettled 无人垫——用图 1 定性这次"漏一半"。

6.2 验证清单

  1. 产物中 grep "allSettled"：usage 模式下应出现 core-js 的 import 引入；
  2. modules:false 时产物保留 import 语句（Webpack 可摇树）；
  3. cacheDirectory 开启后二次转译耗时明显下降。

6.3 复盘经验

  • 排查口诀：老浏览器白屏 → 先定性"语法 or API"（图 1）→ 再查 browserslist 是否覆盖该浏览器 → 最后查 node_modules 依赖是否漏转译（4.1）；
  • 经验：三件套（browserslist/preset-env/useBuiltIns）一个都不能少，理解比背配置重要。

7常见坑 & Debug

五条高频坑。

7.1 只配转译不配 polyfill（漏一半）

现象：老浏览器报 "Promise is not defined"。 原因：转译与 polyfill 正交，preset-env 只转语法。正解：useBuiltIns:'usage' + corejs:3。

7.2 不配 browserslist 全量注入

现象：产物莫名多几百 KB polyfill。原因：preset-env 默认按最保守目标全量转译+垫。正解：显式声明 browserslist（图 2 单一事实源）。

7.3 node_modules 依赖漏转译

现象：本地现代浏览器全好，某老环境白屏，报错指向某个依赖。原因：babel-loader exclude 了 node_modules，而该包发布的是 ES6+。正解：include 白名单纳入该依赖，或要求依赖提供 ES5 产物。

7.4 库项目用 useBuiltIns 污染全局

风险：npm 库全局垫片覆盖宿主版本，宿主行为突变。正解：库用 transform-runtime（按需 import，不改全局）。

7.5 modules 转译毁掉 tree-shaking

现象：产物里塞满没用到的导出。原因：preset-env 默认 ESM→CommonJS，Webpack 摇不掉。正解：modules: false 交 Webpack 处理模块。

8重点讲解

Q1：转译和 Polyfill 的区别？为什么说两者正交？

参考答案：转译是代码文本变换——Babel parse 成 AST、插件改写节点、generate 输出，解决"老引擎看不懂的语法"（箭头函数/可选链）；Polyfill 是运行时补齐——core-js 把缺失API（Promise/allSettled）的实现挂到全局，代码写法不变。正交：两件事独立发生，转译不产生缺失的方法，polyfill 不改变写法——只配转译时 Promise 在 IE 依然是 undefined。排查老浏览器白屏第一步就是定性"语法 or API"。

Q2：preset-env + browserslist + useBuiltIns 三件套怎么协作？

参考答案：browserslist 是目标浏览器的唯一事实源（Babel/Autoprefixer/压缩等全链路共享，改兼容范围只改一处）；preset-env 读它自动决定启用哪些转译插件——目标越新转译越少；useBuiltIns:'usage' 按代码实际用到的 API 注入 core-js@3 垫片（entry 是全量、false 是不垫）。必配纪律：不配 browserslist 会走默认全量（体积爆炸）；modules:false 保留 ESM 交给 Webpack（否则 tree-shaking 失效）。验证：npx browserslist 看解析结果。

Q3：业务应用和 npm 库的 polyfill 策略为什么不同？

参考答案：业务应用是产物终点——全局注入（useBuiltIns:usage）最简单可靠，改全局没人与你冲突；npm 库是装进别人应用的中间件——用 useBuiltIns 会改宿主全局对象（覆盖宿主 Promise 版本，事故级冲突），必须用 @babel/plugin-transform-runtime：polyfill 从 @babel/runtime-corejs3 按需 import、辅助函数复用不内联、不污染全局。记忆法：终点可以占地盘，过客不能动地基。另：babel-loader 记得 cacheDirectory:true（转译是大头开销）。
