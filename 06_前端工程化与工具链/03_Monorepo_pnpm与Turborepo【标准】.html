Monorepo：pnpm workspace 与 Turborepo

标准 定位：一个仓库管多应用多包——用 workspace 协议复用依赖、用缓存加速任务

Monorepo 把多个相关应用与共享包放进同一个仓库统一管理。pnpm workspace 负责"怎么组织包与链接依赖"，解决幽灵依赖与安装速度；Turborepo 负责"怎么编排与缓存跨包任务"。本页讲清这两者的分工与 workspace 协议，并以 业务系统（web 主应用/drawio/工作流多应用 + 5 个公共包）这条真实 monorepo 结构收尾。

1技术点概览

是什么：Monorepo（Monolithic Repository）是"把多个项目/包放在同一个 Git 仓库"的组织方式，相对的是 Polyrepo（每包一个仓库）。JS 生态落地它靠两件工具：

  • 关键pnpm workspace（包管理）：怎么在一个仓库里声明多个包、让它们互相引用、共享同一份 node_modules。
  • Turborepo（任务编排）：怎么按依赖顺序跑 build/test，并用缓存跳过没变化的包的重复构建。

解决什么问题：多包分开仓库时，改一个公共组件要发版、多个仓库分别升级、版本对不上、本地调试 link 来 link 去。Monorepo 让"改公共包 + 改消费它的应用"在一个 PR 里一起完成：

  • 收益：一个 PR 里一起改、一起测试、一起发版，版本天然一致。
  • 代价：仓库变大、需要工具保证"一个包的改动不意外破坏别的包"。
  • 本项目：业务系统 正是 monorepo——web 主应用、drawio、工作流多个应用，共享 API 客户端/通用组件/表单设计器渲染器/DOCX 预览/富文本等公共包。

2核心概念

2.1 pnpm 与硬链接/内容寻址存储

一句话定位：pnpm 全局内容寻址 store 每版本只存一份；store 用硬链接连到项目虚拟仓库，顶层 node_modules 再用符号链接指回它。

  • 关键内容寻址 store：全局维护，每个包版本只存一份。
  • 硬链接：全局 store 与项目虚拟仓库 node_modules/.pnpm/<pkg>@ver/ 之间是硬链接——10 个项目都用 vue@3.4，磁盘上 vue 只存一份。
  • 符号链接：顶层 node_modules/<pkg> 不是实体目录，而是指向 .pnpm 内真实包的符号链接（Windows 上为 junction）——既隔离依赖、又不重复占盘。
  • 收益：比 npm 每项目复制一份 node_modules 又快又省空间，monorepo 里尤其明显。

2.2 Workspace 协议与幽灵依赖（Phantom Dependencies）

一句话定位：pnpm 隔离 node_modules 根治幽灵依赖；workspace:* 是 monorepo 内部互引的写法。

  • 坑幽灵依赖：代码 import { x } from 'lodash' 但自己 package.json 没声明——靠"隔壁恰好装了"才在；隔壁升级删了它就莫名崩。
  • pnpm 解法：符号链接的隔离 node_modules——没声明的包 import 不到。
  • 坑从 npm 迁 pnpm 报错：老包依赖了没声明的幽灵包，隔离后直接 import 失败——临时可在 .npmrc 配 shamefully-hoist=true 摊平过渡，根治仍是补全声明；auto-install-peers=true 则自动装好 peer 依赖。
  • workspace 协议："@rmp/api-client": "workspace:*" = 用本地最新这个包、别去 npm 拉；发版时替换成真实版本号。

2.3 Turborepo 与任务依赖图

一句话定位：把各包脚本任务建成依赖图，按拓扑并行执行，并用输入 hash 缓存跳过。

  • 拓扑并行：api-client 没 build 完，web build 就跑不了——按依赖顺序并行执行。
  • 要点缓存：记录某包输入（源码、依赖）hash，和上次一样就直接恢复 build 结果、跳过真编译。
  • 远程缓存：上面默认是本机缓存；开 Remote Caching 后团队/CI 共享同一份构建产物——别人构建过的包，我本地直接拉缓存复现，才是 monorepo CI 提速的核心收益。
  • 提速来源：改了 web、没改 api-client，就不用重新 build api-client。

2.4 Task Pipeline（任务流水线）与 outputs

一句话定位：turbo.json 声明任务依赖关系与哪些产物要被缓存。

  • 声明："build": {"dependsOn": ["^build"], "outputs": ["dist/**"]}。
  • ^build：先把我所依赖的那些包的 build 跑完再跑我的——^ 指"依赖我所依赖的包"，不是脚本内部顺序。
  • outputs：声明哪些产物要被缓存。

2.5 共享配置与版本一致性

一句话定位：monorepo 另一大收益是"统一"——共享配置抽包、依赖版本统一锁定。

  • 共享配置：ESLint/TSconfig/构建配置抽成共享包，所有 app extends 它。
  • 版本一致：根 package.json 用 pnpm.overrides 锁定大版本，避免"A 用 vue3.4、B 用 vue3.2"漂移。

3工作原理与流程

3.1 一次 turbo build 发生了什么

图 2 Turborepo 任务编排与缓存（示意）

  1. 建依赖图：Turborepo 读各 package.json，谁依赖谁一目了然。
  2. 拓扑排序 + 并行：被依赖的包先 build，无依赖关系的任务并行。
  3. 缓存判断：每个任务算输入 hash（源码文件内容 + 依赖版本），命中缓存就从缓存恢复 outputs，跳过实际执行。

4核心语法与配置要点

4.1 pnpm-workspace.yaml（声明哪些目录是包）

packages:
  - 'apps/*'        # 所有应用
  - 'packages/*'    # 所有共享包

4.2 应用 package.json 里用 workspace 协议引用内部包

{
  "name": "@rmp/web",
  "dependencies": {
    "@rmp/api-client": "workspace:*",
    "@rmp/ui-components": "workspace:*",
    "vue": "^3.4.0"
  }
}
workspace:* 表示"永远用本仓库里最新的本地包"，本地开发时改 api-client，web 立刻生效，无需发版；pnpm publish 时会自动把它替换成真实版本号。

4.3 turbo.json（任务流水线与缓存）

{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": { "cache": false, "persistent": true },
    "test": { "dependsOn": ["^build"], "outputs": [] }
  }
}

4.4 根 package.json 的脚本

{
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "test": "turbo run test"
  }
}

5实战项目经验（实战落地）

5.1 项目背景：业务系统 多应用 + 公共包

一句话定位：前端不是单个应用，而是多应用加一批要被复用的公共包，需要一个仓库管好并让公共包改动即时生效。

  • 应用：web 主应用、drawio、工作流。
  • 公共包：OpenAPI 生成的 API 客户端、通用组件、表单设计器渲染器、DOCX 预览、富文本。

5.2 我的角色与职责

  • 分工：我负责 monorepo 结构、workspace 配置、Turborepo 编排与公共包抽取；前端组协作开发各应用。

5.3 技术栈

  • pnpm workspace + Turborepo；Vue3+TS+Vite；公共包含 API 客户端/组件/渲染器。

5.4 落地设计：workspace 协议 + 任务编排

  • 关键workspace 声明：pnpm-workspace.yaml 声明 apps/* 与 packages/*。
  • workspace 协议引用：应用用 "@rmp/api-client":"workspace:*" 引用共享包，本地改包即时生效。
  • Turborepo 编排：build 任务 dependsOn:["^build"] 保证共享包先 build；outputs:["dist/**"] 让产物可缓存。
  • 统一版本：根 pnpm.overrides 锁定 vue/element-plus 大版本。

5.5 关键实现要点

# 安装整个 monorepo：一条命令装所有包的依赖
pnpm install
# 跑全量 build：turbo 自动按依赖拓扑 + 缓存跳过没变化的包
pnpm build
# 只 build web 及其依赖（缓存命中时秒级）
turbo run build --filter=@rmp/web

5.6 真实问题与解法

  • 坑幽灵依赖：某应用直接 import 没声明的工具包，pnpm 隔离后报错——被迫补声明（这正是 pnpm 的价值）。
  • 坑workspace:* 没替换：发版原样发出导致下游装不上——用 pnpm 自带 publish 流程自动替换。
  • 坑outputs 漏写：dist 路径不对，缓存命中却恢复空产物——修正 outputs 路径。

5.7 量化成果

  • 改一个公共包能在一个 PR 里同步更新所有消费应用，版本天然一致；重复构建被缓存跳过，CI 与本地构建明显变快（缓存命中时秒级）。

5.8 协作与排期过程

  • 契约先行：先抽公共包接口，多应用并行消费；OpenAPI 客户端自动生成，前后端解耦。

5.9 复盘与可复用经验

  • 要点谁用谁声明：幽灵依赖在 pnpm 下会被强制暴露，趁早补声明。
  • 要点outputs 配准：turbo 缓存才有意义；内部 TS 包记得 Vite exclude。

5.10 面试讲法（一句话抓手）

一句话抓手："在实践中 业务系统 用 pnpm workspace + Turborepo 把 web/drawio/工作流三个应用和五个公共包管起来，靠 workspace:* 协议让改公共包即时生效，靠 turbo 缓存把重复 build 从全量压到缓存命中秒级。"

6易错点与面试重点

6.1 幽灵依赖（Phantom Dependencies）

一句话定位：用了没声明的包，靠扁平 node_modules 侥幸工作，pnpm 隔离后直接 import 失败。

正解：谁用谁声明，依赖自包含。

6.2 workspace:* 发版未替换

一句话定位：publish 时没把 workspace:* 替换成真实版本号，下游装不上。

  • 坑现象：内部包发到 npm 后，下游 install 报找不到 "workspace:*"。
  • 正解：用 pnpm 自带 publish 流程（自动替换），或 Changesets 等发版工具统一处理。

6.3 turbo 缓存命中但产物为空

一句话定位：outputs 路径配错，缓存以为"没有产物要存"，恢复时自然空。

  • 坑现象：第二次 build 秒过，但 dist 是空的。
  • 正解：核对 outputs glob 与实际输出目录一致。

6.4 ^build 的含义记错

一句话定位：^build = 先跑完我依赖的包的 build；["build"] = 跑我自己的同名任务。

  • 要点["^build"]：先跑完我所依赖的那些包的 build。
  • ["build"]（无 ^）：跑我自己所有包的同名任务。

6.5 Monorepo 不是银弹

一句话定位：适合"高度共享、需要一起发版"的项目，无关项目硬凑只会臃肿。

判断依据是"共享代码与同步发版的频率"——完全无关、发版节奏独立的项目不必硬凑一个 monorepo。
