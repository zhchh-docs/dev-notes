前端 E2E 测试：Playwright 与 Cypress

标准 定位：端到端测试分层、选择器策略、自动等待与 CI 集成——与 Jest/Vitest 单测互补

单元测试测的是"函数/组件内部对不对"，E2E（End-to-End）测的是"用户从打开页面到完成任务，整条链路通不通"。Playwright 与 Cypress 是当前两大主流 E2E 框架，能真实启动浏览器、模拟点击输入、断言页面最终状态。本页讲测试金字塔里 E2E 的位置、选择器与自动等待策略、CI 并行，并以 业务系统 的测试实践说明：单测项目组已经写了，E2E 处于规划/学习阶段——以及为什么要补这一层。

1技术点概览

是什么：E2E 测试从真实用户视角驱动整个应用：

  • 做法：自动启动浏览器（Chromium/Firefox/WebKit），打开页面，模拟用户点击、输入、跳转，最后断言页面呈现的最终结果。
  • 两大框架：关键Playwright（微软，多浏览器、自动等待、并行强）与 Cypress（开发者体验好、调试直观，但早期为单标签页运行、跨域受限）。

解决什么问题：单测把每个函数都测对了，不代表拼起来能用——路由跳转、接口联调、组件间数据流这些"集成缝隙"只有 E2E 能覆盖：

  • 它抓得到：登录后跳错页、表单提交后列表没刷新、权限路由走错这类"跨模块"回归。
  • 代价：比单测慢、脆（依赖真实浏览器与网络），所以只覆盖关键主流程，不追求全覆盖。
  • 本项目定位：业务系统 已有 Jest/Vitest 单测（见该页），E2E 是项目组规划要补的下一层，目前以学习与试点为主。

2核心概念

2.1 E2E 与单元测试的分工

一句话定位：单测测"轮子转不转"，E2E 测"整车能不能开到目的地"，二者互补不替代。

  • 单测：快、稳定、定位精准，适合纯逻辑（utils、校验、计算），mock 掉一切外部依赖。
  • E2E：慢、贴近真实，适合"登录→建单→列表刷新"这类跨模块主流程，不 mock 浏览器与真实路由。
  • 要点取舍：核心纯逻辑靠单测兜底，关键业务主流程靠少量 E2E 守底——不追求用 E2E 覆盖一切。

2.2 选择器策略（Locator）

一句话定位：选择器写得稳不稳，直接决定测试会不会隔三差五挂（flaky）。

  • 反模式：靠 CSS 路径（.btn:nth-child(2)）或可见文案（文案一改就挂）定位。
  • 关键推荐：Playwright 默认首选 getByRole（按无障碍角色+名称，兼带无障碍语义）；没有合适 role/name 的业务元素再用 getByTestId——专门给测试加 data-testid 属性，与样式/文案解耦。
  • 为什么：UI 改版时常动 class 与文案，但 data-testid 是稳定契约；二者是"默认优先 / 稳定契约兜底"的关系，并非互斥的先后之争。

2.3 自动等待（Auto-waiting）

一句话定位：现代 E2E 框架会自动等元素可点/可见，不用手写 sleep。

  • 痛点：传统写法 sleep(1000)——写久了慢、写短了偶尔挂，是 flaky 头号来源。
  • Playwright/Cypress：点之前自动轮询直到元素可见、可点、不被遮挡，超时才报错。
  • 坑不要手写固定等待：看到 flaky 先怀疑选择器/异步，而不是无脑把 sleep 加大。

2.4 断言（Assertion）与可重试

一句话定位：断言也要"会等"——针对最终状态反复重试直到超时。

  • 可重试断言：expect(locator).toHaveText('...') 在 Playwright 里会自动轮询重试，适配异步渲染。
  • 普通断言：一次性判定、不等。混用是常见坑——断言异步结果必须用可重试断言。

2.5 CI 并行与追踪（Trace）

一句话定位：E2E 慢，必须靠并行与失败时的现场录像让它"在 CI 里也能 debugging"。

  • 并行：Playwright 默认把测试分到多个 worker、甚至多浏览器并发跑，把墙钟时间压下来。
  • 关键Trace / 录像：失败时自动保留页面截图、DOM 快照、操作轨迹，本地能"时间穿梭"回放——这是 E2E 能在 CI 落地的关键。

3工作原理与流程

一句话定位：E2E 通过浏览器驱动协议（CDP）真实操控页面，再叠加自动等待与断言重试。

图 2 从测试脚本到浏览器再到断言结果的 E2E 执行链（示意）

  1. 脚本描述用户行为：用例写成"打开页→点登录→填表单→提交"，不关心内部实现。
  2. 框架自动等待：每个动作前框架轮询元素就绪，省去手写 sleep。
  3. CDP 驱动真实浏览器：通过 Chrome DevTools Protocol 控制真实 Chromium，跑的是和用户一模一样的页面。
  4. 可重试断言判定结果：最终状态对不对由可重试断言判定，失败自动保留 Trace 供回放。

4核心语法与 API 要点

4.1 一个最小 E2E 用例

import { test, expect } from '@playwright/test';

test('登录后能看到需求列表', async ({ page }) => {
  await page.goto('/login');
  // 按角色+占位文案定位，避开脆弱 class
  await page.getByLabel('用户名').fill('demo');
  await page.getByLabel('密码').fill('123456');
  await page.getByRole('button', { name: '登录' }).click();

  // 可重试断言：列表标题最终出现
  await expect(page.getByRole('heading', { name: '需求列表' })).toBeVisible();
  // 用 data-testid 定位业务元素
  await expect(page.locator('[data-testid="req-row"]')).toHaveCount(3);
});
接口 mock：不想 E2E 真打后端时，用 page.route('**/api/reqs', route => route.fulfill({ json: fakeData })) 拦截并返回假数据；配合 page.waitForResponse('**/api/reqs') 等接口返回后再断言，比干等 UI 更稳。

4.2 选择器优先级对比

定位方式示例稳定性
getByRolegetByRole('button',{name:'登录'})官方默认首选，兼无障碍校验
getByTestIdgetByTestId('submit')稳定契约兜底（无合适 role/name 时用）
CSS 路径.list > li:nth-child(2)脆，改版即挂
硬 sleepawait page.waitForTimeout(1000)反模式，制造 flaky

4.3 playwright.config 关键项

export default defineConfig({
  use: { baseURL: 'http://localhost:5173' },
  fullyParallel: true,                 // 用例间并行
  retries: process.env.CI ? 2 : 0,    // CI 上失败自动重试，兜偶发 flaky
  reporter: 'html',                    // 出 HTML 报告，含失败 Trace
});

5实战项目经验（自学 + 自建 Demo）

说明：本节是自学 + 自建 Demo，非生产环境项目。业务系统 已有单测（Jest/Vitest），E2E 在那里只是规划/试点、未大规模铺开；下面是实践中常采用 Playwright 自建的冒烟 demo，用于亲手跑通 E2E 主流程。

5.1 自学背景与动机

一句话定位：补"单测碰不到的跨模块主流程回归"这层缺口——登录鉴权后跳路由、状态流转后列表刷新这类。

  • 缺口：真实项目已有单测覆盖 utils/校验，但跨模块主流程曾在联调漏过；想亲手跑通 E2E 而不只是懂概念。

5.2 搭建的 Demo 是什么

  • 功能：一个登录 → 新建一条记录 → 列表出现新条目的冒烟用例。
  • 技术栈：Playwright（与 Vite 项目天然契合、自动等待 + Trace 成熟），目标是本地 dev server 或起好的构建产物。

5.3 落地步骤（含关键代码）

test('新建需求后列表出现新条目', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: '新建需求' }).click();
  await page.getByLabel('标题').fill('E2E 试点需求');
  await page.getByRole('button', { name: '提交' }).click();
  await expect(page.locator('[data-testid="req-row"]').first()).toContainText('E2E 试点需求');
});

5.4 自学遇到的坑与解决

  • 坑选择器绑文案：用"提交"文案定位，按钮改成"确认提交"用例全挂——改走 data-testid。
  • 坑偶发 flaky：靠 retries + Trace 回放定位，发现是测试数据未清理导致用例间互相污染。

5.5 成果（可验证能力）

  • 要点能用 Playwright 写一条稳定的冒烟主流程，选器解耦到 data-testid、失败留 Trace；可复现：npm i -D @playwright/test → 写上面用例 → npx playwright test。

5.6 与真实项目的差异（诚实说明）

业务系统 里 E2E 只是规划/试点、未大规模铺开——E2E 慢且要维护，项目组保持克制只守主流程；本 demo 是我为跑通 E2E 自建的，未上生产 CI、无多浏览器矩阵。正确分层是"单测测逻辑、E2E 测主流程"，不拿 E2E 覆盖组件内部边界。

5.7 面试讲法（一句话抓手）

一句话抓手："实践中常采用 Playwright 自建过登录→新建→列表断言的冒烟 demo，把选器解耦到 data-testid、靠 retries+Trace 解决 flaky；真实项目里 E2E 是 业务系统 单测之上的规划/试点，只守主流程不贪多。"

6易错点与面试重点

  • 坑flaky test（时过时不过）：同一用例本地绿 CI 红。原因多为固定 sleep、用例间共享状态、时序竞争。正解：用自动等待/可重试断言、用例间隔离、CI 开 retries + Trace 回放定位。
  • 坑选择器脆弱：绑 CSS 路径或可见文案，一改版就挂。正解：默认优先 getByRole（含可访问名），没有合适 role/name 的业务元素用 data-testid 兜底。
  • 坑断言用错种类：异步渲染后用一次性断言，时机没到就误判失败。正解：断言最终状态一律用可重试断言（expect(locator).）。
  • 坑在 CI 里忘记起依赖服务：E2E 要真实后端/数据库，CI 只起前端就跑会全红。正解：流水线里先起依赖或对接测试环境。
  • 面试高频：Playwright vs Cypress 怎么选？答：Cypress 调试体验好、上手快，但早期为单标签页运行、跨域与多标签受限；Playwright 原生多浏览器（Chromium/Firefox/WebKit）、自动等待更强、并行与 Trace 成熟，新团队新项目我倾向 Playwright。
