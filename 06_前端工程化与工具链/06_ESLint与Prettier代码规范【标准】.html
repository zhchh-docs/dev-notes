ESLint 与 Prettier 代码规范

标准 定位：Lint 管"对不对"，Formatter 管"好不好看"——两者分工与 CI 门禁

团队代码规范不靠"约定俗成"，而靠工具强制执行。ESLint 负责发现代码里的逻辑错误与坏味道（正确性），Prettier 负责统一排版格式（可读性）。本页讲清两者的分工边界、规则怎么取舍、编辑器怎么集成、以及 CI 门禁怎么卡死不规范的代码，并用低代码平台团队规范落地收尾。

1技术点概览

是什么：两个工具，分工明确：

  • 关键ESLint（正确性）：JS/TS 静态检查工具，把代码解析成 AST，按规则查出"未使用变量、== vs ===、回调 this 可能错"等问题。
  • Prettier（可读性/排版）：不管逻辑，只管"缩进几个空格、行宽、分号、单双引号"这类排版，一键全项目统一。

解决什么问题：没有工具约束时，团队风格靠口口相传，PR 里大量精力花在"几个空格、命名好不好"上而非业务逻辑。工具化后：

  • 风格由 Prettier 自动定死，争议归零。
  • 正确性由 ESLint 在提交前/CI 里卡死。
  • 本项目：低代码平台这类多人长期协作项目，规范工具是必须的工程基建。

2核心概念

2.1 AST（抽象语法树）与规则机制

一句话定位：ESLint 把源码解析成 AST，每条规则就是"遍历 AST 发现特定节点模式就报错"的检查器。

  • 关键本质：不是文本匹配，而是在语法树上做模式识别。
  • 举例：no-unused-vars 查"声明了却没人用的变量"，eqeqeq 查"用了 == 而不是 ==="。

2.2 规则级别：error / warn / off

一句话定位：每条规则三档——error 卡死、warn 提示、off 关闭，取舍是关键。

  • error：违反就报错、CI 失败。
  • warn：提示但不阻断。
  • off：关闭。

真正会导致 bug 的设 error 卡死，风格偏好设 warn 或交给 Prettier——别把所有规则都开成 error，否则团队天天为格式吵架。

2.3 extends 与共享配置

一句话定位：没人从零配几百条规则，一般继承官方/框架推荐集再叠加兼容集。

  • 典型：extends: ['eslint:recommended', 'plugin:vue/vue3-recommended', '@vue/eslint-config-prettier']。
  • monorepo：这份配置抽成共享包，所有 app 复用（见 Monorepo 页）。

2.4 eslint-config-prettier（消除冲突的关键）

一句话定位：关掉 ESLint 里与 Prettier 冲突的格式规则，明确分工——格式归 Prettier，ESLint 只管逻辑。

ESLint 的格式规则（缩进、引号）和 Prettier 排版会打架——这是"两者如何共存"的标准答案。

2.5 提交前钩子（husky + lint-staged）

一句话定位：commit 前自动跑 lint/format，比等 CI 才报顺滑得多。

  • husky：注册 git 钩子。
  • lint-staged：只对暂存区文件跑（不是全项目，快）。

"保存时编辑器自动 format，提交时自动 lint"，开发者几乎无感，坏代码根本提交不出去。

3工作原理与流程

3.1 代码从写到进主干的规范防线

图 2 保存/提交/CI 三重规范防线（示意）

  1. 保存时：编辑器配 "保存时自动 format"，Prettier 实时排版，ESLint 标出逻辑问题——开发者当场就修。
  2. 提交时：husky 钩子跑 lint-staged，只对本次改动的文件检查（快），不通过就拒绝 commit。
  3. CI 时：PR 流水线全量 lint + 测试，作为最后一道门禁，防住"本地没配钩子"的漏网情况。

4核心配置与要点

4.1 .eslintrc 配置要点

{
  "extends": [
    "eslint:recommended",
    "plugin:vue/vue3-recommended",
    "@vue/eslint-config-prettier"
  ],
  "rules": {
    "no-unused-vars": ["warn"],
    "eqeqeq": ["error", "always"],
    "vue/multi-word-component-names": "off"
  }
}
Flat Config（ESLint v9+）：新版默认用 eslint.config.js（扁平配置），.eslintrc.* 已 deprecated；新写法用 files 数组匹配文件、不再需要 --ext。下面是经典 .eslintrc 写法，理解规则组织即可，新项目建议直接上 Flat Config。

4.2 .prettierrc（排版交给它）

{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "es5"
}

4.3 package.json 脚本与 husky

{
  "scripts": {
    "lint": "eslint . --ext .vue,.js,.ts",
    "format": "prettier --write ."
  },
  "lint-staged": {
    "*.{vue,js,ts}": ["eslint --fix", "prettier --write"]
  }
}
eslint --fix 与 prettier --write 会自动修可自动修的问题（缩进、引号、末尾分号），剩下修不了的（真逻辑问题）才需要人动手。

5实战项目经验（实战落地）

5.1 项目背景：低代码平台多人协作的规范治理

一句话定位：多人并行开发早期无统一规范，PR 大量时间耗在风格争论上，需要工具化规范让争议归零。

  • 项目：低代码平台（2021，Vue2+ElementUI+vue-draggable+CodeMirror+Vuex+Webpack+ESLint+Prettier）。
  • 痛点：无规范时 PR 里争论命名/缩进，新人代码风格五花八门。

5.2 我的角色与职责

  • 分工：我牵头落地 ESLint+Prettier 团队规范、编辑器集成与 CI 门禁。

5.3 技术栈

  • ESLint + Prettier + eslint-config-prettier + husky + lint-staged + VS Code。

5.4 落地设计：正确性与排版分工

  • 关键分工：ESLint 管正确性（未用变量/== vs ===/未处理 promise），Prettier 管排版。
  • 规则取舍：真会出 bug 的规则设 error（如 eqeqeq），风格类交给 Prettier。
  • 编辑器集成：统一 VS Code 保存时自动 format + ESLint 自动修复。
  • 提交钩子+CI：husky+lint-staged 提交时只查暂存文件，CI 全量 lint。

5.5 关键实现要点

# 开发者日常：保存即 format，commit 即 lint
npx husky init                          # 初始化 git 钩子（husky v9+；v8 及以前用 husky install）
npx lint-staged                         # 提交时自动跑（hook 触发）
pnpm lint                               # CI 里全量跑：不通过即失败

5.6 真实问题与解法

  • 坑ESLint 与 Prettier 打架：缩进两边都管——引入 eslint-config-prettier 关掉 ESLint 格式规则。
  • 坑所有规则开 error：团队为风格吵翻——改"逻辑类 error、风格类交 Prettier"。
  • 坑本地没装 husky：靠 CI 全量 lint 兜底拦住。

5.7 量化成果

  • PR 里格式争论基本消失；坏代码在合并前被 CI 拦住；lint-staged 只查暂存文件，commit 保持快速。

5.8 协作与排期过程

  • 推行：先定规则 → 统一编辑器配置 → 接 husky/CI 门禁；存量代码分批 auto-fix。

5.9 复盘与可复用经验

  • 要点正确性 ESLint、排版 Prettier，二者不越界。
  • 要点保存即修 + lint-staged，把规范做到开发者无感。

5.10 面试讲法（一句话抓手）

一句话抓手："在实践中低代码平台牵头落地 ESLint+Prettier，把正确性留给 ESLint、排版交给 Prettier，配 husky+lint-staged 和 CI 门禁，让 PR 里的格式争论归零、坏代码合并前被拦。"

6易错点与面试重点

6.1 ESLint 与 Prettier 规则冲突

一句话定位：两者都想管缩进/引号，保存后格式反复横跳。

  • 坑现象：保存后格式在两种风格间反复横跳，git diff 全是无关格式改动。
  • 正解：引入 eslint-config-prettier，关掉 ESLint 里所有格式类规则，格式全归 Prettier。

6.2 把风格规则也设成 error

一句话定位：风格规则设 error，团队天天为"该不该加尾逗号"吵架。

正解：风格交给 Prettier（不争论、自动统一），ESLint 只把"真会出 bug"的规则设 error。

6.3 lint-staged 跑全项目

一句话定位：每次 commit 都 lint 整个项目，慢得不可接受。

  • 坑现象：commit 极慢。
  • 正解：lint-staged 只对暂存区（本次改动）的文件跑，大项目也能秒过。

6.4 跳过检查强行提交

一句话定位：--no-verify 跳钩子推坏代码，靠 CI 兜底。

  • 坑现象：图快 git commit --no-verify 跳过钩子，把坏代码推上去。
  • 正解：CI 全量 lint 作为兜底门禁，本地跳了也会在 PR 被拦。

6.5 TS 项目漏配 typescript-eslint

一句话定位：TS 项目不挂 @typescript-eslint，类型层面的问题查不出来。

  • 坑现象：TS 类型相关错误 ESLint 查不出来。
  • 正解：用 @typescript-eslint/parser 与对应插件。
