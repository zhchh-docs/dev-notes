前端测试：Jest 与 Vitest

标准 定位：金字塔分层、单元测试、mock 与 Jest/Vitest 选型——以及诚实的覆盖率取舍

前端测试不是"为了凑覆盖率"，而是给核心逻辑一道防回归的保险。本页讲测试金字塔分层、单元测试怎么写、组件与接口怎么 mock、Jest 与 Vitest 的选型，并以 业务系统 的真实单测实践收尾——包括项目组实际写到了什么程度、又主动放弃了哪些不值得测的部分。

1技术点概览

是什么：Jest 与 Vitest 都是 JavaScript 单元测试框架，提供：

  • 能力：断言（expect）、用例组织（test/describe）、mock（把依赖的函数/模块/接口替换成假的）、覆盖率统计。
  • 关键Vitest：Vite 团队出品，API 与 Jest 高度兼容，但直接复用 Vite 的转换与缓存、快很多，是 Vite 项目首选。

解决什么问题：手动点一遍页面验证太脆、容易漏。单测让"核心工具函数/关键组件逻辑"改完后自动验证一次，防止改 A 坏 B（回归）。但要诚实：

  • 收益集中处：纯逻辑（utils、校验、计算）。
  • 性价比低处：组件 UI 与接口联调——这也是 业务系统 实际采取的取舍。

2核心概念

2.1 测试金字塔（Unit / Integration / E2E）

一句话定位：底层单元测试写最多，E2E 只覆盖关键主流程。

  • 关键单元测试：测一个函数/模块，依赖全 mock，又快又多。
  • 组件/集成测试：测一个组件和它的关键交互，用 jsdom 模拟 DOM。
  • E2E（端到端）：真实浏览器点完整流程（Cypress/Playwright），最接近用户但最慢最脆。

2.2 断言（Assertion）

一句话定位：测试核心句式是"输入 X，断言结果是 Y"，三段清晰、一次只验一件事。

  • 句式：expect(add(1,2)).toBe(3)，断言库提供 toBe/toEqual/toBeCalled 等匹配器。
  • 要点匹配器别用混：toBe 用 Object.is 比引用/基本类型；toEqual 递归深比较对象（忽略 undefined 键）；toStrictEqual 更严（连 undefined 键与类型都要一致）。比对象请用 toEqual，别用 toBe。
  • 三段式：Arrange（给定条件）→ Act（执行）→ Assert（断言），一个测试只验证一件事。

2.3 Mock（替身）

一句话定位：把外部依赖换成假实现，让测试只聚焦被测逻辑。

  • 假函数：vi.fn() 造一个能记录调用的假函数。
  • 假模块：vi.mock('@/api') 把整个接口模块替换成返回假数据。
  • 收益：不被网络/时序干扰，且能验证"有没有以正确参数调用某函数"。

2.4 jsdom 与 DOM 环境

一句话定位：Node 没有浏览器 DOM，jsdom 在 Node 里用 JS 模拟出 document/window。

  • 做法：Vitest/Jest 配 environment: 'jsdom'。
  • 何时开：测 Vue/React 组件时必须开，否则报 document is not defined。

2.5 覆盖率（Coverage）的正确看法

一句话定位：覆盖率是参考指标不是目标——100% 不等于没 bug。

  • 误区：100% 覆盖率不代表没 bug（断言可能写得不对）；低覆盖率也不一定差（可能测了关键路径）。
  • 本项目态度：核心纯逻辑覆盖率追高，展示性 UI 不硬凑。

4核心语法与 API 要点

4.1 工具函数单测（最划算的部分）

// utils/format.test.ts
import { describe, it, expect } from 'vitest';
import { formatMoney } from './format';

describe('formatMoney', function () {
  it('给数字加千分位和货币符号', function () {
    expect(formatMoney(1234567)).toBe('¥1,234,567.00');
  });
  it('处理 null 返回占位符', function () {
    expect(formatMoney(null)).toBe('--');
  });
});

4.2 mock 接口依赖

import { vi, it, expect } from 'vitest';
// 把 api 模块整个替换成假实现
vi.mock('@/api/user', function () {
  return { fetchUser: vi.fn(() => Promise.resolve({ id: 1, name: '测试' })) };
});
it('加载后渲染用户名', async function () {
  // 断言组件调用了 fetchUser，且用假返回渲染——不发真请求
});
vi.mock 会被提升（hoisting）：vi.mock 会自动提到所有 import 之前执行，所以它的工厂里不能用顶层 import 进来的变量（要用 vi.hoisted 取），否则报"在 import 后才 mock"。测异步/假定时器则用 vi.useFakeTimers()。

4.3 组件测试（Vue）

import { mount } from '@vue/test-utils';
import Counter from './Counter.vue';
it('点击按钮数字 +1', function () {
  const wrapper = mount(Counter);
  wrapper.find('button').trigger('click');
  expect(wrapper.text()).toContain('1');
});
三段式：Arrange（造输入/挂载组件）→ Act（调用/点击）→ Assert（断言结果）。一个 it 只测一件事，失败时一眼定位。

5实战项目经验（实战落地）

5.1 项目背景：业务系统 单测实践（诚实说明规模）

一句话定位：业务密集、核心纯逻辑改动频繁易回归，单测优先覆盖工具函数与校验，不盲目追全量覆盖。

  • 项目：业务系统（Vue3+Vite+TS）。
  • 核心逻辑：金额/日期格式化、表单校验规则、OpenAPI 请求封装。

5.2 我的角色与职责

  • 分工：我负责给 utils/校验逻辑补单测、接 CI；团队小范围协作。

5.3 技术栈

  • Vitest（项目已用 Vite）+ jsdom + vi.mock；对比参考 Jest。

5.4 落地设计：测什么、不测什么

  • 关键优先纯逻辑：金额格式化/日期/表单校验——最稳定、易写、收益高。
  • 接口 mock：组件测试用 vi.mock 替换 API 模块，不发真请求。
  • 诚实取舍：展示型 UI（布局/样式/纯渲染列表）单测性价比低，主动放弃，不追 100% 覆盖。

5.5 关键实现要点

# 一次性跑全部单测（CI 用）
pnpm vitest run
# 开发时 watch 模式，改代码自动重跑
pnpm vitest

5.6 真实问题与解法

  • 坑mock 过度：把组件内部全 mock，测试绿却没测到真实行为——只 mock 外部依赖。
  • 坑测组件没开 jsdom：报 document is not defined。
  • 坑测实现细节：断言私有变量，重构全红——改测对外行为。

5.7 量化成果

  • 工具函数与关键校验逻辑有回归保护，改格式化/校验规则时单测先报警；PR 流水线 vitest run 不过不许合并。

5.8 协作与排期过程

  • 流程：随功能迭代补对应 utils 单测；CI 接 vitest run 作为合并门禁。

5.9 复盘与可复用经验

  • 要点测行为不测实现：重构不红。
  • 要点纯逻辑优先：把单测花在最易回归的工具函数上，性价比最高。

5.10 面试讲法（一句话抓手）

一句话抓手："在实践中 业务系统 用 Vitest 给金额/日期格式化和表单校验这类纯逻辑补单测，接口用 vi.mock，接 CI 门禁；诚实说项目组没追全量组件覆盖——展示型 UI 单测性价比低，主动放弃。"

6易错点与面试重点

6.1 追求覆盖率数字而非质量

一句话定位：100% 覆盖率 ≠ 无 bug——可能每行都执行到，但断言写得松。

正解：测关键路径与边界，断言要真正验证结果，覆盖率只是参考。

6.2 测实现细节而非行为

一句话定位：测内部私有方法，重构一下测试全红，对外行为却没变。

  • 坑现象：重构组件内部实现，测试全红，对外行为没变。
  • 正解：测"输入→输出/对外交互"，不测内部私有方法与中间状态。

6.3 mock 过度 / mock 不足

一句话定位：mock 过度测不到真实集成，mock 不足又慢又脆。

  • 坑两端坑：mock 过度（什么都替身）测不到真实集成；mock 不足（真发请求）慢且脆、依赖后端。
  • 正解：单测 mock 外部依赖，集成测试才少 mock。

6.4 组件测试忘了 jsdom

一句话定位：组件测试不开 jsdom，mount 就报 document is not defined。

  • 坑正解：组件测试配 environment: 'jsdom'。

6.5 把 E2E 当主力

一句话定位：E2E 慢、脆、维护贵，只覆盖关键主流程。

金字塔原则：E2E 只覆盖登录、下单这种关键主流程，海量逻辑靠单元测试——E2E 写太多会让套件变成天天碎的负担。
