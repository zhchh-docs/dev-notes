前端测试：Jest 与 Vitest

标准 定位：金字塔分层、单元测试、mock 与 Jest/Vitest 选型——以及诚实的覆盖率取舍

前端测试不是"为了凑覆盖率"，而是给核心逻辑一道防回归的保险。本页讲测试金字塔分层、单元测试怎么写、组件与接口怎么 mock、Jest 与 Vitest 的选型，并以 业务系统 的真实单测实践收尾——包括项目组实际写到了什么程度、又主动放弃了哪些不值得测的部分。

1简介与阅读指引

1.1 定位：自动化回归保护网

Jest 与 Vitest 都是 JS 单测框架，提供四件套：断言（expect）、用例组织（test/describe）、mock（把依赖换成假实现）、覆盖率统计。Vitest：Vite 团队出品，API 与 Jest 高度兼容，直接复用 Vite 的转换与缓存、快很多——Vite 项目首选。要诚实：手动点页面验证太脆易漏，单测让"改完后自动验证一次防回归"，但收益集中在纯逻辑，组件 UI 与接口联调性价比低。

1.2 学习目标与阅读指引

  1. 建立测试金字塔分层心智（底层多上层少）；
  2. 掌握三段式用例与匹配器选择（toBe/toEqual/toStrictEqual）；
  3. 会用 vi.mock 替身依赖（含 hoisting 陷阱）与 jsdom 环境；
  4. 建立"测什么不测什么"的诚实取舍观。

难度：★★☆☆☆。姊妹篇：10 E2E（金字塔顶层）。

2核心模型

五个核心模型：金字塔→ 断言→ Mock→ jsdom→ 覆盖率观。

2.1 测试金字塔：Unit / Integration / E2E

单元测试：测一个函数/模块，依赖全 mock，又快又多；组件/集成测试：测组件与关键交互，jsdom 模拟 DOM；E2E：真实浏览器点完整流程，最接近用户但最慢最脆。原则：底层写最多——越靠底层越便宜、快、稳；E2E 只覆盖关键主流程。

2.2 断言：三段式与匹配器

句式 expect(add(1,2)).toBe(3)；匹配器别用混：toBe 用 Object.is（比引用/基本类型）；toEqual 递归深比较对象（忽略 undefined 键）；toStrictEqual 更严（undefined 键与类型都要一致）——比对象用 toEqual，别用 toBe。三段式：Arrange（给定条件）→ Act（执行）→ Assert（断言），一个测试只验证一件事。

2.3 Mock：替身依赖

vi.fn() 造能记录调用的假函数；vi.mock('@/api') 把整个模块替换成假实现。收益：不被网络/时序干扰，且能验证"有没有以正确参数调用某函数"——单测只 mock 外部依赖。

2.4 jsdom：Node 里的假 DOM

Node 没有 DOM，jsdom 用 JS 模拟出 document/window——配 environment: 'jsdom'；测 Vue/React 组件必须开，否则报 document is not defined。

2.5 覆盖率的正确看法

误区：100% 覆盖率 ≠ 没 bug（断言可能写得松）；低覆盖也不一定差（可能测了关键路径）。本项目态度：核心纯逻辑覆盖率追高，展示性 UI 不硬凑——覆盖率是参考指标不是目标。

3核心用法（按场景）

3.1 场景一：工具函数单测（最划算）

// utils/format.test.ts
import { describe, it, expect } from 'vitest';
import { formatMoney } from './format';

describe('formatMoney', function () {
  it('给数字加千分位和货币符号', function () {
    expect(formatMoney(1234567)).toBe('¥1,234,567.00');
  });
  it('处理 null 返回占位符', function () {
    expect(formatMoney(null)).toBe('--');
  });
});

3.2 场景二：mock 接口依赖

import { vi, it, expect } from 'vitest';
// 把 api 模块整个替换成假实现
vi.mock('@/api/user', function () {
  return { fetchUser: vi.fn(() => Promise.resolve({ id: 1, name: '测试' })) };
});
it('加载后渲染用户名', async function () {
  // 断言组件调用了 fetchUser，且用假返回渲染——不发真请求
});
vi.mock 会被提升（hoisting）：自动提到所有 import 之前执行，工厂里不能用顶层 import 进来的变量（要用 vi.hoisted 取）。测异步/假定时器用 vi.useFakeTimers()。

3.3 场景三：组件测试（Vue）

import { mount } from '@vue/test-utils';
import Counter from './Counter.vue';
it('点击按钮数字 +1', function () {
  const wrapper = mount(Counter);
  wrapper.find('button').trigger('click');
  expect(wrapper.text()).toContain('1');
});

三段式：Arrange（挂载组件）→ Act（点击）→ Assert（断言文本）。一个 it 只测一件事，失败一眼定位。

3.4 场景四：日常命令

pnpm vitest run   # 一次性跑全部（CI 门禁用）
pnpm vitest       # watch 模式，改代码自动重跑

4进阶知识点【进阶】

首次学习可整章跳过。前置：三段式与 vi.mock 已会。

4.1 setup 文件与全局注入

setupFiles 里做全局准备（@testing-library/jest-dom 扩展匹配器、cleanup 钩子、canvas stub）——所有测试文件自动执行，避免每个文件重复样板。

4.2 快照测试的边界

toMatchSnapshot 适合稳定结构的序列化对比（配置对象/序列化输出）；慎用于大组件 DOM——动一点全量 diff、人肉 update 快照会让快照沦为"自动改期望"。

4.3 Testing Library 范式：以用户视角测

与 @vue/test-utils 的 mount 找 DOM 不同，Testing Library 提倡按可访问性角色/文本查询（getByRole/getByText），断言用户能看到什么——测行为不测实现的天然实现，重构组件结构测试不红。

4.4 monorepo 里的测试编排

每包各自配 vitest，turbo test dependsOn ^build 编排（07 篇流水线呼应）；共享配置抽 @rmp/vitest-config 包 extends——与共享 ESLint/TSconfig 同构。

4.5 Jest 与 Vitest 迁移边界

API 几乎一致，差异点在配置载体（jest.config vs vite.config 内 test 字段）与个别匹配器/环境变量；老 Jest 项目不必为快而迁——迁移成本要盖过收益，新 Vite 项目直接 Vitest。

6最小可运行 Demo

性质：真实实战（诚实说明规模）——业务系统（Vue3+Vite+TS）：我负责给 utils/校验逻辑补单测、接 CI 门禁；团队小范围协作。

6.1 落地设计：测什么、不测什么

  • 优先纯逻辑：金额/日期格式化、表单校验规则、OpenAPI 请求封装——最稳定易写收益高；
  • 接口 mock：组件测试 vi.mock 替换 API 模块，不发真请求；
  • 诚实取舍：展示型 UI（布局/样式/纯渲染列表）单测性价比低，主动放弃，不追 100% 覆盖。

6.2 踩坑记录

  • 坑mock 过度：把组件内部全 mock，测试绿却没测到真实行为——只 mock 外部依赖；
  • 坑测组件没开 jsdom：报 document is not defined；
  • 坑测实现细节：断言私有变量，重构全红——改测对外行为。

6.3 成果与复盘

  1. 量化：工具函数与关键校验逻辑有回归保护，改格式化/校验规则时单测先报警；PR 流水线 vitest run 不过不许合并；
  2. 可复用经验：测行为不测实现（重构不红）；纯逻辑优先（单测花在最易回归处）；
  3. 一句话抓手："用 Vitest 给金额/日期格式化和表单校验补单测，接口 vi.mock，接 CI 门禁；诚实说没追全量组件覆盖——展示型 UI 性价比低主动放弃。"

7常见坑 & Debug

五条高频坑。

7.1 追覆盖率数字

坑：100% 覆盖但断言松，等于没测。正解：测关键路径与边界，断言真验证结果，覆盖率只参考。

7.2 测实现细节

现象：重构内部实现测试全红，对外行为没变。正解：测"输入→输出/对外交互"，不测私有方法与中间状态。

7.3 mock 过度 / mock 不足

两端坑：mock 过度测不到真实集成；mock 不足真发请求慢且脆。正解：单测 mock 外部依赖，集成测试才少 mock。

7.4 忘开 jsdom

现象：mount 报 document is not defined。正解：environment: 'jsdom'。

7.5 把 E2E 当主力

坑：E2E 慢脆贵，写太多套件天天碎。正解：金字塔原则——E2E 只覆盖登录/下单关键主流程，海量逻辑靠单测（见 10 篇）。

8重点讲解

Q1：测试金字塔是什么？为什么底层多上层少？

参考答案：三层——单元测试（测函数/模块，依赖全 mock，快而多）、组件/集成测试（测组件与交互，jsdom 模拟 DOM）、E2E（真实浏览器走完整流程，最接近用户但最慢最脆）。越靠底层越便宜、快、稳，越靠上层越贵、慢、脆（E2E 依赖环境/网络/数据，任何一环抖动都红）——所以海量逻辑靠单测，E2E 只守登录/下单等关键主流程。把 E2E 当主力会让套件变成天天碎的维护负担。

Q2：toBe / toEqual / toStrictEqual 的区别？mock 的原则？

参考答案：toBe 用 Object.is——比基本类型或引用（比对象会翻车）；toEqual 递归深比较（忽略 undefined 键）；toStrictEqual 连 undefined 键与类型都要求一致。比对象用 toEqual。mock 原则：单测 mock 外部依赖（网络/模块），不 mock 被测逻辑内部——mock 过度测试绿却没测到真实行为，mock 不足真发请求又慢又脆。注意 vi.mock 有 hoisting（自动提到 import 之前），工厂里要用 vi.hoisted 取变量。

Q3：覆盖率怎么看待？"测行为不测实现"是什么意思？

参考答案：覆盖率是参考不是目标——100% 覆盖 ≠ 没 bug（每行执行到但断言可能松）；低覆盖也不一定差。测行为不测实现：断言"输入→输出/对外交互"（函数返回值、组件渲染结果、用户可见文本），不断言内部私有方法与中间状态——效果是重构不红：内部实现改了、对外行为没变时测试仍绿。Testing Library 的 getByRole/getByText 范式是这条原则的天然实现。诚实取舍：展示型 UI 性价比低主动放弃，把测试花在最易回归的纯逻辑上。
