1简介与阅读指引

1.1 定位：物的消息总线

MQTT（ISO/IEC 20922）是发布/订阅协议：设备（publisher）把消息发到 Broker 的主题（topic）上，订阅者（subscriber）按主题收——发送方与接收方互不知道对方存在。设计约束是"低带宽、不稳定网络、低算力终端"：固定头仅 2 字节、明文二进制精简、三种 QoS 档位按代价换可靠性。它管的是"物到系统"的遥测/指令层——本模块前六篇（WebSocket/WebRTC/Janus）管人到人与媒体，MQTT 是传感器/网关/平台之间的那一层。

1.2 横向对比：MQTT 在实时协议族中的位置

维度MQTTWebSocketCoAP
模型发布/订阅（Broker 中枢）点对点全双工类 HTTP 请求/响应
承载TCP / TLS / WebSocketTCPUDP
可靠性QoS 0/1/2 三档内建可靠传输，消息语义自建类 HTTP（CON/NON）
离线消息Retained + 会话保持内建自建无
适用海量设备遥测/指令下发浏览器互动受限设备直连

与本模块的关系：01 篇的电力监控里，摄像头/RTU 遥测数据上平台正是 MQTT 的主场；浏览器端经 MQTT over WebSocket 也能直接订阅设备主题（本篇 3.4）。

1.3 学习目标与阅读指引（诚实声明）

  1. 吃透 QoS 三档的真实代价（本篇中心模型）；
  2. 掌握主题设计与通配符（+/#）；
  3. 会用遗嘱与保留消息建模"设备在线/最后状态"；
  4. 浏览器经 mqtt.js over WebSocket 接入；
  5. 知道 Broker 选型与集群/共享订阅。

诚实声明：本套技术栈生产项目设备接入层由后端负责，MQTT 属前端视角的技术储备（理解遥测链路、浏览器直连能力评估）——代码为自学验证性质。难度：★★☆☆☆。

2核心模型

六个核心模型：发布/订阅与 Broker（总纲）→ QoS 三档→ 主题与通配符→ 遗嘱 LWT→ 保留消息→ KeepAlive 与会话。

2.1 发布/订阅与 Broker：解耦到设备不认识设备

所有消息经 Broker 路由：publisher/subscriber 解耦（空间/时间/同步三重解耦——不同时在线也能收到，见保留消息）。设备只维持一条到 Broker 的长连接；百万级设备接一个集群 Broker（EMQX/Mosquitto/HiveMQ）。

2.2 QoS 三档：按代价选可靠性（中心模型）

  • QoS 0 至多一次：发完即忘，可能丢——适合高频遥测（丢一帧温度无所谓）；
  • QoS 1 至少一次：PUBACK 确认，超时重发——可能重复，消费端要幂等（默认档）；
  • QoS 2 恰好一次：四步握手（PUBREC/PUBREL/PUBCOMP）——不丢不重，代价最大，只给"遥控开关"这类绝对不能重也不能丢的指令。

核心：QoS 是每条消息可选的（发布与订阅双方取低者生效）——"遥测 0、告警 1、遥控 2"是典型分层。

2.3 主题与通配符

主题是斜杠分层字符串（plant/A/station/01/temp）；订阅支持通配符：+ 单层（plant/+/station/+/temp）、# 多层（plant/A/#，只能放末尾）。坑：# 订阅海量主题会把无关数据全拉进客户端——主题即数据库的索引设计，层级顺序按查询频率排（大粒度在前）。

2.4 遗嘱消息（LWT）：设备掉线变成事件

连接时预约一条"遗嘱"（主题+内容+QoS），Broker 检测到非正常断连（KeepAlive 超时/协议错误）时替设备发布——"plant/A/dev01/status → offline"。配合"上线即发 online"的约定，设备在线状态就是两个主题，平台订阅 status 主题即可维护在线表。

2.5 保留消息（Retained）：最后的值即真相

发布时置 retain 标志，Broker 为该主题保存最后一条，新订阅者连接即收到——"设备最后上报的温度/配置"不用等下一帧。与 LWT 组合：offline 也发 retained，任何时刻订阅 status 主题立刻知道每个设备在线与否。

2.6 KeepAlive 与会话

客户端声明 KeepAlive 秒数，超时未发包要发 PINGREQ 探活（对应 02 篇心跳——协议内建）；Clean Session=false 时 Broker 为离线客户端保留订阅与 QoS1/2 待发消息，重连补推（与 SSE Last-Event-ID 同思想，但能力更强）。

3核心用法（按场景）

3.1 场景一：浏览器经 WebSocket 直连 Broker（mqtt.js）

import mqtt from 'mqtt';

const client = mqtt.connect('wss://mqtt.example.com:8084/mqtt', {
  clientId: 'web_' + Math.random().toString(16).slice(2, 10),
  username: 'web-viewer',
  password: token,                    // token 鉴权（Broker 侧校验）
  keepalive: 30,
  clean: false,                       // 保留会话：离线期间的 QoS1 消息补推
  reconnectPeriod: 2000               // 内建重连（库自带退避）
});

client.on('connect', () => {
  client.subscribe('plant/A/+/status', { qos: 1 });
});
client.on('message', (topic, payload) => {
  const dev = topic.split('/')[3];    // 主题即路由：从主题解析设备
  updateDeviceStatus(dev, JSON.parse(payload.toString()));
});

3.2 场景二：QoS 分层发布（遥测/告警/遥控）

// 设备侧视角（Node 模拟网关聚合转发）
client.publish('plant/A/dev01/temp', JSON.stringify({ v: 36.2, ts: Date.now() }),
  { qos: 0 });                                     // 高频遥测：丢了无所谓
client.publish('plant/A/dev01/alarm', JSON.stringify({ level: 2 }),
  { qos: 1 });                                     // 告警：至少一次+消费端幂等
client.publish('plant/A/dev01/cmd', JSON.stringify({ op: 'reboot' }),
  { qos: 2 });                                     // 遥控：恰好一次，绝不重发

3.3 场景三：遗嘱 + 保留消息建在线表

// 设备/网关连接时预约遗嘱
const client = mqtt.connect(url, {
  will: {
    topic: 'plant/A/dev01/status',
    payload: JSON.stringify({ online: false, ts: Date.now() }),
    qos: 1, retain: true               // 掉线通知也保留
  }
});
// 上线后立即发 retained 的 online
client.publish('plant/A/dev01/status', JSON.stringify({ online: true }),
  { qos: 1, retain: true });
// 平台侧：订阅 status 主题 → 断线重连立刻拿到全量设备在线快照

3.4 场景四：主题设计规范（团队契约）

plant/{厂区}/station/{站点}/{设备类型}/{设备id}/{数据类别}
例：plant/A/station/01/inverter/inv007/telemetry   遥测（QoS0，高频）
    plant/A/station/01/inverter/inv007/alarm       告警（QoS1）
    plant/A/station/01/inverter/inv007/cmd         指令下行（QoS2）
    plant/A/station/01/inverter/inv007/status      在线状态（QoS1+retain）
通配示例：订阅全厂告警 → plant/A/+/+/+/alarm
禁止：主题里放时间戳/随机值（导致通配符订阅失效、Broker 主题表膨胀）

4进阶知识点【进阶】

首次学习可整章跳过。前置：QoS/主题/LWT 已会用。

4.1 共享订阅（Shared Subscriptions）与消费扩容

普通订阅下每个订阅者都收全量（广播）；共享订阅 $share/g1/plant/A/#/telemetry 让同组订阅者分摊消息（负载均衡）——后端消费集群水平扩容的关键；g1 是组名，EMQX/Mosquitto 2.x 支持。

4.2 Broker 选型与集群

Mosquitto：轻量单机首选；EMQX：Erlang 集群、百万连接、规则引擎/Webhook 生态（生产主流）；云托管：AWS IoT Core/阿里云 IoT（自带设备影子/规则）。集群要点：主题路由跨节点（EMQX 内建）、共享订阅跨节点、ACL 鉴权集中化。

4.3 安全清单

①TLS（8883/8084）必须，明文 1883 只限内网调试；②per-device 凭据 + ACL（设备 A 只能 pub 自己主题、sub 自己的 cmd——防止一个设备被攻破后全厂横移）；③clientId 与身份绑定防顶替；④主题不放敏感信息（主题对有 subscribe 权限者可见）。

4.4 MQTT 5 新能力

MQTT 5（2019）补齐工程短板：原因码（断开/失败有了明确错误）、主题别名（长主题省带宽）、消息过期（Session Expiry）、共享订阅标准化、用户属性（消息带元数据）。选 Broker 时确认版本支持（Mosquitto 2.x/EMQX 5 均已支持）。

4.5 与本技术栈的链路对照

电力监控全链路：设备/网关 →(MQTT)→ 平台 →(WebSocket)→ 浏览器——MQTT 管海量低功耗遥测上行，WebSocket 管浏览器高频交互，WebRTC 管媒体。三层各选所长：让 MQTT 直达浏览器只有在"浏览器就是订阅终端"（低频看板）时才划算，高频实时仍走 WebSocket/推送服务桥接。

6最小可运行 Demo

性质（诚实声明）：自学验证——本地 Mosquitto + 浏览器 mqtt.js 模拟"设备在线表 + 遥测看板"，验证 QoS/遗嘱/保留消息三模型；生产设备接入由后端负责。

6.1 落地步骤

  1. docker 起 emqx 或 eclipse-mosquitto（开 1883 与 8083 ws）；
  2. Node 脚本模拟设备：连上发 retained online、每秒 QoS0 遥测、预约 LWT 后 kill -9；
  3. 浏览器 3.1 mqtt.js 订阅 status 与 telemetry：验证 kill 后 LWT offline 自动到达；
  4. 重启模拟设备：retained 的 online 与最新遥测无需等待即达；
  5. 故意在 QoS1 主题双订阅复现重复消息，验证按 msgId 幂等去重。

6.2 验证清单

  1. mosquitto_sub 观察 $SYS 主题（Broker 自身统计：连接数/消息数）；
  2. 保留消息：新订阅者连上立即收到每个设备最后状态（不等下一帧）；
  3. clean:false 会话：浏览器离线期间的 QoS1 告警在重连后补推。

6.3 复盘经验

  • 体感：协议心智极小（五个报文类型够用），"在线表/最后状态"两个经典问题有协议内建解——比 WebSocket 自建省一个服务；
  • 边界：主题规划是真正的工程量——主题错了通配符订阅全废；高频实时场景仍要与 WebSocket/推送服务桥接（4.5 分层）；
  • 选型结论：海量设备遥测 → MQTT 是唯一正解；浏览器端只在低频看板场景直连，实时大屏仍走 WebSocket 桥。

7常见坑 & Debug

五条高频坑。

7.1 QoS1 当 QoS2 用，消息重复消费

现象：告警重复入库/遥控执行两次。原因：QoS1 只保证"至少一次"，确认丢失即重发。正解：消费端按 msgId/业务幂等键去重；绝对不能重的才上 QoS2。

7.2 主题设计混乱，通配符订阅失效

现象：想订阅"全厂温度"却收不到，或收到一堆无关数据。原因：主题层级/粒度无规范，甚至把时间戳放进主题。正解：主题即索引——按"大粒度在前"设计层级并写进团队契约（3.4）。

7.3 忘记 retain，新订阅者空等

现象：大屏刷新后设备状态空白几十秒。原因：状态/配置类消息没置 retain，新连接只能等下一帧。正解：状态类消息一律 retained；过期状态要发布空 payload 清除。

7.4 KeepAlive 配置与网络不匹配

现象：设备频繁掉线重连。原因：KeepAlive 太短（弱网下 PING 超时）或 NAT 表超时更短。正解：KeepAlive 取"最大 NAT 空闲的 2/3 左右"，弱网设备适当放大；Broker 侧调大会话过期间隔。

7.5 ACL 缺失，一台设备攻破全网沦陷

风险：所有设备共享一个账号，被攻破后可 pub 任何主题（伪造遥测/下发指令）。正解：per-device 凭据 + ACL 限定"只能 pub 自己的遥测、sub 自己的 cmd"。

8重点讲解

Q1：MQTT 的 QoS 三档各自的真实代价？怎么选档？

参考答案：QoS 0 发完即忘（可能丢）——零额外开销，适合高频遥测（丢一帧无所谓）；QoS 1 PUBLISH→PUBACK，超时重发——保证"至少一次"但可能重复，消费端必须幂等（按 msgId 去重），是默认工作档（告警/状态）；QoS 2 四步握手（PUBREC/PUBREL/PUBCOMP）两端保持状态——"恰好一次"不丢不重，代价两次往返+状态存储，只给遥控/计费类绝对严格消息。规则：QoS 每条消息可选、发布与订阅双方取低者生效；实战分层口诀"遥测 0、告警 1、遥控 2"。反面教训：QoS1 当 QoS2 用又没做幂等，就是重复消费事故。

Q2：遗嘱消息和保留消息怎么组合出"设备在线表"？

参考答案：遗嘱 LWT——连接时预约（主题+payload+QoS），Broker 检测到非正常断连（KeepAlive 超时/协议错误）时替设备发布 offline；保留 Retained——Broker 为主题保存最后一条，新订阅者连接即收。组合拳：设备上线发 status → online（retain），LWT 也设 retain 的 offline——平台订阅 status 主题，任何时刻连接都能立刻拿到全量设备在线快照（不用轮询心跳表）。注意：正常主动断开 Broker 不发遗嘱（DISCONNECT 报文是"好离场"）——主动下线也要自己发 offline retained。

Q3：为什么设备海量接入选 MQTT 而不是 WebSocket？浏览器端怎么接？

参考答案：MQTT 的设计目标就是物端——2 字节固定头（ws 协议帧+HTTP 头重得多）、QoS/遗嘱/保留/会话保持内建（WebSocket 全要自建，见 02 篇手写栈）、Broker 中枢天然支持百万设备解耦（EMQX 集群）。浏览器接入：MQTT over WebSocket（Broker 开 8083/8084，mqtt.js 连 wss://）——浏览器是普通订阅者；分层结论：设备遥测海量低功耗走 MQTT 直达平台，浏览器高频实时走 WebSocket 桥接、低频看板可直连 MQTT——三层协议各选所长（MQTT 物到系统、WebSocket 人到人、WebRTC 媒体）。
