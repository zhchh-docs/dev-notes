SSE 服务器推送

标准 定位：服务器单向推送——基于 HTTP 的轻量实时方案

SSE（Server-Sent Events）是跑在普通 HTTP 上的单向推送协议：响应头 text/event-stream，连接保持打开，服务器随时往里写 data: ... 行。它是"只需要服务器→客户端推送"场景的最优解——不用引入 WebSocket 的协议升级与心跳栈，浏览器 EventSource 原生自带断线自动重连与 Last-Event-ID 续传。代价是单向：客户端要发数据还得走 HTTP 请求。

1简介与阅读指引

1.1 定位：HTTP 上的单向推送

SSE = 客户端发一个普通 HTTP 请求，服务器响应 Content-Type: text/event-stream 且不结束响应，随后随时写入事件行——本质是"一个不结束的 HTTP 响应"。前端用原生 EventSource API 消费。它解决"服务器→客户端单向推送"（日志流/进度条/通知/行情单向下发），不解决双向——客户端上行仍走普通 HTTP 请求。

1.2 横向对比：SSE vs WebSocket vs 轮询

维度SSEWebSocketHTTP 轮询
方向服务器→客户端单向全双工一问一答
协议普通 HTTP（无升级）协议升级 ws://普通 HTTP
断线重连浏览器原生自动+Last-Event-ID 续传自己写心跳+退避天然（每次新请求）
代理/网关友好度高（就是 HTTP）需配置 Upgrade 头高
适用日志流/通知/进度/行情下发聊天/协同/互动低频状态查询

口径：只要不需要"客户端向服务器高频上行"，SSE 就是比 WebSocket 更省的选择——少一套心跳重连栈，复用全部 HTTP 基建（鉴权/CDN/网关）。

1.3 学习目标与阅读指引（诚实声明）

  1. 掌握 event-stream 文本协议（data:/event:/id:/retry: 四种行）；
  2. 理解 EventSource 自动重连与 Last-Event-ID 机制——SSE 的最大卖点；
  3. 会写 Node SSE 端点并处理代理缓冲坑；
  4. 建立与 WebSocket 的准确选型边界。

诚实声明：本套技术栈生产项目以 WebSocket 信令+WebRTC 媒体为主，SSE 属单向推送场景的技术储备（构建进度推送、日志流场景评估用）——本篇代码为自学验证性质。

2核心模型

四个核心模型：event-stream 协议（总纲）→ EventSource 状态与重连→ Last-Event-ID 续传→ HTTP 长连接约束。

2.1 event-stream 文本协议：四种行

服务器按纯文本行写响应，每条事件由空行分隔：

  • data: 消息体（必填，多行 data 会按 \\n 拼接）；
  • event: 自定义事件名（客户端 addEventListener 区分，默认 message）；
  • id: 事件 ID（重连时浏览器自动放进 Last-Event-ID 请求头）；
  • retry: 告诉浏览器重连间隔（毫秒）。

要点：以 : 开头的行是注释——常用作心跳（写 : keep-alive\\n\\n 防代理空闲超时，比 WebSocket 心跳还简单）。

2.2 EventSource：状态与原生重连

new EventSource(url) 三状态：CONNECTING(0)/OPEN(1)/CLOSED(2)。**断线自动重连是浏览器内建行为**——error 后自动按 retry 间隔重连，业务只在 onerror 里做日志与 UI 提示；调用 es.close() 才永久停止。与 WebSocket 对比：省掉整套心跳+退避重连代码。

2.3 Last-Event-ID：断点续传协议内建

每条事件带 id:，浏览器重连时自动带 Last-Event-ID 请求头——服务端据此补发遗漏事件（需要服务端有短期事件缓冲）。这是 SSE 协议层内建的"至少一次送达"基础，WebSocket 要自己实现 seq+补偿接口（02 篇 4.1）。

2.4 HTTP 长连接约束：6 连接限制与 HTTP/2

HTTP/1.1 浏览器对同域并发连接数限 6——开多个 SSE 标签页可能占满连接池阻塞其他请求；HTTP/2 多路复用（单连接多流）解决此问题。生产部署建议：SSE 走独立子域或确保全站 HTTP/2+。

3核心用法（按场景）

3.1 场景一：最简 SSE 端点（Node）

// 服务端：Express 风格
app.get('/api/progress/:taskId', (req, res) => {
  res.set({
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
    'X-Accel-Buffering': 'no'          // 关键：关 Nginx 缓冲（见 7.2）
  });
  res.flushHeaders();

  const send = (data, id) => {
    if (id) res.write(`id: ${id}\\n`);
    res.write(`data: ${JSON.stringify(data)}\\n\\n`);
  };

  // 心跳：每 25s 写一行注释，防代理空闲超时
  const beat = setInterval(() => res.write(': keep-alive\\n\\n'), 25000);

  const un = subscribeProgress(req.params.taskId, (p) => send(p, p.seq));
  req.on('close', () => { clearInterval(beat); un(); });   // 成对清理
});

3.2 场景二：前端 EventSource 消费

const es = new EventSource('/api/progress/task-42');

es.onmessage = (e) => {                 // 默认 message 事件
  const p = JSON.parse(e.data);
  progressBar.set(p.percent);
};
es.addEventListener('done', (e) => {    // 自定义事件名
  es.close();                           // 业务完成：主动永久关闭
});
es.onerror = (e) => {
  // 浏览器会自动重连，这里只做 UI 提示；readyState===CLOSED 才需要手动重建
  if (es.readyState === EventSource.CLOSED) showReconnectBtn();
};

3.3 场景三：带 id 的事件（支持续传）

// 服务端：事件带自增 id，断线重连时按 Last-Event-ID 补发
app.get('/api/logs', (req, res) => {
  const lastId = Number(req.get('Last-Event-ID') || 0);   // 浏览器自动带
  const since = eventBuffer.after(lastId);                // 从缓冲补发遗漏
  since.forEach(ev => res.write(`id: ${ev.seq}\\ndata: ${ev.line}\\n\\n`));
  // ...继续实时推送...
});

3.4 场景四：EventSource 发送凭据

// 跨域 SSE 默认不带 Cookie，需要 withCredentials
const es = new EventSource('https://api.example.com/stream', {
  withCredentials: true
});
// 注意：EventSource 不能自定义请求头——token 走 Cookie 或 URL query 一次性 ticket

4进阶知识点【进阶】

首次学习可整章跳过。前置：event-stream 协议与 EventSource 已会。

4.1 代理缓冲：SSE 第一大坑的完整解法

中间代理（Nginx）默认攒够 buffer 才转发——表现为"本地直连正常、上代理后消息成块到达或全无"。三层解法：①响应头 X-Accel-Buffering: no（Nginx 按头关闭缓冲）；②Nginx 配置 proxy_buffering off; proxy_cache off;；③每条事件后确保 flush（Node res.write 即 flush，PHP 需 ob_flush）。必须真机过代理验证，不能只在本地测。

4.2 SSE 的多路复用设计：一条流多类事件

与其开多条 SSE 连接（撞 6 连接限制），不如一条流按 event 名分流：event: log、event: progress、event: notify 各自 addEventListener——把 SSE 当"订阅了多个频道的单条管道"用。

4.3 与 HTTP/2 的配合

HTTP/2 单连接多流天然适合 SSE（不占并发连接名额、头部压缩）；但注意 HTTP/2 的流控（SETTINGS 初期窗口小会限吞吐，大流量日志流要调窗口）。反向情况：不支持 HTTP/2 的内网老网关，SSE 连接数规划要按 6 上限算。

4.4 断线期间的丢失窗口

Last-Event-ID 只在浏览器自动重连时携带；若服务端重启导致事件缓冲丢失、或客户端 closed 后人工重建，仍有丢失窗口。加固：业务侧关键消息仍要"seq+HTTP 补偿拉取"兜底（与 02 篇 4.1 同构）——SSE 的续传不等于可靠性保证。

4.5 选型决策树（与 02/04 篇合流）

需要双向或客户端高频上行 → WebSocket（自建）或 Socket.io（要自动降级/房间/广播）；纯服务器下行 → SSE（最省）→ 但要求 IE/老内核兼容 → 长轮询兜底。本套技术栈口径：信令用 ws、日志流与进度推送用 SSE。

6最小可运行 Demo

性质（诚实声明）：自学验证——一个"构建进度推送"demo（模拟任务进度流），验证 event-stream 协议、自动重连与 Last-Event-ID 续传；生产项目未使用 SSE。

6.1 落地步骤

  1. Node 起 3.1 进度端点（订阅模拟任务，0-100 每 500ms 推一条，带自增 id）；
  2. 前端 3.2 EventSource 消费，进度条 + done 事件关闭；
  3. 手动杀服务端：观察 onerror 后浏览器自动重连（network 面板看到重发请求且带 Last-Event-ID）；
  4. 重启服务端接上续传逻辑：确认从断点 seq 补发，进度条不回跳；
  5. Nginx 反代下验证：故意不加 X-Accel-Buffering 复现"消息成块到达"，再修复对比。

6.2 验证清单

  1. network 面板：请求 Type 是 eventstream、Time 一直在涨（连接未结束）；
  2. 自定义 event 分流正常（log/progress 各走各的 listener）；
  3. 断线重连不带任何 JS 重连代码——浏览器内建；
  4. 注释行心跳经代理后连接不断。

6.3 复盘经验

  • 体感：实现成本约为 WebSocket 方案的 1/3（无心跳/退避/状态机代码）；
  • 边界：单向才成立——demo 里"取消任务"这类客户端指令仍走 POST，两套通道并存；
  • 选型结论：日志流/进度/通知类需求，SSE 是默认首选，WebSocket 是"需要双向"时才升级。

7常见坑 & Debug

五条高频坑。

7.1 代理缓冲导致消息"成块到达"

现象：本地正常、上 Nginx 后消息攒一大批一起到。原因：代理默认缓冲响应。正解：X-Accel-Buffering: no + proxy_buffering off，真机过代理验证。

7.2 忘记心跳，长连接被掐

现象：静置几分钟后流断了。原因：与 WebSocket 同理，中间设备空闲超时。正解：注释行 : keep-alive 定时写入（比 ws 心跳更简单）。

7.3 HTTP/1.1 六连接占满

现象：开几个 SSE 标签页后其他请求卡住。原因：同域并发连接限 6。正解：一条流按 event 名分流（4.2），或全站升级 HTTP/2。

7.4 跨域 SSE 不带凭据

现象：跨域流鉴权 401。原因：EventSource 默认不带 Cookie 且不能自定义头。正解：withCredentials: true + 服务端 CORS 允许凭据，token 走一次性 ticket。

7.5 压缩导致缓冲叠加

现象：开了 gzip 后消息延迟巨大。原因：压缩器攒数据凑压缩块。正解：text/event-stream 不做 gzip（文本量小压缩收益低），或用支持 flush 的压缩配置。

8重点讲解

Q1：SSE 的协议格式是什么？断线重连与续传是怎么工作的？

参考答案：协议——响应 Content-Type: text/event-stream 且不结束，按行写：data:（消息体）/event:（自定义事件名）/id:（事件 ID）/retry:（重连间隔），空行分隔事件，: 开头是注释（常用作心跳）。重连续传：连接断开时浏览器自动按 retry 间隔重连（业务零代码），重连请求自动携带最后收到的 id 放进 Last-Event-ID 头，服务端从事件缓冲按 id 之后的 seq 补发——这是协议层内建的续传，对比 WebSocket 需要自建心跳+退避+seq 补偿整套栈。

Q2：SSE 和 WebSocket 怎么选？各自的真实边界？

参考答案：分界线是"客户端要不要高频上行"——纯服务器下行（日志流/进度/通知/行情下发）选 SSE：实现成本约 1/3、复用全部 HTTP 基建（鉴权/网关/CORS）、浏览器原生重连；需要双向（聊天/协同/WebRTC 信令）选 WebSocket。SSE 的边界：①单向——上行只能另走 HTTP；②HTTP/1.1 同域 6 连接限制（一条流按 event 分流或上 HTTP/2）；③IE 全系不支持（需 polyfill/长轮询兜底）；④Last-Event-ID 续传依赖服务端事件缓冲，重启即丢——关键业务仍要 seq+HTTP 补偿兜底。

Q3：SSE 上生产最容易踩什么坑？怎么排查？

参考答案：第一大坑是代理缓冲——Nginx 默认攒 buffer 转发，表现为"本地正常、上环境消息成块到达或全无"。排查顺序：①本地直连验证协议正确；②curl -N 直接打代理看是否逐条到达；③确认响应头 X-Accel-Buffering: no 与 Nginx proxy_buffering off；④检查 gzip（event-stream 别压缩）；⑤确认注释行心跳间隔小于空闲超时。方法论：SSE 的问题九成出在"中间层"，不在协议本身——逐跳排除（浏览器→代理→服务端）。
