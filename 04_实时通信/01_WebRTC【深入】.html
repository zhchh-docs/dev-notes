WebRTC 实时通信

深入 定位：浏览器原生 P2P 实时音视频——用一套 JS API 取代插件与流媒体服务器转发

WebRTC（Web Real-Time Communication）是 W3C/IETF 标准化的浏览器原生实时音视频框架，提供 getUserMedia 采集、RTCPeerConnection 建连、DTLS/SRTP 加密传输与 JitterBuffer 抖动缓冲，端到端延迟可压到亚秒级。本页从 PeerConnection/SDP 协商/ICE 候选讲到接收渲染与 getStats 质量统计，并以 2020-2022 年主导的 WebRTC 无插件播放器（Vue2+Janus+Canvas，把变电站监控从 ActiveX 插件迁移到浏览器原生低延迟直播）这条真实链路收尾。

1技术点概览

是什么

一句话定位：让浏览器之间直接做实时音视频与数据传输的开源标准，2011 年 Google 开源后捐给 W3C/IETF。

  • 标准化：浏览器侧 API 由 W3C webrtc-pc 定义，协议侧（ICE/STUN/TURN、SDP、SRTP/DTLS）由 IETF 定。
  • 关键三大家族 API：getUserMedia()（采集摄像头/麦克风/屏幕）、RTCPeerConnection（建连与媒体传输）、RTCDataChannel（P2P 任意数据通道）。

关键心智模型：WebRTC 本身不含信令服务器——浏览器怎么"认识彼此、交换 SDP"要自己搭（WebSocket/HTTP 都行），WebRTC 只负责之后的媒体面。

解决什么问题

一句话定位：它消灭了浏览器端插件（Flash/ActiveX）与高延迟的流式转发。

  • 过去的痛点：监控/会议/客服直播要么要求装 ActiveX 插件（IE 专属、安全告警、换机就崩），要么走 HTTP-FLV/HLS 经 CDN 转发（延迟 3-30 秒）。
  • WebRTC 带来：浏览器直接拿到 SRTP 加密的 RTP 包，端到端延迟压到 200-500ms，无需安装任何东西。

代价：它把"怎么打通 NAT、怎么协商编解码、怎么保质量"这些原本藏在流媒体服务器里的复杂度，部分暴露成了前端要懂的协议细节。

图 1 WebRTC 在"源→SFU→浏览器→渲染"链路中的位置（示意）

横向对比：WebRTC 取代了什么，与 HLS/HTTP-FLV 的取舍

  • vs ActiveX/Flash 插件方案：旧方案要求每台值班机装插件、绑定 IE、安全软件持续告警；WebRTC 是浏览器原生 API，零安装、跨浏览器、天然走 HTTPS/WSS。代价是要在浏览器侧重新实现一套播放器（本项目正是这个改造），且老内核浏览器不支持时需要保留降级。
  • vs HLS / HTTP-FLV / RTSP-over-Web：HLS 基于分片，延迟 3-30s，胜在能走 CDN、抗弱网、播放器生态成熟；HTTP-FLV 延迟 1-3s，需要 flv.js 解封装；WebRTC 延迟 200-500ms，但要求对端是支持 WebRTC 的媒体服务器（Janus/mediasoup/SRS/WHEP），且强依赖 UDP，企业网封 UDP 时要靠 TURN 走 TCP 中继。取舍依据是"延迟是不是硬指标"——监控看回放用 HLS，实时看现场用 WebRTC。
  • WebRTC 直连(P2P) vs 经 SFU：浏览器对浏览器是真 P2P；但监控场景是"多路源推上来、N 个浏览器同时看"，P2P 会让每路源都要和每个观看者各建一条连接，源端带宽爆炸。正确做法是中间架一台 SFU（Selective Forwarding Unit，只转发不混流），浏览器各自只和 SFU 建一条连接——这正是本项目选 Janus 的原因（见 02_Janus 网关页）。

2核心概念

2.1 RTCPeerConnection（对等连接）

一句话定位：WebRTC 的核心对象，抽象"一条到对端的实时连接"，本身是个严格的状态机。

  • 关键内部聚合四件事：本地/远端 SDP、ICE 代理（找路）、DTLS 握手（密钥协商）、SRTP 传输栈 + JitterBuffer（抖动重排）。
  • 不碰 DOM：媒体要显示，得把产出的 MediaStreamTrack 挂到 <video> 或喂给 Canvas。
  • 它是状态机：new→have-local-offer→stable→have-remote-pranswer…。

状态乱跳（比如在 stable 之前又 createOffer）就是后续"协商失败"的根源。

2.2 MediaStream 与 MediaStreamTrack

一句话定位：MediaStream 是"一组轨"的容器，每根 Track 是一路视频或音频。

  • 结构：一个视频轨 + 一个音频轨 = 一路流；Track 有 kind（audio/video）、id、enabled。
  • 接收侧：pc.ontrack 拿远端轨，赋 video.srcObject = event.streams[0] 即可播。
  • 本项目做法：没用 <video> 黑盒，而是把视频轨绘到 Canvas——为叠加监控 OSD（时间戳/通道名/状态字）并统一多路同屏绘制节奏。

2.3 SDP（Session Description Protocol，会话描述协议）

一句话定位：SDP 不是协议而是一段纯文本描述，两端交换它就是"媒体协商"。

  • 描述内容：支持哪些编解码（m=video 行的 H.264/Opus payload type）、媒体端口、加密 fingerprint、ICE 用户名密码、a=rtpmap/a=fmtp（H.264 profile-level-id）等属性。
  • 协商过程：offer 端列出自己会的，answer 端从交集里选出最终编解码与参数。

offer/answer 必须是"一次完整往返"才进入 stable，中途再改就要走协商更新（RENEGOTIATION）。

2.4 ICE（Interactive Connectivity Establishment，连通性建立）

一句话定位：解决"NAT 后两台机器怎么找到一条能通的路"的框架。

  • 关键收集候选（candidate）：主机候选（本机网卡 IP）、srflx（经 STUN 反推的公网映射）、relay（TURN 中继地址）。
  • 互发 + 打洞：候选经信令互发，对每个候选对做 STUN 连通性检查（Binding Request/Response），按优先级选第一个打通的对。
  • 兜底：对称型 NAT 直连打洞失败，回落到 TURN 中继转发。

2.5 STUN 与 TURN

一句话定位：STUN 轻量反问"我公网地址是啥"，TURN 是打不通时的中继兜底。

  • STUN（RFC 5389）：浏览器发包给 STUN 服务器，回包带源 IP:Port，得知 NAT 映射地址。
  • TURN（RFC 5766）：P2P 打不通时把媒体发到 TURN 服务器由它转发，代价是 TURN 的带宽与延迟；生产用 coturn。
  • 怎么判断走没走中继：看 selected pair 的 candidateType——host/srflx 是直连，relay 是中继。

2.6 DTLS 与 SRTP（加密层）

一句话定位：WebRTC 强制加密，握手期 DTLS 协商密钥，媒体面用 SRTP 加密。

  • DTLS-SRTP：交换 SDP 时附证书指纹，先做一次 DTLS 1.2 握手协商会话密钥，再用它把 RTP 包加密成 SRTP（AES + 认证）。
  • 推论：MediaRecorder 抓包看到的是加密流，SDP 里有 fingerprint 行。

时钟漂移 / 证书过期 / NAT 会话超时导致 DTLS 断，是 WebRTC"看几分钟黑一下"的高频根因，需要 ICE 重启恢复。

2.7 信令（Signaling）

一句话定位：WebRTC 规范故意不规定信令——交换 SDP/ICE 候选要应用自己搭。

  • 工程惯例：几乎都用 WebSocket（实时双向）；本项目经 Janus 的 WebSocket/HTTP 发 {janus:"create", ...} 类 JSON。
  • 一条完整信令链：创建会话句柄（handle）→ attach 到 streaming 插件 → getoffer 生成 SDP offer → setRemoteDescription → createAnswer → 回传 answer → 逐个互传 trickle ICE candidate。

2.8 getStats（质量统计）

一句话定位：唯一能在客户端定量回答"卡不卡、走没走中继、丢包多少"的接口。

  • inbound-rtp：framesReceived、freezeCount、jitter、packetsLost。
  • candidate-pair：当前选中链路与 bytesSent/bytesReceived。
  • track：framesDecoded、framesDropped。

本项目用它做质量看板与自动降级，而不是靠用户"看着卡不卡"的主观反馈。

3工作原理与流程

3.1 媒体协商时序：一次建连到底发生了什么

以本项目"浏览器作为 answer 端，从 Janus streaming 拉流"为例。Janus 生成 offer（描述它要发的 H.264 视频轨），浏览器应答。整个协商是一次严格的问答式状态机：

图 2 媒体协商与 ICE/DTLS 建连时序（示意）

  1. 收 offer：对端（Janus）通过信令发来 SDP offer。浏览器 setRemoteDescription(offer) 后，pc.signalingState 进入 have-remote-offer。
  2. 生成 answer：createAnswer() 从 offer 与本端能力的交集里选出编解码（通常 H.264 + Opus），setLocalDescription(answer)，状态进入 stable。
  3. Trickle ICE：两端各自异步收集 candidate，每收集到一个就立刻经信令发给对方并 addIceCandidate——不必等全部收完，这是"trickle"相对"等齐再发"的延迟优化。
  4. 连通性检查：ICE 代理对每个候选对发 STUN Binding，第一个双向都通的对被选中（nominated）。
  5. DTLS 握手：链路通后用 SDP 里的证书指纹做 DTLS 握手，派生出 SRTP 密钥。
  6. 媒体流到达：对端开始发 SRTP 包，浏览器解密解码、进 JitterBuffer，ontrack 回调触发，帧挂上 video/Canvas。

3.2 一帧视频从网络到屏幕的内部流水线

图 3 接收端一帧视频的处理流水线（示意）

这条流水线解释了本项目两个关键现象：① "多路同屏低 CPU" 的优化点不在网络而在解码与渲染——把不需要同时满帧率显示的小窗降到 15fps、复用同一个 Canvas 上下文、避免每路都新建 video 元素，是降 CPU 的主要手段；② "花屏/绿条" 几乎都是解码问题：丢了参考帧（关键帧请求 PLI/FIR 没生效）或硬解与 H.264 profile 不匹配。

4核心语法与 API 要点

4.1 建一条接收型 PeerConnection（本项目核心写法）

// 接收场景：本端不发，只收 Janus 的流。方向用 direction 控制，不是靠 addTrack。
var pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' }
  ]
});

// 关键：声明"我这端只收不发"；若走默认 sendrecv，本端被要求发流（往往要先 getUserMedia 采集摄像头，无设备的值班机就报错/弹权限框）
pc.addTransceiver('video', { direction: 'recvonly' });
pc.addTransceiver('audio', { direction: 'recvonly' });

// 远端轨到达：挂到 video 或喂 Canvas
pc.addEventListener('track', function (ev) {
  var stream = ev.streams[0] || new MediaStream([ev.track]);
  videoEl.srcObject = stream;          // 或：drawToCanvas(ev.track, canvas)
});

// trickle ICE：候选一来就发给 Janus
pc.addEventListener('icecandidate', function (ev) {
  if (ev.candidate) wsSend({ janus: 'trickle', candidate: ev.candidate });
});
两种写法对比：addTrack 声明发送 vs addTransceiver 显式声明方向。addTrack(track) 需要你传入一条本端 track（通常来自 getUserMedia()），并把该 transceiver 协商成 sendrecv——它本身不采集设备，弹摄像头权限是 getUserMedia() 的行为；纯接收端没有可发的本地流，硬走 sendrecv 方向也对不上。正确做法是 addTransceiver('video', {direction:'recvonly'})，这是"只看不发"播放器的标准写法。

4.2 answer 端的完整协商循环

async function handleRemoteOffer(offerSdp) {
  await pc.setRemoteDescription(new RTCSessionDescription({
    type: 'offer', sdp: offerSdp
  }));
  var answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);   // setLocal 后才开始收集 ICE 候选
  wsSend({ janus: 'answer', sdp: pc.localDescription.sdp });
}
// 收到对端 candidate：
async function addRemoteCandidate(cand) {
  try { await pc.addIceCandidate(new RTCIceCandidate(cand)); }
  catch (e) { /* 候选到达过早/过晚，忽略，不影响整体 */ }
}

4.3 Canvas 绘制视频轨（本项目的 OSD 叠加方案）

var ctx = canvas.getContext('2d');
function drawLoop() {
  // video 元素只是"解码后的帧容器"，可见性隐藏；这里把它的当前帧贴到 Canvas
  ctx.drawImage(videoEl, 0, 0, canvas.width, canvas.height);
  // 叠加 OSD：通道名 + 时间戳，随画面缩放自动对齐
  ctx.fillStyle = 'rgba(0,0,0,.45)';
  ctx.fillRect(0, 0, canvas.width, 22);
  ctx.fillStyle = '#7CFC00';
  ctx.font = '13px monospace';
  ctx.fillText('CH-01 ' + new Date().toLocaleTimeString(), 8, 16);
  requestAnimationFrame(drawLoop);
}
videoEl.addEventListener('loadedmetadata', drawLoop);

4.4 getStats：量化质量与判断是否走了中继

setInterval(function () {
  pc.getStats().then(function (report) {
    report.forEach(function (r) {
      if (r.type === 'inbound-rtp' && r.kind === 'video') {
        // framesDecoded 持续增长但 freezeCount 涨 → 卡；packetsLost 高 → 网络差
        console.log('解码帧:', r.framesDecoded, '冻帧:', r.freezeCount,
                    '丢包率:', r.packetsLost / (r.packetsReceived || 1));
      }
      if (r.type === 'candidate-pair' && r.selected) {
        // localCandidateType: host/srflx=直连, relay=TURN 中继
        console.log('当前链路:', r.localCandidateType, '→', r.currentRoundTripTime, 's');
      }
    });
  });
}, 2000);

5实战项目经验（实战落地）

5.1 项目背景：把变电站监控从 ActiveX 搬到浏览器原生

一句话定位：这是一个"去插件化 + 微前端整合"的监控播放端改造项目，业务量级是电力生产监控的长期常驻值班场景。

  • 业务场景：变电站摄像头实时监控，值班人员要在值班室多屏同看多路摄像头流，7×24 常驻。
  • 旧方案痛点：必须装 ActiveX 插件才能播流，绑定 IE；安全软件反复告警；每换一台值班机就要重装插件并过信息安全审计。
  • 后续整合：播放端要被 Qiankun 微前端整合成一个子应用，塞进可视化大屏系统 平台统一入口。
  • 目标：零插件、浏览器原生、端到端低延迟、多路同屏 CPU 可控、可独立部署为子应用。

5.2 我的角色与职责

  • 角色：前端负责人，独立承担播放端从技术选型到上线的全部前端工作。
  • 分工：后端同学负责 Janus 网关部署与摄像头接入；我负责浏览器端播放核心、信令对接、渲染与质量自愈；前端组另有同学做可视化大屏系统 主框架，我按子应用契约接入。
  • 协作边界：信令消息格式由我与后端共同定，质量指标口径双方一起对齐。

5.3 技术栈

  • 前端：WebRTC（RTCPeerConnection）+ Vue2 + Canvas 渲染。
  • 媒体/信令：Janus 网关（SFU，streaming 插件）+ WebSocket 信令。
  • 微前端：Qiankun，把播放器封装为独立部署的子应用。

5.4 落地设计：为什么是 SFU + recvonly + Canvas

  • 关键弃 P2P 选 SFU：多路摄像头源 × 多观看者，P2P 会把源端带宽打爆；摄像头流进 Janus streaming 插件，浏览器作为 answer 端拉流。
  • recvonly：浏览器只收不发，addTransceiver('video', { direction: 'recvonly' })。
  • 信令走 WebSocket：create → attach streaming → getoffer → 回 answer → trickle ICE。
  • Canvas 渲染而非 <video> 黑盒：把解码帧 drawImage 到 Canvas，统一叠加通道名/时间戳 OSD，多路绘制收敛到一个 rAF 循环。

5.5 关键实现要点

// 多路同屏：每一路一个 pc，但渲染共用池化的 video + Canvas，避免每路新建 DOM
function createPlayer(channelId, canvas) {
  var pc = new RTCPeerConnection({ iceServers: STUN_TURN });
  pc.addTransceiver('video', { direction: 'recvonly' });   // 只收不发，别用默认 sendrecv
  var hiddenVideo = document.createElement('video');
  hiddenVideo.muted = true; hiddenVideo.playsInline = true;
  pc.addEventListener('track', function (e) {
    hiddenVideo.srcObject = e.streams[0];
    hiddenVideo.play().catch(function () {/* 自动播放被拦：需用户手势解锁 */});
    bindDrawLoop(hiddenVideo, canvas, channelId);   // 进入统一 rAF 绘制池
  });
  return pc;
}

质量自愈侧：每 2s 调 pc.getStats() 采样 framesDecoded/freezeCount/packetsLost 与 candidate-pair 的 RTT/类型，触发 PLI 请求关键帧或 restartIce()。

var lastFreeze = 0, badStreak = 0;
setInterval(async function () {
  var s = await collectStats(pc);
  if (s.freezeCount - lastFreeze > 0 && s.lossRate > 0.05) {
    badStreak++;
    if (badStreak >= 3) { requestKeyframe(); badStreak = 0; }   // 丢参考帧→请求关键帧
  } else { badStreak = 0; }
  lastFreeze = s.freezeCount;
  if (s.rtt > 0.6 || s.linkType === 'relay') pc.restartIce();   // 链路劣化，ICE 重启
}, 2000);

5.6 真实问题与解法（含量化前后对比）

  • 坑自动播放策略：Chrome 要求带声音媒体需用户手势，muted 后仍偶发 play() reject——catch 后在用户点击页面补一次 play。
  • 坑忘了 recvonly：第一版默认 sendrecv，打开页面就弹摄像头权限、在无摄像头值班机建连失败——改 recvonly 后消失。
  • 坑企业网封 UDP：部分现场只能走 TURN relay，延迟上升。前后对比（估算）：靠 getStats 的 candidateType 监控走中继的路数，把"多少路在 relay"从无监控做到可见，超阈值即扩容 TURN。
  • 坑GPU 上下文爆炸：多路每路新建 video+Canvas 导致 GPU 上下文过多——改池化 + 降帧后稳住。
  • 坑PLI 不是浏览器直接发：要经信令告诉 Janus；restartIce() 必须配合一次新 offer/answer 才算完整重启。

5.7 量化成果

  • 彻底下线 ActiveX：值班机零安装，信息安全审计环节取消插件安装项。
  • 延迟：端到端从插件方案数秒压到约 300-500ms（估算），满足实时监控。
  • 同屏性能：4 路同屏在普通办公机上 CPU 占用可控（池化渲染后）。
  • 可维护性：作为 Qiankun 子应用独立部署/独立路由，主框架升级不影响播放端。

5.8 协作与排期过程

  • 契约先行：先与后端定 WebSocket 信令消息表（create/attach/offer/answer/candidate/PLI），再各自开发。
  • 联调协商点：TURN 服务器地址、STUN/TURN 凭据、信令房间与通道映射，均现场网络环境下反复联调。
  • 排期：按"单路打通 → 多路同屏 → 质量自愈 → Qiankun 子应用封装"分迭代推进，每阶段现场真机验证。

5.9 复盘与可复用经验

  • 要点媒体面与信令面分离：WebSocket 只管控制信令、WebRTC 只管媒体，职责清晰才好排障。
  • 要点接收端默认 recvonly：纯拉流场景别用默认方向，省掉一堆权限/建连坑。
  • 要点质量要可观测：getStats 采样 + 规则自愈，把"偶发花屏"从人肉反馈变成自动恢复。

5.10 面试讲法（一句话抓手）

一句话抓手："我把变电站监控从 ActiveX 插件改成浏览器原生 WebRTC 拉流，用 Janus SFU + recvonly + Canvas 池化渲染做到 300-500ms 低延迟多路同屏，并用 getStats 做了丢帧自动请求关键帧的自愈。"

6易错点与面试重点

6.1 signalingState 状态机乱跳

一句话定位：协商是严格状态机，stable 之外再 createOffer 必错位。

  • 坑现象：建连偶发报 InvalidStateError: Failed to execute 'setLocalDescription'。
  • 原因：stable 状态下才能发新一轮 offer；have-local-offer 时又 createOffer，或 answer 端未 setRemoteDescription 就 createAnswer，都会错位。
  • 正解：一次协商一轮完整往返；中途改方向/加轨走 onnegotiationneeded 触发的增量重协商，别手动再 createOffer。

6.2 recvonly 漏设，纯接收页弹摄像头权限

一句话定位：不声明 direction，浏览器默认 sendrecv，打开就弹采集。

  • 坑现象：监控播放页一打开就要摄像头/麦克风权限，无设备机器直接失败。
  • 原因：addTrack 或 addTransceiver 不指定 direction，默认 sendrecv，浏览器认为本端要发送。
  • 正解：纯拉流端一律 addTransceiver('video',{direction:'recvonly'})，并确认 offer/answer 方向一致。

6.3 trickle ICE 候选到达顺序乱

一句话定位：候选异步乱序到达，可能早于 remoteDescription set 完。

  • 现象：候选经信令乱序到达，偶发 addIceCandidate 报错。
  • 正解：addIceCandidate 包 try/catch 容忍"过早到达"；或先缓存候选，等 setRemoteDescription 完成后批量补加。

6.4 HTTPS/localhost 限制与权限

一句话定位：WebRTC 与媒体采集只在安全上下文（HTTPS/localhost）可用。

  • 坑现象：普通 http 页面 getUserMedia / RTCPeerConnection 直接 undefined 或被拒。
  • 正解：生产必须 HTTPS（信令走 wss）；本地调试用 localhost 或自签证书。

6.5 UDP 被企业防火墙封死

一句话定位：家里通、现场超时，多半是 UDP 被封且没配 TURN。

  • 坑现象：现场建连超时，getStats 一直没有 selected candidate-pair。
  • 原因：现场防火墙封 UDP，host/srflx 候选都打不通，又没配 TURN。
  • 正解：部署 TURN（coturn）配 relay 候选，让流量回落到 TCP/TLS 中继；监控 relay 比例做成本与体验平衡。

6.6 花屏 = 丢关键帧，而非网络"卡"

一句话定位：绿条/马赛克是丢了 H.264 参考帧，要主动请求 IDR。

  • 坑现象：画面绿条/马赛克，过一会儿自己好。
  • 原因：H.264 帧间依赖，丢参考帧后后续 P 帧无法正确解码，直到下个 IDR 关键帧到来才恢复。
  • 正解：主动发 PLI/FIR 请求对端立即出关键帧（经 SFU），配合 getStats 丢包率自动触发。
