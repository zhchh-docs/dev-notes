技术栈详解 · 04 实时通信

音视频基础与流媒体协议

标准 定位：从裸数据到一帧画面的分层——编码、封装、传输、加密各管一段

WebRTC 浏览器那端的"黑盒"背后，是一整套音视频技术栈：像素经 H.264 编码成码流、封进 RTP、用 SRTP 加密、经 UDP 在 ICE 选好的链路上传输，接收端再抖动缓冲、解码上屏。本页把这四层讲清，并以 WebRTC 无插件播放器项目里实际配置的 H.264/Opus 参数、SRTP/DTLS、ICE 流程为例，最后解释"延迟到底从哪来"。

1简介与阅读指引

1.1 定位：分层协议族，而非单一技术

音视频技术栈 = "压缩 + 打包 + 传输 + 加密"的分层组合：编码层（H.264/H.265 视频、Opus/AAC 音频——把原始像素/采样压成码流）→ 封装层（MP4/FLV 混装轨道成文件；RTP 把码流拆成实时传输的包）→ 传输层（RTP/RTCP over UDP 实时传包与反馈，或 HLS over HTTP 传分片）→ 安全层（DTLS 协商密钥、SRTP 加密媒体包）。它同时解决两件事：压缩（1080p 原始每秒上百 MB 传不动）与低延迟传输（TCP 队头阻塞越等越卡）。

1.2 横向对比：三种流媒体路线选型

协议承载延迟量级典型用途
WebRTCSRTP over UDP200-500ms实时监控、视频会议、互动直播
HTTP-FLVFLV over HTTP1-3s网页直播（flv.js），抗弱网
HLSTS 分片 over HTTP3-30s点播、回看、大规模 CDN 分发
RTSPRTP over UDP/TCP低，但浏览器不原生支持摄像头设备侧

口径：实时监控/会议选 WebRTC，直播推流选 RTMP/HTTP-FLV，点播回看与大规模分发选 HLS。

1.3 学习目标与阅读指引

  1. 分清编码 vs 封装（正交的两件事）；
  2. 理解 I/P/B 帧与 GOP——花屏自愈的钥匙；
  3. 讲清为什么实时用 UDP（队头阻塞）；
  4. 会拆端到端延迟构成（选型的核心问题）；
  5. 能读懂 SDP 里的编码协商行。

前置知识：无（本模块地基篇）。难度：★★★☆☆。本篇不涉及：WebRTC 连接建立细节（05 篇展开）、Janus 服务端（06 篇）。

2核心模型

五个核心模型：视频编码（总纲）→ 音频编码→ RTP/RTCP→ 封装格式→ SRTP/DTLS/ICE。

2.1 视频编码：H.264 与 I/P/B 帧

视频编码的本质是时间与空间冗余压缩：关键I 帧（自包含可独立解码，体积最大）、P 帧（只存与前面帧的差值）、B 帧（双向预测）；GOP = 两个 I 帧的间隔。坑丢一个 P 帧（参考帧）会花屏直到下一个 I 帧——这就是前端要能主动发 PLI/FIR 让编码器立刻出 I 帧的原因（06 篇实战）。

2.2 音频编码：Opus

原始数据量 = 采样率 × 位深 × 声道数；Opus（WebRTC 默认）：6-510kbps 可调，融合 SILK（语音）+CELT（音乐），抗丢包低延迟；AAC 偏点播/音乐消费。参数配在 SDP 的 m=audio 行。

2.3 RTP 与 RTCP：数据面与控制面

RTP：把 H.264/Opus 切成带序列号与时间戳的包跑在 UDP 上——序列号查丢包乱序，时间戳做唇形同步；RTCP：周期性互发报告（丢包率/抖动/RTT），供拥塞控制与码率自适应。Why UDP：TCP 丢包重传阻塞后续所有包（队头阻塞），实时场景宁可丢几帧也不能越等越卡——"丢了怎么办"交给上层（请求关键帧/NACK）。

2.4 封装格式：MP4/FLV vs RTP

编码解决"怎么压"，封装解决"怎么装"，两者正交。MP4 是点播容器（moov 元信息头或尾）；FLV 为 HTTP-FLV 直播流式设计；实时场景不用文件容器——直接把 NALU 拆进 RTP 包（RFC 6184），省掉整段封装等待，这正是 WebRTC 低延迟的一部分。flv.js 解的是 FLV 容器，把 H.264 喂给 MSE，真正解码的是浏览器。

2.5 SRTP/DTLS 与 ICE：安全与找路

DTLS 握手期协商密钥 → SRTP 用这把密钥加密后续 RTP 包 → ICE 在 NAT 后找一条能通的链路（host/srflx/relay 候选 + STUN 打洞）——三者构成传输/加密层（05 篇展开）。

3核心用法（按场景）

3.1 场景一：读懂 SDP 编码协商行

m=video 9 UDP/TLS/RTP/SAVPF 96 97       ; 视频媒体行：端口/传输/负载类型
a=rtpmap:96 H264/90000                   ; pt=96 对应 H.264，90kHz 时钟
a=fmtp:96 profile-level-id=42e01f;packetization-mode=1
a=rtpmap:97 rtx/90000                    ; 重传负载（NACK）
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2                ; pt=111 对应 Opus，48kHz 双声道
a=fingerprint:sha-256 AB:CD:...           ; DTLS 证书指纹
a=setup:actpass                          ; 本端既可做 DTLS client 也可做 server

排查"协商出了什么编码"的基本功：m= 行列支持的 payload type，a=rtpmap 映射到编码与时钟，a=fmtp 给编码参数（profile-level-id=42e01f 是 Constrained Baseline，兼容性最好）。

3.2 场景二：协商时限定编码

// 用 setCodecPreferences 把 H.264 排到首选，避免协商出兼容性差的编码
var sender = pc.getSenders()[0];
var codecs = RTCRtpSender.getCapabilities('video').codecs;
var h264 = codecs.find(function (c) { return c.mimeType === 'video/H264'; });
if (h264) sender.setCodecPreferences([h264].concat(codecs));
// 注：纯接收场景由对端 offer 决定，这里用于本端需要约束编码的情况

3.3 场景三：编码器侧参数（前端需理解）

# ffmpeg 把 RTSP 转 WebRTC 喂 Janus 时的常见参数（理解用）
# -c:v libx264        用 H.264 软编码
# -profile:v baseline 选兼容性最好的 profile，老浏览器/硬解都支持
# -g 30               GOP=30：每 30 帧一个关键帧（1s@30fps），花屏恢复快
# -preset ultrafast   降低编码延迟（牺牲压缩率）
# -tune zerolatency   专为低延迟直播调优

3.4 场景四：前端连接配置（与后端契约）

var pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' }

  // 不传 iceTransportPolicy=relay：优先直连，失败再中继

// 打印协商出的实际编码，便于排查

4进阶知识点【进阶】

首次学习可整章跳过。前置：I/P/B 帧与 UDP 之问已清楚。

4.1 NACK / PLI / FIR：丢包恢复三件套

NACK：丢包后按序列号点名重传（毫秒级，适合偶发丢包）；PLI/FIR：请求编码器立刻出新 I 帧（代价大，适合参考帧丢失/新加入者）；FEC：前向纠错冗余包，丢一部分可自行恢复（带宽换恢复速度）。三者是 WebRTC 抗丢包的完整拼图，与"花屏自愈"直接挂钩。

4.2 码率自适应（GCC 拥塞控制）

RTCP 报告的丢包率/RTT + Transport-CC 反馈 → 带宽估计 → 编码器动态调码率/分辨率/帧率。弱网下先降帧率再降分辨率（人眼对帧率敏感度高于分辨率）——这是 WebRTC "越弱网越糊但不断"的原因。

4.3 LL-HLS 与 WebRTC 的中间地带

HLS 走分片路线延迟下限受切片时长约束；LL-HLS 用更短分片（2s）+ 部分分片 + 阻塞式播放列表刷新压到 2-5s——但复杂度陡增。选型再平衡：亚秒级只有 WebRTC/SRT 路线；2-5s 用 LL-HLS；普通分发 HLS 最省。

4.4 MSE 与 MediaSource 扩展

浏览器原生 video 只吃 MP4/WebM 容器；MSE 允许 JS 把媒体段（fMP4/TS）喂进 SourceBuffer 实现流式播放——flv.js/hls.js/dash.js 的共同地基（01 模块 HTML5 媒体篇呼应）。排错基本功：SourceBuffer 的 updateend 事件与 buffered ranges。

4.5 转码与协议网关的位置

摄像头出 RTSP → 流媒体服务器（ZLMediaKit/SRS）协议转换 → 浏览器吃 WebRTC/HTTP-FLV/HLS；跨协议需转封装（快、无损）或转码（慢、有损）。架构口径：设备侧 RTSP 不会消失，浏览器侧只认 HTTP/WebRTC——网关是必然存在的中间层（06 篇 Janus 展开）。

6最小可运行 Demo

性质：真实实战——WebRTC 无插件播放器（2020-2022），变电站摄像头流在浏览器低延迟播放；值班现场有内核较旧的机器，编码兼容性是硬指标。

6.1 角色与落地设计

  • 分工：后端/网关侧管编码参数与加密开关；前端管 RTCPeerConnection 配置、SDP 协商结果验证、打洞策略；
  • 关键取舍：选 H.264 baseline（兼容现场老硬解机器，High profile 老机器解不动花屏）；GOP 约 1 秒（丢参考帧后恢复快）；DTLS-SRTP 加密；ICE 优先直连不强制 relay。

6.2 踩坑记录（含量化对比）

  • 坑profile 与解码端能力不匹配：后端最初用 High profile，现场几台老机器解码失败花屏——统一降到 baseline 解决；
  • 坑现场封 UDP：ICE 全部失败——补 TURN 后才通；
  • 坑GOP 设太长：5 秒一个 I 帧时丢参考帧要等很久才恢复；前后对比：改约 1 秒 GOP 后花屏自愈明显变快。

6.3 成果与复盘

  1. 量化：端到端延迟稳定约 300-500ms（估算）；老机器兼容播放；偶发花屏靠 PLI + 短 GOP 自愈；
  2. 契约先行：与后端定编码 profile/GOP/加密开关/STUN-TURN 地址再联调；老机器花屏时比对协商 mimeType 与解码能力定位到 profile；
  3. 可复用经验：兼容性优先 baseline（有老机器的场景别盲目上 High profile）；短 GOP + PLI 是花屏自愈的关键旋钮。

7常见坑 & Debug

五条高频坑。

7.1 编码与封装分不清

误区：把 MP4 当成"一种视频编码"。正解：H.264 是编码（怎么压），MP4 是封装（怎么装），两者正交。

7.2 为什么实时传输用 UDP 不用 TCP

TCP 队头阻塞：丢一个包，后面所有包都要等它重传，实时流越堵越延迟；UDP 把丢包恢复（请求关键帧/NACK）交给应用层——RTP 正跑在 UDP 上。

7.3 花屏 = 丢参考帧，不是"网络卡"

正解：主动发 PLI/FIR 让对端立刻出关键帧；同时控制 GOP 长度缩短自愈等待。

7.4 HLS 为什么做不了实时

原因：先切完整分片（≥6s）再 HTTP 下发，经 CDN 缓存与播放器缓冲。正解：实时监控选 WebRTC（或 LL-HLS），HLS 留给回放与大规模分发。

7.5 JitterBuffer 越长越好吗

不是：缓冲大→弱网不卡但延迟高；缓冲小→延迟低但一抖就卡/花屏。WebRTC 的 JitterBuffer 动态自适应，不要手动压死。

8重点讲解

Q1：音视频技术栈分几层？各自的代表技术是什么？

参考答案：四层——①编码层：H.264/H.265 视频、Opus/AAC 音频，解决"原始数据压到可传输的码率"（时间/空间冗余压缩）；②封装层：MP4/FLV 把轨道混装成文件，实时场景不用文件容器直接 RTP 拆包；③传输层：RTP/RTCP over UDP（序列号查丢包、时间戳做同步、RTCP 报告供码率自适应），或 HLS over HTTP；④安全层：DTLS 协商密钥 + SRTP 加密 + ICE 找路。关键认知：编码与封装正交；编码决定"画质 vs 码率"，传输协议决定"延迟 vs 抗丢包"。

Q2：为什么实时音视频用 UDP 而不是 TCP？花屏是怎么产生的、怎么自愈？

参考答案：UDP 的理由——TCP 保证可靠但有队头阻塞：丢一个包，后面所有包都要等它重传，实时流越堵越延迟；实时场景宁可丢几帧也不能等，把恢复交给应用层（NACK 点名重传/PLI 请求关键帧/FEC 冗余）。花屏的因果：视频帧分 I（自包含）/P/B（依赖参考帧），丢了参考帧，后续帧全部解不出来，直到下一个 I 帧才恢复——所以自愈两旋钮：①主动发 PLI/FIR 让编码器立刻出新 I 帧；②控制 GOP 长度（实战从 5s 压到 1s，花屏恢复从秒级到亚秒级）。

Q3：端到端延迟由哪几段构成？为什么 HLS 做不了实时监控？

参考答案：五段累加——采集编码（帧间隔/GOP 策略）→ 网络传输（直连低、TURN 中继高）→ 抖动缓冲（最大且最可调的一段，"抗抖 vs 延迟"的权衡）→ 解码（硬解快）→ 渲染上屏。HLS 慢的结构性原因：必须先切满一个完整分片（≥6s）再 HTTP 下发，加 CDN 缓存与播放器缓冲，轻松 3-30s——这是协议设计决定的，不是调优能解决的；所以实时监控选 WebRTC（稳态 200-500ms：一次 DTLS 握手+ICE 打洞后只剩缓冲与网络延迟），HLS 留给点播回看与大规模 CDN 分发，中间地带用 LL-HLS（2-5s）。
