WebSocket 通用实时通信

基础 定位：全双工长连接、HTTP 握手升级、心跳与断线重连——WebRTC 信令的承载通道

HTTP 是"请求-响应、一问一答"，服务器无法主动推消息给浏览器。WebSocket 在一次 HTTP 握手后把连接升级成长连接，双方随时互发数据。本页讲握手升级、数据帧、心跳保活与断线重连四个核心心智，并交代它在 WebRTC 无插件播放器里承担的"信令通道"角色——媒体走 WebRTC，信令走 WebSocket。

1技术点概览

是什么：WebSocket（RFC 6455，2011）是一种在单个 TCP 连接上进行全双工（full-duplex）通信的协议：

  • 本质：先借 HTTP 发起一次握手（带 Upgrade: websocket 头），服务器同意后协议切换为 WebSocket，此后这条连接双方都能随时主动发数据。
  • 与 HTTP 关系：握手阶段是普通 HTTP，握手成功后"升级"成独立的 ws:// 协议，不再是一问一答。

解决什么问题：在 WebSocket 之前，浏览器想拿实时数据只能轮询（反复发 HTTP 请求问"有新消息吗"），既浪费请求又有秒级延迟。WebSocket 把"高频双向消息"变成一次建连、长期复用：

  • 典型场景：聊天室、实时看板、协同编辑、在线客服、行情推送。
  • 在本技术栈里的位置：它是 WebRTC 无插件播放器的信令通道——客户端与 Janus 网关交换 SDP/ICE 用的就是 WebSocket，媒体流本身走 WebRTC（见 sec5）。

2核心概念

2.1 握手与协议升级（Handshake & Upgrade）

一句话定位：WebSocket 不是另起端口，而是复用 80/443 端口、用 HTTP 头"协商升级"成 ws 协议。

  • 客户端发起：发一个普通 HTTP GET，头里带 Upgrade: websocket、Connection: Upgrade、Sec-WebSocket-Key（随机值）。
  • 服务器应答：同意升级则回 101 Switching Protocols，并把 Key 拼成固定串做 SHA-1 再 base64 放进 Sec-WebSocket-Accept，证明"我真的懂 WebSocket"。
  • 之后：同一条 TCP 连接进入 ws 帧交换阶段，不再走 HTTP 请求-响应。
  • 关键为什么重要：复用 80/443 端口意味着能穿过绝大多数企业代理与防火墙，这是它能在 WebRTC 信令里落地的前提。

2.2 数据帧（Frame）

一句话定位：升级之后所有消息都按"帧"切分传输，每帧带类型位。

  • 帧类型：文本帧（opcode 0x1）、二进制帧（0x2）、关闭帧（0x8）、ping（0x9）/pong（0xA）控制帧。
  • 分片：一条大消息可被拆成多个连续帧，最后一帧 FIN 位置 1，接收方拼起来。
  • 掩码：浏览器发往服务器的帧必须带掩码（mask），防中间设备把帧误判成 HTTP 注入——服务器到浏览器方向不掩码。
  • 要点前端层面：用 ws.send(str) 发文本、ws.send(blob/ArrayBuffer) 发二进制，收消息在 onmessage 里拿 event.data，帧细节由浏览器封装好，业务不用手解。

2.3 心跳与保活（Heartbeat / Ping-Pong）

一句话定位：长连接会被中间设备"静默掐断"，必须靠心跳判断连接是否还活着。

  • 为什么需要：Nginx、负载均衡、运营商网关常有"空闲超时"，连接没人说话就被关，但浏览器不知道，表现为"假在线、发消息没反应"。
  • 做法：前端定时（如每 20-30 秒）发一个小心跳（文本或原生 ping），服务器回 pong；一段时间收不到回包就主动重连。
  • 关键心跳间隔：要小于中间设备的空闲超时（常见 60s），否则心跳还没发连接就断了。

2.4 断线重连（Reconnection）

一句话定位：网络抖动、切后台、服务重启都会断，前端必须自动重连并恢复会话。

  • 触发点：onclose 事件里判断不是主动关闭，就进入重连流程。
  • 关闭码语义：e.code===1000 为正常关闭、1001 going away（页面跳转/服务器重启）、1006 异常断开（根本没收到 close 帧）；1001/1006 都应走重连，只有 1000 才是主动关闭。
  • 退避策略：不要立刻疯狂重连（重连风暴会压垮服务器），用指数退避（1s→2s→4s…封顶），并加随机抖动。
  • 会话恢复：重连后带上之前的会话 id/token，服务器据此恢复订阅关系，避免丢消息。

3工作原理与流程

一句话定位：一次握手升级成多帧互发，是 WebSocket 全部工作原理的主干。

图 2 WebSocket 从 HTTP 握手到全双工帧交换的时序（示意）

  1. ① 握手请求：浏览器用普通 HTTP GET 发起，头里声明要升级到 websocket，并带一个随机 Key。
  2. ② 升级应答：服务器回 101，并把 Key 计算成 Accept 值——这一步证明双方都按 WebSocket 规范说话，连接就此"变身"。
  3. ③④ 全双工互发：此后浏览器能发、服务器也能主动推，不再是请求-响应，一条连接复用到底。
  4. ⑤ 心跳保活：定期 ping/pong 探活，一旦超时没回包，前端判定连接已死并触发重连。

关键理解：WebSocket 只解决"双向、实时、低开销的消息通道"，它不负责媒体压缩与抖动缓冲——所以 WebRTC 播放器里，WebSocket 管信令、WebRTC 管媒体，分工互补。

4核心语法与 API 要点

4.1 建立连接与收发消息

// 建立连接（wss:// 是加密版，生产必须用 wss）
const ws = new WebSocket('wss://example.com/ws/signaling');

ws.onopen = () => {
  console.log('信令通道已建立');
  ws.send(JSON.stringify({ type: 'join', room: 'live-101' }));
};

ws.onmessage = (event) => {
  const msg = JSON.parse(event.data); // 业务消息约定用 JSON 文本帧
  switch (msg.type) {
    case 'offer': handleRemoteOffer(msg.sdp); break;
    case 'candidate': handleIceCandidate(msg.candidate); break;
  }
};

ws.onclose = (e) => {
  // 非主动关闭（code 不是 1000）就进入重连
  if (e.code !== 1000) reconnect();
};

ws.onerror = (err) => console.error('ws error', err);

4.2 带心跳与指数退避重连的封装

let timer = null, backoff = 1000;

function startHeartbeat(ws) {
  timer = setInterval(() => {
    if (ws.readyState === WebSocket.OPEN) ws.send('__ping__');
  }, 25000); // 小于中间设备 60s 空闲超时
}

function reconnect() {
  clearInterval(timer);
  setTimeout(() => {
    const ws = new WebSocket(URL);
    // ...绑定事件、恢复会话 id
    backoff = Math.min(backoff * 2, 15000); // 指数退避，封顶 15s
  }, backoff + Math.random() * 1000); // 加随机抖动，避免重连风暴
}

4.3 readyState 状态机

常量值含义
CONNECTING0连接正在建立，还不能 send
OPEN1连接就绪，可收发
CLOSING2正在关闭
CLOSED3已关闭或连接失败

要点发消息前务必判断 ws.readyState === WebSocket.OPEN，否则在 CONNECTING 阶段 send 会直接抛错。

5实战项目经验（自学 + 自建 Demo）

说明：本节是自学 + 自建 Demo，非生产环境项目。下面的聊天室 demo 用于亲手验证握手、心跳与重连；同时挂靠一段在实践中真实项目里的相邻经验（WebRTC 播放器信令），二者严格区分。

5.1 自学背景与动机

一句话定位：补"长连接怎么保活、怎么自动重连"这块只懂概念、没亲手搭过的缺口。

  • 缺口：在实践中真实项目里用过 WebSocket 作信令，但心跳/重连是现成封装。想自己从零写一遍，吃透连接生命周期。

5.2 搭建的 Demo 是什么

  • 功能：一个多房间聊天室——加入房间、广播消息、定时心跳、断线自动重连。
  • 技术栈：Node + ws 库做服务端，原生 WebSocket API 做前端，单页面。
  • 规模：本地单机 demo，房间内广播，几十条消息量级。

5.3 落地步骤（含关键代码）

// 服务端（Node + ws）：按房间广播
const WebSocket = require('ws');
const wss = new WebSocket.Server({ port: 8080 });
wss.on('connection', (ws) => {
  ws.on('message', (data) => {
    const msg = JSON.parse(data);
    if (msg.type === 'join') ws.room = msg.room;
    // 广播给同房间其它连接
    wss.clients.forEach((c) => {
      if (c.readyState === WebSocket.OPEN && c.room === ws.room) c.send(data);
    });
  });
});

前端心跳 + 指数退避重连（见 sec4.2）：每 25s 发 __ping__，断线后按 1s→2s→4s 封顶重连。

5.4 自学过程中遇到的坑与解决

  • 坑无心跳时连接"假死"：本地跑很久没人发消息，socket 被系统静默关——补心跳后才发现这个问题真实存在。
  • 坑重连风暴：一开始 onclose 立刻重连，服务端一重启客户端疯狂连——加指数退避 + 随机抖动解决。
  • 坑send 时机：在 CONNECTING 阶段 send 抛错——加 readyState===OPEN 判断。

5.5 成果（可验证能力清单）

  • 要点能从零跑通一个带房间广播、心跳、指数退避重连的 WebSocket 聊天室；可复现步骤：npm i ws → 跑上面服务端 → 浏览器开两个标签页同房间收发。

6易错点与面试重点

  • 坑以为 WebSocket 能传大文件/流媒体：它只是消息通道，不是媒体协议。原因：WebSocket 没有抖动缓冲、没有音视频编解码与丢包恢复。正解：大文件分片走 HTTP，音视频实时流走 WebRTC，WebSocket 只传控制信令。
  • 坑忘记心跳导致"假在线"：现象是页面没报错但收不到消息。原因：中间代理空闲超时静默断连，浏览器没收到 close 事件。正解：定时 ping/pong + 超时判死 + 重连。
  • 坑重连不加退避：服务一抖动，所有客户端瞬间同时重连形成"重连风暴"把服务器压垮。正解：指数退避 + 随机抖动。
  • 坑生产用 ws:// 明文：企业网关会拦、数据明文可被窃听。正解：全站 https 配套 wss://。
  • 面试高频：HTTP 轮询 / 长轮询 / SSE / WebSocket 怎么选？答：SSE 是服务器单向推、实现简单适合日志流；WebSocket 双向全双工适合互动；轮询简单但浪费请求——按"是否需要双向"与"消息频率"取舍。
