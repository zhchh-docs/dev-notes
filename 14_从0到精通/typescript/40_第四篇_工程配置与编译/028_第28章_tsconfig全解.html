28.1 配置文件发现规则：tsc 去哪儿找配置

先立一个心智模型：tsconfig.json 不是一个"配置库"，而是一次编译的起点。tsc 从"配置所在目录"出发，按 include 圈出所有要编译的文件——所以"在哪个目录运行 tsc"和"配置写了什么"同等重要。

npx tsc                     # 从当前目录向上逐层查找 tsconfig.json，找到最近的那个
npx tsc --project ./configs/tsconfig.build.json   # -p/--project 显式指定（目录或文件）
npx tsc -p .                # 指定当前目录的 tsconfig.json
npx tsc src/index.ts        # 陷阱！指定了具体文件后，tsconfig.json 会被完全忽略

记住一条反直觉规则：一旦在命令行直接给了 .ts 文件，tsconfig.json 就整个失效——不是"部分生效"。想用配置又只想编译个别文件，只能调 include 或用 -p 换配置文件。另外常见查找顺序是先 tsconfig.json，再 jsconfig.json（纯 JS 项目用后者，规则相同）。

编辑器（VS Code）用的配置和命令行用的配置可能不是同一份：编辑器按"当前打开文件向上找"的规则定位 tsconfig。如果某个目录里藏着另一份 tsconfig，编辑器对那里文件的检查结果会和命令行不一致——这是"我本地没报错、CI 却红了"的经典来源。

28.2 核心六组选项总览

tsconfig 里有两百多个选项，但真正决定一个项目"性格"的只有六组。先给全景，后面章节逐一展开：

六组选项管什么展开章节
module / moduleResolution输出什么模块语法 + 怎么找 import 的文件第 29 章
target / lib语法降到哪个 JS 版本 + 认识哪些新 API第 31 章
strict（全家桶）类型检查有多严第 30 章
include / exclude / files这次编译圈进哪些文件本章 28.3
outDir / rootDir编译产物放哪、源码根目录在哪本章 28.3
esModuleInteropESM 与 CommonJS 的互操作兼容本章 28.4
 
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "outDir": "./dist",
    "esModuleInterop": true
  },
  "include": ["src"]
}

tsconfig.json 本质是一个 JSON with Comments 文件（jsonc）：允许写注释、允许尾逗号，但禁止代码。所以给配置加注释是完全合法且强烈推荐的——三个月后没人记得 skipLibCheck 为什么是 true。

28.3 文件范围与输出：include / exclude / files / outDir / rootDir

圈范围用前三个选项，三者的关系是"files 精确点名，include 按模式圈，exclude 再挖掉"：

{
  "files": ["src/main.ts"],              // 精确列出（适合入口极少的小项目）
  "include": ["src/**/*", "test"],       // glob 圈定：** 任意层目录，* 任意文件名
  "exclude": ["src/legacy", "**/*.test.ts"]
}

两个坑：① exclude 挡不住"被 import 进来"的文件——它只影响"从哪里开始圈"，一旦 src/a.ts import 了 src/legacy/old.ts，old.ts 照样进编译；② glob 里 * 不匹配任何目录分隔符，跨目录必须用 **。没写 include 时默认圈当前目录下所有文件——这也是很多项目"一编译跑出一堆无关报错"的原因。

控输出用 outDir / rootDir。不配 rootDir 时，TS 会用"所有输入文件的最长公共父目录"当根：

src/index.ts
src/utils/math.ts          源码

不配 rootDir：             配了 "rootDir": "src"：
dist/                      dist/
  src/index.js               index.js        ← 干净，没有多余的 src 层
  src/utils/math.js          utils/math.js
如果某个输入文件跑到了 rootDir 之外（比如把 ../shared/type.ts import 进来），tsc 直接报错 TS6059：'xxx' is not under 'rootDir'。这是刻意的保护——防止输出目录里的相对结构无法预测。

28.4 esModuleInterop：一个救过无数报错的开关

JS 的两套模块体系（ESM 与 CommonJS，JS 书 71 章回收）在"默认导出"上互相看不顺眼。不开 interop 时，TS 按最保守规则处理，于是你会撞上经典报错：

import fs from "fs"        // ❌ TS1259：模块没有默认导出（未开 interop 时）
// 因为 fs 是 CommonJS 的 module.exports = {...}，TS 认为"只能整包命名导入"

const fs2 = require("fs")  // ❌ TS2597：ESM 语法里根本没有 require 这个名字
{
  "compilerOptions": {
    "esModuleInterop": true,   // 允许 import 默认导入 CommonJS 模块
    "allowSyntheticDefaultImports": true,  // 仅放宽类型检查（被 interop 包含）
    "module": "commonjs"       // interop 在输出为 CJS 或 node16 方案下才真正"垫代码"
  }
}

esModuleInterop 开启后做两件事：编译层面给默认导入垫一个 __importDefault 包装（把 module.exports 整包当成 default），类型层面自带 allowSyntheticDefaultImports。今天所有脚手架默认开它——你几乎从不需要思考，但必须认识它，因为接手老项目时它常常是缺的那块。

28.5 compilerOptions 速查表

遇到不认识的选项，先在这张表里定位它属于哪一类，再决定要不要深挖：

类别代表选项一句话
语言与目标target / lib / jsx输出什么版本 JS、认识哪些 API（31 章）
模块module / moduleResolution输出模块语法 + 找文件算法（29 章）
检查严格度strict 及其 8 个子开关检查多严（30 章）
文件范围include / exclude / files圈进哪些文件
输出outDir / rootDir / noEmit产物位置；noEmit = 只检查不出文件
声明文件declaration / declarationMap是否生成 .d.ts（32 章）
互操作esModuleInterop / allowJsCJS 兼容；把 .js 也纳入检查
路径baseUrl / paths@/ 别名（29 章）
工程化incremental / composite增量缓存与项目引用（33 章）
体检豁免skipLibCheck跳过第三方 .d.ts 内部检查，几乎必开
顶层选项（与 compilerOptions 平级）同样重要：compileOnSave、extends（继承另一份 tsconfig，monorepo 标配）、typeAcquisition、以及 33 章的 references。

28.6 tsc --init 逐块解读

mkdir ts-demo && cd ts-demo
npm init -y
npx tsc --init          # 生成一份带几百行注释的 tsconfig.json

生成物是一大段注释掉的"选项目录"，只有底部几行是生效的。逐块读懂它，等于过了一遍选项地图：

{
  "compilerOptions": {
    /* 语言与环境 */
    "target": "es2016",              // 输出 ES2016 语法（31 章讲怎么选）
    /* 模块 */
    "module": "commonjs",            // 输出 CJS（Node 默认；前端项目通常改 ESNext）
    // "moduleResolution": "node10", // 找文件算法（29 章）
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,  // 大小写敏感性统一，防 Windows/Linux 差异
    /* 检查 */
    "strict": true,                  // 严格全家桶总开关（30 章）
    "skipLibCheck": true,
    /* 输出 */
    // "outDir": "./dist",
    "noEmit": false
  }
}

解读方法就一条：按"语言目标 → 模块 → 检查 → 输出 → 工程化"五个区块扫，每个区块先看默认值是什么、再想自己项目该改成什么。tsc --init 的默认值偏保守（es2016 + commonjs），而现代前端模板（Vite 等）给的是 ESNext + bundler——两份配置的差异本身就是最好的教材。

tsconfig.json 改动后，编辑器通常要重载 TS 服务才生效（VS Code: Ctrl+Shift+P → Restart TS Server）。"改了 paths 却还报红线"多半不是配置错了，而是服务没刷新。
