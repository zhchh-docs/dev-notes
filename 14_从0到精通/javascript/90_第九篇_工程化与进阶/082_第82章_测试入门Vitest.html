82.1 测试金字塔：单元 / 集成 / E2E

自动化测试分三层，越往下越快越多、越往上越慢越少——这就是测试金字塔：

层级测什么特点与比例（约）
单元测试一个函数 / 一个组件，隔离验证毫秒级、成百上千个；约 70%——本章主战场
集成测试几个模块协作（如"函数 + 数据层"）较慢、几十个；约 20%
E2E 测试真实浏览器点完整流程（登录→下单）秒级、脆且贵；约 10%，只盖关键路径
  • 为什么倒过来不行：全是 E2E 的测试套件跑一小时、动不动假失败，团队会开始"跳过测试"——金字塔形状是几十年的血泪教训；
  • 本章工具 Vitest：与 Vite 共享配置、启动即快，API 与 Jest 几乎一致（学一套通用两家）；
  • 测试的价值随时间放大：写测试花 1 倍时间，之后每次改动省下"全功能手测"的 10 倍时间——越常改的代码越值得测。

测试回答的问题不是"代码能不能跑"，而是"改完之后，原来承诺的行为还在不在"——它是重构的安全网（83 章 TS 是另一张网）。

82.2 describe / it / expect 断言全形

一个测试文件的三件套：describe 分组、it（别名 test）描述一条行为、expect 发起断言。

import { describe, it, expect } from "vitest"
import { clamp } from "./math.js"

describe("clamp 限幅函数", () => {
  it("值在区间内时原样返回", () => {
    expect(clamp(5, 0, 10)).toBe(5)
  })

  it("小于下界时返回下界", () => {
    expect(clamp(-3, 0, 10)).toBe(0)
  })

  it("超出上界时返回上界", () => {
    expect(clamp(99, 0, 10)).toBe(10)
  })
})
// 常用匹配器（matcher）速查——够用 90% 的场景：
expect(1 + 1).toBe(2)               // 全等（===，含类型）
expect({ a: 1 }).toEqual({ a: 1 })  // 深比较（对象/数组内容）
expect(name).toBeTruthy()           // 真值（非 undefined/null/''/0/NaN）
expect(list).toContain("x")         // 数组/字符串包含
expect(fn).toThrow()                // 抛了异常（可传匹配串）
expect(fn).not.toBe(0)              // not 取反，任何匹配器都可接
expect(n).toBeGreaterThan(10)       // 数值比较族：LessThan / CloseTo 等
  • it 的名字是句子：写"小于下界时返回下界"，不写"test1"——测试失败时，输出的句子就是一份 bug 报告；
  • toBe vs toEqual：toBe 是 ===（对象比引用），toEqual 比内容——断言对象时用错会"莫名失败"；
  • 一个 it 测一件事：断言多了失败时不知道哪条挂了，排错成本上升。

测试文件的本质是"可执行的规格说明"：每个 it 都是在替未来维护者问一句"这里本来应该这样，对吧？"

82.3 生命周期与夹具：beforeEach

测试之间必须互不污染：上一个测试改了共享状态，下一个就可能假失败。生命周期钩子负责"每场测试前重置现场"——这份现场就叫夹具（fixture）。

import { describe, it, expect, beforeEach, afterEach } from "vitest"

describe("购物车", () => {
  let cart

  beforeEach(() => {
    cart = createCart()        // 每个测试前：全新购物车（夹具）
  })

  afterEach(() => {
    vi.restoreAllMocks()       // 每个测试后：清理 mock，防止泄漏到下个用例
  })

  it("添加商品后总数增加", () => { cart.add("apple"); expect(cart.count).toBe(1) })
  it("空车总数为 0",      () => {                 expect(cart.count).toBe(0) })
  // 第二个测试能过，正说明 beforeEach 生效了——两个测试用的是不同 cart
})
  • 执行顺序：每个 it 前后都会走一遍 beforeEach / afterEach；describe 级的 beforeAll / afterAll 则整组只跑一次（适合贵的初始化，如连数据库）；
  • 铁律：能在 beforeEach 里准备的，绝不写在模块顶层——顶层状态会跨测试文件甚至跨次运行泄漏；
  • 独立性检验法：单独跑任何一个 it 都应该通过。做不到，就是有隐藏的顺序依赖。

测试可靠性的根基是"每场测试都从同一张白纸开始"——beforeEach 就是那张白纸。

82.4 mock 基础：vi.fn

单元测试要"隔离"：被测函数依赖网络、时间、随机数时，用替身（mock）顶住，只验证你的逻辑。vi.fn 是最小可用集。

import { describe, it, expect, vi } from "vitest"

describe("notify 调用回调", () => {
  it("每个用户通知一次", () => {
    const send = vi.fn()                       // 空壳函数：记录一切调用
    notifyUsers(["a", "b"], send)

    expect(send).toHaveBeenCalledTimes(2)      // 被调了 2 次
    expect(send).toHaveBeenCalledWith("a")     // 有一次参数是 "a"
  })

  it("模拟返回值", () => {
    const fetchUser = vi.fn().mockReturnValue({ name: "张三" })
    expect(fetchUser().name).toBe("张三")      // 替身按剧本返回
  })
})
  • vi.fn 的价值：它把"函数被怎么调用"变成可断言的数据（次数、参数、顺序）——这是普通函数做不到的；
  • mockReturnValue / mockImplementation：给替身写剧本；vi.spyOn(obj, "method") 则是"监视真身"；
  • vi.useFakeTimers()：把 Date/setTimeout 换成可控假钟——测 debounce（下一节）的关键道具；
  • 克制原则：mock 越多，测试离真实越远——只 mock 边界（网络、时钟、文件），不 mock 被测逻辑本身。

mock 的定位：把"不可控的世界"替换成"可控的剧本"，让你的函数单独登台演出。

82.5 测行为不测实现：38 章四件套回收

第 38 章我们手写了 debounce / throttle / once / memoize 四件套，当时留了一句话"它们最该被测试"。现在兑现——并且用它示范本章最重要的原则：测行为，不测实现。

import { describe, it, expect, vi, beforeEach, afterEach } from "vitest"
import { debounce, once, memoize } from "./fp.js"

describe("debounce（行为：停止触发 delay 毫秒后才执行一次）", () => {
  beforeEach(() => { vi.useFakeTimers() })     // 假钟：时间由我们说了算
  afterEach(() => { vi.useRealTimers() })

  it("连续调用只执行最后一次", () => {
    const fn = vi.fn()
    const debounced = debounce(fn, 100)

    debounced(); vi.advanceTimersByTime(50)
    debounced(); vi.advanceTimersByTime(50)    // 才 100ms 且中间又触发了
    expect(fn).not.toHaveBeenCalled()          // 还没执行——行为对
    vi.advanceTimersByTime(100)
    expect(fn).toHaveBeenCalledTimes(1)        // 静默 100ms 后执行且仅一次
  })
})

describe("once（行为：多次调用只有首次生效）", () => {
  it("返回值恒定且原函数只跑一次", () => {
    let n = 0
    const init = once(() => ++n)
    expect(init()).toBe(1)
    expect(init()).toBe(1)                     // 第二次拿同一结果
    expect(n).toBe(1)                          // 原函数确实只执行了一次
  })
})

describe("memoize（行为：同参复用结果）", () => {
  it("不同参数各自计算，相同参数走缓存", () => {
    const heavy = vi.fn((x) => x * 2)
    const fast = memoize(heavy)
    fast(3); fast(3); fast(4)
    expect(heavy).toHaveBeenCalledTimes(2)     // 3 走缓存，4 才真算
    expect(fast(3)).toBe(6)
  })
})
  • 什么叫测行为：断言"输入 → 输出 / 调用次数 / 副作用时机"（debounce 的行为就是执行时机）——哪怕你明天把 debounce 内部从 setTimeout 改成 requestAnimationFrame，这些测试一行不改照样该过；
  • 什么叫测实现：断言"内部用了 setTimeout、内部有个 cache 对象"——这类测试在重构时集体变红，红得很冤；
  • 判断法：把函数内部彻底重写但行为不变，测试应该全绿。会红的，就是测到实现了。

测行为不测实现，一句话版：测试盯着"它承诺了什么"，不盯着"它怎么做到的"——前者是契约，后者是你的自由。

82.6 覆盖率：意义与盲区

覆盖率统计"多少代码被测试执行过"，一行命令就能出报告：

npx vitest run --coverage
# 输出示意：
# File        % Stmts   % Branch   % Funcs   % Lines
# fp.js         100%       85%       100%      100%
# api.js         42%       20%        30%       40%   ← api.js 是漏测重灾区
  • 正确的用法：当找漏的探照灯——42% 的文件一眼暴露没被测过；也用于防止回退（CI 里设阈值：覆盖率下降禁止合并）；
  • 盲区一：行覆盖 ≠ 行为验证。expect(result).toBeDefined() 也能"执行"到那一行——代码跑了但没验证对错，覆盖率 100%，bug 照样漏网；
  • 盲区二：分支组合爆炸。两个 if 各测过 true/false 是 100% 分支覆盖，但"两个同时为真"的组合可能没测——组合才是 bug 的老家；
  • 态度：不追求"100% 覆盖率 KPI"，追求"关键路径全覆盖 + 每个断言都在验证行为"。

覆盖率是必要条件不是充分条件：低覆盖一定危险，高覆盖不一定安全——它衡量"测过"，不衡量"测对"。

✓ 本章小结

要点一句话
测试金字塔单元 70% / 集成 20% / E2E 10%；越上越慢越脆，故越少
三件套describe 分组、it 写成句子、expect 断言；toBe 全等 / toEqual 深比
beforeEach每测试前重置夹具；独立性检验：单独跑任何 it 都能过
vi.fn替身记录调用（次数/参数），mockReturnValue 写剧本，假钟控时间
测行为原则断言契约（输入→输出/时机），重构不改测试；盯着实现的重构必红
覆盖率找漏的探照灯；行覆盖≠行为验证，组合分支是盲区

✎ 本章习题

A 基础给第 38 章的 throttle 补一组测试（用假钟）：验证"首次立即执行、密集触发期间被丢弃、冷却后恢复"。至少三个 it，名字写成行为句子。
B 进阶用 vi.fn 测试一个 retry(fn, times) 重试函数：前两次 mock 抛错、第三次成功，断言最终返回成功值且原函数被调 3 次。思考：如果 retry 内部把循环改成递归，你的测试需要改吗？为什么？
C 挑战构造一个"覆盖率 100% 但测不到 bug"的反例：写一个除法函数 divide(a, b)，测试里只用 expect(divide(4, 2)).toBeDefined() 这样的弱断言刷满覆盖，然后说明 divide(1, 0) 的 bug 为什么漏网；再重写断言把网补上（提示：toThrow 与 Infinity 分支）。
