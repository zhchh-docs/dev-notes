84.1 目标浏览器矩阵与 caniuse 习惯

兼容不是"支持一切浏览器"，而是先回答"我的用户用什么"，再决定工程投入。这份清单就叫目标浏览器矩阵。

确定矩阵的依据怎么用
站点统计（百度统计/GA）看真实用户分布：内网系统可能 80% 是某国产浏览器，别按"全球平均"配
业务性质面向消费者的新业务可激进（近两年版本）；政企/ Embedded WebView 要保守
维护成本每多支持一代老浏览器 = 转译更重 + 测试矩阵扩大——矩阵是商业决策不是技术洁癖
 
一个真实项目的矩阵示例（写进团队文档 + browserslist）：
  Chrome / Edge ：最近 2 个大版本
  Firefox       ：最近 2 个大版本
  Safari        ：最近 2 个大版本
  移动端 WebView：iOS Safari 14+、Android Chrome 90+
  IE            ：不支持（写入文档，出问题不修）
  • caniuse（caniuse.com）是查询入口：想用某个特性，先搜它的支持率——"Array.prototype.at 支持哪些版本？"":has() 选择器 safari 几代开始？"——30 秒出答案；
  • 习惯闭环：用新特性前查 caniuse → 对照矩阵 → 三种结论：放心用 / 需要 polyfill / 用特性检测降级（84.2）；
  • 这个矩阵恰好就是 80 章 browserslist 的输入——业务决策与技术配置在这一章接上头。

兼容性工作的第一步不是写代码，而是回答"支持到哪、放弃谁"——没有矩阵的兼容是无限黑洞。

84.2 特性检测：问能力，不问身份

运行时判断"浏览器能不能"的唯一正确姿势是特性检测（feature detection）：直接问"这个能力在不在"，而不是猜"你是什么浏览器"。

// 反例：UA 嗅探（问身份）——脆弱且撒谎
// if (navigator.userAgent.includes("Chrome")) { ... }
// 新浏览器改 UA、老套壳浏览器假冒 UA，一查一个不准

// 正解：特性检测（问能力）
if ("IntersectionObserver" in window) {
  // 67 章回收：懒加载的正规军路线
  const io = new IntersectionObserver((entries) => {
    entries.forEach((e) => {
      if (e.isIntersecting) {
        e.target.src = e.target.dataset.src
        io.unobserve(e.target)
      }
    })
  })
  document.querySelectorAll("img[data-src]").forEach((el) => io.observe(el))
} else {
  // 兜底分支：能力不在，就退而求其次——直接全部加载（慢但能用）
  document.querySelectorAll("img[data-src]").forEach((el) => {
    el.src = el.dataset.src
  })
}
  • 为什么"问能力"可靠：你关心的本来就是"能不能做这件事"，能力存在与否是事实、不可伪装——检测代码天然零维护；
  • CSS 的对应物是 @supports：@supports (display: grid) { ... }，JS 检测能力的 CSS 版；
  • 兜底分支的设计心态：兜底不是"报错消失"，而是明确提供一条较差但可用的路——直接全量加载图片就是合法兜底。

特性检测三段式：检测能力 → 走增强路线 → else 给兜底。写不出兜底的特性，说明它是核心依赖，该换方案或上 polyfill。

84.3 渐进增强 vs 优雅降级

两种兼容哲学，方向相反：

路线出发点典型做法
渐进增强
（从低往高盖楼）		先保证基础功能所有人可用，再逐层加体验语义 HTML + 表单原生可用 → CSS 美化 → JS 增强（动画/懒加载/实时校验）
优雅降级
（从高往低兜底）		按现代浏览器做全量体验，再给老环境打补丁先写 IntersectionObserver 方案，再补 else 分支；先 flex/grid 再回退 float
 
// 渐进增强的 JS 版式：增强是"锦上添花"，缺席不影响核心
const form = document.querySelector("#signup")
form.addEventListener("submit", save)          // 基础：提交一定可用（无 JS 也有 action）

if ("fetch" in window) {                        // 增强：JS 可用才换无刷新提交
  form.addEventListener("submit", async (e) => {
    e.preventDefault()
    await fetch("/api/signup", { method: "POST", body: new FormData(form) })
  })
}
  • 渐进增强的底线是"HTML 本身可用"——表单能提交、链接能跳转，JS 只是体验放大器；
  • 优雅降级开发效率高（单一代码路径起步），但要主动列兜底清单，漏列就是事故；
  • 现实是混用：新业务功能用渐进增强（谁都能下单），视觉效果用优雅降级（老浏览器凑合看）。

选择路线的关键问题："这个功能老浏览器用户能不能没有？"——不能没有，走渐进增强；能接受差版，走优雅降级。

84.4 与 80 章 polyfill 的分工

特性能不能"补"，决定了用哪件工具。80 章 polyfill 与本章特性检测，各管半边天：

特性类型例子工具
纯逻辑 API（可模拟）Array.prototype.at、Promise.allSettledpolyfill（80 章，core-js 按需注入）——补上后老浏览器行为与新浏览器一致
语法特性?.、??、class 私有字段转译（80 章 Babel/esbuild）
依赖浏览器底层的 APIIntersectionObserver、WebGL、Notification特性检测 + 兜底（本章）——逻辑可模拟，但底层能力（渲染管线、系统权限）造不出来
CSS 特性grid、:has()、backdrop-filter@supports + 后备样式——不支持就给一份"能用版"样式
 
// 分工现场：同一个功能里两种手段并用
async function loadComments() {
  if (!("Promise" in window)) return           // 环境太老，兜底直接放弃增强
  const list = await fetch("/api/comments").then((r) => r.json())
  // fetch 已普及基本无需 polyfill；若是 allSettled 这种纯逻辑缺失，
  // 交给 80 章的 core-js 按 useBuiltIns:"usage" 自动注入，不用手写检测
  render(list)
}
  • 口诀：能垫的垫（polyfill，透明无感）、垫不了的测（特性检测，给兜底）、语法转（编译期）；
  • 不要重复防御：core-js 已注入的 API 不必再手写 if 检测——两层保护反而让代码难读、掩盖真实支持情况。

一句话分工：polyfill 负责"造出缺失的函数"，特性检测负责"决定要不要走另一条路"——前者补齐，后者改道。

84.5 实战清单：一次兼容性评审

把本章方法浓缩成一张可执行清单，新功能上线前过一遍：

  • ① 列特性清单：这个功能用到的 JS 语法 / API / CSS 特性，逐个写出名字；
  • ② 逐个查 caniuse：对照矩阵标注"直接可用 / 需转译 / 需 polyfill / 需特性检测"；
  • ③ 检查 browserslist：矩阵变化时同步更新（80 章的"一处声明"），让转译与注入自动跟上；
  • ④ 每个检测必须有兜底：搜一遍 if (... in window)，确认每个 else 分支都有可用的次级方案；
  • ⑤ 真机验证：目标矩阵里最老的环境至少跑一遍主流程（模拟器不算数，WebView 差异大）；
  • ⑥ 放弃也要写下来：明确"不支持 IE / 不支持 Safari 13 以下"写进文档——沉默的放弃是定时炸弹。

兼容性评审的本质：把"默认大家都用最新 Chrome"的侥幸，换成一张写进文档的矩阵和一组带兜底的检测。

✓ 本章小结

要点一句话
目标矩阵按真实用户定支持范围；没有矩阵就没有边界
caniuse用新特性前必查；结论对接 browserslist 与工程配置
特性检测问能力不问身份（弃 UA 嗅探）；in window / @supports；必须有兜底分支
两条路线渐进增强（基础→增强）保底线；优雅降级（全量→兜底）求效率；按"能不能没有"选
与 polyfill 分工纯逻辑 API 垫（80 章）、底层能力测（84 章）、语法转（编译期）
