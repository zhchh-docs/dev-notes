A.1 第一篇 · 入门与环境（第 1-8 章）

① 第 7 章 · getDiscount 折扣函数（B 进阶）

题干写函数 getDiscount(level)：VIP 打 8 折、普通 9 折、未登录（level 为 null/undefined）返回 1。用 ?? 与三元各实现一版，并说明为什么不能用 ||。
// ?? 版：只有 null/undefined 才算"未登录"，0/''/false 都是有意义的值
const getDiscountA = (level) =>
  (level ?? null) === null ? 1
  : level === "vip"        ? 0.8
  :                          0.9

// 三元版：分支平铺，最直白
function getDiscountB(level) {
  if (level === "vip") return 0.8
  if (level === "normal") return 0.9
  return 1
}

解析：|| 会把 ""、0 这类"合法但 falsy"的 level 误判为未登录，而 ?? 只兜底 null/undefined——这正是第 7 章"短路求值"两兄弟的分工线。

② 第 8 章 · {} == !{} 与加法怪象（C 挑战）

题干用 8.4 框架逐步推理 {} == !{} 与 [] + []、[] + {} 的结果（提示：+ 的规则是"有对象先 ToPrimitive"），推理完运行验证。
{} == !{}    // false
// ① 右侧先算：!{} => false（对象恒真值）
// ② false == {} 触发数字转换：两边 ToPrimitive 后再 Number
// ③ {} => "[object Object]" => NaN；false => 0
// ④ NaN == 0 => false

[] + []      // "" —— 两个数组 ToPrimitive 都得 ""，字符串拼接得空串
[] + {}      // "[object Object]" —— [] => ""，{} => "[object Object]"

解析：== 的规则是"对象先转基本类型（默认偏字符串）、布尔先转数字"，两步叠出以上怪象——这也是全书立法"日常只用 ==="的最好注脚。

A.2 第二篇 · 语法核心（第 9-18 章）

① 第 13 章 · 修复定时器里丢失的 this（B 进阶）

题干counter.tick 里 setInterval(function () { this.n++ }) 打印不正常——先运行观察现象，再用箭头函数修复并解释为什么生效。
const counter = { n: 0, tick() {
  setInterval(() => {          // 箭头函数没有自己的 this，
    this.n++                   // 沿词法作用域拿到外层 tick() 的 this —— 即 counter
    console.log(this.n)
  }, 500)
} }
counter.tick()                 // 每半秒打印 1, 2, 3…
// 修复②（bind 版）：setInterval(function () { this.n++ }.bind(this), 500)

解析：普通函数的 this 由调用方式决定（定时器回调里"没人点用"，落到默认绑定），箭头函数的 this 在定义处锁定——词法 this 天然免疫调用方式。

② 第 14 章 · var 循环回调全 3 的两种修法（C 挑战）

题干var 循环回调全 3 的代码，要求不改 let 修复为打印 0/1/2——提示：用 IIFE（第 32 章）或 setTimeout 第三参为每轮"快照"一个值。
// 修法一：IIFE 为每轮制造独立作用域，把当轮 i "快照"进闭包
for (var i = 0; i < 3; i++) {
  ;(function (j) {
    setTimeout(() => console.log(j), 100)   // 打印 0 1 2
  })(i)
}
// 修法二：setTimeout 的第三参会被当作回调的实参传入
for (var i = 0; i < 3; i++) {
  setTimeout((j) => console.log(j), 100, i) // 打印 0 1 2
}

解析：两条路都让每个回调持有各自的 j（值拷贝），不再共享那个"循环结束后才被读取"的全局 i——病根是共享绑定，药方是每轮独立。

A.3 第三篇 · 数据集合（第 19-28 章）

① 第 20 章 · 用 reduce 写 countBy（C 挑战）

题干用 reduce 实现 countBy(arr, fn)：按 fn 的返回值分组计数，如 countBy(["a","b","a"], x=>x) → { a:2, b:1 }。要求初始值显式、箭头函数体超过一行时正确 return。
function countBy(arr, fn) {
  return arr.reduce((acc, item) => {
    const key = fn(item)
    acc[key] = (acc[key] || 0) + 1   // 组内计数 +1
    return acc                       // 关键：箭头函数体有多行，必须显式 return
  }, {})                             // 初始值显式给 {}，空数组也不会抛错
}
countBy(["a", "b", "a"], (x) => x)   // { a: 2, b: 1 }

解析：删掉 return 后下一轮回调拿到的 acc 是 undefined——reduce 静默失败不报错，这是"箭头函数隐式返回"最著名的翻车现场。

② 第 26 章 · 给 deepClone 补 Map/Set 分支（B 进阶）

题干给 26.4 的 deepClone 补上 Map 与 Set 的克隆分支（instanceof 判断后逐项递归），用含 Map 的对象验证独立性。
function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== "object") return value
  if (seen.has(value)) return seen.get(value)          // 防环：先登记再递归
  if (value instanceof Map) {
    const m = new Map()
    seen.set(value, m)
    value.forEach((v, k) => m.set(deepClone(k, seen), deepClone(v, seen)))
    return m
  }
  if (value instanceof Set) {
    const s = new Set()
    seen.set(value, s)
    value.forEach((v) => s.add(deepClone(v, seen)))
    return s
  }
  const out = Array.isArray(value) ? [] : {}
  seen.set(value, out)
  for (const k of Reflect.ownKeys(value)) out[k] = deepClone(value[k], seen)
  return out
}

解析：最容易漏的是 Map 的 key 本身也可能是对象，同样要深拷贝——分支克隆的本质是"容器重建 + 逐项递归"。

③ 第 28 章 · 给 LRU 加 maxAge 过期（C 挑战）

题干为 LRU 增加 maxAge 过期能力（写入时记时间戳，get 时过期即删）——会踩到"Map 遍历中删除"的坑吗？边写边验证。
class LRUCache {
  constructor(max, maxAge = Infinity) {
    this.max = max; this.maxAge = maxAge
    this.map = new Map()               // Map 记住插入顺序 = 使用顺序
  }
  get(key) {
    if (!this.map.has(key)) return undefined
    const hit = this.map.get(key)
    if (Date.now() - hit.at > this.maxAge) {   // 过期：当作没有
      this.map.delete(key); return undefined
    }
    this.map.delete(key); this.map.set(key, hit)  // 重插 = 挪到"最新"端
    return hit.v
  }
  set(key, v) {
    if (this.map.has(key)) this.map.delete(key)
    else if (this.map.size >= this.max) this.map.delete(this.map.keys().next().value)
    this.map.set(key, { v, at: Date.now() })      // 写入时记时间戳
  }
}

解析：不会踩"遍历中删除"的坑——淘汰发生在 set 的"先删最旧"阶段，时机上没有任何迭代正在进行（keys().next().value 只取一个键，不开启遍历）。

A.4 第四篇 · 函数与作用域（第 29-38 章）

① 第 32 章 · 闭包预测：两次调用互不干扰（A 基础）

题干不运行预测：function f() { let n = 1; return () => n++ }，const a = f(), b = f(); a(); a(); console.log(a(), b())——输出是什么？为什么 a 与 b 的 n 互不干扰？
function f() { let n = 1; return () => n++ }
const a = f(), b = f()
a(); a()
console.log(a(), b())   // 3 1
// a() 调了三次：前两次吃掉 1、2，第三次先取 n=3 再自增。

解析：b 是对 f 的另一次调用——新的 n 绑定（新的词法环境）；闭包捕获的是"那一次调用"的环境，不是"函数 f"本身。

② 第 33 章 · this 六连判定（A 基础）

题干判定 this 并给理由：fn()、obj.fn()、obj.a.fn()、fn.call(obj2)、new fn()、const f = obj.fn; f()——六个全对即过关。
fn()          // 默认规则：undefined（严格模式）/ 全局对象（非严格）
obj.fn()      // 隐式绑定：obj（谁点用谁）
obj.a.fn()    // 还是 a：只看"最后一层"调用者，obj 只是个路标
fn.call(obj2) // 显式绑定：obj2（call/apply 直接指定）
new fn()      // new 绑定：新造的那个实例
const f = obj.fn; f()  // undefined/全局：赋值取出后"裸调"，隐式绑定丢失

解析：优先级口诀 new > 显式 > 隐式 > 默认；箭头函数不参与这张表，this 一律取定义处（33.4 判定流程图）。

③ 第 38 章 · 手写四件套 once/memoize/debounce/throttle（A 基础）

题干手写四件套并各配一个 3 行调用验证；给每件标注"闭包里藏了什么"（done/result、cache、timer、last）。
// once：只跑一次 —— 闭包里藏 done
const once = (fn) => { let done = false
  return (...args) => done ? undefined : ((done = true), fn(...args)) }
// memoize：按参数缓存 —— 闭包里藏 cache
const memoize = (fn) => { const cache = new Map()
  return (...args) => { const k = JSON.stringify(args)
    if (!cache.has(k)) cache.set(k, fn(...args))
    return cache.get(k) } }
// debounce：停止触发 n ms 后才执行 —— 闭包里藏 timer
const debounce = (fn, ms) => { let timer
  return (...args) => { clearTimeout(timer)
    timer = setTimeout(() => fn(...args), ms) } }
// throttle：每 n ms 至多执行一次 —— 闭包里藏 last
const throttle = (fn, ms) => { let last = 0
  return (...args) => { const now = Date.now()
    if (now - last >= ms) { last = now; fn(...args) } } }

解析：四件套共用同一副骨架——外层闭包藏状态、内层返回柯里化的执行器，差别只在"藏什么、何时清"。

A.5 第五篇 · 对象与原型（第 39-48 章）

① 第 43 章 · "一代继承"的共享事故与修复（B 进阶）

题干手写四代里的"一代"（Child.prototype = new Parent()），构造两个子实例改引用属性，复现"全体共享"事故；再用三代组合写法修复。
// "一代"写法：实例属性进了原型，所有子实例共享同一个数组
function Parent() { this.tags = ["a"] }
function Child() {}
Child.prototype = new Parent()          // 缺陷源头：new 出的实例充当原型
const c1 = new Child(), c2 = new Child()
c1.tags.push("b")
console.log(c2.tags)                    // ['a', 'b'] —— 全体共享，事故！

// 修复（三代组合式）：实例属性走父构造器调用，原型只放共享方法
function Child2() { Parent.call(this) } // 每个实例自己的 tags
Child2.prototype = Object.create(Parent.prototype)
Child2.prototype.constructor = Child2
// 或直接 class Child2 extends Parent（ES6 双链一步到位，第 41-43 章）。

解析：事故根源是"实例属性"被放进了"原型"（共享层）——修复的思路就一句：变化的归实例（Parent.call(this)），共享的归原型。

② 第 46 章 · 给 myNew 补断言测试集（A 基础）

题干给 myNew 补一个断言测试集：实例属性、原型方法、instanceof、返回值夺舍四项各一条断言。
function myNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype)   // ① 备胎链挂上
  const r = Ctor.apply(obj, args)             // ② this 指向新对象执行
  return (r !== null && (typeof r === "object" || typeof r === "function"))
    ? r : obj                                 // ③④ 返回对象则"夺舍"
}
// ---- 断言测试集 ----
function Person(name) { this.name = name }
Person.prototype.say = function () { return "I am " + this.name }
const p = myNew(Person, "张三")
console.assert(p.name === "张三", "实例属性")
console.assert(p.say() === "I am 张三", "原型方法")
console.assert(p instanceof Person, "instanceof")
function Rogue() { return { hijacked: true } }
console.assert(myNew(Rogue).hijacked === true, "返回值夺舍")

解析：四条断言正好对上 new 的四步机制——造对象挂链、绑 this 执行、按返回值取舍；断言全绿即机制吃透。

③ 第 48 章 · 给 Emitter 加返回值与订阅上限（A 基础）

题干给 Emitter 补 emit 返回值（返回是否有订阅者的布尔）；再给 on 加"同一事件最多 5 个订阅者"上限（超出返回 null 并 warn）——防御性设计练习。
class Emitter {
  constructor() { this.map = new Map() }          // 事件名 -> Set<回调>
  on(type, fn) {
    const set = this.map.get(type) ?? new Set()
    if (set.size >= 5) {                          // 上限 5：超出拒绝并告警
      console.warn(`"${type}" 订阅者已满`)
      return null
    }
    set.add(fn); this.map.set(type, set); return () => this.off(type, fn)
  }
  off(type, fn) { this.map.get(type)?.delete(fn) }
  emit(type, payload) {
    const set = this.map.get(type)
    if (!set || set.size === 0) return false      // 返回值：是否有订阅者
    set.forEach((fn) => fn(payload))
    return true
  }
}

解析：防御性设计的两把尺——"无订阅"是正常态要如实回报（布尔），"超上限"是误用要早失败（null + warn），返回值本身就是 API 文档。

A.6 第六篇 · 异步与事件循环（第 49-58 章）

① 第 54 章 · 批量任务的并发限制（B 进阶）

题干10 个异步任务最多同时跑 3 个，全部完成后按原顺序返回结果——先用 Promise.all 写"分批版"。
// 分批版：每批最多 limit 个，批内 Promise.all，批间 await 串行
async function runInBatches(tasks, limit = 3) {
  const results = []
  for (let i = 0; i < tasks.length; i += limit) {
    const batch = tasks.slice(i, i + limit)
    results.push(...(await Promise.all(batch.map((t) => t()))))
  }
  return results
}
const jobs = Array.from({ length: 10 }, (_, i) =>
  () => new Promise((res) => setTimeout(() => res(i), 100)))
runInBatches(jobs, 3).then(console.log)  // [0,1,…,9]，每批同时只跑 3 个

解析："分批"是并发控制的入门版——简单但有等待浪费（整批中最慢的卡住下一批），"完成一个补一个"的真请求池见第 58 章。

② 第 55 章 · 宏微任务输出题（A 基础）

题干不运行写出输出：同步两行 log 之间夹一个 setTimeout(0) 与一个 Promise.then——顺序是什么？为什么？
console.log("1")
setTimeout(() => console.log("2"), 0)
Promise.resolve().then(() => console.log("3"))
console.log("4")
// 输出：1 4 3 2
// 同步（1、4）→ 清空全部微任务（3）→ 才轮到宏任务（2）

解析：setTimeout(0) 不是"立刻"——它只是排进宏任务队列，而微任务在"每个宏任务之间"整队插优先，永远先清空微任务再碰下一个宏任务。

③ 第 58 章 · 手写请求池（C 挑战）

题干写 createPool(tasks, limit)：同时最多 limit 个任务在飞，完成一个立刻补位一个，全部完成后按原顺序 resolve 结果数组。
function createPool(tasks, limit) {
  return new Promise((resolve) => {
    const results = []
    let i = 0, done = 0                      // i: 下一个待派发 / done: 已完成数
    const next = () => {
      if (done === tasks.length) return resolve(results)
      if (i >= tasks.length) return          // 没有新任务，等在飞的完成
      const idx = i++
      tasks[idx]()
        .then((r) => { results[idx] = r }, () => { results[idx] = null })
        .finally(() => { done++; next() })   // 一个完成，立刻补位
    }
    for (let k = 0; k < Math.min(limit, tasks.length); k++) next()
  })
}

解析：池的核心是"游标 i 派发 + finally 补位"——结果按下标写入所以顺序不乱，失败用第二参兜住不让池断流。

① 第 62 章 · 事件委托：列表一点通（C 挑战）

题干1000 个 li 的待办列表，点击切换完成态——不给每个 li 绑事件，只用一个监听器实现，并说明为什么新增 li 不用重新绑定。
// 只给父级 ul 绑一个：靠冒泡 + target 判定"谁被点"
const ul = document.querySelector("#todo-list")
ul.addEventListener("click", (e) => {
  const li = e.target.closest("li")        // closest 容忍 li 内还有子元素

② 第 66 章 · 给 localStorage 包一层安全壳（B 进阶）

题干localStorage 只能存字符串——封装 store 对象（get/set/remove），get 支持默认值，且用户手改过的脏数据不能让页面崩掉。
const store = {
  get(key, fallback = null) {
    try {
      const raw = localStorage.getItem(key)
      return raw === null ? fallback : JSON.parse(raw)
    } catch { return fallback }            // 手改过的脏数据不至于炸页面
  },
  set(key, value) { localStorage.setItem(key, JSON.stringify(value)) },
  remove(key) { localStorage.removeItem(key) },
}
store.set("cart", [{ id: 1, n: 2 }])
store.get("cart", [])      // [{ id: 1, n: 2 }] —— 存取都过 JSON 一层

解析：存储壳的三道防线——JSON 往返补类型、null 与"存的空值"区分、try/catch 兜脏数据；顺带警惕存进来的字符串渲染进页面会带来 XSS（见第 66 章安全小节）。

A.8 第八篇 · 现代语法与错误处理（第 69-77 章）

① 第 70 章 · 金字塔判空改造（B 进阶）

题干把 user && user.address && user.address.city 的层层判空改写成可选链 + 空值合并，并说明 ?? 与 || 在这里的语义差别。
// 改造前：层层判空，金字塔越叠越高
const city1 = user && user.address && user.address.city
// 改造后：链上任何一环是 null/undefined 就短路返回 undefined
const city2 = user?.address?.city ?? "未知城市"
// 0 和 "" 会原样通过 ??；若业务上"空串也算没有"，才需要 ||
const nick = user?.nick || "匿名"

解析：?. 管"断了没有"，?? 管"断了给什么"——两者语义正交，混用 || 会悄悄吞掉 0 和 ""。

② 第 72 章 · 模块的"活绑定"与循环依赖（C 挑战）

题干解释为什么 import 进来的 count 在 inc() 之后会变（值不是拷贝）；再说明模块循环依赖为什么通常不会炸、炸的条件是什么。
// counter.mjs —— export 出去的不是"值的拷贝"，而是"活的绑定"
export let count = 0
export const inc = () => { count++ }
// main.mjs
import { count, inc } from "./counter.mjs"
inc(); inc()
console.log(count)   // 2 —— import 拿到的是原模块变量的实时视图
// 循环依赖：import 是静态提升的，循环时先拿到"未完成的"绑定；
// 只要不把读取放在模块顶层执行阶段，等函数真正被调用时绑定早已就绪。

解析：ESM 的活绑定 + 静态提升决定了两件事——导出值会变、循环可解；顶层立刻读取未完成绑定（TDZ）才是循环炸掉的唯一姿势。

A.9 第九篇 · 工程化与进阶（第 78-85 章）

① 第 82 章 · 把重活外包给 Worker（B 进阶）

题干主线程算 1 加到一千万会卡死页面——用 Web Worker 搬到子线程算，主线程收结果。
// main.js —— 重活外包给子线程，主线程不卡
const worker = new Worker("sum.js")
worker.postMessage(10_000_000)
worker.onmessage = (e) => console.log("和是", e.data)
// sum.js
self.onmessage = (e) => {
  let s = 0
  for (let i = 1; i <= e.data; i++) s += i
  self.postMessage(s)   // 传递走"结构化克隆"，不是共享内存
}

解析：Worker 三要点——postMessage 传值（结构化克隆）、子线程无 DOM、传函数/原型对象会报错（不可克隆）。

② 第 85 章 · pipe 与 compose（A 基础）

题干用 reduce 实现 pipe（从左到右）与 compose（从右到左），并各写一个两函数组合的例子。
const compose = (...fns) => (x) => fns.reduceRight((acc, f) => f(acc), x)
const pipe = (...fns) => (x) => fns.reduce((acc, f) => f(acc), x)
const trim = (s) => s.trim()
const lower = (s) => s.toLowerCase()
pipe(trim, lower)("  HeLLo  ")   // 'hello' —— 数据从左往右流
compose(lower, trim)("  HeLLo  ") // 'hello' —— 从右往左，镜像看齐

解析：组合不过是"把函数当数据再 reduce 一遍"——方向感是唯一差别，pipe 读起来像流水线，compose 贴近数学记号。

A.10 第十篇 · 性能内存与收官（第 86-97 章）

① 第 88 章 · 虚拟列表核心逻辑（C 挑战）

题干一万行列表滚动卡顿——写出虚拟列表的渲染窗口计算：给定 scrollTop 求应渲染的起止行，并用上下撑高元素保住滚动条。
const rowH = 40, viewH = 600
function render(scrollTop, data) {
  const start = Math.max(0, Math.floor(scrollTop / rowH) - 3)   // 上缓冲 3 行
  const end = Math.min(data.length, start + Math.ceil(viewH / rowH) + 6)
  const topPad = start * rowH, botPad = (data.length - end) * rowH
  return { slice: data.slice(start, end), topPad, botPad }      // 撑住滚动条
}
// 监听 scroll 用 rAF 节流（第 89 章联动），
// 一万行也只常驻 ~20 个 DOM 节点——滚动丝滑的秘密。

解析：虚拟列表 = "渲染窗口 + 上下 padding 撑高"——DOM 少了重排自然轻（第 68 章呼应），缓冲行是防止快速滚动露白的工程余量。

② 第 92 章 · 手写环安全深拷贝（B 进阶）

题干手写 cloneDeep，要求对象里出现 self 自引用也不爆栈——解释"先登记再递归"换成"后登记"为什么会爆。
function cloneDeep(value, seen = new WeakMap()) {
  if (value === null || typeof value !== "object") return value
  if (seen.has(value)) return seen.get(value)      // 环：登记表里有，直接还
  const out = Array.isArray(value) ? [] : {}
  seen.set(value, out)                             // 先登记，再递归
  for (const k of Reflect.ownKeys(value)) out[k] = cloneDeep(value[k], seen)
  return out
}
const a = { name: "a" }; a.self = a
const b = cloneDeep(a)
console.log(b.self === b)   // true —— 副本内部也成环，但不再是死循环

解析："后登记"爆栈的原因：递归下去时表里还没有自己，遇到环只会一路 new 新对象直到溢出；先登记让环在第一时间命中缓存并返回。
