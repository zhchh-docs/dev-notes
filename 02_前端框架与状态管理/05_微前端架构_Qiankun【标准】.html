微前端架构：Qiankun

标准 定位：把巨石应用拆成独立部署、可独立运行的子应用的架构方案

微前端解决的是"巨石前端"问题：一个超大应用多人开发、发版互相掣肘、技术栈被绑架。Qiankun 是蚂蚁开源的微前端方案——一个基座应用按路由加载各子应用，子应用独立开发、独立部署、互不污染。本页讲清基座接入、子应用改造、样式隔离、公共依赖与主子通信，案例来自可视化大屏系统 整合 5+ 子应用、WebRTC 播放器封装为子应用。

1技术点概览

是什么：微前端是一种架构风格——把大型前端应用按业务拆成若干个能独立开发、独立部署、独立运行的小应用，再由一个"基座"把它们按路由组合成一个完整产品。Qiankun 是其主流实现：基座注册子应用列表，路由匹配到哪个就加载哪个的 JS/CSS，在沙箱里渲染，切走时卸载清理。

解决什么问题：巨石应用的发版耦合（改一个小功能要整站回归）、团队协作冲突（同仓库抢分支）、技术栈升级难（老项目无法换技术栈）。微前端让每个子应用按自己节奏走，独立部署。可视化大屏系统 正是把多个独立开发的业务模块整合成一个统一平台。

2核心概念

2.1 基座（Main）与子应用（Sub）

一句话定位：基座负责布局/登录/菜单并注册子应用；子应用是独立工程，被动态加载进基座容器。

  • 基座：第一个加载，负责整体布局、登录态、菜单路由，注册所有子应用。
  • 子应用：独立工程，自带 html/js/css，被基座在匹配路由时动态加载到指定容器。

2.2 路由劫持与动态加载

一句话定位：Qiankun 监听路由，按 activeRule 决定激活哪个子应用，切走时卸载。

  1. 监听浏览器路由变化，按 activeRule 判断该激活哪个子应用。
  2. 请求子应用入口资源（HTML）、执行其 JS、把渲染结果塞进基座容器。
  3. 切走时调用子应用 unmount 卸载清理。

2.3 JS 沙箱与样式隔离

一句话定位：多子应用共存会互相污染全局变量与 CSS，靠沙箱与样式隔离隔开。

  • JS 沙箱：用 proxy 隔离 window，让子应用全局变量互不可见。
  • 样式隔离：strictStyleIsolation: true 把子应用容器转成 Shadow DOM 做强隔离；experimentalStyleIsolation: true 在运行时给子应用样式选择器加前缀（scoped CSS）——两者名字相近、机制不同，按需开启，避免 A 应用样式覆盖 B。

图 1 JS 沙箱 vs 样式隔离（示意）

2.4 主子通信与公共依赖

一句话定位：主子用 initGlobalState 共享状态；公共依赖由基座 externals 提供，避免多实例。

  • 通信：initGlobalState 共享全局状态（登录态、主题），或 props 传参。
  • 公共依赖：Vue/React/axios 由基座 externals 提供，子应用不重复打包，减小体积、避免多实例。

4核心语法与 API 要点

4.1 基座注册子应用

import { registerMicroApps, start, initGlobalState } from 'qiankun';

registerMicroApps([
  {
    name: 'sub-webrtc',                  // 子应用名
    entry: '//localhost:7101',           // 子应用入口
    container: '#subapp-viewport',        // 挂载容器
    activeRule: '/webrtc'                // 路由激活规则
  }
]);
start({ sandbox: { strictStyleIsolation: false } });  // 开启 JS 沙箱

4.2 子应用导出生命周期

// 子应用入口 main.js
let instance = null;
export async function bootstrap() {}              // 只调一次
export async function mount(props) {               // 每次挂载
  instance = render(props.container);
}
export async function unmount() {                  // 卸载清理
  instance.$destroy?.();
  instance = null;
}
// 独立运行时也要能自渲染
if (!window.__POWERED_BY_QIANKUN__) {
  render(document.getElementById('app'));
}

4.3 主子通信（全局状态）

// 基座
export const { onGlobalStateChange, setGlobalState } = initGlobalState({ user: null });
// 子应用 mount(props) 里
props.onGlobalStateChange((state) => console.log('收到登录态', state));

5实战项目经验（实战落地）

5.1 项目背景

一句话定位：可视化大屏系统 用 Qiankun 把多个不同时期、不同小团队开发的模块整合成统一运维平台，并把 WebRTC 播放器封装成可复用子应用。

  • 业务场景：5+ 子应用各自独立部署、技术栈略异，需统一登录/菜单/布局。

5.2 我的角色与职责

  • 角色：前端开发，负责基座接入、子应用改造与 WebRTC 播放器子应用化。
  • 团队与分工：多个小团队各自维护子应用；我负责基座与接入规范。

5.3 技术栈

  • Qiankun + Vue 基座 + 各 Vue2/Vue3 子应用 + WebRTC(Janus)；JS 沙箱 + scoped 样式隔离。

5.4 落地设计

  • 基座分发：基座统一登录/菜单/布局，按路由 activeRule 分发子应用。
  • 子应用改造：导出 bootstrap/mount/unmount，publicPath 改运行时。
  • 隔离：JS 沙箱隔离 window，样式 scoped；登录态经 initGlobalState 下发。
  • 播放器子应用化：WebRTC 播放器作独立子应用，其他模块经路由/消息唤起。

5.5 关键实现要点

// 子应用 webpack/vite 运行时 publicPath 适配
if (window.__POWERED_BY_QIANKUN__) {
  __webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__;
}

5.6 真实问题与解法

  • publicPath 写死：子应用静态资源路径写死，部署子路径后 404；改运行时 publicPath 解决。
  • 全局污染：两个子应用都用全局 $ 或同名组件互染；JS 沙箱 + 不污染 window。
  • 连接未 dispose：WebRTC 子应用切走时 PeerConnection/定时器没在 unmount 清理，切回后多路连接泄漏；unmount 完整 dispose。
  • dev 跨域：子应用 dev 端口跨域被 CORS 拦；dev server 配允许跨域响应头。

5.7 量化成果

  • 5+ 子应用独立发版、互不阻塞；播放器能力被子应用复用。

5.8 协作与排期过程

  • 契约先行：与各子应用团队约定 mount/unmount 生命周期、publicPath、全局变量黑名单。
  • 联调协商：dev 跨域与全局污染问题逐对子应用联调定位。
  • 排期：先接一个子应用跑通基座，再批量改造其余。

5.9 复盘与可复用经验

  • 子应用三件套：生命周期导出 + 运行时 publicPath + 卸载清理，缺一不可。
  • 全局命名要管控：微前端下 window 是共享战场，必须沙箱 + 黑名单。
  • 资源在 unmount 全释放：连接/定时器/监听随子应用卸载而销毁。

5.10 面试讲法

实战要点用 Qiankun 把 5+ 独立部署子应用接入统一基座，踩平了 publicPath 写死、全局污染与 WebRTC 连接在 unmount 未 dispose 这几个微前端经典坑。

6易错点与面试重点

6.1 样式隔离失效/全局污染

一句话定位：不隔离就互相污染——优先 scoped，必要时 ShadowDOM。

  • 正解：优先 scoped CSS，必要时开 strictStyleIsolation（ShadowDOM）。

坑慎用全局 reset，它会无差别覆盖所有子应用。

6.2 子应用 publicPath 写死

一句话定位：资源路径写死，部署到子路径后就 404。

  • 现象：部署到子路径后资源 404。
  • 正解：用 __INJECTED_PUBLIC_PATH_BY_QIANKUN__ 运行时指定。

6.3 卸载不彻底导致内存泄漏

一句话定位：切走子应用时没清理定时器/事件/实例，泄漏累积。

  • 正解：unmount 里清定时器、解绑事件、dispose 图表/连接实例。

真坑WebRTC 子应用切走时 PeerConnection 没 dispose，切回后多路连接泄漏。

6.4 公共依赖多实例

一句话定位：基座和子应用各打一份 Vue，就出现两份实例、状态不通。

  • 现象：两份 Vue 实例、状态不通。
  • 正解：Vue/React 等核心库 externals 由基座提供。

6.5 跨域与资源加载

一句话定位：基座要 fetch 子应用入口，子应用必须放行跨域。

  • 正解：子应用 dev/部署都要允许基座跨域 fetch 入口 HTML 与资源。

要点子应用 dev server 配允许跨域响应头，否则基座 fetch 入口被 CORS 拦。
