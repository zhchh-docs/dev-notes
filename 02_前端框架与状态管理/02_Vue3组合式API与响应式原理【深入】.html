Vue3 组合式 API 与响应式原理

深入 定位：Vue3 的两大升级——组合式逻辑复用 + Proxy 响应式源码级机制

Vue3 带来两件大事：用 Proxy 重写响应式（替代 Vue2 的 Object.defineProperty），以及组合式 API（Composition API）让逻辑按关注点聚合、可抽成 composable 复用。本页从源码级讲透 track/trigger 依赖收集、ref/reactive/computed 的关系、为什么组件更新是异步的，再落到 业务系统 表单设计器/渲染器的 composable 实战。这是 Vue 面试的深水区。

1技术点概览

是什么

Vue3 是 Vue 的第三代重写版本，两大核心升级：组合式 API——不再用 data/methods/computed 分块组织，而是在 setup() 里按"逻辑关注点"自由组织代码，并把可复用逻辑抽成函数（composables）；Proxy 响应式——用 new Proxy(target, handler) 劫持整个对象，替代 Vue2 逐属性 Object.defineProperty。同时 Vue3 原生支持 TypeScript、虚拟 DOM 重写更小更快、支持 Fragments 与多根节点。

解决什么问题

选项式 API 的痛点是"同一逻辑被拆散在 data/methods/watch 各处"——组件一大，要盯着一个功能就得上下滚动找齐。组合式让"一个功能的所有相关代码写在一起"。响应式上，Vue2 的 defineProperty 检测不到新增/删除属性、数组下标赋值，Proxy 从根上解决：深层对象惰性代理、新增删除自动追踪。

图 1 Proxy 响应式的拦截入口（示意）

横向对比：Vue2 选项式 vs Vue3 组合式

图 2 Vue2 选项式 vs Vue3 组合式（示意）

  • 逻辑组织：选项式按"选项类型"分块（data 一块、methods 一块），同一功能被拆散；组合式按"功能"聚合，一个功能的 ref/computed/函数写在一起。组件越大，组合式越好维护。
  • 复用方式：选项式靠 mixins（命名冲突、来源不清）；组合式靠 composable 函数（显式导入、类型清晰）。这是 业务系统 把表单逻辑抽成公共 composable 的原因。
  • 响应式底层：defineProperty 逐属性劫持、检测不到增删；Proxy 整对象代理、增删自动追踪。理解这个差异，才知道 Vue2 的 Vue.set 在 Vue3 为什么消失了。

2核心概念

2.1 组合式 API 与 setup（Composition API）

一句话定位：状态/计算/方法都在 <script setup> 一个作用域里，同一逻辑关注点的代码写在一起。

  • 组织方式：不再分 data/methods/computed 块，模板直接用声明的变量。
  • 优势：普通变量/函数取代选项式的 this.xxx，类型推导更友好、更利于 Tree-shaking、可抽成函数复用。

2.2 ref 与 reactive

一句话定位：ref 包装任意值（模板自动解包、JS 要 .value）；reactive 把对象转成 Proxy。

  • ref(x)：带 .value 的响应式引用；reactive(obj)：对象转 Proxy 代理。
  • 经验法则：基础类型用 ref，对象两者皆可但 ref 更统一。

图 3 ref vs reactive（示意）

坑reactive 解构会失去响应性（解构出普通值），ref 解构后仍保持引用——统一用 ref 返回最稳。

2.3 computed 与 watch / watchEffect

一句话定位：computed 做带缓存的派生值，watch/watchEffect 做副作用。

  • computed：内部建 effect，依赖变才重算、带缓存。
  • watch(source, cb)：观察变化执行回调，默认惰性（首次不跑）、能拿到 oldValue/newValue、可监听多个源、可配 deep/immediate。
  • watchEffect(fn)：自动收集 fn 里用到的响应式依赖、变了重跑；组件挂载时立即执行一次、回调里拿不到 oldValue。

2.4 Proxy 与 Reflect

一句话定位：Proxy 拦截操作，Reflect 提供默认行为，两者配合在"默认行为前后插一脚"。

  • Proxy：包装目标对象，拦截 get/set/has/deleteProperty 等。
  • Reflect：与拦截器同名的默认操作（如 Reflect.get(target,key)）。

组合get 时先 track、再 Reflect.get 返回真值；set 时先 Reflect.set 写值、再 trigger。

2.5 依赖收集 track（Dependency Tracking）

一句话定位：三层映射精确记录"哪个 effect 依赖了哪个对象的哪个属性"。

  • 三层结构：targetMap（WeakMap，键=原始对象）→ depsMap（Map，键=属性名）→ dep（Set，装所有依赖该属性的 effect）。
  • 时机：读属性时若当前正有 effect 在跑，就把它加进对应 dep。

2.6 触发更新 trigger

一句话定位：写属性时取出该属性的 dep，把里面所有 effect 重新执行。

  • 重跑：effect 重跑时重新读依赖，自动建立新关系；旧依赖不再被用就自然解除。

闭环这套"读时收集、写时触发"就是 Vue3 响应式的核心。

2.7 effect 副作用函数与调度

一句话定位：渲染 effect 不是立即执行，而是进更新队列、下一微任务统一 flush——这就是组件更新异步的根因。

  • 批量更新：同一同步代码块内多次修改状态，渲染 effect 在一个微任务 tick 内只执行一次。
  • nextTick：想在更新后操作 DOM，必须 await nextTick()。

2.8 组合式函数 composables

一句话定位：把一组响应式状态与逻辑封装成函数返回，多组件 import 复用——Vue3 逻辑复用的标准答案。

  • 优势：比 mixin 清晰（来源明确、无命名冲突）、比 renderless 组件直接。
  • 实践：业务系统 的表单逻辑、请求 loading 状态都是 composable。

3工作原理与流程

3.1 依赖收集的三层映射结构

图 2 依赖收集的三层映射结构（示意）

  1. 读属性：Proxy.get 拦截，查 targetMap 找到该对象→属性对应的 dep Set。
  2. 登记：把当前正在执行的 effect 加进 dep。
  3. 写属性：Proxy.set 拦截，查 dep，把其中所有 effect 重新调度。
  4. 重跑：effect 重跑时重新读依赖，自动更新 dep。

3.2 为什么更新是异步的

修改状态后，渲染 effect 不是立即执行，而是被放进一个队列（jobQueue），用 Promise.then（微任务）flush。同一次同步代码里改 count 三次，渲染 effect 只会执行一次——这就是批量更新。想在更新后操作 DOM，必须 await nextTick()。

4核心语法与 API 要点

4.1 script setup 基本写法

<script setup>
import { ref, computed, watch } from 'vue';

const count = ref(0);                       // 基础类型用 ref
const double = computed(() => count.value * 2);

watch(count, (nv, ov) => console.log(ov, '→', nv));

function inc() { count.value++; }           // JS 里用 .value
</script>

<template>
  <button @click="inc">{{ count }} ×2 = {{ double }}</button>  <!-- 模板自动解包 -->
</template>

4.2 composable：把逻辑抽出来复用

// useRequest.ts：封装"加载-数据-错误"状态
export function useRequest(fetcher) {
  const data = ref(null);
  const loading = ref(false);
  async function run() {
    loading.value = true;
    try { data.value = await fetcher(); }
    finally { loading.value = false; }
  }
  return { data, loading, run };   // 返回响应式引用，调用方保持响应性
}

4.3 手写一个最小 reactive

let activeEffect = null;
const targetMap = new WeakMap();

function track(target, key) {
  if (!activeEffect) return;
  let depsMap = targetMap.get(target);
  if (!depsMap) targetMap.set(target, (depsMap = new Map()));
  let dep = depsMap.get(key);
  if (!dep) depsMap.set(key, (dep = new Set()));
  dep.add(activeEffect);                 // 登记依赖
}
function trigger(target, key) {
  const depsMap = targetMap.get(target);
  const dep = depsMap?.get(key);
  dep?.forEach(e => e());                // 重跑所有依赖该属性的 effect
}
function reactive(target) {
  return new Proxy(target, {
    get(t, k) { track(t, k); return Reflect.get(t, k); },
    set(t, k, v) { const r = Reflect.set(t, k, v); trigger(t, k); return r; }
  });
}

5实战项目经验（实战落地）

5.1 项目背景

一句话定位：业务系统（Vue3+TS+Pinia）的表单设计器/渲染器要共享同一套字段元数据逻辑，Pinia store 也建立在 ref/reactive 之上。

  • 业务场景：设计态拖拽改字段、渲染态按 schema 生成表单，两端逻辑必须同源。

5.2 我的角色与职责

  • 角色：前端开发，负责抽 composable 复用设计/渲染两端逻辑与 Pinia store 拆分。
  • 团队与分工：前端若干（估算）；我负责表单设计器这一块。

5.3 技术栈

  • Vue3 组合式 API（script setup）+ TypeScript + Pinia（setup 风格）+ ElementPlus。

5.4 落地设计

  • 抽 composable：字段增删改、选中字段、校验状态抽成 useFormSchema()，设计器与渲染器共用。
  • 泛型约束：schema 用 TS 泛型，与公共包 FieldMeta 一致。
  • store 即响应式：Pinia setup 风格里就是 ref + computed。

5.5 关键实现要点

// useFormSchema.ts
export function useFormSchema(initial: FieldMeta[] = []) {
  const fields = ref<FieldMeta[]>(initial);
  const selected = ref<FieldMeta | null>(null);
  function addField(f: FieldMeta) { fields.value.push(f); }
  function removeField(key: string) {
    fields.value = fields.value.filter(f => f.key !== key);
  }
  return { fields, selected, addField, removeField };
}
// 设计器与渲染器各自 import，逻辑单一来源、不漂移
// stores/user.ts（setup 风格）
export const useUserStore = defineStore('user', () => {
  const token = ref('');
  const profile = ref<Profile | null>(null);
  const isLogin = computed(() => !!token.value);
  function setToken(t: string) { token.value = t; }
  return { token, profile, isLogin, setToken };
});

5.6 真实问题与解法

  • 解构后仍是 ref：const { fields } = useFormSchema() 后 fields 还是 ref，要 .value；曾误当普通数组 push 报错。
  • reactive 解构丢响应：reactive schema 解构丢响应性，统一用 ref 返回。
  • 深层 watch 漏 deep：校验在 watch 里做，深层嵌套没加 { deep: true } 不触发，补上后正常。
  • 直接解构 store 丢响应：const { token } = useUserStore() token 变了视图不更新；用 storeToRefs 保持引用。

5.7 量化成果

  • 设计态与渲染态逻辑从两份拷贝合并为一个 composable，改一处两端同步。

5.8 协作与排期过程

  • 契约先行：与后端/产品定 FieldMeta 结构，composable 才好泛型约束。
  • 排期：先做渲染器跑通 schema，再抽 composable 给设计器复用。

5.9 复盘与可复用经验

  • 逻辑同源靠 composable：多入口共享逻辑就抽成函数返回响应式状态。
  • ref 返回优于 reactive 解构：避免响应性丢失。
  • 解构 store 必用 storeToRefs：这是 Pinia 最常见的"视图不更新"坑。

5.10 面试讲法

实战要点用一个 useFormSchema composable 把设计器与渲染器逻辑合并为单一来源，并踩平了解构 ref/reactive/store 丢响应这一连串问题。

6易错点与面试重点

6.1 reactive 解构丢响应性

一句话定位：解构出的是普通值，脱离了 Proxy，所以视图不更新。

  • 现象：const { name } = reactive(obj) 后改 name 视图不更新。
  • 正解：用 ref、或 storeToRefs / toRefs 保持引用。

6.2 ref 在 JS 里忘写 .value

一句话定位：模板自动解包，但 JS 逻辑里必须 .value。

  • 现象：比较 count === 0 永远 false。
  • 正解：ESLint 规则兜底，逻辑里一律 count.value。

6.3 computed 里写副作用

一句话定位：computed 是纯派生、有缓存，副作用应该放 watch。

  • 现象：computed 里发请求/改 DOM。
  • 原因：computed 可能被延迟求值，写副作用不可控。
  • 正解：副作用用 watch/watchEffect。

6.4 改状态后立刻读 DOM

一句话定位：Vue 更新是异步批量的，改完立刻读还是旧值。

  • 现象：改完 ref 立刻读 DOM 还是旧值。
  • 正解：await nextTick()。

6.5 watch 深层对象漏 deep

一句话定位：改嵌套属性要 deep:true，否则不触发。

  • 现象：改嵌套属性 watch 不触发。
  • 正解：深层观察用 watch(obj, cb, { deep: true })，或直接 watch 一个 getter。

6.6 Proxy 不能监听新增删除？

一句话定位：误解——Proxy 能拦截 delete/add，新增/删除天然响应。

  • 误区：以为 Vue3 也有 Vue2 的限制。
  • 口径：Proxy 能拦截 delete/add，新增/删除对象属性天然响应，不需要 Vue.set。
